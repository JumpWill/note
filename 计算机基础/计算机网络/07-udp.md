# UDP 协议 (User Datagram Protocol)

## 一、UDP 概述

### 什么是 UDP

**UDP (User Datagram Protocol，用户数据报协议)**：一种**无连接、面向数据报、尽力而为**的传输层协议。

```text
应用层: DNS、DHCP、NTP、实时音视频、QUIC
                  ↓
传输层: UDP —— 端口复用、数据报、校验和
                  ↓
网络层: IP —— 寻址和路由
                  ↓
链路层: Ethernet / Wi-Fi
```

### UDP 的核心特点

- **无连接**：发送前不建立连接
- **面向数据报**：保留每次发送的消息边界
- **不保证到达**：数据报可能丢失
- **不保证顺序**：数据报可能乱序
- **不自动重传**：可靠性由应用层按需实现
- **不自动流量控制**：发送方需要自行控制速率
- **不内置拥塞控制**：应用协议应避免压垮网络
- **首部很小**：固定 8 字节
- **支持单播、广播和组播**

### UDP 能做什么

UDP 提供的基本能力：

```text
IP 寻址
+ 端口复用
+ 数据报长度
+ 校验和
= 进程之间的轻量数据报传输
```

### 常见 UDP 应用

| 协议/应用 | 默认端口 | 说明 |
| --------- | -------- | ---- |
| DNS | 53 | 普通域名查询 |
| DHCP | 67/68 | 自动分配网络参数 |
| NTP | 123 | 时间同步 |
| SNMP | 161/162 | 网络管理 |
| TFTP | 69 | 简单文件传输 |
| Syslog | 514 | 日志传输 |
| RTP | 动态 | 实时音视频 |
| QUIC / HTTP/3 | 443 | 在 UDP 上实现可靠安全传输 |
| WireGuard | 51820 | VPN 隧道 |

## 二、UDP 报文格式

### 1. UDP 首部

```text
0                   15                  31
+-------------------+-------------------+
| Source Port       | Destination Port  |
+-------------------+-------------------+
| Length            | Checksum          |
+-------------------+-------------------+
| Application Data                      |
+---------------------------------------+
```

UDP 首部固定为 **8 字节**。

### 2. 字段说明

| 字段 | 长度 | 作用 |
| ---- | ---- | ---- |
| **Source Port** | 16 bit | 源端口，可在特定情况下为 0 |
| **Destination Port** | 16 bit | 目的端口 |
| **Length** | 16 bit | UDP 首部与数据的总长度 |
| **Checksum** | 16 bit | 检查伪首部、UDP 首部和数据 |

### 3. Length 字段

```text
UDP Length = 8 字节首部 + 应用数据长度
```

最小合法值为 8，表示没有应用数据。

经典 UDP Length 为 16 bit，因此理论总长度最大为 65535 字节；实际还受 IP 头部、路径 MTU、操作系统和协议实现限制。

### 4. UDP 校验和

UDP 校验和覆盖：

```text
IP 伪首部 + UDP 首部 + UDP 数据 + 必要的填充字节
```

伪首部包含源 IP、目的 IP、协议号和长度，用于发现数据损坏及部分错误投递。

| IP 版本 | UDP 校验和要求 |
| ------- | -------------- |
| IPv4 | 传统 UDP 中可选，值为 0 表示未计算 |
| IPv6 | 一般必须使用，少数标准化隧道场景存在例外 |

抓取本机发出的数据包时，若校验和显示错误，可能是网卡 **Checksum Offload** 尚未完成计算。

### 5. UDP 与 TCP 首部对比

| 项目 | UDP | TCP |
| ---- | --- | --- |
| 最小首部 | 8 字节 | 20 字节 |
| 序列号 | 无 | 有 |
| 确认号 | 无 | 有 |
| 窗口 | 无 | 有 |
| 控制标志 | 无 | SYN、ACK、FIN 等 |
| 选项 | 经典 UDP 无 | MSS、SACK、时间戳等 |

## 三、UDP 数据报与消息边界

### 1. UDP 保留消息边界

发送方：

```text
sendto("hello")
sendto("world")
```

接收方会看到两个独立数据报：

```text
数据报 1:"hello"
数据报 2:"world"
```

UDP 不会像 TCP 一样自动合并为连续字节流。

### 2. 接收缓冲区过小

如果应用提供的接收缓冲区小于数据报：

```text
数据报大小:2000 字节
recvfrom 缓冲区:1024 字节
```

超出的部分通常被截断并丢弃，下一次读取不会继续获得同一个数据报的剩余内容。具体通知方式由操作系统和 API 决定。

### 3. 零长度数据报

UDP 可以发送零长度应用数据：

```text
UDP Length = 8
```

因此，返回 0 字节不一定表示连接关闭；UDP 没有 TCP 的连接关闭语义。

### 4. 一次发送不等于一次网络包

应用一次 `sendto()` 形成一个 UDP 数据报，但网络层可能：

- 对 IPv4 数据包分片
- 通过 GSO 在更后阶段分段
- 因超过 MTU 且禁止分片而发送失败

接收应用只有在完整数据报成功重组后才能读取它。

## 四、UDP 通信过程

### 1. 无连接发送

```text
客户端                                      服务器
  │                                            │
  │ UDP Datagram                              │
  ├───────────────────────────────────────────→│
  │                                            │
  │ UDP Datagram                              │
  │←───────────────────────────────────────────┤
```

发送前没有三次握手，发送后也没有 UDP 层确认。

### 2. 请求响应示例

```text
客户端 192.168.1.10:53000
        │
        │ 查询 example.com
        ▼
DNS 服务器 1.1.1.1:53
        │
        │ 返回 DNS 响应
        ▼
客户端 192.168.1.10:53000
```

DNS 使用自己的事务 ID 匹配请求和响应，并在需要时由应用重试。

### 3. 单向发送

UDP 不要求对方回复：

```text
监控代理 ──UDP 日志──→ 日志服务器
传感器   ──UDP 数据──→ 采集服务器
```

适用于允许少量丢失、优先降低开销的场景。

### 4. 无连接不等于无状态

UDP 协议本身不维护连接状态，但应用可以维护：

- 会话 ID
- 请求 ID
- 对端地址
- 重传计时器
- 加密密钥
- 拥塞状态

QUIC 就是在 UDP 之上实现连接、可靠性、拥塞控制和 TLS 安全。

## 五、UDP Socket

### 1. UDP 服务器流程

```text
socket()
   ↓
bind()
   ↓
recvfrom()
   ↓
sendto()
   ↓
close()
```

UDP 不需要 `listen()` 和 `accept()`。

### 2. UDP 客户端流程

```text
socket()
   ↓
sendto()
   ↓
recvfrom()
   ↓
close()
```

客户端未显式 `bind()` 时，操作系统会自动选择本地 IP 和临时端口。

### 3. Connected UDP

UDP socket 也可以调用 `connect()`：

```text
socket()
   ↓
connect(服务器地址)
   ↓
send()/recv()
```

这**不会建立网络连接或握手**，主要作用是：

- 固定默认对端
- 可以使用 `send()` / `recv()`
- 内核过滤其他来源的数据报
- 某些系统可以更直接地向应用报告异步 ICMP 错误
- 减少每次发送时传入地址的开销

### 4. 端口复用

服务器通过目的端口接收数据。每个数据报还带有源 IP 和源端口，服务器可据此回复不同客户端。

常见 socket 选项：

| 选项 | 作用 |
| ---- | ---- |
| `SO_REUSEADDR` | 允许特定条件下复用本地地址 |
| `SO_REUSEPORT` | 多个 socket 绑定同一地址端口并分担流量 |
| `SO_BROADCAST` | 允许发送 IPv4 广播 |
| `SO_RCVBUF` | 接收缓冲区大小 |
| `SO_SNDBUF` | 发送缓冲区大小 |
| `IP_PKTINFO` | 获取目的地址和接收接口等信息 |
| `IP_MULTICAST_TTL` | IPv4 组播 TTL |

具体语义和可用性依操作系统而异。

## 六、UDP 不可靠性的表现

### 1. 数据报丢失

可能原因：

- 网络拥塞
- 路由或链路故障
- 交换机、路由器队列溢出
- 接收主机内核缓冲区溢出
- 应用读取速度太慢
- 防火墙或 ACL 丢弃
- IP 分片任意一片丢失

### 2. 数据报乱序

不同数据报可能经过不同路径：

```text
发送顺序:1 → 2 → 3
接收顺序:1 → 3 → 2
```

需要有序处理时，应用应增加序列号和重排缓冲区。

### 3. 数据报重复

网络和应用重试可能造成重复：

```text
客户端发送请求 100
响应丢失
客户端重试请求 100
服务器可能处理两次
```

应用应使用请求 ID 和幂等逻辑去重。

### 4. 数据损坏

校验和失败的数据报通常由内核直接丢弃，不交给应用。应用看到的结果通常是“数据报没有到达”，而不是收到损坏内容。

### 5. 没有内置发送反馈

`sendto()` 成功通常只说明：

```text
数据已被本机协议栈接受
```

不代表：

- 数据已到达目标主机
- 目标端口正在监听
- 对端应用已经处理
- 业务操作成功

## 七、在 UDP 上实现可靠性

### 1. 常见机制

应用协议可以按需实现：

- 消息序列号
- 请求/响应 ID
- ACK / NACK
- 超时和重传
- 指数退避
- 乱序重排
- 重复数据去重
- 流量控制
- 拥塞控制
- 前向纠错 FEC

### 2. 简单请求重试

```text
发送 Request ID=100
        ↓
等待响应
        ↓ 超时
重传 Request ID=100
        ↓
服务器识别重复 ID，返回同一结果
```

### 3. 重试必须考虑幂等

安全示例：

```text
查询订单状态
设置配置为指定值
```

有风险的示例：

```text
扣款
创建订单
追加一次计数
```

对非幂等操作，应使用唯一业务 ID 和服务端去重，而不是简单重复执行。

### 4. 不要只实现重传

没有拥塞控制的持续重传可能进一步加剧拥塞。可靠 UDP 协议至少应考虑：

```text
丢包 → 降低发送速率
超时 → 指数退避
恢复 → 谨慎增加速率
```

成熟协议如 QUIC 已实现这些机制，通用场景通常不应重新设计一套传输协议。

## 八、UDP 与 IP 分片

### 1. 为什么会分片

UDP 数据报加上 IP 首部后超过出口 MTU：

```text
UDP 数据 4000 字节
+ UDP 首部 8
+ IPv4 首部 20
> MTU 1500
```

IPv4 可能把它分成多个 IP 分片；IPv6 只能由发送主机使用 Fragment 扩展头分片，路由器不会分片。

### 2. 分片的代价

- 任意一个分片丢失，整个 UDP 数据报无法重组
- 分片增加路由器、主机和防火墙处理压力
- 部分 NAT、防火墙会丢弃分片
- 分片放大丢包概率
- 重组占用内存并存在超时

### 3. 推荐做法

- 应用控制单个数据报大小
- 进行 Path MTU Discovery
- 在应用层分块并独立编号
- 避免依赖中间路由器分片
- 通过协议重传缺失的数据块，而不是整个大对象

### 4. 常见安全载荷估算

普通以太网 MTU 1500：

```text
IPv4:1500 - 20(IP) - 8(UDP) = 1472 字节
IPv6:1500 - 40(IP) - 8(UDP) = 1452 字节
```

实际路径可能有隧道、VPN、额外扩展头或更小 MTU，因此应用常使用更保守的值。QUIC 通常要求路径至少支持 1200 字节 UDP 载荷。

### 5. PMTUD 错误

如果 ICMP Fragmentation Needed 或 ICMPv6 Packet Too Big 被错误拦截，发送方无法获知路径 MTU，可能出现：

```text
小数据报正常
大数据报持续丢失
```

## 九、UDP 广播

### 1. 有限广播

```text
255.255.255.255
```

只在本地网络使用，路由器通常不转发。

### 2. 定向广播

以 `192.168.1.0/24` 为例：

```text
192.168.1.255
```

现代路由器通常默认禁止跨网转发定向广播，以防止放大攻击。

### 3. 广播发送

发送方通常需要启用 `SO_BROADCAST`。

广播用途：

- DHCP Discover
- 局域网设备发现
- 旧式服务发现

### 4. 广播限制

- 仅适用于 IPv4
- 同一广播域中所有设备都要处理
- 不适合高频或大流量传输
- IPv6 没有广播，使用组播代替

## 十、UDP 组播

### 1. 什么是组播

组播把一个数据报发送给加入特定组的一组接收者：

```text
发送者 ──→ 组播地址 239.1.1.1
                ├──→ 接收者 A
                ├──→ 接收者 B
                └──→ 接收者 C
```

### 2. IPv4 组播范围

IPv4 组播地址范围：

```text
224.0.0.0/4
```

常见范围：

| 范围 | 说明 |
| ---- | ---- |
| 224.0.0.0/24 | 本地链路控制协议，路由器通常不转发 |
| 232.0.0.0/8 | Source-Specific Multicast |
| 239.0.0.0/8 | 管理域内组播，类似私有范围 |

### 3. 组成员管理

- IPv4 使用 IGMP
- IPv6 使用 MLD
- 应用加入组播组后，网卡和网络设备才会接收相关流量

### 4. 组播应用

- IPTV
- 行情分发
- 局域网服务发现
- 路由协议
- 一对多实时数据分发

### 5. 组播不保证可靠

UDP 组播仍不保证：

- 每个成员都收到
- 所有成员按同一顺序收到
- 新加入成员获得历史数据

需要可靠性时，应用必须设计补包、快照、序列号等机制。

## 十一、ICMP 错误与 UDP

### 1. 端口不可达

向目标主机未监听的 UDP 端口发送数据时，目标可能返回：

```text
ICMP Destination Unreachable: Port Unreachable
```

UDP 没有 RST 报文。

### 2. 为什么应用不一定立即看到错误

- 普通未连接 UDP socket 的异步错误处理依系统而异
- ICMP 可能被防火墙丢弃
- 目标可能静默丢弃数据
- `sendto()` 返回时错误可能尚未到达

Connected UDP 通常更容易把匹配的 ICMP 错误报告给应用。

### 3. traceroute 与 UDP

传统 Unix `traceroute` 可发送 TTL 逐步增加的 UDP 数据报：

```text
TTL=1 → 第一跳返回 ICMP Time Exceeded
TTL=2 → 第二跳返回 ICMP Time Exceeded
...
到达目标未监听端口 → ICMP Port Unreachable
```

不同系统也可能使用 ICMP 或 TCP 探测。

## 十二、UDP 缓冲区与丢包

### 1. 接收路径

```text
网卡
  ↓
内核网络协议栈
  ↓
UDP socket 接收缓冲区
  ↓
应用 recvfrom()
```

任何阶段处理不及时都可能丢包。

### 2. 接收缓冲区溢出

当应用读取速度低于数据到达速度：

```text
接收缓冲区写满
        ↓
新到数据报被丢弃
```

UDP 不会像 TCP 一样通过接收窗口让发送方自动暂停。

### 3. 查看系统统计

```bash
# Linux UDP 统计
nstat -az | grep -i udp
netstat -su

# Socket 摘要
ss -u -a -n -m
```

重点指标：

- `UdpInDatagrams`
- `UdpNoPorts`
- `UdpInErrors`
- `UdpRcvbufErrors`
- `UdpSndbufErrors`

### 4. 调整缓冲区

可以通过 `SO_RCVBUF`、`SO_SNDBUF` 和系统上限调整，但应先确认根因：

- 应用处理太慢
- 单线程瓶颈
- 突发流量过大
- 数据报过大
- CPU 或网卡队列不足

只增大缓冲区只能吸收更大的短时突发，不能解决长期处理能力不足。

### 5. 批量收发

Linux 高吞吐 UDP 应用可使用：

- `recvmmsg()`：一次接收多个数据报
- `sendmmsg()`：一次发送多个数据报
- `SO_REUSEPORT`：多 socket 分流
- UDP GSO/GRO：减少每数据报处理开销

是否需要这些优化应由性能测量决定。

## 十三、常见 UDP 协议

### 1. DNS

```text
客户端临时端口 → 服务器 UDP 53
```

- 普通查询优先使用 UDP
- 响应截断时可回退 TCP
- 协议使用事务 ID 匹配响应
- EDNS(0) 扩展可用 UDP 载荷大小

### 2. DHCP

```text
客户端 UDP 68
服务器 UDP 67
```

客户端最初没有可用 IP，因此通过 IPv4 广播发现 DHCP 服务器。

### 3. NTP

```text
客户端临时端口 → 服务器 UDP 123
```

通过多个时间戳估算时钟偏移和网络延迟。

### 4. RTP / 实时音视频

- 关注低延迟，过期数据通常没有重传价值
- 使用序列号发现丢包和乱序
- 使用时间戳进行播放同步
- 可配合 RTCP 反馈质量
- 可使用抖动缓冲和 FEC

### 5. QUIC

QUIC 在 UDP 上实现：

- 可靠传输
- 拥塞控制
- TLS 1.3
- 多路复用
- 连接迁移
- 低延迟握手

HTTP/3 使用 QUIC。QUIC 选择 UDP 是为了在用户态快速演进传输功能，不代表它是不可靠协议。

### 6. WireGuard

WireGuard 使用 UDP 承载加密隧道：

- 没有 TCP-over-TCP 问题
- 协议简单
- 支持漫游和端点变化
- 保活与重传由协议按需处理

## 十四、UDP 性能与设计

### 1. UDP 不一定总比 TCP 快

UDP 只提供更少的内置机制。应用如果需要可靠性，仍要实现：

- ACK
- 重传
- 拥塞控制
- 排序
- 连接管理

实现不当可能比成熟 TCP 更慢、更不稳定。

### 2. UDP 适合的场景

- 数据过期后不值得重传
- 应用需要自定义可靠性
- 一对多广播或组播
- 单次简单请求响应
- 需要用户态传输协议，如 QUIC
- 可以容忍少量丢包的实时数据

### 3. UDP 不适合直接使用的场景

- 必须完整传输的大文件
- 不能丢失的业务命令
- 开发方不准备实现可靠性和拥塞控制
- 需要天然有序字节流

这些场景通常优先使用 TCP、QUIC 或成熟应用协议。

### 4. 设计 UDP 应用协议

至少应明确：

```text
消息版本
消息类型
消息长度
请求/会话 ID
序列号
认证信息
超时与重试
最大数据报大小
拥塞与限速策略
重复请求处理
```

### 5. 超时与重试

推荐原则：

- 根据 RTT 设置合理超时
- 使用指数退避
- 限制最大重试次数
- 加入随机抖动
- 对非幂等请求使用唯一 ID
- 失败时提供清晰的业务结果

## 十五、UDP 安全

### 1. 源地址伪造

UDP 无连接，攻击者更容易构造伪造源 IP 的数据报。接收方不能仅因报文来自某个 IP 就认为身份可信。

防护：

- 消息认证码或数字签名
- DTLS、QUIC、IPsec、WireGuard
- 网络入口/出口源地址过滤
- 不依赖源 IP 完成高权限认证

### 2. 反射与放大

如果一个小请求可以触发发往伪造源地址的大响应，公开 UDP 服务可能被滥用于反射放大攻击。

常见防护：

- 不向公网开放无必要的服务
- 禁止开放递归 DNS
- 响应前验证客户端可达性
- 对未验证客户端限制响应大小
- 实施速率限制
- 网络运营方部署 BCP 38 源地址验证

### 3. 数据篡改与窃听

UDP 本身不加密、不认证。应按场景使用：

| 技术 | 场景 |
| ---- | ---- |
| DTLS | 类似 TLS 的数据报安全 |
| QUIC | 安全可靠的连接和流传输 |
| IPsec | 网络层保护 |
| WireGuard | VPN 隧道 |
| 应用签名/MAC | 自定义消息认证 |

### 4. 重放攻击

即使消息已认证，攻击者仍可能重复发送捕获的数据报。应用应使用：

- 单调序列号
- Nonce
- 时间窗口
- 请求 ID 去重
- 会话密钥和重放窗口

### 5. 资源耗尽

无连接服务如果在收到第一包时就分配大量状态，容易被伪造数据报消耗资源。

防护：

- 验证 Cookie / Token 后再分配昂贵状态
- 限制每来源和全局速率
- 设置状态过期时间
- 限制报文大小和解析复杂度
- 在解析前进行长度和格式校验

## 十六、抓包分析

### 1. tcpdump

```bash
# 抓取全部 UDP
sudo tcpdump -i any -n udp

# 抓取指定端口
sudo tcpdump -i any -n 'udp port 53'

# 抓取指定主机
sudo tcpdump -i any -n 'udp and host 192.0.2.10'

# 保存抓包
sudo tcpdump -i any -n udp -w udp.pcap
```

### 2. Wireshark 过滤器

```text
udp
udp.port == 53
udp.srcport == 123
udp.dstport == 51820
udp.length > 1200
icmp.type == 3
icmpv6.type == 1
```

### 3. 抓包重点

- 源、目的 IP
- 源、目的端口
- UDP Length
- 校验和状态
- IP 是否分片
- 请求与响应时间
- 是否出现 ICMP 错误
- 应用层请求 ID 或序列号

### 4. 校验和误报

```text
[bad udp cksum]
```

如果抓包位于发送主机，可能只是校验和卸载。应在接收端或链路镜像点复核，而不是立即判断网络包损坏。

### 5. 分片过滤

Wireshark：

```text
ip.flags.mf == 1
ip.frag_offset > 0
ipv6.nxt == 44
```

分片丢失时，可能只能看到部分 IP 分片，应用层不会收到完整 UDP 数据报。

## 十七、常用排查命令

### 1. 查看 UDP socket

```bash
ss -uan
ss -ulnp
ss -u -a -n -m
```

### 2. 查看监听进程

```bash
ss -ulnp
lsof -nP -iUDP
```

### 3. 发送测试数据

服务端：

```bash
nc -u -l 9999
```

客户端：

```bash
printf 'hello\n' | nc -u 服务器IP 9999
```

UDP 测试没有握手成功提示，应结合服务端输出和抓包判断数据是否到达。

### 4. 测试吞吐和丢包

```bash
# 服务端
iperf3 -s

# 客户端 UDP 测试
iperf3 -c 服务器IP -u -b 10M
```

UDP 测试应逐步提高发送速率，观察：

- 丢包率
- 抖动
- 接收吞吐
- CPU 和网卡负载

### 5. 查看防火墙

```bash
nft list ruleset
iptables -L -n -v
```

云环境还需检查安全组、网络 ACL、负载均衡器和 Kubernetes NetworkPolicy。

## 十八、UDP 故障排查

### 1. 排查流程

```text
1. 检查目标 IP 和路由
2. 检查服务是否绑定正确 IP/端口
3. 检查本机和中间防火墙
4. 在发送端确认数据报已发出
5. 在接收端抓包确认是否到达
6. 检查 ICMP Port Unreachable
7. 检查 IP 分片、MTU 和报文大小
8. 检查 socket 缓冲区和系统丢包计数
9. 检查应用协议 ID、超时、重试和认证
```

### 2. 服务端收不到数据

可能原因：

- 服务未启动或绑定错误地址
- 目的端口错误
- 路由错误
- 防火墙丢弃 UDP
- NAT 映射不存在或过期
- 接收缓冲区溢出
- 校验和错误
- 分片丢失

### 3. 客户端收不到响应

应分别确认：

```text
请求是否到达服务器
服务器是否生成响应
响应是否使用正确目的 IP/端口
响应是否有回程路由
客户端防火墙是否放行
应用是否仍在同一端口等待
```

### 4. 小包正常，大包失败

优先检查：

- Path MTU
- IP 分片
- DF 设置
- ICMP 是否被拦截
- VPN/隧道额外开销
- 应用数据报大小上限

### 5. 高并发时丢包

检查：

- `UdpRcvbufErrors`
- socket 接收缓冲区
- 应用读取速度
- CPU 软中断负载
- 网卡队列和丢包计数
- 单 socket 锁竞争
- 突发流量是否超过处理能力

### 6. NAT 后连接一段时间失效

UDP 没有连接关闭，NAT 设备会按空闲超时删除映射。可按业务需要：

- 发送低频保活
- 缩短应用故障检测时间
- 收到网络变化后重新建立会话
- 不假设公网映射端口永久不变

### 7. 常见问题对照

| 现象 | 常见原因 | 排查重点 |
| ---- | -------- | -------- |
| 完全无响应 | 路由、防火墙、端口错误 | 双端抓包、监听状态 |
| 偶发丢包 | 拥塞、缓冲区溢出 | UDP 统计、接口计数 |
| 乱序 | 多路径、队列变化 | 应用序列号、抓包 |
| 重复处理 | 应用重试、响应丢失 | 请求 ID、幂等性 |
| 大包失败 | MTU、分片、防火墙 | 数据报大小、ICMP |
| 校验和错误 | 链路损坏或卸载显示 | 接收端复核、offload |
| 运行一段时间后断流 | NAT 超时、状态过期 | 保活、NAT 映射 |
| 组播收不到 | 未加组、TTL、交换机配置 | IGMP/MLD、接口、VLAN |

## 十九、UDP 与 TCP、QUIC 对比

| 维度 | UDP | TCP | QUIC |
| ---- | --- | --- | ---- |
| 基础形态 | 数据报 | 字节流 | 基于 UDP 的连接与流 |
| 建连 | 无 | 三次握手 | 集成 TLS 的握手 |
| 可靠性 | 无内置保证 | 可靠有序 | 每个流可靠有序 |
| 消息边界 | 保留 | 不保留 | 提供流，也可提供数据报 |
| 拥塞控制 | 应用负责 | 内置 | 内置 |
| 加密 | 无 | 无，常配 TLS | TLS 1.3 内置 |
| 多路复用 | 应用实现 | 单字节流 | 多个独立流 |
| 队头阻塞 | 应用决定 | 一个丢包阻塞连接字节流 | 丢包通常只阻塞相关流 |
| 连接迁移 | 无连接语义 | 四元组变化通常断开 | 支持 Connection ID 迁移 |
| 广播/组播 | 支持 | 不支持 | 不用于广播/组播 |

选择建议：

- 需要简单数据报、广播或组播：UDP
- 需要成熟可靠字节流：TCP
- 需要安全、多路复用、低握手延迟：优先评估 QUIC

## 二十、核心要点速记

- **UDP = 无连接、面向数据报、尽力而为的传输层协议**
- **UDP 首部固定 8 字节**
- **四个字段：源端口、目的端口、长度、校验和**
- **UDP 保留消息边界，TCP 不保留**
- **UDP 不保证到达、顺序、唯一性和可靠性**
- **`sendto()` 成功不代表对端已经收到或处理**
- **UDP 没有三次握手、四次挥手和 RST**
- **未监听端口可能返回 ICMP Port Unreachable**
- **UDP socket 调用 `connect()` 不会产生网络握手**
- **Connected UDP 固定默认对端并可改善错误报告**
- **IPv4 UDP 校验和传统上可选，IPv6 中一般必须使用**
- **单个数据报过大可能触发 IP 分片**
- **任意分片丢失都会导致整个 UDP 数据报丢失**
- **普通 MTU 1500 时，IPv4 UDP 载荷上限常按 1472 字节估算**
- **实际应用应考虑隧道和路径 MTU，使用更保守的数据报大小**
- **UDP 支持 IPv4 广播和 IP 组播**
- **IPv6 没有广播，使用组播**
- **应用需要可靠性时必须实现 ID、ACK、重传、去重和拥塞控制**
- **重试非幂等操作时必须使用业务 ID 防止重复执行**
- **接收缓冲区满时新数据报会直接丢弃，不会自动反压发送方**
- **`UdpRcvbufErrors` 可帮助定位接收缓冲区溢出**
- **QUIC 在 UDP 上实现可靠传输、拥塞控制和 TLS 1.3**
- **UDP 本身不加密、不认证，应使用 DTLS、QUIC、IPsec 等保护**
- **公开 UDP 服务应防止源地址伪造、反射和放大**
- **UDP 排障应在发送端和接收端同时抓包**
- **`ss -ulnp` 查看 UDP 监听端口**
- **小包正常、大包失败时优先检查 MTU 和 IP 分片**
