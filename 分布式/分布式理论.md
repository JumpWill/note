## 一、CAP 定理

### 1.1 起源

**CAP 定理** 由 **Eric Brewer** 在 2000 年 PODC 大会上提出 (猜想),2002 年由 **Seth Gilbert 和 Nancy Lynch** 给出数学证明。

**全称**: **C**onsistency, **A**vailability, **P**artition Tolerance

### 1.2 三要素详解

| 维度 | 全称 | 含义 | 度量 |
|------|------|------|------|
| **C** | Consistency (一致性) | 所有节点在同一时刻看到的数据完全相同 | 读总是返回最近的写 |
| **A** | Availability (可用性) | 每个请求都能收到响应 (非错误) | 99.9% / 99.99% SLA |
| **P** | Partition Tolerance (分区容错) | 网络分区时系统仍能继续运行 | 分区下能服务 |

#### C 一致性 (强一致性)

```text
一致性 = 所有节点在同一时刻看到的数据完全一致

例:
   T0: 客户端 A 向节点 1 写入 X=1
   T1: 客户端 B 从任意节点读取 X
   T2: B 必须读到 X=1

要求: 写入后,所有后续读必须返回最新值
```

#### A 可用性

```text
可用性 = 每个非故障请求必须收到响应 (不返回错误)

要求:
   - 每个请求必须在合理时间内收到响应 (无超时)
   - 响应可以是非最新的数据

例:
   客户端请求 → 任意节点 → 必定返回 (不报错),即使数据是旧的
```

#### P 分区容错性

```text
分区 = 节点之间网络断开,但节点本身仍能运转

例:
   Node A ←→ Node B ←→ Node C  (正常)
   Node A  ╳  Node B ←→ Node C  (网络分区)

分区容错 = 网络断开时系统仍能对外提供服务
```

### 1.3 定理核心

**Brewer 猜想**: 在网络分区 (P) 发生时,系统**只能**在一致性 (C) 和可用性 (A) 中二选一,**无法同时满足三项**。

```text
                     ┌──────────────┐
                     │   C ∩ A ∩ P   │  ← 不可能存在
                     └──────────────┘

        在 P 发生时,只能选:
        ├─ CP 系统: 放弃 A (拒绝写入/读取)
        └─ AP 系统: 放弃 C (允许读到旧数据)
```

### 1.4 CAP 三大组合

| 组合 | 含义 | 实际场景 |
|------|------|----------|
| **CA** (舍弃 P) | 不允许网络分区 | 单库/单机系统、传统关系数据库 (单机部署) |
| **CP** (舍弃 A) | 分区时停止服务,保证数据一致 | ZooKeeper、etcd、Consul、HBase、MongoDB (副本) |
| **AP** (舍弃 C) | 分区时继续服务,允许数据暂时不一致 | Eureka、Cassandra、DynamoDB、CouchDB、Redis Cluster (默认) |

### 1.5 经典案例

#### ZooKeeper (CP)

```text
场景: Leader 与 Follower 之间网络分区

Zab 协议:
   ├─ 半数以上节点不可达 → Leader 放弃领导,集群停止对外服务
   ├─ 客户端连接: 连接不上 Leader → 报错,而不是返回旧数据
   └─ 优先保证一致性,放弃可用性
```

#### Eureka (AP)

```text
场景: Eureka Server 节点之间网络分区

Eureka 设计:
   ├─ 每个节点都是平等的,无主从
   ├─ 即使分区,各节点仍可独立提供服务
   ├─ 客户端可注册到任意节点
   └─ 分区恢复后,通过复制最终达到一致 (但不保证强一致)
```

#### MySQL (CA, 单机) → MySQL Cluster (CA 变种)

```text
单机 MySQL: CA
   ├─ 无分区 → C 和 A 都能满足
   └─ 主从复制: 主写入 → 异步同步从 → 一致性有滞后

MySQL Group Replication (MGR): CP
   ├─ Paxos 协议保证强一致
   ├─ 网络分区时少数派拒绝写入
   └─ 优先一致性,放弃部分可用性
```

### 1.6 CAP 定理的局限性 ⚠️

#### 误区 1:三选二 ≠ 极端二选一

CAP 不是"非此即彼",而是一个**连续光谱**:

```text
                一致性强
                  ▲
                  │
   CP ───────────┼─────────── AP
                  │
                  │
                  ▼
                可用性强

实际系统多在中间,例如:
- HBase: 倾向 CP,但提供最终一致的副本读取
- Cassandra: 默认 AP,但提供强一致级别 (QUORUM) 选项
```

#### 误区 2:P 不能放弃

Eric Brewer 自己澄清: **"在分布式系统中,网络分区是必然发生的,放弃 P 等同于放弃分布式"**。

```text
现实: 节点越多、网络越复杂,分区概率越高
     - 2 节点: 分区概率 0.01%
     - 100 节点: 分区概率 ~10%
     - 10000 节点: 分区概率 ~50%

结论: 真正的分布式系统必须在 P 发生时做选择 (C 或 A)
```

#### 误区 3:CAP 忽略延迟

```text
CAP 假设:
   - 数据复制是瞬时的
   - 不考虑网络延迟

实际:
   - 主从同步需要时间
   - 即使无分区,读写一致性也有延迟窗口
   - "强一致" 在广域网几乎不可行
```

### 1.7 PACELC 扩展

**PACELC** (Daniel Abadi, 2010): 在 PAC 基础上加入延迟权衡。

```text
PACELC:
   If P (分区):
       在 C 和 A 之间选择
   Else (无分区):
       在 Latency (延迟) 和 Consistency (一致性) 之间选择

例:
   DynamoDB (AP/EL): 分区时 A,正常时为低延迟放弃一致性
   HBase (CP/EC):   分区时 C,正常时为一致性放弃延迟
   Cassandra (AP/EL): 同 DynamoDB
   ZooKeeper (CP/EC): 同 HBase
```

## 二、BASE 理论

### 2.1 起源

**BASE** 由 **Dan Pritchett** (eBay 架构师) 在 2008 年提出,是对 CAP 中 AP 方向的工程实践总结。

**全称**: **B**asically **A**vailable, **S**oft state, **E**ventually consistent

### 2.2 三要素

| 要素 | 含义 | 与 CAP 对应 |
|------|------|--------------|
| **BA** Basically Available | 系统基本可用,允许损失部分可用性 (响应慢、功能降级) | A |
| **S** Soft State | 允许中间状态,数据副本同步存在延迟 | 弱 C |
| **E** Eventually Consistent | 经过一段时间后,数据最终达到一致 | E |

### 2.3 基本可用 (Basically Available)

```text
基本可用 ≠ 完全不可用

实现方式:
1. 响应时间延长
   - 正常 100ms,故障时 1-2s
2. 功能降级
   - 关闭非核心功能 (推荐、评论、搜索)
   - 返回兜底数据 (默认缓存)
3. 流量削峰
   - 限流、熔断、降级
4. 服务降级
   - 返回简化版数据
```

#### 案例: 淘宝双十一

```text
平时: 完整功能 + 100ms 响应
双十一: 简化版首页 + 限流 + 排队 + 1-2s 响应
     → 基本可用,但牺牲了响应时间和非核心功能
```

### 2.4 软状态 (Soft State)

```text
硬状态: 数据状态确定后,任何节点读取都一致 (强一致)
软状态: 允许数据存在中间状态,不同节点数据可能不一致

例:
   订单状态:
   待支付 → 已支付 → 已发货 → 已收货   (硬状态机)
   
   但分布式下:
   Node A: 待支付
   Node B: 已支付   (同步中)
   Node C: 待支付
   → 这是软状态,最终会达到一致
```

### 2.5 最终一致性 (Eventually Consistent)

```text
定义: 系统保证在没有新写入操作的前提下,数据最终会达到一致状态

最终一致 ≠ 强一致:
   强一致: 写入后立即所有节点一致
   最终一致: 写入后经过一段时间 (ms / s / min) 后一致

"最终" 的含义:
   - 没有新的更新操作
   - 经过有限时间 (通常是秒级)
   - 通过异步复制达到一致
```

### 2.6 BASE vs ACID

| 维度 | ACID (传统数据库) | BASE (分布式系统) |
|------|---------------------|---------------------|
| **全称** | Atomicity, Consistency, Isolation, Durability | Basically Available, Soft state, Eventually consistent |
| **目标** | 强一致 | 高可用 + 最终一致 |
| **适用** | 单库/单机事务 | 分布式系统 |
| **实现** | 锁、两阶段提交 | 异步复制、补偿事务 |
| **性能** | 较慢 (同步阻塞) | 较快 (异步非阻塞) |
| **数据一致性** | 立即一致 | 最终一致 |
| **代表** | MySQL InnoDB、PostgreSQL | Cassandra、DynamoDB |

### 2.7 BASE 的工程实现

```text
最终一致性的实现方式:

1. 读时修复 (Read Repair)
   - 读取时检测副本不一致,异步修复
   
2. 写时修复 (Write Repair)
   - 写入时同时修复所有副本
   
3. 异步复制 (Async Replication)
   - 写入主,异步同步到从
   
4. 反熵 (Anti-entropy)
   - 后台定期对比副本,修复差异
   
5. 定时校对 (Quorum Read)
   - 读 R 个副本 + 写 W 个副本,保证 NWR 约束
```

## 三、CAP 的扩展与误区

### 3.1 CAP 忽略的几点

#### 1. 网络延迟

```text
CAP 模型假设:
   - 网络分区是瞬时判断 (是/否)
   - 节点间通信是瞬时同步

实际:
   - 网络延迟是常态
   - 一致性需要时间传播
   - 强一致 + 低延迟 在广域网不可兼得
```

#### 2. 一致性的程度

```text
CAP 把一致性当成二元 (有/无),实际一致性有程度:

强一致性 < 顺序一致性 < 因果一致性 < 读你所写 < 单调读 < 最终一致性

(详见第四章 一致性模型)
```

#### 3. 可用性的程度

```text
CAP 把可用性当成二元,实际可用性也有程度:

完全可用 → 服务降级 → 部分功能 → 只读 → 不可用

100%     99.99%      99.9%       50%      0%
```

### 3.2 ACID vs CAP 中的"一致性"

| 概念 | ACID 的 C | CAP 的 C |
|------|-----------|----------|
| **含义** | 事务前后数据完整性约束 | 分布式节点数据相同 |
| **范围** | 单数据库事务 | 跨节点多副本 |
| **实现** | 锁、约束 | 共识协议、同步 |
| **冲突?** | 不冲突,可同时满足 (单库) | 与 A 互斥 (分布式) |

### 3.3 PACELC 总结表

| 系统 | P 分区时 | E 正常时 | 倾向 |
|------|---------|----------|------|
| DynamoDB | A | L | AP/EL |
| Cassandra | A | L | AP/EL |
| Riak | A | L | AP/EL |
| ZooKeeper | C | C | CP/EC |
| etcd | C | C | CP/EC |
| HBase | C | C | CP/EC |
| MongoDB | C | L (默认) / C (可配) | CP/EL |
| MySQL Replication | A | L | AP/EL |
| Redis Cluster | A | L | AP/EL |

## 四、一致性模型 (Consistency Models)

### 4.1 强一致性家族

#### Linearizability (线性一致性 / 线性化)

**定义**: 所有操作看起来像是按某个全局顺序原子执行,且顺序与实时时间一致。

```text
   T0: 写 X=1 (Node A)
   T1: 读 X   (Node B)
   T2: 读 X   (Node C)

线性一致性要求:
   - 任何读都返回 ≤ 读时刻已完成的最近写
   - 例: T1 读到 1 (因为 T0 已完成)
        T2 读到的 ≥ 1 (因为 T0 已完成)

实现: 强同步复制 (Raft、Paxos、2PC)
性能: 慢,但语义最强
```

#### Sequential Consistency (顺序一致性)

**定义**: 所有操作按某种全局顺序执行,且每个进程看到的顺序与自身操作顺序一致。

```text
   P1: 写 X=1
   P2: 写 X=2
   P3: 读 X=?
   P4: 读 X=?

   顺序一致性: P3 和 P4 看到的顺序必须一致
                (可能都看到 1→2,也可能都看到 2→1)
   但不要求顺序与真实时间一致
   → 比线性一致性弱
```

#### Causal Consistency (因果一致性)

**定义**: 有因果关系的操作必须被所有节点以相同顺序看到;无因果关系的操作可以任意顺序。

```text
   P1: 写 X=1
   P1: 读 X, 写 Y=X+1=2
   P2: 读 Y (看到 2 → 因果依赖于 X=1)

要求:
   - P2 必须先看到 X=1 再看到 Y=2 (因果顺序)
   - 但 P3 写 Z=3,与 X 无因果 → P2 可以任意顺序看 X 和 Z

比顺序一致性弱,比最终一致性强
实现: Vector Clock、COPS 系统
```

### 4.2 弱一致性家族

#### Read-your-writes Consistency (读你所写)

**定义**: 进程写入一个值后,自身后续读必返回该值或更新的值。

```text
   P1: 写 X=1
   P1: 读 X (必须返回 1)

   但 P2: 读 X 可能返回 0 (旧值,允许)
```

#### Monotonic Reads Consistency (单调读一致性)

**定义**: 进程读到的值不会回退。

```text
   P1: 读 X = 1
   P1: 再读 X (必须 ≥ 1)

   保证读到新值后不会读到旧值
```

#### Monotonic Writes Consistency (单调写一致性)

**定义**: 进程对同一 key 的写操作顺序对所有节点都一致。

#### PRAM Consistency (Pipeline RAM)

**定义**: 单个进程的写操作按其发起顺序被其他进程看到,但不同进程的操作可以任意交错。

### 4.3 最终一致性 (Eventual Consistency)

**定义**: 没有新写入后,经过有限时间,所有副本收敛到相同值。

```text
时间窗口:
   T0: 写入 X=1 到 Node A
   T1: 异步复制到 Node B,C,D
   T2: 所有节点 X=1 (收敛)

窗口内: 不同节点可能读到不同值 (旧值)
窗口后: 一致
```

### 4.4 一致性模型对比图

```text
   一致性强度由强到弱:

   ┌──────────────────────────────────────────────┐
   │  Linearizability (线性一致)                   │  最强
   │  ├─ Sequential Consistency (顺序一致)        │
   │  │  ├─ Causal Consistency (因果一致)          │
   │  │  │  ├─ Monotonic Reads + Read-your-writes │
   │  │  │  │  ├─ Monotonic Writes                │
   │  │  │  │  │  ├─ PRAM                         │
   │  │  │  │  │  │  └─ Eventual Consistency      │  最弱
   └──────────────────────────────────────────────┘

   性能由弱到强 (反过来,越弱越快)
```

### 4.5 各模型应用

| 模型 | 性能 | 一致性 | 应用 |
|------|------|--------|------|
| 线性一致 | 慢 | 强 | ZooKeeper、etcd |
| 顺序一致 | 中 | 强 | 部分分布式锁 |
| 因果一致 | 中 | 较强 | COPS、Eiger |
| 读你所写 | 中 | 中 | 个人博客、社交动态 |
| 单调读 | 中 | 中 | 计数器 |
| 最终一致 | 快 | 弱 | DNS、CDN、Cassandra |

## 五、FLP 不可能性

### 5.1 定理内容

**FLP 不可能性** (Fischer, Lynch, Paterson, 1985):

> 在**异步网络**模型下,**即使只有一个节点可能故障**,也不存在一个**确定性**的分布式共识算法能在**有限时间内**达成一致。

### 5.2 关键术语

```text
异步网络 (Asynchronous):
   - 节点间消息可能延迟任意长
   - 但最终会到达 (与同步网络区别:有上界)
   
共识 (Consensus):
   - 所有非故障节点就某个值达成一致
   - 满足: 终止 (Termination)、一致 (Agreement)、有效 (Validity)
   
确定性算法 (Deterministic):
   - 不依赖随机数
   - 相同输入必产生相同输出
```

### 5.3 证明思路

```text
FLP 证明的核心:

1. 假设存在这样的算法 A
2. 构造一个 "敌手" 调度器,人为延迟关键消息
3. 构造两个可能的世界 (configurations):
   - 世界 A: 节点 P1 收到 X=0 后才收到 X=1
   - 世界 B: 节点 P1 收到 X=1 后才收到 X=0
4. 由于异步网络无法区分这两个世界
5. 节点 P1 的决策无法保证在两个世界都一致
6. → 矛盾

结论: 不存在总是能在有限时间达成共识的算法
```

### 5.4 如何绕过 FLP

FLP 不可能性 ≠ 分布式系统无法做共识。绕过方法:

| 方法 | 原理 | 缺点 |
|------|------|------|
| **超时机制** | 假设同步网络 (有超时上界),超时即失败 | 需要时钟同步 |
| **随机化** | 用随机数打破对称性 (例如 Raft 选举) | 可能失败但概率低 |
| **部分同步** | 假设网络最终会同步 (Paxos、Raft 用的) | 故障时延迟可能很长 |
| **许可制** | 限制故障节点数 (如 n=3f+1) | 限制系统规模 |

### 5.5 Paxos / Raft 如何绕过

```text
Paxos / Raft 都基于 "部分同步" 模型 (而不是严格异步):

   - 网络大部分时间是同步的
   - 偶尔出现长延迟,但最终会恢复同步
   - 在同步期间完成共识

   选举超时 / 心跳超时:
   - 假设同步: 超时 = 失败
   - 异步期间: 暂时无法共识,但同步后能恢复

   这不是违反 FLP:
   - FLP 说的是异步网络严格不可能
   - 我们放宽到部分同步,就有解
```

## 六、共识问题与算法 (Consensus)

### 6.1 什么是共识问题

```text
共识 (Consensus) 问题:

N 个节点对某个值 v 达成一致,需要满足:
1. 一致性 (Agreement): 所有非故障节点决定相同的值
2. 有效 (Validity): 决定的值必须来自某个节点提议
3. 终止 (Termination): 每个非故障节点最终会做出决定
```

### 6.2 Paxos 算法

#### 起源

- **Leslie Lamport** 1998 年提出,2001 年完整描述
- 被称为 "分布式共识的基石"
- 工程实现难懂 → 后续 Raft 简化

#### 角色

| 角色 | 职责 |
|------|------|
| **Proposer** | 提出提案 (value + 提案号) |
| **Acceptor** | 投票接受/拒绝提案 |
| **Learner** | 学习被选定的值 (不参与投票) |

#### 两阶段提交 (Basic Paxos)

```text
Phase 1: Prepare (准备)
   Proposer 选择提案号 N (全局唯一且递增)
   发送 Prepare(N) 给多数 Acceptors

   Acceptor 收到 Prepare(N):
   - 如果 N > 之前见过的任何提案号
        → 承诺不再接受 < N 的提案
        → 返回已接受的最大提案号和值 (如果有)
   - 否则: 拒绝

Phase 2: Accept (接受)
   Proposer 收到多数 Acceptor 的承诺:
   - 如果返回了已接受的值: 必须使用该值
   - 否则: 使用自己的值
   发送 Accept(N, value) 给多数 Acceptors

   Acceptor 收到 Accept(N, value):
   - 如果 N >= 已承诺的最大提案号
        → 接受,持久化
   - 否则: 拒绝

   当多数 Acceptor 接受 → value 被选定 (chosen)
```

#### 时序图

```text
   Proposer           Acceptors (多数)
     │                    │
     │─Prepare(1)────────→│
     │                    ├─承诺不再接受<1
     │←─Promise(无值)─────│
     │                    │
     │─Accept(1, X=5)───→│
     │                    ├─接受 X=5
     │←─Accepted──────────│
     │                    │
   选定 X=5 ✓
```

#### Multi-Paxos (优化版)

```text
Basic Paxos 一次只能选一个值,Multi-Paxos 优化:

1. 选举一个稳定 Leader (通过 Basic Paxos)
2. Leader 跳过 Prepare 阶段,直接 Accept
3. 后续值都由 Leader 提议,只需一次 RTT

性能提升:
   Basic Paxos: 2 RTT per value
   Multi-Paxos: 1 RTT per value (稳定后)
```

### 6.3 Raft 算法

#### 起源

**Diego Ongaro 和 John Ousterhout** 2014 年提出,目标是 **让共识算法易于理解**。

#### 三个角色

| 角色 | 职责 |
|------|------|
| **Leader** | 处理所有客户端请求,复制日志到 Follower |
| **Follower** | 被动响应,接收 Leader 日志 |
| **Candidate** | 选举期间的临时角色 |

#### 三个子问题

```text
1. Leader Election (领导者选举)
2. Log Replication (日志复制)
3. Safety (安全性)
```

#### 1. Leader Election

```text
初始: 所有节点都是 Follower

Leader 心跳超时 (默认 150-300ms) → 转为 Candidate
   ↓
Candidate 发起选举:
   - 当前任期号 + 1
   - 投票给自己
   - 向其他节点发送 RequestVote RPC
   ↓
其他节点回复:
   - 每个节点每个任期最多投一票
   - 先来先得
   ↓
获得多数票 (n/2+1) → 成为新 Leader
   ↓
未获得多数票 → 等待下一个选举超时,重新选举
```

**选举超时随机化**:

```text
选举超时时间 = 随机值 (150-300ms)

目的:
   - 避免多个 Candidate 同时发起选举,造成 "split vote"
   - 随机化让某个 Candidate 先超时,拿到多数票

例:
   Node A 超时 200ms, 发起选举
   Node B 超时 350ms, 还没发起
   Node A 拿到 A + B + C 三票 → 成为 Leader
```

#### 2. Log Replication

```text
Client → Leader:
   SET X=5

Leader:
   1. 追加日志条目到本地日志
      [term=1, index=1, X=5]
   2. 并行发送 AppendEntries RPC 给所有 Follower
   3. 等待多数 Follower 确认

Follower:
   - 校验日志连续性 (term 和 index 匹配 prevLog)
   - 追加新条目到本地日志
   - 返回成功

Leader:
   - 收到多数确认 → 提交日志 (committedIndex 推进)
   - 应用到状态机
   - 返回 Client 成功
   - 下一心跳通知 Follower 提交
```

#### 日志一致性保证

```text
Raft 通过两个约束保证一致性:

1. 如果两个日志条目有相同的 (term, index),则:
   - 命令相同
   - 之前的所有日志条目也相同

2. Leader 在选举时:
   - Candidate 必须包含 Leader 的所有已提交条目
   - 多数派响应证明 Candidate 的日志至少与多数节点一样新
```

#### 状态机

```text
   ┌─────────────────────────────────┐
   │         Leader / Follower        │
   ├─────────────────────────────────┤
   │  Persistent State:              │
   │  - currentTerm (当前任期号)     │
   │  - votedFor (投票给谁)         │
   │  - log[] (日志条目)             │
   │                                 │
   │  Volatile State:                │
   │  - commitIndex (已提交位置)     │
   │  - lastApplied (已应用位置)    │
   │                                 │
   │  Leader:                        │
   │  - nextIndex[] (每个 follower) │
   │  - matchIndex[] (每个 follower) │
   └─────────────────────────────────┘
```

### 6.4 Paxos vs Raft

| 维度 | Paxos | Raft |
|------|-------|------|
| 提出时间 | 1998 | 2014 |
| 理解难度 | 难 | 易 |
| 角色 | Proposer/Acceptor/Learner | Leader/Follower/Candidate |
| 选举 | 多 Proposer 竞争 | 强 Leader (任期制) |
| 工程实现 | ZK Zab 自实现 | etcd、Consul |
| Leader 唯一 | 多 Proposer | 强唯一 |
| 日志结构 | 无序 | 严格顺序 |

### 6.5 其他共识算法

#### Zab (ZooKeeper)

```text
Zab = Zookeeper Atomic Broadcast

特点:
- 类 Paxos,简化版
- 强 Leader (选举后,所有写走 Leader)
- ZXID 全局递增事务 ID
- 崩溃恢复时保证已提交的消息不丢
```

#### Gossip (Cassandra / Consul)

```text
Gossip = 谣言传播

特点:
- 去中心化,无 Leader
- 节点周期性与其他随机节点同步状态
- 最终一致,延迟通常 1-2 秒
- 适合大规模集群 (几百到上千节点)
```

## 七、Quorum 机制 (NWR 模型)

### 7.1 概念

**Quorum**: 读写操作的法定人数。

```text
N = 副本总数 (Replication Factor)
W = 写副本数 (写多少副本算成功)
R = 读副本数 (读多少副本返回)

Quorum 约束:
   W + R > N  → 强一致 (读写必有重叠)
   W + R ≤ N  → 最终一致 (读写可能不重叠)
```

### 7.2 强一致场景

```text
N=3, W=2, R=2:

   写: 必须写 2 个副本算成功
   读: 必须读 2 个副本

   读 + 写 = 4 > 3 = N
   → 必有重叠,读到最新值

例:
   写 X=5 到 Node 1, Node 2 (2/3)
   读 X 从 Node 1, Node 2 (返回 5)
   或读 X 从 Node 2, Node 3 (返回 5, 因为 Node 2 已写)
```

### 7.3 一致性与可用性权衡

```text
N=3:

   W=3, R=1: 写阻塞但读快 (Cassandra 默认)
   W=1, R=3: 读阻塞但写快
   W=2, R=2: 平衡 (强一致)
   W=1, R=1: 高可用但可能读到旧值 (最终一致)
```

### 7.4 Sloppy Quorum (松散 Quorum)

```text
传统 Quorum: 严格要求在指定节点集合
Sloppy Quorum: 允许写入"替补"节点 (handoff 节点)

适用: Cassandra
   - 某节点宕机,写可到其他节点
   - 节点恢复后,异步同步数据

例:
   N=3 (Node A, B, C), W=2
   Node A 宕机
   → 写 Node B 和 Node D (替补,不在 N 中)
   → Node A 恢复后,异步从 Node D 取回数据
```

### 7.5 Hinted Handoff (Cassandra 特色)

```text
Sloppy Quorum 的具体实现:

1. Node A 宕机
2. Node B 收到写,发现 Node A 不可达
3. 把写副本到 "hinted" 节点 (例如 Node D)
4. Node A 恢复后,Node D 把 hinted 数据发回 Node A
5. 数据最终达到一致
```

## 八、分布式事务

### 8.1 什么是分布式事务

```text
分布式事务 = 跨多个独立服务/数据库的事务,保证 ACID

例:
   - 下单 (订单服务) → 扣库存 (库存服务) → 扣款 (支付服务)
   - 三个独立系统,需要要么全成功要么全失败

   单一服务内事务: 容易 (本地事务)
   跨服务事务: 难 (网络、机器故障)
```

### 8.2 两阶段提交 (2PC)

#### 角色

| 角色 | 职责 |
|------|------|
| **协调者 (Coordinator / TM)** | 协调各参与者,决定提交或回滚 |
| **参与者 (Participant / RM)** | 执行本地事务,反馈成败 |

#### 阶段

```text
阶段 1: Prepare (准备)

   Coordinator → Participants: Prepare
   ├─ 写日志 (Begin)
   ├─ 锁定资源
   ├─ 写 undo/redo 日志
   ├─ 执行事务 (不提交)
   └─ 返回: Yes (可提交) / No (失败)

   Coordinator 收集所有响应:
   ├─ 全部 Yes → 进入 Phase 2 Commit
   └─ 任意 No → 进入 Phase 2 Rollback


阶段 2: Commit (提交)

   Coordinator → Participants: Commit
   ├─ 写日志 (Commit)
   ├─ 本地提交事务
   └─ 返回: Done
```

#### 时序图

```text
   Coordinator        Participants (Node A, B, C)
        │                    │
        │──Prepare────────→│ A: 准备 ✓
        │                    │ B: 准备 ✓
        │←───Yes ←──────────│ C: 准备 ✓
        │                    │
        │──Commit─────────→│ A: 提交
        │                    │ B: 提交
        │←───Done ←─────────│ C: 提交
        │                    │
       完成 ✓
```

#### 2PC 的问题

```text
1. 同步阻塞
   - Prepare 后所有参与者持有锁,直到收到 Commit/Rollback
   - 阻塞时间长,影响性能

2. 协调者单点故障 ⚠️
   - Coordinator 挂掉 → Participants 阻塞 (没人告诉他们结果)
   - 资源长期锁定,系统不可用

3. 数据不一致
   - Commit 请求阶段,部分参与者收到,部分未收到
   - 收到的提交,没收到的永远不知道该提交还是回滚

4. 脑裂
   - 协调者恢复后,可能与其他节点数据状态不一致
```

### 8.3 三阶段提交 (3PC)

#### 阶段

```text
阶段 1: CanCommit
   Coordinator: 询问所有参与者 "能否提交?"
   Participants: 检查资源,返回 Yes/No
   (不锁定资源)

阶段 2: PreCommit
   Coordinator: 全部 Yes → 发 PreCommit
   Participants: 写 undo/redo 日志,锁定资源
   (锁定资源,但不提交)

阶段 3: DoCommit
   Coordinator: 发 DoCommit
   Participants: 真正提交
```

#### 3PC 的改进与局限

```text
改进:
   - 增加 PreCommit 阶段,降低阻塞时间
   - 超时机制: PreCommit 后超时自动提交

局限:
   - 网络分区时仍可能不一致
   - 实现复杂,实际很少使用
   - 业界主流仍用 2PC + 补偿
```

### 8.4 TCC (Try-Confirm-Cancel)

#### 三个阶段

```text
Try 阶段:
   - 预留资源 (不真正扣减)
   - 例: 冻结库存 5 件 (业务表 status=frozen)
   - 业务校验 (余额是否够)

Confirm 阶段:
   - 真正执行业务
   - 例: 库存 -5 (frozen → used)
   - 必须幂等

Cancel 阶段:
   - 释放预留资源
   - 例: 解冻库存 (frozen → available)
   - 必须幂等
```

#### 优缺点

```text
优点:
   - 无长期锁,性能好
   - 业务控制粒度细
   - 适合高并发场景

缺点:
   - 业务侵入大 (每个服务都要写三个方法)
   - 实现复杂
   - 状态机复杂,容易出错
```

#### 示例代码

```java
public interface TccTransaction {
    // 资源预留
    boolean tryDo(BusinessContext ctx);

    // 真正执行业务
    boolean confirm(BusinessContext ctx);

    // 回滚预留
    boolean cancel(BusinessContext ctx);
}

// 订单服务 TCC
public class OrderTcc implements TccTransaction {
    public boolean tryDo(BusinessContext ctx) {
        // 插入订单,状态 = PENDING
        return orderDao.insert(ctx.getOrder(), "PENDING");
    }

    public boolean confirm(BusinessContext ctx) {
        // 更新订单状态 = CONFIRMED
        return orderDao.updateStatus(ctx.getOrderId(), "CONFIRMED");
    }

    public boolean cancel(BusinessContext ctx) {
        // 删除订单 (或状态 = CANCELLED)
        return orderDao.updateStatus(ctx.getOrderId(), "CANCELLED");
    }
}
```

### 8.5 Saga 模式

#### 概念

```text
Saga = 长事务拆分为多个本地短事务,每个短事务都有补偿操作

例:
   T1 (下单) → T2 (扣库存) → T3 (扣款)
   ↓
   失败回滚: C3 (退款) → C2 (加库存) → C1 (取消订单)
```

#### 两种协调方式

```text
1. 编排式 (Orchestration)
   - 中心化协调器 (Orchestrator)
   - 协调器告诉每个服务做什么
   - 例: Camunda、Conductor

   优点:
   - 集中管理,易调试
   - 业务流程清晰
   缺点:
   - 协调器单点
   - 业务耦合

2. 编舞式 (Choreography)
   - 去中心化,事件驱动
   - 每个服务发布事件,其他服务订阅
   - 例: Apache Kafka + Event Sourcing

   优点:
   - 无单点
   - 服务解耦
   缺点:
   - 流程难追踪
   - 调试复杂
```

#### 示例 (编排式)

```text
下单成功 → 触发 "OrderCreated" 事件
   ↓
库存服务订阅 → 扣库存 → 成功 → 触发 "StockReserved"
   ↓
支付服务订阅 → 扣款 → 成功 → 触发 "PaymentCompleted"
   ↓
订单服务订阅 → 更新订单状态 = "PAID"

任一步失败 → 触发补偿事件 → 反向操作
```

### 8.6 本地消息表 (异步确保)

#### 原理

```text
核心思想: 用本地事务 + 消息表 + 异步重试 实现最终一致

步骤:
1. 业务操作与消息写入同一本地事务 (原子)
   - BEGIN TRANSACTION
   - INSERT INTO order (...)     ← 业务数据
   - INSERT INTO message_queue (...)  ← 待发送消息
   - COMMIT

2. 后台轮询消息表,发送到 MQ (RocketMQ/Kafka)

3. 消费者处理消息,成功后 ACK
   - 失败重试,直到成功
   - 幂等处理
```

#### 优点

```text
- 实现简单 (无 2PC 复杂协议)
- 性能好 (异步)
- 最终一致
- 业界广泛使用 (阿里、字节)
```

### 8.7 各方案对比

| 方案 | 一致性 | 性能 | 实现复杂度 | 适用 |
|------|--------|------|------------|------|
| 2PC | 强一致 | 差 | 中 | 单库多库,小规模 |
| 3PC | 强一致 | 差 | 高 | 极少用 |
| **TCC** | 最终一致 | 好 | 高 | 资金、库存 |
| **Saga** | 最终一致 | 好 | 中 | 长业务流程 |
| **本地消息表** | 最终一致 | 好 | 低 | **最常用** |
| **MQ 事务消息** | 最终一致 | 好 | 中 | RocketMQ 等 |
| **Seata AT** | 最终一致 | 好 | 中 | 阿里系 |

## 九、分布式锁

### 9.1 分布式锁的要求

```text
1. 互斥性 (Mutual Exclusion)
   - 任何时刻只有一个客户端持有锁
   
2. 死锁避免 (Deadlock Free)
   - 必须有超时机制
   - 不能永久持有

3. 容错性 (Fault Tolerance)
   - 单点故障不能丢锁
   - 锁服务要可用

4. 可重入 (Reentrant) [可选]
   - 同一线程可多次获取锁

5. 阻塞/非阻塞 (Blocking/Non-blocking) [可选]
   - 拿不到锁立即返回 vs 等待
```

### 9.2 基于数据库

```sql
-- 简单实现
CREATE TABLE locks (
    id INT PRIMARY KEY,
    lock_name VARCHAR(64) UNIQUE,
    holder VARCHAR(64),
    expire_at TIMESTAMP
);

-- 加锁: INSERT 一条记录 (成功 = 拿到锁)
INSERT INTO locks (id, lock_name, holder, expire_at)
VALUES (1, 'order_lock', 'client-A', NOW() + INTERVAL 10 SECOND);

-- 解锁: DELETE 该记录
DELETE FROM locks WHERE lock_name = 'order_lock' AND holder = 'client-A';
```

**缺点**: 性能差、单点

### 9.3 基于 Redis

#### SET NX EX (单节点)

```bash
SET lock:order  uuid_value  NX  EX  10

# NX = 只在不存在时设置
# EX = 过期时间 10 秒
# uuid_value = 唯一标识,用于安全释放
```

#### 安全释放 (Lua 脚本)

```lua
-- 释放锁: 只有持有者才能释放
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

#### RedLock (多节点)

```text
N 个独立 Redis 节点 (通常 N=5)

加锁:
   1. 依次向 N 个节点 SET NX EX
   2. 统计成功节点数: >= N/2 + 1 → 拿到锁
   3. 计算有效时长: TTL - 消耗时间
   4. 有效时长 > 0 且 拿到多数 → 加锁成功
   5. 否则: 向所有节点 DEL (释放)

争议:
   Martin Kleppmann 批评: 时钟跳跃下 RedLock 不安全
   Antirez 反驳: 工程上够用
   → 业界共识: 单 Redis SET NX EX + Lua 释放即可 (Redisson 看门狗)
```

### 9.4 基于 ZooKeeper

```text
临时顺序节点实现:

1. 客户端在 /locks 路径下创建临时顺序节点
   - 例: /locks/lock_000000001
2. 检查自己是否是最小节点
   - 是 → 获取锁,执行业务
   - 否 → 监听前一个节点的删除事件
3. 前一个节点删除 → 收到通知 → 重新检查
4. 释放锁 → 删除自己的节点 → 触发后续监听
```

#### 优缺点

```text
优点: 强一致 (Zab 协议保证)
缺点: 性能不如 Redis (需写磁盘、ZAB 同步)
```

### 9.5 Redisson 看门狗 (生产推荐)

```java
// Redisson 自动续期机制
RLock lock = redisson.getLock("order_lock");
lock.lock(30, TimeUnit.SECONDS);  // 30 秒过期

// 后台线程每 10 秒 (过期时间 / 3) 自动续期到 30 秒
// 业务执行完后 lock.unlock() 释放

// 业务崩溃 → 看门狗线程停止 → 30 秒后自动释放
// → 不会死锁
```

## 十、时钟与时间

### 10.1 分布式系统中的时间难题

```text
分布式系统没有全局时钟:
- 每台机器有自己的本地时钟
- 不同机器时钟可能偏差很大
- 网络延迟让"同时发生"难定义

例:
   Node A: T=10:00:00.100
   Node B: T=10:00:00.050  ← 慢 50ms
   Node C: T=10:00:00.200  ← 快 100ms

   事件 X 实际发生在 10:00:00.080
   A 认为 X 在 10:00:00.100 (X 已发生)
   B 认为 X 在 10:00:00.050 (X 未发生)
   C 认为 X 在 10:00:00.200 (X 已发生)
```

### 10.2 物理时钟 vs 逻辑时钟

#### 物理时钟 (Physical Clock)

```text
NTP 同步: 多机器通过网络同步时间
   - 精度: 局域网 ms 级,广域网 10-100ms
   - 问题: 跳跃、回拨、偏差

PTP (IEEE 1588): 硬件级时间同步
   - 精度: 微秒级
   - 需特殊网卡
```

#### 逻辑时钟 (Logical Clock, Lamport)

```text
Lamport 时钟:
   - 每个事件附带一个单调递增的逻辑时间戳
   - 规则: 收到消息时,本地时钟 = max(本地,消息时钟) + 1
   
例:
   P1: 事件 a (L=1)
   P1: 事件 b (L=2)
   P1 → P2: 消息携带 L=2
   P2 收到: L = max(本地,2) + 1 = 3

   全序关系: (L, 进程号) 字典序比较
```

#### 向量时钟 (Vector Clock)

```text
每个节点维护一个向量 [N1, N2, N3, ...]
   - Ni 表示节点 i 的事件计数

例:
   Node A: [1, 0, 0]
   Node B: [0, 1, 0]
   Node C: [0, 0, 1]

   Node A 事件: 自己计数 +1 → [2, 0, 0]
   Node A → Node B: 携带 [2, 0, 0]
   Node B 收到: max(本地, 消息) + 1 → max([0,1,0], [2,0,0]) + 1 = [2, 1, 1]

因果关系:
   - V1 ≤ V2 (分量都小于等于) → V1 因果先于 V2
   - 否则 → 并发 (无因果)
```

### 10.3 TrueTime (Google Spanner)

```text
Google Spanner 用 TrueTime API:
   - 返回时间区间 [earliest, latest]
   - 区间宽度 = 时钟不确定性 (通常 < 10ms)
   
TT.now() 返回:
   - earliest: 实际时间 ≥ earliest
   - latest: 实际时间 ≤ latest
   - uncertainty = latest - earliest

Spanner 的 commit wait:
   - 选择时间戳 T
   - 等到 TT.now().latest > T
   - → 保证 T 已被所有节点"过去"
   - → 实现外部一致性 (最强一致性)
```

### 10.4 时钟同步方案对比

| 方案 | 精度 | 复杂度 | 适用 |
|------|------|--------|------|
| NTP | ms-s | 低 | 一般场景 |
| PTP | μs | 中 | 金融交易 |
| GPS | ns | 高 | 电信 |
| 原子钟 | ns | 极高 | 卫星 |
| 逻辑时钟 | N/A | 低 | 事件排序 |
| 向量时钟 | N/A | 中 | 因果一致 |
| TrueTime | ms | 极高 | Spanner |

## 十一、一致性哈希

### 11.1 传统哈希的问题

```text
问题: N 个节点,key 用 hash(key) % N 映射

   Node 数从 N=3 扩展到 N=4
   key 原本在 Node 0 (hash % 3 = 0)
   现在 hash % 4 = 1 → Node 1

   大部分 key 都需要重新映射 → 全量数据迁移
```

### 11.2 一致性哈希原理

```text
一致性哈希 (Consistent Hashing, MIT 1997):

1. 将哈希值空间组织成环形 (0 ~ 2^32-1)
2. 每个节点映射到环上一点 (hash(IP))
3. 每个 key 映射到环上一点 (hash(key))
4. key 沿环顺时针找到的第一个节点就是归属

例:
   环: ... 100 → 200 → 300 → 400 → ...
       Node A (hash=100)
                   Node B (hash=300)
                              Node C (hash=400)

   Key X (hash=250) → 顺时针找 → Node B
```

### 11.3 虚拟节点

```text
问题: 节点少时,数据分布不均 (例如 3 个节点,有的节点可能承载 2 倍数据)

解决: 虚拟节点 (Virtual Node)
   - 每个物理节点映射多个虚拟节点
   - 例: Node A → VNode A1, A2, A3 (均匀分布在环上)

   优点:
   - 数据分布更均匀
   - 节点增减时,只影响相邻虚拟节点
   - 负载均衡
```

### 11.4 应用场景

```text
1. 分布式缓存
   - Memcached client
   - Redis Cluster (16384 槽)

2. 分布式存储
   - Cassandra
   - DynamoDB
   - Riak

3. 负载均衡
   - 一致性哈希负载均衡
   - Nginx upstream 一致性哈希
```

### 11.5 Hash Slot (Redis Cluster)

```text
Redis Cluster 用 Hash Slot 代替一致性哈希:

- 16384 个槽 (0 ~ 16383)
- key 映射到槽: CRC16(key) % 16384
- 槽分配给节点
- 节点增减 → 迁移部分槽 (不是迁移所有 key)

   Cluster 3 节点:
   - Node A: 槽 0-5460
   - Node B: 槽 5461-10922
   - Node C: 槽 10923-16383

   优势:
   - 节点增减只需迁移部分槽 (而不是一致性哈希的部分节点)
   - 槽数量固定,易于管理
```

## 十二、脑裂与仲裁

### 12.1 什么是脑裂 (Split Brain)

```text
脑裂 = 集群因网络分区分裂为多个独立"集群",每个都以为自己是合法的

例:
   5 节点集群
   网络分区:
   ├─ 节点 A, B (能互相通信)
   └─ 节点 C, D, E (能互相通信)

   A,B 选举出新 Leader-α
   C,D,E 选举出新 Leader-β

   → 两个 Leader 都接受写入 → 数据不一致!
```

### 12.2 多数派仲裁

```text
多数派 (Majority / Quorum):
   只有拥有 ≥ N/2+1 节点的分区才能成为合法集群

5 节点:
   - A,B (2 个) → 不是多数派 (需要 3 个) → 不能成为 Leader
   - C,D,E (3 个) → 多数派 → 可以成为 Leader

3 节点:
   - A (1 个) → 不是多数派 → 不能服务
   - B,C (2 个) → 多数派 → 可以服务

2 节点:
   - A (1 个) → 不是多数派
   - B (1 个) → 不是多数派
   → 集群完全不可用 (这正是 2 节点集群不推荐的原因)
```

### 12.3 Lease 机制

```text
Lease = 租约,带超时的授权

   Leader 给 Follower 颁发 Lease:
   - Lease 期间,Follower 承认 Leader 合法
   - Lease 过期: Follower 可以发起新选举

   防止脑裂:
   - Leader 持 Lease,过半节点都响应 → Leader 合法
   - 网络分区时,Leader 失去过半响应 → 自动放弃领导
```

### 12.4 Fencing Token

```text
解决"老 Leader 复活后写入"问题:

   - 每次 Leader 选举时,单调递增 epoch 号
   - 写入时附带当前 epoch
   - 存储系统拒绝 epoch 小的写入

   例:
   ZK zxid / Raft term
   - 老 Leader 复活后,term 较小 → 写入被拒绝
```

## 十三、拜占庭问题与 BFT

### 13.1 拜占庭将军问题

```text
背景 (Lamport 1982):
   拜占庭帝国的多支军队围攻一座城市
   - 各军队由将军率领
   - 只有多数将军一起进攻才能胜利
   - 可能有叛徒 (传递假消息)
   - 通信只能通过信使

问题: 如何在存在叛徒的情况下,所有忠诚将军达成一致行动?
```

### 13.2 拜占庭故障 (Byzantine Fault)

```text
拜占庭故障 = 节点任意行为
   - 发送假消息
   - 不响应
   - 发送冲突消息给不同节点
   - 串通作恶

非拜占庭故障:
   - 崩溃 (Crash Fault): 节点停止响应
   - 遗漏 (Omission Fault): 丢失消息
   - 性能 (Performance Fault): 响应慢
```

### 13.3 拜占庭容错 (BFT)

```text
BFT 算法:
   在 N 个节点中,即使有 f 个节点是拜占庭节点(恶意),系统仍能正确达成共识

   条件: N ≥ 3f + 1
   - N=4, f=1: 容忍 1 个恶意节点
   - N=7, f=2: 容忍 2 个恶意节点
   - N=10, f=3: 容忍 3 个恶意节点

   与 Crash Fault 容错对比:
   - Crash Fault: N ≥ 2f + 1 (Paxos/Raft)
   - Byzantine Fault: N ≥ 3f + 1 (PBFT)
```

### 13.4 PBFT 算法

```text
Practical Byzantine Fault Tolerance (Castro & Liskov 1999)

阶段:
   1. Pre-Prepare (主节点广播请求)
   2. Prepare (所有节点广播 Prepare)
   3. Commit (所有节点广播 Commit)
   4. Reply (返回结果)

复杂度:
   - O(n^2) 消息
   - n=7: 49 条消息
   - 不适合大规模节点
```

### 13.5 何时需要 BFT

```text
需要 BFT 的场景:
   - 区块链 (节点可能作恶)
   - 金融关键系统 (节点可能被攻击)
   - 跨组织联盟链
   - 不可信环境

不需要 BFT 的场景 (用 Crash Fault 模型):
   - 内部集群 (节点受信任,只考虑崩溃)
   - 节点少且物理隔离
   - 性能要求高
   - 大多数互联网系统 (用 Paxos/Raft 即可)
```

## 十四、生产选型与权衡

### 14.1 选型决策树

```text
你的系统需要多强的分布式特性?

1. 单机关系数据库就够?
   → MySQL InnoDB (强一致事务)
   
2. 分布式关系数据库?
   → PostgreSQL + Citus / CockroachDB / TiDB

3. 分布式 KV 缓存?
   ├─ 强一致 + 自动选主 → Redis Sentinel / Cluster
   └─ 最终一致 + 高可用 → Memcached / DynamoDB

4. 分布式协调?
   ├─ 强一致 + Leader → ZooKeeper / etcd
   └─ 最终一致 → Consul

5. 分布式消息队列?
   → Kafka (高吞吐) / RocketMQ (事务消息) / RabbitMQ (灵活路由)

6. 分布式文件系统?
   → HDFS (大文件) / Ceph (通用) / MinIO (对象存储)
```

### 14.2 各场景推荐

#### 配置中心 / 服务发现

```text
要求: 强一致,小数据量,频繁读

推荐:
- etcd (Raft, REST API, k8s 默认)
- ZooKeeper (Zab, Java 生态)
- Consul (Raft + 多数据中心)

对比:
- etcd 性能最好 (10k QPS+)
- ZK 生态成熟 (Dubbo 等)
- Consul 多数据中心友好
```

#### 分布式锁

```text
要求: 互斥、高可用、容错

推荐:
- Redis + Redisson (性能优先)
- ZooKeeper (强一致)
- etcd (强一致 + 简单)

生产推荐: Redis + Redisson
   - 性能高
   - Redisson 看门狗自动续期
   - 集群模式天然支持
```

#### 分布式事务

```text
小规模强一致: 2PC / Seata AT
   - 阿里 Seata: 业界标准
   - 性能可接受

高并发最终一致: 本地消息表 / Saga / MQ 事务消息
   - RocketMQ 事务消息
   - Saga + Choreography

资金场景: TCC
   - 业务可控制,粒度细
```

#### 分布式 ID

```text
要求: 全局唯一、趋势递增、性能高

方案:
1. UUID (无序,索引分裂,DB 不推荐)
2. 自增 ID (单库可,分布式不推荐)
3. 雪花算法 Snowflake (推特)
   - 64 bit: 1 符号 + 41 时间戳 + 10 机器 + 12 序列
   - 4096/ms/节点,理论 4096w/s
4. 滴滴 TinyID (号段模式)
5. 美团 Leaf (Snowflake + 号段)
```

### 14.3 一致性级别与性能对比

| 一致性级别 | 性能 | 延迟 | 适用 |
|------------|------|------|------|
| 强一致 (Linearizable) | 慢 | 高 (10-100ms) | 金融、配置中心 |
| 顺序一致 | 中 | 中 | 部分场景 |
| 因果一致 | 中 | 中 | 社交、协作 |
| 读你所写 | 中 | 中 | 个人状态 |
| 单调读 | 快 | 低 | 计数器、状态 |
| 最终一致 | 最快 | 低 (ms-s) | 缓存、社交动态 |

### 14.4 性能 vs 一致性取舍

```text
                    ┌─────────────┐
                    │ 强一致       │ → 慢但准
                    └─────────────┘
                           ↑ 强
                           │
                    ─ ─ ─ ─ ┼ ─ ─ ─ ─
                           │
                           ↓ 弱
                    ┌─────────────┐
                    │ 最终一致     │ → 快但可能旧
                    └─────────────┘

一般原则:
- 用户感知的数据 (订单状态): 读你所写即可
- 关键数据 (支付、库存): 强一致
- 内容数据 (文章、商品详情): 最终一致
- 统计数据 (UV、PV): 最终一致
```

## 十五、核心要点速记

### CAP / BASE

- **CAP**: 分布式系统三选二,但 P 不能放弃,实际是 C vs A
- **CP**: ZooKeeper、etcd、Consul、HBase
- **AP**: Eureka、Cassandra、DynamoDB、Redis Cluster
- **BASE**: BA (基本可用) + S (软状态) + E (最终一致),AP 的工程实践
- **PACELC**: 在 P 之外,正常时也要在延迟 (L) 和一致 (C) 间权衡

### 一致性模型

- **Linearizability**: 最强,操作实时有序
- **Sequential**: 全局顺序,不必与实时一致
- **Causal**: 因果有序,无关可并行
- **Read-your-writes**: 自己写后必读到
- **Monotonic**: 读到的不会回退
- **Eventual**: 最终一致

### FLP & 共识

- **FLP**: 异步网络 + 单点故障 → 不可能共识 (确定性 + 有限时间)
- **绕过**: 部分同步 + 随机化 + 超时
- **Paxos**: Lamport 1998,两阶段,工程难
- **Raft**: 2014,易理解,强 Leader + 任期
- **Multi-Paxos**: 优化,跳过 Prepare 阶段
- **Zab**: ZooKeeper 用,类 Paxos

### 分布式事务

- **2PC**: 同步阻塞,协调者单点
- **3PC**: 减少阻塞,实际少用
- **TCC**: Try/Confirm/Cancel,业务侵入
- **Saga**: 长事务拆分,补偿操作
- **本地消息表**: 业务事务 + 消息表,异步重试

### 分布式锁

- **Redis SET NX EX**: 单节点,简单
- **Redisson 看门狗**: 自动续期,推荐
- **ZK 临时节点**: 强一致,慢
- **RedLock**: 多节点,争议

### 时间

- **Lamport 时钟**: 逻辑时间,事件排序
- **向量时钟**: 因果关系
- **TrueTime**: Spanner 专用,API 返回时间区间

### 一致性哈希

- **原理**: 环形哈希空间,顺时针查找
- **虚拟节点**: 解决数据倾斜
- **应用**: Redis Cluster (16384 槽)、Cassandra、CDN

### 脑裂

- **多数派**: 只有 ≥ N/2+1 节点才能成为 Leader
- **Lease**: 超时机制,防止老 Leader 复活
- **Fencing Token**: epoch/zxid 拒绝旧 Leader

### BFT

- **Byzantine Fault**: 节点任意作恶
- **BFT 条件**: N ≥ 3f+1 (比 Crash 容错多 1 倍节点)
- **PBFT**: 实用 BFT,O(n^2) 消息
- **适用**: 区块链、不可信环境
- **不适用**: 内部集群 (用 Paxos/Raft 即可)

### 生产选型

- **配置中心**: etcd (Raft) / ZooKeeper (Zab)
- **分布式锁**: Redisson + Redis / ZK / etcd
- **分布式 ID**: Snowflake / Leaf / TinyID
- **分布式事务**: Seata / 本地消息表 / Saga
- **消息队列**: Kafka / RocketMQ / RabbitMQ
