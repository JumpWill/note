## 一、问题背景

### 1.1 什么是双写

```text
双写 = 同时更新两个数据源

典型场景: Redis (缓存) + MySQL (数据库)

┌────────┐
│  App   │
└────┬───┘
     │ 一次业务操作需要更新两个地方:
     │
     ├─→ MySQL (权威,持久化)
     │
     └─→ Redis (缓存,加速读)
```

### 1.2 两个核心问题

```text
问题 1: 更新数据时,是删除缓存还是更新缓存?
   DELETE key     ← 让下次读 miss,主动回填
   UPDATE key=V   ← 直接同步最新值到缓存

问题 2: 写流程中,是先写数据库还是先写缓存?
   ① 写 MySQL → 写 Redis     (Cache-Aside 标准)
   ② 写 Redis → 写 MySQL     (少见)
```

### 1.3 为什么这两个问题如此重要

```text
双写的本质矛盾:

   ① MySQL 和 Redis 是两个独立系统
      - 没有分布式事务 (XA 性能差,生产少用)
      - 任何一个失败都可能导致不一致

   ② 网络延迟不可控
      - 写 MySQL 成功后,Redis 写可能还没到
      - 写 Redis 成功后,MySQL 写可能还没到

   ③ 并发场景复杂
      - 多个客户端同时读写同一个 key
      - 顺序错乱会导致最终不一致
```

## 二、问题 1: 删除缓存 vs 更新缓存

### 2.1 方案对比总览

| 方案 | 实现 | 并发问题 | 推荐度 |
|------|------|---------|--------|
| **更新缓存** | `SET key = new_value` | ⚠️ 多,易脏数据 | ❌ 不推荐 |
| **删除缓存** | `DEL key` | ✅ 少,简单 | ✅ **推荐 (90%)** |
| **延迟双删** | `DEL + 写 DB + 异步 DEL` | ✅ 极少 | ✅ 推荐 + 进阶 |
| **CAS 更新** | Lua 脚本比较版本 | ✅ 极少 | 特定场景 |

### 2.2 更新缓存 (Update Cache) 的并发陷阱 ⚠️

#### 陷阱 1: 双写覆盖(经典并发问题)

```text
【场景】两个客户端并发更新同一行数据

T0: 客户端 A 读 X (用于业务逻辑后)
T1: 客户端 A: UPDATE DB X = 1
T2: 客户端 A: SET Redis X = 1   ← A 的缓存

T1': 客户端 B 读 X (用于业务逻辑后)
T2': 客户端 B: UPDATE DB X = 2
T3': 客户端 B: SET Redis X = 2   ← B 的缓存

但如果执行顺序被打乱:

T1: A: UPDATE DB X = 1
T1': B: UPDATE DB X = 2
T2': B: SET Redis X = 2
T2: A: SET Redis X = 1   ← 旧值 1 覆盖了新值 2 ❌

最终状态:
   - DB = 2 (B 写的)
   - Cache = 1 (A 写的旧值)

问题: B 的更新被 A 覆盖,但 B 是后写入的应该胜出!
```

**为什么会出现**:
- A 和 B 是两个独立的事务
- MySQL 的两阶段提交保证了 DB 内最终一致 (2 > 1)
- Redis 的两次 SET 没顺序保证,可能 A 后于 B 执行

#### 陷阱 2: 写后值丢失

```text
【场景】业务字段是累加/累减操作

代码 (❌):
   void increment(Long id) {
       int newVal = productMapper.selectById(id).getCount() + 1;
       productMapper.updateCount(id, newVal);
       redis.set("product:" + id, JsonUtil.toJson(newVal));
   }

并发问题:
   A 读 X = 100, 准备写 101
   B 读 X = 100, 准备写 101
   A 写 DB X = 101
   A 写 Redis X = 101
   B 写 DB X = 101  (覆盖 A,B 没读 A 的 101)
   B 写 Redis X = 101

结果:
   - DB = 101 (正确累加 1 次,但应该是 102)
   - Redis = 101 (与 DB 一致,但累加语义错了)
```

#### 陷阱 3: 部分字段更新遗漏

```text
【场景】只更新了部分字段,但 SET 用了旧对象

代码 (❌):
   void updatePrice(Long id, BigDecimal newPrice) {
       Product p = productMapper.selectById(id);
       p.setPrice(newPrice);
       productMapper.updateById(p);
       
       // ❌ 把整个对象写回缓存,但其他字段可能是旧的
       redis.set("product:" + id, JsonUtil.toJson(p));
   }

问题:
   - Redis 里的 product 数据,与 DB 的真实状态不一致
   - 比如 productName 是并发被另一个事务改了,但这里 SET 覆盖回去
```

#### 陷阱 4: 写失败导致不一致

```text
【场景】先写 DB 成功,写 Redis 失败

T0: App: UPDATE DB X = new_val ✓
T1: App: SET Redis X = new_val ✗ (网络抖动 / Redis 故障)

结果:
   - DB = new_val (新)
   - Redis = old_val (旧,且永不过期)

后续所有读都命中缓存 (旧值),直到缓存自然过期!
```

### 2.3 删除缓存 (Delete Cache) 的并发陷阱

虽然删除缓存比更新缓存好得多,但**也不是完美的**,仍有一些并发场景会出问题。

#### 陷阱 A: 旧值回写覆盖新值(经典问题)

```text
【场景】先删缓存,再写 DB,中间有并发读

T0: A 线程: DEL Redis X
T1: B 线程: GET Redis X  → miss
T2: B 线程: SELECT DB → X = 1 (读到了旧值,因为 A 还没写 DB)
T3: B 线程: SETEX Redis X = 1   ← 把旧值 1 回写到缓存
T4: A 线程: UPDATE DB X = 2

结果:
   - DB = 2 (新)
   - Redis = 1 (旧,被 B 回写)

问题: 这个旧值会一直存在,直到下次 DELETE 或 TTL 过期!
```

**这是删除缓存方案的"经典漏洞"**,也是后面要讲"延迟双删"的原因。

#### 陷阱 B: 删除缓存失败导致不一致

```text
【场景】写 DB 成功,但 DEL 缓存失败

T0: App: UPDATE DB X = new_val ✓
T1: App: DEL Redis X ✗ (网络抖动 / Redis 故障)

结果:
   - DB = new_val (新)
   - Redis = old_val (旧,永不过期)

后续所有读都命中缓存 (旧值),直到缓存自然过期!
```

**解决方案**: 重试 DEL / 通过 binlog 异步补偿 / 设置短 TTL 兜底

### 2.4 终极方案: 延迟双删 (Delay Double Delete)

为了解决"陷阱 A"(并发读把旧值回写),业界普遍采用 **延迟双删**。

#### 核心思想

```text
不要只删一次缓存,要删两次:

   ① 先删缓存 (挡掉后续的读请求)
   ② 写 DB
   ③ 异步延迟再删一次缓存 (兜底"陷阱 A"中 B 回写的旧值)
```

#### 完整代码

```java
@Transactional
public void updateProduct(Product p) {
    String key = "product:" + p.getId();

    // ① 先删缓存
    redis.del(key);

    // ② 写 DB (事务提交)
    productMapper.updateById(p);

    // ③ 异步延迟再删一次 (关键!)
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);  // 延迟时间 = 业务读 DB + 回写缓存的时间
            redis.del(key);
        } catch (Exception e) {
            log.error("延迟双删失败", e);
        }
    });
}
```

#### 延迟双删为什么有效?

```text
重新审视"陷阱 A"的时序:

T0: A: DEL Redis X (第 1 次)
T1: B: GET Redis X → miss
T2: B: SELECT DB → X = 1 (旧值)
T3: B: SETEX Redis X = 1   ← B 回写旧值 1
T4: A: UPDATE DB X = 2
T5: A: DEL Redis X (第 2 次,延迟 500ms 后)  ← 把 B 回写的旧值再删掉!

结果:
   - DB = 2 (新)
   - Redis = miss (因为 T5 又删了)
   - 下次读会查 DB 并回填 2

关键洞察: 延迟时间需要 > 并发读"读 DB + 回写缓存"的总耗时
   - 一般设置为 500ms ~ 1s
   - 太短: 可能 B 还没回写完成
   - 太长: 不一致窗口长
```

#### 延迟时间的精确计算

```text
理想延迟时间 = max(并发读的处理时间)

并发读的处理时间 = 
   1. SELECT DB 时间 (~ 1-10ms)
   2. 业务逻辑时间 (可能 0-50ms)
   3. SETEX Redis 时间 (~ 1ms)
   总共: ~ 10-100ms

实际推荐:
   - 默认: 500ms (覆盖 99% 场景)
   - 长业务: 1-2s
   - 极简业务: 100-200ms

可以通过监控"读响应时间 P99"来动态调整。
```

### 2.5 基于 binlog 的异步删除 (更稳健的方案)

#### 思想

```text
应用只关心 DB 写入,缓存失效由独立组件异步处理:

   App: 写 DB
        ↓
   DB binlog (ROW 格式)
        ↓
   Canal / Debezium 监听 binlog
        ↓
   解析出变更的 key
        ↓
   DEL Redis

优势:
   - 应用代码零侵入 (不写 DEL 代码)
   - 异步处理,不影响业务性能
   - 即使应用崩溃,binlog 已落盘,可补偿
```

#### 架构图

```text
┌────────┐
│  App   │ ── UPDATE DB ──→ ┌────────┐
└────────┘                   │ MySQL  │
                             └───┬────┘
                                 │ binlog (ROW 格式)
                                 ↓
                          ┌────────────┐
                          │   Canal    │ (或 Debezium, Maxwell)
                          └─────┬──────┘
                                │ 解析为 Cache Event
                                ↓
                          ┌────────────┐
                          │ MQ (Kafka) │ (可选,解耦)
                          └─────┬──────┘
                                ↓
                          ┌────────────┐
                          │  Consumer  │
                          └─────┬──────┘
                                │
                                ↓
                          ┌────────────┐
                          │   Redis    │ ── DEL key ──→
                          └────────────┘
```

#### 代码示例 (Canal 简化版)

```java
@Component
public class BinlogCacheInvalidator {

    @Autowired
    private StringRedisTemplate redis;

    // 订阅 binlog 变更
    @CanalEventListener
    public void onUpdate(CanalEntry entry) {
        // entry = binlog 事件
        if (entry.getEventType() == EventType.UPDATE) {
            String table = entry.getTableName();
            String primaryKey = entry.getPrimaryKey();

            // 根据业务规则计算 cache key
            String cacheKey = buildCacheKey(table, primaryKey);
            redis.del(cacheKey);
        }
    }
}
```

### 2.6 各种方案对比

| 方案 | 一致性 | 实现复杂度 | 性能 | 适用场景 |
|------|--------|------------|------|---------|
| **更新缓存** | ❌ 差 (并发易错) | 低 | 高 (网络 IO 多) | **不推荐** |
| **删除缓存** | ✅ 较好 (有"陷阱 A") | 低 | 高 (少一次 SET) | **大多数场景** |
| **延迟双删** | ✅✅ 好 | 中 | 中 (有 500ms 延迟) | **推荐**,大多数业务 |
| **binlog 异步** | ✅✅✅ 最好 | 高 (需要 Canal) | 异步,不影响业务 | **强一致** 业务 |
| **分布式锁** | ✅✅ 好 | 高 (锁性能差) | 低 | 强一致 + 低并发 |

## 三、问题 2: 先写 DB vs 先写缓存

### 3.1 方案对比

| 方案 | 失败影响 | 一致性 | 推荐度 |
|------|----------|--------|--------|
| **先 DB 后 Cache** | DB 已写,Cache 失败 → 最终一致 (TTL 兜底) | 较好 | ✅ **推荐** |
| **先 Cache 后 DB** | Cache 已写,DB 失败 → 缓存是错误数据 | 较差 | ⚠️ 不推荐 (无特殊理由) |

### 3.2 先写 DB 后写 Cache (Cache-Aside 标准)

#### 正常流程

```text
T0: App: UPDATE DB X = new_val ✓
T1: App: DEL Redis X ✓
    返回成功
```

#### 失败场景分析

```text
场景 1: DB 写失败
   App: UPDATE DB X ✗
        ↓
   抛出异常,流程终止
   ↓
   Cache 没动 → 无不一致 ✓

场景 2: DB 写成功,Cache DEL 失败
   App: UPDATE DB X ✓
   App: DEL Redis X ✗ (网络抖动)
        ↓
   抛出异常 (业务上失败)
   但 DB 已写入
        ↓
   - DB = new_val (新)
   - Redis = old_val (旧,永不过期)
   
   风险: 后续读都返回旧值 (直到 TTL 过期)
```

#### 失败 2 的解决方案

```text
方案 1: 重试 DEL
   写 DB 成功后,DEL 缓存失败时,自动重试 3 次
   最后告警

   public void updateProduct(Product p) {
       productMapper.updateById(p);
       retryDelete("product:" + p.getId(), maxRetry = 3);
   }

方案 2: 异步补偿 (推荐)
   把 DEL 操作写入内存队列 / MQ,失败后异步重试
   即使应用崩溃,重启后从 MQ 拉取补偿

方案 3: 通过 binlog 补偿 (最稳健)
   写 DB 即可,DEL 由 Canal 异步处理 (见上一节)

方案 4: 短 TTL 兜底
   即使 DEL 失败,缓存的 TTL 会让旧值自动过期
   这是兜底,不是首选
```

### 3.3 先写 Cache 后写 DB (为什么通常不推荐)

#### 正常流程

```text
T0: App: SET Redis X = new_val ✓
T1: App: UPDATE DB X = new_val ✓
    返回成功
```

#### 失败场景分析 ⚠️

```text
场景 A: Cache 写成功,DB 写失败 (致命!)
   App: SET Redis X = new_val ✓
   App: UPDATE DB X = new_val ✗ (约束冲突 / 死锁 / 故障)
        ↓
   抛出异常 (业务失败)
   但缓存已写入!
        ↓
   - DB = old_val (旧)
   - Cache = new_val (新,错误的)
   
   风险: 后续所有读都返回错误数据,且可能很久!
```

**这是先 Cache 后 DB 方案的致命缺陷**。具体场景:

```sql
-- DB 端唯一约束冲突
ALTER TABLE products ADD CONSTRAINT uk_name UNIQUE (name);
-- DB 更新违反唯一约束
UPDATE products SET name = 'duplicated' WHERE id = 1;
-- ❌ 抛异常,但缓存里已经是新值了
```

```sql
-- 业务校验失败
UPDATE products SET price = -100 WHERE id = 1;
-- ❌ 价格校验失败抛异常,但缓存里已经是 -100 了
```

#### 场景 A 的"修正"方案及其问题

```text
方案 1: DB 失败时回滚缓存
   public void updateProduct(Product p) {
       redis.set("product:" + p.getId(), JsonUtil.toJson(p));
       try {
           productMapper.updateById(p);
       } catch (Exception e) {
           // 回滚缓存
           Product old = productMapper.selectById(p.getId());
           redis.set("product:" + p.getId(), JsonUtil.toJson(old));
           throw e;
       }
   }

   问题:
   - 回滚需要再次查 DB,可能 DB 也挂了
   - 即使回滚成功,中间有个"新值→旧值"的窗口
   - 并发读可能错过这个回滚 (读到旧值)
```

```text
方案 2: 用事务消息 (Outbox 模式)
   1. 写 DB (同事务写 outbox 表)
   2. 后台进程读 outbox 写 Redis
   
   优点: 不会有"缓存已写但 DB 没写"的不一致
   缺点: 实现复杂
```

#### 为什么"先 Cache 后 DB"在少数场景下也用?

```text
极少数场景用"先 Cache 后 DB":

1. Redis 作为权威数据源 (Redis 本身就是 DB)
   - 例: 用 Redis 存 Session,不存在 MySQL 写失败问题
   - 这其实是 Write-Through (Cache 即权威)

2. 接受最终一致,DB 写失败也不回滚缓存
   - 例: 缓存预热的场景,DB 还没写但缓存已更新(很少见)

3. 写入即生效 (Eager Write)
   - 例: 用户点击按钮立即显示新值,后台异步同步到 DB
   - 这是 Write-Behind 模式,不是 Cache-Aside

总结: 标准 Cache-Aside 模式下,几乎都是"先 DB 后 Cache"
```

### 3.4 决策树

```text
选择"先 DB 后 Cache" 还是 "先 Cache 后 DB"?

Q1: Redis 是否为权威数据源?
   ├─ 是 → Write-Through (Cache 即权威,无需纠结顺序)
   └─ 否 → Q2

Q2: 是否能容忍"Cache 新值而 DB 旧值" (反方向不一致)?
   ├─ 不能 → 必须"先 DB 后 Cache" ✅
   │        写 DB 失败就抛异常,缓存不动
   └─ 能容忍 → Q3

Q3: 写 DB 失败的概率?
   ├─ 较高 (如唯一约束冲突) → 必须"先 DB 后 Cache"
   └─ 极低 (如 Write-Behind 场景) → "先 Cache 后 DB" 也可,但要 Outbox 兜底

生产绝大多数场景: 先 DB 后 Cache ✅
```

### 3.5 顺序与"删除 vs 更新"组合

```text
问题 1 (删除/更新) 与 问题 2 (DB/Cache 顺序) 的组合:

                   ┌─ 先 DB 后 Cache ─┐
                   │                   │
问题 1: 删除缓存 ──┤                   │
                   │  ← Cache-Aside    │
                   │   (推荐组合)       │
                   │                   │
                   └─ 先 Cache 后 DB ──┘
                      (少见,需 Outbox)
```

**推荐的组合是: 先写 DB,再删除缓存**(Cache-Aside 标准做法)。

## 四、综合矩阵: 四种组合对比

### 4.1 四种组合一览

| 组合 | 操作流程 | 一致性 | 实现复杂度 | 推荐度 |
|------|---------|--------|------------|--------|
| **A: 先 DB 后 Update Cache** | UPDATE DB → SET Cache | ❌ 差 | 低 | ❌ |
| **B: 先 DB 后 Delete Cache** | UPDATE DB → DEL Cache | ✅ 好 | 低 | ✅ **推荐** |
| **C: 先 Update Cache 后 DB** | SET Cache → UPDATE DB | ❌ 差 | 中 | ❌ |
| **D: 先 Delete Cache 后 DB** | DEL Cache → UPDATE DB | ✅ 较好 (有陷阱 A) | 低 | ⚠️ 视场景 |

### 4.2 各组合详细分析

#### 组合 A: 先 DB 后 Update Cache

```text
操作: UPDATE DB → SET Redis X = new_val

并发问题:
   - 双写覆盖 (A 覆盖 B)
   - 部分字段丢失
   - 网络分区导致 Redis 失败

失败场景:
   - DB 成功,Cache 失败 → 缓存旧值永存

评价: ❌ 最差,几乎不推荐
```

#### 组合 B: 先 DB 后 Delete Cache (⭐ 推荐)

```text
操作: UPDATE DB → DEL Redis X

并发问题:
   - "陷阱 A" 风险 (B 读 DB 旧值回写)
   - 需要 延迟双删 或 binlog 异步补偿

失败场景:
   - DB 成功,DEL 失败 → 缓存旧值,TTL 兜底

评价: ✅ 推荐,主流做法
```

#### 组合 C: 先 Update Cache 后 DB

```text
操作: SET Redis X = new_val → UPDATE DB

并发问题:
   - 双写覆盖
   - 字段丢失

致命失败:
   - Cache 成功,DB 失败 → 缓存错误值,可能永存

评价: ❌ 不推荐,致命缺陷
```

#### 组合 D: 先 Delete Cache 后 DB

```text
操作: DEL Redis X → UPDATE DB

并发问题:
   - 读穿透 (DEL 后大量读涌向 DB)
   - "陷阱 A" 风险 (B 读 DB 旧值,在 UPDATE 之前回写)

失败场景:
   - DEL 成功,DB 失败 → 缓存未命中,DB 旧值回填 (短时间不一致)

评价: ⚠️ 可用,但需要补偿机制
```

### 4.3 决策矩阵

```text
选择哪种组合? 看一致性要求和实现成本:

                  实现成本
                  低        中          高
              ┌──────────┬──────────┬──────────┐
   最差       │   A     │    B     │    -     │
   一致性      │ (不推荐) │  ⭐推荐 │          │
              ├──────────┼──────────┼──────────┤
   中等        │   D     │    B     │   B+binlog│
   一致性      │          │ +延迟双删│   补偿   │
              ├──────────┼──────────┼──────────┤
   最好        │   -     │    -     │   分布式锁│
   一致性      │          │          │   (低QPS) │
              └──────────┴──────────┴──────────┘

B 组合 (先 DB 后 DEL) 是 90% 业务的首选
```

## 五、读写并发场景分析

### 5.1 四种典型并发场景

下面分析在 Cache-Aside (先 DB 后 DEL) 模式下,各种读写并发的情况。

#### 场景 1: 读 + 写并发 (经典 "陷阱 A")

```text
T0: A 线程: UPDATE DB X = 2
T1: A 线程: DEL Redis X
T2: B 线程: GET Redis X → miss
T3: B 线程: SELECT DB → X = 2 (新值,读到 A 的更新)
T4: B 线程: SETEX Redis X = 2 (新值回写)

结果: 缓存新值 ✓ 一致

T0': A 线程: UPDATE DB X = 2
T1': B 线程: GET Redis X → 命中,返回 old_val
T2': A 线程: UPDATE DB X = 2
T3': A 线程: DEL Redis X
T4': B 线程: 后续读 → miss → 查 DB 拿到 2 → 回填 ✓

只要顺序正确 (DB → DEL → B 的读),就能保证一致
```

#### 场景 2: 写 + 写并发 (双写竞争)

```text
T0: A 线程: UPDATE DB X = 1
T1: B 线程: UPDATE DB X = 2
T2: A 线程: DEL Redis
T3: B 线程: DEL Redis

结果: DB = 2 (B 后写胜),Redis = miss,下次读查到 2
     ✓ 一致
```

#### 场景 3: 写后立即读 (Read-Your-Writes)

```text
T0: App: UPDATE DB X = 2
T1: App: DEL Redis
T2: App: 立即读 X
T3: App: GET Redis → miss
T4: App: SELECT DB → 2 (读到自己的更新)
T5: App: SETEX Redis X = 2

结果: ✓ 一致 (即使读自己刚写的也能拿到新值)
     但有"立即读返回 2"的延迟 (要去 DB 查)
```

#### 场景 4: 写过程中崩溃

```text
T0: App: UPDATE DB X = 2 ✓
T1: App: DEL Redis ✗ (应用崩溃)

结果:
   - DB = 2 (新)
   - Redis = old_val (旧)
   - 后续读都返回旧值,直到 TTL 过期

缓解: 延迟双删 / binlog 补偿 / 短 TTL 兜底
```

### 5.2 延迟双删的时序保证

```text
【延迟双删 完整时序】

T0: A: DEL Redis X (第 1 次删除)
T1: B: GET Redis → miss
T2: B: SELECT DB → X = old_val
T3: B: SETEX Redis X = old_val  ← B 回写旧值
T4: A: UPDATE DB X = new_val
T5: A: 异步延迟 500ms
T6: A: DEL Redis X (第 2 次删除) ← 把 B 回写的旧值清掉

结果:
   - DB = new_val (新)
   - Redis = miss (干净)
   - 下次读 miss → 查 DB → 回填 new_val ✓

延迟时间 ≥ max(读 DB + 回写 Cache 的时间)
```

### 5.3 总结: 并发场景对照表

| 场景 | 顺序 | 是否一致 | 解决方案 |
|------|------|---------|---------|
| 读 + 写 | DB → DEL → 读 | ✅ | 无需 |
| 读 + 写 | DB → DEL → 读 → 回写 | ✅ | 无需 |
| 读 + 写并发 | 读时 DB 已更新 | ✅ | 无需 |
| 写 + 写 | 顺序 DEL | ✅ | 无需 |
| 写 + 写并发 | 后写胜出 | ✅ | DB 锁 |
| 写 + 立即读 | 自己读自己写 | ✅ | 但有延迟 |
| 写过程中崩溃 | DEL 失败 | ❌ | 延迟双删 / 短 TTL |
| 写 + 旧值回写 | "陷阱 A" | ❌ | **延迟双删** |

## 六、生产实践建议

### 6.1 推荐的方案

```text
【90% 业务】: 先 DB 后 DEL (Cache-Aside) + 短 TTL 兜底
   - DB 写成功 → DEL 缓存
   - TTL 设置为业务可容忍不一致时间 (一般 5 分钟 - 1 小时)
   - 即使 DEL 失败,TTL 也会过期

【95% 业务】: 上面 + 延迟双删
   - DEL + 写 DB + 异步 500ms DEL
   - 解决"陷阱 A"

【99% 业务】: 上面 + binlog 异步补偿
   - Canal 监听 binlog,自动 DEL
   - 应用不感知缓存,可靠性高

【99.9% 业务】: 分布式锁
   - 读写都加锁
   - 性能差,只在特殊场景用
```

### 6.2 代码模板

```java
@Service
public class ProductService {

    @Autowired
    private ProductMapper productMapper;

    @Autowired
    private StringRedisTemplate redis;

    @Transactional
    public void updateProduct(Product p) {
        String key = "product:" + p.getId();

        // 1. 先写 DB
        productMapper.updateById(p);

        // 2. 删除缓存 (同步删除)
        try {
            redis.delete(key);
        } catch (Exception e) {
            log.warn("DEL cache failed, will rely on TTL", e);
            // 失败不抛异常,业务继续
        }

        // 3. 延迟双删 (异步)
        asyncDoubleDelete(key, 500);
    }

    private void asyncDoubleDelete(String key, long delayMs) {
        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(delayMs);
                redis.delete(key);
            } catch (Exception e) {
                log.error("延迟双删失败, key={}", key, e);
            }
        });
    }

    public Product getProduct(Long id) {
        String key = "product:" + id;
        String json = redis.opsForValue().get(key);

        if (json != null) {
            return JsonUtil.parse(json, Product.class);
        }

        // miss: 查 DB
        Product p = productMapper.selectById(id);
        if (p == null) {
            // 空值缓存 (短 TTL 防穿透)
            redis.opsForValue().set(key, "__NULL__", Duration.ofSeconds(60));
            return null;
        }

        // 回填 (正常 TTL)
        redis.opsForValue().set(key, JsonUtil.toJson(p), Duration.ofHours(1));
        return p;
    }
}
```

### 6.3 配置建议

```conf
# redis.conf
# DEL 命令失败重试 (在应用层重试)
# 一般应用代码捕获异常后重试 3 次

# TTL 必须设置
# 不能让 key 永不过期 (否则 DEL 失败后永远不一致)
SETEX key 3600 value  # 1 小时 TTL

# 监控 DEL 失败率
# > 0.1% 告警 (说明网络/Redis 有问题)
```

### 6.4 监控指标

```text
必备监控:
   1. DEL 操作失败率 (Redis 异常捕获)
   2. 缓存命中率 (miss 突增说明 DEL 不及时)
   3. 延迟双删任务堆积数
   4. binlog 消费延迟
   5. 缓存与 DB 数据不一致告警 (定时校验)

告警:
   - DEL 失败率 > 0.1%
   - 缓存命中率突降 5%
   - binlog 延迟 > 30s
```

### 6.5 选型决策树

```text
你的业务能容忍多大不一致窗口?

   ├─ 1 秒 (强一致)
   │   → 分布式锁 + 读写串行化
   │
   ├─ 5-10 秒
   │   → binlog 异步补偿 (Canal)
   │
   ├─ 1 分钟
   │   → 延迟双删 + 短 TTL
   │
   └─ 几十分钟到几小时
       → 简单 DEL + 正常 TTL

你的写并发量?

   ├─ 低 (< 100 QPS)
   │   → 可以接受"更新缓存" 方案
   │
   └─ 高 (> 1000 QPS)
       → 必须 "删除缓存" + 延迟双删
```

## 核心要点速记

### 问题 1: 删除 vs 更新缓存

```text
✅ 删除缓存 (DEL):
   - 优点: 简单,无并发问题,易恢复
   - 缺点: 下次读需回填,有"陷阱 A"
   - 推荐: 90% 业务场景

❌ 更新缓存 (SET):
   - 缺点: 双写覆盖、字段丢失、部分失败
   - 推荐: 仅在 Cache 即权威 (Write-Through) 时用

🔄 延迟双删:
   - DEL → 写 DB → 异步 500ms DEL
   - 解决"陷阱 A" 的最佳实践

📡 binlog 异步:
   - Canal 监听 binlog 自动 DEL
   - 应用零侵入,可靠性高
```

### 问题 2: 先 DB vs 先 Cache

```text
✅ 先 DB 后 Cache:
   - DB 是权威,缓存是衍生
   - 即使 Cache 写失败,TTL 兜底
   - 推荐: 标准 Cache-Aside

❌ 先 Cache 后 DB:
   - Cache 已写,DB 失败 → 错误值缓存
   - 致命缺陷,几乎不推荐

⚠️ 特殊情况:
   - Write-Behind: 写 Cache,异步批量写 DB (高吞吐)
   - Write-Through (Redis 即权威): 写 Cache + 同步写 DB
```

### 综合决策

```text
最佳实践组合:
   ✅ 先 DB 后 DEL (Cache-Aside)
   ✅ + 短 TTL 兜底
   ✅ + 延迟双删 解决 "陷阱 A"
   ✅ + binlog 异步补偿 提高可靠性
```

### 三大并发陷阱

```text
1. 双写覆盖 (SET Cache 方案)
   → 改用 DEL

2. 旧值回写 ("陷阱 A")
   → 延迟双删 (DEL → 写 DB → 异步 DEL)

3. DEL 失败
   → 重试 + binlog 兜底 + 短 TTL
```

### 一句话总结

```text
"先写数据库,再删缓存"
"能删不更新"
"延迟双删 + binlog 兜底"
```
