> 本文档系统梳理缓存与数据库协同的三种核心设计模式,以 **Redis + MySQL** 为实际场景,分析每种模式的读写流程、优缺点、适用场景与生产陷阱。

## 一、缓存模型总览

### 1.1 三种核心模式

```text
┌──────────────────────────────────────────────────────────────┐
│  缓存设计模式                                                    │
├──────────────────────────────────────────────────────────────┤
│  1. Cache-Aside (旁路缓存)                                      │
│     - 应用代码直接控制 cache 和 DB                               │
│     - 最常用,生产环境 80%+ 场景                                  │
│     - 典型: Redis + MySQL 读多写少                              │
│                                                               │
│  2. Read-Through / Write-Through (读写穿透)                    │
│     - 应用只与 Cache 交互                                       │
│     - Cache 抽象层负责与 DB 同步                                │
│     - 典型: ORM 二级缓存、Hibernate                            │
│                                                               │
│  3. Write-Behind (异步写回)                                     │
│     - 写 Cache 即返回,异步批量写 DB                             │
│     - 高吞吐场景                                                │
│     - 典型: 计数器、消息队列、日志                              │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 核心维度对比一览

| 模式 | 一致性 | 写性能 | 读性能 | 实现复杂度 | 适用场景 |
|------|--------|--------|--------|------------|----------|
| **Cache-Aside** | 最终一致 | 高 | 高 (命中时) | 低 | **90% 互联网场景** |
| **Read-Through** | 最终一致 | - | 高 | 中 | ORM 缓存层 |
| **Write-Through** | 强一致 | 低 (双写) | 高 | 中 | 强一致要求 |
| **Write-Behind** | 最终一致 | **最高** | 高 | 高 | 高吞吐、可丢数据 |

## 二、Cache-Aside (旁路缓存)

### 2.1 模式概述

**Cache-Aside** 是最常用的缓存模式,**应用代码直接管理** cache 与 DB 的读写。

> 也叫 **Lazy Loading** (懒加载) 或 **Lookup Cache**。

### 2.2 读流程 (Read)

```text
应用代码读数据的标准流程:

┌────────┐
│  App   │
└────┬───┘
     │
     ├─ ① 查 Redis: GET key
     │       │
     │       ├─ 命中 (hit) → 直接返回 value
     │       │
     │       └─ 未命中 (miss) → 继续 ②
     │
     ├─ ② 查 MySQL: SELECT ... FROM table WHERE id = ?
     │       │
     │       └─ 返回数据 → 继续 ③
     │
     └─ ③ 回写 Redis: SETEX key ttl value
            │
            └─ 返回数据给用户
```

### 2.3 写流程 (Write)

```text
应用写数据有两种策略:

【策略 A: 先更新 DB,再删除缓存 (推荐)】
┌────────┐
│  App   │
└────┬───┘
     │
     ├─ ① 写 MySQL: UPDATE table SET ... WHERE id = ?
     │
     ├─ ② 删除 Redis: DEL key
     │
     └─ 返回写入成功

【策略 B: 先更新 DB,再更新缓存 (不推荐,易不一致)】
┌────────┐
│  App   │
└────┬───┘
     │
     ├─ ① 写 MySQL: UPDATE table SET ... WHERE id = ?
     │
     ├─ ② 更新 Redis: SET key value
     │
     └─ 返回写入成功 (但并发下易脏数据)
```

### 2.4 完整代码实现 (Java/Spring)

#### 读操作

```java
public Product getProduct(Long id) {
    String key = "product:" + id;

    // ① 查 Redis
    String json = redis.get(key);
    if (json != null) {
        return JsonUtil.parse(json, Product.class);  // 命中返回
    }

    // ② 查 DB
    Product p = productMapper.selectById(id);
    if (p == null) {
        return null;
    }

    // ③ 回写 Redis (设置 TTL)
    redis.setex(key, 3600, JsonUtil.toJson(p));

    return p;
}
```

#### 写操作 (Cache-Aside 标准做法)

```java
@Transactional
public void updateProduct(Product p) {
    // ① 写 DB
    productMapper.updateById(p);

    // ② 删除缓存 (不是更新!)
    redis.del("product:" + p.getId());
}
```

#### 复杂场景:组合读写

```java
// 列表查询 + 详情查询 各自缓存
public List<Product> listProducts(int page, int size) {
    String key = "product:list:" + page + ":" + size;
    String json = redis.get(key);
    if (json != null) return JsonUtil.parseList(json, Product.class);

    List<Product> list = productMapper.selectPage(page, size);
    redis.setex(key, 300, JsonUtil.toJson(list));  // 短 TTL
    return list;
}
```

### 2.5 优缺点

#### ✅ 优点

```text
1. 实现简单,业务可控
   - 缓存逻辑在应用代码层,清晰可见
   - 调试容易

2. 容错性强
   - Redis 挂了 → 降级到 MySQL,不影响可用性
   - DB 挂了 → 缓存仍可服务 (返回旧数据)

3. 数据最终一致
   - 通过 TTL 自动过期 → 强制重新加载最新数据
   - 即使双写不一致,TTL 兜底

4. 适用场景广
   - 读多写少 (电商商品、新闻、博客)
   - 不要求强一致
```

#### ❌ 缺点

```text
1. 首次读必然 miss (缓存预热问题)
   - 解决: 启动时批量加载热点数据

2. 写后读不一致 (短窗口)
   - 时刻 T: 写 DB → 还没删缓存
   - 时刻 T+1: 读 → 命中缓存 (旧值) ❌
   - 窗口通常 < 1ms,大多数业务可接受
   - 解决: 延迟双删 (详见后面)

3. 缓存击穿风险 (热点 key 过期瞬间)
   - 大量请求同时打到 DB
   - 解决: 互斥锁 / singleflight / 永不过期

4. 缓存穿透风险 (查询不存在的数据)
   - 每次都打到 DB
   - 解决: 布隆过滤器 / 缓存空值
```

### 2.6 双写不一致的经典问题 ⚠️

```text
【问题场景】: 先更新 DB,再更新缓存

T0: A 线程: UPDATE DB X = 1
T1: B 线程: UPDATE DB X = 2
T2: B 线程: SET Redis X = 2  ← 缓存更新为 2
T3: A 线程: SET Redis X = 1  ← 缓存被覆盖为 1 ❌

结果: DB 是 2,缓存是 1 → 不一致!
```

**解决: 先删除缓存,再更新 DB (但仍有窗口)**

```text
【问题场景】: 先删缓存,再更新 DB

T0: A 线程: DEL Redis
T1: B 线程: GET Redis → miss
T2: B 线程: SELECT DB → X = 1 (旧值)
T3: B 线程: SETEX Redis X = 1 ← 回写旧值
T4: A 线程: UPDATE DB X = 2

结果: DB 是 2,缓存是 1 → 不一致! ❌
```

**终极方案: 延迟双删**

```java
@Transactional
public void updateProduct(Product p) {
    // ① 先删缓存
    redis.del("product:" + p.getId());

    // ② 写 DB
    productMapper.updateById(p);

    // ③ 延迟再删一次 (防止 ② 期间的并发读把旧值回写)
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);  // 延迟 500ms (根据业务调整)
            redis.del("product:" + p.getId());
        } catch (Exception e) {
            log.error("延迟双删失败", e);
        }
    });
}
```

### 2.7 生产实现细节

```java
// 完整生产级 Cache-Aside 工具类
@Service
public class CacheAsideTemplate {

    @Autowired
    private StringRedisTemplate redis;

    @Autowired
    private RedisTemplate<String, Object> objectRedis;

    public <T> T getOrLoad(String key, Class<T> clazz,
                           Supplier<T> dbLoader,
                           long ttlSeconds) {
        // 1. 查缓存
        String json = redis.opsForValue().get(key);
        if (json != null) {
            // 反序列化 (NULL 字符串 → null)
            if ("__NULL__".equals(json)) return null;
            return JsonUtil.parse(json, clazz);
        }

        // 2. 查 DB
        T value = dbLoader.get();

        // 3. 回写 (含空值缓存)
        if (value == null) {
            redis.opsForValue().set(key, "__NULL__", 60);  // 空值短 TTL
        } else {
            objectRedis.opsForValue().set(key, value, ttlSeconds, TimeUnit.SECONDS);
        }

        return value;
    }

    public void evict(String key) {
        redis.delete(key);
    }
}
```

## 三、Read-Through / Write-Through (读写穿透)

### 3.1 模式概述

**Read-Through / Write-Through** 把缓存逻辑**封装在数据访问层**,应用**只与 Cache 交互**,由 Cache 抽象层负责与 DB 同步。

```text
┌─────────┐                ┌─────────┐                ┌────────┐
│   App   │ ──── read ──→ │  Cache  │ ── miss ────→  │   DB   │
│         │ ←── value ─── │  Layer  │ ←── value ───  │        │
│         │                └─────────┘                └────────┘
│         │
│  不知道 DB 的存在!
```

### 3.2 Read-Through 读流程

```text
应用调用 Cache.get(key):

   ┌────────┐
   │  App   │
   └────┬───┘
        ↓
   ┌────────────┐
   │ Cache Layer│
   └────┬───────┘
        ↓
   ┌────────────┐    命中    ┌────────────┐
   │ 查缓存     │ ────────→ │ 返回 value │
   └────┬───────┘            └────────────┘
        │ miss
        ↓
   ┌────────────┐
   │ 查 DB      │
   └────┬───────┘
        ↓
   ┌────────────┐
   │ 回写缓存   │
   └────┬───────┘
        ↓
   ┌────────────┐
   │ 返回 value │
   └────────────┘
```

### 3.3 Write-Through 写流程

```text
应用调用 Cache.put(key, value):

   ┌────────┐
   │  App   │
   └────┬───┘
        ↓
   ┌────────────┐
   │ Cache Layer│
   └────┬───────┘
        ↓
   ┌────────────┐    同步    ┌────────┐
   │ 写 DB      │ ────────→ │ MySQL  │
   └────┬───────┘            └────────┘
        ↓
   ┌────────────┐
   │ 写 Cache   │  ← 强一致: DB 和 Cache 都成功后才返回
   └────┬───────┘
        ↓
   ┌────────────┐
   │ 返回成功   │
   └────────────┘
```

### 3.4 实际实现: Spring Cache + Redis

**Read-Through + Write-Through** 经典实现是 **Spring Cache 抽象** + **Redis**。

#### 配置

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        // 配置序列化器
        RedisSerializer<Object> serializer = new GenericJackson2JsonRedisSerializer();

        // 配置不同 TTL
        Map<String, RedisCacheConfiguration> configMap = new HashMap<>();
        configMap.put("product", defaultConfig(serializer).entryTtl(Duration.ofHours(1)));
        configMap.put("user",    defaultConfig(serializer).entryTtl(Duration.ofHours(2)));
        configMap.put("session", defaultConfig(serializer).entryTtl(Duration.ofMinutes(30)));

        return RedisCacheManager.builder(factory)
                .cacheDefaults(defaultConfig(serializer))
                .withInitialCacheConfigurations(configMap)
                .build();
    }

    private RedisCacheConfiguration defaultConfig(RedisSerializer<?> s) {
        return RedisCacheConfiguration.defaultCacheConfig()
                .serializeValuesWith(RedisSerializationContext.SerializationPair.fromSerializer(s))
                .disableCachingNullValues();
    }
}
```

#### 使用

```java
@Service
public class ProductService {

    // Read-Through: 自动从缓存读,miss 则查 DB 并回写
    @Cacheable(value = "product", key = "#id")
    public Product getProduct(Long id) {
        System.out.println("查 DB");  // 仅在 cache miss 时执行
        return productMapper.selectById(id);
    }

    // Write-Through: 自动更新 DB 后,同时更新缓存
    @CachePut(value = "product", key = "#product.id")
    public Product updateProduct(Product product) {
        productMapper.updateById(product);
        return product;  // 返回的对象会写回缓存
    }

    // 主动失效缓存
    @CacheEvict(value = "product", key = "#id")
    public void deleteProduct(Long id) {
        productMapper.deleteById(id);
    }
}
```

### 3.5 优缺点

#### ✅ 优点

```text
1. 应用代码简单
   - 业务方法只关注业务逻辑
   - 不关心缓存细节 (注解驱动)

2. 缓存逻辑统一
   - 集中在 Cache Layer / AOP 切面
   - 便于统一调整策略

3. 一致性较好 (Write-Through)
   - 双写都成功才返回,DB 和 Cache 不会差异过大

4. 适合 ORM 场景
   - Hibernate 二级缓存、JPA Cacheable
   - 无需业务代码感知
```

#### ❌ 缺点

```text
1. 写性能较差 (Write-Through)
   - 每次写都要同时写 DB 和 Cache
   - 写延迟 = DB 写 + Cache 写
   - 高并发写场景瓶颈

2. 缓存层实现复杂
   - 需要 Cache Layer 框架或 AOP 切面
   - 增加调试难度

3. 写穿透问题 (Write-Through)
   - Cache 写失败 → DB 已写,不一致
   - 需要事务回滚机制,实现复杂

4. 强耦合 Cache 实现
   - 切换 Cache (Redis → Memcached) 需重写 Cache Layer
```

### 3.6 Write-Through 的数据不一致问题 ⚠️

```text
【Write-Through 一致性问题】

T0: App 调用 Cache.put(key, X=5)
T1: Cache Layer: BEGIN TX
T2: Cache Layer: UPDATE DB X=5 ✓
T3: Cache Layer: SET Redis X=5 ✗ ← 网络抖动,写 Redis 失败
T4: Cache Layer: ROLLBACK DB

结果:
   - DB X = 5 已写入 → 但 ROLLBACK 回退 (假设事务)
   - Redis X = 旧值 → 不一致

实际处理:
   - 先写 Cache,再写 DB (Write-Through 推荐顺序)
   - DB 失败 → Cache 也要回滚 (难)
```

## 四、Write-Behind (异步写回)

### 4.1 模式概述

**Write-Behind** (也叫 **Write-Back**) 写操作**只写缓存**就返回,DB 写入**异步批量**完成。

```text
┌────────┐
│  App   │
└────┬───┘
     │ 写
     ↓
┌────────┐   异步批量        ┌────────┐
│ Cache  │ ──────────────→ │   DB   │
│        │ (后台线程/消息队列)│        │
└────────┘                  └────────┘
   ↑
   │
  立即返回
```

### 4.2 写流程

```text
应用调用 Cache.put(key, value):

   ┌────────┐
   │  App   │
   └────┬───┘
        ↓
   ┌────────────┐
   │ 写 Cache   │ ← 同步,毫秒级返回
   └────┬───────┘
        ↓
   ┌────────────┐
   │ 返回成功   │ ← 用户感知不到 DB 写入
   └────────────┘

   ══════════════════════════════════════════
   ║    后台异步批量写 DB (延迟 0~秒级)          ║
   ══════════════════════════════════════════
        ↓
   ┌────────────┐
   │ 批量写 DB  │ ← 100 条/批,降低 IO 压力
   └────────────┘
```

### 4.3 读流程

```text
读与 Cache-Aside 类似:
   ① 查 Cache (大概率命中)
   ② miss 才查 DB
   ③ 回写 Cache
```

### 4.4 完整代码实现

#### 方案 1: 内存队列 + 异步线程

```java
@Service
public class WriteBehindCounterService {

    @Autowired
    private StringRedisTemplate redis;

    // 内存队列
    private final BlockingQueue<CountEvent> queue =
        new LinkedBlockingQueue<>(10000);

    @PostConstruct
    public void start() {
        // 后台线程:批量消费
        new Thread(this::flushLoop, "write-behind-flusher").start();
    }

    // 应用写入
    public void increment(Long userId) {
        // 1. 同步写 Redis
        redis.opsForValue().increment("counter:" + userId);

        // 2. 入队待异步写 DB
        queue.offer(new CountEvent(userId, Instant.now()));
    }

    // 后台异步刷新
    private void flushLoop() {
        List<CountEvent> batch = new ArrayList<>(100);
        while (true) {
            try {
                // 阻塞取一批
                queue.drainTo(batch, 100);
                if (!batch.isEmpty()) {
                    flushToDB(batch);
                    batch.clear();
                }
                Thread.sleep(1000);  // 1 秒一批
            } catch (Exception e) {
                log.error("write-behind flush error", e);
            }
        }
    }

    // 批量写 DB (用 INSERT ... ON DUPLICATE KEY UPDATE)
    private void flushToDB(List<CountEvent> batch) {
        // 合并同 userId 的事件 (求和)
        Map<Long, Long> merged = batch.stream()
            .collect(Collectors.groupingBy(
                CountEvent::getUserId,
                Collectors.counting()
            ));

        // 批量 UPSERT
        for (Map.Entry<Long, Long> e : merged.entrySet()) {
            counterMapper.increment(e.getKey(), e.getValue());
        }
    }
}
```

#### 方案 2: Redis Stream + 消费者写 DB

```java
// 应用写入
public void increment(Long userId) {
    String key = "counter:" + userId;
    redis.opsForValue().increment(key);
    // 同时写 Stream (供异步消费)
    redis.opsForStream().add("counter-stream",
        Map.of("user_id", userId.toString(), "ts", Instant.now().toString()));
}

// 消费者异步写 DB
@Scheduled(fixedRate = 5000)  // 每 5 秒
public void flushStreamToDB() {
    List<MapRecord<String, Object, Object>> records =
        redis.opsForStream().range("counter-stream",
            Range.closed("0", "+"));
    if (!records.isEmpty()) {
        flushToDB(records);
        redis.opsForStream().trim("counter-stream", records.size());
    }
}
```

#### 方案 3: Kafka 解耦 (高吞吐)

```java
@Service
public class WriteBehindService {

    @Autowired
    private KafkaTemplate<String, Event> kafka;

    @Autowired
    private StringRedisTemplate redis;

    public void increment(Long userId) {
        // 1. 同步写 Redis
        redis.opsForValue().increment("counter:" + userId);

        // 2. 发到 Kafka (消费者异步落库)
        kafka.send("counter-topic", new CountEvent(userId));
    }
}

@Component
public class CounterConsumer {

    @KafkaListener(topics = "counter-topic", batch = "true")
    public void consume(List<CountEvent> events) {
        // 批量写 DB
        countMapper.batchUpsert(events);
    }
}
```

### 4.5 优缺点

#### ✅ 优点

```text
1. 写性能极高 ⚡
   - 写只需更新缓存 (内存级)
   - 异步批量落库,IO 压力小
   - 适合高频写场景

2. 写吞吐高
   - 数据库压力降低 10-100 倍
   - 批量插入,DB 端也有优化

3. 抗突发流量
   - 缓存吸收流量尖峰
   - DB 平滑消费

4. 适合最终一致场景
   - 计数器、点赞、阅读量、浏览数
   - 日志聚合、消息缓冲
```

#### ❌ 缺点 ⚠️

```text
1. 数据丢失风险 (致命)
   - Cache 挂了 → 所有待写数据丢失
   - 应用崩溃 → 内存队列丢失
   - 必须有 WAL (Write-Ahead Log) 兜底

2. 数据不一致窗口
   - Cache 已更新,DB 还没更新 → 读到不一致
   - 查询时要么绕过 Cache (查 DB),要么接受旧数据

3. 实现复杂
   - 需要后台线程/消息队列
   - 需要失败重试、幂等保证

4. 难以排查问题
   - 数据不一致时,问题定位难

5. 事务支持弱
   - Cache 写成功 ≠ DB 写成功
   - 不能简单回滚
```

### 4.6 数据丢失问题的缓解

```text
方案 1: Cache 持久化
   - Redis 开启 AOF (appendfsync everysec)
   - 重启时从 AOF 恢复

方案 2: 双写 + 异步 (Hybrid)
   - 写 Cache 同时写一个持久队列 (Kafka / RocksDB)
   - 后台从队列消费写 DB
   - Cache 挂了,队列仍在

方案 3: 事务性 Outbox 模式
   - 写业务 DB 的同一事务,写一个 outbox 表
   - 后台进程从 outbox 读出来发到 MQ
   - MQ 消费者异步落库
   - (这是业界最稳妥的方案)
```

### 4.7 典型应用场景

| 场景 | 为什么用 Write-Behind |
|------|----------------------|
| **计数器** (PV/UV/点赞) | 写极频繁,丢几条可接受 |
| **消息队列缓冲** | 解耦生产/消费速度 |
| **日志聚合** | 高吞吐,可丢少量日志 |
| **会话数据** | 频繁更新,可容忍短暂丢失 |
| **推荐系统** | 评分实时写,批量训练 |
| **金融账户** ⚠️ | **一般不推荐**,但可用在缓存预扣 |

## 五、四种模式对比

### 5.1 综合对比表

| 维度 | Cache-Aside | Read-Through | Write-Through | Write-Behind |
|------|-------------|--------------|---------------|--------------|
| **读流程** | App 控制 cache+DB | Cache 抽象层 | Cache 抽象层 | App 控制 |
| **写流程** | App 控制 DB+Cache | N/A | Cache 抽象层双写 | 只写 Cache,异步写 DB |
| **代码侵入** | 中 (业务代码写缓存) | 低 (注解) | 低 (注解) | 中 (需后台线程) |
| **一致性** | 最终一致 | 最终一致 | 强一致 | 最终一致 |
| **写延迟** | 低 (DB 写即可) | N/A | 高 (双写) | **极低** |
| **读延迟** | 低 (命中时) | 低 (命中时) | 低 (命中时) | 低 (命中时) |
| **数据丢失风险** | 无 | 无 | 无 | **有** ⚠️ |
| **实现复杂度** | 低 | 中 | 中 | 高 |
| **代表框架** | 自实现 | Spring Cache | Spring Cache | 自实现 + Kafka |
| **典型场景** | **绝大多数业务** | ORM 二级缓存 | 强一致配置 | 计数器、日志 |

### 5.2 性能 vs 一致性二维图

```text
                  一致性强
                      ▲
                      │
   Write-Through ────┤  (强一致但慢)
                      │
   Cache-Aside ──────┤  (平衡,最常用)
                      │
   Read-Through ─────┤  (平衡,ORM 用)
                      │
                      │
   Write-Behind ─────┤  (高性能但可能丢数据)
                      │
                      ▼
                  一致性弱

   ← 高性能                低性能 →
```

### 5.3 一致性场景分级

```text
【强一致要求】: Write-Through
   - 银行账户余额
   - 支付订单状态
   - 库存扣减

【最终一致够用】: Cache-Aside / Read-Through
   - 商品详情
   - 用户资料
   - 文章内容
   - 配置信息

【可丢少量数据】: Write-Behind
   - 计数器 (PV/UV/点赞)
   - 日志
   - 浏览历史
   - 推荐评分
```

## 六、典型场景选型

### 6.1 电商商品详情

```text
场景: 用户浏览商品详情页
读写比: 1000:1 (读多写少)
一致性: 最终一致可接受

推荐: ✅ Cache-Aside
   - 商品详情缓存 1 小时
   - 商品变更时主动失效缓存
   - 缓存预热: 启动加载 top 1000 商品

代码:
   @Cacheable("product", key = "#id", unless = "#result == null")
   public Product getProduct(Long id) { ... }

   @CacheEvict("product", key = "#product.id")
   public Product updateProduct(Product product) { ... }
```

### 6.2 秒杀库存

```text
场景: 秒杀扣库存
读写比: 10000:1
一致性: 强一致 (不能超卖)

推荐: ✅ Write-Through + Redis Lua
   - Redis Lua 原子扣减 (不超卖)
   - Redis 扣成功后,异步同步到 MySQL (最终一致)
   - 利用 Write-Behind 思想: Redis 内存扣减 → 异步落库

   实际上, 严格不超卖场景会用:
   - Redis Lua 原子判断 + 扣减 (Redis 是权威)
   - 后台异步把 Redis 数据同步到 MySQL
   - MySQL 仅作为持久化备份,实时库存以 Redis 为准
```

### 6.3 文章阅读量

```text
场景: 每篇文章阅读量 +1
读写比: 100:1
一致性: 接受少量丢失 (一篇文章少几个阅读量无所谓)

推荐: ✅ Write-Behind
   - Redis INCR 阅读量 (同步)
   - 后台异步批量累加到 MySQL
   - 高峰期 10w+/s 阅读量也不会压垮 DB
```

### 6.4 用户 Session

```text
场景: 登录后保存 session
读写比: 1:1 (登录读一次,后续每次请求读)
一致性: 强一致 (用户状态不能错)

推荐: ✅ Write-Through (Redis 即权威)
   - 登录时写 Redis (TTL 30 分钟)
   - 续期时刷新 Redis TTL
   - 不需要 MySQL 持久化 session
```

### 6.5 用户资料

```text
场景: 用户头像/昵称/简介
读写比: 10:1
一致性: 读你所写即可 (用户改完昵称,自己刷新应看到)

推荐: ✅ Cache-Aside
   - 读时先查 Redis,miss 查 MySQL
   - 写 MySQL + 删除 Redis (让下次读回填)
   - 写后立即读 → 强制走 MySQL (Hint)
```

### 6.6 配置中心

```text
场景: 系统配置 (如功能开关、白名单)
读写比: 10000:1
一致性: 强一致 (配置变更立即生效)

推荐: ✅ Read-Through + 长 TTL
   - 配置缓存 24 小时
   - 用 Spring Cache @Cacheable
   - 配置变更发布时主动刷新缓存 (通过消息广播)
```

## 七、生产陷阱与最佳实践

### 7.1 三大经典陷阱

#### 陷阱 1: 双写不一致 (Cache-Aside)

```text
【场景】: A 改 X=1,B 改 X=2,并发写

A: UPDATE DB X=1 → DEL Redis
B: UPDATE DB X=2 → DEL Redis
A: SET Redis X=1 ← 旧值覆盖新值 ❌

【解决】: 延迟双删 / 分布式锁 / 写后读强制主库
```

#### 陷阱 2: 缓存击穿 (Cache-Aside)

```text
【场景】: 热点 key 过期瞬间,大量请求同时打到 DB

【解决】:
   - 互斥锁 (Mutex): 同一时刻只有一个线程查 DB
   - singleflight: Go 语言的合并请求模式
   - 逻辑过期: value 中带过期时间,异步刷新
   - 永不过期: 物理不过期,逻辑过期
```

#### 陷阱 3: 缓存雪崩 (Cache-Aside)

```text
【场景】: 大量 key 同时过期,请求全部打到 DB

【解决】:
   - 过期时间加随机值: TTL = 基础时间 + random(0, 300)
   - 多级缓存: 本地缓存 + Redis
   - 熔断降级: DB 压力大时,返回默认值
```

### 7.2 缓存设计 Checklist

```text
【key 设计】
□ key 命名规范: 业务:模块:ID (product:detail:1000)
□ 避免过长 key (浪费内存)
□ 用 Hash Tag 实现多 key 同 slot (Cluster)

【value 设计】
□ 选合适的序列化 (JSON/Protobuf/MessagePack)
□ 压缩大 value (gzip/zstd)
□ 不存敏感信息 (密码、身份证)

【TTL 设计】
□ 永远设置 TTL (避免内存泄漏)
□ 过期时间加随机值 (避免雪崩)
□ TTL 短于 DB 数据有效期

【更新策略】
□ Cache-Aside 用 Delete 而非 Update
□ 写后读强制主库 (避免延迟读)
□ 监控命中率 (90%+ 为健康)

【容错】
□ 缓存挂了 → 降级到 DB
□ DB 挂了 → 缓存可继续读 (返回旧值)
□ 监控 cache miss rate 突增 (DB 故障先兆)
```

### 7.3 监控指标

```text
必备监控:
   1. 命中率 = hit / (hit + miss)        → 目标 > 90%
   2. 平均延迟 (Redis + DB)
   3. 慢查询 (Redis slowlog, DB slow query)
   4. 内存使用 (Redis used_memory)
   5. 网络流量 (in/out kbps)

告警:
   - 命中率突降 → DB 压力上升
   - Redis 连接数耗尽
   - 单 key 大小异常 (大 key)
   - 缓存预热失败
```

### 7.4 选型决策树

```text
开始
  │
  ├─ Q: 需要强一致?
  │     │
  │     ├─ 是 → Write-Through (或 Redis Lua 原子操作)
  │     │
  │     └─ 否 → Q: 写多读少?
  │             │
  │             ├─ 是 (写极频繁) → Write-Behind (计数器/日志)
  │             │
  │             └─ 否 → 读多写少 → Q: 业务代码与缓存耦合度?
  │                       │
  │                       ├─ 想要低耦合 → Read-Through (Spring Cache)
  │                       │
  │                       └─ 可以接受业务写缓存 → Cache-Aside (最常用) ✅
```

## 核心要点速记

### Cache-Aside (推荐 80% 场景)

- **读**: 查 Cache → miss → 查 DB → 回写 Cache
- **写**: 写 DB → **删 Cache** (不是更新)
- **优点**: 简单、容错强、最终一致
- **缺点**: 首次 miss 必穿透、双写不一致窗口、击穿风险
- **解决**: 延迟双删、互斥锁、布隆过滤器、TTL 加随机值
- **代表**: 90% 互联网业务 (商品、用户、文章)

### Read-Through / Write-Through

- **Read**: App → Cache (miss 自动查 DB 并回填)
- **Write**: App → Cache (同步写 DB + Cache,都成功才返回)
- **优点**: 应用代码简单、一致性好 (Write-Through)
- **缺点**: 写延迟高、Cache 层复杂
- **代表**: Spring Cache @Cacheable、ORM 二级缓存
- **强一致场景**: Write-Through 用于配置中心、银行余额

### Write-Behind (异步写回)

- **写**: App → Cache → 立即返回 → **异步批量**写 DB
- **优点**: 写性能极高、抗突发流量
- **缺点**: 数据丢失风险 ⚠️、一致性窗口、实现复杂
- **代表**: 计数器 (PV/UV/点赞)、日志聚合、Kafka 缓冲
- **缓解**: Redis AOF 持久化、Kafka outbox、idempotent consumer

### 决策速记

```text
强一致 → Write-Through
读多写少、最终一致 → Cache-Aside (首选) ✅
ORM 二级缓存 → Read-Through
高频写、可丢少量 → Write-Behind
```

### 三大陷阱

```text
1. 双写不一致 → 延迟双删 + 互斥锁
2. 缓存击穿 → mutex / singleflight / 永不过期
3. 缓存雪崩 → TTL 加随机值 + 多级缓存 + 熔断
```
