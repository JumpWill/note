# Kafka 常见问题排查 (Troubleshooting)

> 适用版本:Kafka 3.5+(KRaft GA)、3.6+(KIP-848)、3.7+。ZK 模式内容保留兼容说明。
> 阅读建议:按目录定位场景,先看"排查流程图"再下钻细节。

## 一、故障排查思路总览

### 1. 分层定位原则

```text
┌──────────────────────────────────────────────────────────────┐
│  Layer 1  业务应用层   生产者/消费者代码?序列化?分区策略?     │
│     ↓                                                        │
│  Layer 2  客户端层     Producer/Consumer 配置?版本兼容?     │
│     ↓                                                        │
│  Layer 3  Broker 层    Controller/Broker/Topic 状态?       │
│     ↓                                                        │
│  Layer 4  KRaft/ZK 层  元数据一致性?Controller 选举?       │
│     ↓                                                        │
│  Layer 5  操作系统层   CPU/内存/磁盘IO/网络?FD/Page Cache? │
│     ↓                                                        │
│  Layer 6  硬件层       磁盘/网卡/交换机的健康?              │
└──────────────────────────────────────────────────────────────┘
```

**黄金法则**:**先确认现象(报错、监控、消费延迟)→ 再分层下钻 → 优先查配置和日志,最后查代码逻辑**。80% 的问题通过日志+配置就能定位。

### 2. 通用排查流程

| 步骤 | 动作                          | 工具/命令                                                |
|------|-------------------------------|-----------------------------------------------------------|
| 1    | 确认现象(报错、Lag、监控告警)| Kafka 日志、应用日志、Prometheus 指标、JMX               |
| 2    | 收集现场(进程、Topic、Group)| `jps`、`kafka-broker-api-versions.sh`、`kafka-topics.sh` |
| 3    | 缩小范围(客户端/Broker/OS)  | `top`、`iostat`、`sar`、`jstat`                          |
| 4    | 定位根因                      | Controller 日志、Broker 日志、`kafka-consumer-groups.sh`  |
| 5    | 修复 + 验证 + 归档            | 滚动重启、回滚预案、RCA 报告                              |

### 3. 必备诊断命令速查

```bash
# 进程
jps -l                           # 查找 Kafka 进程(KafkaMain, ControllerMain)
ps -ef | grep -i kafka

# 端口
ss -tlnp | grep -E '9092|9093|9094'   # PLAINTEXT/SSL/Controller

# 日志
tail -f logs/kafkaServer.log            # KRaft Broker
tail -f logs/controller.log             # KRaft Controller 节点
tail -f logs/kafka-request.log          # 请求日志
grep -E 'ERROR|WARN' logs/*.log | tail -100

# Topic / Partition
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --topic orders --describe
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --all-groups --describe

# Controller
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 \
  describe --status
```

## 二、启动失败类问题

### 1. KRaft 集群无法启动

**现象**:`KafkaServer` 启动后立刻退出,日志报 `No `meta.properties` found`、`Unable to read controller quorum`、`InvalidClusterIdException`。

**可能原因**:

| 原因                                              | 排查                                                      |
|---------------------------------------------------|-----------------------------------------------------------|
| `meta.properties` 缺失或损坏                       | `ls -la data_dir/__cluster_metadata-0/` 目录是否存在     |
| `cluster.id` 不一致(Broker 和 Controller 不一致) | 对比所有节点的 `meta.properties` 文件                     |
| `controller.quorum.voters` 配置错误                | 必须包含奇数个 Controller,格式 `id@host:port`            |
| `process.roles` 配置冲突(同时为 broker+controller) | 角色职责分离,或明确接受混合模式                           |
| 第一次启动未自动生成元数据                         | KRaft 首次启动需初始化(自动生成 cluster.id)             |

**排查步骤**:

```bash
# 1. 看启动日志
grep -E 'Cluster ID|FATAL|ERROR' logs/kafkaServer.log | tail -50

# 2. 检查 meta.properties
cat data_dir/__cluster_metadata-0/meta.properties
# 正确示例:
# cluster.id=5L6g3nShT-eCq8HtC6qEtA
# node.id=1

# 3. 检查所有节点 cluster.id 是否一致
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "cat /data/kafka/__cluster_metadata-0/meta.properties | grep cluster.id"
done

# 4. 检查 quorum voters
grep -A2 "controller.quorum.voters" config/kraft/server.properties

# 5. 元数据 quorum 状态
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

**解决方案**:

```bash
# A) cluster.id 不一致 - 重新格式化(慎用,会清空元数据)
# 停所有节点后:
rm -rf data_dir/__cluster_metadata-0/
bin/kafka-storage.sh format -t <cluster-id> -c config/kraft/server.properties

# B) 修复 controller.quorum.voters
# 必须是奇数,如 3 或 5
controller.quorum.voters=1@node1:9093,2@node2:9093,3@node3:9093

# C) 如果是 Broker 和 Controller 集群不一致
# 分别格式化两个集群,使用不同 data.dir
```

**预防**:`process.roles=broker,controller`(混合模式需充分评估)、统一自动化配置管理(Ansible/SaltStack)、cluster.id 生成后备份。

### 2. 元数据损坏恢复

**现象**:Broker 启动报 `CorruptIndexException`、`IndexOutOfBoundsException`,Consumer 报 `UNKNOWN_TOPIC_OR_PARTITION`。

**可能原因**:

- 磁盘故障导致 `__cluster_metadata-0/0.log` 文件损坏
- 非正常关机(直接 kill -9、断电)导致日志未刷盘
- `meta.properties` 文件被人为误删

**排查步骤**:

```bash
# 1. 查看元数据目录
ls -la data_dir/__cluster_metadata-0/

# 2. 看 Broker 日志具体错误
grep -i "corrupt\|index out of bounds" logs/kafkaServer.log

# 3. 检查磁盘
df -h data_dir
dmesg | grep -i "i/o error"
```

**解决方案**:

```bash
# 方案 1:从备份恢复元数据(推荐,需提前备份)
cp -r backup/__cluster_metadata-0/* data_dir/__cluster_metadata-0/

# 方案 2:重置元数据(危险,会丢失所有 topic 配置)
# 仅在所有 Controller 节点都损坏且无备份时使用
rm -rf data_dir/__cluster_metadata-0/
bin/kafka-storage.sh format -t $(kafka-storage.sh random-uuid) \
  -c config/kraft/server.properties

# 方案 3:从快照恢复
# KRaft 默认每 N 条记录生成快照
ls data_dir/__cluster_metadata-0/*.snapshot
# 选择最近一个有效快照
```

**预防**:定期备份 `__cluster_metadata-0/` 目录、`log.flush.interval.messages=1`(折中吞吐与安全)、UPS 保护、监控 `__consumer_offsets` 健康。

### 3. 端口冲突

**现象**:`Address already in use: bind`、`java.net.BindException`。

**可能原因**:

| 端口用途       | 默认 | 冲突常见原因                                      |
|----------------|------|---------------------------------------------------|
| PLAINTEXT      | 9092 | 多个 Broker 同机未分散 / 残留进程                 |
| SSL             | 9093 | 同上                                              |
| Controller      | 9094 | KRaft 集群端口冲突 / 与历史 ZooKeeper 端口重叠  |
| JMX             | 9999 | 监控端口冲突                                      |

**排查步骤**:

```bash
# 1. 看谁占用
ss -tlnp | grep -E '9092|9093|9094'
lsof -i :9092

# 2. 看 Kafka 进程
jps -l
ps -ef | grep -i kafka

# 3. 看 Broker 配置
grep -E "listeners=|controller\.listener|inter\.broker" config/server.properties

# 4. 残留进程(异常崩溃后)
pgrep -f kafka.Kafka | xargs -r kill -9
```

**解决方案**:

```bash
# A) 修改端口
listeners=PLAINTEXT://0.0.0.0:9192,CONTROLLER://0.0.0.0:9194
controller.quorum.voters=1@node1:9194,2@node2:9194,3@node3:9194

# B) 杀掉残留进程
pkill -9 -f kafka.Kafka
sleep 3
ps -ef | grep -i kafka  # 确认无残留

# C) 多 Broker 同机必须分端口
# node1:9092, node2:9092 物理隔离即可;但若同 IP 同机,需 port increment
```

### 4. 配置文件错误

**现象**:启动报 `Invalid config`、`Unknown configuration`、`KafkaConfigException`。

**常见错误**:

```bash
# 错误 1:配置项不存在或拼写错(版本升级后)
# 例:log.cleanup.policy (应为 log.cleanup.policy)
# 例:offset.topic.replication.factor (默认是 3,但 KRaft 推荐 1)

# 错误 2:动态配置错误(alter-topic / alter-broker)
# Kafka 3.x 大量配置已支持动态修改,无需重启

# 错误 3:配置项类型错误
# 例:num.partitions=abc (应为整数)

# 错误 4:ZK 模式配置写到 KRaft
# 例 KRaft 中不能配:zookeeper.connect
```

**排查步骤**:

```bash
# 1. 启动前台模式,直接看报错
bin/kafka-server-start.sh config/kraft/server.properties

# 2. 验证配置文件
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type brokers --entity-name 1

# 3. 对比参考配置
diff config/kraft/server.properties \
     config/kraft/server.properties.template
```

**解决方案**:

```ini
# 关键 KRaft 配置参考
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@node1:9093,2@node2:9093,3@node3:9093
listeners=PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
advertised.listeners=PLAINTEXT://node1:9092
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
listener.security.protocol.map=PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT
log.dirs=/data1/kafka,/data2/kafka  # 多盘
num.partitions=3
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
```

## 三、生产端问题

### 1. 消息丢失(acks=0、retries=0)

**现象**:生产者 `send()` 返回成功,但消费端查不到消息;监控显示"发送量 100W,消费 95W"。

**可能原因**:

| 配置                              | 风险                                                              |
|-----------------------------------|-------------------------------------------------------------------|
| `acks=0`                          | 不等 Broker 确认,网络抖动即丢失                                  |
| `acks=1`                          | 仅 Leader 确认,Leader 写盘前崩溃即丢失                            |
| `acks=all` + `retries=0`          | 不重试,瞬时错误直接失败                                          |
| `enable.idempotence=false`        | 无幂等,重试导致重复 + 部分丢失                                    |
| `max.in.flight.requests.per.connection > 5` | 幂等开启时不能超 5(0.11.0+ 后)                          |

**排查步骤**:

```bash
# 1. 查看生产者配置
grep -E "acks=|retries=|enable.idempotence|max.in.flight" \
  /opt/app/conf/producer.properties

# 2. 应用代码确认发送回调
# KafkaProducer.send() 返回 Future,要 get() 或 callback 处理失败

# 3. Broker 端 ack 时延
bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092

# 4. 抓包验证网络(高级)
tcpdump -i eth0 'port 9092' -w /tmp/kafka.pcap
```

**解决方案**(生产推荐配置):

```properties
# producer.properties
bootstrap.servers=node1:9092,node2:9092,node3:9092

# 关键三件套
acks=all                          # 等所有 ISR 确认
retries=2147483647                # 无限重试(Integer.MAX_VALUE)
enable.idempotence=true           # 幂等(依赖 acks=all + retries>0)
max.in.flight.requests.per.connection=5  # 幂等模式下 ≤5

# 配套
delivery.timeout.ms=120000        # 总超时(含重试)
request.timeout.ms=30000          # 单次 RPC 超时
compression.type=lz4              # 压缩
linger.ms=10                       # 批量
batch.size=32768
```

**Java 代码示例**:

```java
Properties props = new Properties();
props.put("bootstrap.servers", "node1:9092,node2:9092,node3:9092");
props.put("acks", "all");
props.put("retries", Integer.MAX_VALUE);
props.put("enable.idempotence", true);
props.put("max.in.flight.requests.per.connection", 5);
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());

// 同步发送(简单可靠)
RecordMetadata meta = producer.send(record).get();
// 异步 + 回调
producer.send(record, (m, e) -> {
    if (e != null) {
        log.error("send failed", e);
        // 落库/重试/告警
    }
});
```

### 2. 消息重复(无幂等性)

**现象**:同一条业务消息被处理两次(如订单被扣款两次)。

**可能原因**:

- 生产者发送失败重试 + 服务端已写入(无幂等)
- 消费端先消费后 commit,提交失败后再次消费
- 再均衡 (Rebalance) 时未完成的消息被重新分配

**解决方案**:

```java
// 生产端:开启幂等 + 事务
props.put("enable.idempotence", true);   // 单分区幂等
// 或
props.put("transactional.id", "tx-pid-1");  // 跨分区幂等(事务)

producer.initTransactions();
producer.beginTransaction();
try {
    producer.send(record1);
    producer.send(record2);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}

// 消费端:业务幂等(去重表 / 唯一键)
consumer.poll(...);
for (ConsumerRecord<String, String> r : records) {
    String key = r.key();  // 业务唯一键
    if (dedupService.isProcessed(key)) {
        continue;
    }
    process(r.value());
    dedupService.markProcessed(key);
    consumer.commitSync();  // 处理完再提交
}
```

### 3. 消息乱序

**现象**:同一订单的"创建"、"支付"、"发货"消息顺序错乱。

**根因**:

```text
┌──────────────────────────────────────────────────────┐
│ 默认配置:max.in.flight.requests.per.connection=5     │
│                                                       │
│ 生产者发送 msg1,msg2,msg3                              │
│                                                       │
│ msg1 ───→ Broker                                     │
│ msg2 ───→ Broker (网络延迟先到)                       │
│ msg3 ───→ Broker                                     │
│                                                       │
│ 写入顺序:msg2,msg3,msg1 → 乱序!                       │
│                                                       │
│ 幂等开启时,Kafka 会按 PID+Sequence 排序后写入,      │
│ 但 max.in.flight > 5 后排序失效                       │
└──────────────────────────────────────────────────────┘
```

**解决方案**:

| 方案                            | 说明                                                                |
|---------------------------------|---------------------------------------------------------------------|
| `max.in.flight.requests.per.connection=1` | 最强保序,但吞吐下降到 1/5                                          |
| 单分区保序                      | 把同业务消息 hash 到同一分区(`key=userId`),全局保证同 key 有序       |
| `enable.idempotence=true` + `max.in.flight ≤ 5` | 多数场景足够,Kafka 自动按 sequence 排序                            |
| 应用层加 sequence 字段          | 兜底,消费端按 seq 排序                                              |

```properties
# 生产者推荐
enable.idempotence=true
max.in.flight.requests.per.connection=5
# 若业务强保序要求:
max.in.flight.requests.per.connection=1
```

### 4. 发送延迟高

**现象**:`record.latency` P99 > 100ms。

**排查流程**:

```bash
# 1. 看生产端指标(应用层)
# Metrics: record-send-rate, request-latency-avg, batch-size-avg

# 2. 看 Broker 端指标
bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092
# 通过 JMX
jconsole <broker-pid>
# 或
echo "get -b kafka.server:type=BrokerTopicMetrics,name=TotalProduceRequestsPerSec" | \
  nc localhost 9999

# 3. 网络
mtr node1
iperf3 -c node1 -p 9092

# 4. 磁盘
iostat -x 1
# 关注:await、%util、w/s
```

**根因与方案**:

| 根因                  | 排查                                          | 方案                                                  |
|-----------------------|-----------------------------------------------|-------------------------------------------------------|
| 批量配置不合理        | `linger.ms=0`                                 | `linger.ms=10~50`,`batch.size=64KB+`                  |
| 压缩 CPU 瓶颈        | `compression.type=zstd`                       | 改 `lz4`,或加大 `linger.ms`                          |
| 网络 RTT 高           | `mtr` 看出跨机柜                              | 同机柜就近部署 / `client.dns.lookup=use_all_dns_ips`  |
| Broker Page Cache 不足| `free -m`,`vmstat 1`                          | 加大内存,`num.io.threads` 调优                         |
| ISR 收缩/副本同步慢   | `kafka-topics.sh --describe` 看 `isr`         | `replica.lag.time.max.ms` 调整,排查慢 Follower        |
| GC 停顿               | GC log                                        | 调 `KAFKA_HEAP_OPTS=-Xmx6g`,改 G1GC                  |

## 四、消费端问题

### 1. 消费者 Lag 持续增长

**现象**:`kafka-consumer-groups.sh` 显示 `LAG` 列持续增大,业务消息积压。

**排查流程**:

```bash
# 1. 看 lag
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer
# 输出:
# GROUP           TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-consumer  orders   0          10000           15000           5000
# order-consumer  orders   1          12000           15000           3000

# 2. 看消费者实例数与分配
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer --members --verbose

# 3. 看 broker 端积压
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --all-groups --describe | awk '{print $6}' | sort -nr | head

# 4. 看 Topic 健康度
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --topic orders --describe
# 看 partitions、isr、replicas
```

**Lag 增长流程图**:

```text
            [Lag 告警]
                │
        ┌───────┼───────┐
        ↓       ↓       ↓
   生产太快?  消费太慢? Broker 慢?
        │       │       │
        ↓       ↓       ↓
   Topic 分区  单实例  ISR 收缩?
   数不足?     处理慢? GC/磁盘?
        │       │       │
        └───────┼───────┘
                ↓
        ┌───────┼───────┐
        ↓       ↓       ↓
   加分区  扩容实例  调 GC/磁盘
```

**解决方案**:

| 场景              | 方案                                                                 |
|-------------------|----------------------------------------------------------------------|
| 生产太快          | 增加 Topic 分区(单分区并行度上限 = 1 消费者实例)                     |
| 单实例慢          | 水平扩容消费者实例(注意:实例数 ≤ 分区数)                              |
| 处理逻辑慢        | 异步化、批量处理、外部 IO 异步化                                       |
| Broker 慢         | 排查 GC、磁盘 IO(`iostat -x 1`)、`num.io.threads`                    |
| 业务逻辑抛异常     | 看应用日志,死循环?N+1 查询?外部接口慢?                              |
| 反压(下游写慢)   | 限流、上游降级、增加下游并行                                          |

**关键配置**:

```properties
# 消费者提升吞吐
max.poll.records=500            # 单次 poll 拉取量
fetch.min.bytes=1               # 至少 1 字节就返回(低延迟)
fetch.max.wait.ms=500           # 长轮询等待
max.partition.fetch.bytes=1048576  # 单分区 1MB
session.timeout.ms=45000        # 心跳超时
heartbeat.interval.ms=15000     # 心跳间隔(1/3 session.timeout)
```

### 2. 重复消费

**现象**:同一条消息被处理多次。

**根因分析**:

```text
┌─────────────────────────────────────────────────────────────┐
│ 场景 1:先 commit 后处理                                       │
│   poll → commitSync() → 处理逻辑报错 → 重启后重新消费       │
│   风险:业务漏处理 ✗                                          │
│                                                              │
│ 场景 2:先处理后 commit,但 commit 失败                         │
│   poll → 处理逻辑 → commitSync() 抛异常 → 下次 poll 再消费   │
│   风险:业务重复处理 ✓ (本次主题)                              │
│                                                              │
│ 场景 3:Rebalance 时未 commit                                 │
│   poll → 处理中 → 触发 Rebalance → 消息重新分配给其他实例    │
│   风险:重复消费(未 commit 的 offset 重置)                    │
└─────────────────────────────────────────────────────────────┘
```

**解决方案**:

```java
// 推荐:手动 commit + 业务幂等
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
    
    for (ConsumerRecord<String, String> record : records) {
        try {
            // 1. 业务幂等处理
            processWithIdempotent(record);
            
            // 2. 记录待提交 offset (下一条)
            commitMap.put(
                new TopicPartition(record.topic(), record.partition()),
                new OffsetAndMetadata(record.offset() + 1)
            );
        } catch (Exception e) {
            log.error("process failed, offset={}", record.offset(), e);
            // 不提交,下次重新消费;但要做幂等
        }
    }
    
    // 3. 批量 commit(降低 RPC)
    if (!commitMap.isEmpty()) {
        consumer.commitSync(commitMap);
    }
}
```

**关键点**:
- `enable.auto.commit=false` 手动控制
- 业务层幂等(去重表/Redis SET/DB unique key)
- 处理成功后再 commit
- Rebalance 时用 `ConsumerRebalanceListener` 优雅处理

### 3. 消息丢失(手动 commit + 自动 commit 配合不当)

**场景**:`enable.auto.commit=true` + 应用先 commit 后处理 → 消息丢失。

**示例**:

```java
// 危险代码 ❌
props.put("enable.auto.commit", "true");
consumer.poll(Duration.ofMillis(500));
// 此时已经触发自动 commit(默认 5 秒)
process(records);  // 假设处理耗时 10 秒,中间崩溃
// 再次启动,offset 已 commit,消息丢失
```

**解决方案**:

```java
// 方案 A:全手动
props.put("enable.auto.commit", "false");
// 处理后再 commitSync

// 方案 B:延后自动 commit
props.put("enable.auto.commit", "true");
props.put("auto.commit.interval.ms", "5000");
// 但确保处理时间 < 5 秒;不推荐用于关键业务

// 方案 C:auto-commit + 处理结果异步处理
// 同 A,推荐
```

### 4. Rebalance 频繁

**现象**:日志频繁出现 `Successfully joined group` / `Revoking assignment`,消费 lag 抖动。

**根因排查**:

```bash
# 1. 看 consumer 日志
grep -E "rebalance|rejoin|revoking" logs/consumer.log

# 2. 看 GC 时间(超过 session.timeout 触发 rebalance)
jstat -gcutil <consumer-pid> 1s

# 3. 看 poll 间隔
# 应用长时间不 poll,也会被踢出
```

**常见原因**:

| 原因                            | 表现                              | 解决                                                  |
|---------------------------------|-----------------------------------|-------------------------------------------------------|
| `max.poll.interval.ms` 太短     | 单次 poll 处理慢被踢出            | `max.poll.interval.ms=300000`(5 分钟)                |
| 处理逻辑慢(外部 IO/DB)          | 处理时间 > max.poll.interval       | 异步化、增加 max.poll.interval                        |
| `session.timeout.ms` 太短       | 心跳超时被踢                      | 调整到 10-60 秒                                       |
| GC 停顿长                       | `jstat` 看到 Full GC 几秒到十几秒 | 调 JVM 参数、排查内存泄漏                              |
| 网络抖动                        | 心跳包丢失                        | 调高 session.timeout,或排查网络                        |
| 消费者实例频繁重启              | 部署问题                          | 容器化时调整 readinessProbe                          |

**参数推荐**:

```properties
# 平衡延迟和稳定性
session.timeout.ms=45000          # 45 秒
heartbeat.interval.ms=15000       # 15 秒(session/3)
max.poll.interval.ms=300000       # 5 分钟
max.poll.records=200              # 单次 poll 适量
```

**Rebalance Listener**:

```java
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // 在 rebalance 前 commit 当前 offset
        consumer.commitSync(currentOffsets);
        // 关闭外部连接/flush 缓存
    }
    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // 重置 offset / 恢复连接
    }
});
```

### 5. OOM(max.poll.records 过大)

**现象**:消费者进程 `OutOfMemoryError`,重启后又 OOM。

**根因**:`max.poll.records=10000` + 单条消息大 + 内存累积处理 = 内存爆炸。

**排查**:

```bash
# 1. 看堆内存
jstat -gc <consumer-pid> 1s
# 看 OGC/PGC 增长

# 2. 拉取消息大小
bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
  --describe --topic orders
# 看 logSize

# 3. GC 日志
grep -E "Full GC|gc pause" gc.log
```

**解决方案**:

```properties
# 关键:限制每次拉取量
max.poll.records=100              # 默认 500,根据消息大小调
fetch.max.bytes=52428800          # 50MB
max.partition.fetch.bytes=1048576 # 单分区 1MB
```

```java
// 消费者内部及时释放
List<ConsumerRecord<String, byte[]>> records = consumer.poll(...).records();
processInBatch(records);
records.clear();  // 显式帮助 GC
```

### 1. 副本滞后(ISR 收缩)

```bash

# 输出示例:
# Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2
#                            ↑                            ↑   ↑
#                          Leader                     完整副本  当前 ISR(少 3)
```

**根因排查**:

```bash
# 1. 看 Follower 状态

```

**常见根因**:

| 根因                        | 排查                                  | 解决                                  |
|-----------------------------|---------------------------------------|---------------------------------------|
| Follower 磁盘慢            | `iostat -x`,`%util > 80%`             | 换 SSD/加盘/`num.replica.fetchers`    |
| Follower GC 停顿            | GC log                                | JVM 调优                              |
| 网络抖动(同 Follower)      | `mtr node2`                           | 网络/交换机排查                       |

```bash

  --entity-type brokers --entity-default \
  --alter --add-config replica.lag.time.max.ms=60000

replica.lag.time.max.ms=60000
```

**根本解决**:扩容磁盘、升级 SSD、拆分区、`num.replica.fetchers=4`(并发拉取)。

### 3. 磁盘写满

**现象**:Broker 报 `Log dir ... is full`,Producer 报 `RecordTooLargeException` 或写入失败。

**排查**:

```bash
# 1. 看磁盘
df -h /data1 /data2

bin/kafka-configs.sh --bootstrap-server localhost:9092 \

# 3. 看哪些 topic 占空间最大
bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
```

| 方案                          | 命令/配置                                          |
|-------------------------------|----------------------------------------------------|
| 立即清理旧数据                | 调小 `log.retention.hours` 动态生效               |

| 启用压缩                      | `log.cleanup.policy=compact`                       |
| 增加 Topic 分区,横向扩展     | 单盘 IO 总是瓶颈                                   |

```bash
bin/kafka-configs.sh --bootstrap-server localhost:9092 \

  --entity-type clients --entity-name clientA \
  --alter --add-config producer_byte_rate=10485760  # 10MB/s
```

**预防**:`log.retention.hours=168`(7 天)、监控磁盘使用率 > 70% 告警、Page Cache 充足(`vmstat 1` 看 `bi/bo`)。

### 4. 磁盘 IO 高

**排查**:

```bash

# 关注:

#   rkB/s, wkB/s   读写带宽
```

**根因**:

| 场景             | 排查                                          | 方案                                  |
|------------------|-----------------------------------------------|---------------------------------------|

## 九、性能问题

### 1. Broker 频繁 GC

**现象**:GC 日志显示 Full GC 频繁,Broker 响应慢,Producer 重试增加。

**排查**:

```bash
# 1. GC 统计
jstat -gcutil <broker-pid> 1s
# FGC 次数快速增长、FGCT 单次 > 1s 是危险信号

# 2. GC 日志(启动参数已开启)
grep "Full GC\|pause" gc.log | tail

# 3. 堆内存分布
jmap -heap <broker-pid>
jmap -histo:live <broker-pid> | head -20
```

**典型参数**:

```bash
# 推荐 G1GC(Java 11+ 默认)
KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
# 或 CMS(老版本)
KAFKA_HEAP_OPTS="-Xms6g -Xmx6g -XX:+UseG1GC -XX:MaxGCPauseMillis=20"
```

**调优**:

```properties
# 关键:
log.flush.interval.messages=10000    # 不要太小
log.segment.bytes=1073741824          # 1GB,减少文件描述符
num.replica.fetchers=4                # 副本拉取并发
```

### 2. Page Cache 不足

**现象**:磁盘读 IO 高(本应该是顺序写为主),`vmstat` 显示 `bo` 远大于 `bi`。

**排查**:

```bash
free -h
# 看 cached 列
vmstat 1
# bi/bo:bo 应 >> bi(顺序写),若 bi 大则 Page Cache 不足
```

**解决方案**:

- 加大内存:`Xmx` 不要超过物理内存 50%(OS 也要用 Page Cache)
- SSD 替换 HDD(IOPS 提升)
- 多盘分摊:`log.dirs=/data1,/data2,/data3`

### 3. 网络带宽打满

**现象**:`sar -n DEV 1` 显示网卡带宽接近上限,生产/消费延迟高。

**排查**:

```bash
sar -n DEV 1
# 看 rxkB/s, txkB/s
iftop -i eth0  # 看哪个连接占带宽
```

**解决方案**:

```properties
# 1. 限流
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type clients --entity-name app \
  --alter --add-config producer_byte_rate=52428800  # 50MB/s

# 2. 压缩
compression.type=lz4  # 或 zstd(更高压缩率)

# 3. 批量
linger.ms=50
batch.size=131072  # 128KB

# 4. 加大网卡 / 10GbE / 多网卡 bond
```

```java
// 业务幂等方案对比
方案 1:数据库唯一索引(强一致)
```

### 2. 消息顺序错乱

**详细方案见第三章第三节**,本节给出业务兜底:

```java
// 方案:消息带 sequence,业务层排序(适合非实时场景)
class Message {
    long seq;
    Object data;
}

// 缓冲区排序 + 批量处理
PriorityQueue<Message> buffer = new PriorityQueue<>(Comparator.comparingLong(m -> m.seq));
while (running) {
    for (ConsumerRecord<String, String> r : consumer.poll(...)) {
        buffer.add(parse(r.value()));
    }
    while (!buffer.isEmpty() && buffer.peek().seq == expectedSeq) {
        process(buffer.poll().data);
        expectedSeq++;
    }
}
```

## 十三、实战案例

### 案例 1:电商大促当晚 Lag 暴增

**时间**:2025-11-11 20:00,双十一开场 30 分钟。

**现象**:
- 订单消费者 Lag 从 1000 飙升到 200 万
- 应用日志出现大量 `CommitFailedException`
- Broker 监控显示 GC 频繁,磁盘 IO 90%+

**排查过程**:

```bash
# 1. 看 Lag
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer | head
# LAG: 100, 2000000, 3000000...

# 2. 看消费者实例
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer --members
# 只有 2 个实例(正常 4 个)

# 3. 看应用日志
grep "OOM\|kafka.consumer" /var/log/app.log | tail
# OOMKilled 出现 2 次

# 4. 看 Broker 状态
ssh broker1 "iostat -x 1"
# %util 95%, await 50ms
```

**根因**:
1. 单条订单消息从平均 5KB 涨到 50KB(包含促销优惠明细)
2. `max.poll.records=2000` × 50KB = 100MB,2 次 OOM
3. 消费者实例被 OOMKilled,Kubernetes 自动拉起但处理慢

**解决**:
1. 紧急:`max.poll.records` 调到 200
2. 扩容消费者实例 4 → 8(分区数足够)
3. 优化:消息精简(只传订单 ID,详情走 RPC 查询)
4. 加监控:消息体积 P99 告警

**复盘**:
- 大促前必须压测全链路
- 配置必须与业务量匹配
- 关键参数应做动态化(可热修改)

**时间**:2026-03-15 03:00,运维误操作。

**现象**:

### 案例 3:消息重复导致资损

**时间**:2026-01-20,支付链路。

**现象**:
- 同一订单被扣款 2 次
- 客服投诉量突增

**排查**:
```bash
# 1. 看生产者配置
grep "enable.idempotence" producer.properties
# (空,即默认 false)

# 2. 看代码
# KafkaProducer.send(record).get() 失败时,代码直接抛异常
# 但实际上消息可能已经写入(Producer 端重试)
```

**根因**:
- 生产者未开启幂等
- 业务代码 try-catch 失败后,直接跳到 commit,没做业务幂等
- 收到重试的消息后,业务再次扣款

**解决**:
```java
// 1. 生产端开启幂等 + 事务
props.put("enable.idempotence", true);
props.put("acks", "all");
props.put("retries", Integer.MAX_VALUE);

// 2. 消费端业务幂等(数据库唯一键)
@Transactional
public void processPayment(OrderMessage msg) {
    // 唯一键:order_id
    int rows = jdbc.update(
        "INSERT INTO payment(order_id, amount) VALUES(?, ?) " +
        "ON DUPLICATE KEY UPDATE id=id",  // 重复则不更新
        msg.orderId, msg.amount
    );
    if (rows == 0) {
        log.info("duplicate payment, ignore: {}", msg.orderId);
    }
}

// 3. 手动 commit
consumer.commitSync();
```

**复盘**:
- 金融场景必须全链路幂等
- 监控"重复消息率"作为告警指标
- 单元测试必须包含"幂等性"用例

### 案例 7:Consumer 频繁 Full GC 导致服务雪崩

**时间**:2026-04-20,灰度上线新版本消费者。

**现象**:
- 新版本消费者上线后,5 分钟内开始频繁 Full GC
- 单次 Full GC 停顿 8-12 秒
- Coordinator 误判消费者死亡,触发 Rebalance
- 雪崩:重启后继续 GC,继续 Rebalance,服务彻底不可用

**排查过程**:

```bash
# 1. 看 GC 日志
grep "Full GC" /var/log/app/gc.log | tail -20
# [2026-04-20T10:15:30.000+0800][info][gc] GC(1234) Pause Full (System.gc()) 
# 8123ms->0ms

# 2. 堆内存分析
jmap -heap <consumer-pid>
# Heap Configuration:
#    MaxHeapSize              = 4294967296 (4.0GB)
#    NewSize                  = 1363144 (1.3MB)

# 3. 看对象分布
jmap -histo:live <consumer-pid> | head -30
# 输出:大量 com.fasterxml.jackson.databind.node.ObjectNode 实例,占用 2GB+

# 4. 看代码 changelog
git log --oneline -20
# abc1234 新增:批量反序列化整个 JSON payload 到内存
```

**根因**:
- 新版本代码将每条 Kafka 消息的整个 JSON 完整加载到内存树中
- 单批 500 条 × 50KB JSON = 25MB,反序列化后膨胀到 100-200MB
- 4GB 堆几分钟内填满,触发频繁 Full GC
- 旧版本是流式解析,内存稳定

**解决**:
```java
// 错误做法 ❌
// 把整个 JSON 加载到内存
ObjectNode root = (ObjectNode) mapper.readTree(record.value());

// 正确做法 ✅
// 流式解析,逐字段处理
try (JsonParser parser = mapper.getFactory().createParser(record.value())) {
    while (parser.nextToken() != null) {
        String field = parser.currentName();
        if ("orderId".equals(field)) {
            String orderId = parser.getValueAsString();
            processField(orderId);
        }
        // 立即释放
    }
}
```

**进一步优化**:
```properties
# 1. 调小批量
max.poll.records=100       # 原来 500
fetch.max.bytes=1048576    # 1MB

# 2. JVM 调优
KAFKA_HEAP_OPTS="-Xmx6g -Xms6g -XX:+UseG1GC -XX:MaxGCPauseMillis=100 \
  -XX:+ParallelRefProcEnabled -XX:+UseStringDeduplication"

# 3. 调整 Kafka 参数,适配业务
session.timeout.ms=60000   # 60 秒
max.poll.interval.ms=600000 # 10 分钟
```

### 案例 8:误删 Topic 导致数据丢失

**时间**:2026-06-08,运维清理脚本误执行。

**现象**:
- 业务突然报"Topic 不存在"
- 生产者发消息全部失败
- 已积累的数据全部丢失

**排查过程**:
```bash
# 1. 看 Topic 列表
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list | grep order
# (空) - 没有 order 这个 topic 了

# 2. 看操作审计
# 通过 audit log 或堡垒机回溯
# 看到运维执行:bin/kafka-topics.sh --delete --topic order*
# shell glob 把所有 order* 的 topic 都删了(包括订单核心 topic)

# 3. 看 delete 是否可恢复
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --list --exclude-internal
```

**根因**:
- 清理脚本误用通配符 `order*`,把核心订单 topic 一并删除
- 误以为 order-topic-old 是临时 topic,实际 order-topic、order-topic-v2 才是生产
- Kafka 的 `--delete` 不可逆(默认设置)

**解决方案**(事后补救):

```bash
# 1. 如果 MirrorMaker 2 有备份,从备份恢复
# 但通常实时业务要求 RTO < 1 小时,MirrorMaker 同步延迟 30 秒左右可接受

# 2. 如果有 Kafka Connect S3 Sink,可以从 S3 重建 Topic
bin/kafka-connect-etc
# 但完整重建需要重新消费历史数据,影响业务

# 3. 临时方案:业务侧从 DB 重建
# 订单数据可从 MySQL 重建(若 DB 是 source of truth)
# 但消息已彻底丢失,无法追回

# 4. 启用 delete.topic.enable=false(防再次)
# 但已删除的无法恢复
echo "delete.topic.enable=false" >> config/kraft/server.properties
```

**预防措施**:
```bash
# 1. 删除前必须人工确认
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --delete --topic <exact-name>  # 不用通配符

# 2. 启用保护
delete.topic.enable=false  # 默认 true,生产推荐 false

# 3. 备份必做
# - MirrorMaker 2 / 备份集群
# - Kafka Connect S3 Sink(每日)
# - 关键 Topic 写入多副本

# 4. SOP
# 删除 Topic 必须:
#   - 双人复核(运维 + 业务 owner)
#   - 在变更系统走工单
#   - 灰度(先 list 确认,再 delete)
```

**复盘**:
- 任何删除操作必须双人复核
- 自动化脚本必须显式列出待删除 topic,不允许 glob
- 必须有完整备份体系
- "宁可多备份,不可省磁盘"

### 案例 9:跨地域 MirrorMaker 2 同步延迟

**时间**:2026-07-01,跨地域容灾演练。

**现象**:
- 主集群在北京,备集群在上海
- MirrorMaker 2 同步延迟从 100ms 涨到 5 分钟+
- 演练切流时数据不一致(上海缺北京最近 5 分钟的数据)

**排查**:
```bash
# 1. 看 MirrorMaker 2 状态
mm2 status
# 看到 connector 状态 running,但 lag 在涨

# 2. 看网络
mtr shanghai-broker
# RTT 30ms(正常),无丢包

# 3. 看带宽
sar -n DEV 1
# 千兆网卡已用 70%

# 4. 看 MirrorMaker 2 配置
# emit-heartbeats-interval=1000
# offset-syncs-topic-replication-factor=3  # 跨地域 3 副本网络瓶颈
```

**根因**:
1. MirrorMaker 2 默认 `offset-syncs-topic.replication.factor=3`
2. 跨地域同步 3 副本,网络往返 30ms × 3 = 90ms 起步
3. 高峰期,北京到上海的专线被打满
4. 同地域 `__offset_syncs` topic 副本同步延迟

**解决方案**:
```properties
# 1. 跨地域降低副本数
offset-syncs-topic.replication.factor=2
# 注:必须确保 min.insync.replicas=1

# 2. 增加 MirrorMaker 2 并行度
# mm2.properties:
# tasks.max=8 (原来 4)

# 3. 启用压缩
compression.type=lz4

# 4. 增加带宽 / 多链路
# 业务方扩容专线 1Gbps → 5Gbps

# 5. 接受最终一致性
# 跨地域 RPO < 30 秒(同步)+ 异步累积延迟
```

**进一步优化(长期)**:
```text
┌─────────────────────────────────────────────────────────┐
│ 主集群(北京)                                             │
│   ↓ MM2 (1) 同步                                         │
│ 中转集群(上海) ←→ 同城备集群(上海)                       │
│   ↓ MM2 (2) 同步                                         │
│ 异地容灾集群(广州)                                       │
└─────────────────────────────────────────────────────────┘

- 多级 MM2,减少单链路压力
- 同城 RPO < 1 秒,异地 RPO < 30 秒
```

**复盘**:
- 跨地域容灾必须有 SLA 文档
- MirrorMaker 2 不是"开了就好",需要持续调优
- 网络和带宽是跨地域同步的核心瓶颈
- 演练必须常态化(每季度)

### 案例 10:Producer 端突发重试风暴

**时间**:2026-08-03,业务上线新功能。

**现象**:
- Producer 端 `record-retry-rate` 从 0.1% 涨到 30%
- Broker 端 `request-queue-size` 飙到 5000
- 业务方观察 `record-error-rate` 同步上涨

**排查过程**:
```bash
# 1. 看 Producer JMX
echo "get -b kafka.producer:type=producer-metrics,name=record-retry-rate" | \
  nc localhost 9999
# 30.5

# 2. 看 Broker 端请求队列
echo "get -b kafka.server:type=KafkaRequestHandlerPool,name=RequestQueueSize" | \
  nc broker1 9999
# 5000 (正常 < 100)

# 3. 看 Broker GC
ssh broker1 "jstat -gcutil $(pgrep -f kafka.Kafka) 1s"
# S0    S1    E    O    M    CCS   YGC   YGCT   FGC   FGCT
# 0.00  0.00 100.00 89.43 95.21 92.15    12   0.123   4    0.456
# 老年代 89%,Full GC 4 次(正常应该接近 0)

# 4. 看 Broker 磁盘
ssh broker1 "iostat -x 1"
# await 30ms, %util 95%
```

**根因**:
1. 新业务功能上线,消息量从 5W/s 涨到 30W/s
2. Broker 磁盘 IO 跟不上,Produce 请求变慢
3. Producer 默认 `delivery.timeout.ms=120000`(2 分钟)
4. 在 2 分钟内,Producer 不断重试,加重 Broker 负担
5. 恶性循环:Broker 慢 → Producer 重试 → Broker 更慢

**解决方案**:

```properties
# 短期(立即止血):
# 1. Producer 端降低重试影响
delivery.timeout.ms=30000    # 30 秒超时
request.timeout.ms=10000     # 10 秒单次 RPC
# 让失败快速暴露,而不是堆积

# 2. Broker 端提升 IO
# 加大 log.flush.interval(降低刷盘频率)
log.flush.interval.messages=100000
log.flush.interval.ms=5000

# 3. 临时限流(防止雪崩)
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type clients --entity-name new-business \
  --alter --add-config producer_byte_rate=20971520  # 20MB/s
```

```properties
# 长期(根治):
# 1. 容量规划:预测业务量 + 50% 余量部署
# 2. Broker 加盘 / 换 SSD
# 3. Topic 增加分区,水平扩展
# 4. 业务分级:核心业务/非核心业务,核心独占 Topic
# 5. 熔断:Producer 端用 Resilience4j,失败率 > 30% 直接拒绝
```

**复盘**:
- 大流量上线前必须压测
- Producer 默认重试参数过宽容,可能掩盖问题
- 必须有"快速失败"机制,不要让故障蔓延
- 容量评估:`峰值 × 1.5` 而非平均值

### 案例 11:Kafka 集群迁移后消费 offset 错乱

**时间**:2026-08-10,旧集群 → 新集群迁移。

**现象**:
- 应用切到新集群后,Consumer 重复消费近 2 天的数据
- 部分业务触发幂等校验报错(如重复扣款)
- 数据准确性核对发现新老集群 offset 计算不一致

**根因排查**:

```bash
# 1. 看老集群 offset
bin/kafka-consumer-groups.sh --bootstrap-server old-kafka:9092 \
  --describe --group order-consumer
# 2 天前:offset=1000000,新集群:offset=800000

# 2. 看新集群 offset
bin/kafka-consumer-groups.sh --bootstrap-server new-kafka:9092 \
  --describe --group order-consumer
# offset 比老集群少 200000

# 3. 对比两边消息数
bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server old-kafka:9092 --topic orders
# 2 天累积:3000000 条

bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server new-kafka:9092 --topic orders
# 累积:2800000 条

# 4. 看新老集群配置
diff old-config/kraft/server.properties new-config/kraft/server.properties
# 差异:log.message.timestamp.type=CreateTime vs LogAppendTime
# 差异:message.timestamp.difference.max.ms=9223372036854775807
```

**根因**:
- 老集群用 `CreateTime`(业务时间),新集群默认 `LogAppendTime`(Broker 写入时间)
- 新集群消费者用"上一次提交时间戳"作为起点查询
- 老 offset 是 `CreateTime` 基准,与新集群的 `LogAppendTime` 不对齐
- 导致部分数据未被消费就被跳过

**解决方案**:

```properties
# 方案 A:统一时间戳类型(生产推荐)
log.message.timestamp.type=CreateTime
message.timestamp.difference.max.ms=9223372036854775807
```

```bash
# 方案 B:迁移前手动 reset offset,精确对齐
# 1. 暂停老集群消费者
# 2. 记录老集群最后 offset
LAST_OFFSET=1000000
# 3. 在新集群手动设置 offset
bin/kafka-consumer-groups.sh --bootstrap-server new-kafka:9092 \
  --group order-consumer \
  --topic orders:0=1000000,orders:1=1005000,... \
  --reset-offsets --execute
```

**预防措施**:
```text
┌──────────────────────────────────────────────────────────┐
│ 1. 迁移前清单                                                │
│    - 时间戳类型必须一致                                       │
│    - 压缩算法、压缩类型统一                                   │
│    - 消息格式版本匹配(0/1/2)                                 │
│    - 副本数、min.insync.replicas 一致                        │
│                                                              │
│ 2. 灰度迁移                                                   │
│    - 1% 流量切新集群,观察 offset 与延迟                       │
│    - 灰度 24-48 小时,无异常切 100%                           │
│                                                              │
│ 3. 双写验证                                                   │
│    - 生产者同时写新老集群                                     │
│    - 消费者对比两边的消息,确认一致                            │
└──────────────────────────────────────────────────────────┘
```

**复盘**:
- 集群迁移必须完整对比配置
- 不能只测"能写能读",必须测"读到对的数据"
- 建议用 MirrorMaker 2 双写验证,而非全量切流

## 十三·六、容量规划与性能压测

### 1. 容量评估公式

```text
磁盘需求 = 日均消息量 × 平均消息大小 × 保留天数 × 副本数 / 压缩率

例:
  日均消息: 5 亿条
  平均大小: 1KB
  保留天数: 7
  副本数:   3
  压缩率:   0.3(lz4)

磁盘 = 500_000_000 × 1KB × 7 × 3 / 0.3
     = 35TB
```

### 2. 关键参数决策表

| 业务特征               | 推荐配置                                                                 |
|------------------------|--------------------------------------------------------------------------|
| 高吞吐(>10W QPS)      | 分区数 = 业务并发度 × 2,`batch.size=128KB`,`linger.ms=50`                |
| 低延迟(< 10ms)         | `linger.ms=0`,副本数=2(容忍 1 故障即可),`acks=1`(折中)                  |
| 强保序                 | 单分区 + `max.in.flight=1`                                               |
| 数据持久性优先         | `replication.factor=3`,`acks=all`,`min.insync.replicas=2`                |
| 大消息(> 1MB)          | `message.max.bytes` 调大,考虑用外部存储 + 仅传 ID                       |

### 3. 压测方法

```bash
# 1. 使用 kafka-producer-perf-test
bin/kafka-producer-perf-test.sh \
  --bootstrap-server localhost:9092 \
  --topic perf-test \
  --num-records 10000000 \
  --record-size 1024 \
  --throughput 100000 \
  --producer-props \
    acks=all \
    compression.type=lz4 \
    linger.ms=10

# 2. 使用 kafka-consumer-perf-test
bin/kafka-consumer-perf-test.sh \
  --bootstrap-server localhost:9092 \
  --topic perf-test \
  --messages 10000000 \
  --group perf-consumer

# 3. 输出解读
# 100000 records sent, 953.45 records/sec (0.95 MB/sec), 
# 95.10 ms avg latency, 350.00 ms max latency
# 100000 records received, 1024.00 KB/sec
```

### 4. 压测 checklist

```text
[ ] 消息大小:均匀分布(1KB / 10KB / 100KB)
[ ] Topic 分区数:与生产一致
[ ] 副本数 / min.insync.replicas:与生产一致
[ ] Broker 数量 / 配置:与生产一致
[ ] 网络:与生产一致(同机房/跨机房)
[ ] 压测时长:至少 30 分钟(覆盖 GC / Page Cache 预热)
[ ] 监控:压测期间全量采集(CPU/IO/GC/Lag)
[ ] 故障注入:随机 kill 一个 broker,验证容错
[ ] 峰值/平均值:压出 P99 / 峰值,作为容量基准
```

### 5. 容量预警分级

| 指标                     | 黄色预警        | 红色预警        | 应急动作              |
|--------------------------|-----------------|-----------------|-----------------------|
| 磁盘使用率               | > 70%           | > 85%           | 加盘 / 清数据         |
| Consumer Lag             | > 10000         | > 100000        | 扩容实例 / 优化代码   |
| CPU 使用率               | > 70%           | > 85%           | 加节点 / 优化 GC      |
| 网络带宽                 | > 70%           | > 85%           | 升网卡 / 限流         |
| Full GC 频率             | > 1 次/小时     | > 1 次/分钟     | 调优 JVM / 排查泄漏  |

## 十三·七、升级与迁移专题

### 1. Kafka 版本升级流程

```text
[1] 兼容性评估(最重要)
    - Broker 3.x 之间: 滚动升级(roll-by-roll)
    - 客户端: 0.10/0.11/1.x/2.x/3.x 通常兼容
    - 协议: Kafka 3.x 客户端连老版本 Broker 通常 OK
    - 检查 breaking changes(KIP 列表)

[2] 测试环境验证
    - 同等数据量压测
    - 故障注入(随机 kill)
    - 监控指标回归

[3] 生产环境升级
    - 1) 先升级所有 KRaft Controller(必须先升级!)
    - 2) 再升级 Broker(rolling)
    - 3) 最后升级客户端
    - 每个节点升级间隔 5-10 分钟

[4] 验证 & 回滚
    - 观察 24-48 小时
    - 出问题可降级(Kafka 3.x 支持)
```

### 2. ZK → KRaft 迁移

**适用版本**:Kafka 2.8+(KRaft 预览)、3.3+(生产)、3.5+(GA)。

```bash
# 步骤 1:升级到 3.5+(仍用 ZK 模式)
# 步骤 2:开启 KRaft 双写(3.3+ 引入)
# 步骤 3:切流量到 KRaft 集群
# 步骤 4:下线 ZK 集群

# KRaft 独立集群初始化(全新集群)
bin/kafka-storage.sh random-uuid  # 生成 cluster.id
bin/kafka-storage.sh format -t <uuid> -c config/kraft/server.properties
bin/kafka-server-start.sh config/kraft/server.properties
```

**风险点**:
- ZK 元数据导入可能不完整(检查 `__consumer_offsets`)
- 客户端协议版本必须支持 KRaft(2.8+)
- 切换期间不要修改 Topic 配置,可能造成不一致

## 十三·九、Kafka 常见异常分类速查

### 1. Producer 异常

| 异常                                       | 含义                       | 解决                                          |
|--------------------------------------------|----------------------------|-----------------------------------------------|
| `TimeoutException`                          | 发送超时                   | 调 `delivery.timeout.ms`/排查网络             |
| `RetriableException`                        | 可重试                     | 自动重试或扩大重试次数                        |
| `RecordTooLargeException`                   | 消息超限                   | 调 `max.request.size` 或拆消息               |
| `InvalidTopicException`                     | Topic 不存在               | 创建 Topic 或开启 auto.create                |
| `NotLeaderForPartitionException`            | 非 Leader                  | 自动恢复,检查 `unclean.leader.election`      |
| `UnknownTopicOrPartitionException`          | Topic/Partition 不存在     | 元数据问题,Controller 状态                   |
| `MessageSizeTooLargeException`              | 消息过大(服务端拒绝)      | 调 `message.max.bytes`                       |
| `AuthorizationException`                    | ACL 拒绝                   | `kafka-acls.sh --add`                        |
| `OutOfOrderSequenceException`               | 幂等性破坏                 | 升级客户端或保持 `max.in.flight ≤ 5`         |
| `ProducerFencedException`                   | 事务被 fence              | 检查 `transactional.id` 唯一性               |

### 2. Consumer 异常

| 异常                                       | 含义                       | 解决                                          |
|--------------------------------------------|----------------------------|-----------------------------------------------|
| `CommitFailedException`                    | Offset 提交失败           | 不能跨 group 提交,排查 rebalance            |
| `WakeupException`                          | 手动 wakeup                | 正常流程,用于优雅停止                        |
| `RebalanceInProgressException`              | Rebalance 中               | 等待完成,不要在回调里 poll                   |
| `ConsumerTimeoutException`                 | 消费超时                   | 调 `max.poll.interval.ms`                    |
| `OffsetOutOfRangeException`                | offset 超出范围            | 重置 offset 或调整 retention                 |
| `InvalidGroupIdException`                  | group id 非法              | 检查 group 命名                              |
| `TopicAuthorizationException`              | Topic 无权限               | ACL 配置                                     |
| `FencedInstanceIdException`                | KIP-848 新协议             | 检查 `group.instance.id`                      |

## 十三·十一、踩坑经验与最佳实践

### 1. 生产环境铁律(经过验证)

```text
1. 必须开启幂等:enable.idempotence=true
2. 必须开启 SASL/ACL:任何能访问 Kafka 的人都应该有最小权限
3. 必须保留至少 3 副本:replication.factor=3 + min.insync.replicas=2
4. 必须禁止 unclean leader:unclean.leader.election.enable=false
5. 必须有监控告警:Lag / 磁盘 / GC / Offline Partition 必须覆盖
6. 必须有备份:MirrorMaker 2 或 Kafka Connect 同步到备份集群
7. 必须有版本兼容矩阵:升级前必查
8. 必须有 on-call 轮值:5 分钟响应
9. 必须有应急 SOP:切流、回滚、重启、数据恢复
10. 必须有定期演练:每季度一次故障演练
```

### 2. 常见反模式(踩过的坑)

```text
反模式 1:全局 1 个巨型 Topic
  后果:磁盘竞争、分区无法独立扩容、单点故障影响所有业务
  正确:按业务拆分 Topic,关键业务独立 Topic

反模式 2:消息里塞整个业务对象
  后果:消息体巨大、网络带宽浪费、Consumer 内存爆炸
  正确:消息只传 ID,详情走 RPC 查询

反模式 3:消费者实例数 = 业务线程数
  后果:Rebalance 频繁,实例数 > 分区数浪费
  正确:消费者实例数 ≤ 分区数,业务并行度通过实例数扩展

反模式 4:自动 commit + 业务逻辑
  后果:commit 完业务崩溃 = 消息丢失;业务完 commit 崩溃 = 重复消费
  正确:手动 commit + 业务幂等

反模式 5:不设保留时间(默认 7 天不一定合适)
  后果:磁盘暴涨 / 关键数据过期
  正确:根据业务显式设置 retention

反模式 6:无差别 kafka-topics.sh --delete
  后果:误删核心 Topic,数据全丢
  正确:delete.topic.enable=false + 人工复核

反模式 7:无监控上线
  后果:故障无人发现,客户投诉才知道
  正确:必须先有监控告警,再上线

反模式 8:测试用 1 副本
  后果:测试结论与生产不符,生产出问题
  正确:测试环境尽量复刻生产(包括副本数、配置)
```

## 十三·十二、高频 Q&A(社区精华)

### Q1:Kafka 是不是保证消息不丢?

**A**:Kafka 只保证"已 commit"的 offset 之前消息不丢。链路全链路防丢失需:
1. 生产端 `acks=all` + `enable.idempotence=true` + 同步确认
2. Broker 端 `min.insync.replicas=2` + `replication.factor=3`
3. 消费端手动 commit + 业务幂等

### Q2:Consumer 拉消息慢,会不会导致 Producer 报错?

**A**:不会。Kafka 是"拉"模型,Consumer 慢只影响自己 lag,不影响 Broker。但 Consumer lag 过大意味着 Topic 数据积累,可能触发磁盘满 → Broker 写入失败。

### Q3:为什么 Kafka 不像 MySQL 有"主从复制延迟"概念?

**A**:Kafka 的 Follower 同步由 Broker 端自动管理(基于 ISR),生产者写到 Leader,Follower 异步拉取同步。**关键差异**:
- MySQL 从库可能延迟几秒到几小时
- Kafka Follower 同步通常在毫秒级,延迟过大会被踢出 ISR

### Q4:Kafka 如何保证消息顺序?

**A**:**单分区内严格有序**,全局不保证。保证顺序的方法:
- 把同业务消息路由到同一分区(hash 业务 key)
- 生产端 `max.in.flight.requests.per.connection=1`(牺牲吞吐)
- 开启幂等(Kafka 自动按 sequence 排序)

### Q5:为什么我的 Topic 一边写一边消费,offset 一直不动?

**A**:检查消费组是否真正提交 offset:
```bash
bin/kafka-consumer-groups.sh --bootstrap-server X:9092 \
  --describe --group G
```
- 如果 `CURRENT-OFFSET` 不变 → 消费者没提交(可能是 enable.auto.commit=false 又没手动 commit)
- 如果 `LAG` 一直是 0 但消息堆积 → 消费了但没真正处理

### Q6:Kafka 集群需要多少个 Broker?

**A**:取决于业务需求:
- **开发/测试**:1-3 个
- **小规模生产**:3 个(容忍 1 故障)
- **中等规模**:5-7 个
- **大规模/金融**:7+ 个,跨机柜/跨机房部署
- **KRaft Controller**:3 个(单独)或 5 个(高可用)

### Q7:磁盘是 SSD 还是 HDD?

**A**:
- **HDD**:成本低,适合日志类、批量 ETL 场景
- **SSD**:低延迟,适合在线业务(订单、支付)
- **NVMe**:极致性能,适合极端吞吐场景
- 关键:顺序读写为主,机械盘也不差

### Q8:Kafka 适合做消息队列吗?和 RabbitMQ 比?

**A**:**适用场景不同**:

| 场景                | Kafka         | RabbitMQ       |
|---------------------|---------------|----------------|
| 高吞吐(百万级/秒)  | 优势明显      | 不适合         |
| 严格顺序保证         | 单分区保证    | 队列内保证      |
| 消息回溯(重消费)   | 原生支持      | 不支持          |
| 复杂路由            | 需要流处理    | 路由灵活        |
| 延迟敏感(< 10ms)   | 可达          | 优势            |
| 事务消息             | 支持(EOS)     | 支持(有限)      |
| 运维复杂度          | 中-高         | 中              |

选型原则:**大数据量、流式处理、需回溯** → Kafka;**低延迟、复杂路由** → RabbitMQ。

### Q9:Kafka 的数据保留策略怎么选?

**A**:
- `delete`(默认):按时间/大小删除,适合普通消息
- `compact`:只保留每条 key 的最新值,适合配置/状态同步
- `delete,compact`:先压缩后删除(混合)
- 推荐:多数 Topic 用 delete + 合理 retention(7-30 天)

### Q10:如何知道 Kafka 集群的容量上限?

**A**:压测!生产前必做:
```bash
bin/kafka-producer-perf-test.sh --num-records 10000000 \
  --record-size 1024 --throughput -1
```
观察:
- 极限 QPS
- P99 延迟
- CPU/IO/网络峰值

一般**保留 50% 余量**作为生产容量上限。

### Q11:Kafka 能不能做"广播"(一个消息给多个消费者)?

**A**:**天然支持**!通过 consumer group:
- **不同 group**:每个 group 收到全量消息(广播)
- **同一 group 内**:每条消息只被一个实例消费(负载均衡)
- 这是 Kafka 的核心模型,无需额外配置

### Q12:Controller 节点挂了,Producer/Consumer 还能用吗?

**A**:**能用,但有限制**:
- 已有的 Topic/Partition 元数据被 Producer/Consumer 缓存
- 现有读写不受影响
- 但创建新 Topic、扩容、迁移等元数据操作会失败
- 直到 Controller 重新选举完成(通常秒级)

### Q13:为什么 Kafka 3.x 默认推荐 KRaft?

**A**:KRaft 替代 ZooKeeper 的优势:
- 简化部署(无需维护 ZK 集群)
- 元数据性能提升(KIP-500)
- 故障恢复更快(从分钟级降到秒级)
- 支持更大规模(10 万+ Partition)
- 官方长期方向(4.x 完全弃用 ZK)

### Q14:Kafka 消息体大小限制多少?

**A**:
- Broker 默认 1MB(`message.max.bytes`)
- Topic 默认继承
- Producer 默认 1MB(`max.request.size`)
- Consumer 默认 1MB(`fetch.max.bytes`)
- 单条超过 1MB 需全部调大
- 强烈建议:**消息体不要超过 1MB**,过大消息应拆分或用外部存储

### Q15:如何实现 Kafka 的精确一次消费?

**A**:Kafka 3.x 提供两种语义:
1. **幂等生产者 + 手动 commit + 业务幂等**:够用,推荐
2. **Kafka 事务**(EOS):
```java
producer.initTransactions();
producer.beginTransaction();
producer.send(record1);
producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
producer.commitTransaction();
```
事务可保证"消费-处理-生产"的原子性,但性能损耗较大,按需使用。

## 十五、核心要点速记

### 排查哲学

- **排查顺序**:业务 → 客户端 → Broker → 操作系统 → 硬件,从表象到底层,不要跳级
- **黄金法则**:80% 的故障通过"看日志 + 看监控 + 看配置"就能定位,无需读源码
- **预防 > 排查**:监控告警、容量巡检、灾备演练,比事后排查高效 10 倍
- **永远先看日志**:`kafkaServer.log` 和 `controller.log` 是第一手资料,先 grep 再分析
- **永远不要盲目重启**:尤其 Controller 节点,先看 quorum 状态,避免加剧脑裂
- **永远先 dump 数据**:任何破坏性操作前,先备份 Topic/元数据

### 核心工具(熟记 5 个命令)

- `kafka-consumer-groups.sh --describe --group G`:看 Lag、offset 进度
- `kafka-topics.sh --topic T --describe`:看分区、ISR、Leader 分布
- `kafka-metadata-quorum.sh describe --status`:KRaft Controller 状态
- `kafka-configs.sh --describe --entity-type X --entity-name Y`:看动态配置
- `kafka-log-dirs.sh --describe`:看磁盘占用分布

### 关键配置三件套

- **生产配置三件套**:`acks=all` + `retries=Integer.MAX_VALUE` + `enable.idempotence=true`
- **强保序三件套**:`enable.idempotence=true` + `max.in.flight ≤ 5` + 同 key 同分区
- **副本强一致**:`replication.factor=3` + `min.insync.replicas=2` + `unclean.leader.election.enable=false`

### 高频故障模式速查

| 故障现象                | 第一动作                                         |
|-------------------------|--------------------------------------------------|
| 消费者 Lag 增长         | `kafka-consumer-groups.sh --describe` 看哪个分区 |
| Producer 报错           | 看异常类型(超时/超限/鉴权),对应解决              |
| Broker 不可用            | `kafka-metadata-quorum.sh describe --status`     |
| 磁盘写满                | `df -h` + `kafka-log-dirs.sh`                   |
| Rebalance 频繁          | 看 GC 日志 + `max.poll.interval.ms` 配置         |
| Controller 选举失败     | 检查 `controller.quorum.voters` 配置             |
| 消息丢失                | 检查 acks + min.insync.replicas + 消费 commit   |
| 消息重复                | 业务幂等(数据库唯一键/Redis SET)                |
| 性能下降                | `iostat -x` 看磁盘 / `jstat` 看 GC / `sar` 看网络 |
| 客户端连接失败          | 检查 SASL/SSL 配置 + 网络 ACL + bootstrap.servers |

### 监控告警红线

- **Offline Partition > 0** → Critical(立即响应)
- **UnderReplicated Partition > 0**(持续 5 分钟)→ Warning
- **Consumer Lag > 10000** → Warning(按业务调阈值)
- **磁盘 > 85%** → Critical
- **Full GC 频率 > 1 次/小时** → Warning
- **请求队列 > 200** → Warning
- **Controller 节点 < 3** → Critical

### KRaft 关键点

- **节点数**:3 或 5 个 Controller(奇数,容忍 1 或 2 个故障)
- **配置**:`controller.quorum.voters=1@n1:9093,2@n2:9093,3@n3:9093`
- **角色分离**:生产推荐 Broker 与 Controller 分离部署(混合模式需评估)
- **首次启动**:必须用 `kafka-storage.sh format` 初始化
- **故障恢复**:Controller 选举秒级完成,通常无需人工干预

### 容量规划基线

- **磁盘**:`日均消息量 × 平均大小 × 保留天数 × 副本数 / 压缩率 × 1.5`(余量)
- **分区数**:`业务并发度 × 2`(留扩展空间)
- **消费者实例数**:`≤ 分区数`,建议 = 分区数(满载)
- **内存**:`Xmx ≤ 物理内存 50%`,剩余给 OS Page Cache
- **网络**:留 50% 余量,高峰期避免饱和

### 性能调优 Check

- G1GC + `MaxGCPauseMillis=20`
- `linger.ms=10~50` + `batch.size=64KB+`
- `compression.type=lz4`(平衡)/ `zstd`(高压缩)
- `num.io.threads=8`(按 CPU 核数调整)
- `num.replica.fetchers=4`(副本同步并发)

### 灾备铁律

- **必须有备份**:MirrorMaker 2 / Kafka Connect / 双集群
- **必须有切流 SOP**:主备切换 RTO < 5 分钟
- **必须有跨地域**:异地容灾,避免单机房故障
- **定期演练**:每季度一次真实切流演练
- **数据可恢复**:任何删除前必备份,任何写入必验证

### 变更管理 Check

- **灰度发布**:1% → 5% → 20% → 50% → 100%
- **配置 review**:双人复核 + 变更系统工单
- **压测验证**:升级前必须做同等规模压测
- **回滚预案**:每个变更必须能回滚
- **观察期**:24-48 小时观察,无异常才算成功

### 安全 Check

- **SASL**:生产必开,SCRAM-SHA-256 或 SCRAM-SHA-512
- **ACL**:最小权限原则,每个业务方独立用户
- **SSL**:跨公网/跨机房必开,内网可选
- **网络隔离**:Kafka 不暴露公网
- **审计日志**:记录所有 ACL 变更

### 心态 Check

- 不要"差不多就行",生产配置必须精确
- 不要"重启就好",根因没找到会反复
- 不要"客户没投诉就没事",监控告警是唯一标准
- 不要"加机器就行",先看瓶颈在哪
- 不要"看别人这么配我也这么配",按业务选配置
- 不要"上线再说",上线前必须压测

> **最后提醒**:Kafka 故障大多数是配置不当和资源不足,定期做容量评估、配置 review、灾备演练,比事后排查高效 10 倍。一个优秀的 Kafka 工程师,不是排查故障最快的人,而是**让故障不发生**的人。
>
> **永远记住**:
> - 监控告警是第一道防线
> - 灾备演练是最后一道防线
> - 业务幂等是终极防线
> - 配置规范是日常防线
> - 复盘改进是成长防线
