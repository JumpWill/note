# Kafka 体系结构

## 一、Kafka 概述

**Apache Kafka** 最初由 LinkedIn 开发,后捐赠给 Apache 基金会,目前是世界上最流行的**分布式事件流平台 (Distributed Event Streaming Platform)**。Kafka 兼具**消息队列**、**分布式存储**、**流处理**三重定位,被广泛应用于日志收集、监控数据聚合、消息推送、事件溯源、变更数据捕获 (CDC) 等场景。

**核心特性**:

- **高吞吐**:单机可处理数十万级 TPS,顺序写盘 + 零拷贝 + 页缓存
- **水平扩展**:Topic 分区可跨 Broker 集群,无感知扩容
- **持久化**:消息持久化到磁盘,支持回溯消费
- **容错性**:多副本机制,允许 N-1 个 Broker 故障
- **实时性**:毫秒级端到端延迟
- **生态丰富**:Connect、Kafka Streams、KSQL、Kraft

> **Kafka 不是什么**:Kafka 不是严格意义上的传统消息队列 (如 RabbitMQ),它把消息持久化日志看作**分布式提交日志 (Distributed Commit Log)**,消费模型更接近"拉模式 + 偏移量回放"。

## 二、Kafka 整体架构总览

Kafka 经典架构由 **Producer(生产者)**、**Broker 集群(代理服务器)**、**Consumer(消费者)**、**协调服务 (ZooKeeper 或 KRaft Controller Quorum)** 四大角色组成。

```text
┌──────────────────────────────────────────────────────────────────────┐
│                          Kafka 集群整体架构                          │
│                                                                      │
│  ┌──────────────┐                                                    │
│  │  Producer A  │──┐                                                 │
│  └──────────────┘  │     ┌──────────────────────────────────────┐    │
│  ┌──────────────┐  │     │         Broker 集群                  │    │
│  │  Producer B  │──┼────►│  ┌────────┐ ┌────────┐ ┌────────┐  │    │
│  └──────────────┘  │     │  │Broker 0│ │Broker 1│ │Broker 2│  │    │
│  ┌──────────────┐  │     │  │Topic-A │ │Topic-B │ │Topic-A │  │    │
│  │  Producer C  │──┘     │  │ P0 P1  │ │ P0 P1  │ │ P0 P1  │  │    │
│  └──────────────┘        │  │ P2(L)  │ │ P2(F)  │ │ P2(L)  │  │    │
│                          │  └────────┘ └────────┘ └────────┘  │    │
│                          │       ▲          ▲          ▲        │    │
│                          │       └──────────┼──────────┘        │    │
│                          │                  │ 副本同步 (ISR)     │    │
│                          └──────┬───────────┴───────────────────┘    │
│                                 │                                    │
│                                 │ 元数据/选举                        │
│                                 ↓                                    │
│  ┌──────────────────────────────────────────────────────────────┐    │
│  │   协调服务 (Cluster Metadata Service)                         │    │
│  │   ┌────────────────┐  或  ┌─────────────────────────────┐    │    │
│  │   │  ZooKeeper 集群 │     │  KRaft Controller Quorum    │    │    │
│  │   │  (旧架构)       │     │  (Kafka 3.3+,新架构)        │    │    │
│  │   └────────────────┘     └─────────────────────────────┘    │    │
│  └──────────────────────────────────────────────────────────────┘    │
│                                                                      │
│                                 │                                    │
│                                 ↓ 拉取消息                            │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐               │
│  │ Consumer A   │  │ Consumer B   │  │ Consumer C   │               │
│  │ (Group: g1)  │  │ (Group: g1)  │  │ (Group: g2)  │               │
│  └──────────────┘  └──────────────┘  └──────────────┘               │
└──────────────────────────────────────────────────────────────────────┘
```

**四类角色职责表**:

| 角色              | 英文              | 职责                                                            |
|-------------------|-------------------|-----------------------------------------------------------------|
| **Producer**      | 生产者            | 负责将消息发送到 Kafka Topic                                   |
| **Broker**        | 代理服务器        | 负责消息的存储、复制、转发(集群由多个 Broker 组成)             |
| **Consumer**      | 消费者            | 从 Broker 拉取(Pull)消息并处理                                |
| **协调服务**      | Coordination      | ZK 旧架构 / KRaft Controller 新架构,管理集群元数据与选举      |

## 三、核心概念

Kafka 涉及大量专有名词,理解这些概念是掌握 Kafka 的基础。

### 1. 核心概念速查表

| 概念                        | 英文                       | 一句话解释                                                       |
|-----------------------------|----------------------------|------------------------------------------------------------------|
| **Broker**                  | 代理服务器                 | 一个 Kafka 服务节点,负责消息的存储与转发                         |
| **Topic**                   | 主题                       | 消息的分类标签,生产者往 Topic 发,消费者从 Topic 读               |
| **Partition**               | 分区                       | Topic 的物理分片,每个 Partition 是一份有序追加日志              |
| **Replica**                 | 副本                       | Partition 的拷贝,提供数据冗余                                    |
| **Leader Replica**          | 主副本                     | 负责所有读写请求的副本                                            |
| **Follower Replica**        | 从副本                     | 被动从 Leader 拉取数据同步的副本                                  |
| **ISR**                     | In-Sync Replicas           | 与 Leader 保持同步的副本集合(包括 Leader 自身)                  |
| **OSR**                     | Out-of-Sync Replicas       | 落后 Leader 太多、被踢出 ISR 的副本                               |
| **AR**                      | Assigned Replicas          | 分区所有副本的总集 = ISR + OSR                                   |
| **HW**                      | High Watermark             | 高水位,Consumer 可见的最大位移                                   |
| **LEO**                     | Log End Offset             | 日志末端位移,下一条待写入消息的偏移                              |
| **Offset**                  | 位移                       | 消息在 Partition 内的唯一编号(单调递增 64 位 Long)              |
| **Consumer Group**          | 消费组                     | 一组 Consumer 实例,共同消费一个 Topic,互不重复                  |
| **Record**                  | 消息记录                   | Kafka 传输的最小数据单元 (Key + Value + Timestamp + Headers)   |

### 2. Broker

**Broker** 是 Kafka 集群中的一个服务节点(一个 JVM 进程),负责接收 Producer 消息、持久化到磁盘、为 Consumer 提供拉取服务。一个 Kafka 集群由多个 Broker 组成,每个 Broker 都有一个全局唯一的 ID(`broker.id`)。

**核心职责**:

- 接收并处理 Producer 的写入请求
- 持久化消息到本地磁盘 (Partition Log)
- 维护并同步各分区的副本 (Leader/Follower)
- 响应 Consumer 的拉取请求
- 参与 Controller 选举 (仅在 ZK 模式下)

**关键参数**:

| 参数                          | 说明                                              |
|-------------------------------|---------------------------------------------------|
| `broker.id`                   | Broker 唯一标识,集群内不可重复                    |
| `listeners`                   | 监听地址(PLAINTEXT/SSL/SASL)                    |
| `log.dirs`                    | 消息日志存储目录(可多目录,逗号分隔)              |
| `num.network.threads`         | 网络线程数(默认 3)                                |
| `num.io.threads`              | 磁盘 I/O 线程数(默认 8)                          |
| `log.retention.hours`          | 消息默认保留时间(默认 168 小时 = 7 天)           |
| `log.segment.bytes`            | 单个日志段文件大小(默认 1 GB)                    |

### 3. Topic

**Topic** 是 Kafka 中**消息的逻辑分类**。一个 Topic 可以看作一个"消息通道",生产者往 Topic 写,消费者从 Topic 读。

```bash
# 创建 Topic(3 个分区,2 个副本)
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic order-events \
  --partitions 3 --replication-factor 2

# 查看 Topic 列表
kafka-topics.sh --bootstrap-server localhost:9092 --list

# 查看 Topic 详情
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic order-events
```

**Topic 特性**:

- **逻辑概念**:Topic 本身不存储数据,数据分布在它的各个 Partition 上
- **多订阅者**:同一个 Topic 可被多个 Consumer Group 独立消费,**互不干扰**
- **不可变**:Topic 一旦创建,副本数可调整,但分区数只允许增加(不减少)

### 4. Partition

**Partition** 是 Topic 的**物理分片单位**,每个 Partition 在物理上对应一个**有序的、不可变的追加日志 (Append-only Log)**。

```text
Topic: order-events (3 partitions)
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Partition 0 (Broker 0)      Partition 1 (Broker 1)         │
│  ┌─────────────────────┐     ┌─────────────────────┐        │
│  │ Offset 0: msg-A     │     │ Offset 0: msg-X     │        │
│  │ Offset 1: msg-B     │     │ Offset 1: msg-Y     │        │
│  │ Offset 2: msg-C     │     │ Offset 2: msg-Z     │        │
│  │ Offset 3: msg-D     │     │ Offset 3  ...       │        │
│  │   ...               │     │                     │        │
│  └─────────────────────┘     └─────────────────────┘        │
│                                                             │
│  Partition 2 (Broker 2)                                     │
│  ┌─────────────────────┐                                   │
│  │ Offset 0: msg-P     │                                   │
│  │ Offset 1: msg-Q     │                                   │
│  │   ...               │                                   │
│  └─────────────────────┘                                   │
└─────────────────────────────────────────────────────────────┘
```

**Partition 的关键特性**:

| 特性          | 说明                                                                 |
|---------------|----------------------------------------------------------------------|
| **有序性**    | 同一 Partition 内消息严格有序(按 Offset)                            |
| **不可变性**  | 消息只能追加,不能修改、不能删除(仅按保留策略过期)                  |
| **持久化**    | 写入磁盘,默认按 `log.retention.hours` 过期                          |
| **可切片**    | 每个 Partition 被切分为多个 Log Segment 文件(`00000000.log` 等)    |
| **并发单位**  | Partition 是 Kafka 并行处理的最小单位                                |

> **顺序保证**:Kafka 只能保证**单分区内有序**,跨分区不保证全局有序。要全局有序,只能把分区数设为 1。

### 5. Replica

**Replica (副本)** 是 Partition 的冗余拷贝,用于**容错和高可用**。每个 Partition 在创建时根据 `replication-factor` 配置在多个 Broker 上创建副本。

```text
Topic: order-events, Partition 0 (replication-factor = 3)

┌────────────┐  ┌────────────┐  ┌────────────┐
│  Broker 0  │  │  Broker 1  │  │  Broker 2  │
│  Replica 0 │  │  Replica 0 │  │  Replica 0 │
│  (Leader)  │←─│  (Follower)│  │  (Follower)│
│            │  │            │  │            │
└────────────┘  └────────────┘  └────────────┘
       ↑              ↑              ↑
       │              │              │
       └──────────────┴──────────────┘
              ISR (In-Sync Replicas)
```

**副本数与可用性**:

| `replication-factor` | 允许同时宕机的 Broker 数 | 适用场景           |
|----------------------|--------------------------|--------------------|
| 1                    | 0                        | 仅限开发测试       |
| 2                    | 1                        | 容忍单点故障       |
| 3                    | 2                        | 生产环境推荐       |
| 5                    | 4                        | 金融级高可用       |

### 6. Leader Replica 与 Follower Replica

每个 Partition 的多个副本中**只有一个是 Leader**,其余都是 Follower。

| 角色       | 职责                                                                    |
|------------|-------------------------------------------------------------------------|
| **Leader** | 负责所有读写请求(Producer 发送、Consumer 拉取都过 Leader)             |
| **Follower** | 被动从 Leader 拉取数据(`replica.fetch.min.bytes` 控制节奏),保持同步 |

**选举时机**:Leader 故障时,Controller 会从 ISR 中选举新的 Leader;若 ISR 为空,根据 `unclean.leader.election.enable` 决定是否从 OSR 选举。

### 7. ISR (In-Sync Replicas)

**ISR** 是**与 Leader 保持同步的副本集合**,由 Leader 维护。判定标准:

- Follower 的 LEO ≥ Leader 的 HW - `replica.lag.time.max.ms`(默认 30000 ms)
- 也就是说,Follower 必须在最近 30 秒内拉取过数据,并跟上 Leader 的进度

```text
Partition 0 的副本关系:

   AR = {Replica-0, Replica-1, Replica-2}
        ├── ISR = {Replica-0 (Leader), Replica-1}        ← 同步中
        └── OSR = {Replica-2}                            ← 落后太多,被踢出
```

**ISR 的关键作用**:

- **Leader 选举的候选池**:新 Leader 必须从 ISR 中选出(保证数据不丢)
- **数据可靠性的衡量**:ack=all 时,所有 ISR 都写入才返回成功
- **延迟可观测**:`kafka-consumer-groups.sh` 可看 lag

### 8. OSR (Out-of-Sync Replicas)

**OSR** 是被踢出 ISR 的副本,通常因为:

- 网络抖动导致长时间拉取不到数据
- Broker 进程卡顿、磁盘性能下降
- 进程崩溃恢复后追赶进度

**OSR 的命运**:

- 满足同步条件后自动重新加入 ISR
- 通过 `unclean.leader.election.enable=true` 才有可能在 ISR 为空时上位(但会丢数据)

### 9. HW (High Watermark)

**HW (高水位)** 是**所有副本都已同步的消息最大偏移**,即 Consumer 可见的最大位移。

```text
Partition 0:
  Replica-0 (Leader): [0, 1, 2, 3, 4, 5]   LEO = 6
  Replica-1 (Follower): [0, 1, 2, 3, 4]      LEO = 5
  Replica-2 (Follower): [0, 1, 2, 3]        LEO = 4

  HW = 4  (三副本共有部分)
  Consumer 只能消费 [0, 4)
```

**HW 的意义**:`Consumer` 只能拉取到 HW 之前的数据,这样保证**即使 Leader 切换,也不会读到未同步的消息**。

### 10. LEO (Log End Offset)

**LEO (日志末端位移)** 是**下一条待写入消息的偏移**,等于"已写入消息数量"。

- Leader 维护自己的 LEO
- Follower 维护自己的 LEO
- Leader 的 LEO 通常 ≥ Follower 的 LEO

**LEO 与 HW 的关系**:`LEO >= HW`,当所有副本同步推进,LEO 与 HW 同步增长。

### 11. AR (Assigned Replicas)

**AR** 是 Partition 的**所有副本的全集**,包含 ISR 和 OSR。

```
AR = ISR ∪ OSR
```

AR 在创建 Topic 时确定,**不可动态减少**(只能通过增加副本因子扩充)。

## 四、Producer 概念

### 1. Record (消息记录) 结构

Kafka 中传输的最小数据单元是 **Record (记录)**,结构如下:

```text
Record (ProducerRecord<K, V>)
├── topic      : String         主题名
├── partition  : Integer        分区号(可选,Partitioner 自动选择)
├── key        : K              键(可选,用于分区路由)
├── value      : V              值(必填,实际消息体)
├── timestamp  : Long           时间戳(默认 System.currentTimeMillis)
├── headers    : List<Header>   头部键值对(Kafka 0.11+)
└── checksum   : CRC32          校验和(保证消息完整性)
```

**Record 字段说明**:

| 字段         | 类型     | 是否必填 | 说明                                              |
|--------------|----------|----------|---------------------------------------------------|
| `topic`      | String   | 是       | 目标 Topic                                        |
| `partition`  | Integer  | 否       | 显式指定分区(若指定 key 通常不指定 partition)   |
| `key`        | 任意     | 否       | 用于 **Partitioner** 路由,**有 key 才能保证分区一致** |
| `value`      | 任意     | 是       | 实际消息体,需被 Serializer 序列化                |
| `timestamp`  | Long     | 否       | 默认当前时间,可指定 LogAppendTime/CreateTime     |
| `headers`    | List     | 否       | 附加元数据 (traceId、source 等),0.11+ 支持     |

**示例代码 (Java)**:

```java
ProducerRecord<String, String> record = new ProducerRecord<>(
    "order-events",                          // topic
    "order-20260818-001",                    // key
    "{\"orderId\":1,\"amount\":99.9}"        // value
);
record.headers().add("traceId", "abc-123".getBytes());
producer.send(record);
```

### 2. Partitioner (分区器)

**Partitioner** 决定消息发往 Topic 的**哪个分区**。默认 `org.apache.kafka.clients.producer.internals.DefaultPartitioner`:

```text
如果指定了 partition   → 直接发到该 partition
如果指定了 key (非 null)  → 对 key 做 hash (murmur2)  →  hash % numPartitions
如果 key 和 partition 都未指定 → 轮询 (round-robin) 分配
```

**分区策略对比**:

| 策略                         | 行为                          | 适用场景                |
|------------------------------|-------------------------------|-------------------------|
| **Key 哈希**                 | 同一 Key 一定到同一 Partition | 顺序保证 (如同一用户)   |
| **轮询**                     | 均匀分配,无 Key 时默认       | 负载均衡                |
| **自定义 Partitioner**       | 实现 `Partitioner` 接口       | 业务定制路由            |
| **Sticky Partitioner**       | 2.4+ 批量发送时黏到一个分区  | 提升 batch 效率         |

> **坑点**:分区数量变化会导致**Key 哈希取模结果变化**,从而使"同一 Key"在不同分区间重新分布,打破顺序保证。

### 3. Serializer (序列化器)

Kafka 消息在网络中传输必须**序列化为字节数组**。Producer 通过 `Serializer` 接口把 Key/Value 转为 `byte[]`。

**常见 Serializer**:

| Serializer             | 序列化结果         | 适用场景                |
|------------------------|--------------------|-------------------------|
| `StringSerializer`     | UTF-8 字节         | 文本数据                |
| `IntegerSerializer`    | 4 字节 int         | 整数                    |
| `ByteArraySerializer`  | 原始字节           | 二进制                  |
| `LongSerializer`       | 8 字节 long        | 长整型                  |
| `FloatSerializer`      | 4 字节 float       | 浮点                    |
| `DoubleSerializer`     | 8 字节 double      | 双精度                  |
| JSON (第三方)          | JSON 字符串        | 结构化数据(Jackson)    |
| **Avro** (Confluent)   | 二进制 + Schema    | 强类型 + Schema 演进   |
| **Protobuf**           | 二进制 + Schema    | 跨语言、紧凑           |

**注意**:Producer 和 Consumer 端的 Serializer/Deserializer 必须**配套使用**。

## 五、Consumer 概念

### 1. Consumer Group (消费组)

**Consumer Group** 是 Kafka 实现**广播 (Broadcast)** 与**单播 (Unicast)** 模型的关键设计。

- 同一 Consumer Group 内的多个 Consumer 实例**共同消费一个 Topic**,每条消息**只被组内一个 Consumer 消费**
- 不同 Consumer Group 之间**互不干扰**,每条消息**被每个组都消费一次**

```text
Topic: order-events (3 partitions)

Consumer Group "g1"(订单服务):              Consumer Group "g2"(分析服务):
┌──────────────┐ ┌──────────────┐ ┌──────────────┐   ┌──────────────┐
│  Consumer A  │ │  Consumer B  │ │  Consumer C  │   │  Consumer D  │
│  Partition 0 │ │  Partition 1 │ │  Partition 2 │   │  Partition 0 │
│              │ │              │ │              │   │  Partition 1 │
│              │ │              │ │              │   │  Partition 2 │
└──────────────┘ └──────────────┘ └──────────────┘   └──────────────┘
                                                  (g2 独立全量消费)
```

**Consumer Group 行为表**:

| Consumer 数 vs Partition 数 | 行为                                                                          |
|------------------------------|-------------------------------------------------------------------------------|
| C < P                        | 部分 Consumer 消费多个 Partition(负载不均)                                  |
| C = P                        | 理想状态,一一对应                                                            |
| C > P                        | 多余 Consumer 处于空闲,不会分配到 Partition(`group.max.idle.ms` 后心跳超时可被踢) |

### 2. Consumer 实例

**Consumer 实例** 是消费组中的实际工作单元,与 Partition 的对应关系由 **Group Coordinator** 负责分配。

**Consumer 关键参数**:

| 参数                          | 默认值       | 说明                                                  |
|-------------------------------|--------------|-------------------------------------------------------|
| `group.id`                    | 必填         | Consumer Group 标识                                  |
| `enable.auto.commit`          | true         | 是否自动提交 Offset                                   |
| `auto.offset.reset`           | latest       | 无 Offset 时从哪开始 (latest/earliest/none)         |
| `max.poll.records`            | 500          | 一次 `poll()` 最多返回记录数                          |
| `session.timeout.ms`          | 10000 ms     | Session 超时(超过未心跳视为宕机)                    |
| `heartbeat.interval.ms`       | 3000 ms      | 心跳间隔(应小于 session.timeout 的 1/3)             |
| `max.poll.interval.ms`        | 300000 ms    | 两次 `poll()` 最大间隔,超时会被踢出组               |
| `fetch.min.bytes`             | 1            | 拉取最小字节数(默认可调到 10KB+ 提升吞吐)           |
| `fetch.max.bytes`            | 52428800     | 拉取最大字节数(50 MB)                                |

### 3. Offset (位移)

**Offset** 是消息在 Partition 内的**唯一编号**(64 位 Long,单调递增)。Offset 标识消费进度,**每个 Consumer Group 独立维护**自己消费的 Offset。

```text
Partition 0:
  Offset 0 → 1 → 2 → 3 → 4 → 5 → 6 → ...
                ↑
              当前 Consumer 消费位置 (committed offset = 3)
```

**Offset 的关键特性**:

- **分区级独立**:每个 Partition 都有自己的 Offset 空间
- **消费组级独立**:不同 Consumer Group 维护各自的 Offset
- **持久化**:默认存储在 `__consumer_offsets` Topic(Kafka 内部 Topic)
- **可回溯**:通过 `seek()` 重置 Offset 可重复消费

### 4. Offset 提交方式

`enable.auto.commit` 控制是否自动提交,但一般生产环境**关闭自动提交,改为手动精确控制**。

| 提交方式       | 配置                                   | 语义                          | 风险                            |
|----------------|----------------------------------------|-------------------------------|---------------------------------|
| **自动提交**   | `enable.auto.commit=true`              | 定时(默认 5 s)批量提交        | 重复消费/丢失(取决于 poll 后何时提交) |
| **手动同步**   | `commitSync()`                         | 同步阻塞,失败重试           | 阻塞消费,影响吞吐              |
| **手动异步**   | `commitAsync(callback)`                | 异步提交,性能好              | 失败可能漏提交,有重复消费      |
| **精确一次**   | `sendOffsetsToTransaction()` (Kafka EOS)| 与业务事务捆绑,Kafka 0.11+ | 复杂,性能开销                  |

**示例代码**:

```java
// 关闭自动提交
props.put("enable.auto.commit", "false");

// 手动同步提交
consumer.subscribe(Arrays.asList("order-events"));
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        process(record);
    }
    consumer.commitSync();  // 处理完再提交
}
```

## 六、ZooKeeper 与 KRaft 模式对比

Kafka 集群的**元数据管理**与**Controller 选举**经历了两个阶段:

### 1. 旧架构:依赖 ZooKeeper

```text
                    ┌───────────────────────────┐
                    │      ZooKeeper 集群       │
                    │  /brokers/topics         │
                    │  /brokers/ids            │
                    │  /controller             │
                    │  /consumers/...          │
                    └─────────────┬─────────────┘
                                  │ 监听 + 临时节点
                    ┌─────────────┴─────────────┐
                    │                            │
              ┌─────▼─────┐               ┌──────▼────┐
              │ Broker 0  │               │ Broker 1  │
              │ (Controller)              │           │
              │  管理分区副本状态          │           │
              └───────────┘               └───────────┘
```

**ZooKeeper 在 Kafka 中的职责**:

| 职责                       | 存储内容                                                  |
|----------------------------|-----------------------------------------------------------|
| **Broker 注册**            | `/brokers/ids/[brokerId]` 临时节点                       |
| **Topic 元数据**           | `/brokers/topics/[topic]` 持久节点                       |
| **Controller 选举**        | `/controller` 临时节点(最先创建者获胜)                  |
| **Consumer Group 偏移量**  | 旧版本存 ZK,新版本存 `__consumer_offsets`              |
| **ACL 权限**               | `/kafka-acl/...`(部分版本)                              |

**ZooKeeper 方案的痛点**:

- **运维复杂**:多一套集群,需独立调优
- **扩展性瓶颈**:ZK 写性能差,集群规模受限(单集群 Broker 数 ≤ 万级)
- **脑裂风险**:ZK 选举 + Kafka 自身 Leader 选举,两级选举耦合
- **延迟高**:所有元数据变更都要走 ZK,路径长

### 2. 新架构:KRaft (Kafka Raft)

**KRaft** 是 Kafka 3.3+ 引入的**内置一致性协议**,完全摆脱 ZooKeeper,所有元数据由 Kafka 自身的 **Controller Quorum** 管理。

```text
              ┌────────────────────────────────────────┐
              │    Controller Quorum (3 或 5 节点)    │
              │  ┌──────────┐ ┌──────────┐ ┌──────────┐│
              │  │Controller│ │Controller│ │Controller││
              │  │    0     │ │    1     │ │    2     ││
              │  │ (Active) │ │(Follower)│ │(Follower)││
              │  └──────────┘ └──────────┘ └──────────┘│
              │         Raft 协议同步元数据日志          │
              └────────────────────┬───────────────────┘
                                   │
              ┌────────────────────┴───────────────────┐
              │            Broker 集群                │
              │   ┌────────┐ ┌────────┐ ┌────────┐    │
              │   │Broker 0│ │Broker 1│ │Broker 2│    │
              │   └────────┘ └────────┘ └────────┘    │
              └───────────────────────────────────────┘
```

**KRaft 核心组件**:

| 组件                       | 职责                                                              |
|----------------------------|-------------------------------------------------------------------|
| **Controller Quorum**      | 由奇数个 (3/5/7) Controller 节点组成,通过 Raft 协议选主        |
| **Active Controller**      | 当前 Leader 的 Controller,处理所有元数据变更请求               |
| **Follower Controller**    | 备份状态,Active 故障时接管                                       |
| **__cluster_metadata Topic** | 内部 Topic,持久化所有集群元数据(Raft Log)                   |

**KRaft 关键优势**:

| 优势                  | 说明                                                            |
|-----------------------|-----------------------------------------------------------------|
| **运维简化**          | 不再依赖 ZK,集群只需维护 Kafka 自身                            |
| **扩展性提升**        | 可支持 **百万级 Partition** (ZK 模式约 20 万上限)              |
| **故障恢复更快**      | Controller 故障切换毫秒级 (ZK 模式需 10-30 秒)                |
| **元数据一致性强**    | 基于 Raft 强一致性,避免脑裂                                    |
| **部署成本低**        | 少一套集群,减少 3-5 台 ZK 节点                                 |

### 3. ZooKeeper vs KRaft 对比

| 维度           | ZooKeeper 模式                  | KRaft 模式                            |
|----------------|----------------------------------|---------------------------------------|
| **元数据存储** | ZooKeeper ZNode                   | 内部 `__cluster_metadata` Topic       |
| **选举协议**   | ZAB(ZK 原子广播)                | Raft                                  |
| **Controller 数量** | 通常 1 个 Active + 多个 Standby | 3/5/7 节点 Quorum(避免单点)       |
| **故障切换**   | 10-30 秒                         | 毫秒级                                |
| **Partition 上限** | 受限于 ZK 性能                 | 百万级                                |
| **运维复杂度** | 高 (ZK + Kafka 双运维)          | 低(只运维 Kafka)                     |
| **成熟度**     | 稳定,生产用得多                 | 3.3+ 标记 GA,生产可逐步迁移          |
| **推荐状态**   | 仍可用,新集群建议直接 KRaft     | 未来方向                              |

## 七、控制器 Controller (集群的大脑)

**Controller** 是 Kafka 集群中**特殊的 Broker**,负责管理**整个集群的元数据和状态**。它是 Kafka 集群的"大脑"。

### 1. Controller 的核心职责

| 职责                      | 说明                                                                 |
|---------------------------|----------------------------------------------------------------------|
| **Broker 上下线管理**     | 监听 Broker 变化,维护集群成员列表                                  |
| **Topic 管理**            | 创建/删除 Topic,增加 Partition,调整副本因子                       |
| **分区 Leader 选举**      | 当某个 Partition 的 Leader 故障,从 ISR 中选新 Leader               |
| **副本管理**              | 维护副本状态(分区的 Follower 列表、ISR 集合)                     |
| **数据迁移**              | 副本重新分配、副本下线、磁盘均衡                                  |
| **配置管理**              | 动态更新 Topic / Broker 配置                                       |

### 2. Controller 选举机制

**ZK 模式**:

```text
所有 Broker 都尝试创建临时节点 /controller
→ 第一个创建成功的成为 Active Controller
→ 其他 Broker 在 /controller 上监听
→ Active Controller 故障时,临时节点消失
→ 监听者立刻抢锁,选举新的 Controller
```

**KRaft 模式**:

```text
Controller Quorum 内部通过 Raft 选主
→ 拥有最新 __cluster_metadata 日志的 Controller 成为 Active
→ Follower Controller 持续同步元数据
→ Active 故障时,Raft 自动选举新 Leader
```

## 八、协调服务详解

### 1. 旧协调服务:ZooKeeper

**架构层级**:Kafka 集群 ↔ ZooKeeper 集群(2 层)

ZooKeeper 为 Kafka 提供:

- 分布式协调与元数据存储
- 临时节点 + Watcher 机制实现 Broker 上下线感知
- Zab 协议保证元数据一致性

**ZK 选 Controller 流程**:

```text
1. Kafka 启动时,所有 Broker 尝试在 ZK 创建 /controller 临时节点
2. 只有第一个成功的 Broker 成为 Active Controller
3. 其他 Broker 在 /controller 上注册 Watcher
4. Active Controller 周期性写心跳到 ZK
5. 若 Active 故障,临时节点消失
6. Watcher 触发,其他 Broker 重新争抢创建 /controller
7. 新的 Active Controller 选举产生
```

ZK 模式下,**Controller 是单点**(虽然可以热备),所有元数据变更都要通过它处理。

### 2. 新协调服务:KRaft Controller Quorum

**架构层级**:单层(Kafka 内部完成)

**KRaft 选举流程**:

```text
1. Controller Quorum 节点启动,初始化为 Follower
2. Follower 在 election timeout 内未收到 AppendEntries
3. 变为 Candidate,发起 RequestVote RPC
4. 获得多数 (Quorum) 投票的 Candidate 成为新 Leader
5. 新 Leader 周期性发送心跳(AppendEntries)维持权威
6. 元数据变更通过 Leader 写入 __cluster_metadata Topic
7. Follower 同步日志,保证一致性
```

**Quorum 节点的角色与配置**:

| 角色                | 数量 (推荐) | 职责                                                  |
|---------------------|-------------|-------------------------------------------------------|
| **Broker + Controller** | 3-5       | 既是 Broker 也兼 Controller,节省资源               |
| **纯 Controller**   | 3-5         | 专门用于元数据管控,大集群推荐                       |
| **Quorum 大小**     | 奇数        | 3/5/7,容忍 N/2 故障(如 5 节点容忍 2 个故障)         |

**典型配置 (server.properties)**:

```properties
# KRaft 模式核心配置
process.roles=broker,controller      # 同时承担 broker 和 controller
node.id=1
controller.quorum.voters=1@node1:9093,2@node2:9093,3@node3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://node1:9092
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
```

## 十二、Kafka 3.x 与 Kafka 2.x 架构差异

| 维度               | Kafka 2.x                          | Kafka 3.x                              |
|--------------------|------------------------------------|----------------------------------------|
| **协调服务**       | ZooKeeper 强依赖                  | KRaft(3.3+ GA,旧版本保留 ZK 兼容)  |
| **Consumer API**   | 老的 SimpleConsumer / HighLevelConsumer | 统一为 KafkaConsumer (0.11+)         |
| **幂等性**         | 0.11+ 幂等 Producer               | 完善,默认支持幂等                     |
| **事务**           | 0.11+ 引入                         | 全面稳定,支持 EOS                     |
| **Broker 协议**    | 单一版本                           | 协议版本化管理,支持滚动升级           |
| **ZStandard**      | 不支持                             | 3.0+ 原生支持 ZSTD 压缩                |
| **Kafka Streams**  | 基础流处理                         | 性能优化,支持 Exactly-Once            |
| **KIP 改进**       | -                                  | KIP-500 (KRaft)、KIP-405 (Tiered Storage) 等 |
| **强删**           | 旧 Scala Consumer API 仍可用       | 0.10 旧 API 完全移除                   |
| **推荐状态**       | 维护模式                           | 新集群首选 3.x                         |

**Kafka 3.x 主要新特性**:

- **KRaft 控制器**:不再依赖 ZK,运维更简单
- **分层存储 (Tiered Storage)**:冷数据卸载到对象存储 (S3/OSS),突破本地磁盘限制
- **事务改进**:事务 API 简化,性能提升
- **强类型 API**:Kafka Streams DSL 增强

## 十三、Kafka 与传统 MQ 架构对比

| 维度                | Kafka                                | 传统 MQ (RabbitMQ/RocketMQ/ActiveMQ) |
|---------------------|--------------------------------------|--------------------------------------|
| **数据模型**        | 分布式日志 (Commit Log)              | 队列 / Topic + Queue                  |
| **消费模式**        | Pull (Consumer 主动拉取)             | Push (Broker 推送) / Pull 都有       |
| **消息顺序**        | 单 Partition 内有序                  | 单 Queue 严格有序                     |
| **持久化**          | 顺序写磁盘 + 副本                    | 内存 + 磁盘持久化                     |
| **堆积能力**        | 极强 (磁盘决定上限)                  | 一般 (内存积压可能影响性能)           |
| **回溯消费**        | 支持 (Offset 任意重置)              | 一般不支持或代价大                    |
| **延迟**            | 毫秒级 (通常 5-50 ms)               | 毫秒级 (通常 1-10 ms)                |
| **吞吐量**          | 百万级 TPS                            | 万级 TPS                              |
| **路由能力**        | 弱 (仅按 Key 哈希)                  | 强 (Routing Key / Binding)            |
| **消息优先级**      | 不支持                               | 支持                                  |
| **定时消息**        | 不支持                               | 支持 (RocketMQ Delay)                |
| **集群规模**        | 单集群百万级 Partition               | 一般千级                              |
| **典型场景**        | 日志流、事件溯源、CDC、大数据管道     | 业务消息、订单交易、通知推送           |

**Kafka 的核心定位**:**分布式事件流平台**,而非传统消息队列。它以**存储**和**流**为核心理念,把消息持久化日志作为不可变的事件流,在此基础上构建消息、存储、流处理三大能力。

## 十四、核心要点速记

- **Kafka 架构四大角色**:Producer、Broker、Consumer、协调服务 (ZK/KRaft)
- **Broker**:Kafka 服务节点,负责消息存储、转发、复制
- **Topic**:逻辑分类,物理上由多个 Partition 组成
- **Partition**:Topic 的物理分片,**有序追加日志**,并发处理的最小单位
- **Replica**:每个 Partition 的冗余拷贝,数量 = `replication-factor`
- **Leader / Follower**:每个 Partition 有 1 个 Leader 和 N-1 个 Follower
- **ISR**:与 Leader 保持同步的副本集合,Leader 选举的候选池
- **OSR**:落后 Leader 太多的副本,被踢出 ISR
- **HW (High Watermark)**:所有副本都已同步的最大 Offset,Consumer 可见边界
- **LEO (Log End Offset)**:下一条待写入消息的 Offset
- **AR = ISR + OSR**:所有副本的全集
- **Record 结构**:Topic + Partition + Key + Value + Timestamp + Headers
- **Partitioner**:决定 Record 发到哪个 Partition,默认 Key 哈希
- **Serializer**:负责 Record 序列化,Producer/Consumer 端必须配套
- **Consumer Group**:同一组内分区互斥,不同组各自独立消费
- **Offset**:分区级位移,默认 5 秒自动提交,生产环境建议手动同步
- **ZooKeeper 模式**:旧架构,依赖 ZK 存元数据 + 选举 Controller
- **KRaft 模式**:Kafka 3.3+ GA,内置 Raft 协议,**不再依赖 ZK**
- **Controller**:集群的大脑,负责元数据管理、Leader 选举、副本管理
- **Controller Quorum**:KRaft 模式下 3/5/7 节点组成,通过 Raft 协议选主
- **消息生命周期**:Producer → Partitioner → Accumulator → Broker Leader → Follower → Consumer Poll → Offset Commit
- **Kafka 3.x**:KRaft、分层存储、事务增强、ZSTD 压缩
- **Kafka ≠ 传统 MQ**:Kafka 是分布式事件流平台,以日志为核心,提供高吞吐和回溯消费
- **Partition 上限**:KRaft 模式支持百万级,ZK 模式约 20 万
- **典型场景**:日志收集、CDC、事件溯源、大数据管道、实时监控
