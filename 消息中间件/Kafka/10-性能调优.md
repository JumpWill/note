# 性能调优 (Performance Tuning)

## 一、性能调优概述

### 1. 调优目标

Kafka 性能调优的核心是平衡四个维度:

- **吞吐量 (Throughput)**:单位时间内能处理的消息数(MB/s 或 records/s)
- **延迟 (Latency)**:从生产到消费的端到端耗时(P50 / P99 / P999)
- **持久性 (Durability)**:消息不丢失的保证程度(由 `acks` 和副本数决定)
- **资源利用率 (Resource Efficiency)**:CPU、内存、磁盘 IO、网络的利用效率

这四个目标常常相互制约,**调优的本质是在它们之间找到业务可接受的平衡点**。

```text
  吞吐量 ↑
     │
     │        延迟 ↑
     │           │
     │           │   高吞吐 + 低延迟 = 极致性能(昂贵)
     │           │   高吞吐 + 高延迟 = 批量优先
     │           │   低吞吐 + 低延迟 = 实时优先
     │           │
     └──────────────────→ 资源
```

### 2. 性能调优金字塔

性能问题出现时,优化顺序非常重要,**应从金字塔顶端向下逐层排查**:

```text
                          ▲
                         ╱ ╲
                        ╱   ╲
                       ╱ 业务 ╲          ← 业务设计:消息大小、批量、压缩
                      ╱───────╲
                     ╱  Topic  ╲        ← 分区数、副本数、分区键
                    ╱  设计层   ╲
                   ╱─────────────╲
                  ╱   客户端参数   ╲      ← Producer/Consumer 参数
                 ╱   (应用层)      ╲
                ╱───────────────────╲
               ╱    Broker 配置      ╲   ← server.properties
              ╱      (Kafka 层)       ╲
             ╱─────────────────────────╲
            ╱        JVM 调优           ╲  ← GC、堆内存
           ╱─────────────────────────────╲
          ╱       操作系统 / 文件系统       ╲ ← ulimit、swappiness、文件系统
         ╱─────────────────────────────────╲
        ╱            硬件 / 网络             ╲ ← SSD、网卡、Jumbo Frame
       ╱─────────────────────────────────────╲

       ★ 上层问题占 80% 性能瓶颈 ★
       ★ 越往上性价比越高 ★
```

**调优黄金法则**:**先测量、后优化、不要凭直觉改参数**。

### 3. 调优方法论

```text
1. 定目标: SLA 是什么?
   - 峰值吞吐: 100 MB/s?
   - P99 延迟: < 50ms?
   - 可用性: 99.99%?

2. 测基线: 当前什么水平?
   - kafka-producer-perf-test 跑一遍
   - 记录关键指标 (records/sec、MB/sec、p99)

3. 定位瓶颈: CPU? 内存? IO? 网络?
   - iostat、vmstat、netstat、sar
   - JMX 指标: kafka.consumer:type=consumer-fetch-manager-metrics

4. 分析原因: 为什么慢?
   - 单条消息太小? 频繁 RPC?
   - acks=all 等待时间过长?
   - 磁盘随机 IO?
   - GC 停顿?

5. 改一处: 一次只改一个参数
   - 小步迭代, 避免蝴蝶效应

6. 测改进: 对比基线, 确认有效

7. 继续优化: 返回步骤 3
```

## 二、Broker 调优

Broker 是 Kafka 集群的核心节点,合理的 Broker 配置对性能至关重要。所有参数均在 `server.properties` 中配置。

### 1. 核心网络与 IO 线程

#### 1.1 num.network.threads

**作用**:处理网络请求的线程数(接收请求、把请求放入请求队列、从响应队列取出响应返回给客户端)。

```properties
# 默认 3, 推荐 = CPU 核数 (但不超过核数,因为是 IO 密集型)
num.network.threads = 8
```

**调整原则**:
- 纯网络 IO 密集型,设为 CPU 核数
- 业务混合型,可设为 CPU 核数的一半

#### 1.2 num.io.threads

**作用**:处理磁盘 IO 的线程数(从请求队列取请求、处理 Produce/Fetch 写盘读盘)。

```properties
# 默认 8, 推荐 = 磁盘数量 × 1~2 (单盘 SSA/NVMe 可调到 16)
num.io.threads = 16
```

**调整原则**:
- IO 线程过少 → 请求队列堆积,延迟升高
- IO 线程过多 → 线程切换开销,得不偿失
- 推荐: **磁盘数 × 1~3**

#### 1.3 num.replica.fetchers

**作用**:从源 Broker 拉取消息的副本 fetcher 线程数。

```properties
# 默认 1, 推荐 4~8 (副本同步是写入延迟的关键)
num.replica.fetchers = 4
```

**为什么重要**:如果 ISR 副本落后太多,Leader 会把它们踢出 ISR,影响 `acks=all` 的延迟。提高该值可加速副本同步。

### 2. 网络缓冲区

```properties
# Socket 发送缓冲区(默认 100KB)
socket.send.buffer.bytes = 102400

# Socket 接收缓冲区(默认 64KB)
socket.receive.buffer.bytes = 65536

# 推荐值 (10MB, 提高网络吞吐)
socket.send.buffer.bytes = 10485760
socket.receive.buffer.bytes = 10485760

# 请求最大大小(默认 1MB,影响单次请求消息量)
message.max.bytes = 10485760      # 10MB

# 单分区最大消息大小
max.message.bytes = 10485760
```

**注意**:`socket.*.buffer.bytes` 是 Kafka 端建议值,操作系统实际会 `min(SO_SNDBUF, wmem_default)`,所以也要调 OS 参数 `net.core.wmem_default`。

### 3. 日志刷盘策略

```properties
# 多久把内存数据 fsync 到磁盘
log.flush.interval.messages = 10000   # 每 10000 条消息刷一次
log.flush.interval.ms = 1000          # 或者每秒刷一次

# 推荐: 不要主动刷盘!
# Kafka 依赖 OS Page Cache + 副本机制保证可靠性
# OS 会异步刷盘,效率最高
log.flush.interval.messages = 10000
log.flush.interval.ms = 1000
```

**关键认识**:
- Kafka **不建议**频繁 fsync(由 OS 决定刷盘时机)
- 副本机制 (`replication.factor >= 3` + `acks=all`) 已经能保证可靠性
- 强制 fsync 反而会拖慢吞吐

### 4. 日志段与保留策略

```properties
# 每个日志段大小(默认 1GB)
log.segment.bytes = 1073741824       # 1GB
# 推荐: 1-2GB, 太小会频繁创建 segment, 太大恢复慢

# 日志保留时间(默认 7 天 = 168 小时)
log.retention.hours = 168
# 推荐: 根据业务调整, 一般 3-7 天

# 日志保留字节数 (二选一, -1 表示不限制)
log.retention.bytes = -1

# 日志段删除策略 (delete 或 compact)
log.cleanup.policy = delete
```

**经验**:
- `log.segment.bytes` 越大, 单文件 IO 顺序性越好, 但 segment 切换恢复越慢
- 高吞吐场景: 2-5 GB
- 低延迟场景: 256 MB - 1 GB

### 5. Broker 调优参数速查表

| 参数 | 默认值 | 推荐值 | 说明 |
|------|--------|--------|------|
| `num.network.threads` | 3 | CPU 核数 | 网络请求处理 |
| `num.io.threads` | 8 | 磁盘数 × 1~3 | 磁盘 IO 处理 |
| `num.replica.fetchers` | 1 | 4~8 | 副本同步 |
| `socket.send.buffer.bytes` | 100KB | 10MB | 发送缓冲 |
| `socket.receive.buffer.bytes` | 64KB | 10MB | 接收缓冲 |
| `message.max.bytes` | 1MB | 10MB | 单请求最大 |
| `log.segment.bytes` | 1GB | 1-2GB | 日志段大小 |
| `log.retention.hours` | 168 | 72-168 | 保留时间 |
| `log.flush.interval.ms` | 9223372036854775807(不刷) | 1000 | 刷盘间隔 |
| `num.partitions` (默认) | 1 | 根据业务 | 每 topic 默认分区 |

## 三、Topic 设计调优

Topic 是 Kafka 的逻辑数据单元,合理的 Topic 设计是性能的基础。

### 1. 分区数选择

**分区数是 Kafka 性能的关键设计参数**,影响并行度。

#### 1.1 分区数与吞吐的关系

```text
分区数 = Producer 写并行度上限 = Consumer 读并行度上限

  ┌──────────────────────────────────────────┐
  │   分区数与吞吐的关系                       │
  │                                          │
  │   吞吐 ↑                                  │
  │        │     ╱  ← 线性增长区              │
  │        │    ╱                              │
  │        │   ╱                               │
  │        │  ╱                                │
  │        │ ╱     ╱────  ← 趋于稳定         │
  │        │╱     ╱                            │
  │        └────────────────────→ 分区数      │
  │             ▲                              │
  │          最优点                             │
  │      (再增加分区数, 吞吐不再增长)            │
  └──────────────────────────────────────────┘
```

分区数过少 → 写入 / 消费成为瓶颈
分区数过多 → Controller 压力大,文件句柄多,故障恢复慢

#### 1.2 分区数计算公式

```text
分区数 = max(
    目标吞吐 / 单分区吞吐,
    消费者实例数,
    生产者实例数 × 写并行度
)

单分区吞吐参考值:
  - 普通磁盘 + 默认参数: 10-30 MB/s
  - SSD + 调优参数:   50-100 MB/s
  - NVMe + 极致调优:  100-300 MB/s
```

**示例**:
```text
目标: 1 GB/s 总吞吐
单分区吞吐: 100 MB/s
需要分区数: 1024 MB/s ÷ 100 MB/s = 11
考虑冗余: 16-32 分区
消费者实例数: 20 → 分区数 ≥ 20
最终选择: 32 分区
```

#### 1.3 分区数过多的问题

```text
- 文件句柄增加(每分区需要 2 个文件: index + log)
- Controller 状态管理压力大 (ZK 或 KRaft)
- 故障恢复时 Leader 选举慢
- 端到端延迟增加(更多网络跳)
- 内存中维护的对象增多(每分区 ~264B 元数据)
```

**经验上限**: 单 Broker 分区数不超过 **2000-4000**,集群不超过 **10000-20000**。

### 2. 副本数选择

副本数决定了可靠性和读吞吐(从副本可读)。

| 副本数 | 可靠性 | 读吞吐 | 磁盘占用 | 适用场景 |
|--------|--------|--------|----------|----------|
| **1** | 最低 | 1x | 1x | 开发测试 |
| **2** | 中 | 2x | 2x | 非关键业务 |
| **3** | 高 | 3x | 3x | **生产推荐** |
| **5** | 极高 | 5x | 5x | 金融级 |

**3 副本 vs 5 副本**:

```text
3 副本 (生产标准):
  - 可容忍 1 副本故障
  - 写入延迟: 同步 2 个副本
  - 成本: 3 倍磁盘

5 副本 (金融级):
  - 可容忍 2 副本同时故障
  - 写入延迟: 同步 4 个副本 (更慢!)
  - 成本: 5 倍磁盘
  - 仅在极高 SLA 场景使用
```

### 3. 分区键 (Key) 选择

分区键决定了消息落入哪个分区,**分区键选择不当会导致数据倾斜**。

#### 3.1 数据倾斜问题

```text
场景: 用 user_id 作为 key, 大 V 用户消息量占 50%

  分区 0 (user_A 大 V):  50,000 msg/s  ← 热点!
  分区 1 (普通用户):      1,000 msg/s
  分区 2 (普通用户):      1,000 msg/s
  分区 3 (普通用户):      1,000 msg/s
  
  → 分区 0 成为瓶颈, 整体吞吐受限于它
```

#### 3.2 分区键设计原则

```text
✓ 高基数 (distinct 值多):
    - user_id (百万级)
    - order_id (千万级)
    - device_id

✗ 低基数 (distinct 值少):
    - status (只有几个值)
    - region (只有几十个值)
    - 布尔字段 (true/false)
```

#### 3.3 解决热点方案

```java
// 方案 1: key 加盐 (推荐)
String saltedKey = user_id + "_" + (hash(user_id) % 16);
// 同一用户的消息分散到 16 个分区, 处理时再聚合

// 方案 2: 使用 murmur2 自定义分区器
public class HashPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        // 自定义哈希
        return Math.abs(Murmur2.hash(keyBytes)) % cluster.partitionCountForTopic(topic);
    }
}

// 方案 3: 不指定 key, 让 Kafka 轮询分配 (Round Robin)
// 但这会失去消息顺序保证
producer.send(new ProducerRecord<>("topic", value));
```

## 四、Producer 调优

Producer 是性能的关键路径,**调优 Producer 通常能带来 5-10 倍的吞吐提升**。

### 1. 核心参数

#### 1.1 batch.size

**作用**:Producer 将多条消息合并为一个 batch 发送,**直接决定单次请求的消息量**。

```properties
# 默认 16KB, 推荐 64KB - 256KB (根据消息大小调整)
batch.size = 65536      # 64KB
```

```text
batch.size = 16KB 时:
  每次请求: ~10 条消息 (假设 1.5KB/条)
  网络利用率: 低

batch.size = 128KB 时:
  每次请求: ~80 条消息
  网络利用率: 高
  吞吐提升: 5-10 倍
```

**调整原则**:
- 消息小 (< 1KB): batch.size = 256KB - 1MB
- 消息中 (1-10KB): batch.size = 64KB - 256KB
- 消息大 (> 10KB): batch.size = 32KB - 64KB

#### 1.2 linger.ms

**作用**:发送前等待更多消息加入 batch 的时间。

```properties
# 默认 0 (立即发送, 不等)
linger.ms = 10
```

```text
linger.ms = 0:   立即发送, batch 永远装不满, 网络利用率低
linger.ms = 5:   等待 5ms, 大概率装满 batch
linger.ms = 20:  等待 20ms, batch 几乎必满, 但延迟增加 20ms

推荐: 5-20ms (吞吐和延迟的甜蜜点)
```

#### 1.3 compression.type

**作用**:压缩消息体,减少网络传输和磁盘占用。

```properties
# 默认 none, 推荐 lz4 或 zstd
compression.type = lz4
```

| 压缩算法 | 压缩比 | CPU 开销 | 速度 | 推荐场景 |
|----------|--------|----------|------|----------|
| **none** | 1x | 0 | 最快 | 已压缩数据 (图片、视频) |
| **gzip** | 3-4x | 高 | 慢 | 存档、低吞吐 |
| **snappy** | 2x | 中 | 快 | 通用 |
| **lz4** | 2-3x | 低 | **最快** | **生产推荐** |
| **zstd** | 3-4x | 中 | 快 | 高压缩比 + 速度兼顾 |

#### 1.4 acks

**作用**:Producer 写入确认级别。

```properties
# acks = 0: 不等待确认, 最快, 最不安全
# acks = 1: 等 Leader 写入, 中等
# acks = all (或 -1): 等所有 ISR 副本写入, 最慢, 最安全
acks = all
```

| acks | 延迟 | 可靠性 | 吞吐 | 适用 |
|------|------|--------|------|------|
| `0` | 最低 | 最差 | 最高 | 日志收集、可容忍丢失 |
| `1` | 中 | 中 | 中 | 内部系统 |
| **`all`** | 高 | **最高** | 中 | **生产推荐** |

#### 1.5 buffer.memory

**作用**:Producer 缓冲未发送消息的总内存。

```properties
# 默认 32MB, 高吞吐场景加大
buffer.memory = 67108864    # 64MB
```

**触发背压**: 缓冲区满时,`producer.send()` 会阻塞 (默认 `max.block.ms=60000`)。

### 2. Producer 完整配置示例 (Java)

```java
Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092,broker2:9092,broker3:9092");

// === 性能核心参数 ===
props.put("acks", "all");                    // 可靠性
props.put("batch.size", 65536);              // 64KB batch
props.put("linger.ms", 10);                  // 等待 10ms
props.put("compression.type", "lz4");        // LZ4 压缩
props.put("buffer.memory", 67108864);        // 64MB 缓冲

// === 可靠性补充 ===
props.put("retries", Integer.MAX_VALUE);     // 无限重试
props.put("enable.idempotence", true);       // 幂等性 (防重复)
props.put("max.in.flight.requests.per.connection", 5);  // 幂等下最多 5

// === 网络优化 ===
props.put("send.buffer.bytes", 131072);      // 128KB socket 发送缓冲
props.put("receive.buffer.bytes", 65536);    // 64KB socket 接收缓冲
props.put("request.timeout.ms", 30000);

// 创建 Producer
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

### 3. Producer 调优参数速查表

| 参数 | 默认值 | 推荐值 | 影响 |
|------|--------|--------|------|
| `batch.size` | 16KB | 64KB-256KB | 吞吐 ↑↑ |
| `linger.ms` | 0 | 5-20 | 吞吐 ↑↑, 延迟 ↑ |
| `compression.type` | none | lz4 / zstd | 吞吐 ↑↑, CPU ↑ |
| `acks` | 1 | all | 可靠性 ↑, 吞吐 ↓ |
| `buffer.memory` | 32MB | 64-128MB | 抗突发能力 |
| `retries` | 0 | MAX_VALUE | 可靠性 |
| `enable.idempotence` | false | true | 防重复 |
| `max.in.flight.requests.per.connection` | 5 | 5 | 吞吐 |
| `send.buffer.bytes` | 128KB | 256KB-1MB | 网络吞吐 |

## 五、Consumer 调优

### 1. 核心参数

#### 1.1 fetch.min.bytes

**作用**:Consumer 每次 fetch 请求最少获取多少字节,**控制 Consumer 等待 batch 装满**。

```properties
# 默认 1B (来一个字节就返回), 推荐 1KB - 10KB
fetch.min.bytes = 1024
```

```text
fetch.min.bytes = 1B:
  几乎立即返回, 但每次请求字节少, 网络利用率低

fetch.min.bytes = 1MB:
  等待 batch 装满 1MB, 吞吐提升, 但延迟增加
```

#### 1.2 fetch.max.wait.ms

**作用**:等待 fetch.min.bytes 装满的最长时间(超时即返回)。

```properties
# 默认 500ms
fetch.max.wait.ms = 500
```

**配合使用**:`fetch.min.bytes=10KB + fetch.max.wait.ms=500ms`,要么 batch 装满 10KB,要么等 500ms,谁先满足返回谁。

#### 1.3 max.poll.records

**作用**:单次 poll() 返回的最大消息数。

```properties
# 默认 500, 根据业务处理能力调整
max.poll.records = 500
```

```text
max.poll.records 太小: 频繁 poll, RPC 开销大
max.poll.records 太大: 单次处理时间长, 触发 rebalance 风险
推荐: 100-1000, 根据单条消息处理时间计算
```

**计算公式**:
```text
max.poll.records = 单批处理时间 ≤ max.poll.interval.ms / 2
```

#### 1.4 max.poll.interval.ms

**作用**:两次 poll 之间的最大间隔,**超过则被认为 consumer 已死,触发 rebalance**。

```properties
# 默认 5 分钟
max.poll.interval.ms = 300000
```

**触发场景**:
```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    // 处理每批消息
    for (ConsumerRecord<String, String> record : records) {
        processRecord(record);   // 如果 processRecord 很慢, > 5min 则触发 rebalance
    }
}
```

**优化方案**:
- 异步处理 + 手动提交
- 加大 `max.poll.interval.ms`

#### 1.5 session.timeout.ms & heartbeat.interval.ms

```properties
# session 超时(默认 10s, Broker 多久没收到心跳认为 consumer 死了)
session.timeout.ms = 10000

# 心跳间隔(默认 3s, 必须小于 session.timeout.ms / 3)
heartbeat.interval.ms = 3000
```

## 六、JVM 调优

Kafka Broker 是 JVM 应用,JVM 调优对稳定性至关重要。

### 1. Heap Size

```text
Kafka 特殊之处:
  - Kafka 大量使用 OS Page Cache, 不强依赖 JVM Heap
  - Heap 主要用于: 消息批次缓冲、索引、Producer 缓存
  - 堆越大, GC 越慢, 但 Page Cache 越少
  
推荐: 6-8GB Heap, 其余内存留给 Page Cache
```

```bash
# 启动脚本 (kafka-server-start.sh)
export KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
# Xms = Xmx, 避免堆动态调整带来的停顿
```

```text
  物理内存 64GB:
  ┌─────────────────────┐
  │ Page Cache: 50GB    │  ← 操作系统管理, 用于缓存 log 文件
  ├─────────────────────┤
  │ Heap: 6GB           │  ← JVM 堆, 用于批次缓冲
  ├─────────────────────┤
  │ 系统 / 其他: 8GB     │
  └─────────────────────┘
```

### 2. GC 选择

| GC | 适用堆大小 | 停顿时间 | 推荐度 |
|-----|-----------|----------|--------|
| **CMS** | < 8GB | 中 | 老项目 |
| **G1** | 6-32GB | 低 | **推荐** |
| **ZGC** | > 32GB | < 1ms | 超大堆 |
| **Shenandoah** | > 32GB | < 1ms | RedHat 系 |

#### 2.1 G1 推荐配置 (JDK 11+ 默认)

```bash
export KAFKA_JVM_PERFORMANCE_OPTS="-server \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:+ExplicitGCInvokesConcurrent"
```

**关键参数**:
- `MaxGCPauseMillis=20`: 目标最大停顿 20ms
- `InitiatingHeapOccupancyPercent=35`: 堆使用 35% 触发并发标记 (避免 Full GC)
- `ExplicitGCInvokesConcurrent`: 显式 GC 也并发执行

#### 2.2 避免 Full GC

```text
Full GC 触发原因:
  - 老年代满
  - 永久代/元空间满
  - System.gc() 调用 (需禁用)
  - Promotion Failed (Survivor 不够)

预防:
  - 堆不要设太大 (> 32GB, Full GC 难)
  - 启用 G1/ZGC (并发收集)
  - 监控 GC 日志: -Xlog:gc*:file=gc.log:time
```

### 3. JVM 参数推荐

```bash
# Heap
-Xms6g
-Xmx6g

# GC (G1)
-XX:+UseG1GC
-XX:MaxGCPauseMillis=20

-XX:+ParallelRefProcEnabled
-XX:+UseStringDeduplication

# 元数据
-XX:MetaspaceSize=96m
-XX:MaxMetaspaceSize=256m

# 异常处理

```

## 八、磁盘 IO 调优

Kafka 的性能严重依赖磁盘 IO 性能,**磁盘往往是第一瓶颈**。

### 1. 顺序 IO vs 随机 IO

**核心认识**: Kafka 通过**顺序追加写**+ **Page Cache**+ **零拷贝**, 把随机读写变成顺序读写, 即使是 HDD 也能达到很高吞吐。

```text
传统数据库 (MySQL InnoDB):
  随机读 + 随机写 (B+Tree 索引)
  → 严重依赖 SSD

Kafka:
  顺序写 (追加 log)
  + Page Cache (热数据在内存)
  + sendfile() / mmap (零拷贝读)
  → HDD 也能扛高吞吐 (但 SSD 更好)
```

### 2. 多盘分散 (RAID vs JBOD)

**强烈推荐 JBOD (Just a Bunch Of Disks)**, 不要用 RAID5/6!

```text
RAID5/6:
  - 写性能差 (每次写需要读 + 计算校验 + 写)
  - 单盘故障重建时间长 (TB 级可能 24h+)
  - 重建期间 IO 受影响

JBOD (Kafka 推荐):
  - 每盘独立, 单盘故障只影响该盘数据
  - 通过多副本保证可靠性 (不需要 RAID)
  - Kafka 通过 log.dirs 配置多块盘
```

```properties
# server.properties
log.dirs=/kafka/disk1,/kafka/disk2,/kafka/disk3,/kafka/disk4

# Kafka 自动将不同分区分散到不同磁盘
```

### 3. SSD vs HDD

| 维度 | HDD (7200 RPM) | SATA SSD | NVMe SSD |
|------|----------------|----------|----------|
| IOPS | 75-150 | 50K-100K | 100K-500K |
| 顺序读 | 200 MB/s | 550 MB/s | 3-7 GB/s |
| 顺序写 | 200 MB/s | 500 MB/s | 2-5 GB/s |
| 延迟 | 5-10 ms | < 0.1 ms | < 0.05 ms |
| 价格/TB | 低 | 中 | 高 |

**选型建议**:
```text
- 日志收集 (追求成本): HDD + 副本数=3 ✓
- 业务消息 (延迟敏感): SATA SSD ✓
- 金融/支付 (极致性能): NVMe SSD
```

## 十二、性能调优 Checklist

按优先级排序的完整 Checklist:

### 1. 业务层 (★ 最重要)

- [ ] **消息大小合理**: 避免单条 > 1MB
- [ ] **使用批量发送**: 应用层合并小消息
- [ ] **避免空 key**: 导致粘性分区器
- [ ] **压缩在 Producer**: 不要存已压缩数据

### 2. Topic 设计

- [ ] **分区数足够**: `max(目标吞吐/单分区, 消费者数)`
- [ ] **副本数 ≥ 3**: 生产环境最低 3 副本
- [ ] **分区键高基数**: 避免热点
- [ ] **业务隔离**: 不同业务用不同 topic, 避免相互影响

### 3. Producer

- [ ] `batch.size = 64KB-256KB`
- [ ] `linger.ms = 5-20`
- [ ] `compression.type = lz4 / zstd`
- [ ] `acks = all`
- [ ] `enable.idempotence = true`
- [ ] `buffer.memory ≥ 64MB`

### 4. Consumer

- [ ] `fetch.min.bytes = 1KB-10KB`
- [ ] `max.poll.records = 100-1000`
- [ ] `enable.auto.commit = false` (手动提交)
- [ ] 异步处理避免 `max.poll.interval.ms` 超时

### 5. Broker

- [ ] `num.io.threads = 磁盘数 × 1~3`
- [ ] `num.network.threads = CPU 核数`
- [ ] `num.replica.fetchers = 4-8`
- [ ] `socket.*.buffer.bytes = 10MB`
- [ ] `log.segment.bytes = 1-2GB`

### 6. JVM

- [ ] `Xms = Xmx = 6-8GB`

### 8. 硬件 / 网络

## 十三、实战案例:从 10MB/s 到 1GB/s

### 1. 背景

某电商订单系统, Kafka 集群 3 Broker, 8 核 16GB 内存, 7200 RPM HDD × 4。
最初吞吐只有 10 MB/s, 业务高峰期消息积压严重。

### 2. 问题诊断

```bash
# 1. 压测基线
bin/kafka-producer-perf-test.sh --topic orders --num-records 1000000 --record-size 1024

# 结果
# 10000 records/sec, 10 MB/sec, avg latency 200ms, max latency 2000ms
# 结论: 严重不足, 业务需要 200 MB/sec
```

```bash
# 2. 看 OS 指标
iostat -x 1
# %util: 95%+, await: 50ms+   ← 磁盘 IO 瓶颈!
vmstat 1
# si/so: 不为 0                ← 有 swap
sar -n DEV 1
# 网卡: 200 Mbps               ← 网络也接近瓶颈
```

```bash
# 3. 看 JVM
jstat -gcutil <pid>
# O: 85%+                     ← 老年代占用高, Full GC 频繁
```

### 3. 优化步骤

#### 3.1 第一轮: Producer 参数调优

```java
// 修改前
batch.size = 16384            // 16KB
linger.ms = 0
compression.type = none
acks = 1

// 修改后
batch.size = 131072           // 128KB
linger.ms = 20
compression.type = lz4
acks = all
buffer.memory = 67108864      // 64MB
```

**效果**: 10 MB/s → **80 MB/s** (8 倍提升)

#### 3.2 第二轮: Topic 分区扩容

```bash
# 分区从 6 扩到 24
kafka-topics.sh --alter --topic orders --partitions 24
```

**效果**: 80 MB/s → **200 MB/s**

#### 3.3 第三轮: 操作系统与硬件

```bash
# 1. 调整 OS
ulimit -n 100000
sysctl -w vm.swappiness=1
sysctl -w net.core.wmem_max=16777216

# 2. 文件系统改为 XFS, 挂载 noatime
umount /data && mkfs.xfs -f /dev/sdb && mount -o noatime /dev/sdb /data

# 3. 升级到 SSD (3 块 NVMe)

# 4. 万兆网卡 + Jumbo Frame
ip link set eth0 mtu 9000
```

**效果**: 200 MB/s → **500 MB/s**

#### 3.4 第四轮: Broker + JVM 调优

```properties
# server.properties
num.network.threads = 8
num.io.threads = 16
num.replica.fetchers = 4
socket.send.buffer.bytes = 10485760
socket.receive.buffer.bytes = 10485760
log.segment.bytes = 2147483648      # 2GB
log.dirs=/data1,/data2,/data3       # 多盘分散
```

```bash
# Kafka JVM
export KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
export KAFKA_JVM_PERFORMANCE_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=20"
```

**效果**: 500 MB/s → **800 MB/s**

#### 3.5 第五轮: 极致优化

```bash
# 1. 增加 broker 到 6 节点
# 2. 分区扩到 60
# 3. 启用 sendfile / mmap
```

**效果**: 800 MB/s → **1 GB/s**

### 4. 优化效果汇总

```text
优化前:   10 MB/s,   P99 延迟 2000ms, 磁盘 IO 100%
         ↓ Producer 调优 (批 + 压 + linger)
         80 MB/s,    P99 延迟 500ms,  磁盘 IO 80%
         ↓ 分区扩容 (6 → 24)
         200 MB/s,   P99 延迟 200ms,  磁盘 IO 60%
         ↓ OS + SSD + 万兆
         500 MB/s,   P99 延迟 80ms,   磁盘 IO 40%
         ↓ Broker + JVM 调优
         800 MB/s,   P99 延迟 30ms,   磁盘 IO 25%
         ↓ 扩容 broker + 分区
         1 GB/s,     P99 延迟 15ms,   磁盘 IO 15%   ✓
```

**100 倍提升, 主要来自 Producer 调优和硬件升级**。

### 5. 经验教训

```text
1. Producer 调优性价比最高 (8 倍)
2. 分区扩容要适度, 不要一次扩太多
3. OS 参数调优零成本但收益明显
4. 硬件升级要分阶段, 不要一开始就堆砌
5. 监控先行, 否则不知道瓶颈在哪
6. 每次只改一处, 才能定位有效优化
```

## 十四、核心要点速记

### 1. 性能调优金字塔

```text
业务设计 → Topic 设计 → 客户端参数 → Broker 配置 → JVM → OS → 硬件

★ 80% 性能问题在上三层
★ 越往上性价比越高
```

### 2. 关键参数速记

| 参数 | 默认 | 推荐 | 提升 |
|------|------|------|------|
| `batch.size` | 16KB | 128KB | 吞吐 ×5-10 |
| `linger.ms` | 0 | 10-20 | 吞吐 ×2-3 |
| `compression.type` | none | lz4 | 吞吐 ×2-3 |
| `fetch.min.bytes` | 1B | 10KB | Consumer ×2-5 |
| Heap Size | - | 6-8GB | 避免 Full GC |
| `vm.swappiness` | 60 | 1 | 避免 swap |

### 3. 调优口诀

- **批大等小** — batch.size 大, linger.ms 小
- **压快多发** — lz4/zstd 压缩 + 异步发送
- **副本够多** — `replication.factor=3 + acks=all`
- **分区分散** — 多分区 + 多磁盘 + 多 Broker
- **堆要适中** — 6-8GB, 让位 Page Cache
- **页内核优** — 调 OS + 文件系统 + 网卡
- **监控先行** — 先有基线, 后有优化

### 4. 性能基线参考

```text
默认 Producer (16KB batch, linger=0, no compression):
  ~ 10-30 MB/s per Broker

优化 Producer (128KB batch, linger=10, lz4):
  ~ 100-300 MB/s per Broker

极致优化 (SSD + 万兆 + 32 分区):
  ~ 500 MB/s+ per Broker

单分区吞吐上限:
  HDD:  10-30 MB/s
  SSD:  50-100 MB/s
  NVMe: 100-300 MB/s
```

### 5. 排查流程

```text
1. 现象: 吞吐不达预期 / 延迟高 / Lag 积压
2. 压测: kafka-producer-perf-test 跑基线
3. OS 指标: iostat / vmstat / sar / netstat
4. JVM 指标: GC 日志 + jstat
5. Kafka 指标: JMX / kafka_exporter
6. 定位瓶颈: CPU / 磁盘 / 网络 / GC
7. 一处优化, 一次只改一个参数
8. 对比基线, 验证有效
9. 继续循环
```

### 6. 黄金法则

1. **先测量后优化** — 没有数据不要改参数
2. **一次改一处** — 避免蝴蝶效应
3. **从上层到下层** — 业务问题占 80%
4. **Producer 优先** — 投入小收益大
5. **副本是基础** — 性能建立在可靠性之上
6. **监控全覆盖** — 没有监控就没有优化
7. **业务驱动** — 性能服务于业务 SLA
