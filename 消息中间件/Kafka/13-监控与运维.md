## 一、Kafka 监控概述

### 1. 为什么需要监控 Kafka

Kafka 作为分布式消息中间件,跑在生产环境必须回答四个核心问题:

- **是否活着**:Broker / Controller / Coordinator 进程是否健康,集群是否有 Leader 不可用
- **跑得快不快**:Producer/Consumer 延迟、吞吐量、Broker 网络/磁盘 IO
- **数据有没有丢**:副本是否同步 (ISR)、Controller 是否切换、消费位移是否提交
- **扛不扛得住**:磁盘空间、网络带宽、Page Cache 利用率,是否需要扩容

Kafka 监控缺失带来的"四大经典故障":

```text
故障 1: 磁盘写满
  现象: producer 写入报 "NotEnoughReplicasException"
  根因: 没有监控磁盘使用率,lag 不断增长但没人发现
  解决: 监控 kafka-data 目录使用率 + lag 趋势

故障 2: Consumer 假死
  现象: 业务数据停止更新,但没人告警
  根因: 消费者 group rebalance 卡死,offset 不再提交
  解决: 监控 consumer offset 是否持续增长

故障 3: ISR 频繁收缩
  现象: 写入性能下降,偶发 NotEnoughReplicas
  根因: Follower 副本因磁盘慢或网络抖动被踢出 ISR
  解决: 监控 IsrShrinksPerSec,排查慢节点

故障 4: Controller 不可用
  现象: 集群几乎所有元数据操作失败
  根因: 没有 ActiveControllerCount 告警,Controller 切换未感知
  解决: 监控 kafka_controller_stats_active_controller_count
```

**铁律**:线上 Kafka 集群必须同时具备**指标监控** + **日志监控** + **告警** 三套体系。

### 2. Kafka 监控的层次

Kafka 监控分为四层,从下到上递进:

| 层级 | 内容 | 工具 |
|------|------|------|
| **硬件层** | CPU、内存、磁盘、网卡、磁盘 IO | node_exporter, iostat, vmstat |
| **JVM 层** | GC、Heap、线程数、JMX | JMX Exporter, jstat |
| **Broker 层** | Controller、Replica、ISR、网络请求 | kafka_exporter, JMX |
| **业务层** | Producer/Consumer 延迟、消息积压、消息丢失 | kafka-lag-exporter, Burrow, 自研探针 |

## 二、内置监控指标 (JMX 体系)

### 1. JMX 是什么

Kafka Broker 是一个标准的 JVM 进程,**所有运行指标都通过 JMX (Java Management Extensions) 暴露**。JMX 是 Kafka 监控的底层基础。

```text
┌──────────────────────────────────────────────────────────┐
│  Kafka Broker (JVM 进程)                              │
│   ↓                                                    │
│  MBean (Managed Bean, 被管理的对象)                    │
│   ↓                                                    │
│  JMX MBean Server (内置于 JVM)                         │
│   ↓                                                    │
│  远程访问方式:                                          │
│    1. JMX Exporter (Prometheus 格式,推荐)              │
│    2. JMX Transporter (InfluxDB/Graphite)             │
│    3. jconsole / Java Mission Control (GUI)           │
│    4. Jolokia (HTTP API)                              │
└──────────────────────────────────────────────────────────┘
```

### 2. 开启 JMX 远程访问

修改 Kafka 启动脚本 `kafka-server-start.sh`,加入 JMX 参数:

```bash
# 在 KAFKA_HEAP_OPTS 同级位置添加 JMX 配置
export KAFKA_JMX_OPTS="-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9999 \
  -Dcom.sun.management.jmxremote.local.only=false \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false"

# 或者使用 KAFKA_OPTS (生产推荐)
export KAFKA_OPTS="$KAFKA_OPTS -Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9999 \
  -Dcom.sun.management.jmxremote.rmi.port=9999 \
  -Djava.rmi.server.hostname=$(hostname -I | awk '{print $1}')"
```

**生产环境必须开启鉴权**:

```bash
# 1. 创建密码文件
cp $KAFKA_HOME/config/jmxremote.password.template \
   $KAFKA_HOME/config/jmxremote.password
# 修改 jmxremote.password,为 monitorRole 设置密码
# monitorRole QED
# controlRole R&D

chmod 600 $KAFKA_HOME/config/jmxremote.password

# 2. 配置访问控制文件
# jmxremote.access
# monitorRole readonly
# controlRole readwrite

# 3. 启动参数添加认证
export KAFKA_OPTS="$KAFKA_OPTS \
  -Dcom.sun.management.jmxremote.port=9999 \
  -Dcom.sun.management.jmxremote.authenticate=true \
  -Dcom.sun.management.jmxremote.password.file=$KAFKA_HOME/config/jmxremote.password \
  -Dcom.sun.management.jmxremote.access.file=$KAFKA_HOME/config/jmxremote.access"
```

### 3. Kafka MBean 命名空间

Kafka 的所有 MBean 都按 `kafka.<type>:<name>` 命名空间组织:

```text
kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec
kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec
kafka.server:type=BrokerTopicMetrics,name=BytesOutPerSec
kafka.server:type=BrokerTopicMetrics,name=RequestsPerSec
kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions
kafka.network:type=RequestMetrics,name=TotalTimeMs,request=Produce
kafka.log:type=Log,name=LogEndOffset,topic=*,partition=*
kafka.controller:type=ControllerStats,name=ActiveControllerCount
kafka.consumer:type=consumer-fetch-manager-metrics,client-id=*
kafka.producer:type=producer-metrics,client-id=*
```

### 4. 主要 MBean 模块对照表

| MBean 前缀 | 模块 | 主要指标 |
|-----------|------|----------|
| `kafka.server:type=BrokerTopicMetrics` | Broker 核心流量 | MessagesInPerSec, BytesInPerSec, BytesOutPerSec |
| `kafka.server:type=ReplicaManager` | 副本管理 | UnderReplicatedPartitions, IsrExpandsPerSec, IsrShrinksPerSec |
| `kafka.server:type=KafkaRequestHandlerPool` | 请求处理线程池 | NetworkProcessorAvgIdlePercent, RequestHandlerAvgIdlePercent |
| `kafka.network:type=RequestMetrics` | 网络请求延迟分位数 | TotalTimeMs, FetchTimeMs, ProduceTimeMs (P50/P95/P99) |
| `kafka.log:type=Log` | 日志段 | LogEndOffset, NumLogSegments, Size |
| `kafka.controller:type=ControllerStats` | Controller | ActiveControllerCount, UncleanLeaderElectionsPerSec |
| `kafka.consumer:type=*` | Consumer 客户端 | records-consumed-rate, fetch-latency-avg, records-lag-max |
| `kafka.producer:type=*` | Producer 客户端 | record-send-rate, request-latency-avg, buffer-available-bytes |
| `java.lang:type=Memory` / `GarbageCollector` | JVM 运行时 | HeapMemoryUsage, GcCount, GcTime |

### 5. 用 jconsole 验证 JMX

```bash
# 启动 jconsole (本地机器)
jconsole
# 远程进程: service:jmx:rmi:///jndi/rmi://<broker-ip>:9999/jmxrmi

# 或用命令行工具 cmdline-jmxclient
java -jar cmdline-jmxclient.jar - <broker-ip>:9999 \
  "kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec"
```

### 6. JMX 监控的坑

```text
坑 1: JMX 端口未配置认证 → 任何人可读取敏感指标
坑 2: JMX RMI 协议走随机端口 → 防火墙规则难写 → 务必固定 rmi.port
坑 3: JMX Exporter 默认拉取所有 MBean → 内存/CPU 飙升 → 必须白名单
坑 4: Kafka 2.0+ 默认 jmx_server 已禁用 ssl → 生产必须显式开启
坑 5: 容器化部署 JMX 跨网络访问复杂 → 用 JMX Exporter sidecar 更稳
```

## 三、核心监控指标详解

### 1. Broker 核心指标

#### 1.1 流量类

| 指标 | MBean | 单位 | 健康阈值 | 含义 |
|------|-------|------|----------|------|
| `MessagesInPerSec` | BrokerTopicMetrics | msg/s | < 集群瓶颈 | Broker 接收的消息速率 |
| `BytesInPerSec` | BrokerTopicMetrics | byte/s | < 网卡带宽 | Broker 接收的字节速率 |
| `BytesOutPerSec` | BrokerTopicMetrics | byte/s | < 网卡带宽 | Broker 发送的字节速率 |
| `RequestsPerSec` | BrokerTopicMetrics | req/s | < 处理能力 | 每秒请求数 (Produce/Fetch 都算) |

**关键观察**: `BytesInPerSec` + `BytesOutPerSec` 之和应该 < 网卡带宽的 70%。

#### 1.2 副本同步类

| 指标 | MBean | 健康值 | 异常处理 |
|------|-------|--------|----------|
| `UnderReplicatedPartitions` | ReplicaManager | 0 | > 0 → 检查 ISR 收缩、Broker 宕机 |
| `IsrShrinksPerSec` | ReplicaManager | 接近 0 | 持续 > 0 → 网络抖动或磁盘慢 |
| `IsrExpandsPerSec` | ReplicaManager | 接近 0 | 持续 > 0 → 集群不稳定 |
| `ActiveControllerCount` | ControllerStats | 1 (全集群) | 0 → 集群脑裂或 Controller 不可用 |

#### 1.3 网络/线程类

| 指标 | MBean | 健康值 | 含义 |
|------|-------|--------|------|
| `NetworkProcessorAvgIdlePercent` | NetworkThread | > 30% | 网络线程空闲率,< 30% 需扩容或加分区 |
| `RequestHandlerAvgIdlePercent` | RequestHandlerPool | > 30% | 请求处理线程空闲率 |
| `TotalTimeMs` (P99) | RequestMetrics | < SLA | 请求处理 P99 延迟 |

**网络线程 (NetworkThread)** 是 Kafka 接收/发送数据的核心,默认 3 个线程,可通过 `num.network.threads` 调整。每个线程负责一组连接。

**请求处理线程 (IOThread)** 负责实际处理请求,默认 8 个,通过 `num.io.threads` 调整。当这两个线程空闲率都低于 30% 时,说明 Broker 已经接近处理极限,必须扩容。

#### 1.4 延迟分位数 (Quantile)

Kafka 2.4+ 在 `kafka.network:type=RequestMetrics,name=TotalTimeMs` 中暴露延迟分位数:

#### 1.4 延迟分位数 (Quantile)

Kafka 2.4+ 在 `kafka.network:type=RequestMetrics,name=TotalTimeMs` 中暴露延迟分位数:

```text
request=Produce    → 生产请求
request=Fetch      → 消费请求
request=Metadata   → 元数据请求
request=JoinGroup  → 消费者组加入
request=SyncGroup  → 消费者组同步
```

**重点关注**:
- `Produce P99 < 50ms`
- `Fetch P99 < 100ms`
- `Metadata P99 < 100ms` (高并发下 Metadata 是常见瓶颈)

### 2. Topic / Partition 指标

| 指标 | MBean | 健康值 | 含义 |
|------|-------|--------|------|
| `LogEndOffset` | kafka.log:type=Log | 持续增长 | 分区最新 offset |
| `NumLogSegments` | kafka.log:type=Log | 稳定 | 当前 Log Segment 数 |
| `Size` | kafka.log:type=Log | < 磁盘容量 | 分区文件总大小 |
| `UnderReplicatedPartitions` | kafka.server | 0 | 未充分复制的分区 |

**Kafka 0.11+ 通过 `kafka-log-retention` 提供 per-topic 监控,优先用 kafka_exporter 暴露的 topic 级指标。**

### 3. Consumer 指标

Consumer 客户端启动时开启 JMX,默认暴露在 `kafka.consumer:type=*,client-id=*`:

| 指标 | 含义 | 健康值 |
|------|------|--------|
| `records-consumed-rate` | 每秒消费记录数 | 接近生产速率 |
| `fetch-rate` | 每秒 fetch 请求数 | 稳定 |
| `fetch-latency-avg` | 平均 fetch 延迟 | < 100ms |
| `records-lag-max` | 最大 lag | 接近 0 |
| `records-lag-avg` | 平均 lag | 接近 0 |
| `bytes-consumed-rate` | 每秒消费字节数 | 接近生产字节数 |
| `coordinator-rebalance-rate` | Rebalance 频率 | 偶发,不持续 |

**核心指标公式**:

```text
Lag = LogEndOffset (Broker 端最新 offset) - CurrentOffset (Consumer 端提交 offset)

  实际 lag ≈ records-lag-max (实时)
  历史 lag 趋势 ≈ 需要从 Broker + Consumer offset 计算
```

### 4. Producer 指标

Producer 客户端默认开启 JMX,暴露在 `kafka.producer:type=*,client-id=*`:

| 指标 | 含义 | 健康值 |
|------|------|--------|
| `record-send-rate` | 每秒发送记录数 | 稳定 |
| `record-error-rate` | 每秒发送失败率 | 接近 0 |
| `request-latency-avg` | 平均请求延迟 | < 50ms |
| `request-latency-max` | 最大请求延迟 | < SLA |
| `batch-size-avg` | 平均批量大小 | 接近 batch.size |
| `buffer-available-bytes` | 缓冲区可用字节 | > 0,不能长期 0 |
| `buffer-exhausted-rate` | 缓冲区耗尽速率 | 0 (非 0 表示 producer 卡顿) |
| `compression-rate-avg` | 平均压缩率 | 0.3 ~ 0.7 |

**关键告警**: `buffer-available-bytes` 持续为 0 + `buffer-exhausted-rate > 0` 表示 Producer 已被反压。

### 5. 副本滞后 (replica.lag)

**replica.lag 是衡量副本同步健康度的核心指标**。

```text
Follower 副本滞后 = Leader LogEndOffset - Follower LogEndOffset

健康值: < replica.lag.max.messages (默认 4000) 且持续 < 数秒
异常值: > replica.lag.max.messages → Follower 会被踢出 ISR
```

**关键监控指标**:

| MBean | 指标 | 健康 |
|-------|------|------|
| `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` | 未充分复制分区数 | 0 |
| `kafka.server:type=ReplicaManager,name=IsrShrinksPerSec` | ISR 收缩速率 | 接近 0 |
| `kafka.server:type=ReplicaFetcherManager,name=MaxLag,clientId=*` | Follower 最大 lag | < 阈值 |
| `kafka.server:type=ReplicaFetcherManager,name=MinFetchRate,clientId=*` | Follower 最小拉取速率 | > 0 |

**Lag 排查流程**:

```text
Lag 升高
  ↓
1. 查看 UnderReplicatedPartitions 是否 > 0
  ↓ 是
2. 看 IsrShrinksPerSec 变化 → 检查 Follower 是否被踢出
  ↓
3. 查看 Follower 磁盘 IO、网络、CPU
  ↓
4. 检查 replica.fetch.min.bytes / replica.fetch.max.bytes 是否合理
  ↓
5. 调大 num.replica.fetchers (默认 1,可调到 4-8)
```

## 四、Kafka Exporter + Prometheus

### 1. kafka_exporter 是什么

[kafka_exporter](https://github.com/danielqsj/kafka_exporter) 是 Daniel 维护的开源工具,通过 Kafka Admin Client + JMX 暴露 **Kafka 集群指标给 Prometheus**。

**核心特点**:
- 自动发现所有 Topic、Partition、Consumer Group
- 暴露 Lag、ISR、Replica、Log Size 等关键指标
- 与 Kafka 版本兼容 (Kafka 0.10 ~ 3.x)
- 部署简单,单二进制
- 默认以 HTTP 形式暴露 `/metrics` 端点
- 支持 topic 和 group 过滤,减少无用指标

**kafka_exporter 与 JMX Exporter 的关系**:

```text
┌──────────────────────────────────────────────────────────────┐
│  Kafka Broker (JVM 进程)                                  │
│      │                                                     │
│      ├─── Admin Client API ──→ kafka_exporter              │
│      │    (Topic / Partition / Group 元数据)             │
│      │                                                     │
│      └─── JMX MBeans ──→ JMX Exporter (可选,更细粒度)    │
│           (GC / Heap / 线程池 / Network 延迟分位数)        │
│                                                              │
│   推荐: kafka_exporter + JMX Exporter 同时部署,互补         │
└──────────────────────────────────────────────────────────────┘
```

### 2. 部署 kafka_exporter

#### 2.1 二进制部署 (推荐)

```bash
# 1. 下载 (以 Linux/amd64 为例)
wget https://github.com/danielqsj/kafka_exporter/releases/download/v1.7.0/kafka_exporter-1.7.0.linux-amd64.tar.gz
tar -xzf kafka_exporter-1.7.0.linux-amd64.tar.gz
cd kafka_exporter-1.7.0.linux-amd64

# 2. 启动 (监听 9308 端口)
./kafka_exporter \
  --kafka.server=kafka-1:9092 \
  --kafka.server=kafka-2:9092 \
  --kafka.server=kafka-3:9092 \
  --web.listen-address=:9308 &

# 3. 验证
curl http://localhost:9308/metrics | head -20
```

#### 2.2 关键启动参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `--kafka.server` | `kafka:9092` | Kafka Broker 地址,逗号分隔多个 |
| `--web.listen-address` | `:9308` | 监听端口 |
| `--topic.filter` | (空) | 过滤 topic,正则匹配 |
| `--group.filter` | (空) | 过滤 consumer group |
| `--log.level` | `info` | 日志级别 |
| `--kafka.client.dial-timeout` | `10s` | 客户端超时 |
| `--kafka.client.read-timeout` | `13s` | 读取超时 |

#### 2.3 Docker 部署

## 六、消费者 Lag 监控 (关键)

### 1. 为什么 Lag 监控是重中之重

**Lag 是 Kafka 监控的核心黄金指标**:

```text
Lag = 消费速率落后生产速率的程度

Lag 持续升高 = 消费者处理能力不足 = 数据积压 = 最终 OOM 或磁盘爆

Lag 升高处理不及时:
  ↓
消费者追不上生产
  ↓
Log 不断增长 → 磁盘撑爆
  ↓
Broker 不可用 → 全链路雪崩
```

**Lag 的四个严重程度**:

| 等级 | 阈值 (示例) | 处置 |
|------|-------------|------|
| **OK** | < 1000 | 正常 |
| **WARN** | 1000 ~ 10000 | 关注,排查消费者 |
| **ERROR** | 10000 ~ 100000 | 告警,业务可能受影响 |
| **STALL** | 持续增长不下降 / offset 不动 | 紧急,消费者可能死了 |

**Lag 的来源细分**:

```text
Lag 组成:
  LogEndOffset (Broker 端最新 offset)
  - CurrentOffset (Consumer 已提交 offset)
  = Consumer 已读但未处理的消息数

按消费者位置细分:
  • 消费者从未消费过: 历史 lag (积压)
  • 消费者跟不上生产: 实时 lag
  • 消费者处理后未提交: 未确认 lag
```

### 2. Lag 监控方案对比

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **kafka_exporter** | 部署简单,够用 | 单次拉取,无历史,瞬时值 | 中小集群 |
| **Burrow (LinkedIn)** | 评估 lag 状态 (OK/WARN/ERROR/STALL),无阈值 | 配置复杂,文档少,LinkedIn 已弃维 | 中大规模 |
| **kafka-lag-exporter** | 纯 Lag,支持 Slack/PagerDuty 告警 | 只监控 Lag,其他指标要看其他工具 | 仅需 Lag |
| **自研脚本** | 完全可控 | 开发成本高 | 大厂定制场景 |

### 5. 自定义脚本 (Shell 一行命令)

```bash
#!/bin/bash
# kafka-lag.sh - 简单 Lag 检查脚本

KAFKA_BROKERS="kafka-1:9092,kafka-2:9092,kafka-3:9092"
KAFKA_HOME=/opt/kafka
GROUP=$1
TOPIC=$2

if [ -z "$GROUP" ] || [ -z "$TOPIC" ]; then
  echo "Usage: $0 <group> <topic>"
  exit 1
fi

# 获取 group offsets
OFFSETS=$($KAFKA_HOME/bin/kafka-consumer-groups.sh \
  --bootstrap-server $KAFKA_BROKERS \
  --describe --group $GROUP 2>/dev/null)

# 过滤目标 topic
echo "$OFFSETS" | grep " $TOPIC " | while read line; do
  partition=$(echo "$line" | awk '{print $2}')
  current=$(echo "$line" | awk '{print $3}')
  log_end=$(echo "$line" | awk '{print $4}')
  lag=$(echo "$line" | awk '{print $5}')
  echo "Topic=$TOPIC Partition=$partition Current=$current LogEnd=$log_end Lag=$lag"
done
```

**Python 版本** (推荐):

```python
#!/usr/bin/env python3
"""kafka_lag_monitor.py - Lag 监控并上报到 Pushgateway"""

from kafka import KafkaAdminClient, KafkaConsumer, TopicPartition
import requests

BROKERS = ['kafka-1:9092', 'kafka-2:9092', 'kafka-3:9092']
PUSHGATEWAY = 'http://pushgateway:9091'
THRESHOLD = 10000

admin = KafkaAdminClient(bootstrap_servers=BROKERS)
groups = admin.list_consumer_groups()

consumer = KafkaConsumer(bootstrap_servers=BROKERS)
lag_metrics = []

for group_id, _ in groups:
    offsets = admin.list_consumer_group_offsets(group_id)
    for tp, offset_meta in offsets.items():
        # 获取 LEO
        consumer.assign([tp])
        consumer.seek_to_end(tp)
        end_offset = consumer.position(tp)
        consumer.seek(tp, offset_meta.offset)
        
        lag = end_offset - offset_meta.offset
        if lag > THRESHOLD:
            print(f"ALERT: group={group_id} topic={tp.topic} partition={tp.partition} lag={lag}")
        lag_metrics.append((group_id, tp.topic, tp.partition, lag))

# 上报到 Pushgateway
for group_id, topic, partition, lag in lag_metrics:
    metric = f'kafka_consumer_lag{{group="{group_id}",topic="{topic}",partition="{partition}"}} {lag}'
    requests.post(f'{PUSHGATEWAY}/metrics/job/kafka_lag', data=metric)
```

## 七、JMX 监控

### 1. JMX Exporter (推荐)

**JMX Exporter** 是 Prometheus 官方维护的 JVM 指标导出器,**作为 Java agent 嵌入 Kafka 进程**,把 JMX 指标转成 Prometheus 格式。

**为什么必须用 JMX Exporter 而不是纯 kafka_exporter**:

```text
纯 kafka_exporter:
  ✓ 部署简单
  ✓ 涵盖 Lag、ISR、Replica
  ✗ 没有 JVM 详细指标
  ✗ 没有 Network/Request 分位数延迟
  ✗ 看不到 GC、Heap、线程池细节

kafka_exporter + JMX Exporter:
  ✓ 涵盖全部 kafka_exporter 能力
  ✓ 加上 JVM / GC / Heap 完整指标
  ✓ 加上 Network/Request 分位数延迟
  ✓ 加上 Controller、Replica Fetcher 细节
  → 这是生产环境的完整方案
```

### 4. Python 综合巡检脚本

```python
#!/usr/bin/env python3
"""kafka_health_check.py - 综合健康检查"""

from kafka import KafkaAdminClient
from kafka.admin import ConfigResource, ConfigResourceType
import sys

BROKERS = ['kafka-1:9092', 'kafka-2:9092', 'kafka-3:9092']
admin = KafkaAdminClient(bootstrap_servers=BROKERS)

def check_brokers():
    cluster_info = admin.describe_cluster()
    print(f"✓ Brokers: {len(cluster_info['brokers'])}")
    for b in cluster_info['brokers']:
        print(f"  - id={b['node_id']} host={b['host']}:{b['port']}")
    
    print(f"✓ Controller: {cluster_info['controller_id']}")
    return len(cluster_info['brokers']) >= 3

def check_topics():
    topics = admin.list_topics()
    print(f"✓ Topics: {len(topics)}")
    return True

def check_under_replicated():
    """检查每个分区的 ISR 是否等于 Replica 数"""
    under_replicated = 0
    topics = admin.list_topics()
    for topic in topics:
        if topic.startswith('_'):
            continue
        partitions = admin.describe_topics([topic])[0]['partitions']
        for p in partitions:
            replicas = len(p['replicas'])
            isr = len(p['isr_nodes'])
            if isr < replicas:
                under_replicated += 1
                print(f"⚠ {topic}-{p['partition_id']} replicas={replicas} isr={isr}")
    print(f"{'⚠' if under_replicated > 0 else '✓'} Under-replicated partitions: {under_replicated}")
    return under_replicated == 0

def main():
    print("=== Kafka Cluster Health Check ===\n")
    check_brokers()
    print()
    check_topics()
    print()
    check_under_replicated()

if __name__ == "__main__":
    main()
```

### 1. 关键告警项分类

| 类别 | 告警项 | 严重级别 |
|------|--------|----------|
| **可用性** | Broker 离线 | Critical |
| **可用性** | Controller 不可用 | Critical |
| **可用性** | Active Controller Count = 0 | Critical |
| **数据安全** | UnderReplicatedPartitions > 0 | Critical |
| **数据安全** | ISR 收缩速率 > 阈值 | Warning |
| **数据安全** | Unclean Leader Election | Critical |
| **容量** | 磁盘使用 > 80% | Warning |
| **容量** | 磁盘使用 > 90% | Critical |
| **消费** | Consumer Lag > 10000 | Warning |
| **消费** | Consumer Lag > 100000 | Critical |
| **消费** | Consumer Group 无心跳 | Critical |
| **性能** | NetworkProcessorAvgIdle < 30% | Warning |
| **性能** | Produce P99 > 200ms | Warning |
| **性能** | Fetch P99 > 500ms | Warning |
| **JVM** | GC 时间占比 > 10% | Warning |
| **JVM** | Full GC 频率 > 1/min | Warning |

**告警分级原则**:

```text
P0 (Critical, 立刻响应):
  • Broker 不可用
  • Controller 不可用
  • Unclean Leader Election
  • 磁盘写满
  → 立刻处理,可能影响业务

P1 (Error, 5 分钟内响应):
  • UnderReplicatedPartitions > 0 持续
  • Consumer Lag > 100000
  • GC 长时间暂停
  → 工作时间立即处理

P2 (Warning, 工作时间处理):
  • Consumer Lag 警告
  • ISR 偶发收缩
  • 磁盘使用率 > 80%
  → 安排工作日处理

P3 (Info, 关注):
  • 部分分区 leader 不在 preferred replica
  → 周会讨论
```

## 十二、运维操作

### 1. 滚动重启 (Rolling Restart)

#### 1.1 为什么要滚动重启

- 升级 Kafka 版本
- 修改 Broker 配置
- 修复 OS / 容器漏洞
- 节点维护

**关键原则**:**一次只重启一个 Broker**,确保集群始终可用。

#### 1.2 重启前的"5 个确认"

```text
□ 确认 1:集群当前是健康状态
  → UnderReplicatedPartitions = 0
  → ISR 收缩速率 = 0
  → 所有 broker 都已加入集群

□ 确认 2:已备份 server.properties 和 zk 数据
  → server.properties 是 broker 核心配置
  → zk 包含 topic 配置、acl、消费位移元数据

□ 确认 3:确认 broker id 不会冲突
  → server.properties 中 broker.id = N
  → zk 中 /brokers/ids/N 也存在

□ 确认 4:通知业务方
  → 提前 24 小时通告
  → 选业务低峰期 (通常是深夜)

□ 确认 5:准备回滚方案
  → 保留旧二进制目录 (改名不要删除)
  → 保留旧 server.properties
  → 保留 ZK 快照
```

#### 1.2 操作步骤

```bash
# === Step 1: 检查集群状态 ===
kafka-broker-api-versions.sh --bootstrap-server kafka-1:9092 | head

# === Step 2: 设置 Throttle (可选,避免重启风暴) ===
# 让 producer/consumer 重试时不会触发完整 leader rebalance
# 但 kafka-reassign-partitions 操作不需要

# === Step 3: 检查每个 broker 的 in-sync 状态 ===
kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --describe --topic critical-topic | grep -v "Isr: 3"

# === Step 4: 一个一个重启 ===

# 4.1 停止第一个 broker (假设 broker-1)
ssh kafka-1
systemctl stop kafka

# 4.2 升级配置或二进制
# (修改 server.properties,或升级 kafka 二进制)
cp /opt/kafka.new/bin/* /opt/kafka/bin/

# 4.3 启动
systemctl start kafka
# 或: kafka-server-start.sh -daemon config/server.properties

# 4.4 验证已加入集群
sleep 30
kafka-broker-api-versions.sh --bootstrap-server kafka-1:9092 \
  | grep "kafka-1"

# === Step 5: 重复 Step 4 处理 broker-2, broker-3 ===
```

#### 1.3 滚动重启的检查清单

```text
□ 集群当前是 healthy (无 UnderReplicatedPartitions)
□ 已经备份 server.properties
□ 已经确认 ZK 中 broker id 与配置文件一致
□ 重启一个后等待至少 30 秒确认完全恢复
□ 监控 ISR 收缩与恢复 (在 Grafana 观察)
□ 提前通知业务方 (通常选择业务低峰)
□ 准备回滚方案 (保留旧二进制目录)
```

### 2. 分区扩容 (kafka-reassign-partitions)

#### 2.1 生成分区扩容方案

**场景**: Topic `orders` 从 3 分区扩到 6 分区,同时调整副本分布。

```bash
# 1. 准备 JSON 文件 (增加分区)
cat > topics-to-move.json << 'EOF'
{
  "topics": [
    { "topic": "orders" }
  ],
  "version": 1
}
EOF

# 2. 生成方案 (扩到 6 分区)
kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --topics-to-move-json-file topics-to-move.json \
  --broker-list "1,2,3,4,5,6" \
  --generate

# 输出会包含两种方案:
#   Current partition replica assignment (当前分配)
#   Proposed partition reassignment configuration (推荐方案)
```

**注意**: `--generate` 只生成方案,**不会执行**。

#### 2.2 重新分配 (调整副本分布)

```bash
# 1. 编写目标分配 JSON
cat > reassignment.json << 'EOF'
{
  "version": 1,
  "partitions": [
    {
      "topic": "orders",
      "partition": 0,
      "replicas": [1, 2, 3]
    },
    {
      "topic": "orders",
      "partition": 1,
      "replicas": [2, 3, 4]
    },
    ...
  ]
}
EOF

# 2. 执行
kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassignment.json \
  --execute

# 3. 查看进度
kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassignment.json \
  --verify
```

#### 2.3 注意事项

```text
坑 1: 分区数只能增加,不能减少!
      → 减少分区需要重建 topic,数据迁移

坑 2: reassignment 过程对集群有压力
      → 单次操作不要超过 100 个分区
      → 用 --throttle 限速: --throttle 50000000 (50MB/s)

坑 3: reassignment 过程会显著增加网络流量
      → 在业务低峰期执行

坑 4: reassignment 失败的处理
      → 使用 --cancel 取消
      → 或重新执行 --execute (会从上次进度继续)
```

#### 2.4 增加分区数 (扩分区)

```bash
# 增加分区 (不能减少)
kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --alter --topic orders \
  --partitions 6

# 验证
kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --describe --topic orders
```

**坑**: 增加分区后,key 的 hash 分布会变化(因为分区数变了),消息路由到不同分区,**消费者**不受影响但需要关注业务。

### 3. 数据迁移 (MirrorMaker 2)

#### 3.1 MirrorMaker 2 vs MirrorMaker 1

| 维度 | MM1 (老) | MM2 (新) |
|------|----------|----------|
| 架构 | 多个 Consumer + Producer | 统一 Connect 框架 |
| 可靠性 | 容易丢数据 | Exactly-once 支持 |
| Topic 命名 | 源 topic 名带前缀 | 保留 topic 名 |
| 配置 | 单文件 | 多 connector |
| 活跃维护 | ❌ 已停更 | ✅ Apache Kafka 主项目 |

**生产环境只用 MM2**。

#### 3.2 MM2 部署

```bash
# 1. 下载 MM2 插件 (通常和 Kafka 同目录)
ls /opt/kafka/plugins/mirror-maker-2/

# 2. 准备配置文件 (connect-mirror-maker.properties)
cat > config/connect-mirror-maker.properties << 'EOF'
# Kafka Connect 基础配置
bootstrap.servers=source-kafka:9092

# Source cluster
clusters=source, target

source.bootstrap.servers=source-kafka:9092
source.client.id=mm2-source

target.bootstrap.servers=target-kafka:9092
target.client.id=mm2-target

# 同步所有 topic (除了内部)
source->target.enabled=true
source->target.topics=.*
source->target.topics.excluded=__.*,_.*

# 同步 consumer group offsets
source->target.groups=.*
source->target.groups.excluded=console-consumer-.*,connect-.*

# 副本配置 (跨数据中心时降低)
source->target.replication.factor=1

# 检查点 (Mirror 心跳 topic)
source->target.checkpoints.topic.replication.factor=1
source->target.offset.syncs.topic.replication.factor=1
source->target.status.store.replication.factor=1

# 同步频率
source->target.refresh.topics.interval.seconds=10
source->target.refresh.groups.interval.seconds=10

# ACL 与 topic 配置同步
source->target.sync.topic.configs.enabled=true
source->target.sync.topic.acls.enabled=true
EOF

# 3. 启动 (使用 Kafka Connect Distributed 模式)
./bin/connect-distributed.sh config/connect-mirror-maker.properties &

# 4. 验证 connector 已创建
curl -s http://localhost:8083/connectors
# 输出: ["source->target"]
```

#### 3.3 MM2 高级用法

```bash
# 单向同步 A → B
clusters = A, B
A->B.enabled = true

# 双向同步 A ↔ B
clusters = A, B
A->B.enabled = true
B->A.enabled = true

# 主动-被动 (active-active) 模式
A->B.enabled = true
B->A.enabled = true
# 配合 BusinessKeyResolver 避免循环
```

#### 3.4 MM2 监控

```bash
# 查看 mirror source connector 状态
curl http://localhost:8083/connectors/source->target/status | jq

# 监控 lag
curl http://localhost:8083/connectors/source->target/source-task-metrics | jq
```

### 4. 集群扩容 (添加 Broker)

#### 4.1 扩容步骤

```bash
# === Step 1: 准备新 Broker ===

# 1.1 安装 Kafka (与现有 broker 同版本)
# 1.2 配置 server.properties,设置唯一 broker.id
# 关键差异:
broker.id=4                       # 新 broker id
listeners=PLAINTEXT://:9092
log.dirs=/kafka-data
zookeeper.connect=zookeeper-1:2181,zookeeper-2:2181,zookeeper-3:2181

# 1.3 启动新 broker
kafka-server-start.sh -daemon config/server.properties

# === Step 2: 验证加入集群 ===

# 2.1 检查 broker 列表
kafka-broker-api-versions.sh --bootstrap-server kafka-1:9092 \
  | grep "id:"

# 2.2 查看 zk
zookeeper-shell.sh zookeeper-1:2181 <<< "ls /brokers/ids"
# 应返回 [1, 2, 3, 4]

# === Step 3: 迁移分区到新 broker ===

# 3.1 生成方案
cat > topics-to-move.json << 'EOF'
{
  "topics": [
    {"topic": "orders"},
    {"topic": "payments"}
  ],
  "version": 1
}
EOF

kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --topics-to-move-json-file topics-to-move.json \
  --broker-list "1,2,3,4" \
  --generate

# 3.2 执行迁移 (写入生成的 JSON)
kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassignment.json \
  --execute \
  --throttle 50000000

# 3.3 监控进度
watch -n 10 'kafka-reassign-partitions.sh \
  --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassignment.json \
  --verify'
```

#### 4.2 扩容注意事项

```text
坑 1: 新 broker 加入后,分区不会自动迁移!
      → 必须显式执行 kafka-reassign-partitions

坑 2: 扩容不会提升吞吐 (除非新 broker 接管部分流量)
      → 迁移分区后才会有负载分担

坑 3: 扩容会触发数据大量复制
      → 网络带宽会被打满
      → 用 --throttle 限制

坑 4: 副本数小于 broker 数
      → 比如 3 副本部署 5 broker,只能容 2 故障
      → 建议副本数 = floor(broker 数 / 2)
```

#### 4.3 扩容的性能影响评估

```text
reassignment 过程:
  1. 新副本从 Leader 拉取所有数据
  2. 同步追平后切换
  3. 完成后删除老副本

影响:
  • 网络流量:单 broker 多复制 RF-1 份数据
  • 磁盘 IO:Leader 多出 1 倍的读 + 网络发送
  • 时间:与数据量相关,TB 级可能要几小时

限流公式:
  --throttle 100000000    # 100 MB/s
  --throttle 50000000     # 50 MB/s
  → 推荐 50-100 MB/s,避免影响生产
```

## 十三、容量规划

### 1. 容量规划三要素

```text
┌────────────────────────────────────────────────────┐
│         Kafka 容量规划 = 磁盘 + 网络 + 内存           │
├────────────────────────────────────────────────────┤
│  磁盘: 存得下消息                                   │
│  网络: 传得动流量                                   │
│  内存: 缓存得住热点                                 │
└────────────────────────────────────────────────────┘
```

**容量规划的核心思想**:

```text
业务需求 ─→ 推算流量 ─→ 推算资源
   │            │           │
   │            │           │
 QPS/TPS   生产速率     磁盘容量
 消息大小   保留时间     网络带宽
 SLA      副本数       内存容量
```

**必须考虑三个乘数**:

```text
磁盘 = 消息量 × 副本数 × 冗余系数
网络 = 生产量 × 副本同步系数 + 消费量
内存 = 热点数据 + JVM Heap
```

**不能仅看平均值**,要考虑峰值。峰值一般是平均值的 2-5 倍 (电商大促、突发事件)。

### 2. 磁盘容量估算

#### 2.1 公式

```text
磁盘容量 = 生产速率 × 保留时间 × 副本数 × (1 + 预留冗余)

单位说明:
  生产速率: byte/s 或 GB/day
  保留时间: 秒/天
  副本数: replication.factor (通常 2-3)
  预留冗余: 0.2 (20% 预留,给 compaction 和临时文件)
```

#### 2.2 示例

```text
业务场景:
  生产速率: 100 MB/s
  保留时间: 7 天
  副本数: 3
  预留冗余: 1.2

计算:
  每日生产 = 100 MB/s × 86400 s = 8.64 TB/day
  7 天保留 = 8.64 × 7 = 60.48 TB
  3 副本 = 60.48 × 3 = 181.44 TB
  含 20% 冗余 = 181.44 × 1.2 = 217.73 TB

→ 需要集群总磁盘 ≈ 218 TB
→ 5 个 broker × 10 盘(每盘 5 TB) = 250 TB (富余)
```

#### 2.3 磁盘选型

| 类型 | IOPS | 带宽 | 适用 |
|------|------|------|------|
| **SATA HDD** | ~200 | 150 MB/s | 冷数据,大吞吐 |
| **SAS HDD** | ~400 | 200 MB/s | 一般业务 |
| **SATA SSD** | 50K+ | 500 MB/s | 主流推荐 |
| **NVMe SSD** | 500K+ | 3 GB/s | 高 IO 场景 |

**Kafka 推荐**: SATA SSD (性价比高),预算允许 NVMe。

### 3. 网络带宽估算

#### 3.1 公式

```text
集群所需带宽 = 总生产速率 × (副本数 - 1) × 1.3
              + 消费速率 × 1
              + 30% 余量

简化版:
  入向带宽 = 生产速率 × (副本数) × 1.3   [副本同步]
  出向带宽 = 生产速率 × (副本数 - 1) × 1.3 + 消费速率
```

#### 3.2 示例

```text
业务场景:
  生产速率: 100 MB/s (单 broker 接收)
  副本数: 3
  消费速率: 200 MB/s (sum)
  10 Gbps 网卡

计算:
  副本同步 = 100 MB/s × (3 - 1) = 200 MB/s 出向
  消费 = 200 MB/s 出向
  合计 = 400 MB/s
  含 30% 余量 = 520 MB/s
  转换为 Gbps = 520 × 8 / 1024 ≈ 4.1 Gbps

→ 10 Gbps 网卡足够,有 5+ Gbps 富余
```

#### 3.3 网络瓶颈判断

```bash
# 实时监控网络
iftop -i eth0
# 或 sar
sar -n DEV 1
```

**指标判断**:

| 场景 | 阈值 | 处理 |
|------|------|------|
| 正常 | < 50% 网卡带宽 | OK |
| 警告 | 50-70% 网卡带宽 | 考虑扩容 |
| 严重 | > 70% 网卡带宽 | 必须扩容 |

### 4. 内存规划

#### 4.1 Kafka 内存组成

```text
┌──────────────────────────────────────────────────────┐
│  Kafka Broker 内存构成                                │
├──────────────────────────────────────────────────────┤
│                                                      │
│  1. JVM Heap (受 Xmx 限制)                           │
│     • Partition 对象                                  │
│     • Producer/Consumer 缓存 (server 端)             │
│     • 各种缓存池                                       │
│     推荐: 6-16 GB,过大导致 GC 时间长                  │
│                                                      │
│  2. Page Cache (操作系统,主要性能依赖)                │
│     • 实际消息缓存                                    │
│     • 推荐: 物理内存的 50%+ 留给 OS                   │
│                                                      │
│  3. Socket Buffer (网络)                              │
│     • send / receive buffer                          │
│                                                      │
└──────────────────────────────────────────────────────┘
```

#### 4.2 内存估算

```text
总内存需求 = JVM Heap + Page Cache + 其他

Page Cache 推荐: 至少能装下所有 hot segment
  hot segment 大小 ≈ 单个 log.segment.bytes (默认 1 GB)
  
  假设 100 个 hot partitions,每个 1 GB
  Page Cache = 100 GB

JVM Heap: 6-16 GB (取决于 connection 数)

总内存 = 8 GB (Heap) + 100 GB (Page Cache) + 系统开销 = 128 GB (服务器内存)
```

#### 4.3 JVM 参数推荐

```bash
export KAFKA_HEAP_OPTS="-Xms8g -Xmx8g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:+DisableExplicitGC"

# G1 GC 是 Kafka 推荐选择 (Java 9+)
# MaxGCPauseMillis 控制 GC 暂停时间,推荐 20ms
# InitiatingHeapOccupancyPercent 控制何时开始混合 GC
```

**JVM 调优建议**:

```text
Heap 大小选择:
  4 GB 以下:小集群,无压力
  6-8 GB:中型集群,生产推荐
  16 GB:大型集群,但要注意 GC 时间
  32 GB+:不推荐,GC 暂停会变长

GC 选择:
  Java 8:  G1 GC (默认)
  Java 11+:ZGC / G1 (ZGC 暂停 < 1ms,但吞吐量略低)

JVM 关键参数:
  -Xms = -Xmx                  # 避免动态扩容
  -XX:+UseG1GC                  # Kafka 推荐 G1
  -XX:MaxGCPauseMillis=20       # GC 暂停上限
  -XX:+DisableExplicitGC        # 禁止应用 GC
  -XX:+HeapDumpOnOutOfMemoryError  # OOM 时 dump
  -XX:HeapDumpPath=/var/log/kafka/heapdump.hprof
```

**GC 监控命令**:

```bash
# 查看 GC 频率和时间
jstat -gcutil <pid> 1s

# 输出:
# S0    S1    E     O     M     CCS   YGC   YGCT   FGC  FGCT   GCT
# 0.00  0.00  25.00 60.00 95.00 90.00  100   1.000  5    0.500  1.500
#                ↑
#              Eden 使用率 25%
#
# FGC (Full GC Count): < 5 次/小时 正常
# FGCT (Full GC Time): < 100ms/次 正常
```

### 5. 容量规划总表

| 业务规模 | 日数据量 | 集群规模 | 磁盘 | 内存 | 网络 |
|----------|---------|----------|------|------|------|
| **小型** | < 100 GB | 3 broker | 1 TB/盘 × 4 = 4 TB/台 | 32 GB | 1 Gbps |
| **中型** | 100 GB ~ 1 TB | 5-10 broker | 4 TB/盘 × 8 = 32 TB/台 | 64 GB | 10 Gbps |
| **大型** | 1 TB ~ 10 TB | 10-30 broker | 8 TB/盘 × 12 = 96 TB/台 | 128 GB | 25 Gbps |
| **超大型** | > 10 TB | 30+ broker | 16 TB/盘 × 24 = 384 TB/台 | 256 GB | 100 Gbps |

## 十四、备份与恢复

### 1. Kafka 数据可靠性基础

Kafka 数据可靠性的**三个支柱**:

```text
┌──────────────────────────────────────────────────────────┐
│  1. 多副本机制 (Replication Factor)                       │
│     • RF ≥ 3 是生产标准                                   │
│     • min.insync.replicas = 2 是数据安全底线               │
│                                                          │
│  2. 副本同步确认 (Acks)                                   │
│     • acks = all + min.insync.replicas = 2               │
│     • 这是真正"不丢数据"的配置                            │
│                                                          │
│  3. Unclean Leader Election 关闭                          │
│     • unclean.leader.election.enable = false              │
│     • 防止数据丢失的兜底                                  │
└──────────────────────────────────────────────────────────┘
```

**Producer 端可靠性配置**:

```properties
# Producer 端:防止发送丢数据
acks = all                                  # 必须等所有 ISR 确认
retries = 2147483647                        # 无限重试
max.in.flight.requests.per.connection = 5   # 保证顺序
enable.idempotence = true                   # 幂等
delivery.timeout.ms = 120000                # 总超时
```

**Consumer 端可靠性配置**:

```properties
# Consumer 端:防止消费丢数据
enable.auto.commit = false                  # 手动提交 offset
auto.offset.reset = earliest                # 从头开始(谨慎)
isolation.level = read_committed            # 只读已提交事务
max.poll.records = 500                      # 单次拉取上限
session.timeout.ms = 10000                  # 心跳超时
```

**可靠性级别对比**:

| 场景 | 配置 | 可靠性 | 性能 |
|------|------|--------|------|
| **最高** | acks=all, RF=3, min.isr=2, 幂等, 事务 | 100% | 低 |
| **高** | acks=all, RF=3, min.isr=2, 幂等 | 99.999% | 中 |
| **一般** | acks=1, RF=3 | 99.99% | 中 |
| **低** | acks=0, RF=2 | 99.9% | 高 |

### 2. 备份策略对比

| 备份类型 | 工具 | 优点 | 缺点 |
|----------|------|------|------|
| **文件级** | rsync / cp / snapshot | 简单 | 备份期间可能不一致 |
| **MirrorMaker 2** | Kafka 内置 | 在线,持续 | 实时镜像,不能恢复历史 |
| **文件系统快照** | LVM/ZFS | 一致性强 | 复杂,停机/冻结 |
| **对象存储** | S3 + Custom | 异地 | 需要自定义开发 |

### 3. 文件级备份

#### 3.1 停机备份 (最简单)

```bash
# 1. 停止所有 broker (确保一致性)
ssh kafka-1 "systemctl stop kafka"
ssh kafka-2 "systemctl stop kafka"
ssh kafka-3 "systemctl stop kafka"

# 2. 备份数据目录
ssh kafka-1 "tar czf /backup/kafka-data-$(date +%Y%m%d).tar.gz /kafka-data"

# 3. 启动
ssh kafka-1 "systemctl start kafka"
```

#### 3.2 在线备份 (有风险)

```bash
# 用 rsync 实时同步 (注意不保证一致性)
rsync -av --delete /kafka-data/ backup-server:/backup/kafka-data/

# 但 Kafka 写入中,可能导致数据不一致
# 改进: 先 freeze topic, 再 rsync
```

### 4. MirrorMaker 2 灾备

MirrorMaker 2 本质是**实时数据同步**,灾备场景:

```text
┌─────────────────────────────────────────────────────────────┐
│  灾备架构                                                     │
│                                                              │
│   机房 A (主)                机房 B (灾备)                   │
```

**MM2 双向同步 (active-active)**:

```text
场景:
  两个机房都需要写,各自本地优先

配置:
  primary->dr.enabled = true
  dr->primary.enabled = true

风险:
  • 同一消息可能在两端都写 (重复)
  • 同一 key 的消息可能在不同机房处理,顺序混乱

解决方案:
  1. 按业务分区:某些 topic 只在 A,某些只在 B
  2. 按 key 路由:key 前缀决定写哪个机房
  3. 用 BusinessKeyResolver 在 MM2 层去重

生产建议:
  • 优先用 active-passive (单向同步)
  • 必须用 active-active 时,做好去重
```

### 5. 完整备份恢复策略

#### 5.1 推荐备份架构

```text
┌────────────────────────────────────────────────────────────────┐
│  生产环境 Kafka 备份恢复策略                                    │
│                                                                │
│  1. 多副本 (RF=3) + min.insync.replicas=2 → 在线数据冗余      │
│                                                                │
│  2. MirrorMaker 2 → 异地灾备集群 (RPO ≈ 0)                    │
│                                                                │
│  3. 每日文件级快照 → S3/OSS (RPO ≤ 24h,防逻辑错误)             │
│                                                                │
│  4. ZK 数据单独备份 (ZK 配置 / Topic 配置)                     │
│                                                                │
│  RPO:  0 (主) / 24h (S3 备份)                                 │
│  RTO:  < 5 min (灾备切换) / 几小时 (S3 恢复)                  │
└────────────────────────────────────────────────────────────────┘
```

#### 5.2 文件级备份脚本

```bash
#!/bin/bash
# kafka_backup.sh - 每日文件级备份

BACKUP_DIR=/backup/kafka/$(date +%Y%m%d)
KAFKA_DATA=/kafka-data
BROKERS="kafka-1 kafka-2 kafka-3"

# 1. 创建备份目录
mkdir -p $BACKUP_DIR

# 2. 对每个 broker 备份
for broker in $BROKERS; do
  echo "备份 $broker..."
  
  ssh $broker "
    # 用 cp -l 创建 hard-link snapshot (几乎瞬时)
    cp -al $KAFKA_DATA $BACKUP_DIR/$broker-snapshot
    tar czf $BACKUP_DIR/$broker-$(date +%Y%m%d).tar.gz \
      $BACKUP_DIR/$broker-snapshot
    rm -rf $BACKUP_DIR/$broker-snapshot
  " &
done

wait

# 3. 同步到 S3 (使用 aws-cli)
aws s3 sync $BACKUP_DIR s3://my-kafka-backup/$(date +%Y%m%d)/

# 4. 清理 7 天前的本地备份
find /backup/kafka -mtime +7 -exec rm -rf {} \;

# 5. 清理 30 天前的 S3 备份
aws s3 rm s3://my-kafka-backup/ --recursive --exclude "*" \
  --include "$(date -d '30 days ago' +%Y%m%d)/*"
```

**关键技巧**: `cp -al` 创建 hard-link 快照,**几乎零开销**,备份期间不影响 Kafka 运行。然后异步压缩、清理。

#### 5.3 恢复流程

```bash
# === 场景 1: 单个 broker 数据损坏 ===
# 因为有 RF=3,自动从其他 broker 副本恢复
# 只需重启该 broker 即可

# === 场景 2: 整个集群数据损坏 (如误操作删除 topic) ===

# 1. 停止所有 broker
for b in kafka-1 kafka-2 kafka-3; do
  ssh $b "systemctl stop kafka"
done

# 2. 清空数据目录
for b in kafka-1 kafka-2 kafka-3; do
  ssh $b "rm -rf /kafka-data/*"
done

# 3. 从 S3 恢复
aws s3 cp s3://my-kafka-backup/20260818/kafka-1-20260818.tar.gz /tmp/
for b in kafka-1 kafka-2 kafka-3; do
  ssh $b "tar xzf /tmp/$b-20260818.tar.gz -C /kafka-data/"
done

# 4. 启动 broker
for b in kafka-1 kafka-2 kafka-3; do
  ssh $b "systemctl start kafka"
done

# 5. 验证
kafka-topics.sh --bootstrap-server kafka-1:9092 --list
```

### 6. ZK 数据备份

**ZK 也需要单独备份**,因为 Topic 配置、Acl、消费位移等元数据都存 ZK。

```bash
# 1. 用 zk 工具导出
zookeeper-shell.sh zookeeper-1:2181 <<< "
  ls /
  get /config/topics/orders
"

# 2. 备份 zk dataDir (找 zk 配置: dataDir=/var/lib/zookeeper)

# 3. Kafka 0.10+ 把 consumer offsets 移到 Kafka 自身 (内部 topic __consumer_offsets)
#    但 topic 配置 / ACL 还在 ZK
```

### 7. 备份恢复速查表

| 场景 | 备份方式 | 恢复方式 | RTO |
|------|----------|----------|-----|
| **单 broker 故障** | RF≥3 副本 | 自动恢复 / 重启 broker | < 5 min |
| **集群误删 topic** | 文件级备份 + MM2 | 恢复 topic + 回放数据 | < 30 min |
| **数据中心灾难** | MM2 异地灾备 | 切换应用连接到灾备 | < 5 min |
| **逻辑数据错误** | 文件级备份 (S3) | 创建新 topic 回放历史 | 数小时 |
| **Kafka 软件 BUG 导致数据损坏** | 升级 + 文件级备份 | 回滚版本 + 数据修复 | 1-2 小时 |

## 十六、生产级 Broker 配置参考

### 1. 通用生产配置模板

```properties
# === Broker 基础配置 ===
broker.id=0

advertised.listeners=PLAINTEXT://kafka-1:9092

socket.send.buffer.bytes=102400
socket.receive.buffer.bytes=102400

# === Log 配置 ===

log.segment.ms=604800000             # 7 天
log.retention.hours=168              # 默认保留 7 天
log.retention.bytes=-1               # 不按大小限制
log.cleanup.policy=delete            # delete 或 compact
log.cleaner.enable=true              # 启用 cleaner (compact 需要)
log.cleaner.threads=2
log.cleaner.dedupe.buffer.size=134217728  # 128MB

# === 副本配置 ===
default.replication.factor=3         # 默认 RF=3

unclean.leader.election.enable=false # 关闭 unclean 选举

# === 性能配置 ===

replica.fetch.min.bytes=1
replica.fetch.max.bytes=1048576      # 1MB
replica.fetch.response.max.bytes=10485760  # 10MB

# === ZK 配置 ===
zookeeper.connect=zookeeper-1:2181,zookeeper-2:2181,zookeeper-3:2181
zookeeper.session.timeout.ms=18000
zookeeper.connection.timeout.ms=10000

# === Group Coordinator ===
group.initial.rebalance.delay.ms=3000
offsets.topic.replication.factor=3   # __consumer_offsets 用 3 副本
offsets.topic.num.partitions=50
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2

# === 压缩配置 ===
compression.type=producer            # 由 producer 决定
```

### 2. 关键参数详解

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `num.partitions` | 10-50 | 默认分区数,影响写入并行度 |
| `log.segment.bytes` | 1 GB | 太大恢复慢,太小文件多 |
| `log.retention.hours` | 168 | 7 天,根据业务调 |
| `min.insync.replicas` | 2 | 数据安全底线 |
| `unclean.leader.election.enable` | false | 防数据丢失 |
| `num.replica.fetchers` | 4 | Follower 拉取并行度 |
| `group.initial.rebalance.delay.ms` | 3000 | 新 group 加入延迟 |
| `offsets.topic.replication.factor` | 3 | 消费位移主题必须 3 副本 |

## 十七、灾备演练 (Disaster Recovery Drill)

### 1. 为什么要做灾备演练

```text
"备份从来不是问题,恢复才是"

生产环境 100% 做了备份,但真正能恢复的不到 50%
  • 备份文件损坏 (没验证过)
  • 恢复脚本错误 (没测过)
  • 恢复时间超过 RTO (没演练过)
  • 关键步骤漏掉 (ZK 数据未恢复)

灾备演练是验证备份有效性的唯一方法
```

### 2. 灾备演练清单

```text
□ 演练 1:单 broker 故障
  • 模拟:关掉一个 broker
  • 预期:集群继续服务,数据不丢
  • 验证:消费/生产正常,ISR 恢复

□ 演练 2:整集群故障 (机房断电)
  • 模拟:整个集群不可用
  • 预期:切换到灾备集群,RTO < 5 分钟
  • 验证:灾备集群可消费最新数据

□ 演练 3:Zookeeper 故障
  • 模拟:ZK 集群不可用
  • 预期:Kafka 仍能服务现有连接,新连接可能失败
  • 验证:Kafka 集群不依赖 ZK 也能短期运行

□ 演练 4:磁盘故障
  • 模拟:broker 磁盘损坏
  • 预期:从其他 broker 副本恢复
  • 验证:数据完整性

□ 演练 5:数据误删除
  • 模拟:误删 topic
  • 预期:从 S3 备份恢复
  • 验证:数据完整性,RTO 满足预期
```

### 3. 灾备演练频率

| 演练类型 | 频率 | 范围 |
|----------|------|------|
| **单 broker 故障** | 每季度 | 生产环境 |
| **整集群切换** | 每半年 | 灾备环境 |
| **数据恢复** | 每半年 | 备份环境 |
| **全年大演练** | 每年 | 真实生产切换演练 |

### 4. 演练注意事项

```text
1. 在低峰期演练
2. 提前通知所有相关人员
3. 准备回滚方案
4. 监控所有关键指标
5. 记录每个步骤耗时
6. 演练后复盘改进
```

## 十六、运维常见问题 FAQ

```text
紧急处理 (5 分钟):
  1. 删除不需要的 topic 数据
     kafka-topics.sh --bootstrap-server kafka:9092 --delete --topic test-topic
  2. 调整 retention.ms (缩短保留时间)
     kafka-configs.sh --bootstrap-server kafka:9092 \
       --entity-type topics --entity-name orders \
       --alter --add-config retention.ms=86400000
  3. 增加 broker / 扩容磁盘 (根本方案)

注意:
  • Kafka 默认 log.retention.hours = 168 (7 天)
  • 调整 retention 不会立刻释放空间,要等下一个 segment 切换
  • 真正紧急可用:删除整个 topic (危险操作!)
```

### Q2:Consumer 一直 rebalance 怎么办?

```text
排查步骤:
  1. 查看 consumer 日志,确认 rebalance 触发原因
     • 成员加入 (新 consumer 启动)
     • 成员离开 (consumer 崩溃)
     • 订阅的 topic 变化

  2. 如果是成员离开:
     • session.timeout.ms 太短 → 调大到 30s
     • max.poll.interval.ms 太短 → 调大到 300s
     • consumer 处理逻辑慢 → 优化代码
     • GC 暂停过长 → 调整 JVM

  3. 如果持续 rebalance,关闭 group rebalance:
     group.initial.rebalance.delay.ms = 0

常见原因:
  • consumer 代码 OOM 被 kill
  • 慢 SQL / 慢 RPC 阻塞处理
  • GC 暂停超过 session.timeout
  • 网络抖动导致心跳丢失
```

### Q3:Producer 发送超时?

```text
检查清单:
  □ acks=all 且 min.insync.replicas=2?
    → 可能 ISR 不足,等待副本追上
  □ 副本在迁移 (reassignment)?
    → reassignment 期间副本数减少
  □ 磁盘 IO 100%?
    → 看 broker 的 iostat
  □ Producer buffer 满?
    → 看 buffer-available-bytes (应该 > 0)

调整:
  delivery.timeout.ms = 120000    # 总超时 2 分钟
  request.timeout.ms = 30000      # 单请求超时 30s
  retries = Integer.MAX_VALUE     # 无限重试
  max.in.flight.requests.per.connection = 5  # 保序
```

### Q4:如何选择 Kafka 版本?

```text
版本选择原则:
  1. 选社区活跃维护的版本 (Kafka 3.x)
  2. 不要用最新的 minor (等小版本稳定后再上)
  3. 跨大版本升级要做完整测试

推荐版本 (2026 年):
  • Kafka 3.6.x LTS
  • Kafka 3.7.x (有 KRaft 增强)
  • Kafka 3.8.x (最新稳定)

避免:
  • Kafka 2.0 之前 (已 EOL)
  • Kafka 2.4 (老,缺少新功能)
  • Kafka 2.8 (新,但 0.11 协议兼容性需要测试)
```

### Q5:Kafka 性能调优要点?

```text
Broker 端:
  • num.network.threads = max(3, CPU/4)
  • num.io.threads = max(8, CPU * 2)
  • log.segment.bytes = 1 GB (默认)
  • log.flush.interval.messages = 大数字 (页缓存)
  • replica.fetch.min.bytes = 1 KB
  • replica.fetch.max.bytes = 1 MB

Producer 端:
  • batch.size = 64 KB ~ 1 MB
  • linger.ms = 5 ~ 20 ms
  • compression.type = lz4 / zstd
  • acks = all (数据安全) / 1 (性能)

Consumer 端:
  • fetch.min.bytes = 1 KB
  • fetch.max.wait.ms = 500 ms
  • max.poll.records = 500 ~ 1000
  • enable.auto.commit = false (手动)
```

### Q7:Kafka 3.x 是否还需要 ZK?

```text
Kafka 3.x 引入 KRaft 模式 (Kafka Raft) 替代 ZK

当前状态 (2026):
  • KRaft 模式 GA (General Availability)
  • 生产环境推荐使用 KRaft 模式
  • 老集群可继续用 ZK,但建议迁移

KRaft vs ZK 对比:
  • 部署: KRaft 模式无需 ZK 集群,运维更简单
  • 性能: KRaft 模式元数据操作更快
  • 扩展: KRaft 模式支持更大集群
  • 元数据: KRaft 模式支持 __cluster_metadata topic

迁移路径:
  1. 在同一集群启动 KRaft Controller (双模式运行)
  2. 数据迁移:__cluster_metadata 取代 ZK 中的元数据
  3. 切换连接:broker 与 controller 通信
  4. 下线 ZK

生产建议:
  • 新集群直接用 KRaft 模式
  • 老集群可保持 ZK 模式,但规划迁移
  • 关注官方迁移工具的成熟度
```

### Q8:如何处理 __consumer_offsets 损坏?

```text
现象:
  • consumer 无法提交 offset
  • group coordinator 报错
  • 所有 consumer 都被踢出 group

修复方法:
  1. 不能直接删除 __consumer_offsets (会丢所有 offset)
  2. 用 kafka-reassign-partitions 替换损坏的副本
  3. 重启 broker 让其重建

预防:
  • offsets.topic.replication.factor = 3 (必须 3 副本)
  • 不要用单点部署
  • 监控 __consumer_offsets 的 ISR
```

### Q9:Kafka 集群如何水平扩展?

```text
扩展步骤:
  1. 添加新 broker (无分区迁移)
     → 集群规模增大,但负载不会自动分散
  2. 用 kafka-reassign-partitions 迁移分区
     → 负载分散到新 broker
  3. 增加 topic partition 数
     → 提高并行度,但 key 路由会变化

注意事项:
  • 分区迁移过程会消耗网络带宽
  • partition 数只能增不能减 (减少需重建 topic)
  • 建议每次扩容 1-2 个 broker,不要一次扩太多
  • 监控迁移进度,避免长时间影响业务
```

### 6. 故障应急响应流程

```text
故障发生
  ↓
1. 收到告警 (PagerDuty / 企业微信)
  ↓
2. 5 分钟内:初步判断 (看 Grafana Dashboard)
  ↓
3. 15 分钟内:定位 (用 PromQL 查询关键指标)
  ↓
4. 30 分钟内:执行应急方案
  ↓
5. 故障恢复后:复盘,改进监控/告警
  ↓
6. 24 小时内:输出故障报告

应急方案选择:
  • Broker 不可用 → 重启 broker / 启用备机
  • 磁盘写满 → 删除无用数据 / 扩容
  • Lag 过高 → 扩容消费者 / 优化处理逻辑
  • ISR 收缩 → 排查慢节点 / 调参数
  • Controller 不可用 → 重启 controller / 检查 ZK
```

### 7. 监控的"反模式"

```text
反模式 1:装了 exporter 但没人看 Dashboard
  现象: 数据在采集,但没人看
  解决: 真正使用 Grafana 看,定期审视

反模式 2:告警太多导致疲劳
  现象: 几十条告警同时触发,真正的告警被淹没
  解决: 只配 P0/P1,定期 review

反模式 3:只看当前值,不看趋势
  现象: 看到 lag=10000 没反应,等 lag=100000 才慌
  解决: 配预测告警(增长率) + 趋势图

反模式 4:告警阈值一值不变
  现象: 业务增长后,旧阈值不再适用
  解决: 季度 review 阈值

反模式 5:忽略错误日志
  现象: 只看指标,不看 logs/server.log
  解决: 日志集中采集 (ELK) + 关键字告警
```

### 10. Kafka 集群升级流程详解

**版本升级原则**:

```text
1. 一次只升级一个 broker (滚动)
2. 升级前完整备份
3. 升级后观察至少 1 小时
4. 准备回滚方案
5. 业务低峰期操作
```

**Kafka 2.x → 3.x 升级注意事项**:

```text
重大变化:
  • Java 8 移除,需要 Java 11+
  • 移除一些旧 Producer/Consumer API
  • Kafka Streams API 变化
  • 默认配置调整
  • ZK 兼容性变化

升级前检查:
  □ 客户端是否还支持 Java 8?
  □ 自定义 Serdes 是否需要更新?
  □ Streams 代码是否使用了废弃 API?
  □ Kafka Connect 插件兼容性?
  □ Schema Registry 版本兼容?

升级步骤:
  1. 测试环境升级完整测试
  2. 生产环境小流量测试
  3. 生产环境完整升级
  4. 监控关键指标至少 7 天

回滚方案:
  • 保留旧版本二进制目录 (如 kafka-old)
  • 旧版本配置完整备份
  • 旧版本 ZK 数据快照
  • 一键回滚脚本 (切换软链接)
```

### 11. Producer/Consumer 端最佳实践

**Producer 最佳实践**:

```java
// Java Producer 配置 (生产级)
Properties props = new Properties();
props.put("bootstrap.servers", "kafka-1:9092,kafka-2:9092,kafka-3:9092");
props.put("acks", "all");                                // 数据安全
props.put("enable.idempotence", "true");                 // 幂等
props.put("max.in.flight.requests.per.connection", "5"); // 保序
props.put("retries", Integer.MAX_VALUE);                 // 无限重试
props.put("delivery.timeout.ms", "120000");              // 2分钟超时
props.put("compression.type", "lz4");                    // 压缩
props.put("linger.ms", "10");                            // 攒批
props.put("batch.size", "65536");                        // 64KB 批量
props.put("buffer.memory", "67108864");                  // 64MB 缓冲区

// 关键: 异常处理
producer.send(record, (metadata, exception) -> {
  if (exception != null) {
    // 重试逻辑 + 告警
  }
});
```

**Consumer 最佳实践**:

```java
// Java Consumer 配置
Properties props = new Properties();
props.put("bootstrap.servers", "kafka-1:9092,kafka-2:9092,kafka-3:9092");
props.put("group.id", "order-consumer");
props.put("enable.auto.commit", "false");                // 手动提交
props.put("auto.offset.reset", "earliest");
props.put("max.poll.records", "500");                    // 单次拉取上限
props.put("max.poll.interval.ms", "300000");             // 5分钟
props.put("session.timeout.ms", "30000");                // 30秒
props.put("isolation.level", "read_committed");          // 只读已提交

// 关键: 处理逻辑不能超过 max.poll.interval.ms
while (running) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
  for (ConsumerRecord<String, String> record : records) {
    // 处理逻辑
    process(record);
  }
  // 处理完成后提交
  consumer.commitSync();
}
```

**避免的坑**:

```text
坑 1:Consumer 关闭前没 commit → offset 丢失
坑 2:Producer.send() 不处理异常 → 消息丢失
坑 3:Consumer 处理太慢 → 触发 rebalance
坑 4:Producer buffer 满没监控 → 反压
坑 5:用同一个 KafkaConsumer 多线程调用 → 线程不安全
```

### 2. 一次性部署脚本

```bash
#!/bin/bash
# deploy-kafka-monitoring.sh
# 一次性部署 kafka_exporter + JMX Exporter

set -e

KAFKA_HOME=/opt/kafka
BROKERS="kafka-1:9092,kafka-2:9092,kafka-3:9092"
EXPORTER_PORT=9308
JMX_PORT=9309

# 1. 下载 kafka_exporter
cd /tmp
wget -q https://github.com/danielqsj/kafka_exporter/releases/download/v1.7.0/kafka_exporter-1.7.0.linux-amd64.tar.gz
tar -xzf kafka_exporter-1.7.0.linux-amd64.tar.gz
mv kafka_exporter-1.7.0.linux-amd64 /opt/kafka-exporter

# 2. 创建 systemd 服务
cat > /etc/systemd/system/kafka-exporter.service << EOF
[Unit]
Description=Kafka Exporter
After=network.target

[Service]
Type=simple
User=kafka
ExecStart=/opt/kafka-exporter/kafka_exporter \
  --kafka.server=$BROKERS \
  --web.listen-address=:$EXPORTER_PORT
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

# 3. 下载 JMX Exporter jar
wget -q https://repo1.maven.org/maven2/io/prometheus/jmx/jmx_prometheus_javaagent/0.19.0/jmx_prometheus_javaagent-0.19.0.jar \
  -O $KAFKA_HOME/libs/jmx_prometheus_javaagent.jar

# 4. 配置 JMX Exporter rules
cat > $KAFKA_HOME/config/jmx-exporter.yml << 'EOF'
---
startDelaySeconds: 0
ssl: false
lowercaseOutputName: true
rules:
  - pattern: "kafka.server<type=BrokerTopicMetrics, name=(.+)><>Count"
    name: "kafka_server_broker_topic_metrics_$1_total"
  - pattern: "kafka.server<type=BrokerTopicMetrics, name=(.+)><>OneMinuteRate"
    name: "kafka_server_broker_topic_metrics_$1_rate"
  - pattern: "kafka.server<type=ReplicaManager, name=(.+)><>Value"
    name: "kafka_server_replica_manager_$1"
    type: GAUGE
  - pattern: "kafka.network<type=RequestMetrics, name=TotalTimeMs, request=(.+), quantile=(\\w+)><>Value"
    name: "kafka_network_request_total_time_ms"
    labels:
      request: "$1"
      quantile: "$2"
    type: GAUGE
  - pattern: "java.lang<type=GarbageCollector, name=(.+)><>CollectionCount"
    name: "jvm_gc_collection_count"
    labels:
      gc: "$1"
    type: COUNTER
EOF

# 5. 修改 Kafka 启动配置
echo "" >> $KAFKA_HOME/bin/kafka-server-start.sh
echo "export KAFKA_OPTS=\"\$KAFKA_OPTS -javaagent:$KAFKA_HOME/libs/jmx_prometheus_javaagent.jar=$JMX_PORT:$KAFKA_HOME/config/jmx-exporter.yml\"" >> $KAFKA_HOME/bin/kafka-server-start.sh

# 6. 启动
systemctl daemon-reload
systemctl enable kafka-exporter
systemctl start kafka-exporter

# 7. 验证
sleep 5
curl -s http://localhost:$EXPORTER_PORT/metrics | head
echo "Kafka monitoring stack deployed successfully!"
```

### 5. 跨集群数据一致性校验

```python
#!/usr/bin/env python3
"""cross_cluster_compare.py
对比两个 Kafka 集群的 message offset,验证数据一致性
"""

from kafka import KafkaConsumer, TopicPartition

CLUSTER_A = ['cluster-a-1:9092', 'cluster-a-2:9092']
CLUSTER_B = ['cluster-b-1:9092', 'cluster-b-2:9092']
TOPIC = 'orders'

def get_end_offsets(brokers, topic):
    consumer = KafkaConsumer(bootstrap_servers=brokers)
    partitions = consumer.partitions_for_topic(topic)
    tps = [TopicPartition(topic, p) for p in partitions]
    end_offsets = consumer.end_offsets(tps)
    consumer.close()
    return end_offsets

offsets_a = get_end_offsets(CLUSTER_A, TOPIC)
offsets_b = get_end_offsets(CLUSTER_B, TOPIC)

print(f"=== Cluster A ({TOPIC}) ===")
for tp, offset in sorted(offsets_a.items()):
    print(f"  {tp.partition}: {offset}")

print(f"\n=== Cluster B ({TOPIC}) ===")
for tp, offset in sorted(offsets_b.items()):
    print(f"  {tp.partition}: {offset}")

# 对比
diff_count = 0
for tp in offsets_a:
    a_offset = offsets_a[tp]
    b_offset = offsets_b.get(tp, 0)
    diff = abs(a_offset - b_offset)
    if diff > 100:  # 允许小差异
        print(f"  WARN: partition {tp.partition} diff={diff} (a={a_offset}, b={b_offset})")
        diff_count += 1

if diff_count == 0:
    print("\n✓ 数据一致")
else:
    print(f"\n⚠ {diff_count} 个分区差异较大")
```

### 3. 自动扩容分区

```python
#!/usr/bin/env python3
"""auto_scale_partitions.py
当 lag 持续过高时,自动扩容分区
"""

import requests
from kafka.admin import KafkaAdminClient
import subprocess

PROMETHEUS = 'http://prometheus:9090'
LAG_THRESHOLD = 100000
MIN_PARTITIONS = 10
MAX_PARTITIONS = 200

def get_lag(consumer_group, topic):
    """从 Prometheus 查询 lag"""
    query = f'''
    sum by (partition) (
      kafka_consumergroup_log_end_offset{{consumergroup="{consumer_group}", topic="{topic}"}}
      - on(topic, partition) group_right()
      kafka_consumergroup_current_offset{{consumergroup="{consumer_group}", topic="{topic}"}}
    )
    '''
    response = requests.get(f'{PROMETHEUS}/api/v1/query', params={'query': query})
    return response.json()['data']['result']

def get_current_partitions(admin, topic):
    """获取当前分区数"""
    info = admin.describe_topics([topic])
    return len(info[0]['partitions'])

def should_scale_up(lag_results, threshold):
    """判断是否需要扩容"""
    total_lag = sum(float(r['value'][1]) for r in lag_results)
    return total_lag > threshold

admin = KafkaAdminClient(bootstrap_servers=['kafka-1:9092'])

# 检查所有 consumer group
groups = admin.list_consumer_groups()
for group_id, _ in groups:
    # ... 获取该 group 消费的 topic
    # ... 查询 lag
    if should_scale_up(lag_results, LAG_THRESHOLD):
        current = get_current_partitions(admin, topic)
        if current < MAX_PARTITIONS:
            new_count = min(current * 2, MAX_PARTITIONS)
            print(f"Scaling {topic} from {current} to {new_count} partitions")
            # 调 kafka-topics.sh --alter
            subprocess.run([
                'kafka-topics.sh', '--bootstrap-server', 'kafka-1:9092',
                '--alter', '--topic', topic, '--partitions', str(new_count)
            ])
```

### 6. 故障自愈脚本

```python
#!/usr/bin/env python3
"""auto_recovery.py
基于监控告警的故障自愈
"""

import requests
import subprocess
import time

PROMETHEUS = 'http://prometheus:9090'

def query_prom(query):
    """查询 Prometheus"""
    response = requests.get(f'{PROMETHEUS}/api/v1/query', params={'query': query})
    return response.json()['data']['result']

def recover_broker(host):
    """重启 broker"""
    print(f"恢复 broker {host}")
    subprocess.run(['ssh', host, 'systemctl', 'restart', 'kafka'])
    time.sleep(30)
    # 验证
    result = query_prom(f'up{{instance=~"{host}.*"}}')
    return len(result) > 0 and float(result[0]['value'][1]) == 1

def main():
    # 检查离线的 broker
    down_brokers = query_prom('up{job="kafka-exporter"} == 0')
    
    for broker in down_brokers:
        host = broker['metric']['instance'].split(':')[0]
        if recover_broker(host):
            print(f"✓ {host} 恢复成功")
        else:
            print(f"✗ {host} 恢复失败,需要人工介入")
            # 发送告警
            send_alert(f"Broker {host} 自愈失败,需要人工处理")

if __name__ == "__main__":
    main()
```

### 案例 1:某电商大促 Kafka 调优

```text
背景:
  • 业务:某电商双 11 大促
  • 流量:生产峰值 50 万 msg/s
  • 集群:5 broker, RF=3
  • 问题:大促开始后 Producer 延迟飙到 5s

排查:
  1. 看 broker 端 NetworkProcessorAvgIdle = 5%
     → 网络线程接近打满

  2. 看 broker 端 Network 延迟 P99 = 800ms
     → 网络处理不过来

  3. 看 topic 分区数 = 30
     → 不够,5 broker × 30 partition 还行
     → 但单 broker 处理 18 个 partition,过多

  4. 看 broker 机器配置:
     → 8 CPU / 32 GB 内存
     → num.network.threads=3, num.io.threads=8 (默认)

调优:
  1. 增加 partition 数:30 → 60
  2. 增加 network threads:3 → 8
  3. 增加 io threads:8 → 16
  4. Producer 端 batch.size:16 KB → 64 KB
  5. Producer 端 linger.ms:0 → 10

效果:
  • Producer 延迟:5s → 50ms
  • Broker CPU 利用率:90% → 60%
  • 网络吞吐:30% → 50% 网卡
```

### 案例 2:某金融 Kafka 数据丢失事件

```text
背景:
  • 业务:某支付系统
  • 事件:由于 broker 配置错误,导致 1 小时内 100 万条交易数据丢失
  • 原因分析:
    
    1. 该集群 RF=2, min.insync.replicas=1 (配置过低)
    2. Producer 配置 acks=1 (非 all)
    3. 一个 broker 故障时,Producer 仍写入
    4. 但因为 RF=2 + min.isr=1,数据写入新 leader 但旧 leader 副本丢失
    5. 故障 broker 恢复后,从错误源头复制,数据丢失

复盘:
  • 数据安全配置错误是根本原因
  • 监控告警缺失:
    - 没有 Unclean Leader Election 告警
    - 没有 ISR 收缩告警
  • 演练缺失:
    - 没有做过 broker 故障演练
    - 没有验证过 RF=2 的数据可靠性

改进:
  1. RF=2 → RF=3
  2. min.insync.replicas=1 → 2
  3. Producer acks=1 → all
  4. 增加告警:
     - UncleanLeaderElectionsPerSec > 0
     - IsrShrinksPerSec > 0
     - 离线的 broker 数
  5. 每季度做故障演练
```

### 案例 3:某视频网站 Consumer 优化

```text
背景:
  • 业务:某视频网站播放日志
  • 数据:每天 100 亿条
  • 问题:Consumer 一直 lag,达 5000 万

分析:
  1. topic 有 100 个 partition
  2. 消费者 10 个实例
  3. 每个实例消费 10 个 partition
  4. 单实例处理 100 亿 / 10 / 86400 = 11.6 万 msg/s
  5. 单条消息处理 = 1ms (含数据库写入)
  6. 单实例吞吐上限 = 1000 msg/s
  7. 实际需要 11.6 万,差距 100 倍

解决方案:
  1. 短期:扩容 consumer 到 1000 个实例
  2. 根本:批量写入数据库
     • 原来是 1 条 1 次写入
     • 改为 1000 条 1 次写入
  3. 优化后:单实例吞吐 = 1 万 msg/s
  4. 实际只需 12 个 consumer 实例

效果:
  • Consumer 数:1000 → 12
  • Lag:5000 万 → < 1000
  • 数据库写入压力:降低 100 倍
```

### 案例 4:某社交平台跨集群迁移

```text
背景:
  • 业务:某社交平台从 Kafka 2.4 迁移到 3.5
  • 集群:20 broker, 10000+ topic
  • 挑战:不停机迁移,数据不丢

迁移方案:
  1. 部署新集群 (Kafka 3.5)
  2. 配置 MirrorMaker 2 (老→新)
  3. 应用层双写:
     • Producer 同时写入老 + 新集群
     • Consumer 暂时只读老集群
  4. 验证新集群数据完整性
  5. 应用层切读:
     • Consumer 切换到新集群
     • 保留老集群只读 (回滚用)
  6. 应用层停止写老集群
  7. 保留老集群 30 天
  8. 下线老集群

总耗时:3 个月
关键监控:
  • MM2 同步 lag < 5 分钟
  • 新集群消息数 = 老集群消息数
  • 端到端延迟监控
```

## 二十四、监控体系总结

### 1. 监控的本质

```text
监控不是为了收集数据,而是为了:

1. 知道系统是否正常 (可用性)
2. 知道系统是否高效 (性能)
3. 知道系统是否安全 (数据安全)
4. 知道未来是否撑得住 (容量)

最终目的:让系统持续稳定地为业务服务
```

### 2. 监控的核心价值

```text
价值 1: 故障快速响应
  • 告警 → 通知 → 响应 → 恢复
  • 从小时级降到分钟级

价值 2: 问题提前发现
  • 趋势分析 → 提前扩容
  • 容量预警 → 避免故障

价值 3: 性能持续优化
  • 瓶颈定位 → 优化方向
  • 数据驱动决策

价值 4: 业务洞察
  • 流量分析 → 业务决策
  • 数据血缘 → 业务理解

价值 5: 自动化基础
  • 监控数据 → 自动化触发
  • 自愈系统 → 减少人工
```

### 3. 监控建设的常见误区

```text
误区 1: 工具主义
  现象: 追求最新最全的工具
  真相: 工具是手段,业务价值才是目标

误区 2: 大而全
  现象: 上来就搭建完整体系
  真相: 应该循序渐进,L1 → L2 → L3

误区 3: 数据收集就够了
  现象: 装完 exporter 就不管了
  真相: 必须配置告警、绘制 Dashboard

误区 4: 阈值拍脑袋
  现象: 阈值拍脑袋,不根据业务调整
  真相: 阈值需要观察和调优

误区 5: 告警就是监控
  现象: 只关注告警
  真相: 告警只是监控的一部分,趋势同样重要

误区 6: 一次性建设
  现象: 一次性把所有都建好
  真相: 监控体系是演进的,持续优化
```

### 4. 监控建设的最佳实践

```text
实践 1: 从业务出发
  • 业务 SLA 是什么?
  • 关键指标是什么?
  • 用户痛点是什么?

实践 2: 从简单开始
  • 先 node_exporter + kafka_exporter
  • 先 3-5 个关键告警
  • 先 1 个核心 Dashboard

实践 3: 持续迭代
  • 每周 review 监控数据
  • 每月添加新告警
  • 每季度评估覆盖度

实践 4: 文档化
  • 监控架构文档
  • 告警 runbook
  • 故障复盘文档

实践 5: 演练驱动
  • 故障演练
  • 告警演练
  • 灾备演练

实践 6: 自动化优先
  • 监控自动化
  • 告警自动化
  • 自愈自动化
```

### 5. 监控与可观测性

```text
可观测性 (Observability) 三大支柱:

1. Metrics (指标)
   • 数值型时间序列
   • 用于趋势分析、告警
   • Kafka 监控核心

2. Logs (日志)
   • 离散事件
   • 用于故障排查
   • Kafka server.log

3. Traces (链路追踪)
   • 请求级调用链
   • 用于全链路分析
   • APM 集成

Kafka 监控重点是 Metrics,但 Logs 和 Traces 也必不可少
```

## 十五、核心要点速记

### 1. 监控体系四层

```text
硬件层  → node_exporter (CPU/Mem/Disk/Net)
JVM 层  → JMX Exporter (GC/Heap/Thread)
Broker 层 → kafka_exporter (流量/副本/Lag)
业务层  → Burrow / kafka-lag-exporter / 自定义
```

### 2. 核心监控黄金指标

| 指标 | 阈值 | 检查方式 |
|------|------|----------|
| `MessagesInPerSec` | 根据容量 | Grafana |
| `BytesIn/OutPerSec` | < 网卡带宽 70% | Grafana |
| `UnderReplicatedPartitions` | 0 | kafka_exporter |
| `NetworkProcessorAvgIdlePercent` | > 30% | JMX |
| `Produce P99` | < 50ms | JMX |
| `Fetch P99` | < 100ms | JMX |
| `Consumer Lag` | < 业务容忍 | kafka-lag-exporter |
| `ISR 收缩速率` | ≈ 0 | JMX |
| `磁盘使用率` | < 80% | node_exporter |

### 3. kafka_exporter 关键指标

```text
kafka_topic_partition_in_sync_replicas          # ISR 数量
kafka_topic_partition_under_replicated_partition  # 副本不足
kafka_consumergroup_log_end_offset              # LEO
kafka_consumergroup_current_offset              # 消费位移
Lag = LEO - current_offset
```

### 4. 告警优先级

```text
Critical (立即响应,通知 on-call):
  • Broker 离线
  • Controller 不可用
  • Unclean Leader Election
  • Consumer Lag > 100000
  • 磁盘使用率 > 90%

Warning (工作时间处理):
  • UnderReplicatedPartitions > 0
  • ISR 收缩过快
  • Consumer Lag > 10000
  • Produce P99 > 200ms
  • 磁盘使用率 > 80%
```

### 5. 运维操作原则

```text
✓ 一次只操作一个 Broker
✓ 关键操作前先备份 (server.properties + ZK 数据)
✓ 操作后验证 (kafka-broker-api-versions.sh)
✓ 监控告警的"事后复盘" > "事前预防"
✓ 容量规划要提前 6 个月,不要等问题出现才扩容
✓ 滚动重启选择业务低峰期
✓ reassign-partitions 用 --throttle 限速
```

### 6. 容量规划公式

```text
磁盘容量 = 生产速率 × 保留时间 × 副本数 × 1.2 (冗余)
网络带宽 = 生产速率 × 副本数 × 1.3 + 消费速率
内存     = JVM Heap (8 GB) + Page Cache (业务决定)

示例 (生产 100 MB/s,保留 7 天,RF=3):
  磁盘 = 100 × 86400 × 7 × 3 × 1.2 ≈ 218 TB
  带宽 = 100 × 3 × 1.3 + 200 ≈ 590 MB/s ≈ 4.7 Gbps
```

### 7. 备份恢复三件套

```text
1. 多副本 (RF≥3, min.insync.replicas=2)  → 在线数据冗余
2. MirrorMaker 2                          → 异地实时灾备
3. 文件级备份 + S3/OSS                    → 应对逻辑错误

RPO: 0 (主) / 24h (S3)
RTO: < 5 min (灾备切换) / 数小时 (S3 恢复)
```

### 8. 监控工具速查

| 工具 | 用途 | 选型建议 |
|------|------|----------|
| **kafka_exporter** | Kafka 全指标 → Prometheus | 必装 |
| **JMX Exporter** | JVM 详细指标 → Prometheus | 装 |
| **kafka-lag-exporter** | 专门 Lag + 告警 | 装 |
| **Burrow** | Lag 状态评估 | 大集群 |
| **CMAK** | 集群管理 UI | ⚠️ 停更 |
| **AKHQ** | 集群管理 UI (替代 CMAK) | 推荐 |
| **Confluent Control Center** | 商业版全功能 | 大企业 |

### 9. 排查流程速记

```text
1. 业务报障 → 现象是什么?
2. 看 Grafana → 哪个指标异常? (Lag? ISR? CPU?)
3. 看 Broker 日志 → 有无 ERROR/WARN?
4. 看 ZK 状态 → Controller 在线吗?
5. 看 Consumer 状态 → Group 在 rebalance?
7. 定位根因 → 网络? 磁盘? 配置?
8. 修复 → 滚动重启 / 扩容 / 调整分区
9. 验证 → 指标恢复
10. 复盘 → 改进告警阈值
```

### 10. 金句

- **没有告警的监控 = 没有监控**
- **Lag 是 Kafka 的核心黄金指标**
- **ISR 收缩 = 数据安全亮红灯**
- **备份是最后一道防线,不能替代高可用**
- **容量规划提前 6 个月,不要等问题暴露才扩容**
- **滚动重启:一次一个,确保集群永远可用**
- **MM2 是跨集群数据同步的事实标准**

### 11. 故障排查 Playbook

#### 11.1 案例 1:Consumer Lag 持续增长

```text
现象:
  • Grafana 显示 consumer-group "order-consumer" lag 从 1000 增长到 50000
  • 业务反馈订单数据延迟

排查:
  1. 看 broker 端 MessagesInPerSec (生产速率)
     → 50000 msg/s (业务大促)
  
  2. 看 consumer 端 records-consumed-rate
     → 30000 msg/s (追不上生产)
  
  3. 看 consumer 端 fetch-latency-avg
     → 5ms (网络正常)
  
  4. 看 consumer 进程
     → ps -ef | grep consumer
     → 仅有 3 个消费者实例
     
  5. 看 partition 数
     → topic 有 20 个 partition,但只有 3 个 consumer
     → 20 个 partition 分给 3 个 consumer 处理
  
  6. 单 consumer 处理 6.67 个 partition,合计消费 30000 msg/s
     → 单 partition 需消费 1500 msg/s = 250/s (处理不过来)

解决方案:
  a. 临时方案:增加 consumer 实例 (扩容到 20)
  b. 根本方案:优化 consumer 处理逻辑 / 增加 partition 数
```

#### 11.2 案例 2:ISR 频繁收缩

```text
现象:
  • IsrShrinksPerSec 持续 > 0
  • UnderReplicatedPartitions > 0 (间歇性)
  • 偶发 NotEnoughReplicasException

排查:
  1. 看哪个 broker 上的 Follower 在被踢
     → kafka-broker-api-versions.sh 确认 broker 列表
     → 看每台机器的 UnderReplicatedPartitions 分布
  
  2. 看被踢 broker 的性能指标
     → node_exporter: CPU 高 / 磁盘 IO 高 / 网络丢包
  
  3. 看 replica.lag.max.messages (默认 4000)
     → Follower 落后超过 4000 条就被踢
  
  4. 看 replica.fetch.min.bytes / replica.fetch.max.bytes
     → 默认 fetch 太慢

解决方案:
  a. 短期:调大 replica.lag.time.max.ms (默认 30000 → 60000)
  b. 短期:增大 num.replica.fetchers (默认 1 → 4)
  c. 根本:解决慢 broker 问题 (升级磁盘 / 优化网络)
```

#### 11.3 案例 3:Controller 切换风暴

```text
现象:
  • ActiveControllerCount 在 0/1 间频繁跳变
  • kafka_controller_stats_unclean_leader_elections 增加
  • Producer 偶发 MetadataResponse 失败

排查:
  1. 看 ZK 日志 → 是否有 GC 暂停 / 网络抖动
  2. 看 Controller broker 进程日志 → 是否在主动退出
  3. 看 session.timeout.ms → 默认 18s 是否够

解决方案:
  a. 调整 zookeeper.session.timeout.ms = 30000
  b. 给 Controller broker 配置更高优先级
  c. 排查 ZK 端问题
```

#### 12.1 监控建设顺序


#### 12.2 常见误区

```text
误区 1:装了 kafka_exporter 就够了
  真相:必须配合 JMX Exporter + node_exporter

误区 2:告警越多越好
  真相:告警疲劳导致真告警被忽略,只配 P0/P1

误区 3:只看平均值
  真相:必须看 P95/P99 分位数

  真相:网络、内存、CPU 都要看

  真相:监控只能发现问题,日志才能定位问题

  真相:Kafka 是软件,任何软件都有 bug
```
