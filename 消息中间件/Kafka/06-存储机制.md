# Kafka 存储机制

> 本章深入剖析 Kafka 的底层存储机制:日志分片 (Log Segment) 模型、磁盘文件结构 (`.log`/`.index`/`.timeindex`/`.snapshot`/`.txnindex`)、消息物理格式 (Record Batch / Record)、稀疏索引与二分查找、零拷贝与页缓存、日志清理策略 (Retention / Compact)、文件恢复,以及与关系型数据库 / 传统文件系统在存储模型上的本质差异。

---

## 一、Kafka 存储概述

### 1. Kafka 为什么快?——存储设计的三条主线

Kafka 之所以能在普通机械磁盘上实现**百万级 TPS**,根源在于它的存储设计打破了"数据库 = 随机读写"的天花板。三条主线贯穿始终:

1. **磁盘顺序读写**:所有消息按 offset 追加写入,顺序访问磁盘。机械盘顺序写性能 ≈ 随机写的数百倍,SSD 也仍有数倍差距。
2. **零拷贝 (Zero Copy)**:Consumer 拉取消息时,通过 `sendfile()` / `mmap` 让数据从 Page Cache **直接送到网卡**,跳过 JVM 堆和用户态缓冲区。
3. **页缓存 (Page Cache) + 批量网络传输**:Producer/Consumer 与磁盘的交互都通过 OS Page Cache,Producer 攒批、Consumer 批量拉取,网络往返与磁盘 I/O 都被摊薄。

这三条主线都建立在 Kafka **把消息当作"日志文件"** 而不是"表记录"来对待的核心抽象之上。

### 2. 存储模型基本概念

| 概念                  | 含义                                                              |
|-----------------------|------------------------------------------------------------------|
| **Topic**             | 消息主题,逻辑分类,一个 Topic 可被分为多个 Partition             |
| **Partition**         | 物理分片,一个 Partition 是一个**有序、不可变**的消息序列         |
| **Offset**            | 分区内单调递增的 64 位整数,消息的唯一编号 (分区级别)             |
| **Log**               | Partition 在磁盘上的物理表现,即一组 Log Segment 文件的集合       |
| **Log Segment**       | 日志分片,Log 按大小/时间切分的物理文件段                         |
| **Replica**           | Partition 的副本,Leader 负责读写,Follower 负责备份              |
| **HW (High Watermark)** | 已完成 ISR 同步的最高 offset,Consumer 最多能消费到 HW            |
| **LSO (Log Start Offset)** | 日志的起始 offset,Retention 清理后会被推进                  |

### 3. 存储目录结构

Kafka 默认将所有 Partition 的日志存放在 `log.dirs` 指定的目录下,典型结构如下:

```text
log.dirs/
├── topic-orders-0/                          # Topic:orders,Partition 0
│   ├── 00000000000000000000.log             # Log Segment,起始 offset = 0
│   ├── 00000000000000000000.index
│   ├── 00000000000000000000.timeindex
│   ├── 00000000000000000000.txnindex         # 启用事务后才有
│   ├── 00000000000123456789.log             # 滚动后的新 Segment
│   ├── 00000000000123456789.index
│   ├── 00000000000123456789.timeindex
│   ├── leader-epoch-checkpoint               # Leader Epoch 检查点
│   └── partition.metadata                   # 分区元数据(版本号等)
├── topic-orders-1/
│   └── ...
├── topic-orders-2/
│   └── ...
├── __consumer_offsets-0/                    # 内部 Topic,保存消费位移
│   └── ...
└── __transaction_state-0/                   # 内部 Topic,事务状态
    └── ...
```

每个分区一个目录,目录名格式为 `<topic>-<partitionId>`。**同名同分区目录在不同 Broker 上数据不同**(因为各自存的是副本)。

### 4. 关键特性总结

| 特性                  | 说明                                                                |
|----------------------|---------------------------------------------------------------------|
| **顺序写入**         | 消息按 offset 追加,磁盘几乎零寻道                                 |
| **不可变性**         | 已写入的消息不可修改(只能产生新消息或被清理)                       |
| **分区分段**         | 每个 Partition 内部按 segment 切分,便于清理与恢复                  |
| **稀疏索引**         | `.index` 不是每条消息都建索引,而是间隔建索引,内存开销极小           |
| **零拷贝传输**       | Consumer 拉取走 sendfile/mmap,几乎不消耗 JVM 堆                    |
| **OS 页面缓存**      | 热数据天然驻留 Page Cache,重启不丢、不重建                          |
| **批量 + 压缩**      | Record Batch 内可对多条消息一起压缩,broker 端不解压直转            |

### 5. 一条消息从生产到落盘的完整路径

为了建立整体印象,我们跟踪一条消息从 Producer 到磁盘的完整生命周期:

```text
1. Producer 端
   ├─ 业务调用 producer.send(record) 提交一条消息
   ├─ 消息进入 RecordAccumulator(内存中的 Map<TopicPartition, Deque<ProducerBatch>>)
   ├─ 按 batch.size (默认 16 KB) 攒批,或 linger.ms (默认 0) 到时触发发送
   ├─ Sender 线程拉取批次,封装进 ClientRequest
   └─ 发送到对应 Partition 的 Leader Broker (经 Partitioner 路由)

2. Broker 端 (KafkaRequestHandler 线程)
   ├─ 解析 Produce 请求,获取 RecordBatch
   ├─ 校验 producerId / epoch / sequence(幂等检查)
   ├─ 检查 acks、min.insync.replicas 是否满足
   ├─ 写入 Partition 的 active Segment
   │    ├─ 先写 Page Cache (内存追加)
   │    ├─ 更新 LEO (Log End Offset)
   │    ├─ 更新索引 .index / .timeindex (按 interval 间隔)
   │    └─ 通知各 ReplicaFetcher 线程
   └─ 返回 Produce Response 给 Producer

3. Follower 副本同步
   ├─ ReplicaFetcher 线程从 Leader Fetch 数据
   ├─ 通过 sendfile 走零拷贝传输
   ├─ 写入本地 active Segment
   └─ 同步推进本地 LEO 与 Fetch Offset

4. 异步刷盘
   ├─ Log Flusher 线程按 log.flush.interval.ms / messages 触发 fsync
   └─ OS 后台按 dirty ratio 阈值主动回写 Page Cache 到磁盘

5. 返回确认
   └─ Leader 在所有 ISR Follower 追上后,提升 HW,完成 ack
```

从这条路径可以看到,Kafka 的写入路径**只有"追加到末尾"一种 I/O 模式**,没有任何"查找空闲块 / 维护 B+Tree / 写 WAL"的复杂开销——这是它高吞吐的根本原因。

### 6. 与传统 MQ 的存储对比

| 中间件        | 存储模型              | 典型吞吐         | 顺序性保证        |
|--------------|---------------------|-----------------|------------------|
| **Kafka**   | 日志 + 分段 + 稀疏索引  | 百万级 msg/s    | 分区内强有序       |
| **RabbitMQ**| 队列 + 索引(B+Tree)   | 万级 msg/s     | 队列内 FIFO       |
| **ActiveMQ**| 队列 + KahaDB         | 千级 msg/s     | 队列内 FIFO       |
| **RocketMQ**| CommitLog + ConsumeQueue | 十万级 msg/s | 队列内强有序       |
| **Pulsar**  | BookKeeper 分段日志   | 百万级 msg/s    | 分区内强有序       |

RabbitMQ 在消息达到一定数量后会显著变慢,因为它要维护索引树;Kafka 无论消息量多少,写入开销几乎恒定,**这是消息中间件选型时最常被忽略的关键差异**。

### 7. 存储相关的关键 Broker 配置一览

```properties
# 数据目录(可配多个,用逗号分隔)
log.dirs=/var/lib/kafka/data

# 单 Segment 大小
log.segment.bytes=1073741824        # 1 GB
log.segment.ms=-1                    # 不强制按时间滚动

# 索引间隔与最大大小
log.index.interval.bytes=4096       # 每 4 KB 一条索引
log.index.size.max.bytes=10485760   # 索引文件 10 MB 上限

# 消息保留
log.retention.hours=168             # 7 天
log.retention.bytes=-1              # 不限制总大小
log.retention.check.interval.ms=300000  # 5 分钟检查一次

# 清理策略
log.cleanup.policy=delete           # delete / compact / 组合
log.cleaner.min.cleanable.ratio=0.5
log.cleaner.threads=1
log.cleaner.delete.retention.ms=86400000  # tombstone 保留 24h

# 刷盘
log.flush.interval.messages=9223372036854775807  # 默认极大,关闭主动 flush
log.flush.interval.ms=9223372036854775807         # 同上
log.flush.scheduler.interval.ms=9223372036854775807

# 副本相关(与存储强相关)
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false

# 文件描述符
num.recovery.threads.per.data.dir=1
```

注意 `log.flush.*` 三个默认值都是 `Long.MAX_VALUE`,**意味着默认完全关闭主动刷盘**——这是有意为之,因为 OS 的 Page Cache + 后台回写已经足够。生产中**不建议**主动修改这三个值,除非有明确的数据安全要求(且能接受吞吐下降)。

### 8. Producer / Consumer 侧的存储相关配置

Producer 端真正影响磁盘的是 `linger.ms` + `batch.size` 的攒批策略:

```properties
# Producer 攒批
linger.ms=5               # 等待 5ms 凑批(增加延迟,提升吞吐)
batch.size=32768           # 32 KB 一批
compression.type=lz4       # Producer 端压缩(broker 端保持)
acks=all                   # 必须等所有 ISR 确认
enable.idempotence=true    # 幂等(防重复)
max.in.flight.requests.per.connection=5  # 幂等开启后最大 5
```

Consumer 端影响读取效率的:

```properties
# Consumer 拉取
fetch.min.bytes=1          # broker 端最小返回字节数
fetch.max.bytes=52428800   # 50 MB 单次最大
max.partition.fetch.bytes=1048576  # 1 MB per partition
fetch.max.wait.ms=500      # 最长等待 500ms
isolation.level=read_committed  # 事务消费级别
```

Consumer 拉到的数据**只走内存**(自己的 fetcher buffer),**不会写本地文件**——Kafka 的"存储"在 Consumer 侧几乎为零,这是它与 RabbitMQ 的另一个本质区别。

## 二、日志分片 (Log Segment) 详解

### 1. 什么是 Log Segment

一个 Partition 的"日志"在物理上并不是一个巨大的单文件,而是被切分为**多个固定大小的 Segment 文件**。每个 Segment 独立封闭,可以单独被创建、滚动、删除、恢复。

```text
┌────────────────────────────────────────────────────────────────────────┐
│  Partition: topic-orders-0  (Log)                                       │
│                                                                        │
│   Segment 0               Segment 1               Segment 2            │
│  ┌───────────────┐       ┌───────────────┐       ┌───────────────┐     │
│  │   .log        │       │   .log        │       │   .log        │     │
│  │   .index      │       │   .index      │       │   .index      │     │
│  │   .timeindex  │       │   .timeindex  │       │   .timeindex  │     │
│  │ (000...00000) │       │ (000...12345) │       │ (000...98765) │     │
│  │  offset 范围  │       │  offset 范围  │       │  offset 范围  │     │
│  │  [0, 12344]   │       │  [12345,98764]│       │  [98765, ...] │     │
│  └───────────────┘       └───────────────┘       └───────────────┘     │
│       active(写入)        sealed(只读)              sealed(只读)        │
└────────────────────────────────────────────────────────────────────────┘
```

- **活跃 Segment (Active Segment)**:当前正在写入的 Segment,文件后缀 `.log` 在写入中。
- **已封口 Segment (Sealed Segment)**:达到滚动条件后被关闭,之后只读,等待被清理。

### 2. Segment 滚动策略

Kafka 提供**三类滚动触发条件**,任意一个满足即触发滚动 (Rolling)。

#### 2.1 基于大小

| 配置项                              | 默认值     | 含义                              |
|------------------------------------|-----------|----------------------------------|
| `log.segment.bytes`                | 1073741824 (1 GB) | 单个 Segment 文件最大字节数   |
| `log.segment.bytes.max` (新版本)   | 与上同    | 单 Segment 硬上限                  |

> **默认值 1 GB** 是 Kafka 团队经过大量压测的"甜点值":既能减少文件描述符占用,又能在常见 Retention 周期内保留足够历史。生产可按业务调小到 256 MB / 512 MB,以加快清理粒度。

#### 2.2 基于时间

| 配置项                              | 默认值     | 含义                                          |
|------------------------------------|-----------|----------------------------------------------|
| `log.roll.ms`                      | -1        | 强制按时间滚动,覆盖 segment.ms 的计算结果     |
| `log.roll.hours`                   | 168 (7 天)| 已弃用,新版本以 `log.roll.ms` 为主           |
| `log.segment.ms` (新版本)          | 604800000 | 同 `log.roll.ms`                              |

即使 Segment 没写满,达到这个时长也会强制滚动。**目的是避免出现一个 Segment 永远不封口导致清理线程无法删除旧数据**。

#### 2.3 基于索引满

| 配置项                              | 默认值     | 含义                                          |
|------------------------------------|-----------|----------------------------------------------|
| `log.index.size.max.bytes`         | 10485760 (10 MB) | `.index` 文件的最大字节数            |
| `log.index.interval.bytes`         | 4096      | 每写入多少字节向 `.index` 加一条索引          |

当索引文件接近上限,Segment 也会滚动(避免索引过大影响加载)。

#### 2.4 滚动流程

```text
   Producer 写入新消息
         │
         ▼
   ┌──────────────────────────┐
   │ 追加到 active segment    │
   │ 检查滚动触发条件:        │
   │  - size >= segment.bytes │
   │  - age >= segment.ms     │
   │  - index >= index.max    │
   └──────────────────────────┘
         │
         ▼ (任一满足)
   1. 关闭当前 .log / .index / .timeindex
   2. 创建新 Segment,baseOffset = 当前 LEO
   3. 标记旧 Segment 为 sealed(只读)
   4. 通知 LogCleaner / LogRetention 线程
```

### 3. Segment 文件命名规则

Segment 文件的**文件名就是该 Segment 中第一条消息的 offset (baseOffset)**,固定 20 位十进制数字,不足前补 0:

```text
00000000000000000000.log         ← baseOffset = 0
00000000000123456789.log         ← baseOffset = 123456789
00000000000987654321.log         ← baseOffset = 987654321
```

**为什么用 baseOffset 而非自增 ID?**

- offset 是单调递增的,文件名天然有序
- 可以用 `ls` 直接看到分区的 offset 范围
- 启动恢复时,按文件名排序即可得到消息的物理顺序
- 计算"下一个 Segment 的 baseOffset"无需查表,直接读当前 Segment 最后一个 offset

> Kafka 2.0 之前,文件名是**前一个 Segment 的最后一个 offset**,之后的版本改成了**本 Segment 的起始 offset (baseOffset)**。注意版本差异,排障时不要混淆。

### 4. 滚动策略的实际取舍

```text
场景 A: 流量平稳 (每分钟 1 万条,单条 1 KB)
   ├─ 大小触发:约 17 分钟一次
   ├─ 时间触发:7 天一次
   └─ 主导因素:大小 (17 分钟)

场景 B: 流量极小 (每小时 100 条)
   ├─ 大小触发:永不触发
   ├─ 时间触发:7 天一次
   └─ 主导因素:时间 (保证日志有滚动,可被清理)

场景 C: 流量突发 (突然每秒 10 万条)
   ├─ 大小触发:1 GB 大约 100 秒一次
   ├─ 时间触发:不触发
   └─ 主导因素:大小 (防止单 Segment 过大)

结论:
   - 大流量场景:按大小滚动,生成大量 Segment
   - 小流量场景:必须配置时间滚动,避免"永远不封口"导致清理无效
```

### 5. Segment 与 Partition 的关系

一个 Partition 目录下**只允许一个 active Segment**,其它都是 sealed。当 active Segment 滚动后:

1. 创建新空文件,baseOffset = 当前 LEO
2. 把 LEO 写入新文件(即使没有消息,文件也存在,长度为 0)
3. 所有后续写入走新文件
4. 旧 Segment 进入"待清理"队列

```text
滚动前后对比:

滚动前:
   00000000000000000.log  (active, 已写 800 MB)
   00000000000800000.log  (sealed)
   00000000001600000.log  (sealed)

滚动后:
   00000000000000000.log  (sealed)
   00000000000800000.log  (sealed)
   00000000001600000.log  (sealed, 写满 1 GB)
   00000000002400000.log  (active, 新建,0 字节)
```

### 6. 删除 Segment 的流程

```text
Retention 线程定时(默认 5 分钟一次)扫描:
   1. 收集所有 sealed Segment
   2. 计算每个 Segment 的最大时间戳 maxTimestamp
   3. if (now - maxTimestamp > retention.ms):
        把该 Segment 加入待删除集合
   4. 对所有"待删除"Segment,先检查:
        - 是否还有活跃 Consumer 没消费完
        - 是否被 MirrorMaker 等其他消费者引用
   5. 文件系统 unlink .log / .index / .timeindex
   6. 推进 Log Start Offset (LSO)
```

**整段删除而非逐条删除的好处**:不需要维护"消息级删除标记",不需要重建索引,操作是 O(1) 的 inode 释放。代价是**粒度粗**(可能多保留几分钟的数据)。

## 三、文件结构

### 1. .log —— 消息数据文件

`.log` 是真正的消息存储文件,一个 Record 都不能丢,顺序追加写。文件内部按 **Record Batch** 切分,每个 Batch 自描述(包含 magic、CRC、压缩算法、消息条数等元信息)。

### 2. .index —— 位移索引

`.index` 是**位移 (offset) → 物理位置 (position)** 的映射文件,采用**稀疏索引**——不是每条消息一条索引,而是按 `log.index.interval.bytes` (默认 4 KB) 间隔建一条索引。

索引项格式 (V2 版本):

```text
┌────────────┬────────────┐
│  offset    │  position  │    8 字节     4 字节
│ (int32)    │ (int32)    │
└────────────┴────────────┘
   相对 offset   物理字节偏移
   (相对 baseOffset)
```

- 索引项 `offset` 是**相对于 baseOffset 的 4 字节有符号整数**(而不是完整 64 位)
- 这就是为什么单个 Segment 内的 offset 差值被限制在约 21 亿条 (2^31) 内

### 3. .timeindex —— 时间戳索引

`.timeindex` 是 **timestamp → offset** 的映射,用于按时间戳定位消息(例如 `offsetsForTimes` 接口)。

```text
┌────────────┬────────────┐
│ timestamp  │   offset   │    8 字节     4 字节
│ (int64)    │  (int32)   │
└────────────┴────────────┘
```

- `timestamp` 是消息的 `CreateTime` 或 `LogAppendTime`(取决于 `log.message.timestamp.type` 配置)
- `offset` 是相对于 baseOffset 的偏移
- 同样按 `log.index.interval.bytes` 间隔写入

> `.timeindex` 不是必备文件:Kafka 在每次滚动 Segment 或写满索引时,会异步重建 `.timeindex`,即使文件丢失也不影响功能,只是按时间查找会退化为线性扫描。

### 4. .snapshot —— 检查点 (事务相关)

`__transaction_state` Topic 的分区目录下会有 `.snapshot` 文件,作用类似数据库的 **checkpoint**,用于:

- 记录事务协调者 (Transaction Coordinator) 已处理的事务状态
- 启动时**快速恢复**事务元数据,避免重放全部日志
- 仅事务特性开启 (`transaction.state.log.replication.factor` 配置存在)时才有意义

`.snapshot` 文件与 `.log` 配套,文件名同样以 baseOffset 命名,内容是二进制序列化的 `TransactionState` 对象集合。

### 5. .txnindex —— 事务索引

启用事务后,Producer 写入的消息会带上 **事务控制标记 (control batch)** 与事务 ID。`.txnindex` 用来:

- **快速定位** 哪些 offset 属于哪个事务
- **事务中止 (abort)** 时精确定位待标记 (tombstone) 的消息
- 与 `.snapshot` 配合完成事务的提交 / 中止流程

> 普通业务 Topic 的 Partition 目录下一般不会出现 `.txnindex`,**只有当该 Topic 被显式配置了事务相关的 Producer** 时才会有。

### 6. 配套文件

| 文件                              | 作用                                                              |
|----------------------------------|------------------------------------------------------------------|
| `leader-epoch-checkpoint`        | 记录本分区 Leader 历次切换的 epoch 与对应起始 offset              |
| `partition.metadata`             | 分区元数据快照,包含版本号(用于兼容性)                            |
| `replication-offset-checkpoint`  | (在父目录) 所有 Partition 已确认复制的最大 offset                 |
| `recovery-point-offset-checkpoint` | (在父目录) 所有 Partition 已刷盘的最大 offset                   |

`leader-epoch-checkpoint` 是 Kafka 0.11+ 用于**防止数据回滚 / 覆盖丢失**的关键机制,详见 [Kafka 集群与 ISR](#) 相关章节。

## 四、消息物理结构

### 1. 三层结构:Log → Record Batch → Record

Kafka 在磁盘上存储的最小"消息单位"是 **Record**,但**写入和读取的最小单位是 Record Batch**。

```text
Segment (.log)
└── RecordBatch      # 一个批次(由 Producer 一次发送 或 broker 拼接)
    ├── RecordBatch Header
    ├── Record 1
    ├── Record 2
    ├── Record 3
    └── ...
```

### 2. Record Batch 详解 (V2 格式)

V2 是 Kafka 0.11+ 默认的消息格式,主要目的是**支持事务、幂等、压缩、变长字段**。

```text
┌──────────────────────────────────────────────────────────────────┐
│                    RecordBatch (V2)                                │
├──────────────────────────────────────────────────────────────────┤
│  baseOffset             : int64     批次起始 offset                │
│  batchLength            : int32     批次总字节数(从下一字段开始) │
│  partitionLeaderEpoch   : int32     Leader Epoch                  │
│  magic                  : int8      格式版本 (V2 = 2)             │
│  crc                    : int32     CRC32C 校验 (后续字段)         │
│  attributes             : int16     压缩/时间戳类型/事务标记       │
│  lastOffsetDelta        : int32     最后一条消息相对 baseOffset   │
│  firstTimestamp         : int64     第一条消息时间戳              │
│  maxTimestamp           : int64     最大时间戳                    │
│  producerId             : int64     Producer ID (幂等)            │
│  producerEpoch          : int16     Producer Epoch                │
│  baseSequence           : int32     基础 sequence (幂等)          │
│  records.length         : int32     Records 数组字节数            │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  Record 1 (变长)                                         │    │
│  │  Record 2 (变长)                                         │    │
│  │  ...                                                     │    │
│  │  Record N (变长)                                         │    │
│  └──────────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────┘
```

#### 2.1 attributes 字段 (16 bit)

```text
bit 0 ~ 2 : 压缩算法 (0=none, 1=gzip, 2=snappy, 3=lz4, 4=zstd)
bit 3     : 时间戳类型 (0=CreateTime, 1=LogAppendTime)
bit 4     : 是否事务型 (Transactional)
bit 5     : 是否控制批 (Control Batch, 用于事务 commit/abort)
bit 6 ~ 15: 保留
```

#### 2.2 baseSequence / producerId / producerEpoch

这三个字段是**幂等 Producer** 与 **EOS (Exactly Once Semantics)** 的基石:

- `producerId`:Producer 首次启动时由 broker 分配,唯一标识
- `producerEpoch`:Producer 每次重启递增,用于**世代控制**
- `baseSequence`:本 Batch 内第一条消息的 sequence 号,broker 通过它**检测重复 / 乱序**

broker 端会缓存 `(producerId, producerEpoch) → (lastSequence, lastOffset)`,凡是 sequence 不连续的消息都会被丢弃。

### 3. Record 详解

```text
┌──────────────────────────────────────────────────────────────────┐
│                    Record (V2)                                    │
├──────────────────────────────────────────────────────────────────┤
│  length             : varint      后续字节数 (变长头)            │
│  attributes         : int8        已弃用,占位 0                  │
│  timestampDelta     : varint      相对 batch.firstTimestamp 的偏移│
│  offsetDelta        : varint      相对 batch.baseOffset 的偏移   │
│  keyLength          : varint      Key 字节数 (-1 表示 null)      │
│  key                : byte[]      Key 字节                       │
│  valueLength        : varint      Value 字节数 (-1 表示 null)    │
│  value              : byte[]      Value 字节                     │
│  Headers.length     : varint      Header 个数                    │
│  ┌────────────────────────────────────────────────────────┐      │
│  │  Header 1:                                             │      │
│  │    headerKeyLength  : varint                           │      │
│  │    headerKey        : byte[]                           │      │
│  │    headerValueLength: varint                           │      │
│  │    headerValue      : byte[]                           │      │
│  └────────────────────────────────────────────────────────┘      │
│  ... 更多 Header                                                   │
└──────────────────────────────────────────────────────────────────┘
```

V2 大量使用 **Varint (变长整数) 编码**,原因是大多数 timestampDelta / offsetDelta / keyLength 都是小整数,用 1~2 字节就能表示,大幅压缩 Record 头部。

#### Varint 编码示例

| 数值       | 二进制          | 占用字节       |
|-----------|---------------|---------------|
| 1         | `0000001`     | 1 B           |
| 127       | `1111111`     | 1 B (最大单字节)|
| 128       | `0000001 0000000` | 2 B        |
| 16383     | —             | 2 B (最大两字节)|
| 16384     | —             | 3 B           |

Kafka Varint 是**有符号 ZigZag 编码**,先做 `(n << 1) ^ (n >> 31)`,把负数也变成小整数,再变长编码。例如 -1 编码后是 1,只占 1 字节。

### 3.5 V0/V1/V2 格式逐字节对比

```text
V0 Record (Kafka 0.10 之前):
┌─────────────────────────────────────────────┐
│ offset (8B)                                 │
│ messageSize (4B)                            │
│ crc (4B)        ← 已经支持 CRC              │
│ magic (1B) = 0                              │
│ attributes (1B)                             │
│ timestamp (8B)    ← 0.10 之前不存在!        │
│ key (变长)                                  │
│ value (变长)                                │
└─────────────────────────────────────────────┘

V1 Record (Kafka 0.10):
┌─────────────────────────────────────────────┐
│ offset (8B)                                 │
│ messageSize (4B)                            │
│ crc (4B)                                    │
│ magic (1B) = 1                              │
│ attributes (1B)                             │
│ timestamp (8B)    ← 新增!                   │
│ key (变长)                                  │
│ value (变长)                                │
└─────────────────────────────────────────────┘

V2 Record (Kafka 0.11+,默认):
┌─────────────────────────────────────────────┐
│ length (varint)                             │
│ attributes (int8)        ← 占位用,总是 0    │
│ timestampDelta (varint)  ← 相对 batch       │
│ offsetDelta (varint)     ← 相对 batch       │
│ keyLength (varint)                            │
│ key (byte[])                                  │
│ valueLength (varint)                          │
│ value (byte[])                                │
│ Headers (数组, varint 编码)                  │
└─────────────────────────────────────────────┘
```

V2 与 V0/V1 的**根本差异**是:
- V2 把"多条消息打包"作为基本单位(RecordBatch)
- V2 全面 varint 化,空间开销大幅下降
- V2 引入幂等 / 事务字段

### 3.6 一个真实 Record 的二进制布局示例

假设发送 3 条消息到一个空 Partition:

```text
RecordBatch (baseOffset = 0):
┌─────────────────────────────────────────────────────────┐
│ 00 00 00 00 00 00 00 00   baseOffset = 0                 │
│ 00 00 01 14              batchLength = 276 字节          │
│ 00 00 00 00              partitionLeaderEpoch = 0        │
│ 02                       magic = V2                     │
│ 4F 31 AC 1C              CRC32C = 0x4F31AC1C             │
│ 00 10                    attributes = 0001 0000 (无压缩) │
│ 00 00 00 02              lastOffsetDelta = 2            │

│ 00 00 01 6B D5 78 78 42  maxTimestamp  = 1700000000002  │
│ FF FF FF FF FF FF FF FF  producerId = -1 (非幂等)       │
│ FF FF                    producerEpoch = -1             │
│ FF FF FF FF              baseSequence = -1             │
│ 00 00 00 E8              records.length = 232           │
│ ──────────── Record 1 (offset 0) ──────────              │
│ 1F                       length = 31                    │
│ 00                       attributes = 0                 │
│ 00                       timestampDelta = 0             │
│ 00                       offsetDelta = 0                │

```

### 4. CRC 校验

每个 RecordBatch 都有一个 **CRC32C** 校验值,覆盖从 `attributes` 字段到最后一个 Record 的所有字节:

```text
┌──────────────────────────────┐
│ baseOffset (8B)              │
│ batchLength (4B)             │
│ partitionLeaderEpoch (4B)    │
│ magic (1B)                   │
│ crc (4B)  ◄─── 计算起点       │
│ attributes (2B)              │
│ lastOffsetDelta (4B)         │
│ firstTimestamp (8B)          │
│ maxTimestamp (8B)            │
│ producerId (8B)              │
│ producerEpoch (2B)           │
│ baseSequence (4B)            │
│ records.length (4B)          │
│ ...Record...                 │
└──────────────────────────────┘
```

**为什么从 attributes 开始?**
因为前 4 个字段(baseOffset / batchLength / partitionLeaderEpoch / magic)在校验时需要先于 crc 读取,以确定批次边界。

**CRC 不一致时的处理:**
- 抛出 `CorruptRecordException`
- Consumer / ReplicaFetcher 会跳过该 Batch,直接从下一个 Batch 开始
- 生产环境通常意味着磁盘损坏或网络异常,需立即排查

### 5. 压缩

Kafka 的压缩是**整 Batch 压缩**,即把整个 `records` 数组用一种算法压缩后,作为一个整体存入 `value` 区(注意 V2 格式下是压缩在 records 区域,而不是按 Record 压缩)。

```text
  RecordBatch (V2)
    ├── Batch Header (不压缩)
    └── Records 区域 (压缩)
         ├── 压缩算法: gzip / snappy / lz4 / zstd
         └── 压缩粒度: 一个 Batch 一整块
```

**优点**:
- 跨消息的重复字段(如 timestampDelta、offsetDelta、key)压缩率极高
- broker 端**不解压直接转发**给 Consumer,解压责任交给 Consumer

**缺点**:
- 单条消息**无法随机读取**,必须解压整个 Batch 才能拿到中间某条
- 因此压缩率与 Batch 大小强相关——Batch 越大,压缩越好,延迟也越高

### 6. 消息格式版本演进

| 版本  | magic | 引入版本     | 关键变化                                                            |
|-------|-------|-------------|-------------------------------------------------------------------|
| V0    | 0     | 0.10.0 之前  | 最原始格式,无 CRC,字段定长                                       |
| V1    | 1     | 0.10.0 起    | 增加 timestamp(8B)、CRC32C 校验                                   |
| V2    | 2     | 0.11.0 起    | Varint 编码、RecordBatch 抽象、事务支持、幂等支持                  |

> Kafka 不允许**不同版本的 Segment 混合存储**——一旦 broker 升级到 V2,新写入的消息必须按 V2 编码,但**老的 V0/V1 Segment 仍然可读**(惰性升级)。

## 五、索引机制

### 1. 为什么需要索引

Kafka 的 `.log` 文件是**顺序追加**的,纯追加结构本不需要索引。但 Kafka 必须支持两类查询:

1. **按 offset 定位消息**:Consumer 从指定 offset 开始拉取
2. **按时间戳定位消息**:运维场景,如"7 天前的某个时刻的 offset"

如果每次都线性扫描整个 `.log`,延迟不可接受。Kafka 的解法是**稀疏索引 + 二分查找**。

### 2. 稀疏索引原理

`.index` 不是为每条消息都建立索引,而是**每隔 `log.index.interval.bytes` (默认 4096) 字节**建立一条索引。

```text
.log 文件 (假设每条消息 1 KB,index.interval.bytes = 4096)
─────────────────────────────────────────────────────────
offset 0   ┐
offset 1   │ 0 ~ 4095 字节 (约 4 条消息),稀疏索引区
offset 2   │
offset 3   │
offset 4   │ 4096 ~ 8191 字节 (约 4 条消息),稀疏索引区
offset 5   │
offset 6   │
offset 7   │
offset 8   │ ...
           │

.index 文件内容 (4 条索引)
┌───────────────────┬───────────────────┐
│ offset (relative) │ position (绝对)   │
├───────────────────┼───────────────────┤
│        0          │        0          │  ← 第 1 条索引 (offset 0, position 0)
│        4          │     4096          │  ← 第 2 条索引 (offset 4, position 4096)
│        8          │     8192          │  ← 第 3 条索引
│       12          │    12288          │  ← 第 4 条索引
└───────────────────┴───────────────────┘
```

**好处**:
- 索引文件本身极小(1 GB 的 Segment 最多产生约 1 GB / 4 KB ≈ 25 万条索引 ≈ 3 MB)
- 整个 `.index` 可以**全部加载到内存**,查询 O(log N) 二分

**代价**:
- 定位精度有限:只能定位到某个"区间"的起点,**区间内还要顺序扫描**
- 默认 4096 字节 ≈ 1~4 条消息,顺序扫描代价极低,可忽略

### 3. 按 offset 查找流程

```text
Consumer 请求: 读取 offset = 5000 的消息
        │
        ▼
  1. 用二分查找定位 offset 5000 所在的 Segment
     (Segment 文件名 < 5000 ≤ 下一个 Segment 文件名)
        │
        ▼
  2. 加载该 Segment 的 .index 文件到内存
     (单 Segment 索引 ≈ MB 级,常驻内存)
        │
        ▼
  3. 在 .index 中二分查找:找到 ≤ 5000 的最大索引项
     例如找到 [offset=4996, position=20480]
        │
        ▼
  4. 从 position=20480 开始,顺序扫描 .log
     找到 offset=5000 对应的 Record
        │
        ▼
  5. 返回该 Record 所在的 RecordBatch
```

**复杂度**:
- Segment 选择:O(log Segments),Segments 一般 < 1000,可忽略
- `.index` 二分:O(log IndexEntries),单 Segment 索引 ≈ 25 万条,二分只需 ~18 次
- 顺序扫描:4096 字节内最多 1~4 条消息,**常数级**

### 4. 按时间戳查找

Kafka 提供 `Consumer.offsetsForTimes(Map<TopicPartition, Long> timestampsToSearch)` 接口:

```java
Map<TopicPartition, OffsetAndTimestamp> offsets = 
    consumer.offsetsForTimes(timestamps);
```

流程几乎相同,但查的是 `.timeindex` 而非 `.index`:

```text
请求: 查找 timestamp = T 的 offset
   │
   ▼
1. 二分查找 .timeindex,找到 ≤ T 的最大索引项
   例: [timestamp=T-10ms, offset=4996]
   │
   ▼
2. 拿到 offset=4996,再走"按 offset 查找"流程
   最终得到该时间戳对应的 offset
```

### 5. 索引机制的局限性

| 操作                    | 索引是否覆盖    | 实际代价                          |
|-----------------------|---------------|---------------------------------|
| 按精确 offset 查找      | ✓ 是          | O(log N) + 4 KB 顺序扫            |
| 按时间戳范围查找        | ✓ 是          | O(log N) + 顺序扫                 |
| 按 Value / Key 内容查找  | ✗ 否          | **全 Segment 扫描**              |
| 按 Header 查找          | ✗ 否          | **全 Segment 扫描**              |
| 模糊 / 全文检索          | ✗ 否          | **必须外部系统 (ES)**            |

**重要结论**:Kafka **不是数据库**,不适合做"按字段查消息"。要做此类查询,必须:
1. 配合 Elasticsearch / ClickHouse / Druid 等构建二级索引
2. 或使用 Kafka Connect + JDBC Sink 写入 OLTP / OLAP 数据库

### 6. 索引的 mmap 加载细节

```java
// Kafka 启动时(简化)
for (File indexFile : listIndexFiles()) {
    FileChannel ch = FileChannel.open(indexFile, READ, WRITE);
    MappedByteBuffer buf = ch.map(
        MapMode.READ_WRITE, 0, ch.size()
    );
    offsetIndex = new OffsetIndex(buf, ...);
}
```

mmap 后:
- 读 `.index` 不需要 read() 系统调用,直接指针访问
- 修改 `.index` 会触发 OS 自动 write-back(但 Kafka 实际很少修改索引)
- 整个 Segment 的索引常驻 Page Cache,**重启不重建**

### 7. 索引大小估算公式

```
单 Segment 索引条目数 = log.segment.bytes / log.index.interval.bytes
                    = 1 GB / 4 KB
                    ≈ 262144 条

单 Segment 索引大小 = 262144 × 8 字节 (int32 + int32)
                   ≈ 2 MB

100 个 Segment 总索引 ≈ 200 MB  (全部常驻内存完全可接受)
```

### 5. 索引示意图

```text
   .index 文件                          .log 文件
   ┌────────────┬────────────┐          ┌─────────────────────────┐
   │   offset   │  position  │          │  RecordBatch(包含记录 0~3)│  ← pos 0
   ├────────────┼────────────┤          ├─────────────────────────┤
   │     0      │     0      │─────────→│  RecordBatch(包含记录 4~7)│  ← pos 4096
   ├────────────┼────────────┤          ├─────────────────────────┤
   │     8      │   8192     │─────────→│  RecordBatch(包含记录 8~11)│  ← pos 8192
   ├────────────┼────────────┤          ├─────────────────────────┤
   │    16      │  16384     │─────────→│  RecordBatch(包含记录 12~15)│ ← pos 12288
   └────────────┴────────────┘          └─────────────────────────┘
                                               │
                                               ▼
                                       顺序扫描至目标 offset
```

## 六、磁盘读写机制

### 1. 顺序写盘 (Sequential Write)

#### 1.1 为什么顺序写比随机写快?

机械盘 (HDD) 的 I/O 延迟由三部分组成:

| 操作                      | 典型耗时        |
|--------------------------|----------------|
| **磁头寻道 (seek)**       | 5 ~ 10 ms      |
| **盘片旋转 (rotation)**   | 0 ~ 4 ms (7200 RPM) |
| **数据传输 (transfer)**    | 几十 MB/s      |

随机读写的瓶颈在于 **seek + rotation**,每次寻道后只能读 / 写一个很小的块(4 KB)。顺序读写则完全跳过 seek,**HDD 顺序写也能跑到 100 MB/s 以上**。

SSD 虽然没有机械寻道,但内部依然有 **GC / Wear Leveling / Block Erase** 等开销,**顺序写仍优于随机写数倍**。

#### 1.2 Kafka 顺序写的实现

```text
Producer 线程
   │
   ▼
batch.size 攒批 (默认 16 KB)
   │
   ▼
linger.ms 等待 (默认 0,即不等待,但允许累积)
   │
   ▼
sender 线程拉取 RecordBatch,发到对应 Partition Leader
   │
   ▼
Broker 写入 Page Cache
   │
   ▼
后台 flush 线程按 log.flush.interval.ms / log.flush.interval.messages
   │  周期性 fsync 到磁盘
   ▼
磁盘上的 .log 文件 (只追加)
```

**Producer 端 `acks=all` + 副本同步** 保证数据不丢,但**单条消息的写盘路径只有"追加到 active Segment 的末尾"一条**,磁盘几乎零寻道。

### 2. 零拷贝 (Zero Copy)

#### 2.1 传统四次拷贝

Consumer 拉取消息时,**如果走传统 I/O 路径**,数据要在以下缓冲区之间拷贝 4 次:

```text
┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
│  .log    │ ──①──│ Page     │ ──②──│ Kernel   │ ──③──│ User     │ ──④──→ Socket
│ (磁盘)   │ read │ Cache    │ copy │ Socket   │ copy │ Buffer   │ send│ (网卡)
└──────────┘      └──────────┘      └──────────┘      └──────────┘
                  (内核态)            (内核态)          (用户态)
```

1. **DMA 拷贝**:磁盘 → Page Cache (内核)
2. **CPU 拷贝**:Page Cache → 内核 Socket Buffer
3. **CPU 拷贝**:内核 Socket Buffer → 用户态缓冲区 (JVM Heap)
4. **DMA 拷贝**:Socket Buffer → 网卡

数据在**内核 ↔ 用户态**之间来回搬动,既消耗 CPU 又消耗内存带宽。

#### 2.2 sendfile() 零拷贝

Kafka 使用 `sendfile()` (Linux 系统调用),让数据**直接从 Page Cache 送到网卡**,完全跳过用户态:

```text
┌──────────┐      ┌──────────┐      ┌──────────┐
│  .log    │ ──①──│ Page     │ ──②──│   NIC    │
│ (磁盘)   │ DMA  │ Cache    │ DMA  │ (网卡)   │
└──────────┘      └──────────┘      └──────────┘
                  (内核态)            (内核态)
```

- 仅 2 次拷贝,且都在内核 / DMA 之间
- 用户态代码只是**记录描述符**,完全不接触数据
- CPU 占用显著降低,**网络吞吐可提升 2~3 倍**

#### 2.3 mmap + 零拷贝

Kafka 在**索引文件 (`.index` / `.timeindex`) 的加载**上使用 `mmap()`:

```text
.java.nio.MappedByteBuffer
        │
        ▼
   mmap 系统调用
        │
        ▼
  Page Cache 区域 ─── 应用程序可直接访问
        │
        ▼
   (修改 mmap 区域会触发 OS 自动写回磁盘)
```

mmap 的好处:

- 索引文件**不需要 read()/write() 系统调用**,通过指针直接读写
- **修改自动同步**到磁盘(通过 msync 或 OS 策略)
- 适合"读多写少 + 随机访问"的场景(比如索引)

#### 2.4 sendfile vs mmap 对比

| 维度       | sendfile (数据)                | mmap (索引)                       |
|-----------|-------------------------------|----------------------------------|
| 适用对象   | `.log` (消息数据)              | `.index` / `.timeindex` (索引)   |
| 流向       | 内核 → 网卡                    | 磁盘 ↔ 内核(双向)                |
| 用户态访问 | 否,完全内核                   | 是,Java 指针直接读写              |
| 写盘责任   | 内核自动                       | 应用程序需主动 msync              |
| 典型场景   | Consumer 拉取、Follower 同步   | Consumer 按 offset 精确查找       |

### 3. 页缓存 (Page Cache)

Kafka **几乎不维护 JVM 堆内缓存**,完全依赖 OS 的 Page Cache。

#### 3.1 Page Cache 是什么

Linux 把空闲内存用作磁盘的**统一缓存层**:

```text
┌───────────────────────────────────────────────┐
│              Linux Memory                       │
│  ┌───────────────────────────────────────────┐ │
│  │        Page Cache (大部分)               │ │
│  │   ┌─────────┐  ┌─────────┐  ┌─────────┐  │ │
│  │   │.log 缓存│  │.index缓存│  │ 其他文件 │  │ │
│  │   └─────────┘  └─────────┘  └─────────┘  │ │
│  └───────────────────────────────────────────┘ │
│  ┌───────────────────────────────────────────┐ │
│  │        Kernel Heap                       │ │
│  └───────────────────────────────────────────┘ │
│  ┌───────────────────────────────────────────┐ │
│  │        User Process Memory (JVM 堆等)    │ │
│  └───────────────────────────────────────────┘ │
└───────────────────────────────────────────────┘
```

#### 3.2 Page Cache 的好处

| 好处        | 说明                                                                |
|-----------|--------------------------------------------------------------------|
| **冷启动即热** | OS 已为 `.log` 建立缓存,**Kafka 重启无需"预热缓存"**               |
| **避免 GC**  | 数据在堆外,**JVM 不用管理这块内存**,GC 暂停几乎为零                 |
| **自动淘汰** | OS 按 LRU 回收冷数据,不需要 Kafka 自己实现                          |
| **顺序预读** | OS 会预读相邻 Page,**Consumer 顺序拉取有加速效果**                  |
| **写回合并** | 多个写入会被合并到 Page,**减少 fsync 次数**                        |

#### 3.3 生产建议

- `log.flush.interval.messages` / `log.flush.interval.ms` **不要设置过小**,让 OS 自由调度刷盘
- 给 Broker **预留 50% 以上物理内存**给 Page Cache(其余给 JVM + 系统)
- 如果发现 Page Cache 命中率低,考虑**减少活跃 Segment 数**(滚动阈值调小)

### 4. 顺序读 + 异步刷盘

#### 4.1 Consumer 顺序读

Consumer 几乎总是从 LEO 开始**顺序向后读**,OS 会做**预读 (read-ahead)**,把磁盘 I/O 摊薄到几乎为零。

#### 4.2 异步刷盘

Producer 写入 broker 的路径:

```text
Producer Record
   │
   ▼
Socket → broker 网络层
   │
   ▼
写入 Page Cache ──── (内存,极快)
   │
   ▼
返回 ack 给 Producer
   │
   ▼
[异步]  flush 线程定时 fsync
       (log.flush.interval.ms / messages)
```

**默认配置下,broker 在 Page Cache 写入成功后就 ack**,即使机器断电,只要 Page Cache 中已确认,理论上就认为"成功"。**真正的磁盘持久化由 OS 后台异步完成**。

如果要更严格的持久化保证,可以设置:

```properties
# 每写入 10000 条强制刷盘
log.flush.interval.messages=10000
# 或每 1000 ms 强制刷盘
log.flush.interval.ms=1000
```

但这会**显著降低吞吐**,生产中通常不开启,而是依赖**多副本 + acks=all** 来保证可靠性。

#### 4.3 fsync 的代价实测参考

| 写入模式                          | 单 Partition TPS   | 延迟 P99         |
|----------------------------------|-------------------|------------------|
| 不 fsync (默认, 仅 Page Cache)    | 80,000 ~ 120,000  | 5 ~ 10 ms       |
| 每 1 万条 fsync 一次               | 60,000 ~ 90,000   | 10 ~ 20 ms      |
| 每条 fsync                         | 1,000 ~ 3,000     | 100 ~ 500 ms    |

**单条 fsync 性能下降 100 倍**,这就是为什么 Kafka 默认交给 OS 处理。

### 5. 文件系统选择

Kafka 强烈推荐使用 **ext4** 或 **xfs**:

| 文件系统     | 推荐度     | 关键差异                                          |
|------------|----------|--------------------------------------------------|
| **ext4**   | ✓ 推荐   | 稳定、广泛使用,kafka 早期版本默认                |
| **xfs**    | ✓✓ 更推荐 | 大文件写入更优,删除性能更好(Kafka 2.0+ 官方推荐)|
| btrfs     | ✗ 避免    | CoW 特性与 Kafka 的"覆盖写"模型冲突             |
| ZFS       | ✗ 避免    | ARC 缓存与 Page Cache 双层缓存,浪费内存         |
| NFS       | ✗ 严禁    | 网络文件系统,延迟与一致性不可控                  |

**关键 mount 选项**(生产推荐):

```bash
# ext4
mount -o noatime,data=writeback,barrier=0 /dev/sdb /var/lib/kafka/data

# xfs
mount -o noatime,allocsize=64m /dev/sdb /var/lib/kafka/data
```

- `noatime`:不更新文件访问时间,减少写入
- `data=writeback`:ext4 模式,可能丢失最近几秒数据但更快
- `allocsize=64m`:xfs 预分配 64 MB,顺序写性能更佳

### 6. 磁盘类型建议

```text
机械盘 (HDD):
   - 顺序写 100 ~ 200 MB/s
   - 单盘成本低,适合冷数据 / 大容量场景
   - 缺点:故障率高,IOPS 低

SATA SSD:
   - 顺序写 400 ~ 800 MB/s
   - 中等成本,通用首选
   - 缺点:寿命有限,需要监控 DWPD

NVMe SSD:
   - 顺序写 1 ~ 3 GB/s
   - 高吞吐场景首选 (Kafka Connect / 实时数仓)
   - 缺点:成本高,通常需要 RAID

RAID 配置:
   - 生产环境必须 RAID10,不能 RAID5/6
   - RAID5 的写惩罚会显著降低 Kafka 吞吐
```

## 七、日志清理 (Log Retention)

### 1. 清理的两条路径

Kafka 提供两种日志清理策略,通过 `log.cleanup.policy` 设置:

| 策略                  | 取值              | 行为                                                                  |
|----------------------|------------------|----------------------------------------------------------------------|
| **delete** (默认)    | "delete"         | 按时间 / 大小 / 起始 offset 过期删除整段 Segment                       |
| **compact**          | "compact"        | 保留每个 Key 的最新版本,**合并相同 Key 的旧版本**(类似 LSM-Tree 合并) |

**两种策略可组合**:`log.cleanup.policy=compact,delete` 同时启用——先 compact,再按 delete 规则删陈旧 Segment。

### 2. 基于时间的保留 (Retention by Time)

| 配置项                              | 默认值           | 含义                                              |
|------------------------------------|-----------------|--------------------------------------------------|
| `log.retention.hours`              | 168 (7 天)      | 保留最近 N 小时,超出时间的 Segment 被删除         |
| `log.retention.minutes`            | -1              | 优先级高于 hours                                   |
| `log.retention.ms`                 | -1              | 最高优先级,毫秒精度                               |

**判断逻辑**:

```
Segment.maxTimestamp + retention.ms < now()  ⇒  删除该 Segment
```

Kafka 周期性扫描所有 Segment,**整段删除**(不会精确到 message 级),简化了清理流程。

### 3. 基于大小的保留 (Retention by Size)

| 配置项                              | 默认值     | 含义                                              |
|------------------------------------|-----------|--------------------------------------------------|
| `log.retention.bytes`              | -1 (无限) | Partition 总大小上限,超出部分从最旧 Segment 删除  |
| `log.segment.bytes`                | 1 GB      | 单 Segment 大小,影响"按大小清理"的粒度             |

**判断逻辑**:

```
Partition 当前总字节数 > log.retention.bytes
   → 删除最旧的 Segment(整段),直到 ≤ 阈值
```

### 4. 基于起始 offset 的保留

Kafka 0.10.2+ 引入了 `log.retention.minutes` 的另一种语义——**保留直到 offset ≥ LSO (Log Start Offset)**。

```text
删除规则:
   若 Segment 的最后一条消息 offset < LSO
   且 Segment 被所有活跃 Consumer 消费过
   ⇒  可删除
```

LSO 实际上是"已不再需要的最小 offset":

```
LSO = min(
    Consumer 当前消费位移,
    事务型 Topic 的 lastStableOffset,
    Compact 后的清理点
)
```

### 5. compact 策略详解

#### 5.1 核心思想

Compact 不是按时间清理,而是**只保留每个 Key 的最新版本**:

```text
原始日志 (按 offset 顺序):
┌────────┬────────┬────────┬────────┬────────┬────────┐
│ K=A    │ K=B    │ K=C    │ K=A    │ K=B    │ K=A    │
│ offset │ offset │ offset │ offset │ offset │ offset │
│   1    │   2    │   3    │   4    │   5    │   6    │
└────────┴────────┴────────┴────────┴────────┴────────┘
                       ↓ Compact 后
┌────────┬────────┬────────┐
│ K=C    │ K=B    │ K=A    │
│ offset │ offset │ offset │
│   3    │   5    │   6    │
└────────┴────────┴────────┘
   (保留最新值)
```

**适用场景**:
- **状态存储**:用户配置、运行时参数(最新配置覆盖历史)
- **变更日志 (CDC)**:只关心最新状态
- **物化视图缓存**:实时聚合表的最新值

#### 5.2 Compact 的实现:Log Cleaner

Log Cleaner 是 Kafka 内部的后台线程(默认 1 个,可配),工作流程类似 LSM-Tree 的合并:

```text
┌────────────┐    ┌────────────┐    ┌────────────┐
│  dirty     │ →  │   clean    │ →  │   clean    │
│  Segment   │    │  Segment   │    │  Segment   │
│ (待压缩)   │    │ (压缩中)   │    │ (已完成)   │
└────────────┘    └────────────┘    └────────────┘

1. 选择 dirty ratio 最高的 log
2. 拷贝所有 Key 的最新版本到新 Segment
3. 旧 dirty Segment 被删除
4. 维护 "cleaner offset"(压缩进度)
```

#### 5.3 tombstone (墓碑)

Compact 还会处理 **tombstone 消息**——Value 为 null 的消息,表示"删除这个 Key":

```text
原始:
offset 1: K=A → "value1"
offset 2: K=A → null    ← tombstone
offset 3: K=A → "value2"

Compact 后 (考虑 tombstones):
   ┌───────────────────────┐
   │ K=A → null  (墓碑保留)│   ← 删除标记本身保留一段时间
   │ K=A → "value2"        │   ← 真正的新值
   └───────────────────────┘

Compact 后 (经过墓碑保留期后):
   ┌───────────────────┐
   │ K=A → "value2"    │   ← 墓碑被清理
   └───────────────────┘
```

`tombstone` 保留期由 `log.cleaner.delete.retention.ms` 控制,默认 24 小时,目的是确保 Consumer 有时间看到删除事件。

#### 5.4 关键配置

| 配置项                              | 默认值           | 含义                                            |
|------------------------------------|-----------------|------------------------------------------------|
| `log.cleanup.policy`               | delete          | 设为 compact 启用                              |
| `log.cleaner.min.cleanable.ratio`  | 0.5             | dirty / total 比例,达到该值触发 compact        |
| `log.cleaner.threads`              | 1               | compact 后台线程数                              |
| `log.cleaner.io.max.bytes.per.second` | 无限制       | compact 限速,防止抢占磁盘                       |
| `log.cleaner.delete.retention.ms`  | 86400000 (24h)  | tombstone 保留时间                              |
| `log.segment.ms`                   | 7 天            | compact 的 Segment 大小上限,影响 compact 粒度  |
| `log.segment.bytes`                | 1 GB            | compact 的 Segment 字节上限                     |

### 6. delete vs compact 对比

| 维度         | delete                                       | compact                                      |
|-------------|----------------------------------------------|----------------------------------------------|
| **目标**    | 控制磁盘占用,过期数据不再保留                  | 保留全部 Key 的最新状态                      |
| **粒度**    | 整段 Segment 删除                             | 按 Key 合并,可能删 message                  |
| **恢复**    | 不可恢复(数据已被删)                          | 不可恢复(旧版本被覆盖)                      |
| **空间**    | 取决于 retention 时间窗口                      | 取决于 Key 基数(可能无限增长)               |
| **CPU**     | 极低,只扫描时间戳                            | 较高,需重建 + 排序 + 压缩                   |
| **典型场景**| 日志、事件流、监控数据                        | 状态、配置、CDC、KTable 物化视图            |
| **磁盘 I/O**| 周期性删除                                    | 周期性合并                                   |

```text
┌───────────────────────────────────────────────────────────────┐
│                  Kafka 日志清理全景                              │
│                                                               │
│   ┌─────────────┐     启用     ┌─────────────┐                │
│   │   Producer  │ ──────────→ │  Partition  │                │
│   │   写入      │             │   Log       │                │
│   └─────────────┘             └──────┬──────┘                │
│                                       │                       │
│                                       ▼                       │
│                          ┌────────────────────────┐           │
│                          │  清理策略判定            │          │
│                          └──────────┬─────────────┘           │
│                                     │                         │
│                  ┌──────────────────┴────────────────┐       │
│                  │ log.cleanup.policy                │       │
│                  └──────────┬─────────────┬─────────┘       │
│                             │             │                 │
│                  ┌──────────▼──┐    ┌─────▼────────┐        │
│                  │   delete   │    │   compact    │        │
│                  └──────────┬──┘    └─────┬────────┘        │
│                             │             │                 │
│                  时间/大小/起始offset    按Key合并          │
│                  整段删除Segment       保留最新版本          │
│                             │             │                 │
│                             └──────┬──────┘                 │
│                                    ▼                         │
│                            磁盘空间释放                      │
└───────────────────────────────────────────────────────────────┘
```

## 八、消息删除策略总结

| 场景                       | 推荐策略              | 原因                                                              |
|---------------------------|---------------------|------------------------------------------------------------------|
| **业务日志、事件流**        | delete               | 只关心近期数据,过期即可丢弃                                       |
| **监控数据、Metric 流**     | delete + 短保留      | 数据价值衰减快,按小时级保留即可                                  |
| **用户状态、配置中心**      | compact              | 关心最新值,历史状态可覆盖                                        |
| **CDC 数据、变更日志**      | compact              | 表的最新状态可重放,历史变更可压缩                                |
| **聚合统计、物化视图**      | compact              | KTable 模式天然适合 compact                                       |
| **Kafka 内部 `__consumer_offsets`** | compact      | 只需保留每个 group 的最新位移即可                                |
| **Kafka 内部 `__transaction_state`** | compact     | 事务状态有生命周期,压缩可节省大量空间                            |
| **合规留存 (法规要求)**      | delete + 长保留      | 必须保留 N 天,compact 不适用(不能覆盖)                          |

**实战配置示例**:

```properties
# 业务日志 Topic: 7 天保留
log.retention.hours=168
log.cleanup.policy=delete
log.segment.bytes=1073741824

# 配置中心 Topic: 永久保留最新值
log.cleanup.policy=compact
log.cleaner.min.cleanable.ratio=0.5
log.segment.ms=3600000

# 监控数据 Topic: 6 小时保留
log.retention.hours=6
log.cleanup.policy=delete
log.segment.bytes=268435456
```

### 9. 混合策略:compact + delete

`log.cleanup.policy=compact,delete` 同时启用时:

```text
1. LogCleaner 负责 compact (合并相同 Key)
2. LogRetener 在 compact 之后,继续按 retention 删除整段 Segment
3. 两个操作作用于不同维度,可以共存
```

适用场景:**变更日志 (CDC)**——既需要保留每个 Key 的最新值,又需要按时间窗口清理极老的数据。

### 10. 清理对 Lag 计算的影响

Consumer Lag 的"基准线"是 **LSO (Log Start Offset)**,不是 0:

```text
Lag = (最新 offset) - (Consumer 提交 offset)
但当 Consumer 提交 offset < LSO 时,数据已被删除,该 offset 不可达
此时 Consumer 必须:
   - 重置到 LSO (auto.offset.reset=earliest)
   - 或直接跳过 (auto.offset.reset=latest)
```

**生产建议**:
- 监控 Lag 时,**关注 Consumer offset 是否已经接近 LSO**
- 如果太接近,说明 Retention 时间太短,需要延长
- LSO 在 `kafka-log-dirs.sh` 输出中可以看到

**实战配置示例**:

```properties
# 业务日志 Topic: 7 天保留
log.retention.hours=168
log.cleanup.policy=delete
log.segment.bytes=1073741824

# 配置中心 Topic: 永久保留最新值
log.cleanup.policy=compact
log.cleaner.min.cleanable.ratio=0.5
log.segment.ms=3600000

# 监控数据 Topic: 6 小时保留
log.retention.hours=6
log.cleanup.policy=delete
log.segment.bytes=268435456
```

## 九、文件恢复

### 1. Broker 启动时做什么

Broker 重启时会扫描 `log.dirs`,对每个 Partition 目录执行以下步骤:

```text
1. 读取 partition.metadata,确定该分区版本
   │
2. 加载 leader-epoch-checkpoint
   │  记录历次 Leader 切换的 epoch → offset 映射
   │  用于防止数据回滚
   │
3. 扫描所有 .log Segment 文件
   │  按 baseOffset 排序,确定 [earliest, latest]
   │
4. 加载所有 .index / .timeindex 文件到内存 (mmap)
   │
5. 重建 HighWatermark、LogStartOffset
   │  - HW 来自 ZK / KRaft 的副本状态
   │  - LSO 取本地实际最早未删除 offset
   │
6. 检查 CRC,丢弃损坏的 Batch
   │
7. 启动 LogCleaner / LogRetener 线程
```

### 2. 索引重建

**正常情况**:`.index` / `.timeindex` 是 mmap 加载,**不需重建**。

**异常情况**:索引文件丢失或损坏时,Kafka 提供两种恢复路径:

| 损坏对象       | 严重程度 | 恢复方式                                                            |
|--------------|---------|-------------------------------------------------------------------|
| `.index`     | 中      | 启动时扫描整个 `.log`,**重新构建索引**(按 `log.index.interval.bytes` 间隔) |
| `.timeindex` | 低      | 同上,但仅按需重建;`.timeindex` 丢失不影响正常读写                 |
| `.log`       | 严重    | **无法恢复**,只能从 Leader 重新拉取副本                          |

### 3. CRC 校验

#### 3.1 何时校验

- **启动加载**:扫描所有 Batch,验证 CRC,丢弃不通过的
- **Consumer 读取**:每条消息读取后立即校验
- **Follower 同步**:从 Leader Fetch 时会重新计算 CRC,与 Leader 端对比

#### 3.2 CRC 失败的常见原因

| 原因               | 说明                                              |
|------------------|--------------------------------------------------|
| 磁盘扇区损坏       | 多见于老旧 HDD / 不正当关机                       |
| 内存 bit-flip     | 极少见,但 ECC 内存也不是 100% 可靠               |
| 文件系统 bug      | 极端情况下 ext4 / xfs 写入不一致                  |
| Kafka Bug        | 历史上 KAFKA-5506 等曾导致 CRC 误判              |

#### 3.3 损坏后的处理

```text
1. 记录日志,标记损坏 offset
2. 尝试从 ISR 副本恢复
3. 若 ISR 全坏,从离线备份 / MirrorMaker 恢复
4. 仍无法恢复 → 该 Batch 不可用,业务需降级
```

### 4. Leader Epoch 防回滚

Kafka 0.11+ 引入 `leader-epoch-checkpoint`,在以下场景防止数据**被旧 Leader 覆盖**:

```text
场景:
  Leader A (HW=100)  ── 写入 offset 101
       │
       │  Leader A 短暂宕机,offset 101 未复制给任何 Follower
       │
       ▼
  Leader B 上位 (HW=100)
       │
       │  Leader A 恢复,变成 Follower
       │
       ▼
  Leader A 试图"补回" offset 101
       │
       ▼
  Leader B 通过 epoch-checkpoint 发现:
    "epoch 5 的 HW = 100,不允许接受 epoch 4 写入的 offset 101"
       │
       ▼
  拒绝写入,Leader A 截断日志到 HW=100
```

## 十、与传统文件系统 / 数据库的对比

### 1. Kafka 顺序 IO vs 数据库随机 IO

| 维度                | 关系型数据库 (MySQL InnoDB)              | Kafka                                    |
|--------------------|-------------------------------------------|------------------------------------------|
| **数据模型**        | 关系表,B+Tree 索引                         | 日志,顺序追加                            |
| **写入方式**        | INSERT/UPDATE/DELETE,**随机修改页面**     | append,**只能追加**                     |
| **典型 I/O**        | 随机读写 + WAL                              | 顺序读写                                  |
| **查找方式**        | B+Tree 索引(主键 / 二级索引)              | 稀疏索引 + 二分 + 顺序扫描                |
| **数据可变性**      | 可任意修改                                | 一旦写入不可变(只能追加或过期删除)        |
| **事务粒度**        | 行级 + MVCC                                | Producer → Broker 幂等 + 事务             |
| **典型吞吐**        | 千 ~ 万 TPS                                | 十万 ~ 百万 TPS                           |
| **典型延迟**        | 毫秒 ~ 十毫秒                              | 毫秒 ~ 十毫秒(批量后)                   |

### 2. 内存使用模型对比

| 数据库          | 主要内存用途                          | Kafka                                  |
|----------------|------------------------------------|---------------------------------------|
| **MySQL InnoDB** | Buffer Pool (数据页 + 索引页缓存)    | 几乎不用 JVM 堆,**主要靠 OS Page Cache** |
| **Oracle**     | Buffer Cache + Library Cache       | 同上                                    |
| **Redis**      | 数据集全内存                          | 不适用                                  |
| **Kafka**      | Page Cache (OS 级) + 索引文件 mmap  | 不维护业务数据缓存                       |

**为什么 Kafka 不在 JVM 堆里缓存?**

- JVM 堆越大,GC 暂停越长,影响 P99 延迟
- 堆内对象有额外开销(Kafka Record 对象头 ≈ 40 字节)
- OS 的 Page Cache **比任何应用层缓存都更"懂"磁盘**——它知道哪些 Page 即将被回写、哪些不会再被读

### 3. 零拷贝对比

| I/O 路径                         | 拷贝次数 | 适用场景                                |
|----------------------------------|---------|---------------------------------------|
| 传统 read + write               | 4 次    | 早期 Java I/O                          |
| **sendfile (零拷贝)**            | **2 次** | **Kafka 消息数据传输**                |
| mmap + write                    | 2~3 次  | Kafka 索引文件                         |
| splice / tee                     | 2 次    | 同 sendfile,内核间管道                |

### 4. 索引结构对比

| 系统           | 索引类型                                  | 大小                       |
|--------------|-----------------------------------------|---------------------------|
| **MySQL**     | B+Tree,聚簇 / 二级索引                     | GB 级,部分在内存,部分在磁盘 |
| **Elasticsearch** | 倒排索引 + LSM                          | MB ~ GB 级,常驻堆或 FS    |
| **Kafka**     | 稀疏索引 (offset → position)               | MB 级,**全部 mmap 进内存** |
| **Redis**     | Hash / Skiplist                           | 数据集大小,全内存          |

**Kafka 的索引本质上是"线性映射的快捷方式"**——它的查询模式远比数据库简单(只支持 offset / 时间戳两类查找),所以不需要 B+Tree 这种"全能"结构。

### 5. 数据可靠性对比

| 系统           | 默认可靠性          | 数据丢失边界                                   |
|--------------|------------------|---------------------------------------------|
| **MySQL InnoDB** | 高 (WAL + 副本)   | 最后已 checkpoint 之后的数据,通常毫秒级        |
| **Kafka (acks=all)** | 高 (多副本同步)   | ISR 全部故障时,可能丢失最后未同步的消息       |
| **RabbitMQ** | 中 (持久化 + 镜像)  | mirror 同步延迟内的消息                       |
| **Redis (AOF)** | 高                 | last fsync 之后的数据                         |

### 6. 一致性模型对比

| 模型                | Kafka 实现                       | 数据库实现                     |
|--------------------|----------------------------------|-------------------------------|
| **强一致**          | acks=all + min.insync.replicas   | Serializable + 2PL              |
| **最终一致**        | 默认 (acks=1)                    | Async replication               |
| **因果一致**        | 单分区有序 + 幂等 Producer       | 不直接提供                     |
| **读己之写**        | 不适用 (异步)                    | READ COMMITTED 隔离级          |

### 7. 写入语义 (Producer → Broker)

| 语义            | 实现方式                              | Kafka 配置                       |
|----------------|-------------------------------------|----------------------------------|
| **at most once** | 失败不重试                          | retries=0, acks=0                |
| **at least once** | 失败无限重试,可能重复               | retries=MAX, acks=all             |
| **exactly once** | 幂等 + 事务,broker 端去重          | enable.idempotence=true + 事务 API |

Kafka 通过**幂等 Producer** + **事务 API** 实现了**端到端 exactly once**,这是消息中间件领域相对独特的保证。

### 8. Kafka 为什么不直接用数据库的存储模型

很多 Kafka 的设计"看起来反常识",根本原因是它**不打算做数据库**:

| 反常识设计                    | 数据库会怎么做              | Kafka 的理由                          |
|------------------------------|--------------------------|-------------------------------------|
| 不在内存缓存数据              | Buffer Pool 全量缓存       | OS Page Cache 已更高效                |
| 用稀疏索引而非 B+Tree          | 必然 B+Tree                | 查询模式太简单,杀鸡用牛刀              |
| 整段删除而非精确删除          | 按行 DELETE                | 减少清理复杂度,接受粗粒度              |
| 文件名用 offset 而非 ID       | 自增主键或 UUID            | 利用单调性避免额外查找                 |
| 关闭 JVM 堆缓存               | 一切皆缓存                 | 避免 GC,降低延迟抖动                  |
| 不支持事务回滚单个消息         | 完整 ACID                  | 顺序日志本身不支持"在中间修改"          |

简言之:**Kafka 用文件系统的简单性,换取了数据库无法企及的吞吐量**。

---
|---------------|------------------------------------------|---------------------------|
| **MySQL**     | B+Tree,聚簇 / 二级索引                     | GB 级,部分在内存,部分在磁盘 |
| **Elasticsearch** | 倒排索引 + LSM                          | MB ~ GB 级,常驻堆或 FS    |
| **Kafka**     | 稀疏索引 (offset → position)               | MB 级,**全部 mmap 进内存** |
| **Redis**     | Hash / Skiplist                           | 数据集大小,全内存          |

**Kafka 的索引本质上是"线性映射的快捷方式"**——它的查询模式远比数据库简单(只支持 offset / 时间戳两类查找),所以不需要 B+Tree 这种"全能"结构。

```
log.segment.bytes         = 1 GB
```


- 方案 A:`log.segment.bytes = 512 MB`,Segment 数翻倍 → 1400 个 → 700 GB ❌(没用)
- 方案 B:`log.segment.bytes = 512 MB`,但调小 `log.retention.hours = 72` → 350 GB ✓
- 方案 C:`log.retention.bytes = 350 GB`,删除最旧 Segment → 350 GB ✓
- 方案 D:压缩率 2x(`compression.type=lz4`) → 350 GB ✓

#### 5.1 高吞吐场景

### 10. 典型故障与处理清单

| 故障现象                | 可能原因                          | 应急处理                                          |
|-----------------------|----------------------------------|------------------------------------------------|
| Producer 报 `RecordTooLargeException` | 单条消息 > 1 MB (默认) | 调 `max.request.size` 与 `message.max.bytes`    |

### 11. 生产环境容量规划

假设业务要求:

```text
日均消息量: 100 亿条
平均消息大小: 1 KB
保留时间: 7 天
副本数: 3
```

**容量计算**:

```text
1. 原始数据量: 100 亿 × 1 KB = 100 亿 KB ≈ 930 GB / 天
2. 副本数放大: 930 × 3 = 2.79 TB / 天
3. 7 天保留: 2.79 × 7 = 19.5 TB 总占用
4. 压缩率 (lz4) ≈ 2 倍: 19.5 / 2 = 9.75 TB
5. Segment 数: 9.75 TB / 1 GB ≈ 10000 个
6. 索引大小: 10000 × 2 MB = 20 GB (可全量加载)

推荐硬件:
   - Broker 数量: 6 ~ 10 台 (考虑副本分布)
   - 每台磁盘: 2 TB (留 50% 给 OS / Page Cache)
   - 每台内存: 32 GB (16 GB Page Cache + 16 GB Heap/OS)
   - 每台网卡: 万兆 (10 Gbps)
```

## 核心要点速记

- **Kafka 是"日志文件系统"**,而不是数据库——所有设计都围绕"顺序写、不可变、批量"展开。
- **三层物理结构**:Segment → RecordBatch → Record。RecordBatch 是读写最小单位,自带 CRC、自带压缩、自带事务标记。
- **稀疏索引 (`.index`) + 二分查找** 让按 offset 查找 O(log N) 完成,索引文件本身可全部 mmap 进内存(单 Segment 索引几 MB)。
- **顺序写盘 + 零拷贝 (sendfile) + Page Cache** 是 Kafka 性能三大基石,共同把网络 / 磁盘 / CPU 的开销压到接近理论极限。
- **滚动策略**支持按大小、时间、索引满触发;Segment 文件名 = baseOffset,天然有序。
- **两种清理策略**:delete (按时间/大小整段删除) 适合日志流,compact (按 Key 保留最新值) 适合状态存储。
- **Compact 的 tombstone** 机制保证删除标记可传播,但保留期过后会被清理。
- **文件恢复依赖 mmap + 重建**:索引丢失可重建,日志丢失必须依赖副本恢复。
- **Leader Epoch Checkpoint** 防止旧 Leader 恢复时回滚覆盖新数据,Kafka 0.11+ 必开。
- **生产配置"三看"**:看吞吐(看 Segment 大小)、看磁盘(看 Retention)、看延迟(看 Page Cache 与刷盘策略)。

> Kafka 的存储设计是分布式系统工程的经典范例:**用最朴素的"日志 + 索引"抽象,加上 OS 级优化(sendfile / mmap / Page Cache),跑出了比关系型数据库高两个数量级的吞吐**。理解它,对设计任何"高写入、低查询"系统都有借鉴意义。

### 附:实战中容易踩的 10 个坑

1. **把 Kafka 当数据库用** —— 想做"按 Value 查询",应当用 ES / ClickHouse 等作为外部索引,Kafka 只负责传输。
2. **acks=0 上生产** —— 性能高但丢消息,除非业务允许丢失(如纯埋点)。
3. **max.message.bytes 默认 1 MB** —— 大消息需同步调大 `max.request.size` 与 Consumer 端 `fetch.max.bytes`。
4. **副本数 1** —— 生产环境任何 Topic 都必须 ≥ 3 副本,且 `min.insync.replicas ≥ 2`。
5. **unclean.leader.election.enable=true** —— 可能从 OSR 选 Leader,造成数据丢失,生产必须关闭。
6. **Retention 时间设得过短** —— Consumer 一次重启就可能错过数据,导致 `OffsetOutOfRangeException`。
7. **Page Cache 被换出** —— Broker 上运行其他内存密集型服务(如 Redis、Hadoop),会严重拖慢 Kafka。
8. **磁盘单点** —— 没用 RAID,坏一块盘就丢一份数据;生产必须 RAID10。
9. **过度压缩** —— Producer + Broker 双层压缩,既不省空间又消耗 CPU,选一层即可。
10. **没启用幂等** —— Producer 端 `enable.idempotence=true` 是默认应当开启的选项,几乎无代价。

### 附:从源码看 Kafka 存储

```scala
// 简化的 Log 类结构(对应源码 kafka.log.Log)
class Log(
  val dir: File,                       // Partition 目录
  val config: LogConfig,               // 配置(log.retention.hours 等)
  val logStartOffset: Long,            // LSO
  val recoveryPoint: Long,             // 已恢复的 offset
  val scheduler: Scheduler,            // 异步调度器(清理/刷盘)
  val time: Time = Time.SYSTEM,
  val brokerTopicStats: BrokerTopicStats = ...
) {
  private val segments: ConcurrentNavigableMap[java.lang.Long, LogSegment] = 
    new ConcurrentSkipListMap[java.lang.Long, LogSegment]()

  def activeSegment = segments.lastEntry().getValue
  def append(records: MemoryRecords): Long = { ... }  // 追加消息
  def read(startOffset: Long, maxLength: Int): FetchDataInfo = { ... }  // 读取
}
```

Log 用 `ConcurrentSkipListMap` 管理所有 Segment,key 为 baseOffset,因此**按 offset 找 Segment 就是 O(log N)** 的有序 map 查找。这与之前讲的"二分查找"本质上是同一个思想——只是用 JDK 的 SkipList 容器来实现而已。

### 附:Kafka 与 LSM-Tree 的对比

Kafka 的 Log + Compact 实际上和 LSM-Tree (Log-Structured Merge Tree) 有相似之处:

| 维度            | LSM-Tree (RocksDB / LevelDB)        | Kafka Log                          |
|---------------|--------------------------------------|------------------------------------|
| **写入**       | MemTable + SSTable,后台 Compaction   | active Segment + LogCleaner         |
| **读取**       | Bloom Filter + 多级 SSTable 查找     | 稀疏索引 + 单 Segment 顺序扫        |
| **压缩触发**   | size-tiered / leveled                | dirty ratio > threshold            |
| **空间放大**   | 存在(中间层未合并)                   | 存在(正在 compact 的 dirty Segment)|
| **典型场景**   | 嵌入式 KV 存储                         | 分布式日志                            |

可以理解为 Kafka 是**分布式版的 LSM-Tree**,只是"存储"被分到了多个 Broker 上,Compaction 变成了后台线程而非嵌入式线程。
