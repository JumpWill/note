# Kafka 生态与集成

> 本章系统梳理 Kafka 生态全景:从生态总览、Connect、Streams、Schema Registry、MirrorMaker、REST Proxy,到多语言 SDK 与大数据生态集成。Kafka 不只是一个消息队列,它已经演化为一个**完整的流数据平台 (Streaming Platform)**,围绕"消息总线"构建了上下游完整工具链。理解 Kafka 生态,等于掌握了现代实时数据架构的蓝图。

---

## 一、Kafka 生态总览

### 1.1 从消息队列到流数据平台

Kafka 最初只是 LinkedIn 内部的消息中间件,经过十余年演进,已经成为一个围绕**日志流 (Log Stream)** 的完整生态。它的定位也发生了根本性变化:

```text
传统 MQ 视角 (2010~):
  "把消息从 A 搬到 B"

现代 Kafka 平台视角 (2018~):
  "以日志为中心,把数据库、缓存、搜索、数据湖、流处理、微服务全部串起来"
```

### 1.2 生态全景图

### 1.3 五大支柱组件

| 组件                       | 作用                                                          | 主要用户                 |
|--------------------------|-------------------------------------------------------------|----------------------|
| **Kafka Broker**         | 核心消息存储与传输                                            | 所有 Kafka 用户         |
| **Kafka Connect**        | 异构数据源与 Kafka 之间的高可靠、可分布式 ETL 框架             | 数据集成、CDC、ETL     |
| **Kafka Streams**        | 轻量级 Java 库,在应用进程内做流处理                           | 业务实时计算            |
| **ksqlDB**               | 基于 Kafka Streams 的 SQL 化流处理引擎                        | 数据分析师、SQL 用户    |
| **Schema Registry**      | 集中式 Schema 管理 + 演进兼容控制                             | 数据治理、契约优先      |

**辅助工具**包括 REST Proxy、MirrorMaker、CLI 工具 (kafka-topics.sh / kafka-console-consumer.sh)、客户端 SDK、Admin API、TestKit、Kafka Connect 插件生态等。

### 1.4 为什么需要生态

只有 Broker 的 Kafka,本质上只是个"高速日志文件系统",它**不能**:

- 直接消费 MySQL binlog
- 直接把数据写入 S3
- 直接做流式聚合、去重、连接
- 直接对外提供 HTTP/JSON 接口
- 自动适配下游 Schema 变更

生态组件把这些"最后一公里"补齐,真正让 Kafka 成为企业级流数据平台的"中枢神经"。

## 二、Kafka Connect

### 2.1 概念与定位

**Kafka Connect** 是 Kafka 官方提供的**数据集成框架**,用于在 Kafka 与外部系统 (数据库、搜索、文件系统、消息队列) 之间**可扩展、可靠、声明式**地搬运数据。

```text
                   Kafka Connect
                       │
        ┌──────────────┴──────────────┐
        │                             │
        ▼                             ▼
┌──────────────────┐          ┌──────────────────┐
│ Source Connector │          │  Sink Connector  │
│  (外部 → Kafka)  │          │  (Kafka → 外部)  │
└──────────────────┘          └──────────────────┘
```

| 类型              | 数据方向             | 典型场景                                                  |
|------------------|--------------------|-------------------------------------------------------|
| **Source Connector** | 外部系统 → Kafka | MySQL Debezium CDC、JDBC 全量/增量、文件采集、API 拉取 |
| **Sink Connector**   | Kafka → 外部系统   | Kafka → ES、Kafka → S3、Kafka → HDFS、Kafka → JDBC  |

Connect 的核心价值是:**用户只写配置,不写代码**。一个完整的 CDC 链路只需几行 properties + JSON 配置即可上线。

### 2.2 核心概念

| 概念            | 含义                                                                  |
|---------------|---------------------------------------------------------------------|
| **Connector** | 高级别抽象,定义"从哪里到哪里、怎么映射"                                     |
| **Task**      | Connector 拆分出的最小执行单元,真正做数据搬运的进程/线程                      |
| **Worker**    | 运行 Connector 的进程,独立模式 = 单进程,分布式模式 = 集群                       |
| **Converter** | 消息格式转换,Source 把外部数据转成 Kafka 内部格式,Sink 反向 (常用 AvroConverter) |
| **Transform (SMT)** | 单条消息级别的转换,如 `InsertField`、`ExtractField`、`MaskField`、`ReplaceField` |
| **Offset**    | Task 的位点,Source 记录已读位置,Sink 记录已写位置                        |
| **Dead Letter Queue** | 处理失败的消息送入指定 topic,不阻塞主链路                              |

### 2.3 独立模式 vs 分布式模式

| 维度       | **Standalone (独立模式)**        | **Distributed (分布式模式)**             |
|----------|----------------------------------|------------------------------------------|
| 部署       | 单进程加载所有 Connector 配置        | 多 worker 进程组成集群                       |
| 配置文件  | `connect-standalone.properties` + 每个 Connector 一个 properties | `connect-distributed.properties` + REST API 提交 |
| 适用场景   | 本地开发、测试、单实例 ETL           | 生产环境、高可用、横向扩展                   |
| 故障恢复   | Worker 挂 = Connector 全停        | Worker 挂 = Task 自动漂移到其他 Worker       |
| 扩展性     | 受单机资源限制                      | 增加 Worker 即可水平扩展                     |
| 配置管理   | 文件                              | REST API (`/connectors`)                  |
| 推荐度    | 仅测试                            | 生产必选                                   |

**独立模式启动示例** (开发用):

```bash
bin/connect-standalone.sh \
  config/connect-standalone.properties \
  config/mysql-source.properties \
  config/es-sink.properties
```

**分布式模式启动示例** (生产用):

```bash
bin/connect-distributed.sh config/connect-distributed.properties
# 然后通过 REST API 提交
curl -X POST http://localhost:8083/connectors \
  -H "Content-Type: application/json" \
  -d @mysql-source.json
```

### 2.4 常用 Connector 速览

| Connector                                          | 类型      | 主要用途                                         |
|--------------------------------------------------|---------|--------------------------------------------|
| **Debezium MySQL Source**                         | Source   | MySQL binlog CDC,全量+增量,业界事实标准               |
| **Debezium PostgreSQL Source**                    | Source   | PostgreSQL logical decoding CDC                |
| **Debezium MongoDB Source**                       | Source   | MongoDB oplog CDC                              |
| **JDBC Source (Confluent)**                       | Source   | 通用 SQL 轮询(全量/增量列),适合中小数据量             |
| **JDBC Sink (Confluent)**                         | Sink     | Kafka → 任意 JDBC 数据库                         |
| **Elasticsearch Sink**                            | Sink     | Kafka → ES(支持按 Key 路由、按时间索引)             |
| **S3 Sink (Confluent / Amazon)**                  | Sink     | Kafka → S3,支持 Parquet/Avro/JSON、按时间分区       |
| **HDFS Sink**                                     | Sink     | Kafka → HDFS,用于对接 Hadoop 数据湖                |
| **File Pulse Source**                             | Source   | 监听目录新文件入库                                 |
| **HTTP Source**                                   | Source   | HTTP 长轮询入 Kafka                               |
| **MQTT Source / Sink**                            | 双向      | IoT 设备消息桥接                                  |

### 2.5 REST API 详解

Connect 分布式模式暴露完整的 REST API,用于动态管理 Connector、Task、配置:

| 方法 / 路径                                                    | 功能                         |
|--------------------------------------------------------------|----------------------------|
| `GET    /connectors`                                          | 列出所有 Connector              |
| `POST   /connectors`                                          | 创建 Connector(提交 JSON 配置)  |
| `GET    /connectors/{name}`                                   | 查看 Connector 详情            |
| `GET    /connectors/{name}/status`                            | 查看状态 (RUNNING/FAILED/...) |
| `PUT    /connectors/{name}/config`                            | 更新配置                       |
| `GET    /connectors/{name}/config`                            | 查看当前配置                    |
| `POST   /connectors/{name}/restart`                           | 重启 Connector                |
| `PUT    /connectors/{name}/pause` / `resume`                  | 暂停 / 恢复                   |
| `DELETE /connectors/{name}`                                   | 删除                          |
| `GET    /connectors/{name}/tasks`                             | 列出所有 Task                 |
| `POST   /connectors/{name}/tasks/{taskId}/restart`            | 重启单个 Task                 |

这些 API 也是监控、CI/CD、Operator (如 Strimzi) 与 Connect 交互的核心入口。

### 2.6 Connector 配置示例 (JDBC Source)

```properties
name=mysql-source-orders
connector.class=io.confluent.connect.jdbc.JdbcSourceConnector
tasks.max=2

# 数据源
connection.url=jdbc:mysql://mysql-host:3306/ecommerce?useSSL=false
connection.user=etl_user
connection.password=etl_pass

# 增量策略
mode=incrementing
incrementing.column.name=id
# 增量 + 时间戳
# mode=timestamp
# timestamp.column.name=update_time

# 表白名单(支持正则)
table.whitelist=orders,order_items,users

# Topic 命名模板
topic.prefix=cdc.mysql.

# 轮询间隔
poll.interval.ms=1000

# 消息格式
key.converter=org.apache.kafka.connect.storage.StringConverter
value.converter=io.confluent.connect.avro.AvroConverter
value.converter.schema.registry.url=http://schema-registry:8081

# 错误处理
errors.tolerance=none
errors.deadletter.queue.topic.name=dlq.cdc.mysql
```

## 三、Kafka Streams

### 3.1 流处理概念

**流处理 (Stream Processing)** 是对**无界、连续**的数据集做实时计算,与批处理相对应。

```text
批处理:收集完一批数据后整体计算 (MapReduce、Spark Batch)
       ───────────────►  ───────────────►  ───────────────►
       Job T1            Job T2            Job T3

流处理:每来一条/每来一个窗口就计算一次
       ─► ─► ─► ─► ─► ─► ─► ─► ─► ─► ─► ─► ─► ─► ─►
       处理节点持续消费,毫秒级延迟
```

Kafka Streams 是 **Java 库** 而非集群:不需要单独部署,与应用进程同生共死,直接通过 `maven/gradle` 引入即可。它的定位是**轻量级、嵌入式、与 Kafka 原生集成**。

### 3.2 三大数据结构

Kafka Streams 的核心抽象是 **KStream、KTable、GlobalKTable**,理解它们的差异是掌握 Streams 的关键。

| 维度                | **KStream**                                  | **KTable**                                  | **GlobalKTable**                            |
|-------------------|----------------------------------------------|---------------------------------------------|---------------------------------------------|
| **抽象**          | 一条记录流 (record stream)                  | 更新日志 (changelog stream)                 | 全量维度表 (dimension table)               |
| **主键语义**      | 每条独立,与 key 无关         | 同一 key 的最新值                           | 每个 instance 都持有完整 key-value          |
| **操作**          | map / filter / flatMap / join (stream-stream) | aggregate / reduce / join (stream-table) | join (stream-globalTable)                  |
| **数据来源**      | 任意 topic                                   | compacted topic                             | 任意 compacted topic                        |
| **状态**          | 无状态                                       | 本地状态存储 (RocksDB)                       | 内存/RocksDB,全量                           |
| **典型用途**      | 事件流、日志、点击流、订单事件                 | 账户余额、配置、用户画像、维度信息            | 国家代码表、商品分类表 (小且不变)            |
| **并行度**        | 按分区                                       | 按 key 的 hash 分区                          | 不分区,所有 instance 全量                   |
| **每分区一份**    | 否                                           | 是 (分区一致)                                | 否 (全量副本)                                |

### 3.3 KStream vs KTable 对比图

```text
KStream (事件流,无状态):
   key    value
   ─────────────
   u1     click_001       每个事件独立处理
   u1     click_002       "u1 点了两次"
   u1     click_003       → 不能直接说"u1 最新点击是 003"

KTable (更新日志,Key 状态):
   key    value           同一 key 的最新值覆盖
   ─────────────
   u1     click_001       u1 现在状态 = click_001
   u1     click_002       u1 现在状态 = click_002  (覆盖)
   u1     click_003       u1 现在状态 = click_003  (再覆盖)
                          → KTable 永远代表"现在这一刻"
```

**经典场景**:
- `KStream<K, ClickEvent>` × `KTable<K, UserInfo>` = **事件流关联用户维度**
- `KStream<K, Order>` × `GlobalKTable<K, Product>` = **订单关联商品全量表** (商品少,适合 Global)

### 3.4 状态存储 (State Store)

KTable / Aggregate / Join 的背后都是**状态存储**,默认实现是 **RocksDB** (嵌入式 KV 存储,LSM-Tree,写性能极佳):

```text
Kafka Streams Topology
       │
       ├── Source Processor  ── 读 topic
       │
       ├── Stream Processor  ── 无状态 map/filter
       │
       ├── State Store        ── RocksDB 实例 (changelog topic 备份)
       │       │
       │       ├── 内存部分 (block cache)
       │       └── 磁盘部分 (sst files)
       │
       └── Sink Processor   ── 写回 topic
```

**关键特性**:
- **Changelog Topic**:每个状态存储对应一个内部 compacted topic,做容灾备份,WAL 角色
- **Standby Replica**:可为状态存储开启 standby 实例,故障时秒级切换
- **查询能力**:通过 **Interactive Queries** 直接查询本地状态,做"低延迟 KV 服务"

```java
// Interactive Queries 伪代码
ReadOnlyKeyValueStore<String, Long> store =
    streams.store(StoreQueryParameters.fromNameAndType("count-store", QueryableStoreTypes.keyValueStore()));

Long value = store.get("user_123");   // 毫秒级响应
```

### 3.5 窗口操作 (Windowing)

Streams 提供三类窗口,把无界流切成**有界块**进行聚合:

| 窗口类型                | 行为                                                         | 典型用途                          |
|----------------------|------------------------------------------------------------|---------------------------------|
| **Tumbling (滚动)**    | 固定大小、**不重叠**,每条数据只属于一个窗口                       | 每分钟 PV、每小时订单数               |
| **Hopping (滑动)**     | 固定大小、**可重叠**,由 `window-size` + `advance-interval` 决定 | 每 5 分钟统计过去 10 分钟的活跃用户    |
| **Session (会话)**     | 按 key 的活跃间隙动态切分,`inactivity-gap` 触发新窗口           | 用户会话时长、行为序列分析             |
| **Global (全局)**     | 单窗口覆盖所有数据                                            | 离线批处理风格的全量聚合                |

```java
// Hopping Window 示例:每 10 秒输出过去 30 秒的订单总额
KTable<Windowed<String>, Double> sales =
    orders
        .groupByKey()
        .windowedBy(TimeWindows.of(Duration.ofSeconds(30))
                            .advanceBy(Duration.ofSeconds(10)))
        .aggregate(
            () -> 0.0,
            (key, order, total) -> total + order.amount(),
            Materialized.as("sales-30s-store"));
```

### 3.6 Processor API 与 DSL

Kafka Streams 提供两层 API:

**1. DSL (High-Level)** — 声明式,90% 场景够用:

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, Order> orders = builder.stream("orders");

KTable<String, Long> userOrderCount = orders
    .filter((k, v) -> "PAID".equals(v.getStatus()))
    .groupByKey()
    .count(Materialized.as("user-order-count"));

userOrderCount.toStream().to("user-order-count-output");
```

**2. Processor API (Low-Level)** — 命令式,可精细控制:

```java
Topology topology = new Topology();
topology.addSource("source", "orders")
        .addProcessor("custom", () -> new MyProcessor(), "source")
        .addStateStore(
            Stores.keyValueStoreBuilder(
                Stores.inMemoryKeyValueStore("my-store"),
                Serdes.String(),
                Serdes.Long()),
            "custom")
        .addSink("sink", "orders-processed", "custom");
```

| 维度       | DSL                  | Processor API                  |
|----------|----------------------|--------------------------------|
| 学习曲线   | 低                    | 中-高                          |
| 表达力     | 标准算子                | 完全自定义                      |
| 状态管理   | 自动                  | 手动 `context.getStateStore()` |
| 适用人群   | 业务开发者              | 平台/中间件开发者                |
| 性能优化空间| 编译器内做了一些优化       | 可手动调到极致                  |

### 3.7 Exactly Once 处理

Kafka Streams 通过 **EOS (Exactly-Once Semantics)** 保证"即使崩溃,处理结果也不会重复也不会丢失":

```text
              ┌──────────────────────────────────┐
              │   Streams EOS 三件套            │
              └──────────────────────────────────┘
                            │
   ┌────────────────────────┼────────────────────────┐
   │                        │                        │
   ▼                        ▼                        ▼
┌────────┐              ┌────────┐              ┌────────┐
│ 生产幂等 │              │ 事务 API │              │ 状态存储 │
│ (0.11+) │              │ (0.11+) │              │ 隔离级别 │
└────────┘              └────────┘              └────────┘
   │                        │                        │
   └────────────────────────┴────────────────────────┘
                            │
                            ▼
                  "读 + 处理 + 写"作为一个原子事务
```

**实现机制**:
- 生产端:Producer ID + Sequence Number,Broker 端去重
- 消费端:`read_committed` 隔离级别,只消费已提交的事务消息
- 状态存储:每条记录的处理与状态变更在同一事务内提交

```properties
# 启用 EOS
processing.guarantee=exactly_once_v2
# 或 exactly_once (旧)
```

EOS 代价:吞吐量比 `at_least_once` 低约 10~30%,换来**端到端不重不丢**。

### 3.8 与 Flink / Spark Streaming 对比

| 维度              | **Kafka Streams**            | **Apache Flink**            | **Spark Streaming / Structured Streaming** |
|-----------------|------------------------------|-----------------------------|-------------------------------------------|
| 部署形态          | Java 库,嵌入应用                  | 独立集群 (JM + TM)              | 独立集群 (Driver + Executor)              |
| API              | DSL + Processor API            | DataStream + Table + SQL     | DStream (RDD) / Structured Streaming      |
| 状态后端          | RocksDB (本地)                | RocksDB / Heap / FSState     | HDFS / S3 / RocksDB (state backend)       |
| 窗口             | 滚动 / 滑动 / 会话 / 全局          | 滚动 / 滑动 / 会话 / 全局         | 滚动 / 滑动 / 会话                          |
| 时间语义          | Event-Time (默认)             | Event-Time / Processing-Time | Event-Time (Structured Streaming)         |
| 水印 (Watermark) | 不支持原生                      | 支持                        | 支持                                       |
| 跨语言           | 仅 JVM 语言                    | 多语言 (Scala/Java/Python)    | 多语言 (Scala/Java/Python/R)             |
| 适用场景          | 中小规模、与 Kafka 紧耦合、嵌入应用   | 大规模、复杂流处理、低延迟         | 大规模、与批处理统一 API、近实时            |
| 运维复杂度        | 极低 (跟应用一起)                | 中 (集群)                    | 中-高 (集群)                              |

## 四、Kafka Schema Registry

### 4.1 为什么需要 Schema Registry

Kafka 消息是**字节序列**,Producer 和 Consumer 必须就**数据格式**达成一致。直接用 JSON 虽然方便,但**没有版本控制、没有兼容性约束、没有类型校验**,一旦上游改了字段,下游静默崩。

```text
无 Schema Registry:
   Producer: "name": "will"        ──┐
   Producer: "name": "will",        ─┤── 下游解析时崩溃 or 字段丢失
           "age": 18                  │
   Consumer: 解析?字段是 name 还是 userName? age 是 number 还是 string? 

有 Schema Registry:
   Producer: 上传 Schema → 注册 → 用 Schema ID 写消息
   Consumer: 读 Schema ID → 拉 Schema → 安全反序列化
   Registry: 检查兼容性,不兼容就拒绝
```

### 4.2 三种主流 Schema 格式

| 格式              | 优点                                              | 缺点                              | 适用场景                |
|-----------------|-------------------------------------------------|---------------------------------|---------------------|
| **Avro**        | 二进制紧凑、支持丰富类型、有 IDL、支持演进              | 需配合 schema,调试稍麻烦           | 数据管道主流选择          |
| **Protobuf**    | 性能极佳、跨语言一流、Google 背书                      | Schema 信息不存数据,改动需小心      | 微服务 RPC、跨语言       |
| **JSON Schema** | 可读性强、Schema 即文档                            | 数据本身冗余大、性能差               | 调试场景、外部接口        |

**Avro 示例** (`.avsc`):

```json
{
  "type": "record",
  "name": "Order",
  "namespace": "com.example.order",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "userId",  "type": "string" },
    { "name": "amount",  "type": "double" },
    { "name": "status",  "type": { "type": "enum", "name": "Status",
                                   "symbols": ["NEW","PAID","SHIPPED"] } }
  ]
}
```

### 4.3 Confluent Schema Registry 部署

Schema Registry 本身是无状态服务,**状态存放在一个内部 Kafka topic `_schemas`** 上,所以**天然高可用、可水平扩展**:

```text
              ┌──────────────────────┐
              │ Confluent SR 集群    │
              │ (每个节点无状态)       │
              └──────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   ┌─────────┐    ┌─────────┐    ┌─────────┐
   │ SR-1    │    │ SR-2    │    │ SR-3    │   (3 节点 HA)
   └─────────┘    └─────────┘    └─────────┘
        │              │              │
        └──────────────┼──────────────┘
                       ▼
        ┌──────────────────────────┐
        │  Kafka topic: _schemas   │   (compact,持久化所有 schema)
        └──────────────────────────┘
```

**客户端交互**:

```bash
# 注册 schema
curl -X POST http://sr:8081/subjects/orders-value/versions \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  -d '{"schema": "{...}"}'

# 查询最新 schema
curl http://sr:8081/subjects/orders-value/versions/latest

# 兼容性校验
curl -X POST http://sr:8081/compatibility/subjects/orders-value/versions/latest \
  -d '{"schema": "{...new...}"}'
```

### 4.4 Schema 演进与兼容性

Schema 不是一成不变的,业务演进必然要求字段增减。Registry 通过**兼容性检查**保护消费端:

| 兼容性级别              | 含义                                                                       |
|----------------------|--------------------------------------------------------------------------|
| **BACKWARD** (默认)    | 新 Schema 可读旧数据 (删字段、加可选字段);Consumer 先升级,Producer 后升级           |
| **FORWARD**          | 旧 Schema 可读新数据 (加字段);Producer 先升级,Consumer 后升级                   |
| **FULL**             | 既 BACKWARD 又 FORWARD (增/删可选字段、调整默认值)                              |
| **BACKWARD_TRANSITIVE** | 所有历史版本都能被新版本读                                              |
| **NONE**             | 不检查兼容性 (慎用)                                                         |

```bash
# 设置主题兼容性级别
curl -X PUT http://sr:8081/config/orders-value \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  -d '{"compatibility": "FULL"}'
```

## 六、Kafka MirrorMaker 2 (跨集群复制)

### 6.1 跨集群复制的必要性

```text
场景 A:同城双活      两机房 Kafka 互备,任一机房故障可秒级切换
场景 B:异地灾备      北京 → 上海单向复制,应对城市级故障
场景 C:数据汇聚      全国多地 Kafka → 总部 Kafka 做集中分析
场景 D:合规隔离      生产/测试/预发环境 Kafka 完全隔离,通过 MirrorMaker 按需同步
```

### 6.2 MirrorMaker 2 vs MirrorMaker 1

| 维度          | **MM1 (旧)**             | **MM2 (新,推荐)**                  |
|-------------|--------------------------|-------------------------------------|
| 内核          | 基于 Consumer + Producer  | 同样基于 Connect 框架                 |
| Topic 映射   | 手动配置                  | 自动同步 + `MirrorSourceConnector`   |
| Offset 转换  | 不支持                    | 支持跨集群 offset 同步                  |
| 集群身份      | 不区分                    | 通过 `source.cluster.alias` 区分      |
| 配置方式      | consumer/producer properties | 纯 Connect REST API                  |
| 推荐度       | 已不推荐                  | Kafka 2.4+ 默认方案                   |

### 6.3 主动-被动 (Active-Passive)

```text
   ┌──────────────────┐             ┌──────────────────┐
   │  Primary Cluster │ ─────MM2──► │  DR Cluster      │
   │  (生产读写)        │             │  (只读备份)        │
   │  Kafka-DC1       │             │  Kafka-DC2       │
   └──────────────────┘             └──────────────────┘

用途:灾备、机房故障切换
故障时:Consumer 从 DC2 启动消费,业务继续
```

### 6.4 主动-主动 (Active-Active)

```text
   ┌──────────────────┐             ┌──────────────────┐
   │  Cluster A       │ ◄────────►  │  Cluster B       │
   │  Kafka-DC1       │             │  Kafka-DC2       │
   └──────────────────┘             └──────────────────┘
        ▲                                 ▲
        │                                 │
    业务 1                              业务 2
   (用户 A~M)                          (用户 N~Z)

用途:两地用户就近写入,跨集群同步后全量可见
风险:双写冲突、循环复制,需启用 ACL 与 topic 白名单
```

### 6.5 MirrorMaker 2 配置示例

```properties
# connect-mirror-maker.properties
clusters=primary,secondary

primary.bootstrap.servers=primary-kafka:9092
secondary.bootstrap.servers=secondary-kafka:9092

# 同步方向
primary->secondary.enabled=true
secondary->primary.enabled=false

# 同步 topic 白名单
primary->secondary.topics=orders,users,payments

# 同步消费组 (复制 offset)
primary->secondary.groups=order-consumer,payment-consumer

# 同步频率与并发
tasks.max=4
offset.sync.interval.seconds=10

# 心跳 topic (必须!)
heartbeat.topic.name=mm2-heartbeat
heartbeat.interval.ms=3000

# checkpoint topic
checkpoints.topic.name=mm2-offset-translation
```

启动:

```bash
bin/connect-mirror-maker.sh config/connect-mirror-maker.properties
```

`primary.orders` topic 复制到对端后变为 `primary.orders` (用 `source.cluster.alias` 前缀避免冲突)。

## 七、Kafka REST Proxy

### 7.1 Confluent REST Proxy 是什么

REST Proxy 是 **HTTP 代理层**,让无法直接用 Kafka 客户端的语言/工具能访问 Kafka:

```text
                                ┌────────────────────┐
HTTP Client (浏览器/curl/Python)│  REST Proxy        │
        │                       │  (Java Service)    │
        │  HTTP/JSON            └─────────┬──────────┘
        ▼                                  │
   GET /topics/orders/messages     内部协议:Kafka Protocol
   POST /topics/orders                     │
                                           │
                                ┌──────────▼──────────┐
                                │   Kafka Cluster    │
                                └────────────────────┘
```

### 7.2 典型使用场景

| 场景                       | 是否适合用 REST Proxy                  |
|--------------------------|----------------------------------|
| **快速调试、curl 验证**     | 极佳                                 |
| **前端直接读写 Kafka**      | 适合(避免暴露 Kafka 协议)            |
| **低吞吐数据上报** (IoT 简单设备) | 适合                              |
| **跨语言轻量集成**           | 适合                                  |
| **生产级高吞吐业务**         | **不推荐**,延迟与吞吐都不如原生客户端     |
| **消费位点精确控制**         | 不支持,需原生客户端                       |

### 7.3 核心 API

```bash
# 列出 topics
curl http://rest-proxy:8082/topics

# 生产消息
curl -X POST http://rest-proxy:8082/topics/orders \
  -H "Content-Type: application/vnd.kafka.json.v2+json" \
  -d '{
    "records": [
      {"key": "u1", "value": {"order_id": "1001", "amount": 99.5}},
      {"key": "u2", "value": {"order_id": "1002", "amount": 199.0}}
    ]
  }'

# 消费消息 (需要先创建 consumer instance)
curl -X POST http://rest-proxy:8082/consumers/my-group \
  -H "Content-Type: application/vnd.kafka.json.v2+json" \
  -d '{"name": "my-consumer", "format": "json", "auto.offset.reset": "earliest"}'

curl -X POST http://rest-proxy:8082/consumers/my-group/instances/my-consumer/subscription \
  -H "Content-Type: application/vnd.kafka.json.v2+json" \
  -d '{"topics": ["orders"]}'

curl -X GET http://rest-proxy:8082/consumers/my-group/instances/my-consumer/records
```

**注意**:REST Proxy **不是 Kafka 替代品**。原生客户端 (`confluent-kafka-python`、`kafka-clients`) 性能高 10~100 倍。

## 九、Schema 演进最佳实践

### 9.1 演进原则

| 原则                          | 说明                                                      |
|------------------------------|---------------------------------------------------------|
| **永远向后兼容**                | 新 Schema 能读旧数据;`BACKWARD` 兼容性是底线                |
| **永远不删必填字段**            | 只能删除**可选**字段 (有默认值)                            |
| **新增字段必有默认值**          | 否则旧 Consumer 会抛错                                     |
| **类型变更要谨慎**              | int → long OK,int → string 危险                          |
| **重命名字段 = 新建+废弃**      | 直接改名会被视为删除+新建,需两步过渡                          |
| **枚举值只能加不能删**          | 删除会破坏正在解析的旧数据                                   |
| **小步快跑,避免大版本跳跃**      | 一次一两个字段,出问题易回滚                                  |

### 9.2 字段变更对照表

| 操作                              | 兼容性        | 推荐度          |
|--------------------------------|------------|---------------|
| 新增可选字段 (with default)        | BACKWARD    | 推荐           |
| 删除可选字段                       | BACKWARD    | 推荐           |
| 新增必填字段 (无 default)          | 不兼容        | 禁止           |
| 删除必填字段                       | 不兼容        | 禁止           |
| int → long                      | BACKWARD    | 推荐           |
| string → bytes                  | 不兼容        | 禁止           |
| 重命名字段                         | 等价于删除+新增  | 必须两步过渡     |
| 调整字段顺序                       | 兼容          | 安全           |

### 9.3 客户端行为建议

```java
// Java Avro 反序列化:严格模式 vs 字段忽略
// 严格:Unknown field → 抛异常
// 宽松:Unknown field → 忽略
// Avro 默认行为:严格,需注意 Schema 兼容性
```

```python
# confluent-kafka-python:Avro 反序列化
# 自动通过 Schema Registry 拉取 schema,失败时报错
# 业务侧应在 schema 不兼容时做熔断或兜底反序列化 (JSON)
```

### 10.1 流式架构中的中枢

### 10.2 与 Flink 集成

Flink 内置 Kafka Source/Sink,是 Kafka 最强的消费端之一:

```java
// Flink Kafka Source (新 API,FLIP-27)
KafkaSource<Order> source = KafkaSource.<Order>builder()
    .setBootstrapServers("kafka:9092")
    .setGroupId("flink-consumer")
    .setTopics("cdc.orders")
    .setStartingOffsets(OffsetsInitializer.committedOffsets())
    .setValueOnlyDeserializer(new AvroDeserializationSchema<>(Order.class))
    .build();

DataStream<Order> stream = env.fromSource(source,
                                          WatermarkStrategy.noWatermarks(),
                                          "Kafka Source");
```

**优势**:Flink 提供更强大的**窗口、状态、水印、Exactly-Once**,适合复杂流处理;Kafka Streams 适合**简单、与 Kafka 紧耦合**的轻量场景。

```text
   ┌────────────┐                ┌────────────┐
   │ Order Svc  │  OrderCreated  │ Inventory  │
   │  (创建订单) │ ─────────────► │  Svc       │

                                 └────────────┘
```

**核心模式**:**Choreography (编排)** 而非 Orchestration (编制)。每个服务发布领域事件,其他服务订阅。

```java
// Order Svc 发布事件
kafkaTemplate.send("order.events",
                   order.getId().toString(),
                   new OrderCreatedEvent(order));

// Inventory Svc 订阅并处理
@KafkaListener(topics = "order.events", groupId = "inventory")
public void handle(ConsumerRecord<String, DomainEvent> record) {
    if (record.value() instanceof OrderCreatedEvent evt) {
        inventoryService.deduct(evt.orderId(), evt.items());
        kafkaTemplate.send("inventory.events", "StockReserved");
    }
}
```

**优势**:
- 服务之间**松耦合**,新增消费者不影响生产者
- 天然**事件溯源 (Event Sourcing)**:Kafka 即事件日志
- 支持**重试、补偿、Saga** 模式
- 与 **CQRS** 模式天然契合

## 十二、核心要点速记

- **Kafka 生态 = Broker + Connect + Streams + Schema Registry + REST Proxy + MirrorMaker** 五大支柱,围绕"日志流"展开。
- **Kafka Connect** 是数据集成的事实标准,**Source 把数据搬进 Kafka,Sink 把数据搬出 Kafka**,生产环境必用**分布式模式**。
- **Debezium** 是 MySQL/PG/MongoDB CDC 的事实标准,基于 binlog/oplog,提供**全量快照 + 增量订阅**。
- **Kafka Streams** 是**嵌入式 Java 库**,不是集群;`KStream` = 事件流、`KTable` = Key 状态、`GlobalKTable` = 全量维度表。
- **状态存储**默认是 RocksDB,通过 **changelog topic** 做容灾;**Standby Replica** 提供秒级故障切换。
- **窗口**三类:滚动 (无重叠)、滑动 (可重叠)、会话 (按活跃间隙);Hopping Window 用 `advance-by` 控制步长。
- **EOS** 通过 Producer 幂等 + 事务 API + `read_committed` 三件套实现,**Stream 端到端不重不丢**。
- **Schema Registry** 把 Schema 集中存放在内部 topic `_schemas`,提供 **Avro/Protobuf/JSON Schema** 三大格式的统一管理。
- **Schema 兼容性**默认 `BACKWARD`:新 Schema 能读旧数据;**新增可选字段 + 删除可选字段**是最安全的演进。
- **MirrorMaker 2** 是 Kafka 2.4+ 的跨集群复制方案,**主动-被动**用于灾备,**主动-主动**用于双活。
- **REST Proxy** 适合调试、轻量接入、低吞吐场景;**生产高吞吐必须用原生客户端**。
- **客户端 SDK 选型**:**Java 用 kafka-clients**,**Python 用 confluent-kafka-python** (避开 kafka-python),**Go 用 sarama/kafka-go**,**Node 用 kafkajs/node-rdkafka**。
- **librdkafka 系列** (C++/Python/Go/.NET/Rust) **性能与稳定性都接近 Java**,生产首选。
- **Kafka 与 Flink 集成** 是实时架构最常见的组合;Flink 负责复杂流处理,Kafka 负责数据总线。
- **Kafka 与 Spark Structured Streaming** 统一流批 API,**checkpoint** 必须落到 HDFS/S3 等可靠存储。
- **ClickHouse Kafka Engine** 可免中间层直连 Kafka;**Iceberg/Hudi + Kafka** 是流式数据湖的标准范式。
- **事件驱动微服务** (Choreography) 是 Kafka 的杀手锏,**Kafka 即事件日志**,天然 Event Sourcing + CQRS。
- **生产配置基线**:`acks=all` + `enable.idempotence=true` + `retries=MAX` + `compression.type=lz4` + `linger.ms=10~50` + `isolation.level=read_committed`(EOS 时)。
- **Schema 演进铁律**:**永远向后兼容,永远不删必填字段,新增字段必有默认值,类型变更要谨慎,枚举只能加不能删**。
- **Kafka 生态总哲学**:**把数据库 / 缓存 / 搜索 / 数据湖 / 流处理 / 微服务 全部串起来**,让 Kafka 成为企业**流数据平台的中枢神经**。

> Kafka 不只是一个消息队列,它是一个**完整的流数据平台 (Streaming Platform)**。掌握 Connect + Streams + Schema Registry 三大件,等于掌握了现代实时数据架构的**生产工具链**;理解 MirrorMaker + REST Proxy + 多语言 SDK,等于掌握了**跨集群 / 跨语言 / 跨地域**的企业级落地能力。生态的边界,就是实时架构的边界。
