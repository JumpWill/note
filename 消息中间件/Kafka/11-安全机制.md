# Kafka 安全机制 (Kafka Security)

## 一、Kafka 安全概述

### 1. 为什么需要安全机制

Kafka 在企业环境中常承载订单、交易、日志等敏感数据,默认情况下 Kafka 集群对任何能访问 Broker 的客户端开放,这在生产环境是绝对不可接受的。常见的安全威胁包括:

- **未授权访问**:任何人连上 Broker 即可生产/消费任意 Topic
- **数据泄露**:消息在网络传输中明文,可能被中间人嗅探
- **权限越权**:一个应用账号能读到所有 Topic,违反最小权限原则
- **元数据泄露**:Topic 名称、消费组信息本身就可能包含业务秘密
- **审计缺失**:无法追溯谁在什么时间访问了哪些 Topic
- **合规风险**:GDPR、PCI-DSS、等保 2.0、HIPAA 等对数据安全有强制要求

### 2. Kafka 安全的三层防护

```
┌──────────────────────────────────────────────┐
│  客户端                                      │
└──────────────────┬───────────────────────────┘
                   │ 传输通道
┌──────────────────▼───────────────────────────┐
│  第一层:加密传输 (Encryption in Transit)      │
│  - SSL/TLS 加密客户端与 Broker 之间的数据     │
│  - 防止网络嗅探与中间人攻击                    │
└──────────────────┬───────────────────────────┘
                   │ 已加密
┌──────────────────▼───────────────────────────┐┐
│  第二层:身份认证 (Authentication)             ││
│  - 验证"你是谁"                              ││
│  - SASL/PLAIN、SASL/SCRAM、SASL/GSSAPI        ││
│  - mTLS 双向证书认证                          ││
└──────────────────┬───────────────────────────┘┘
                   │ 身份已确认
┌──────────────────▼───────────────────────────┐
│  第三层:权限授权 (Authorization)              │
│  - 决定"你能做什么"                          │
│  - 基于 ACL 的细粒度授权                       │
│  - Topic、Group、Cluster、TransactionalId      │
└──────────────────────────────────────────────┘
```

### 3. 安全特性版本演进

| 版本 | 重要特性 |
|------|----------|
| 0.9.0.0 | 引入 SSL/TLS 加密和基于文件的 ACL |
| 0.10.0.0 | 引入 SASL/Kerberos |
| 0.10.2.0 | 引入 SASL/PLAIN、SASL/SCRAM |
| 0.11.0.0 | 引入 ACL 增强、Delegation Token |
| 1.0.0 | Kafka Connect 集成 ACL |
| 2.0.0 | AdminClient 增强 |
| 2.3.0 | ACL 支持 ConsumerGroup 精确匹配 |
| 2.4.0 | 引入 OAuth 2.0 Bearer Token 认证 |
| 2.5.0 | KRaft 模式预览 |
| 2.6.0 | SASL/OAUTHBEARER OIDC 支持 |
| 3.0.0 | KRaft 生产可用,简化安全配置 |
| 3.3.0+ | KRaft 模式下 SASL 端口独立配置 |
| 3.5+ | KRaft 安全机制完全成熟,推荐替代 Zookeeper |

### 4. 安全特性依赖关系

```
SSL/TLS  →  独立可用,只解决加密
SASL      →  独立可用,只解决认证
ACL       →  必须依赖 SASL/SSL 才能生效(需要先认证身份)
```

> **重要提示**:Kafka 0.10.2 之前,SSL 和 SASL 不能在同一个 Broker 上同时使用。后续版本可以混用,如 `SASL_SSL` 监听器同时提供认证与加密。

### 5. 监听器 (Listener) 安全矩阵

Broker 监听器决定了使用哪种安全协议,Kafka 支持以下组合:

| 协议 | 加密 | 认证 |
|------|------|------|
| `PLAINTEXT` | 否 | 否 |
| `SSL` | 是 | 是(mTLS) |
| `SASL_PLAINTEXT` | 否 | 是(SASL) |
| `SASL_SSL` | 是 | 是(SASL + SSL) |

生产环境强烈推荐 `SASL_SSL` 监听器,既加密又认证。

## 二、认证 Authentication

### 1. 认证方式总览

Kafka 支持多种认证机制,可同时启用多种,通过不同监听器暴露。

| 认证方式 | 加密 | 复杂度 | 适用场景 | 推荐度 |
|----------|------|--------|----------|--------|
| **SASL/PLAIN** | 否(需配合 SSL) | 低 | 内部测试、学习 | 不推荐生产 |
| **SASL/SCRAM** | 否(需配合 SSL) | 中 | 通用生产环境 | **推荐** |
| **SASL/GSSAPI** (Kerberos) | 否(需配合 SSL) | 高 | 大型企业、已有 KDC | 企业环境 |
| **SASL/OAUTHBEARER** | 否(需配合 SSL) | 中 | 云原生、SSO 集成 | 云环境 |
| **SSL/TLS 客户端认证 (mTLS)** | 是 | 中 | 高安全等级 | 金融、政企 |
| **Delegation Token** | 否 | 中 | 多租户中间件 | 较少使用 |

### 2. SASL/PLAIN

最简单但最不安全的 SASL 机制,密码以明文方式从客户端传到 Broker(可被中间人嗅探)。**生产环境必须配合 SSL 加密**。

#### 原理

```
客户端                Broker
  │                     │
  │  发送用户名:密码     │
  │ ──────────────────> │
  │   (明文 Base64)     │
  │                     │  → 查 JAAS/系统配置
  │                     │  → 验证密码
  │  认证结果            │
  │ <────────────────── │
```

#### JAAS 配置示例 (服务端)

```properties
# /opt/kafka/config/kafka_server_jaas.conf
KafkaServer {
    org.apache.kafka.common.security.plain.PlainLoginModule required
    username="admin"
    password="admin-secret"
    user_admin="admin-secret"
    user_alice="alice-secret"
    user_bob="bob-secret";
};
```

> **注意**:JAAS 文件中的明文密码风险高,生产应通过环境变量或密钥管理加载。

### 3. SASL/SCRAM (推荐)

SCRAM (Salted Challenge Response Authentication Mechanism) 是基于挑战-应答的强认证机制,**密码不以明文传输**,由 ZooKeeper 存储密码哈希。生产环境首选方案。

#### SCRAM 类型对比

| 类型 | 说明 |
|------|------|
| **SCRAM-SHA-256** | Kafka 0.10.2+,默认,适合绝大多数场景 |
| **SCRAM-SHA-512** | Kafka 2.0+,更安全的哈希算法 |

#### SCRAM 认证流程

```
客户端                                       Broker / Zookeeper
  │                                                  │
  │  ① 连接,声明 SCRAM-SHA-256                       │
  │ ──────────────────────────────────────────────>  │
  │                                                  │
  │  ② 挑战:nonce、迭代次数、salt                    │
  │ <──────────────────────────────────────────────  │
  │                                                  │
  │  ③ 计算 ClientProof = HMAC(password, ...)          │
  │ ──────────────────────────────────────────────>  │
  │                                                  │
  │                       计算期望 ServerSignature      │
  │                                                  │
  │  ④ 验证 + 返回 ServerSignature                    │
  │ <──────────────────────────────────────────────  │
  │                                                  │
  │  ⑤ 客户端验证 ServerSignature 防止中间人          │
```

#### SCRAM 优势

- 密码不在网络传输明文
- 服务端只存 salt + 迭代次数 + 哈希值
- 支持密码迭代,抗暴力破解
- 集中存储在 ZooKeeper / KRaft 元数据中,易管理

### 4. SASL/GSSAPI (Kerberos)

适合已部署 Kerberos (Active Directory、MIT KDC) 的企业,实现单点登录和集中身份管理。

#### 工作流程

```
Kafka Client → Kafka Broker (GSSAPI)
   │
   └─→ KDC (Key Distribution Center)
         │
         └─→ 颁发 TGT (Ticket Granting Ticket)
               │
               └─→ 颁发 Service Ticket for Kafka
                     │
                     └─→ 客户端凭 TGT + Service Ticket 登录 Broker
```

#### 优点

- 与企业 AD/LDAP 集成,统一身份
- 支持单点登录 (SSO)
- 无需明文密码存储

#### 缺点

- 需要独立维护 KDC,运维复杂
- 客户端需要 kinit 初始化凭证
- 跨域信任配置复杂

### 5. SSL/TLS 客户端认证 (mTLS)

基于证书的双向认证,客户端与 Broker 互相验证证书,常用于金融、政务等高安全场景。

```
客户端                                    Broker
  │                                         │
  │  ① ClientHello (携带 client cert)       │
  │ ──────────────────────────────────────> │
  │                                         │
  │  ② ServerHello + Server Certificate     │
  │ <────────────────────────────────────── │
  │                                         │
  │  ③ 客户端验证服务器证书                 │
  │  ④ 服务器验证客户端证书                 │
  │                                         │
  │  ⑤ 双方用协商的对称密钥加密后续通信     │
```

#### 证书类型

| 证书 | 用途 |
|------|------|
| **CA Root Certificate** | 自签根证书,签发 Server/Client 证书 |
| **Server Certificate** | Broker 端使用,客户端连接时验证 |
| **Client Certificate** | 客户端使用,Broker 端可选验证 |

### 6. 认证方式综合对比表

| 维度 | SASL/PLAIN | SASL/SCRAM | SASL/GSSAPI | mTLS |
|------|-----------|------------|-------------|------|
| 密码传输安全 | 否 | 是 | 是 | 是 |
| 部署复杂度 | 低 | 中 | 高 | 中 |
| 性能开销 | 低 | 中 | 中 | 高(握手慢) |
| 密码存储 | 明文 | 哈希+salt | KDC | 私钥 |
| 密码轮换 | 改 JAAS 重启 | kafka-configs 热改 | kadmin | 重发证书 |
| 与 LDAP 集成 | 否 | 否 | 是(经 AD) | 否 |
| 多租户隔离 | 一般 | 强 | 强 | 强 |
| **推荐使用** | 学习/测试 | **生产首选** | 已建 KDC | 高安全场景 |

## 三、配置 SASL/SCRAM 认证 (完整步骤)

### 1. 完整流程图

```
┌─────────────────────────────────────────────────────┐
│ Step 1: 在 Broker 创建 SCRAM 用户                     │
│ (kafka-configs.sh --create --alter --entity-type users)│
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 2: 配置 Server 端 JAAS 文件 (kafka_server_jaas)  │
│ 指定 ScramLoginModule                                │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 3: 配置 server.properties                        │
│  - listeners=SASL_SSL://...                          │
│  - security.inter.broker.protocol=SASL_SSL           │
│  - sasl.mechanism.inter.broker.protocol=SCRAM-SHA-256 │
│  - authorizer.class.name=ACLAuthorizer               │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 4: 配置 Client 端 JAAS / sasl config            │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 5: 启动并验证                                    │
│  kafkacat -b ... -X security.protocol=SASL_SSL ...   │
└─────────────────────────────────────────────────────┘
```

### 2. 创建 SCRAM 用户

SCRAM 凭证存储在 ZooKeeper 或 KRaft 元数据中 (`/__cluster_metadata/0/SCRAM` 路径下),由 Broker 提供 `kafka-configs.sh` 工具进行管理。

#### 创建用户 (首次)

```bash
# 在 Zookeeper 模式 (Kafka < 3.0)
bin/kafka-configs.sh --zookeeper zk1:2181,zk2:2181,zk3:2181 \
  --create --alter \
  --entity-type users \
  --entity-name alice \
  --add-config 'SCRAM-SHA-256=[password=alice-secret],SCRAM-SHA-512=[password=alice-secret]'

# 在 KRaft 模式 (Kafka >= 3.0, 推荐)
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --create --alter \
  --entity-type users \
  --entity-name alice \
  --add-config 'SCRAM-SHA-256=[password=alice-secret],SCRAM-SHA-512=[password=alice-secret]'
```

参数说明:

| 参数 | 含义 |
|------|------|
| `--entity-type users` | 操作的实体类型为 SCRAM 用户 |
| `--entity-name alice` | 用户名 |
| `--add-config` | 凭证配置,SCRAM-SHA-256 和 SCRAM-SHA-512 可同时设置 |
| `password=...` | 明文密码,Broker 内部计算哈希后存储 |

#### 修改密码 (热生效,无需重启)

```bash
# 修改 alice 的密码 (IT 同事交接后)
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --alter \
  --entity-type users \
  --entity-name alice \
  --add-config 'SCRAM-SHA-256=[password=new-alice-secret]'

# 同时修改 SHA-256 和 SHA-512
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --alter \
  --entity-type users \
  --entity-name alice \
  --add-config 'SCRAM-SHA-256=[password=new-secret],SCRAM-SHA-512=[password=new-secret]'
```

#### 删除用户

```bash
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --alter \
  --entity-type users \
  --entity-name alice \
  --delete-config 'SCRAM-SHA-512' \
  --delete-config 'SCRAM-SHA-256'

# 完整删除:同时删除两个 SCRAM 配置
```

#### 查看用户列表

```bash
# 列出所有 SCRAM 用户
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --describe --entity-type users

# 输出示例:
# Configs for user 'alice' are:
#   SCRAM-SHA-256=password=****,salt=...,stored_key=...,server_key=...
#   SCRAM-SHA-512=password=****,salt=...,stored_key=...,server_key=...
```

> **关键提示**:`password=****` 表示密码已隐藏,实际只存哈希值,这是 SCRAM 的安全基础。

### 3. 创建管理员用户

管理员用户用于超级用户 (`super.users`) 配置,绕过所有 ACL 检查。

```bash
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --create --alter \
  --entity-type users \
  --entity-name admin \
  --add-config 'SCRAM-SHA-512=[password=admin-super-secret]'
```

### 4. 配置 Server 端 JAAS 文件

路径:`config/kafka_server_jaas.conf`

```properties
# Kafka Broker JAAS 配置 (SCRAM-SHA-256 + SCRAM-SHA-512)
KafkaServer {
    org.apache.kafka.common.security.scram.ScramLoginModule required
    username="admin"
    password="admin-super-secret";
};
```

> 提示:Broker 自己也需 SCRAM 凭证,因为 `inter.broker.protocol` 可能也是 SASL_SSL。**Broker 间通信**用的用户名通常为 `admin` 或专门的 inter-broker 账号。

### 5. 配置 server.properties

```properties
# ============================================
# 监听器配置
# ============================================
# SASL_SSL 监听器:同时提供认证和加密
listeners=SASL_SSL://broker1:9092,CONTROLLER://broker1:9093
# 对外广告地址 (客户端连接用)
advertised.listeners=SASL_SSL://broker1:9092

# ============================================
# 安全协议映射 (用于 inter-broker、controller 等内部通信)
# ============================================
# Broker 间通信:也用 SASL_SSL
security.inter.broker.protocol=SASL_SSL
# Controller (KRaft) 间通信:SASL_SSL
controller.listener.names=CONTROLLER
listener.security.protocol.map=CONTROLLER:SASL_SSL,SASL_SSL:SASL_SSL

# ============================================
# SASL 配置
# ============================================
sasl.enabled.mechanisms=SCRAM-SHA-256,SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512
# Broker 间认证时使用的用户名(必须是 SCRAM 用户)
# 通过环境变量或外部配置注入

# ============================================
# SSL 配置
# ============================================
ssl.keystore.location=/var/private/ssl/broker.keystore.jks
ssl.keystore.password=keystore-password
ssl.key.password=key-password
ssl.truststore.location=/var/private/ssl/broker.truststore.jks
ssl.truststore.password=truststore-password
ssl.client.auth=required

# ============================================
# 授权 (ACL) 配置
# ============================================
authorizer.class.name=org.apache.kafka.security.authorizer.AclAuthorizer
allow.everyone.if.no.acl.found=false
super.users=User:admin;User:CN=ops-team,O=MyCompany

# ============================================
# ZooKeeper (ZK 模式) 自身安全 (可选)
# ============================================
# zookeeper.set.acl=true
```

### 6. 客户端连接配置

#### 方式一:JAAS 文件 (传统方式)

`config/kafka_client_jaas.conf`

```properties
KafkaClient {
    org.apache.kafka.common.security.scram.ScramLoginModule required
    username="alice"
    password="alice-secret";
};
```

#### 方式二:客户端属性 (推荐,无需 JAAS 文件)

```properties
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-256
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="alice" password="alice-secret";
ssl.truststore.location=/var/private/ssl/client.truststore.jks
ssl.truststore.password=truststore-password
```

#### 方式三:Java 代码

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092");
props.put(ProducerConfig.SECURITY_PROTOCOL_CONFIG, "SASL_SSL");
props.put("sasl.mechanism", "SCRAM-SHA-256");
props.put("sasl.jaas.config",
    "org.apache.kafka.common.security.scram.ScramLoginModule required "
  + "username=\"alice\" password=\"alice-secret\";");
props.put("ssl.truststore.location", "/var/private/ssl/client.truststore.jks");
props.put("ssl.truststore.password", "truststore-password");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

#### 方式四:kcat (kafkacat) 验证

```bash
# 列出所有 Topic
kcat -b broker1:9092 \
  -X security.protocol=SASL_SSL \
  -X sasl.mechanism=SCRAM-SHA-256 \
  -X sasl.username=alice \
  -X sasl.password=alice-secret \
  -X ssl.ca.location=/var/private/ssl/ca.pem \
  -L

# 消费消息
kcat -b broker1:9092 \
  -X security.protocol=SASL_SSL \
  -X sasl.mechanism=SCRAM-SHA-256 \
  -X sasl.username=alice \
  -X sasl.password=alice-secret \
  -X ssl.ca.location=/var/private/ssl/ca.pem \
  -t test-topic -c 0 -e
```

## 四、授权 Authorization

### 1. ACL 机制概述

Kafka 的授权通过 ACL (Access Control List) 实现,**默认拒绝所有访问** (`allow.everyone.if.no.acl.found=false`),必须显式授予权限。

#### 关键概念

| 概念 | 说明 |
|------|------|
| **Principal (主体)** | 被授权的对象,通常是 `User:alice`、`User:CN=...,O=...` |
| **Resource (资源)** | 被保护的对象:Topic、Group、Cluster、TransactionalId |
| **Operation (操作)** | 允许的动作:Read、Write、Create、Describe 等 |
| **Permission (权限)** | Principal × Resource × Operation 三元组 |
| **AclAuthorizer** | 默认的 ACL 授权器实现 |
| **__cluster_metadata** | ACL 持久化在 KRaft 内部 Topic 或 Zookeeper |

### 2. kafka-acls 命令详解

`kafka-acls.sh` 是 ACL 管理工具,语法结构:

```bash
kafka-acls.sh --bootstrap-server <brokers> \
  --operation <OP> \
  --topic <topic> \
  --group <group> \
  --cluster \
  --allow-principal <principal> \
  --deny-principal <principal>
```

#### 完整选项

| 选项 | 说明 |
|------|------|
| `--add` | 添加 ACL(默认) |
| `--remove` | 移除 ACL |
| `--list` | 列出所有 ACL |
| `--allow-principal User:alice` | 允许该 principal |
| `--deny-principal User:bob` | 拒绝该 principal |
| `--operation Read` | 操作类型 |
| `--topic test-topic` | 限定 Topic |
| `--topic '*'` | 所有 Topic |
| `--group test-group` | 消费组 |
| `--cluster` | Cluster 级操作 |
| `--resource-type transactional` | 事务 ID |

### 3. 资源类型 (Resource Types)

Kafka 4 类受 ACL 保护的资源:

| 资源类型 | 说明 | 示例 |
|----------|------|------|
| **Topic** | 最常用,控制对 Topic 的读写、创建、删除等 | `test-topic`、`*` |
| **Group** | Consumer Group,控制提交 offset 等 | `my-group`、`*` |
| **Cluster** | 集群级,如创建 Topic、查看 broker 列表等 | `kafka-cluster` |
| **TransactionalId** | 事务 ID,控制幂等生产者事务 | `my-tx-id`、`*` |

> **注意**:`kafka-acls.sh` 中 `--group` 选项对应 Group 资源类型,`--transactional-id` 对应 TransactionalId 资源类型。

### 4. 操作类型 (Operations)

Kafka 10+ 种操作,每个资源类型有不同操作:

#### Topic 级操作

| 操作 | 含义 | 触发场景 |
|------|------|----------|
| **Read** | 读消息 | 消费者消费 Topic |
| **Write** | 写消息 | 生产者发送消息 |
| **Create** | 创建 Topic | `kafka-topics --create` |
| **Delete** | 删除 Topic | `kafka-topics --delete` |
| **Alter** | 修改 Topic 配置 | `kafka-configs --alter` |
| **Describe** | 查看 Topic 元数据 | `kafka-topics --describe` |
| **DescribeConfigs** | 查看 Topic 配置 | `kafka-configs --describe` |
| **AlterConfigs** | 修改 Topic 配置 | `kafka-configs --alter` |
| **ClusterAction** | 集群动作,如 leader election | (较少用) |

#### Group 级操作

| 操作 | 含义 |
|------|------|
| **Read** | 读 offset 等 |
| **Describe** | 查看消费组 |
| **Delete** | 删除消费组(2.4+) |
| **CommitOffsets** | 提交 offset(隐式) |
| **Heartbeat** | 心跳(隐式) |

> 消费 Topic 时,通常需要 **Topic:Describe + Group:Read** 同时具备。

#### Cluster 级操作

| 操作 | 含义 |
|------|------|
| **Create** | 创建 Topic |
| **Alter** | 修改集群 |
| **Describe** | 查看集群元数据 |
| **ClusterAction** | 更新集群信息 |
| **DescribeConfigs** | 查看 broker 配置 |
| **AlterConfigs** | 修改 broker 配置 |
| **IdempotentWrite** | 幂等写入(事务前置) |

#### TransactionalId 操作

| 操作 | 含义 |
|------|------|
| **Describe** | 查看事务 ID |
| **Write** | 写入事务 |
| **Alter** | 修改事务 ID 关联(2.4+) |

### 5. ACL 模式策略

#### Allow vs Deny

```
权限规则按以下顺序应用:
1. Deny 规则 (优先级最高)
2. Allow 规则
3. 默认拒绝 (allow.everyone.if.no.acl.found=false)
```

#### 通配符

| 模式 | 说明 |
|------|------|
| `--topic '*'` | 匹配所有 Topic(注意 shell 引号) |
| `--topic 'test.*'` | 匹配以 test. 开头 |
| `--topic '*_topic'` | 匹配以 _topic 结尾 |
| `--group '*'` | 匹配所有消费组 |
| `User:*` | 匹配所有用户(慎用) |

## 五、ACL 配置实战

### 1. 给用户授予 Topic 读写权限

```bash
# 1) 给 alice 授予 test-topic 的读写权限
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:alice \
  --topic test-topic \
  --operation Read \
  --operation Write

# 2) 同时给消费组权限(消费消息必须)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:alice \
  --group test-group \
  --operation Read

# 3) 允许 alice 描述 Topic 元数据 (kcat -L 等命令需要)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:alice \
  --topic test-topic \
  --operation Describe

# 4) 允许 alice 描述消费组
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:alice \
  --group test-group \
  --operation Describe
```

### 2. 限制消费者消费特定 Topic

场景:bob 只能消费 `market-data-*` 这类 Topic,其他 Topic 一律拒绝。

```bash
# 1) 允许 bob 读 market-data-*
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:bob \
  --topic 'market-data-*' \
  --operation Read --operation Describe

# 2) 允许 bob 使用 market-group 消费组
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:bob \
  --group 'market-*' \
  --operation Read --operation Describe

# 由于默认拒绝,bob 无法访问其他 Topic
```

### 3. 给生产者授予 Topic 创建权限

```bash
# 允许 app-producer 在指定前缀下创建 Topic
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:app-producer \
  --topic 'app-events-*' \
  --operation Create \
  --operation Describe \
  --operation Write

# 同时需要 Cluster:Describe
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:app-producer \
  --cluster \
  --operation Describe
```

### 4. 启用事务的生产者

```bash
# 1) 给事务生产者授予 TransactionalId 权限
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:tx-producer \
  --transactional-id 'tx-app-1' \
  --operation Describe \
  --operation Write

# 2) 授予 Topic 的幂等写入(事务前置条件)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:tx-producer \
  --cluster \
  --operation IdempotentWrite
```

### 5. 跨 Topic 模式匹配

```bash
# 给 admin 授权所有 Topic 的所有操作 (慎用,运维账号除外)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:admin \
  --topic '*' \
  --operation All

# 给运维组授予所有 Group 操作
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:ops \
  --group '*' \
  --operation All

# 授予 Cluster 级 Describe (查 broker、Topic 列表)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:ops \
  --cluster \
  --operation Describe \
  --operation ClusterAction
```

### 6. 撤销 ACL 规则

```bash
# 撤销 alice 对 test-topic 的读权限
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --remove \
  --allow-principal User:alice \
  --topic test-topic \
  --operation Read

# 完全移除 alice 的所有权限 (按资源类型逐一删除)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --remove \
  --allow-principal User:alice \
  --topic '*' \
  --operation All

# 撤销 Cluster 权限
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --remove \
  --allow-principal User:alice \
  --cluster \
  --operation All
```

### 7. 拒绝显式 (Deny) 规则

Denylist 通常用于临时禁用某用户,但需要谨慎,因为 Deny 优先级高于 Allow。

```bash
# 拒绝 alice 对 finance-* 的所有访问 (即使有通配 Allow)
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --deny-principal User:alice \
  --topic 'finance-*' \
  --operation All
```

### 8. 查询 ACL 列表

```bash
# 列出所有 ACL
bin/kafka-acls.sh --bootstrap-server broker1:9092 --list

# 过滤某用户的规则
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --list --principal User:alice

# 过滤某 Topic 的规则
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --list --topic test-topic

# 输出格式:
# Current ACLs for resource `Resource(type=TOPIC, name='test-topic', patternType=LITERAL)`:
#   (principal=User:alice, operation=READ, permissionType=ALLOW)
#   (principal=User:alice, operation=WRITE, permissionType=ALLOW)
```

### 9. 基于 IP 的 ACL (Kafka 2.1+)

```bash
# 仅允许从 10.0.0.0/24 来的 alice
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --allow-principal User:alice \
  --allow-host 10.0.0.0/24 \
  --topic test-topic \
  --operation Read

# 仅拒绝某 IP
bin/kafka-acls.sh --bootstrap-server broker1:9092 \
  --add \
  --deny-principal User:alice \
  --deny-host 192.168.1.100 \
  --topic '*' \
  --operation All
```

> **注意**:`--allow-host`/`--deny-host` 需 Kafka 2.1+。

## 六、传输加密 SSL/TLS

### 1. SSL/TLS 工作流

```
1. TLS 握手
   ClientHello → ServerHello + Server Cert
   客户端验证服务器证书 (检查 CA 签发、域名、有效期)
   ServerHello Done

2. 密钥交换
   Client Key Exchange (RSA / DH / ECDHE)
   → 双方推导出对称会话密钥

3. 对称加密通信
   AES-256-GCM / ChaCha20-Poly1305 等加密应用数据
```

### 2. 生成证书

#### 完整 OpenSSL 脚本

```bash
#!/bin/bash
# gen-certs.sh
# 生成 Kafka 全套 SSL 证书 (Server + Client + CA)

set -e
CA_DIR=/var/private/ssl
DAYS=3650  # 10 年

mkdir -p $CA_DIR
cd $CA_DIR

# 1. 生成 CA 私钥与自签证书
openssl req -new -x509 -nodes \
  -keyout ca-key \
  -out ca-cert \
  -days $DAYS \
  -subj "/CN=Kafka-CA/O=MyCompany/C=CN"

# 2. 生成服务器 keystore (JKS)
keytool -genkey -noprompt \
  -alias broker \
  -keyalg RSA \
  -keysize 2048 \
  -validity $DAYS \
  -keystore kafka.server.keystore.jks \
  -storepass keystore-password \
  -keypass key-password \
  -dname "CN=broker.kafka,O=MyCompany"

# 3. 生成 CA 信任库
keytool -keystore kafka.server.truststore.jks \
  -alias CARoot \
  -import -noprompt \
  -file ca-cert \
  -storepass truststore-password

# 4. 导出服务器证书
keytool -keystore kafka.server.keystore.jks \
  -alias broker \
  -certreq -file cert-file \
  -storepass keystore-password

# 5. CA 签发服务器证书
openssl x509 -req -CA ca-cert -CAkey ca-key \
  -in cert-file -out cert-signed \
  -days $DAYS -CAcreateserial

# 6. 导入 CA 证书与签名证书到 keystore
keytool -keystore kafka.server.keystore.jks \
  -alias CARoot -import -noprompt -file ca-cert \
  -storepass keystore-password

keytool -keystore kafka.server.keystore.jks \
  -alias broker -import -file cert-signed \
  -storepass keystore-password

# 7. 同样为客户端生成 keystore
keytool -genkey -noprompt \
  -alias client \
  -keyalg RSA -keysize 2048 \
  -validity $DAYS \
  -keystore kafka.client.keystore.jks \
  -storepass keystore-password \
  -keypass key-password \
  -dname "CN=client,O=MyCompany"

keytool -keystore kafka.client.truststore.jks \
  -alias CARoot -import -noprompt -file ca-cert \
  -storepass truststore-password

keytool -keystore kafka.client.keystore.jks \
  -alias CARoot -import -noprompt -file ca-cert \
  -storepass keystore-password

keytool -keystore kafka.client.keystore.jks \
  -alias client -certreq -file client-cert-file \
  -storepass keystore-password

openssl x509 -req -CA ca-cert -CAkey ca-key \
  -in client-cert-file -out client-cert-signed \
  -days $DAYS -CAcreateserial

keytool -keystore kafka.client.keystore.jks \
  -alias client -import -file client-cert-signed \
  -storepass keystore-password

# 8. 清理临时文件
rm -f cert-file cert-signed client-cert-file client-cert-signed
ls -la $CA_DIR
```

#### 多 Broker SAN 证书

生产环境通常是多 Broker,客户端通过负载均衡器或 DNS 连接,需要 SAN (Subject Alternative Name) 证书:

```bash
# 1. 创建 openssl.cnf 指定 SAN
cat > openssl.cnf <<EOF
[req]
distinguished_name = req_distinguished_name
req_extensions = v3_req
prompt = no

[req_distinguished_name]
CN = kafka-cluster

[v3_req]
subjectAltName = @alt_names

[alt_names]
DNS.1 = kafka1.example.com
DNS.2 = kafka2.example.com
DNS.3 = kafka3.example.com
DNS.4 = kafka.example.com
IP.1  = 10.0.0.11
IP.2  = 10.0.0.12
IP.3  = 10.0.0.13
EOF

# 2. 用此配置生成证书请求
openssl req -new -key server.key -out server.csr -config openssl.cnf

# 3. CA 签发
openssl x509 -req -in server.csr -CA ca-cert -CAkey ca-key \
  -CAcreateserial -out server-cert.pem -days 3650 -extensions v3_req -extfile openssl.cnf
```

### 3. Broker 启用 SSL

#### server.properties SSL 配置

```properties
# 启用 SSL 端点
listeners=SSL://broker1:9092

# Keystore (服务器证书 + 私钥)
ssl.keystore.location=/var/private/ssl/kafka.server.keystore.jks
ssl.keystore.password=keystore-password
ssl.key.password=key-password

# Truststore (CA 证书)
ssl.truststore.location=/var/private/ssl/kafka.server.truststore.jks
ssl.truststore.password=truststore-password

# 客户端认证:required 表示双向认证, requested 表示可选
ssl.client.auth=required

# 启用的协议与算法
ssl.enabled.protocols=TLSv1.2,TLSv1.3
ssl.protocol=TLSv1.3
ssl.cipher.suites=TLS_AES_256_GCM_SHA384,TLS_AES_128_GCM_SHA256
```

#### 协议与算法推荐

| 版本 | 推荐协议 | 推荐算法 |
|------|----------|----------|
| Kafka < 2.5 | TLSv1.2 | ECDHE-RSA-AES256-GCM-SHA384 |
| Kafka >= 2.5 | TLSv1.3 | TLS_AES_256_GCM_SHA384 |
| 高安全 | TLSv1.3 + 国家商用密码 SM2/SM4 | 国密改造 |

### 4. 客户端 SSL 连接

```properties
security.protocol=SSL
ssl.truststore.location=/var/private/ssl/kafka.client.truststore.jks
ssl.truststore.password=truststore-password
# 仅双向认证需要
ssl.keystore.location=/var/private/ssl/kafka.client.keystore.jks
ssl.keystore.password=keystore-password
ssl.key.password=key-password
```

#### 客户端 SSL 验证命令

```bash
# 1. 用 openssl 验证 SSL 握手
openssl s_client -connect broker1:9092 -showcerts < /dev/null

# 2. 用 kcat 验证
kcat -b broker1:9092 \
  -X security.protocol=SSL \
  -X ssl.ca.location=/var/private/ssl/ca-cert \
  -L
```

### 5. SSL 性能影响

| 指标 | 影响 | 说明 |
|------|------|------|
| **握手延迟** | +50-200ms (首连接) | TLS 握手涉及密钥交换 |
| **吞吐** | -10% ~ -30% (TLSv1.2)<br>-5% ~ -15% (TLSv1.3) | CPU 加解密开销 |
| **CPU 使用** | +1-2 核 | AES-NI 可显著降低 |
| **会话复用** | 0 额外开销 | SSL session resumption 避免重复握手 |

#### 性能优化建议

```properties
# 启用会话复用
ssl.session.timeout.ms=180000

# 启用 OCSP Stapling (Kafka 2.4+)
ssl.ocsp stapling.response.timeout.ms=5000

# 启用 AES-NI 硬件加速 (需要 CPU 支持)
# 默认 Kafka 自动使用

# 调整网络线程
num.network.threads=8
```

## 七、KRaft 模式下的安全 (Kafka 3.x)

### 1. KRaft 与 Zookeeper 模式的安全差异

| 维度 | Zookeeper 模式 | KRaft 模式 |
|------|----------------|------------|
| ACL 存储位置 | `/kafka-acls` znodes | `__cluster_metadata` 内部 Topic |
| SCRAM 存储 | `/config/users` znodes | `__cluster_metadata` 内部 Topic |
| Controller 通信 | 通过 ZK 间接 | 直接通过 Controller 监听器 |
| ZooKeeper 安全 | 需额外保护 ZK | 无需 ZK |
| Broker 元数据同步 | 通过 ZK 同步 | 通过 KRaft 共识协议 |

### 2. KRaft 监听器配置

KRaft 模式中,需要单独配置 **Controller 监听器**,并指定其安全协议:

```properties
# ============================================
# KRaft 监听器配置
# ============================================

# 所有监听器:对外客户端 + Controller 内部
listeners=PLAINTEXT://broker1:9092,CONTROLLER://broker1:9093

# Controller 监听器名称映射 (KRaft 特有)
# Controller 通信也需要安全
controller.listener.names=CONTROLLER
listener.security.protocol.map=CONTROLLER:SASL_SSL,PLAINTEXT:PLAINTEXT,SASL_SSL:SASL_SSL

# 客户端连接地址
advertised.listeners=PLAINTEXT://broker1:9092

# KRaft 角色
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@broker1:9093,2@broker2:9093,3@broker3:9093

# Controller 之间也用 SASL_SSL
security.inter.broker.protocol=SASL_SSL
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512
```

### 3. Controller 与 Broker 间的认证

#### Controller 监听器配置 (KRaft 安全)

```properties
# =====================
# Controller 监听器:独立 SASL_SSL 端口
# =====================
listeners=CONTROLLER://:9093,SASL_SSL://:9092

# Controller 监听器对应的安全协议
listener.security.protocol.map=CONTROLLER:SASL_SSL,SASL_SSL:SASL_SSL,PLAINTEXT:PLAINTEXT

# Controller 监听器对应 SASL 机制
# (3.3+ 可独立配置,旧版本继承 broker 端)
controller.sasl.enable=true
controller.sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512

# 客户端连接端口仍为 9092
advertised.listeners=SASL_SSL://broker1:9092
```

#### 验证 Controller 安全连接

```bash
# 查看 Controller 端口监听
ss -tlnp | grep 9093

# 测试 Controller 间连接 (kafka-metadata-quorum 工具)
bin/kafka-metadata-quorum.sh --bootstrap-server broker1:9092 \
  --command-status

# 输出应包含 cluster_id 和 voter 信息
```

### 4. KRaft 集群初始化 (带安全)

```bash
# 1. 格式化存储目录
bin/kafka-storage.sh format \
  -t $(bin/kafka-storage.sh random-uuid) \
  -c config/kraft/server.properties

# 2. 启动 (Broker+Controller 同进程)
bin/kafka-server-start.sh -daemon config/kraft/server.properties
```

### 5. KRaft 模式下创建 SCRAM 用户

KRaft 模式下 SCRAM 用户直接在 `__cluster_metadata` Topic 中,使用与 ZK 模式相同的命令:

```bash
# 创建用户 (与 ZK 模式命令相同)
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --create --alter --entity-type users --entity-name alice \
  --add-config 'SCRAM-SHA-512=[password=alice-secret]'

# 修改密码 (热生效)
bin/kafka-configs.sh --bootstrap-server broker1:9092 \
  --alter --entity-type users --entity-name alice \
  --add-config 'SCRAM-SHA-512=[password=new-secret]'
```

## 八、安全最佳实践

### 1. 最小权限原则

```
原则:每个用户只应拥有完成业务所必需的最小权限集合。

反例 (避免):
  --allow-principal User:app --topic '*' --operation All
  (一个应用账号通配所有 Topic 的所有操作)

正例 (推荐):
  --allow-principal User:app-producer \
    --topic 'order-events' \
    --operation Write --operation Describe
  --allow-principal User:app-producer \
    --cluster --operation Describe
  --allow-principal User:app-producer \
    --transactional-id 'tx-app-1' --operation Write --operation Describe
```

### 2. 账号分类管理

| 账号类别 | 示例 | 权限范围 |
|----------|------|----------|
| **超级管理员** | admin | 所有权限 (仅 1-2 个) |
| **运维账号** | ops, monitor | Cluster 全部、Topic Describe |
| **应用账号** | order-app, payment-app | 仅自有 Topic 读写 |
| **消费账号** | analytics, etl | 仅消费自有 Topic |
| **审计账号** | audit, compliance | 仅 Describe,用于审计 |
| **开发账号** | dev, qa | 仅测试环境 Topic |

### 3. 定期更换密码

```bash
# 每 90 天轮换密码脚本示例
#!/bin/bash
# rotate-scram.sh
USERS="alice bob app-producer app-consumer"
NEW_PASSWORD=$(openssl rand -base64 16)

for USER in $USERS; do
  /opt/kafka/bin/kafka-configs.sh --bootstrap-server broker1:9092 \
    --alter --entity-type users --entity-name $USER \
```

### 4. 网络隔离

```
生产 Kafka 集群应部署在内网,多层防火墙:

Internet
  │
  └── Application Load Balancer (公网入口,可选)
        │
        └── DMZ (Web/Edge 服务)
              │
              └── Internal Network (10.0.0.0/8)
                    │
                    ├── Kafka Brokers (10.10.0.0/24)
                    │     - 仅允许内网访问 9092
                    │     - 防火墙: iptables / security group
                    │
                    └── Application Servers (10.20.0.0/16)
                          - 只能访问 Kafka Brokers
```

**端口最小开放原则**:

| 端口 | 谁需要 | 防火墙策略 |
|------|--------|-----------|
| 9092 (SASL_SSL) | 客户端应用 | 仅允许 App Server 网段 |
| 9093 (Controller) | 仅 Broker 之间 | 仅允许 Broker 子网 |
| 2181 (ZK,若用) | 仅 Broker 之间 | 仅允许 Broker 子网 |
| 22 (SSH) | 运维 | 仅允许堡垒机 |

```bash
  -storepass $PASSWORD -alias broker 2>/dev/null \
```

### 1. LDAP 集成

Kafka 自身不直接支持 LDAP,但可通过以下方式集成:

#### 方式一:同步 LDAP 用户到 SCRAM

```bash
#!/bin/bash
# sync-ldap-to-kafka.sh
# 从 LDAP 同步用户到 Kafka SCRAM
LDAP_HOST="ldap.example.com"
LDAP_BASE="ou=users,dc=example,dc=com"

# 1. 列出 LDAP 用户
USERS=$(ldapsearch -x -H ldap://$LDAP_HOST -b $LDAP_BASE "(objectClass=person)" uid)

# 2. 为每个用户创建 SCRAM 凭证
for USER in $(echo "$USERS" | grep "^uid:" | awk '{print $2}'); do
  PASSWORD=$(ldapsearch -x ... "(uid=$USER)" userPassword)
  bin/kafka-configs.sh --bootstrap-server broker1:9092 \
    --create --alter --entity-type users --entity-name $USER \
    --add-config "SCRAM-SHA-512=[password=$PASSWORD]"
done
```

### 2. OAuth 2.0 (Kafka 2.4+)

通过 SASL/OAUTHBEARER 机制,客户端向 OAuth 2.0 服务器申请 token,Kafka Broker 验证 token。

#### 工作流程

```
Kafka Client                                    Kafka Broker       OAuth Server
  │                                                  │
  │  ① POST /oauth/token (client_credentials)         │
  │ ──────────────────────────────────────────────── │ → OAuth Server
  │                                                  │   (验证 client_id/client_secret)
  │  返回 access_token (JWT)                         │
  │ <──────────────────────────────────────────────── │
  │                                                  │
  │  ② SASL/OAUTHBEARER 携带 token 连接               │
  │ ──────────────────────────────────────────────> │
  │                                                  │ ③ 验证 token
  │                                                  │   - 签名验证
  │                                                  │   - 检查过期
  │                                                  │   - 提取 principal
  │                                                  │
  │  ④ 认证成功,授权请求                            │
  │ <──────────────────────────────────────────────  │
```

```bash
# deploy-kafka-security.sh
# 部署前检查与初始化

set -e

BROKER=broker1:9092
ADMIN_USER="admin"
ADMIN_PASSWORD="${KAFKA_ADMIN_PASSWORD}"

# 3. 等待 SCRAM 凭证生效
sleep 10

# 4. 创建业务用户
for USER in app-producer app-consumer etl-consumer; do
  PASSWORD=$(openssl rand -base64 16)
  /opt/kafka/bin/kafka-configs.sh --bootstrap-server $BROKER \
    --create --alter --entity-type users --entity-name $USER \
    --add-config "SCRAM-SHA-512=[password=$PASSWORD]"

done

# 5. 创建 Topic 并授权
for TOPIC in order-events user-events audit-log; do
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server $BROKER \
    --create --topic $TOPIC --partitions 3 --replication-factor 3 \
    --config min.insync.replicas=2 || true

/opt/kafka/bin/kafka-acls.sh --bootstrap-server $BROKER \
  --add --allow-principal User:app-producer \

  --add --allow-principal User:app-consumer \
  --topic order-events --group app-consumer-group \
  --operation Read --operation Describe

/opt/kafka/bin/kafka-acls.sh --bootstrap-server $BROKER \
  --add --allow-principal User:etl-consumer \
  --topic '*' --operation Read --operation Describe
```

## 核心要点速记

### 1. 安全三层架构

```
加密传输 (SSL/TLS)
   ↓
身份认证 (SASL/SCRAM 推荐)
   ↓
权限授权 (ACL 默认拒绝,按需放行)
```

### 2. 认证方式选择

- **学习/测试**:SASL/PLAIN
- **生产首选**:SASL/SCRAM (SCRAM-SHA-512)
- **已有 KDC**:SASL/GSSAPI (Kerberos)
- **云原生**:SASL/OAUTHBEARER
- **金融高安全**:SSL 双向认证 (mTLS)

### 3. SCRAM 凭证管理命令

```bash
# 创建: --create --alter
# 修改: --alter (热生效)
# 删除: --alter --delete-config 'SCRAM-SHA-256' --delete-config 'SCRAM-SHA-512'
# 查看: --describe --entity-type users
```

### 4. ACL 命令模板

```bash
# 读
kafka-acls.sh --add --allow-principal User:alice \
  --topic test --operation Read

# 写
kafka-acls.sh --add --allow-principal User:alice \
  --topic test --operation Write

# 消费必备组合
kafka-acls.sh --add --allow-principal User:alice \
  --topic test --operation Read --operation Describe
kafka-acls.sh --add --allow-principal User:alice \
  --group grp --operation Read

# 事务前置
kafka-acls.sh --add --allow-principal User:alice \
  --cluster --operation IdempotentWrite
```

### 5. 资源类型

- **Topic**:Read/Write/Create/Delete/Alter/Describe
- **Group**:Read/Describe/Delete
- **Cluster**:Create/Alter/Describe/ClusterAction/IdempotentWrite
- **TransactionalId**:Describe/Write

### 6. KRaft 安全要点

- `process.roles=broker,controller`
- `controller.listener.names=CONTROLLER`
- `listener.security.protocol.map=CONTROLLER:SASL_SSL`
- `security.inter.broker.protocol=SASL_SSL`
- SCRAM 与 ACL 存储在 `__cluster_metadata` 内部 Topic

### 7. SSL 配置要点

```
服务端:
  ssl.keystore.location / password
  ssl.truststore.location / password
  ssl.client.auth=required
  ssl.enabled.protocols=TLSv1.3,TLSv1.2

客户端:
  ssl.truststore.location / password
  (双向认证时) ssl.keystore.location / password
```

### 8. 性能与安全平衡

| 安全特性 | 性能开销 | 缓解措施 |
|----------|----------|----------|
| SSL/TLS | -10%~30% | 启用 TLS 1.3、AES-NI、SSL session resumption |
| SASL/SCRAM | -3%~5% | SCRAM-SHA-256 (SHA-512 略慢) |
| ACL | -2%~5% | 减少 ACL 规则数量,使用前缀匹配 |
| 加密数据本身 | 应用层处理 | 客户端加密敏感字段 |

### 9. 关键安全配置

```properties
# 必须配置
authorizer.class.name=org.apache.kafka.security.authorizer.AclAuthorizer
allow.everyone.if.no.acl.found=false
super.users=User:admin

# 监听器
listeners=SASL_SSL://broker:9092
security.inter.broker.protocol=SASL_SSL

# SASL
sasl.enabled.mechanisms=SCRAM-SHA-256,SCRAM-SHA-512

# SSL
ssl.client.auth=required
ssl.endpoint.identification.algorithm=HTTPS
```

### 10. 应急响应命令速查

```bash
# 锁定用户 (改密码)
kafka-configs.sh --bootstrap-server b:9092 --alter \
  --entity-type users --entity-name alice \
  --add-config 'SCRAM-SHA-512=[password=disabled]'

# 撤销某用户所有权限
for OP in Read Write Create Delete Alter Describe; do
  kafka-acls.sh --bootstrap-server b:9092 --remove \
    --allow-principal User:alice --topic '*' --operation $OP
done

# 撤销 Cluster 权限
kafka-acls.sh --bootstrap-server b:9092 --remove \
  --allow-principal User:alice --cluster --operation All
```

### 11. 常见陷阱

- **忘配 `super.users`** 导致自己也被 ACL 拒绝
- **JAAS 文件密码明文** → 用环境变量或 KMS 注入
- **证书过期未监控** → 提前 30 天告警
- **未启用 SSL 时用 SASL/PLAIN** → 明文密码泄露
- **`allow.everyone.if.no.acl.found=true`** → 等于无 ACL
- **应用账号授予 `Cluster:All`** → 可删除任意 Topic
- **消费 Topic 缺 `Group:Read`** → 提交 offset 失败
- **生产端缺 `Cluster:IdempotentWrite`** → 幂等失效

### 12. 安全最佳实践一句话总结

**KRaft + SASL_SSL + SASL/SCRAM-SHA-512 + mTLS + ACL + 最小权限 + 定期轮换 + 全面审计 = 生产级 Kafka 安全**。
