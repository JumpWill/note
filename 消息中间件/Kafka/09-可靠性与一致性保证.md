# Kafka 可靠性与一致性保证 (Reliability & Consistency Guarantee)

> 本章系统讲解 Kafka 在消息可靠性、一致性方面的完整能力体系：消息可靠性的三大问题（丢、重复、乱序）、三种消息传递语义（At most once / At least once / Exactly once）的取舍与实现方式、幂等性 Producer 的 PID + Sequence Number 机制、事务型 Producer 的 API 体系与隔离级别、Kafka Streams 的 EOS 流处理保证、消费者侧 Exactly Once 的手动提交与业务幂等、端到端 EOS 架构设计，以及金融交易与电商订单两大实战案例。理解可靠性与一致性是构建 0 丢失、可重放金融级消息系统的基石。

## 一、消息可靠性问题概述

### 1. 消息系统的三大可靠性问题

消息中间件在分布式环境下运行时，理论上可能遭遇的可靠性问题分为三大类。任何可靠性方案的设计，都是围绕解决这些问题展开。

```text
┌───────────────────────────────────────────────────────────────┐
│                消息系统三大可靠性问题                            │
├──────────────┬────────────────────────────────────────────────┤
│  1. 消息丢失  │ Loss    → 消息发出后,接收方从未看到            │
│              │ 影响:数据丢失,业务中断                            │
├──────────────┼────────────────────────────────────────────────┤
│  2. 消息重复  │ Duplicate → 同一条消息被消费多次                  │
│              │ 影响:重复扣款、重复发货、资金错误                  │
├──────────────┼────────────────────────────────────────────────┤
│  3. 消息乱序  │ Disorder  → 消息到达顺序与生产顺序不一致          │
│              │ 影响:状态机错乱、时序依赖业务出错                  │
└──────────────┴────────────────────────────────────────────────┘
```

### 2. Kafka 中三大问题的具体场景

| 问题类型 | Producer 侧 | Broker 侧 | Consumer 侧 |
|----------|-------------|-----------|-------------|
| **消息丢失** | 网络抖动导致 ack 超时未重发 | leader 宕机,follower 未同步完成 | 消费后未提交 offset,重启重读 |
| **消息重复** | 重试机制导致消息重发 | min.insync.replicas 配置过松 | 提交 offset 前宕机,重启重复消费 |
| **消息乱序** | 多分区并行发送,max.in.flight 限制 | 分区副本切换 | 多线程消费、rebalance 触发 |

### 3. Kafka 可靠性保证的三大支柱

Kafka 通过三个维度的协作保证消息可靠性,任何一环出现缺口,整体可靠性都会崩溃。

```text
┌────────────────────────────────────────────────────────────────┐
│                Kafka 可靠性保证的三大支柱                        │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   Producer 端          Broker 端            Consumer 端         │
│   ┌──────────┐        ┌──────────┐         ┌──────────┐        │
│   │ acks=all │        │副本机制   │         │手动提交   │        │
│   │幂等性    │        │ISR 集合   │         │offset    │        │
│   │事务      │        │HW/LEO    │         │业务幂等   │        │
│   └──────────┘        └──────────┘         └──────────┘        │
│         │                    │                     │           │
│         └──────── 一致性协议(共识) ───────────────┘            │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

## 二、三种消息传递语义

### 1. 三大语义定义

消息系统领域定义了三种语义,用于描述消息从 Producer 到 Consumer 的传递保证强度。三者在「丢」「重」两个维度上做权衡,无法同时消除两者。

| 语义 | 英文 | 丢消息 | 重消息 | 性能 | 典型场景 |
|------|------|--------|--------|------|----------|
| **最多一次** | At most once | 可能 | 不可能 | 最高 | 日志采集、监控埋点 |
| **至少一次** | At least once | 不可能 | 可能 | 中 | 业务通知、订单流转 |
| **精确一次** | Exactly once | 不可能 | 不可能 | 最低 | 金融交易、资金扣减 |

### 2. 三种语义对比图

```text
┌────────────────────────────────────────────────────────────────┐
│              三种消息传递语义的权衡三角                          │
│                                                                │
│                       性能                                     │
│                       ▲                                        │
│                      /│\                                       │
│                     / │ \                                      │
│                    /  │  \                                     │
│                   /   │   \                                    │
│                  /    │    \                                   │
│                 /  At most  \                                  │
│                /    once     \                                 │
│               /   (不丢不能)  \                                │
│              /                \                                │
│             /  ──────────────  \                               │
│            /   │             │   \                             │
│           /    │  At least   │    \                            │
│          /     │   once      │     \                           │
│         /      │  (不丢可能重)│      \                          │
│        /       │             │       \                         │
│       ◀────────┼─────────────┼────────▶                       │
│   允许丢失     │ Exactly once│     允许重复                    │
│               │ (不丢不重)   │                                │
│               └─────────────┘                                 │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 3. 三大语义的数学表述

设 `P(x)` 表示消息 `x` 被投递到 Consumer 的次数,`N(x)` 表示该消息理论应投递次数。

- **At most once**: `P(x) ≤ N(x)` —— 可能丢,但绝不重
- **At least once**: `P(x) ≥ N(x)` —— 绝不丢,但可能重
- **Exactly once**: `P(x) = N(x)` —— 既不丢也不重

> **本质结论**:在分布式系统中,**Exactly once 严格意义上不可能**。业界所说的 EOS 是指「**有效一次**」,即业务语义层面不丢不重(允许底层重传但通过幂等去重)。

### 4. 三种语义与 Kafka 默认行为

| 语义 | Producer 默认配置 | Consumer 默认配置 | Kafka 是否原生支持 |
|------|-------------------|-------------------|-------------------|
| At most once | acks=0、不重试 | auto.offset.reset=latest,先 commit 再处理 | 支持(需手动配置) |
| At least once | acks=all、重试 | 先处理再 commit | 支持(Kafka 默认) |
| Exactly once | enable.idempotence=true + 事务 | 手动提交 + 业务幂等 | 支持(0.11+) |

## 三、At most once 实现

### 1. 核心思想

**At most once(最多一次)** 的核心是 **优先放弃,不让重试**。任何可能引起重发的环节都要关闭,确保消息最多到达一次,适用于可容忍丢失但不能容忍重复的场景,如日志、监控。

### 2. Producer 实现方式

```java
// ponytail: At most once 的 producer 配置 —— 关闭一切可能引起重传的参数
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("acks", "0");                    // 不等 broker 确认,fire-and-forget
props.put("retries", 0);                   // 失败不重试
props.put("max.in.flight.requests.per.connection", "1"); // 避免乱序重试
props.put("enable.idempotence", "false"); // 关闭幂等

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// 发送顺序:先发送,再考虑业务提交
producer.send(new ProducerRecord<>("topic", "key", "value"));
// 不关心发送结果,即使失败也丢弃
```

### 3. Consumer 实现方式

```java
// ponytail: At most once 的 consumer —— 先提交 offset,再处理消息
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "at-most-once-group");
props.put("enable.auto.commit", "false");      // 关闭自动提交
props.put("auto.offset.reset", "latest");      // 从最新位置开始

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Arrays.asList("topic"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        // ⚠️ 先提交 offset,再处理 —— 失败也不会重读
        consumer.commitSync();
        try {
            handleRecord(record);
        } catch (Exception e) {
            log.error("处理失败,直接丢弃:{}", e.getMessage());
            // 不抛异常,不重试
        }
    }
}
```

### 4. At most once 的故障路径

```text
┌──────────────────────────────────────────────────────────────────┐
│              At most once 故障路径分析                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Producer                                                       │
│  ├── 网络抖动 → 消息丢失(无重试)              → 丢 ✗              │
│  ├── Broker 宕机 → 消息丢失                  → 丢 ✗              │
│  └── Broker 收到但应答丢失 → 消息可能重复      → 重 ✗              │
│                                                                  │
│  Consumer                                                        │
│  ├── 提交 offset 后宕机 → 已处理消息丢失      → 丢 ✗              │
│  └── 处理失败抛异常 → 消息直接丢弃             → 丢 ✗              │
│                                                                  │
│  结论:宁可丢,绝不重                                              │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 5. 适用场景

- **应用日志采集**:丢一两条日志影响有限
- **监控指标上报**:重复反而会污染统计
- **UV 统计**:轻微丢失可接受
- **调试信息传输**:偶尔丢失不致命

## 四、At least once 实现

### 1. 核心思想

**At least once(至少一次)** 的核心是 **绝不丢失,允许重复**。一切可能引起丢消息的环节都要加强,通过重试机制确保消息至少被送达一次。绝大多数业务场景采用此语义。

### 2. Producer 实现方式

```java
// ponytail: At least once 的 producer 配置 —— 强化可靠性,允许重复
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("acks", "all");                    // 等待所有 ISR 副本确认
props.put("retries", Integer.MAX_VALUE);     // 无限重试
props.put("max.in.flight.requests.per.connection", "5");
props.put("delivery.timeout.ms", "300000");  // 投递总超时 5 分钟
props.put("enable.idempotence", "false");    // 此处关闭幂等,允许业务去重

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// 同步发送,失败重试直至成功
for (Message msg : messages) {
    try {
        producer.send(new ProducerRecord<>("topic", msg.getKey(), msg.getValue()))
                .get(10, TimeUnit.SECONDS); // 同步阻塞,等结果
    } catch (Exception e) {
        // 重试失败,业务侧决定是否持久化到本地重发队列
        retryQueue.put(msg);
    }
}
```

### 3. Consumer 实现方式

```java
// ponytail: At least once 的 consumer —— 先处理,再提交 offset
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "at-least-once-group");
props.put("enable.auto.commit", "false"); // 必须手动提交

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Arrays.asList("topic"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        try {
            // ✅ 先处理业务逻辑
            handleRecord(record);
            // ✅ 处理成功后再提交 offset
            // 注意:此处仍存在「处理成功但提交失败」的极小窗口,导致重复
        } catch (Exception e) {
            log.error("处理失败,不提交 offset,下次重试", e);
            // 不提交,下次 poll 会重新消费该消息
            break;
        }
    }
    // 批量提交,提升吞吐
    consumer.commitSync();
}
```

### 4. At least once 的故障路径

```text
┌──────────────────────────────────────────────────────────────────┐
│              At least once 故障路径分析                          │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Producer                                                       │
│  ├── 发送失败 → 重试 → 至少到达一次            → 不丢 ✓           │
│  ├── Broker 收到但应答丢失 → 重试 → 消息重复    → 重 ✗             │
│  └── acks=all + 重试 → 极少数重复可业务去重    → 弱影响           │
│                                                                  │
│  Consumer                                                        │
│  ├── 处理成功提交前宕机 → 重启重复消费         → 重 ✗             │
│  ├── 业务处理失败 → 不提交 → 下次重试          → 不丢 ✓           │
│  └── offset 提交失败 → 下次重复消费            → 重 ✗             │
│                                                                  │
│  结论:绝不丢,可能重,通过业务幂等消化重复                        │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 5. 适用场景

- **订单创建通知**:可重复处理(业务侧有订单号去重)
- **用户行为埋点**:轻微重复不影响业务
- **邮件短信发送**:有外部幂等或人工兜底
- **大多数业务通知场景**

## 五、Exactly once 三大难点

### 1. 为什么分布式 Exactly Once 难

在分布式系统中,要实现严格意义的 Exactly Once 必须解决 **生产、传输、消费** 三个环节中的不确定性,任意环节都可能因网络分区、节点宕机、消息重发引入「重复」或「丢失」。

```text
┌──────────────────────────────────────────────────────────────────┐
│              Exactly Once 三大难点                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Producer                Broker              Consumer           │
│   ┌──────────┐           ┌──────────┐        ┌──────────┐        │
│   │生产不重复 │           │存储不丢失 │        │消费不重复 │        │
│   │   ↓      │  网络可能  │   ↓      │  网络可能│   ↓      │        │
│   │  重试去重 │ ←──重发──→ │副本同步   │ ←─重投──→│ 幂等消费 │        │
│   └──────────┘           └──────────┘        └──────────┘        │
│                                                                  │
│   难点:                                                           │
│   1. 网络不可靠 → 必须重试 → 引入重复                             │
│   2. 节点可能宕机 → 必须持久化 → 可能恢复时重复                   │
│   3. 顺序不可保 → 多分区并行 → 引入并发重复                       │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 三大难点的逐一剖析

#### 难点一:生产不重复

Producer 端为保证可靠性而重试,但重试过程中第一次请求实际已经成功,仅 ack 丢失,导致 Broker 收到重复消息。

```text
Producer                  Broker
   │ ──── send(msg1) ──────► │  ← 第一次,写入成功
   │                          │
   │ ◄─── (ack 丢失) ──────── │
   │                          │
   │ ──── send(msg1) 重试 ──► │  ← 第二次,产生重复
```

#### 难点二:消费不重复

Consumer 处理消息后,在提交 offset 之前崩溃,重启后从上次 offset 重新消费,导致已处理的消息被再次处理。

```text
Consumer                  Kafka
   │ 消费 msg1,offset=100  │
   │ ──── handle(msg1) ──── │  ← 处理成功
   │                          │
   │ 提交 offset 前崩溃       │
   │                          │
   │ 重启,offset 仍为 99      │
   │ ──── handle(msg1) ──── │  ← 重复处理
```

#### 难点三:处理不重复

即使消费成功,业务侧的写库、调用下游等副作用如果不可幂等,会产生重复效果。即使 Kafka 层面保证 Exactly Once,业务语义仍可能重复。

```text
Consumer                   DB
   │ 收到 msg1 (扣款请求)    │
   │ ──── UPDATE 余额 ─────► │  ← 第一次扣款
   │                          │
   │ 重启,重复消费 msg1       │
   │ ──── UPDATE 余额 ─────► │  ← 重复扣款!
```

## 六、Exactly once 实现方案

### 1. 三大方案对比

Kafka 0.11+ 引入了完整的 Exactly Once 语义支持,通过 **幂等性、事务、业务幂等** 三大支柱协同实现。

| 方案 | 解决问题 | 实现机制 | 限制 |
|------|----------|----------|------|
| **幂等性 Producer** | 生产不重复 | PID + Sequence Number 去重 | 仅单分区、单会话 |
| **事务型 Producer** | 生产不重复 + 跨分区原子写 | 事务协调者 + 二阶段提交 | 跨分区原子性,性能开销 |
| **幂等 + 事务** | 端到端 EOS | 幂等作基础 + 事务跨分区原子 + offset 与业务原子提交 | Kafka Streams / Consumer-rebalance 场景受限 |
| **业务幂等** | 处理不重复 | 业务层去重表 / 唯一索引 | 需业务配合,与 Kafka 无关 |

### 2. 三方案协同关系

```text
┌──────────────────────────────────────────────────────────────────┐
│              EOS 三方案协同金字塔                                 │
│                                                                  │
│                          ▲                                       │
│                         ╱ ╲                                      │
│                        ╱   ╲                                     │
│                       ╱ 端  ╲                                    │
│                      ╱  到  ╲                                    │
│                     ╱  端   ╲                                   │
│                    ╱   EOS   ╲                                   │
│                   ╱(幂等+事务) ╲                                  │
│                  ╱             ╲                                  │
│                 ╱───────────────╲                                │
│                ╱   幂等 + 业务幂等  ╲                              │
│               ╱                   ╲                              │
│              ╱   幂等性 Producer    ╲                            │
│             ╱   (生产层去重基础)     ╲                            │
│            ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔                               │
│                                                                  │
│   越往上,覆盖范围越广,实现复杂度越高                              │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 3. 方案选型决策树

```text
你的业务是否允许重复?
│
├── 否 → 你需要 Exactly Once
│         │
│         ├── 仅单分区 + 单会话? → 启用幂等性 Producer
│         │
│         ├── 跨分区/跨主题原子写? → 启用事务型 Producer
│         │
│         ├── Kafka Streams 流处理? → 启用幂等 + 事务(EOS)
│         │
│         └── Consumer-rebalance 场景? → 幂等 + 事务 + 业务幂等
│
└── 是 → 你只需要 At Least Once + 业务幂等即可
```

## 七、幂等性 Producer 详解

### 1. 核心原理

幂等性 Producer 的核心是 **PID(Producer ID) + Sequence Number** 二元组去重。每个 Producer 实例启动时获取唯一 PID,每条消息携带单调递增的 Sequence Number,Broker 端按 `(PID, 分区)` 缓存最近序列号,重复消息直接丢弃。

```text
┌──────────────────────────────────────────────────────────────────┐
│              幂等性 Producer 工作原理                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Producer                                Broker                │
│   ┌─────────────────┐                     ┌─────────────────┐    │
│   │ PID = 12345     │                     │ 缓存映射表:      │    │
│   │ (启动时分配)     │                     │ (PID, 分区) → seq │    │
│   ├─────────────────┤                     ├─────────────────┤    │
│   │ seq=0 msg1 ─────────────► 写入 ──→    │ (12345, p0)=0  │    │
│   │ seq=1 msg2 ─────────────► 写入 ──→    │ (12345, p0)=1  │    │
│   │ seq=2 msg3 ─────────────► 重试 ──→    │ 检测 seq=2 > 1  │    │
│   │   (重发)         │           重复!     │ 写入,更新=2    │    │
│   │ seq=2 msg3 ─────────────► 写入 ──→    │ 检测 seq=2 == 2 │    │
│   │                 │           丢弃! ✗    │ 丢弃,返回成功    │    │
│   └─────────────────┘                     └─────────────────┘    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 关键概念

| 概念 | 含义 | 作用 |
|------|------|------|
| **PID** | Producer ID,Producer 启动时由 Broker 分配 | 唯一标识一个 Producer 实例 |
| **Sequence Number** | 每分区单调递增的序列号,从 0 开始 | 标识同一分区内的消息顺序 |
| **epoch** | Producer 的代际号,防止僵尸 PID | 旧 Producer 重启后,新 Producer 顶替 |
| **broker 端缓存** | 存储最近 5 个序列号的位图 | 高效检测重复,无需扫描磁盘 |

### 3. 启用幂等性的配置

```java
// ponytail: 幂等性 Producer —— 单分区单会话内保证不重

props.put("bootstrap.servers", "localhost:9092");
props.put("enable.idempotence", "true");     // ⭐ 核心开关
props.put("acks", "all");                    // 强制要求所有副本确认
props.put("retries", Integer.MAX_VALUE);     // 强制开启无限重试
props.put("max.in.flight.requests.per.connection", "5"); // ≤5 才能保证幂等
// 上述三项在 enable.idempotence=true 时被强制设置,不可手动覆盖

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

### 4. 幂等性 Producer 的三大限制

```text
┌──────────────────────────────────────────────────────────────────┐
│              幂等性 Producer 三大限制                             │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   限制 1:仅保证单分区不重复                                       │
│   ├── 不同分区之间不保证原子性                                    │
│   └── 多分区写入仍可能部分成功部分失败                            │
│                                                                  │
│   限制 2:仅保证单会话不重复                                       │
│   ├── Producer 重启会重新分配 PID,旧 PID 失效                         │

│                                                                  │
│   限制 3:不能与事务同时使用                                       │
│   ├── 事务型 Producer 已内含幂等能力                              │
│   └── enable.idempotence 与 transactional.id 互斥                   │
│                                                                  │

```

### 5. 幂等性 vs 普通 Producer 性能对比

## 八、事务型 Producer 详解

### 1. 事务 API 体系

Kafka 0.11+ 引入的事务型 Producer,通过 **事务协调者(Transaction Coordinator)** 实现跨分区、跨主题的原子写。核心 API 五个:

| API | 作用 | 调用时机 |
|-----|------|----------|
| `initTransactions()` | 初始化事务,与协调者建立连接 | Producer 创建后,业务开始前 |
| `beginTransaction()` | 开启新事务 | 业务逻辑前 |
| `send(...)` | 在事务中发送消息 | 业务逻辑中 |
| `commitTransaction()` | 提交事务,所有消息可见 | 业务逻辑成功后 |
| `abortTransaction()` | 中止事务,丢弃所有消息 | 业务逻辑失败后 |
| `sendOffsetsToTransaction()` | 将消费 offset 与消息原子提交 | EOS 场景专用 |

### 2. 事务型 Producer 时序图

```text
┌──────────────────────────────────────────────────────────────────┐
│              事务型 Producer 时序图                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Producer         Transaction Coordinator      Broker            │
│  ┌──────┐         ┌────────────────────┐      ┌──────┐           │
│  │      │         │                    │      │      │           │
│  │ init │────────►│ 注册 PID,获取 epoch │      │      │           │
│  │      │         │                    │      │      │           │
│  │begin │────────►│ 标记事务开始        │      │      │           │
│  │      │         │ 返回事务 ID          │      │      │           │
│  │      │         │                    │      │      │           │
│  │ send │─────────────────── 写入分区 ──►│────►│ msg1 │           │
│  │ send │─────────────────── 写入分区 ──►│────►│ msg2 │           │
│  │ send │─────────────────── 写入分区 ──►│────►│ msg3 │           │
│  │      │         │                    │      │      │           │

│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 3. 事务型 Producer 示例代码

```java
// ponytail: 事务型 Producer —— 跨分区原子写
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("enable.idempotence", "true");
props.put("transactional.id", "my-transactional-id"); // ⭐ 必须设置,唯一标识事务
props.put("acks", "all");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// 1. 初始化事务(只能调用一次)
producer.initTransactions();

try {
    // 2. 开启事务
    producer.beginTransaction();

    // 3. 在事务中发送多条消息(跨分区/跨主题)
    producer.send(new ProducerRecord<>("orders", "order1", "create"));
    producer.send(new ProducerRecord<>("orders", "order2", "create"));
    producer.send(new ProducerRecord<>("inventory", "item1", "decrement"));

    // 4. 模拟业务逻辑
    doBusinessLogic();

    // 5. 提交事务
    producer.commitTransaction();
} catch (Exception e) {
    // 6. 异常时中止事务
    producer.abortTransaction();
    throw e;
}
```

### 4. 事务隔离级别

Kafka 提供 **read_committed** 与 **read_uncommitted** 两种隔离级别,控制 Consumer 是否能读到未提交事务中的消息。

| 隔离级别 | 配置 | 行为 | 适用场景 |
|----------|------|------|----------|
| **read_uncommitted** | `isolation.level=read_uncommitted` (默认) | Consumer 可读到所有消息,包括未提交事务中的脏数据 | 日志、监控(可容忍脏读) |
| **read_committed** | `isolation.level=read_committed` | Consumer 仅能读到已提交事务的消息,未提交事务的消息不可见 | 业务处理(必须 EOS) |

```java
// ponytail: Consumer 配置 read_committed 以保证 EOS
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "eos-group");
props.put("isolation.level", "read_committed");  // ⭐ 关键配置
props.put("enable.auto.commit", "false");
```

### 5. 事务与 offset 关联

事务型 Producer 的杀手锏是 **将 Consumer offset 与业务消息原子提交**,即消费者处理消息后,通过 `sendOffsetsToTransaction` 将 offset 作为事务的一部分提交,实现「消费 + 处理 + offset 提交」三者原子化。

```java
// ponytail: sendOffsetsToTransaction —— 消费与生产的原子绑定
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProps);
consumer.subscribe(Arrays.asList("input-topic"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    if (!records.isEmpty()) {
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (TopicPartition partition : records.partitions()) {
            long offset = records.records(partition).get(records.records(partition).size() - 1).offset();
            offsets.put(partition, new OffsetAndMetadata(offset + 1));
        }

        producer.beginTransaction();
        try {
            // 业务处理
            for (ConsumerRecord<String, String> record : records) {
                producer.send(new ProducerRecord<>("output-topic", record.key(), process(record)));
            }

            // ⭐ 关键:把 offset 与业务消息原子提交
            producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());

            producer.commitTransaction();
        } catch (Exception e) {
            producer.abortTransaction();
            throw e;
        }
    }
}
```

## 九、幂等性 + 事务型 Producer 协同

### 1. 一站式 Exactly Once 架构

幂等性解决「单分区单会话不重复」,事务解决「跨分区原子写 + offset 绑定」,两者协同构成 Kafka 端到端 EOS 的基石。

```text
┌──────────────────────────────────────────────────────────────────┐
│              幂等性 + 事务 协同架构                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Consumer              Producer             Broker              │
│   ┌────────┐             ┌────────┐           ┌────────┐          │
│   │ poll() │────────────►│beginTx │           │        │          │
│   │        │             │        │           │        │          │
│   │        │             │ 幂等性  │           │        │          │
│   │        │             │ 去重    │           │        │          │
│   │        │             │ send() │─────────►│ partition │       │
│   │        │             │ send() │─────────►│ partition │       │
│   │        │             │ send() │─────────►│ partition │       │
│   │        │             │ sendOffsetsToTx() ─────►__consumer_offsets│
│   │        │             │ commit │           │        │          │
│   │        │             │        │ 2PC:    │        │          │
│   │        │             │        │ preCommit ─► marker │         │
│   │        │             │        │ commit ──► marker │         │
│   └────────┘             └────────┘           └────────┘          │
│                                                                  │
│   结果:消费、处理、生产、offset 提交,全部原子                     │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 事务状态机

| 状态 | 含义 | 允许的转换 |
|------|------|------------|
| `Empty` | 事务已结束或未开始 | → Ongoing |
| `Ongoing` | 事务进行中,可发送消息 | → PrepareCommit / PrepareAbort |
| `PrepareCommit` | 事务已提交准备阶段 | → CompleteCommit |
| `PrepareAbort` | 事务已中止准备阶段 | → CompleteAbort |
| `CompleteCommit` | 事务已完成提交,消息可见 | → Empty |
| `CompleteAbort` | 事务已完成中止,消息丢弃 | → Empty |

### 3. 事务过期与僵尸检测

Producer 长时间未提交事务会导致事务过期,Kafka 通过 `transaction.timeout.ms` (默认 60 秒) 控制。僵尸事务(Producer 宕机遗留)通过 epoch 机制检测,新 Producer 顶替后旧事务自动失效。

```text
┌──────────────────────────────────────────────────────────────────┐
│              僵尸事务检测机制                                      │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   时刻 T1: Producer A 启动,获得 epoch=1,开启事务                  │
│   时刻 T2: Producer A 宕机,事务卡住                              │
│   时刻 T3: Producer A 重启,获得 epoch=2,顶替旧事务                │
│   时刻 T4: Producer A 提交 epoch=1 的事务                         │
│           → 协调者发现 epoch 不匹配,拒绝,标记为僵尸              │
│   时刻 T5: 协调者异步中断 epoch=1 的事务,丢弃其消息                │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 十、流处理 EOS

### 1. Kafka Streams 的 EOS 实现

Kafka Streams 通过内置的 **Exactly Once Semantics (EOS)** 功能,在流处理场景下实现端到端不重不漏。核心依赖 **幂等性 + 事务 + 状态存储** 三者协同。

```text

│              Kafka Streams EOS 架构                               │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Input Topic                                                    │
│   ┌────────┐                                                     │
│   │ msg1   │                                                     │
│   │ msg2   │ ──────┐                                             │
│   │ msg3   │       │                                             │
│   └────────┘       ▼                                             │
│              ┌──────────────┐                                     │
│              │ Source Task  │                                     │
│              │ (消费+转换)    │                                     │
│              └──────┬───────┘                                     │
│                     │                                             │
│                     ▼                                             │
│              ┌──────────────┐     ┌──────────────┐               │
│              │ Stream Task  │────►│ State Store  │               │
│              │ (聚合/连接)    │     │ (RocksDB)    │               │
│              └──────┬───────┘     └──────┬───────┘               │
│                     │                     │                       │
│                     └──────────┬──────────┘                       │
│                                ▼                                  │
│              ┌──────────────────────────┐                         │
│              │ Sink Task (生产+提交)    │                         │

│                         │                                         │
│                         ▼                                         │
│                   Output Topic                                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 启用 Kafka Streams EOS

```java
// ponytail: Kafka Streams EOS 配置 —— 开启 processing.guarantee
Properties props = new Properties();
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "my-streams-app");
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
         StreamsConfig.EXACTLY_ONCE_V2);  // ⭐ 核心开关,Kafka 2.5+ 推荐
props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass());
props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass());

StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> source = builder.stream("input-topic");
source.mapValues(v -> process(v)).to("output-topic");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();
```

### 3. 处理保证语义 (Processing Guarantee Semantics, PES)

Kafka Streams 提供三种 PES,与消息传递语义一一对应。

| PES | 实现 | 数据丢失 | 数据重复 | 性能 |
|-----|------|----------|----------|------|
| **At most once** | 先 commit offset 再处理 | 可能 | 不可能 | 最高 |
| **At least once** | 先处理再 commit offset | 不可能 | 可能 | 中 |
| **Exactly once (EOS)** | 幂等 + 事务 + 状态存储原子提交 | 不可能 | 不可能 | 最低 |

### 4. EOS_V1 vs EOS_V2

| 特性 | EOS_V1 (Kafka 0.11+) | EOS_V2 (Kafka 2.5+) |
|------|---------------------|---------------------|
| 状态存储原子性 | 不保证 | 保证 |
| 任务再平衡时数据丢失 | 可能 | 几乎不可能 |
| 性能 | 较低 | 较高(优化版) |
| 推荐 | 旧版本兼容 | **新项目必选** |

## 十一、消费者侧 Exactly Once

### 1. Consumer 的责任边界

即使 Producer 与 Broker 端实现 EOS,Consumer 侧仍可能因业务逻辑非幂等而引入重复。Consumer 侧的 EOS 核心是 **手动提交 offset + 业务幂等性设计**。

```text
┌──────────────────────────────────────────────────────────────────┐
│              Consumer 侧 EOS 三层防线                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   第一层:Kafka Consumer 提交 offset                              │
│   └── 通过事务或手动 commit 控制                                  │
│                                                                  │
│   第二层:业务逻辑幂等                                            │
│   └── 通过唯一索引、去重表、版本号实现                            │
│                                                                  │
│   第三层:外部副作用幂等                                          │
│   └── 通过外部系统幂等接口(如支付幂等 token)                     │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 手动提交 offset 的最佳实践

```java
// ponytail: 手动提交 offset 的两种模式 —— 按需选择
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "eos-consumer-group");
props.put("enable.auto.commit", "false");    // 必须关闭自动提交
props.put("auto.offset.reset", "earliest");
props.put("isolation.level", "read_committed");

KafkaConsumer<String, String> consumer = new KafkaProducer<>(props);
consumer.subscribe(Arrays.asList("topic"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        // 业务处理 —— 必须幂等
        idempotentHandle(record);

        // 方案 A:每条消息提交一次(吞吐低,精度高)
        // consumer.commitSync(Collections.singletonMap(
        //     new TopicPartition(record.topic(), record.partition()),
        //     new OffsetAndMetadata(record.offset() + 1)
        // ));

        // 方案 B:批量提交(推荐,平衡性能与精度)
        consumer.commitSync(); // 提交 poll 内的所有 offset
    }
}
```

### 3. 业务幂等性的三种实现

| 实现方式 | 原理 | 适用场景 |
|----------|------|----------|
| **唯一索引** | DB 表对消息 ID 建唯一索引,重复 INSERT 失败 | 数据库写入场景 |
| **去重表** | Redis/Memory 记录已处理的消息 ID,处理前先查 | 高频去重,内存有限 |
| **版本号/CAS** | 业务字段携带版本号,update 时检查版本一致 | 状态机类业务 |
| **外部幂等接口** | 支付等外部系统提供幂等 token | 跨系统调用 |

### 4. 业务幂等示例代码

```java
// ponytail: 业务幂等 —— 基于唯一索引
public void idempotentHandle(ConsumerRecord<String, OrderMessage> record) {
    OrderMessage order = record.value();
    String messageId = record.key(); // 假设 key 即消息 ID

    try {
        // 唯一索引保证重复 INSERT 失败,不产生副作用
        orderDao.insert(new OrderRow(messageId, order.getAmount(), order.getUserId()));
    } catch (DuplicateKeyException e) {
        log.warn("消息 {} 已处理,跳过", messageId);
        // 不抛异常,正常提交 offset
    }
}
```

```text
│                            ▼                                      │
│   ┌──────────────────────────────────────────────────────────┐   │
│   │  下游系统(数据仓库/缓存/外部 API)                         │   │
│   │  └── 通过幂等接口或去重表保证最终不重                      │   │
│   └──────────────────────────────────────────────────────────┘   │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. EOS 实现的四道关卡

| 关卡 | 关键技术 | 解决的不重不漏 |
|------|----------|----------------|
| **生产关** | 幂等性 Producer (PID+Seq) | 单分区不重 |
| **跨分区关** | 事务型 Producer (2PC) | 跨分区原子 |
| **流处理关** | Kafka Streams EOS_V2 | 状态与输出原子 |
| **消费关** | sendOffsetsToTransaction + 业务幂等 | 消费与处理原子 |

### 3. EOS 的局限性

| 限制 | 说明 |
|------|------|
| 跨系统不保证 | Kafka 与下游 DB 之间仍可能失败,需要 outbox / 2PC 中间层 |
| 性能开销 | EOS 比 At least once 性能低 20%~30% |
| 事务超时 | `transaction.timeout.ms` 默认 60 秒,长事务需手动调大 |
| 版本要求 | Producer/Consumer/Broker 需 ≥ 0.11,推荐 ≥ 2.5 |

```java
// ponytail: 金融交易 Producer —— 事务型 + 幂等
Properties producerProps = new Properties();
producerProps.put("bootstrap.servers", "kafka-cluster:9092");
producerProps.put("transactional.id", "transfer-producer-" + instanceId);
producerProps.put("enable.idempotence", "true");
producerProps.put("acks", "all");

KafkaProducer<String, TransferMessage> producer = new KafkaProducer<>(producerProps, strSerde, transferSerde);
producer.initTransactions();

public void sendTransfer(TransferMessage transfer) {
    producer.beginTransaction();
    try {
        // 业务校验 + 数据库写入(outbox 表) + Kafka 发送在同一事务
        transferService.saveOutbox(transfer); // 写 outbox 表
        producer.send(new ProducerRecord<>("transfer", transfer.getTransferId(), transfer));
        producer.sendOffsetsToTransaction(getConsumerOffsets(), consumerGroupMetadata);
        producer.commitTransaction();
    } catch (Exception e) {
        producer.abortTransaction();
        // 告警 + 重试
        throw new TransferException("转账消息发送失败", e);
    }
}
```

```java
// ponytail: 金融交易 Consumer —— 业务幂等 + 手动提交
Properties consumerProps = new Properties();
consumerProps.put("bootstrap.servers", "kafka-cluster:9092");
consumerProps.put("group.id", "account-consumer");
consumerProps.put("isolation.level", "read_committed");
consumerProps.put("enable.auto.commit", "false");

KafkaConsumer<String, TransferMessage> consumer = new KafkaConsumer<>(consumerProps);
consumer.subscribe(Arrays.asList("transfer"));

while (running) {
    ConsumerRecords<String, TransferMessage> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, TransferMessage> record : records) {
        TransferMessage transfer = record.value();
        try {
            // 业务幂等 —— 数据库唯一索引(transfer_id)
            accountService.executeTransfer(transfer);
            consumer.commitSync(Collections.singletonMap(
                new TopicPartition(record.topic(), record.partition()),
                new OffsetAndMetadata(record.offset() + 1)
            ));
        } catch (DuplicateKeyException e) {
            log.warn("转账 {} 已处理,跳过", transfer.getTransferId());
            consumer.commitSync(); // 即使重复也提交,避免下次再处理
        }
    }
}
```

```java
public void idempotentShip(PaymentEvent payment) {

    String idempotencyKey = "ship-" + orderId;

    // 调用下游发货 API,携带 idempotency key

    }
}
```

## 核心要点速记

### 一、三种消息传递语义

- **At most once**:可能丢,绝不重,性能最高,适用日志/监控
- **At least once**:绝不丢,可能重,业务默认,需业务幂等配合
- **Exactly once**:既不丢也不重,Kafka 通过幂等 + 事务实现,业务侧仍需幂等

### 二、At most once vs At least once 关键差异

| 维度 | At most once | At least once |
|------|--------------|---------------|
| Producer ack | 0(无确认) | all(全确认) |
| Producer 重试 | 关闭 | 开启 |
| Consumer 提交 | 先提交再处理 | 先处理再提交 |
| 业务要求 | 可容忍丢失 | 需业务幂等 |

### 三、幂等性 Producer 三要素

- **PID**:Producer 唯一标识,启动时分配
- **Sequence Number**:分区级单调递增序列
- **epoch**:代际号,防止僵尸 PID
- 限制:仅单分区、单会话、不能与事务同时用

### 四、事务型 Producer 五大 API

- `initTransactions()` 初始化,只能调用一次
- `beginTransaction()` 开启事务
- `send(...)` 在事务中发送
- `commitTransaction()` 提交事务(2PC)
- `abortTransaction()` 中止事务
- 附加:`sendOffsetsToTransaction()` 绑定 offset

### 五、事务隔离级别

- `read_uncommitted`:可读未提交事务(默认,可能脏读)
- `read_committed`:仅读已提交事务(EOS 必选)

### 六、Kafka Streams EOS_V2

- 配置:`processing.guarantee=exactly_once_v2`
- 优势:状态存储 + 输出 + offset 三者原子
- 适用:Kafka 2.5+,推荐新项目使用

### 七、Consumer 侧 EOS 三层防线

1. **手动提交 offset**:`enable.auto.commit=false`
2. **事务绑定 offset**:`sendOffsetsToTransaction`
3. **业务幂等性**:唯一索引 / 去重表 / 幂等 token

### 八、生产环境配置速记

- Producer:`acks=all` + `enable.idempotence=true` + `retries=MAX` + `transactional.id`(如需事务)
- Consumer:`enable.auto.commit=false` + `isolation.level=read_committed`(如需 EOS)
- Broker:`min.insync.replicas=2` + `replication.factor=3` + `unclean.leader.election.enable=false`

### 九、EOS 端到端流程速记

1. Producer 幂等性 → 单分区不重
2. Producer 事务 → 跨分区原子 + offset 绑定
3. Broker ISR + min.insync.replicas → 不丢
4. Consumer read_committed → 不读脏数据
5. Consumer 手动提交 + 业务幂等 → 处理不重

### 十、实战案例核心要点

- **金融场景**:事务型 Producer + 幂等消费 + transfer_id 唯一索引
- **电商场景**:Kafka Streams EOS_V2 + 下游幂等 token + 数据库唯一索引兜底

### 十一、一句话总结

> Kafka 的 EOS 是**「幂等性 + 事务 + 业务幂等」三层防线**的协同结果,**永远不要相信单一层能解决所有问题**。生产环境默认启用幂等性,关键业务额外启用事务,任何外部副作用都需业务幂等兜底。

### 十二、可靠性 vs 性能取舍口诀

- **可以丢**:日志/监控 → `acks=0`,极致吞吐
- **不能丢可以重**:大多数业务 → `acks=all` + 幂等 + 业务幂等
- **既不能丢也不能重**:金融/资金 → `acks=all` + 事务 + 业务幂等 + outbox 模式
