# Kafka 实战案例集

> 从生产实践出发,梳理 12 个最具代表性的 Kafka 工程案例,涵盖**日志采集、事件驱动、CDC 同步、实时数仓、Event Sourcing、秒杀削峰、IoT 接入、跨中心灾备、性能调优**等典型场景,每个案例均给出架构图、完整配置与可运行代码。

---

## 一、实战案例概述

Kafka 在生产环境中的角色千差万别,但**底层模式**相对收敛。从"消息流的走向"来看,几乎所有案例都可以归入下面五类:

| 模式 | 描述 | 典型案例 |
|------|------|----------|
| **采集管道** | 业务侧 → Kafka → 下游存储 | 用户行为、日志聚合、IoT 接入 |
| **事件总线** | 微服务之间通过 Kafka 异步解耦 | 订单事件驱动、秒杀削峰 |
| **CDC 同步** | 数据库变更日志 → Kafka → 多副本消费 | MySQL → ES 同步、实时数仓 |
| **流式计算** | Kafka 作为流处理引擎的 Source/Sink | Lambda 架构、实时数据仓库 |
| **灾备链路** | 主中心 Kafka → 镜像 → 备中心 | 跨数据中心容灾 |

下面 12 个案例按"由浅入深"顺序展开,每个案例都遵循统一的四段式结构:**场景 → 架构 → 关键代码/配置 → 经验总结**。

## 二、案例 1:用户行为日志采集管道

### 1. 场景描述

**业务诉求**:某电商网站日活 500 万,每天产生 **40 亿+** 用户行为事件(点击、浏览、停留、加入购物车),需要将这些事件:

- **实时**进入推荐系统做特征计算(秒级延迟)
- **准实时**写入 HDFS 做 T+1 用户画像(分钟级延迟)
- **近实时**进入 ES 提供运营查询(分钟级延迟)

直接通过 HTTP/ETL 落库的方案,在峰值流量(大促秒杀)下数据库会先崩。采用 **Kafka 作为缓冲层**,前端只关心"丢到 Kafka",后续由多个 Consumer Group 各自消费。

### 2. 整体架构

```text
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Web/APP 端  │  │  微信小程序  │  │  第三方埋点  │
│  JS SDK      │  │  JS SDK      │  │  服务端 API  │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │  HTTP/Native    │                 │
       ▼                 ▼                 ▼
   ┌──────────────────────────────────────────────┐
   │     采集网关 (Nginx + Lua / Spring Boot)     │
   │   - 校验、采样、压缩 (Protobuf)              │
   │   - 异步发送 Kafka (背压机制)                │
   └─────────────────┬────────────────────────────┘
                     │
                     ▼
   ┌──────────────────────────────────────────────┐
   │        Kafka Cluster (3 Brokers)             │
   │   Topic: user_behavior_log                   │
   │   - 12 分区 (按 user_id 哈希)                │
   │   - 副本数 = 3, retention = 72h              │
   └─────────────────┬────────────────────────────┘

        ┌────────────┼─────────────┬──────────────┐
        ▼            ▼             ▼              ▼
```

#### 3.2 采集网关生产者 (Java)

```java
@Component
public class BehaviorProducer {

    private final KafkaProducer<String, byte[]> producer;

    public BehaviorProducer(@Value("${kafka.bootstrap}") String bootstrap) {
        Properties p = new Properties();
        p.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrap);
        p.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
              StringSerializer.class.getName());
        p.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
              ByteArraySerializer.class.getName());

        // 性能关键参数
        p.put(ProducerConfig.LINGER_MS_CONFIG, 50);          // 批量延迟
        p.put(ProducerConfig.BATCH_SIZE_CONFIG, 64 * 1024);  // 64KB
        p.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
        p.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 256 * 1024 * 1024L); // 256MB
        p.put(ProducerConfig.ACKS_CONFIG, "1");              // 性能/可靠平衡
        p.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        p.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);

        this.producer = new KafkaProducer<>(p);
    }

    public void send(UserBehaviorEvent event) {
        // 用 user_id 做 Key,保证同一用户事件落到同一分区
        String key = event.getUserId();
        ProducerRecord<String, byte[]> record =
            new ProducerRecord<>("user_behavior_log", key,
                                 event.toByteArray());
        producer.send(record, (md, ex) -> {
            if (ex != null) {
                log.error("Send failed: {}", ex.getMessage());
                // 失败落入本地磁盘队列,后台线程重试
                localFallback.push(event);
            }
        });
    }
}
```

### 4. 经验总结

| 坑 | 解决方案 |
|------|---------|
| 大促期间 Kafka 突发流量 | 提前 1 周扩分区(12 → 24),并且压测 Producer 端到端 |
| 用户 ID 哈希不均导致分区倾斜 | 改用 **MurmurHash** 或加盐(`user_id + random%100`)分桶 |
| 客户端时间戳不准 | 服务端补 `ingest_time` 字段,事件时间用客户端 + 服务端双时间戳 |
| 采集网关单点 | Gateway 多实例 + 本地磁盘队列(丢消息可控) |
| HDFS 小文件 | `flush.size=10000` + `rotate.interval.ms=600000` 双触发 |

## 三、案例 2:订单微服务事件驱动

### 1. 场景描述

电商下单流程涉及多个微服务协作,传统 RPC 链式调用会导致:

- **同步阻塞**:任一服务慢,整个下单链路慢
- **级联失败**:库存服务挂掉,下单不可用
- **数据不一致**:支付成功但库存没扣,需要分布式事务补偿

采用 **Kafka 事件驱动 + 最终一致性**,各服务通过事件解耦,大幅提升吞吐和可用性。

### 2. 整体架构

```text
┌─────────┐   创建订单事件    ┌─────────┐
│  Cart   ├─────────────────►│ Order   │
│ Service │                  │ Service │
└─────────┘                  └────┬────┘
                                  │ OrderCreated
                                  ▼
   ┌─────────────────────────────────────────────────────┐
   │             Kafka: order-events (12 partitions)     │
   │                                                     │
   │   Topic: order-created / stock-deducted /           │
   │          payment-success / shipping-event           │
   └────┬───────────────┬───────────────┬───────────────┘
        │               │               │
        ▼               ▼               ▼
   ┌─────────┐    ┌─────────┐     ┌─────────┐
   │ Inventory│    │ Payment │     │ Shipping│
   │ Service  │    │ Service │     │ Service │
   └─────────┘    └─────────┘     └─────────┘
        │               │               │
        ▼               ▼               ▼
   ┌─────────────────────────────────────────┐
   │        各自本地库 + Outbox 表          │
   └─────────────────────────────────────────┘
```

### 3. 完整代码(Spring Boot + Kafka)

#### 3.1 订单服务发布者

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;
    private final OrderRepository orderRepository;

    @Transactional
    public Order createOrder(CreateOrderRequest req) {
        // 1. 本地事务:创建订单
        Order order = new Order();
        order.setUserId(req.getUserId());
        order.setAmount(req.getAmount());
        order.setStatus(OrderStatus.PENDING);
        orderRepository.save(order);

        // 2. 同一事务写 Outbox (保证发布与业务原子性)
        Outbox outbox = new Outbox();
        outbox.setAggregateId(order.getId());
        outbox.setEventType("OrderCreated");
        outbox.setPayload(JsonUtil.toJson(toEvent(order)));
        outboxRepository.save(outbox);

        // 3. 由独立 Poller 定时读取 Outbox 并发送到 Kafka
        return order;
    }
}

@Component
@RequiredArgsConstructor
public class OutboxPoller {

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, String> kafka;

    @Scheduled(fixedDelay = 100)
    @Transactional
    public void poll() {
        List<Outbox> pending = outboxRepository.findTop100ByStatus(OutboxStatus.PENDING);
        for (Outbox o : pending) {
            kafka.send("order-events", o.getAggregateId(), o.getPayload())
                 .whenComplete((res, ex) -> {
                     if (ex == null) o.setStatus(OutboxStatus.SENT);
                     // 失败保留 PENDING,下一轮重试
                 });
        }
    }
}
```

#### 3.2 库存服务消费者(Saga 参与者)

```java
@Component
@RequiredArgsConstructor
public class InventoryConsumer {

    private final InventoryService inventoryService;

    @KafkaListener(topics = "order-events",
                   groupId = "inventory-service",
                   containerFactory = "manualAckFactory")
    public void onMessage(ConsumerRecord<String, OrderEvent> record,
                          Acknowledgment ack) {
        OrderEvent event = record.value();
        try {
            if ("OrderCreated".equals(event.getType())) {
                // 扣减库存
                inventoryService.deduct(event.getOrderId(),
                                        event.getItems());
                // 发布库存已扣减事件
                publishEvent("StockDeducted", event.getOrderId());
            } else if ("OrderCancelled".equals(event.getType())) {
                inventoryService.restore(event.getOrderId(), event.getItems());
            }
            ack.acknowledge();
        } catch (InsufficientStockException e) {
            // 业务异常:发补偿事件,触发订单取消
            publishEvent("StockInsufficient", event.getOrderId());
            ack.acknowledge();
        } catch (Exception e) {
            // 系统异常:不 ack,下一轮重试
            log.error("Consume failed", e);
        }
    }
}
```

#### 3.3 配置要点 (application.yml)

```yaml
spring:
  kafka:
    bootstrap-servers: kafka-1:9092,kafka-2:9092,kafka-3:9092
    producer:
      acks: all
      retries: 5
      properties:
        enable.idempotence: true
        max.in.flight.requests.per.connection: 5
        compression.type: lz4
    consumer:
      group-id: order-service
      auto-offset-reset: earliest

      concurrency: 4
```

### 4. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| 业务事务与消息发送不一致 | **Outbox 模式**:业务与消息同事务写本地表,独立 Poller 投递 |
| 消费者幂等 | 业务表加 `event_id` 唯一索引,重复消息直接跳过 |
| Saga 失败补偿 | 每个 Saga 步骤配对**补偿事件**,失败时反向补偿 |
| 顺序保证 | 同一 `order_id` 走相同分区(用 Key 路由),单分区单消费者顺序消费 |
| 重复消费 | 业务唯一键 + Redis 布隆过滤器双保险 |

## 四、案例 3:MySQL → Kafka 实时同步 (CDC)

### 1. 场景描述

业务 MySQL 集群承担 OLTP 写入,**下游**有多个异构存储(ES、Hive、Redis 缓存、数据仓库)需要**近实时**拿到数据变更。如果用业务双写,需要改业务代码,且容易遗漏。**Debezium** 通过读取 MySQL `binlog` 实现零侵入 CDC,把变更事件推送到 Kafka,下游各取所需。

### 2. 整体架构

```text

│  MySQL Master├──────────────►│ Debezium MySQL        │
│  (row-based) │              │ Source Connector      │
└──────────────┘              │ (Kafka Connect)       │
                              └──────────┬────────────┘
                                         │
                                         ▼
                          ┌──────────────────────────┐
                          │  Kafka: mysql.cdc.orders │
                          │  (60 partitions)         │
                          └──────────┬───────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
        ┌──────────┐           ┌──────────┐          ┌─────────────┐
        │  ES Sink │           │  HDFS    │          │  Redis      │
        │ Connector│           │  Sink    │          │  Sink(自己) │
        │ (搜索)   │           │ (归档)   │          │  (缓存预热) │
```

### 4. 关键代码:自定义 Redis 缓存预热

```java
@KafkaListener(topics = "mysql.cdc.orders",
               groupId = "redis-cache-warmer")
public void onChange(ConsumerRecord<String, ChangeEvent> record) {
    ChangeEvent<String, Order> event = record.value();
    String orderId = event.getKey();

    switch (event.getOp()) {
        case "c":  // create
        case "u":  // update
            redisTemplate.opsForValue()
                       .set("order:" + orderId,
                            JsonUtil.toJson(event.getAfter()),
                            Duration.ofHours(24));
            break;
        case "d":  // delete
            redisTemplate.delete("order:" + orderId);
            break;
    }
}
```

### 5. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| binlog `STATEMENT` 格式导致数据丢失 | 必须用 `ROW` 格式 |
| 初始快照长时间锁表 | `snapshot.mode=initial` + `snapshot.locking.mode=minimal` |
| 下游消费跟不上 | 增加 Connector 分区(`tasks.max`),扩容下游 |
| 字段类型映射(JSON/Decimal) | 配置 `decimal.handling.mode=double` |
| 消费位点回退 | 配合 Kafka 事务 + ES 幂等写入 |

## 五、案例 4:实时数据仓库(Lambda 架构)

### 1. 场景描述

企业需要建设实时数仓,业务日志(MySQL CDC + 行为日志 + 业务事实)既要支持**分钟级实时报表**(大屏、风控),也要支持**T+1 离线全量报表**(财务、对账)。**Lambda 架构**将数据流一分为二:实时层(Flink) + 离线层(Spark),最终在**应用层**做合并。

### 2. 整体架构

```text
                          ┌──────────────────────┐
                          │      Sources         │
                          │  MySQL CDC / 行为日志 │
                          └──────────┬───────────┘
                                     │
                                     ▼
                          ┌──────────────────────┐
                          │   Kafka (ODS 层)     │
                          │  原始数据保留 7 天    │
                          └──────────┬───────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
   ┌────────────────────┐  ┌────────────────────┐  ┌────────────────┐
   │  Flink 实时层      │  │  Flink 准实时层     │  │  Spark 离线层  │
   │  (秒级延迟)        │  │  (分钟级)           │  │  (T+1 全量)    │
   │                    │  │                    │  │                │
   │  Kafka → Flink     │  │  Kafka → Hudi      │  │  Kafka→HDFS    │
   │  → Kafka (DWD)     │  │  (近实时维度表)    │  │  → Hive (DWD) │
   └─────────┬──────────┘  └────────┬───────────┘  └───────┬────────┘
             ▼                     ▼                        ▼
   ┌────────────────────┐  ┌────────────────────┐  ┌────────────────┐
   │  Kafka (DWS 层)    │  │  Hudi DWS 表       │  │  Hive DWS 表   │
   └─────────┬──────────┘  └────────┬───────────┘  └───────┬────────┘
             └──────────┬──────────┘                        │
                        ▼                                   ▼
              ┌──────────────────────┐         ┌────────────────────┐
              │   ClickHouse/Doris   │         │  ClickHouse/Doris  │
              │   (实时大屏、风控)    │         │  (历史全量报表)     │
              └──────────────────────┘         └────────────────────┘
```

### 3. 关键代码

#### 3.1 Flink 实时层(简化)

```java
StreamExecutionEnvironment env =
    StreamExecutionEnvironment.getExecutionEnvironment();

KafkaSource<String> source = KafkaSource.<String>builder()
    .setBootstrapServers("kafka:9092")
    .setTopics("ods.order_events")
    .setGroupId("flink-realtime-dwd")
    .setStartingOffsets(OffsetsInitializer.latest())
    .build();

DataStream<OrderEvent> orders = env.fromSource(source, ...)
    .map(json -> JsonUtil.parse(json, OrderEvent.class))
    .filter(Objects::nonNull)
    .keyBy(OrderEvent::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new OrderAggregate(), new OrderWindowFunction());

orders.addSink(new FlinkKafkaProducer<>("dws.user_order_1min", ...));

env.execute("realtime-dwd");
```

### 4. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| 实时离线数据口径不一致 | **统一指标定义**(OneService),实时/离线共用同一份口径 |
| Kafka ODS 消费位点丢失 | Flink Checkpoint + Kafka Offset 三方存储 |
| Hudi 小文件 | `hoodie.parquet.small.file.limit` 调大 + 定时 Compaction |
| 实时 + 离线双链路维护成本 | **流批一体** (Iceberg/Hudi 隐藏批流差异) |
| 状态后端瓶颈 | Flink 状态用 RocksDB + 增量 Checkpoint |

## 六、案例 5:Kafka 在 Event Sourcing 中的应用

### 1. 场景描述

**事件溯源(Event Sourcing)** 把"状态"看作"事件的累积"。订单每次状态变更都产生事件,追加到 Kafka(等同于事件存储),**不直接修改状态**;状态由事件回放得到。优势:**审计完整、可回放、天然支持 CQRS**。

### 2. 整体架构

```text
   Command                    ┌─────────────────────┐
┌──────────┐   领域事件        │   Kafka             │
│  API     ├─────────────────►│ Topic: order-events │
│  Request │                  │   (Append-Only)     │
└──────────┘                  └──────────┬──────────┘
                                          │
                                          ▼
                              ┌───────────────────────┐
                              │  Event Store          │
                              │  (Kafka + 周期快照)   │
                              └──────────┬────────────┘
                                         │
                  ┌──────────────────────┼──────────────────────┐
                  ▼                      ▼                      ▼
            ┌──────────┐           ┌──────────┐          ┌──────────────┐
            │ Read     │           │ Read     │          │ Projector    │
            │ Model A  │           │ Model B  │          │ → MySQL      │
            │ (订单视图)│           │ (统计视图)│          │ (CQRS 同步)  │
            └──────────┘           └──────────┘          └──────────────┘
```

### 3. 完整代码示例

#### 3.1 事件定义

```java
public sealed interface OrderEvent
        permits OrderCreated, OrderPaid, OrderShipped, OrderCancelled {

    String orderId();
    long version();
}

public record OrderCreated(String orderId, long version,
                           String userId, BigDecimal amount,
                           List<OrderItem> items) implements OrderEvent {}

public record OrderPaid(String orderId, long version,
                        String paymentId, Instant paidAt) implements OrderEvent {}
```

#### 3.2 聚合根

```java
public class OrderAggregate {
    private String orderId;
    private OrderStatus status;
    private BigDecimal paidAmount = BigDecimal.ZERO;
    private final List<OrderEvent> uncommitted = new ArrayList<>();

    // 应用命令,加载事件
    public void loadFromHistory(List<OrderEvent> history) {
        for (OrderEvent e : history) apply(e);
    }

    public void create(String userId, BigDecimal amount, List<OrderItem> items) {
        if (status != null) throw new IllegalStateException("Already exists");
        uncommitted.add(new OrderGenerated(
            orderId, nextVersion(), userId, amount, items));
        apply(uncommitted.get(uncommitted.size() - 1));
    }

    public void pay(String paymentId) {
        if (status != OrderStatus.CREATED)
            throw new IllegalStateException("Not payable");
        uncommitted.add(new OrderPaid(orderId, nextVersion(),
                                       paymentId, Instant.now()));
        apply(uncommitted.get(uncommitted.size() - 1));
    }

    private void apply(OrderEvent e) {
        switch (e) {
            case OrderCreated ec -> {
                this.orderId = ec.orderId();
                this.status  = OrderStatus.CREATED;
            }
            case OrderPaid ep -> {
                this.paidAmount = ep.amount();
                this.status     = OrderStatus.PAID;
            }
            default -> {}
        }
    }

    public List<OrderEvent> flush() {
        var copy = List.copyOf(uncommitted);
        uncommitted.clear();
        return copy;
    }
}
```

#### 3.3 仓储(写入 Kafka)

```java
@Repository
public class OrderEventRepository {

    private final KafkaTemplate<String, OrderEvent> kafka;
    private final OrderSnapshotRepository snapRepo;

    public void save(OrderAggregate agg) {
        List<OrderEvent> events = agg.flush();
        for (OrderEvent e : events) {
            kafka.send("order-events", agg.getOrderId(), e)
                 .whenComplete((r, ex) -> {
                     if (ex != null) {
                         // 失败落本地重试队列
                         fallbackQueue.put(e);
                     }
                 });
        }
        // 每 100 个事件写一次快照(加速回放)
        if (agg.getVersion() % 100 == 0) {
            snapRepo.save(new OrderSnapshot(agg.getOrderId(),
                                              agg.getVersion(),
                                              agg.toSnapshot()));
        }
    }

    public OrderAggregate load(String orderId) {
        // 1. 读最新快照
        OrderSnapshot snap = snapRepo.findLatest(orderId).orElse(null);
        OrderAggregate agg = new OrderAggregate();
        long fromVersion = 0;
        if (snap != null) {
            agg.restoreFromSnapshot(snap.getState());
            fromVersion = snap.getVersion() + 1;
        }

        // 2. 从 Kafka 读 fromVersion 之后的事件
        ConsumerRecords<String, OrderEvent> records =
            kafkaConsumer.poll("order-events",
                               orderId, fromVersion);
        for (OrderEvent e : records) {
            agg.apply(e);
        }
        return agg;
    }
}
```

### 4. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| 事件回放慢 | 每 100/500/1000 个事件写一次快照 |
| 事件 schema 演进 | Avro/Protobuf + Schema Registry 严格管理 |
| 写多读多,CQRS 同步延迟 | 多个独立 Projector 并行消费同一 Topic |
| 事件重复 | 业务幂等 + Kafka 事务 |
| Kafka 容量撑爆 | 冷事件归档到对象存储,Kafka 只保留近期 |

## 七、案例 6:秒杀系统流量削峰

### 1. 场景描述

秒杀活动瞬时流量是日常的 **100 ~ 1000 倍**,如果直接打到后端服务,数据库会被瞬间压垮。采用 **Kafka 消息队列**做缓冲,把"瞬时冲击"变成"平稳处理"。

### 2. 整体架构

```text
┌──────────────┐  HTTP 抢单   ┌──────────────┐
│   用户       ├─────────────►│  接入层      │
└──────────────┘              │  Nginx+Lua   │
                              │  (限流/防刷) │
                              └──────┬───────┘
                                     │ 异步入队
                                     ▼
                              ┌──────────────┐
                              │   Redis      │
                              │  (库存预扣)  │
                              └──────┬───────┘
                                     │ 异步下单事件
                                     ▼
   ┌──────────────────────────────────────────────────┐
   │        Kafka: seckill_order (24 partitions)      │
   │        - 限速消费(每个分区 200 QPS)              │
   └─────────────────┬────────────────────────────────┘
                     │
                     ▼
   ┌──────────────────────────────────────────────────┐
   │      秒杀 Worker (24 消费者实例)                 │
   │      - 单机 200 QPS,集群总 4800 QPS             │
   └─────────────────┬────────────────────────────────┘
                     │
                     ▼
   ┌──────────────────────────────────────────────────┐
   │      MySQL (分库分表) + ES (订单检索)           │
   └──────────────────────────────────────────────────┘
```

### 3. 关键配置

#### 3.1 Kafka Topic 参数(专门优化)

```bash
kafka-topics.sh --create \
  --topic seckill_order \
  --partitions 24 \
  --replication-factor 3 \
  --config compression.type=lz4 \
  --config retention.ms=3600000 \
  --config flush.messages=10000 \
  --config flush.ms=5000
```

#### 3.2 消费限速(`quotas`)

```properties
# 在 server.properties 中按客户端限速
# 限制用户接入层 Producer 写入速率,避免爆掉 Broker
quota.producer.default=20971520   # 20 MB/s
quota.consumer.default=20971520
```

#### 3.3 容量规划

| 指标 | 日常 | 大促预估 | 配置 |
|------|------|----------|------|
| 峰值 QPS | 500 | 50,000 | 接入层限流到 5000,QPS 超限直接返回 |
| 消息量/秒 | 200 | 30,000 | Kafka 集群 5 Brokers × 6000 msg/s |
| 消费 Worker | 4 | 48 | 每 Worker 600 QPS,Kafka 顺序消费 |
| 消息大小 | 2 KB | 2 KB | LZ4 压缩后约 1 KB |
| 带宽 | 0.4 MB/s | 30 MB/s | 单 Broker 千兆网卡足够 |

### 4. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| 瞬时洪峰压垮 Broker | 接入层先限流,再写入;Kafka 不限流就是接盘侠 |
| 消息积压 | 监控 `lag`,消费者横向扩容 + 缩短单消息处理时间 |
| 重复下单 | Redis `SETNX` + 业务唯一索引双重防重 |
| 公平性 | Kafka 分区用 `user_id` 哈希,避免单个用户被多 Worker 抢 |
| 回压 | Worker 处理慢时暂停拉取(默认 `max.poll.interval.ms`) |

## 八、案例 7:日志聚合与监控

### 1. 场景描述

数百个微服务实例每天产生 TB 级日志,需要**统一采集、检索、告警**。传统 ELK 直接传 ES 在高峰期容易丢日志,引入 Kafka 缓冲后:

```text
       │

   │ (Sidecar)│    │ (Daemon) │    │ (Daemon) │
   └────┬─────┘    └────┬─────┘    └────┬─────┘
        └────────────────┼─────────────────┘
                         ▼
              ┌──────────────────────┐
              │  Kafka               │
              │  Topic: app-logs     │
              │  Topic: nginx-logs   │
              │  Topic: sys-logs     │
              └──────────┬───────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
  ┌──────────┐    ┌──────────┐    ┌────────────┐
  │ Logstash │    │ Flink    │    │ Kafka      │
  │ → ES     │    │ (异常    │    │ Connect    │
  │ (检索)   │    │  检测)  │    │ → S3       │
  └──────────┘    └──────────┘    └────────────┘
```

### 3. Filebeat 配置

```yaml
filebeat.inputs:
  - type: container
    paths:
      - /var/log/containers/*.log
    multiline.pattern: '^[0-9]{4}-[0-9]{2}-[0-9]{2}'
    multiline.negate: true
    multiline.match: after

processors:
  - add_kubernetes_metadata: ~
  - drop_fields:
      fields: ["agent.ephemeral_id", "ecs.version"]

output.kafka:
  hosts: ["kafka-1:9092", "kafka-2:9092", "kafka-3:9092"]

  compression: lz4

backoff.max: 60s
```

### 4. 经验总结

| 坑 | 解决方案 |
|-----|---------|
| 日志丢失 | Filebeat 用 `at-least-once`,关键日志本地缓存 24h |
| 日志风暴 | Filebeat 限速 + 采样 + 多行合并 |
| ES 写入压力 | Kafka 缓冲 + Logstash 批量写 ES |
| 多租户隔离 | 按服务/团队分 Topic,权限用 ACL 隔离 |
| 监控 | 监控 Kafka `log.flush.rate` 与消费者 `lag` |

## 十、案例 9:Kafka 作为分布式系统事件总线

### 1. 场景描述

微服务间有多种异步通信模式,Kafka 在不同模式下的应用:

```text
┌────────────────────────────────────────────────────────────┐
│              Saga 模式 (长事务分布式协调)                   │
│  Order ──► Payment ──► Inventory ──► Shipping              │
│     │           │             │             │               │
│     └───────────┴─────────────┴─────────────┘               │
│                  Kafka 事件总线                              │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│              Event Sourcing (状态由事件推导)               │
│  见案例 5 的完整代码                                       │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│              CDC + Outbox 模式 (DB 事件化)                 │
│  MySQL → Debezium → Kafka → 下游                          │
│  见案例 3 + 案例 2 的 Outbox                              │
└────────────────────────────────────────────────────────────┘
```

### 2. Saga 模式代码(订单流程)

```java
@Component
public class OrderSaga {

    @KafkaListener(topics = "saga-events", groupId = "order-saga")
    public void handle(ConsumerRecord<String, SagaEvent> record, Acknowledgment ack) {
        SagaEvent ev = record.value();
        SagaState state = stateRepo.load(ev.getSagaId());

        switch (ev.getType()) {
            case "CreateOrder":
                state.setStatus("PAYMENT_PENDING");
                kafka.send("saga-events", state.getSagaId(),
                           new SagaEvent("ProcessPayment", ev.getSagaId()));
                break;
            case "PaymentSuccess":
                state.setStatus("INVENTORY_PENDING");
                kafka.send("saga-events", state.getSagaId(),
                           new SagaEvent("DeductInventory", ev.getSagaId()));
                break;
            case "InventorySuccess":
                state.setStatus("SHIPPING_PENDING");
                kafka.send("saga-events", state.getSagaId(),
                           new SagaEvent("ArrangeShipping", ev.getSagaId()));
                break;
            case "ShippingSuccess":
                state.setStatus("COMPLETED");
                break;
            case "PaymentFailed":
            case "InventoryFailed":
                // 触发反向补偿
                kafka.send("saga-events", state.getSagaId(),
                           new SagaEvent("CancelOrder", ev.getSagaId()));
                break;
        }
        stateRepo.save(state);
        ack.acknowledge();
    }
}
```

### 3. 经验总结

| 模式 | 适用 | 复杂度 |
|------|------|--------|
| **直接调用** | 强一致、低延迟 | 低 |
| **Saga + 事件** | 长事务,最终一致 | 中 |
| **Event Sourcing** | 审计、时序追溯 | 高 |
| **CDC + Outbox** | 已有 DB,无侵入 | 中 |
| **请求/响应 (Kafka 不擅长)** | 同步调用 | 高(不推荐) |

### 1. 案例 11.1:百万 QPS 写入优化

#### 1.1 优化前后对比

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 峰值 QPS | 12 万 | **110 万** | 9.2x |
| 平均延迟 P99 | 850 ms | **45 ms** | 18x |
| Broker CPU | 85% | 60% | -25% |
| 磁盘 IO 利用率 | 95% | 55% | -40% |

#### 1.2 关键调优项

```properties
# === Producer 端 ===
linger.ms=20                  # 适度批量
batch.size=131072             # 128KB
compression.type=lz4
acks=1                        # 非关键业务可放宽
```

#### 1.3 关键代码:顺序写 + 零拷贝

```java
// 单线程批量发送,避免锁竞争
ExecutorService pool = Executors.newFixedThreadPool(8);
for (List<Event> batch : batches) {
    pool.submit(() -> {
        for (Event e : batch) {
            kafka.send(new ProducerRecord<>("topic", e.getKey(), e));
        }
        // 不 flush,让 linger.ms 决定何时发送
    });
}
```

### 2. 案例 11.2:消费 Lag 治理

#### 2.1 Lag 监控

```promql
# 关键告警
sum by (consumer_group) (kafka_consumergroup_lag) > 100000
```

#### 2.2 治理手段

| 措施 | 适用 | 收益 |
|------|------|------|
| 增加消费者实例 | 短时间处理能力不足 | 线性扩展(受分区数限制) |
| 异步消费 + 批处理 | 单条消息处理慢 | 5~10x 提升 |
| 跳过非关键消息 | 大促期间 | 临时降级 |
| 拆分 Topic | 不同业务混在一起 | 隔离干扰 |
| 提高 Producer 压缩率 | 带宽打满 | 节省 50% 带宽 |

#### 2.3 异步消费示例

```java
@KafkaListener(topics = "high-volume", concurrency = "8")
public void onMessage(List<ConsumerRecord<String, Event>> records,
                      Acknowledgment ack) {
    // 批量异步处理
    CompletableFuture.allOf(
        records.stream()
            .map(r -> CompletableFuture.runAsync(
                () -> process(r.value()), executor))
            .toArray(CompletableFuture[]::new)
    ).join();
    ack.acknowledge();
}
```

|----------|---------------------|------|

### 4. 经验总结

- **QPS 上不去**:先看 Producer batch/lz4,再看分区数,最后看 Broker IO
- **Lag 飙高**:消费者处理慢是元凶,先优化业务逻辑,再扩容
- **磁盘满**:分层存储 + 缩短保留时间 + 提高压缩率

## 十五、面试题速答

### 1. Kafka 在秒杀场景的核心价值?

> **削峰填谷**:瞬时 50,000 QPS 进入 Kafka,后台 Worker 按自身能力(4800 QPS)平稳消费,避免压垮数据库。配套 Redis 预扣库存防止超卖。

### 2. 如何保证 Kafka 消息不丢?

> **Producer**: `acks=all` + `enable.idempotence=true` + `max.in.flight.requests.per.connection<=5`
> **Broker**: `replication.factor>=3` + `min.insync.replicas>=2`
> **Consumer**: 关闭自动提交,处理成功后再手动 ack

### 3. Debezium 与业务双写对比?

> Debezium **无侵入**,不改业务代码;基于 binlog,可靠性高;但要求 binlog ROW 格式,且不能 DROP 大表。业务双写侵入性强,容易遗漏,适合单业务线。

### 4. Lambda 架构痛点?

> **双链路维护成本**(实时 + 离线),口径难一致;**资源浪费**(同一份数据算两次)。演进方向:**流批一体**(Iceberg/Hudi + Flink 流批统一 API)。

### 5. Event Sourcing 与普通事件驱动区别?

> 普通事件驱动:**消息触发后续动作**,事件可以丢。
> Event Sourcing:**事件是状态的唯一来源**,不能丢,需要快照加速回放。

### 6. Kafka 为什么不适合做请求/响应?

> Kafka 没有点对点寻址;消息广播给所有订阅者;延迟比 RPC 高;不适合事务性同步调用。**RPC 选 gRPC/HTTP,异步事件选 Kafka**。

### 7. MirrorMaker 2 vs 1?

> MM1 单 Connect Worker,**不能水平扩展**,topic 重命名有限制。MM2 基于 Connect 框架,**可水平扩展**,支持 ACL 同步、Offset 自动转换,推荐使用。

### 8. 百万 QPS 写入的关键参数?

> `linger.ms=20`、`batch.size=128KB`、`compression.type=lz4`、`acks=1`(非关键)、`partitions>=96`、`buffer.memory=512MB`。

### 9. 消费 Lag 怎么治理?

> 先看是 **Producer 太快** 还是 **Consumer 太慢**。Consumer 慢:优化业务 + 异步 + 批处理 + 增加实例(受分区数限制)。Producer 太快:限流 + 采样 + 拆分。

### 10. KRaft vs Zookeeper?

> KRaft(Kafka 3.3+)是**官方新架构**:无 ZK 依赖、Controller 选举更快(秒级 vs 几十秒)、部署简单、可扩展到 100 万分区。**新集群直接用 KRaft**,旧集群升级路径清晰。
