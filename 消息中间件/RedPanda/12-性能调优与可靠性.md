# RedPanda 性能调优与可靠性

## 一、性能调优概述

### 1.1 RedPanda 与 Kafka 调优的本质差异

RedPanda 的 C++ 实现 + Seastar 异步框架 + thread-per-core 架构,使其性能调优哲学与 Kafka **截然不同**。理解这些差异,是开始 RedPanda 调优的前提。

```text
┌──────────────────────────┬──────────────────────────┬──────────────────────────┐
│         维度             │        Kafka             │       RedPanda           │
├──────────────────────────┼──────────────────────────┼──────────────────────────┤
│ 运行时                   │  JVM + ZooKeeper/KRaft   │  C++ 单二进制,无外部依赖 │
│ GC 影响                  │  关键调优点              │  ★ 不存在 GC            │
│ 线程模型                 │  共享线程池              │  thread-per-core(每核 1) │
│ IO 模型                  │  Java NIO / epoll       │  Seastar / io_uring      │
│ 内存模型                 │  JVM Heap + Page Cache   │  自管内存 + Page Cache   │
│ 副本协议                 │  ISR(动态)              │  Raft(强一致)            │
│ 默认压缩                 │  none                    │  ★ 默认 lz4             │
│ 默认 acks                │  1                       │  ★ 默认 all             │
│ 默认 idempotent          │  false                   │  ★ 默认 true            │
│ 默认 retention           │  7 天                    │  7 天,但 Tiered 无限     │
│ 调优复杂度               │  ★★★★★                 │  ★★★                    │
│ 性能基线                 │  1x                      │  5-10x                   │
│ P99 延迟基线             │  8-15 ms                 │  ★ < 5 ms               │
└──────────────────────────┴──────────────────────────┴──────────────────────────┘
```

**核心差异**:RedPanda **默认就是 Kafka 调优后的状态**。`acks=all`、`enable.idempotence=true`、`compression.type=lz4`、`retries=MAX` 在 RedPanda 中是**出厂默认值**,不需要手动开启。这意味着 RedPanda 的性能调优"基线"远高于 Kafka,但仍有许多可调空间。

### 1.2 RedPanda 调优目标

RedPanda 调优同样需要平衡四个维度,但因为底层架构已经优秀,主要工作是**让硬件和操作系统匹配 Seastar 的 thread-per-core 模型**。

- **吞吐量 (Throughput)**:单分区可承载 GB/s 级(同 Kafka 单分区上限的 5-10 倍)
- **延迟 (Latency)**:P99 < 5ms 是常态,极致场景可 < 1ms
- **持久性 (Durability)**:默认 `acks=all` + Raft 强一致,无数据丢失风险
- **资源效率 (Resource Efficiency)**:相同吞吐下,CPU/内存占用约为 Kafka 的 1/3

```text
                          ▲
                         ╱ ╲
                        ╱   ╲
                       ╱ 业务 ╲          ← 业务设计:消息大小、批量、压缩
                      ╱───────╲
                     ╱  Topic  ╲        ← 分区数、副本数、retention.ms
                    ╱  设计层   ╲
                   ╱─────────────╲
                  ╱   客户端参数   ╲      ← Producer/Consumer(rpk / Kafka 客户端)
                 ╱   (应用层)      ╲
                ╱───────────────────╲
               ╱  redpanda.yaml     ╲   ← Seastar / Raft / 分层存储
              ╱      (Broker 层)      ╲
             ╱─────────────────────────╲
            ╱      进程资源隔离          ╲  ← cgroup / CPU 亲和 / 内存池
           ╱─────────────────────────────╲
          ╱       操作系统 / 文件系统       ╲ ← ulimit、swappiness、XFS
         ╱─────────────────────────────────╲
        ╱            硬件 / 网络             ╲ ← NVMe、网卡、Jumbo Frame
       ╱─────────────────────────────────────╲

       RedPanda: 上层(80%)同等重要
       RedPanda: 底层(OS/硬件)权重更高(无 JVM 屏蔽)
```

### 1.3 调优方法论

```text
1. 定目标: SLA 是什么?
   - 峰值吞吐: 1 GB/s?
   - P99 延迟: < 5ms?
   - 可用性: 99.99%?

2. 测基线: 当前什么水平?
   - rpk topic produce-perf 跑一遍
   - 记录 records/sec、MB/sec、p99

3. 看 Seastar 内部指标(核心!)
   - rpk redpanda admin api 查看
   - /metrics 接口(Prometheus 格式)

4. 看 OS 指标
   - iostat、vmstat、netstat、sar
   - perf top / bpftrace(线程级)

5. 分析瓶颈
   - 单核 CPU 跑满 → 调 batch / 压缩
   - Page Cache 命中率低 → 加大内存
   - 网络 P99 高 → 调 TCP buffer / RSS

6. 改一处, 测改进
7. 继续优化
```

**特别提示**:`rpk redpafka admin api` 和 `rpk redpanda status` 是 RedPanda 调优的核心工具,**先熟悉再调参**。

### 1.4 RedPanda 调优"反直觉"清单

```text
不要做的事:
  - 调整 num.io.threads(Kafka 有,RedPanda 没有,Seastar 自管)
  - 调整 num.network.threads(同上)
  - 调整 JVM 参数(没有 JVM)
  - 设置 log.flush.interval.ms(RedPanda 用 seastar disk IO 控制)

要做的事:
  - 调整线程亲和性(线程绑核)
  - 调整内存总量(reserved_memory / memory)
  - 启用 io_uring
  - 配置 Raft 参数
  - 配置 Tiered Storage
```

## 二、硬件选型与服务器调优

RedPanda 的 thread-per-core 架构对硬件非常敏感,**CPU 核数 > CPU 频率 > 内存频率**。

### 1. CPU 选择

#### 1.1 核数比频率重要

RedPanda 一个 shard(分片)对应一个核,**单分区吞吐与单核性能强绑定**。

```text
  单分区吞吐 vs 单核频率:
  
  3.0 GHz 单核:  ~500 MB/s 单分区
  2.5 GHz 单核:  ~420 MB/s 单分区
  2.0 GHz 单核:  ~330 MB/s 单分区
  
  16 核 @ 2.5GHz vs 8 核 @ 3.0GHz:
    - 16 核: 16 × 420 = 6720 MB/s(理论上限)
    - 8 核:  8 × 500  = 4000 MB/s
    - 优先选多核!
```

#### 1.2 推荐 CPU 型号

| 用途 | 推荐 | 核数 | 备注 |
|------|------|------|------|
| **开发/测试** | Intel Xeon E 系列 8 核 | 8 核 | 性价比 |
| **生产 - 中小** | AMD EPYC 7003/9004 系列 | 16-32 核 | 高核数 + 高性价比 |
| **生产 - 大规模** | Intel Xeon Scalable 4 代/5 代 | 24-48 核 | 高单核 + AVX-512 |
| **极致性能** | AWS Graviton 3/4(ARM) | 64 核 | 同价格多 30% 核 |

**关键参数**:
- 启用 **AVX-512**(压缩加速 2-3x)
- 启用 **NUMA 平衡**(`numactl --interleave=all`)
- 关闭超线程?——**保持开启**,RedPanda 已经知道哪些线程共享核

#### 1.3 CPU 亲和性配置

RedPanda Seastar 自动绑核,但可以手动验证:

```bash
# 查看 RedPanda 进程绑核情况
ps -eo pid,comm,psr | grep redpanda

# 手动绑核(可选,rpk 已经自动做了)
taskset -cp 0-15 <redpanda_pid>
```

### 2. 内存配置

RedPanda 内存由两部分组成:**用户态内存池** + **OS Page Cache**。

```text
  物理内存 64GB 推荐分配:
  ┌────────────────────────────┐
  │ Page Cache:  40-50 GB  (60-80%)│  ← 操作系统管理, 用于缓存 log
  ├────────────────────────────┤
  │ RedPanda 内存池: 12-16 GB │  ← Seastar memory 分配
  ├────────────────────────────┤
  │ 系统 / 其他:   4-6 GB     │
  └────────────────────────────┘
```

**为什么 Page Cache 比例这么高**:RedPanda 同 Kafka,大量读依赖 Page Cache(`read-ahead`、`drop-behind`)。

#### 2.1 redpanda.yaml 内存配置

```yaml
# 总预留内存(Seastar 内存池上限)
# 推荐: 物理内存的 20-30%
reserved_memory: 17179869184   # 16GB

# Page Cache 由 OS 自动管理,RedPanda 不直接控制
# 但可以通过下列参数影响 Page Cache 行为:
```

#### 2.2 内存与并发

```text
  内存池大小 vs 单分区吞吐:
  
  16 GB 内存池:  支持 ~ 5000 分区, ~10 GB/s 集群吞吐
  32 GB 内存池:  支持 ~ 12000 分区, ~25 GB/s 集群吞吐
  64 GB 内存池:  支持 ~ 25000 分区, ~50 GB/s 集群吞吐
  
  注: 分区数还受单分区日志大小、retention、replication 影响
```

### 3. 磁盘选择

RedPanda **强制使用 XFS**,推荐 NVMe SSD。

| 磁盘类型 | 顺序读 MB/s | 顺序写 MB/s | IOPS | 延迟 | 价格/TB | 推荐度 |
|----------|-------------|-------------|------|------|---------|--------|
| **HDD 7200** | 200 | 200 | 75-150 | 5-10 ms | 低 | 仅开发 |
| **SATA SSD** | 550 | 500 | 50K-100K | < 0.1 ms | 中 | 一般 |
| **NVMe SSD** | 3000-7000 | 2000-5000 | 100K-500K | < 0.05 ms | 中高 | **生产推荐** |
| **NVMe Gen5** | 12000+ | 10000+ | 1M+ | < 0.03 ms | 高 | 极致性能 |

#### 3.1 多盘配置 (JBOD)

```yaml
# redpanda.yaml
# 多块磁盘,RedPanda 自动将不同 partition 分散到不同盘
data_directory: /var/lib/redpanda/data
# 或者多目录(推荐,每块盘一个目录)
# 注意: RedPanda 不直接支持 log.dirs 多目录语法,使用 mount bind
```

```bash
# 推荐挂载方式: 每块盘独立挂载点
/dev/nvme0n1  /var/lib/redpanda/data0  xfs  noatime,allocsize=64m  0 0
/dev/nvme1n1  /var/lib/redpanda/data1  xfs  noatime,allocsize=64m  0 0
/dev/nvme2n1  /var/lib/redpanda/data2  xfs  noatime,allocsize=64m  0 0

# 或者用 mdadm JBOD(不要 RAID5/6,理由同 Kafka)
mdadm --create /dev/md0 --level=linear --raid-devices=4 /dev/nvme[0-3]n1
```

#### 3.2 磁盘 IO 调度器

```bash
# NVMe: 推荐 none 或 mq-deadline
echo none > /sys/block/nvme0n1/queue/scheduler

# SATA SSD: mq-deadline
echo mq-deadline > /sys/block/sda/queue/scheduler

# 调整队列深度
echo 1024 > /sys/block/nvme0n1/queue/nr_requests
```

### 4. 网络选择

RedPanda 强依赖网络,**10 Gbps 是底线,25/100 Gbps 推荐**。

| 业务规模 | 推荐网络 | 吞吐上限 |
|----------|----------|----------|
| 开发测试 | 1 Gbps | ~ 100 MB/s |
| 中小生产 | **10 Gbps** | ~ 1 GB/s |
| 大规模生产 | **25 Gbps** | ~ 2.5 GB/s |
| 极致性能 | **100 Gbps** | ~ 10 GB/s |

#### 4.1 网卡多队列 (RSS)

```bash
# 查看网卡队列数
ethtool -l eth0
# combined 8

# 启用 RSS(接收端缩放)
ethtool -K eth0 rxhash on
ethtool -K eth0 ntuple on

# 调整 IRQ 亲和性
systemctl status irqbalance
# irqbalance 服务必须运行
```

## 三、操作系统调优

RedPanda 对 OS 的依赖比 Kafka 更重(因为没有 JVM 缓冲),OS 调优是必经步骤。

### 1. 文件描述符与进程限制

```bash
# /etc/security/limits.d/99-redpanda.conf
*       soft    nofile  1048576
*       hard    nofile  1048576
*       soft    nproc   65536
*       hard    nproc   65536

# systemd 级别(更可靠)
# /etc/systemd/system/redpanda.service.d/override.conf
[Service]
LimitNOFILE=1048576
LimitNPROC=65536
LimitMEMLOCK=infinity
LimitCORE=infinity
```

**为什么需要这么多 FD**:
```text
10000 分区 × 3 副本 × (1 log + 1 index + 1 compaction) ≈ 90000 FD
+ 连接 socket(每客户端 1 个) ≈ 100000+ FD
+ 内核连接跟踪、文件等
```

### 2. vm.swappiness

```bash
# 强烈推荐 1(Kafka 也是)
sysctl -w vm.swappiness=1

# /etc/sysctl.d/99-redpanda.conf
vm.swappiness = 1
```

**为什么是 1 不是 0**:值为 0 时 OOM Killer 更激进,值为 1 给内核保留最小 swap 兜底。

### 3. 网络参数

```bash
# /etc/sysctl.d/99-redpanda.conf

# TCP 连接队列
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# TCP 缓冲区(RedPanda 推荐)
net.core.rmem_default = 262144
net.core.wmem_default = 262144
net.core.rmem_max = 16777216      # 16MB
net.core.wmem_max = 16777216      # 16MB
net.ipv4.tcp_rmem = 4096 65536 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# TIME_WAIT 优化
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15

# 连接跟踪
net.ipv4.tcp_max_tw_buckets = 524288
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_sack = 1
net.ipv4.tcp_window_scaling = 1

# 高吞吐
net.core.netdev_max_backlog = 250000
net.ipv4.tcp_no_metrics_save = 1
net.ipv4.tcp_congestion_control = cubic

# 应用
sudo sysctl -p /etc/sysctl.d/99-redpanda.conf
```

### 4. 文件系统

**强制使用 XFS**(RedPanda 官方明确要求)。

```bash
# 格式化
mkfs.xfs -f -L redpanda /dev/nvme0n1

# 挂载选项
# /etc/fstab
UUID=xxx  /var/lib/redpanda  xfs  noatime,allocsize=64m,noikeep  0 0

# 重要选项说明:
#   noatime     - 不更新文件访问时间(关键!)
#   allocsize=64m - 预分配空间, 减少碎片
#   noikeep     - 不保留空 inode(节省空间)
#   logbufs=8   - 增加日志缓冲区
#   logbsize=256k - 增加日志块大小
```

**为什么不用 ext4 / ZFS / BTRFS**:
```text
ext4:  - 不支持 reflink, Tiered Storage upload 慢
        - 大目录性能下降
ZFS:   - ARC 缓存与 Page Cache 双重缓存, 内存浪费
        - 不在官方支持列表
BTRFS: - CoW 不适合顺序追加写
        - 不在官方支持列表
```

### 5. Huge Pages

```bash
# 关闭透明大页(THP) - RedPanda Seastar 自管内存, THP 会干扰
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# /etc/rc.local 或 systemd 启动脚本
```


#### 1.1 IO 类配置

```yaml
# IO 后台任务优先级
# 通过 rpk 配置 IO 调度(参见后面 IO 调度章节)
```

#### 1.2 Reactor 配置

**关键参数**:

### 2. 内存池

#### 2.1 reserved_memory 配置

```yaml
# redpanda.yaml
# 这是 Seastar 内存池的总上限
# 注意: 这部分内存从 Page Cache 中扣除

# 实际启动参数: --memory=17179869184 --reserve-memory=2G
```

#### 2.2 内存分配器选择

```bash
# RedPanda 内部使用 jemalloc(默认)
# 在 /etc/redpanda/redpanda.env 中:
MALLOC_CONF="background_thread:true,metadata_thp:auto,dirty_decay_ms:9000000000,muzzy_decay_ms:9000000000"
```

**jemalloc 调优核心**:
- `background_thread:true` - 启用后台 GC 线程
- `metadata_thp:auto` - 元数据使用透明大页
- `dirty_decay_ms / muzzy_decay_ms` - 延迟释放,减少持续分配开销

### 3. IO 调度

### 4. 进程资源隔离 (cgroup v2)

```bash
# /etc/systemd/system/redpanda.service.d/override.conf

```

## 五、Topic 设计调优

### 1. 分区数选择

分区数选择逻辑与 Kafka 类似,但 RedPanda 因为单核性能强,**单分区吞吐上限更高**。

```text
  分区数与吞吐的关系(RedPanda):
  
  吞吐 ↑
       │       ╱──── 线性增长区
       │      ╱
       │     ╱
       │    ╱──── 趋于稳定(> 64 分区后边际收益小)
       │   ╱
       │  ╱
       └────────────────────→ 分区数
  
  RedPanda 单分区吞吐参考:
    - NVMe + 调优:  300-800 MB/s
    - SATA SSD:     100-300 MB/s
    - HDD:          30-80 MB/s
```

#### 1.1 分区数计算公式

```text
分区数 = max(
    目标吞吐 / 单分区吞吐,
    消费者实例数,
    生产者实例数 × 写并行度
)

单分区吞吐参考值(RedPanda):
  - NVMe SSD + 调优: 500 MB/s
  - SATA SSD:        200 MB/s
  - HDD:             50 MB/s

示例: 
  目标 5 GB/s, 单分区 500 MB/s
  → 需要 10 个分区
  → 加上冗余和未来扩展, 选 16-32 分区
  → 考虑消费者实例 20 个, 选 max(10, 20) = 20 分区
  → 最终: 32 分区
```

#### 1.2 创建 Topic 命令

```bash
rpk topic create orders \
  --partitions 32 \
  --replicas 3 \
  --config retention.ms=604800000 \
  --config segment.ms=3600000 \
  --config compression.type=zstd
```

### 2. 副本数选择

```yaml
# redpanda.yaml 全局默认副本数
default_topic_partitions: 1
default_topic_replications: 3   # 默认 3 副本
```

| 副本数 | 可靠性 | 延迟影响 | 适用 |
|--------|--------|----------|------|
| 1 | 最低 | 最低 | 开发测试 |
| **3** | **生产标准** | **中等** | **生产推荐** |
| 5 | 极高 | 高 | 金融级 |

**RedPanda 副本机制特点**:
- Raft 强一致,**所有副本同步才返回 ack**
- 副本数增加 1,延迟线性增加 1-2ms
- 推荐 3 副本,核心数据可考虑 5 副本

### 3. 分区键设计

同 Kafka,**避免数据倾斜**:

```bash
# 热点 key 检测
rpk topic describe orders
# 查看各分区的消息速率分布

# 自定义分区器(Java 客户端)
public class HashPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        return Math.abs(Murmur2.hash(keyBytes)) % cluster.partitionCountForTopic(topic);
    }
}
```

## 六、Producer 调优

RedPanda 完全兼容 Kafka Producer,客户端参数 90% 与 Kafka 相同,但有几个**RedPanda 特有**的优化点。

### 1. 核心参数(与 Kafka 类似)

#### 1.1 batch.size

```properties
# 默认 16KB, RedPanda 推荐 128KB - 1MB
# 因为 RedPanda 单分区吞吐高, 可以用更大 batch
batch.size = 131072    # 128KB
```

#### 1.2 linger.ms

```properties
# 默认 0, 推荐 5-20ms
# RedPanda 因为 Raft 同步开销固定, linger 影响相对更小
linger.ms = 10
```

#### 1.3 compression.type

```properties
# RedPanda 支持: none, gzip, snappy, lz4, zstd, zstd-secure
# 默认 lz4, 推荐 zstd(压缩比更高, AVX-512 加速)
compression.type = zstd
```

**RedPanda 压缩算法对比**:

| 算法 | 压缩比 | CPU 开销 | 速度 | 推荐度 |
|------|--------|----------|------|--------|
| none | 1x | 0 | 最快 | 不推荐 |
| gzip | 3-4x | 高 | 慢 | 归档 |
| snappy | 2x | 中 | 快 | 一般 |
| lz4 | 2-3x | 低 | **最快** | 默认 |
| **zstd** | 3-4x | 中 | **快** | **推荐** |
| zstd-secure | 3-4x | 高 | 中 | 加密压缩 |

#### 1.4 acks

```properties
# RedPanda 推荐 acks=all
# 但 RedPanda 有"client only"模式,允许更细粒度控制
acks = all
```

**RedPanda acks 行为**:
- `acks=0`:不等待,最快但可能丢数据
- `acks=1`:等 Leader 落盘,中等(Leader 故障可能丢)
- `acks=all`:等所有副本落盘,**最安全(RedPanda 默认)**

#### 1.5 enable.idempotence

```properties
# RedPanda 客户端默认 true
# 防止 Producer 重试导致重复消息
enable.idempotence = true
```

## 十四、可靠性保证

### 1. 写入可靠性

## 十七、实战案例:百万 QPS 优化

### 1. 背景

某金融支付公司,订单系统需要处理**峰值 100 万 QPS**(1KB 消息),要求 P99 < 10ms。原 Kafka 集群(P99 35ms,峰值 250MB/s)无法满足,迁移到 RedPanda。

### 2. 初始基线

```bash
# 第一次压测
rpk topic produce-perf \
  --topic orders \
  --num-records 10000000 \
  --record-size 1024 \
  --throughput -1

# 结果
# 650000 records/sec, 635 MB/sec, avg 5.2 ms, p99 8.5 ms
# 离目标 100 万 QPS 还差 35%
```

### 3. 瓶颈诊断

```bash
# 1. 检查 OS
iostat -x 1
# nvme0n1: %util 45%, await 0.8 ms  → 磁盘健康
# nvme1n1: %util 38%

vmstat 1
# CPU: 75% idle     → CPU 健康
# si/so: 0           → 无 swap

sar -n DEV 1
# eth0: 6.5 Gbps    → 网络接近 70% 占用, 瓶颈!

# 2. 检查 RedPanda
rpk redpanda status
# 3 节点, 各 16 核, 内存 32GB
# 都健康
```

**结论**:网络是瓶颈(10Gbps 网卡用满)。

### 4. 优化步骤

#### 4.1 第一轮:网卡升级 + 网络调优

```bash
# 1. 升级到 25Gbps 网卡
# 2. 启用 Jumbo Frame
ip link set eth0 mtu 9000

# 3. 调整 TCP 缓冲区
sysctl -w net.core.rmem_max=33554432   # 32MB
sysctl -w net.core.wmem_max=33554432
```

**效果**: 65 万 → **85 万 records/sec**

#### 4.2 第二轮:Producer 调优

```java
// 修改前
batch.size = 16384        // 16KB
linger.ms = 0
compression.type = lz4

// 修改后
batch.size = 524288       // 512KB
linger.ms = 5
compression.type = zstd
buffer.memory = 268435456  // 256MB
```

**效果**: 85 万 → **110 万 records/sec** ✓

#### 4.3 第三轮:Topic 分区扩容

```bash
# 分区从 16 扩到 48
rpk topic alter orders --partitions 48
```

**效果**: 110 万 → **125 万 records/sec**

#### 4.4 第四轮:启用 Tiered Storage + OS 调优

```yaml
# redpanda.yaml
cloud_storage_enabled: true
cloud_storage_cache_size: 10737418240
```

```bash
# 关闭 THP, 调整 swappiness
echo never > /sys/kernel/mm/transparent_hugepage/enabled
sysctl -w vm.swappiness=1
```

**效果**: 125 万 → **135 万 records/sec**,磁盘空间节省 70%

#### 4.5 第五轮:添加节点

```bash
# 集群从 3 节点扩到 5 节点
# 每节点 32 核 + 64GB
```

**效果**: 135 万 → **180 万 records/sec**,冗余度提升

### 5. 优化效果汇总

```text
初始 (3 节点, 16核, 32GB, 默认配置):
  65 万 records/sec,  P99 8.5 ms
  
  ↓ 网卡升级 (10G → 25G) + Jumbo Frame
  85 万 records/sec,  P99 7.2 ms
  
  ↓ Producer 调优 (batch 16K→512K, linger=5, zstd)
  110 万 records/sec, P99 5.8 ms
  
  ↓ Topic 分区扩容 (16 → 48)
  125 万 records/sec, P99 5.2 ms
  
  ↓ Tiered Storage + OS 调优
  135 万 records/sec, P99 4.8 ms
  
  ↓ 集群扩容 (3 节点 → 5 节点)
  180 万 records/sec, P99 4.5 ms  ✓ 达成目标!
```

**关键收益**:
- 吞吐提升 **2.77 倍**(65万 → 180万)
- P99 延迟降低 **47%**(8.5ms → 4.5ms)
- 磁盘成本降低 **70%**(Tiered Storage)
- 满足 100 万 QPS 业务目标,留有 80% 冗余

### 6. 经验教训

```text
1. RedPanda 默认配置已经很好, 主要工作在上层
2. 网络瓶颈在 10Gbps 时容易出现, 提前规划 25G
3. Producer batch 调到 512KB 后收益明显, 但再大收益递减

```

## 十八、核心要点速记

### 1. RedPanda vs Kafka 调优差异

```text
Kafka 调优重点:               RedPanda 调优重点:
  - JVM 堆 / GC                  - 内存池(reserved_memory)
  - num.io.threads               - io_uring 后端
  - log.flush.interval           - Raft 心跳 / 选举
  - 副本拉取线程                 - Tiered Storage 缓存
  - broker 端代码路径            - Seastar 自动调优

RedPanda 默认即 Kafka 调优后:
  acks=all        ✓
  lz4 压缩        ✓
  idempotent      ✓
  high watermark  ✓
```

### 2. 调优金字塔

```text
业务设计 → Topic 设计 → 客户端参数 → redpanda.yaml → OS → 硬件

RedPanda 特点:
  - 越往上性价比越高(同 Kafka)
  - 但 OS / 硬件权重更高(没有 JVM 屏蔽)
  - Tiered Storage 是 RedPanda 独有的杀手锏
```

### 3. 关键参数速记

| 参数 | 默认 | 推荐 | 提升 |
|------|------|------|------|
| `batch.size` | 16KB | 512KB | 吞吐 ×5-10 |
| `linger.ms` | 0 | 5-10 | 吞吐 ×2-3 |
| `compression.type` | lz4 | zstd | 吞吐 ×3 + 网络减半 |
| `fetch.min.bytes` | 1B | 1-10KB | Consumer ×2-5 |
| `reserved_memory` | 物理 × 80% | 物理 × 25-30% | 避免 OOM |
| `vm.swappiness` | 60 | 1 | 避免 swap |

### 4. 调优口诀

- **核多频高** — RedPanda 吃多核,16+ 起步
- **内够盘快** — 内存 32GB+, NVMe SSD 标配
- **网快隔流** — 25Gbps+, 客户端/集群流量分离
- **压快批大** — zstd 压缩 + 128KB+ batch
- **分区分散** — 多分区 + 多磁盘 + 多节点
- **T 存储强** — Tiered Storage 开启
- **监控先行** — 默认即好, 监控保稳

### 5. 性能基线参考

```text
RedPanda 默认(3 节点 NVMe):
  写入: ~ 600 MB/s
  P99:  ~ 8 ms
  
RedPanda 调优(同硬件):
  写入: ~ 1500 MB/s (2.5x)
  P99:  ~ 5 ms
  
RedPanda 极致(集群扩容 + 25G 网):
  写入: ~ 3000+ MB/s
  P99:  ~ 3 ms
  
Kafka 调优(同硬件对照):
  写入: ~ 300 MB/s (1/5)
  P99:  ~ 15 ms (3x)
```

### 6. 排查流程

```text
1. 现象: 吞吐不达预期 / 延迟高 / Lag 积压
2. 压测: rpk topic produce-perf 跑基线
3. OS 指标: iostat / vmstat / sar / netstat
4. RedPanda 指标: /metrics 端点 / rpk redpanda status
5. 定位瓶颈: CPU(单核满) / 磁盘(util 100%) / 网络(带宽满)
6. 一处优化, 一次只改一个参数
7. 对比基线, 验证有效
8. 继续循环
```

### 7. 黄金法则

1. **先测量后优化** — 没有数据不要改参数
2. **一次改一处** — 避免蝴蝶效应
3. **从上层到下层** — 业务问题占 80%
4. **Producer 优先** — 投入小收益大
5. **可靠性是基础** — RedPanda 默认就好,不要破坏
6. **监控全覆盖** — 没有监控就没有优化
7. **Tiered Storage 是杀手锏** — 大幅降低存储成本
8. **业务驱动** — 性能服务于业务 SLA

### 8. 一句话总结

> **RedPanda 默认即 Kafka 调优后,主要调优空间在硬件匹配(Tiered Storage + NVMe + 25G 网)和 Producer 批量化(zstd + 大 batch), 99% 的性能问题可以通过这两层解决。**
