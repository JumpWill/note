# RedPanda 集群部署与扩展

## 一、集群部署概述

### 1.1 部署模式分类

RedPanda 与 Kafka/ZK 体系的根本不同在于:它把 Raft 共识、存储、计算都集成到了单一二进制 `redpanda`,**没有 ZooKeeper,没有 Controller/Broker 分离的概念**,所有节点天然既是数据节点也是元数据节点。这让 RedPanda 的部署模型显著简化。

| 模式 | 协调组件 | 数据节点数 | 推荐场景 |
|------|----------|-----------|----------|
| **单节点开发模式** | 内置 Raft(单副本) | 1 | 本地开发、功能验证 |
| **3 节点生产集群** | 内置 Raft | 3 | 中小生产、起步阶段 |
| **5+ 节点大规模** | 内置 Raft | 5/7/9+ | 高吞吐、核心链路 |
| **多区域/混合云** | 内置 Raft + Tiered Storage | 跨 AZ/Region | 异地多活、灾备 |
| **Kubernetes** | Operator + Helm | 任意 | 云原生、弹性伸缩 |
| **Shadow Link** | 内置 Raft + 远程同步 | 任意 | 跨集群数据复制(RedPanda 特色) |

### 1.2 节点特性

RedPanda 是 C++ 实现的单进程服务,**所有节点同质**,无 Controller/Broker 区分:

```text
┌─────────────────────────────────────────────────────────────┐
│                   RedPanda 节点统一角色                     │
├─────────────────────────────────────────────────────────────┤
│  • 数据节点:负责 Partition 的生产/消费 IO、存储、日志       │
│  • Raft 参与者:每个 Partition 的 3 副本(默认)共同投票     │
│  • Controller 候选:集群元数据变更通过内部 topic 走 Raft    │
│  • Admin 暴露:HTTP Admin API 用于管控(rpk 调用入口)        │
│  • Schema Registry:Wasm/Schema 内嵌(可选启动)              │
│  • Iceberg Sink:数据入湖(可选集成)                          │
│                                                             │
│  没有 ZooKeeper!没有 KRaft controller 进程!                 │
│  一台机器即一个完整的 Raft peer                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 集群规模选型

| 集群规模 | 推荐节点数 | 适用 QPS 量级 | 典型场景 |
|----------|-----------|---------------|----------|
| 单节点开发 | 1 | < 1 万 | 本地调试、CI 测试 |
| 小型生产 | 3 | < 10 万 | 创业公司初期、内部系统 |
| 中型生产 | 5 | 10~50 万 | 中等业务规模 |
| 大型生产 | 7~9 | 50~200 万 | 核心链路、海量日志 |
| 超大规模 | 15+ | 200 万+ | 跨 AZ、多区域 |
| 灾备/聚合 | 多集群 | 任意 | Shadow Link 跨集群 |

## 二、节点规划

### 2.1 机器规格

RedPanda 是 IO/网络密集型服务,对 CPU 单核性能、磁盘 IOPS、网络带宽要求都很高。

| 维度 | 最低 | 推荐 | 备注 |
|------|------|------|------|
| **CPU** | 4 核 | 8~16 核(高主频) | 优先单核性能,RedPanda 是单进程多线程 |
| **内存** | 8 GB | 32~64 GB | 用于 PageCache、连接缓冲、批量处理 |
| **磁盘** | 100 GB SSD | 1~4 TB NVMe SSD | Tiered Storage 可下沉到对象存储 |
| **网络** | 千兆 | 万兆(10GbE)+ | 跨节点复制 + 客户端 IO,带宽常是瓶颈 |
| **文件描述符** | 65536 | 131072 | 每个连接、每个文件都要 FD |

#### CPU 选型特别注意

RedPanda 主线程模型对 **CPU 单核频率** 非常敏感,大量使用 `seastar` 框架的 share-nothing 架构。

- **首选**:高主频 Intel Xeon(如 3.5GHz+ 的 Gold 系列)或 AMD EPYC(高频型号)
- **次选**:核心数多但主频低的型号(如 32 核 2.0GHz),吞吐量不升反降
- **云上**:AWS `c6i.4xlarge`(16 核 3.5GHz)、阿里云 `ecs.c7.4xlarge`
- **ARM/Graviton**:RedPanda 已支持 ARM64,Graviton3 比同价位 x86 性能高 30%+

#### 内存分配参考

```text
┌─────────────────────────────────────────────┐
│  64GB 内存分配建议                            │
├──────────────┬──────────────────────────────┤
│  OS/PageCache│  20 GB(供内核缓存热数据)    │
├──────────────┼──────────────────────────────┤
│  RedPanda RSS│  16~24 GB(批处理、网络缓冲) │
├──────────────┼──────────────────────────────┤
│  Admin/工具  │  1~2 GB                     │
├──────────────┼──────────────────────────────┤
│  预留        │  8~16 GB(故障/突发流量)     │
└──────────────┴──────────────────────────────┘
```

### 2.2 操作系统调优

RedPanda 官方提供 `rpk system tune` 命令一键调优,所有节点执行一次即可。

#### ulimit 调优

```bash
# 文件描述符
cat >> /etc/security/limits.conf << 'EOF'
*  soft  nofile      131072
*  hard  nofile      131072
*  soft  nproc       65536
*  hard  nproc       65536
EOF

# 重新登录生效
ulimit -n 131072
```

#### sysctl 调优

```bash
cat >> /etc/sysctl.conf << 'EOF'
# 虚拟内存
vm.swappiness=1
vm.dirty_background_ratio=5
vm.dirty_ratio=40

# 网络
net.core.somaxconn=4096
net.ipv4.tcp_max_syn_backlog=4096
net.core.netdev_max_backlog=250000
net.ipv4.tcp_rmem=4096 87380 16777216
net.ipv4.tcp_wmem=4096 65536 16777216
net.ipv4.tcp_congestion_control=BBR

# 文件系统
fs.file-max=2097152
fs.nr_open=1048576
EOF
sysctl -p
```

#### XFS 文件系统

RedPanda 推荐使用 **XFS** 存放数据目录(`/var/lib/redpanda/data`)。

```bash
# 创建挂载(数据盘示例 /dev/nvme1n1)
mkfs.xfs -f /dev/nvme1n1
mkdir -p /var/lib/redpanda/data
mount -o noatime,nodiratime,allocsize=64m /dev/nvme1n1 /var/lib/redpanda/data

# 写入 fstab
echo "UUID=$(blkid -s UUID -o value /dev/nvme1n1) /var/lib/redpanda/data xfs noatime,nodiratime,allocsize=64m 0 2" >> /etc/fstab
```

| 文件系统 | 是否推荐 | 备注 |
|----------|----------|------|
| XFS | **强烈推荐** | 高并发写、空间预分配 |
| ext4 | 可用 | 性能略低,小集群可接受 |
| ZFS | 不推荐 | 性能损耗 30%,且有 CoW 副作用 |
| Btrfs | 不推荐 | 同上 |

#### 一键调优(rpk)

```bash
# 自动检测并调优当前节点(需要 root 或 sudo)
sudo rpk system tune

# 查看当前是否已调优
sudo rpk system tune --check
```

## 三、单节点开发环境

最常见的本地开发模式,用于功能测试、SDK 调试、demo 验证。

### 3.1 单节点模式启动

```bash
# 方式 1:直接用 rpk 启动(自动生成 redpanda.yaml)
rpk redpanda start \
  --overprovisioned \
  --smp 4 \
  --memory 4G \
  --reserve-memory 0M \
  --node-id 0 \
  --check=false

# 方式 2:docker 单节点
docker run -d --name=redpanda \
  --network=host \
  -e RP_NODE_ID=0 \
  -e RP_KAFKA_API=PLAINTEXT://0.0.0.0:9092 \
  -e RP_ADMIN=0.0.0.0:9644 \
  docker.redpanda.com/redpandadata/redpanda:latest \
  redpanda start --overprovisioned --smp 1 --memory 1G --reserve-memory 0M --node-id 0 --check=false
```

### 3.2 关键参数说明

| 参数 | 含义 | 推荐值 |
|------|------|--------|
| `--overprovisioned` | 关闭 CPU/内存资源检查(单节点/CI 场景) | 开发:开启;生产:关闭 |
| `--smp N` | RedPanda 进程可用的 CPU 核数 | 等于物理核数(生产) |
| `--memory GB` | RedPanda 进程可用的内存 | 总内存的 60% |
| `--reserve-memory MB` | 给 OS PageCache 预留的内存 | 通常 0(开发)或总内存 25%(生产) |
| `--node-id` | 节点唯一 ID(集群内必须唯一) | 0/1/2/... |
| `--check=false` | 跳过启动前的资源检查 | 开发调试用 |

### 3.3 验证单节点

```bash
# 查看集群状态
rpk cluster info
# 输出:
# CLUSTER
# =======
# redpanda.4a8b9c... (localhost:9092)
#
# 0 live nodes, 0 partitions

# 创建 topic 测试
rpk topic create test-topic -p 3 -r 1
rpk topic list
rpk topic produce test-topic <<< "hello redpanda"
rpk topic consume test-topic --num 1
```

## 四、3 节点生产集群(最常见)

### 4.1 节点规划

| 主机名 | IP | node.id | 角色 | Kafka 端口 | Admin 端口 |
|--------|-----|---------|------|-----------|-----------|
| rp-node-01 | 10.0.1.11 | 0 | broker+raft | 9092 | 9644 |
| rp-node-02 | 10.0.1.12 | 1 | broker+raft | 9092 | 9644 |
| rp-node-03 | 10.0.1.13 | 2 | broker+raft | 9092 | 9644 |

**所有节点同质**,没有 controller/broker 之分。3 节点是最小高可用配置,可容忍 1 节点故障。

### 4.2 完整 redpanda.yaml 配置

`/etc/redpanda/redpanda.yaml`(三台通用,仅 `node_id` 不同):

```yaml
# ============ 集群标识 ============
redpanda:
  data_directory: /var/lib/redpanda/data
  empty_seed_starts_cluster: false   # 集群已有,设为 false
  seed_servers:
    - host:
        address: 10.0.1.11
        port: 33145
    - host:
        address: 10.0.1.12
        port: 33145
    - host:
        address: 10.0.1.13
        port: 33145

# ============ 节点配置 ============
  node_id: 0                          # node-02 改为 1,node-03 改为 2

# ============ RPC(节点间 Raft) ============
  rpc_server:
    address: 0.0.0.0
    port: 33145
    advertised_address: 10.0.1.11     # node-02 改为 12.0.1.12,node-03 改为 10.0.1.13
  rpc_server_tls: []                  # 生产可加 TLS,本节先明文

# ============ Kafka API(客户端) ============
  kafka_api:
    address: 0.0.0.0
    port: 9092
    advertised_address: 10.0.1.11

# ============ Admin API ============
  admin:
    address: 0.0.0.0
    port: 9644
    advertised_address: 10.0.1.11

# ============ 监听器安全 ============
  kafka_api_tls: []
  admin_api_tls: []

# ============ 资源 ============
  developer_mode: false
  skip_thread_availability_checks: false
  skip_balance_core_check: false

# ============ 内存 ============
# 预留 8G 给 OS PageCache(64G 总内存场景)
# RedPanda RSS 通过 --memory 控制,rpk 启动时传入

# ============ Topic 默认参数 ============
  default_topic_partitions: 3
  default_topic_replications: 3

# ============ 内部 Topic(关键!) ============
internal_topic_replication_factor: 3
# 注意:3 节点集群必须为 3,单节点必须为 1,2 节点集群不可用!

# ============ 批量与并发 ============
  kafka_batch_max_bytes: 1048576     # 1MB
  kafka_request_max_bytes: 33554432  # 32MB
  kafka_connection_rate_limit: 1000

# ============ 日志保留 ============
  log_segment_size: 134217728        # 128MB
  retention_bytes: 107374182400      # 100GB/topic
  log_retention_ms: 604800000        # 7 天

# ============ 性能 ============
  group_topic_partitions: 16
  enable_idempotence: true
  enable_transactions: true
  tx_timeout_ms: 60000

# ============ 集群管理 ============
  cluster_id: "rp-cluster-prod-01"

# ============ Admin 限制 ============
  admin_api_dir: /var/lib/redpanda/admin

# ============ 管控(默认 60s) ============
  health_monitor_tick_interval: 3000
  health_monitor_max_metadata_age: 10000
```

### 4.3 启动集群

```bash
# 在 node-01 上启动(必须先起 node-01)
sudo systemctl start redpanda

# 在 node-02 上启动
sudo systemctl start redpanda

# 在 node-03 上启动
sudo systemctl start redpanda

# systemd unit 文件示例 /etc/systemd/system/redpanda.service
```

`/etc/systemd/system/redpanda.service`:

```ini
[Unit]
Description=RedPanda Kafka-compatible broker
Documentation=https://docs.redpanda.com/
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=redpanda
Group=redpanda
LimitNOFILE=131072
LimitNPROC=65536
LimitMEMLOCK=infinity
Environment="RP_NODE_ID=0"
Environment="RP_MACHINE_ID_FILE=/var/lib/redpanda/data/machine_id"
ExecStart=/usr/bin/rpk redpanda start \
  --config /etc/redpanda/redpanda.yaml \
  --smp 8 \
  --memory 24G \
  --reserve-memory 8G \
  --overprovisioned=false \
  --check=true
ExecStop=/usr/bin/rpk redpanda stop
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

### 4.4 验证集群

```bash
# 查看集群信息(任一节点执行)
rpk cluster info -X brokers=10.0.1.11:9092,10.0.1.12:9092,10.0.1.13:9092

# 输出示例:
# CLUSTER
# =======
# redpanda.5a8b9c2d-... 
#
# Live nodes (3):
#
#   Node ID  Address      
#   0        10.0.1.11:9092
#   1        10.0.1.12:9092
#   2        10.0.1.13:9092

# 查看健康状态
rpk cluster health

# 输出:
# CLUSTER HEALTH
# ==============
# Healthy:           true
# Unhealthy reasons: none
# Controller ID:     0      (内部 Raft leader)
# All partitions:    12
# Under-replicated:  0
# Offline:           0

# 创建 topic
rpk topic create orders -p 6 -r 3
rpk topic list
rpk topic describe orders

# 生产/消费测试
echo "hello" | rpk topic produce orders
rpk topic consume orders --num 1
```

## 五、5+ 节点大规模集群

### 5.1 节点规划

5 节点可以容忍 2 节点同时故障,是更稳健的生产配置:

| 主机名 | IP | node.id | rack | 用途 |
|--------|-----|---------|------|------|
| rp-node-01 | 10.0.1.11 | 0 | rack-A | broker+raft |
| rp-node-02 | 10.0.1.12 | 1 | rack-A | broker+raft |
| rp-node-03 | 10.0.1.13 | 2 | rack-B | broker+raft |
| rp-node-04 | 10.0.1.14 | 3 | rack-B | broker+raft |
| rp-node-05 | 10.0.1.15 | 4 | rack-C | broker+raft |

### 5.2 关键调整

相比 3 节点集群,5 节点需要调整:

```yaml
# 内部 topic 副本数保持 3(无需随节点数增加)
internal_topic_replication_factor: 3

# 但 topic 默认副本数可以提高到 3(5 节点集群通常用 RF=3)
default_topic_replications: 3

# seed_servers 列表更新
seed_servers:
  - host: { address: 10.0.1.11, port: 33145 }
  - host: { address: 10.0.1.12, port: 33145 }
  - host: { address: 10.0.1.13, port: 33145 }
  - host: { address: 10.0.1.14, port: 33145 }
  - host: { address: 10.0.1.15, port: 33145 }
```

### 5.3 Rack Awareness(机架感知)

5+ 节点集群建议启用机架感知,把副本分布到不同机架:

```yaml
redpanda:
  # rack 标识(每台机器不同)
  rack: "rack-A"     # node-02: rack-A,node-03: rack-B...
```

启用后,创建 topic 时 RedPanda 会优先把 3 副本分布到不同 rack。也可以手工指定:

```bash
rpk topic create orders -p 6 -r 3 \
  --assignment "0:0,3,4;1:1,4,2;2:2,3,1;3:3,0,1;4:4,2,0;5:0,2,3"
```

## 六、混合云/多区域集群

### 6.1 拓扑分类

| 拓扑 | 适用 | 延迟要求 | RedPanda 方案 |
|------|------|----------|---------------|
| **同城多 AZ** | 同城双活 | < 5 ms | 1 集群跨 AZ + 副本 |
| **两地三中心** | 双活+灾备 | < 50 ms | 主集群+Shadow Link |
| **跨洲复制** | 全球部署 | 100+ ms | Shadow Link + Tiered Storage |

### 6.2 同城多 AZ 部署

```text
┌──────────────────────────────────────────────────────────┐
│  AZ-1 (主)             │  AZ-2 (备)                      │
├────────────────────────┼─────────────────────────────────┤
│  rp-node-01 (10.0.1.11)│  rp-node-04 (10.0.2.14)         │
│  rp-node-02 (10.0.1.12)│  rp-node-05 (10.0.2.15)         │
│  rp-node-03 (10.0.1.13)│  rp-node-06 (10.0.2.16)         │
└────────────────────────┴─────────────────────────────────┘
```

关键调优(跨 AZ 延迟较高):

```yaml
redpanda:
  # 增加 RPC 超时(默认 3s)
  raft_election_timeout_ms: 5000
  
  # 减少后台压力
  enable_controller_log_sampling: false
```

### 6.3 跨区域:Shadow Link

跨区域推荐使用 **Shadow Linking**(RedPanda 核心特色,详见第十三节),而不是单集群跨 Region:

```text
┌────────────────┐   Shadow Link    ┌────────────────┐
│   区域 A       │ ◄─────────────►  │   区域 B       │
│   主集群       │   异步复制       │   备集群       │
│   3 节点       │                  │   3 节点       │
└────────────────┘                  └────────────────┘
```

## 七、Kubernetes Operator 部署

### 7.1 Redpanda Operator 介绍

Redpanda Operator 是 Kubernetes 原生的集群管理方式,提供:

- **声明式集群定义**:通过 CRD(`RedpandaCluster`、`Topic`、`User`、`ACL` 等)
- **自动化运维**:扩缩容、滚动升级、节点修复
- **Helm Chart 集成**:`redpanda/redpanda` Chart 一键安装
- **Console UI**:可视化管控(可选)

| Operator 版本 | 对应 RedPanda | 备注 |
|---------------|---------------|------|
| v2.x | 23.x+ | Helm Chart 优先,operator 简化 |
| v3.x | 24.x+ | 重写为 Helm Operator 风格 |

### 7.2 Helm Chart 安装

#### 添加仓库

```bash
helm repo add redpanda https://charts.redpanda.com
helm repo update
```

#### 配置 values.yaml

```yaml
# values.yaml
image:
  repository: docker.redpanda.com/redpandadata/redpanda
  tag: v24.2.7

# 集群节点
statefulset:
  replicas: 3
  antiAffinity:
    enabled: true
    type: hard
  podDisruptionBudget:
    enabled: true
    minAvailable: 2

# 资源
resources:
  requests:
    cpu: 4
    memory: 16Gi
  limits:
    cpu: 8
    memory: 24Gi

# 存储
storage:
  size: 1Ti
  storageClassName: gp3

# 配置
config:
  cluster:
    kafka_api: {}
    rpc_server: {}
  node:
    "developer_mode": false
  tuning:
    "rpk_system_tune": true

# 监听器
listeners:
  kafka:
    port: 9092
    tls:
      enabled: false
  admin:
    port: 9644

# Console UI(可选)
console:
  enabled: true
  service:
    type: LoadBalancer
```

#### 执行安装

```bash
# 创建 namespace
kubectl create namespace redpanda

# 安装
helm install redpanda redpanda/redpanda \
  --namespace redpanda \
  --values values.yaml \
  --version 5.7.5

# 查看进度
kubectl get pods -n redpanda -w
# NAME                READY   STATUS    RESTARTS   AGE
# redpanda-0          1/1     Running   0          2m
# redpanda-1          1/1     Running   0          2m
# redpanda-2          1/1     Running   0          2m

# 查看 service
kubectl get svc -n redpanda
```

### 7.3 自定义资源(CRD)

Redpanda Operator 提供以下 CRD:

#### RedpandaCluster(主资源)

```yaml
apiVersion: cluster.redpanda.com/v1alpha1
kind: RedpandaCluster
metadata:
  name: redpanda
  namespace: redpanda
spec:
  replicas: 3
  image: docker.redpanda.com/redpandadata/redpanda:v24.2.7
  resources:
    requests:
      cpu: 4
      memory: 16Gi
    limits:
      cpu: 8
      memory: 24Gi
  storage:
    capacity: 1Ti
    storageClassName: gp3
  listeners:
    kafka:
      port: 9092
      tls: false
    admin:
      port: 9644
```

#### Topic CRD

```yaml
apiVersion: cluster.redpanda.com/v1alpha1
kind: Topic
metadata:
  name: orders
  namespace: redpanda
spec:
  partitions: 12
  replicas: 3
  configuration:
    retention.ms: 604800000
    cleanup.policy: delete
    compression.type: producer
```

```text
│  RedPanda 集群扩容流程                                       │
├─────────────────────────────────────────────────────────────┤
```

### 9.2 增加节点

#### 步骤 1:准备新节点

新节点 `redpanda.yaml`:

```yaml
redpanda:
  node_id: 3                          # 与现有节点不同
  seed_servers:
    - host: { address: 10.0.1.11, port: 33145 }   # 现有集群任一节点
    - host: { address: 10.0.1.12, port: 33145 }
    - host: { address: 10.0.1.13, port: 33145 }

```

#### 步骤 2:启动新节点

```bash
sudo systemctl start redpanda
# 新节点启动后自动加入集群,无需重启老节点
```

#### 步骤 3:验证

```bash
rpk cluster info
# 应显示 4 个节点
```

### 9.3 迁移分区到新节点

RedPanda 不会自动均衡分区,需要手动触发:

```bash
# 查看当前分区分布
rpk cluster partitions list --topic orders

# 自动均衡(把分区均匀分布到所有 broker)
rpk cluster partitions balance

# 或者手工指定 partition 的副本分布

# 批量调整示例:把所有 partition 副本数增加到 4

```

### 9.4 移除节点

```text
┌─────────────────────────────────────────────────────────────┐
│  节点下线流程(4 节点 → 3 节点)                              │
├─────────────────────────────────────────────────────────────┤
│  1. rpk topic move-replicas 把目标节点上的副本迁走           │
│     ↓                                                       │
│  2. 确认目标节点上无分区(under-replicated=0)                │
│     ↓                                                       │
│  3. systemctl stop redpanda                                  │
│     ↓                                                       │
│  4. (可选)从集群 seed_servers 列表移除                      │
│     ↓                                                       │
│  5. 更新其他节点 redpanda.yaml 移除该 seed                  │
└─────────────────────────────────────────────────────────────┘
```

## 十、滚动重启

### 10.1 触发场景

- 配置文件修改(`rpk redpanda config set`)
- OS 内核升级
- 机器维护(BIOS、固件)
- 滚动升级前的预备步骤

### 10.2 滚动重启流程

```text
┌─────────────────────────────────────────────────────────────┐
│  滚动重启:逐台处理,避免集群不可用                           │
├─────────────────────────────────────────────────────────────┤
│  对每台节点:                                                │
│  1. rpk cluster partitions list --node N                    │
│     查看该节点上是否有 partition leader                     │
│  2. 若有 leader,先 rpk cluster partitions move-leader 迁走  │
│  3. systemctl stop redpanda                                 │
│  4. (维护操作:修改配置/升级内核)                           │
│  5. systemctl start redpanda                                │
│  6. 等待该节点状态健康(under-replicated=0)                  │
│  7. 等待 30s-1min 后再处理下一台                            │
└─────────────────────────────────────────────────────────────┘
```

### 10.3 一键脚本示例

```bash
#!/bin/bash
# rolling-restart.sh
NODES=("10.0.1.11" "10.0.1.12" "10.0.1.13")
WAIT_SECONDS=60

for NODE in "${NODES[@]}"; do
  echo "===== Restarting $NODE ====="
  
  # 1. 迁走该节点上的 leader
  LEADER_PARTITIONS=$(rpk cluster partitions list --node $NODE 2>/dev/null | grep "LEADER" | wc -l)
  if [ "$LEADER_PARTITIONS" -gt 0 ]; then
    echo "Moving leader partitions off $NODE..."
    rpk cluster partitions balance
    sleep 10
  fi
  
  # 2. 重启
  ssh $NODE "systemctl restart redpanda"
  
  # 3. 等待健康
  echo "Waiting for $NODE to be healthy..."
  sleep $WAIT_SECONDS
  
  # 4. 检查健康
  HEALTH=$(rpk cluster health 2>/dev/null | grep "Healthy" | awk '{print $2}')
  if [ "$HEALTH" != "true" ]; then
    echo "ERROR: Cluster unhealthy after restart of $NODE, aborting"
    exit 1
  fi
done
echo "===== Rolling restart completed ====="
```

## 十二、升级 RedPanda

### 12.1 版本号规范

RedPanda 遵循语义化版本:`v<major>.<minor>.<patch>`

- **小版本升级**(patch):23.2.5 → 23.2.6,Bug 修复,直接滚动重启
- **次版本升级**(minor):23.2 → 23.3,新特性,通常兼容协议
- **大版本升级**(major):23.x → 24.x,可能有协议变更,需读 release notes

### 12.2 小版本升级(滚动)

```bash
# 1. 阅读 release notes
# https://github.com/redpanda-data/redpanda/releases

# 2. 备份配置
cp /etc/redpanda/redpanda.yaml /etc/redpanda/redpanda.yaml.bak

# 3. 在每个节点上升级 rpm/deb 包
sudo rpm -Uvh redpanda-23.2.6-1.el8.x86_64.rpm
# 或
sudo apt install ./redpanda_23.2.6_amd64.deb

# 4. 滚动重启(逐台)
for node in node-01 node-02 node-03; do
  ssh $node "systemctl restart redpanda"
  sleep 60
  rpk cluster health
done

# 5. 验证版本
rpk version
```

### 12.3 大版本升级

```bash
# 1. 详细阅读升级指南(每个大版本都有专属文档)
# https://docs.redpanda.com/current/upgrade/

# 2. 检查不兼容项
rpk cluster config export | grep -i "deprecat"

# 3. 测试环境先行升级
# 测试集群升级 → 跑全套回归 → 观察 24h

# 4. 生产环境灰度
# 单节点升级 → 观察 1h → 1/3 → 全量
```

### 12.4 灰度升级流程

```text
┌─────────────────────────────────────────────────────────────┐
│  灰度升级策略                                                │
├─────────────────────────────────────────────────────────────┤
│  阶段 1: 1 节点(node-03,非 leader) → 观察 1h              │
│  阶段 2: 1/3 集群(node-02,03) → 观察 6h                    │
```

## 十三、Shadow Linking(核心特色)

### 13.1 概念

Shadow Linking 是 RedPanda 24.x 引入的**内置跨集群数据复制功能**,类似 Kafka MirrorMaker 2,但深度集成到 RedPanda 内核,**无需单独部署 Connect 集群**。

```text
┌─────────────────────────────────────────────────────────────┐
│                    Shadow Link 架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌────────────────────┐         ┌────────────────────┐       │
│  │  Shadow Cluster    │         │  Source Cluster    │       │
│  │  (消费者角色)       │         │  (生产者角色)       │       │
│  │                    │         │                    │       │
│  │  ┌──────────────┐  │  Fetch  │  ┌──────────────┐  │       │
│  │  │ Shadow Topic │◄─┼─────────┼──┤ Source Topic │  │       │
│  │  │  (只读副本)   │  │  异步   │  │  (原始数据)   │  │       │
│  │  └──────────────┘  │         │  └──────────────┘  │       │
│  │                    │         │                    │       │
│  │  RedPanda 节点 N   │         │  RedPanda 节点 M   │       │
│  └────────────────────┘         └────────────────────┘       │
│                                                             │
│  • 源集群无感知,不被影响                                    │
│  • 目标集群通过 Shadow Link 拉取数据                        │
│  • 支持 topic 筛选、offset 转换、ACL 同步                   │
└─────────────────────────────────────────────────────────────┘
```

### 13.2 与 Kafka MirrorMaker 2 对比

| 维度 | Kafka MirrorMaker 2 | RedPanda Shadow Link |
|------|---------------------|----------------------|
| 部署方式 | 独立 Connect 集群 | 内置(RedPanda 自身就是消费者) |
| 资源开销 | 需要专门的 worker | 复用 RedPanda 集群资源 |
| 配置复杂度 | `connect-mirror-maker.properties` | `rpk shadow link create` |
| 延迟 | 取决于 worker 数量与网络 | 单一跳点,延迟更低 |
| Exactly-once | 支持,但需谨慎配置 | 通过 Shadow Topic 副本实现 |
| 协议兼容 | 仅 Kafka 协议 | 仅 RedPanda 协议(Kafka 客户端可消费) |
| Topic 重命名 | 支持 | 支持 |
| ACL 同步 | 部分 | 支持 |

### 13.3 配置示例

#### 创建 Shadow Link

```bash
# 在目标集群上创建 Shadow Link(连接到源集群)
rpk shadow link create my-shadow \
  --source-brokers 10.0.0.1:9092,10.0.0.2:9092,10.0.0.3:9092 \
  --source-tls-enabled=false \
  --source-scram-username=link-user \
  --source-scram-password=secret \
  --name my-shadow-link

# 查看 Shadow Link
rpk shadow link list
rpk shadow link status my-shadow
```

#### 指定同步的 Topic

```bash
# 创建时指定
rpk shadow link create my-shadow \
  --source-brokers 10.0.0.1:9092 \
  --topic-name-pattern "^orders\\..*"   # 仅同步 orders.* 开头的 topic

# 修改已有 Shadow Link
rpk shadow link edit my-shadow --topic-name-pattern "^(orders|users)\\..*"
```

#### 查看同步进度

```bash
rpk shadow link status my-shadow
# 输出:
# NAME        STATUS    SOURCE CLUSTER    LAG       TOPICS
# my-shadow   Healthy   prod-cluster-a    1234      42

# 详细
rpk shadow link topic list my-shadow
```

### 13.4 应用场景

| 场景 | 说明 | 配置要点 |
|------|------|----------|
| **跨区域灾备** | 主备集群,主故障时切流 | 异步复制,RPO 秒级 |
| **数据聚合** | 多个边缘集群同步到中央 | 中央集群作为 Shadow,反向多源 |
| **Kafka 迁移** | 从 Kafka 集群迁移到 RedPanda | 源设为 Kafka,目标 RedPanda |
| **跨云复制** | 阿里云 ↔ AWS | Shadow Link 穿透公网 |
| **读写分离** | 主集群写、备集群读报表 | 备集群只读消费者 |

### 13.5 双向同步注意

双向同步会导致 **循环复制**,必须用 topic 命名区分:

```text
源集群(主)           目标集群(备)
topic-A          ─►  topic-A
topic-A-replica  ◄─  (来自备的回流,会被丢弃)
```

**避免循环复制**:源端 topic 命名加前缀(`prod-orders`),目标端自动同步为(`prod-orders`),不会反向回流。

## 十七、集群巡检清单

### 17.1 健康检查

```bash
#!/bin/bash
# redpanda-health-check.sh
BROKERS="10.0.1.11:9092,10.0.1.12:9092,10.0.1.13:9092"

echo "===== 1. 集群节点 ====="
rpk -X brokers=$BROKERS cluster info 2>/dev/null | grep -E "Live nodes|Node ID"

echo "===== 2. 集群健康 ====="
rpk -X brokers=$BROKERS cluster health

echo "===== 3. Under-replicated partitions ====="
rpk -X brokers=$BROKERS cluster partitions list --under-replicated 2>/dev/null | wc -l

echo "===== 4. 没有 Leader 的 partition ====="
rpk -X brokers=$BROKERS cluster partitions list --offline 2>/dev/null | wc -l

echo "===== 5. 消费者 lag ====="
rpk -X brokers=$BROKERS group list 2>/dev/null
for g in $(rpk -X brokers=$BROKERS group list 2>/dev/null | tail -n+2 | awk '{print $1}'); do
  LAG=$(rpk -X brokers=$BROKERS group describe $g 2>/dev/null | grep "Lag" | awk '{print $2}')
  echo "  Group $g: lag=$LAG"
done

echo "===== 6. 磁盘使用 ====="
df -h /var/lib/redpanda/data | grep -v tmpfs

echo "===== 7. RedPanda 进程 ====="
ps aux | grep -i redpanda | grep -v grep | wc -l
```

### 17.2 巡检 Checklist

| 检查项 | 命令 | 阈值 | 处理 |
|--------|------|------|------|
| **节点存活** | `rpk cluster info` | 节点数 == 预期 | 异常节点排查 |
| **集群健康** | `rpk cluster health` | `Healthy: true` | 不健康查日志 |
| **Under-replicated** | `rpk cluster partitions list --under-replicated` | 应为 0 | 持续 > 0 检查 Follower |
| **Offline partition** | `rpk cluster partitions list --offline` | 应为 0 | > 0 立即告警 |
| **消费者 lag** | `rpk group describe` | 视业务定 | 异常 group 排查消费 |
| **磁盘使用率** | `df -h` | < 75% | 触达 80% 扩盘 |
| **文件描述符** | `lsof -p <pid> \| wc -l` | < 80% ulimit | 调高 ulimit |
| **网络流量** | `sar -n DEV 1` | < 70% 带宽 | 排查热点 partition |
| **RedPanda 内存** | `ps -o rss` | 在 --memory 范围内 | RSS 过高触发 GC |
| **配置漂移** | 比对 redpanda.yaml git 仓库 | 无差异 | 记录漂移来源 |

### 17.3 常见告警与处置

| 告警 | 可能原因 | 处置 |
|------|----------|------|
| Under-replicated > 0 | Follower 掉队、网络抖动、磁盘满 | 查日志、检查网络/磁盘 |
| `LEADER_NOT_AVAILABLE` | Leader broker 故障 | 重启故障 broker,触发 leader 选举 |
| `OFFLINE_PARTITIONS` | 多副本同时不可用 | 立即查 5xx 日志 |
| Cluster not Healthy | 元数据异常 | `rpk cluster health --exit-when-healthy` 等待 |
| Node ID conflict | 重复 node_id | 重新分配 node_id |
| Disk usage > 80% | 数据增长过快 | 扩盘 / 缩短 retention / 启用 Tiered Storage |

## 十八、核心要点速记

- **RedPanda 是单二进制**:没有 ZooKeeper、没有 Controller/Broker 分离,所有节点天然既是数据节点又是 Raft 参与者,部署比 Kafka 简单得多
- **同质节点**:每台 `redpanda` 进程都是同质的,角色平等,3 节点是**最小高可用配置**
- **节点规模选型**:开发 1 节点、小生产 3 节点、中等生产 5 节点、大规模 7+ 节点
- **CPU 偏好高频**:RedPanda 单进程多线程,主频 > 核数,推荐 8 核 3.5GHz+;ARM Graviton3 性价比更优
- **内存分配**:总内存 60% 给 RedPanda(`--memory`),25% 给 OS PageCache(`--reserve-memory`)
- **网络必备万兆**:跨节点 Raft 复制 + 客户端 IO,千兆网络必成瓶颈
- **文件系统用 XFS**:`mkfs.xfs` + `noatime,nodiratime,allocsize=64m`;避免 ZFS/Btrfs
- **一键调优**:`sudo rpk system tune` 自动配置 ulimit、sysctl、XFS,**所有节点执行一次**
- **单节点参数**:`--overprovisioned --smp 1 --memory 1G --reserve-memory 0M --check=false`
- **3 节点集群**:`internal_topic_replication_factor: 3` 必须为 3,否则内部 topic 无法创建
- **`seed_servers`**:集群所有节点互列,**包含自己**,新增节点时 seed 指向已有节点即可加入
- **`advertise_*_addr`**:**必须配置可路由地址**,不能用 localhost,否则客户端连不上
- **集群验证三件套**:`rpk cluster info`(节点列表)、`rpk cluster health`(健康)、`rpk topic list`(topic)
- **扩容流程**:新节点启动 → 自动加入 Raft 组 → `rpk cluster partitions balance` 均衡分布;**RedPanda 不会自动均衡**
- **缩容流程**:迁走 leader → 迁走副本 → 停节点 → 更新 seed 列表;**under-replicated=0 才停**
- **滚动重启顺序**:每台迁走 leader → 停 → 维护 → 启 → 等健康 → 下一台;每次间隔 30s-1min
- **动态配置**:`rpk cluster config set xxx yyy` 在线生效,无需重启(如 `log_retention_ms`、`kafka_batch_max_bytes`)
- **静态配置**:修改 `redpanda.yaml` + 滚动重启(如 `node_id`、`seed_servers`、`data_directory`)
- **配置导出备份**:`rpk cluster config export > backup.yaml` 用于版本化
- **升级顺序**:小版本(同次版本内)直接滚动升级;大版本必须读 release notes + 测试集群先行
- **回滚限制**:小版本可回滚(`rpm -Uvh --oldpackage`),大版本需从备份恢复
- **Shadow Linking**:RedPanda 内置的跨集群复制,无需 Connect 集群,比 MirrorMaker2 更简单
- **避免循环复制**:Shadow Link 单向流动,源端 topic 加前缀区分
- **Iceberg 集成**:开启 `iceberg.enabled=true` + `ice.warehouse=s3://...`,自动写 Parquet 到数据湖
- **Kubernetes 部署**:`helm install redpanda redpanda/redpanda --version 5.7.5` 一键完成,CRD 管理 Topic/User/ACL
- **Docker Compose 部署**:适合开发与 CI,3 节点用 `--seeds=redpanda-0,...,redpanda-2` 互连
- **健康巡检**:`rpk cluster health` + `rpk cluster partitions list --under-replicated` 必须为 0
- **常见坑点**:
  - 2 节点集群**不可用**(过半存活 = 2 节点,无法容错),**生产必须 3/5/7 节点**
  - `internal_topic_replication_factor` 单节点必须为 1,多节点必须为 3
  - `advertise_*_addr` 用 localhost 会导致客户端连接失败
  - RedPanda 不会自动均衡分区,扩容后必须手动 `rpk cluster partitions balance`
  - `kill -9` 可能导致未刷盘数据丢失,务必用 `systemctl stop` 或 `rpk redpanda stop`
  - Shadow Link 双向同步必须用 topic 前缀避免循环
