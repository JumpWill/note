# RedPanda 体系结构与核心概念

## 一、RedPanda 整体架构总览

**RedPanda** 是由 RedPanda Data 公司开发的 **Kafka API 兼容**的分布式事件流平台。它使用 C++ 实现,内核基于 **Seastar 异步框架**,采用 **thread-per-core (每核一线程)** 模型,内置 **Raft 共识协议**,目标是 **用更少的资源、更低的延迟、更简单的运维** 提供与 Kafka 完全兼容的流式存储服务。

**核心定位**:

- **100% Kafka API 兼容**:Producer / Consumer / Admin / Schema Registry 协议均与 Apache Kafka 兼容,现有 Kafka 客户端无需任何修改即可连接
- **单二进制部署**:一个 `redpanda` 可执行文件即一个 Broker,没有 JVM、没有 ZooKeeper、没有 Controller 进程分离
- **极致低延迟**:P99 延迟通常比 Kafka 低一个数量级 (毫秒级 -> 百微秒级)
- **资源高效**:相同吞吐量下内存占用约为 Kafka 的 1/10,无 JVM 预热、无 GC 停顿

## 二、核心设计哲学

RedPanda 的整体设计深受 ScyllaDB (NoSQL 数据库) 团队影响,核心哲学可以归结为四点:**Thread-per-core、无 GC、异步编程、共享内存架构**。这四点共同造就了它低延迟、低资源占用的特性。

### 1. Thread-per-core 模型

**Thread-per-core (每核一线程)** 是 RedPanda 最关键的架构决策。它的核心思想是:**让每个 CPU 核心独占一个应用线程,该线程运行在该核心上,永不跨核迁移**。

#### 与 Kafka 的线程池模型对比

```text
┌──────────────────────────────────┬──────────────────────────────────┐
│       Kafka 线程池模型           │     RedPanda Thread-per-core     │
├──────────────────────────────────┼──────────────────────────────────┤
│                                  │                                  │
│   1 个 JVM 进程                  │   1 个 redpanda 进程             │
│   ┌──────────────────────┐      │   ┌──────────────────────┐        │
│   │ Acceptor Thread      │      │   │ Shard 0 (绑定 Core 0)│        │
│   ├──────────────────────┤      │   │  - Reactor           │        │
│   │ num.network.threads  │      │   │  - 分区处理           │        │
│   │ (默认 3)             │      │   │  - IO 完成            │        │
│   ├──────────────────────┤      │   ├──────────────────────┤        │
│   │ num.io.threads       │      │   │ Shard 1 (绑定 Core 1)│        │
│   │ (默认 8)             │      │   ├──────────────────────┤        │
│   ├──────────────────────┤      │   │ Shard 2 (绑定 Core 2)│        │
│   │ Request Processor    │      │   ├──────────────────────┤        │
│   │ Thread Pool          │      │   │ Shard 3 (绑定 Core 3)│        │
│   ├──────────────────────┤      │   │  ...                 │        │
│   │ GC Threads           │      │   │  总数 = CPU 核数      │        │
│   └──────────────────────┘      │   └──────────────────────┘        │
│   线程数 = 几十~几百            │   线程数 = CPU 核数               │
│   频繁上下文切换                 │   几乎无上下文切换                │
│   锁竞争激烈                     │   几乎无锁 (单线程访问自己的数据) │
└──────────────────────────────────┴──────────────────────────────────┘
```

**Thread-per-core 的核心优势**:

| 优势               | 说明                                                                 |
|--------------------|----------------------------------------------------------------------|
| **无上下文切换**   | 线程固定绑定到核心,操作系统调度器不会把它换到其他核,L1/L2 cache 全部命中 |
| **无锁数据结构**   | 每个 shard 独立处理自己的数据,无需加锁,避免 lock-free 算法复杂性 |
| **NUMA 友好**      | 线程和内存都在本地节点上,跨 NUMA 访问几乎消失                         |
| **可预测的延迟**   | 没有 GC 停顿、没有线程调度抖动,P99/P999 延迟非常稳定                 |
| **线性扩展**       | 性能几乎与核心数线性正比,不会出现"加核反降"的拐点                     |

**Thread-per-core 的代价**:

- 单个 shard 故障即整个进程崩溃 (无 JVM 那种 try/catch 兜底)
- 难以利用 SMT 超线程 (HT 实际上是另一个逻辑核心)
- 编程模型更复杂:不能直接用 std::thread/std::mutex 共享数据

### 2. 无 GC (C++ 优势)

RedPanda 采用 **C++ 17/20** 实现,内核基于 Seastar 框架的**内存池 + RAII** 模式管理内存,**完全避免 GC**。

**为什么无 GC 如此重要**:

```text
延迟分布对比示意:

Kafka (JVM GC)                    RedPanda (无 GC)
  │                                  │
  │   ┌──┐ GC 停顿 50ms             │          ┌─┐
  │   │  │                          │          │ │ 偶尔软中断
  │   │  │ ┌─┐                     │ ┌─┐ ┌─┐  │ │ ┌─┐ ┌─┐ ┌─┐
  │   │  │ │ │                     │ │ │ │ │  │ │ │ │ │ │ │ │ │
  ──┴───┴─┴─┴──────────────────     ─┴─┴─┴─┴──┴─┴─┴─┴─┴─┴─┴─┴─┴─► time
   P50=2ms  P99=200ms              P50=1ms  P99=5ms
```

**内存管理策略**:

| 策略                    | 说明                                                              |
|-------------------------|-------------------------------------------------------------------|
| **slab allocator**      | 大对象从 slab 池分配,避免 `malloc` 锁竞争                          |
| **per-shard 内存池**    | 每个 shard 独立的内存池,跨 shard 释放会通过消息传递               |
| **零拷贝转发**          | 分片间的消息通过指针传递,不复制数据                                |
| **RAII**                | C++ 对象生命周期与栈/智能指针绑定,无需 GC 扫描                     |
| **`std::pmr` 内存资源** | C++17 多态分配器,精细控制内存来源                                 |

### 3. 异步编程 (Seastar 框架)

RedPanda 所有 I/O 路径都是**异步**的。**没有阻塞调用、没有线程切换**——一个 shard 上的所有任务通过协程 / Future 串联。

```cpp
// RedPanda 风格的伪代码 (基于 Seastar)
seastar::future<> produce_record(record r) {
    // 1. 异步追加到本地 log
    return log->append(std::move(r))
        .then([this](offset o) {
            // 2. 异步复制到 follower (Raft)
            return consensus->replicate(o);
        })
        .then([this](offset committed) {
            // 3. 异步返回 ACK 给 producer
            return conn->write(make_ack(committed));
        });
}
```

**异步的关键收益**:

- **单线程吞吐极高**:没有线程切换开销,一个 shard 可处理数十万 QPS
- **I/O 等待期间可处理其他请求**:连接、磁盘、网络 I/O 全部异步
- **背压 (back-pressure) 自然**:网络拥塞时上游自动降速

### 4. 共享内存架构

同一进程内,**shard 之间通过共享内存通信**,但通过**消息传递 (message passing)** 而非共享可变状态。

```text
┌──────────────────────────────────────────────────┐
│         进程内 (单 redpanda 实例)                │
│                                                  │
│  Shard 0      Shard 1      Shard 2      Shard 3  │
│  ┌────┐       ┌────┐       ┌────┐       ┌────┐  │
│  │队列 │◄─────►│队列 │◄─────►│队列 │◄─────►│队列 │
│  └────┘  smp  └────┘  smp  └────┘  smp  └────┘  │
│                                                  │
│  共享: 共享地址空间 (text/data/heap)             │
│  隔离: 各自的栈、内存池、cache 亲和性           │
│  通信: smp::submit_to + 无锁队列                 │
└──────────────────────────────────────────────────┘
```

## 三、Seastar 框架

**Seastar** 是 RedPanda 团队 (与 ScyllaDB 共用) 开发的 **高性能异步 C++ 框架**,专为 thread-per-core 模型设计。RedPanda 内核的所有网络、磁盘、定时器、内存管理都构建在 Seastar 之上。

### 1. 核心概念

| 概念                  | 说明                                                                  |
|-----------------------|-----------------------------------------------------------------------|
| **shard**             | 一个线程 + 一组独占资源 (内存池、CPU 亲和性),通常 1:1 对应一个 CPU 核心 |
| **reactor**           | 每个 shard 上的事件循环 (epoll/io_uring 驱动),处理所有 I/O 事件       |
| **Future/Promise**    | 异步操作的结果占位符,`then()` 串联下一步                              |
| **coroutine**         | C++20 协程,可用同步语法写异步代码 (`co_await`)                       |
| **smp**               | "symmetric multi-processing" API,跨 shard 通信原语                    |
| **memory pool**       | 每个 shard 独立的内存分配器,避免跨 shard 锁竞争                       |

### 2. Future 与 Promise

Seastar 的 Future 类似 Rust 的 `Future` 或 JS 的 `Promise`,但**线程亲和**——回调只在创建 Future 的那个 shard 上执行,无需加锁。

```cpp
// 同步风格 (C++20 协程)
seastar::future<offset> append_record(record r) {
    auto o = co_await log->append(std::move(r));      // 异步追加
    auto committed = co_await consensus->replicate(o); // 异步复制
    co_return committed;
}

// 或回调风格 (C++17)
log->append(std::move(r))
    .then([](offset o) { return consensus->replicate(o); })
    .then([](offset committed) { /* 返回 ACK */ });
```

**Future 的特性**:

- **zero-allocation futures**:栈上分配的轻量 Future,不触发堆分配
- **chainable**:`.then()` 返回新 Future,可无限串联
- **exceptional**:异常沿链传播,`.handle_exception()` 兜底

### 3. 共享内存下的无锁队列

**Sharded queue** 是 Seastar 的核心数据结构:每个 shard 维护一对**无锁 SPSC 队列**,与邻居 shard 通信时直接 push 到对方的队列。

```text
Shard 0 的 inbound queue (来自其他 shard):
┌────────────────────────────────────┐
│ msg_A ─► msg_B ─► msg_C ─► ...     │
└────────────────────────────────────┘
   ▲
   │ 其他 shard 通过 smp::submit_to 投递
   │
Shard 1 想让 Shard 0 执行某函数:
  smp::submit_to(0, [args...] { ... });
  → 该函数被序列化进 Shard 0 的 inbound queue
  → Shard 0 的 reactor 从队列取出并执行
```

**为什么不用锁**:

- 锁会让线程睡眠,而 Seastar 线程模型下根本不存在"线程阻塞"概念
- 跨 shard 通信应该是消息传递,而不是共享状态 + 锁
- 无锁队列在 SPSC 模式下性能极高 (~100M ops/s)

### 4. shard-per-core 调度

Seastar 的事件循环 (reactor) 在每个 shard 上独立运行:

```text
Shard 0 的 reactor 主循环 (伪代码):
┌────────────────────────────────────────────┐
│ while (!stopped) {                         │
│   1. poll 网络事件 (epoll/io_uring)        │
│   2. poll 磁盘事件 (io_uring)              │
│   3. 处理 inbound queue (其他 shard 投递)   │
│   4. 处理定时器 (timer wheel)              │
│   5. 处理已完成 Future (then 回调)          │
│   6. 没有任务则进入轻量空闲                  │
│ }                                          │
└────────────────────────────────────────────┘
```

**关键特性**:

- **CPU 亲和性**:`taskset -c 0 redpanda` 把 shard 0 钉死在 core 0
- **io_uring** (Linux 5.1+):一个 ring buffer 处理所有异步 I/O,无需 syscall 阻塞
- **DPDK / XDP 可选**:Seastar 可旁路内核网络栈,极致场景下吞吐翻倍

## 四、核心概念

RedPanda 与 Kafka 在概念层面高度相似,这是"100% Kafka API 兼容"的基石。但底层实现完全不同。

### 1. 核心概念速查表

| 概念                      | 英文              | 一句话解释                                                       |
|---------------------------|-------------------|------------------------------------------------------------------|
| **Broker / Node**         | 代理服务器        | RedPanda 集群中的一个服务节点,一个 `redpanda` 进程即一个 Broker   |
| **Topic**                 | 主题              | 消息的逻辑分类,与 Kafka 完全一致                                |
| **Partition**             | 分区              | Topic 的物理分片,每分区独立 Raft 组                             |
| **Replica**              | 副本              | Partition 的冗余拷贝,通过 Raft 同步                            |
| **Leader / Follower**    | 主/从副本         | 每个分区只有一个 Leader,其余 Follower 复制 Leader 的日志         |
| **Log Segment**           | 日志段            | 磁盘上的物理文件 (默认 1GB),消息只追加                          |
| **Record Batch**          | 记录批次          | 一组打包写入的记录 (与 Kafka 的 `RecordBatch` 格式兼容)        |
| **Offset**                | 位移              | 消息在 Partition 内的唯一编号 (64 位 Long)                      |
| **Kafka API 兼容层**      | Compatibility     | Pandaproxy 实现的 Kafka wire protocol                          |

### 2. Broker (节点)

**Broker** 是 RedPanda 集群中的一个服务节点,部署形态为**单个 Linux 进程** (`/usr/bin/redpanda`)。

**Broker 启动参数**:

```bash
redpanda \
  --overprovisioned \
  --node-id=0 \
  --check=false \
  --smp=4 \                # shard 数 (= CPU 核数)
  --memory=8G \            # 进程最大内存
  --reserve-memory=1G \    # 留给系统 cache 的内存
  --rpc-addr=0.0.0.0:33145 \
  --kafka-addr=0.0.0.0:9092 \
  --advertise-kafka-addr=192.168.1.10:9092 \
  --data-dir=/var/lib/redpanda/data
```

**单 Broker 内部结构**:

```text
┌──────────────────────────────────────────────────┐
│            1 个 redpanda 进程 = 1 个 Broker      │
│                                                  │
│  Shard 0         Shard 1         Shard 2         │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐     │
│  │ Reactor  │    │ Reactor  │    │ Reactor  │     │
│  ├──────────┤    ├──────────┤    ├──────────┤     │
│  │ 分区表    │    │ 分区表    │    │ 分区表    │     │
│  │ P0 P3 P6 │    │ P1 P4 P7 │    │ P2 P5 P8 │     │
│  ├──────────┤    ├──────────┤    ├──────────┤     │
│  │ Raft 状态│    │ Raft 状态│    │ Raft 状态│     │
│  ├──────────┤    ├──────────┤    ├──────────┤     │
│  │ 内存池    │    │ 内存池    │    │ 内存池    │     │
│  └──────────┘    └──────────┘    └──────────┘     │
│                                                  │
│  共享: 文件描述符、TCP listener、配置            │
│  隔离: 各自的 partition 状态、Raft 状态          │
└──────────────────────────────────────────────────┘
```

**分区与 shard 的映射**:

- 默认情况下,Partition 按 hash(namespace/topic/partition_id) 均匀分配到各 shard
- 一个 Partition 的所有状态 (log、Raft、cache) 只存在于一个 shard 上
- 不同 shard 的 Partition 通过 smp 消息传递通信

### 3. Topic

**Topic** 的语义与 Kafka 完全一致,客户端可使用任何 Kafka 客户端 SDK 直接读写。

```bash
# 使用 Kafka 工具创建 RedPanda Topic
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic order-events \
  --partitions 6 --replication-factor 3

# 查看 Topic (返回格式与 Kafka 完全一致)
```

### 4. Partition (分区)

**Partition** 是 Topic 的物理分片单位,与 Kafka 相同:

- **单分区内有序**:消息按 Offset 严格有序追加
- **不可变日志**:只能追加,不能修改、不能删除 (按 retention 过期)
- **并行单位**:Producer/Consumer 跨分区并行,互不阻塞

```text
Partition 0 (在某个 Broker 的某个 shard 上):

Log 文件 (data/redpanda/order-events/0_2/):
  ┌─────────────────┐
  │ 00000000.log    │ ← segment 1 (默认 1GB,满则 roll)
  │ 00000010.log    │ ← segment 2
  │ 00000020.log    │ ← segment 3 (active)
  └─────────────────┘

内存中的索引:
  ┌─────────────────┐
  │ index_state     │ ← base_offset, committed_offset
  │ segment_index   │ ← offset → file position
  └─────────────────┘
```

**Partition 与 shard 的关系**:

- RedPanda 默认采用 **`use_readers_proxy = false`** 时,Partition 与 shard 1:1 绑定
- 若 `use_readers_proxy = true`,读取路径可跨 shard (适合高扇出消费)

### 5. Replica (副本)

**Replica** 是 Partition 的冗余拷贝,通过 **Raft 协议**实时同步。

```text
Partition 0, replication-factor = 3

┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Broker 0    │  │  Broker 1    │  │  Broker 2    │
│  Replica A   │  │  Replica B   │  │  Replica C   │
│  (Leader)    │  │  (Follower)  │  │  (Follower)  │
│              │  │              │  │              │
│  term: 5     │  │  term: 5     │  │  term: 5     │
│  log: [0,N)  │  │  log: [0,M)  │  │  log: [0,M)  │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └────── AppendEntries RPC ──────────┘
       │
       ▼
   Client → Leader only (读与写)
```

**副本特性**:

| 特性         | Kafka                          | RedPanda                                |
|--------------|--------------------------------|-----------------------------------------|
| **协议**     | 早期 ZooKeeper,后 KRaft       | 一开始就 Raft                           |
| **同步方式** | Follower 主动拉取 (`fetch`)   | Leader 主动推送 (`AppendEntries`)       |
| **Leader 选举** | Controller 选 (ZK/KRaft 模式) | 每个 Partition 自己的 Raft 组自选      |
| **脑裂保护** | epoch (ZK) / epoch (KRaft)   | term (Raft 原生)                        |

### 6. Log Segment

**Log Segment** 是 Partition 在磁盘上的物理文件,默认大小 1GB。Segment 文件满后滚动 (roll) 成新文件,旧文件可被压缩 (compaction) 或删除 (deletion)。

```text
data/redpanda/<namespace>/<topic>-<partition_id>_<group_id>/
├── 00000000.log          ← segment 1 (sealed)
├── 00000000.index        ← offset → position 索引
├── 00000010.log          ← segment 2 (sealed)
├── 00000010.index
├── 00000020.log          ← segment 3 (active,正在写入)
├── 00000020.index
├── manifest.json          ← segment 元数据
├── recovery_state         ← 重放状态
└── snapshot              ← Raft snapshot (若开启)
```

**Segment 的关键参数**:

| 参数                       | 默认值      | 说明                                       |
|----------------------------|-------------|--------------------------------------------|
| `log_segment_size`        | 1 GiB       | 单个 segment 文件大小                      |
| `log_segment_ms`          | 2 小时      | 按时间滚动 segment                          |
| `retention_bytes`         | -1 (无限)   | 按大小保留                                 |
| `retention_ms`            | 7 天        | 按时间保留                                 |
| `compaction`              | false       | 是否启用压缩 (清理相同 key 的旧消息)       |

### 7. Record Batch

**Record Batch** 是 RedPanda 单次写入的最小单位,与 Kafka 0.11+ 的 `RecordBatch` 二进制格式完全一致。

```text
Record Batch 结构 (与 Kafka 兼容):
┌──────────────────────────────────────────────────┐
│ baseOffset: int64                               │
│ batchLength: int32                              │
│ partitionLeaderEpoch: int32                     │
│ magic: int8 (v2)                                │
│ crc: int32 (CRC-32C)                            │
│ attributes: int16 (compression, timestamp type) │
│ lastOffsetDelta: int32 (本 batch 内 delta)      │
│ baseTimestamp: int64                            │
│ maxTimestamp: int64                             │
│ producerId: int64 (幂等生产者)                  │
│ producerEpoch: int16                            │
│ baseSequence: int32 (幂等顺序)                  │
│ records: [                                      │
│   ┌────────────────────────────────┐            │
│   │ Record:                        │            │
│   │   length: varint               │            │
│   │   attributes: int8             │            │
│   │   timestampDelta: varlong      │            │
│   │   offsetDelta: varint          │            │
│   │   keyLength: varint            │            │
│   │   key: byte[]                  │            │
│   │   valueLen: varint             │            │
│   │   value: byte[]                │            │
│   │   Headers: [name, value]       │            │

└──────────────────────────────────────────────────┘
```

**与 Kafka 的兼容性证明**:任何 Kafka producer 写入的 batch,RedPanda 可直接解析和存储;反之亦然。

### 8. Offset

**Offset** 是消息在 Partition 内的唯一编号,**64 位 Long**,单调递增,严格追加。

```text
Partition 0 的 Offset 序列:

Offset 0     Offset 1     Offset 2     Offset 3
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│  msg-A  │ │  msg-B  │ │  msg-C  │ │  msg-D  │
└─────────┘ └─────────┘ └─────────┘ └─────────┘
   ▲                                            ▲
   │                                            │
   log_start_offset                          high_watermark
```

**几个关键 Offset 值**:

| Offset 类型            | 说明                                                       |
|------------------------|------------------------------------------------------------|
| `log_start_offset`     | Partition 当前最早可读 Offset (可能因 compaction 推进) |
| `high_watermark`       | 已提交的最大 Offset (= 所有副本同步到的位置)              |
| `log_end_offset (LEO)` | 下一条待写入消息的 Offset                                   |
| `committed_offset`     | Raft 已 commit 的 Offset (类似 Kafka 的 HW)              |

### 9. Kafka API 兼容协议层

RedPanda 通过 **Pandaproxy** 实现 Kafka wire protocol,客户端无需任何修改:

```text
客户端 → TCP 9092 → Pandaproxy → Seastar reactor → shard 处理

支持的协议:
  - Produce (v0~v9)
  - Fetch (v0~v13)
  - ListOffsets
  - Metadata
  - CreateTopics / DeleteTopics
  - JoinGroup / SyncGroup / Heartbeat (Consumer Group)
  - InitProducerId / EndTxn (幂等与事务)
  - DescribeAcls / CreateAcls (ACL)
  - ...
```

**Pandaproxy 的角色**:

- 解析 Kafka 二进制请求
- 路由到对应 shard 上的 Partition
- 序列化响应返回客户端

## 五、Raft 共识协议

**Raft** 是 RedPanda 与 Kafka 在**一致性协议层面**的最大差异。RedPanda **从一开始 (v0.x) 就内置 Raft**,而 Kafka 历经 ZooKeeper → KRaft 的多年过渡。

### 1. RedPanda Raft vs Kafka KRaft 对比

| 维度                 | Kafka (KRaft)                          | RedPanda (Raft)                       |
|----------------------|----------------------------------------|---------------------------------------|
| **首次引入**         | Kafka 2.8 (preview),3.3 GA            | v0.x (2019)                          |
| **覆盖范围**         | 仅 Controller Quorum (元数据)         | 每个 Partition 都有自己的 Raft 组   |
| **架构演进**         | 从 ZooKeeper 过渡到 KRaft              | 一步到位,无 ZK 时代                   |
| **副本同步方向**     | Follower 拉取 (FetchRequest)          | Leader 推送 (AppendEntries)          |
| **选举触发**         | Controller 主动调度                    | 任期超时自动触发                      |
| **脑裂保护**         | epoch                                  | term                                  |
| **元数据载体**       | `__cluster_metadata` 内部 Topic        | `__cluster_metadata` 内部 Topic      |
| **部署复杂度**       | Broker + Controller 进程 (可合部)     | 单进程                                |

### 2. 内置 Raft,无需 ZK / 独立 Controller

```text
Kafka KRaft (过渡架构):
┌────────────────────────────────────────┐
│  Kafka Brokers (多个)                  │
│  + KRaft Controller Quorum (3 个进程) │
│  + (历史) ZooKeeper 集群              │
│  → 3 种进程要管理                       │
└────────────────────────────────────────┘

RedPanda 内置 Raft:
┌────────────────────────────────────────┐
│  RedPanda Brokers (N 个)               │
│  → 每个 Broker 自带 Controller 角色    │
│  → 元数据通过 __cluster_metadata Topic │
│  → 1 种进程要管理                       │
└────────────────────────────────────────┘
```

**RedPanda 的两层 Raft**:

1. **数据 Raft**:每个 Partition 一个 Raft 组,负责数据日志的 commit
2. **元数据 Raft**:特殊的 Partition group (`__cluster_metadata`),负责集群成员、Topic/Partition 分配、配置变更

两层 Raft 共享同一套代码库 (`v/raft`),只是配置不同。

### 3. Controller 与 Leader 选举

**Controller** 在 RedPanda 中是个**虚拟角色**,由持有 `__cluster_metadata` Partition 的 Leader 节点担任。

```text
集群中 Controller 选举:

所有 Broker 都参与 __cluster_metadata 的 Raft 组
Term = 3:
  Broker 0: Leader (term=3)
  Broker 1: Follower
  Broker 2: Follower

Broker 0 宕机 → 新选举:
  Term = 4:
    Broker 1: 新 Leader
    Broker 0: (恢复后) Follower
```

**Partition Leader 选举**:

```text
每个 Partition 都是独立的 Raft 组,选举独立进行:

Partition 0 (term=5):  Leader = Broker 0
Partition 1 (term=7):  Leader = Broker 1     ← 不同任期
Partition 2 (term=5):  Leader = Broker 2
Partition 3 (term=6):  Leader = Broker 0

当 Broker 0 故障:
Partition 0 触发选举 → 新 Leader (Broker 1 或 2)
Partition 3 触发选举 → 新 Leader
Partition 1/2 不受影响 (Leader 不在 Broker 0)
```

**Raft 选举过程** (简化):

```
1. Follower 在 election_timeout (随机 150-300ms) 内未收到 AppendEntries
2. Follower 转为 Candidate,term++,投自己一票,广播 RequestVote RPC
3. 获得多数票 (N/2 + 1) 的 Candidate 成为新 Leader
4. 新 Leader 立即发送空 AppendEntries (heartbeat) 维持权威
```

## 八、性能优势根源

RedPanda 相比 Kafka 的性能优势不是某一个 trick,而是**架构选择叠加效应**的结果。

### 1. 零拷贝 (Zero-copy)

```text
传统路径 (4 次拷贝 + 2 次 syscall):
  disk → kernel cache → user buffer → socket buffer → NIC
  ╰────────╮  ╰────────╮  ╰────────╮  ╰────────╮
     copy   1   copy  2    copy  3    copy  4

RedPanda 路径 (1 次拷贝 + 0 次 syscall,使用 sendfile/io_uring):
  disk → kernel cache → NIC
  ╰────────╮  ╰────────╮
    copy 1   zero copy
```

**实现细节**:
- 读取路径:使用 `splice()` 或 io_uring 的 fixed buffer,**避免数据进入用户空间**
- 网络发送:基于 DPDK/XDP 可进一步零拷贝
- Raft 复制:Leader 在转发到 Follower 时,**只发送 file position 引用,Follower 自己从磁盘读**

### 2. 内存池化

**slab allocator**:
```text
进程启动时预分配大块内存 (例如 8GB):
  ┌─────────────────────────────────────────────┐
  │          大块 mmap 区域                     │
  │  ┌─────┬─────┬─────┬─────┬─────┬─────┐     │
  │  │slab0│slab1│slab2│slab3│slab4│slab5│     │
  │  │64B  │128B │256B │512B │1KB  │2KB  │     │
  │  │     │     │     │     │     │     │     │
  │  └─────┴─────┴─────┴─────┴─────┴─────┘     │
  │                                             │
  │  大对象 (>2KB) 走普通 malloc                 │
  └─────────────────────────────────────────────┘

分配时:按 size class 找空闲 slot,O(1)
释放时:回到 free list,O(1)
跨 shard 释放:通过消息传递,异步处理
```

**收益**:
- 无 `malloc` 锁竞争 (多线程下 `malloc` 是著名瓶颈)
- 内存布局对 cache 友好,减少 false sharing
- 进程占用内存可控 (避免 OOM)

### 3. 协程调度

**协程 vs 线程**:

```text
线程模型 (Kafka):
  1 次请求 = 多个线程协作
  ┌──────┐ 切换 ┌──────┐ 切换 ┌──────┐ 切换 ┌──────┐
  │accept │ → │network│ → │  IO  │ → │process│ → done
  └──────┘ 1us   └──────┘ 1us   └──────┘ 1us   └──────┘
  总开销: ~4 次上下文切换,每次 1-10us

协程模型 (RedPanda):
  1 次请求 = 同一线程上的协程切换
  ┌──────┐ 切换 ┌──────┐ 切换 ┌──────┐ 切换 ┌──────┐
  │co_1  │ → │co_2  │ → │co_3  │ → │co_4  │ → done
  └──────┘ 0ns   └──────┘ 0ns   └──────┘ 0ns   └──────┘
  总开销: ~4 次协程切换,每次 ~100ns
```

**Seastar 实现**:基于 ucontext/Boost.Context 自制协程,栈仅 32-64KB,**可创建数十万个协程**,单线程调度数十万并发任务。

### 4. 异步 I/O

**io_uring** (Linux 5.1+) 是 Seastar 的核心:

```text
传统 epoll 模型:
  用户态: syscall(epoll_wait) → 内核扫描 → 返回就绪 fd → 用户态 read → syscall(read) → 内核读盘 → 返回
  → 至少 4 次 syscall,频繁陷入内核

io_uring 模型:
  用户态: 提交 SQE (submission queue entry) → 内核异步处理 → 用户态轮询 CQE (completion queue entry)
  → syscall 几乎消失,内核完成磁盘 I/O 后直接放结果到 CQE
  → 批量提交 (一次提交多个 I/O),减少 syscall 次数
```

**RedPanda 的 I/O 路径**:
- 网络:epoll (默认) / DPDK / XDP
- 磁盘:io_uring (Linux) / 传统 AIO (兼容老内核)
- 文件:Direct I/O 绕过 Page Cache (可选)

## 九、内部请求处理时序

以 Producer 发送一条消息为例,展示 RedPanda 内部完整处理时序。

```text
Producer.send(record) → redpanda 内部处理:

时间     组件                   动作
─────────────────────────────────────────────────────────────────
T+0ms    Producer                序列化 RecordBatch
T+1ms    TCP 9092                建立/复用连接,发送 ProduceRequest
T+2ms    Pandaproxy              解析 Kafka 协议,定位 topic/partition
T+2ms    smp::submit_to          跨 shard 转发到持有该 partition 的 shard
T+3ms    partition_shard         接收请求,校验幂等性 / 事务状态
T+4ms    consensus.append        Raft 阶段 1:Leader 本地追加 (uncommitted)
T+5ms    consensus.replicate     Raft 阶段 2:广播给 Follower (AppendEntries)
         ├─► Broker 1 Follower    写入本地 log,返回成功
         └─► Broker 2 Follower    写入本地 log,返回成功
T+8ms    consensus               收到多数 ACK,committed_offset 推进
T+9ms    smp::submit_to(0)       返回 ACK 给 Pandaproxy 所在 shard
T+10ms   Pandaproxy              序列化 ProduceResponse
T+12ms   TCP 9092                返回给 Producer
─────────────────────────────────────────────────────────────────
总耗时: ~10-15ms (P99)
```

**关键时序点**:

1. **请求路由**:`Pandaproxy` 根据 `topic-partition` 哈希定位到持有该分区的 shard
2. **跨 shard 通信**:`smp::submit_to()` 把请求投递到目标 shard 的 inbound queue
3. **本地 Raft 写入**:目标 shard 上,`consensus.append` 把 record 加到本地未提交日志
4. **副本复制**:`AppendEntries` RPC 异步发给所有 Follower,**不阻塞主线程**
5. **commit 推进**:收到多数 ACK 后,`committed_offset` 推进,触发 ACK 回传
6. **响应回传**:通过 `smp::submit_to()` 回到 Pandaproxy 所在 shard,序列化返回

**Consumer Fetch 路径类似**,区别在于:
- Consumer 可指定 `replica_id` (Follower fetch) 减少 Leader 压力
- Follower fetch 跳过 Raft commit 等待,直接读本地日志 (用于低延迟读)

## 十、磁盘 I/O 模型

### 1. Direct I/O 绕过 Page Cache

**默认 (Linux Page Cache)**:

```text
写入路径:
  user buffer ──copy──► page cache ──async flush──► disk
                ╰── syscall(write) ──╯    ╰── kworker ──╯

读取路径:
  page cache hit → 直接返回 (快)
  page cache miss → 从磁盘加载到 page cache → 返回
```

**Direct I/O (RedPanda 默认开启,可选)**:

```text
写入路径:
  user buffer ──DMA──► disk (O_DIRECT 绕过 page cache)
       ╰── syscall(write) with O_DIRECT ──╯

读取路径:
  disk ──DMA──► user buffer (每次都从磁盘读)
       ╰── syscall(read) with O_DIRECT ──╯
```

**为什么用 Direct I/O**:

| 优势                          | 说明                                                      |
|-------------------------------|-----------------------------------------------------------|
| **避免双重缓存**              | RedPanda 自身有内存池 (slab),不需要 OS page cache 重复缓存 |
| **可预测的内存占用**          | 不会因 page cache 抢占应用内存                            |
| **冷数据明确分离**            | OS 不知道数据"热"还是"冷",Tiered Storage 由应用控制       |
| **减少 page cache 抖动**      | 大数据流下,page cache 经常被冲刷,徒增 IO                 |

**Direct I/O 的代价**:
- 读放大:每次小读都要走磁盘 (但顺序读性能很好)
- 需要应用层 cache (RedPanda 用 slab 替代)

### 2. 缓存策略

RedPanda 内置**两级缓存**:

| 缓存层级           | 位置                | 用途                                              |
|--------------------|---------------------|---------------------------------------------------|
| **chunk cache**    | 内存 (per-shard)   | 最近读取的 record batch,加速热数据访问           |
| **index cache**    | 内存 (per-shard)   | offset → file position 索引,加速定位             |
| **OS page cache**  | 内核 (关闭或有限用) | 仅作为磁盘的读取缓冲,Direct I/O 时绕过          |
| **Tiered Storage** | S3/GCS/Azure       | 冷数据卸载,按对象存储成本计费                    |

**配置示例**:

```yaml
# redpanda.yaml
storage:
  read_buffer_size: 16384           # 16KB 读取块大小
  write_buffer_size: 65536          # 64KB 写入缓冲
  target_batch_size: 1048576        # 1MB 批量大小
  
cloud_storage:
  enabled: true
  bucket: my-redpanda-bucket
  region: us-east-1
  interval: 1 hour                  # 上传间隔
```

## 十一、内存模型

### 1. 进程内 Shard 隔离

RedPanda 单进程内有 N 个 shard (N = CPU 核心数),**每个 shard 是一份完整的栈 + 内存池**,几乎独立运行。

```text
进程地址空间 (单 redpanda 进程):
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Text 段 (代码,所有 shard 共享)                         │
│  Data 段 (全局/静态变量,所有 shard 共享)                │
│  Heap 段 (堆,各 shard 独立内存池)                      │
│                                                         │
│  Shard 0 栈 ┐                                           │
│  Shard 1 栈 │  每个 shard 有独立栈 (~几 MB)              │
│  Shard 2 栈 │  永不被其他 shard 使用                    │
│  Shard 3 栈 ┘                                           │
│                                                         │
│  mmap 区域 (slab pool,各 shard 独立)                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ shard 0  │ │ shard 1  │ │ shard 2  │ │ shard 3  │    │
│  │ memory   │ │ memory   │ │ memory   │ │ memory   │    │
│  │ pool     │ │ pool     │ │ pool     │ │ pool     │    │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘    │
│                                                         │
│  内核态资源 (TCP listener、文件描述符,所有 shard 共享) │
└─────────────────────────────────────────────────────────┘
```

### 2. 无锁通信

**核心规则**:同一份数据的所有权只属于一个 shard。

```text
数据所有权示意:

Shard 0 拥有 Partition 0 的所有数据:
  - log_manager (磁盘句柄)
  - consensus (Raft 状态机)
  - chunk cache
  - index cache

Shard 1 想访问 Partition 0?
  → 必须通过 smp::submit_to(0, ...) 把请求投递过去
  → 不能直接读 Shard 0 的内存 (会破坏所有权)

跨 shard 的消息传输:
  Shard A ──[无锁 SPSC 队列]──► Shard B
       (来自 A 的 outbound)       (A 写入 B 的 inbound)
```

**特殊例外**:

- **只读共享**:某些全局查找表 (如 Topic 元数据) 用 `const` 共享,所有 shard 只读不写
- **原子变量**:用于跨 shard 标志位 (如"shard 是否进入退出流程")

### 3. 内存分配示意

```text
Shard 0 的 slab pool (启动时预分配 2GB):

  ┌────────────────────────────────────────────┐
  │ slab_64   │ slab_128  │ slab_256  │ slab_512│
  │  4096 个  │  2048 个  │  1024 个  │  512 个 │
  │  slot     │  slot     │  slot     │  slot   │
  ├───────────┴───────────┴───────────┴─────────┤
  │ slab_1K   │ slab_2K   │ slab_4K   │ slab_8K │
  │  256 个   │  128 个   │  64 个    │  32 个  │
  ├───────────┴───────────┴───────────┴─────────┤
  │   大对象 (>8K) 走 malloc/free                │
  └────────────────────────────────────────────┘

分配 record_batch (~1KB):
  → 在 slab_1K 中找到一个空闲 slot
  → O(1) 时间

释放 record_batch:
  → 回到 slab_1K 的 free list
  → O(1) 时间,无锁
```

## 十二、关键设计权衡

RedPanda 的设计并非"完美无瑕",每项选择都伴随权衡。

### 1. 主要权衡表

| 设计选择                       | 收益                                       | 代价                                       |
|--------------------------------|--------------------------------------------|--------------------------------------------|
| **C++ 而非 JVM**               | 无 GC、低延迟、低内存占用                   | 生态较小、构建复杂、人才稀缺               |
| **Thread-per-core**           | 无锁、无上下文切换、可预测延迟             | 单 shard 故障=进程崩溃、编程模型复杂       |
| **无 GC**                     | 延迟稳定、内存可控                         | 内存管理责任回到应用层、内存泄漏风险       |
| **内置 Raft**                 | 简单部署、无 ZK                            | 必须理解 Raft 才能 debug                   |
| **单二进制部署**               | 运维简单、镜像小                           | 多租户隔离差、横向扩展粒度粗               |
| **Direct I/O**                | 可控内存、避免双重缓存                     | 读放大、需要应用层 cache                   |
| **Kafka 协议兼容**             | 客户端无修改、生态复用                     | 永远被 Kafka 协议演进"拖着走"             |
| **不分层 (单进程包含所有组件)** | 简单、低延迟                              | 任何组件 bug 都可能影响整个进程             |

### 2. 适用 vs 不适用场景

**适用**:
- 极致低延迟场景 (高频交易、实时推荐、广告竞价)
- 资源受限环境 (边缘计算、容器化部署)
- 运维极简诉求 (不想管 ZK / Controller)
- 不想被 JVM 调优折磨

**不适用**:
- 需要 Kafka Connect / Streams 等 JVM 生态 (RedPanda 不内置)
- 已有大量 Kafka 工具链依赖 (虽然协议兼容,但部分高级特性缺失)
- 团队全是 Java 背景、缺乏 C++ 调优能力
- 需要 Kafka 刚发布的最前沿特性 (RedPanda 跟进有滞后)

### 3. 调试与可观测性

**挑战**:C++ 进程的崩溃可能没有 JVM 那么详细的栈追踪。

**RedPanda 的应对**:

- 详细的 metrics (Prometheus)
- 内置 Admin API (9644) 查询集群状态
- 崩溃时自动生成 coredump
- 支持 gdb/lldb 调试
- 提供 `rpk` CLI 工具

## 核心要点速记

1. **RedPanda = Kafka 兼容 + C++ 重写**——协议 100% 兼容,实现完全重写,主打低延迟与简化运维。

3. **Thread-per-core 模型**——每核一个应用线程,绑定 CPU 亲和性,**没有上下文切换、没有跨核 cache 失效**。

4. **无 GC 是关键**——C++ + 内存池 + RAII,**P99 延迟稳定在毫秒级**,远胜 JVM GC 抖动。

5. **Seastar 框架是基础**——`Future`/`Promise`/协程、`io_uring`、`shard-per-core` 调度,**所有 I/O 异步**。

6. **跨 shard 通信靠消息传递**——`smp::submit_to` + 无锁 SPSC 队列,数据所有权独占,**避免锁**。

7. **内置 Raft 是设计核心**——从一开始就 Raft,每个 Partition 独立 Raft 组,**无需 ZooKeeper / Controller 进程**。

8. **Raft 由 Leader 主动推送**——`AppendEntries` RPC,Follower 不主动拉取,延迟更可控。

9. **单二进制单进程**——一个 `redpanda` 即一切,Broker + Controller + Schema Registry + HTTP Proxy 全部内嵌。

10. **Direct I/O + 自管缓存**——绕过 OS page cache,内存池充当应用层缓存**可控、可预测**。

11. **与 Kafka 对比**:Java/多线程/GC vs C++/thread-per-core/无 GC,**资源占用 ~1/10,延迟低 ~10x**。

12. **代价**:C++ 生态小、单 shard 故障即进程崩溃、需要 C++ 调优能力。

13. **冷存储 (Tiered Storage)** 是 RedPanda 一等公民,S3/GCS/Azure 原生集成,适合数据长期保留场景。

14. **调试比 Kafka 难**:无 JVM 那种丰富工具链,需依赖 metrics、Admin API、coredump 分析。

15. **核心适用场景**:低延迟、资源敏感、运维简化诉求;**不适用**:重度依赖 Kafka Connect/Streams 等 JVM 生态。

16. **版本演进注意**:RedPanda 还在快速迭代,部分 Kafka 新特性可能暂未跟进,选型前需评估功能对齐度。
