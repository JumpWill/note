# RedPanda 安全机制 (RedPanda Security)

## 一、RedPanda 安全概述

### 1. 为什么需要安全机制

RedPanda 作为高性能的 Kafka 兼容流处理平台,在企业环境中常承载订单、交易、日志、用户行为等敏感数据。默认情况下 RedPanda 集群对任何能访问节点的客户端完全开放,这在生产环境是绝对不可接受的。常见的安全威胁包括:

- **未授权访问**:任何人连上 Broker 即可生产/消费任意 Topic,窃取业务数据
- **数据泄露**:消息在网络传输中以明文传输,可能被中间人嗅探获取
- **权限越权**:一个应用账号能读到所有 Topic,违反最小权限原则
- **元数据泄露**:Topic 名称、消费组信息本身就可能包含业务秘密
- **审计缺失**:无法追溯谁在什么时间访问了哪些 Topic、提交了什么 offset
- **合规风险**:GDPR、PCI-DSS、等保 2.0、HIPAA、SOX 等法规对数据安全有强制要求
- **内部威胁**:运维或开发人员越权访问敏感 Topic
- **供应链攻击**:客户端凭证泄露导致外部攻击者接入集群

### 2. RedPanda 安全的三层防护

RedPanda 继承了 Kafka 的三层安全模型,同时做了一些简化与增强:

```
┌──────────────────────────────────────────────┐
│  客户端                                      │
└──────────────────┬───────────────────────────┘
                   │ 传输通道
┌──────────────────▼───────────────────────────┐
│  第一层:加密传输 (Encryption in Transit)      │
│  - TLS 加密客户端与 Broker 之间的数据         │
│  - 防止网络嗅探与中间人攻击                    │
└──────────────────┬───────────────────────────┘
                   │ 已加密
┌──────────────────▼───────────────────────────┐
│  第二层:身份认证 (Authentication)             │
│  - 验证"你是谁"                              │
│  - SASL/PLAIN、SASL/SCRAM                    │
│  - mTLS 双向证书认证                          │
└──────────────────┬───────────────────────────┘
                   │ 身份已确认
┌──────────────────▼───────────────────────────┐
│  第三层:权限授权 (Authorization)              │
│  - 决定"你能做什么"                          │
│  - 基于 ACL 的细粒度授权                       │
│  - Topic、Group、Cluster、TransactionalId、Schema │
└──────────────────────────────────────────────┘
```

### 4. RedPanda 与 Kafka 安全模型对比

RedPanda 与 Kafka 在安全设计上高度兼容,但配置方式有显著差异:

| 维度 | Kafka | RedPanda |
|------|-------|----------|
| 配置文件 | `server.properties` | `redpanda.yaml`(YAML 格式) |
| 管理工具 | `kafka-acls.sh`、`kafka-configs.sh` | `rpk acl`、`rpk cluster user` |
| 监听器模型 | `listeners=PLAINTEXT://...,SSL://...` | 分别配置 `kafka_api`、`rpc_server`、`admin` |
| 凭证存储 | ZK 或 KRaft `__cluster_metadata` | 内部 `__redpanda_internal_topic` |
| SASL 实现 | JAAS 配置文件 | 直接在 redpanda.yaml 中或环境变量 |
| 内部 RPC | 无独立安全 | `rpc_server` 独立 TLS 配置 |
| 启动用户 | 普通用户即可 | 需 `root` 或 `--overprovisioned` |

### 5. 安全特性依赖关系

```
TLS/SSL  →  独立可用,只解决加密传输
SASL     →  独立可用,只解决身份认证
ACL      →  必须依赖 SASL/SSL 才能生效(需要先认证身份)
mTLS     →  TLS 的子集,同时提供加密 + 客户端认证
```

> **重要提示**:RedPanda 推荐同时启用 TLS + SASL + ACL,任一层缺位都意味着攻击面。例如只开 SASL/PLAIN 不开 TLS,密码会被网络嗅探。

### 6. RedPanda 监听器安全矩阵

RedPanda 有三类监听器,各自独立配置安全协议:

| 监听器 | 用途 | 默认端口 | 推荐协议 |
|--------|------|----------|----------|
| `kafka_api` | Kafka 协议客户端连接 | 9092 | `SASL_SSL` |
| `rpc_server` | 内部节点间通信(强一致) | 33145 | `TLS`(仅 TLS) |
| `admin` | Admin API(管控) | 9644 | `HTTPS` |

> 与 Kafka 不同,RedPanda 的 `rpc_server` 监听器仅支持 TLS,不支持 SASL,因为内部通信优先追求性能与节点互信。

## 二、认证 Authentication

### 1. 认证方式总览

RedPanda 支持以下认证机制:

| 认证方式 | 加密 | 复杂度 | 适用场景 | 推荐度 |
|----------|------|--------|----------|--------|
| **SASL/PLAIN** | 否(需配合 TLS) | 低 | 内部测试、学习 | 不推荐生产 |
| **SASL/SCRAM-SHA-256** | 否(需配合 TLS) | 中 | 通用生产环境 | **推荐** |
| **SASL/SCRAM-SHA-512** | 否(需配合 TLS) | 中 | 高安全等级 | 推荐 |
| **mTLS 双向证书认证** | 是 | 中 | 金融、政企 | 高安全场景 |
| **SASL/OAUTHBEARER** | 否(需配合 TLS) | 高 | 云原生、SSO | 企业版 |

### 2. SASL/PLAIN

最简单但最不安全的 SASL 机制,密码以明文方式从客户端传到 Broker(可被中间人嗅探)。**生产环境必须配合 TLS 加密**。

#### 原理

```
客户端                RedPanda Broker
  │                     │
  │  发送用户名:密码     │
  │ ──────────────────> │
  │   (明文 Base64)     │
  │                     │  → 查内置 SCRAM 存储
  │                     │  → 验证密码
  │  认证结果            │
  │ <────────────────── │
```

> RedPanda 与 Kafka 不同,Kafka SASL/PLAIN 由 JAAS 文件提供凭证,而 RedPanda 内部用 SCRAM 存储统一管理所有 SASL 用户(PLAIN 凭证也会被转换为 SCRAM 哈希存储)。

#### 风险点:
- 客户端到 Broker 之间的密码可被嗅探(必须配 TLS)
- 服务端日志若打印错误日志可能泄露部分密码片段
- 不支持密码轮换的优雅过渡期

### 3. SASL/SCRAM (推荐)

SCRAM (Salted Challenge Response Authentication Mechanism) 是基于挑战-应答的强认证机制,**密码不以明文传输**,由 RedPanda 内部 Topic 存储密码哈希。

#### SCRAM 类型对比

| 类型 | 说明 | 推荐度 |
|------|------|--------|
| **SCRAM-SHA-256** | 默认,256 位哈希 | 绝大多数场景 |
| **SCRAM-SHA-512** | 512 位哈希,抗碰撞更强 | 高安全场景 |

#### SCRAM 认证流程

```
客户端                                       RedPanda Broker
  │                                                  │
  │  ① 连接,声明 SCRAM-SHA-256                       │
  │ ──────────────────────────────────────────────>  │
  │                                                  │
  │  ② 挑战:nonce、迭代次数、salt                    │
  │ <──────────────────────────────────────────────  │
  │                                                  │
  │  ③ 计算 ClientProof = HMAC(password, ...)          │
  │ ──────────────────────────────────────────────>  │
  │                                                  │
  │                       计算期望 ServerSignature      │
  │                                                  │
  │  ④ 验证 + 返回 ServerSignature                    │
  │ <──────────────────────────────────────────────  │
  │                                                  │
  │  ⑤ 客户端验证 ServerSignature 防止中间人          │
```

#### SCRAM 优势

- 密码不在网络传输明文
- 服务端只存 salt + 迭代次数 + 哈希值
- 支持密码迭代,抗暴力破解
- 集中存储在 RedPanda 内部 Topic,易管理
- 凭证修改热生效,无需重启

### 4. mTLS 双向证书认证

基于证书的双向认证,客户端与 Broker 互相验证证书,常用于金融、政务等高安全场景。

```
客户端                                    RedPanda Broker
  │                                         │
  │  ① ClientHello (携带 client cert)       │
  │ ──────────────────────────────────────> │
  │                                         │
  │  ② ServerHello + Server Certificate     │
  │ <────────────────────────────────────── │
  │                                         │
  │  ③ 客户端验证服务器证书                 │
  │  ④ Broker 验证客户端证书                │
  │                                         │
  │  ⑤ 双方用协商的对称密钥加密后续通信     │
```

#### 证书类型

| 证书 | 用途 |
|------|------|
| **CA Root Certificate** | 自签根证书,签发 Server/Client 证书 |
| **Server Certificate** | Broker 端使用,客户端连接时验证 |
| **Client Certificate** | 客户端使用,Broker 端验证身份 |

### 5. SASL/OAUTHBEARER (企业版)

RedPanda 企业版支持 OAuth 2.0 / OIDC 集成,通过 JWT Token 认证。

### 6. 认证方式综合对比表

| 维度 | SASL/PLAIN | SASL/SCRAM-SHA-256 | SASL/SCRAM-SHA-512 | mTLS |
|------|-----------|---------------------|---------------------|------|
| 密码传输安全 | 否(需配 TLS) | 是 | 是 | 是 |
| 部署复杂度 | 低 | 中 | 中 | 中 |
| 性能开销 | 低 | 低 | 中 | 高(握手慢) |
| 密码存储 | SCRAM 哈希 | SCRAM 哈希 | SCRAM 哈希 | 私钥 |
| 密码轮换 | rpk 在线改 | rpk 在线改 | rpk 在线改 | 重发证书 |
| 与 LDAP 集成 | 间接(同步脚本) | 间接(同步脚本) | 间接(同步脚本) | 否 |
| 多租户隔离 | 强 | 强 | 强 | 强 |
| **推荐使用** | 学习/测试 | **生产首选** | 高安全 | 金融、政企 |

## 三、配置 SASL/SCRAM 认证 (完整步骤)

### 1. 完整流程图

```
┌─────────────────────────────────────────────────────┐
│ Step 1: 在 redpanda.yaml 启用 SASL 与 TLS             │
│   - kafka_api: [authentication_method: sasl]         │
│   - kafka_api: [ssl: enabled]                        │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 2: 准备 TLS 证书 (CA + Server + 可选 Client)    │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 3: 重启 RedPanda 节点加载配置                   │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 4: 使用 rpk cluster user 创建 SCRAM 用户        │
│   rpk cluster user create alice -p 'secret'         │
└────────────────────────┬────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────┐
│ Step 5: 客户端配置 SASL 凭证并验证                   │
│   rpk topic list -X user=alice                      │
└─────────────────────────────────────────────────────┘
```

### 2. redpanda.yaml 启用 SASL

```yaml
# /etc/redpanda/redpanda.yaml
redpanda:
  data_directory: /var/lib/redpanda/data
  
  # Kafka API 监听器 (客户端连接)
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: internal
      authentication_method: sasl    # 关键:启用 SASL
      ssl:                            # 关键:启用 TLS
        enabled: true
        require_client_auth: false    # 单向 TLS(配合 SASL)
        cert_file: /etc/redpanda/certs/broker.crt
        key_file: /etc/redpanda/certs/broker.key
        truststore_file: /etc/redpanda/certs/ca.crt
    
  # 内部 RPC 监听器 (节点间通信)
  rpc_server:
    address: 0.0.0.0
    port: 33145
    tls:
      enabled: true
      require_client_auth: true       # RPC 必须双向认证
      cert_file: /etc/redpanda/certs/broker.crt
      key_file: /etc/redpanda/certs/broker.key
      truststore_file: /etc/redpanda/certs/ca.crt
  
  # Admin API 监听器 (管控)
  admin:
    - address: 0.0.0.0
      port: 9644
      name: internal
      enabled: true
      tls:
        enabled: true
        cert_file: /etc/redpanda/certs/admin.crt
        key_file: /etc/redpanda/certs/admin.key
        truststore_file: /etc/redpanda/certs/ca.crt

# 集群信息(每个节点不同)
node_id: 1
cluster_id: "redpanda-cluster-001"
```

### 3. 启动 RedPanda 并验证 SASL

```bash
# 1. 启动服务(以 root 启动或加 --overprovisioned)
systemctl start redpanda

# 2. 查看启动日志(确认 SASL 已启用)
journalctl -u redpanda -f | grep -i "sasl\|tls"

# 3. 验证监听器
ss -tlnp | grep -E "9092|33145|9644"
# 应看到三个端口都监听

# 4. 验证 TLS 握手
openssl s_client -connect redpanda1:9092 -showcerts < /dev/null
# 应能成功握手并看到证书
```

### 4. 创建 SCRAM 用户

RedPanda 使用 `rpk cluster user` 管理 SCRAM 用户。

#### 创建用户 (首次)

```bash
# 语法:rpk cluster user create <username> -p <password>
rpk cluster user create alice \
  -p 'alice-secret-password' \
  --mechanism SCRAM-SHA-256

# 同时启用 SHA-512(高安全场景)
rpk cluster user create alice \
  -p 'alice-secret-password' \
  --mechanism SCRAM-SHA-256 \
  --mechanism SCRAM-SHA-512

# 通过 stdin 输入密码(避免 shell 历史)
rpk cluster user create alice --mechanism SCRAM-SHA-256
# 提示: Enter password: ********
```

#### 参数说明

| 参数 | 含义 |
|------|------|
| `<username>` | 用户名(Principal: `User:alice`) |
| `-p <password>` | 明文密码,内部计算哈希后存储 |
| `--mechanism` | SCRAM 算法,可多个 |
| `--api-urls` | Admin API 地址,默认 `localhost:9644` |

#### 修改密码 (热生效,无需重启)

```bash
# 修改 alice 的密码
rpk cluster user alter alice \
  -p 'new-alice-password' \
  --mechanism SCRAM-SHA-256

# 通过 stdin 输入
rpk cluster user alter alice --mechanism SCRAM-SHA-256
# 提示: Enter password: ********
```

#### 删除用户

```bash
# 完全删除 alice
rpk cluster user delete alice

# 同时删除多个机制
rpk cluster user delete alice --mechanism SCRAM-SHA-256
rpk cluster user delete alice --mechanism SCRAM-SHA-512
```

#### 查看用户列表

```bash
# 列出所有 SCRAM 用户
rpk cluster user list

# 输出示例:
# ALICE
# BOB
# APP-PRODUCER

# 查看某用户详情(需 Admin API)
curl -sk -u admin:admin-password \
  https://redpanda1:9644/v1/security/users/alice
```

> **关键提示**:密码不会以明文形式回显,RedPanda 内部存储的是 salt + 哈希值,这是 SCRAM 的安全基础。

### 5. 创建管理员用户

```bash
# 1. 创建管理员 SCRAM 用户
rpk cluster user create admin \
  -p 'admin-super-secret' \
  --mechanism SCRAM-SHA-512

# 2. 授权为超级用户(绕过 ACL 检查)
# 通过 redpanda.yaml 配置 superusers
rpk cluster config set superusers '["admin"]'

# 或直接编辑 redpanda.yaml:
#   superusers: ["admin"]
```

### 6. 客户端连接配置

#### 方式一:rpk 命令行(推荐)

```bash
# 1. 全局配置 rpk(避免每次输入)
rpk profile create prod \
  --brokers redpanda1:9092,redpanda2:9092 \
  --user alice \
  --password 'alice-secret' \
  --sasl-mechanism SCRAM-SHA-256 \
  --tls-ca /etc/redpanda/certs/ca.crt

# 2. 切换到 prod profile
rpk profile use prod

# 3. 列出 Topic
rpk topic list

# 4. 查看集群信息
rpk cluster info

# 5. 生产消息
echo "hello" | rpk topic produce test-topic

# 6. 消费消息
rpk topic consume test-topic --num 10
```

#### 方式二:每次指定参数

```bash
# 列出 Topic
rpk topic list \
  --brokers redpanda1:9092 \
  --user alice \
  --password 'alice-secret' \
  --sasl-mechanism SCRAM-SHA-256 \
  --tls-ca /etc/redpanda/certs/ca.crt

# 消费消息
rpk topic consume test-topic \
  --brokers redpanda1:9092 \
  --user alice \
  --password 'alice-secret' \
  --sasl-mechanism SCRAM-SHA-256 \
  --tls-ca /etc/redpanda/certs/ca.crt \
  --num 10
```

#### 方式三:环境变量(适合 CI/CD)

```bash
# 设置环境变量
export REDPANDA_BROKERS="redpanda1:9092,redpanda2:9092"
export REDPANDA_USER="alice"
export REDPANDA_PASSWORD="alice-secret"
export REDPANDA_SASL_MECHANISM="SCRAM-SHA-256"
export REDPANDA_TLS_CA="/etc/redpanda/certs/ca.crt"

# rpk 自动读取
rpk topic list
```

#### 方式四:Java 代码

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "redpanda1:9092");
props.put(ProducerConfig.SECURITY_PROTOCOL_CONFIG, "SASL_SSL");
props.put("sasl.mechanism", "SCRAM-SHA-256");
props.put("sasl.jaas.config",
    "org.apache.kafka.common.security.scram.ScramLoginModule required "
  + "username=\"alice\" password=\"alice-secret\";");
props.put("ssl.truststore.location", "/etc/redpanda/certs/client.truststore.jks");
props.put("ssl.truststore.password", "truststore-password");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

#### 方式五:Python (kafka-python)

```python
from kafka import KafkaProducer
import ssl

context = ssl.create_default_context()
context.load_verify_locations("/etc/redpanda/certs/ca.crt")

producer = KafkaProducer(
    bootstrap_servers=["redpanda1:9092"],
    security_protocol="SASL_SSL",
    sasl_mechanism="SCRAM-SHA-256",
    sasl_plain_username="alice",
    sasl_plain_password="alice-secret",
    ssl_context=context,
)

producer.send("test-topic", b"hello")
producer.flush()
```

### 7. 完整命令验证清单

```bash
# 1. 启动 RedPanda
systemctl start redpanda

# 2. 验证监听器
```

## 四、授权 ACL

### 1. ACL 机制概述

RedPanda 的授权通过 ACL (Access Control List) 实现,**默认拒绝所有访问**(`allow_acl=null`),必须显式授予权限。

#### 关键概念

| 概念 | 说明 |
|------|------|
| **Principal (主体)** | 被授权的对象,通常是 `User:alice` |
| **Resource (资源)** | 被保护的对象:Topic、Group、Cluster、TransactionalId、Schema |
| **Operation (操作)** | 允许的动作:Read、Write、Create、Describe 等 |
| **Permission (权限)** | Principal × Resource × Operation 三元组 |
| **allow_acl / deny_acl** | ACL 规则,可设全局默认或针对具体资源 |
| **__redpanda_internal_topic** | ACL 持久化在 RedPanda 内部 Topic |

### 2. rpk acl 命令总览

```bash
# 语法
rpk acl create [flags]
rpk acl delete [flags]
rpk acl list [flags]

# 通用参数
--brokers <list>           # Broker 列表
--user <string>            # SASL 用户名
--password <string>        # SASL 密码
--sasl-mechanism <string>  # SCRAM-SHA-256 / SCRAM-SHA-512
--tls-ca <file>            # CA 证书
```

### 3. 资源类型 (Resource Types)

RedPanda 5 类受 ACL 保护的资源:

| 资源类型 | 说明 | rpk 参数 |
|----------|------|----------|
| **Topic** | 控制对 Topic 的读写、创建、删除等 | `--topic` |
| **Group** | Consumer Group,控制提交 offset 等 | `--group` |
| **Cluster** | 集群级,如创建 Topic、查看 broker 列表等 | `--cluster` |
| **TransactionalId** | 事务 ID,控制幂等生产者事务 | `--transactional-id` |
| **Schema** | Schema Registry 中 Schema | `--schema` |

### 4. 操作类型 (Operations)

#### Topic 级操作

| 操作 | 含义 | 触发场景 |
|------|------|----------|
| **READ** | 读消息 | 消费者消费 Topic |
| **WRITE** | 写消息 | 生产者发送消息 |
| **CREATE** | 创建 Topic | `rpk topic create` |
| **DELETE** | 删除 Topic | `rpk topic delete` |
| **ALTER** | 修改 Topic 配置 | `rpk topic alter-config` |
| **DESCRIBE** | 查看 Topic 元数据 | `rpk topic list`、`rpk topic describe` |
| **DESCRIBE_CONFIGS** | 查看 Topic 配置 | `rpk topic describe-configs` |
| **ALTER_CONFIGS** | 修改 Topic 配置 | `rpk topic alter-configs` |

#### Group 级操作

| 操作 | 含义 |
|------|------|
| **READ** | 读 offset 等 |
| **DESCRIBE** | 查看消费组 |
| **DELETE** | 删除消费组 |
| **COMMIT_OFFSETS** | 提交 offset(隐式) |

> 消费 Topic 时,通常需要 **Topic:READ + Topic:DESCRIBE + Group:READ + Group:DESCRIBE** 同时具备。

#### Cluster 级操作

| 操作 | 含义 |
|------|------|
| **CREATE** | 创建 Topic |
| **ALTER** | 修改集群 |
| **DESCRIBE** | 查看集群元数据 |
| **CLUSTER_ACTION** | 更新集群信息 |
| **DESCRIBE_CONFIGS** | 查看 broker 配置 |
| **ALTER_CONFIGS** | 修改 broker 配置 |
| **IDEMPOTENT_WRITE** | 幂等写入(事务前置) |

#### TransactionalId 操作

| 操作 | 含义 |
|------|------|
| **DESCRIBE** | 查看事务 ID |
| **WRITE** | 写入事务 |
| **ALTER** | 修改事务 ID 关联 |

#### Schema 操作(企业版 Schema Registry)

| 操作 | 含义 |
|------|------|
| **DESCRIBE** | 查看 Schema |
| **READ** | 读取 Schema 内容 |
| **WRITE** | 创建/更新 Schema |
| **DELETE** | 删除 Schema |

### 5. rpk acl create 完整语法

```bash
rpk acl create [flags]

# 关键 flags
--allow-principal <string>      # 允许该 principal(可多个 --allow-principal)
--deny-principal <string>       # 拒绝该 principal
--operation <string>            # 操作类型,可多个(READ, WRITE, CREATE...)
--topic <string>                # 限定 Topic,可模式匹配
--group <string>                # 消费组
--cluster                       # Cluster 级操作
--transactional-id <string>     # 事务 ID
--schema <string>               # Schema Registry 资源
--resource-pattern-type <type>  # match | prefixed | any(默认 match)
```

#### 完整示例

```bash
# 给 alice 授予 test-topic 的读写权限
rpk acl create \
  --allow-principal User:alice \
  --operation READ --operation WRITE --operation DESCRIBE \
  --topic test-topic

# 同时给消费组权限(消费消息必须)
rpk acl create \
  --allow-principal User:alice \
  --operation READ --operation DESCRIBE \
  --group test-group

# 允许 alice 描述集群(列出 Topic 等)
rpk acl create \
  --allow-principal User:alice \
  --operation DESCRIBE \
  --cluster

# 给 bob 授予所有 Topic 的读权限(慎用)
rpk acl create \
  --allow-principal User:bob \
  --operation READ --operation DESCRIBE \
  --topic '*' \
  --resource-pattern-type any
```

### 6. ACL 模式匹配 (Pattern Types)

| 模式 | 说明 | 示例 |
|------|------|------|
| `match`(默认) | 字面匹配 | `test-topic` 精确匹配 |
| `prefixed` | 前缀匹配 | `order-` 匹配 `order-events`、`order-payments` |
| `any` | 任意匹配(`*`) | 匹配所有资源 |

```bash
# 匹配所有 Topic(慎用)
rpk acl create \
  --allow-principal User:ops \
  --operation ALL \
  --topic '*' \
  --resource-pattern-type any

# 匹配以 order- 开头的 Topic
rpk acl create \
  --allow-principal User:order-app \
  --operation READ --operation DESCRIBE \
  --topic 'order-' \
  --resource-pattern-type prefixed
```

### 7. 撤销 ACL 规则

```bash
# 撤销 alice 对 test-topic 的读权限
rpk acl delete \
  --allow-principal User:alice \
  --operation READ \
  --topic test-topic

# 完全移除 alice 的所有权限(按资源类型逐一删除)
rpk acl delete \
  --allow-principal User:alice \
  --operation ALL \
  --topic '*' \
  --resource-pattern-type any

# 撤销 Cluster 权限
rpk acl delete \
  --allow-principal User:alice \
  --operation ALL \
  --cluster
```

### 8. 查询 ACL 列表

```bash
# 列出所有 ACL
rpk acl list

# 过滤某用户的规则
rpk acl list --principal User:alice

# 过滤某 Topic 的规则
rpk acl list --topic test-topic

# 输出格式:
# PRINCIPAL     RESOURCE  RESOURCE-TYPE  PATTERN  PERMISSION  OPERATION
# User:alice    test-topic  TOPIC          LITERAL  ALLOW       READ
# User:alice    test-topic  TOPIC          LITERAL  ALLOW       WRITE
# User:alice    test-group  GROUP          LITERAL  ALLOW       READ
```

## 五、ACL 配置实战

### 1. 应用账号(生产)

场景:`order-app` 只能向 `order-events` Topic 写消息。

```bash
# 1. 创建 SCRAM 凭证
rpk cluster user create order-app \
  -p 'order-app-secret' \
  --mechanism SCRAM-SHA-256

# 2. 授予 Topic 写权限
rpk acl create \
  --allow-principal User:order-app \
  --operation WRITE --operation DESCRIBE \
  --topic order-events

# 3. 授予 Cluster DESCRIBE 权限(列出 Topic 元数据)
rpk acl create \
  --allow-principal User:order-app \
  --operation DESCRIBE \
  --cluster

# 验证:order-app 现在能:
#   - rpk topic list  (cluster DESCRIBE)
#   - rpk topic describe order-events  (topic DESCRIBE)
#   - echo "msg" | rpk topic produce order-events  (topic WRITE)
# 但不能:
#   - rpk topic consume order-events  (无 READ)
#   - rpk topic create new-topic  (无 CREATE)
```

### 2. 消费者账号

场景:`analytics-consumer` 只能消费 `analytics-events` 和 `analytics-snapshot` 两个 Topic。

```bash
# 1. 创建 SCRAM 凭证
rpk cluster user create analytics-consumer \
  -p 'analytics-secret' \
  --mechanism SCRAM-SHA-256

# 2. 授予 Topic READ 权限(可使用 prefix 模式)
rpk acl create \
  --allow-principal User:analytics-consumer \
  --operation READ --operation DESCRIBE \
  --topic 'analytics-' \
  --resource-pattern-type prefixed

# 3. 授予 Group 权限(消费必须)
rpk acl create \
  --allow-principal User:analytics-consumer \
  --operation READ --operation DESCRIBE \
  --group 'analytics-' \
  --resource-pattern-type prefixed

# 4. 授予 Cluster DESCRIBE
rpk acl create \
  --allow-principal User:analytics-consumer \
  --operation DESCRIBE \
  --cluster

# 验证:analytics-consumer 现在能:
#   - rpk topic consume analytics-events --group analytics-grp-1
#   - rpk topic consume analytics-snapshot --group analytics-grp-2
# 但不能:
#   - 写任何 Topic
#   - 读 order-events、payment-events 等非 analytics-* Topic
```

### 3. 管理员账号

场景:`ops-admin` 需要管理所有 Topic、Group、Cluster。

```bash
# 1. 创建 SCRAM 凭证
rpk cluster user create ops-admin \
  -p 'ops-super-secret' \
  --mechanism SCRAM-SHA-512

# 2. 设为 superuser(配置 redpanda.yaml 后重启,或运行时配置)
rpk cluster config set superusers '["ops-admin"]'

# 或在 redpanda.yaml 中设置:
# redpanda:
#   superusers: ["ops-admin"]

# 3. superuser 自动绕过所有 ACL 检查
# 无需额外授予,即可执行所有操作

# 注意:也可以用 ACL 显式授权(慎用)
rpk acl create \
  --allow-principal User:ops-admin \
  --operation ALL \
  --topic '*' \
  --resource-pattern-type any

rpk acl create \
  --allow-principal User:ops-admin \
  --operation ALL \
  --group '*' \
  --resource-pattern-type any

rpk acl create \
  --allow-principal User:ops-admin \
  --operation ALL \
  --cluster
```

### 4. 跨域访问场景

#### 场景 A:多应用共享 Topic 读权限

```bash
# 三个应用都需要读 user-events
for APP in app1 app2 app3; do
  rpk cluster user create $APP \
    -p "$APP-secret" --mechanism SCRAM-SHA-256
  
  rpk acl create \
    --allow-principal User:$APP \
    --operation READ --operation DESCRIBE \
    --topic user-events
done
```

#### 场景 B:开发者只读测试 Topic

```bash
# 开发者 alice 只读 dev-* Topic
rpk acl create \
  --allow-principal User:alice \
  --operation READ --operation DESCRIBE \
  --topic 'dev-' \
  --resource-pattern-type prefixed

# 开发者 alice 列出 Topic(cluster DESCRIBE)
rpk acl create \
  --allow-principal User:alice \
  --operation DESCRIBE \
  --cluster
```

#### 场景 C:ETL 跨账号批量消费

```bash
# ETL 服务批量读所有 Topic
rpk acl create \
  --allow-principal User:etl-consumer \
  --operation READ --operation DESCRIBE \
  --topic '*' \
  --resource-pattern-type any

# 但 ETL 不能写、不能删 Topic
```

### 5. 显式 Deny 规则

Denylist 用于临时禁用某用户/资源,优先级高于 Allow。

```bash
# 拒绝 bob 访问 finance-* Topic(即使有更宽泛的 Allow)
rpk acl create \
  --deny-principal User:bob \
  --operation ALL \
  --topic 'finance-' \
  --resource-pattern-type prefixed
```

## 六、传输加密 TLS/SSL

### 1. TLS/SSL 工作流

```
1. TLS 握手
   ClientHello → ServerHello + Server Cert
   客户端验证服务器证书 (检查 CA 签发、域名、有效期)
   ServerHello Done

2. 密钥交换
   Client Key Exchange (RSA / DH / ECDHE)
   → 双方推导出对称会话密钥

3. 对称加密通信
   AES-256-GCM / ChaCha20-Poly1305 等加密应用数据
```

### 2. 生成证书

#### 完整 OpenSSL 脚本

```bash
#!/bin/bash
# gen-redpanda-certs.sh
# 生成 RedPanda 全套 TLS 证书

set -e
CERT_DIR=/etc/redpanda/certs
DAYS=3650  # 10 年

mkdir -p $CERT_DIR
cd $CERT_DIR

# 1. 生成 CA 私钥与自签证书
openssl req -new -x509 -nodes \
  -keyout ca.key \
  -out ca.crt \
  -days $DAYS \
  -subj "/CN=RedPanda-CA/O=MyCompany/C=CN"

# 2. 生成 Broker 私钥与 CSR(多节点 SAN)
cat > openssl.cnf <<EOF
[req]
distinguished_name = req_distinguished_name
req_extensions = v3_req
prompt = no

[req_distinguished_name]
CN = redpanda-cluster

[v3_req]
subjectAltName = @alt_names

[alt_names]
DNS.1 = redpanda1.example.com
DNS.2 = redpanda2.example.com
DNS.3 = redpanda3.example.com
DNS.4 = redpanda.example.com
IP.1  = 10.0.0.11
IP.2  = 10.0.0.12
IP.3  = 10.0.0.13
EOF

openssl req -new -nodes \
  -keyout broker.key \
  -out broker.csr \
  -config openssl.cnf \
  -subj "/CN=redpanda-cluster/O=MyCompany"

# 3. CA 签发 Broker 证书
openssl x509 -req \
  -in broker.csr \
  -CA ca.crt \
  -CAkey ca.key \
  -CAcreateserial \
  -out broker.crt \
  -days $DAYS \
  -extensions v3_req \
  -extfile openssl.cnf

# 4. 生成 Admin 证书(可选,独立)
openssl req -new -nodes \
  -keyout admin.key \
  -out admin.csr \
  -subj "/CN=redpanda-admin/O=MyCompany"

openssl x509 -req \
  -in admin.csr \
  -CA ca.crt \
  -CAkey ca.key \
  -CAcreateserial \
  -out admin.crt \
  -days $DAYS

# 5. 清理临时文件
rm -f *.csr *.cnf ca.srl

# 6. 设置权限
chmod 600 *.key
chmod 644 *.crt

ls -la $CERT_DIR
```

#### 简化方法:rpk 内置证书生成(开发测试用)

```bash
# RedPanda 提供 rpk 生成开发证书(仅用于测试/开发)
rpk generate cert \
  --ca-key /etc/redpanda/certs/ca.key \
  --ca-cert /etc/redpanda/certs/ca.crt \
  --brokers redpanda1:9092,redpanda2:9092,redpanda3:9092 \
  --output /etc/redpanda/certs

# 输出 broker.crt、broker.key、admin.crt、admin.key
```

### 3. RedPanda 启用 TLS

#### Kafka API 端口 TLS

```yaml
# /etc/redpanda/redpanda.yaml
redpanda:
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: internal
      authentication_method: sasl
      ssl:

        key_file: /etc/redpanda/certs/broker.key
        truststore_file: /etc/redpanda/certs/ca.crt
        # 可选:允许的 TLS 版本
        min_tls_version: "TLSv1.2"
```

#### 内部 RPC 端口 TLS

```yaml
redpanda:
  rpc_server:
    address: 0.0.0.0
    port: 33145

      require_client_auth: true           # RPC 必须双向认证

      key_file: /etc/redpanda/certs/broker.key
      truststore_file: /etc/redpanda/certs/ca.crt
```

#### Admin API 端口 TLS


```bash

```

#### Java 客户端

```properties
# client.properties
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-256
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="alice" password="alice-secret";

```

```bash

  -file /etc/redpanda/certs/ca.crt \
  -keystore /etc/redpanda/certs/client.truststore.jks \
  -storepass truststore-password
```

### 6. TLS 性能影响

| 指标 | 影响 | 说明 |
|------|------|------|
| **握手延迟** | +50-200ms (首连接) | TLS 握手涉及密钥交换 |
| **吞吐** | -10% ~ -30% (TLSv1.2)<br>-5% ~ -15% (TLSv1.3) | CPU 加解密开销 |
| **CPU 使用** | +1-2 核 | AES-NI 可显著降低 |
| **会话复用** | 0 额外开销 | SSL session resumption |

## 七、mTLS 双向认证

### 1. 什么是 mTLS

mTLS (mutual TLS) 在标准 TLS 基础上,增加 **服务端验证客户端证书** 的步骤,实现双向身份认证。

```
单向 TLS:服务端证书 → 客户端验证服务端
双向 mTLS:服务端证书 + 客户端证书 → 双向验证
```

### 2. 客户端证书生成

```bash
#!/bin/bash
# gen-client-certs.sh

set -e
CERT_DIR=/etc/redpanda/certs

# 1. 为客户端 alice 生成私钥与 CSR
openssl req -new -nodes \
  -keyout alice.key \
  -out alice.csr \
  -subj "/CN=alice/O=MyApp"

# 2. CA 签发客户端证书
openssl x509 -req \
  -in alice.csr \
  -CA $CERT_DIR/ca.crt \
  -CAkey $CERT_DIR/ca.key \
  -CAcreateserial \
  -out alice.crt \
  -days 3650

# 3. 打包成 PKCS#12 格式(Java 客户端需要)
openssl pkcs12 -export \
  -in alice.crt \
  -inkey alice.key \
  -certfile $CERT_DIR/ca.crt \
  -name alice \
  -out alice.p12 \
  -password pass:alice-p12-password

# 清理
rm -f alice.csr
chmod 600 alice.key alice.p12
```

### 3. 服务端验证客户端证书

#### Kafka API 启用 mTLS

```yaml
redpanda:
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: internal
      authentication_method: sasl    # 可与 SASL 并存,作为增强
      ssl:
        enabled: true
        require_client_auth: true    # 关键:要求客户端证书
        cert_file: /etc/redpanda/certs/broker.crt
        key_file: /etc/redpanda/certs/broker.key
        truststore_file: /etc/redpanda/certs/ca.crt
```

#### 仅启用 mTLS(无需 SASL)

```yaml
redpanda:
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: internal
      authentication_method: mtls    # 仅 mTLS 认证
      ssl:
        enabled: true
        require_client_auth: true    # 必须双向认证
        cert_file: /etc/redpanda/certs/broker.crt
        key_file: /etc/redpanda/certs/broker.key
        truststore_file: /etc/redpanda/certs/ca.crt
```

> **注意**:`authentication_method: mtls` 仅 RedPanda 24.1+ 支持,旧版本需用 SASL + mTLS 组合。

### 4. 客户端 mTLS 配置

#### rpk 客户端 mTLS

```bash
# 仅 mTLS 模式(无 SASL)
rpk profile create prod-mtls \
  --brokers redpanda1:9092 \
  --tls-ca /etc/redpanda/certs/ca.crt \
  --tls-cert /etc/redpanda/certs/alice.crt \
  --tls-key /etc/redpanda/certs/alice.key

# SASL + mTLS 组合(更安全)
```

### 6. mTLS 最佳实践

- **客户端证书唯一性**:每个客户端使用不同证书,便于审计追踪
- **证书有效期**:生产建议 1-2 年,便于轮换
- **证书吊销**:使用 CRL 或 OCSP 管理吊销列表(RedPanda 24.2+ 支持 OCSP Stapling)
- **客户端私钥保护**:私钥文件 `chmod 600`,绝不进入 Git
- **Subject DN 命名规范**:CN 用应用名或账号名,O 用业务部门,便于审计识别

### 1. 最小权限原则


## 十二、与外部系统集成

### 1. LDAP 集成

RedPanda 自身不直接支持 LDAP,但企业版提供 LDAP 同步功能,或通过脚本同步 LDAP 用户到 SCRAM。

#### 方式一:rpk + 同步脚本(自建)

```bash
#!/bin/bash
# sync-ldap-to-redpanda.sh
# 从 LDAP 同步用户到 RedPanda SCRAM

LDAP_HOST="ldap.example.com"
LDAP_BASE="ou=users,dc=example,dc=com"
RPK="rpk --brokers redpanda1:9092 \
  --user admin --password '${ADMIN_PASSWORD}' \
  --sasl-mechanism SCRAM-SHA-512 \
  --tls-ca /etc/redpanda/certs/ca.crt"

# 1. 列出 LDAP 用户
USERS=$(ldapsearch -x -H ldap://$LDAP_HOST -b $LDAP_BASE \
  "(objectClass=person)" uid 2>/dev/null \
  | grep "^uid:" | awk '{print $2}')

# 2. 为每个 LDAP 用户创建 SCRAM 凭证
for USER in $USERS; do
  # 从 LDAP 取密码(假设 LDAP 允许读 userPassword)
  LDAP_PWD=$(ldapsearch -x -H ldap://$LDAP_HOST -b $LDAP_BASE \
    "(uid=$USER)" userPassword 2>/dev/null \
    | grep "^userPassword:" | awk '{print $2}')
  
  # 在 RedPanda 创建/更新用户
  if $RPK cluster user list | grep -qw "$USER"; then
    $RPK cluster user alter "$USER" \
      -p "$LDAP_PWD" \
      --mechanism SCRAM-SHA-256
  else
    $RPK cluster user create "$USER" \
      -p "$LDAP_PWD" \
      --mechanism SCRAM-SHA-256
  fi
done

echo "LDAP 同步完成"
```

#### 方式二:企业版 RedPanda(原生 LDAP)

```
企业版配置(redpanda.yaml):

  ldap:
```

### 2. OAuth 2.0 / OIDC 集成

RedPanda 企业版支持 OAuth 2.0 / OIDC 集成,客户端通过 JWT Token 认证。

#### 工作流程

```
Kafka Client                       RedPanda Broker       OAuth/OIDC Server
  │                                      │
  │  ① POST /oauth/token (client_credentials)│
  │ ─────────────────────────────────────── │ → OAuth Server
  │                                      │   (验证 client_id/client_secret)
  │  返回 access_token (JWT)             │
  │ <───────────────────────────────────── │
  │                                      │
  │  ② SASL/OAUTHBEARER 携带 token 连接   │
  │ ────────────────────────────────────> │
  │                                      │ ③ 验证 token
  │                                      │   - JWT 签名验证
  │                                      │   - 检查过期
  │                                      │   - 提取 principal
  │                                      │
  │  ④ 认证成功,授权请求                  │
  │ <──────────────────────────────────── │
```

#### Broker 配置

```yaml
# /etc/redpanda/redpanda.yaml
redpanda:
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: internal
      authentication_method: oauthbearer    # 启用 OAuth
      ssl:
        enabled: true
        cert_file: /etc/redpanda/certs/broker.crt
        key_file: /etc/redpanda/certs/broker.key
        truststore_file: /etc/redpanda/certs/ca.crt
  
  # OAuth 配置(企业版)
  oauthbearer:
    issuer: https://oauth-server.example.com
```

### 4. 部署流程检查清单

```bash
#!/bin/bash
# deploy-redpanda-security.sh
# RedPanda 安全部署脚本

set -e

# 1. 安装证书
mkdir -p /etc/redpanda/certs
cp /tmp/ca.crt /tmp/broker.crt /tmp/broker.key /tmp/admin.crt /tmp/admin.key \
  /etc/redpanda/certs/
chmod 600 /etc/redpanda/certs/*.key
chmod 644 /etc/redpanda/certs/*.crt
chown -R redpanda:redpanda /etc/redpanda/certs/

# 2. 部署配置
cp /tmp/redpanda.yaml /etc/redpanda/redpanda.yaml
chmod 640 /etc/redpanda/redpanda.yaml
chown redpanda:redpanda /etc/redpanda/redpanda.yaml

# 3. 启动 RedPanda
systemctl restart redpanda
sleep 15

# 4. 验证启动
ss -tlnp | grep -E "9092|33145|9644"
journalctl -u redpanda --since "1 minute ago" | grep -i "started\|ready"

# 5. 创建管理员用户
rpk cluster user create admin \
  -p "${ADMIN_PASSWORD}" \
  --mechanism SCRAM-SHA-512

# 6. 等待 SCRAM 凭证生效
sleep 5

# 7. 创建业务用户
for USER in order-app analytics-consumer etl-consumer; do
  USER_PASSWORD=$(openssl rand -base64 16)
  rpk cluster user create $USER \
    -p "$USER_PASSWORD" \
    --mechanism SCRAM-SHA-256
  echo "$USER: $USER_PASSWORD" | tee -a /tmp/redpanda-users.txt
done
chmod 600 /tmp/redpanda-users.txt

# 8. 创建 Topic 并授权
for TOPIC in order-events user-events audit-log; do
  rpk topic create $TOPIC -p 3 -r 3 \
    --user admin --password "${ADMIN_PASSWORD}" \
    --sasl-mechanism SCRAM-SHA-512 \
    --tls-ca /etc/redpanda/certs/ca.crt || true
done

# 9. 创建 ACL(以 admin 身份)
ADMIN_RPK="rpk --user admin --password ${ADMIN_PASSWORD} \
  --sasl-mechanism SCRAM-SHA-512 --tls-ca /etc/redpanda/certs/ca.crt"

$ADMIN_RPK acl create \
  --allow-principal User:order-app \
  --operation WRITE --operation DESCRIBE \
  --topic order-events

$ADMIN_RPK acl create \
  --allow-principal User:order-app \
  --operation DESCRIBE --cluster

$ADMIN_RPK acl create \
  --allow-principal User:analytics-consumer \
  --operation READ --operation DESCRIBE \
  --topic 'analytics-' --resource-pattern-type prefixed

$ADMIN_RPK acl create \
  --allow-principal User:analytics-consumer \
  --operation READ --operation DESCRIBE \
  --group 'analytics-' --resource-pattern-type prefixed

echo "===== RedPanda 安全部署完成 ====="
echo "用户凭证: /tmp/redpanda-users.txt (chmod 600)"
```

## 核心要点速记

### 1. 安全三层架构

```
加密传输 (TLS/SSL)
   ↓
身份认证 (SASL/SCRAM 推荐)
   ↓
权限授权 (ACL 默认拒绝,按需放行)
```

### 2. 认证方式选择

- **学习/测试**:SASL/PLAIN
- **生产首选**:SASL/SCRAM-SHA-256
- **高安全场景**:SASL/SCRAM-SHA-512
- **金融/政企**:mTLS 双向认证
- **云原生**:SASL/OAUTHBEARER(企业版)

### 3. RedPanda 与 Kafka 安全命令对比

| 操作 | Kafka | RedPanda |
|------|-------|----------|
| 创建 SCRAM 用户 | `kafka-configs.sh --create --alter --entity-type users` | `rpk cluster user create` |
| 修改密码 | `kafka-configs.sh --alter` | `rpk cluster user alter` |
| 删除用户 | `kafka-configs.sh --alter --delete-config` | `rpk cluster user delete` |
| 列出用户 | `kafka-configs.sh --describe --entity-type users` | `rpk cluster user list` |
| 创建 ACL | `kafka-acls.sh --add` | `rpk acl create` |
| 删除 ACL | `kafka-acls.sh --remove` | `rpk acl delete` |
| 列出 ACL | `kafka-acls.sh --list` | `rpk acl list` |

### 4. SCRAM 凭证管理命令速查

```bash
# 创建:rpk cluster user create
rpk cluster user create alice -p 'secret' --mechanism SCRAM-SHA-256

# 修改(热生效):rpk cluster user alter
rpk cluster user alter alice -p 'new-secret' --mechanism SCRAM-SHA-256

# 删除:rpk cluster user delete
rpk cluster user delete alice

# 查看:rpk cluster user list
rpk cluster user list
```

### 5. ACL 命令模板

```bash
# 读权限
rpk acl create --allow-principal User:alice \
  --operation READ --operation DESCRIBE --topic test-topic

# 写权限
rpk acl create --allow-principal User:alice \
  --operation WRITE --operation DESCRIBE --topic test-topic

# 消费必备组合
rpk acl create --allow-principal User:alice \
  --operation READ --operation DESCRIBE --topic test-topic
rpk acl create --allow-principal User:alice \
  --operation READ --operation DESCRIBE --group test-group

# 事务前置
rpk acl create --allow-principal User:alice \
  --operation IDEMPOTENT_WRITE --cluster

# 前缀匹配
rpk acl create --allow-principal User:alice \
  --operation READ --topic 'order-' --resource-pattern-type prefixed
```

### 6. 资源类型

- **Topic**:READ/WRITE/CREATE/DELETE/ALTER/DESCRIBE
- **Group**:READ/DESCRIBE/DELETE
- **Cluster**:CREATE/ALTER/DESCRIBE/CLUSTER_ACTION/IDEMPOTENT_WRITE
- **TransactionalId**:DESCRIBE/WRITE
- **Schema**(企业版):DESCRIBE/READ/WRITE/DELETE

### 7. 监听器安全要点

```yaml
kafka_api:
  authentication_method: sasl       # 或 mtls
  ssl.enabled: true
  ssl.require_client_auth: false    # sasl 时 false,mtls 时 true

rpc_server:
  tls.enabled: true                 # 必须
  tls.require_client_auth: true     # 必须双向认证

admin:
  tls.enabled: true                 # 必须 HTTPS
```

### 8. TLS 配置要点

```
服务端 (redpanda.yaml):
  ssl.cert_file / ssl.key_file / ssl.truststore_file
  ssl.enabled: true
  ssl.require_client_auth: <true|false>
  ssl.min_tls_version: "TLSv1.2"

客户端 (rpk):
  --tls-ca /etc/redpanda/certs/ca.crt
  --tls-cert /etc/redpanda/certs/alice.crt  (mTLS)
  --tls-key /etc/redpanda/certs/alice.key   (mTLS)
```

### 9. 性能与安全平衡

| 安全特性 | 性能开销 | 缓解措施 |
|----------|----------|----------|
| TLS/SSL | -10%~30% | 启用 TLS 1.3、AES-NI、SSL session resumption |
| SASL/SCRAM | -3%~5% | SCRAM-SHA-256(SHA-512 略慢) |
| mTLS | -15%~40% | 复用 TLS session、AES-NI 硬件加速 |
| ACL | -2%~5% | 减少 ACL 规则数量,使用 prefix 匹配 |
| 加密数据本身 | 应用层处理 | 客户端加密敏感字段 |

### 10. 关键安全配置(redpanda.yaml)

```yaml
redpanda:
  kafka_api:
    - authentication_method: sasl    # 或 mtls
      ssl.enabled: true
  
  rpc_server:
    tls.enabled: true                # 必须
    tls.require_client_auth: true    # 必须
  
  admin:
    - tls.enabled: true
  
  superusers: ["admin"]              # 超级用户
```

### 11. 应急响应命令速查

```bash
# 撤销某用户所有权限

  --operation ALL --topic '*' --resource-pattern-type any

# 撤销 Cluster 权限
rpk acl delete --allow-principal User:alice \
  --operation ALL --cluster

# 临时拒绝某用户某资源
rpk acl create --deny-principal User:alice \
  --operation ALL --topic 'sensitive-*' --resource-pattern-type prefixed
```

### 12. 常见陷阱

- **忘配 `superusers`** 导致自己也被 ACL 拒绝 → 至少保留 1 个 superuser
- **证书私钥文件权限过宽** → `chmod 600 *.key`
- **证书过期未监控** → 提前 30 天告警
- **未启用 TLS 时用 SASL/PLAIN** → 密码被嗅探
- **`require_client_auth: false` + 无 SASL** → 客户端可匿名访问
- **RPC 端口未 TLS** → 节点间通信明文,集群被入侵
- **应用账号授予 `--topic '*' --operation ALL`** → 可删任意 Topic
- **消费 Topic 缺 `--group READ`** → 提交 offset 失败
- **生产端缺 `--cluster IDEMPOTENT_WRITE`** → 幂等失效
- **监听器绑 0.0.0.0 又无防火墙** → 暴露公网
- **ACL 规则过多** → 性能下降,用 prefixed 匹配

### 13. 安全最佳实践一句话总结

**KRaft 模式 + SASL_SSL(SCRAM-SHA-256) + RPC TLS mTLS + ACL 默认拒绝 + 最小权限 + 定期轮换 + 全面审计 + 三层网络隔离 = 生产级 RedPanda 安全**。
