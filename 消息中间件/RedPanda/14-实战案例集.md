## 二、案例 1:Kafka → Redpanda 迁移(金融支付)

### 场景

- **业务**:支付系统核心交易消息
- **挑战**:Kafka P99 延迟 30ms+ 不满足低延迟要求
- **目标**:迁移到 Redpanda,P99 降至 < 5ms,零停机切换

### 架构

```text
阶段 1 (并行运行):
   ┌─────────┐                ┌─────────┐
   │ 应用 A   │ ──produce──→ │  Kafka  │ ←──── 历史数据
   └─────────┘                └────┬────┘
                                    │ MirrorMaker2
                                    ↓
                               ┌─────────┐
                               │Redpanda│
                               └────┬────┘
                                    │
   ┌─────────┐                       │
   │ 应用 A   │ ──verify───→ 验证数据一致
   └─────────┘

阶段 2 (切换):
   ┌─────────┐
   │ 应用 A   │ ──produce──→ ┌─────────┐
   └─────────┘                │Redpanda│
                              └─────────┘

阶段 3 (回收):
                               ┌─────────┐
                               │  Kafka  │ ←─── 保留 7 天回滚
                               └─────────┘
```

### 完整迁移步骤

**1. 部署 Redpanda 集群**

```bash
# docker-compose.yml
version: '3.8'
services:
  rp1:
    image: redpandadata/redpanda:v23.3.1
    command: >
      redpanda start
        --overprovisioned
        --smp 1
        --memory 2G
        --reserve-memory 0M
        --check=false
        --node-id 0
        --seeds rp1:33145
        --kafka-addr PLAINTEXT://0.0.0.0:9092
        --advertise-kafka-addr rp1:9092
        --rpc-addr rp1:33145
        --advertise-rpc-addr rp1:33145
        --smp 1
    ports:
      - "9092:9092"
      - "33145:33145"
    volumes:
      - rp1-data:/var/lib/redpanda/data
```

**2. MirrorMaker2 双向同步**

```bash
# connect-mirror-maker.properties
clusters = kafka, redpanda

kafka.bootstrap.servers = kafka1:9092
redpanda.bootstrap.servers = rp1:9092

# 双向复制
kafka->redpanda.enabled = true
redpanda->kafka.enabled = true
```

**3. 验证数据一致**

```bash
# 使用 kafkacat 验证
kafkacat -b kafka:9092 -t payment.events -C -e -o beginning > /tmp/kafka.txt
kafkacat -b rp1:9092 -t payment.events -C -e -o beginning > /tmp/rp.txt

# 校验一致性
diff /tmp/kafka.txt /tmp/rp.txt
```

**4. 灰度切换流量**

```java
// 在应用配置中按比例切换
@Value("${redpanda.weight:0}")  // 从 0 开始,逐步增加到 100
private int redpandaWeight;

@Bean
public Producer<String, String> kafkaProducer() {
    return new KafkaProducer<>(kafkaProps());
}

@Bean
public Producer<String, String> redpandaProducer() {
    return new KafkaProducer<>(redpandaProps());
}

// 双写
public void send(String topic, String key, String value) {
    kafkaProducer.send(new ProducerRecord<>(topic, key, value));
    if (random(100) < redpandaWeight) {
        redpandaProducer.send(new ProducerRecord<>(topic, key, value));
    }
}
```

**5. 完全切换后停 Kafka**

```bash
# 7 天观察期后,停止 Kafka 集群
docker-compose stop kafka1 kafka2 kafka3
```

### 效果

- **延迟**:P99 从 30ms 降至 4ms (7.5x 提升)
- **吞吐**:峰值从 5 万 → 8 万 records/s
- **稳定性**:GC 暂停从 200ms 降至 0

## 三、案例 2:实时风控流处理(Wasm Transform)

### 场景

- **业务**:电商交易反欺诈
- **挑战**:每笔交易需 50ms 内完成风险评分
- **目标**:在 Broker 端用 Wasm Transform 完成特征提取,降低延迟

### 架构

```text
交易请求
   ↓
   Redpanda (produce)
   ↓
   Wasm Transform: 特征提取 (P99 < 1ms)
   ↓
   Redpanda (consume) - 风控服务
   ↓
   风险评分
   ↓
   决策结果写入 Redpanda
```

### 完整 Rust Wasm Transform

```rust
// Cargo.toml
[package]
name = "fraud-feature-extract"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
redpanda-transform-sdk = "1.0"
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"

// src/lib.rs
use redpanda_transform_sdk::*;

#[derive(Serialize, Deserialize)]
struct Transaction {
    user_id: String,
    amount: f64,
    timestamp: i64,
    ip: String,
    device_id: String,
}

#[derive(Serialize)]
struct Features {
    user_id: String,
    amount: f64,
    hour_of_day: u32,
    is_night: bool,
    amount_log: f64,
    device_risk_score: f32,
}

fn transform(event: Record, writer: &mut Writer) -> Result<(), Error> {
    let tx: Transaction = serde_json::from_slice(event.value)?;
    
    let hour = ((tx.timestamp / 3600) % 24) as u32;
    let is_night = hour < 6 || hour > 22;
    let amount_log = (tx.amount + 1.0).ln();
    
    let features = Features {
        user_id: tx.user_id.clone(),
        amount: tx.amount,
        hour_of_day: hour,
        is_night,
        amount_log,
        device_risk_score: calculate_risk(&tx.device_id),
    };
    
    let output = serde_json::to_vec(&features)?;
    writer.write(Some(event.key), Some(&output));
    Ok(())
}
```

### 部署

```bash
cargo build --release --target wasm32-wasi

rpk transform deploy fraud-features \
  --input-topic transactions \
  --output-topic transactions.features \
  --path target/wasm32-wasi/release/fraud-feature-extract.wasm
```

### 效果

- **延迟**:特征提取 0.5ms (传统微服务 8ms)
- **吞吐**:单 Broker 30 万 records/s
- **节省资源**:不需要单独风控微服务

## 五、案例 4:金融行情分发

### 场景

- **业务**:股票/期货实时行情推送
- **挑战**:1 万个客户端订阅,要求 P99 < 10ms
- **目标**:超低延迟行情分发

### 架构

```text
行情源 (CTP/LF/HP) 
   ↓ (高频推送)
   Redpanda Cluster (3 节点)
   ↓
   多个消费者组
   ├─ 行情展示 (Web)
   ├─ 风控计算
   ├─ 数据落库
   └─ 量化交易
```

### 关键配置

```yaml
# redpanda.yaml
kafka:
  # 禁用批量延迟,立即发送
  batch_max_bytes: 16384
  batch_delay_ms: 0  # 关键!

  # 调整 socket
  tcp_socket_send_buf: 131072  # 128KB
  tcp_socket_recv_buf: 131072
```

### 客户端订阅

```java
// 行情客户端
Properties props = new Properties();
props.put("bootstrap.servers", "rp:9092");
props.put("group.id", "market-display-" + UUID.randomUUID());
props.put("auto.offset.reset", "latest");  // 关键: 只关心最新
props.put("fetch.min.bytes", "1");         // 立即返回,不等待
props.put("fetch.max.wait.ms", "0");      // 不等待
props.put("enable.auto.commit", "true");
props.put("auto.commit.interval.ms", "100");  // 100ms 提交

KafkaConsumer<String, MarketData> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("market.quote.*"));

while (running) {
    ConsumerRecords<String, MarketData> records = consumer.poll(Duration.ofMillis(50));
    for (ConsumerRecord<String, MarketData> record : records) {
        // 推送到前端 WebSocket
        pushToFrontend(record.value());
    }
}
```

### 效果

- **延迟**:P99 = 3ms (Kafka 同期为 15ms)
- **吞吐**:50 万 quotes/s
- **稳定性**:P99.9 < 10ms

## 六、案例 5:Event Sourcing 订单状态

### 场景

- **业务**:电商订单状态流转(下单→支付→发货→收货→退款)
- **挑战**:完整审计 + 状态回溯
- **目标**:用 Compacted Topic 存储订单事件流

### Compacted Topic 设计

```sql
-- 创建 compacted topic
rpk topic create order-events \
  --partitions 12 \
  --replicas 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.1 \
  --config segment.ms=3600000
```

### 事件格式

```json
{
  "event_id": "evt-uuid-001",
  "order_id": "ORDER-12345",
  "event_type": "OrderPaid",
  "timestamp": "2026-08-18T10:00:00Z",
  "data": {
    "payment_method": "credit_card",
    "amount": 299.99,
    "currency": "CNY"
  }
}
```

### 完整代码示例

```java
@Service
public class OrderEventStore {
    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;
    
    public void appendEvent(String orderId, OrderEvent event) {
        String key = orderId;  // 关键: 用 orderId 作 key,compact 时只保留最新
        String value = JsonUtil.toJson(event);
        kafkaTemplate.send("order-events", key, value);
    }
    
    public List<OrderEvent> getOrderHistory(String orderId) {
        // 从 compacted topic 读取
        List<OrderEvent> events = new ArrayList<>();
        ConsumerRecord<String, String> record = kafkaTemplate.receive("order-events", 0, offset);
        // ... 解析
        return events;
    }
    
    public Order getCurrentState(String orderId) {
        // Compacted Topic 只保留每个 key 的最新值
        String currentValue = redis.get("order:state:" + orderId);
        return JsonUtil.parse(currentValue, Order.class);
    }
}
```

### 状态重建

```bash
# 触发压缩
rpk topic compact order-events

# 查看压缩状态
rpk topic describe order-events | grep -i clean
```

## 七、案例 6:CDC 数据入湖(MySQL → Iceberg)

### 场景

- **业务**:业务数据库 → 实时数据湖
- **挑战**:MySQL binlog 实时同步到 Iceberg 表
- **目标**:分钟级延迟的近实时数据湖

### 架构

```text
MySQL
   ↓ binlog
   Debezium MySQL Connector
   ↓ produce to Kafka API
   Redpanda
   ↓ consume
   Redpanda Iceberg Topics (内置集成!)
   ↓
   S3 / MinIO 存储 (Parquet + Iceberg metadata)
```

### 关键配置

```yaml
# redpanda.yaml - 启用 Iceberg 集成
iceberg:
  enabled: true
  catalog:
    type: s3_tables  # 或 rest, glue
  warehouse: s3://my-bucket/iceberg-warehouse
  auto_create_topics:
    - name: mysql.cdc.orders
      partition_by: ["date"]
      flush_interval_ms: 60000  # 1 分钟刷一次
```

### 优势

- **无需 Flink/Spark**:Redpanda 直接输出 Iceberg 格式
- **降低延迟**:从 5-10 分钟 → 1-2 分钟
- **降低复杂度**:少一套流处理系统

## 八、案例 7:跨区域灾备(金融)

### 场景

- **业务**:金融交易系统,RPO < 1 分钟

- **目标**:Shadow Linking 自动双向同步

### 架构

```text
北京集群 (主)
   ↓ Shadow Link
   ↓ 双向同步

   ↓ Shadow Link
   ↓

```

### 配置

```bash

  --source redpanda://beijing-broker:33145

  --source redpanda://beijing-broker:33145
```

```bash
# 主集群故障时,提升备集群
ssh shanghai-redpanda "rpk cluster health"

# 切换应用流量到备集群
# (通过 DNS / VIP / Service Mesh)
```

- **RPO**:通常 5-30 秒 (shadow link 同步延迟)
- **RTO**:30-60 秒 (DNS 切换时间)

## 九、案例 8:在线业务渐进迁移(SaaS)

### 场景

- **业务**:SaaS 产品从 MySQL + 直接写入改为消息驱动
- **挑战**:500 万在线用户,不能停机
- **目标**:灰度上线,逐步切流

### 双写架构

```text
              ┌──→ MySQL (双写 1)
业务服务 ────┤
              └──→ Redpanda (双写 2)
                       ↓
                   异步消费 (新业务)
```

### 关键代码

```java
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;
    
    @Value("${dual.write.kafka:true}")
    private boolean kafkaWriteEnabled;
    
    @Transactional
    public void createOrder(Order order) {
        // 1. 写 MySQL (主要)
        orderMapper.insert(order);
        
        // 2. 写 Redpanda (异步,失败不影响主流程)
        if (kafkaWriteEnabled) {
            try {
                kafkaTemplate.send("orders", 
                    order.getId().toString(), 
                    JsonUtil.toJson(order));
            } catch (Exception e) {
                log.warn("Kafka 写入失败", e);
                // 失败可重试或补偿,不影响 MySQL 事务
            }
        }
    }
}
```

### 灰度切流

```yaml
# application.yml
dual:
  write:
    mysql: true   # 总是写 MySQL
    kafka: true   # 灰度期间开启

# 切流比例
gray:
  read-from-kafka: 10%   # 10% 读从 Kafka
  # 然后逐步 50%, 100%
```

## 十、案例 9:性能调优实战(从 50ms 到 5ms)

### 初始状态

```text
P50 延迟: 10ms
P99 延迟: 50ms
P999 延迟: 200ms
吞吐量: 50,000 records/s
CPU 利用率: 60%
```

### 优化轮次

**第 1 轮:Batch 优化**

```yaml
# Producer 端
batch.size: 65536        # 64KB (原 16KB)
linger.ms: 10           # 10ms (原 5ms)
compression.type: zstd  # 改用 zstd
```

效果:P50 → 7ms,P99 → 30ms

**第 2 轮:网络优化**

```bash
# OS 层
sudo sysctl -w net.core.rmem_max=26214400
sudo sysctl -w net.core.wmem_max=26214400
sudo sysctl -w net.ipv4.tcp_rmem='4096 87380 26214400'
sudo sysctl -w net.ipv4.tcp_wmem='4096 65536 26214400'
```

效果:P99 → 15ms

**第 3 轮:JVM/内存调优(无 GC)**

```yaml
# Redpanda 进程 (C++, 无 JVM)
resource_limits:
  memory: 8G
  cpu cores: 8
```

效果:P99 → 8ms (主要因为无 GC 暂停)

**第 4 轮:磁盘优化**

```bash
# 使用 NVMe SSD
sudo mkfs.xfs -f /dev/nvme0n1
sudo mount -o noatime,nodiratime,discard /dev/nvme0n1 /var/lib/redpanda
```

效果:P999 → 50ms

**第 5 轮:Follower Read**

```yaml
# 允许 Follower 处理读请求
kafka:
  enable_idempotence: true
# 客户端代码
producer.flush()  # 强制等待 ACK
```

效果:P99 → 5ms ✅

### 最终状态

```text
P50 延迟: 2ms
P99 延迟: 5ms (-90%)
P999 延迟: 50ms (-75%)
吞吐量: 120,000 records/s (+140%)
```

## 十二、案例 11:Wasm 数据脱敏

### 场景

- 信用卡号、身份证号需在消息流转中脱敏
- 不能影响下游消费

### 完整 Rust 代码

```rust
use redpanda_transform_sdk::*;

#[derive(Serialize, Deserialize)]
struct PaymentRecord {
    user_id: String,
    card_number: String,
    id_number: String,
    amount: f64,
}

fn transform(event: Record, writer: &mut Writer) -> Result<(), Error> {
    let mut payment: PaymentRecord = serde_json::from_slice(event.value)?;
    
    // 脱敏: 信用卡号保留前4后4
    payment.card_number = mask_card(&payment.card_number);
    // 脱敏: 身份证号保留前6后4
    payment.id_number = mask_id(&payment.id_number);
    
    let output = serde_json::to_vec(&payment)?;
    writer.write(Some(event.key), Some(&output));
    Ok(())
}

fn mask_card(card: &str) -> String {
    if card.len() < 8 { return "*".repeat(card.len()); }
    let prefix = &card[..4];
    let suffix = &card[card.len()-4..];
    format!("{}***{}", prefix, suffix)
}

fn mask_id(id: &str) -> String {
    if id.len() < 10 { return "*".repeat(id.len()); }
    let prefix = &id[..6];
    let suffix = &id[id.len()-4..];
    format!("{}****{}", prefix, suffix)
}
```

### 部署

```bash
cargo build --release --target wasm32-wasi

rpk transform deploy payment-mask \
  --input-topic payments.raw \
  --output-topic payments.masked \
  --path target/wasm32-wasi/release/payment-mask.wasm
```

### 效果

- **处理延迟**:0.3ms / 消息
- **CPU 占用**:< 5% 单核
- **脱敏覆盖**:100% (所有写入自动脱敏)

## 十三、案例 12:Tiered Storage 成本优化

### 场景

- 业务:日志数据,保留 1 年
- 挑战:本地磁盘昂贵,1 年 50TB 数据
- 目标:用 S3 存历史数据,本地只保留近期

### 配置

```yaml
cloud_storage:
  enabled: true
  bucket: redpanda-logs
  region: us-east-1
  access_key: ${AWS_ACCESS_KEY_ID}
  secret_key: ${AWS_SECRET_ACCESS_KEY}

# 关键:控制本地保留时间
log_retention_ms: 86400000        # 本地保留 1 天
cloud_storage_segment_max_upload_interval_ms: 30000  # 30s 上传一次

# 旧数据自动上传到 S3
```

### 容量规划

```text
原始需求: 50TB / 1 年 (本地 SSD $200/TB/月 = $120k/年)

Tiered Storage 方案:
   本地 (1TB SSD): $200/月
   S3 (50TB Standard): $1150/月
   S3 IA (迁移老数据): $325/月 (90 天后)
   总计: $1675/月 = $20k/年

节省: 83% ($100k/年)
```

### 效果

- **存储成本**:降低 83%
- **查询延迟**:热数据 5ms, 冷数据 50-200ms (S3 GET)
- **数据可用**:100% (本地 + S3)

## 十五、核心要点速记

### RedPanda 实战经验总结

- **Kafka 客户端直接兼容**:迁移零代码改动
- **Shadow Linking 是迁移利器**:双跑验证零停机
- **Wasm Transform 是杀手锏**:Broker 端数据处理
- **Tiered Storage 节约 80%+ 成本**:S3 长期存储
- **Iceberg 集成简化数据湖**:无需 Flink/Spark
- **P99 延迟 < 5ms**:Thread-per-core + 无 GC 优势
- **运维简单**:单二进制,无 ZK/KRaft 依赖

### 选型场景

```text
场景                              推荐度
─────────────────────────────────────────
需要超低延迟 (< 10ms)              ⭐⭐⭐⭐⭐ 必选
需要单二进制简化运维                ⭐⭐⭐⭐⭐ 必选
需要 Wasm Transform                ⭐⭐⭐⭐⭐ 必选
需要内置 Tiered Storage            ⭐⭐⭐⭐⭐ 必选
需要内置 Schema Registry           ⭐⭐⭐⭐ 推荐
需要 C++ 性能优势                  ⭐⭐⭐⭐⭐ 必选
从 Kafka 迁移                      ⭐⭐⭐⭐ 推荐 (兼容)
需要 Kafka Streams                  ⭐⭐⭐ 不推荐 (需自己集成)
需要 Confluent 商业功能            ⭐⭐ 谨慎 (部分有)
```

### 关键迁移策略

```text
1. 用 Shadow Linking 双跑
2. Kafka 客户端无需改动
3. 逐步切流 (10% → 50% → 100%)
4. 保留 Kafka 集群 7 天回滚
5. 监控对比 Kafka vs Redpanda 性能
```
