# RedPanda 常见问题排查 (Troubleshooting)

> 适用版本:RedPanda 23.x / 24.x / 25.x(基于 `rpk` CLI 与 Admin API)。
> 阅读建议:按目录定位场景,先看"排查流程图"再下钻细节;RedPanda 的故障面比 Kafka 收敛得多(无 JVM、无 Controller 选举、无 Page Cache 调优),但 Tiered Storage、Shadow Linking、Wasm Transform 是新增故障域。

---

## 一、故障排查思路总览

### 1. 分层定位原则

```text
┌──────────────────────────────────────────────────────────────┐
│  Layer 1  业务应用层   生产者/消费者代码?序列化?分区策略?     │
│     ↓                                                        │
│  Layer 2  客户端层     librdkafka / Sarama / rpk 版本兼容?   │
│     ↓                                                        │
│  Layer 3  Broker 层    RedPanda 进程状态?Topic/Partition?   │
│     ↓                                                        │
│  Layer 4  Raft 层      Controller(0 节点)选举?Raft quorum?  │
│     ↓                                                        │
│  Layer 5  存储层       本地盘 / Tiered Storage (S3/MinIO)?  │
│     ↓                                                        │
│  Layer 6  操作系统层   CPU/内存/磁盘IO/网络?FD 限制?cgroup?   │
│     ↓                                                        │
│  Layer 7  硬件层       NVMe/SSD/网卡健康?                       │
└──────────────────────────────────────────────────────────────┘
```

**与 Kafka 的关键差异**(运维视角):
- RedPanda 单二进制单角色:Controller 功能内置,但无独立 Controller 节点概念,集群任何节点都可成为 Leader,故障面比 Kafka 小很多
- 无 JVM 依赖:GC 停顿不再是常规排查项,但 C++ 内存问题(如 `std::bad_alloc`)需要不同工具链
- 无 Page Cache 显式调优:RedPanda 有自己的 chunk cache(默认 128MB),与 Kafka 依赖 OS Page Cache 不同
- Tiered Storage、Shadow Linking、Wasm Transform 是新增故障域,运维需要掌握 S3 配置、跨集群同步、Wasm 部署
- 配置文件 `redpanda.yaml`(YAML)而非 `server.properties`(Java properties),配置体验更好
- `rpk` CLI 统一了所有操作,而 Kafka 需要记忆 `kafka-topics.sh`、`kafka-consumer-groups.sh`、`kafka-configs.sh` 等多个脚本

**黄金法则**:**先确认现象(报错、监控、Lag)→ 分层下钻 → 优先看 `rpk` 命令输出和 `/var/log/redpanda/*.log`,最后查代码逻辑**。这是一条经过无数次真实故障验证的铁律,适用于绝大多数场景:你看到的表象(Lag 增长、报错)往往不是根因,只是症状;不深入底层就急于修复,只会让问题反复发生。

### 2. 通用排查流程

| 步骤 | 动作                          | 工具/命令                                                |
|------|-------------------------------|-----------------------------------------------------------|
| 1    | 确认现象                      | `rpk topic consume`、`rpk cluster info`、应用日志        |
| 2    | 收集现场                      | `rpk status`、`rpk cluster health`                       |
| 3    | 缩小范围(客户端/Broker/OS)   | `top`、`iostat`、`sar`、`ss`                             |
| 4    | 定位根因                      | `/var/log/redpanda/controller.log`、`broker.log`         |
| 5    | 修复 + 验证 + 归档            | 滚动重启、回滚预案、RCA 报告                              |

### 3. 必备诊断命令速查

```bash
# 集群状态
rpk cluster info                          # 集群 ID、控制器、broker 列表
rpk cluster health                        # 健康度(under-replicated 等)
rpk status                                # 当前节点状态(本地)

# Topic / Partition
rpk topic list                            # 列出所有 topic
rpk topic describe <topic>                # 详细分区信息
rpk topic consume <topic> -n 10 -o start # 消费最近 10 条

# Group / Lag
rpk group list                            # 消费组列表
rpk group describe <group>                # 消费组 lag 详情

# Broker 内部状态
rpk redpanda admin brokers list           # Admin API:broker 列表
rpk redpanda admin partitions list        # 分区分布

# 日志
journalctl -u redpanda -f                 # systemd 启动的 RedPanda
tail -f /var/log/redpanda/redpanda.log    # 直接看日志
grep -E 'ERROR|WARN' /var/log/redpanda/*.log | tail -100

# 进程与端口
pgrep -fa redpanda
ss -tlnp | grep -E '9092|33145|9644'     # Kafka API / Admin / Schema Registry
```

## 二、启动失败类问题

### 1. 配置文件错误

**现象**:`redpanda` 进程启动后立刻退出,日志报 `Config error`、`Invalid value for <key>`、`Failed to parse`。

**常见错误**:

| 配置项                         | 常见错误                                       | 正确示例                                    |
|--------------------------------|------------------------------------------------|---------------------------------------------|
| `redpanda.listeners`           | 端口冲突、协议格式错                           | `{'plaintext://0.0.0.0:9092'}`            |
| `redpanda.advertised_listeners` | 客户端无法解析(主机名/DNS 错)                | `{'plaintext://node1.example.com:9092'}`  |
| `cluster.initial_cluster_id`   | 多节点不一致,首次启动失败                      | 三个节点相同 UUID                           |
| `redpanda.seed_servers`            | 写成本地 IP,集群节点互不可达 | 列出所有 broker 地址                           |
| `node_id`                       | 节点 ID 冲突(重复)                            | 集群内唯一                                  |

**排查步骤**:

```bash
# 1. 前台启动看报错
sudo rpk redpanda start --config /etc/redpanda/redpanda.yaml
# 或
sudo systemctl status redpanda -l
journalctl -xeu redpanda --no-pager | tail -50

# 2. 验证配置语法
rpk redpanda config set --help  # 测试命令

# 3. 直接 YAML 解析
python3 -c "import yaml; yaml.safe_load(open('/etc/redpanda/redpanda.yaml'))"

# 4. 对比参考配置
diff /etc/redpanda/redpanda.yaml \
     /etc/redpanda/redpanda.yaml.bak

# 5. 看具体哪个字段错
grep -i "config\|invalid\|parse" /var/log/redpanda/redpanda.log | tail -20
```

**解决方案**(核心配置示例):

```yaml
# /etc/redpanda/redpanda.yaml 关键字段
redpanda:
  data_directory: /var/lib/redpanda/data
  empty_seed_starts_cluster: false   # 严禁 true,除非测试
  seed_servers:
    - host: {ipv4: 10.0.0.1, port: 33145}
      node_id: 1
    - host: {ipv4: 10.0.0.2, port: 33145}
      node_id: 2
    - host: {ipv4: 10.0.0.3, port: 33145}
      node_id: 3
  rpc_server:
    address: 0.0.0.0
    port: 33145
  kafka_api:
    - address: 0.0.0.0
      port: 9092
      name: plaintext
  kafka_api_tls:
    - address: 0.0.0.0
      port: 9093
      name: tls
      enabled: false   # 按需开启
  admin:
    - address: 0.0.0.0
      port: 9644
  node_id: 1   # 必须唯一
  developer_mode: false   # 生产严禁 true

cluster_id: "your-cluster-uuid"
```

**预防**:统一配置管理(Ansible/Helm)、配置 review、CI 校验 YAML 语法。

### 2. 端口冲突

**现象**:启动报 `Address already in use`、`bind: address in use`、`Failed to listen on port`。

**端口清单**:

| 用途                  | 默认端口 | 冲突常见原因                                       |
|-----------------------|----------|----------------------------------------------------|
| Kafka API (PLAINTEXT)| 9092     | 多 Broker 同机 / 残留进程 / 其他服务占用           |
| Kafka API (TLS)       | 9093     | 同上                                               |
| RPC(内部 Raft)        | 33145    | 同上 / 防火墙阻断                                  |
| Admin API             | 9644     | 监控/COS 类似端口冲突                              |
| Schema Registry       | 8081     | HTTP 服务冲突                                      |
| HTTP Proxy / PandaProxy | 8082     | 同上                                              |
| Kafka Connect         | 8083     | 同上                                               |

**排查步骤**:

```bash
# 1. 看谁占用
ss -tlnp | grep -E '9092|33145|9644'
sudo lsof -i :9092
sudo lsof -i :33145

# 2. 看 RedPanda 进程
pgrep -fa redpanda
ps -ef | grep redpanda

# 3. 检查配置端口
grep -E 'port:|address:' /etc/redpanda/redpanda.yaml

# 4. 残留进程(异常崩溃后)
pgrep -fa redpanda | awk '{print $1}' | xargs -r sudo kill -9
sleep 3
ps -ef | grep redpanda   # 确认无残留
```

**解决方案**:

```yaml
# A) 修改端口
redpanda:
  kafka_api:
    - address: 0.0.0.0
      port: 19092     # 改到不冲突端口
  rpc_server:
    port: 33145       # RPC 端口保持,否则节点间不可达

# B) 杀掉残留进程
sudo pkill -9 -f redpanda
sleep 5
ps -ef | grep redpanda   # 确认无残留

# C) 多 Broker 同机(测试环境)
# 必须改所有端口(node1: 9092/33145/9644,node2: 9192/33245/9744)
```

### 3. 数据目录权限

**现象**:启动报 `Permission denied`、`Failed to open data dir`、`Cannot create lock file`。

**根因**:RedPanda 默认以 `redpanda` 用户运行,但数据目录由 `root` 创建或权限被改。

**排查步骤**:

```bash
# 1. 看数据目录属主
ls -ld /var/lib/redpanda/data
ls -ld /var/lib/redpanda

# 2. 看运行用户
ps -ef | grep redpanda
# 应该是 redpanda 用户

# 3. 看错误
journalctl -u redpanda | grep -i "permission\|denied"
```

**解决方案**:

```bash
# 修复权限
sudo chown -R redpanda:redpanda /var/lib/redpanda
sudo chmod 750 /var/lib/redpanda/data

# 如果 SELinux/AppArmor 启用
sudo setsebool -P nis_enabled 1   # 例
sudo aa-complain /etc/apparmor.d/*   # 临时放行

# 验证
sudo -u redpanda ls /var/lib/redpanda/data
```

### 4. 集群 ID 不匹配

**现象**:节点加入集群报 `Mismatched cluster_id`、`cluster_id mismatch`,集群无法形成。这种错误通常出现在节点扩容、灾备恢复或配置回滚场景。

**根因**:每个节点 `cluster_id` 必须相同;新节点加入用了错的 cluster ID。常见原因包括:Ansible 模板渲染失败、运维手动拷贝配置时复制粘贴错误、灾备恢复时用了不同集群的备份、不同环境(测试/生产)配置混用。

**排查步骤**:

```bash
# 1. 看每个节点的 cluster_id
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "grep 'cluster_id' /etc/redpanda/redpanda.yaml"
done

# 2. 看数据目录内的 cluster_id 文件
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "cat /var/lib/redpanda/data/cluster.json 2>/dev/null || \
          find /var/lib/redpanda/data -name 'cluster_id*' -exec cat {} \;"
done

# 3. 看启动日志
ssh node3 "grep -i 'cluster_id' /var/log/redpanda/redpanda.log | tail"
```

**解决方案**:

```bash
# A) 修改配置统一 cluster_id
# 三个节点使用同一个 UUID(从第一个节点的 meta 目录查)
OLD_ID=$(ssh node1 "cat /var/lib/redpanda/data/cluster.json | jq -r .cluster_id")
# 把 OLD_ID 同步到 node2、node3 配置

# B) 重新初始化集群(慎用,清空数据)
sudo systemctl stop redpanda
sudo rm -rf /var/lib/redpanda/data/*
sudo systemctl start redpanda
# 注意:只有全新集群才这么做

# C) 节点加入已有集群
# 直接修改新节点的 cluster_id 配置,与现网一致
```

**预防**:Ansible 统一推送配置、首次部署记录 cluster_id、备份数据目录。

## 三、集群故障

### 1. 节点无法加入

**现象**:新节点启动后,`rpk cluster health` 中节点状态显示 `down` 或不在列表;日志报 `Failed to connect to seed`、`Connection refused`、`No route to host`。这种现象经常出现在集群扩容、节点替换、灾备切换等运维场景,需要在 30 分钟内恢复以避免业务影响。

**可能原因**:

| 原因                              | 排查                                                    |
|-----------------------------------|---------------------------------------------------------|
| 节点间 RPC(33145)不可达          | `nc -zv node1 33145`,防火墙/SG                         |
| `seed_servers` 配置错误           | IP/端口/节点 ID 写错                                    |
| `node_id` 冲突                    | 集群内已存在该 ID                                       |
| `cluster.initial_cluster_id` 不一致 | 写错或拼写错                                            |
| `empty_seed_starts_cluster` 状态不一致 | 一个 true、一个 false                                |
| mTLS 双向认证证书未配              | `rpk redpanda admin certs list` 看证书状态             |
| 时间不同步(>5 分钟)               | `chronyc tracking`                                      |

**排查步骤**:

```bash
# 1. 看新节点状态
rpk status
# 输出:Self joined?  false  → 没加入集群

# 2. 看健康度
rpk cluster health
# 输出:"unhealthy": true, missing partitions 等

# 3. 看 Admin API
curl -s http://localhost:9644/v1/brokers | jq .

# 4. 看新节点日志
journalctl -u redpanda -n 200 | grep -iE "seed|cluster|join"

# 5. 验证网络
nc -zv node1 33145
nc -zv node1 9092
mtr node1

# 6. 看证书状态(开启 mTLS 时)
rpk redpanda admin certs list
```

**解决方案**:

```bash
# A) 网络问题
# 防火墙开启 33145、9092 端口
sudo firewall-cmd --add-port=33145/tcp --permanent
sudo firewall-cmd --add-port=9092/tcp --permanent
sudo firewall-cmd --reload

# B) seed_servers 错误
# 修改 /etc/redpanda/redpanda.yaml 中:
seed_servers:
  - host: {ipv4: <正确IP>, port: 33145}
    node_id: <正确ID>
# 重启
sudo systemctl restart redpanda

# C) 时间同步
sudo chronyc makestep
# 或
sudo ntpdate node1

# D) mTLS 证书问题
rpk redpanda admin certs renew --api
```

**预防措施**:在节点部署前做好配置校验,使用 Ansible/Puppet 等配置管理工具统一推送,避免手工拷贝配置;集群内部启用 NTP/chrony 服务保证时间同步误差小于 5 秒;提前做好防火墙策略模板,新节点加入时自动应用;生产环境部署监控告警,节点加入失败后 5 分钟内通知 on-call。

### 2. Raft 选举失败

**现象**:集群无 Leader,所有写操作失败,`rpk cluster health` 显示 `no_leader`,消费者报 `NotLeaderForPartition` 或超时。这种情况比节点无法加入更严重,因为直接影响读写可用性。

**可能原因**:

| 原因                          | 排查                                                  |
|-------------------------------|-------------------------------------------------------|
| 多数节点不可用                | `rpk cluster info`,少于半数节点在线                   |
| 网络分区(过半节点孤立)      | `mtr`、`ping` 验证                                     |
| 多数节点 `cluster_id` 不一致  | 见 §二.4                                              |
| 多数节点数据目录损坏          | 看启动日志                                            |
| `seed_servers` 互相不可达    | RPC 端口 33145 不通                                  |

**排查步骤**:

```bash
# 1. 看 broker 列表与 Leader
rpk cluster info
# 输出:
#   ID    HOST     PORT
#   1     node1    9092
#   2     node2    9092   ← 看不到 node3?
#   3     node3    9092

# 2. 看所有节点是否在线
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "rpk status 2>&1 | head -5"
done

# 3. 看是否在选举中
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "journalctl -u redpanda --since '5 min ago' | grep -iE 'election|leader'"
done

# 4. Admin API 看 partition 健康
curl -s http://localhost:9644/v1/partitions/0/0/leaderless | jq .
curl -s http://localhost:9644/v1/partitions/0/0/followers | jq .
```

**解决方案**:

```bash
# A) 网络分区恢复
# 等待网络恢复;Raft 自动重新选举(秒级)
mtr node1

# B) 数据目录损坏
# 1. 停所有节点
sudo systemctl stop redpanda

# 2. 找健康的多数节点(健康数据目录的)
# 3. 把损坏节点的数据目录清空,让节点以新成员身份加入
sudo rm -rf /var/lib/redpanda/data/*

# 4. 重启(从 seed 拉元数据)
sudo systemctl start redpanda

# 注意:必须保证多数节点数据完好,否则会丢数据

# C) 时间不同步
sudo ntpdate node1
sudo systemctl restart redpanda
```

**预防**:部署监控告警 `no_leader` 分区 > 0、跨机房部署用 3 副本、证书 + 节点数双校验。在生产环境部署中,选举失败的危害往往是业务级灾难性的——所有写入请求都会失败,消费者可能错失关键事件。因此建议遵循以下原则:一是节点数必须为奇数(3 或 5),以满足 Raft 多数派要求;二是部署跨机备灾,避免单机房故障导致全部节点失效;三是关键告警必须秒级响应,no_leader 持续超过 30 秒应立即触发 on-call;四是建立定期的健康度巡检机制,通过自动化脚本每天检查 `rpk cluster health` 输出并归档。

### 3. 脑裂(Split-Brain)

**现象**:两个子集群各自选出 Leader,客户端连接随机失败;两边写入后无法合流。脑裂是分布式系统最严重的故障之一,会导致数据不一致和重复处理。

**根因**:RedPanda 基于 Raft 共识,理论不会脑裂。但若:
- 多数节点数据目录被同时修改(异常运维,例如手工删除文件)
- 网络分区后两半各自形成 quorum(违反 Raft 多数原则,实际几乎不可能)
- 时钟严重漂移导致 lease 过期,旧 Leader 没及时下台

**排查**:

```bash
# 1. 看每个分区的 Leader
for t in $(rpk topic list -X brokers=localhost:9092); do
  for p in 0 1 2; do
    curl -s http://localhost:9644/v1/partitions/$t/$p/leaderless | jq .
  done
done

# 2. 看 broker 视图一致性
curl -s http://node1:9644/v1/brokers | jq . > /tmp/brokers_node1.json
curl -s http://node2:9644/v1/brokers | jq . > /tmp/brokers_node2.json
diff /tmp/brokers_node1.json /tmp/brokers_node2.json
# 不一致 → 真脑裂

# 3. 看节点时间
for n in node1 node2 node3; do
  echo "=== $n ==="
  ssh $n "date && chronyc tracking | grep 'Last offset'"
done
```

**解决方案**:

```bash
# 1. 立即隔离可疑节点(让集群回退到正确状态)
# 停止可疑节点的 RedPanda
sudo systemctl stop redpanda   # 在脑裂节点上

# 2. 验证恢复
rpk cluster info
# 期望:多数节点视角一致

# 3. 如果数据不一致(极端情况)
# 必须从备份恢复或重建集群
# (极少见,通常停止脑裂节点后自动修复)

# 4. 时间同步
sudo ntpdate <NTP_SERVER>
```

**预防**:`empty_seed_starts_cluster=false`、节点数 3 或 5(奇数)、时钟同步(NTP/chrony)、禁止手动修改数据目录。

## 四、性能问题

### 1. CPU 高

**现象**:`top` 显示 `redpanda` 进程 CPU 接近 100%(单核或多核),Producer/Consumer 延迟升高。这种情况往往不是单点问题,而是多种因素叠加,需要从客户端配置、服务端资源、业务流量三方面综合判断。

**常见根因**:

| 根因                          | 排查                                                     |
|-------------------------------|----------------------------------------------------------|
| 大量压缩(zstd/lz4)           | 客户端 `compression.type=zstd`,关闭/切换                 |
| Wasm Transform 复杂逻辑       | 看 Wasm 指标                                            |
| 加密(Kafka TLS + Schema Registry) | 客户端配置 `security.protocol=SSL`                       |
| Raft 心跳/选举风暴            | 日志频繁 `election`,节点频繁重启                          |
| 频繁 GC(C++ 内部)            | 看 log:`stall`、`allocation failure`                    |

**排查步骤**:

```bash
# 1. 看 CPU 分布
top -H -p $(pgrep -f redpanda)
# 看哪个线程占 CPU

# 2. perf 采样热点(高级)
sudo perf top -p $(pgrep -f redpanda)
# 或 bpftrace 一行
sudo bpftrace -e 'kprobe:do_sys_open { @[comm] = count(); }' --pid $(pgrep -f redpanda)

# 3. 看 redpanda 内部指标(Admin API)
curl -s http://localhost:9644/metrics | grep -E "cpu_usage|stall"
curl -s http://localhost:9644/public_metrics | grep -E "cpu"

# 4. 看 broker log
grep -i "stall\|backpressure\|overload" /var/log/redpanda/redpanda.log
```

**解决方案**:

```bash
# A) 关闭客户端压缩
# librdkafka:
#   compression.type=none   (默认)
# 或服务端的:客户端不改,服务端不能用

# B) 加大 RedPanda 资源
# k8s:resources.limits.cpu 提高
# 物理机:绑核、扩容

# C) 调优 RedPanda 内部线程
# redpanda.yaml:
redpanda:
  smp_service_group_size: 8   # 默认 8,可调
  raft_learner_rate: 1
  # 参考:redpanda.yaml tuning 文档

# D) Wasm 优化或下线
rpk transform list
# 关闭热点 transform
```

### 2. 内存不足

**现象**:RedPanda 进程被 OOM Killer 杀掉(dmesg 看到 `oom-kill`);`top` 显示 `RES` 接近物理内存。

**根因**:RedPanda 默认每个 broker 使用较多内存(Page Cache 不如 Kafka,但内部有 chunk cache + Raft buffer)。

**排查步骤**:

```bash
# 1. 看系统内存
free -h
cat /proc/meminfo | grep -E "MemTotal|MemAvailable|Cached"

# 2. 看 RedPanda 内存
ps -o pid,rss,vsz,comm -p $(pgrep -f redpanda)
# RSS 看实际占用

# 3. 看 cgroup 限制(k8s)
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.usage_in_bytes

# 4. OOM 日志
dmesg | grep -i "oom\|kill"
journalctl -k | grep -i "oom"

# 5. RedPanda 内部指标
curl -s http://localhost:9644/public_metrics | grep -i memory
```

**解决方案**:

```yaml
# A) 物理机:加大内存(推荐 ≥ 16GB/broker)
# B) K8s:提高 resources.limits.memory
resources:
  limits:
    memory: 16Gi

# C) 调优 redpanda.yaml
redpanda:
  # 限制 chunk cache,防止占用过多 Page Cache
  chunk_cache_size: 134217728   # 128MB(默认)
  # 限制 connection rate
  kafka_connection_rate_limit: 1000
```

**预防**:`RES < 50% 物理内存`、监控 `process_resident_memory_bytes` 告警、提前扩容。RedPanda 的内存模型与 Kafka 不同:Kafka 依赖 JVM 堆 + OS Page Cache,需要精细调优 `Xmx` 和 Page Cache 比例;而 RedPanda 是 C++ 程序,内存使用更可控,但也意味着内存泄漏更难排查——一旦发生,只能通过 core dump 和 gdb 分析。建议每季度做一次内存基线对比,记录 RSS 增长曲线,出现异常增长立即排查。物理服务器部署时,内存建议预留 50% 给 OS 缓冲和突发流量;K8s 部署时 memory limit 必须谨慎设置,避免 OOMKill 与实际使用冲突;监控指标至少包含 `vector_memory_available_bytes`、`process_resident_memory_bytes`、`cgroup memory.usage_in_bytes` 三层视角。

### 3. 磁盘 IO 高

**现象**:`iostat -x 1` 显示 `%util > 80%` 或 `await > 10ms`,Broker 处理延迟上升;生产者/消费者延迟告警。

**排查步骤**:

```bash
# 1. 看磁盘 IO
iostat -x 1
# 关注:
#   r/s, w/s         读写 IOPS
#   rkB/s, wkB/s     读写带宽
#   await            平均 IO 等待(毫秒)
#   %util            利用率
#   aqu-sz           队列长度

# 2. 看哪个进程在打 IO
iotop -o
pidstat -d -p $(pgrep -f redpanda) 1

# 3. 看是读多还是写多
# iotop 看具体进程(RedPanda 内部有 IO 优先级)

# 4. 看日志是否有 IO 错误
dmesg | grep -i "i/o error"
journalctl -u redpanda | grep -i "io error\|disk full"
```

**根因与方案**:

| 场景               | 排查                                | 方案                                                          |
|--------------------|-------------------------------------|---------------------------------------------------------------|
| 顺序写打满         | `iostat`,`w/s` 高                  | NVMe、RAID 0、调 `log_segment_size`                          |
| 大量 compaction    | log `compaction` 频繁               | 减少 `compacted` topic 数 / 调 `compaction_interval`         |
| Tiered Storage 上传 | log `cloud_storage` 频繁            | 调整 `cloud_storage_segment_upload_timeout` / 限速上传        |
| Page Cache 不足    | `free`,Page Cache 命中率低           | 加大内存                                                      |
| 慢盘(HDD/远端 SAN)| `iostat -x` 的 await 抖动          | 换 NVMe / 本地盘                                             |

**关键参数**:

```yaml
redpanda:
  log_segment_size: 134217728   # 128MB 默认
  retention_bytes: 1073741824   # 1GB 默认
  compaction_interval: 10485760  # 默认
  # Tiered Storage 限速
  cloud_storage_max_throughput_per_shard: 100000000  # 100MB/s
  cloud_storage_initial_backoff: 100
```

### 4. 网络瓶颈

**现象**:Producer/Consumer 报 `request timeout`、`connection reset`,`sar -n DEV 1` 显示网卡打满。

**排查步骤**:

```bash
# 1. 看网络吞吐
sar -n DEV 1
# 或
iftop -i eth0 -P

# 2. 看网络错误
netstat -i
# 或
ip -s link show eth0

# 3. 看延迟
mtr node1

# 4. 看连接数
ss -s
ss -tan | wc -l   # 当前连接
ss -tan 'sport = :9092' | wc -l   # Kafka API 连接

# 5. RedPanda 内部
curl -s http://localhost:9644/public_metrics | grep -i connection
```

**解决方案**:

```yaml
# A) 提高 OS 网络 buffer
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728

sudo sysctl -w net.ipv4.tcp_wmem='4096 65536 134217728'

# B) 调优 RedPanda
redpanda:
  kafka_connection_rate_limit: 5000
  kafka_client_max_inflight_requests: 500

# C) 客户端参数
# librdkafka:
#   socket.keepalive.enable=true
#   socket.nagle.disable=true
#   reconnect.backoff.ms=200

# D) 网络硬件升级
# 1Gbps → 10Gbps → 25Gbps
# 网卡绑定(LACP)、RSS 多队列
```

## 五、副本问题

### 1. 副本滞后

**现象**:`rpk topic describe <topic>` 显示分区副本数不足或 `isr` 列表缺失;`rpk cluster health` 报 `under-replicated`。这是分布式消息系统最常见的故障之一,通常不会立即影响可用性,但会累积延迟并在节点故障时放大影响。

```bash
rpk topic describe orders -X brokers=node1:9092
# 输出:
# PARTITION  LEADER  REPLICAS  ISR
# 0          1       [1 2 3]   [1 2]   ← ISR 缺 3,3 滞后
# 1          2       [1 2 3]   [2 3]
```

**根因排查**:

```bash
# 1. 看健康度
rpk cluster health
# "unhealthy_reasons": ["under_replicated_partitions: 1"]

# 2. Admin API 看具体分区
curl -s http://localhost:9644/v1/partitions/orders/0/replicas | jq .
curl -s http://localhost:9644/v1/partitions/orders/0/followers | jq .

# 3. 看 Follower 节点日志
ssh node3 "journalctl -u redpanda --since '5m ago' | grep -iE 'orders|partition 0|lag'"

# 4. 看 Follower 节点磁盘
ssh node3 "df -h /var/lib/redpanda/data && iostat -x 1"

# 5. 看网络
mtr node3
```

**常见根因**:

| 根因                            | 排查                                  | 解决方案                                |
|---------------------------------|---------------------------------------|-----------------------------------------|
| Follower 磁盘慢                | `iostat -x`,`%util > 80%`            | 换 SSD/NVMe                             |
| Follower 进程挂                  | `systemctl status redpanda`             | 重启                                    |
| 节点间 RPC 抖动                  | `mtr`,`ping`                          | 网络/防火墙                             |
| Follower CPU 忙                | `top -H -p <pid>`                    | 资源扩容                                |
| Follower OOM                   | `dmesg \| grep -i oom`               | 内存扩容                                |
| `raft_learner_rate` 配置过低   | `redpanda.yaml`                       | 调高                                    |

**解决方案**:

```bash
# 临时止血:提高副本滞后容忍(redpanda.yaml)
redpanda:
  raft_election_timeout: 1500  # 默认 1.5s
  # 重新拉取的间隔
  reclaim_batch_size: 65536
```

**根本解决**:扩磁盘、改 SSD、调 `raft_learner_rate=5`(默认 1)、增加 CPU。

### 2. ISR 收缩

**现象**:`rpk topic describe` 中 `isr` 列小于 `replicas`;Follower 节点离线超过阈值被踢出 ISR。

**ISR 收缩条件**(RedPanda):
- Follower 节点宕机
- Follower 落后 Leader 超过 `replicate_append_timeout`(默认 5s)
- Follower 在 `heartbeat_interval`(默认 100ms) 内未响应

**排查步骤**:

```bash
# 1. 看所有 ISR 异常分区
rpk cluster health
# 或 Admin API
curl -s http://localhost:9644/v1/partitions/orders/0/followers | jq .
# last_reconciled_offset、last_visible_offset 差异大 → 副本滞后

# 2. 看 Follower 节点健康
ssh node3 "systemctl status redpanda"
ssh node3 "journalctl -u redpanda --since '10m ago' | grep -iE 'error|crash|killed'"

# 3. 看 OS 层
ssh node3 "dmesg | tail -20"
ssh node3 "iostat 1 3"

# 4. 看网络
mtr node3
```

**解决方案**:

```yaml
# redpanda.yaml 调整
redpanda:
  replicate_append_timeout: 5000   # 5 秒默认
  # 提高容忍,但牺牲安全性
  # 生产推荐:不调,直接修问题

  # 增加副本同步并发
  recovery_throttle_bytes: 1073741824  # 1GB/s
```

**预防**:监控告警 `isr_shrink_count > 0`、节点打散到不同机柜、磁盘/内存容量规划。

### 3. 副本不可用

**现象**:`rpk topic describe` 显示某些分区无 Leader,生产/消费报 `LeaderNotAvailable`、`UNKNOWN_TOPIC_OR_PARTITION`。

**排查步骤**:

```bash
# 1. 看所有无 Leader 分区
rpk cluster health
# 输出:{"unhealthy_reasons": ["leaderless_partitions: 5"]}

# 2. Admin API 看具体
curl -s http://localhost:9644/v1/partitions/orders/0/leaderless | jq .
# true → 真无 Leader

# 3. 看健康度详情
curl -s http://localhost:9644/v1/cluster/health | jq .

# 4. 看 broker 列表(是否过半)
rpk cluster info
```

**解决方案**:

```bash
# A) 多数节点存活:等待自动重新选举(秒级)
rpk cluster health

# B) 多数节点不可用:必须恢复节点
# 1. 网络问题恢复
# 2. 节点进程恢复
sudo systemctl start redpanda   # 在故障节点上

# C) 数据目录损坏:清空 + 让节点重新加入
sudo systemctl stop redpanda
sudo rm -rf /var/lib/redpanda/data/*   # 慎用!
sudo systemctl start redpanda

# D) 强制重建副本(危险,慎用)
# 用 rpk redpanda admin partitions transfer-leadership
rpk redpanda admin partitions transfer-leadership --partition 0 --topic orders --new-leader 2
```

## 六、Leader 频繁切换

**现象**:`rpk topic describe` 显示 Leader 列频繁变化;Producer 报 `NotLeaderForPartition`;消费者频繁 rebalance。

**根因排查**:

```bash
# 1. 看集群事件
rpk cluster audit list --limit 50
# 看谁在做 leadership 操作

# 2. 看 controller log(谁在调度)
journalctl -u redpanda | grep -iE "leader|election|transfer" | tail

# 3. 看所有 broker 健康
for n in node1 node2 node3; do
  ssh $n "systemctl status redpanda"
done

# 4. 看节点 OOM/重启
dmesg | grep -i "killed\|restart\|crash" | tail

# 5. Admin API 看 leadership 变更
curl -s http://localhost:9644/v1/audit/leader_transfer | jq .
```

**常见根因**:

| 根因                          | 排查                                | 解决方案                                |
|-------------------------------|-------------------------------------|-----------------------------------------|
| 节点 OOM/kill                | `dmesg \| grep kill`               | 调内存、防 OOM                          |
| 节点频繁重启                  | `journalctl` 看启动记录            | systemd 调优                            |
| 磁盘满                        | `df -h`                            | 扩容、清理                              |
| 网络抖动(RPC)                | `mtr`,RPC 端口 33145 抖动           | 网络/交换机                             |
| `raft_election_timeout` 过小 | redpanda.yaml                      | 调到 3s+                                |
| 手动 transfer leadership     | 变更管理记录                        | 检查流程                                |

**生产推荐配置**:

```yaml
redpanda:
  raft_election_timeout: 3000         # 默认 1.5s,放宽到 3s 减少抖动
  raft_heartbeat_interval: 500        # 默认 100ms(election_timeout/3)
  # 防止节点抖动导致频繁选举
  enable_idempotence: true            # 生产端用 librdkafka.enable.idempotence
```

## 七、Consumer 问题

### 1. Lag 持续增长

**现象**:`rpk group describe <group>` 显示 `LAG` 列持续增大,业务消息积压。这是 Kafka/RedPanda 系统最常见的告警,但根因多种多样,必须分层定位。Lag 增长的原因通常可以归为三大类:生产速度超过消费能力(消费侧瓶颈)、单分区处理过慢(单实例瓶颈)、Broker 端写入变慢(服务端瓶颈),具体定位时需要从消费侧看 partition 分配,再回溯到 broker 端指标。

**排查流程**:

```bash
# 1. 看 lag
rpk group describe order-consumer -X brokers=node1:9092
# 输出:
# GROUP           TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-consumer  orders 0          10000           50000           40000

# 2. 看消费者实例与分配
rpk group describe order-consumer --verbose -X brokers=node1:9092
# 看是否多个实例都分配了分区

# 3. 看 broker 端积压
rpk topic describe orders -X brokers=node1:9092
# 看 Leader 分区 log-end-offset

# 4. 看 topic 健康
rpk cluster health
```

**Lag 增长流程图**:

```text
            [Lag 告警]
                │
        ┌───────┼───────┐
        ↓       ↓       ↓
   生产太快?  消费太慢? Broker 慢?
        │       │       │
        ↓       ↓       ↓
   Topic 分区  单实例  ISR 收缩?
   数不足?     处理慢? GC/磁盘?
        │       │       │
        └───────┼───────┘
                ↓
        ┌───────┼───────┐
        ↓       ↓       ↓
   加分区  扩容实例  调磁盘
```

**解决方案**:

| 场景              | 方案                                                          |
|-------------------|---------------------------------------------------------------|
| 生产太快          | 增加 Topic 分区(单分区并行度上限 = 1 消费者实例)              |
| 单实例慢          | 水平扩容消费者实例(注意:实例数 ≤ 分区数)                       |
| 处理逻辑慢        | 异步化、批量处理、外部 IO 异步化                                |
| Broker 慢         | 排查 GC、磁盘 IO(`iostat -x 1`)                              |
| 业务逻辑抛异常     | 看应用日志,死循环?N+1 查询?外部接口慢?                       |
| 反压(下游写慢)   | 限流、上游降级、增加下游并行                                   |

**关键配置**(librdkafka):

```c
// 消费者提升吞吐
rd_kafka_conf_set(conf, "max.poll.records", "500", NULL);
rd_kafka_conf_set(conf, "fetch.min.bytes", "1", NULL);
rd_kafka_conf_set(conf, "fetch.wait.max.ms", "500", NULL);
rd_kafka_conf_set(conf, "max.partition.fetch.bytes", "1048576", NULL);
rd_kafka_conf_set(conf, "session.timeout.ms", "45000", NULL);
rd_kafka_conf_set(conf, "heartbeat.interval.ms", "15000", NULL);
rd_kafka_conf_set(conf, "max.poll.interval.ms", "300000", NULL);  // 5 分钟
```

### 2. Rebalance 频繁

**现象**:日志频繁 `Group rebalance`、`Member join`;消费者 lag 抖动。

**根因排查**:

```bash
# 1. 看消费者日志
grep -E "rebalance|join|leave" app.log | tail -50

# 2. 看心跳超时
# librdkafka 默认 session.timeout.ms=45s,heartbeat=3s

# 3. 看 GC / poll 间隔
# 应用长时间不 poll,会被踢出
```

**常见原因**:

| 原因                              | 表现                          | 解决                                                  |
|-----------------------------------|-------------------------------|-------------------------------------------------------|
| `max.poll.interval.ms` 太短       | 单次 poll 处理慢被踢出       | 调到 300000(5 分钟)                                  |
| 处理逻辑慢(外部 IO/DB)            | 处理时间 > max.poll.interval | 异步化、增加 max.poll.interval                        |
| `session.timeout.ms` 太短         | 心跳超时被踢                 | 调整到 30-60 秒                                       |
| 网络抖动                          | 心跳包丢失                   | 调高 session.timeout,或排查网络                        |
| 消费者实例频繁重启                | 部署问题                     | 容器化时调整 readinessProbe                          |

**参数推荐**:

```c
rd_kafka_conf_set(conf, "session.timeout.ms", "45000", NULL);    // 45s
rd_kafka_conf_set(conf, "heartbeat.interval.ms", "15000", NULL); // 15s
rd_kafka_conf_set(conf, "max.poll.interval.ms", "300000", NULL); // 5 分钟
rd_kafka_conf_set(conf, "max.poll.records", "200", NULL);
```

### 3. OOM

**现象**:消费者进程 `OutOfMemoryError`,重启后又 OOM。这种情况常发生在突发流量或业务变更后,排查时要特别关注消息大小和单条处理逻辑的内存占用。

**根因**:`max.poll.records=10000` + 单条消息大 + 内存累积处理 = 内存爆炸。

**排查**:

```bash
# 1. 看堆内存
ps -o pid,rss,vsz -p <consumer-pid>
# 或 jstat(Java 消费者)

# 2. 拉取消息大小
rpk topic describe orders
# 看 log-end-offset / partition count

# 3. GC 日志(Java 消费者)
grep -E "Full GC|gc pause" gc.log

# 4. 看 librdkafka 内部统计(用 KIP-794 metric 或 rdkafka_stat)
# 看 broker 端 fetch 的字节数
```

**解决方案**:

```c
// 关键:限制每次拉取量
rd_kafka_conf_set(conf, "max.poll.records", "100", NULL);
rd_kafka_conf_set(conf, "fetch.max.bytes", "52428800", NULL);       // 50MB
rd_kafka_conf_set(conf, "max.partition.fetch.bytes", "1048576", NULL); // 1MB

// 消费者内部及时释放
while (running) {
    rd_kafka_message_t *rkm;
    while ((rkm = rd_kafka_consumer_poll(c, 100)) != NULL) {
        process(rkm);
        rd_kafka_message_destroy(rkm);  // 显式释放
    }
}
```

## 八、Tiered Storage 问题

### 1. 上传失败

**现象**:日志报 `Failed to upload segment to S3`、`cloud_storage_uploads_failed` 指标上升;数据仍在本地盘但未归档。Tiered Storage 上传失败会导致本地盘压力上升,因为老数据无法释放;长期不解决会引发磁盘告警甚至数据丢失风险。

**常见根因**:

| 根因                            | 排查                                                  |
|---------------------------------|-------------------------------------------------------|
| S3/MinIO 凭证错误              | `rpk redpanda admin secrets list`                    |
| Bucket 不存在/无写权限         | `aws s3 ls s3://bucket/` 或 `mc ls local/bucket`     |
| 网络不可达 S3                  | `curl -v https://s3.amazonaws.com`                    |
| Bucket 区域错                  | 客户端/服务端区域不一致                              |
| `cloud_storage_segment_size` 太小 | 上传太频繁,API 限流                                |
| TLS 证书错误                   | `openssl s_client -connect s3.amazonaws.com:443`      |

**排查步骤**:

```bash
# 1. 看 Tiered Storage 指标
curl -s http://localhost:9644/public_metrics | grep -i cloud_storage

# 2. 看相关日志
journalctl -u redpanda | grep -iE "cloud_storage|s3|upload" | tail -50

# 3. 看 credentials
rpk redpanda admin secrets list
# 验证 ID/Secret 正确

# 4. 测试网络
curl -v https://<bucket>.<endpoint>.amazonaws.com
# 或 mc
mc ls local/<bucket>

# 5. 看 segment 是否生成
ls -la /var/lib/redpanda/data/redpanda/cloud_storage/<namespace>/<topic>/
```

**解决方案**:

```bash
# A) 凭证错误
rpk redpanda admin secrets create --name s3-credentials \
  --access-key <KEY> --secret-key <SECRET>

# B) Bucket 权限
aws s3api put-bucket-policy --bucket <bucket> --policy file://policy.json

# C) 调整上传参数
# redpanda.yaml:
redpanda:
  cloud_storage_enable: true
  cloud_storage_bucket: "my-bucket"
  cloud_storage_region: "us-east-1"
  cloud_storage_segment_upload_timeout: 30000  # 30s
  cloud_storage_initial_backoff_ms: 100
  cloud_storage_segment_max_upload_interval: 60000  # 60s
```

### 2. 下载慢

**现象**:消费者开启 `fetch.from.follower=true` 或读取旧数据时,延迟高;日志 `cloud_storage_segment_download_latency` 高。

**排查**:

```bash
# 1. 看下载指标
curl -s http://localhost:9644/public_metrics | grep -i "cloud_storage.*download"

# 2. 看 S3 端延迟
curl -w "time_total: %{time_total}\n" -o /dev/null -s \
  https://<bucket>.s3.amazonaws.com/test/object

# 3. 看 network 带宽
sar -n DEV 1
```

**解决方案**:

```yaml
# redpanda.yaml
redpanda:
  cloud_storage_cache_size: 1073741824   # 1GB 本地缓存
  cloud_storage_readreplica_manifest_sync_timeout_ms: 30000
```

### 3. 凭证过期

**现象**:日志报 `SignatureDoesNotMatch`、`ExpiredToken`、`InvalidAccessKeyId`;上传/下载突然失败。

**排查步骤**:

```bash
# 1. 看凭证状态
rpk redpanda admin secrets list

# 2. 看 STS 临时凭证(如果是 IAM Role)
# K8s:看 Service Account annotation
# EC2:看 instance metadata
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

**解决方案**:

```bash
# A) 更新凭证
rpk redpanda admin secrets update --name s3-credentials \
  --access-key <NEW_KEY> --secret-key <NEW_SECRET>

# B) 配置自动刷新(如果用 IAM Role)
redpanda:
  cloud_storage_credentials_source: "aws_instance_metadata"  # 或 "sts"

# C) K8s 用 IRSA(ServiceAccount 注解 IAM Role)
```

## 十、Shadow Linking 问题

**现象**:Shadow Link 状态异常,远端 topic 数据未同步或同步延迟;`rpk shadow link list` 显示 `state: faulted`。Shadow Link 是 RedPanda 的跨集群复制机制,常用于灾备和异地多活;出现故障会导致主备集群数据不一致,影响切流决策。

**常见根因**:

| 根因                              | 排查                                                  |
|-----------------------------------|-------------------------------------------------------|
| 远端集群不可达                    | `nc -zv <remote> 9092`                                |
| 远端集群认证失败                  | 凭证过期/错误                                         |
| `bootstrap_servers` 错误          | `rpk shadow link describe <name>`                     |
| TLS 证书问题                      | `rpk redpanda admin certs list`                       |
| topic name mapping 错误           | 配置的 source → destination 错                        |
| 远端集群无源 topic                | 在远端 `rpk topic list` 验证                          |

**排查步骤**:

```bash
# 1. 看 shadow link 状态
rpk shadow link list
rpk shadow link describe my-link

# 2. 看同步进度
rpk shadow link status my-link
# 看 source offset vs destination offset

# 3. 看错误日志
journalctl -u redpanda | grep -iE "shadow|link" | tail

# 4. 测试远端连接
nc -zv <remote-broker> 9092
```

**解决方案**:

```bash
# A) 重置 shadow link
rpk shadow link delete my-link
rpk shadow link create my-link \
  --bootstrap-servers <remote>:9092 \
  --source-topic <src-topic> --destination-topic <dst-topic>

# B) 修复凭证
rpk shadow link edit my-link --config /tmp/shadow-config.yaml

# C) 跳过失败 topic
rpk shadow link edit my-link --exclude <topic>
```

## 十一、Schema Registry 问题

**现象**:客户端 schema 注册失败,返回 `Subject ... not found`、`Invalid schema`、`Schema registry connection refused`。Schema Registry 是 schema 演进的中心,如果出现故障,会导致所有依赖 schema 序列化的业务中断。

**常见根因**:

| 根因                            | 排查                                                  |
|---------------------------------|-------------------------------------------------------|
| Schema Registry 未启动          | `rpk redpanda config show \| grep schema_registry`     |
| Schema Registry 端口错          | 默认 8081                                             |
| `auto.create.topics.enable=false` | Schema Registry 无法自动建 topic                       |
| 客户端配置的 URL 错              | 客户端 schema registry url 配置                       |
| 兼容性检查失败                  | `rpk registry subject describe <subject>`             |
| 引用错(import 引用 schema)    | `rpk registry ref list <subject>`                     |

**排查步骤**:

```bash
# 1. Schema Registry 状态
curl -s http://localhost:8081/subjects
# 或
rpk registry subject list

# 2. 看具体 subject
rpk registry subject describe orders-value

# 3. 看兼容性配置
rpk registry config describe orders-value

# 4. 测试注册
echo '{"type":"string"}' > /tmp/schema.json
rpk registry subject create orders-value /tmp/schema.json

# 5. 看 RedPanda 日志
journalctl -u redpanda | grep -i "schema" | tail
```

**解决方案**:

```yaml
# A) 开启 Schema Registry
# redpanda.yaml
schema_registry:
  enabled: true
  schema_registry_api:
    - address: 0.0.0.0
      port: 8081

# B) 修改兼容性策略
rpk registry config set orders-value --compatibility BACKWARD

# C) 修正 schema(消除兼容性错误)
# 客户端:使用兼容版本
# 服务端:增大兼容性策略或迁移到新 subject
```

## 十二、Wasm Transform 问题

**现象**:Wasm 脚本未触发或执行失败;`rpk transform list` 显示 `status: failed`;日志报 `wasm error`、`failed to invoke`。Wasm Transform 是 RedPanda 的轻量级流处理能力,如果执行失败会导致数据处理链路中断。

**常见根因**:

| 根因                              | 排查                                                  |
|-----------------------------------|-------------------------------------------------------|
| Wasm 模块文件路径错              | `ls -la /etc/redpanda/wasm/<name>.wasm`               |
| 签名缺失/错误                    | RedPanda Wasm 需要 `rpk` 签名                         |
| 内存限制超                        | Wasm 用内存 > 配置                                    |
| `input_topic`/`output_topic` 错 | transform 配置错                                     |
| SDK 不兼容                        | Wasm 编译时 SDK 版本过旧                              |
| `status` 是 `disabled`           | 集群级别禁用 transform                                |

**排查步骤**:

```bash
# 1. 看 transform 列表
rpk transform list

# 2. 看具体 transform
rpk transform describe <name>

# 3. 看 wasm 内部错误
journalctl -u redpanda | grep -iE "wasm|transform" | tail -50

# 4. 看 metrics
curl -s http://localhost:9644/public_metrics | grep -i "transform\|wasm"
```

**解决方案**:

```bash
# A) 重新部署 transform
# 重新签名 + 部署
rpk transform deploy /tmp/transform.wasm \
  --name my-transform --input-topic in --output-topic out

# B) 调整内存限制
# redpanda.yaml
redpanda:
  wasm_max_memory_per_call: 16777216   # 16MB 默认

# C) 关闭 transform(临时止血)
rpk transform disable <name>

# D) 重新签名
rpk sign --in=transform.wasm --out=transform-signed.wasm
```

## 十三、紧急恢复

### 1. 节点崩溃后数据恢复

**场景**:单节点崩溃(`systemctl status redpanda` 显示 failed 或重启失败),需要恢复数据或重建节点。

**恢复流程**:

```bash
# 步骤 1:评估损坏程度
sudo systemctl status redpanda
journalctl -xeu redpanda --since '1 hour ago' | tail

# 步骤 2:尝试重启
sudo systemctl start redpanda
sleep 10
sudo systemctl status redpanda

# 步骤 3:如果仍然失败,看数据目录
ls -la /var/lib/redpanda/data/
du -sh /var/lib/redpanda/data/*

# 步骤 4:看具体错误
journalctl -u redpanda -n 200 --no-pager

# 步骤 5:决策:数据保留还是清空重建

# 5a) 数据目录健康 → 保留数据,修复启动
sudo chown -R redpanda:redpanda /var/lib/redpanda/data
sudo systemctl start redpanda

# 5b) 数据目录损坏 → 清空,让节点从 seed 重新拉数据
sudo systemctl stop redpanda
sudo rm -rf /var/lib/redpanda/data/*
sudo systemctl start redpanda
# 注意:此操作会让节点变成"空节点",集群会从其他节点复制数据
```

**关键校验**:

```bash
# 节点起来后验证
rpk status
rpk cluster health
rpk topic list

# 验证分区数据
for t in $(rpk topic list); do
  rpk topic describe $t
done
```

### 2. 集群数据重建

**场景**:整个集群数据丢失,需要从备份/Shadow Link/Tiered Storage 重建。

**场景 A:从 Tiered Storage 重建**:

```bash
# 1. 准备全新集群(3 节点或更多)
# 2. 配置相同的 cluster_id 和 redpanda.yaml
# 3. 配置 Tiered Storage
# 4. 启动集群
# 5. 触发 Shadow Link 或 Restore

# 从 Tiered Storage restore
rpk topic create orders --partitions 3 -X brokers=localhost:9092
# 实际上 Tiered Storage 数据是"只读",不能直接 restore 到新 topic
# 通常用 Shadow Link 从原集群恢复
```

**场景 B:从 Shadow Link 重建**:

```bash
# 1. 配置 Shadow Link 指向原集群
rpk shadow link create recovery-link \
  --bootstrap-servers <original>:9092 \
  --source-topic orders \
  --destination-topic orders-recovered

# 2. 等同步完成
rpk shadow link status recovery-link

# 3. 验证数据
rpk topic consume orders-recovered -n 10
```

**场景 C:从备份(S3/对象存储)恢复**:

```bash
# 1. 拉取备份(用 rpk redpanda admin 工具)
# 2. 校验 MD5
# 3. 解压到数据目录
# 4. 修改 cluster_id 与原集群一致
# 5. 启动
```

**预防**:定期测试恢复 SLA(每季度一次灾备演练);Shadow Link 备用集群;Tiered Storage 跨地域;S3 备份。

## 十五、实战案例

### 案例 1:节点启动失败(配置错误)

**时间**:2026-04-12 14:30,新节点扩容时。

**现象**:
- 新节点加入集群失败
- 日志:`Failed to parse config: missing field 'node_id'`

**排查**:

```bash
# 1. 看节点状态
ssh new-node "rpk status"
# 输出:Error: connection refused

# 2. 看 systemd 状态
ssh new-node "systemctl status redpanda"
# 输出:active (exited)

# 3. 看日志
ssh new-node "journalctl -xeu redpanda | tail -30"
# 输出:yaml-cpp:error at line 23: missing key 'node_id'
```

**根因**:Ansible 模板中 `node_id` 占位符没被替换(渲染为字符串 `"{{ node_id }}"`)。

**解决**:

```bash
# 1. 修复配置
# /etc/redpanda/redpanda.yaml 中:
#   node_id: "{{ node_id }}"   ← 错的
# 改为:
#   node_id: 4                 ← 正确(集群内唯一)

# 2. 重启
sudo systemctl restart redpanda
sleep 10
rpk status

# 4. 验证加入
rpk cluster info
# 期望:能看到 4 个节点
```

**复盘**:
- Ansible 模板必须有 Jinja2 syntax check
- 渲染后必须校验 YAML
- 新节点加入后必须有 health check

### 案例 2:性能下降排查

**时间**:2026-06-08 09:00,业务高峰期。

**现象**:
- Producer P99 延迟从 20ms 涨到 500ms
- Consumer Lag 持续增长
- Broker CPU 90%+

**排查**:

```bash
# 1. 看集群健康
rpk cluster health
# 输出:under_replicated_partitions > 0

# 2. 看 CPU
top -H -p $(pgrep -f redpanda)
# 输出:压缩线程占 70%

# 3. 看客户端
grep "compression" producer.properties
# 输出:compression.type=zstd

# 4. 看网络
sar -n DEV 1
# 网卡正常

# 5. 看 Tiered Storage
curl -s http://localhost:9644/public_metrics | grep cloud_storage_upload
# 上传量正常
```

**根因**:
- 客户端开启 zstd 压缩,RedPanda 端需解压 + 重新压缩存储,CPU 飙升
- 凌晨业务方改客户端配置,没通知运维

**解决**:

```yaml
# 客户端:关闭 zstd,改用 lz4
producer.properties:
  compression.type=lz4
# 验证 CPU 下降
top -H -p $(pgrep -f redpanda)
```

**复盘**:
- 客户端配置变更必须有 review
- Producer 端 CPU 监控必加
- RedPanda 端配置 (librdkafka 客户端默认 `compression.type=lz4`)

### 案例 3:副本滞后

**时间**:2026-07-22 03:00,定时任务运行。

**现象**:
- `rpk cluster health` 报 `under_replicated_partitions: 50`
- Lag 持续 10 分钟

**排查**:

```bash
# 1. 看 ISR 收缩
rpk topic describe orders -X brokers=node1:9092
# 输出:多个分区 ISR 缺 3

# 2. 看节点 3 状态
ssh node3 "systemctl status redpanda"
# 输出:active(running)

# 3. 看磁盘
ssh node3 "df -h /var/lib/redpanda/data"
# 输出:Use% 95%,只有 2GB 剩余

# 4. 看 IO
ssh node3 "iostat -x 1"
# 输出:%util 98%,await 200ms
```

**根因**:定时任务大量写入,节点 3 磁盘满,IO 排队,副本同步慢被踢出 ISR。

**解决**:

```bash
# 1. 紧急清理旧数据
# 改 retention 至短时间
rpk topic config set orders --set retention.bytes=10737418240  # 10GB
# 或
rpk topic delete <old-topic>

# 2. 扩磁盘
# 加盘、扩 LVM

# 3. 验证恢复
sleep 60
rpk cluster health
# 期望:under_replicated_partitions=0
```

**复盘**:
- 磁盘容量必须按 70% 监控
- 定时任务写入量必须评估
- Tiered Storage 必须开启(老数据归档)

### 案例 4:Tiered Storage 上传失败

**时间**:2026-05-15 11:20,S3 凭证轮转后。

**现象**:
- 新数据未上传 S3
- 日志:`Failed to upload segment: SignatureDoesNotMatch`

**排查**:

```bash
# 1. 看凭证
rpk redpanda admin secrets list
# 输出:secret 创建时间 1 年前

# 2. 看错误
journalctl -u redpanda | grep -i "cloud_storage\|s3" | tail -20
# 输出:SignatureDoesNotMatch

# 3. 测试 S3
mc ls local/bucket
# 输出:AccessDenied
```

**根因**:S3 凭证被轮转,RedPanda 仍用旧凭证。

**解决**:

```bash
# 1. 更新凭证
rpk redpanda admin secrets update --name s3-credentials \
  --access-key <NEW_KEY> --secret-key <NEW_SECRET>

# 2. 验证
sleep 30
curl -s http://localhost:9644/public_metrics | grep cloud_storage_uploads_failed
# 期望不再增长
```

**复盘**:
- 凭证轮转必须有 checklist
- 监控 `cloud_storage_uploads_failed_total > 0` 告警

### 案例 5:数据丢失排查

**时间**:2026-08-02 02:00,业务方反馈关键数据找不到。

**现象**:
- `rpk topic consume orders` 从 offset 0 看不到历史消息
- 监控显示:`retention.bytes=1073741824`(1GB)被触发

**排查**:

```bash
# 1. 看 topic 配置
rpk topic describe orders
# 输出:Topic 配置 OK

# 2. 看保留策略
rpk topic config get orders
# 输出:retention.bytes=1073741824,retention.ms=604800000

# 3. 看 earliest offset
rpk topic consume orders -o start -n 1
# 输出:offset 太大,说明最早数据已清理

# 4. 看 Tiered Storage(如果开了)
rpk redpanda admin cloud-storage list-segments orders
# 输出:云端有 segment
```

**根因**:`retention.bytes=1GB` 配置过小,3 天前数据被本地清理;但 Tiered Storage 开启,云端仍有。

**解决**:

```bash
# 1. 从 Tiered Storage 恢复(创建新 topic)
rpk topic create orders-recovered --partitions 3 -X brokers=localhost:9092
# 或用 Shadow Link

# 2. 调整 retention
rpk topic config set orders --set retention.bytes=107374182400  # 100GB
rpk topic config set orders --set retention.ms=2592000000       # 30 天

# 3. 验证
rpk topic consume orders -o start -n 5
```

**复盘**:
- retention 配置必须与容量规划匹配
- Tiered Storage 必须开启(防本地清理)
- 关键业务数据必须双副本(本地 + 远程)

## 十七、核心要点速记

### 排查哲学

- **排查顺序**:业务 → 客户端 → Broker → 操作系统 → 硬件,从表象到底层,不要跳级
- **黄金法则**:80% 的故障通过 `rpk` 命令 + `/var/log/redpanda/` 就能定位,无需读源码
- **预防 > 排查**:监控告警、容量巡检、灾备演练,比事后排查高效 10 倍
- **永远先看日志**:`journalctl -u redpanda` 是第一手资料,先 grep 再分析
- **永远不要盲目重启**:集群级故障先看 `rpk cluster health`,避免加剧脑裂
- **永远先 dump 数据**:任何破坏性操作前,先备份数据目录或用 Shadow Link

### 核心工具(熟记 5 个命令)

- `rpk cluster health`:看 leaderless、under-replicated
- `rpk topic describe <topic>`:看分区、ISR、Leader 分布
- `rpk group describe <group>`:看 Lag、offset 进度
- `rpk redpanda admin partitions transfer-leadership`:手动迁移 Leader
- `curl http://localhost:9644/public_metrics`:Prometheus 指标

### 关键配置三件套

- **生产配置三件套**:`acks=all` + `enable.idempotence=true` + `retries=Integer.MAX_VALUE`(生产者)
- **副本强一致**:`replication.factor=3` + 节点数 ≥ 3(奇数)
- **Tiered Storage 必开**:本地保留短,云端保留长,默认配置

### RedPanda 特有差异(对比 Kafka)

| 项                | Kafka                       | RedPanda                              |
|-------------------|------------------------------|---------------------------------------|
| 控制平面         | ZK 或 KRaft 独立 Controller | 内置 Raft(任何节点可做 Leader)        |
| 语言/运行时      | JVM (Scala/Java)            | C++(无 JVM)                           |
| 配置文件         | `server.properties`         | `redpanda.yaml` (YAML)                |
| 启动              | `kafka-server-start.sh`     | `redpanda` + systemd                 |
| 客户端 CLI        | `kafka-topics.sh` 等        | `rpk`(统一)                           |
| Page Cache        | OS 透明使用 | 内置 chunk cache                       |
| 存储后端         | 本地 + 可选 Tiered(自 3.6) | 本地 + Tiered Storage(S3/MinIO)内置  |
| 跨集群复制       | MirrorMaker 2              | Shadow Linking                        |
| 流处理           | Kafka Streams / ksqlDB      | Wasm Transform                        |
| Schema 管理       | Confluent Schema Registry   | 内置 Schema Registry                  |

### 高频故障模式速查

| 故障现象                | 第一动作                                         |
|-------------------------|--------------------------------------------------|
| 消费者 Lag 增长         | `rpk group describe` 看哪个分区                   |
| Producer 报错           | 看异常类型(超时/超限/鉴权),对应解决              |
| Broker 不可用            | `rpk cluster health` + `rpk status`              |
| 磁盘写满                | `df -h` + 调 `retention.bytes`                   |
| Rebalance 频繁          | 看心跳超时 + `max.poll.interval.ms` 配置         |
| 选举失败                | 检查 `cluster_id` + `seed_servers`              |
| Tiered 上传失败         | `rpk redpanda admin secrets list`               |
| Shadow 同步失败         | `rpk shadow link status <name>`                  |
| Wasm 执行失败           | `rpk transform list` 看 status                   |
| Schema 注册失败         | `rpk registry subject describe`                 |

### 监控告警红线

- **Leaderless Partitions > 0** → Critical(立即响应)
- **UnderReplicated Partitions > 0**(持续 5 分钟)→ Warning
- **Consumer Lag > 10000** → Warning(按业务调阈值)
- **磁盘 > 85%** → Critical
- **CPU > 80%**(持续 5 分钟)→ Warning
- **Cloud Storage Uploads Failed > 0** → Warning
- **Broker 节点 < 3** → Critical

### 容量规划基线

- **磁盘**:`日均消息量 × 平均大小 × 保留天数 × 副本数 / 压缩率 × 1.5`(余量),**Tiered Storage 开启可大幅降低**
- **分区数**:`业务并发度 × 2`(留扩展空间)
- **消费者实例数**:`≤ 分区数`,建议 = 分区数(满载)
- **内存**:单 broker ≥ 16GB(高吞吐场景)
- **网络**:留 50% 余量,高峰期避免饱和
- **节点数**:3 或 5(奇数),生产推荐 5

### 性能调优 Check

- 客户端 `linger.ms=10~50` + `batch.size=64KB+`
- 客户端 `compression.type=lz4`(平衡)/ `zstd`(高压缩,需关注服务端 CPU)
- `cloud_storage_max_throughput_per_shard` 按网络带宽调整
- 监控告警:`request_latency` P99 > 100ms
- 定期 `rpk cluster health` 巡检

### 灾备铁律

- **必须有备份**:Tiered Storage(S3/MinIO)+ Shadow Link
- **必须有切流 SOP**:主备切换 RTO < 5 分钟
- **必须有跨地域**:异地容灾,避免单机房故障
- **定期演练**:每季度一次真实切流演练
- **数据可恢复**:任何删除前必备份,任何写入必验证

### 变更管理 Check

- **灰度发布**:1% → 5% → 20% → 50% → 100%
- **配置 review**:双人复核 + 变更系统工单
- **压测验证**:升级前必须做同等规模压测
- **回滚预案**:每个变更必须能回滚
- **观察期**:24-48 小时观察,无异常才算成功
- **客户端/服务端版本一致性**:librdkafka 与 RedPanda 版本兼容

### 安全 Check

- **mTLS**:生产必开,Kafka TLS + RPC TLS
- **ACL**:最小权限原则,每个业务方独立用户
- **SASL**:SCRAM-SHA-256 或 SCRAM-SHA-512
- **Schema Registry 鉴权**:开启基础认证或外部 IdP
- **网络隔离**:RedPanda 不暴露公网
- **审计日志**:记录所有 ACL 变更

### 心态 Check

- 不要"差不多就行",生产配置必须精确
- 不要"重启就好",根因没找到会反复
- 不要"客户没投诉就没事",监控告警是唯一标准
- 不要"加机器就行",先看瓶颈在哪
- 不要"看别人这么配我也这么配",按业务选配置
- 不要"上线再说",上线前必须压测
- 不要"凭感觉调参数",每次改动必须有数据支撑

### RedPanda 特有建议

- **多看 rpk**:它统一了所有操作,不需要记 Kafka 多个脚本
- **善用 Admin API**:HTTP API 比 kafka 协议更易调试
- **开启 Tiered Storage**:本地保留 24h-7d,云端保留 30-365 天
- **使用 Shadow Link**:跨集群复制和灾备首选
- **Wasm Transform 谨慎**:性能 + 资源消耗评估
- **关注 C++ 内存**:不像 JVM 有 GC,但 C++ 内存泄漏更难查
