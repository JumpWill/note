## 一、监控概述

### 监控层次

```text
┌────────────────────────────────────────┐
│  1. 业务层: 应用消息成功率/延迟         │
├────────────────────────────────────────┤
│  2. 客户端层: Producer/Consumer 指标    │
├────────────────────────────────────────┤
│  3. 集群层: 节点状态、副本、副本滞后     │
├────────────────────────────────────────┤
│  4. 进程层: CPU、内存、IO、文件描述符   │
├────────────────────────────────────────┤
│  5. 操作系统层: ulimit、TCP、磁盘       │
├────────────────────────────────────────┤
│  6. 硬件层: 服务器、网络、存储          │
└────────────────────────────────────────┘
```

### RedPanda 监控工具链

```text
内置工具    →    rpk cluster info / health / debug
   ↓
指标暴露    →    /public_metrics (Prometheus 格式)
   ↓
采集存储    →    Prometheus / VictoriaMetrics
   ↓
可视化      →    Grafana Dashboard
   ↓
告警        →    Alertmanager + Slack/PagerDuty
```

## 二、内置监控命令(rpk)

### rpk cluster

```bash
# 集群基本信息
rpk cluster info
# 输出: cluster_id, nodes (id, address, status)

# 集群健康检查
rpk cluster health
# 输出: 节点健康状态

# 集群整体状态
rpk status
# 显示 partitions, leaders, replicas

# 调试模式(详细)
rpk cluster debug info

# 查看某个 broker
rpk cluster logdirs --broker 0

# 查看 controller 状态
rpk redpanda controller status
```

### rpk topic

```bash
# 查看 topic 列表
rpk topic list

# 查看 topic 详情
rpk topic describe payments

# 查看 topic 配置
rpk topic describe-config payments
```

### rpk group

```bash
# 查看消费组列表
rpk group list

# 查看消费组状态 (含 Lag)
rpk group describe my-consumer-group

# 输出: state, members, lag (per partition)
```

### rpk redpanda

```bash
# 查看 admin API 状态
rpk redpanda admin status

# 查看 Raft 状态
rpk redpanda controller status

# 健康检查
rpk redpanda status
```

## 三、Prometheus 集成

### 启用内置 Prometheus Exporter

Redpanda 默认在 **9644 端口**暴露 Prometheus 指标。

```yaml
# redpanda.yaml
redpanda:
  admin:
    - address: 0.0.0.0
      port: 9644

# 指标路径
# http://<broker>:9644/public_metrics
# http://<broker>:9644/metrics (内部)
```

### Prometheus 配置

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'redpanda'
    static_configs:
      - targets:
        - 'rp1:9644'
        - 'rp2:9644'
        - 'rp3:9644'
    
    scrape_interval: 15s
    metrics_path: /public_metrics
```

```text
Redpanda 默认暴露 ~200 个指标,主要分类:

1. 集群指标: redpanda_cluster_*
2. 节点指标: redpanda_node_*
3. Partition 指标: redpanda_partition_*
4. Kafka 协议: kafka_*, redpanda_kafka_*
5. RPC: rpc_*
6. 存储: storage_*, disk_*
7. Raft: redpanda_raft_*
8. Controller: controller_*
```

## 五、核心监控指标

### 集群级指标

| 指标 | 含义 | 监控值 |
|------|------|--------|
| `redpanda_cluster_brokers_count` | 节点数 | 期望值 |
| `redpanda_cluster_topics_count` | topic 数 | 业务相关 |
| `redpanda_cluster_partitions_count` | 分区总数 | 业务相关 |
| `redpanda_cluster_unavailable_partitions` | 不可用分区 | **必须 = 0** |
| `redpanda_cluster_under_replicated_partitions` | 副本不足分区 | **必须 = 0** |

### 节点级指标(系统资源)

| 指标 | 含义 | 告警阈值 |
|------|------|----------|
| `process_cpu_seconds_total` | CPU 使用率 | > 80% 警告 |
| `process_resident_memory_bytes` | 物理内存 | > 80% 警告 |
| `process_open_fds` | 打开文件数 | > 80% ulimit 警告 |
| `redpanda_disk_free_bytes` | 磁盘空闲 | < 20% 警告 |
| `redpanda_disk_free_space_alert` | 磁盘空间预警 | **必须 = 0** |

### Partition 级别指标

| 指标 | 含义 |
|------|------|
| `redpanda_partition_records_count` | 消息总数 |
| `redpanda_partition_committed_offset` | 已提交位移 |
| `redpanda_partition_high_watermark` | 高水位 |
| `redpanda_partition_under_replicated_replicas` | 副本不足计数 |
| `redpanda_kafka_request_bytes_total` | 请求字节数 |
| `redpanda_kafka_request_records_total` | 请求消息数 |

### Kafka 协议指标(关键)

| 指标 | 含义 |
|------|------|
| `redpanda_kafka_request_latency_seconds_*` | 请求延迟(直方图) |
| `redpanda_kafka_requests_total{api="PRODUCE"}` | 生产请求数 |
| `redpanda_kafka_requests_total{api="FETCH"}` | 消费请求数 |
| `redpanda_kafka_consumer_group_topic_lag_*` | Consumer Lag |

### Raft 指标(RedPanda 特有)

| 指标 | 含义 |
|------|------|
| `redpanda_raft_leadership_changes_total` | Leader 切换次数 |
| `redpanda_raft_recovery_attempts_total` | 恢复尝试次数 |
| `redpanda_raft_group_recovery_count` | 分组恢复次数 |
| `redpanda_raft_group_configuration_updates_total` | 配置变更次数 |

## 六、Consumer Lag 监控

### rpk group describe

```bash
# 查看消费组 lag
rpk group describe my-consumer-group

# 输出示例:
# GROUP           TOPIC      PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# my-consumer-group payments   0          1000            1500            500
# my-consumer-group payments   1          2000            2500            500

# 关键指标: LAG = LOG-END-OFFSET - CURRENT-OFFSET
```

### 持续监控脚本

```bash
#!/bin/bash
# check_consumer_lag.sh
# 定期检查 consumer lag,超阈值告警

GROUP="my-consumer-group"
THRESHOLD=10000

rpk group describe $GROUP --format json | \
  jq -r '.[] | "\(.topic):\(.partition) lag=\(.lag)"' | \
while read line; do
  lag=$(echo $line | grep -oP 'lag=\K\d+')
  if [ "$lag" -gt "$THRESHOLD" ]; then
    echo "ALERT: $line exceeds threshold $THRESHOLD"
    # 发送告警
  fi
done
```

### Prometheus 告警

```yaml
# prometheus alert rules
- alert: KafkaConsumerLag
  expr: sum by(consumer_group, topic) (kafka_consumergroup_lag) > 10000
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "Consumer {{ $labels.consumer_group }} lag > 10000"
```

## 七、告警规则

### 关键告警项

```yaml
groups:
- name: redpanda_alerts
  rules:
  # ===== 集群可用性 =====
  - alert: RedpandaBrokerDown
    expr: up{job="redpanda"} == 0
    for: 1m
    labels:
      severity: critical
    annotations:
      summary: "Redpanda broker {{ $labels.instance }} 不可达"

  - alert: RedpandaBrokersDown
    expr: count(redpanda_cluster_brokers_count) < 3
    for: 2m
    labels:
      severity: critical

  # ===== Partition 健康 =====
  - alert: UnavailablePartitions
    expr: redpanda_cluster_unavailable_partitions > 0
    for: 1m
    labels:
      severity: critical

  - alert: UnderReplicatedPartitions
    expr: redpanda_cluster_under_replicated_partitions > 0
    for: 5m
    labels:
      severity: warning

  # ===== 资源 =====
  - alert: RedpandaHighCPU
    expr: rate(process_cpu_seconds_total[5m]) * 100 > 80
    for: 10m
    labels:
      severity: warning

  - alert: RedpandaHighMemory
    expr: process_resident_memory_bytes / 1024 / 1024 / 1024 > 25  # 假设 32GB 总内存
    for: 10m
    labels:
      severity: warning

  - alert: RedpandaDiskSpaceLow
    expr: redpanda_disk_free_bytes < 50 * 1024 * 1024 * 1024  # < 50GB
    for: 5m
    labels:
      severity: critical

  - alert: RedpandaFDsHigh
    expr: process_open_fds / process_max_fds > 0.8
    for: 5m
    labels:
      severity: warning

  # ===== 性能 =====
  - alert: RedpandaHighProduceLatency
    expr: histogram_quantile(0.99, rate(redpanda_kafka_request_latency_seconds_bucket{api="PRODUCE"}[5m])) > 0.1  # 100ms
    for: 5m
    labels:
      severity: warning

  - alert: RedpandaHighConsumeLatency
    expr: histogram_quantile(0.99, rate(redpanda_kafka_request_latency_seconds_bucket{api="FETCH"}[5m])) > 0.5  # 500ms
    for: 5m
    labels:
      severity: warning

  # ===== Raft =====
  - alert: RaftLeadershipChanges
    expr: increase(redpanda_raft_leadership_changes_total[5m]) > 3
    for: 1m
    labels:
      severity: warning
```

## 八、运维操作

### 8.1 健康检查脚本

```bash
#!/bin/bash
# health_check.sh
# 每日巡检脚本

set -e
echo "=== RedPanda Cluster Health Check ==="
echo "Time: $(date)"
echo

# 1. 集群信息
echo "[1] Cluster Info"
rpk cluster info

# 2. 健康状态
echo
echo "[2] Health Status"
rpk cluster health

# 3. 节点资源
echo
echo "[3] Node Resources"
for node in rp1 rp2 rp3; do
  echo "--- $node ---"
  ssh $node "top -bn1 | head -3; df -h /var/lib/redpanda"
done

# 4. 检查不可用分区
echo
echo "[4] Unavailable Partitions"
unavailable=$(rpk cluster health --exit-when-unhealthy=false 2>&1 | grep -c "unavailable" || echo 0)
echo "Unavailable partitions: $unavailable"

# 5. Consumer Lag
echo
echo "[5] Consumer Group Lag"
rpk group list | tail -n +2 | while read group rest; do
  lag=$(rpk group describe $group 2>/dev/null | awk '/^.* / {sum += $5} END {print sum}')
  echo "$group total lag: $lag"
done

# 6. 磁盘空间
echo
echo "[6] Disk Space"
df -h /var/lib/redpanda

echo "=== Health Check Complete ==="
```

### 8.2 滚动重启

```bash
#!/bin/bash
# rolling_restart.sh
# 逐台重启 Redpanda 节点

NODES=("rp1" "rp2" "rp3")

for node in "${NODES[@]}"; do
  echo "=== Restarting $node ==="
  
  # 1. 先关闭(确保副本数够)
  ssh $node "sudo systemctl restart redpanda"
  
  # 2. 等待启动
  sleep 10
  
  # 3. 验证节点恢复
  rpk cluster health | grep $node
  
  # 4. 等待集群稳定
  sleep 30
done
```

### 8.3 配置变更

```bash
# 查看所有可配置项
rpk cluster config list

# 动态配置(无需重启)
rpk cluster config set log_segment_size 134217728

# 查看当前值
rpk cluster config get log_segment_size

# 编辑配置(交互式)
rpk cluster config edit
```

### 8.4 分区扩容

```bash
# 查看当前分区分布
rpk topic describe payments

# 1. 添加节点
# (扩容节点,启动新 broker,加入集群)

# 2. 重新分配分区(将部分分区迁移到新节点)
rpk cluster partitions move \
  --topic payments \
  --partition 0 \
  --to rp4

# 3. 批量迁移(平衡所有分区)
rpk cluster partitions balance --replicas 3
```

### 8.5 节点替换

```bash
# 1. 移除故障节点
rpk cluster nodes decommission --node-id 2

# 2. 启动新节点,加入集群
# 在新节点上启动 redpanda
sudo systemctl start redpanda

# 3. 验证
rpk cluster info
```

## 九、容量规划

### 磁盘容量

```text
公式:
   磁盘需求 = 写入速率 × 保留时间 × 副本数 × 压缩率倒数

例:
   - 写入速率: 100 MB/s
   - 保留: 7 天 = 604800 秒
   - 副本: 3
   - 压缩: zstd 压缩比 0.4

   需求 = 100 × 604800 × 3 × (1/0.4) / 1024 / 1024 / 1024 ≈ 42 TB

Tiered Storage 后:
   本地保留 1 天 = 100 × 86400 × 3 × (1/0.4) / 1024 / 1024 / 1024 ≈ 6 TB
   S3 存 6 天 = 36 TB(便宜)
```

### 网络带宽

```text
公式:
   网络带宽需求 = 峰值写入速率 × 副本数 + 跨数据中心同步

例:
   - 峰值写入: 500 MB/s
   - 副本: 3
   - 网络 IO: 500 × 3 = 1.5 GB/s

   推荐万兆网卡(10 Gbps = 1.25 GB/s) 可能不够,需要 25 Gbps 或多网卡 bonding
```

### 内存规划

```text
RedPanda 内存消耗:
   - 进程内存: 4-8 GB (按数据量)
   - OS Page Cache: 建议 8-16 GB (缓存热数据)
   - 其他系统进程: 2 GB

总计: 16 GB 起步,32 GB 推荐

   推荐配置(8.0+):
      redpanda.resource_limits.memory: "16G"
      (其中 OS cache 优先,redpanda 不会挤占 page cache)
```

### CPU 规划

```text
公式:
   CPU 核心数 = (峰值 QPS / 50,000) × 1.5

例:
   - 峰值 20 万 QPS
   - 核心数: 200000 / 50000 × 1.5 ≈ 6 核
   - 推荐: 8 核 (留 1.5x 冗余)

   注意: RedPanda 是 thread-per-core,核心数很重要
```

## 十一、升级与回滚

```bash
# 1. 升级前备份配置和数据
sudo cp /etc/redpanda/redpanda.yaml /etc/redpanda/redpanda.yaml.bak
```

```bash

# 或用备份恢复数据
sudo systemctl stop redpanda
sudo rsync -av /backup/redpanda-bak/ /var/lib/redpanda/
sudo systemctl start redpanda
```

## 十二、监控运维实战案例

### 案例 1:突发 Lag 告警

**现象**:Prometheus 告警:Consumer Lag > 100,000

**排查步骤**:

```bash
# 1. 查看 lag 详情
rpk group describe my-consumer-group

# 2. 查看 partition 状态
rpk cluster partitions list --topic payments | head

# 3. 检查 broker 负载
rpk status
# 看 broker 0 CPU/IO 状态

# 4. 检查网络
ping rp1

# 5. 检查磁盘 IO
ssh rp1 "iostat -x 1 5"
```

**根因**:broker 0 磁盘 IO 100% busy

**解决**:
```bash
# 1. 临时: 增加 broker 0 分区数
rpk cluster partitions balance --replicas 3

# 2. 长期: 升级磁盘到 NVMe SSD
# 3. 启用 Tiered Storage 减少本地 IO
```

### 案例 2:节点 OOM

**现象**:broker 2 被 OOM Killer 杀掉,重启后又被杀

**排查**:

```bash
# 1. 查看系统日志
dmesg | grep -i "out of memory"
# 输出: Out of memory: Killed process 1234 (redpanda)

# 2. 检查 Redpanda 内存配置
rpk redpanda admin config get memory

# 3. 检查 Page Cache 使用
free -h
# 缓冲区和缓存占用过高
```

**解决**:
```yaml
# redpanda.yaml
redpanda:
  resource_limits:
    memory: "8G"  # 限制最大内存,防止 OOM

# 增加机器内存到 32GB
# 或启用 swap(临时方案)
```

### 案例 3:Leader 频繁切换

**现象**:每分钟 5 次 Leader 切换

**排查**:

```bash
# 1. 查看 Raft 指标
rpk cluster health

# 2. 查看网络延迟
ping -c 100 rp2 | tail

# 3. 查看系统时间同步
chronyc sources
```

**根因**:节点时间不同步(偏差 200ms),导致 Raft 心跳超时

**解决**:
```bash
# 同步时间
sudo chrony sources -v
sudo systemctl restart chronyd

# 优化 Raft 超时
rpk cluster config set raft_election_timeout_ms 2000
```

## 核心要点速记

### 监控三大支柱

```text
1. 集群健康: Broker 数、不可用分区、副本滞后 = 必须 0
2. 性能指标: P99 延迟、吞吐量、连接数
3. 资源使用: CPU、内存、磁盘 IO、文件描述符
```

### 关键告警阈值

```text
┌────────────────────────────┬────────────┐
│ 告警项                      │ 阈值       │
├────────────────────────────┼────────────┤
│ unavailable_partitions > 0  │ 立即处理   │
│ under_replicated > 0 (持续) │ 5分钟内    │
│ Broker CPU > 80%           │ 10分钟     │
│ 磁盘空闲 < 20%             │ 立即处理   │
│ P99 延迟 > 100ms           │ 5分钟      │
│ Consumer Lag > 阈值        │ 5分钟      │
│ 文件描述符 > 80%           │ 5分钟      │
└────────────────────────────┴────────────┘
```

### 容量规划公式

```text
磁盘需求 = 写入速率 × 保留时间 × 副本数 / 压缩率
网络带宽 = 峰值写入 × 副本数
CPU 核心数 = (峰值 QPS / 50,000) × 1.5
内存 = 16GB 起步,32GB 推荐
```

### 备份策略

```text
- 文件级: 停服 + rsync (影响大)
- Tiered Storage: 自动异地 (推荐)
- Shadow Linking: 跨集群同步 (灾备)
```

### 运维操作要点

```text
1. 滚动重启: 逐台,每次间隔 30 秒
2. 扩容: 先加节点,再平衡分区
3. 配置变更: 区分动态 vs 静态
4. 升级: 小版本直接升,大版本逐级
5. 回滚: 备份配置和数据,15 分钟内完成
```

### 监控工具速查

```bash
# 健康检查
rpk cluster info

# 业务指标
rpk topic list

rpk debug info
```

### 紧急 Checklist

```text
□ 不可用分区 = 0? (否则立即处理)
□ 副本不足分区 = 0?
□ 所有 broker HEALTHY?
□ 磁盘空闲 > 20%?
□ 监控和告警正常?
□ Consumer Lag 在合理范围?
□ 备份任务执行成功?
□ 客户端连接正常?
□ 最近一次成功写入在 1 分钟内?
```
