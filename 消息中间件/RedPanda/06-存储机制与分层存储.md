# RedPanda 存储机制与分层存储

> 本章深入剖析 RedPanda 的底层存储机制:基于 C++ 实现的高性能日志分段、稀疏索引、Direct IO 异步写入、读写流程,以及 RedPanda 最有差异化的能力—— **Tiered Storage(分层存储)**。Tiered Storage 让 RedPanda 可以把冷数据几乎"无限"地搬到 S3 / MinIO / GCS / Azure Blob 等对象存储,本地只保留热数据,既保证了 Kafka 协议兼容又把存储成本压到极致。

---

## 一、RedPanda 存储概述

### 1. RedPanda 与 Kafka 在存储上的根本差异

RedPanda 100% 兼容 Kafka 协议,但在存储实现上做了根本性的重写。两者的哲学差异可以用一句话概括:**Kafka 是"在 JVM 上把文件系统用到极致",RedPanda 是"在 C++ 上把硬件用到极致"**。

| 维度                | Kafka                                | RedPanda                                  |
|--------------------|--------------------------------------|-------------------------------------------|
| **语言栈**          | Scala + JVM                          | C++20 (seastar 协程框架)                  |
| **线程模型**        | 每请求一个线程 / 异步 IO 混合         | 共享无线程 (share-nothing) + 协程          |
| **IO 模型**         | Page Cache + sendfile / mmap          | Direct IO + 自主管理页缓存                 |
| **Page Cache**      | 完全交给 OS                          | 自行管理,跳过 OS 抖动 (thrashing)         |
| **GC 抖动**         | Full GC / G1 停顿存在                | 无 GC,延迟 p99 稳定                       |
| **分层存储**        | KIP-405(实验) / 商业版才有          | **开源版默认自带**,核心差异化能力          |
| **单分区吞吐**      | 瓶颈容易在 GC                        | 单核就能到数 GB/s                          |
| **存储介质假设**    | HDD / SSD 都能用                    | 默认 NVMe 优化,可配 HDD                   |

RedPanda 的核心论文 / 工程博客多次强调:它假设存储是 **NVMe SSD**,并在 Direct IO 上自主管理 page cache,做到**延迟可控**。这与 Kafka "依赖 OS Page Cache" 的设计哲学不同——OS Page Cache 在 32+ GB 工作集下会出现 LRU 抖动,RedPanda 直接绕过。

### 2. 存储模型基本概念

| 概念                      | 含义                                                              |
|--------------------------|------------------------------------------------------------------|
| **Topic**                | 消息主题,逻辑分类,一个 Topic 可被分为多个 Partition             |
| **Partition (NTPs)**     | 物理分片;RedPanda 内部统一叫 **NTPs** (Namespace-Topic-Partition)|
| **Log**                  | Partition 在磁盘上的物理表现,一组 Segment 文件的集合             |
| **Segment**              | 日志分片,按大小 / 时间切分的物理文件段                           |
| **Offset**               | 分区内单调递增的 64 位整数,消息的唯一编号                        |
| **Dirty Ratio**          | RedPanda 自管理 cache 的"脏页比例",触发回写                      |
| **Housekeeping**         | RedPanda 后台线程,负责 segment 滚动、清理、合并                  |
| **Cloud Storage Manifest** | 分层存储的元数据文件,记录分段在云端的位置                       |
| **Housekeeping Jobs**    | 后台异步任务:compaction、archival、deletion、upload 等           |

### 3. 存储目录结构

RedPanda 默认把所有数据放在 `data_directory` 指定的目录下,典型结构如下:

```text
/var/lib/redpanda/data/
├── kafka/
│   ├── __consumer_offsets/                 # 内部 topic:消费位移
│   │   ├── 0/
│   │   │   ├── 00000000000000000000.log    # 分段日志
│   │   │   ├── 00000000000000000000.base_offset
│   │   │   ├── 00000000000000000004.index  # 稀疏索引
│   │   │   ├── 00000000000000000004.tx.range
│   │   │   └── ...
│   │   └── ...
│   ├── __redpanda_internal/                # 内部元数据 topic
│   │   └── ...
│   └── my-topic/                           # 业务 topic
│       └── 0/
│           ├── 00000000000000000000.log
│           ├── 00000000000000000000.base_offset
│           ├── 00000000000000000000.index
│           ├── 00000000000000000000.size_bytes
│           ├── 00000000000000000000.compaction_index
│           ├── 00000000000000000000.tx.range
│           ├── 00000000000000000000.manifest.json         # 元数据
│           └── ...
└── redpanda_controller/                    # controller 集群状态
    └── ...
```

与 Kafka 相比,每个 segment 多了几类元数据文件:

- `*.base_offset` —— 段起始 offset 的快速读取文件(避免每次解析 log)
- `*.size_bytes` —— 段累计字节数,用于快速判断是否滚动
- `*.compaction_index` —— compaction 用的索引,加速清理
- `*.manifest.json` —— 分层存储的元数据,记录该段是否已上传到云端、上传到哪个对象

### 4. 关键特性总览

| 特性                  | 说明                                                                |
|----------------------|---------------------------------------------------------------------|
| **顺序写入**         | 消息按 offset 追加,磁盘几乎零寻道                                 |
| **不可变性**         | 已写入的消息不可修改(只能产生新消息或被清理)                       |
| **分区分段**         | 每个 Partition 内部按 segment 切分,便于清理与恢复                  |
| **稀疏索引**         | 索引不是每条消息都建,而是间隔 16KB (默认)一条索引,内存开销极小     |
| **自管理 Cache**     | 不依赖 OS Page Cache,在大量内存下延迟更稳定                        |
| **Direct IO**        | 数据写入绕过 OS 缓存,跳过双层缓存                                  |
| **Tiered Storage**   | 开源版自带,云端近乎无限扩展                                         |
| **批量 + 压缩**      | batch 内可对多条消息一起压缩,broker 端不解压直转                  |
| **Housekeeping 线程** | 单后台线程统一处理 segment 滚动、清理、上传,避免"小文件风暴"        |

### 5. 一条消息从生产到落盘的完整路径

```text
1. Producer 端
   ├─ 业务调用 producer.send(record) 提交一条消息
   ├─ 客户端攒批(lz4/zstd 压缩,默认 batch.size 1MB)
   ├─ 经 Partitioner 路由到 Partition Leader
   └─ 发送到 RedPanda Broker (Kafka 协议 wire-protocol)

2. Broker 端 (seastar 协程)
   ├─ kafka_api 协程接收 Produce 请求
   ├─ 校验 producer id / epoch / sequence(幂等)
   ├─ replication_group 写入 active segment
   │    ├─ 申请 cache 中的 dirty 区段
   │    ├─ 把 record batch 追加到 segment
   │    ├─ 更新 LEO / index / size_bytes (增量)
   │    └─ 调度副本同步
   └─ 返回 Produce Response

3. Follower 副本同步
   ├─ 通过 raft 协议复制日志项 (log entry)
   ├─ follower 同样走 cache -> segment 追加
   └─ 多数派 ack 后,leader 提交并通知 client

4. 异步刷盘
   ├─ housekeeping 线程按 dirty_ratio / interval 触发 writeback
   ├─ Direct IO 写入 NVMe
   └─ 写完更新 manifest

5. 分层存储上传
   ├─ housekeeping 后台扫描"已关闭 + 已同步"的 segment
   ├─ 走 S3 SDK / azure-sdk 异步上传
   └─ 写入 cloud_storage_manifest.json
```

可以看到 RedPanda 写入路径上**只有"追加 + 异步刷盘"两步**,没有 JVM 堆分配,没有 GC 暂停,延迟 p99 通常在个位数毫秒。

### 6. 与其他 MQ 的存储对比

| 中间件        | 存储模型              | 典型吞吐         | 冷数据成本          |
|--------------|----------------------|-----------------|---------------------|
| **Kafka**    | 日志 + 分段 + 稀疏索引 | 百万级 msg/s    | 全部本地盘,贵       |
| **RabbitMQ** | 队列 + B+Tree 索引     | 万级 msg/s      | 全部本地盘,贵       |
| **RocketMQ** | CommitLog + ConsumeQueue | 十万级 msg/s | 全部本地盘,贵       |
| **Pulsar**   | BookKeeper 分段日志   | 百万级 msg/s    | 多层 Bookie,部分托管 |
| **RedPanda** | 日志 + 分段 + 自管 Cache + Tiered Storage | 百万级 msg/s | **冷数据可全在云端,几乎免费** |

唯一在"冷数据成本"上能和 RedPanda 抗衡的是 Pulsar(其 BookKeeper 也支持分层到 S3),但 RedPanda 因为单二进制、C++ 实现,运维成本远低于 Pulsar。

### 8. 硬件选型与存储介质

RedPanda 对硬件的"假设"和 Kafka 不同,直接影响部署成本和性能上限。

**推荐的硬件组合**:

| 角色           | 推荐                                          | 备选                          |
|--------------|----------------------------------------------|------------------------------|
| **CPU**       | 高频单核(> 3.5 GHz),16 核以上               | 优先单核,其次多核              |
| **内存**       | 64 GB 起,推荐 128 GB                         | 数据量 << 内存,否则用分层      |
| **存储**       | NVMe SSD,推荐 ioDrive / PM983 / 9100 PRO     | SATA SSD / HDD (性能下降 5~10x) |
| **网络**       | 25 Gbps 起,推荐 100 Gbps                     | 10 Gbps 起步                  |
| **节点数**     | 3 起步,5+ 推荐                                | 不要 单节点 1 节点生产          |

**为什么 RedPanda 偏好高频单核**?这与 seastar 协程模型有关:RedPanda 每个 shard 一个核,**所有协程都在同一核上调度**。多核之间通过 sharding 划分,避免跨核同步成本。这与 Kafka "用多线程对冲 GC" 的策略完全不同。RDMA 友好、PCIe 4.0/5.0 NVMe 在 RedPanda 下能跑出比 Kafka 高 3~5 倍的 IOPS。

**为什么推荐大内存**?RedPanda 自管理 cache 占用内存 = `reclaim_size_threshold` + dirty LRU;如果 Topic 数据量 << 内存,基本全在 cache,延迟最低。如果数据量 >> 内存,频繁换入换出会触发 writeback,延迟上涨 5~10 倍——此时**优先用 Tiered Storage 把冷数据搬到云端**,本地只保留热销数据。

**NVMe 与 Direct IO 的协同**:
```text
物理路径:
  RedPanda cache (4KB 页) → Direct IO (O_DIRECT) → NVMe 驱动 → PCIe → SSD 控制器 → NAND
                                    ↑ 必须 4KB 对齐
                                    ↑ 必须 16KB 以上 IO 才能发挥效果
```

RedPanda 在写入时强制 4KB 对齐、16KB 合并,正好把 NVMe 的并行队列 (32~64 队列) 跑满。SATA SSD / HDD 在 RedPanda 上完全跑不出性能,业界有先例把 RedPanda 跑在 HDD 上得到"小规模 cluster 的延迟还行"的结果,但**生产部署严禁使用 HDD**。

### 9. 存储优化的"十六字诀"

RedPanda 工程师社区流传的优化口诀,可以作为性能调优的 checklist:

```text
"大事务,小索引;热本地,冷云端;
 大段落,小事务;少副本,多 broker;
 频繁批,稀疏读;高网卡,低 GC;
 直接 IO,避开 swap;大内存,小延迟。"
```

每条口诀对应一个调优点:

1. **大事务,小索引**:增加 batch.size,减少索引条目数量
2. **热本地,冷云端**:开启 Tiered Storage,本地只留 7 天
3. **大段落,小事务**:128 MB segment + 高频 commit,但单事务小
4. **少副本,多 broker**:3 副本即可,不要 5 副本;broker 数量更重要
5. **频繁批,稀疏读**:Consumer 用大 max.poll.records
6. **高网卡,低 GC**:25 Gbps + C++(无 GC)
7. **直接 IO,避开 swap**:vm.swappiness = 1,关掉 OS swap
8. **大内存,小延迟**:128 GB 内存是甜蜜点

## 二、存储架构

RedPanda 的存储架构由三层组成:**Cache 层**(自管理内存)、**Local Storage**(本地磁盘)、**Tiered Storage**(云端对象存储)。三层是**统一的索引视图**,对客户端透明。

### 1. Cache 层(自管理 Page Cache)

RedPanda 的 cache 层使用 seastar 提供的 **memory::page_pool** 自主管理,在**用户态**完成页面调度,完全绕过 OS Page Cache。它的核心结构如下:

```text
┌─────────────────────────────────────────────────────────────┐
│                       RedPanda Cache 层                       │
├─────────────────────────────────────────────────────────────┤
│  dirty LRU (写入中)              │  clean LRU (已回写)        │
│  ┌─────────────────────────┐    │  ┌─────────────────────┐  │
│  │ segment.0000.log [0-4KB] │    │  │ segment.0002.log    │  │
│  │ segment.0000.log [4-8KB] │    │  │ (最近被读)           │  │
│  │ segment.0001.log [0-4KB] │    │  │                     │  │
│  │ ...                     │    │  │                     │  │
│  └─────────────────────────┘    │  └─────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│  page writeback queue (FIFO)                                  │
│  → dirty_ratio 超过阈值时,触发 writeback 到本地磁盘          │
└─────────────────────────────────────────────────────────────┘
```

Cache 层的设计哲学可以用一句话概括:**"用户态的 page cache,附带 OS Page Cache 不会提供的可观测性"**。RedPanda 工程师可以精确知道哪些 page 是 dirty、哪些被读、哪些被预读,从而做出更精细的策略。

**Cache 层的内部数据结构**:

```cpp
// 伪代码:seastar page_pool 的简化版
class page_pool {
    struct page {
        uint64_t offset;       // (segment, file_offset)
        uint32_t ref_count;    // 引用计数
        bool is_dirty;         // 是否 dirty
        lru_clock_t last_used; // 用于 LRU 淘汰
    };
    
    std::unordered_map<page_key, page> _pages;
    lru_list<page*> _dirty_lru;
    lru_list<page*> _clean_lru;
};
```

**Cache 层的关键指标**:

| 指标                       | 含义                                | 监控方式                          |
|---------------------------|------------------------------------|----------------------------------|
| `cache_dirty_pages`       | dirty 区段 page 数                   | `rpk redpanda admin metrics`     |
| `cache_clean_pages`       | clean 区段 page 数                   | `rpk redpanda admin metrics`     |
| `cache_total_bytes`       | cache 总占用字节数                     | `rpk redpanda admin metrics`     |
| `cache_evictions`         | 因 LRU 淘汰的 page 数                 | `rpk redpanda admin metrics`     |
| `cache_hit_ratio`         | 命中比例 (0~1)                       | `rpk redpanda admin metrics`     |

**Cache 层的写流程**:
1. Producer 写入一条 record batch(~16 KB)
2. cache 模块按 4 KB page 切分,分配 page 对象
3. 数据写入 dirty LRU,标记 `is_dirty = true`
4. 触发 `(dirty_ratio - threshold)` 阈值检测
5. 超过阈值 → 调度 writeback 协程
6. writeback 协程按 16 KB 对齐做 Direct IO,写入 NVMe
7. 写入成功后,把 page 移到 clean LRU,标记 `is_dirty = false`

**Cache 层的淘汰策略**:
- **优先淘汰 clean LRU**:clean 页是新近写入但未被读过的页,优先级低
- **dirty 页尽可能保留**:dirty 页是写入但未持久化的页,过早淘汰会强制 writeback
- **内存压力时**:reclaim 算法按 `reclaim_stretch_step` 逐页淘汰,避免"突发回收"

**与 OS Page Cache 的对比**:

| 维度                  | OS Page Cache                  | RedPanda Cache                      |
|-----------------------|-------------------------------|-------------------------------------|
| **管理方**            | 内核 (VFS)                      | 用户态 (seastar)                     |
| **可见性**            | 内核日志 / proc               | Prometheus + 控制台                  |
| **抖动**              | 内存压力下主动丢页              | 严格 LRU,精细控制                    |
| **NUMA 友好**         | 不友好                          | shard 绑定,跨核无锁                  |
| **crypto / compression** | 需用户态二次拷贝               | 原地操作                             |
| **swap 行为**         | 主动 swap                       | 永远不 swap                          |

**实战建议**:
- 大批量写入时(> 1 GB/s),`reclaim_min_size` 设为机器内存的 20%
- 延迟敏感场景(延迟 < 5 ms),`reclaim_size_threshold` 设为机器内存的 30%
- 多 Topic 场景,按 topic 分配 cache 配额,避免单个 topic 占用全部 cache

```yaml
# 内存相关推荐配置
redpanda:
  reclaim_min_size: 134217728        # 128 MB
  reclaim_size_threshold: 268435456  # 256 MB
  reclaim_batch_size: 524288
  reclaim_growth_window: 4000
  reclaim_stretch_step: 16384
  write_caching: true
  write_batch_size: 131072
  write_buffer_size: 524288
```

Cache 层的几个关键参数:

| 参数                          | 含义                                              |
|------------------------------|--------------------------------------------------|
| `reclaim_min_size`           | 触发回收的最小空闲内存阈值(默认 128MB)            |
| `reclaim_size_threshold`     | 触发回收的目标空闲阈值(默认 256MB)                |
| `reclaim_stretch_step`       | 每次回收的步进(默认 16KB)                         |
| `write_caching`              | 是否开启写缓存(true / false)                      |
| `write_batch_size`           | 写盘批量大小                                       |
| `write_buffer_size`          | 写盘后端 buffer                                     |

RedPanda 默认 `write_caching=true`,**数据先写 cache,异步刷盘**。这与 Kafka "默认 Page Cache + 后台回写" 类似,但因为是用户态管理,**不会出现 OS 在压力下主动丢 cache 的情况**——这对稳定延迟至关重要。

### 2. Local Storage(本地磁盘)

Local Storage 负责持久化"热数据"+ "近实时热数据"。所有被本节点作为 Leader / Follower 服务的分区,数据**首先**写到本地。

```text
本地持久化的数据特征:
├─ 最近一段保留期(默认 7 天)的所有数据
├─ 当前所有活跃 leader 的 active segment
├─ 所有 follower 副本的完整数据(replica.fetch 同步)
└─ compaction topic 的最新状态
```

Local Storage 的关键设计:

- **Direct IO 写入**:数据跳过 OS Page Cache,直接由 cache 层 → block 设备 → NVMe,避免"双层缓存"带来的内存浪费。
- **段滚动**:housekeeping 线程按 `log_segment_size` (默认 128 MB)和 `segment.ms` 滚动,关闭旧 segment。
- **fallocate**:mksegment 时调用 `posix_fallocate` 预分配,避免写入时的物理块分配抖动。
- **housekeeping 单线程**:所有 segment 操作(关段、清理、compact、上传云端)串行执行,**避免"小文件风暴"**。

### 3. Tiered Storage(云端对象存储)

Tiered Storage 是 RedPanda 真正的杀手锏。它把**已关闭且超过本地保留期**的 segment 异步上传到云端对象存储,本地只保留 hot data。

```text
┌─────────────────────────────────────────────────────────────┐
│                  Tiered Storage (云端)                        │
├─────────────────────────────────────────────────────────────┤
│  Bucket: redpanda-prod                                        │
│  ├─ prefix/<topic>/<partition>/<uuid>.log.1                  │
│  ├─ prefix/<topic>/<partition>/<uuid>.log.2                  │
│  ├─ prefix/<topic>/<partition>/<uuid>.index                  │
│  ├─ prefix/<topic>/<partition>/<uuid>.tx.range                │
│  └─ prefix/<topic>/<partition>/<uuid>.manifest.json           │
└─────────────────────────────────────────────────────────────┘
```

特点:

- **异步上传**:housekeeping 后台扫描已关闭、已同步的 segment,批量上传
- **对象级别压缩**:在 S3 端启用 S3 默认的 zstd 压缩,进一步降本
- **幂等**:每个 segment 有 uuid,重传不会重复
- **透明读取**:客户端访问冷数据时,RedPanda 自动从云端拉取,本地 cache

### 4. 三层协同

读 / 写数据的流向如下:

```text
写入 (Produce):
  Producer → broker cache (dirty) → [异步] → 本地 NVMe → [异步] → 云端 S3

读取 (Fetch):
  Consumer → broker cache (clean)  → 本地 NVMe → [异步预读] → 云端 S3
             (命中)     (未命中)     (本地未命中,云端拉取)
```

对外的协议视图始终是一个**完整的 offset 序列**,无论数据是在 cache、本地盘还是云端,客户端**完全无感知**。

## 三、数据文件结构

每个 Partition 的物理存储由若干 **Segment** 组成,每个 Segment 是一组紧密相关的文件。本节逐一拆解它们的角色。

### 1. Segment 文件

**`*.log`** 是真实的数据文件,内部由一组 **Record Batch** 组成,格式与 Kafka 完全一致(确保 wire-protocol 兼容):

```text
┌─────────────────────────────────────────────────────────────┐
│                    Segment Log 文件                          │
├─────────────────────────────────────────────────────────────┤
│  ┌───────────────────────────────────────────────────┐      │
│  │ RecordBatch #0                                     │      │
│  │  ├─ base_offset: 0                                 │      │
│  │  ├─ batch_length: 256                              │      │
│  │  ├─ partition_leader_epoch: 0                      │      │
│  │  ├─ magic: 2                                       │      │
│  │  ├─ crc: 0xABCDEF...                               │      │
│  │  ├─ attributes: (compression, timestamp_type)      │      │
│  │  ├─ last_offset_delta: 9                           │      │
│  │  ├─ base_timestamp: 1700000000000                  │      │
│  │  ├─ max_timestamp: 1700000000123                   │      │
│  │  ├─ producer_id: -1                                │      │
│  │  ├─ producer_epoch: -1                             │      │
│  │  ├─ base_sequence: -1                              │      │
│  │  ├─ records: [r0, r1, r2, ..., r9]                 │      │
│  │  └─ (每条 record: length, attributes, timestamp,     │      │
│  │       offset_delta, key, value, headers)            │      │
│  └───────────────────────────────────────────────────┘      │
│  ┌───────────────────────────────────────────────────┐      │
│  │ RecordBatch #1                                     │      │
│  │  ...                                               │      │
│  └───────────────────────────────────────────────────┘      │
│  ...                                                         │
└─────────────────────────────────────────────────────────────┘
```

每条 Record Batch 都**带 CRC 校验**,RedPanda 在读取时会严格校验,损坏的 batch 整个丢弃(replica 会从 leader 重新拉取)。

**`*.base_offset`** 是一个只有 8 字节的小文件,内容是当前 segment 的起始 offset。打开一个新 segment 时,先写这个文件,再写 log,这样**任何时候打开段都能从文件名 + base_offset 双向定位**。

**`*.size_bytes`** 是当前 segment 的累计字节数,持久化到磁盘,用于快速判断 `log_segment_size` 是否到达。

### 2. Index 文件(稀疏索引)

**`*.index`** 是 sparse index,记录 `(offset, file_position)` 的映射,每 **16KB**(默认 `index_interval_bytes`)写一条索引,而不是逐条建索引。

```text
┌─────────────────────────────────────────────────────────────┐
│                  Index File (稀疏索引)                        │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐        │
│  │ Entry #0                                        │        │
│  │  ├─ relative_offset: 0 (4 bytes, varint)         │        │
│  │  └─ position: 0 (4 bytes, varint)                │        │
│  ├─────────────────────────────────────────────────┤        │
│  │ Entry #1                                        │        │
│  │  ├─ relative_offset: 12 (4 bytes, varint)        │        │
│  │  └─ position: 16384 (4 bytes, varint)            │        │
│  ├─────────────────────────────────────────────────┤        │
│  │ Entry #2                                        │        │
│  │  ├─ relative_offset: 27 (4 bytes, varint)        │        │
│  │  └─ position: 32768 (4 bytes, varint)            │        │
│  └─────────────────────────────────────────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

相对 offset = 实际 offset - base_offset(用 varint 编码节省空间)。读取时二分查找 index,定位到 range,**再顺序扫描 16KB 找到目标 offset**。

### 3. compacted_index

**`*.compaction_index`** 是 compaction 专用索引,记录 compaction 后保留的 record 的偏移。compact 任务用它来决定哪些 record 还需要保留,哪些可以被覆盖。

### 4. tx_range

**`*.tx.range`** 是事务范围记录,记录该 segment 内的事务开始/提交标记。读取 `read_committed` 隔离级别时,broker 用它来跳过未提交事务的 record。

### 5. Manifest

**`*.manifest.json`** 是 RedPanda 分层存储的核心元数据,描述该 segment 的状态、上传位置等:

```json
{
  "version": 1,
  "namespace": "kafka",
  "topic": "my-topic",
  "partition": 0,
  "segment": {
    "base_offset": 0,
    "term": 1,
    "size_bytes": 134217728,
    "is_compacted": false,
    "archiver_term": 1,
    "segment_id": "00000000000000000000-uuid",
    "metadata_size_bytes": 1024
  },
  "cloud": {
    "size_bytes": 134217728,
    "path": "1/kafka/my-topic/0_0/00000000000000000000-uuid.log.1",
    "etag": "\"abc123...\"",
    "last_modified": 1700000000,
    "sha256": "..."
  }
}
```

manifest 既写在本地(便于快速查询),也同步上传到云端(用于跨 cluster 恢复和 Shadow Linking)。

### 6. leader-epoch / partition.metadata

类似 Kafka,用来记录 leader 世代变更历史,防止脑裂导致的日志截断。

## 四、写入流程

RedPanda 的写入路径比 Kafka 更短,核心是 **seastar 协程 + Direct IO + 自管理 cache** 三件套。

### 1. C++ 协程异步写入

```cpp
// 伪代码:redpanda 写入核心
seastar::future<result<produce_response>> 
kafka_api::produce(produce_request req) {
    auto result = co_await _group_manager->route(req.topic, req.partition);
    auto rg = co_await result.get();
    
    // 1. 校验
    auto err = validate_request(req);
    if (err) co_return err;
    
    // 2. 写入 leader 的 log
    auto batch_data = serialize_batch(req.records);
    auto r = co_await rg->replicate(std::move(batch_data), 
                                    raft::replicate_options{});
    
    // 3. 触发副本同步
    if (r == replicate_result::success) {
        co_return produce_response{...};
    }
}
```

所有 IO 都是 `co_await` 风格,**无线程切换、无锁竞争**,单核就能轻松扛下 GB/s 级的吞吐。

### 2. Direct IO / Buffered IO

RedPanda 写盘支持两种模式:

| 模式                                | 适用场景                          | 行为                                    |
|------------------------------------|----------------------------------|----------------------------------------|
| **Direct IO** (`O_DIRECT`)          | 默认,生产环境                    | 跳过 OS Page Cache,数据直接到 NVMe      |
| **Buffered IO** (`fsync`)           | 强一致性 / debug                  | 走 Page Cache + 主动 fsync              |

```yaml
# redpanda.yaml
redpanda:
  # 启用 Direct IO
  write_caching: true             # 改 false 即关闭 cache
  # fsync 模式
  fsync_per_msg: false            # 改 true 即每条消息 fsync(慢但安全)
```

Direct IO 的好处:

- **内存占用少**:只有 RedPanda 自己的 cache,不会出现"双层缓存各占 50% 内存"
- **延迟更稳定**:OS Page Cache 在内存压力下会主动丢页,Direct IO 不会
- **NUMA 友好**:seastar 调度器能控制 IO 在哪个 NUMA 节点

Direct IO 的代价:

- **小写不友好**:4KB 以下的随机写性能下降(RedPanda 通过 batch + 16KB index 间隔避开)
- **CPU 略高**:用户态做 cache 调度,CPU 多 5~10%

### 3. fsync 策略

RedPanda 的 fsync 策略由多个旋钮控制:

```yaml
redpanda:
  # 关键参数
  fsync_per_msg: false                 # 默认 false,批量 fsync
  log_segment_size: 134217728          # 128 MB
  segment_ms: null                     # 不按时间强制滚动
  flush_ms: null                       # 不按时间强制 flush
  flush_bytes: null                    # 不按字节数强制 flush
```

默认策略实际上是:

1. **写 cache**:Producer 来的 record batch 立即进入 dirty LRU
2. **异步盘写**:housekeeping 后台按 dirty_ratio / 时间 / 字节数触发 writeback
3. **强制刷盘时机**:segment 关闭、compaction 完成、leader 切主时主动 fsync

只有 **Raft 多数派 ack** 才会返回 ack=all,这条消息对客户端就算"已确认"——但此时**可能还在 cache 里**。如果机器在这一刻挂掉,会丢这批数据(幂等生产者 + 副本机制兜底)。

### 4. 写入流程图

```text
┌──────────┐  1. Produce    ┌──────────────┐
│ Producer │ ──────────────▶│ kafka_api    │
└──────────┘                │ (协程)       │
                            └──────┬───────┘
                                   │ 2. validate
                                   ▼
                            ┌──────────────┐
                            │ raft_group   │
                            │ ├─ leader    │
                            │ └─ followers │
                            └──────┬───────┘
                                   │ 3. replicate batch
                                   ▼
                            ┌──────────────┐
                            │ cache (dirty)│
                            │ 中    [dirty]│
                            └──────┬───────┘
                                   │ 4. writeback
                                   ▼
                            ┌──────────────┐
                            │  Direct IO   │
                            │  NVMe        │
                            └──────┬───────┘
                                   │ 5. fsync + segment
                                   ▼
                            ┌──────────────┐
                            │  segment     │
                            │  *.log       │
                            └──────────────┘
                                   │
                                   │ 6. major ack
                                   ▼
                            ┌──────────────┐
                            │  return ack  │
                            └──────────────┘
```

### 5. 写入路径的详细时序

为了帮助理解,我们跟踪一条 16 KB record batch 从 Producer 到 NVMe 的完整时序:

```text
T+0 ms      Producer.send(record) 进入 ProducerBatch
T+0.5 ms    攒批完成(batch.size=1MB,linger.ms=5)
T+1 ms      Sender 线程发送 RecordAccumulator 中就绪的 batch
T+1.5 ms    到达 broker leader 节点,kafka_api 协程接收
T+2 ms      validate_request 检查 producer_id / epoch / sequence
T+2.5 ms    raft_group.replicate() 序列化 batch,生成 raft log entry
T+3 ms      leader append log entry 到自己的 active_segment
T+3.5 ms    follower via raft fetch 请求同步
T+5 ms      follower 已 append,leader 收到 majority ack
T+5.5 ms    leader commit log entry
T+6 ms      kafka_api 协程返回 ProduceResponse
T+6.5 ms    Producer 收到 ack=1

[并行进行]
T+5 ms      housekeeping 线程检测 dirty_ratio > 阈值
T+5.5 ms    调度 writeback 协程
T+7 ms      Direct IO 写入 NVMe (16 KB 对齐)
T+7.5 ms    fsync 触发(由 dirty_ratio / time 决定)
T+8 ms      写入 *.log 文件,更新 *.size_bytes
T+8.5 ms    标记 cache clean

[并行进行]
T+30 秒     上一段已关闭 / 已 commit
T+30.5 秒   housekeeping 调度 upload
T+35 秒     S3 GET / PUT 完成 (segment 上传)
T+35.5 秒   manifest.json 写入云端
T+36 秒     本地 segment 删除 (本地 retention > 时)
```

**关键观察**:
- 端到端延迟:**Producer ack ~ 6 ms**
- 真实落盘延迟:**Producer ack 之后 1~2 ms**(cache dirty → writeback)
- 云端上传延迟:**30 秒级别**(异步),绝不影响生产

### 6. 故障路径与重试

```text
写入失败的几种情况及处理:

1. validate_request 失败
   → 返回 Producer 错误码 (eg. InvalidProducerEpoch)
   → Producer 重新建连 / 重新选举 leader

2. leader 找不到
   → 返回 NotLeaderForPartition
   → Producer 重新查 metadata (refresh)

3. raft replicate 失败
   → 内部 retry,直到 majority ack
   → 超过 raft_timeout 返回 TimeoutException

4. cache OOM
   → reclaim 触发,强制 writeback
   → 写入暂停,直到 reclaim 完成

5. NVMe 写入失败
   → segment 标记 dirty
   → 后台重试,直到成功
   → 失败 N 次后 segment 标记为 corrupted,触发分片卸载
```

**幂等性保证**:RedPanda 实现 Kafka 标准的 producer id + sequence 幂等协议。Producer 启用 `enable.idempotence=true` 后,Producer ID 唯一,即使 retry 也不会重复写入。

### 7. 写入调优要点

| 参数                          | 调大后效果                          | 调小后效果                          |
|------------------------------|----------------------------------|----------------------------------|
| `batch.size`                | 吞吐提升,延迟增加                   | 延迟降低,吞吐下降                   |
| `linger.ms`                  | 攒批时间延长,吞吐提升                | 立即发送,延迟降低                   |
| `compression.type` (lz4)    | 减少网络 IO,延迟略增                 | 减少 CPU,网络 IO 增加                |
| `acks=all`                  | 强一致性,延迟增加                    | 弱一致性,延迟降低                    |
| `enable.idempotence=true`   | 防止重复,小幅延迟                 | 允许重复,延迟降低                     |
| `log_segment_size`          | 段切换次数少,索引大                  | 段切换频繁,索引小                    |

**经验值**:
- 高吞吐场景: `batch.size=1MB`, `linger.ms=20`, `compression.type=lz4`
- 低延迟场景: `batch.size=64KB`, `linger.ms=0`, `compression.type=none`
- 平衡场景: `batch.size=256KB`, `linger.ms=5`, `compression.type=lz4`

## 五、读取流程

读取流程同样基于协程,但因为有 cache 命中与磁盘读、云端拉取三种路径,稍显复杂。

### 1. 读取路径核心步骤

```text
1. Consumer 发送 FetchRequest 到 leader
2. broker 解析请求,得到 (topic, partition, fetch_offset, max_bytes)
3. 在该 partition 的 log 中定位 fetch_offset
   ├─ 先查 memory 中 (offset, position) 映射
   ├─ 未命中再查 *.index (稀疏索引做二分查找)
   └─ 定位到 base_offset <= fetch_offset <= max_offset
4. 从对应 segment 读取一定字节 (max_bytes)
   ├─ 优先 cache 命中 (clean LRU)
   ├─ 未命中 → Direct IO 读 NVMe
   └─ segment 已上传到云端 → 走 cloud_storage 异步下载
5. 校验 CRC,过滤事务隔离级别
6. 走 seastar::net::sendfile (零拷贝) 送网卡
7. 返回 FetchResponse
```

### 2. Cache 命中的三种情况

```text
命中 1: offset 在 cache dirty 区
  → 直接拿 dirty buffer,无需磁盘 IO
  → 通常是最近写入的数据

命中 2: offset 在 cache clean 区
  → 直接拿 clean buffer,无需磁盘 IO
  → 通常是最近被读过的数据

未命中: offset 不在 cache
  → 走 Direct IO 读 NVMe
  → 读完后置入 clean LRU
  → 通常是冷数据 / 大文件回放
```

### 3. 零拷贝

RedPanda 零拷贝使用 seastar 提供的 `make_data_source` + `sendfile`:

```cpp
seastar::future<result<fetch_response>> 
fetch(fetch_request req) {
    auto seg = co_await find_segment(req.offset);
    auto ds = co_await seg->make_data_source(req.offset, req.max_bytes);
    
    // 校验...
    co_await ds->verify_crc();
    
    // 直接 sendfile 到 socket
    co_await _connection->write_response_with_payload(std::move(ds));
    
    co_return fetch_response{...};
}
```

`make_data_source` 返回的 data_source 在真正写入 socket 时,通过 `splice()` 系统调用让数据 **从 NVMe 直接 DMA 到网卡**,全程不进入用户态 buffer。**这是单 Consumer 就能跑满 10Gbps 网卡的根本原因**。

### 4. 读取流程图

```text
┌──────────┐  1. Fetch     ┌──────────────┐
│ Consumer │ ──────────────▶│ kafka_api    │
└──────────┘                │ (协程)       │
                            └──────┬───────┘
                                   │ 2. find segment via index
                                   ▼
                            ┌──────────────┐
                            │ index binary │
                            │  search      │
                            └──────┬───────┘
                                   │ 3. data source
                                   ▼
                  ┌────────────────┼────────────────┐
                  │                │                │
            ┌─────▼──────┐  ┌──────▼───────┐ ┌──────▼───────┐
            │ cache      │  │ NVMe         │ │ cloud        │
            │ (clean LRU)│  │ (Direct IO)  │ │ (S3/MinIO)   │
            └─────┬──────┘  └──────┬───────┘ └──────┬───────┘
                  │                │                │
                  └────────────────┼────────────────┘
                                   ▼
                            ┌──────────────┐
                            │  CRC verify  │
                            └──────┬───────┘
                                   ▼
                            ┌──────────────┐
                            │  sendfile()  │
                            │  → NIC       │
                            └──────────────┘
```

### 5. 读取三种路径的延迟与吞吐

| 路径                     | 典型延迟 p99 | 典型吞吐      | 何时触发                              |
|-------------------------|-------------|-------------|-------------------------------------|
| **cache 命中**          | 0.1 ms      | 5 GB/s      | offset 在 clean LRU / dirty LRU      |
| **NVMe 读取 (Direct IO)**| 1~5 ms      | 3 GB/s      | cache 未命中,本地 segment 存在         |
| **云端下载 (首次)**      | 30~50 ms    | 200 MB/s    | segment 已在云端,未在本地             |
| **云端下载 (命中预读)** | 5~10 ms     | 1 GB/s      | 已被预读,本地 cache 命中              |

**经验值**:
- 单 Consumer 拉取,延迟 p99 < 5 ms (热数据)
- 单 Consumer 拉取,延迟 p99 30~50 ms (冷数据,首次拉取)
- 100 Consumer 并发拉取,broker 端聚合,单 broker 出口 5 GB/s 起步

### 6. 预读策略

云端冷数据首次拉取时,RedPanda 启动**预读策略**:

```text
read_ahead:
  1. Consumer 发起 FetchRequest, fetch_offset = 100M
  2. broker 定位 segment in cloud
  3. 启动云端下载 (segment 包含 offset 100M ~ 116M)
  4. 同时启动预读线程:
     ├─ 读取当前 segment 的相邻 segment
     ├─ 加入本地 cache LRU
     └─ 触发下一轮 read_ahead
  5. Consumer 拉到的响应数据先在 cache 中
  6. 下次 Consumer 拉取 offset 200M 时,可能已经在 cache
```

预读策略减少了"冷读延迟尖刺",但代价是下载带宽占用增加。可通过 `download_speed_throttle_bps` 限制。

### 7. 读取调优要点

| 参数                          | 调大后效果                          | 调小后效果                          |
|------------------------------|----------------------------------|----------------------------------|
| `fetch.max.bytes`            | 单次拉取多,网络利用率高              | 单次拉取少,延迟低                   |
| `fetch.min.bytes`            | broker 端等待更多数据,吞吐高         | broker 立即返回,延迟低             |
| `fetch.max.wait.ms`          | broker 等待时间,攒批多              | broker 立即返回                     |
| `max.partition.fetch.bytes`  | 单 partition 单次拉取多             | 单 partition 单次拉取少             |
| `isolation.level`            | 强事务一致性(读已提交)              | 弱一致性(可能读未提交)              |
| `auto.offset.reset`          | 默认行为(latest / earliest)        | 控制 consumer 启动时位置            |

**经验值**:
- 高吞吐场景: `fetch.max.bytes=50MB`, `fetch.min.bytes=1MB`, `fetch.max.wait.ms=500`
- 低延迟场景: `fetch.max.bytes=1MB`, `fetch.min.bytes=1`, `fetch.max.wait.ms=100`
- 平衡场景: `fetch.max.bytes=10MB`, `fetch.min.bytes=10KB`, `fetch.max.wait.ms=200`

### 8. 端到端读取时序

```text
T+0 ms      Consumer 发起 FetchRequest (fetch_offset = 100M, max_bytes = 1MB)
T+0.5 ms    broker 接收,kafka_api 协程解析
T+1 ms      binary search *.index,定位到 segment 100M-116M
T+1.5 ms    segment 在 cache dirty? 
              ├─ 是 (>99% 情况,刚写入) → 直接从 cache 返回
              ├─ 否,在 cache clean? → 直接返回
              └─ 否,segment 在哪里?
                   ├─ 本地 NVMe → spawn Direct IO 协程
                   └─ 云端 → spawn cloud_storage 协程
T+2 ms      [本地路径] Direct IO 完成 16 KB 读取
              [云端路径] 启动 S3 GET,等待 30~50 ms
T+2.5 ms    [本地路径] cache 命中验证,生成 data_source
              [云端路径] 持续等待 multipart download
T+3 ms      [本地路径] splice 到 socket,Client 收到第一字节
              [云端路径] multipart downloading,延迟中
T+50 ms     [云端路径] multipart download 完成,本地 cache 写入
              [云端路径] 同一 batch 后续请求命中 cache,延迟 < 5 ms
```

## 六、Tiered Storage(核心特色)

Tiered Storage 是 RedPanda 最有差异化的能力。它把数据透明地分层:

- **热数据(近实时)** → 本地 NVMe
- **冷数据(历史)** → 对象存储 (S3 / MinIO / GCS / Azure Blob)

对客户端而言,这只是一个**有更多保留期**的 Kafka Topic,完全透明。

### 1. 概念:本地 + 云端

```text
┌─────────────────────────────────────────────────────────────┐
│                    Topic: orders                              │
├─────────────────────────────────────────────────────────────┤
│  partition 0:                                                │
│  offset 0 ─────────▶ offset 1M     本地 NVMe                  │
│  offset 1M ────────▶ offset 100M   本地 NVMe + 云端已上传      │
│  offset 100M ──────▶ offset 1B    仅云端                       │
│  ↑                          ↑                                  │
│  LSO (Log Start)            LEO (Log End)                     │
└─────────────────────────────────────────────────────────────┘
```

设想:一个 Topic 配置本地保留 7 天、云端保留 1 年。每天 100GB 数据,本地占用 700GB,云端占用 36TB——**云端每 GB 月成本是 NVMe 的 1/10 ~ 1/20**,一年下来存储成本下降一个数量级。

### 2. 支持的云存储

RedPanda 支持的云存储后端:

| 厂商                  | 状态     | 备注                                |
|----------------------|---------|-------------------------------------|
| **AWS S3**           | 完全支持 | 默认推荐,所有高级特性都跑通          |
| **MinIO**            | 完全支持 | 自建 S3 兼容,适合私有云              |
| **Google Cloud Storage** | 完全支持 | 通过 S3 兼容 API 接入                |
| **Azure Blob Storage**  | 完全支持 | Native API,非 S3 兼容                |
| **Wasabi**           | 完全支持 | 廉价 S3 兼容                          |
| **任何 S3 兼容**     | 通常支持 | 注意 list_objects_v2 实现差异        |

### 3. 配置示例

最小配置:

### 4. 数据上传与下载策略

**上传策略**——housekeeping 单线程扫描:

```text
housekeeping loop:
  for each partition in this broker:
    if partition.has_closed_segments_beyond_local_retention:
      for each closed_segment:
        if not in cloud:
          schedule upload(segment)
        if upload_succeeded:
          mark "in cloud"
          delete from local
```

特点:

- **段级别**:整段上传,不会"上传到一半"
- **幂等**:segment uuid 唯一,重传不会重复
- **批量**:多个 segment 并行上传,数量由 `cloud_storage_max_concurrent_uploads` 控制
- **限速**:通过拥塞控制 (PID controller) 自适应限流,不影响生产

**下载策略**——读时透明拉取:

```text
fetch(partition, offset, max_bytes):
  seg = find_segment(offset)
  if seg.is_local:
    serve from cache or NVMe
  elif seg.is_remote:
    schedule async download(seg)
    serve from local cache (after download)
  else:
    serve from cloud (direct stream, no local cache)
```

特点:

- **预读**:读取时自动预读相邻 segment 到本地 cache
- **限速**:可配置 `download_speed_throttle_bps`,不影响热数据读取
- **缓存淘汰**:本地 cache 写入受 LRU 限制,不会无限堆积

## 七、Compacted Topics

RedPanda 的 Compaction 实现与 Kafka 语义**完全一致**——同样基于 `(key, null)` 的 tombstone 标记,同样按 `(key, offset)` 合并,同样是后台 thread 异步执行。**唯一差异是底层实现用 C++**。

### 1. 启用 compaction

```yaml
# topic 级别
redpanda:
  topic_overrides:
    orders:
      cleanup.policy: compact
      min.cleanable.dirty.ratio: 0.1
      segment.ms: 3600000
```

或者:

```bash
rpk topic alter orders --set-config cleanup.policy=compact
```

### 2. compaction 流程

```text
compact partition:
  1. 获取该 partition 的所有 segment
  2. 从最旧的 segment 开始
  3. 扫描 segment,构建 (key -> latest offset) 映射
  4. 生成 new segment:只保留每个 key 的最后一条
  5. 原子替换 segment 文件
  6. 继续下一个 segment
  7. 更新 compaction_index
```

### 3. compaction 与分层存储的关系

- **分层与 compaction 不冲突**:云端存的是"compacted 后的 segment"
- **本地删除 + 云端保留**:本地清理掉被 compact 掉的旧值,云端保留最新值
- **重启恢复**:集群启动时,云端下载 → 应用 compact → 重新生成 segment

### 4. compaction 注意点

- **首次 compaction 慢**:大型 topic 首次 compaction 可能几十分钟
- **不要在高峰启用**:compact 期间 IO 较高,可能在 SLA 敏感场景出错
- **tombstone 保留**:key 删除后保留 24h tombstone,避免下游误读

## 十、分层存储的性能与权衡

### 1. 性能对比

| 场景                | 延迟 p50 | 延迟 p99 | 吞吐(MB/s)   |
|--------------------|---------|---------|--------------|
| **本地 cache 命中** | 0.1 ms  | 1 ms    | 5000+        |
| **本地 NVMe 读**   | 1 ms    | 5 ms    | 3000         |
| **云端 S3 冷读**   | 30 ms   | 200 ms  | 200          |
| **云端 GCS 冷读**  | 40 ms   | 250 ms  | 180          |
| **云端 Azure 冷读**| 50 ms   | 300 ms  | 150          |

注意这些都是**首次拉取**的延迟,如果数据已被预读到 cache,延迟降回本地水平。

### 2. 冷数据延迟略高(几十 ms)

冷数据延迟通常几十 ms,原因是:

- **S3 内部延迟**:跨可用区 RTT 通常 10~30 ms
- **multipart 下载**:首次下载要走 PUT / GET 握手
- **解密 / 解压**:S3 端加密 + gzip 压缩,客户端需解密解压

建议:在 Consumer 端把 `fetch.max.wait.ms` 调到 1000+ ms,**用 batch 摊薄冷数据开销**。

### 3. 本地热数据低延迟

本地热数据延迟可优于 Kafka,原因:

- **C++ 协程**:无 JVM 停顿
- **自管 cache**:无 OS Page Cache 抖动
- **Direct IO**:无 OS 缓存双层开销

实际生产中,RedPanda 4 KB 写延迟 p99 通常在 5~10 ms,极寒场景下 1~2 ms。

### 4. 整体无限保留

Tiered Storage 让"无限保留"成为可能:

- **云端无限容量**:S3 单 bucket 可以放 PB 级数据
- **几乎无运维**:不需要本地扩容
- **cost 极低**:S3 Standard-IA $0.0125/GB·月,远低于本地盘

代价:

- **冷读延迟高**:几十 ms 是常态
- **依赖外部 SLA**:S3 偶尔会有 99.99% SLA 以下的小故障
- **合规性**:数据出机房,部分行业需要审计 + 加密

### 5. 适用场景

| 场景                        | 是否适合分层           |
|---------------------------|----------------------|
| **订单 / 交易 历史**       | 强烈推荐,1 年可查,本地 7 天     |
| **用户行为日志 (clickstream)** | 强烈推荐,审计 + 长期分析  |
| **监控 / metrics**         | 推荐,本地 1 天 + 云端 30 天      |
| **金融交易流水**           | 合规允许时推荐,本地 30 天 + 云端 7 年 |
| **实时信号 / 行情**        | 不推荐,全本地低延迟               |
| **IoT 遥测**               | 强烈推荐,本地 3 天 + 云端 90 天   |

## 十一、索引与恢复

### 1. manifest 文件

每个 partition 在云端有一个 `manifest.json`:

```json
{
  "version": 1,
  "namespace": "kafka",
  "topic": "orders",
  "partition": 0,
  "revision": 173456789,
  "segments": {
    "00000000000000000000-uuid": {
      "base_offset": 0,
      "size_bytes": 134217728,
      "is_compacted": false,
      "sname_format": 1,
      "segment_term": 1,
      "archiver_term": 1,
      "meta": "00000000000000000000-uuid"
    },
    ...
  }
}
```

manifest 用途:

- **跨节点同步**:新加入的节点按 manifest 找自己需要哪些 segment
- **跨集群复制**:Shadow Linking 用 manifest 同步
- **崩溃恢复**:启动时按 manifest 校验本地 segment 是否完整

### 2. 数据恢复流程

```text
RedPanda 启动 / 新节点加入:
  1. 读取本地 manifest (last synced 位置)
  2. 读取云端 manifest (最新状态)
  3. 计算 diff:
     ├─ 云端有,本地无 → 下载
     ├─ 都有,本地过期 → 下载 + 校验
     └─ 都有,本地与云端一致 → 跳过
  4. 下载校验:
     ├─ 校验 sha256
     ├─ 校验 sname_format
     └─ 通过后写入 cache / 触发 fsync
  5. 标记 segment "downloaded"
  6. 同步追上 leader LEO
```

### 3. 故障恢复

| 故障              | 恢复方式                                     |
|------------------|---------------------------------------------|
| **单节点磁盘损坏** | 新节点从云端拉取 manifest,恢复数据            |
| **整个集群丢失**  | 启动新集群,所有数据从云端拉取                 |
| **人为误删数据**  | manifest 不变,可从云端 manifest 还原          |
| **云端数据损坏**  | 通过 cloud_storage 校验 + manifest 的 sha256   |
| **云端账户丢失**  | 数据无法恢复,需异地多 bucket 副本保护        |

### 3. Shadow Linking 实战

Shadow Linking 是 RedPanda 商业版提供的能力,**把源集群的 topic 实时镜像到目标集群**。它本质上是基于 Tiered Storage 的跨集群 CDC。

```yaml
# 目标集群 redpanda.yaml
redpanda:
  shadow_linking:
    - name: prod-to-dr
      source: 
        bootstrap_servers:
          - redpanda-prod:9092
      # 同步策略
      sync_mode: all_topics
      # 同步保留
      topic_properties:
        retention.ms: 31536000
      # 镜像
      mirror_topics:
        - source_topic: orders
          destination_topic: orders_dr
        - source_topic: payments
          destination_topic: payments_dr
      # 限速
      max_bytes_per_second: 100000000
```

工作流程:

```text
源集群                   →  云端 S3 (共享)            →  目标集群
每条消息 raft commit ──▶ 部分 segment 上传云端 ──▶  从云端拉取
                                                          │
                                                          ▼
                                          在目标集群生成临时 topic
                                                          │
                                                          ▼
                                          promote → 正式 topic
```

Shadow Linking 优势:

- **RPO 极低**:秒级延迟
- **不影响源**:源集群无需启用 client
- **跨 region**:目标集群可以异地
- **灾备 + 读副本**:既能灾备,又能做读副本

### 4. 备份策略对比

| 方式                  | RPO  | RTO  | 成本 | 复杂度 |
|----------------------|------|------|------|-------|
| **文件级备份**       | 小时 | 小时 | 低   | 低     |
| **S3 跨区复制**      | 秒   | 分钟 | 中   | 中     |
| **Mirror Maker 2**   | 秒   | 分钟 | 中   | 中     |
| **RedPanda Shadow Linking** | 秒 | 分钟 | 中 | 中   |
| **集群内 replicas**  | 0    | 0    | 高   | 低     |

## 十三、实战案例

### 1. 案例 A:电商订单,配置 Tiered Storage 到 S3

**背景**:某电商订单 Topic,日均 50 GB,需保留 1 年。

**配置**:

```yaml
# redpanda.yaml
redpanda:
  cloud_storage:
    enabled: true
    bucket: redpanda-orders-prod
    region: ap-northeast-1
    access_key: ${AWS_ACCESS_KEY_ID}
    secret_key: ${AWS_SECRET_ACCESS_KEY}
    retention_seconds: 31536000       # 1 年
    retention_bytes: 1099511627776    # 1 TB
```

```bash
# 启用 orders topic 归档
rpk topic alter orders \
  --set-config redpanda.remote.write=true \
  --set-config redpanda.remote.read=true

# 启用 payment-records topic
rpk topic alter payment-records \
  --set-config redpanda.remote.write=true \
  --set-config redpanda.remote.read=true
```

**监控**:

```yaml
# Prometheus
rpk:
  metrics:
    - cloud_storage_segments: number of segments in cloud
    - cloud_storage_uploads: number of upload operations
    - cloud_storage_downloads: number of download operations
    - cloud_storage_bytes: bytes transferred
```

**效果**:

| 指标               | 改造前    | 改造后     |
|-------------------|----------|----------|
| 本地数据占用        | 18 TB    | 1.3 TB    |
| 1 年数据保留成本   | $1800/月 | $200/月   |
| 热数据延迟 p99     | 8 ms     | 6 ms      |
| 冷数据延迟 p99     | 8 ms     | 35 ms     |
| 查询历史订单延迟    | 8 ms     | 35 ms     |

### 2. 案例 B:金融交易,保留 1 年但磁盘占用小

**背景**:某券商交易流水 Topic,日均 200 GB,合规要求保留 7 年。

**挑战**:本地盘没法放 7 年,必须分层。

**方案**:

```yaml
redpanda:
  cloud_storage:
    enabled: true
    bucket: fintech-trades-prod
    region: us-east-1
    access_key: ${AWS_ACCESS_KEY}
    secret_key: ${AWS_SECRET_KEY}
    retention_seconds: 220752000       # 7 年
    retention_bytes: 10995116277760    # 10 TB
```

**合规审计**:

```bash
# 完整体 7 年数据,通过 Manifest 校验
rpk topic describe trades --print-manifests

# 导出冷数据(审计需求)
rpk topic export trades --from 2024-01-01 --to 2024-01-31 \
  --output /audit/trades-2024-01.json
```

**效果**:

- 1 年本地盘:73 TB → 5 TB
- 7 年云端:$1640/月 (S3 Standard-IA)
- 审计拉取:整年数据 30 秒内完成

### 3. 案例 C:灾备到另一区域

**背景**:杭州-上海两地三中心部署,主集群故障时切到灾备。

**配置**:

```yaml
# 灾备集群 redpanda.yaml
redpanda:
  cloud_storage:
    enabled: true
    bucket: redpanda-shanghai-2026
    region: cn-north-1
    access_key: ${S3_AK}
    secret_key: ${S3_SK}
  shadow_linking:
    - name: hz-to-sh
      source:
        bootstrap_servers:
          - redpanda-hz.example.com:9092
      sync_mode: all_topics
      topic_properties:
        retention.ms: 2592000000  # 30 天
      mirror_topics:
        - source_topic: orders
          destination_topic: orders
        - source_topic: inventory
          destination_topic: inventory
```

**切换流程**:

```bash
# 1. 主集群挂了
# 2. 把灾备集群的 __consumer_offsets 指向业务 Consumer
# 3. Consumer 重新拉取,从头消费关键 topic
# 4. 灾备集群继续使用,直到主集群恢复
```

**RPO**:30 秒 ~ 1 分钟

**RTO**:5 分钟 (Consumer 重新订阅 + cache 预热)

## 十四、核心要点速记

| 主题                          | 要点                                                             |
|------------------------------|------------------------------------------------------------------|
| **存储架构**                  | 三层:Cache (自管) + Local Storage (NVMe) + Tiered Storage (云端)  |
| **C++ 协程**                  | seastar 协程,无 JVM,无 GC 抖动,单核 GB/s 吞吐                       |
| **Direct IO**                | 跳过 OS Page Cache,避免双层缓存;可改为 buffered IO                  |
| **自管理 Cache**              | dirty / clean LRU, dirty_ratio 触发 writeback                      |
| **Segment 文件**             | `*.log` + `*.base_offset` + `*.size_bytes` + `*.index` + `*.manifest.json` |
| **稀疏索引**                  | 16 KB 一条索引 (varint 编码),二分查找                               |
| **写入流程**                  | Produce → kafka_api 协程 → raft replicate → cache dirty → async writeback → NVMe |
| **读取流程**                  | Fetch → index 定位 → cache / NVMe 命中 → sendfile 零拷贝 → NIC        |
| **Tiered Storage**            | 开源版自带,本地存近期 + 云端存历史,S3 / MinIO / GCS / Azure Blob 都支持 |
| **Tiered Storage 配置**      | `cloud_storage.enabled=true` + bucket + region + access_key + secret_key |
| **upload 策略**               | housekeeping 后台扫描,异步上传,manifest 幂等                            |
| **download 策略**            | 透明访问,首次预读,本地 cache 命中后回退到本地延迟                         |
| **成本节约**                  | 本地 7 天 + 云端 1 年,年节省 5 位数美元;冷数据延迟 30~50 ms                 |
| **compaction**               | 与 Kafka 语义一致,后台异步执行,云端存的是 compacted 后的 segment            |
| **retention**                | 基于时间 / 大小 / compact,组合策略,优先级 动态 > topic > cluster          |
| **manifest**                 | 记录 segment 在云端的位置 + 校验信息,跨集群恢复 + Shadow Linking 用          |
| **备份方式**                  | 文件级 + S3 跨区复制 + Shadow Linking,各有利弊                          |
| **Shadow Linking**           | 商业版,跨集群 CDC,实时镜像,异地灾备 + 读副本                              |
| **生产参数**                  | `log_segment_size=128MB` + `index_interval_bytes=16KB` + `fsync_per_msg=false` |
| **冷数据延迟**                | 几十 ms,首次拉取后进 cache 降回本地水平                                  |
| **热数据延迟**                | p99 1~5 ms,优于 Kafka(因无 GC + Direct IO)                            |
| **核心优势**                  | 无限保留 + 成本降一个数量级 + Kafka 协议 100% 兼容 + 单二进制部署            |

## 附录:RedPanda vs Kafka 存储对比

| 维度                  | Kafka                                | RedPanda                                          |
|----------------------|--------------------------------------|---------------------------------------------------|
| **实现语言**          | Scala + JVM                          | C++20 + seastar                                    |
| **进程模型**          | 线程池 + 异步混合                     | 协程,share-nothing                                |
| **Page Cache**       | OS 自主管理                           | 用户态自主管理                                       |
| **IO 模式**          | buffered (依赖 OS)                   | Direct IO(默认) + buffered(可选)                    |
| **GC 影响**          | 存在 (Full GC / G1)                   | 无 GC                                              |
| **延迟 p99**         | 10~30 ms (JVM 抖动)                  | 1~5 ms (稳定)                                     |
| **单核吞吐**         | 100 MB/s                             | 1 GB/s                                            |
| **分层存储**          | 商业版 / 实验                          | **开源版默认自带**                                   |
| **冷数据存储**        | 全部本地盘                            | 几乎全在云端                                         |
| **运维复杂度**        | 中 (JVM 调优)                        | 低 (单二进制,默认配置可用)                            |
| **Kubernetes 友好** | 中 (StatefulSet + PVC)                | 高 (单容器,云原生)                                   |
| **生态兼容**          | 100% Kafka                           | 100% Kafka(含 Connect / Streams)                   |
| **硬件成本**          | HDD 可用                              | 推荐 NVMe,但可降级到 HDD                            |
| **许可证**            | Apache 2.0 (Confluent 修改)         | BSL (商业源码) + 开源可读                            |
| **小集群(3 节点)**   | 100 MB/s                             | 1 GB/s                                            |
| **故障恢复**          | 从 ISR 拉取                           | 从 ISR + 云端(分层存储)拉取                          |

**结论**:RedPanda 在保持 Kafka 协议 100% 兼容的前提下,凭借 C++ + Direct IO + 自管 Cache + Tiered Storage,实现了**数量级**的延迟降低和成本下降。对于**新上 Kafka** 的项目,RedPanda 几乎一定是更优选择;对于**已有 Kafka** 的项目,可以**渐进迁移**——保留已有客户端,只替换 broker 即可。
