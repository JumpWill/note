## 一、读写分离概述

### 1.1 什么是读写分离

**读写分离 (Read-Write Splitting)** 是将数据库的**写操作**与**读操作**分发到不同数据库节点上的架构模式:

- **写操作 (INSERT/UPDATE/DELETE/DDL)** → 主库 (Primary)
- **读操作 (SELECT)** → 从库 (Secondary/Replica)

```text
                ┌─────────────────────────┐
                │      Application         │
                │                          │
                │  ┌──────────┐  ┌────────┐│
                │  │ 写连接池 │  │读连接池││
                │  └────┬─────┘  └───┬────┘│
                └───────┼────────────┼────┘
                        │            │
                ┌───────▼────┐  ┌────▼─────┐
                │  Primary   │  │ Replica-1│
                │  (主库)    │  │ (从库1)  │
                │  INSERT/   │  │ SELECT   │
                │  UPDATE    │  │          │
                └──────┬─────┘  └────┬─────┘
                       │   复制 binlog │
                       └──────────────┘
                ┌───────┴────┐
                │ Replica-2  │
                │  (从库2)   │
                │  SELECT    │
                └────────────┘
```

### 1.2 为什么需要读写分离

| 痛点 | 读写分离如何解决 |
|------|------------------|
| 单机 IO 压力大 | 读请求分散到多个从库,降低主库负载 |
| 读多写少(如 10:1) | 主库专心写,从库并行扩展读能力 |
| 单机带宽被打满 | 多从库分别承担读流量 |
| 主库 CPU 持续高位 | 复杂报表、分析查询从从库走 |
| 备份影响主库性能 | 备份从从库做,不影响主库 |

### 1.3 读写分离 vs 主从复制

```text
主从复制 (Replication)  是 数据库 层面的机制
   ↓ 提供基础能力
读写分离 (R/W Split)   是 应用/中间件 层面的架构模式
   ↓ 解决流量分发
高可用 (HA)             是 故障切换 层面的方案
   ↓ 解决故障恢复
```

- **主从复制**: 必须先有,提供数据副本
- **读写分离**: 建立在复制之上,把流量按类型分发
- **高可用**: 在复制 + 读写分离基础上,提供故障切换

### 1.4 读写分离与一致性

⚠️ **核心矛盾**: 主从复制是异步的,主从延迟会导致**读已写入的数据查不到**。

```sql
-- 主库写入
INSERT INTO orders (id, status) VALUES (1, 'paid');
-- 主库返回 Client OK

-- 立刻从从库查询
SELECT status FROM orders WHERE id = 1;
-- 由于复制延迟,从库可能还没收到这条 binlog
-- 返回: NULL  ← 不一致!
```

**业务影响**: 用户刚下单,刷新页面看不到订单。

### 1.5 读写分离适用场景

| 场景 | 适合度 | 说明 |
|------|--------|------|
| 读 >> 写 (电商商品页、新闻、博客) | ⭐⭐⭐⭐⭐ | 收益最大 |
| 报表/分析/ETL 走从库 | ⭐⭐⭐⭐⭐ | 不影响业务 |
| 强一致性读 (支付、库存) | ⭐⭐ | 需走主库,读写分离收益小 |
| 海量写 (万级 TPS) | ⭐ | 同步复制延迟已是大问题 |

## 三、方式 1:应用代码层

### 3.1 Spring Boot + 多数据源

```java
// application.yml
spring:
  datasource:
    master:
      url: jdbc:mysql://10.0.0.11:3306/mydb
      username: app
      password: xxx
      driver-class-name: com.mysql.cj.jdbc.Driver
    slave:
      url: jdbc:mysql://10.0.0.12:3306/mydb
      username: app
      password: xxx
```

```java
// 数据源配置
@Configuration
public class DataSourceConfig {

    @Bean("masterDataSource")
    @ConfigurationProperties("spring.datasource.master")
    public DataSource masterDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean("slaveDataSource")
    @ConfigurationProperties("spring.datasource.slave")
    public DataSource slaveDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    public DataSource routingDataSource(
            @Qualifier("masterDataSource") DataSource master,
            @Qualifier("slaveDataSource") DataSource slave) {

        Map<Object, Object> targetDataSources = new HashMap<>();
        targetDataSources.put("master", master);
        targetDataSources.put("slave", slave);

        AbstractRoutingDataSource routing = new AbstractRoutingDataSource() {
            @Override
            protected Object determineCurrentLookupKey() {
                return TransactionContext.isReadOnly() ? "slave" : "master";
            }
        };
        routing.setTargetDataSources(targetDataSources);
        routing.setDefaultTargetDataSource(master);
        return routing;
    }
}
```

### 3.2 优缺点

**优点**:
- 零组件依赖
- 完全可控的路由逻辑
- 性能最优 (无中间层)

**缺点**:
- 业务侵入: 强制读主场景需业务自己判断
- 主从切换: 应用无感知,需配合 VIP 或 DNS
- 散落: 读写逻辑分散在 DAO 层
- 难维护: 切换数据源后配置散乱

**适用**: 小型应用、读流量小、对一致性要求不严

## 四、方式 2:ShardingSphere-JDBC (推荐)

### 4.1 原理

**ShardingSphere-JDBC** 是 Apache ShardingSphere 的客户端 jar,通过 JDBC 拦截器实现读写分离:

```text
   Application
        ↓
   ┌────────────────────────────────┐
   │  ShardingSphere-JDBC           │
   │  ┌──────────────────────────┐  │
   │  │ SQL Parser → Rewrite      │  │
   │  │       ↓                   │  │
   │  │ Router (按 SELECT 路由)   │  │
   │  │       ↓                   │  │
   │  │ Executor → Master/Replica │  │
   │  └──────────────────────────┘  │
   └────────────────────────────────┘
        ↓                  ↓
   Master DataSource   Replica DataSource(s)
```

**核心特性**:
- 业务代码**完全无感知**
- 自动识别 SELECT 走从库,其他走主库
- 支持事务强制走主
- 支持 Hint 强制走主(`@HintManager`)
- 与 MyBatis/Hibernate/JPA 无缝集成

### 4.2 Maven 依赖

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.0</version>
</dependency>
```

### 4.3 Spring Boot 配置(application.yml)

```yaml
spring:
  shardingsphere:
    datasource:
      names: master,slave0,slave1

      master:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://10.0.0.11:3306/mydb
        username: app
        password: xxx
        connection-timeout: 30000
        maximum-pool-size: 20

      slave0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://10.0.0.12:3306/mydb
        username: app
        password: xxx
        maximum-pool-size: 50

      slave1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://10.0.0.13:3306/mydb
        username: app
        password: xxx
        maximum-pool-size: 50

    rules:
      readwrite-splitting:
        data-sources:
          mydb:
            static-strategy:
              # 写主库
              write-data-source-name: master
              # 读负载均衡到从库
              read-data-source-names: slave0,slave1
            load-balancer-name: round-robin
        load-balancers:
          round-robin:
            type: ROUND_ROBIN     # 轮询
          # weight:
          #   type: WEIGHT
          #   props:
          #     slave0: 5         # 权重
          #     slave1: 5

    props:
      sql-show: true              # 调试时打印 SQL 路由
```

### 4.4 Hint 强制走主

```java
// 场景: 订单状态变更后立即查询,需强制走主
HintManager hintManager = HintManager.getInstance();
hintManager.setWriteRouteOnly();      // 强制走主库
try {
    // 写
    ordersMapper.updateStatus(1, "paid");
    // 立刻读 (强制主库)
    Order order = ordersMapper.findById(1);
} finally {
    hintManager.close();
}
```

```java
// MyBatis 注解方式
@Hint("writeRouteOnly")
public Order findByIdAfterUpdate(@Param("id") Long id);
```

### 4.5 完整 Spring Boot 示例

```java
@Service
public class OrderService {

    @Autowired
    private OrdersMapper ordersMapper;

    // 读操作,自动路由到从库
    public Order getOrder(Long id) {
        return ordersMapper.findById(id);
    }

    // 写操作,自动路由到主库
    @Transactional
    public void createOrder(Order order) {
        ordersMapper.insert(order);
    }

    // 写后读: 强制主库
    public Order getOrderAfterWrite(Long id) {
        HintManager hintManager = HintManager.getInstance();
        hintManager.setWriteRouteOnly();
        try {
            return ordersMapper.findById(id);
        } finally {
            hintManager.close();
        }
    }
}
```

### 4.6 优缺点

**优点**:
- 与应用代码完全解耦,只改配置不改代码
- 性能损耗极小 (JDBC 层拦截,无网络跳转)
- 支持复杂路由策略 (轮询、权重、自定义)
- 与分库分表无缝集成

**缺点**:
- 仅 Java 生态
- 同一应用多数据源时,需注意事务
- 调试需开启 `sql-show`

## 五、方式 3:ProxySQL (中间件方案,业界标准)

### 5.1 ProxySQL 概述

**ProxySQL** 是用 C++ 编写的高性能 MySQL 代理,功能:

- **读写分离路由** (按 SQL 自动判断)
- **连接池** (后端连接复用,降低后端压力)
- **查询缓存** (结果缓存)
- **查询重写** (SQL 改写)
- **后端节点动态管理** (上下线、权重调整)
- **流量镜像** (生产 SQL 复制到测试环境)
- **高可用** (结合 MHA、Orchestrator 自动感知)

```text
   Client App
       ↓
   ┌──────────────────────┐
   │  ProxySQL (6033)     │  ← 应用只需连这个端口
   │  - 解析 SQL          │
   │  - 判断读写          │
   │  - 路由到对应后端    │
   └─────────┬────────────┘
             │
       ┌─────┴─────────────┐
       ↓                   ↓
   hostgroup 0          hostgroup 1
   (写/强一致)          (读)
       ↓                   ↓
   ┌────────┐         ┌────────┐
   │Master  │         │Slave-1 │
   │10.0.11 │         │10.0.12 │
   └────────┘         └────────┘
                          ↓
                     ┌────────┐
                     │Slave-2 │
                     │10.0.13 │
                     └────────┘
```

### 5.2 安装

```bash
# Ubuntu/Debian
wget https://repo.proxysql.com/ProxySQL/proxysql_2.6.2-ubuntu22_amd64.deb
dpkg -i proxysql_2.6.2-ubuntu22_amd64.deb
systemctl start proxysql

# 或 Docker
docker run -d --name proxysql \
  -p 6033:6033 -p 6032:6032 \
  -v /path/to/proxysql.cnf:/etc/proxysql.cnf \
  proxysql/proxysql
```

### 5.3 核心概念:三层配置

```text
┌─────────────────────────────────────────────────┐
│  Layer 1: RUNTIME (运行时,内存中)               │
│  - 应用实际生效的配置                              │
│  - 可通过 SQL 修改                                │
│  - 持久化到 DISK                                  │
├─────────────────────────────────────────────────┤
│  Layer 2: MEMORY                                  │
│  - 从 DISK 加载到内存,待 RUNTIME 应用              │
│  - 修改 MEMORY 后需 LOAD TO RUNTIME               │
├─────────────────────────────────────────────────┤
│  Layer 3: DISK (磁盘 /etc/proxysql.cnf)          │
│  - 持久化配置                                     │
│  - 启动时加载到 MEMORY                             │
│  - 修改后需 SAVE TO DISK                          │
└─────────────────────────────────────────────────┘
```

### 5.4 关键表结构

```sql
-- mysql_servers: 后端 MySQL 节点
SELECT * FROM mysql_servers;
-- hostgroup_id, hostname, port, weight, max_connections, comment

-- mysql_replication_hostgroups: 主从关系定义
```

### 5.5 完整实战配置

#### 步骤 1:连接 ProxySQL 管理端口

```bash
mysql -u admin -padmin -h 127.0.0.1 -P 6032 --prompt='ProxySQL Admin> '
```

#### 步骤 2:配置后端 MySQL 节点

```sql
-- 后端节点
INSERT INTO mysql_servers (hostgroup_id, hostname, port, weight, max_connections, comment)
VALUES
  (0, '10.0.0.11', 3306, 1, 1000, 'Master'),
  (1, '10.0.0.12', 3306, 1, 2000, 'Slave-1'),
  (1, '10.0.0.13', 3306, 1, 2000, 'Slave-2');

-- 定义主从 hostgroup (read_only=0 是主)
INSERT INTO mysql_replication_hostgroups (writer_hostgroup, reader_hostgroup, comment)
VALUES (0, 1, 'Master-Slave Cluster');

LOAD MYSQL SERVERS TO RUNTIME;
SAVE MYSQL SERVERS TO DISK;
```

#### 步骤 3:配置应用账号

```sql
-- 应用账号
INSERT INTO mysql_users (username, password, default_hostgroup, max_connections)
VALUES ('app_user', 'app_password', 0, 200);

LOAD MYSQL USERS TO RUNTIME;
SAVE MYSQL USERS TO DISK;
```

#### 步骤 4:配置读写路由规则

```sql
-- 自动根据 read_only 识别主从
-- 无需手动规则, ProxySQL 自动根据 mysql_replication_hostgroups 路由

-- 但仍可加自定义规则
INSERT INTO mysql_query_rules (rule_id, active, match_digest, destination_hostgroup, apply)
VALUES
  -- 强制某些 SELECT 走主 (强一致)
  (10, 1, '^SELECT .* FOR UPDATE$', 0, 1),
  (11, 1, '^SELECT .* LOCK IN SHARE MODE$', 0, 1),
  -- 自定义: 用户表的读强制主库
  (20, 1, '^SELECT .* FROM users WHERE', 0, 1),
  -- 大查询路由到指定从库 (后端 hint 方式)
  (30, 1, '^SELECT /\\*\\+ MYSQL_HINT=large \\*/', 1, 1);

LOAD MYSQL QUERY RULES TO RUNTIME;
SAVE MYSQL QUERY RULES TO DISK;
```

## 六、方式 4:MySQL Router (官方)

### 6.1 概述

**MySQL Router** 是 MySQL 官方提供的轻量级中间件,MySQL 8.0+ 默认搭配 InnoDB Cluster:

- 自动路由读写请求
- 自动检测主从切换
- 与 MGR 完美集成
- 高可用(Restarter 自动重启)

### 6.2 安装

```bash
# Ubuntu
apt install mysql-router

# 或二进制
wget https://dev.mysql.com/get/Downloads/MySQL-Router/mysql-router-8.0.32-linux-glibc2.28-x86_64.tar.xz
tar xf mysql-router-8.0.32-linux-glibc2.28-x86_64.tar.xz -C /opt
ln -s /opt/mysql-router-8.0.32-linux-glibc2.28-x86_64 /opt/mysql-router
```

### 6.3 配置(基于 MGR)

```ini
# /etc/mysqlrouter/mysqlrouter.conf

[DEFAULT]
logging_folder = /var/log/mysqlrouter
runtime_folder = /var/run/mysqlrouter
data_folder = /var/lib/mysqlrouter
config_folder = /etc/mysqlrouter

[logger]
level = INFO

# 主库路由 (写)
[routing:primary_rw]
bind_address = 0.0.0.0
bind_port = 6446
destinations = 10.0.0.11:3306,10.0.0.12:3306,10.0.0.13:3306
mode = read-write
protocol = classic

# 从库路由 (读)
[routing:replica_ro]
bind_address = 0.0.0.0
bind_port = 6447
destinations = 10.0.0.11:3306,10.0.0.12:3306,10.0.0.13:3306
mode = read-only
protocol = classic
```

### 6.5 主从切换自动感知

```text
MGR PRIMARY 故障
   ↓ (XCOM 检测)

   ↓
```

**应用完全无感知** — 这就是 MySQL Router 与 MGR 结合的最大优势。

### 6.6 优缺点

- 官方原生,与 MGR 集成最完美
- 自动感知拓扑变化
- 资源占用低 (Java/C++ 二进制)
- 配置简单

**缺点**:
- 仅支持 MySQL 协议
- 高级特性(查询缓存、限流)需 ProxySQL
- 单进程,高可用需配合 Keepalived

## 八、延迟问题与一致性方案

### 8.1 主从延迟的根本原因

```text
主库 binlog → 主库 binlog dump → 网络 → 从库 I/O → 从库 relay log → 从库 SQL 回放 → 从库应用
```

每一环节都有延迟,总和就是 `Seconds_Behind_Master`。

### 8.2 业务侧一致性方案

#### 方案 1:强制读主库 (Write-After-Read Consistency)

```java
// 写后立刻读 → 强制主库
@Transactional
public Order updateAndQuery(Long orderId, String newStatus) {
    ordersMapper.updateStatus(orderId, newStatus);   // 写

    // 强制从主库读 (避免延迟读)
    HintManager hint = HintManager.getInstance();
    hint.setWriteRouteOnly();
    try {
        return ordersMapper.findById(orderId);          // 读主库
    } finally {
        hint.close();
    }
}
```

**适用**: 写后立即读自己刚写的数据

#### 方案 2:Session 一致性 (Session Consistency)

```java
// 用户会话期间所有读都走主库
HttpSession session = request.getSession();
session.setAttribute("forceMaster", true);

// 拦截器判断
if (session.getAttribute("forceMaster") != null) {
    HintManager hint = HintManager.getInstance();
    hint.setWriteRouteOnly();
    // ... 该请求所有读都走主
}
```

**适用**: 用户操作连贯性要求高(付款流程)

#### 方案 3:准实时一致性 (Read-Your-Writes via GTID)

```sql
-- ShardingSphere 准实时一致性: 用户写入 GTID > 用户上次读 GTID → 走主库
-- 自动识别 5s 内的写入必须读主库
```

#### 方案 4:业务容忍延迟 (Read-After-Write Tolerance)

```text
电商商品列表: 用户接受几秒延迟 → 走从库
电商订单详情: 必须立即看到 → 走主库
商品库存查询: 必须精确 → 走主库
内容浏览量: 接受延迟 → 走从库
```

### 8.3 中间件侧缓解

| 中间件 | 缓解方案 |
|--------|----------|
| **ShardingSphere-JDBC** | HintManager.setWriteRouteOnly() 强制主 |
| **ProxySQL** | mysql_query_rules 规则,或 comment hint (`/*+ hostgroup=0 */`) |
| **MySQL Router** | 直接连 PRIMARY 端口 (6446) |

### 8.4 数据库侧缓解

```ini
# 半同步复制: 写主后,从库立即收到 binlog (RPO=0)
plugin-load = "rpl_semi_sync_master=semisync_master.so"
rpl_semi_sync_master_enabled = 1
rpl_semi_sync_master_timeout = 1000    # 1s 超时降级异步

# 5.7+ after_sync 模式 (默认)
```

半同步后,延迟可控制在几十毫秒级,多数业务可接受。

### 8.5 监控延迟

#### 应用心跳表

```sql
CREATE TABLE t_heartbeat (
  id INT PRIMARY KEY,
  ts TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 主库定时写
INSERT INTO t_heartbeat VALUES (1, NOW()) ON DUPLICATE KEY UPDATE ts = NOW();

-- 应用读从库时验证
SELECT TIMESTAMPDIFF(SECOND, ts, NOW()) AS lag FROM t_heartbeat WHERE id = 1;
-- 如果 lag > 阈值 → 走主库
```

#### SHOW SLAVE STATUS

```sql
SHOW SLAVE STATUS\G
Seconds_Behind_Master: 0   -- 关键指标
```

## 十、读写分离的性能调优

### 10.1 连接池配置

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50         # 主库不宜过大 (写并发有限)
      minimum-idle: 10
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
      # 从库可适当放大
      slave:
        maximum-pool-size: 100
```

### 10.2 中间件连接池

| 中间件 | 关键配置 | 推荐 |
|--------|----------|------|
| **ProxySQL** | `mysql-users.max_connections` | 主 1000, 从 2000 |
| **ShardingSphere-JDBC** | HikariCP `maximumPoolSize` | 主 20, 从 50 |
| **MySQL Router** | 系统文件描述符限制 | ulimit ≥ 65536 |

### 10.3 读负载均衡算法

| 算法 | 适用 | 备注 |
|------|------|------|
| **轮询 (ROUND_ROBIN)** | 从库配置相同 | 简单均衡 |
| **权重 (WEIGHT)** | 从库配置不同 | 性能好的从库权重高 |
| **随机 (RANDOM)** | 大规模集群 | 分布均匀 |
| **最小连接 (LEAST_ACTIVE)** | 长连接 | 减少空闲从库压力 |
| **响应时间 (RESPONSE_TIME)** | 异构从库 | 自动感知性能差异 |

ProxySQL 内置这些算法;ShardingSphere 支持自定义 SPI。

### 10.4 慢查询识别

```sql
-- ProxySQL: 找出慢路由
SELECT digest, digest_text,
       count_star, sum_time, hostgroup,
       avg_time / 1000000 avg_ms
FROM stats_mysql_query_digest
ORDER BY sum_time DESC LIMIT 20;

-- 把慢查询路由到专用从库 (避免拖累业务)
INSERT INTO mysql_query_rules (rule_id, match_digest, destination_hostgroup, apply)
VALUES (100, '^SELECT .*FROM big_table ORDER BY', 2, 1);  -- 路由到 hostgroup 2
```

## 十一、读写分离的注意事项

### 11.1 事务中读

```sql
START TRANSACTION;
  -- 自动路由到从库
  SELECT @balance := balance FROM accounts WHERE id=1;
  -- 应该走主库!事务内读需最新数据
  UPDATE accounts SET balance = @balance - 100 WHERE id=1;
COMMIT;
```

**问题**: 事务内 `SELECT` 自动路由到从库,但**同一事务的读必须从主库**(同一连接)。

**ShardingSphere 默认**: 事务内的读**仍走从库**。

**ProxySQL 默认**: 事务内的读**仍走从库**。

**解决**:
- ShardingSphere: `HintManager.setWriteRouteOnly()`
- ProxySQL: 规则 `match_digest: 'IN_TRANSACTION.*SELECT'` → 主库

### 11.2 大事务影响

```sql
START TRANSACTION;
  UPDATE big_table SET status='processed' WHERE create_time < '2020-01-01';  -- 100 万行
COMMIT;
```

**问题**:
- 主库执行时间长
- 复制到从库后,从库 SQL 线程回放慢
- 延迟增大,后续 SELECT 走从库看不到刚更新数据

**解决**:
- 拆分大事务
- 强制读主(`setWriteRouteOnly`)

### 11.3 强制走主的场景

| 场景 | 必须主库 |
|------|----------|
| 写后立即读 | ✓ |
| 事务内读 | ✓ |
| 强一致性需求 (支付/库存) | ✓ |
| 实时统计 (准确数字) | ✓ |
| 报表分析 | ✗ 走从库 |
| 普通列表查询 | ✗ 走从库 |

### 11.4 延迟感知读

```java
// 应用层监控主从延迟,延迟大时走主库
public boolean isDelayed() {
    long lag = heartbeatMapper.getReplicationLag();
    return lag > THRESHOLD_SECONDS;  // 例如 > 3s
}

public Order getOrder(Long id) {
    if (isDelayed()) {
        // 强制主库
        HintManager hint = HintManager.getInstance();
        hint.setWriteRouteOnly();
        try {
            return ordersMapper.findById(id);
        } finally {
            hint.close();
        }
    }
    return ordersMapper.findById(id);
}
```

## 十二、各方案选型决策

### 12.1 决策树

```text
应用是否 Java?
├─ 是 ─┬─ 需要分库分表?
│      ├─ 是 ── ShardingSphere-JDBC (读写分离 + 分库分表一站式)
│      └─ 否 ── ShardingSphere-JDBC (仅读写分离) 或 ProxySQL
│
└─ 否 ─┬─ 使用 MySQL 8.0 + MGR?
       ├─ 是 ── MySQL Router (官方推荐,自动感知)
       └─ 否 ─┬─ 想要 SQL 路由灵活性?
              ├─ 是 ── ProxySQL
              └─ 否 ── ShardingSphere-Proxy
```

### 12.2 生产推荐组合

| 场景 | 推荐方案 |
|------|----------|
| Java + 主从复制 | **ShardingSphere-JDBC** |
| Java + MGR | **ShardingSphere-JDBC + MySQL Router** (入口双层) |
| Java + 分库分表 | **ShardingSphere-JDBC** (同时支持分库分表) |
| 多语言 + MySQL 8.0 + MGR | **MySQL Router** |
| 多语言 + 复杂路由规则 | **ProxySQL** |
| 多语言 + 分库分表 | **ShardingSphere-Proxy** |
| 极高 QPS (> 100k) | **直接连主从**(不引入中间件,应用代码层控制) |

```text
基准 (1k 并发 SELECT):
├─ 直接连主:        ~50,000 QPS

├─ ProxySQL:        ~40,000 QPS  (损耗 ~20%)
```

## 十四、核心要点速记

- **读写分离** = 把 SELECT 分发到从库,把写操作保留在主库
- **本质**: 建立在主从复制之上的**应用/中间件层**模式
- **4 种实现**: 应用代码层、JDBC 拦截、Proxy 中间件、官方 Router
- **Java 推荐**: **ShardingSphere-JDBC** (与分库分表无缝集成)
- **多语言推荐**: **ProxySQL** (业界标准) 或 **MySQL Router** (官方,MGR 集成)
- **核心矛盾**: 主从延迟 → 写后立即读不一致
- **三大解决**: 强制读主 (Hint)、半同步复制、Session 一致性
- **事务内读**: 默认走从库,业务可强制走主 (`setWriteRouteOnly`)
- **MySQL Router + MGR**: 主从切换应用零感知 (官方推荐组合)
- **ShardingSphere-JDBC**: 性能损耗最低 (~10%),应用代码零侵入
- **ProxySQL**: 业界标准中间件,支持复杂规则 + 连接池 + 缓存
- **强制走主场景**: 写后立即读、事务内读、支付/库存等强一致
- **可走从库场景**: 报表分析、商品列表、内容浏览量、历史查询
- **生产推荐**: 主 1 + 从 2-3 + 半同步 + 中间件 + 心跳监控
- **避免**: 1 主 1 从(无故障切换余量)、异步复制 + 强一致需求
- **监控**: 读写比例、主从延迟、中间件连接数、后端节点状态
- **Hint 强制主**: ShardingSphere `@Hint`、ProxySQL `/*+ hostgroup=0 */`
