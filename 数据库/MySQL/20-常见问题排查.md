# MySQL 常见问题排查 (Troubleshooting)

## 一、故障排查思路总览

### 1. 自上而下分层定位

```text
┌─────────────────────────────────────────────┐
│  1. 应用层     SQL 烂?连接池满?超时设置?    │
│     ↓                                        │
│  2. MySQL 层   慢查询?锁?复制?配置?         │
│     ↓                                        │
│  3. OS 层      CPU/内存/IO/网络瓶颈?       │
│     ↓                                        │
│  4. 硬件层     磁盘坏?网卡丢包?内存故障?   │
└─────────────────────────────────────────────┘
```

**黄金法则**:**先看症状,再逐层下钻**。80% 的问题在前两层就能定位。

### 2. 排查通用流程

| 步骤 | 动作                          | 工具                          |
|------|-------------------------------|-------------------------------|
| 1    | 确认现象(报错、日志、监控)   | error log、慢日志、应用日志   |
| 2    | 收集现场(进程、状态、变量)   | `SHOW PROCESSLIST`、`SHOW STATUS` |
| 3    | 缩小范围(应用/MySQL/OS)      | `top`、`iostat`、`vmstat`     |
| 4    | 定位根因                      | 慢日志、`EXPLAIN`、`SHOW ENGINE INNODB STATUS` |
| 5    | 修复 + 验证 + 归档            | 备份、回滚预案                |

### 3. 必须会的诊断命令

```sql
-- 进程与锁
SHOW PROCESSLIST;
SHOW FULL PROCESSLIST;
SHOW ENGINE INNODB STATUS\G

-- 状态变量
SHOW GLOBAL STATUS LIKE 'Threads%';
SHOW GLOBAL STATUS LIKE 'Innodb_%';

-- 变量
SHOW VARIABLES LIKE 'max_connections';

-- 主从
SHOW SLAVE STATUS\G
SHOW MASTER STATUS;

-- 错误码
perror 1062
```

## 二、连接类问题

### 1. 1045 Access denied for user

**现象**:`ERROR 1045 (28000): Access denied for user 'app'@'10.0.0.5'`

**可能原因**:

| 原因              | 排查                                              |
|-------------------|---------------------------------------------------|
| 用户名/密码错      | 确认连接串                                        |
| 用户不存在         | `SELECT user,host FROM mysql.user;`               |
| Host 不匹配        | `'app'@'localhost'` 不等于 `'app'@'%'`           |
| 密码插件不兼容     | 客户端是 `caching_sha2_password`,驱动未升级      |

**排查步骤**:

```sql
-- 看用户
SELECT user, host, plugin FROM mysql.user WHERE user='app';

-- 看权限
SHOW GRANTS FOR 'app'@'10.0.0.5';

-- 改密码(8.0)
ALTER USER 'app'@'10.0.0.5' IDENTIFIED WITH mysql_native_password BY 'pwd';
FLUSH PRIVILEGES;
```

### 2. 2003 Can't connect to MySQL server

**现象**:`ERROR 2003: Can't connect to MySQL server on '10.0.0.5' (111)`

**可能原因**:

- mysqld 没启动
- 端口未监听
- 防火墙挡住
- bind-address 只绑 127.0.0.1

**排查步骤**:

```bash
# 看进程
ps -ef | grep mysqld

# 看端口
ss -tlnp | grep 3306
netstat -tlnp | grep 3306

# 看防火墙
iptables -L -n | grep 3306
firewall-cmd --list-ports

# 看 bind
grep bind-address /etc/my.cnf
```

**解决**:启动服务 → 开放端口 → 注释或修改 `bind-address = 0.0.0.0`

### 3. 2013 Lost connection / 2006 Server has gone away

**现象**:`Lost connection to MySQL server during query`

**可能原因**:

| 原因                  | 原因值                                |
|-----------------------|---------------------------------------|
| 查询包超 max_allowed_packet | `max_allowed_packet` 默认 16M-64M |
| wait_timeout 太短     | 默认 8 小时,但被调到 30 秒            |
| 网络中断(跨机房)      | tcp_keepalive、RST                    |
| 大字段(BLOB/TEXT)     | 单条记录超大                          |
| KILL 杀进程           | DBA 主动 kill                         |

**排查与解决**:

```sql
-- 看 timeout
SHOW VARIABLES LIKE '%timeout%';
SHOW VARIABLES LIKE 'max_allowed_packet';

-- 调大
SET GLOBAL max_allowed_packet = 64 * 1024 * 1024;
SET GLOBAL wait_timeout = 28800;
SET GLOBAL interactive_timeout = 28800;
```

应用层:开启重连、检查驱动 keepalive、检查长连接复用。

### 4. 1130 Host is not allowed to connect

**原因**:用户授权的 Host 段不含客户端 IP。

```sql
-- 解决方案:授权
CREATE USER 'app'@'10.0.0.%' IDENTIFIED BY 'pwd';
GRANT ALL ON app_db.* TO 'app'@'10.0.0.%';
FLUSH PRIVILEGES;

-- 或直接改
UPDATE mysql.user SET host='%' WHERE user='app';
FLUSH PRIVILEGES;
```

### 5. Too many connections

**现象**:`ERROR 1040 (HY000): Too many connections`

**排查**:

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS LIKE 'Max_used_connections';
SHOW GLOBAL STATUS LIKE 'Threads_connected';
```

**解决方案**:

| 层级     | 做法                                                  |
|----------|-------------------------------------------------------|
| 配置     | `max_connections = 1000` 起步                         |
| 应用     | 用连接池(Druid/HikariCP),设上限与超时                |
| 数据库   | `wait_timeout = 300`(5 分钟),踢掉空闲连接             |
| 紧急     | `SHOW PROCESSLIST;` 后 `KILL <id>;`                  |
| 终极     | `gdb -p $(pidof mysqld) -ex 'set max_connections=2000' -ex 'detach'` |

## 三、性能类问题

### 1. 慢查询排查

**定位**:

```sql
-- 1. 开启慢日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;

-- 2. 看慢日志
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 3. 用 mysqldumpslow 分析
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log
```

**分析**:

```sql
-- 看正在跑的慢查询
SELECT * FROM information_schema.PROCESSLIST 
WHERE COMMAND != 'Sleep' AND TIME > 5;

-- EXPLAIN 看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
EXPLAIN FORMAT=JSON SELECT ...;

-- 看表统计
SELECT * FROM information_schema.TABLES 
WHERE TABLE_SCHEMA = 'app_db' ORDER BY DATA_LENGTH DESC LIMIT 10;
```

**常见根因**:缺索引、函数/类型转换导致索引失效、深分页(OFFSET 大)、临时表/文件排序、统计信息不准。

### 2. 突发 CPU 飙高

**排查**:

```bash
# 1. 看系统 CPU
top
mpstat 1

# 2. 看 mysqld 进程
top -H -p $(pidof mysqld)
# 找到 CPU 高的线程 ID(TID)

# 3. 转成 16 进制,查 thread 在干啥
printf '%x\n' 12345
# 看 stack(8.0 用 performance_schema)
SELECT * FROM performance_schema.threads WHERE THREAD_OS_ID = 12345\G
```

**常见根因**:

- 大量全表扫描(慢查询)
- 大量排序/分组(filesort)
- 大量并发短查询(连接风暴)
- 复制 SQL 线程单线程追不上

**紧急止血**:`KILL` 慢查询;调 `innodb_thread_concurrency`;拉慢查询阈值。

### 3. 突发 IO 飙高

**排查**:

```bash
iostat -x 1         # 看 await、%util
iotop -o            # 看哪个进程
pidstat -d -p $(pidof mysqld) 1
```

**常见根因**:

- `innodb_flush_log_at_trx_commit = 1` + 高写入
- binlog 写入高峰
- 大量 `SELECT ... FOR UPDATE` 触发脏页刷盘
- 磁盘损坏/RAID 卡 BBU 没电

### 4. 查询慢但表不大

**典型场景**:表只有 10 万行,但一条 SELECT 跑 30 秒。

**根因清单**:

| 原因                    | 检查方法                                    |
|-------------------------|---------------------------------------------|
| 索引选错(函数/类型转换) | `EXPLAIN`,看 key 列                         |
| 深分页                  | `LIMIT 100000, 20` 改为游标分页            |
| 锁等待                  | `SHOW ENGINE INNODB STATUS` 看 lock 段      |
| 统计信息不准            | `ANALYZE TABLE t;`                          |
| 隐式字符集转换          | `EXPLAIN` 中 Extra 含 `utf8mb4`            |
| 触发器/视图递归         | 检查 trigger 链                            |

## 四、锁类问题

### 1. 死锁排查

**查看死锁日志**:

```sql
SHOW ENGINE INNODB STATUS\G
```

死锁日志结构:

```text
------------------------
LATEST DETECTED DEADLOCK
------------------------
2024-01-15 10:23:45 0x7f8b
*** (1) TRANSACTION:
TRANSACTION 12345, ACTIVE 5 sec
mysql tables in use 1, locked 1
LOCK WAIT 3 lock struct(s), heap size 1136, 2 row lock(s)
MySQL thread id 50, OS thread handle 140512345, query id 123 ...
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 10 page no 5 n bits 72 index PRIMARY of table `app`.`orders`
*** (2) TRANSACTION:
...
*** (2) HOLDS THE LOCK(S):
...
*** WE ROLL BACK TRANSACTION (2)
```

**关键字段**:

- `WAITING FOR THIS LOCK TO BE GRANTED`:等的是哪个索引的锁
- `HOLDS THE LOCK(S)`:持有哪些锁
- `Locks rec butnot gap`:记录锁
- `Locks gap before rec`:间隙锁(可能伤及无辜)

**常见死锁场景**:

1. **不同顺序加锁**:事务 A 先锁 1 再锁 2,事务 B 先锁 2 再锁 1
2. **间隙锁冲突**:RR 隔离级别下范围更新
3. **唯一索引插入**:next-key lock

**解决方案**:

- 统一访问顺序(按主键排序)
- 降低隔离级别到 RC
- 缩小事务范围
- 加索引(让锁更精确)

### 2. 锁等待超长

**排查**:

```sql
-- 谁在等
SELECT * FROM information_schema.INNODB_TRX 
WHERE trx_state = 'RUNNING' AND trx_started < NOW() - INTERVAL 60 SECOND;

-- 谁在持锁
SELECT * FROM sys.innodb_lock_waits\G

-- 看锁详情
SELECT * FROM performance_schema.data_locks LIMIT 10\G
SELECT * FROM performance_schema.data_lock_waits\G
```

**紧急**:`KILL <thread_id>;`

**调优**:`innodb_lock_wait_timeout`(默认 50 秒)。

### 3. 元数据锁等待 (MDL)

**现象**:`Waiting for table metadata lock`

**场景**:有长查询未结束,DDL 被卡住。

**排查**:

```sql
SELECT * FROM performance_schema.metadata_locks 
WHERE OBJECT_NAME = 'orders'\G

-- 看谁占着
SELECT id, user, host, db, command, time, state, info 
FROM information_schema.PROCESSLIST 
WHERE db IS NOT NULL AND command != 'Sleep' 
ORDER BY time DESC;
```

**解决**:KILL 持锁的会话。**预防**:DDL 前确保无活跃查询。

## 五、复制类问题

### 1. 主从复制中断

**查看状态**:

```sql
SHOW SLAVE STATUS\G
```

关键字段:

| 字段               | 含义                               |
|--------------------|------------------------------------|
| `Slave_IO_Running` | IO 线程(拉 binlog)                |
| `Slave_SQL_Running`| SQL 线程(回放)                    |
| `Last_IO_Error`    | IO 报错                            |
| `Last_SQL_Error`   | SQL 报错                           |
| `Seconds_Behind_Master` | 主从延迟(秒)                 |

**IO 线程常见错误**:

```text
# 主库连不上
Last_IO_Error: error connecting to master 'rep@10.0.0.1:3306' - retry-time: 60

# 解决
STOP SLAVE;
CHANGE MASTER TO MASTER_HOST='10.0.0.1', MASTER_USER='rep',
    MASTER_PASSWORD='xxx', MASTER_LOG_FILE='mysql-bin.000005',
    MASTER_LOG_POS=4;
START SLAVE;
```

**SQL 线程常见错误**(主键冲突、字段不存在、删表后从库还来写):

```sql
-- 方法 1:跳过错误(临时)
STOP SLAVE;
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;

-- 方法 2:跳过指定错误
SET GLOBAL slave_skip_errors = '1062,1054,1146';

-- 方法 3:精准修复后重启
STOP SLAVE;
-- ... 修数据 ...
START SLAVE;
```

### 2. 主从延迟严重

**判断**:`Seconds_Behind_Master` 持续 > 100。

**根因**:

- 主库大事务(批量 update/delete)
- 主库并发高,从库单线程追不上
- 从库 IO/网络慢
- 从库配置低

**排查**:

```sql
-- 主库大事务
SHOW MASTER STATUS;
SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND = 'Query';

-- 从库性能
SHOW GLOBAL STATUS LIKE 'Slave%';
```

**解决**:

| 方案          | 适用场景                    |
|---------------|-----------------------------|
| MySQL 5.7+ 多线程回放 | `slave_parallel_workers`  |
| 拆大事务      | 业务配合                    |
| 提升从库配置  | 硬件                        |
| 用 GTID       | 自动定位                    |
| 半同步        | 主库等从库 ACK             |

```ini
# my.cnf 从库
slave_parallel_workers = 8
slave_parallel_type = LOGICAL_CLOCK
slave_preserve_commit_order = ON
```

### 3. 主从数据不一致

**排查**:

```bash
# Percona Toolkit
pt-table-checksum h=master,D=app,t=orders --execute
pt-table-sync h=master --execute --print
```

**修复**:

1. 业务低峰期停写
2. `pt-table-sync` 从主库同步到从库
3. 校验后恢复

**预防**:开启 `read_only`、启用 GTID、半同步复制。

## 六、空间类问题

### 1. ibdata1 暴涨

**原因**:共享表空间 + 未开启 `innodb_file_per_table`。

**解决**:

```bash
# 1. 全量备份
mysqldump --all-databases > /backup/full.sql

# 2. 改配置
echo 'innodb_file_per_table = 1' >> /etc/my.cnf

# 3. 重启 + 重导
systemctl restart mysqld
mysql < /backup/full.sql
```

**事后**:每张表都会变成独立的 `.ibd` 文件,删除可释放。

### 2. 表空间满 (Table is full)

**现象**:`The table 'orders' is full`

**原因**:表空间超过文件系统限制(单文件 2T 或磁盘满)。

**排查**:

```bash
df -h /var/lib/mysql
du -sh /var/lib/mysql/ibdata1
```

**解决**:

- 加磁盘
- 启用独立表空间
- 分区表
- 清理数据

### 3. binlog 暴涨

**排查**:

```bash
ls -lh /var/lib/mysql/mysql-bin.*
```

**解决**:

```sql
-- 手动清理(从 000005 开始删)
PURGE BINARY LOGS TO 'mysql-bin.000005';

-- 按时间
PURGE BINARY LOGS BEFORE '2024-01-01 00:00:00';

-- 设置过期时间(秒)
SET GLOBAL binlog_expire_logs_seconds = 604800;  -- 7 天

-- 配 config 永久生效
expire_logs_days = 7
```

**注意**:主从架构需先确认从库已追到对应位置。

### 4. tmpdir 不够 (Sort aborted)

**现象**:`Sort aborted: Out of memory`

**排查**:

```bash
df -h /tmp
SHOW VARIABLES LIKE 'tmpdir';
```

**解决**:

```bash
# 1. 清 /tmp
rm -f /tmp/MY*  # mysql 临时文件

# 2. 改 tmpdir 到大空间
mkdir -p /data/mysql_tmp
chown mysql:mysql /data/mysql_tmp
# my.cnf
tmpdir = /data/mysql/tmp

# 3. 优化 SQL:减少 filesort
# 加索引让 ORDER BY 走索引
```

## 七、崩溃恢复

### 1. 服务器崩溃后

**innodb_force_recovery 模式**:

| 模式 | 作用                                                   |
|------|--------------------------------------------------------|
| 0    | 正常运行                                               |
| 1    | (SRV_FORCE_IGNORE_CORRUPT)忽略检查到的 corrupt 页     |
| 2    | (SRV_FORCE_NO_BACKGROUND)阻止主线程和后台线程运行      |
| 3    | (SRV_FORCE_NO_TRX_UNDO)不执行事务回滚                  |
| 4    | (SRV_FORCE_NO_IBUF_MERGE)不执行插入缓冲合并            |
| 5    | (SRV_FORCE_NO_UNDO_LOG_SCAN)不查看 undo log           |
| 6    | (SRV_FORCE_NO_LOG_REDO)不执行 redo log 前滚            |

**8 种 force recovery** 数字范围 0-6(共 7 档,加上 0 共 8 种配置)。

**使用流程**:

```bash
# 1. 先尝试正常启动
systemctl start mysqld

# 2. 失败就加 recovery
vi /etc/my.cnf
[mysqld]
innodb_force_recovery = 1

systemctl start mysqld

# 3. 不行逐步加(最多 6)
innodb_force_recovery = 6

# 4. 立即 mysqldump 出来
mysqldump --all-databases > /backup/dump.sql

# 5. 改回 0,清 datadir,重新初始化
innodb_force_recovery = 0
mysqld --initialize-insecure --user=mysql
mysql < /backup/dump.sql
```

**注意**:force_recovery 越大,丢失数据越多,只用于抢救。

## 九、数据损坏

**排查**:

```bash
# 看 error log
grep -i "corrupt" /var/log/mysqld.log
```

**修复流程**:

```

CHECK TABLE orders;

REPAIR TABLE orders USE_FRM;
```

## 十、主键冲突

### 1. Duplicate entry

**现象**:`ERROR 1062 (23000): Duplicate entry '100' for key 'PRIMARY'`

**排查**:

```sql
SELECT * FROM orders WHERE id = 100;
SHOW CREATE TABLE orders;
```

**常见原因**:插入前未查重;并发插入;主从切换后重复 ID。

### 2. AUTO_INCREMENT 跳号

**原因**:

- INSERT 失败回滚(消耗了 ID)
- 显式插入大 ID 后
- `innodb_autoinc_lock_mode = 2`(默认)批量插入分配大段

**查看**:`SELECT LAST_INSERT_ID();`

**解决**:业务不用连续 ID 用 `BIGINT AUTO_INCREMENT`,或用 UUID/Snowflake。

## 十一、字符集问题

### 1. 乱码

**根因**:客户端、连接、存储字符集不一致。

**统一为 utf8mb4**:

```ini
# my.cnf
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci

[client]
default-character-set = utf8mb4

[mysql]
default-character-set = utf8mb4
```

**连接指定**:`SET NAMES utf8mb4;`

### 2. 字符集不一致

```sql
-- 查表字符集
SELECT TABLE_NAME, TABLE_COLLATION 
FROM information_schema.TABLES 
WHERE TABLE_SCHEMA = 'app_db';

-- 改
ALTER TABLE orders CONVERT TO CHARACTER SET utf8mb4;
```

## 十二、内存相关

### 1. OOM

**排查**:

```bash
dmesg | grep -i "killed process"
grep "Out of memory" /var/log/messages
```

**解决**:

- 调 `innodb_buffer_pool_size`(总内存 60-70%)
- 限制 `tmp_table_size`、`max_heap_table_size`
- 调 `performance_schema` 内存
- 关 NUMA 或绑核

### 2. Buffer Pool 命中率低

**计算**:

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- 命中率
SELECT 1 - (
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') /
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests')
) AS hit_rate;
```

**理想命中率** > 99%。

**优化**:

- 加大 `innodb_buffer_pool_size`
- 预热:`SELECT ... INTO OUTFILE` / `mysql_dump` 后 LOAD
- `innodb_buffer_pool_dump_at_shutdown = ON`

## 十六、核心要点速记

- **排查顺序**:应用 → MySQL → OS → 硬件
- **连接类**:1045 看授权,2003 看端口,2013 看 timeout
- **慢查询**:`slow_query_log` + `EXPLAIN` + 索引
- **死锁**:`SHOW ENGINE INNODB STATUS`,看 WAITING/HOLDS
- **复制**:`SHOW SLAVE STATUS`,IO/SQL 线程独立排查
- **空间**:`ibdata1` 用 `innodb_file_per_table=1`;`binlog` 设 `expire_logs_days`
- **崩溃恢复**:`innodb_force_recovery` 0→6,先 dump 再重导
- **数据损坏**:InnoDB 用 force recovery + dump 重导;MyISAM 用 `REPAIR TABLE`
- **字符集**:统一 `utf8mb4`
- **OOM**:调 `innodb_buffer_pool_size` ≈ 物理内存 60-70%
- **命中率**:`1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests`
- **perror**:查错误码含义
- **CHECKLIST**:评估影响 → 拍现场 → 止血 → 定位 → 修复 → 复盘
- **Percona Toolkit**:`pt-query-digest` 慢日志、`pt-online-schema-change` 在线 DDL
- **mysqld_exporter**:关键指标拉 Prometheus
- **永远先 dump**:force_recovery 模式下第一时间导出数据
- **永远不盲目 kill**:先看 PROCESSLIST,杀长锁的
- **永远不忽视 MDL**:DDL 卡顿元凶
- **预防 > 排查**:监控、巡检、备份、演练
