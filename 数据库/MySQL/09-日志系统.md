# MySQL 日志系统 (Logging System)

> 本章系统讲解 MySQL 的日志体系:Server 层日志(错误日志、慢查询日志、通用日志、二进制日志)与 InnoDB 引擎层日志(redo log、undo log)的工作机制、配置方法、分析工具,以及日志之间如何协作(两阶段提交)保证数据一致性。

---

## 一、MySQL 日志系统总览

### 1. 为什么需要日志

数据库系统对日志的依赖远超过普通的应用程序。日志在 MySQL 中承担 **故障恢复、数据复制、审计追溯、性能调优** 等多重角色。

```
┌────────────────────────────────────────────────────────────────┐
│                       MySQL 日志的四大作用                       │
├────────────────────────────────────────────────────────────────┤
│  1. 崩溃恢复 (Crash Recovery)                                   │
│     - 系统异常断电时,redo log 保证已提交事务不丢失              │
│     - undo log 保证未提交事务可以回滚                            │
│                                                                │
│  2. 数据复制 (Replication)                                       │
│     - binlog 是主从复制的核心,记录所有数据变更                   │
│     - relay log 是从库的中转日志                                 │
│                                                                │
│  3. 数据恢复 (Point-in-Time Recovery)                            │
│     - 全量备份 + binlog 增量,可恢复到任意时间点                  │
│                                                                │
│  4. 审计与性能分析 (Audit & Profiling)                           │
│     - 慢查询日志、通用日志、错误日志支撑问题排查                 │
└────────────────────────────────────────────────────────────────┘
```

### 2. 日志分类总览

MySQL 的日志按"层次"可以分为 **Server 层日志** 与 **引擎层日志** 两类,Server 层日志由 MySQL Server 自身管理,引擎层日志由具体存储引擎(InnoDB)管理。

| 日志          | 层级       | 默认开启 | 主要作用                              | 关键参数                |
|---------------|------------|----------|---------------------------------------|-------------------------|
| **错误日志**      | Server     | 是       | 启动、运行、关闭过程的错误与警告      | `log_error`             |
| **慢查询日志**    | Server     | 否       | 记录超过阈值的 SQL,用于性能调优       | `slow_query_log`        |
| **通用日志**      | Server     | 否       | 记录所有 SQL(性能影响大,慎用)         | `general_log`           |
| **二进制日志**    | Server     | 否(建议开)| 记录数据变更,用于复制与恢复           | `log_bin`               |
| **InnoDB redo log** | 引擎层   | 是       | 保证事务持久性,崩溃恢复              | `innodb_log_file_size`  |
| **InnoDB undo log** | 引擎层   | 是       | 事务回滚 + MVCC 多版本                | `innodb_undo_tablespaces` |
| **relay log**   | Server     | 否       | 主从复制中从库的中转日志              | `relay_log`             |

### 3. 各日志的位置与命名

```text
# 默认存放目录(由 datadir 决定)
/var/lib/mysql/
├── ib_logfile0              # InnoDB redo log 第 1 个文件
├── ib_logfile1              # InnoDB redo log 第 2 个文件
├── undo_001                 # undo 表空间文件(8.0+)
├── undo_002                 # undo 表空间文件(8.0+)
├── mysql-bin.000001         # binlog 文件(开启后)
├── mysql-bin.000002         # binlog 文件
├── mysql-bin.index          # binlog 索引文件
├── relay-bin.000001         # relay log 文件(从库)
├── slow.log                 # 慢查询日志(若开启)
├── general.log              # 通用日志(若开启)
└── hostname.err             # 错误日志(默认以主机名命名)
```

### 4. 日志系统协作全景图

```
┌──────────────────────────────────────────────────────────────────────┐
│                          客户端发起 UPDATE                            │
└──────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────────┐
│  Server 层                                                            │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │  1. 查询解析 → 优化 → 执行                                       │ │
│  │  2. 写 binlog cache (内存)                                       │ │
│  │  3. 事务提交 → binlog 刷盘 (write+fsync)                         │ │
│  └─────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────────┐
│  InnoDB 引擎层                                                        │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │  1. 加载数据页到 Buffer Pool                                     │ │
│  │  2. 写 undo log (用于回滚 + MVCC)                                │ │
│  │  3. 在 Buffer Pool 中修改数据(脏页)                              │ │
│  │  4. 写 redo log buffer (内存)                                   │ │
│  │  5. 事务提交 → redo log 刷盘 (write+fsync)                      │ │
│  │  6. 异步刷脏页到表空间 (.ibd)                                    │ │
│  └─────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                  两阶段提交保证 binlog 与 redo log 一致性
```

## 二、错误日志 (Error Log)

### 1. 作用与默认行为

错误日志是 MySQL **最重要的诊断日志**,记录 MySQL **启动、运行、关闭**过程中的所有错误、警告、关键事件。即使其他日志全部关闭,错误日志也始终开启。

**记录内容**:

- 启动/关闭信息(版本、参数、buffer pool 大小等)
- 严重错误(崩溃、无法启动、磁盘满、连接异常)
- 警告信息(参数不推荐、磁盘空间不足)
- 主从复制异常
- InnoDB 关键事件(检查点、表空间变更)

### 2. 查看错误日志位置

```sql
-- 查看错误日志路径
SHOW VARIABLES LIKE 'log_error';

-- 查看更详细的信息
SHOW VARIABLES LIKE 'log_error%';
+--------------------+----------------------------+
| Variable_name      | Value                      |
+--------------------+----------------------------+
| log_error          | /var/log/mysql/error.log   |
| log_error_services | log_filter_internal;log_sink_internal |
| log_error_verbosity| 2                          |
+--------------------+----------------------------+
```

### 3. 配置错误日志

```ini
# /etc/my.cnf
[mysqld]
log_error = /var/log/mysql/error.log

# 8.0.16+ 新增,可独立控制 verbosity
log_error_verbosity = 3      # 1=ERROR, 2=ERROR+WARNING, 3=ERROR+WARNING+INFORMATION
```

**verbosity 级别**:

| 级别 | 内容                    |
|------|-------------------------|
| 1    | 仅 ERROR                |
| 2    | ERROR + WARNING(默认)   |
| 3    | ERROR + WARNING + NOTE  |

> 注意:`log_error` 是 **动态参数吗?否**。修改后必须重启 MySQL 才能生效。

### 4. 查看错误日志

```bash
# 实时跟踪
tail -f /var/log/mysql/error.log

# 查找错误
grep -i "error" /var/log/mysql/error.log | tail -50

# 查找启动时间(便于定位上次重启时间)
grep "ready for connections" /var/log/mysql/error.log

# 查找 InnoDB 关键信息
grep -i "innodb" /var/log/mysql/error.log

# 查找主从复制异常
grep -i "slave\|replication" /var/log/mysql/error.log
```

### 5. 错误日志轮转

MySQL **不会自动轮转**错误日志,需要外部工具(如 `logrotate`)或手动操作。

```bash
# 手动轮转
mv /var/log/mysql/error.log /var/log/mysql/error.log.old
mysqladmin -u root -p flush-logs   # 通知 MySQL 重新打开
# MySQL 关闭旧 fd,创建新文件继续写入

# 使用 logrotate(推荐)
```

**logrotate 配置示例** `/etc/logrotate.d/mysql`:

```text
/var/log/mysql/error.log {
    daily
    rotate 7
    missingok
    notifempty
    compress
    delaycompress
    copytruncate
    create 0640 mysql mysql
    sharedscripts
    postrotate
        # mysqld 在写入时会自己重新创建(若用 create)
        # 若用 copytruncate 则不需要重载
    endscript
}
```

> `copytruncate` vs 重启:由于错误日志不能动态关闭,生产上常用 `copytruncate` 方式滚动,避免重启实例。

## 三、慢查询日志 (Slow Query Log)

### 1. 作用

慢查询日志记录 **执行时间超过 `long_query_time` 阈值** 的 SQL 语句,是性能调优的首要依据。

**记录内容**:
- 执行时间(秒)
- 锁等待时间
- 返回行数 / 扫描行数
- 完整 SQL 文本
- 主机、用户、时间戳

### 2. 开启慢查询日志

```ini
# /etc/my.cnf
[mysqld]
slow_query_log = ON                                   # 开启
slow_query_log_file = /var/log/mysql/slow.log         # 路径(默认 hostname-slow.log)
long_query_time = 1                                   # 阈值(秒),默认 10s,推荐 0.5~2s
log_slow_extra = ON                                   # 8.0.14+ 记录额外信息(执行计划等)
log_queries_not_using_indexes = ON                    # 记录未走索引的查询(可选)
```

**动态开启**(无需重启):

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;
```

### 3. mysqldumpslow 分析工具

`mysqldumpslow` 是 MySQL 自带的慢查询分析工具,功能简单但够用。

```bash
# 查看最慢的 10 条 SQL
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按出现次数排序
mysqldumpslow -s c -t 10 /var/log/mysql/slow.log

# 按锁等待时间排序
mysqldumpslow -s l -t 10 /var/log/mysql/slow.log

# 按扫描行数排序
mysqldumpslow -s r -t 10 /var/log/mysql/slow.log

# 显示完整 SQL(默认会 S=SELECT T=TABLE 化简)
mysqldumpslow -a -s t -t 5 /var/log/mysql/slow.log

# 仅看某个数据库的
mysqldumpslow -g "mydb" /var/log/mysql/slow.log
```

**排序字段对照表**:

| 选项 | 含义                  |
|------|-----------------------|
| `t`  | 总耗时 (Query_time)   |
| `l`  | 锁时间 (Lock_time)    |
| `r`  | 扫描行数 (Rows_sent)  |
| `c`  | 执行次数 (Count)      |
| `at` | 平均耗时              |
| `al` | 平均锁时间            |
| `ar` | 平均扫描行数          |

### 4. pt-query-digest (Percona Toolkit)

`pt-query-digest` 是 **业界最强大的 MySQL 慢查询分析工具**,支持详细统计、聚合、报告输出。

**安装**:

```bash
# 安装 Percona Toolkit
yum install percona-toolkit          # CentOS/RHEL
apt install percona-toolkit          # Debian/Ubuntu
brew install percona-toolkit         # macOS
```

**使用**:

```bash
# 基本分析
pt-query-digest /var/log/mysql/slow.log > slow_report.txt

# 分析并输出到文件
pt-query-digest /var/log/mysql/slow.log --output slowlog > report.log

# 实时分析(从 mysql 进程 stdin)
pt-query-digest --processlist h=localhost,u=root,p=xxx --run-time 30s

# 仅分析某段时间
pt-query-digest --since '2024-01-15 00:00:00' --until '2024-01-16 00:00:00' slow.log

# 仅过滤特定数据库
pt-query-digest --filter '($event->{db} || "") =~ m/mydb/' slow.log
```

### 5. Performance Schema 替代方案

对于更高的实时性,可以开启 `performance_schema` 中的 events_statements 表,精度更高(微秒级),且不写磁盘。

```sql
-- 查看当前慢查询
SELECT * FROM performance_schema.events_statements_history_long
WHERE TIMER_WAIT > 1000000000  -- 1秒,单位皮秒
ORDER BY TIMER_WAIT DESC LIMIT 10;

-- 实时统计
SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1000000000 AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
```

## 四、通用日志 (General Log)

### 1. 作用与代价

通用日志 **记录所有到达 MySQL 的 SQL 语句**(包括连接/断开、SELECT、UPDATE 等)。它能完整还原某个时间窗口内的全部活动,**但代价极高**:

- 每条 SQL 都写一次磁盘
- 高 QPS 场景下,I/O 开销巨大(可达 30%-50%)
- 文件增长极快

**典型用途**:

- 调试某个诡异问题
- 审计某段时间的访问(短窗口开启)
- 学习 SQL 流量特征

### 2. 配置通用日志

```ini
# /etc/my.cnf
[mysqld]
general_log = ON                                    # 开启
general_log_file = /var/log/mysql/general.log       # 路径
log_output = FILE                                   # TABLE 也可(8.0+),FILE 是默认
```

**动态开启**:

```sql
SET GLOBAL general_log = ON;
SET GLOBAL log_output = 'TABLE';  -- 写到 mysql.general_log 表,8.0 支持
```

> **生产环境强烈建议关闭**(`general_log = OFF`),仅在调试时短暂开启。

### 3. 临时开启调试的小技巧

```sql
-- 短窗口开启(假设默认 OFF)
SET GLOBAL general_log = ON;

-- 让接下来的某个时间段所有 SQL 都入日志
-- ... 执行被诊断的业务 ...
SELECT * FROM some_table WHERE ...;

-- 立即关闭
SET GLOBAL general_log = OFF;

-- 查看日志内容(若输出到 TABLE)
SELECT event_time, command_type, argument
FROM mysql.general_log
WHERE event_time > NOW() - INTERVAL 10 MINUTE
ORDER BY event_time DESC;
```

> 注意:开启后立即影响性能;若服务器 QPS 高,**请慎重使用 TABLE 输出**,避免 `mysql.general_log` 表过大。

### 4. log_output 选项

```ini
log_output = TABLE                 # 8.0+ 推荐,查询方便
log_output = FILE                  # 传统方式
log_output = TABLE,FILE            # 同时输出
```

## 五、二进制日志 (Binary Log, binlog)

### 1. binlog 概述

**binlog** 是 MySQL Server 层维护的逻辑日志,记录 **所有修改数据的 SQL 或行变更**,不记录 SELECT 等查询。binlog 是 **MySQL 复制和数据恢复** 的核心。

**核心特征**:

| 特性     | 说明                                                    |
|----------|---------------------------------------------------------|
| 层级     | Server 层(与引擎无关)                                  |
| 内容     | 数据变更事件(insert/update/delete/DDL)                  |
| 格式     | 二进制,需用 mysqlbinlog 解析                           |
| 顺序     | 按事务提交顺序追加                                      |
| 大小     | 达到 `max_binlog_size` 自动切换新文件                   |
| 索引     | `mysql-bin.index` 记录所有 binlog 文件名                |

### 2. binlog 的三大格式

| 格式       | 含义                       | 优点                       | 缺点                       | 适用场景           |
|------------|----------------------------|----------------------------|----------------------------|--------------------|
| **STATEMENT** | 记录 SQL 语句              | 文件小、可读性高           | 不安全(随机函数、触发器等) | 简单业务(已不推荐)|
| **ROW**      | 记录每行的变更             | 安全(行级确定)、支持 row 复制 | 文件大 | **强烈推荐**       |
| **MIXED**    | 默认 STATEMENT,特殊场景用 ROW | 平衡 | 行为不可预测 | 老版本兼容过渡     |

**版本演进**:

- MySQL 5.7.7 之前:默认 `STATEMENT`
- MySQL 5.7.7+:**默认 `ROW`**
- MySQL 8.0:**默认 `ROW`**

### 3. 配置 binlog

```ini
# /etc/my.cnf
[mysqld]
# 必须开启 binlog(主从复制、恢复都需要)
log_bin = /var/lib/mysql/mysql-bin           # binlog 文件前缀(开启后不可关闭,只能设路径)

# 服务器 ID(主从复制必须唯一)
server_id = 1                                # 主从环境必须唯一

# binlog 格式
binlog_format = ROW                          # 推荐 ROW

# 单个 binlog 文件最大大小
max_binlog_size = 1G                         # 默认 1GB

# binlog 保留天数(8.0+ 推荐)
binlog_expire_logs_auto_purge = ON
expire_logs_days = 7                         # 保留 7 天(MySQL 8.0 默认 30 天)

# binlog 缓存大小(大事务场景)
binlog_cache_size = 1M                       # 单事务缓存,默认 64K
max_binlog_cache_size = 2G                   # 最大缓存

# sync_binlog(刷盘策略,见下文)
sync_binlog = 1                              # 最安全,每事务 fsync
sync_binlog = 0                              # 仅写入 OS 缓存,由 OS 刷盘(性能最好)

# binlog 写入策略
binlog_order_commits = ON                    # 按 commit 顺序写(主从一致)

# binlog 行元数据(8.0+)
binlog_row_image = FULL                      # FULL(全部列) / MINIMAL(只变更列)
binlog_row_metadata = FULL_LOG_GROUP
```

### 4. binlog 写入机制 (深入)

binlog 的写入涉及 **binlog cache** 与 **fsync** 两个关键机制。

#### 4.1 写入流程

```
┌──────────────────────────────────────────────────────────────────┐
│                         binlog 写入流程                           │
│                                                                  │
│  事务执行                                                          │
│    │                                                              │
│    ▼                                                              │
│  binlog cache (per-thread,内存)                                    │
│    │   写入过程:                                                    │
│    │   - 每个连接独立的 binlog cache                                │
│    │   - 事务执行期间所有事件先写入 cache                           │
│    │   - 缓存满或事务结束时,write 到 binlog file                    │
│    ▼                                                              │
│  write() 系统调用                                                  │
│    │   - 数据进入 OS page cache                                    │
│    │   - 速度快,但断电丢失                                        │
│    ▼                                                              │
│  fsync() 系统调用                                                  │
│    │   - 强制刷盘到磁盘                                            │
│    │   - 慢(毫秒级),但保证不丢                                    │
│    ▼                                                              │
│  binlog file (磁盘)                                                │
└──────────────────────────────────────────────────────────────────┘
```

#### 4.2 sync_binlog 三种策略

| sync_binlog 值 | 含义                          | 性能 | 安全性 | 适用场景           |
|----------------|-------------------------------|------|--------|--------------------|
| **0**          | 仅 write,fsync 由 OS 决定     | 最高 | 最差   | 可丢失几分钟数据   |
| **1**          | 每事务 commit 都 fsync        | 最差 | 最高   | **金融级、生产推荐** |
| **N (N>1)**    | 每 N 次事务 commit fsync 一次 | 折中 | 折中   | 中等可靠性场景     |

> **生产强烈推荐 `sync_binlog = 1`**,以保证主从一致性;若允许丢失少量数据,可用 `sync_binlog = 100` 或 `0` 提升吞吐。

#### 4.3 两阶段写入的 cache 行为

```
执行 SQL → binlog cache(写入)
              │
              ▼
        COMMIT 命令触发
              │
              ▼
      binlog cache → write 到 binlog file
              │
              ▼
    sync_binlog 决定是否 fsync
              │
              ▼
       binlog 文件落盘
```

**事务回滚时的处理**:未提交的 binlog cache 内容会清空,不写入文件。

### 5. binlog 事件结构

每个 binlog 文件由多个 **事件 (Event)** 组成,常见的事件类型:

| 事件类型             | 含义                                  |
|----------------------|---------------------------------------|
| `Format_description`  | 文件格式描述                          |
| `Query`              | DDL/STATEMENT 格式的 DML             |
| `Table_map`          | ROW 格式:映射表 ID 到库表            |
| `Write_rows`         | ROW 格式:插入行                      |
| `Update_rows`        | ROW 格式:更新行                      |
| `Delete_rows`        | ROW 格式:删除行                      |
| `Xid`                | 事务结束标识                          |
| `Rotate`             | 文件切换事件                          |
| `Gtid`               | GTID 事件(8.0+)                     |

## 六、redo log (重做日志)

### 1. WAL (Write-Ahead Logging) 思想

InnoDB 采用 **WAL(预写日志)** 机制:**先写日志,再写磁盘**。这是关系型数据库实现 **持久性 (Durability)** 的关键设计。

```
┌──────────────────────────────────────────────────────────┐
│                      WAL 思想                            │
│                                                          │
│   1. 事务提交时,先写 redo log 并 fsync 到磁盘             │
│   2. 数据页的修改,稍后再异步刷到磁盘(.ibd)                │
│   3. 即使数据库崩溃,redo log 可以恢复已提交数据           │
│                                                          │
│   优势:                                                  │
│   - 顺序写日志(快),避免随机写数据页(慢)                  │
│   - 事务提交即可保证持久性,数据页延迟刷盘                 │
│   - 减少磁盘 IO,提升吞吐                                  │
└──────────────────────────────────────────────────────────┘
```

### 2. redo log 的关键概念

| 概念                    | 含义                                        |
|-------------------------|---------------------------------------------|
| **redo log buffer**     | 内存中的日志缓冲(全局共享)                  |
| **redo log file**       | 磁盘上的日志文件,默认 `ib_logfile0/1`     |
| **LSN (Log Sequence Number)** | 日志序列号,单调递增,标识 redo log 位置 |
| **checkpoint**          | 已刷盘的数据页 LSN,表示 LSN 之前的数据安全 |
| **dirty page**          | Buffer Pool 中被修改但未刷盘的数据页        |

### 3. redo log 物理结构

```text
磁盘上的 redo log 文件(循环写):
┌────────────────────────────────────────────────────┐
│ ib_logfile0  (固定大小,如 1G)                       │
├────────────────────────────────────────────────────┤
│  [log block 0]  [log block 1]  [log block 2]  ...  │
│     512B           512B           512B               │
└────────────────────────────────────────────────────┘
                        │
                        ▼ 循环写满则回到开头
┌────────────────────────────────────────────────────┐
│ ib_logfile1  (固定大小,如 1G)                       │
├────────────────────────────────────────────────────┤
│  [log block 0]  [log block 1]  [log block 2]  ...  │
└────────────────────────────────────────────────────┘

写指针(write pos) ──►             ┐
                                  │  可写区域(checkpoint - write pos)
checkpoint ──────────────►         ┘
```

### 4. 配置 redo log

```ini
# /etc/my.cnf
[mysqld]
# redo log 文件路径
innodb_log_group_home_dir = /var/lib/mysql/

# redo log 文件大小(8.0+)
innodb_log_file_size = 2G          # 推荐:Buffer Pool 的 25%-50%

# redo log 文件个数(8.0 默认 2,8.0.30+ 支持最多 96 个)
innodb_log_files_in_group = 2

# redo log 缓冲区大小(默认 16MB,通常足够)
innodb_log_buffer_size = 16M

# 刷盘策略(默认 1)
innodb_flush_log_at_trx_commit = 1

# 8.0+ 改进参数
innodb_log_write_ahead_size = 8192  # 提前写盘粒度
innodb_log_spin_cpu_abs_lwm = 80    # 自旋等待阈值
innodb_log_spin_cpu_pct_hwm = 50
```

### 5. innodb_flush_log_at_trx_commit 三种策略

| 值 | 含义                                                        | 性能 | 安全性 | 丢数据风险     |
|----|-------------------------------------------------------------|------|--------|----------------|
| **0** | 写入 log buffer 后,每秒写盘并 fsync 一次                  | 最高 | 最差   | 最多丢 1 秒数据 |
| **1** | **每事务提交都 write + fsync** (默认)                    | 最差 | 最高   | **不丢任何已提交数据** |
| **2** | 每事务提交都 write,但每秒 fsync 一次                      | 中等 | 中等   | 最多丢 1 秒数据(OS 崩溃)|

> **生产环境强烈推荐 `innodb_flush_log_at_trx_commit = 1`**,这是 **ACID 中 D (Durability)** 的真正保证。

### 6. LSN (Log Sequence Number) 机制

LSN 是 InnoDB 的内部"时间戳",**单调递增**,记录在 redo log 中。

```
┌────────────────────────────────────────────────────────────────┐
│                         LSN 体系                                │
│                                                                │
│  Buffer Pool 数据页有: page_lsn  (该页最后修改的 LSN)          │
│  redo log 当前写:   log_sequence_number  (最新写入位置)         │
│  已刷盘位置:        checkpoint_lsn                              │
│                                                                │
│  关系: page_lsn ≤ checkpoint_lsn → 该页已刷盘,数据安全          │
│       page_lsn > checkpoint_lsn → 脏页,崩溃后需 redo log 重做   │
└────────────────────────────────────────────────────────────────┘
```

**查看 LSN**:

```sql
SHOW ENGINE INNODB STATUS\G
-- 在输出中找到:
LOG
---
Log sequence number          123456789012
Log buffer assigned up to    123456789012
Log buffer completed up to   123456789012
Log written up to            123456789012
Log flushed up to            123456789012
Added dirty pages up to      123456789012
Pages flushed up to          123456000000
Last checkpoint at           123456000000
```

### 7. checkpoint 与 flush 策略

#### 7.1 checkpoint 的作用

- 表示 **LSN 之前的脏页已全部刷盘**
- 表示 **LSN 之前的 redo log 可以覆盖(回收空间)**
- 避免 redo log 文件无限增长

#### 7.2 checkpoint 触发条件

```
┌─────────────────────────────────────────────────────────────────┐
│                   checkpoint 触发场景                           │
│                                                                 │
│  1. Sharp Checkpoint: 数据库关闭时                              │
│     - 将所有脏页刷盘                                            │
│                                                                 │
│  2. Fuzzy Checkpoint: 数据库运行中                              │
│     a. 脏页比例超过阈值 (innodb_max_dirty_pages_pct)            │
│     b. redo log 空间不足 (write pos 接近 checkpoint)            │
│     c. 每 1 秒(innodb_io_capacity 控制刷盘速度)                │
│     d. LSN 与 checkpoint 差值过大                               │
└─────────────────────────────────────────────────────────────────┘
```

#### 7.3 关键参数

```ini
# 脏页比例上限(默认 90,8.0 推荐 50-75)
innodb_max_dirty_pages_pct = 75
innodb_max_dirty_pages_pct_lwm = 0     # 后台异步刷盘的"低水位"

# IO 容量(决定刷盘速度)
innodb_io_capacity = 200               # 磁盘 IO 能力,SSD 可设 2000+
innodb_io_capacity_max = 2000

# 单次刷脏页数量限制
innodb_adaptive_flushing = ON         # 自适应刷盘
innodb_adaptive_flushing_lwm = 10
```

### 8. redo log 写入时序图 (含 WAL)

```
┌──────────────────────────────────────────────────────────────────────┐
│                       UPDATE 事务执行流程                             │
│                                                                      │
│  T1  ──┐                                                              │
│  T2    │  客户端执行 UPDATE                                           │
│  T3    │    │                                                         │
│  T4    │    ▼                                                         │
│  T5    │  InnoDB 加载数据页到 Buffer Pool                              │
│  T6    │    │                                                         │
│  T7    │    ▼                                                         │
│  T8    │  写 undo log (用于回滚 + MVCC)                               │
│  T9    │    │                                                         │
│  T10   │    ▼                                                         │
│  T11   │  在 Buffer Pool 中修改数据(产生脏页)                         │
│  T12   │    │                                                         │
│  T13   │    ▼                                                         │
│  T14   │  生成 redo log 写入 redo log buffer (内存)                   │
│  T15   │    │                                                         │
│  T16   │    ▼                                                         │
│  T17   │  执行 COMMIT                                                  │
│  T18   │    │                                                         │
│  T19   │    ▼                                                         │
│  T20   │  redo log buffer → redo log file (write + fsync)            │
│  T21   │    │  ┌─ 若 innodb_flush_log_at_trx_commit=1,同步 fsync       │
│  T22   │    ▼                                                         │
│  T23   │  事务提交成功,返回客户端 OK                                    │
│  T24   │    │                                                         │
│  T25   │    ▼  (异步,后台线程执行)                                    │
│  T26   │  Buffer Pool 脏页 → 磁盘 (.ibd 数据文件)                     │
│  T27   └─ checkpoint 推进                                              │
└──────────────────────────────────────────────────────────────────────┘
```

### 9. 组提交 (Group Commit) 优化

为提升 redo log 写入吞吐,InnoDB 引入 **组提交**:多个事务的日志合并成一次 fsync。

```
单事务 fsync:                              组提交 fsync:
T1 ─write→ fsync (1ms)                    T1 ─write─┐
T2 ─write→ fsync (1ms)                    T2 ─write─┼─ 一次 fsync (1ms)
T3 ─write→ fsync (1ms)                    T3 ─write─┘
合计 3ms                                  合计 1ms
```

**MySQL 8.0 组提交流程**:

```
┌────────────────────────────────────────────────────────────────┐
│                    Group Commit 三阶段                          │
│                                                                │
│  Stage 1 (Flush):    多个事务共享一次 redo log flush            │
│  Stage 2 (Sync):     多个事务共享一次 fsync                     │
│  Stage 3 (Commit):   多个事务同时提交,释放锁                    │
│                                                                │
│  同一阶段的事务组,共享一次 IO,显著提升高并发提交性能            │
└────────────────────────────────────────────────────────────────┘
```

**配置**:

```ini
# 8.0+ 默认开启
binlog_group_commit_sync_delay = 0       # 同步前等待微秒(累积更多事务)
binlog_group_commit_sync_no_delay_count = 0
```

## 七、undo log (回滚日志)

### 1. 作用

undo log 是 InnoDB 引擎层的逻辑日志,记录 **数据修改前的镜像**。它有两个核心作用:

```
┌──────────────────────────────────────────────────────────────────┐
│                    undo log 的两大作用                            │
│                                                                  │
│   1. 事务回滚 (Rollback)                                          │
│      - 事务未提交时,使用 undo log 撤销修改                        │
│      - 是 ACID 中 A (Atomicity) 的实现基础                        │
│                                                                  │
│   2. MVCC (Multi-Version Concurrency Control)                    │
│      - 读已提交 (RC) 与可重复读 (RR) 隔离级别依赖 undo log         │
│      - 提供快照读(snapshot read)能力                              │
└──────────────────────────────────────────────────────────────────┘
```

### 2. undo log 格式

| 类型             | 触发动作 | 何时删除                       |
|------------------|----------|--------------------------------|
| **insert undo log** | INSERT  | 事务提交后可立即删除            |
| **update undo log** | UPDATE / DELETE | 不能立即删除(可能用于 MVCC) |

**update undo log 内容**:

```
┌──────────────────────────────────────────────────┐
│  UPDATE user SET name='B' WHERE id=1;            │
│                                                  │
│  undo log 记录:                                    │
│  - trx_id (事务ID)                                │
│  - 主键 + 被修改列的旧值(用于定位行 + 还原数据)    │
│  - prev_version (指向更老版本的 undo log)         │
│  - 主键索引 + 二级索引的修改记录                  │
└──────────────────────────────────────────────────┘
```

### 3. undo log 在 MVCC 中的作用

**MVCC 机制下,读已提交/可重复读的读视图 (Read View) 拼接方式**:

```
  当前活跃事务列表: [T1, T3]
  自己的 trx_id: T5
  读视图的 up_limit_id: T1(最早活跃事务)
  读视图的 low_limit_id: T5(自己的下一个)
  
  ─────────────────────────────────────────────────
  数据的不同版本链(undo log 链接):
  
  最新数据(Buffer Pool 中)        trx_id = T5 (自己修改)
       │
       │  通过 undo log 回滚指针
       ▼
  之前版本                       trx_id = T3 (已提交)
       │
       │  通过 undo log 回滚指针
       ▼
  更老版本                       trx_id = T1 (已提交)
       │
       │  通过 undo log 回滚指针
       ▼
  最老版本                       trx_id = T0 (已提交)
  
  ─────────────────────────────────────────────────
  MVCC 读取规则:
  1. trx_id == 自己的 trx_id  → 可见(自己改的)
  2. trx_id < up_limit_id    → 可见(早于活跃事务)
  3. trx_id >= low_limit_id  → 不可见(未来事务)
  4. trx_id 在活跃列表中      → 不可见
  5. 其他情况                → 不可见,沿 undo 链找更老版本
```

### 4. 回滚段 (Rollback Segment)

undo log 按 **回滚段** 组织管理。

```
┌──────────────────────────────────────────────────────────────────┐
│                     回滚段结构                                    │
│                                                                  │
│  InnoDB(默认 128 个回滚段,8.0+ 可配置最多 128)                   │
│     │                                                            │
│     ├── Rollback Segment 1                                       │
│     │     ├── Undo Slot 1                                        │
│     │     ├── Undo Slot 2                                        │
│     │     └── ...                                                │
│     ├── Rollback Segment 2                                       │
│     │     ├── Undo Slot 1                                        │
│     │     └── ...                                                │
│     └── ...                                                      │
│                                                                  │
│  每个回滚段最多支持 1024 个事务并发                                │
└──────────────────────────────────────────────────────────────────┘
```

**配置**:

```ini
innodb_undo_directory = /var/lib/mysql/      # undo 文件目录
innodb_undo_tablespaces = 2                   # undo 表空间数(默认 2)
innodb_undo_logs = 128                        # 回滚段数量(默认 128)
innodb_max_undo_log_size = 1G                 # 单个 undo 表空间阈值
innodb_purge_rseg_truncate_frequency = 128    # 收缩 undo 表空间的频率
```

### 5. purge 机制

**purge 线程** 负责清理不再需要的 undo log:

- **insert undo log**:事务提交后立即可以清理
- **update undo log**:需要等待 **所有 Read View** 都不再引用该版本后才能清理

```
┌─────────────────────────────────────────────────────────────────┐
│                      purge 触发条件                              │
│                                                                 │
│   1. 每秒由后台 purge 线程定期执行                               │
│   2. 批量清理,避免频繁 IO                                       │
│   3. 控制参数:innodb_purge_threads(默认 4)                      │
│   4. 与系统表空间收缩配合,避免 undo 表空间膨胀                   │
└─────────────────────────────────────────────────────────────────┘
```

**查看 purge 状态**:

```sql
SHOW ENGINE INNODB STATUS\G
-- 在 TRANSACTIONS 部分查找:
-- History list length 12    -- 表示还有 12 个 undo log 未清理
```

### 6. undo 表空间管理 (8.0+)

```sql
-- 创建独立的 undo 表空间(8.0+ 推荐)
CREATE UNDO TABLESPACE undo_003 ADD DATAFILE 'undo_003.ibu';

-- 删除(需先设为 inactive)
ALTER UNDO TABLESPACE undo_003 SET INACTIVE;
DROP UNDO TABLESPACE undo_003;

-- 查看
SELECT * FROM INFORMATION_SCHEMA.INNODB_TABLESPACES
WHERE NAME LIKE 'innodb_undo%';
```

## 八、binlog 与 redo log 的两阶段提交 (XA/2PC)

### 1. 为什么需要两阶段提交

**场景**:事务提交时,需要同时保证 **Server 层 binlog** 与 **引擎层 redo log** 一致。

**问题**:

- 若先写 binlog,后写 redo log:binlog 已落盘,redo log 写失败 → 从库可能执行(看到 binlog),但主库重启后丢失该事务 → **主从数据不一致**
- 若先写 redo log,后写 binlog:redo log 已落盘,binlog 写失败 → 主库重启后 redo log 重做该事务(数据存在),但从库没收到 binlog → **从库数据丢失**

**解决方案**:**两阶段提交 (Two-Phase Commit, 2PC / XA)**。

### 2. 两阶段提交时序图

```
┌──────────────────────────────────────────────────────────────────────────┐
│                          两阶段提交时序图                                 │
│                                                                          │
│  Client         MySQL Server        InnoDB        OS/Disk                │
│    │                │                 │              │                     │
│    │  UPDATE        │                 │              │                     │
│    │ ──────────────►│                 │              │                     │
│    │                │ 准备事务        │              │                     │
│    │                │ ──────────────► │              │                     │
│    │                │                 │ 写 undo log  │                     │
│    │                │                 │ 修改 Buffer  │                     │
│    │                │                 │ 写 redo log  │                     │
│    │                │                 │   buffer     │                     │
│    │                │ ◄────────────── │              │                     │
│    │                │                 │              │                     │
│    │                │ COMMIT          │              │                     │
│    │                │ ──────────────► │              │                     │
│    │                │                 │              │                     │
│    │                │ ────── Phase 1: Prepare ──────►│                     │
│    │                │                 │              │                     │
│    │                │  写 binlog      │              │                     │
│    │                │  (cache → file) │              │                     │
│    │                │                 │              │                     │
│    │                │  标记 redo log  │              │                     │
│    │                │  为 Prepare 状态 │              │                     │
│    │                │                 │              │                     │
│    │                │ ────── Phase 2: Commit ───────►│                     │
│    │                │                 │              │                     │
│    │                │  fsync binlog   │              │                     │
│    │                │  (sync_binlog)  │              │                     │
│    │                │                 │              │                     │
│    │                │  标记 redo log │              │                     │
│    │                │  为 Commit      │              │                     │
│    │                │                 │              │                     │
│    │                │ ◄───────────────────── 全部完成 │                     │
│    │                │                 │              │                     │
│    │  COMMIT OK     │                 │              │                     │
│    │ ◄───────────── │                 │              │                     │
│    │                │                 │              │                     │
│                                                                          │
│  时间轴:                                                                  │
│  T1: BEGIN                                                               │
│  T2: SQL 执行,Buffer Pool 修改,redo log buffer 写入                       │
│  T3: COMMIT 触发                                                          │
│  T4: 准备阶段 - 写 binlog 到 cache,标记 redo 为 prepare                  │
│  T5: 提交阶段 - binlog fsync 落盘,redo log 标记 commit                  │
│  T6: 返回客户端 OK                                                         │
└──────────────────────────────────────────────────────────────────────────┘
```

### 3. 关键阶段详解

```
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  ┌─────────────┐                                                        │
│  │  Prepare 阶段 │  Server 层:                                            │
│  │              │  - 写 binlog 到 binlog cache                          │
│  │              │  - 将 binlog cache 写入 binlog file                    │
│  │              │  - 按 sync_binlog 决定是否 fsync                       │
│  │              │                                                        │
│  │              │  InnoDB 层:                                             │
│  │              │  - 将 redo log buffer 写入 redo log file              │
│  │              │  - 写入 prepare 标记(MTR commit)                      │
│  │              │  - 事务仍处于"未最终提交"状态                          │
│  │              │                                                        │
│  └─────────────┘                                                        │
│           │                                                              │
│           ▼                                                              │
│  ┌─────────────┐                                                        │
│  │  Commit 阶段  │  Server 层:                                            │
│  │              │  - binlog 完成 fsync                                  │
│  │              │                                                        │
│  │              │  InnoDB 层:                                             │
│  │              │  - redo log 写入 commit 标记                          │
│  │              │  - 释放锁、提交事务                                    │
│  │              │                                                        │
│  └─────────────┘                                                        │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### 4. 崩溃恢复时的处理

MySQL 重启时,扫描 redo log,根据 binlog 是否落盘判断处理方式:

```
┌──────────────────────────────────────────────────────────────────────┐
│                  崩溃恢复逻辑                                         │
│                                                                      │
│  场景 1: binlog 已落盘,redo log 也已落盘                              │
│   → 事务已成功提交,提交给用户,但崩溃在 commit 标记前                   │
│   → 修复:redo log 标记为 commit,事务生效(从库可能未应用,需保证一致)   │
│                                                                      │
│  场景 2: binlog 未落盘,redo log 已 prepare                            │
│   → 事务未真正提交,需要回滚                                            │
│   → 修复:undo log 回滚该事务,redo log 标记为 abort                    │
│                                                                      │
│  场景 3: binlog 已落盘,redo log 处于 prepare 但未 commit               │
│   → 事务已复制到从库,需保证主库也提交                                  │
│   → 修复:redo log 标记为 commit                                       │
│                                                                      │
│  场景 4: redo log 未落盘                                              │
│   → 事务没提交,直接忽略                                                │
│                                                                      │
│  结论:两阶段提交保证了 binlog 与 redo log 的强一致性                  │
└──────────────────────────────────────────────────────────────────────┘
```

### 5. 查看 prepare/commit 状态

```bash
# 使用 mysqlbinlog 查看包含 XA 标记的事务
mysqlbinlog --verbose /var/lib/mysql/mysql-bin.000001 | grep -A 2 "XA"

# 输出示例:
# XA START X'78696431...', X'31302e32372e313030'
# XA END X'78696431...', X'31302e32372e313030'
# XA PREPARE X'78696431...', X'31302e32372e313030'
# XA COMMIT X'78696431...', X'31302e32372e313030'
```

## 九、主从复制中的 relay log

### 1. relay log 概述

**relay log** 是从库接收主库 binlog 后写入的中转日志,由 SQL 线程读取并执行。它与 binlog 结构类似,但仅存在于从库。

```
┌──────────────────────────────────────────────────────────────────────┐
│                        主从复制全流程                                 │
│                                                                      │
│   ┌──────────┐    binlog    ┌──────────┐   relay log   ┌──────────┐ │
│   │  Master  │  ──────────► │ Network  │  ──────────►  │  Slave   │ │
│   │          │              │  (TCP)   │               │          │ │
│   │          │              │          │               │          │ │
│   │  binlog  │              │          │   SQL 线程     │  应用    │ │
│   │  dump    │              │          │   ──────────► │  数据    │ │
│   │  线程    │              │          │               │          │ │
│   └──────────┘              │          │               └──────────┘ │
│                             │          │                              │
│                       ┌──────▼──────┐                                 │
│                       │  I/O 线程    │                                 │
│                       │  拉取 binlog │                                 │
│                       │  写入 relay  │                                 │
│                       │  log         │                                 │
│                       └─────────────┘                                 │
└──────────────────────────────────────────────────────────────────────┘
```

### 2. 配置 relay log

```ini
# 从库 my.cnf
[mysqld]
server_id = 2                          # 必须唯一(与主库不同)

# relay log 配置
relay_log = /var/lib/mysql/relay-bin   # 中继日志文件前缀
relay_log_index = /var/lib/mysql/relay-bin.index
relay_log_info_repository = TABLE      # 8.0 推荐,记录在 mysql.slave_relay_log_info 表

# 自动清理
relay_log_purge = ON                   # 自动清理(默认 ON)
relay_log_recovery = ON                # 故障后自动重定位

# 多线程复制
slave_parallel_workers = 4             # 并行回放线程数(8.0+)
slave_parallel_type = LOGICAL_CLOCK    # 8.0 推荐基于组提交并行
```

### 3. relay log 与 binlog 的关系

| 维度           | binlog                              | relay log                          |
|----------------|-------------------------------------|-------------------------------------|
| 位置           | 主库                                | 从库                                |
| 内容           | 主库的所有数据变更                   | 主库 binlog 的副本                  |
| 写入           | 主库 dump 线程                      | 从库 I/O 线程                       |
| 读取           | 从库 I/O 线程                       | 从库 SQL 线程                       |
| 是否可关闭     | 是(影响复制与恢复)                  | 是(`skip_slave_start` 等)           |
| 清理           | `expire_logs_days`                  | `relay_log_purge = ON`              |

### 4. relay log 的查看

```sql
-- 从库:查看当前 relay log 应用状态
SHOW SLAVE STATUS\G
-- 重点字段:
-- Relay_Master_Log_File: 主库的 binlog 文件
-- Exec_Master_Log_Pos:   已应用的 binlog 位置
-- Relay_Log_File:        当前的 relay log 文件
-- Relay_Log_Pos:         当前的 relay log 位置
-- Seconds_Behind_Master: 复制延迟(秒)

-- 8.0.22+ 用 SHOW REPLICA STATUS(语义更明确)
SHOW REPLICA STATUS\G
```

### 5. relay log 的清理

```sql
-- 手动清理
PURGE RELAY LOGS BEFORE '2024-01-15 00:00:00';
PURGE RELAY LOGS TO 'relay-bin.000010';

-- 自动清理
SET GLOBAL relay_log_purge = ON;
-- 由 slave 启动时自动检查并清理(默认行为)

-- 重置复制(清空 relay log 和复制信息)
RESET SLAVE;        -- 8.0.22 前
RESET REPLICA;      -- 8.0.22+
```

### 3. 慢查询日志的轮转

### 2. 关键调优参数速查

```ini
innodb_flush_log_at_trx_commit = 1        # 安全;特殊场景可用 2

# ========== 慢查询调优 ==========
slow_query_log = ON
long_query_time = 1                       # 推荐 0.5-2s
log_slow_extra = ON

# ========== 通用日志(默认关闭) ==========

```

### 3. 调优场景参考

#### 场景 1:金融/支付(强一致)

```ini
sync_binlog = 1

expire_logs_days = 30                    # 长保留便于审计
```

#### 场景 2:互联网高并发(可少量丢)

```ini
sync_binlog = 100

binlog_format = ROW
innodb_log_file_size = 4G                # 大日志减少切换
```

#### 场景 3:从库 / 备库(性能优先)

### 4. innodb_flush_method 优化

```ini
innodb_flush_method = O_DIRECT           # 推荐,绕过 OS cache,减少双缓冲
# 备选: fsync(默认)、O_DSYNC、ALL_O_DIRECT
```

**O_DIRECT 优势**:

- 跳过 OS page cache,避免双缓冲
- 减少内存占用
- 数据直达磁盘

> 注意:在某些文件系统和内核版本上 O_DIRECT 可能有问题,需测试后启用。

| `Seconds_Behind_Master`               | < 30                | 复制延迟         |

## 十二、实战排查案例

### 案例 1:主从数据不一致

**现象**:从库 `Seconds_Behind_Master = 0`,但数据仍不一致。

**排查步骤**:

```bash
# 1. 用 mysqlbinlog 对比 binlog 是否一致
mysqlbinlog --read-from-remote-server --host=master --user=repl --password=xxx \
            --raw --stop-never mysql-bin.000100 > /tmp/master.binlog

# 2. 对比主从 binlog 位点
# 主库:
SHOW MASTER STATUS;
# 从库:
SHOW SLAVE STATUS\G
# 对比 Relay_Master_Log_File + Exec_Master_Log_Pos

# 3. 使用 pt-table-checksum 检测差异
pt-table-checksum h=master,u=checksum_user,p=xxx --databases=mydb

# 4. 使用 pt-table-sync 修复
pt-table-sync --print h=slave,u=sync_user,p=xxx
```

### 案例 2:慢查询突增

**现象**:应用响应变慢,慢查询日志暴涨。

**排查步骤**:

```bash
# 1. 实时查看慢查询
tail -f /var/log/mysql/slow.log

# 2. pt-query-digest 立即分析
pt-query-digest --since '5 minutes ago' /var/log/mysql/slow.log

# 3. 检查 performance_schema
SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1000000000 AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;

# 4. 检查 EXPLAIN
EXPLAIN ANALYZE <your_slow_sql>;
```

### 案例 3:磁盘被 binlog 撑满

**现象**:`expire_logs_days` 已设置但磁盘仍满。

**排查**:

```bash
# 查看所有 binlog
ls -lh /var/lib/mysql/mysql-bin.*
mysql -e "SHOW BINARY LOGS;"

# 立即清理
mysql -e "PURGE BINARY LOGS BEFORE NOW() - INTERVAL 7 DAY;"

# 检查主从复制是否正在读取
mysql -e "SHOW SLAVE STATUS\G"  # 看 Relay_Master_Log_File
```

### 案例 4:redo log 切换导致性能抖动

**现象**:业务周期性出现几十毫秒延迟。

**排查**:

```sql
-- 查看 checkpoint 与 write pos 差值
SHOW ENGINE INNODB STATUS\G
-- 看 Log sequence number / Last checkpoint at
-- 若差值 > 70% innodb_log_file_size,说明日志压力大
```

**优化**:

```ini
# 增大 redo log 文件大小
innodb_log_file_size = 4G          # 默认 2G(8.0+)
innodb_log_files_in_group = 2
```

## 十三、核心要点速记

### 1. 七大日志速记表

| 日志       | 层级       | 默认开启 | 关键参数                          | 速记                       |
|------------|------------|----------|-----------------------------------|----------------------------|
| 错误日志   | Server     | 是       | `log_error`                       | 启动/错误,**始终开启**     |
| 慢查询日志 | Server     | 否       | `slow_query_log`, `long_query_time` | 性能调优                  |
| 通用日志   | Server     | 否       | `general_log`                     | **生产不要开**              |
| binlog     | Server     | 否(建议) | `log_bin`, `binlog_format=ROW`    | 复制 + 恢复                 |
| redo log   | InnoDB     | 是       | `innodb_log_file_size`            | WAL,持久性                 |
| undo log   | InnoDB     | 是       | `innodb_undo_tablespaces`         | 回滚 + MVCC                |
| relay log  | Server(从) | 否       | `relay_log`                       | 从库中转                   |

### 2. WAL 机制速记

- **WAL = Write-Ahead Logging**
- 先写 redo log 再刷数据页
- `innodb_flush_log_at_trx_commit = 1` 是 **ACID 中 D 的真正保证**
- redo log 顺序写,数据页随机写;**用顺序 IO 换随机 IO**

### 3. 两阶段提交速记

```
Prepare 阶段: 写 binlog + redo log 标记 prepare
Commit 阶段:  binlog fsync + redo log 标记 commit
崩溃恢复:
  binlog 有 + redo 有 prepare → redo 标 commit
  binlog 无 + redo 有 prepare → undo 回滚
```

### 4. 三大日志格式速记

- **STATEMENT**:记 SQL,小不安全(已不推荐)
- **ROW**:记行,大但安全(**强烈推荐**)
- **MIXED**:STATEMENT 优先,特殊用 ROW

### 5. 调优速记

- **金融场景**:`sync_binlog=1`, `flush_log=1`, ROW 格式
- **互联网高并发**:`sync_binlog=100`, `flush_log=2`
- **从库**:`log_slave_updates=OFF`, `relay_log_purge=ON`
- **`Binlog_cache_disk_use` 必须为 0**,否则调大 `binlog_cache_size`
- **`Innodb_log_waits` 必须为 0**,否则调大 `innodb_log_buffer_size`

### 6. 关键命令速记

```bash
# 查看错误日志路径
SHOW VARIABLES LIKE 'log_error';

# 开启慢查询
SET GLOBAL slow_query_log = ON;

# 解析 binlog
mysqlbinlog -v mysql-bin.000001

# 清理 binlog
PURGE BINARY LOGS BEFORE '2024-01-01';

# 清理 relay log
PURGE RELAY LOGS BEFORE '2024-01-01';

# 查看 redo log 状态
SHOW ENGINE INNODB STATUS\G
```

### 7. 一句话总结

- **binlog** 解决复制与恢复,**redo log** 解决持久性,**undo log** 解决原子性 + MVCC,**两阶段提交**解决两者一致性。
- **WAL** 是核心思想:**先写日志,再写磁盘**。
- **生产推荐**:`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`、`binlog_format=ROW`、`sync_relay_log=1`。
- **监控告警**:binlog 容量、redo log 等待、History list length、Seconds_Behind_Master。
