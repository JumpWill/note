# MySQL 锁机制 (Lock Mechanism)

## 一、锁概述

### 1. 为什么需要锁

数据库是一个**多用户并发访问**的系统,同一时刻可能有上百个事务在读写同一张表。如果没有锁的保护,**数据一致性**将彻底崩塌。

锁的核心使命是:**在并发访问下,保证数据的正确性、隔离性与一致性**。

```text
                       并发访问的典型问题

   事务 A                            事务 B
     │                                  │
     ├── SELECT balance FROM account    │
     │   WHERE id = 1;   -- 读到 100    │
     │                                  ├── UPDATE account
     │                                  │   SET balance = 50
     │                                  │   WHERE id = 1;
     ├── UPDATE account                │
     │   SET balance = balance - 30    │   ← 已读到旧值 100
     │   WHERE id = 1;                 │
     │                                  │
     ▼                                  ▼
   最终 balance = 70 (期望)
   实际 balance = 20 (丢失更新!)
```

### 2. 并发事务带来的问题

| 问题         | 英文                | 含义                                       | 典型场景                            |
|--------------|---------------------|--------------------------------------------|-------------------------------------|
| **脏读**     | Dirty Read          | 读到其他事务**未提交**的数据               | A 改了未提交,B 读到了,A 回滚 → B 读到假数据 |
| **不可重复读** | Non-repeatable Read | 同一行,**两次读**结果不一致                | A 读 → B 改 → A 再读,值变了       |
| **幻读**     | Phantom Read        | 同一查询,**两次范围读**记录数不一致         | A 查 10 条 → B 插入 1 条 → A 再查 11 条 |
| **丢失更新** | Lost Update         | 两个事务都基于旧值更新,后者覆盖前者       | 并发扣库存、并发转账                |

### 3. SQL 标准的事务隔离级别

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;
-- MySQL 8.0 默认: REPEATABLE READ
```

| 隔离级别                | 脏读 | 不可重复读 | 幻读 | 锁实现 |
|-------------------------|------|-----------|------|--------|
| **READ UNCOMMITTED**    | ✔    | ✔         | ✔    | 几乎不加锁 |
| **READ COMMITTED**      | ✘    | ✔         | ✔    | 行锁 + 读快照 |
| **REPEATABLE READ** ★   | ✘    | ✘         | ✔(InnoDB 靠 Next-Key Lock 解决) | 行锁 + MVCC + Gap Lock |
| **SERIALIZABLE**        | ✘    | ✘         | ✘    | 全表锁,接近单线程 |

> **MySQL InnoDB 默认 REPEATABLE READ**,通过 **Next-Key Lock** 在很大程度上避免了幻读(并非完全杜绝)。

### 4. 锁 vs MVCC

- **MVCC (Multi-Version Concurrency Control)**:无锁读,读快照,适合**读多写少**
- **锁**:阻塞式同步,适合**写并发**场景

InnoDB = **MVCC + 锁** 的混合实现:**SELECT 默认走 MVCC(快照读)**,**写操作 + 部分 SELECT 走锁(当前读)**。

## 二、锁分类总览

MySQL 的"锁"是一个庞大的体系,可以按多个维度划分。

### 1. 按粒度划分

```text
                            MySQL 锁
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
    全局锁                表级锁                 行级锁 (InnoDB)
  (Global Lock)      (Table Lock)              (Row Lock)
        │                     │                     │
   FLUSH TABLES        ┌───────┼───────┐      ┌──────┼──────┐
   WITH READ LOCK      │       │       │      │      │      │
                      表锁   元数据锁  意向锁   行锁   间隙锁  临键锁
                            (MDL)   (IS/IX)         (Gap)  (Next-Key)
```

| 粒度   | 引擎           | 开销 | 并发度 | 死锁概率 | 适用 |
|--------|----------------|------|--------|----------|------|
| 全局锁 | MyISAM/InnoDB  | 大   | 极低   | 低       | 全库备份(慎用) |
| 表级锁 | MyISAM/InnoDB  | 中   | 低     | 低       | DDL、整表维护 |
| 行级锁 | **InnoDB**     | 大   | 高     | 高       | OLTP 默认 |

### 2. 按类型划分(共享/排他)

| 类型     | 英文           | 简称 | 别称     | 兼容性 |
|----------|----------------|------|----------|--------|
| **共享锁** | Shared Lock   | **S** | 读锁     | S 与 S 兼容,其他互斥 |
| **排他锁** | Exclusive Lock | **X** | 写锁     | 与所有互斥 |

### 3. 按意向划分(InnoDB)

| 锁       | 英文                | 作用对象 |
|----------|---------------------|----------|
| **意向共享锁** | Intention Shared | IS | 表级,表示"事务打算给某些行加 S 锁" |
| **意向排他锁** | Intention Exclusive | IX | 表级,表示"事务打算给某些行加 X 锁" |

### 4. 按算法划分(InnoDB 行锁)

| 算法                  | 英文             | 锁的范围                |
|-----------------------|------------------|-------------------------|
| **记录锁**            | Record Lock      | 单个索引记录             |
| **间隙锁**            | Gap Lock         | 索引记录之间的间隙,**不含当前记录** |
| **临键锁** ★          | Next-Key Lock    | **记录 + 间隙**(左开右闭) |
| **插入意向锁**        | Insert Intention | 插入时的特殊间隙锁       |

### 5. 一图概览

```text
                       MySQL 锁的全景
   ┌─────────────────────────────────────────────────┐
   │              全局锁 (FTWRL)                       │
   ├─────────────────────────────────────────────────┤
   │              表级锁                              │
   │  ┌─────────────┬──────────────┬───────────────┐ │
   │  │  表锁       │  MDL         │  意向锁 IS/IX  │ │
   │  │  (Lock Tables)│ (元数据锁)  │  (表级标记)    │ │
   │  └─────────────┴──────────────┴───────────────┘ │
   ├─────────────────────────────────────────────────┤
   │              行级锁 (InnoDB 核心)                 │
   │  ┌─────────┬─────────┬─────────────┬──────────┐ │
   │  │ Record  │ Gap     │ Next-Key    │ Insert   │ │
   │  │ Lock    │ Lock    │ Lock        │ Intention│ │
   │  └─────────┴─────────┴─────────────┴──────────┘ │
   ├─────────────────────────────────────────────────┤
   │              自增锁 AUTO-INC                       │
   └─────────────────────────────────────────────────┘
```

## 三、全局锁

### 1. 什么是全局锁

**全局锁**对**整个数据库实例**加锁,加锁后**所有写操作**(INSERT/UPDATE/DELETE/DDL)阻塞,**读操作**(SELECT)受配置影响。

### 2. 加锁命令

```sql
-- 加全局读锁
FLUSH TABLES WITH READ LOCK;     -- 简称 FTWRL

-- 释放
UNLOCK TABLES;
```

```bash
# mysqldump 使用 FTWRL 实现一致备份
mysqldump --single-transaction --master-data=2 mydb > dump.sql
# --single-transaction 靠 InnoDB 的 MVCC 实现一致性,无需 FTWRL
```

### 3. 应用场景

- **全库逻辑备份**:早期 MySQL 没有 `mysqldump --single-transaction` 时,只能 FTWRL
- **主从切换**:保证所有从库数据一致(极少用)
- **数据迁移**:避免迁移过程中数据被改

### 4. 危害

- **整个库只读**,业务中断
- **持有锁期间,所有写操作排队等待**,严重时导致连接堆积、雪崩
- 主库 FTWRL 后,主从延迟会瞬间拉大

### 5. 替代方案

| 方案                       | 适用         | 优点 |
|----------------------------|--------------|------|
| `mysqldump --single-transaction` | InnoDB 全库备份 | 不阻塞 DML,推荐 |
| `xtrabackup --backup`      | 物理备份     | 几乎不阻塞 |
| `SET GLOBAL read_only = ON` | 只读模式    | 不阻塞 DML,仅阻塞 DDL/DML |

```sql
-- 单事务一致性备份 (推荐)
mysqldump -uroot -p --single-transaction --master-data=2 \
  --databases mydb > mydb.sql
```

## 四、表级锁

表级锁是 MySQL 中粒度较大的锁,主要包括三类:**表锁**、**元数据锁 (MDL)**、**意向锁**。

### 1. 表锁 (Table Lock)

#### (1) 命令

```sql
-- 加表锁
LOCK TABLES table_name [AS alias] READ | WRITE;     -- READ = 共享, WRITE = 排他

-- 释放
UNLOCK TABLES;     -- 或断开连接自动释放
```

#### (2) 特点

- **MyISAM 引擎天然使用表锁**(无行锁能力)
- **InnoDB 一般不用表锁**(有性能更好的行锁),但仍支持
- 持有表锁时,**当前会话也不能访问其他未锁定的表**
- 写锁优先级高于读锁,排队容易写优先(starvation)

```sql
-- 案例:会话 A 加写锁
LOCK TABLES user WRITE;
SELECT * FROM user WHERE id = 1;
UPDATE user SET name = 'x' WHERE id = 1;
-- 此时其他会话无法读/写 user 表

UNLOCK TABLES;
```

#### (3) 监控表锁竞争

```sql
-- 查看表锁争用
SHOW STATUS LIKE 'Table_locks%';
-- Table_locks_immediate: 立即获取锁的次数
-- Table_locks_waited:    等待锁的次数(越大说明竞争越激烈)

-- 查看谁在持有表锁
SHOW OPEN TABLES WHERE In_use > 0;
```

### 2. 元数据锁 (MDL, Metadata Lock)

#### (1) 什么是 MDL

**MDL (Metadata Lock)** 是 MySQL 5.5 引入的,**不需要显式使用**,系统自动加上,**保证表结构与数据的一致性**。

#### (2) 加锁规则

| SQL 操作             | MDL 类型   | 说明 |
|---------------------|------------|------|
| `SELECT`             | MDL **SHARED_READ**  | 读 MDL 锁,允许多个读 |
| `INSERT/UPDATE/DELETE` | MDL **SHARED_WRITE** | 写 MDL 锁,允许多个写 |
| `ALTER TABLE`        | MDL **EXCLUSIVE**    | 排他锁,阻塞所有读写 |
| `FLUSH TABLES WITH READ LOCK` | MDL 全局 EXCLUSIVE | |

```text
MDL 兼容性矩阵 (类似读写锁):

                  SHARED_READ   SHARED_WRITE   EXCLUSIVE
SHARED_READ          ✔              ✔            ✘
SHARED_WRITE         ✔              ✔            ✘
EXCLUSIVE            ✘              ✘            ✘

★ 多读、多写可并发,但有写操作时 ALTER 阻塞
★ 有 ALTER 时,所有读写全部阻塞(关键!)
```

#### (3) MDL 的经典坑:ALTER 阻塞读写

```text
                MDL 阻塞典型案例

时间线:
T1: 会话 A: SELECT * FROM user;    (拿 MDL_SHARED_READ)
T2: 会话 B: ALTER TABLE user ADD COLUMN x INT;
                            (需要 MDL_EXCLUSIVE,等待 A)
T3: 会话 C: SELECT * FROM user WHERE id = 1;
                            (需要 MDL_SHARED_READ,但被 B 阻塞)
T4: 会话 D: INSERT INTO user ...;
                            (需要 MDL_SHARED_WRITE,也被 B 阻塞)
T5: 会话 E: SELECT * FROM user ...;
                            (全部阻塞 → 表"卡死" → 雪崩)
```

**后果**:表上**所有 SELECT/INSERT/UPDATE 全部排队**,新连接继续堆积,连接池打满,业务中断。

**应对**:

```bash
# 1. 找到阻塞的会话
SELECT * FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'mydb' AND OBJECT_NAME = 'user'\G

# 2. 杀掉阻塞会话
SELECT id, state, info FROM information_schema.processlist
WHERE info LIKE '%ALTER TABLE user%';
KILL <pid>;

# 3. 业务侧:大表 ALTER 加超时与重试,避免长时间阻塞
SET SESSION lock_wait_timeout = 30;     -- 等待 30s 自动放弃
```

> **MySQL 8.0** 起增加了 `ALTER TABLE ... NOWAIT` 选项,发现锁冲突立即报错而非等待。

## 五、行级锁详解

**行级锁**是 InnoDB 的灵魂,**只在 InnoDB (或 NDB) 引擎下存在**,粒度最小、并发度最高。

### 1. 行锁的两大类算法

| 算法            | 锁的范围                         | 触发条件 |
|-----------------|----------------------------------|----------|
| **Record Lock** | 单个索引记录                      | 等值查询命中唯一索引 |
| **Gap Lock**    | 索引记录之间的间隙(不含记录本身) | 范围查询、命中不唯一 |
| **Next-Key Lock** | Record + Gap(左开右闭区间)    | REPEATABLE READ 默认 |

### 2. Record Lock (记录锁)

```sql
-- 等值命中主键 → Record Lock
SELECT * FROM user WHERE id = 10 FOR UPDATE;
-- 仅锁住 id=10 这一行
```

```text
Record Lock 锁定的就是 B+Tree 叶子节点中的一条索引记录

         B+Tree 叶子节点 (某个数据页)

   ┌─────────────────────────────────────┐
   │ id=5 │ id=10 │ id=20 │ id=30 │ id=40 │
   └──────┴───────┴───────┴───────┴───────┘
                ▲
              Record Lock on id=10 (X)
```

### 3. Gap Lock (间隙锁)

```sql
-- 准备数据
CREATE TABLE t (id INT PRIMARY KEY, v INT);
INSERT INTO t VALUES (10, 1), (20, 2), (30, 3);
-- 表中 id: 10, 20, 30

-- REPEATABLE READ 隔离级别
BEGIN;
SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;
-- 锁住区间 (10, 20] 和 (20, 30),即 gap (10,20) 和 (20,30)
-- 其他事务无法在 (10, 30) 区间内插入新 id
```

```text
Gap Lock 锁定的"间隙"区间

  索引值:    10     20     30     40
            │      │      │      │
            ▼      ▼      ▼      ▼
       ┌────┬─────┬─────┬─────┬────┐
       │    │█████│█████│     │    │
       └────┴─────┴─────┴─────┴────┘
                  ▲     ▲
                  │     │
                Gap Lock 在 (10, 30) 之间

★ Gap Lock 不锁记录本身,只锁"间隙",目的是防止新插入
★ 间隙区间是左开右闭:(10, 20) 表示 (10, 20),不含 10, 含 20
```

**特点**:

- **Gap Lock 之间不互斥**:两个事务可以在**同一间隙**上都加 Gap Lock(都是"防止插入")
- **Gap Lock 只在 REPEATABLE READ 及以上才有**
- **READ COMMITTED 隔离级别下没有 Gap Lock**(MySQL 5.7+)

### 4. Next-Key Lock (临键锁) ★

```text
Next-Key Lock = Record Lock + Gap Lock

每个 Next-Key Lock 锁定的区间是 (前一个值, 当前值],即"左开右闭"

  假设索引值: 10, 20, 30, 40

  锁 id=20 的 Next-Key Lock:
    ┌────────────────────────────────────┐
    │   (10, 20]    ← Next-Key Lock       │
    │   ↑          ↑                      │
    │  间隙        记录                    │
    └────────────────────────────────────┘

  锁 id BETWEEN 15 AND 25 的 Next-Key Lock:
    ┌─────────────┬─────────────┐
    │  (10, 20]   │  (20, 30]   │   ← 两个 Next-Key Lock
    └─────────────┴─────────────┘
```

**Next-Key Lock 是 InnoDB 默认的 REPEATABLE READ 行锁算法**,它通过**锁住记录 + 锁住间隙**,从根本上避免了"幻读"。

```sql
-- 准备
CREATE TABLE t_gap (
    id  INT PRIMARY KEY,
    val VARCHAR(20)
);
INSERT INTO t_gap VALUES (10, 'a'), (20, 'b'), (30, 'c');

-- 会话 A
SET SESSION transaction_isolation = 'REPEATABLE-READ';
BEGIN;
SELECT * FROM t_gap WHERE id = 20 FOR UPDATE;
-- 此时在 (10, 20] 和 (20, 30) 上加 Next-Key Lock

-- 会话 B
BEGIN;
INSERT INTO t_gap VALUES (15, 'x');    -- ★ 被阻塞!在 (10, 20) 间隙内
INSERT INTO t_gap VALUES (25, 'y');    -- ★ 被阻塞!在 (20, 30) 间隙内
INSERT INTO t_gap VALUES ( 5, 'z');    -- ✔ 通过(5 < 10)
COMMIT;
```

## 六、共享锁(S Lock)与排他锁(X Lock)

这是**行级锁的最底层分类**,所有行锁算法都基于这两种模式。

### 1. 共享锁 (Shared Lock, S Lock)

- 又称**读锁**,允许事务读取一行
- **多个事务可以同时持有同一行的 S 锁**
- 但任何事务持有 S 锁时,**其他事务不能加 X 锁**(不能改)

```sql
-- 加共享锁
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;   -- MySQL 5.7
SELECT * FROM user WHERE id = 1 FOR SHARE;             -- MySQL 8.0 推荐
```

### 2. 排他锁 (Exclusive Lock, X Lock)

- 又称**写锁**,允许事务更新或删除一行
- 持有 X 锁时,**其他事务既不能加 S 锁也不能加 X 锁**

```sql
-- 加排他锁 (当前读)
SELECT * FROM user WHERE id = 1 FOR UPDATE;            -- 主流写法
SELECT * FROM user WHERE id = 1 FOR UPDATE NOWAIT;     -- 8.0+,锁不住立即报错
SELECT * FROM user WHERE id = 1 FOR UPDATE SKIP LOCKED; -- 8.0+,跳过已锁住的行
```

### 3. 行锁兼容矩阵

| 已持有 \ 申请 | **S Lock** | **X Lock** |
|---------------|------------|------------|
| **S Lock**    | ✔ 兼容     | ✘ 冲突     |
| **X Lock**    | ✘ 冲突     | ✘ 冲突     |

```text
锁兼容示意:

事务 A ──S──→  记录 R    S  R
事务 B ──S──→  记录 R    ✔ 允许(同时读)

事务 A ──S──→  记录 R
事务 B ──X──→  记录 R    ✘ 阻塞(等 A 释放)

事务 A ──X──→  记录 R
事务 B ──S──→  记录 R    ✘ 阻塞
事务 C ──X──→  记录 R    ✘ 阻塞
```

### 4. 快照读 vs 当前读

| 类型       | 实现     | 是否加锁 | 例子 |
|------------|----------|----------|------|
| **快照读** | MVCC     | **不加锁** | `SELECT * FROM user WHERE id = 1` |
| **当前读** | 锁       | 加 X/S 锁 | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT` |

```sql
-- 快照读 (默认)
SELECT * FROM user WHERE id = 1;          -- MVCC,不阻塞

-- 当前读
SELECT * FROM user WHERE id = 1 FOR UPDATE;   -- 加 X 锁,阻塞其他读写
UPDATE user SET name = 'x' WHERE id = 1;      -- 隐式当前读
DELETE FROM user WHERE id = 1;                -- 隐式当前读
INSERT INTO user (...) VALUES (...);          -- 隐式当前读
```

## 七、意向锁 (Intention Lock)

### 1. 为什么需要意向锁

假设事务 A 要给表中**某行**加 X 锁,事务 B 想**给整张表**加表锁(WRITE)。InnoDB 必须**快速判断**:表里是否已经有行被锁住了?

```text
问题场景:

事务 A: SELECT * FROM user WHERE id = 5 FOR UPDATE;
        -- 锁住了 user 表的 id=5 这一行

事务 B: LOCK TABLES user WRITE;
        -- 想锁整张 user 表
        -- 如果不知道 A 已经锁了 id=5,B 拿到表锁,A 也释放不了行锁
        -- → 死锁 / 矛盾

解决: 事务 A 在锁 id=5 的同时,顺便在表级别加一个"意向锁"
       表示"我打算锁这表里的某些行"
```

### 2. 两种意向锁

| 锁名     | 英文                | 含义 |
|----------|---------------------|------|
| **意向共享锁** | Intention Shared (IS)  | 事务**打算**给某些行加 S 锁 |
| **意向排他锁** | Intention Exclusive (IX) | 事务**打算**给某些行加 X 锁 |

```sql
-- 意向锁由 InnoDB 自动加,无需用户手动

-- SELECT ... LOCK IN SHARE MODE → 自动加 IS
-- SELECT ... FOR UPDATE        → 自动加 IX
-- INSERT/UPDATE/DELETE          → 自动加 IX
```

### 3. 完整锁兼容矩阵

```text
申请 ─→          S    X    IS    IX
已持 ↓
  S              ✔    ✘    ✔     ✘
  X              ✘    ✘    ✘     ✘
  IS             ✔    ✘    ✔     ✔
  IX             ✘    ✘    ✔     ✔

★ 表级: X 与所有冲突,S 仅与 X 冲突
★ 意向锁 IS/IX 之间互相兼容,它们只是"声明"
★ 意向锁 IX 与行级 X 锁兼容(IX 是表级声明,X 是行级真实锁)
```

**说明**:

- **IX 与 IX 兼容**:两个事务都想改不同行,允许
- **IS 与 IS 兼容**:两个事务都想读不同行,允许
- **IX 与 IS 兼容**:A 想改,B 想读(不同行),允许
- **X 与任何都冲突**:行级写锁是"真锁",别人不能动
- **S 与 IX 冲突**:A 想读全表,B 想改行 → B 的 IX 让 A 的 S 阻塞

### 4. 加锁流程(以事务 A `FOR UPDATE` 为例)

```text
事务 A: SELECT * FROM user WHERE id = 5 FOR UPDATE;

Step 1: 自动在 user 表上加 IX (Intention Exclusive)
Step 2: 在 id=5 这条索引记录上加 Record X Lock

完整锁状态:
  user 表:   IX
  id=5 行:   X (Record Lock)
```

## 八、插入意向锁 (Insert Intention Lock)

### 1. 什么是插入意向锁

**Insert Intention Lock** 是一种特殊的**间隙锁 (Gap Lock)**,由 `INSERT` 操作在插入位置加上,表示"我打算在这个间隙插入新行"。

### 2. 与普通 Gap Lock 的区别

| 维度     | Gap Lock              | Insert Intention Lock       |
|----------|-----------------------|-----------------------------|
| 触发     | `SELECT ... FOR UPDATE` (范围) | `INSERT`                |
| 作用     | 阻塞 INSERT           | 标记"我要插入这里"          |
| 冲突     | 与 INSERT 冲突        | 与 Gap Lock / 记录锁冲突    |
| 兼容性   | 不同事务可同时加      | 不同事务可同时加(不同位置)  |

### 3. 案例:插入意向锁导致的等待

```sql
-- 数据准备
CREATE TABLE t (id INT PRIMARY KEY, v INT);
INSERT INTO t VALUES (10, 1), (30, 3);
-- 索引间隙: (10, 30)

-- 会话 A (RR 隔离)
SET SESSION transaction_isolation = 'REPEATABLE-READ';
BEGIN;
SELECT * FROM t WHERE id BETWEEN 10 AND 30 FOR UPDATE;
-- 加 Next-Key Lock: (10, 30] 和 (30, +∞)

-- 会话 B
BEGIN;
INSERT INTO t VALUES (20, 2);
-- ★ 在 (10, 30) 间隙加 Insert Intention Lock,被 A 的 Gap Lock 阻塞
-- 等待状态: lock_wait_timeout 默认 50s

COMMIT;
-- A 提交后,B 自动唤醒
```

```text
插入意向锁的阻塞示意:

  索引:        10       30
              │        │
   会话 A:    ████ (10,30] Next-Key Lock
              ▲
              │
   会话 B:   在 (10,30) 内 INSERT id=20
              │
              └── 加 Insert Intention Lock
                  → 等待 A 的 Gap Lock 释放
```

### 4. 关键点

- **Insert Intention Lock 之间不互斥**(在不同位置插入)
- **Insert Intention 与 Gap Lock 冲突**(这是阻塞的根源)
- 唤醒后,**插入操作要再检查唯一约束**(避免唯一键冲突)

## 九、自增锁 (AUTO-INC Lock)

### 1. 什么是自增锁

**AUTO-INC Lock** 是一种特殊的**表级锁**,加在执行 `INSERT` 的表上,保证自增列(`AUTO_INCREMENT`)的值**单调递增、连续不重复**。

### 2. 锁模式 (`innodb_autoinc_lock_mode`)

| 模式  | 名称               | 行为 | 优缺点 |
|-------|--------------------|------|--------|
| **0** | traditional        | 所有 INSERT 加 AUTO-INC 锁,语句结束释放 | 连续性最好,**并发最差** |
| **1** | consecutive (默认) | 普通 INSERT 加锁,结束后释放;bulk insert 预留连续区间 | 平衡,**5.7 默认** |
| **2** | interleaved        | **不加锁**,由 binlog 决定顺序;多个 INSERT 可并发获取自增值 | **并发最高**,但自增值**不连续** |

```sql
-- 查看当前模式
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';

-- MySQL 8.0 默认值: 2
```

### 3. 三种模式的对比

```text
模式 0:  ┌─ T1 INSERT ─┐  ┌─ T2 INSERT ─┐
         │ 持 AUTO-INC  │  │ 等待...      │
         └──────────────┘  └──────────────┘
         自增值: 1, 2, 3, 4 (完全连续)

模式 1:  ┌─ T1 INSERT ─┐  ┌─ T2 INSERT ─┐
         │ 持 AUTO-INC  │  │ 等待...      │
         │ (拿 1~10)    │  │ (拿 11~20)   │
         └──────────────┘  └──────────────┘
         自增值: 1~10, 11~20 (区间内连续)

模式 2:  ┌─ T1 INSERT ─┐┌─ T2 INSERT ─┐
         │ 1, 3, 5...   ││ 2, 4, 6...   │
         └──────────────┘└──────────────┘
         自增值: 1, 2, 3, 4 (交错,不保证连续)
```

### 4. 实际表现

```sql
-- 模式 2 下,rollback 不会回滚自增值
INSERT INTO user(name) VALUES ('a');    -- id=1
ROLLBACK;
INSERT INTO user(name) VALUES ('b');    -- id=3 (不是 2)
```

### 5. 复制场景的注意事项

- **基于语句的复制 (Statement-Based)**:必须使用模式 0 或 1,保证主从自增值一致
- **基于行的复制 (Row-Based)**:可以使用模式 2
- **MySQL 8.0 默认 Row-Based + 模式 2**,并发度最高

## 十一、死锁的产生与排查

### 1. 什么是死锁

**死锁 (Deadlock)**:两个或多个事务**互相等待对方释放锁**,形成循环等待,**永远无法继续**。

```text
                    死锁的循环等待

       事务 A                    事务 B
          │                         │
          ├─ 持有 lock_1            │
          │                         ├─ 持有 lock_2
          │                         │
          ├─ 等待 lock_2 ─────→    │
          │                         │
          │      ←───── 等待 lock_1 ┤
          │                         │
          ▼                         ▼
       谁都走不动 → InnoDB 自动回滚一个事务
```

### 2. InnoDB 的处理策略

InnoDB 自动检测死锁,发现后**主动回滚其中一个事务**(回滚代价最小的事务),让其他事务继续执行。

```sql
-- 被回滚的事务收到错误:
-- ERROR 1213 (40001): Deadlock found when trying to get lock;
--                     try restarting transaction
```

### 3. 死锁产生的四大必要条件

| 条件 | 含义 |
|------|------|
| **互斥** | 锁是排他的 |
| **持有并等待** | 事务持锁不放,继续申请新锁 |
| **不可剥夺** | 锁只能由持有者主动释放 |
| **循环等待** | 形成 T1 → T2 → T3 → ... → T1 |

### 4. 典型死锁案例(间隙锁)

```sql
-- 准备数据
CREATE TABLE t_dl (
    id  INT PRIMARY KEY,
    v   INT
);
INSERT INTO t_dl VALUES (10, 1), (20, 2), (30, 3);

SET SESSION transaction_isolation = 'REPEATABLE-READ';
```

```text
死锁场景 (两个事务互相请求对方的间隙锁):

会话 A (T_A)                          会话 B (T_B)
────────────────────────────────    ────────────────────────────────
BEGIN;                                BEGIN;
                                     
DELETE FROM t_dl                      DELETE FROM t_dl
WHERE id = 20;                        WHERE id = 30;
-- 加 Record X Lock on id=20
-- 加 Next-Key Lock on (10,20]
                                     
                                     -- 加 Record X Lock on id=30
                                     -- 加 Next-Key Lock on (20,30]

INSERT INTO t_dl                      
VALUES (15, 0);                       
-- 在 (10,20) 间隙加 Insert Intention
-- 但 A 已经锁住 (10,20],且持有 id=20
-- ★ 等待 B 释放? 不,A 是等待自己的 Gap Lock 释放? 
                                     
                                     INSERT INTO t_dl
                                     VALUES (25, 0);
                                     -- 在 (20,30) 间隙加 Insert Intention
                                     -- 等待 A 的 Gap Lock (10,20]

                                     -- 实际上,InnoDB 检测到死锁
                                     -- 回滚 B (B 报错: Deadlock found)

                                     ERROR 1213: Deadlock found
```

## 十二、锁等待与超时

### 1. 锁等待的流程

```text
锁等待的生命周期:

事务 T 申请锁
    │
    ▼
锁空闲? ── 是 ──→ 立即获取,继续执行
    │
    否(被持有)
    │
    ▼
进入等待队列 (innodb_lock_wait_timeout)
    │
    ▼
超时? ── 是 ──→ 报错 ERROR 1205:
    │           Lock wait timeout exceeded;
    │           try restarting transaction
    │
    否(锁被释放)
    │
    ▼
唤醒,获取锁,继续执行
```

### 2. innodb_lock_wait_timeout

```sql
-- 查看当前超时设置 (默认 50s)
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';

-- 设置 (SESSION 级别)
SET SESSION innodb_lock_wait_timeout = 10;

-- 设置 (GLOBAL 级别,谨慎)
SET GLOBAL innodb_lock_wait_timeout = 10;
```

| 参数 | 默认 | 含义 |
|------|------|------|
| `innodb_lock_wait_timeout` | 50 (秒) | 行锁等待超时时间 |
| `lock_wait_timeout` | 31536000 (1年) | 元数据锁 (MDL) 等待超时 |

### 3. 锁等待的查看与处理

```sql
-- 1. 找出正在等待的事务
SELECT
    trx_id,
    trx_state,
    trx_query,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS wait_sec
FROM information_schema.innodb_trx
WHERE trx_state = 'LOCK WAIT';

-- 2. 找出对应的 thread_id (用于 KILL)
SELECT
    trx_id,
    trx_mysql_thread_id AS thread_id
FROM information_schema.innodb_trx
WHERE trx_state = 'LOCK WAIT';

-- 3. KILL 等待线程 (注意:这会让该事务回滚,不会杀掉持锁线程)
KILL <thread_id>;
```

### 4. NOWAIT 与 SKIP LOCKED (8.0+)

```sql
-- NOWAIT: 拿不到锁立即报错,不等待
SELECT * FROM user WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR 3572 (HY000): Statement aborted because lock(s) could not be
--                     acquired immediately and NOWAIT is set.

-- SKIP LOCKED: 跳过已锁的行,只处理未锁的行
SELECT * FROM user WHERE age > 10
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- 任务队列场景:工人只拿没人做的任务
```

```text
SKIP LOCKED 典型应用:任务队列

┌──────────┐    ┌──────────┐    ┌──────────┐
│  Worker  │    │  Worker  │    │  Worker  │
│   A      │    │   B      │    │   C      │
└────┬─────┘    └────┬─────┘    └────┬─────┘
     │ 拿 task 1,3,5 │ 拿 task 2,4   │ 拿 task 6,7
     ▼               ▼               ▼
  ┌──────────────────────────────┐
  │     task_queue                │
  │  [1✓][2✓][3✓][4✓][5✓][6✓][7✓] │
  └──────────────────────────────┘

★ 多个 Worker 并行,各取未锁的 task,不互相等待
★ 经典实现:分布式任务调度、订单抢单
```

## 十三、锁的优化策略

### 1. 核心原则

```text
                  锁优化的"三条铁律"

   1. 索引用得好 → 锁粒度细、范围小、冲突少
   2. 事务短小 → 持有锁时间短,减少等待
   3. 隔离级别合理 → 在业务可接受范围内,用低隔离级别
```

### 2. 索引设计:让行锁精准,避免大范围锁

```sql
-- 反例:无索引导致锁全表
SELECT * FROM user WHERE name = '张三' FOR UPDATE;
-- name 没索引 → 全表扫描 → 锁住所有行(退化为表锁)

-- 正例:有索引 → 只锁一行
ALTER TABLE user ADD INDEX idx_name (name);
SELECT * FROM user WHERE name = '张三' FOR UPDATE;
-- 仅锁 name='张三' 的行
```

**索引与锁的关系**:

```text
没有索引:  SELECT ... FOR UPDATE
           ┌─────────────────────────────────┐
           │ 全表扫描 → 锁所有行 (退化为表锁)   │
           └─────────────────────────────────┘
                 性能极差,并发崩溃

有索引:    SELECT ... FOR UPDATE WHERE indexed_col = ?
           ┌─────────┐
           │ 仅锁该行 │
           └─────────┘
                 并发度高
```

### 3. 控制事务粒度:事务越小越好

```sql
-- 反例:事务中包含远程调用
BEGIN;
SELECT * FROM user WHERE id = 1 FOR UPDATE;
-- ... 这里调用了一个慢 HTTP 接口,耗时 3 秒 ...
UPDATE user SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- 正例:事务中只放数据库操作
BEGIN;
SELECT * FROM user WHERE id = 1 FOR UPDATE;
UPDATE user SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- 远程调用挪到事务外
```

```sql
-- 反例:大批量操作
BEGIN;
UPDATE user SET status = 1 WHERE type = 'A';   -- 100 万行,事务巨大
COMMIT;

-- 正例:分批提交
-- 循环:
UPDATE user SET status = 1 WHERE type = 'A' LIMIT 1000;
-- 每 1000 行一个事务,持锁时间短
```

### 4. 降低隔离级别

| 隔离级别      | 锁行为 | 适用场景 |
|---------------|--------|----------|
| **READ COMMITTED** | 无 Gap Lock,只锁命中记录 | 读多写少,可接受幻读 |
| **REPEATABLE READ**| 有 Gap Lock,锁范围大 | 默认,适合一致性要求高 |

```sql
-- 对一致性要求没那么高的报表业务
SET SESSION transaction_isolation = 'READ-COMMITTED';
-- 减少 Gap Lock,提高并发
```

### 5. 读写分离

```text
              主从读写分离架构

                ┌──────┐
                │ App  │
                └──┬───┘
         ┌─────────┼─────────┐
         ▼                   ▼
      写 Master           读 Slave
         │                   ▲
         ▼                   │
      主库 (写) ───复制──→ 从库 (读)

★ 写操作只走主,大量读操作分散到从
★ 主库的写锁竞争大幅减少
★ 从库几乎不阻塞(只读)
```

### 6. 热点行分片

```text
热点行问题:1000 个并发都在改 id=1 的余额

解决:把一行拆成多行

  余额表 (拆分前)         余额表 (拆分后)
  ┌────────────┐         ┌────────────┐
  │ user_id=1  │         │ user_id=1, shard=0 │
  │ balance=X  │   →     │ balance=X/4 │
  └────────────┘         ├────────────┤
                         │ user_id=1, shard=1 │
                         │ balance=X/4 │
                         ├────────────┤
                         │ user_id=1, shard=2 │
                         │ balance=X/4 │
                         ├────────────┤
                         │ user_id=1, shard=3 │
                         │ balance=X/4 │
                         └────────────┘
  1000 个并发全堵在     250 个并发 × 4 个分片
  id=1 这一行          并发能力提升 4 倍
```

### 7. 其他优化手段

| 手段                  | 说明 |
|-----------------------|------|
| **减少范围查询**       | 用 LIMIT、精确条件 |
| **避免 `SELECT *`**   | 用具体列,减少回表 |
| **避免长事务**         | 设置 `innodb_lock_wait_timeout` |
| **使用 NOWAIT/SKIP LOCKED** | 8.0+,减少无谓等待 |
| **批量插入分组**       | `INSERT INTO ... VALUES (...), (...)` 减少锁次数 |
| **关闭自适应 Hash**    | `innodb_adaptive_hash_index = OFF` (高并发写场景) |
| **避免 `ORDER BY RAND()`** | 临时表排序 |

## 十四、锁冲突典型案例

### 1. 案例 1:间隙锁导致的死锁

```sql
CREATE TABLE t_od (
    id INT PRIMARY KEY,
    v  INT
);
INSERT INTO t_od VALUES (1, 10), (5, 50), (9, 90);

SET SESSION transaction_isolation = 'REPEATABLE-READ';
```

```text
复现步骤:

T1: 会话 A                          T2: 会话 B
─────────────────────────────────────────────────
BEGIN;                                BEGIN;
                                     
SELECT * FROM t_od                   
WHERE id BETWEEN 1 AND 9             
FOR UPDATE;                           
-- 锁 (1,5], (5,9], (9,+∞)            
                                      SELECT * FROM t_od
                                      WHERE id BETWEEN 1 AND 9
                                      FOR UPDATE;
                                      -- ★ 等待 A 的 Gap Lock

                                      -- 实际上 A 持有锁,B 在等
                                      -- 不构成死锁(单向等待)

-- ★ 死锁需要交叉等待!
```

**真正的死锁复现**:

```text
T1: 会话 A                          T2: 会话 B
─────────────────────────────────────────────────
BEGIN;                                BEGIN;
                                     
UPDATE t_od SET v = v + 1            
WHERE id = 5;                         
-- 锁 id=5                             
                                      UPDATE t_od SET v = v + 1
                                      WHERE id = 9;
                                      -- 锁 id=9
                                     
INSERT INTO t_od VALUES (7, 70);      
-- 等 id=9 的 Gap Lock (5,9)          
                                      INSERT INTO t_od VALUES (3, 30);
                                      -- 等 id=5 的 Gap Lock (1,5)
                                     
-- ★ 双向等待 → 死锁!
-- InnoDB 检测后回滚一个事务
```

```text
            死锁形成示意

   会话 A                      会话 B
      │                            │
      ├─ X lock on id=5 ──┐        │
      │                    │        │
      │                    ├─ X lock on id=9
      │                    │        │
      ├─ 等待 id=9 区间 ────┤        │
      │                    │        │
      │                    ├─ 等待 id=5 区间
      │                            │
      ▼                            ▼
    A 等 B                          B 等 A
       ←──── 循环等待 →→→→→→→→→→
             DEADLOCK!
```

**SHOW ENGINE INNODB STATUS 关键输出**:

```text
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 2001, ACTIVE 5 sec inserting
mysql thread id 20, query id 300 localhost root
INSERT INTO t_od VALUES (7, 70)
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 page no 3 n bits 80 index PRIMARY of table `mydb`.`t_od`
    lock_mode X locks gap before rec insert intention waiting
Record lock, heap no 5 PHYSICAL RECORD: n_fields 4; ...
 0: len 4; hex 80000009; asc     9;;

*** (2) TRANSACTION:
TRANSACTION 2002, ACTIVE 3 sec inserting
mysql thread id 21, query id 301 localhost root
INSERT INTO t_od VALUES (3, 30)
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 page no 3 n bits 80 index PRIMARY of table `mydb`.`t_od`
    lock_mode X locks gap before rec insert intention waiting
Record lock, heap no 4 PHYSICAL RECORD: n_fields 4; ...
 0: len 4; hex 80000005; asc     5;;

*** WE ROLL BACK TRANSACTION (2)
```

**解决方案**:

```sql
-- 方案 1:统一 SQL 顺序
-- 两个会话都先更新小 id,再更新大 id
-- A: UPDATE id=5; UPDATE id=9;
-- B: UPDATE id=5; UPDATE id=9;

-- 方案 2:业务允许时用 READ COMMITTED (无 Gap Lock)
SET SESSION transaction_isolation = 'READ-COMMITTED';

-- 方案 3:把 INSERT 拆成 SELECT + INSERT,先检查再插入
SELECT * FROM t_od WHERE id = 7 FOR UPDATE;
INSERT INTO t_od VALUES (7, 70);

-- 方案 4:用应用层分布式锁串行化
```

### 2. 案例 2:唯一键冲突导致的死锁

```sql
CREATE TABLE t_uk (
    id INT PRIMARY KEY AUTO_INCREMENT,
    uk VARCHAR(32) UNIQUE
);

INSERT INTO t_uk VALUES (NULL, 'a'), (NULL, 'b'), (NULL, 'c');
```

```text
T1: 会话 A                          T2: 会话 B
─────────────────────────────────────────────────
BEGIN;                                BEGIN;
                                     
INSERT INTO t_uk (uk)                 
VALUES ('x');                         
-- 假设自增 id=4                    
                                      INSERT INTO t_uk (uk)
                                      VALUES ('x');
                                      -- 假设自增 id=5

-- 此时两个事务都持有 S 锁 (读唯一键)
-- 都想升级到 X 锁插入
                                     
-- ★ 互相等待对方释放 S 锁 → 死锁!
```

```text
唯一键冲突的死锁:

   A 持有 S lock on 'x'    B 持有 S lock on 'x'
            │                          │
            └──── 互相等对方释放 ──────┘
                    DEADLOCK

★ 解决:应用层先 SELECT 确认,再 INSERT;或用 INSERT ... ON DUPLICATE KEY UPDATE
```

```sql
-- 解决方案 1:先查后插 (不保证原子,但多数情况够用)
INSERT INTO t_uk (uk)
SELECT 'x' FROM dual
WHERE NOT EXISTS (SELECT 1 FROM t_uk WHERE uk = 'x');

-- 解决方案 2:INSERT IGNORE (冲突忽略)
INSERT IGNORE INTO t_uk (uk) VALUES ('x');

-- 解决方案 3:ON DUPLICATE KEY UPDATE (冲突更新)
INSERT INTO t_uk (uk) VALUES ('x')
ON DUPLICATE KEY UPDATE uk = 'x';

-- 解决方案 4:分布式唯一 ID (雪花算法),避免业务唯一键冲突
```

### 3. 案例 3:索引缺失导致锁升级

```sql
CREATE TABLE t_no_idx (
    id INT PRIMARY KEY,
    no_idx_col VARCHAR(50)
);

-- 表中 100 万行

-- 没有索引,DELETE 锁全表
DELETE FROM t_no_idx WHERE no_idx_col = 'x';
-- ★ 全表扫描 → 锁住所有 100 万行
```

**对比**:

```sql
-- 加索引后
ALTER TABLE t_no_idx ADD INDEX idx_col (no_idx_col);

-- 只锁匹配的行 + 间隙
DELETE FROM t_no_idx WHERE no_idx_col = 'x';
-- ★ 仅锁 no_idx_col = 'x' 的行(可能几十行)
```

**结论**:**没有索引,行锁退化为表锁**,这是性能杀手。

### 4. 案例 4:UPDATE 走错索引导致死锁

```sql
CREATE TABLE t_wrong_idx (
    a INT,
    b INT,
    c INT,
    INDEX idx_a (a),
    INDEX idx_b (b)
);
INSERT INTO t_wrong_idx VALUES (1, 1, 1), (2, 2, 2), (3, 3, 3);
```

```text
T1: 会话 A                          T2: 会话 B
─────────────────────────────────────────────────
BEGIN;                                BEGIN;
                                     
UPDATE t_wrong_idx SET c = c + 1      
WHERE a = 1;                          
-- 用 idx_a,锁 a=1 的行               
                                      UPDATE t_wrong_idx SET c = c + 1
                                      WHERE b = 2;
                                      -- 用 idx_b,锁 b=2 的行

UPDATE t_wrong_idx SET c = c + 1      
WHERE b = 2;                          
-- ★ 想要 b=2 的锁,与 B 冲突           
                                      UPDATE t_wrong_idx SET c = c + 1
                                      WHERE a = 1;
                                      -- ★ 想要 a=1 的锁,与 A 冲突
                                     
-- ★ 双向等待 → 死锁!
```

**解决**:保证**多事务更新走相同索引顺序**(按主键或固定列),或用 `FORCE INDEX`。

## 十五、核心要点速记

### 1. 锁的体系

```text
                 MySQL 锁机制核心体系

  ┌──────────┐ ┌──────────┐ ┌──────────────────────────┐
  │ 全局锁   │ │ 表级锁   │ │ 行级锁 (InnoDB 核心)       │
  │ FTWRL    │ │ 表锁     │ │  Record / Gap / Next-Key  │
  │          │ │ MDL      │ │  IS / IX / Insert Intent │
  │          │ │ 意向锁   │ │  AUTO-INC                 │
  └──────────┘ └──────────┘ └──────────────────────────┘
```

### 2. 锁兼容矩阵(完整)

| 已持 \ 申请 | **S** | **X** | **IS** | **IX** |
|-------------|-------|-------|--------|--------|
| **S**       | ✔     | ✘     | ✔      | ✘      |
| **X**       | ✘     | ✘     | ✘      | ✘      |
| **IS**      | ✔     | ✘     | ✔      | ✔      |
| **IX**      | ✘     | ✘     | ✔      | ✔      |

### 3. 三种行锁算法

| 算法            | 锁定范围       | 触发           | 隔离级别 |
|-----------------|----------------|----------------|----------|
| **Record Lock** | 单条记录       | 等值唯一索引   | RR / RC  |
| **Gap Lock**    | 间隙(不含记录) | 范围扫描       | RR       |
| **Next-Key Lock** | 记录 + 间隙  | RR 默认        | RR       |

### 4. 关键命令速查

```sql
-- 查看锁
SHOW ENGINE INNODB STATUS \G
SELECT * FROM performance_schema.data_locks;
SELECT * FROM information_schema.innodb_trx;

-- 查看锁等待
SELECT * FROM sys.innodb_lock_waits;
SELECT * FROM performance_schema.data_lock_waits;

-- KILL 阻塞线程
KILL <thread_id>;

-- 设置参数
SET SESSION transaction_isolation = 'REPEATABLE-READ';
SET SESSION innodb_lock_wait_timeout = 10;

-- 当前读加锁
SELECT ... FOR UPDATE;             -- X 锁
SELECT ... FOR SHARE;              -- S 锁 (8.0+)
SELECT ... FOR UPDATE NOWAIT;      -- 8.0+
SELECT ... FOR UPDATE SKIP LOCKED; -- 8.0+
```

### 5. 排查流程

```text
        锁问题排查标准流程

Step 1: 确认现象
        - 应用报错? Lock wait timeout / Deadlock
        - SQL 慢? 在 SHOW PROCESSLIST 里看 State

Step 2: 查等待关系
        SELECT * FROM sys.innodb_lock_waits;
        → 拿到 blocking_pid, waiting_pid

Step 3: 看锁详情
        SELECT * FROM performance_schema.data_locks
        WHERE lock_table = '...';
        → 知道锁了哪些行,什么类型

Step 4: 分析业务
        - 阻塞线程在跑什么 SQL? 是否长事务?
        - 等待线程的 SQL 是热点操作吗?
        - 是否有索引? 是否走了错索引?

Step 5: 处理
        短期: KILL 阻塞线程
        长期: 加索引、缩短事务、降隔离级别、业务改造
```

### 6. 口诀

```text
              锁优化口诀

       索引必加,事务要短
       隔离合理,范围避免
       当前读少,快照读多
       读写分离,热点分片
       死锁捕获,自动重试
       锁等待超时,合理设置
       SHOW ENGINE 查死锁
       data_locks 实时看
```

### 7. 常见陷阱速查

| 陷阱 | 后果 | 解决 |
|------|------|------|
| 无索引的 `WHERE` | 锁全表 | 加索引 |
| 大事务 + 远程调用 | 锁持有久 | 事务只放 DB 操作 |
| 频繁范围查询(RR) | Gap Lock 多 | 降级到 RC |
| 共享 INSERT 唯一键 | 死锁 | 业务层预检查 |
| MDL ALTER 阻塞读写 | 表卡死 | 设超时,夜间 DDL |
| AUTO_INC 模式选错 | 主从不一致 | binlog 格式与模式匹配 |

### 8. 一句话总结

> **MySQL InnoDB 锁机制的核心,是"用 Next-Key Lock 在 RR 隔离级别下避免幻读",而我们日常要做的,是"用索引让锁精准,用短事务让锁快速释放,用合理隔离级别让锁不过度"。**
