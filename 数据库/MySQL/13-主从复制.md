# MySQL 主从复制 (Master-Slave Replication)

## 一、主从复制概述

### 1.1 什么是主从复制

**主从复制 (Replication)**:MySQL 通过将主库 (Master) 的数据变更**异步**或**半同步**地复制到一个或多个从库 (Slave/Replica),从而实现数据冗余、读写分离和高可用的核心机制。

复制本质上解决的是**单点**问题:单机 MySQL 在写入能力、容灾能力、数据备份上都存在天花板,而复制则是 MySQL 走向生产环境的必经之路。

### 1.2 主从复制的三大作用

| 作用         | 说明                                                                 |
|--------------|----------------------------------------------------------------------|
| **读写分离** | 写入走主库,查询走从库,大幅扩展读能力                                |
| **数据备份** | 从库实时持有主库副本,既是热备也是逻辑备份                            |
| **高可用基础** | 主库故障时可将从库提升 (promote) 为新主库,实现故障转移 (failover) |
| **数据分析** | 复杂报表、ETL、数据挖掘在从库执行,不影响主库性能                    |
| **异地容灾** | 跨机房、跨地域部署从库,应对机房级故障                                |

### 1.3 主从复制与其他高可用方案的对比

| 方案                | 一致性 | 性能影响 | 复杂度 | 适用场景                  |
|---------------------|--------|----------|--------|---------------------------|
| **异步复制**        | 弱     | 最小     | 低     | 多数互联网业务(默认)      |
| **半同步复制**      | 中     | 中       | 中     | 金融、电商(推荐)          |
| **同步复制 (NDB)**  | 强     | 高       | 高     | 电信、特殊行业            |
| **MGR (Group Replication)** | 强 | 中    | 高     | MySQL 5.7+,新一代方案     |
| **PXC / Galera**    | 强     | 中       | 高     | Percona / MariaDB 生态    |

## 二、复制架构演进

### 2.1 一主一从 (Master-Slave)

最基础、最常见的复制架构,主库负责所有写入,从库作为只读副本。

```text
   ┌──────────────┐    binlog     ┌──────────────┐
   │   Master     │ ───────────> │    Slave     │
   │  (写/读)     │   异步推送    │   (只读)     │
   └──────────────┘               └──────────────┘
```

**用途**:
- 读写分离(主写从读)
- 数据备份
- 主库故障时手动切换

**缺点**:
- 单点写,主库压力大
- 从库只能读,无法横向扩展写能力

### 2.2 一主多从 (Master-Multiple Slaves)

主库复制到多个从库,常用于读多写少的场景(如电商商品页、新闻站)。

```text
                       ┌──────────────┐
                  ┌──> │   Slave-1    │ (应用 A 读)
   ┌──────────┐  │    └──────────────┘
   │  Master  │ ─�    ┌──────────────┐
   │ (写)     │  ├──> │   Slave-2    │ (应用 B 读)
   └──────────┘  │    └──────────────┘
                 │    ┌──────────────┐
                 └──> │   Slave-3    │ (BI 报表)
                      └──────────────┘
```

**优点**:
- 读能力线性扩展
- 不同从库承担不同业务(报表、备份、外网查询)
- 故障隔离,单个从库挂掉不影响主库

**缺点**:
- 主库仍为单点
- 主库 binlog 推送多份,从库多了会增大主库 IO

### 2.3 级联复制 (Cascading Replication)

主库只复制到一个从库 (中继从库),该从库再向下复制给其他从库,缓解主库压力。

```text
   ┌──────────────┐
   │   Master     │ ───┐
   └──────────────┘    │  (主库只推一份)
                       ↓
                ┌──────────────┐
                │ Relay Master │ (中继)
                └──────────────┘
                       │  (向下分发)
         ┌─────────────┼─────────────┐
         ↓             ↓             ↓
   �──────────┐  ┌──────────┐  ┌──────────┐
   │ Slave-1  │  │ Slave-2  │  │ Slave-3  │
   └──────────┘  └──────────┘  └──────────┘
```

**配置**(中继从库开启 `log_slave_updates`):

```ini
[mysqld]
log_slave_updates = 1   # 从库 SQL 线程回放后,记入自己的 binlog
log_bin = /var/lib/mysql/mysql-bin
server_id = 100
```

**优点**:
- 主库 IO 压力骤降(只需推一份 binlog)
- 支持海量从库

**缺点**:
- 复制链路变长,延迟叠加
- 中继从库挂了,其下游全部断掉

### 2.4 双主复制 (Master-Master)

两台 MySQL 互为主备,各自承担部分写入,通过**双向复制**同步。

```text
        ┌──────────┐  binlog  ┌──────────┐
        │ Master-A │ <─────── │ Master-B │
        │  写 A    │ ───────> │  写 B    │
        └──────────┘  binlog  └──────────┘
```

**适用场景**:
- 不同业务使用不同主库(分片写入)
- 异地多活(弱一致)

**重大风险**:
- **自增主键冲突**:必须配置不同的 `auto_increment_offset` 和 `auto_increment_increment`
- **数据冲突**:同一行被两端同时修改,后到的写入覆盖
- **循环复制**:必须开启 `log_slave_updates` 并设置 `replicate-same-server-id=0`

**生产建议**:
- 业务侧避免双写
- 或使用 **MySQL Group Replication (MGR)** 替代,自带冲突检测

### 2.5 环形复制 (Ring Replication)

三个及以上节点首尾相连,组成环。早期 MariaDB Galera 衍生方案,现已不推荐(故障检测慢、单点撕裂)。

```text
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │  Node A  │─>│  Node B  │─>│  Node C  │
   └──────────┘  └──────────┘  └──────────┘
        ▲                            │
        └────────────────────────────┘
```

**已被淘汰**:
- 节点故障易造成脑裂
- 一致性协议弱

**替代方案**:**MGR (MySQL Group Replication)** / **Galera Cluster** / **InnoDB ClusterSet**。

## 三、复制原理详解

### 3.1 核心三线程模型

主从复制的本质是**三个线程**的协作:

| 线程        | 所在  | 作用                                                   |
|-------------|-------|--------------------------------------------------------|
| **Binlog Dump 线程** | 主库 | 监听 binlog,推送给从库                                 |
| **I/O 线程** | 从库  | 接收主库 binlog,写入本地 **relay log** (中继日志)     |
| **SQL 线程** | 从库  | 读取 relay log,解析并回放(8.0 之后可多线程,即 MTS) |

### 3.2 主库 Binlog Dump 写入流程

主库对每一次数据修改(INSERT/UPDATE/DELETE/DDL),都会按**复制格式**写入 binlog:

```text
Client: INSERT INTO t1 VALUES (...)
        │
        ▼
主库执行器:写入 InnoDB redo log + binlog
        │
        ▼
binlog 文件:  /var/lib/mysql/mysql-bin.000001
        │
        ▼
Binlog Dump 线程:读取 binlog events,推送给已连接的所有从库
```

**关键参数**:

```ini
[mysqld]
server_id        = 1                 # 主库 ID,集群中必须唯一
log_bin          = /var/lib/mysql/mysql-bin  # binlog 路径(开启复制必须)
binlog_format    = ROW               # 推荐 ROW
expire_logs_days = 7                 # 自动清理
max_binlog_size  = 1G                # 单文件大小
sync_binlog      = 1                 # 每次事务 commit 都刷盘(强一致)
```

### 3.3 从库 I/O 线程拉取 Binlog

从库启动 I/O 线程后:

```text
1. 连接主库 (用户名/密码/端口)
2. 告知主库:从哪个 binlog 文件 + position 开始拉取
3. 主库 Binlog Dump 线程开始推送
4. 从库 I/O 线程接收,写入本地文件 relay-log
5. 同时记录 master.info (主库信息) 与 relay-log.info (中继日志位置)
```

**关键文件**:

```text
/var/lib/mysql/
├── relay-bin.000001         # 中继日志
├── relay-bin.index          # 中继日志索引
├── master.info              # 主库连接信息 + binlog 位点
└── relay-log.info           # 当前 relay log 应用位置
```

### 3.4 从库 SQL 线程回放 Relay Log

```text
relay-bin.000001
        │
        ▼
SQL 线程读取 event
        │
        ▼
解析为 SQL 语句(STATEMENT)或 行变更 (ROW)
        │
        ▼
在从库上重新执行 → 写入 InnoDB
        │
        ▼
更新 relay-log.info 中的应用位置
```

### 3.5 详细时序图(重点)

```text
  ┌─────────────────────────┐                          ┌─────────────────────────┐
  │        Master           │                          │        Slave            │
  │  ┌───────────────────┐  │                          │  ┌───────────────────┐  │
  │  │ Client SQL        │  │                          │  │  I/O Thread       │  │
  │  └───────────────────┘  │                          │  └───────────────────┘  │
  │            │             │                          │            │             │
  │            ▼             │                          │            │             │
  │  ┌───────────────────┐  │                          │            │             │
  │  │ Engine InnoDB     │  │                          │            │             │
  │  │ - redo log        │  │                          │            │             │
  │  │ - binlog (write)  │  │                          │            │             │
  │  └───────────────────┘  │                          │            │             │
  │            │             │                          │            │             │
  │            ▼             │                          │            │             │
  │  �───────────────────┐  │                          │            │             │
  │  │ Binlog Dump       │  │ ① 推送 binlog events     │            │             │
  │  │ Thread            │ ─┼─────────────────────────>│ ② 写入 relay log       │
  │  │                   │  │  (半同步:等待 ACK)        │            │             │
  │  └───────────────────┘  │                          │            │             │
  │            ▲             │                          │            ▼             │
  │            │             │                          │  ┌───────────────────┐  │
  │            │ ⑥ commit    │                          │  │  SQL Thread       │  │
  │            │ (after ack) │                          │  │  (回放)           │  │
  └────────────┼─────────────┘                          │  └───────────────────┘  │
               │                                        │            │             │
               │                                        │            ▼             │
               │                                        │  ┌───────────────────┐  │
               │                                        │  │ Engine InnoDB     │  │
               │                                        │  │  (本地数据)       │  │
               │                                        │  └───────────────────┘  │
               │                                        └─────────────────────────┘
```

**详细步骤拆解**:

```text
1.  Client 在 Master 执行 INSERT
2.  Master 将变更写入 redo log (prepare)
3.  Master 将变更写入 binlog
4.  Master commit redo log (commit)
5.  Binlog Dump 线程感知新 event,推送给 Slave I/O 线程
    [异步]:Master 不等待
    [半同步 after_sync]:Master 等待至少 1 个 Slave ACK 后才 commit
    [半同步 after_commit]:Master commit 后等待 ACK(默认,旧版)
6.  Slave I/O 线程接收 event,写入 relay log
7.  Slave SQL 线程读取 relay log,执行相同变更
8.  Slave 写入 redo log + binlog (若开启 log_slave_updates)
```

## 四、复制模式

### 4.1 基于 Binlog Position(传统模式)

MySQL 5.6 之前唯一可用的复制模式,通过**文件名 + 偏移量**唯一定位复制位置:

```sql
-- 主库查看 binlog 位置
SHOW MASTER STATUS;
+------------------+----------+
| File             | Position |
+------------------+----------+
| mysql-bin.000003 |      154 |
+------------------+----------+

-- 从库配置
CHANGE MASTER TO
  MASTER_HOST='192.168.1.10',
  MASTER_USER='repl',
  MASTER_PASSWORD='xxx',
  MASTER_LOG_FILE='mysql-bin.000003',
  MASTER_LOG_POS=154;
```

**优点**:简单直观。
**缺点**:
- 切换主库时**必须重新计算位点**,易出错
- 不能跳过一个事务(漏掉容易追平失败)
- 运维复杂

### 4.2 基于 GTID(MySQL 5.6+ 推荐)

**GTID (Global Transaction Identifier)**:全局事务标识符,格式为

```text
GTID = source_id:transaction_id
   = server_uuid:事务序号
```

例如:`3E11FA47-71CA-11E1-9E33-C80AA9429562:1-23`

**特点**:
- 全局唯一
- 自带幂等性(从库可判断事务是否已执行)
- 切换主库无需重新找位点
- 配合 `CHANGE MASTER TO MASTER_AUTO_POSITION=1` 自动定位

**主库配置**:

```ini
[mysqld]
gtid_mode                = ON
enforce_gtid_consistency = ON
```

**从库配置**:

```sql
CHANGE MASTER TO
  MASTER_HOST='192.168.1.10',
  MASTER_USER='repl',
  MASTER_PASSWORD='xxx',
  MASTER_AUTO_POSITION=1;
```

### 4.3 GTID vs Position 对比表

| 维度                | Binlog Position          | GTID                            |
|---------------------|--------------------------|----------------------------------|
| 引入版本            | 早期                     | 5.6 (实验), 5.7+ (推荐)         |
| 定位方式            | file:position            | server_uuid:txn_id               |
| 主从切换            | 需手动算新位点           | 自动定位                        |
| 跳过事务            | 手动 `SET GLOBAL SQL_SLAVE_SKIP_COUNTER` | 注入空事务即可            |
| 幂等性              | 无                       | 内置幂等(从库断点续传安全)      |
| 多源复制            | 复杂                     | 天然支持                        |
| 故障恢复复杂度      | 高                       | 低                              |
| 性能开销            | 无                       | 极小(每事务多写 8 字节)         |
| 生产推荐            | 不推荐                   | **强烈推荐**                    |

## 五、复制格式

### 5.1 STATEMENT 模式 (SBR)

**Statement-Based Replication**:记录**原始 SQL 语句**,从库重放 SQL。

```sql
-- binlog 内容示例
SET TIMESTAMP=1700000000;
UPDATE t1 SET c1 = c1 + 1 WHERE id = 1;
```

**优点**:
- binlog 文件小(只记 SQL)
- 便于审计、查看
- 早期版本默认

**缺点**:
- 非确定性函数 (`NOW()`, `UUID()`, `RAND()`) 主从结果不一致
- 触发器、存储过程行为难一致
- 慢 SQL 从库同样慢

### 5.2 ROW 模式 (RBR)

**Row-Based Replication**:记录**每一行的实际变更**(Before Image + After Image)。

```text
-- binlog 内容(伪人类可读)
### UPDATE `test`.`t1`
### WHERE
###   @1=1 /* INT meta=0 nullable=0 is_null=0 */
###   @2='old' /* VARSTRING meta=0 nullable=0 is_null=0 */
### SET
###   @1=1 /* INT meta=0 nullable=0 is_null=0 */
###   @2='new'
```

**优点**:
- 完全一致(主从行级同步)
- 适合函数、触发器
- 行级粒度,部分行可被并行

**缺点**:
- binlog 体积大(全表 UPDATE 会爆)
- 可读性差,需用 `mysqlbinlog -v` 解析

### 5.3 MIXED 模式 (MBR)

**Mixed-Based Replication**:MySQL 自动选择,**大多数 DDL 用 STATEMENT,DML 默认 ROW**。

```text
DDL (CREATE/ALTER/DROP)  ──>  STATEMENT
确定性 DML (简单 UPDATE) ──>  STATEMENT
非确定性 DML (UUID/RAND/NOW) ──>  ROW
```

### 5.4 格式对比表

| 维度            | STATEMENT     | ROW                  | MIXED              |
|-----------------|---------------|----------------------|--------------------|
| binlog 大小     | 最小          | 最大                  | 中                 |
| 主从一致性      | 差(函数坑)   | 强                   | 中                 |
| 可读性          | 高            | 低(需 mysqlbinlog)   | 中                 |
| 性能影响        | 低            | 中(网络 IO 大)       | 中                 |
| 主从延迟        | 高(慢 SQL)   | 低                   | 中                 |
| 适用场景        | 已不推荐      | **生产推荐**          | 过渡方案           |
| MySQL 默认      | 5.0-5.6 默认  | 8.0 默认              | 早期过渡           |

**生产建议**:统一使用 **`binlog_format = ROW`**。

## 六、复制类型

### 6.1 异步复制 (Asynchronous) —— 默认

```text
Master commit ──> 立即返回 Client
           │
           └──> Binlog Dump Thread 推送 (不等待 ACK)
```

**特点**:
- 性能最佳
- 主库宕机时,已提交的事务可能**未送达**从库 → 数据丢失

### 6.2 半同步复制 (Semi-Synchronous)

MySQL 5.5 引入,需安装插件 `semisync_master` / `semisync_slave`。

```text
Master 写入 binlog ──> 等待至少 N 个 Slave ACK
        │                    │
        ▼                    ▼
    收到 ACK              Slave I/O 写入 relay log
        │
        ▼
Master commit ──> 返回 Client
```

#### (1) After Commit (旧)

```text
prepare → write binlog → commit → 等 Slave ACK → 返回 Client
```

**问题**:主库 commit 后才等 ACK,如果 ACK 前主库宕机,从库应用了 binlog 会出现"幻读"。

#### (2) After Sync (5.7+,推荐)

```text
prepare → write binlog → 等 Slave ACK → commit → 返回 Client
```

**优势**:主库 commit 之前已确保从库收到 binlog,**真正零丢失**(RPO=0)。

#### (3) 配置半同步

```sql
-- 主库
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 10000;  -- 10s 后降级为异步
SET GLOBAL rpl_semi_sync_master_wait_for_slave_count = 1;  -- 至少 1 个 ACK

-- 从库
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';
SET GLOBAL rpl_semi_sync_slave_enabled = 1;
```

**永久配置**:

```ini
# 主库
[mysqld]
plugin-load                = "rpl_semi_sync_master=semisync_master.so"
rpl_semi_sync_master_enabled     = 1
rpl_semi_sync_master_timeout     = 10000
rpl_semi_sync_master_wait_for_slave_count = 1

# 从库
[mysqld]
plugin-load                = "rpl_semi_sync_slave=semisync_slave.so"
rpl_semi_sync_slave_enabled       = 1
```

### 6.3 同步复制 (Synchronous)

主库必须等待**所有**从库 commit 才返回。**MySQL 原生不支持**(NDB Cluster 支持)。

**替代**:**MGR (Group Replication)** 或 **Galera Cluster**,基于 Paxos / Cert-based 一致性协议。

### 6.4 三种复制类型对比

| 维度         | 异步                  | 半同步 (after_sync)        | 同步 (MGR)             |
|--------------|----------------------|----------------------------|-------------------------|
| 数据丢失 (RPO) | 可能丢失             | 0                          | 0                       |
| 主库延迟     | 最小                 | 中(网络往返)               | 较高                    |
| 性能         | 最高                 | 中                         | 较低                    |
| 主库故障切换 | 易(可能丢数据)       | 中(数据安全)               | 难(需多数节点存活)      |
| 推荐场景     | 多数互联网业务        | 金融、电商                 | 强一致核心库            |

## 七、搭建主从复制(完整实战步骤)

### 7.1 环境准备

| 角色    | IP             | 端口  | server_id |
|---------|----------------|-------|-----------|
| Master  | 192.168.1.10   | 3306  | 1         |
| Slave-1 | 192.168.1.11   | 3306  | 2         |
| Slave-2 | 192.168.1.12   | 3306  | 3         |

### 7.2 主库配置

```ini
# /etc/my.cnf
[mysqld]
server_id          = 1
log_bin            = /var/lib/mysql/mysql-bin
binlog_format      = ROW
gtid_mode          = ON
enforce_gtid_consistency = ON
expire_logs_days   = 7
```

## 八、基于 GTID 的复制搭建(完整流程)

### 8.1 GTID 复制优势

- 自动定位,无需记 binlog 位点
- 跳过错误事务简单
- 多源复制友好

### 8.2 主库开启 GTID

```ini
[mysqld]
gtid_mode                = ON
enforce_gtid_consistency = ON
```

### 8.3 查看 GTID 集合

```sql
-- 主库
SHOW MASTER STATUS;
-- 或
SELECT @@global.gtid_executed;

-- 从库
SELECT @@global.gtid_purged;   -- 已清除的 GTID
SELECT @@global.gtid_executed; -- 已执行的 GTID
```

### 8.4 完整 GTID 复制搭建步骤

```text
1. 主从都开启 gtid_mode + enforce_gtid_consistency
2. 主库全量备份(带 --set-gtid-purged=COMMENTED 或 AUTO)
3. 备份文件包含 GTID PURGED 信息
4. 从库导入备份后,RESET MASTER 清空 gtid_executed
5. SET GLOBAL gtid_purged = '<从备份文件读到的 GTID>';
6. CHANGE MASTER TO MASTER_AUTO_POSITION=1
7. START SLAVE
8. SHOW SLAVE STATUS 验证 Retrieved = Executed
```

### 8.5 跳过事务(GTID 模式)

```sql
-- 注入空事务跳过错误
SET GTID_NEXT = '3e11fa47-71ca-11e1-9e33-c80aa9429562:24';
BEGIN;
COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
START SLAVE;
```

## 九、主从切换与角色切换

### 9.1 Switchover(计划内切换)

**场景**:主库维护、机房搬迁、主动降级。

```sql
-- 1. 主库停止写入
FLUSH TABLES WITH READ LOCK;

-- 2. 记录主库状态
SHOW MASTER STATUS;

-- 3. 从库停止复制,关闭 read_only
STOP SLAVE;
RESET SLAVE ALL;
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

-- 4. 业务切到新主库

-- 5. 原主库降级为从库,指向新主
CHANGE MASTER TO
  MASTER_HOST='192.168.1.11',
  MASTER_USER='repl',
  MASTER_PASSWORD='xxx',
  MASTER_AUTO_POSITION=1;
START SLAVE;
```

### 9.2 Failover(故障切换)

**场景**:主库宕机,需将某个从库提升为新主库。

**手动流程**:

```sql
-- 1. 选延迟最小、数据最新的从库
-- 2. 停止其复制
STOP SLAVE;
RESET SLAVE ALL;

-- 3. 关闭 read_only
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

-- 4. 业务切到新主库

-- 5. 其他从库指向新主
CHANGE MASTER TO MASTER_HOST='新主IP', MASTER_AUTO_POSITION=1;
START SLAVE;
```

**自动工具**:
- **MHA (Master High Availability)** —— 经典方案,Yahoo 开源
- **MHA-Manager + Node**
- **Orchestrator** —— GitHub 开源,基于拓扑感知
- **MySQL InnoDB ClusterSet** —— 8.0+

### 9.3 GTID 下 Failover 更安全

```text
普通切换:必须保证新主库包含所有已执行事务,否则丢数据
GTID 切换:每个从库的 Executed_Gtid_Set 清晰可见,
         选最大集合的从库提升,其他从库自动追平
```

**判断最佳候选**:

```sql
SELECT
  @@server_uuid,
  @@global.gtid_executed;
```

选 GTID 集合最大的、延迟最小的、数据最新的。

## 十、复制延迟问题

### 10.1 延迟定义

**Seconds_Behind_Master**:从库 SQL 线程回放位置 与 主库最新 binlog 位置 的差值(秒)。

```sql
SHOW SLAVE STATUS\G
Seconds_Behind_Master: 0     -- 0 表示同步
```

### 10.2 延迟原因分析

| 原因                       | 说明                                                       |
|----------------------------|------------------------------------------------------------|
| 从库硬件差                 | 主库 SSD,从库 HDD                                          |
| 从库单线程回放             | 默认 SQL 线程单线程(MTS 可解决)                            |
| 主库大事务                 | 批量 UPDATE/DELETE 一次性刷出大量行                         |
| 网络 RTT                   | 跨机房复制,RTT 高                                          |
| 从库锁阻塞                 | 长事务、未提交 DDL                                          |
| 表无主键                   | ROW 模式必须有主键,否则逐行扫描定位                        |
| 从库承担过多读             | 业务查询挤占复制资源                                       |

### 10.3 主从不一致案例

#### (1) 自增 ID 不一致(异步复制导致)

```sql
-- 主库
INSERT INTO orders (user_id) VALUES (1);
-- 主库: id = 100
-- 从库延迟时插入:
INSERT INTO orders (user_id) VALUES (1);
-- 从库: id = 99
-- 之后同步追上,主库的 id=100 落到从库
-- → 业务从从库读到的可能是旧 id
```

#### (2) SQL 函数不一致

```sql
-- 主库
INSERT INTO t1 VALUES (NOW());
-- 从库(异步,延迟 5s)
-- 主库 NOW = 10:00:00
-- 从库回放时 NOW = 10:00:05 → 不一致
```

**STATEMENT 模式下尤其严重**,ROW 模式可避免(记录行变更)。

### 10.4 并行复制 (Multi-Threaded Slave, MTS)

**5.6 引入库级并行**;**5.7 引入基于 logical_clock 的并行**;**8.0 默认开启**且支持 `WRITESET_SESSION` / `WRITESET_PARALLEL`。

#### (1) 配置 MTS

```ini
[mysqld]
slave_parallel_type            = LOGICAL_CLOCK     # 5.7+ 推荐
# 或 8.0:
slave_parallel_type            = WRITESET          # 基于 writeset 哈希并行
slave_parallel_workers         = 16                # 并行线程数,=CPU 核数
slave_preserve_commit_order    = ON                # 必须开,保序
slave_parallel_max_queued     = 131072            # 队列大小
slave_parallel_workers        = 8                 # 实际并发数
```

```sql
-- 动态修改
SET GLOBAL slave_parallel_type = 'WRITESET';
SET GLOBAL slave_parallel_workers = 16;
```

#### (2) 验证并行复制

```sql
SHOW PROCESSLIST;
-- 会看到多个 "Slave Worker" 线程
```

#### (3) 不同并行策略对比

| 策略                  | 适用                          | 限制                  |
|-----------------------|-------------------------------|-----------------------|
| `DATABASE`(5.6)       | 多库独立                      | 单库无并行            |
| `LOGICAL_CLOCK`(5.7)  | 同库多事务并行                | 需同一 logical_clock  |
| `WRITESET`(8.0)       | 同库不同行并行                | 同一行的多个事务需串行 |
| `WRITESET_SESSION`    | 同会话串行,跨会话并行        | 同会话事务串行        |

### 10.5 监控延迟

#### (1) SHOW SLAVE STATUS

```sql
SHOW SLAVE STATUS\G
Seconds_Behind_Master: 0       -- 主指标
```

#### (2) performance_schema

```sql
-- 8.0
SELECT * FROM performance_schema.replication_applier_status;
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- 查看每个 worker 的延迟
SELECT
  worker_id,
  last_applied_transaction,
  last_error,
  applying_transaction
FROM performance_schema.replication_applier_status_by_worker;
```

#### (3) 复制心跳表

```sql
CREATE TABLE t_heartbeat (
  id INT PRIMARY KEY,
  ts TIMESTAMP
);

-- 主库定时更新
INSERT INTO t_heartbeat VALUES (1, NOW()) ON DUPLICATE KEY UPDATE ts=NOW();

-- 从库比较 NOW() 与 ts 的差值
SELECT TIMESTAMPDIFF(SECOND, ts, NOW()) AS lag FROM t_heartbeat WHERE id=1;
```

**优势**:比 `Seconds_Behind_Master` 更精确(后者只算 binlog 位置,不反映真实业务延迟)。

#### (4) 监控告警

```text
延迟 < 10s   正常(绿)
10s ~ 60s    警告(黄)
> 60s        告警(红)
```

## 十一、主从数据一致性校验

### 11.1 pt-table-checksum (Percona Toolkit)

**功能**:在线校验主从数据一致性。

**原理**:
- 主库对每张表计算 checksum(分块,避免长事务)
- 同步到从库回放
- 比对主从 checksum 是否一致

**使用**:

```bash
pt-table-checksum \
  --host=192.168.1.10 --user=root --password=xxx \
  --replicate=test.checksums \
  --databases=app_db \
  --tables=orders,users \
  --nocheck-binlog-format \
  --chunk-size=1000
```

输出:

```text
            TS ERRORS  DIFFS     ROWS  CHUNKS SKIPPED    TIME TABLE
2026-08-14 10:30:00   0   0    1000000    100       0   10.5 app_db.orders
2026-08-14 10:30:15   0   1     500000    50       0    5.2 app_db.users
```

`DIFFS > 0` 说明有差异。

### 11.2 pt-table-sync (修复工具)

**功能**:把主从差异修复同步(单向或双向)。

```bash
# 打印修复 SQL,不执行
pt-table-sync \
  --host=192.168.1.10 --user=root --password=xxx \
  --replicate=test.checksums \
  --databases=app_db \
  --print

# 确认后执行
pt-table-sync \
  --host=192.168.1.10 --user=root --password=xxx \
  --replicate=test.checksums \
  --databases=app_db \
  --execute
```

### 11.3 其他校验工具

| 工具                          | 特点                                   |
|-------------------------------|----------------------------------------|
| `pt-table-checksum`           | Percona Toolkit,事实标准               |
| `mysqlrplcheck`               | MySQL Utilities,功能较弱               |
| `go-mysql-diff`               | Go 实现,轻量                          |
| `Yearning` / `Archery`        | 平台化方案,带 SQL 审核                  |

## 十二、复制过滤

### 12.1 过滤维度

MySQL 提供四种过滤选项,**只影响从库**,主库照写:

| 参数                         | 作用                                  |
|------------------------------|---------------------------------------|
| `replicate-do-db`            | 仅复制指定库                          |
| `replicate-ignore-db`        | 忽略指定库                            |
| `replicate-do-table`         | 仅复制指定表                          |
| `replicate-ignore-table`     | 忽略指定表                            |
| `replicate-wild-do-table`    | 通配符匹配要复制的表                  |
| `replicate-wild-ignore-table`| 通配符匹配要忽略的表                  |
| `replicate-rewrite-db`       | 把 from_db 改写成 to_db               |

### 12.2 配置示例

```ini
[mysqld]
replicate-do-db            = app_db
replicate-wild-ignore-table = app_db.tmp_%
replicate-ignore-table      = mysql.user
```

### 12.3 过滤的坑

**危险场景**:`USE` 语句在跨库查询时容易绕过过滤:

```sql
USE mysql;
INSERT INTO app_db.t1 VALUES (1);
-- 因为 USE 是 mysql,过滤规则把整个语句丢掉
-- 但实际写的是 app_db.t1 → 数据丢失
```

**生产建议**:
- 过滤规则不要混用 `replicate-do-db` 和 `replicate-ignore-db`
- 优先用 `replicate-wild-do-table` 精确匹配
- 主库端用 `binlog-do-db` 更安全(写 binlog 时就过滤)

## 十三、复制故障排查

### 13.1 IO 线程失败常见原因

| 错误信息                                  | 原因                              | 解决方案                          |
|-------------------------------------------|-----------------------------------|-----------------------------------|
| `Could not find first log file name`      | 主库 binlog 已 purge              | 从库全量重搭                      |
| `Got fatal error 1236 from master`        | 主库 binlog 缺失                  | 重新 change master to 新位点      |
| `Access denied for user 'repl'@...`       | 账号密码错                        | 重建账号                          |
| `Can't connect to MySQL server`           | 网络/防火墙/端口                  | 检查连通性                        |
| `Master is configured with GTID`          | GTID 模式不一致                   | 统一配置                          |

**排查命令**:

```sql
SHOW SLAVE STATUS\G
Last_IO_Error: error connecting to master 'repl@192.168.1.10:3306' ...
```

### 13.2 SQL 线程失败常见原因

| 错误                                       | 原因                            | 解决方案                          |
|--------------------------------------------|---------------------------------|-----------------------------------|
| `Duplicate entry 'xx' for key 'PRIMARY'`   | 主从键冲突(异常写入)           | 跳过 / pt-table-sync 修复        |
| `Cannot find table 'xx'`                   | 从库缺失表                      | 重建表                            |
| `Table 'xx' doesn't exist`                 | 表不存在(过滤规则导致)         | 检查过滤规则                      |
| `Column 'xx' cannot be null`               | 主从表结构不一致                | 同步结构                          |
| `Can't execute DDL on slave`               | ROW 模式下 DDL 跳过问题         | `SET GLOBAL SQL_SLAVE_SKIP_COUNTER = 1` |

**排查命令**:


## 十四、核心要点速记

- **复制三线程**:Binlog Dump(主) + I/O(从) + SQL(从)
- **binlog 三格式**:STATEMENT(不推荐) / ROW(生产首选) / MIXED(过渡)
- **复制两模式**:Binlog Position(旧) / GTID(5.6+ 推荐)
- **GTID** = `server_uuid:transaction_id`,全局唯一,自动定位
- **复制类型**:异步(默认) / 半同步 after_sync(零丢失) / 同步(原 MySQL 不支持)
- **半同步 after_sync** 比 after_commit 安全:commit 之前已等 ACK
- **架构演进**:一主一从 → 一主多从 → 级联(`log_slave_updates`) → 双主(慎用)
- **MTS 并行复制**:8.0 默认 `WRITESET`,配置 `slave_parallel_workers`
- **延迟监控**:`Seconds_Behind_Master`(粗略) + 业务心跳表(精确)
- **一致性校验**:`pt-table-checksum` + `pt-table-sync` 是事实标准
- **过滤规则**:`replicate-wild-do-table` 比 `replicate-do-db` 更安全
- **IO 线程失败**:网络 / 账号 / binlog 缺失
- **SQL 线程失败**:主从数据冲突 / 表结构不一致
- **GTID 跳过事务**:注入空事务 `SET GTID_NEXT = 'xxx'; BEGIN; COMMIT;`
- **主从切换**:Switchover(计划内) / Failover(故障),GTID 下更安全
- **生产推荐**:`ROW + GTID + 半同步 after_sync + MTS + 至少 2 个从库`
- **`Seconds_Behind_Master = 0`** 是健康的核心标志
- **双主复制**需要不同 `auto_increment_offset`,且业务避免双写
- **MGR** 是 MySQL 5.7+ 的同步复制方案,Paxos 协议,推荐替代双主
