# MySQL 事务 (Transaction)

## 一、事务概念

### 1.1 什么是事务

**事务(Transaction)** 是数据库中一组不可分割的操作集合,这组操作要么**全部成功**,要么**全部失败回滚**,不存在中间状态。

最经典的例子是**转账**:

```text
张三给李四转账 1000 元

步骤 1: UPDATE account SET balance = balance - 1000 WHERE name = '张三';
步骤 2: UPDATE account SET balance = balance + 1000 WHERE name = '李四';

如果步骤 1 成功、步骤 2 失败(比如宕机),
→ 张三少了 1000,李四没收到 → 钱凭空消失!

事务保证:两步要么都成功,要么都不做。
```

### 1.2 事务的 ACID 特性

```text
┌──────────────────────────────────────────────────────────┐
│                     ACID 四大特性                          │
├──────────────┬───────────────────────────────────────────┤
│ A 原子性      │ Atomicity   → 全做 or 全不做              │
│              │ 实现:undo log(回滚日志)                 │
├──────────────┼───────────────────────────────────────────┤
│ C 一致性      │ Consistency → 数据从一个合法态到另一合法态 │
│              │ 实现:AID + 业务约束共同保证               │
├──────────────┼───────────────────────────────────────────┤
│ I 隔离性      │ Isolation   → 并发事务互不干扰            │
│              │ 实现:锁 + MVCC                           │
├──────────────┼───────────────────────────────────────────┤
│ D 持久性      │ Durability  → 提交后永久生效,宕机不丢    │
│              │ 实现:redo log(重做日志)+ WAL           │
└──────────────┴───────────────────────────────────────────┘
```

#### 原子性 (Atomicity)

事务是最小执行单元,不可再分。事务中的所有操作,要么全部提交成功,要么全部失败回滚。

**实现原理**:InnoDB 使用 **undo log**。每次修改数据前,先把"如何撤销这次修改"记录到 undo log:

| 原操作 | undo log 记录 |
|--------|--------------|
| INSERT | 对应一条 DELETE |
| DELETE | 对应一条 INSERT |
| UPDATE | 对应一条反向 UPDATE(记录旧值) |

`ROLLBACK` 时,InnoDB 逆序执行 undo log 中的补偿操作,把数据恢复原状。

#### 一致性 (Consistency)

事务执行前后,数据库都必须处于**合法状态**。合法性由两部分定义:

- **数据库层约束**:主键唯一、外键引用、NOT NULL、CHECK、唯一索引
- **业务层约束**:转账前后总金额不变、库存不能为负

一致性是**目的**,原子性、隔离性、持久性是**手段**。

#### 隔离性 (Isolation)

多个事务并发执行时,一个事务的中间状态不应被其它事务看到。MySQL 通过**锁机制**和 **MVCC(多版本并发控制)** 实现不同强度的隔离。

#### 持久性 (Durability)

事务一旦 COMMIT,修改就永久保存,即使数据库随后崩溃也不会丢失。

**实现原理**:**WAL(Write-Ahead Logging,预写日志)**

```text
      修改数据流程(WAL)
 ┌─────────────────────────────────┐
 │ 1. 修改 Buffer Pool 中的内存页    │  ← 快
 │ 2. 写 redo log buffer            │
 │ 3. COMMIT 时刷 redo log 到磁盘    │  ← 顺序写,快
 │ 4. 返回客户端"提交成功"           │
 │ 5. 脏页由后台线程异步刷盘          │  ← 随机写,慢,可延后
 └─────────────────────────────────┘

 崩溃恢复:重启后用 redo log 重放,把已提交但未刷盘的修改补上。
```

关键参数 `innodb_flush_log_at_trx_commit`:

| 值 | 行为 | 安全性 | 性能 |
|----|------|--------|------|
| 0 | 每秒由后台线程写并刷盘 | 崩溃丢 1 秒数据 | 最高 |
| 1 | 每次提交都写并 fsync(**默认**) | 不丢数据 | 最低 |
| 2 | 每次提交写 OS 缓存,每秒 fsync | MySQL 崩溃不丢,OS 崩溃丢 1 秒 | 中 |

```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

## 二、事务语法

### 2.1 基本语句

| 语句 | 作用 |
|------|------|
| `START TRANSACTION` | 显式开启事务(标准 SQL) |
| `BEGIN` / `BEGIN WORK` | 开启事务(MySQL 别名) |
| `COMMIT` | 提交事务,持久化所有修改 |
| `ROLLBACK` | 回滚事务,撤销所有修改 |
| `SAVEPOINT 名字` | 设置保存点 |
| `ROLLBACK TO 名字` | 回滚到指定保存点 |
| `RELEASE SAVEPOINT 名字` | 释放保存点 |
| `SET autocommit = 0/1` | 关闭/开启自动提交 |

### 2.2 准备演示表

```sql
CREATE DATABASE IF NOT EXISTS trx_demo;
USE trx_demo;

CREATE TABLE account (
    id      INT PRIMARY KEY AUTO_INCREMENT,
    name    VARCHAR(20) NOT NULL,
    balance DECIMAL(10,2) NOT NULL DEFAULT 0,
    UNIQUE KEY uk_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO account (name, balance) VALUES
('张三', 1000.00), ('李四', 1000.00), ('王五', 1000.00);
```

```text
mysql> SELECT * FROM account;
+----+--------+---------+
| id | name   | balance |
+----+--------+---------+
|  1 | 张三   | 1000.00 |
|  2 | 李四   | 1000.00 |
|  3 | 王五   | 1000.00 |
+----+--------+---------+
3 rows in set (0.00 sec)
```

### 2.3 提交事务

```sql
START TRANSACTION;

UPDATE account SET balance = balance - 200 WHERE name = '张三';
UPDATE account SET balance = balance + 200 WHERE name = '李四';

COMMIT;
```

```text
mysql> SELECT * FROM account;
+----+--------+---------+
| id | name   | balance |
+----+--------+---------+
|  1 | 张三   |  800.00 |
|  2 | 李四   | 1200.00 |
|  3 | 王五   | 1000.00 |
+----+--------+---------+
```

### 2.4 回滚事务

```sql
START TRANSACTION;

UPDATE account SET balance = 0 WHERE name = '王五';
SELECT * FROM account WHERE name = '王五';   -- 事务内可见:0.00

ROLLBACK;

SELECT * FROM account WHERE name = '王五';   -- 回滚后:1000.00
```

```text
-- ROLLBACK 前(事务内自己看)
+----+--------+---------+
| id | name   | balance |
+----+--------+---------+
|  3 | 王五   |    0.00 |
+----+--------+---------+

-- ROLLBACK 后
+----+--------+---------+
| id | name   | balance |
+----+--------+---------+
|  3 | 王五   | 1000.00 |
+----+--------+---------+
```

### 2.5 START TRANSACTION 的修饰符

```sql
-- 只读事务:优化器可跳过部分事务开销,性能更好
START TRANSACTION READ ONLY;

-- 读写事务(默认)
START TRANSACTION READ WRITE;

-- 一致性快照:立即创建 Read View,而不是等到第一条 SELECT
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

> `WITH CONSISTENT SNAPSHOT` 在 RR 隔离级别下很重要:普通 `START TRANSACTION` 是**延迟启动**,直到第一条快照读语句才真正确定视图。

### 2.6 SAVEPOINT 保存点

保存点允许**部分回滚**,而不必放弃整个事务。

```sql
START TRANSACTION;

INSERT INTO account (name, balance) VALUES ('赵六', 500);
SAVEPOINT sp1;

INSERT INTO account (name, balance) VALUES ('钱七', 600);
SAVEPOINT sp2;

INSERT INTO account (name, balance) VALUES ('孙八', 700);

-- 只撤销"孙八"
ROLLBACK TO sp2;

SELECT name FROM account;
```

```text
+--------+
| name   |
+--------+
| 张三   |
| 李四   |
| 王五   |
| 赵六   |
| 钱七   |
+--------+
```

```sql
-- 继续回滚到 sp1,"钱七"也被撤销
ROLLBACK TO sp1;
SELECT name FROM account;
```

```text
+--------+
| name   |
+--------+
| 张三   |
| 李四   |
| 王五   |
| 赵六   |
+--------+
```

```sql
COMMIT;   -- 最终只有"赵六"被真正写入
```

保存点规则:

- `ROLLBACK TO sp` **不会结束事务**,事务仍在进行
- 回滚到某保存点后,该点之后创建的保存点自动失效
- 同名 SAVEPOINT 会覆盖旧的
- 回滚到不存在的保存点报错:`ERROR 1305 (42000): SAVEPOINT sp3 does not exist`
- `COMMIT` / `ROLLBACK` 会释放所有保存点

```text
        SAVEPOINT 回滚示意
 BEGIN
   │
   ├── INSERT 赵六
   │   ● sp1 ◄──────────── ROLLBACK TO sp1
   ├── INSERT 钱七
   │   ● sp2 ◄──── ROLLBACK TO sp2
   ├── INSERT 孙八
   │
 COMMIT   → 实际落库:赵六
```

## 三、事务的自动提交 (autocommit)

### 3.1 默认行为

MySQL 默认 `autocommit = ON`,意味着**每一条 SQL 语句都是一个独立事务**,执行完自动提交。

```sql
SHOW VARIABLES LIKE 'autocommit';
```

```text
+---------------+-------+
| Variable_name | Value |
+---------------+-------+
| autocommit    | ON    |
+---------------+-------+
```

```sql
-- autocommit = ON 时,这条语句等价于:
-- START TRANSACTION; UPDATE ...; COMMIT;
UPDATE account SET balance = balance - 100 WHERE name = '张三';
```

### 3.2 关闭自动提交

```sql
SET autocommit = 0;          -- 仅当前会话
SET GLOBAL autocommit = 0;   -- 全局(新连接生效,不影响已有连接)
```

关闭后,**任何一条 DML 语句都会隐式开启事务**,必须手动 `COMMIT` 或 `ROLLBACK`:

```sql
SET autocommit = 0;

UPDATE account SET balance = 9999 WHERE name = '张三';
-- 此时没有提交!其它会话看不到,且行锁一直持有

COMMIT;   -- 必须手动提交
```

> ⚠️ 生产事故常见来源:客户端(如某些 JDBC 配置、MySQL Workbench)关闭了 autocommit,开发者执行完 UPDATE 忘记 COMMIT,导致**行锁长期不释放**,其他事务大量超时。

### 3.3 三种开启事务的方式对比

| 方式 | 是否需要手动提交 | 说明 |
|------|-----------------|------|
| `autocommit=1` + 单条 SQL | 否 | 每条语句自动提交 |
| `autocommit=1` + `START TRANSACTION` | 是 | 显式事务,临时忽略 autocommit |
| `autocommit=0` | 是 | 所有语句都在事务中 |

```text
     autocommit = ON                  autocommit = OFF
 ┌───────────────────────┐        ┌───────────────────────┐
 │ UPDATE  → 自动 COMMIT │        │ UPDATE  ┐              │
 │ INSERT  → 自动 COMMIT │        │ INSERT  ├─ 同一事务    │
 │ DELETE  → 自动 COMMIT │        │ DELETE  ┘              │
 └───────────────────────┘        │ COMMIT ← 必须手动      │
                                  └───────────────────────┘
```

### 3.4 completion_type

控制 `COMMIT` 之后的行为:

```sql
SET completion_type = 1;  -- COMMIT 后自动开启新事务(等价 COMMIT AND CHAIN)
SET completion_type = 2;  -- COMMIT 后断开连接(等价 COMMIT AND RELEASE)
SET completion_type = 0;  -- 默认,普通提交
```

```sql
COMMIT AND CHAIN;      -- 提交并立刻用相同隔离级别开启新事务
COMMIT AND NO CHAIN;   -- 普通提交
COMMIT AND RELEASE;    -- 提交并断开连接
```

## 四、隐式提交场景

有些语句执行时会**强制提交当前事务**,即使你正处在 `START TRANSACTION` 中。这类语句称为**隐式提交(Implicit Commit)**。

### 4.1 会触发隐式提交的语句

| 类别 | 语句举例 |
|------|---------|
| DDL | `CREATE/ALTER/DROP TABLE`、`CREATE/DROP INDEX`、`CREATE/DROP DATABASE`、`TRUNCATE TABLE` |
| 权限操作 | `GRANT`、`REVOKE`、`SET PASSWORD`、`CREATE USER`、`DROP USER`、`ALTER USER`、`RENAME USER` |
| 事务控制 | `START TRANSACTION`(在已有事务中再开一个)、`SET autocommit = 1` |
| 锁相关 | `LOCK TABLES`、`UNLOCK TABLES` |
| 数据加载 | `LOAD DATA`(部分版本) |
| 复制相关 | `START SLAVE`、`STOP SLAVE`、`CHANGE MASTER TO`、`RESET MASTER` |
| 管理语句 | `ANALYZE TABLE`、`OPTIMIZE TABLE`、`REPAIR TABLE`、`CHECK TABLE`、`FLUSH`、`CACHE INDEX` |

### 4.2 演示:DDL 导致无法回滚

```sql
START TRANSACTION;

UPDATE account SET balance = 1 WHERE name = '张三';

CREATE TABLE tmp_log (id INT);   -- ← DDL,隐式提交了上面的 UPDATE!

ROLLBACK;                        -- 无效,UPDATE 已被提交

SELECT balance FROM account WHERE name = '张三';
```

```text
+---------+
| balance |
+---------+
|    1.00 |    ← 回滚失败,值已被永久修改
+---------+
```

### 4.3 演示:嵌套 START TRANSACTION

MySQL **不支持真正的嵌套事务**。在事务中再次执行 `START TRANSACTION` 会先提交前一个事务。

```sql
START TRANSACTION;
UPDATE account SET balance = 100 WHERE name = '李四';

START TRANSACTION;      -- ← 隐式提交上面的 UPDATE
UPDATE account SET balance = 200 WHERE name = '王五';
ROLLBACK;               -- 只回滚了王五

SELECT name, balance FROM account WHERE name IN ('李四','王五');
```

```text
+--------+---------+
| name   | balance |
+--------+---------+
| 李四   |  100.00 |   ← 被隐式提交,保留
| 王五   | 1000.00 |   ← 成功回滚
+--------+---------+
```

> 需要"嵌套"语义时,用 **SAVEPOINT** 模拟(Spring 的 `PROPAGATION_NESTED` 正是基于保存点实现的)。

### 4.4 DELETE vs TRUNCATE

```sql
START TRANSACTION;
DELETE FROM tmp_log;      -- DML,可回滚
ROLLBACK;                 -- ✅ 数据恢复

START TRANSACTION;
TRUNCATE TABLE tmp_log;   -- DDL,隐式提交
ROLLBACK;                 -- ❌ 无效,数据已清空
```

## 五、事务隔离级别

### 5.1 四种标准隔离级别

SQL 标准定义了四种隔离级别,隔离性由弱到强、并发性由强到弱:

```text
 并发性能 高 ──────────────────────────────────► 低
 隔离强度 弱 ──────────────────────────────────► 强

 READ        READ        REPEATABLE     SERIALIZABLE
 UNCOMMITTED COMMITTED   READ
 (RU)        (RC)        (RR,默认)      (串行化)
```

### 5.2 隔离级别与并发问题对照表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现机制 |
|---------|------|-----------|------|---------|
| READ UNCOMMITTED | ✅ 可能 | ✅ 可能 | ✅ 可能 | 不加读锁,直接读最新数据 |
| READ COMMITTED | ❌ 不会 | ✅ 可能 | ✅ 可能 | MVCC,**每条语句**生成新 Read View |
| REPEATABLE READ | ❌ 不会 | ❌ 不会 | ⚠️ 标准会 / InnoDB 基本不会 | MVCC,**事务首次快照读**生成一次 Read View + 间隙锁 |
| SERIALIZABLE | ❌ 不会 | ❌ 不会 | ❌ 不会 | 所有 SELECT 隐式加共享锁,读写互斥 |

> **注意**:InnoDB 的 RR 级别通过 **MVCC(解决快照读幻读)+ Next-Key Lock(解决当前读幻读)** 基本消除了幻读,这是 InnoDB 强于标准 SQL 定义的地方。

### 5.3 查看与设置隔离级别

```sql
-- MySQL 8.0
SELECT @@transaction_isolation;         -- 会话级
SELECT @@global.transaction_isolation;  -- 全局级

-- MySQL 5.7 及以前
SELECT @@tx_isolation;
```

```text
+-------------------------+
| @@transaction_isolation |
+-------------------------+
| REPEATABLE-READ         |
+-------------------------+
```

```sql
-- 设置当前会话
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 设置全局(仅对新连接生效)
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 只对下一个事务生效
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

配置文件持久化:

```ini
[mysqld]
transaction-isolation = READ-COMMITTED
```

### 5.4 为什么很多互联网公司改用 RC?

| 对比项 | REPEATABLE READ | READ COMMITTED |
|--------|----------------|----------------|
| 间隙锁 | 使用,锁范围大 | 基本不用(仅外键、唯一键检查) |
| 死锁概率 | 较高 | 较低 |
| 并发度 | 较低 | 较高 |
| binlog 格式要求 | STATEMENT 也安全 | 必须 ROW |
| 主从一致性 | 天然保证 | 依赖 ROW 格式 |
| 长事务对 undo 的压力 | 大(视图持续整个事务) | 小 |

Oracle、PostgreSQL 默认都是 RC;阿里、腾讯等大厂 MySQL 规范也普遍推荐 RC。

## 六、各隔离级别下的并发问题

### 6.1 三大并发读问题

```text
┌────────────────────────────────────────────────────────────┐
│ 脏读 (Dirty Read)                                           │
│   读到了别的事务【未提交】的数据,对方回滚后数据就是错的     │
├────────────────────────────────────────────────────────────┤
│ 不可重复读 (Non-Repeatable Read)                            │
│   同一事务内两次读【同一行】,结果不同(别人 UPDATE 并提交) │
├────────────────────────────────────────────────────────────┤
│ 幻读 (Phantom Read)                                         │
│   同一事务内两次【范围查询】,行数不同(别人 INSERT 并提交)│
└────────────────────────────────────────────────────────────┘
```

**不可重复读 vs 幻读的区别**:

| 维度 | 不可重复读 | 幻读 |
|------|-----------|------|
| 关注点 | 同一行的**内容**变了 | 结果集的**行数**变了 |
| 触发操作 | UPDATE / DELETE | INSERT |
| 解决手段 | 行锁 / MVCC | 间隙锁 / Next-Key Lock |

### 6.2 还有两个写问题

**丢失更新 (Lost Update)**

```text
事务A 读 balance=1000
事务B 读 balance=1000
事务A 写 balance=1000-100=900,提交
事务B 写 balance=1000-200=800,提交   ← A 的扣款被覆盖了!
```

解决:悲观锁 `SELECT ... FOR UPDATE`,或乐观锁版本号:

```sql
-- 悲观锁
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = 1;

-- 乐观锁
UPDATE account SET balance = 900, version = version + 1
WHERE id = 1 AND version = 5;   -- 影响行数为 0 则说明被别人改过,重试

-- 最简单:让数据库自己算(原子操作)
UPDATE account SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
```

## 七、事务隔离级别演示

以下所有演示需要**两个终端窗口**,分别称为 Session A 和 Session B。

初始化数据:

```sql
USE trx_demo;
TRUNCATE TABLE account;
INSERT INTO account (id, name, balance) VALUES
(1, '张三', 1000.00), (2, '李四', 1000.00), (3, '王五', 1000.00);
```

### 7.1 READ UNCOMMITTED — 脏读

两个 session 都执行:

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

```text
时间轴  Session A                              Session B
─────────────────────────────────────────────────────────────────────
 T1    START TRANSACTION;                      START TRANSACTION;

 T2                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |
                                               +---------+

 T3    UPDATE account
       SET balance = 5000 WHERE id = 1;
       (未提交)

 T4                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 5000.00 |  ← 脏读!
                                               +---------+

 T5    ROLLBACK;

 T6                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |  ← 刚才读到的是幻觉
                                               +---------+
                                               COMMIT;
```

**危害**:如果 Session B 在 T4 基于 5000 做了业务决策(比如放款),事务 A 回滚后就造成资损。

### 7.2 READ COMMITTED — 解决脏读,存在不可重复读

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

```text
时间轴  Session A                              Session B (RC)
─────────────────────────────────────────────────────────────────────
 T1    START TRANSACTION;                      START TRANSACTION;

 T2                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |
                                               +---------+

 T3    UPDATE account
       SET balance = 5000 WHERE id = 1;
       (未提交)

 T4                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |  ← 无脏读 ✅
                                               +---------+

 T5    COMMIT;

 T6                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 5000.00 |  ← 不可重复读 ❌
                                               +---------+
                                               COMMIT;
```

同一个事务 B 内,T2、T4、T6 三次读同一行,得到了不同结果。

**危害场景**:一个报表事务先统计总额、再统计明细,中间数据被改,导致报表自相矛盾。

### 7.3 REPEATABLE READ — 解决不可重复读

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

```text
时间轴  Session A                              Session B (RR)
─────────────────────────────────────────────────────────────────────
 T1    START TRANSACTION;                      START TRANSACTION;

 T2                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |  ← 建立 Read View
                                               +---------+

 T3    UPDATE account
       SET balance = 5000 WHERE id = 1;
       COMMIT;

 T4                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 1000.00 |  ← 可重复读 ✅
                                               +---------+

 T5                                            COMMIT;

 T6                                            SELECT balance FROM account
                                               WHERE id = 1;
                                               +---------+
                                               | 5000.00 |  ← 事务结束后才看到
                                               +---------+
```

### 7.4 RR 下的"当前读幻读"现象

RR 的 MVCC 只保护**快照读**。如果事务中混用快照读和当前读,会看到一个有趣的现象:

```text
时间轴  Session A                              Session B (RR)
─────────────────────────────────────────────────────────────────────
 T1                                            START TRANSACTION;
                                               SELECT COUNT(*) FROM account;
                                               +----------+
                                               | 3        |
                                               +----------+

 T2    INSERT INTO account
       VALUES (4,'赵六',800);
       COMMIT;

 T3                                            SELECT COUNT(*) FROM account;
                                               +----------+
                                               | 3        |  ← 快照读,没幻读 ✅
                                               +----------+

 T4                                            SELECT COUNT(*) FROM account
                                               FOR UPDATE;      -- 当前读
                                               +----------+
                                               | 4        |  ← 幻行出现 ⚠️
                                               +----------+

 T5                                            UPDATE account SET balance=0;
                                               -- 影响 4 行(当前读)
                                               SELECT COUNT(*) FROM account
                                               WHERE balance=0;
                                               +----------+
                                               | 4        |  ← 自己改的都能看见
                                               +----------+
```

> 结论:**RR 下的快照读不会幻读,当前读靠 Next-Key Lock 阻止别人插入**。上例中 B 的第一次读是快照读、没加锁,所以 A 才插得进来。若 B 一开始就用 `FOR UPDATE`,A 的 INSERT 会被间隙锁阻塞。

### 7.5 SERIALIZABLE — 完全串行

```sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

```text
时间轴  Session A                              Session B (SERIALIZABLE)
─────────────────────────────────────────────────────────────────────
 T1                                            START TRANSACTION;
                                               SELECT * FROM account
                                               WHERE id = 1;
                                               (隐式加 S 锁)

 T2    START TRANSACTION;
       UPDATE account
       SET balance = 5000 WHERE id = 1;
       ...  ← 阻塞中,等待 S 锁释放

 T3                                            COMMIT;   -- 释放锁

 T4    Query OK, 1 row affected
       (5.32 sec)   ← 阻塞结束
       COMMIT;
```

若等待超时:

```text
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 默认 50 秒
```

### 7.6 死锁演示

```text
时间轴  Session A                              Session B
─────────────────────────────────────────────────────────────────────
 T1    START TRANSACTION;                      START TRANSACTION;

 T2    UPDATE account SET balance=balance-100
       WHERE id = 1;   -- 持有 id=1 的 X 锁

 T3                                            UPDATE account SET balance=balance-100
                                               WHERE id = 2;   -- 持有 id=2 的 X 锁

 T4    UPDATE account SET balance=balance+100
       WHERE id = 2;   -- 等待 B 释放 id=2

 T5                                            UPDATE account SET balance=balance+100
                                               WHERE id = 1;   -- 等待 A 释放 id=1
                                               → 死锁!
                                               ERROR 1213 (40001): Deadlock found
                                               when trying to get lock; try
                                               restarting transaction
```

InnoDB 检测到死锁后会自动回滚**代价较小**的那个事务。查看最近一次死锁:

```sql
SHOW ENGINE INNODB STATUS\G
-- 关注 LATEST DETECTED DEADLOCK 段落
```

避免死锁的实用做法:按**固定顺序**访问资源(如始终按 id 升序加锁)。

## 八、一致性读(快照读)与当前读

### 8.1 两种读的定义

| 类型 | 别名 | 是否加锁 | 读到的数据 |
|------|------|---------|-----------|
| 一致性读 | 快照读 / Consistent Read | 不加锁 | Read View 对应的历史版本 |
| 当前读 | 锁定读 / Current Read | 加锁 | 最新已提交版本 |

### 8.2 哪些语句是快照读

```sql
SELECT * FROM account WHERE id = 1;          -- 普通 SELECT(RC/RR 下)
SELECT COUNT(*) FROM account;
```

### 8.3 哪些语句是当前读

```sql
SELECT ... LOCK IN SHARE MODE;   -- 5.7 语法,加 S 锁
SELECT ... FOR SHARE;            -- 8.0 语法,加 S 锁
SELECT ... FOR UPDATE;           -- 加 X 锁

INSERT INTO ...;                 -- 隐式当前读
UPDATE ...;                      -- 隐式当前读
DELETE FROM ...;                 -- 隐式当前读
```

**为什么 DML 必须是当前读?** 因为要在最新数据上加锁修改,否则会基于过期数据覆盖别人的更新(丢失更新)。

### 8.4 MySQL 8.0 的锁等待选项

```sql
-- 拿不到锁立刻报错,不等待
SELECT * FROM account WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR 3572 (HY000): Statement aborted because lock(s) could not be acquired
--                     immediately and NOWAIT is set.

-- 拿不到锁就跳过被锁的行(适合队列表抢单场景)
SELECT * FROM task WHERE status = 0 LIMIT 10 FOR UPDATE SKIP LOCKED;
```

### 8.5 快照读与当前读的直观对比

```text
数据行 id=1 的版本链(最新在左)

  [balance=5000] ─► [balance=1000] ─► [balance=800]
   trx_id=102        trx_id=100        trx_id=98
        │                  │
        │                  └── 快照读(Read View 只认 ≤100 的版本)
        └───────────────────── 当前读(总是取最新已提交)
```

## 九、READ VIEW 机制

### 9.1 隐藏字段与版本链

InnoDB 每行数据都有三个隐藏字段:

| 字段 | 大小 | 说明 |
|------|------|------|
| `DB_TRX_ID` | 6 字节 | 最后一次修改该行的事务 ID |
| `DB_ROLL_PTR` | 7 字节 | 回滚指针,指向 undo log 中的上一版本 |
| `DB_ROW_ID` | 6 字节 | 隐藏主键(无主键且无唯一索引时才有) |

通过 `DB_ROLL_PTR` 串起来的就是**版本链**:

```text
     聚簇索引记录(最新)
   ┌──────────────────────────────┐
   │ id=1 balance=5000            │
   │ DB_TRX_ID = 102              │
   │ DB_ROLL_PTR ────────────┐    │
   └─────────────────────────│────┘
                             ▼
                    ┌──────────────────────┐   undo log
                    │ balance=1000         │
                    │ DB_TRX_ID = 100      │
                    │ DB_ROLL_PTR ────┐    │
                    └─────────────────│────┘
                                      ▼
                             ┌──────────────────┐
                             │ balance=800      │
                             │ DB_TRX_ID = 98   │
                             │ DB_ROLL_PTR=NULL │
                             └──────────────────┘
```

### 9.2 Read View 的四个核心字段

| 字段 | 含义 |
|------|------|
| `m_ids` | 创建 Read View 时,**当前活跃(未提交)** 的事务 ID 集合 |
| `min_trx_id` | `m_ids` 中的最小值 |
| `max_trx_id` | 系统即将分配给下一个事务的 ID(不是 m_ids 最大值) |
| `creator_trx_id` | 创建该 Read View 的事务自己的 ID |

### 9.3 可见性判断算法

对版本链上的每个版本,取其 `DB_TRX_ID = trx_id`,按顺序判断:

```text
┌──────────────────────────────────────────────────────────────┐
│ 1. trx_id == creator_trx_id ?                                │
│      → 可见(自己改的自己当然看得见)                        │
├──────────────────────────────────────────────────────────────┤
│ 2. trx_id < min_trx_id ?                                     │
│      → 可见(创建视图前就已提交)                            │
├──────────────────────────────────────────────────────────────┤
│ 3. trx_id >= max_trx_id ?                                    │
│      → 不可见(视图创建之后才开启的事务)                    │
├──────────────────────────────────────────────────────────────┤
│ 4. min_trx_id <= trx_id < max_trx_id:                        │
│      trx_id ∈ m_ids ? → 不可见(当时还没提交)               │
│      trx_id ∉ m_ids ? → 可见(当时已提交)                   │
└──────────────────────────────────────────────────────────────┘
        ▼ 不可见就顺着 DB_ROLL_PTR 找上一版本,重复判断
        ▼ 找到头都不可见 → 该行对本事务不存在
```

### 9.4 RC 与 RR 的唯一差别

```text
 READ COMMITTED                      REPEATABLE READ
 ┌───────────────────────┐           ┌───────────────────────┐
 │ BEGIN                 │           │ BEGIN                 │
 │ SELECT → 建 ReadView1 │           │ SELECT → 建 ReadView1 │
 │ SELECT → 建 ReadView2 │           │ SELECT → 复用 View1   │
 │ SELECT → 建 ReadView3 │           │ SELECT → 复用 View1   │
 │ COMMIT                │           │ COMMIT                │
 └───────────────────────┘           └───────────────────────┘
   每条语句一个视图                     整个事务一个视图
   → 能看到别人新提交的                → 始终看到同一份快照
   → 不可重复读                        → 可重复读
```

**一句话记忆**:RC 是**语句级**快照,RR 是**事务级**快照。

### 9.5 手工推演一个例子

假设当前活跃事务为 `{100, 200}`,下一个事务 ID 为 `300`,事务 200 执行快照读:

```text
Read View:
  m_ids          = [100, 200]
  min_trx_id     = 100
  max_trx_id     = 300
  creator_trx_id = 200

版本链: [trx_id=250] → [trx_id=200] → [trx_id=100] → [trx_id=80]

判断:
  250: 100<=250<300 且 250∉m_ids → 可见?
       ⚠️ 注意 250 是在视图创建前就已提交的事务 → 可见,返回该版本
  (若 250 仍活跃则应在 m_ids 中,此处不在,说明已提交)
```

再看事务 100 的视角(`creator_trx_id = 100`):

```text
版本链: [trx_id=250] → [trx_id=200] → [trx_id=100] → [trx_id=80]
  250 → 可见(已提交且 < max_trx_id)
```

若 250 尚未提交,则 m_ids = [100, 200, 250],判断为不可见,继续向下找 200,200 ∈ m_ids 也不可见,再找 100 —— 等于 creator_trx_id,可见。

### 9.6 undo log 的两种类型

| 类型 | 产生语句 | 何时删除 |
|------|---------|---------|
| insert undo log | INSERT | 事务提交后立即可删除(不需要 MVCC) |
| update undo log | UPDATE / DELETE | 需等到没有任何 Read View 依赖它时,由 purge 线程删除 |

这解释了为什么**长事务会导致 undo 表空间暴涨**:只要老事务的 Read View 还在,历史版本就不能被清理。

## 十、长事务的危害与监控

### 10.1 长事务的四大危害

```text
┌──────────────────────────────────────────────────────────┐
│ 1. undo log 膨胀                                          │
│    老视图不释放 → purge 无法回收 → ibdata1 / undo 暴涨   │
│    (ibdata1 只增不减,只能重建实例才能回收)              │
├──────────────────────────────────────────────────────────┤
│ 2. 锁长期占用                                             │
│    行锁、间隙锁持有到事务结束 → 其它事务大面积等待/超时   │
├──────────────────────────────────────────────────────────┤
│ 3. 主从延迟                                               │
│    大事务的 binlog 在从库串行重放 → 秒级甚至分钟级延迟    │
├──────────────────────────────────────────────────────────┤
│ 4. 回滚代价高 / MDL 阻塞                                  │
│    大事务回滚耗时可能比执行还久;未提交事务持有 MDL 锁,   │
│    导致 DDL 卡住,进而后续所有查询排队(雪崩)            │
└──────────────────────────────────────────────────────────┘
```

### 10.2 查询当前运行的事务

       LEFT(trx_query, 50) AS query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

| 421990 | LOCK WAIT | 2026-08-14 10:41:55 |           40 |      93 |
+--------+-----------+---------------------+--------------+---------+
```

## 十一、分布式事务简介

### 11.1 为什么需要分布式事务

单机事务只能保证**一个数据库实例**内的 ACID。当业务跨越多个库(分库分表)、或跨越多个服务(订单库 + 库存库)时,就需要分布式事务。

### 11.2 两阶段提交 (2PC)

```text
              ┌──────────────────┐
              │ 事务协调者 (TM)   │
              └────────┬─────────┘
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ RM1 订单 │    │ RM2 库存 │    │ RM3 账务 │
  └─────────┘    └─────────┘    └─────────┘

阶段一:PREPARE(投票)
  TM → 所有 RM: "准备好了吗?"
  RM: 执行事务但不提交,写 redo/undo,回复 YES / NO

阶段二:COMMIT / ROLLBACK(执行)
  全部 YES → TM 广播 COMMIT
  任一 NO   → TM 广播 ROLLBACK
```

**2PC 的问题**:

| 问题 | 说明 |
|------|------|
| 同步阻塞 | 参与者在 PREPARE 后一直持锁等待 |
| 单点故障 | TM 挂掉,RM 永远悬挂在 prepare 状态 |
| 数据不一致 | 第二阶段部分 RM 收到 COMMIT、部分没收到 |

### 11.3 MySQL XA 事务

MySQL 实现了 XA 规范(InnoDB 支持)。

```sql
XA START 'xid1';                    -- 开启,进入 ACTIVE
UPDATE account SET balance = balance - 100 WHERE id = 1;
XA END 'xid1';                      -- 进入 IDLE
XA PREPARE 'xid1';                  -- 进入 PREPARED(第一阶段)
XA COMMIT 'xid1';                   -- 第二阶段提交
-- 或 XA ROLLBACK 'xid1';
```

状态机:

```text
  XA START            XA END           XA PREPARE        XA COMMIT
 ─────────► ACTIVE ──────────► IDLE ─────────────► PREPARED ─────────► 完成
                                │                      │
                                └── XA COMMIT ONE PHASE┘  XA ROLLBACK
```

查看悬挂的 XA 事务(崩溃恢复时非常有用):

```sql
XA RECOVER;
```

```text
+----------+--------------+--------------+------+
| formatID | gtrid_length | bqual_length | data |
+----------+--------------+--------------+------+
|        1 |            4 |            0 | xid1 |
+----------+--------------+--------------+------+
```

```sql
XA ROLLBACK 'xid1';   -- 人工清理悬挂事务
```

**注意事项**:

- 同一连接内 XA 事务与本地事务**不能混用**
- XA 事务在 `PREPARED` 状态下持有锁,连接断开后事务仍存在,必须显式处理
- MySQL 5.7 之前 XA 与 binlog 配合有 bug,生产使用建议 5.7+

### 11.4 MySQL 内部的两阶段提交

即使单机,MySQL 也在用 2PC:协调 **redo log(InnoDB)** 与 **binlog(Server 层)** 的一致性。

```text
  UPDATE 执行
      │
      ├─► 写 redo log,标记 prepare 状态   ← 阶段一
      ├─► 写 binlog 并 fsync
      └─► 写 redo log,标记 commit 状态    ← 阶段二

  崩溃恢复规则:
    redo=commit          → 直接提交
    redo=prepare + binlog完整 → 提交
    redo=prepare + binlog缺失 → 回滚
```

这保证了主库与从库(依赖 binlog)不会出现数据不一致。

### 11.5 柔性事务方案(实际业务更常用)

2PC 太重,互联网场景多采用**最终一致性**方案:

| 方案 | 核心思想 | 适用场景 |
|------|---------|---------|
| TCC | Try 预留资源 / Confirm 确认 / Cancel 取消 | 强一致要求、能改造业务接口 |
| 本地消息表 | 业务与消息写同一本地事务,轮询投递 | 简单可靠,容忍延迟 |
| 事务消息 | RocketMQ 半消息 + 回查 | 异步解耦 |
| Saga | 长事务拆成多个本地事务 + 补偿 | 流程长、跨多服务 |
| 最大努力通知 | 重试通知 + 对账兜底 | 支付回调类 |

常见框架:Seata(AT / TCC / Saga / XA 模式)、Hmily、DTM。

## 十二、事务最佳实践

### 12.1 事务要短

```sql
-- ❌ 反例:事务里塞了 RPC 调用和文件 IO
START TRANSACTION;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
-- 调用第三方支付接口(可能 3 秒超时)...
-- 生成 PDF 文件...
UPDATE orders SET status = 1 WHERE id = 1;
COMMIT;

-- ✅ 正例:先做外部调用,事务只包住数据库操作
-- 1. 调用第三方支付(事务外)
-- 2. 开事务
START TRANSACTION;
UPDATE orders SET status = 1 WHERE id = 1 AND status = 0;
COMMIT;
```

原则:**事务中不做网络调用、不做大计算、不等用户输入**。

### 12.2 大批量操作要分批

```sql
-- ❌ 一次删除 1000 万行:巨大 undo、长时间锁、主从延迟
DELETE FROM log WHERE created_at < '2024-01-01';

-- ✅ 分批删除
-- 循环执行直到 affected rows = 0
DELETE FROM log WHERE created_at < '2024-01-01' LIMIT 2000;
```

### 12.3 固定顺序访问,减少死锁

```sql
-- ❌ A 转 B 与 B 转 A 并发时容易死锁
-- ✅ 始终按 id 升序加锁
START TRANSACTION;
SELECT * FROM account WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

### 12.4 应用层必须处理死锁重试

```java
int retry = 3;
while (retry-- > 0) {
    try {
        transferMoney(from, to, amount);
        break;
    } catch (DeadlockLoserDataAccessException e) {
        if (retry == 0) throw e;
        Thread.sleep(50 + random.nextInt(100));  // 随机退避
    }
}
```

死锁不是 bug,是并发系统的正常现象,**必须**在应用层重试。

### 12.5 用条件更新代替"读-改-写"

```sql
-- ❌ 需要额外加锁,且易出错
SELECT stock FROM product WHERE id = 1;     -- 应用判断 stock >= 1
UPDATE product SET stock = stock - 1 WHERE id = 1;

-- ✅ 一条语句原子完成,影响行数为 0 即库存不足
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
```

### 12.6 索引与锁范围

RR 隔离级别下,**没有走索引的更新会锁全表所有行**:

```sql
-- name 无索引 → 全表扫描 → 每行都加锁
UPDATE account SET balance = 0 WHERE name = '张三';

-- 建索引后只锁命中行 + 间隙
ALTER TABLE account ADD INDEX idx_name (name);
```

### 12.7 其他清单

| 建议 | 原因 |
|------|------|
| 显式指定隔离级别,别依赖默认值 | 不同环境配置可能不同 |
| 高并发场景考虑 RC + ROW binlog | 减少间隙锁与死锁 |
| 只读操作用 `START TRANSACTION READ ONLY` | 跳过事务 ID 分配等开销 |
| 不要在事务里 `SELECT *` 大结果集 | 内存与锁开销 |
| 连接池必须校验 autocommit 状态 | 防止连接复用时状态污染 |
| 监控 `innodb_trx` 长事务并告警 | 提前发现忘记 COMMIT |
| DDL 前先确认没有长事务 | 避免 MDL 锁雪崩 |
| Spring 中注意 `@Transactional` 自调用失效 | 代理机制导致事务不生效 |

### 12.8 Spring 事务传播行为速览

| 传播行为 | 说明 |
|---------|------|
| REQUIRED(默认) | 有事务就加入,没有就新建 |
| REQUIRES_NEW | 总是新建事务,挂起外层 |
| NESTED | 用 SAVEPOINT 建嵌套事务,可部分回滚 |
| SUPPORTS | 有就加入,没有就非事务执行 |
| NOT_SUPPORTED | 挂起当前事务,非事务执行 |
| MANDATORY | 必须有事务,否则抛异常 |
| NEVER | 必须没有事务,否则抛异常 |

## 核心要点速记

```text
【ACID】
  A 原子性 → undo log 回滚
  C 一致性 → 目的,由 AID 保证
  I 隔离性 → 锁 + MVCC
  D 持久性 → redo log + WAL

【语法】
  START TRANSACTION / BEGIN → COMMIT / ROLLBACK
  SAVEPOINT sp / ROLLBACK TO sp(部分回滚,不结束事务)
  autocommit 默认 ON,每条 SQL 一个事务

【隐式提交】
  DDL、TRUNCATE、GRANT、LOCK TABLES、再次 START TRANSACTION
  → MySQL 无真正嵌套事务,用 SAVEPOINT 模拟

【隔离级别】
  RU  → 脏读、不可重复读、幻读 全有
  RC  → 解决脏读            (语句级 Read View)
  RR  → 解决不可重复读(默认)(事务级 Read View + Next-Key Lock)
  SER → 全解决,读写互斥,串行

【并发问题】
  脏读       = 读到未提交
  不可重复读 = 同一行两次读内容不同 (UPDATE)
  幻读       = 范围查询行数变了     (INSERT)

【读的两种模式】
  快照读:普通 SELECT,不加锁,读版本链历史版本
  当前读:FOR UPDATE / FOR SHARE / INSERT / UPDATE / DELETE,加锁读最新

【Read View 四字段】
  m_ids(活跃事务)/ min_trx_id / max_trx_id / creator_trx_id
  可见性:自己改的可见;< min 可见;>= max 不可见;
          区间内看是否在 m_ids,在则不可见
  RC 每条语句建视图,RR 整个事务一个视图 ← 二者唯一差别

【长事务】
  危害:undo 膨胀、锁不释放、主从延迟、MDL 阻塞
  监控:information_schema.innodb_trx、sys.innodb_lock_waits
  处置:KILL 连接 / 设 wait_timeout / innodb_lock_wait_timeout

【分布式事务】
  XA:XA START → END → PREPARE → COMMIT,XA RECOVER 查悬挂
  MySQL 内部 2PC:redo(prepare) → binlog → redo(commit)
  柔性事务:TCC / 本地消息表 / 事务消息 / Saga

【最佳实践】
  事务要短、不含 RPC;大批量分批;固定顺序加锁;
  死锁必重试;条件更新替代读改写;更新务必走索引
```
