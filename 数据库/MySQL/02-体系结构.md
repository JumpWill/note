# MySQL 体系结构

## 一、MySQL 概述

**MySQL** 是世界上最流行的开源关系型数据库之一,采用 **客户端/服务器 (Client/Server)** 架构,支持 SQL 作为数据访问语言。MySQL 的核心设计理念是**可插拔的存储引擎**,使得查询处理层与底层数据存储解耦,从而可以针对不同业务场景选用最合适的存储引擎。

**主要特性**:

- 多用户、多线程
- 支持事务(取决于存储引擎)
- 可插拔存储引擎(Pluggable Storage Engine)
- 跨平台(Linux、Windows、macOS)
- 主从复制、高可用集群
- 丰富的客户端 API 和连接器

---

## 二、MySQL 整体架构总览

MySQL 整体可以划分为三大逻辑层次:**客户端层、Server 层、存储引擎层**,再往下是操作系统与硬件。

```text
┌──────────────────────────────────────────────────────────────┐
│  1. 客户端层 (Client Layer)                                  │
│     - mysql 命令行、Navicat、DataGrip、JDBC、ODBC、PHP 驱动  │
│     - 各种语言的 MySQL Connector/Driver                      │
│     - 通过连接协议(C/S)与 MySQL Server 通信                  │
├──────────────────────────────────────────────────────────────┤
│  2. MySQL Server 层 (Server Layer)                           │
│     ┌────────────────────────────────────────────────────┐   │
│     │  连接器 (Connectors / Connection Pool)              │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  查询缓存 (Query Cache)  [8.0 已移除]               │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  分析器 (Parser / Lexer)                            │   │
│     │  词法分析 + 语法分析 → AST                          │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  预处理器 (Preprocessor)                            │   │
│     │  语义检查、表/列存在性、权限校验                    │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  优化器 (Optimizer)                                 │   │
│     │  RBO + CBO + 查询重写 + 索引选择                    │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  执行器 (Executor / Query Execution Engine)         │   │
│     │  调用存储引擎 API,获取/写入数据                     │   │
│     └────────────────────────────────────────────────────┘   │
├──────────────────────────────────────────────────────────────┤
│  3. 存储引擎层 (Storage Engine Layer) — 可插拔              │
│     InnoDB │ MyISAM │ Memory │ Archive │ NDB │ CSV │ Blackhole│
│     各引擎提供统一的 Handler API(Server 层不感知差异)        │
├──────────────────────────────────────────────────────────────┤
│  4. 文件系统层 (File System)                                 │
│     .frm .ibd .MYD .MYI .ibdata redo/undo/binlog/slow log   │
├──────────────────────────────────────────────────────────────┤
│  5. 操作系统 / 硬件 (OS & Hardware)                          │
│     内存、磁盘(SSD/HDD)、网络、CPU                          │
└──────────────────────────────────────────────────────────────┘
```

**注意**:
- Server 层在 MySQL 5.7 之前是单层结构,5.7+ 优化器/执行器已重写,8.0 移除 Query Cache。
- 存储引擎层是 MySQL 与其他数据库(如 PostgreSQL)最大的区别,实现了**存储与计算分离**。

## 三、连接层 (Connection Layer)

### 1. 连接器 (Connector)

连接器负责**客户端与服务端的通信**,主要职责:

- 维护客户端连接
- 验证用户名、密码
- 验证客户端是否有权访问目标数据库
- 获取该用户的权限信息(读入内存,后续依赖此缓存)

**连接命令**:

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p
```

**关键参数**:

| 参数                          | 说明                          |
|-------------------------------|-------------------------------|
| `max_connections`             | 最大并发连接数(默认 151)     |
| `wait_timeout`                | 非交互连接空闲超时(默认 8h)  |
| `interactive_timeout`         | 交互连接超时(默认 8h)        |
| `connect_timeout`             | 连接握手超时                  |
| `max_user_connections`        | 单用户最大连接                |
| `skip-name-resolve`           | 跳过 DNS 反向解析(生产推荐)  |

**权限验证**示例:

```sql
-- 修改 root 密码
ALTER USER 'root'@'localhost' IDENTIFIED BY 'newpwd';

-- 创建新用户
CREATE USER 'app'@'%' IDENTIFIED BY 'pwd123';

-- 授权
GRANT SELECT, INSERT, UPDATE ON shop.* TO 'app'@'%';

-- 刷新权限
FLUSH PRIVILEGES;
```

> **注意**:连接器一旦完成身份验证,后续该连接上的所有权限判断都基于**连接时读入的权限快照**,即便管理员后续修改了权限,该连接也只在重新建立时才生效。

### 2. 连接池 / 长连接管理

MySQL 客户端到服务端是一个 TCP 长连接(默认不立即断开)。频繁创建/销毁连接代价大(TCP 三次握手 + 鉴权开销),所以应用层通常会使用**连接池**:

- **Druid (Java)**:阿里开源,监控强
- **HikariCP (Java)**:性能极致的轻量连接池
- **c3p0 / DBCP**:老牌连接池
- **DBUtils / SQLAlchemy Pool**:其他语言

**长连接的问题**:MySQL 在执行过程中使用的内存(临时表、排序缓冲等)是在**连接对象**里管理的,长连接累积可能导致内存占用过大,出现 `MySQL server has gone away` 或 OOM。

**解决方案**:

```sql
-- 1. 定期断开长连接(应用侧)
-- 2. 客户端主动重置连接
mysql_reset_connection();

-- 3. 服务端设置自动回收
SET GLOBAL wait_timeout = 28800;
SET GLOBAL interactive_timeout = 28800;
```

### 3. 通信协议

MySQL 客户端与服务端之间使用**半双工**通信协议,支持多种协议:

| 协议                            | 说明                                    |
|---------------------------------|-----------------------------------------|
| **MySQL Native Protocol (TCP)** | 默认,基于 TCP/SSL                       |
| **Unix Socket**                 | 本机连接(默认 `/tmp/mysql.sock`)        |
| **Named Pipe (Windows)**        | Windows 命名管道                         |
| **Shared Memory (Windows)**     | 共享内存(效率最高,但仅 Windows)        |
| **X Protocol**                  | MySQL 5.7+ 提供,基于 Google Protobuf   |

**MySQL 协议特点**:

- 半双工:客户端发送请求,服务端返回响应,不能同时
- 简单、紧凑、二进制格式
- 支持 SSL/TLS 加密(8.0 默认支持认证插件 `caching_sha2_password`)
- 支持压缩 (`--compress`)

```text
客户端                              服务端
   │                                  │
   │  TCP 三次握手                     │
   │ <──────────────────────────────> │
   │                                  │
   │  客户端认证包(用户名/密码/库名)  │
   │ ───────────────────────────────> │
   │                                  │
   │  OK / Error 包                   │
   │ <─────────────────────────────── │
   │                                  │
   │  COM_QUERY 请求                  │
   │ ───────────────────────────────> │
   │                                  │
   │  Result Set / OK                 │
   │ <─────────────────────────────── │
```

## 四、查询缓存 (Query Cache) — 8.0 已移除

> MySQL 5.7 及之前版本提供查询缓存;**8.0 起已彻底移除**该功能,因为它在高并发写入场景下弊大于利。

### 1. 工作原理

以 `SELECT` 语句的文本和结果集作为缓存:

```sql
-- 第一次执行
SELECT * FROM user WHERE id = 1;
-- 结果被缓存,key = SQL 文本 hash

-- 第二次执行同样的 SQL
SELECT * FROM user WHERE id = 1;
-- 直接返回缓存(命中)
```

### 2. 命中条件(非常严格)

- SQL 文本必须**完全一致**(空格、大小写、注释都算)
- 表数据**未发生任何修改**
- 当前用户有相同访问权限
- 使用了确定性的函数(如 `NOW()` 不缓存)

### 3. 为何被废弃

| 问题                 | 说明                                                       |
|----------------------|------------------------------------------------------------|
| 命中率低             | 任何一次写操作都会清空对应表的**所有**缓存                |
| 内存碎片             | 缓存粒度小,易产生碎片                                     |
| 锁竞争               | 缓存失效瞬间大量请求同时尝试写缓存,严重时成为瓶颈        |
| 维护成本高           | 监控、调优、失效逻辑复杂                                  |
| 缓存语义过于严格     | `SELECT 1+1` 与 `SELECT 1 + 1` 视为不同                   |

**现代替代方案**:

- 应用层缓存 (Redis / Memcached)
- 物化视图 / 汇总表
- ProxySQL / MySQL Router 内置缓存
- **Buffer Pool** 在引擎层提供更高效的热点数据缓存

## 五、分析器 (Parser)

分析器的工作是**把 SQL 文本变成 MySQL 能理解的结构**,分为**词法分析**和**语法分析**两步。

### 1. 词法分析 (Lexer)

将 SQL 字符串拆解成**词元 (Token)**,识别关键字、标识符、字面量、运算符。

```sql
SELECT id, name FROM user WHERE age > 18;
```

拆解为:

| Token 类型    | Token 值     |
|---------------|--------------|
| KEYWORD       | SELECT       |
| IDENTIFIER    | id           |
| PUNCT         | ,            |
| IDENTIFIER    | name         |
| KEYWORD       | FROM         |
| IDENTIFIER    | user         |
| KEYWORD       | WHERE        |
| IDENTIFIER    | age          |
| OPERATOR      | >            |
| LITERAL       | 18           |
| PUNCT         | ;            |

### 2. 语法分析 (Parser)

根据 MySQL 语法规则(基于 **Yacc/Bison** 生成的 LALR 语法树),把 Token 序列组织成**抽象语法树 (AST)**。

```text
SELECT_STMT
├── select_list
│   ├── column_ref: id
│   └── column_ref: name
├── from_clause
│   └── table_ref: user
└── where_clause
    └── binary_op: >
        ├── column_ref: age
        └── literal: 18
```

### 3. 预处理器 (Preprocessor)

- 检查表、列是否存在
- 解析通配符 `*` 展开为全部列
- 校验别名
- 检查权限(粗粒度)
- 处理提示 (hints):`/*+ INDEX(t idx_name) */`

> 如果分析器发现错误,客户端会收到类似 `You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '...'` 的报错。

## 六、优化器 (Optimizer)

优化器是 MySQL Server 层**最聪明的组件**,负责把分析器生成的 AST **改写并转化为最优执行计划**。

### 1. 优化器的两大流派

| 优化策略  | 英文                | 思想                                   | 代表数据库            |
|-----------|---------------------|----------------------------------------|-----------------------|
| **RBO**   | Rule-Based Optimizer | 依据硬编码规则(优先级匹配)选择执行路径 | 早期 Oracle、PostgreSQL |
| **CBO**   | Cost-Based Optimizer | 依据统计信息估算成本,选成本最低方案   | 现代 MySQL、Oracle、SQL Server |

**MySQL 5.7+ 默认使用 CBO**,核心公式:

```
Cost = I/O 成本 + CPU 成本 + 内存成本 + 远程成本
```

优化器会枚举候选执行计划(基于**动态规划** + **贪心**),选择总成本最低者。

### 2. 优化器能做什么

#### (1) 逻辑优化 (查询重写)

```sql
-- 1. 谓词下推
SELECT * FROM t1 JOIN t2 ON t1.id = t2.id
WHERE t1.age > 18;
-- 优化为
SELECT * FROM (SELECT * FROM t1 WHERE age > 18) t1
JOIN t2 ON t1.id = t2.id;

-- 2. 常量折叠
SELECT * FROM t WHERE id = 1 + 2;
-- 等价
SELECT * FROM t WHERE id = 3;

-- 3. 等价变换
WHERE a > 10 AND a > 5  →  WHERE a > 10
WHERE NOT (a > 10)       →  WHERE a <= 10

-- 4. 外连接消除
SELECT * FROM t1 LEFT JOIN t2 ON t1.id = t2.id
WHERE t2.x IS NOT NULL;
-- 等价 INNER JOIN

-- 5. 子查询改写
SELECT * FROM t1 WHERE id IN (SELECT id FROM t2 WHERE name = 'a');
-- 改写为 semi-join
```

#### (2) 物理优化 (访问路径选择)

- **单表**:全表扫描、索引扫描、索引覆盖扫描、范围扫描、唯一扫描
- **多表**:Nested Loop Join、Hash Join(8.0.18+)、Sort Merge Join
- **排序**:filesort、索引顺序读取
- **聚合**:流式聚合、Hash 聚合

#### (3) 索引选择

当一个表有多个索引时,优化器根据**统计信息**估算每个索引的代价:

```sql
-- 强制使用索引(优先级最高)
SELECT * FROM t FORCE INDEX (idx_name) WHERE name = 'a';

-- 忽略指定索引
SELECT * FROM t IGNORE INDEX (idx_age) WHERE age = 18;

-- 索引提示(MySQL 8.0+)
SELECT /*+ INDEX(t idx_name) */ * FROM t WHERE name = 'a';
```

#### (4) 表 join 顺序

```sql
SELECT * FROM t1, t2, t3 WHERE t1.id = t2.id AND t2.id = t3.id;
```

3 张表有 3! = 6 种 join 顺序,优化器通过**动态规划**选择总成本最低的顺序。当表很多时(> 7),会切换为**贪心算法**(`optimizer_search_depth`)。

### 3. 查看执行计划

```sql
EXPLAIN SELECT * FROM user WHERE age > 18;

EXPLAIN FORMAT=JSON SELECT * FROM user WHERE age > 18;  -- JSON 格式
EXPLAIN FORMAT=TREE SELECT * FROM user WHERE age > 18;  -- TREE 格式(8.0.16+)
EXPLAIN ANALYZE SELECT * FROM user WHERE age > 18;       -- 实际执行统计
```

**EXPLAIN 关键字段**:

| 字段             | 含义                                             |
|------------------|--------------------------------------------------|
| `id`             | SELECT 序号                                       |
| `select_type`    | 查询类型(SIMPLE/PRIMARY/SUBQUERY/UNION/DERIVED) |
| `table`          | 表名                                             |
| `partitions`     | 命中的分区                                       |
| `type`           | 访问类型(system > const > eq_ref > ref > range > index > ALL) |
| `possible_keys`  | 可能用到的索引                                   |
| `key`            | 实际使用的索引                                   |
| `key_len`        | 索引使用长度(字节)                              |
| `ref`            | 与索引比较的列或常量                             |
| `rows`           | 优化器估算需要扫描的行数                         |
| `filtered`       | 条件过滤后剩余行百分比                           |
| `Extra`          | 额外信息(Using filesort / Using temporary / Using index) |

## 七、执行器 (Executor)

执行器根据优化器生成的**执行计划**,调用**存储引擎 API** 取数据并处理。

### 1. 执行器工作流程

```text
1. 权限校验 (精确到表/列级)
2. 打开表,获取存储引擎 Handler
3. 按照执行计划:
   a. 调用 handler.index_read / rnd_init / index_first 等
   b. 逐行获取数据
   c. 过滤(不满足 WHERE 条件的行丢弃)
   d. 排序(ORDER BY)
   e. 聚合(GROUP BY)
   f. 关联(JOIN)
4. 发送结果集给客户端
5. 关闭 Handler,释放资源
```

### 2. 调用引擎 API 示例

```sql
SELECT * FROM user WHERE name = 'tom' LIMIT 1;
```

执行器流程(假设 `name` 有索引):

```text
1. 调用 innodb 的 index_read 接口
   → 走 idx_name 索引定位 'tom'
2. 命中主键 → 通过主键回表 → 拿到完整行
3. LIMIT 1 → 找到第一条就停
4. 返回客户端
```

### 3. 有索引 vs 无索引

```sql
-- 无索引
SELECT * FROM user WHERE name = 'tom';
```

执行器会:

1. 调用 `innodb` 的 `rnd_init`
2. 循环调用 `rnd_next` 逐行扫全表
3. 每行检查 `name = 'tom'`,命中则返回
4. 扫完为止

这就是为什么大表必须建索引——**执行器能不能走索引,决定了一次查询是 O(1) 还是 O(N)**。

### 4. 慢查询日志

执行器会将执行时间超过 `long_query_time` 的 SQL 记录到慢日志:

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1.0;  -- 秒
SET GLOBAL log_output = 'TABLE';   -- 输出到 mysql.slow_log 表
```

## 八、存储引擎层 (Storage Engine Layer)

存储引擎是 MySQL **真正负责数据存储与读取**的组件,Server 层通过统一的 **Handler API** 与之交互,**存储引擎可插拔**是 MySQL 的核心特色。

### 1. 常见存储引擎

| 引擎        | 事务 | 锁粒度       | 索引结构     | 适用场景                |
|-------------|------|--------------|--------------|-------------------------|
| **InnoDB**  | 支持 | 行锁(默认)  | B+Tree       | OLTP、默认引擎(8.0+)  |
| **MyISAM**  | 不支持 | 表锁       | B+Tree       | 读多写少、统计类(已不推荐) |
| **Memory**  | 不支持 | 表锁       | Hash/B+Tree  | 临时表、缓存(重启丢失) |
| **Archive** | 不支持 | 行锁       | 压缩存储     | 日志归档                |
| **NDB**     | 支持 | 行锁       | Hash         | MySQL Cluster 集群      |
| **CSV**     | 不支持 | 表锁       | 文本         | 导入导出 CSV            |
| **Blackhole**| 不支持 | 无       | /            | 中继/黑洞,主从复制测试 |
| **Federated**| 不支持 | 表锁     | 远程表       | 访问远程 MySQL 表(已废弃) |

### 2. 查看与设置存储引擎

```sql
-- 查看支持的引擎
SHOW ENGINES;

-- 查看某表的引擎
SHOW TABLE STATUS LIKE 'user';

-- 建表指定引擎
CREATE TABLE log (
  id INT PRIMARY KEY AUTO_INCREMENT,
  msg TEXT
) ENGINE = Archive;

-- 改表引擎
ALTER TABLE user ENGINE = InnoDB;
```

### 3. InnoDB 核心特性

- **事务**:ACID、MVCC、Undo Log
- **行级锁 + 间隙锁**:高并发下表现好
- **聚簇索引**:数据即索引,主键组织数据
- **Buffer Pool**:内存缓存数据页与索引页
- **Redo/Undo Log**:持久化与回滚
- **自适应哈希索引 (AHI)**:自动将热点页转 Hash
- **Change Buffer**:二级索引变更缓存
- **Doublewrite Buffer**:防止页断裂

### 4. Handler API

Server 层访问存储引擎,只调用以下标准接口:

```cpp
class handler {
public:
    int rnd_init();              // 全表扫描初始化
    int rnd_next();              // 读下一行
    int index_init();            // 索引扫描初始化
    int index_read();            // 索引读
    int index_next();            // 下一行
    int write_row();             // 插入
    int update_row();            // 更新
    int delete_row();            // 删除
    int commit();                // 事务提交
    int rollback();              // 回滚
};
```

这样设计的好处:**优化器/执行器逻辑复用**,新增一个引擎只要实现这套接口即可。

### 5. 引擎选择建议

| 业务场景                       | 推荐引擎     |
|--------------------------------|--------------|
| 高并发 OLTP(订单、交易)       | InnoDB       |
| 只读 / 极少写入 / 复杂统计    | MyISAM(谨慎) |
| 临时表 / 高速缓存              | Memory       |
| 日志归档(只 insert + select)  | Archive      |
| 默认(没有特殊要求)             | InnoDB       |

## 九、SQL 执行完整流程(从连接到返回)

以一条带索引的查询为例,完整画出 MySQL 内部每一步:

```sql
SELECT id, name FROM user WHERE age = 25 AND status = 1
ORDER BY create_time DESC LIMIT 10;
```

### 1. 整体流程图

```text
┌──────────────────────────────────────────────────────────────────┐
│                          客户端                                  │
│  (mysql / JDBC / Navicat)                                       │
└────────────────────────┬─────────────────────────────────────────┘
                         │  1. 发起连接(TCP 握手)
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  连接器 (Connector)                                              │
│  - 校验用户名/密码(失败则拒绝)                                 │
│  - 加载该用户的权限快照到内存                                    │
│  - 分配/复用连接对象(线程)                                      │
└────────────────────────┬─────────────────────────────────────────┘
                         │  2. 接收 SQL 文本
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  查询缓存 (Query Cache)  [8.0 已移除]                            │
│  - 检查缓存命中                                                  │
│  - 命中直接返回,未命中则继续                                    │
└────────────────────────┬─────────────────────────────────────────┘
                         │  3. 进入分析器
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  分析器 (Parser)                                                 │
│  3.1 词法分析:把 SQL 拆为 Token 序列                            │
│  3.2 语法分析:生成 AST                                          │
│  3.3 预处理器:检查表/列是否存在、解析 *、校验权限               │
│  输出:解析树(SELECT_STMT)                                      │
└────────────────────────┬─────────────────────────────────────────┘                         │  4. 进入优化器
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  优化器 (Optimizer)                                              │
│  4.1 逻辑优化:谓词下推、外连接消除、子查询改写                 │
│  4.2 物理优化:                                                    │
│      - 选索引 idx_age_status 还是 idx_status?                    │
│      - 选 Nested Loop Join 还是 Hash Join?                       │
│      - 排序方式 filesort 还是走索引?                             │
│      - 估算每种方案的成本(行数 × 单行代价)                     │
│  4.3 输出:EXPLAIN 看到的执行计划                                │
│                                                                  │
│  本例最终选择:                                                    │
│  ┌──────────────────────────────────────────────────────┐        │
│  │ 1. 用 idx_age_status (age, status) 索引             │        │
│  │ 2. 找到 age=25 AND status=1 的记录                  │        │
│  │ 3. 按 create_time DESC 排序(filesort)               │        │
│  │ 4. LIMIT 10 取前 10 条                                │        │
│  └──────────────────────────────────────────────────────┘        │
└────────────────────────┬─────────────────────────────────────────┘
                         │  5. 进入执行器
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  执行器 (Executor)                                               │
│  5.1 权限二次校验(精确到列)                                     │
│  5.2 打开表,获取 InnoDB Handler                                 │
│  5.3 调用 handler.index_init(idx_age_status)                    │
│  5.4 循环:                                                      │
│        index_read → 判断 WHERE 条件 → 收集行 → 放入 sort buffer │
│  5.5 排序:filesort (归并排序)                                    │
│  5.6 LIMIT 10 截取前 10 条                                       │
│  5.7 构造结果集                                                  │
│  5.8 释放 Handler                                                │
└────────────────────────┬─────────────────────────────────────────┘
                         │  6. 返回结果
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  InnoDB 存储引擎                                                 │
│  - 内存:Buffer Pool 中是否有 idx_age_status 数据页?            │
│    - 有 → 直接返回(逻辑读)                                      │
│    - 无 → 从磁盘读取(物理读)                                    │
│  - 读到的页放入 Buffer Pool (LRU)                                │
│  - 应用 MVCC 可见性,按 ReadView 过滤                            │
│  - 命中 Undo Log 处理旧版本                                      │
└────────────────────────┬─────────────────────────────────────────┘
                         │  7. 结果回到客户端
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│                          客户端                                  │
│  - 接收 Result Set(列元数据 + 数据行)                          │
│  - 展示 / 处理                                                    │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 写操作流程补充

```sql
UPDATE user SET name = 'tom' WHERE id = 100;
```

写操作多了 **日志与锁** 环节:

```text
分析器 → 优化器 → 执行器
                ↓
            InnoDB:
            1. 加行锁 (X Lock)
            2. 读入数据页到 Buffer Pool
            3. 修改前 → 写 Undo Log (旧版本)
            4. 修改后 → 写 Redo Log (prepare 状态)
            5. 执行器调用 binlog 写 (server 层)
            6. Redo Log 提交 (commit 状态) — 两阶段提交
            7. 释放锁
```

**关键点**:`Server 层的 binlog` + `InnoDB 的 redo log` 通过**两阶段提交 (XA)** 保证一致性。

## 十、线程模型 (Thread Model)

MySQL 采用**单进程多线程**架构:一个 `mysqld` 进程,内部有多个线程分工合作。

### 1. 线程分类

| 线程类型                  | 数量            | 作用                          |
|---------------------------|-----------------|-------------------------------|
| **主线程 (Main)**         | 1               | 启动、监听、调度其他线程     |
| **连接线程 (Connection)** | 1 个/客户端连接 | 接收并处理客户端请求          |
| **IO 线程**               | 多(read/write)  | 异步磁盘 I/O                  |
| **Purge 线程**            | 1~4             | 清理 Undo Log                 |
| **Page Cleaner 线程**     | 1~4             | 将脏页刷回磁盘                |
| **Master 线程 (InnoDB)**  | 1               | 后台核心调度                  |
| **Dump 线程**             | 1/从库          | 主从复制 — 主库发送 binlog    |
| **SQL 线程**              | 1/从库          | 主从复制 — 从库重放 binlog    |
| **Log Writer**            | 1               | 写 Redo Log                   |
| **Log Flusher**           | 1               | 刷 Redo Log 到磁盘            |

### 2. 连接线程模型

```text
客户端 A ──→ 连接线程 A
客户端 B ──→ 连接线程 B
客户端 C ──→ 连接线程 C
            ⋮
客户端 N ──→ 连接线程 N
```

- 每来一个客户端连接,主线程就 fork 一个线程(或从线程池取)
- 线程处理完一个请求后**不会立即销毁**,而是等待该连接的下个请求
- 超时(由 `wait_timeout` 控制)后才被回收

### 3. 线程池 (Thread Pool)

**MySQL Enterprise Edition** 提供线程池插件,Community 5.6+ 也支持:

```sql
-- 安装插件
INSTALL PLUGIN thread_pool SONAME 'thread_pool.so';

-- 配置
SET GLOBAL thread_pool_size = 16;
SET GLOBAL thread_pool_algorithm = 1;  -- 0=低并发,1=高并发
```

**作用**:把"每连接一线程"改为"多连接共享线程池",应对**短连接高并发**场景(如秒杀),避免线程爆炸。

## 十一、内存结构 (Memory Structure)

MySQL 进程启动时即向操作系统申请一大块内存,内部由多个**内存结构**分工使用。

### 1. Server 层内存

| 内存结构                  | 作用                                     | 关键参数                                |
|---------------------------|------------------------------------------|------------------------------------------|
| **Query Cache**           | 缓存 SELECT 结果(8.0 移除)              | `query_cache_size`                       |
| **Table Cache**           | 缓存表结构(`.frm` 打开后的句柄)        | `table_open_cache`                       |
| **Table Definition Cache**| 缓存表定义信息                           | `table_definition_cache`                 |
| **Thread Cache**          | 缓存空闲连接线程                         | `thread_cache_size`                      |
| **Sort Buffer**           | filesort 用的排序缓冲                    | `sort_buffer_size` (会话级)             |
| **Join Buffer**           | Block Nested Loop Join 缓冲              | `join_buffer_size` (会话级)             |
| **Read Buffer / Read Rand**| 顺序读 / 随机读缓冲                     | `read_buffer_size`, `read_rnd_buffer_size` |
| **Tmp Table (MEMORY)**    | 中间结果(超过限制则落磁盘)              | `tmp_table_size`, `max_heap_table_size`  |
| **Net Buffer**            | 网络收发缓冲                             | `net_buffer_length`, `max_allowed_packet` |

### 2. InnoDB 内存 (InnoDB Buffer Pool)

InnoDB 的内存核心是 **Buffer Pool**,用于缓存**数据页和索引页**。

```text
┌──────────────────────────────────────────────────────┐
│                  InnoDB Buffer Pool                  │
│                     (默认 128 MB)                    │
│                                                       │
│  ┌──────────────────┐  ┌──────────────────┐          │
│  │  数据页 (Dirty)  │  │  索引页 (Dirty)  │          │
│  │  被修改未刷盘     │  │  被修改未刷盘     │          │
│  └──────────────────┘  └──────────────────┘          │
│                                                       │
│  ┌──────────────────┐  ┌──────────────────┐          │
│  │  数据页 (Clean)  │  │  索引页 (Clean)  │          │
│  │  与磁盘一致       │  │  与磁盘一致       │          │
│  └──────────────────┘  └──────────────────┘          │
│                                                       │
│  ┌──────────────────┐  ┌──────────────────┐          │
│  │  AHI (Adaptive   │  │  Change Buffer   │          │
│  │  Hash Index)     │  │  (二级索引变更)  │          │
│  └──────────────────┘  └──────────────────┘          │
└──────────────────────────────────────────────────────┘
```

**关键参数**:

| 参数                          | 默认值 | 说明                            |
|-------------------------------|--------|---------------------------------|
| `innodb_buffer_pool_size`     | 128 MB | Buffer Pool 总大小(建议物理内存的 50-70%) |
| `innodb_buffer_pool_instances`| 8      | 实例数(每实例独立管理 LRU)     |
| `innodb_log_buffer_size`      | 16 MB  | Redo Log 缓冲                   |
| `innodb_change_buffer_max_size`| 25   | Change Buffer 占 Buffer Pool 比例 |

**LRU 改进算法 (Midpoint LRU)**:

```text
┌──────────────────────────────────┐
│  Young 区 (热点,5/8)            │ ← 频繁访问,不被淘汰
├──────────────────────────────────┤
│  Midpoint 插入点                 │ ← 新页默认插入这里
├──────────────────────────────────┤
│  Old 区 (冷数据,3/8)            │ ← 长时间未访问会被淘汰
└──────────────────────────────────┘
```

InnoDB 没有用经典 LRU(因为全表扫描会"污染"热点),而是把新页插入到 **midpoint**,停留超过 `innodb_old_blocks_time` 后才晋升到 Young,避免冷数据冲掉热点。

### 3. 其他关键内存结构

- **Log Buffer**:写 Redo Log 的缓冲,事务 commit 时或满时刷盘
- **Change Buffer**:对二级索引的修改(insert/update/delete)先缓存,后台线程合并写入
- **Adaptive Hash Index (AHI)**:把热点 B+Tree 页转 Hash,加速等值查询
- **Lock Info**:行锁信息 (bitmap),占用空间小
- **Data Dictionary**:数据字典(8.0 后用 InnoDB 自身表存,无独立内存)

MySQL 的物理文件根据存储引擎不同而不同,以下是 MySQL 8.0 默认(`InnoDB`)的主要文件。

├── ib_logfile1             # Redo Log 2

### 2. InnoDB 文件

| 文件/结构        | 作用                                              |
|------------------|---------------------------------------------------|
| `.frm`           | 表结构定义(8.0 已合并到 `.ibd`)                  |
| `.ibd`           | 独立表空间(数据 + 索引 + 表结构)                 |
| `ibdata1`        | 系统表空间(数据字典、双写缓冲、undo log 系统表段) |

**InnoDB 逻辑存储结构**:

```text
Tablespace (表空间)
  └── Segment (段) — 数据段/索引段/回滚段
        └── Extent (区, 1MB = 64 pages × 16KB)
              └── Page (页, 16KB)
                    └── Row (行)
```

### 3. 日志文件

| 日志        | 产生者 | 作用                        | 关键参数                  |
|-------------|--------|-----------------------------|---------------------------|
| **Redo Log**| InnoDB | 崩溃恢复(crash-safe)        | `innodb_log_file_size`, `innodb_log_files_in_group` |
| **Undo Log**| InnoDB | MVCC + 事务回滚             | `innodb_undo_tablespaces` |
| **Binlog**  | Server | 主从复制 + 时间点恢复(PITR) | `log_bin`, `binlog_format` |
| **Error Log**| MySQL | 启动/运行/错误信息          | `log_error`               |
| **Slow Log**| Server | 慢查询记录                  | `slow_query_log`, `long_query_time` |
| **General Log**| Server| 所有 SQL(慎开)            | `general_log`             |
| **Relay Log**| 从库  | 接收主库 binlog 后落地      | `relay_log`               |

**Redo Log 与 Binlog 区别**:

| 维度       | Redo Log                  | Binlog                  |
|------------|---------------------------|-------------------------|
| 归属       | InnoDB 引擎层             | Server 层               |
| 记录内容   | 物理日志(页修改)         | 逻辑日志(SQL 行)       |
| 写入方式   | 循环覆盖                 | 追加不覆盖              |
| 用途       | 崩溃恢复                 | 复制 + 时间点恢复       |
| 大小       | 固定(`innodb_log_file_size`) | 累计增长              |
| 触发刷盘   | `innodb_flush_log_at_trx_commit` | `sync_binlog`     |

### 4. 其他文件

| 文件                  | 作用                                                |
|-----------------------|-----------------------------------------------------|
| `pid` 文件            | 进程 ID                                             |
| `socket` 文件         | Unix 本地通信                                       |

| `.TRN / .TRG`         | MyISAM 的触发器定义(8.0 已移走)                    |
| `.opt`                | 数据库选项(8.0 已废弃)                             |

## 十三、核心要点速记

- **MySQL 三大层**:客户端层 → Server 层 → 存储引擎层 → 文件系统 → 硬件
- **Server 层职责**:连接器、查询缓存(8.0 移除)、分析器、优化器、执行器
- **存储引擎层职责**:真正存取数据,InnoDB 是 8.0 默认引擎
- **连接器**:负责身份验证、连接管理、权限快照
- **分析器**:词法 + 语法 → AST
- **优化器**:RBO + CBO,产出最优执行计划(索引选择、join 顺序、查询重写)
- **执行器**:调存储引擎 API 返回数据
- **Handler API**:Server 与存储引擎的唯一桥梁,实现可插拔
- **SQL 完整流程**:连接 → 解析 → 优化 → 执行 → 引擎 → 结果
- **线程模型**:单进程多线程,每连接一线程(或用 Thread Pool)
- **内存核心**:Server 层有 sort/join buffer;InnoDB 的 Buffer Pool 是热点数据主战场
- **物理文件**:`.ibd`(数据/索引)、`ib_logfile`(Redo)、`binlog.*`(复制/PITR)、undo 表空间
- **Redo Log 引擎层物理、Binlog Server 层逻辑**,二者通过两阶段提交保证一致性
- **MVCC** 是 InnoDB 高并发的关键,依赖 Undo Log + ReadView
- **Buffer Pool 的 Midpoint LRU** 防止全表扫描污染热点
- **EXPLAIN** 是诊断 SQL 性能的首选工具
