# MySQL 分库分表 (Sharding)

## 一、为什么需要分库分表

### 1.1 单库单表的性能瓶颈

MySQL 单库单表在数据量、并发量、容量增长到一定规模后,会出现明显的性能拐点,再往上走,各种优化手段(索引、SQL 调优、缓存、读写分离)收益递减。

| 指标            | 经验拐点              | 现象                                          |
|-----------------|-----------------------|-----------------------------------------------|
| 单表行数        | **2000 万 ~ 5000 万** | B+Tree 高度从 3 层变 4 层,IO 翻倍             |
| 单表容量        | **> 10 GB**           | 全表扫描、ALTER TABLE、备份恢复变慢           |
| 单库连接数      | **> 1000**            | 连接耗尽,线程上下文切换严重                  |
| 单库 TPS        | **~ 5000**            | InnoDB 行锁竞争、buffer pool 抖动             |
| 单库 QPS        | **~ 1 万 ~ 2 万**     | CPU 接近饱和                                  |

> **B+Tree 高度与 IO 关系**(假设页大小 16KB,每页 1170 个键值指针):
> - 高度 2:约 **1170 × 1170 ≈ 137 万**行 → **2 次 IO**
> - 高度 3:约 **1170³ ≈ 16 亿**行 → **3 次 IO**
> - 高度 4:约 **1170⁴ ≈ 1900 亿**行 → **4 次 IO**
>
> 当行数过多导致高度变 4,即使有索引,每条查询都要多一次磁盘 IO,在 SSD 上也明显可感知。

### 1.2 瓶颈的三个维度

```text
                    ┌─────────────────────────────┐
                    │         单库单表瓶颈         │
                    └──────────────┬──────────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            │                      │                      │
            ▼                      ▼                      ▼
     ┌────────────┐         ┌────────────┐         ┌────────────┐
     │  数据量瓶颈 │         │  并发量瓶颈 │         │  存储瓶颈  │
     │            │         │            │         │            │
     │ 行数过多   │         │ 写锁竞争   │         │ 磁盘占满   │
     │ 单表过大   │         │ 连接耗尽   │         │ 备份缓慢   │
     │ ALTER 慢   │         │ CPU 打满   │         │ 主从延迟   │
     └────────────┘         └────────────┘         └────────────┘
```

- **数据量瓶颈**:单表行数过多导致索引效率下降,查询变慢
- **并发量瓶颈**:单库连接/锁/事务竞争激烈,TPS 上不去
- **存储瓶颈**:磁盘/备份/恢复成本线性上升,扩展困难

### 1.3 解决方案演进

```text
阶段 1:单机 MySQL
  └─ 数据量小,直接读写

阶段 2:读写分离 (主从 + 读写分流)
  └─ 缓解读压力,但写仍是单点

阶段 3:缓存 + 索引优化 (Redis + SQL 调优)
  └─ 进一步缓解读压力

阶段 4:分库分表 (Sharding)  ← 本章重点
  └─ 解决写瓶颈 + 容量瓶颈
```

### 1.4 分库分表能解决什么,不能解决什么

| 能解决                                                     | 不能解决                                          |
|------------------------------------------------------------|---------------------------------------------------|
| 单表数据量过大导致的查询慢                                 | 频繁的全表扫描(应靠索引/缓存)                    |
| 单库写并发过高                                             | 跨分片的复杂 JOIN                                 |
| 单库存储容量不足                                           | 海量数据写入(如 IoT 日志,应考虑 NoSQL)          |
| 主从延迟严重                                               | DBA 失误、SQL 写得太烂                            |
| 备份恢复慢                                                 | 业务设计本身的问题(冷热不分)                     |

## 二、分库分表 vs 读写分离 vs 分区

### 2.1 三者对比

| 维度        | 分区 (Partition)               | 读写分离 (Master-Slave)         | 分库分表 (Sharding)            |
|-------------|--------------------------------|---------------------------------|--------------------------------|
| **层次**    | 单库单表,逻辑拆分             | 单库多实例,数据冗余             | 多库多表,水平扩展              |
| **目的**    | 单表过大,优化索引与查询       | 提升读并发                      | 提升写并发 + 单表容量          |
| **实现**    | MySQL 原生 PARTITION BY        | 主从复制 + 中间件/应用分流      | 客户端代理 / 代理层中间件       |
| **数据**    | 一份,逻辑分多个分区           | 多份(主+从)                    | 一份,分散到 N 个库 M 张表     |
| **JOIN**    | 跨分区可 JOIN(同库)          | 同库 JOIN 没问题                 | 跨库 JOIN 困难                  |
| **事务**    | 本地事务                      | 同库事务没问题                  | 分布式事务                      |
| **复杂度**  | 低                            | 中                              | 高                              |
| **典型场景**| 单表 500 万~2000 万行         | 读多写少,读压力大               | 单库写并发 > 5000,容量 > 1 TB |

### 2.2 关系

```text
分区:  单库内部,单表横向拆分(物理上一组文件,逻辑上一个表)
        ↓ 当分区也搞不定
读写分离: 多副本,提升读能力,写还是单点
        ↓ 当写也撑不住
分库分表: 多写多读,水平扩展(真正的分布式数据库)
```

### 2.3 一张图看清演进

```text
[单库单表]   ──表行数变多──>   [分区表]   ──写并发变高──>   [读写分离]
                                                              │
                                                              ▼
                                          [主库写入撑不住]
                                                              │
                                                              ▼
                                                      [分库分表]
                                                              │
                                                              ▼
                                  [单库分表 → 多库分表 → 单元化/单元化部署]
```

## 三、拆分维度

### 3.1 垂直拆分

按**业务**或**列**拆分,把一个"宽"数据库/表拆成多个"窄"数据库/表。

#### (1) 垂直分库 (按业务拆分)

按业务领域把不同表分到不同数据库,每个库独立部署。

```text
拆分前(单库):
  ┌─────────────────────────────┐
  │  db_order (电商单库)         │
  │   ├─ user 表                │
  │   ├─ order 表               │
  │   ├─ product 表             │
  │   ├─ payment 表             │
  │   └─ inventory 表           │
  └─────────────────────────────┘

拆分后(按业务):
  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
  │ db_user      │ │ db_order     │ │ db_product   │ │ db_payment   │
  │  ├─ user     │ │  ├─ order    │ │  ├─ product  │ │  ├─ payment  │
  │  └─ address  │ │  └─ item     │ │  └─ category │ │  └─ refund   │
  └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

**优点**:
- 业务解耦,各库可独立优化(连接池、缓存、索引)
- 故障隔离,一个库挂了不影响其他库

**缺点**:
- 跨库 JOIN 难
- 分布式事务
- 应用层要管理多个数据源

#### (2) 垂直分表 (按列拆分)

把一张宽表按"访问频率"或"列大小"拆成多张表。

```text
拆分前:
  ┌──────────────────────────────────────────┐
  │  member (30 列)                          │
  │   ├─ id, name, mobile (基础)             │
  │   ├─ age, gender, avatar, bio (扩展)     │
  │   └─ last_login_ip, register_source...   │
  └──────────────────────────────────────────┘

拆分后:
  ┌────────────────────────┐  ┌──────────────────────────────┐
  │  member_base (热)      │  │  member_extend (冷)          │
  │   ├─ id                │  │   ├─ id (FK)                 │
  │   ├─ name              │  │   ├─ age, gender             │
  │   ├─ mobile            │  │   ├─ avatar (BLOB)           │
  │   └─ status            │  │   ├─ bio (TEXT)              │
  │  (访问频繁,小字段)     │  │   └─ register_source         │
  └────────────────────────┘  │  (访问少,大字段)             │
                              └──────────────────────────────┘
```

**典型场景**:
- 大字段(TEXT/BLOB)单独拆出
- 频繁访问的列(基础信息)和偶尔访问的列(扩展信息)分离

### 3.2 水平拆分 (Sharding)

按**数据行**拆分,把一张表的行分散到 N 个库 M 张表,每张表结构相同。

```text
拆分前:
  ┌──────────────────────────────────────┐
  │  order (10 亿行)                     │
  └──────────────────────────────────────┘

拆分后(按 user_id 哈希取模 4 库 × 4 表):
  ┌──────────────────────┐
  │  db_order_0          │  ┌──────────────────────┐
  │   ├─ order_0         │  │  db_order_1          │
  │   ├─ order_1         │  │   ├─ order_0         │
  │   ├─ order_2         │  │   ├─ order_1         │
  │   └─ order_3         │  │   ├─ order_2         │
  └──────────────────────┘  │   └─ order_3         │
                            └──────────────────────┘
  ┌──────────────────────┐  ┌──────────────────────┐
  │  db_order_2          │  │  db_order_3          │
  │   ├─ order_0         │  │   ├─ order_0         │
  │   ├─ order_1         │  │   ├─ order_1         │
  │   ├─ order_2         │  │   ├─ order_2         │
  │   └─ order_3         │  │   └─ order_3         │
  └──────────────────────┘  └──────────────────────┘
  16 张物理表,每张约 6250 万行
```

**优点**:
- 单表行数降到几百万,索引效率高
- 写并发分散到 N 个库
- 容量可水平扩展

**缺点**:
- 跨片 JOIN 困难
- 分布式事务
- 全局唯一 ID
- 跨片分页、排序、聚合
- 扩容复杂

### 3.3 垂直 + 水平组合

实战中通常是**先垂直,再水平**。

```text
第一步:垂直分库(按业务)
  电商 → db_user / db_order / db_product / db_payment

第二步:对热点库(如 db_order)再做水平拆分
  db_order → db_order_0..3 (按 user_id 哈希)

第三步:对超大表(如订单详情)继续水平拆分
  order_item → order_item_0..7 (按 order_id 哈希)
```

```text
电商系统典型拆分图:
┌─────────────────────┐
│  应用层              │
└─────────────────────┘
        │
   ┌────┴─────┬─────────────┬─────────────┐
   ▼          ▼             ▼             ▼
┌────────┐ ┌──────────────┐ ┌──────────┐ ┌──────────┐
│ 用户库  │ │ 订单库(分片) │ │ 商品库   │ │ 支付库   │
│ 单库    │ │ N 库 × M 表  │ │ 单库     │ │ 单库     │
└────────┘ └──────────────┘ └──────────┘ └──────────┘
              │
       ┌──────┼──────┬──────┐
       ▼      ▼      ▼      ▼
    ds_0   ds_1   ds_2   ds_3
```

## 四、分片策略 (Sharding Strategy)

### 4.1 哈希取模分片

按 Sharding Key 哈希后对 N 取模,定位到具体分片。

**路由公式**:`hash(sharding_key) % N = 分片序号`

```text
假设 N = 4
  user_id=100  → hash(100) % 4 = 0  → ds_0.order_0
  user_id=101  → hash(101) % 4 = 1  → ds_1.order_0
  user_id=102  → hash(102) % 4 = 2  → ds_2.order_0
  user_id=103  → hash(103) % 4 = 3  → ds_3.order_0
```

**优点**:
- 数据均匀分布,无热点
- 实现简单

**缺点**:
- **扩容困难**:N 从 4 改 8,几乎所有数据都要重新分配
- 常用做法是**成倍扩容**(2→4→8),但仍要迁移 50% 数据
- 哈希函数要稳定(不能换 hash 算法)

### 4.2 范围分片 (Range)

按 Sharding Key 的范围(数值、时间、地区)分片。

```text
按时间范围:
  order_2020  : 2020-01-01 ~ 2020-12-31
  order_2021  : 2021-01-01 ~ 2021-12-31
  order_2022  : 2022-01-01 ~ 2022-12-31
  order_2023  : 2023-01-01 ~ 2023-12-31

按地区范围:
  order_cn    : user_id 以 1 开头(中国)
  order_us    : user_id 以 2 开头(美国)
  order_eu    : user_id 以 3 开头(欧洲)

按数值范围:
  order_0_1kw : id 1 ~ 1000 万
  order_1_2kw : id 1000 万 ~ 2000 万
```

**优点**:
- 扩容简单(新增分片)
- 范围查询高效(同片连续)

**缺点**:
- **热点问题**:最新的片被频繁访问,旧数据变冷
- 适合有明显时间/范围特征的业务

### 4.3 一致性 Hash

将 Sharding Key 和节点都映射到 2^32 哈希环上,顺时针找到第一个节点。

```text
哈希环(2^32):
                         0
                         │
                         │
              ┌──────────┼──────────┐
              │          │          │
              │          │          │
   ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
              Node A    Node B    Node C
              (顺时针 → 查找下一个节点)

查找 user_id=100:
  hash(100) → 圆环上的某点 P
  顺时针 → 命中 Node B → 数据存到 Node B
```

**节点分布示意**:

```text
                   0
                   │
            Node D │
   ┌───────────────┼────────────────┐
   │               │                │
   │    Node A ─── │ ─── Node B     │
   │               │                │
   │           Node C               │
   └───────────────┼────────────────┘
                   │
```

**优点**:
- **扩容影响小**:新增一个节点,只影响该节点到上一个节点之间的数据,无需全量迁移
- 适合节点动态变化的场景

**缺点**:
- 实现相对复杂
- 数据倾斜(节点少时)需要**虚拟节点**解决

**虚拟节点**:
```text
每个真实节点映射多个虚拟节点,均匀分布在哈希环上:

真实节点 A → 虚拟节点 A1, A2, A3 (均匀分布)
真实节点 B → 虚拟节点 B1, B2, B3
真实节点 C → 虚拟节点 C1, C2, C3
...
```

### 4.4 业务分片

按业务属性分片,如按租户 ID、地区、行业。

```text
多租户 SaaS:
  tenant_id % 8 → 8 个库
  每库内部再按业务表分

外卖业务:
  按城市分:db_bj / db_sh / db_gz / db_sz ...
  北京用户订单 → db_bj
  上海用户订单 → db_sh
```

**优点**:
- 业务内聚,自然边界
- 便于单元化(每个分片对应完整业务)

**缺点**:
- 数据分布可能不均(某城市订单远多于其他)
- 需要提前规划分片维度

### 4.5 分片策略对比

| 策略         | 数据均匀性 | 扩容难度 | 范围查询 | 复杂度 | 典型场景                |
|--------------|------------|----------|----------|--------|-------------------------|
| **哈希取模** | 好         | 难       | 差       | 低     | 用户/订单核心表         |
| **范围分片** | 差(热点)  | 易       | 好       | 低     | 日志、订单(按时间)     |
| **一致性Hash**| 好         | 易       | 一般     | 中     | 缓存(Redis)、动态扩容 |
| **业务分片** | 看业务     | 看业务   | 看业务   | 中     | 多租户、单元化           |

## 五、分片键 (Sharding Key) 选择原则

### 5.1 什么是分片键

分片键 = 决定数据落到哪个分片的字段。

```sql
-- Sharding Key = user_id
-- 根据 user_id 决定数据在哪个库哪张表
SELECT * FROM order WHERE user_id = 100;
-- 路由计算 → ds_1.order_3
```

### 5.2 选择原则

| 原则           | 说明                                                                |
|----------------|---------------------------------------------------------------------|
| **高频查询字段** | 把最常 WHERE 的字段作为分片键,避免扫所有分片                       |
| **均匀分布**     | 避免热点(如用 user_id 比用 status_id 好,后者只有几个值)           |
| **业务相关**     | 业务上能"聚簇"的字段(如用户维度的订单,按 user_id 拆)            |
| **稳定不变**     | 不要选会频繁更新的字段作为分片键                                   |
| **避免跨片**     | 业务上 80% 的查询能落到单分片                                       |
| **非空唯一**     | 一般要求 NOT NULL 且分布均匀                                       |

### 5.3 反例:差的分片键

```text
差 1:用 status (0/1/2/3) → 数据严重倾斜
差 2:用 create_time → 最新热点数据集中
差 3:用地区(省份) → 数据不均,北京/上海远多于西藏
差 4:用 NULL 多的字段 → 路由不到正确分片
```

### 5.4 复合分片键

某些复杂场景用单一分片键不够,引入复合分片键。

```text
场景:订单表既要按用户查,又要按商家查
方案 1:双写(冗余),user_id 和 merchant_id 各一份
方案 2:基因法,将 user_id 和 merchant_id 编码到一个分片字段
方案 3:ES / 异构索引(查询库),DB 只做主键维度
```

**基因法示意**:
```text
user_id 后 6 位二进制
  101010 → 后 2 位 10 → 基因 = 2

merchant_id 生成时,把基因 2 嵌入到 merchant_id 的特定位
  merchant_id = 0x1234_5678_XXXX
                                  ↑
                                  嵌入基因 2

订单查询时,先按 user_id 算出基因,再按基因匹配 merchant_id
  保证同一 user 的订单和 merchant 的查询落到同一分片
```

## 六、分库分表带来的问题

### 6.1 问题清单

```text
分库分表后必须面对的 6 大问题:
  1. 跨库 JOIN
  2. 分布式事务
  3. 全局唯一 ID
  4. 跨分片分页 / 排序 / 聚合
  5. 二次查询
  6. 扩容 / 数据迁移
```

### 6.2 跨库 JOIN(基本禁止)

```text
JOIN 涉及两张表的物理位置:
  ┌────────────┐         ┌────────────┐
  │  ds_0      │         │  ds_1      │
  │  order_0   │         │  order_0   │
  └────────────┘         └────────────┘
        │                      │
        └────── 跨库 JOIN ─────┘
            性能差(网络 IO)
            可能不支持(中间件)
```

**解决方案**:

| 方案             | 说明                                                |
|------------------|-----------------------------------------------------|
| **冗余字段**     | 在 order 表冗余 user_name,避免 JOIN user           |
| **全局表**       | 小表(省份、字典)广播到所有分片                    |
| **数据组装**     | 第一次查 A,第二次查 B,应用层拼装                   |
| **ES / 宽表**    | 离线宽表导入 ES,复杂查询走 ES                       |
| **绑定表**       | 关系紧密的表强制同分片规则,JOIN 退化为单库 JOIN    |

### 6.3 分布式事务

一笔订单要写订单库 + 支付库 + 库存库,跨库事务如何保证一致性?

详见第八节。

### 6.4 全局唯一 ID

每张表都从 1 开始自增,会冲突,需要一个全局唯一 ID 方案。

详见第七节。

### 6.5 跨分片分页、排序、聚合

```sql
-- 业务:查所有订单按时间倒序,分页
SELECT * FROM order ORDER BY create_time DESC LIMIT 100000, 20;
```

分库分表后:
```text
1. 每个分片查自己片内的 top 100020 条 → 内存排序
2. 归并所有分片结果 → 全局排序
3. 取 LIMIT 100000, 20

问题:
  - 每个分片要查 100020 条,深分页性能差
  - 数据量大,归并排序内存爆
```

**解决方案**:

| 方案             | 说明                                                        |
|------------------|-------------------------------------------------------------|
| **禁止深分页**   | 业务上避免,如只能用 search_after / 游标分页                |
| **二次查询**     | 见 6.6 节                                                   |
| **ES 接管**      | 把搜索/分页/排序交给 Elasticsearch                          |
| **冗余宽表**     | 离线聚合数据到宽表,只查宽表                                |

### 6.6 二次查询

适用场景:按非分片键过滤 + 按分片键排序的分页。

```text
需求:查 "北京" 的所有用户订单,按 user_id 排序,分页

第一次查询:
  在每个分片查询 "北京" 的订单,记录最小 user_id
  → min_user_id_global = 各分片最小的 user_id 中的最小值

第二次查询:
  在每个分片查询 "北京" AND user_id >= min_user_id_global 的订单
  → 各分片结果合并即为正确结果
```

详细步骤:
```text
ds_0 北京订单: user_id ∈ [10, 30, 50, 70]      min = 10
ds_1 北京订单: user_id ∈ [20, 40, 60, 80]      min = 20
ds_2 北京订单: user_id ∈ [15, 35, 55, 75]      min = 15
ds_3 北京订单: user_id ∈ [25, 45, 65, 85]      min = 25

→ 全局 min = 10

第二次查询:
  在每个分片查 "北京" AND user_id >= 10
  合并即可得到正确排序
```

### 7.4 雪花算法 Snowflake (Twitter)

64 位 ID = 1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列号

```text
0 | 0000000 00000000 00000000 00000000 00000000 0 | 00000 00000 | 0000 00000000
^                  ^                                ^             ^
符号(0)          41 位时间戳(ms)                   10 位机器     12 位序列号
                                                    (workerId)   (sequence)
                                                    = 1024 节点   = 每 ms 4096 个

总长度:64 bit = 8 byte
理论 QPS:4096 × 1000 = 409 万/ms (单机)
可用时间:2^41 / (1000 × 60 × 60 × 24 × 365) ≈ 69 年 (从 2016 起)
```

**完整 Java 实现**:

```java
public class SnowflakeIdGenerator {

    // 起始时间戳:2026-01-01 00:00:00
    private static final long START_TIMESTAMP = 1735660800000L;

    // 各部分占位数
    private static final long WORKER_ID_BITS = 10L;
    private static final long SEQUENCE_BITS = 12L;

    // 最大值
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);   // 1023
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);    // 4095

    // 位移
    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;           // 12
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;  // 22

    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdGenerator(long workerId) {
        if (workerId > MAX_WORKER_ID || workerId < 0) {
            throw new IllegalArgumentException("workerId 越界");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = currentTime();

        // 时钟回拨检查
        if (timestamp < lastTimestamp) {
            throw new RuntimeException(
                "时钟回拨,等待 " + (lastTimestamp - timestamp) + " ms");
        }

        // 同一毫秒内,序列号递增
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0L) {
                // 当前毫秒序列号用完,等到下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = timestamp;

        // 拼接 64 位 ID
        return ((timestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
             | (workerId << WORKER_ID_SHIFT)
             | sequence;
    }

    private long waitNextMillis(long lastTimestamp) {
        long timestamp = currentTime();
        while (timestamp <= lastTimestamp) {
            timestamp = currentTime();
        }
        return timestamp;
    }

    private long currentTime() {
        return System.currentTimeMillis();
    }

    public static void main(String[] args) {
        SnowflakeIdGenerator gen = new SnowflakeIdGenerator(1);
        for (int i = 0; i < 10; i++) {
            System.out.println(gen.nextId());
        }
    }
}
```

**输出示例**:
```
507841892723200001
507841892723200002
507841892723200003
...
```

**时钟回拨问题**:

```text
Snowflake 严重依赖时间戳,如果机器时钟回拨(运维调时间、NTP 同步),会生成重复 ID

解决:
  1. 启动时记录基准时间戳,运行时记录上次时间戳
  2. 时钟回拨 < 5ms:等待追上
  3. 时钟回拨较多:报警,拒绝发号
  4. 美团 Leaf 用 ZK 持久化 workerId,雪花算法 + 弱依赖时间
  5. 滴滴 TinyID 增加趋势递增兜底
```

### 7.5 数据库号段模式

预分配 ID 段,应用从号段内自增,耗尽再申请。

```sql
CREATE TABLE id_alloc (
  biz_type VARCHAR(32) PRIMARY KEY,
  max_id   BIGINT NOT NULL DEFAULT 1,    -- 当前最大 ID
  step     INT NOT NULL DEFAULT 1000,    -- 每次申请的步长
  version  BIGINT NOT NULL DEFAULT 0     -- 乐观锁
);

-- 申请一段
UPDATE id_alloc
SET max_id = max_id + step, version = version + 1
WHERE biz_type = 'order';

-- 取回 max_id - step + 1 到 max_id 这一段 ID 用
```

**优点**:
- DB 压力小(每 N 个 ID 才写一次 DB)
- 趋势递增

**代表实现**:
- **滴滴 TinyID**:号段 + 异步加载预分配
- **美团 Leaf**:号段 + Snowflake

## 八、分布式事务方案

### 8.1 为什么需要

```text
下单流程:
  1. 创建订单 (db_order)
  2. 扣减库存 (db_inventory)
  3. 扣款    (db_payment)

要求:要么都成功,要么都失败(原子性)
分库分表后,这是 3 个独立库 → 单机事务已无法覆盖
```

### 8.2 CAP 定理

```text
C (Consistency) 一致性:所有节点同一时间看到同一数据
A (Availability) 可用性:每个请求都能收到响应
P (Partition tolerance) 分区容错:网络分区时系统仍能运行

分布式系统 P 必选,只能在 C 和 A 之间取舍:
  CP 系统:强一致,牺牲可用 → Zookeeper / etcd
  AP 系统:高可用,牺牲强一致 → Eureka / Cassandra
  实际生产多为 AP + 最终一致
```

### 8.3 方案对比

| 方案                | 一致性 | 性能 | 复杂度 | 适用场景                       |
|---------------------|--------|------|--------|--------------------------------|
| **2PC / XA**        | 强一致 | 差   | 中     | 银行、传统企业,低并发         |
| **TCC**             | 最终一致 | 中 | 高     | 资金、库存                     |
| **本地消息表**      | 最终一致 | 中 | 低     | 异步场景,业务解耦             |
| **RocketMQ 事务消息**| 最终一致 | 高 | 中     | 电商下单、支付                 |
| **Seata**           | 多种    | 高 | 中     | 阿里系 / 通用                  |
| **Saga**            | 最终一致 | 中 | 高     | 长事务、跨多服务               |

### 8.4 2PC / XA

**两阶段提交**,数据库层面的分布式事务协议。

```text
阶段 1:Prepare (投票)
  协调者 TM → 所有 RM: "你们能不能提交?"
       │
       ├──> db_order:   能/不能 (写 undo/redo,锁资源)
       ├──> db_payment: 能/不能
       └──> db_stock:   能/不能

阶段 2:Commit / Rollback (执行)
  TM 根据投票结果:
    全 yes → 所有 RM: 提交
    有一个 no → 所有 RM: 回滚
```

**缺点**:
- **同步阻塞**:Prepare 后锁资源,等所有 RM 响应
- **协调者单点**:TM 挂了,RM 一直等
- **数据不一致**:Commit 阶段部分 RM 收到,部分没收到

### 8.5 TCC (Try-Confirm-Cancel)

业务层面的两阶段提交,把资源预留放到应用层。

```text
Try 阶段:
  - 锁定资源(库存预扣、金额冻结)
  - 不真正修改数据,只预留

Confirm 阶段:
  - 真正执行业务(库存扣减、扣款)
  - 必须成功(失败要重试)

Cancel 阶段:
  - 释放 Try 预留的资源
  - 失败要重试

举例:下单扣库存
  Try:    stock.Try(deduct=1)  → 预扣库存,记录冻结
  Confirm: stock.Confirm()      → 真正扣减
  Cancel:  stock.Cancel()       → 释放冻结
```

**代码示例**:

```java
public interface TccStockService {
    @TwoPhaseBusinessAction(name = "stockDeduct")
    boolean tryDeduct(BusinessActionContext ctx, long skuId, int qty);

    boolean confirmDeduct(BusinessActionContext ctx);

    boolean cancelDeduct(BusinessActionContext ctx);
}

@Component
public class TccStockServiceImpl implements TccStockService {

    @Autowired private StockMapper stockMapper;
    @Autowired private FrozenStockMapper frozenMapper;

    @Override
    public boolean tryDeduct(BusinessActionContext ctx, long skuId, int qty) {
        // 1. 冻结库存
        int rows = stockMapper.freeze(skuId, qty);
        if (rows == 0) return false;
        // 2. 记录冻结明细
        frozenMapper.insert(ctx.getXid(), skuId, qty);
        return true;
    }

    @Override
    public boolean confirmDeduct(BusinessActionContext ctx) {
        // 真正扣减
        frozenMapper.confirm(ctx.getXid());
        stockMapper.deduct(ctx.getXid());
        return true;
    }

    @Override
    public boolean cancelDeduct(BusinessActionContext ctx) {
        // 释放冻结
        frozenMapper.cancel(ctx.getXid());
        stockMapper.unfreeze(ctx.getXid());
        return true;
    }
}
```

### 8.6 本地消息表

最常用、最简单的最终一致性方案。

```text
步骤:
  1. 业务方在同一个本地事务中:
     - 写业务表 (order)
     - 写消息表 (outbox),status='待发送'
  2. 定时任务扫描消息表,投递到 MQ
  3. MQ 消费者处理下游业务,处理完回写 status='已完成'

  ┌─────────────────┐
  │   业务事务       │
  │   ├─ 写 order   │
  │   └─ 写 outbox  │ (同一事务)
  └─────────────────┘
           │
           ▼
  ┌─────────────────┐
  │ 定时任务(轮询)   │
  │  outbox → MQ     │
  └─────────────────┘
           │
           ▼
  ┌─────────────────┐
  │ 下游消费 + 幂等  │
  └─────────────────┘
```

**优点**:实现简单,不依赖特定 MQ
**缺点**:有延迟(轮询间隔)

### 8.7 RocketMQ 事务消息

RocketMQ 4.3+ 提供的原生事务消息支持。

```text
流程:
  1. Producer 发送 Half(半)消息到 MQ
  2. MQ 持久化,返回 OK
  3. Producer 执行本地事务 (写 order)
  4. Producer 根据本地事务结果发送 Commit / Rollback
     - Commit → MQ 把 Half 消息变为可投递
     - Rollback → MQ 删除 Half 消息
  5. 如果 Producer 没响应(超时),MQ 反查 Producer
  6. Consumer 收到消息后,处理下游业务

  Producer            MQ                Consumer
      │  Half Msg      │                    │
      ├───────────────>│                    │
      │  OK             │                    │
      │<────────────────┤                    │
      │                 │                    │
      │  本地事务        │                    │
      │  (写 order)     │                    │
      │                 │                    │
      │  Commit/Rollback│                    │
      ├───────────────>│                    │
      │                 │                    │
      │                 │ 投递消息           │
      │                 ├───────────────────>│
      │                 │                    │ 处理下游
```

### 8.8 Seata (阿里)

Seata 提供 AT、TCC、SAGA、XA 四种模式。

**AT 模式**(默认,推荐):
```text
1. 一阶段:解析 SQL,生成前镜像 + 后镜像
2. 写 undo_log 表(本地)
3. 提交本地事务
4. 二阶段:
   - 成功 → 异步删除 undo_log
   - 失败 → 用 undo_log 回滚

特点:
  - 自动补偿(不需要写 Try/Confirm/Cancel)
  - 全局锁防脏写
  - 性能好(无锁等待)

Seata 架构:
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │   TC     │  │   TM     │  │   RM     │
  │ 协调者   │  │ 发起者   │  │ 资源     │
  │ (Server) │  │ (Client) │  │ (Client) │
  └──────────┘  └──────────┘  └──────────┘
```

### 8.9 Saga 模式

把长事务拆成多个本地事务,每个本地事务都有对应的补偿操作。

```text
T1 → T2 → T3 → T4 → 成功
       │
       └── 失败 → C1 ← C2 ← C3 ← C4 (逆向补偿)

T1 / C1:正向 + 逆向补偿成对出现
失败时从最近的 T 向前回滚

适用于:
  - 跨多服务的业务流程(订单 → 支付 → 物流 → 售后)
  - 业务流程长(秒级以上)
  - 不能用 TCC 锁资源的场景

框架:
  - Apache ServiceComb Saga
  - Seata Saga
```

```yaml
                sharding-algorithm-name: db_hash_mod
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: tbl_hash_mod

        # 2) 绑定表(强制 JOIN 时不退化为笛卡尔积)
        binding-tables:
          - order,order_item

        # 3) 广播表(每个库都全量)
        broadcast-tables:
          - dict_region
          - dict_industry

        # 4) 分片算法
        sharding-algorithms:
          db_hash_mod:
            type: HASH_MOD
            props:
              sharding-count: 4
          tbl_hash_mod:
            type: HASH_MOD
            props:
              sharding-count: 4

        # 5) 分布式主键
        key-generators:
          snowflake:
            type: SNOWFLAKE
            props:
              worker-id: 1

    # ==================== 属性 ====================
    props:
      sql-show: true                    # 打印 SQL
      sql-simple: true
      check-table-metadata-enabled: false
      query-with-cipher-column: false
```

### 10.4 路由流程

```text
执行 SQL:
  SELECT * FROM order WHERE user_id = 100

Sharding-JDBC 内部流程:

  ┌──────────────────┐
  │ SQL 解析 (Parse)  │  词法 + 语法分析
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │ SQL 改写 (Rewrite)│  逻辑表 → 实际表,补充分片键
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │ SQL 路由 (Route)  │  根据分片键决定去哪些库哪些表
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │ SQL 执行 (Execute)│  并行/串行发到真实库
  └────────┬─────────┘
           ▼
  ┌──────────────────┐
  │ 结果归并 (Merge)  │  内存合并 / 排序 / 聚合 / 分页
  └──────────────────┘
```

**路由类型**:

| 类型                | 触发条件                                  |
|---------------------|-------------------------------------------|
| **直接路由**        | Hint 强制指定                             |
| **标准路由**        | WHERE 带分片键的 `=` `IN` `BETWEEN`        |
| **笛卡尔积路由**    | 多表无关联,全分片遍历                     |
| **全库表路由**      | 广播表、不带分片键的查询                  |

### 10.5 绑定表 & 广播表

```sql
-- 绑定表:order 和 order_item 强制同分片规则
-- JOIN 不会变成笛卡尔积,只查同分片的两张表
SELECT o.*, i.*
FROM order o
JOIN order_item i ON o.order_id = i.order_id
WHERE o.user_id = 100;
-- 路由到:ds_1.order_1 + ds_1.order_item_1(同分片)

-- 广播表:每个 ds_0..3 都有完整 dict_region
SELECT o.*, r.region_name
FROM order o
JOIN dict_region r ON o.region_id = r.id
WHERE o.user_id = 100;
-- 路由到:ds_1.order_x + 任一 ds 的 dict_region(本地 JOIN)
```

### 10.6 Hint 强制路由

```java
// 强制把 SQL 路由到 ds_1
HintManager hintManager = HintManager.getInstance();
hintManager.setDatabaseShardingValue(1);
try {
    jdbcTemplate.queryForList("SELECT * FROM order");
} finally {
    hintManager.close();
}
```

## 十一、MyCat 实战

### 11.1 核心概念

| 概念          | 说明                                                |
|---------------|-----------------------------------------------------|
| **schema**    | 逻辑库(应用视角的库)                              |
| **table**     | 逻辑表                                              |
| **dataNode**  | 数据节点(物理库)                                  |
| **dataHost**  | 数据主机(物理库所在服务器)                        |
| **rule**      | 分片规则                                            |
| **ER 表**     | 子表跟随父表落到同节点(类似绑定表)               |

```text
应用视角:
  Schema (db_order)
    ├─ LogicTable (order)
    └─ LogicTable (order_item)

  db_order_0 (10.0.0.1:3306)
  db_order_1 (10.0.0.2:3306)
  db_order_2 (10.0.0.3:3306)
```

#### (3) rule.xml(分片规则)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mycat:rule SYSTEM "rule.dtd">
<mycat:rule xmlns:mycat="http://io.mycat/">

    <!-- 规则 1:取模 -->
    <tableRule name="sharding-by-userid-mod4">
        <rule>
            <columns>user_id</columns>
            <algorithm>mod-long</algorithm>
        </rule>
    </tableRule>
    <function name="mod-long" class="io.mycat.route.function.PartitionByMod">
        <property name="count">4</property>
    </function>

    <!-- 规则 2:范围分片(按时间) -->

        <rule>
            <columns>create_time</columns>
            <algorithm>partbymonth</algorithm>
        </rule>
    </tableRule>
    <function name="partbymonth" class="io.mycat.route.function.PartitionByMonth">
        <property name="dateFormat">yyyy-MM-dd</property>
        <property name="sBeginDate">2024-01-01</property>
        <property name="sEndDate">2026-12-31</property>
    </function>

    <!-- 规则 3:雪花算法 -->
    <tableRule name="sharding-by-snowflake">
        <rule>
            <columns>id</columns>
            <algorithm>partition-by-snowflake</algorithm>
        </rule>
    </tableRule>
    <function name="partition-by-snowflake"
              class="io.mycat.route.function.PartitionBySnowflake">
        <property name="workerId">1</property>
        <property name="count">4</property>
    </function>

    <!-- 规则 4:一致性 Hash -->
    <tableRule name="sharding-by-murmur">
        <rule>
            <columns>user_id</columns>
            <algorithm>murmur</algorithm>
        </rule>
    </tableRule>
    <function name="murmur" class="io.mycat.route.function.PartitionByMurmurHash">
        <property name="seed">0</property>
        <property name="count">4</property>
        <property name="virtualBucketTimes">160</property>
    </function>
</mycat:rule>
```

## 十二、数据迁移方案 (单库 → 分库分表)

### 12.1 总体思路

```text
双写阶段(不停服迁移):
  ┌─────────────────┐         ┌─────────────────┐
  │   老库(单库)    │         │   新库(分库分表)│
  └────────┬────────┘         └────────┬────────┘
           │                           │
           │   应用层双写              │
           └────────────┬──────────────┘
                        ▼
              ┌──────────────────┐
              │  MySQL Binlog    │
              │  Canal 订阅       │
              │  增量同步到新库    │
              └──────────────────┘

历史数据全量迁移:
  - 分批 SELECT,按 user_id 范围,写入新库对应分片
  - 工具:DATAx、DataX-Web、ShardingSphere-Scaling、阿里 DTS

切换:
  1. 老库停写(短暂)
  2. 校验新老库数据一致性
  3. 切读流量到新库
  4. 切写流量到新库
  5. 老库只读,留作回滚

回滚预案:
  - 切换过程保留老库可写 5~30 分钟
  - 异常时回切老库
```

### 12.2 全量迁移工具

| 工具                         | 厂商      | 特点                                  |
|------------------------------|-----------|---------------------------------------|
| **DataX**                    | 阿里      | 离线同步,JSON 配置,支持异构数据库     |
| **ShardingSphere-Scaling**   | Apache    | Sharding 官方迁移方案,自动校验        |
| **阿里 DTS**                 | 阿里云    | 商业,支持 MySQL 各种迁移场景          |
| **Canal**                    | 阿里      | Binlog 订阅,做增量同步                |
| **Maxwell**                  | Zendesk   | Binlog → JSON,做轻量增量              |

```text
ShardingSphere 自带迁移方案:

  ┌──────────────────┐
  │   老库集群       │ ──Binlog──┐
  └──────────────────┘           │
                                 ▼
                        ┌──────────────────┐
```

## 十三、扩容方案

### 13.1 成倍扩容 (2 → 4 → 8)

哈希取模方案常用,但要迁移 50% 数据。

```text
原方案:hash(user_id) % 4
  节点 0, 1, 2, 3

扩容:hash(user_id) % 8
  节点 0, 1, 2, 3, 4, 5, 6, 7

数据迁移:
  原节点 0 的数据中,hash % 8 == 0 留下,其余迁走
  原节点 1 的数据中,hash % 8 == 1 留下,其余迁走
  ...
  原节点 3 的数据中,hash % 8 == 3 留下,其余迁走
  + 新增节点 4, 5, 6, 7 接收迁移数据

数据迁移量 ≈ 50%(每个原节点迁走一半)
```

### 13.2 平滑扩容 (一致性 Hash)

```text
一致性 Hash 扩容:
  原节点 4 个: A, B, C, D
  新增节点 1 个: E

  哈希环上 E 的位置:
   ┌─────────────────────────┐
   │     A       B           │
   │   ─●───●───●───●───●─   │
   │  ↑       ↑           E  │
   │  原节点   原节点    ↑   │
   │                  新节点 │
   └─────────────────────────┘

只有 "D 到 E 之间" 这段环上的数据需要从 D 迁到 E
其他节点数据完全不动
迁移量 ≈ 1/N
```

### 13.3 实战推荐:成倍扩容

```text
实际生产多采用 "成倍扩容",原因:

  1. 一致性 Hash 节点少时数据倾斜,需大量虚拟节点,运维复杂
  2. 成倍扩容实现简单,数据迁移好做
  3. 业务初期规划好容量,基本 2-3 次扩容够用几年
```

### 13.4 扩容步骤

```text
1. 准备新节点 (ds_4, ds_5, ds_6, ds_7)
2. 修改分片规则 (从 4 库 → 8 库)
3. 双写过渡(老库 + 新库同时写)
4. 全量迁移老库数据到新库对应分片
5. 增量追平(Canal 订阅老库 Binlog)
6. 校验一致性
7. 切流量(读 → 写)
8. 下线老节点
```

## 十四、分库分表最佳实践

### 14.1 规划阶段

- **不要过度设计**:数据量 < 1000 万、QPS < 5000,单库单表足够
- **数据量预估**:按业务增速估算 2~3 年容量
- **分片数预留**:`实际节点数 × 2`,给扩容留空间
- **分片键选好**:查询最高频的字段,且分布均匀

### 14.2 设计阶段

| 设计原则          | 说明                                                |
|-------------------|-----------------------------------------------------|
| **核心表分片**    | 用户表、订单表等核心大表做分片                      |
| **小表不分片**    | 字典表、省份表保持单库,用全局表/广播表               |
| **避免跨片 JOIN** | 强需求就用宽表冗余,或 ES                          |
| **避免跨片事务**  | 业务拆解,异步化(本地消息表)                       |
| **索引冗余**      | 同一份数据按不同分片键冗余多份                      |

### 14.3 实施阶段

- **灰度切流**:先切 10% 流量 → 50% → 100%
- **可回滚**:切换保留老库可写 30 分钟以上
- **监控告警**:每个分片的 QPS、延迟、主键使用率
- **压测必做**:模拟真实数据量、并发,验证中间件性能

### 14.4 运维阶段

```text
1. 慢 SQL 监控(每分片)
2. 各分片数据量均衡度(不均 > 20% 要警觉)
3. 全局主键使用率(雪花 ID 用 40 年,但 workerId 要预留)
4. 中间件版本升级(每年至少一次)
5. 容量预警(单分片 > 70% 触发预警)
6. 备份策略:每个分片独立备份,合并恢复脚本
```

### 14.5 何时不分库分表

| 场景                          | 替代方案                |
|-------------------------------|-------------------------|
| 数据量 < 1000 万              | 索引 + 缓存 + 读写分离  |
| 主要是读,写很少              | 读写分离 + ES           |
| 业务多变,表结构常改           | 单库(后期再拆)         |
| 团队无中间件运维能力          | 直接上 TiDB / OceanBase |

### 14.6 新一代方案:NewSQL

当分库分表 + 中间件太复杂时,可以考虑原生分布式数据库:

| 数据库          | 厂商      | 特点                                        |
|-----------------|-----------|---------------------------------------------|
| **TiDB**        | PingCAP   | 兼容 MySQL 协议,自动分片,水平扩展           |
| **OceanBase**   | 阿里      | 金融级强一致,Oracle 兼容                    |
| **PolarDB-X**   | 阿里云    | MySQL 兼容,云原生分布式                     |
| **CockroachDB** | 开源      | PostgreSQL 兼容,全球分布式                  |

```text
传统方案:MySQL + 中间件 = 分库分表
  - 应用层处理分片路由
  - 自己解决分布式事务、ID

新一代方案:NewSQL (TiDB / OceanBase)
  - 数据库自己处理分片
  - 分布式事务原生支持
  - 应用无感知
  - 成本:部署运维复杂度换业务复杂度
```

## 十五、核心要点速记

### 15.1 何时分

- 单表 > **2000 万行**考虑分表
- 单库 > **10 GB** / QPS > 5000 考虑分库
- 写并发 > 5000 TPS 必分库

### 15.2 怎么分

| 维度     | 选择                            |
|----------|---------------------------------|
| 先垂直   | 按业务/列拆                     |
| 再水平   | 按行拆(选好 Sharding Key)     |
| 分片策略 | 哈希取模(均匀)+ 范围(易扩容) |

### 15.3 Sharding Key 选择

- 高频查询字段
- 均匀分布
- 业务上聚簇
- 稳定不变
- 避免 NULL

### 15.4 必须解决的问题

| 问题       | 方案                                |
|------------|-------------------------------------|
| 跨库 JOIN  | 冗余字段、宽表、ES                  |
| 分布式事务 | Seata AT / TCC / 本地消息表         |
| 全局 ID    | 雪花算法 / 号段模式                 |
| 跨片分页   | ES / 二次查询 / 禁深分页            |
| 扩容       | 成倍扩容 + 双写过渡                  |

### 15.5 中间件

- **首选 Sharding-JDBC**:性能高、Java 友好、社区活跃
- **跨语言选 Sharding-Proxy / MyCat**
- **NewSQL 兜底**:TiDB / OceanBase

### 15.6 全局 ID 选择

- 小规模 → Redis INCR
- 大多数 → **雪花算法** (Twitter / 美团 Leaf)
- 强一致需求 → 数据库号段

### 15.7 分布式事务选择

- 性能优先 → **RocketMQ 事务消息 / 本地消息表**(最终一致)
- 业务复杂 → **Seata AT**(自动补偿)
- 资金类 → **TCC**(强一致 + 高性能)

### 15.8 迁移与扩容

1. 全量 + 增量双写过渡
2. 校验一致性后再切
3. 保留老库可写 30 分钟,便于回滚
4. 成倍扩容比一致性 Hash 简单

### 15.9 心法口诀

```text
先垂直,后水平
键选准,片均匀
冗余宽表代 JOIN
最终一致替强分
先双写,后切换
成倍扩,留余量
监控全,压测勤
```

### 15.10 常见反模式

| 反模式                                  | 后果                              |
|-----------------------------------------|-----------------------------------|
| 用 status / create_time 当分片键       | 数据严重倾斜                      |
| 深分页 + 全分片扫描                     | OOM、响应超时                     |
| 跨库 JOIN 不限制                        | 慢 SQL 拖垮中间件                 |
| 中间件直接接管老库,无灰度切流          | 出问题无法回滚                    |
| 主键用 UUID                             | B+Tree 页分裂,写入性能差          |
| 不做数据校验就切流                      | 数据不一致,排查成本极高          |
