# MySQL 索引

## 一、索引的本质与作用

### 1. 什么是索引

**索引 (Index)** 是数据库中一种**专门的数据结构**,用于**加速数据的查找与检索**。它的核心思想与书籍的目录一致:先在目录中定位章节,再翻到对应页码,而不是一页一页地翻。

在 MySQL 中,索引是在**存储引擎层**实现的(不是 Server 层),所以不同引擎( InnoDB、MyISAM、Memory )支持的索引类型和能力各不相同。

### 2. 索引的本质

- 索引是**表的一个或多个列**上的**有序数据结构**
- 这个数据结构本身**也占用磁盘/内存**
- 维护索引会**带来写入开销**(插入、更新、删除时要同步更新索引)
- 索引是**用空间换时间**的典型方案

```text
                    不带索引                          带索引
            ┌──────────────────┐             ┌──────────────────────┐
            │ 全表扫描 (Scan)  │             │ 索引定位 + 回表       │
            │ 时间: O(n)       │             │ 时间: O(log n) + IO  │
            │ 每次 IO 一页      │             │ B+Tree 高度决定 IO   │
            └──────────────────┘             └──────────────────────┘
```

### 3. 索引的两大核心作用

#### (1) 减少磁盘 IO

数据库的数据存储在磁盘上,**IO 次数直接决定查询性能**。一个 100 万行的表,如果全表扫描,即使每页 16KB,也要扫描上万页,代价巨大。

而 B+Tree 索引(3~4 层)即使表上亿行,也只需要 **3~4 次磁盘 IO** 就能定位到数据位置——这就是"千万级表毫秒级查询"的本质。

#### (2) 避免排序 (加速 ORDER BY / GROUP BY)

- 索引本身就是**有序**的(B+Tree 按 key 升序存储)
- 如果 ORDER BY / GROUP BY 的字段正好命中索引,MySQL 可以**直接按索引顺序读出**,无需额外排序(filesort)
- 反之,若不命中索引,MySQL 需要把结果集加载到内存,在**内存里排序**,代价随数据量线性增长

```sql
-- 假设 idx_age 是 B+Tree 索引
EXPLAIN SELECT * FROM user ORDER BY age;     -- Using filesort (无索引)
ALTER TABLE user ADD INDEX idx_age (age);
EXPLAIN SELECT * FROM user ORDER BY age;     -- 无 filesort,直接走索引顺序
```

### 4. 索引的代价

| 操作 | 影响 |
|------|------|
| INSERT | 需插入索引页(可能页分裂) |
| UPDATE | 若修改索引列,需更新索引 |
| DELETE | 需标记删除,可能产生碎片 |
| SELECT | 维护成本低,只读不写 |
| 磁盘空间 | 索引本身要占空间(可能比数据还大) |
| 优化器选择 | 索引多了反而让优化器难选 |

> **关键原则**:索引不是越多越好,而是**该有的有,没用的别建**。

### 5. 索引使用场景

```sql
-- 适合建索引
SELECT * FROM user WHERE id = 100;                      -- 主键/唯一键
SELECT * FROM order WHERE user_id = 100 AND status = 1;  -- 高频条件列
SELECT * FROM log ORDER BY create_time DESC LIMIT 20;    -- 排序字段
SELECT user_id FROM order GROUP BY user_id;              -- 分组字段

-- 不适合建索引
SELECT * FROM user WHERE YEAR(create_time) = 2025;       -- 函数破坏索引
SELECT * FROM user WHERE name LIKE '%三%';               -- 前导模糊
SELECT COUNT(*) FROM user;                               -- 聚合统计
```

## 二、索引分类总览

MySQL 索引可以从多个维度分类,常见的分类方式如下。

### 1. 按数据结构分类

| 类型 | 支持引擎 | 特点 |
|------|----------|------|
| **B+Tree** | InnoDB、MyISAM、Memory(默认) | 范围查询、排序、点查全能,默认推荐 |
| **HASH** | Memory、NDB | 仅等值查询极快,无序、范围查询慢 |
| **FULLTEXT** | InnoDB(5.6+)、MyISAM | 全文检索,倒排索引 |
| **SPATIAL** | InnoDB(5.7+)、MyISAM | 空间数据(R 树),GIS 用 |
| **R-Tree** | MyISAM | 二维空间索引 |

> **MySQL 5.7 及以上 InnoDB 默认就是 B+Tree**,本节重点讨论 B+Tree。

### 2. 按物理存储分类

| 类型 | 含义 | 实现 |
|------|------|------|
| **聚簇索引 (Clustered)** | 索引与数据行**物理上一起存储** | InnoDB 主键索引 |
| **非聚簇索引 (Non-clustered)** | 索引与数据**分开存储**,叶子节点存**主键/指针** | InnoDB 二级索引、MyISAM 全部索引 |

### 3. 按字段特性分类

| 类型 | 特点 | 数量 |
|------|------|------|
| **主键索引 (PRIMARY KEY)** | 唯一且非空,InnoDB 即聚簇索引 | 一张表只能有 1 个 |
| **唯一索引 (UNIQUE)** | 值唯一,允许 NULL(多个) | 一张表可有多个 |
| **普通索引 (INDEX / KEY)** | 无约束,仅加速查询 | 可有多个 |
| **复合索引 (Composite)** | 多列组合,遵循最左前缀 | 可有多个 |
| **前缀索引 (Prefix)** | 只索引字符串前 N 个字符 | 用于长字符串 |

### 4. 按列数分类

- **单列索引**:针对单个列
- **复合索引(联合索引)**:多个列组合,如 `INDEX idx_a_b (a, b)`

### 5. 一图概览

```text

                                │   MySQL 索引   │
                                └──────┬───────┘
                                       │
        ┌──────────────┬───────────────┼───────────────┬──────────────┐
        │              │               │               │              │
   ┌────▼────┐    ┌────▼────┐    ┌─────▼────┐    ┌─────▼────┐   ┌─────▼────┐
   │ 数据结构 │    │  物理存储 │    │ 字段特性 │    │  列数    │   │  其他    │
   └────┬────┘    └────┬────┘    └─────┬────┘    └─────┬────┘   └─────┬────┘
        │              │               │               │              │
  ┌─────┴─────┐  ┌────┴─────┐    ┌────┴────┐    ┌─────┴─────┐   ┌────┴─────┐
  │ B+Tree    │  │ 聚簇     │    │ 主键    │    │ 单列      │   │ 前缀     │
```

## 三、B+Tree 数据结构详解

### 1. 为什么是 B+Tree

数据库索引要解决的核心矛盾是:**磁盘 IO 次数**。

- **二叉树 / 红黑树**:树太高(深度 = log₂N),100 万节点约 20 层,**每次磁盘读一页代价巨大**
- **B-Tree**:每个节点都存数据,空间利用率低,范围查询要回溯
- **B+Tree**:**非叶子节点只存 key,叶子节点存数据 + 链表相连**,完美匹配磁盘预读和范围扫描

### 2. B+Tree 核心特征

1. **多路平衡查找树**,每个节点有 m 个 key、m+1 个子节点
2. **非叶子节点只存索引键 (key) + 指针**,不存实际数据
3. **所有数据都存在叶子节点**,且**叶子节点按 key 升序链表相连**
4. **叶子节点之间是双向链表**(MySQL 实现),便于范围扫描
5. 树高度极低:**3~4 层即可支持千万~亿级数据**

### 3. B+Tree 结构图(ASCII)

```text
                                  B+Tree (高度 = 3)
                          假设每个节点可存 3 个 key
                   
                                    [ 50 | 100 ]                  ← 根 (非叶子)
                                   /     |      \
                                 /       |       \
                                /        |        \
                               /         |         \
                  [ 10 | 30 ]           [ 70 | 90 ]              ← 非叶子
                  /   |    \            /    |    \
                 /    |     \          /     |     \
                /     |      \        /      |      \
         (叶子链表,有序,双向连接)

    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ 5  10 20 │⇄  │ 25 30 40 │⇄  │ 50 60 70 │⇄  │ 80 90 100│  ← 叶子节点
    │ R1 R2 R3 │    │ R4 R5 R6 │    │ R7 R8 R9 │    │ R10 R11 │    (存实际数据)
    └──────────┘    └──────────┘    └──────────┘    └──────────┘

    ★ 叶子节点之间通过双向链表连接,范围扫描只需顺着链表读
    ★ 每个叶子节点内部 key 也是有序的(便于二分查找)
```

### 4. B+Tree vs B-Tree vs 二叉树 vs 红黑树

| 维度 | 二叉树 | 红黑树 | B-Tree | **B+Tree** |
|------|--------|--------|--------|-----------|
| 树高(100万数据) | ~20 | ~20 | ~4 | **~3** |
| 数据存储 | 各节点 | 各节点 | 各节点 | **仅叶子** |
| 范围查询 | 中序遍历 | 中序遍历 | 需回溯 | **链表直接遍历** |
| 磁盘 IO | 多 | 多 | 中 | **少** |
| 等值查询 | 慢 | 慢 | 中 | **快** |
| 排序支持 | 需额外排 | 需额外排 | 部分 | **天然有序** |
| 空间利用率 | 低 | 低 | 中 | **高** |

```text
B-Tree (数据分散在所有节点)                B+Tree (数据只在叶子节点)

        [ 50 | 100 ]                              [ 50 | 100 ]
       /     |      \                            /     |      \
      /      |       \                          /      |       \
 [10|30 + 数据] [70|90 + 数据]              [10|30 *]  [70|90 *]
   /  |  \       /  |  \                     / | \      / | \
 [5] [15] [25] [55] [75] [95]           [5*][15*][25*][55*][75*][95*]   ← *
                                      * 表示叶子节点存数据
                                      非叶子节点只存 key

★ B-Tree 范围查询:查完 5 后要回溯到父节点,再找右子树
★ B+Tree 范围查询:查完 5 后顺着叶子链表向后读 10,15,...
```

### 5. 一次查询的 IO 流程

```text
查询:SELECT * FROM user WHERE id = 89

Step 1 (根节点):  读磁盘 → [ 50 | 100 ] → 89 > 50 且 89 < 100 → 走中间指针
Step 2 (中间节点): 读磁盘 → [ 70 | 90 ]  → 89 < 90 → 走最右指针
Step 3 (叶子节点): 读磁盘 → [ 80 | 89 | 100 ] → 命中 89 → 取数据

总计: 3 次磁盘 IO  (树高 = 3)
```

### 6. MySQL B+Tree 的实际参数

InnoDB 中 B+Tree 的参数与磁盘页大小直接相关:

- **页大小**:`innodb_page_size`,默认 **16 KB**
- **非叶子节点 key + 指针约 14B(key=8B + 指针=6B → bigint 主键)**
- **每个非叶子节点可存** ≈ 16KB / 14B ≈ **1170 个 key**
- **叶子节点除 key 外,还存数据行(聚簇索引存整行,二级索引存主键)**
- **假设一行 1KB,叶子节点可存 16 行**
- **总行数 ≈ 1170 × 1170 × 16 ≈ 2190 万**(3 层)

```text
树高 vs 数据量(InnoDB B+Tree, 默认 16KB 页, bigint 主键)

       树高 2  ≈           约 2 万行
       树高 3  ≈        约 2 千万行
       树高 4  ≈     约 200 亿行(理论上限)
       实际生产树高通常 = 3
```

> **核心推论**:只要 B+Tree 高度 ≤ 4,即使表数据 200 亿,一次查询也只需 3~4 次 IO。这就是 MySQL 单表能撑亿级数据的根本原因。

## 四、InnoDB 索引实现

### 1. InnoDB 索引的两大类

- **聚簇索引 (Clustered Index)**:每张表**只有一个**,叶子节点**存整行数据**
- **二级索引 (Secondary Index)**:叶子节点**存主键值**(不是指针)

### 2. 聚簇索引

#### (1) 聚簇索引的生成规则

按以下顺序**自动选择**(用户无感):

1. **主键 PRIMARY KEY** → 主键就是聚簇索引
2. 无主键 → 第一个 **NOT NULL + UNIQUE** 索引
3. 都没有 → InnoDB **自动生成 6 字节的 row_id** 作为隐藏聚簇键

#### (2) 聚簇索引的特点

- **数据行物理上按聚簇键顺序存储**(插入顺序无关,最终物理有序)
- **聚簇索引 = 数据 = 表本身**(叶子节点就是数据页)
- **二级索引的叶子节点存的不是行指针,而是主键值**

```text
InnoDB 聚簇索引 (主键 id) 结构

                    [ 50 | 100 ]
                   /     |      \
                  /      |       \
                 /       |        \
          [10|30]     [70|90]       ← 非叶子:只存主键
            /|\         /|\
           / | \       / | \
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ 5,10,20  │  │50,60,70  │  │80,90,100 │  ← 叶子节点(数据页)
     │ 整行数据  │  │ 整行数据 │  │ 整行数据  │    存完整的行
     └──────────┘  └──────────┘  └──────────┘
```

### 3. 二级索引(辅助索引)

```text
InnoDB 二级索引 (idx_name) 结构

                    [ B | M ]                              ← 非叶子
                   /   |    \
                  /    |     \
                 /     |      \
          [A|B]  [D|J]  [P|T]                               ← 非叶子
           /|\    /|\    /|\
          / | \  / | \  / | \
     ┌───────┐ ┌───────┐ ┌───────┐
     │ Alice │ │ Bob   │ │ Peter │  ← 叶子节点
     │ id=5  │ │ id=10 │ │ id=80 │    只存: 索引列 + 主键
     │ id=15 │ │ id=20 │ │ id=85 │
     │ ...   │ │ ...   │ │ ...   │
     └───────┘ └───────┘ └───────┘

★ 二级索引叶子节点 = 索引列值 + 对应行的主键值
★ 通过二级索引查询,先拿到主键,再回聚簇索引找整行
```

### 4. 回表查询(Bookmark Lookup)

**回表**:通过二级索引拿到主键后,**再回到聚簇索引查整行**的过程。

```sql
CREATE TABLE user (
    id   INT PRIMARY KEY,          -- 聚簇索引
    name VARCHAR(64),
    age  INT,
    INDEX idx_name (name)          -- 二级索引
);

SELECT * FROM user WHERE name = '张三';   -- ★ 触发回表
```

```text
回表流程 (3~4 次 IO):

Step 1: 在 idx_name B+Tree 上找到 name='张三' → 得到 id=100
Step 2: 用 id=100 去聚簇索引查找整行
Step 3: 取出所有列(name、age、...)
       = 共 2 棵 B+Tree 各一次遍历

★ 优化方向:
  1. 尽量 SELECT 需要的列,而非 SELECT * (减少回表)
  2. 用覆盖索引避免回表 (详见第十节)
```

### 5. 自适应 Hash 索引 (AHI)

InnoDB 还会在**内存**自动为**频繁访问的索引页**建立 **Hash 索引**,等值查询极快:

```sql
SHOW ENGINE INNODB STATUS \G     -- 查看 AHI 使用情况
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';   -- 默认 ON
```

- **AHI 是自动的、内存级**,重启失效
- 适合**等值查询 (`=`、`IN`)**,**不适合范围查询**
- 高并发写场景可考虑关闭(锁竞争)

## 五、MyISAM 索引实现

### 1. MyISAM 的索引特点

- **所有索引都是非聚簇索引**
- 索引文件 `.MYI` 与数据文件 `.MYD` **完全分离**
- 叶子节点存的是**数据行的物理指针(磁盘地址)**,不是主键
- **主键索引和二级索引结构完全相同**

### 2. MyISAM 索引结构

```text
MyISAM 主键索引 (MYI 文件)              MyISAM 数据文件 (MYD)

            [ 50 | 100 ]                  ┌──────────┐
           /     |      \                 │ Row 1    │ ← 地址 0x0001
          /      |       \                │ Row 2    │ ← 地址 0x0002
         /       |        \               │ Row 3    │ ← 地址 0x0003
   [10|30]  [70|90]                       │ ...      │
    /|\      /|\                           │ Row N    │ ← 地址 0xFFFF
   / | \    / | \                          └──────────┘
  /  |  \  /  |  \                              ▲
 [5] [15] [55] [75] [95]                        │
  |   |    |    |    |                          │
  ↓   ↓    ↓    ↓    ↓                          │
 0x01 0x02 0x03 0x04 0x05 ...   ← 物理地址      │
  ↓   ↓    ↓    ↓    ↓                          │
  └────┴────┴────┴────┴──────────── 直接定位到数据文件

★ 二级索引结构和主键索引结构一模一样,叶子节点也是磁盘地址
```

### 3. InnoDB vs MyISAM 索引对比

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 聚簇/非聚簇 | 聚簇(主键)+ 非聚簇(其他) | 全部非聚簇 |
| 叶子节点内容 | 主键索引存整行,其他存主键 | 存**磁盘地址** |
| 回表 | 二级索引要回表(根据主键) | 直接定位磁盘 |
| 主键要求 | 必须显式定义(推荐) | 可不显式 |
| 行锁 | 支持 | 只支持表锁 |
| 事务 | 支持 | 不支持 |
| 适用 | 默认、OLTP | 读多写少、归档 |

### 4. 实战建议

```sql
-- 现代 MySQL 默认引擎是 InnoDB
SHOW VARIABLES LIKE 'default_storage_engine';

-- MyISAM 适合:只读日志表、临时统计表、文本搜索归档
-- InnoDB 适合:99% 的业务场景
```

## 六、Hash 索引

### 1. Hash 索引原理

- 用**哈希函数**把 key 映射到桶(bucket),等值查询**理论 O(1)**
- 哈希表是**无序**的,不支持范围查询、不支持排序

```text
Hash 索引原理示意

    key:         哈希函数        bucket:
    "Alice"  ──────────────→    3  → 指向 id=10
    "Bob"    ──────────────→    5  → 指向 id=20
    "Peter"  ──────────────→    7  → 指向 id=80
    "张三"   ──────────────→    1  → 指向 id=100

★ O(1) 定位
× 不支持: 范围、排序、最左前缀
```

### 2. Memory 引擎的 Hash 索引

```sql
CREATE TABLE t_hash (
    id   INT,
    name VARCHAR(64),
    INDEX USING HASH (name)        -- Memory 引擎可指定 HASH 索引
) ENGINE=MEMORY;
```

| 引擎 | 支持的索引 | 默认 |
|------|-----------|------|
| Memory | HASH、B+Tree | HASH |
| InnoDB | B+Tree(+ AHI 内部) | B+Tree |
| MyISAM | B+Tree | B+Tree |
| NDB    | HASH、B+Tree | HASH |

### 3. 自适应 Hash 索引 (InnoDB AHI)

InnoDB 会在内存中**自动**为热数据页建立 Hash 索引,**用户不可控**:

```sql
-- 查看 AHI
SHOW ENGINE INNODB STATUS \G

-- 关键字段:
INSERT BUFFER AND ADAPTIVE HASH INDEX
Ibuf: size 1, free list len 0, seg size 2, 0 merges
Hash table size 4425293, node heap has 1223 buffer(s)
0.00 hash searches/s, 0.00 non-hash searches/s
```

### 4. Hash 索引的优缺点

| 优点 | 缺点 |
|------|------|
| 等值查询极快 (O(1)) | **不支持范围查询** |
| 内存级 Hash 不占磁盘 | **不支持排序** |
| | **不支持最左前缀** |
| | **哈希冲突**需要拉链法 |
| | **不支持部分索引列查询** |

### 5. 模拟 Hash 索引(应用层技巧)

```sql
-- 场景:URL 太长,索引占空间
-- 解决:新增 url_crc 列存哈希值,建索引,查询时带 CRC
ALTER TABLE url_table ADD url_crc BIGINT;
ALTER TABLE url_table ADD INDEX idx_crc (url_crc);

SELECT * FROM url_table
WHERE url_crc = CRC32('https://example.com/long-url')  -- CRC 是 MySQL 内置
  AND url = 'https://example.com/long-url';
```

## 七、全文索引 (FULLTEXT)

### 1. 全文索引适用场景

- `LIKE '%xxx%'` 前导模糊导致**全表扫描**
- 全文索引用**倒排索引**,能极快匹配关键词
- 适用:文章内容搜索、商品描述、日志分析

### 2. 倒排索引原理

```text
普通索引(正排):
  文档1: "MySQL 索引 性能"
  文档2: "MySQL 事务"
  文档3: "Redis 缓存"

倒排索引:
  "MySQL"  → 文档1, 文档2
  "索引"   → 文档1
  "性能"   → 文档1
  "事务"   → 文档2
  "Redis"  → 文档3
  "缓存"   → 文档3

★ 查"MySQL 事务" → 求交集 = {文档2}
```

### 3. 全文索引使用

```sql
-- 建表时建全文索引
CREATE TABLE article (
    id      INT PRIMARY KEY AUTO_INCREMENT,
    title   VARCHAR(255),
    content TEXT,
    FULLTEXT INDEX ft_title_content (title, content) WITH PARSER ngram
) ENGINE=InnoDB;

-- 或追加
ALTER TABLE article ADD FULLTEXT INDEX ft_title (title) WITH PARSER ngram;

-- 查询:自然语言模式 (默认)
SELECT * FROM article
WHERE MATCH(title, content) AGAINST('MySQL 索引' IN NATURAL LANGUAGE MODE);

-- 查询:布尔模式 (支持 + - *)
SELECT * FROM article
WHERE MATCH(title, content) AGAINST('+MySQL -Redis' IN BOOLEAN MODE);
```

### 4. NGRAM 解析器(中文友好)

MySQL 默认全文索引按**空格分词**,对中文不友好。**NGRAM** 按字符切分:

```sql
-- 创建 NGRAM 全文索引
ALTER TABLE article ADD FULLTEXT INDEX ft_content (content) WITH PARSER ngram;

-- 设置 ngram_token size
SET ngram_token_size = 2;     -- 默认 2,中文建议 2

-- 查询
SELECT * FROM article
WHERE MATCH(content) AGAINST('索引' IN BOOLEAN MODE);
```

### 5. 全文索引的限制

| 限制 | 说明 |
|------|------|
| 引擎 | InnoDB 5.6+、MyISAM(老) |
| 字段类型 | CHAR、VARCHAR、TEXT |
| 最小词长 | `innodb_ft_min_token_size` 默认 3 |
| 最大词长 | `innodb_ft_max_token_size` 默认 84 |
| 中文 | 需用 NGRAM |
| 性能 | 大数据量时不如 Elasticsearch |

## 八、索引的创建与删除

### 1. 创建索引

#### (1) 建表时创建

```sql
CREATE TABLE user (
    id        INT PRIMARY KEY AUTO_INCREMENT,
    name      VARCHAR(64) NOT NULL,
    email     VARCHAR(128),
    age       INT,
    create_dt DATETIME,

    -- 主键索引(自动聚簇)
    PRIMARY KEY (id),

    -- 唯一索引
    UNIQUE KEY uk_email (email),

    -- 普通索引
    KEY idx_name (name),

    -- 复合索引
    KEY idx_age_name (age, name),

    -- 前缀索引(只对字符串)
    KEY idx_name_prefix (name(10)),

    -- 全文索引
    FULLTEXT KEY ft_name (name) WITH PARSER ngram
) ENGINE=InnoDB;
```

#### (2) 表已存在时创建

```sql
-- 方式 1:CREATE INDEX
CREATE INDEX idx_name ON user(name);
CREATE UNIQUE INDEX uk_email ON user(email);
CREATE INDEX idx_age_name ON user(age, name);

-- 方式 2:ALTER TABLE
ALTER TABLE user ADD INDEX idx_name (name);
ALTER TABLE user ADD UNIQUE INDEX uk_email (email);
ALTER TABLE user ADD FULLTEXT INDEX ft_name (name) WITH PARSER ngram;

-- 前缀索引
CREATE INDEX idx_email_prefix ON user(email(20));
```

#### (3) 在线创建索引 (Online DDL)

```sql
-- MySQL 5.6+ 支持 Online DDL,不锁表(读写仍可)
ALTER TABLE user ADD INDEX idx_name (name), ALGORITHM=INPLACE, LOCK=NONE;

-- ALGORITHM 选项:
--   INPLACE: 原地修改,可能读不阻塞,写可能阻塞
--   COPY:    拷表,锁表
--   DEFAULT: 自动选择

-- LOCK 选项:
--   NONE:  读写都不阻塞(最优)
--   SHARED: 读不阻塞,写阻塞
--   EXCLUSIVE: 读写都阻塞
```

### 2. 删除索引

```sql
-- 方式 1:DROP INDEX (保留主键)
DROP INDEX idx_name ON user;
DROP INDEX uk_email ON user;

-- 方式 2:ALTER TABLE DROP
ALTER TABLE user DROP INDEX idx_name;
ALTER TABLE user DROP PRIMARY KEY;   -- 删除主键(特殊)

-- 注意:无法直接删除主键索引,如果要改主键:
ALTER TABLE user DROP PRIMARY KEY, ADD PRIMARY KEY (new_col);
```

### 3. 重建索引

```sql
-- 索引长期使用后可能碎片化,可重建
ALTER TABLE user ENGINE=InnoDB;          -- 重建表与所有索引
-- 或
OPTIMIZE TABLE user;                       -- 推荐
-- 或
ALTER TABLE user DROP INDEX idx_name, ADD INDEX idx_name (name);
```

## 十、覆盖索引与回表查询

### 1. 什么是覆盖索引

**覆盖索引 (Covering Index)**:查询所需的所有列**都能从索引树中拿到**,**无需回表**。

```text
普通索引覆盖索引的差异:

                            普通二级索引       覆盖索引
SELECT name, age           name, age 都在索引   name, age 都在索引
SELECT 主键                 主键在二级索引       主键在二级索引
SELECT 其他列               ★ 触发回表           ★ 无需回表
```

### 2. 覆盖索引示例

```sql
CREATE TABLE user (
    id   INT PRIMARY KEY,
    name VARCHAR(64),
    age  INT,
    city VARCHAR(64),
    INDEX idx_name_age (name, age)
);

-- ★ 覆盖索引:查询列都在 idx_name_age 中
EXPLAIN SELECT id, name, age FROM user WHERE name = '张三';
-- Extra: Using index   ← 命中!

-- ★ 触发回表:city 不在索引中
EXPLAIN SELECT id, name, age, city FROM user WHERE name = '张三';
-- Extra: Using where; Using index  ← 用到索引但要回表
```

### 3. EXPLAIN Extra 关键标志

| Extra | 含义 |
|-------|------|
| **Using index** | 覆盖索引,无需回表(最优) |
| Using where | 用 WHERE 过滤 |
| Using index condition | ICP 索引下推 |
| Using temporary | 用临时表(常见于 GROUP BY) |
| Using filesort | 文件排序(需优化) |
| Using join buffer | 用连接缓冲 |
| Impossible WHERE | WHERE 永远为 FALSE |

### 4. 实战:为回表优化建索引

```sql
-- 业务:SELECT id, name FROM user WHERE age = 20;
-- 现状:只有 idx_age → 触发回表拿 name

ALTER TABLE user ADD INDEX idx_age_name (age, name);

EXPLAIN SELECT id, name FROM user WHERE age = 20;
-- key: idx_age_name
-- Extra: Using index   ★ 不再回表
```

### 5. 总结对比

| 查询 | 索引 | 回表? |
|------|------|-------|
| `SELECT id FROM user WHERE name = 'x'` | idx_name | 否(id 在二级索引叶子) |
| `SELECT name FROM user WHERE name = 'x'` | idx_name | 否 |
| `SELECT * FROM user WHERE name = 'x'` | idx_name | **是**(取所有列) |
| `SELECT id, name FROM user WHERE name = 'x'` | idx_name(name, id) | 否(覆盖索引) |

## 十一、最左前缀原则

### 1. 概念

**最左前缀 (Leftmost Prefix)**:复合索引 `(a, b, c)` 相当于建了三个索引:

- `(a)`
- `(a, b)`
- `(a, b, c)`

但**不**包含 `(b)`、`(c)`、`(b, c)`。

```text
复合索引 (a, b, c) 的存储顺序(按 a, b, c 升序):

(a=1, b=1, c=1) → (a=1, b=1, c=5) → (a=1, b=2, c=3) →
(a=1, b=3, c=9) → (a=2, b=1, c=7) → (a=2, b=4, c=2) → ...

★ 先按 a 排序,a 相同再看 b,b 相同再看 c
★ 跳过 a 直接用 b,c → 无法定位 → 全索引扫描或全表扫描
```

### 2. 命中规则(详细)

| WHERE 条件 | 能否命中索引 | 命中的索引列 |
|-----------|------------|-------------|
| `WHERE a = 1` | ✅ | a |
| `WHERE a = 1 AND b = 2` | ✅ | a, b |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ | a, b, c |
| `WHERE a = 1 AND c = 3` | ✅ (a 部分),c 无效 | a |
| `WHERE b = 2` | ❌ | 无 |
| `WHERE c = 3` | ❌ | 无 |
| `WHERE a = 1 OR b = 2` | ❌ | 无(OR 拆成两部分) |
| `ORDER BY a` | ✅ | a |
| `ORDER BY a, b` | ✅ | a, b |
| `ORDER BY b` | ❌ | 无 |

### 3. EXPLAIN 示例

```sql
CREATE TABLE t (
    a INT, b INT, c INT, d INT,
    INDEX idx_a_b_c (a, b, c)
);

-- 案例 1:命中 a,b
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;
-- key_len = (a + b) = 4 + 4 = 8(假设都是 INT)

-- 案例 2:只命中 a
EXPLAIN SELECT * FROM t WHERE a = 1 AND c = 3;
-- key_len = 4 (只有 a)

-- 案例 3:完全不命中
EXPLAIN SELECT * FROM t WHERE b = 2;
-- key: NULL,type: ALL (全表扫描)
```

### 4. key_len 计算规则

`key_len` 反映索引实际使用的字节数:

| 列类型 | key_len(非空) | key_len(可空,多 1B) |
|--------|--------------|--------------------|
| TINYINT | 1 | 1 (NOT NULL 不多) |
| INT | 4 | 5 |
| BIGINT | 8 | 9 |
| VARCHAR(N) utf8mb4 | 4N+2 | 4N+3 |
| VARCHAR(N) utf8 | 3N+2 | 3N+3 |
| DATETIME | 8 | 8 (NOT NULL) |

```text
示例:
INDEX idx_a_b (a INT, b VARCHAR(10))
- 索引完整长度 = 4 + (10*3+2) = 36 (utf8)

WHERE a = 1 → key_len = 4 (只用 a)
WHERE a = 1 AND b = 'x' → key_len = 36 (用 a 和 b)
```

### 5. 实战:索引顺序设计

```sql
-- 场景:WHERE a = ? AND b = ?,  ORDER BY c
-- 建议:INDEX (a, b, c)  -- WHERE 命中 a,b, ORDER BY 用 c

-- 场景:高频 a = ? 等值,偶尔 ORDER BY c
-- 建议:INDEX (a)  +  INDEX (c)  -- 拆成两个单列索引

-- 场景:WHERE a = ? AND b > ?  -- 范围
-- 建议:INDEX (a, b)  -- a 等值,b 范围
--     × 不建议 (a, b, c),因为 c 不会用到

-- ★ 高频列在前,范围列放最后,选择性高的列在前
```

## 十二、索引下推 (ICP, Index Condition Pushdown)

### 1. 什么是 ICP

**索引下推 (Index Condition Pushdown, MySQL 5.6+)**:在**存储引擎层**利用**索引**直接过滤**不属于索引的列**,减少**回表次数**。

### 2. ICP 之前的问题(回表再过滤)

```text
关闭 ICP 时:SELECT * FROM user WHERE name = '张' AND age = 20

索引 idx_name 只包含 name

Step 1: 在 idx_name 中找出所有 name LIKE '张%' 的记录 → 假设 100 条
Step 2: 每条都回表(共 100 次回表),Server 层再过滤 age = 20 → 假设剩 10 条
Step 3: 返回 10 条给客户端

★ 浪费:90 次回表都白做了
```

### 3. ICP 之后的优化

```text
开启 ICP 后:

Step 1: 在 idx_name 中找出所有 name LIKE '张%' 的记录
Step 2: 在存储引擎层**直接用 age = 20 过滤**(因为 age 在索引中或已读取)
Step 3: 只对**过滤后剩下的**(假设 10 条)回表

★ 减少 90 次回表
```

### 4. ICP 的关键:索引覆盖的列

```sql
CREATE TABLE user (
    id   INT PRIMARY KEY,
    name VARCHAR(64),
    age  INT,
    city VARCHAR(64),
    INDEX idx_name (name)            -- 只有 name
);

-- 此时 age 不在 idx_name 中,ICP 不会生效
EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 20;

-- 把 age 加入索引,ICP 才能生效
ALTER TABLE user ADD INDEX idx_name_age (name, age);

EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
-- Extra: Using index condition   ★ ICP 生效
```

### 5. EXPLAIN 对比 ICP

```sql
-- 案例 1:无 ICP(老版本或索引不包含过滤列)
EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
-- type: range, key: idx_name
-- Extra: Using where    ← Server 层过滤

-- 案例 2:有 ICP
EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
-- type: range, key: idx_name_age
-- Extra: Using index condition   ← ICP 生效
```

### 6. ICP 控制开关

```sql
-- 默认 ON
SET optimizer_switch = 'index_condition_pushdown=on';
SET optimizer_switch = 'index_condition_pushdown=off';   -- 关闭

-- 查看当前状态
SHOW VARIABLES LIKE 'optimizer_switch';
```

### 7. ICP 适用条件

- 只能用于**二级索引**(聚簇索引没必要)
- 只能下推**非索引条件的列**(索引内的列已经在索引树过滤过了)
- 主要适用于 **InnoDB 和 MyISAM**

## 十三、MRR (Multi-Range Read)

### 1. 什么是 MRR

**MRR (Multi-Range Read, MySQL 5.6+)**:将**随机 IO 转换为顺序 IO** 的优化。

### 2. 传统回表的 IO 问题

```text
无 MRR:SELECT * FROM user WHERE age BETWEEN 20 AND 30

假设 idx_age 命中 1000 条记录,每条都要回表
传统:按 idx_age 顺序回表 → 主键是 5, 1000, 30, 800, 60, ...
      → 随机 IO(磁盘到处跳)

★ 磁头来回寻道,慢!
```

### 3. MRR 的优化

```text
有 MRR:

Step 1: 在 idx_age 中找出所有 id = (5, 30, 60, 800, 1000)
Step 2: **排序** id → (5, 30, 60, 800, 1000)
Step 3: 按排序后的顺序回表 → 5, 30, 60, 800, 1000
        → 接近顺序 IO

★ 大幅减少磁头寻道,SSD 也受益(合并多个 IO 请求)
```

### 4. EXPLAIN 对比

```sql
-- 关闭 MRR
SET optimizer_switch = 'mrr=off';

EXPLAIN SELECT * FROM user WHERE age BETWEEN 20 AND 30;
-- Extra: Using where

-- 开启 MRR
SET optimizer_switch = 'mrr=on,mrr_cost_based=on';

EXPLAIN SELECT * FROM user WHERE age BETWEEN 20 AND 30;
-- Extra: Using MRR   ← 命中
```

### 5. MRR 与 ICP、BKA 配合

```text
完整查询优化链路:

SQL → ICP 在引擎层过滤 → MRR 排序主键 → 顺序回表 → BKA 嵌套循环 join
                                                          ↑
                                                  MySQL 8.0 默认开启
```

## 十四、索引设计的最佳实践

### 1. 黄金原则

```text
1. 不是越多越好:每个索引都增加写入开销
2. 选择性高优先:重复值少的列建索引收益大
3. 高频查询优先:用得多的列才值得建
4. 复合优于多单列:(a,b,c) 一个比 (a) (b) (c) 三个高效
5. 前缀长度合理:长字符串用前缀索引
6. 范围列放最后:等值列在前,范围列在后
7. 避免冗余索引:(a) 和 (a, b) 同时存在 → 删 (a)
```

### 2. 索引选择性的估算

**选择性 = 不同值数量 / 总行数**,越大越好(理想是 1,主键完美)。

```sql
SELECT
    COUNT(DISTINCT column_name) / COUNT(*) AS selectivity
FROM table_name;
```

| 列 | 选择性 | 是否建议索引 |
|----|--------|-------------|
| 用户 ID | 1.0 | 必须 |
| 性别(男/女) | 0.0001 | 不建议 |
| 手机号 | 1.0 | 强烈建议 |
| 状态(0/1/2/3) | 0.0003 | 一般 |
| 订单号 | 1.0 | 强烈建议 |

### 3. 前缀索引的长度选择

```sql
-- 目标:选择性接近整列,索引体积尽量小
SELECT
    COUNT(DISTINCT LEFT(email, 5)) / COUNT(*)  AS s5,
    COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS s10,
    COUNT(DISTINCT LEFT(email, 15)) / COUNT(*) AS s15,
    COUNT(DISTINCT email) / COUNT(*)          AS sfull
FROM user;

-- 找到选择性趋近整列时的最小长度 L
ALTER TABLE user ADD INDEX idx_email_prefix (email(L));
```

### 4. 常见索引设计模式

#### (1) 主键建议

```sql
-- ★ 自增 INT / BIGINT 是首选
CREATE TABLE t (id BIGINT PRIMARY KEY AUTO_INCREMENT, ...);

-- 不建议:
-- 1) UUID(无序,频繁页分裂)
-- 2) 长字符串(索引大)
-- 3) 业务字段(难维护)
```

#### (2) 联合索引

```sql
-- 业务:WHERE a = ? AND b = ?, ORDER BY c
ALTER TABLE order ADD INDEX idx_a_b_c (a, b, c);

-- 业务:WHERE a IN (?) AND b = ?    → a 在前
ALTER TABLE log ADD INDEX idx_a_b (a, b);
```

#### (3) 覆盖索引

```sql
-- 业务:SELECT name FROM user WHERE age = ?
ALTER TABLE user ADD INDEX idx_age_name (age, name);
-- ↑ 覆盖 name,避免回表
```

#### (4) 前缀索引

```sql
-- 业务:WHERE url = ?
ALTER TABLE log ADD INDEX idx_url (url(64));
```

### 5. 索引失效的预防

```sql
-- 1. 不在索引列上用函数
WHERE DATE(create_dt) = '2025-01-01'      -- ✗
WHERE create_dt >= '2025-01-01' AND create_dt < '2025-01-02'  -- ✓

-- 2. 不做类型转换
WHERE phone = 13800138000       -- ✗ (phone 是 VARCHAR)
WHERE phone = '13800138000'     -- ✓

-- 3. 不做前导模糊
WHERE name LIKE '%张%'           -- ✗
WHERE name LIKE '张%'            -- ✓

-- 4. 不做不等值或 OR 滥用
WHERE age > 20 OR name = 'x'    -- ✗
WHERE age > 20 UNION ALL ...    -- ✓
```

### 6. 索引维护建议

```sql
-- 定期分析表,更新统计信息
ANALYZE TABLE user;

-- 优化表,减少碎片
OPTIMIZE TABLE user;

-- 监控慢查询
SET long_query_time = 1;
SET slow_query_log = ON;

-- 开启 performance_schema / sys schema (MySQL 5.7+)
SELECT * FROM sys.statement_analysis;
SELECT * FROM sys.schema_tables_with_full_table_scans;
```

## 十五、索引失效的常见场景

下面列举**最常见的索引失效场景**,每条都附 SQL 与 EXPLAIN 对比。

### 1. 违反最左前缀

```sql
CREATE TABLE t (a INT, b INT, c INT, INDEX idx_a_b (a, b));

-- ★ 失效
EXPLAIN SELECT * FROM t WHERE b = 2;
-- type: ALL, key: NULL

-- ★ 命中
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;
-- type: ref, key: idx_a_b
```

### 2. 索引列上用函数或计算

```sql
CREATE TABLE user (id INT PRIMARY KEY, create_dt DATETIME, age INT);

-- ★ 失效
EXPLAIN SELECT * FROM user WHERE YEAR(create_dt) = 2025;
-- type: ALL

-- ★ 改写后命中
EXPLAIN SELECT * FROM user
WHERE create_dt >= '2025-01-01' AND create_dt < '2026-01-01';

-- ★ 失效
EXPLAIN SELECT * FROM user WHERE age + 1 = 30;

-- ★ 改写后命中
EXPLAIN SELECT * FROM user WHERE age = 29;
```

### 3. 隐式类型转换

```sql
CREATE TABLE user (id INT PRIMARY KEY, phone VARCHAR(20), INDEX idx_phone (phone));

-- ★ 失效
EXPLAIN SELECT * FROM user WHERE phone = 13800138000;
-- phone 是 VARCHAR,传 INT → 索引失效

-- ★ 命中
EXPLAIN SELECT * FROM user WHERE phone = '13800138000';
```

### 4. 隐式字符集转换(JOIN)

```sql
-- 表 A 用 utf8,表 B 用 utf8mb4 → JOIN 时可能触发转换
-- ★ 失效
SELECT * FROM a JOIN b ON a.name = b.name WHERE a.name = 'x';
-- 索引可能用不上

-- ★ 解决:统一字符集
ALTER TABLE a CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 5. 前导模糊查询

```sql
CREATE TABLE user (id INT, name VARCHAR(64), INDEX idx_name (name));

-- ★ 失效
EXPLAIN SELECT * FROM user WHERE name LIKE '%张%';
-- type: ALL

-- ★ 命中
EXPLAIN SELECT * FROM user WHERE name LIKE '张%';
-- type: range, key: idx_name
```

### 6. OR 滥用

```sql
CREATE TABLE user (id INT, name VARCHAR(64), age INT,
                   INDEX idx_name (name), INDEX idx_age (age));

-- ★ 部分失效
EXPLAIN SELECT * FROM user WHERE name = '张三' OR age = 20;
-- type: index_merge (有索引合并,但不一定好)
-- 更好:UNION ALL

-- ★ 重写
EXPLAIN
SELECT * FROM user WHERE name = '张三'
UNION ALL
SELECT * FROM user WHERE age = 20 AND name != '张三';
```

### 7. 不等号 `!=` / `<>`

```sql
-- ★ 通常失效(取决于数据分布)
EXPLAIN SELECT * FROM user WHERE name != '张三';
-- 优化器可能选择全表扫描,因为大多数行都满足

-- ★ 建议:用具体值或 NOT IN 子查询重写
```

### 8. IS NULL / IS NOT NULL

```sql
-- ★ 通常可以走索引
EXPLAIN SELECT * FROM user WHERE name IS NULL;

-- ★ 但 IS NOT NULL 在某些数据分布下可能失效
EXPLAIN SELECT * FROM user WHERE name IS NOT NULL;
```

### 9. 范围条件后失效

```sql
CREATE TABLE t (a INT, b INT, c INT, INDEX idx_a_b_c (a, b, c));

-- ★ b 是范围,c 完全失效
EXPLAIN SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 2;
-- key_len = a + b,c 不会用到

-- ★ 改写:把等值列放前面
EXPLAIN SELECT * FROM t WHERE a = 1 AND c = 2 AND b > 10;
-- 依然只用到 a + b(范围列必须在等值列之后)
-- 最好的方案是把 c 也建索引,或调整业务逻辑
```

### 10. ORDER BY / GROUP BY 方向不一致

```sql
CREATE TABLE t (a INT, b INT, INDEX idx_a_b (a, b));

-- ★ 失效
EXPLAIN SELECT * FROM t ORDER BY a ASC, b DESC;
-- 一个升序一个降序 → MySQL 无法用索引排序

-- ★ 解决 1:统一方向
EXPLAIN SELECT * FROM t ORDER BY a ASC, b ASC;

-- ★ 解决 2:加 DESC 索引(MySQL 8.0+)
ALTER TABLE t ADD INDEX idx_a_b_desc (a DESC, b DESC);
```

### 11. 数据量过少

```sql
-- 当表只有几十行时,优化器认为全表扫描比走索引更快
EXPLAIN SELECT * FROM small_table WHERE indexed_col = 'x';
-- type: ALL (即使有索引)
```

### 12. 统计信息过期

```sql
-- 大量写入后,Cardinality 估算不准,优化器可能错选
ANALYZE TABLE user;   -- 强制更新统计信息
```

### 13. 汇总:索引失效速查表

| 场景 | 失效 | 改写 |
|------|------|------|
| 违反最左前缀 | `WHERE b = ?` | `WHERE a = ? AND b = ?` |
| 索引列用函数 | `WHERE YEAR(dt) = 2025` | `WHERE dt BETWEEN ...` |
| 索引列计算 | `WHERE age + 1 = 30` | `WHERE age = 29` |
| 隐式类型转换 | `phone = 13800...` | `phone = '13800...'` |
| 前导模糊 | `LIKE '%x%'` | `LIKE 'x%'` 或全文索引 |
| OR 滥用 | `a = 1 OR b = 2` | UNION ALL 或单列索引合并 |
| 范围后列 | `a=1 AND b>10 AND c=2` | 调整顺序或拆索引 |
| 排序方向不一致 | `ORDER BY a, b DESC` | 统一方向或 DESC 索引 |
| NOT / != | `WHERE name != 'x'` | 重新设计查询 |
| 数据量少 | 几十行 | 正常,无需优化 |

## 十六、Cardinality 与索引选择性

### 1. 什么是 Cardinality

**Cardinality** = 索引中**不同值的数量**(估算值,不是精确值)。

```sql
SHOW INDEX FROM user;
-- 重点字段:Cardinality
```

| 场景 | Cardinality | 含义 |
|------|-------------|------|
| 性别(男/女) | 2 | 极低选择性 |
| 状态(0/1/2) | 3 | 低选择性 |
| 城市(几十个) | 几百 | 中等选择性 |
| 用户 ID | 100 万 | 完美选择性 |
| 手机号 | 100 万 | 完美选择性 |

### 2. Cardinality 怎么来

```sql
-- 1) 估算(默认,InnoDB 8 个随机页采样)
SHOW INDEX FROM user;
-- Cardinality 列就是采样估算值

-- 2) 强制更新
ANALYZE TABLE user;

-- 3) 采样参数
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';
-- 默认 20 页,越大越精确,但越慢

-- 4) 是否持久化
SHOW VARIABLES LIKE 'innodb_stats_persistent';
-- ON: 持久化(重启保留);OFF: 内存(重启丢失)
```

### 3. 选择性计算

```sql
-- 越接近 1,选择性越好,索引收益越大
SELECT
    COUNT(DISTINCT col) / COUNT(*) AS selectivity
FROM user;

-- 推荐规则:
-- 1) selectivity > 0.1 → 适合建索引
-- 2) selectivity < 0.01 → 索引可能不划算
```

### 4. Cardinality 与优化器

```sql
-- Cardinality 越大,优化器越倾向走索引
-- Cardinality 越小,优化器越倾向全表扫描

-- 案例:status 列只有 3 个值
-- 即使建了索引,WHERE status = 1 仍可能全表扫描
EXPLAIN SELECT * FROM order WHERE status = 1;
-- type: ALL  ← 优化器认为走索引更慢
```

### 5. 高效索引的标准

```text
高效索引:
1. Cardinality 高(不同值多)
2. 索引覆盖查询所需列(避免回表)
3. 索引长度小(占空间少,缓存命中率高)
4. 符合查询模式(WHERE / ORDER BY / JOIN)
5. 不是冗余索引

低效索引:
1. Cardinality 低(选择性差)
2. 重复建索引(如已有 (a,b) 又建 (a))
3. 索引列大量 NULL(可能不被索引)
4. 表数据极少(全表扫描更快)
```

## 十七、FORCE INDEX / IGNORE INDEX / USE INDEX

### 1. 三个 HINT 的作用

| HINT | 作用 | 优先级 |
|------|------|--------|
| **USE INDEX** | 建议优化器使用某索引(可忽略) | 低(建议) |
| **FORCE INDEX** | 强制使用某索引(无法拒绝) | **高(强制)** |
| **IGNORE INDEX** | 忽略某索引(不让用) | 强制排除 |

### 2. USE INDEX

```sql
-- 告诉优化器:优先考虑 idx_name
EXPLAIN SELECT * FROM user USE INDEX (idx_name) WHERE name = '张三' AND age = 20;
-- 优化器仍可选择不走 idx_name(例如发现 idx_age_name 更好)

-- 语法变体:USE INDEX FOR JOIN / ORDER BY / GROUP BY
EXPLAIN SELECT * FROM user USE INDEX FOR JOIN (idx_name)
WHERE name = '张三';
```

### 3. FORCE INDEX

```sql
-- 强制走 idx_name,即使优化器认为其他更优
EXPLAIN SELECT * FROM user FORCE INDEX (idx_name)
WHERE name = '张三' AND age = 20;

-- 案例:小数据量时,优化器选错索引
CREATE TABLE order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT,
    status TINYINT,
    INDEX idx_user (user_id),
    INDEX idx_status (status)
);

-- 优化器可能选 idx_status (因为 status 过滤后行少)
-- 但实际 user_id 选择性更高
EXPLAIN SELECT * FROM order
WHERE user_id = 100 AND status = 1;
-- 可能错误地选 idx_status

-- 强制走 idx_user
EXPLAIN SELECT * FROM order FORCE INDEX (idx_user)
WHERE user_id = 100 AND status = 1;
```

### 4. IGNORE INDEX

```sql
-- 不让优化器用 idx_age
EXPLAIN SELECT * FROM user IGNORE INDEX (idx_age)
WHERE name = '张三' AND age = 20;

-- 案例:某索引因历史原因存在,新查询不该用它
```

### 5. JOIN 中的 HINT

```sql
SELECT * FROM user u
FORCE INDEX (idx_user_id)              -- user 用 idx_user_id
JOIN order o
FORCE INDEX (idx_user_id)              -- order 用 idx_user_id
ON u.id = o.user_id;
```

### 6. 实战建议

```text
★ FORCE INDEX 慎用:
  - 优化器通常比人更准
  - 数据分布变化后,FORCE 可能反而更慢
  - 优先优化索引,而不是绕过优化器

★ USE INDEX 适用:
  - 优化器误判时(可选)
  - 调试优化器行为

★ IGNORE INDEX 适用:
  - 测试某索引是否真的有效
  - 排除明显错误的索引选择
```

### 7. 实战案例对比

```sql
-- 表:order 表有 1 亿行,字段:user_id, status, create_dt
CREATE TABLE order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT,
    status TINYINT,
    create_dt DATETIME,
    INDEX idx_user (user_id),
    INDEX idx_status (status),
    INDEX idx_create (create_dt)
);

-- 查询:某用户已完成的订单
SELECT * FROM order WHERE user_id = 100 AND status = 1;

-- 默认行为:优化器可能选错
EXPLAIN SELECT * FROM order WHERE user_id = 100 AND status = 1;
-- key: idx_status (status 选择性太低!)

-- 强制走更优索引
EXPLAIN SELECT * FROM order FORCE INDEX (idx_user)
WHERE user_id = 100 AND status = 1;
-- key: idx_user  (user_id 选择性高)

-- ★ 更好的做法:建联合索引
ALTER TABLE order ADD INDEX idx_user_status (user_id, status);

EXPLAIN SELECT * FROM order WHERE user_id = 100 AND status = 1;
-- key: idx_user_status  (一步到位)
```

## 十八、核心要点速记

- **索引本质**:用空间换时间,**加速查找 + 加速排序**,代价是写入开销和磁盘空间
- **默认引擎 InnoDB**,默认索引结构 **B+Tree**
- **B+Tree** 优势:树高 3~4 层,磁盘 IO 极少;叶子链表支持范围扫描
- **聚簇索引** = 数据 = 表本身(InnoDB 主键);二级索引叶子存**主键值**
- **回表**:二级索引 → 主键 → 聚簇索引;**覆盖索引** 可避免回表
- **最左前缀**:复合索引 `(a,b,c)` 命中顺序 **a → a,b → a,b,c**,跳 a 无效
- **索引下推 (ICP)**:在引擎层用索引列过滤,**减少回表次数**
- **MRR**:把随机回表 IO 转**顺序 IO**,减少寻道
- **索引失效**最常见:函数 / 计算 / 类型转换 / 前导模糊 / 范围后列 / 不等号
- **EXPLAIN 关键字段**:`type`、`key`、`key_len`、`rows`、`Extra`(Using index / filesort / temporary)
- **Cardinality** = 不同值数量,**越大选择性越好**,索引收益越大
- **HINT**:USE INDEX 建议、FORCE INDEX 强制、IGNORE INDEX 排除,**慎用 FORCE**
- **设计原则**:高频在前、选择性高在前、范围列放最后、覆盖查询列、避免冗余
- **Online DDL** (5.6+):`ALGORITHM=INPLACE, LOCK=NONE` 不阻塞读写
- **全文索引**:InnoDB 5.6+ 支持,中文用 **NGRAM** 解析器
- **Hash 索引**:Memory 引擎或 InnoDB **自适应 Hash**(用户不可控)
- **type 性能排序**(优→劣):`system > const > eq_ref > ref > range > index > ALL`
- **索引不是越多越好**,该有的有、没用的删;**定期 ANALYZE / OPTIMIZE**

### 索引设计口诀

```text
        等值列在前,范围列放最后
        高频列在前,选择性高在前
        覆盖查询列,避免回表 IO
        长串用前缀,函数计算要规避
        复合一个顶三个,冗余索引必删除
```
