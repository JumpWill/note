# MySQL 备份与恢复 (Backup & Recovery)

> 本章覆盖 MySQL 备份与恢复的完整体系:备份策略 RPO/RTO、物理/逻辑/全量/增量/冷热备份分类、mysqldump 工具详解、mysqlpump、XtraBackup 热备份、binlog 时间点恢复 (PITR)、快照备份、备份验证、自动化脚本与灾备演练。

## 一、备份概述

### 1. 为什么必须备份

数据库是企业的核心资产,备份是**数据安全最后一道防线**。常见故障场景:

- **硬件故障**:磁盘损坏、服务器宕机
- **人为错误**:误删表、误执行 DROP/UPDATE/DELETE、误上线
- **软件 Bug**:应用逻辑导致数据损坏
- **自然灾害**:机房火灾、洪水、断电
- **安全攻击**:勒索病毒、SQL 注入、黑客入侵
- **升级失败**:主从切换、版本升级、回滚

> **铁律**:没有备份,就没有真正的数据安全。任何高可用、容灾方案都不能替代备份。

### 2. 备份策略核心指标 — RPO 与 RTO

| 指标 | 名称 | 含义 | 衡量 |
|------|------|------|------|
| **RPO** | Recovery Point Objective | 灾难发生后能恢复到的数据时间点 | 可容忍的数据丢失量 |
| **RTO** | Recovery Time Objective | 灾难发生后恢复服务的最长时间 | 业务可容忍的停机时间 |

```text
示例:
  RPO = 1 小时 → 最多丢失 1 小时数据 → 至少 1 小时备份一次
  RTO = 30 分钟 → 故障后 30 分钟内必须恢复服务

业务分级:
  • 金融核心交易: RPO ≈ 0, RTO < 5 分钟 (需同步复制 + 实时备份)
  • 电商订单:     RPO < 5 分钟, RTO < 30 分钟
  • 内部系统:     RPO < 1 小时, RTO < 4 小时
  • 日志/分析库:  RPO < 24 小时, RTO < 24 小时
```

### 3. 备份三原则 (3-2-1 原则)

业界通用的数据保护黄金法则:

- **3** 份数据副本 (生产 + 2 份备份)
- **2** 种不同介质 (本地磁盘 + 异地磁带/对象存储)
- **1** 份异地存放 (Off-site,防机房级灾难)

```text
                    ┌── 备份 1: 本地 SSD (日常恢复)
生产数据 ──┬────────┤
          │        └── 备份 2: 异地对象存储 (S3/OSS, 防机房灾难)
          │
          └── 备份 3: 冷归档存储 (低成本, 长期保留)
```

## 二、备份分类

### 1. 物理备份 vs 逻辑备份

| 维度 | 物理备份 | 逻辑备份 |
|------|----------|----------|
| **原理** | 复制磁盘上的数据文件 | 导出 SQL 语句/数据 |
| **工具** | XtraBackup、mysqlbackup、cp/rsync | mysqldump、mysqlpump、SELECT...INTO OUTFILE |
| **速度** | 极快 (TB 级小时级) | 慢 (TB 级数十小时) |
| **跨版本/平台** | 同版本/同平台 | 跨版本、跨平台 |
| **跨引擎** | 强相关 (InnoDB 文件) | 无关 (SQL 通用) |
| **单表恢复** | 较难 (整库为单位) | 易 (单行 SQL 即可) |
| **一致性** | 需工具保证 | mysqldump --single-transaction 即可 |
| **可读性** | 二进制文件 | 文本 SQL |
| **压缩比** | 中等 | 高 |
| **适用场景** | 大库生产备份 | 小库、迁移、灵活恢复 |

### 2. 全量备份 vs 增量备份 vs 差异备份

```text
时间线:  周一 ── 周二 ── 周三 ── 周四 ── 周五 ── 周六 ── 周日
         │      │      │      │      │      │      │
数据变化: 10      5      8      3      6      4      2 (GB)
```

| 类型 | 周日恢复 | 备份量 | 恢复速度 | 存储成本 |
|------|----------|--------|----------|----------|
| **全量** | 只需周日全量 | 10 GB (每天) | 最快 | 最高 |
| **增量** | 周日全量 + 周一~六所有增量 | 10 + 5 + 8 + 3 + 6 + 4 + 2 = 38 GB | 慢 | 最低 |
| **差异** | 周日全量 + 周六差异 | 10 + (5+8+3+6+4+2) = 38 GB | 中 | 中 |

**特点**:
- **全量**:单独一份就能恢复,但占空间大
- **增量**:基于上一次备份,空间最小,但恢复需按顺序重放
- **差异**:基于上一次全量,恢复只需全量 + 一次差异,折中方案

### 3. 冷备份、温备份、热备份

| 类型 | 数据库状态 | 是否停服 | 一致性 | 适用 |
|------|------------|----------|--------|------|
| **冷备份 (Cold)** | 完全关闭 | 是 | 强一致 | 维护窗口 |
| **温备份 (Warm)** | 只读 / 加全局锁 | 部分 | 较强 | 可接受短锁 |
| **热备份 (Hot)** | 正常运行读写 | 否 | 工具保证 | 7×24 生产 |

```text
冷备份流程:
  1. 停止 MySQL: systemctl stop mysqld
  2. 拷贝数据目录: cp -r /var/lib/mysql /backup/
  3. 启动 MySQL: systemctl start mysqld

热备份流程 (XtraBackup):
  1. 拷贝 InnoDB 数据文件 (持续)
  2. 记录 LSN (日志序列号)
  3. 拷贝 redo log
  4. 备份结束时执行 FLUSH TABLES WITH READ LOCK 几秒
  5. 拷贝 binlog 位点
  6. 解锁
```

### 4. 在线备份 vs 离线备份

- **在线备份 (Online)**:数据库运行时执行,业务不中断 — 主要生产场景
- **离线备份 (Offline)**:数据库停机后执行 — 维护窗口、迁移

## 三、备份方式对比

| 方式 | 一致性 | 速度 | 粒度 | 跨平台 | 复杂度 |
|------|--------|------|------|--------|--------|
| **mysqldump** | 强 (单事务) | 慢 | 对象级 | 强 | 低 |
| **mysqlpump** | 强 | 中 (并行) | 对象级 | 强 | 低 |
| **XtraBackup** | 强 | 极快 | 整库 | 中 | 中 |
| **mysqlbackup** | 强 | 极快 | 整库 | 中 | 中 |

| **cp/rsync** | 需停服 | 快 | 整库 | 弱 | 低 |

## 四、逻辑备份工具 — mysqldump

### 1. mysqldump 概述

**mysqldump** 是 MySQL 自带的**逻辑备份**客户端工具,生成 SQL 脚本 (CREATE + INSERT)。

- **优点**:跨平台、跨版本、灵活、可选对象
- **缺点**:单线程,大库慢
- **本质**:把数据库对象导出为 SQL 语句

### 2. 完整语法

```bash
mysqldump [OPTIONS] database [tables]   # 单库或多表
mysqldump [OPTIONS] --databases [OPTIONS] DB1 DB2 ...  # 多库
mysqldump [OPTIONS] --all-databases [OPTIONS]          # 全库
```

**通用连接参数**:

| 参数 | 说明 |
|------|------|
| `-u, --user=name` | 用户名 |
| `-p, --password[=pwd]` | 密码 (建议交互输入) |
| `-h, --host=name` | 主机 |
| `-P, --port=#` | 端口 |
| `-S, --socket=name` | socket 文件 |
| `--protocol=tcp` | 强制 TCP |

### 3. 核心参数详解

#### 输出控制

| 参数 | 说明 |
|------|------|
| `--add-drop-database` | 每个 CREATE DATABASE 前加 DROP |
| `--add-drop-table` | 默认开启,CREATE TABLE 前加 DROP TABLE |
| `--add-drop-trigger` | trigger 前加 DROP TRIGGER |
| `-n, --no-create-db` | 不导出 CREATE DATABASE |
| `-t, --no-create-info` | 只导出数据,不导出表结构 |
| `-d, --no-data` | 只导出表结构,不导出数据 |
| `-c, --complete-insert` | 使用完整 INSERT (含列名) |
| `-e, --extended-insert` | 多行合一 INSERT (默认启用) |
| `--skip-extended-insert` | 每行一条 INSERT |
| `--replace` | 用 REPLACE 代替 INSERT |
| `--insert-ignore` | 用 INSERT IGNORE |
| `-X, --xml` | 导出为 XML |
| `--fields-terminated-by=` | 字段分隔符 (CSV) |
| `--lines-terminated-by=` | 行分隔符 |

#### 字符集与兼容性

| 参数 | 说明 |
|------|------|
| `--default-character-set=utf8mb4` | 客户端字符集 |
| `--compatible=name` | 兼容模式 (ansi/mysql323/postgresql 等) |
| `--set-charset` | 添加 SET NAMES (默认) |

#### 事务与一致性

| 参数 | 说明 |
|------|------|
| `--single-transaction` | **InnoDB 必备**,单事务一致性读 |
| `--quick, -q` | 不缓存全表,逐行查询 |
| `--lock-tables` | 锁所有库的所有表 (MyISAM) |
| `--lock-all-tables, -x` | 全局读锁 (FLUSH TABLES WITH READ LOCK) |
| `--master-data[=#]` | 记录 binlog 位点:1=注释,2=可执行 |
| `--flush-logs` | 备份开始时 flush logs |
| `--flush-privileges` | 备份 mysql 库时刷新权限 |

#### 对象与数据

| 参数 | 说明 |
|------|------|
| `-R, --routines` | 导出存储过程和函数 |
| `--triggers` | 默认开启,导出触发器 |
| `-E, --events` | 导出事件 |
| `--skip-triggers` | 不导出触发器 |
| `-F, --force` | 出错继续 |
| `-w, --where='condition'` | 仅导出符合条件的数据 |
| `--no-data, -d` | 只导出结构 |

#### 性能与并行

| 参数 | 说明 |
|------|------|
| `--max-allowed-packet=#` | 最大包大小,默认 24MB |
| `--net-buffer-length=#` | 网络缓冲,默认 1MB |
| `--parallel-schemas=N` | 并行,MySQL 5.7+ (mysqlpump 才有) |

### 4. 备份示例

#### (1) 单库备份

```bash
# 备份单个数据库
mysqldump -uroot -p mydb > /backup/mydb_$(date +%Y%m%d).sql

# 备份单库 + 完整 INSERT + 压缩
mysqldump -uroot -p --complete-insert --single-transaction mydb | gzip > /backup/mydb.sql.gz

# 备份单库 + 存储过程 + 触发器 + 事件
mysqldump -uroot -p -R -E --triggers mydb > /backup/mydb_full.sql

# 只导出结构 (无数据)
mysqldump -uroot -p --no-data mydb > /backup/mydb_schema.sql

# 只导出数据 (无结构)
mysqldump -uroot -p --no-create-info mydb > /backup/mydb_data.sql

# 导出单表
mysqldump -uroot -p mydb users > /backup/users.sql

# 按条件导出数据
mysqldump -uroot -p mydb orders --where="created_at >= '2024-01-01'" > /backup/orders_2024.sql
```

#### (2) 多库备份

```bash
# 备份多个指定库
mysqldump -uroot -p --databases db1 db2 db3 > /backup/multi_db.sql

# 备份时排除某些库
mysqldump -uroot -p --databases $(mysql -uroot -p -e "SHOW DATABASES" | grep -Ev "^(Database|information_schema|performance_schema|sys|mysql)$") > /backup/all_except_system.sql
```

#### (3) 全库备份

```bash
# 全库备份 (含系统库)
mysqldump -uroot -p --all-databases --single-transaction --routines --events --triggers > /backup/all_db.sql

# 全库备份 + 压缩 + 记录 binlog 位点
mysqldump -uroot -p \
  --all-databases \
  --single-transaction \
  --master-data=2 \
  --routines --events --triggers \
  | gzip > /backup/all_db_$(date +%Y%m%d_%H%M%S).sql.gz

# 分库备份 (每个库一个文件,推荐)
for db in $(mysql -uroot -p -N -e "SHOW DATABASES" | grep -v "information_schema\|performance_schema\|sys"); do
  mysqldump -uroot -p --single-transaction --routines --events \
    --databases $db | gzip > /backup/${db}_$(date +%Y%m%d).sql.gz
done
```

### 5. --single-transaction (InnoDB 一致性备份关键)

**原理**:在一个 REPEATABLE READ 事务里执行,获得一致性快照,期间其他会话写入不影响备份。

```bash
mysqldump -uroot -p --single-transaction --master-data=2 mydb > /backup/mydb.sql
```

**关键点**:
- 适用于 **InnoDB** 引擎
- 备份期间**不加锁**,业务可正常写入
- 整个备份时间长,需保证 `innodb_lock_wait_timeout` > 备份时长
- **MyISAM 表无法保证一致性**,需配合 `--lock-tables`

**使用场景**:
```bash
# 7×24 不停机备份
mysqldump -uroot -p \
  --single-transaction \
  --quick \
  --routines --events \
  --master-data=2 \
  --triggers \
  mydb | gzip > /backup/mydb_$(date +%Y%m%d_%H%M%S).sql.gz
```

### 6. --master-data (主从搭建场景)

```bash
# --master-data=1: 注释形式记录 binlog 位点 (CHANGE MASTER TO 注释)
# --master-data=2: 可执行 CHANGE MASTER TO (默认值)
mysqldump -uroot -p --master-data=2 --single-transaction --all-databases > /backup/master.sql
```

**生成的 SQL**:

```sql
-- 值为 1 时:
-- CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000123', MASTER_LOG_POS=456789;

-- 值为 2 时 (直接可执行):
CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000123', MASTER_LOG_POS=456789;
```

**注意事项**:
- **必须**与 `--single-transaction` 同时使用 (GTID 可不强制)
- GTID 模式下推荐 `--set-gtid-purged=OFF` (避免 GTID 已被 purge 问题)
- 记录了恢复起点,后续可用 binlog 做 PITR

### 7. --routines / --triggers / --events

```bash
mysqldump -uroot -p \
  --routines      # 存储过程、函数
  --triggers      # 默认开,触发器
  --events        # 事件调度器
  --single-transaction \
  mydb > /backup/mydb_full.sql
```

**关键点**:
- `--triggers` 默认就是 on,无需显式声明
- `--routines` 默认关闭,必须显式开启
- `--events` 默认关闭

### 8. 备份压缩与恢复

```bash
# 备份时压缩 (流式)
mysqldump -uroot -p mydb | gzip > /backup/mydb.sql.gz
mysqldump -uroot -p mydb | xz > /backup/mydb.sql.xz
mysqldump -uroot -p mydb | zstd > /backup/mydb.sql.zst

# 恢复
gunzip < /backup/mydb.sql.gz | mysql -uroot -p
# 或
zcat /backup/mydb.sql.gz | mysql -uroot -p
```

### 9. 恢复

```bash
# 整库恢复
mysql -uroot -p < /backup/mydb.sql

# 恢复前先创建空库或解压
mysql -uroot -p -e "CREATE DATABASE mydb"
mysql -uroot -p mydb < /backup/mydb.sql

# 部分恢复 (从全库备份 grep)
grep -E "^INSERT INTO \`users\`" /backup/all_db.sql | mysql -uroot -p mydb

# 验证
mysql -uroot -p -e "SELECT COUNT(*) FROM mydb.users"
```

> **重要**:恢复操作本身也是 DDL + DML,需进入 binlog,慎用 `SET SQL_LOG_BIN=0` 避免循环复制。

## 五、mysqldump + binlog 实现时间点恢复 (PITR)

### 1. 原理

```text
时间点恢复 (Point-In-Time Recovery, PITR) = 全量备份 + binlog 重放

步骤:
  1. 恢复最近一次全量备份 (假设周日 0 点)
  2. 应用从备份到故障点的所有 binlog (周日 0 点 → 周三 10 点误操作前)
```

### 2. 完整流程

```bash
# === 准备工作 ===
# 1. 开启 binlog (重要!无 binlog 无法 PITR)
# my.cnf
[mysqld]
log_bin = /var/log/mysql/mysql-bin.log
server_id = 1
binlog_format = ROW
expire_logs_days = 7
gtid_mode = ON
enforce_gtid_consistency = ON

# 2. 当前 binlog 位点
mysql -uroot -p -e "SHOW MASTER STATUS"
# File: mysql-bin.000123, Position: 456789
# Executed_Gtid_Set: 3E11FA47-71CA-11E9-....

# === 步骤 1: 全量备份 ===
mysqldump -uroot -p \
  --single-transaction \
  --master-data=2 \
  --routines --events \
  --all-databases \
  | gzip > /backup/full_$(date +%Y%m%d).sql.gz

# === 步骤 2: 持续备份 binlog ===
# 定时 flush 并归档
mysql -uroot -p -e "FLUSH LOGS"
cp /var/log/mysql/mysql-bin.0* /backup/binlog/

# === 步骤 3: 故障发生 (假设周三 10:30 误删 users 表) ===
# 当前 binlog
mysql -uroot -p -e "SHOW MASTER STATUS"

# === 步骤 4: 恢复 ===

# 4.1 停止 MySQL
systemctl stop mysqld

# 4.2 备份当前数据 (防止二次损坏)
mv /var/lib/mysql /var/lib/mysql.bak
mkdir /var/lib/mysql
chown mysql:mysql /var/lib/mysql

# 4.3 初始化数据目录 (恢复上下文)
mysqld --initialize-insecure --user=mysql
# 或还原上次全量: cp -r /backup/data_full /var/lib/mysql

# 4.4 恢复全量备份
gunzip < /backup/full_20240115.sql.gz | mysql -uroot -p

# 4.5 查看全量备份的 binlog 位点
head -50 /backup/full_20240115.sql | grep "CHANGE MASTER"

# 4.6 重放从备份到故障前的 binlog
# 找到误操作的位置
mysqlbinlog --base64-output=DECODE-ROWS \
  /backup/binlog/mysql-bin.000125 \
  /backup/binlog/mysql-bin.000126 \
  | grep -B 5 -A 5 "DROP TABLE \`users\`" \
  > /tmp/drop_users.sql

# 查看 binlog 事件,定位误操作的位点
mysqlbinlog --start-datetime="2024-01-17 00:00:00" \
  --stop-datetime="2024-01-17 10:30:00" \
  /backup/binlog/mysql-bin.000126 | less

# 4.7 重放,跳过误操作
mysqlbinlog --stop-datetime="2024-01-17 10:29:00" \
  /backup/binlog/mysql-bin.000126 | mysql -uroot -p

# === 步骤 5: 验证 ===
mysql -uroot -p -e "SELECT COUNT(*) FROM mydb.users"
```

### 3. 基于 GTID 的 PITR

```bash
# 查看 GTID
mysql -uroot -p -e "SHOW MASTER STATUS"

# 基于 GTID 集合恢复
mysqlbinlog --include-gtids='3E11FA47-71CA-11E9-...:1-1000' \
  --exclude-gtids='3E11FA47-71CA-11E9-...:950' \
  /backup/binlog/mysql-bin.000126 | mysql -uroot -p

# 跳过误操作对应的事务
SET GTID_NEXT="3E11FA47-71CA-11E9-...:950";
BEGIN; COMMIT;
SET GTID_NEXT="AUTOMATIC";
```

## 六、mysqlpump (并行逻辑备份,MySQL 5.7+)

### 1. 概述

**mysqlpump** 是 MySQL 5.7 引入的并行逻辑备份工具,mysqldump 的"升级版"。

- 多线程并行 (按库/表)
- 压缩传输
- 进度条
- 更好的对象过滤

### 2. 与 mysqldump 对比

| 维度 | mysqldump | mysqlpump |
|------|-----------|-----------|
| 并行 | 单线程 | 按库/表并行 |
| 压缩 | 外部 | 内置 |
| 进度 | 无 | 有 |
| 过滤 | 简单 | 强大 (include/exclude) |
| 兼容性 | 5.0+ | 5.7+ |

### 3. 完整示例

```bash
# 全库并行备份 (8 线程)
mysqlpump -uroot -p \
  --default-parallelism=8 \
  --single-transaction \
  --routines --events \
  --all-databases \
  > /backup/all_pump.sql

# 压缩备份
mysqlpump -uroot -p \
  --compress-output=ZLIB \
  --default-parallelism=8 \
  --all-databases \
  > /backup/all_pump.sql.zlib

# 排除某个库
mysqlpump -uroot -p \
  --exclude-databases=tmp \
  --exclude-tables=tmp.session_log \
  --all-databases \
  > /backup/pump_exclude.sql

# 仅备份指定的库
mysqlpump -uroot -p \
  --include-databases=mydb,testdb \
  --include-tables=mydb.users,mydb.orders \
  > /backup/pump_included.sql

# 进度条 + 详细日志
mysqlpump -uroot -p \
  --default-parallelism=4 \
  --log-progress=progress.txt \
  --watch-progress \
  --all-databases \
  > /backup/pump.sql
```

### 4. 恢复

```bash
# 解压恢复
zlib_decompress < /backup/all_pump.sql.zlib | mysql -uroot -p
# 或
mysqlpump --compress-output=ZLIB ... > /backup/pump.sql.zlib
# 解压工具: zlib_decompress (MySQL 自带)

# 直接恢复
mysql -uroot -p < /backup/all_pump.sql
```

## 七、物理备份工具 — Percona XtraBackup (热备份之王)

### 1. 概述

**Percona XtraBackup** (简称 PXB,命令 `xtrabackup`) 是业界使用最广的**开源热备份**工具,专门针对 InnoDB/XtraDB。

**核心特性**:
- **热备份**:业务无感知,不停服
- **增量备份**:物理块级别 diff
- **并行**:多线程备份/恢复
- **一致性**:通过 redo log + undo log 保证
- **压缩、加密、流式**

```text
xtrabackup 8.0 版本对应命令:
  xtrabackup --backup ...        # 备份
  xtrabackup --prepare ...       # 准备 (apply redo/undo)
  xtrabackup --copy-back ...     # 恢复
  xtrabackup --move-back ...     # 恢复并移动
```

### 2. 安装

```bash
# Ubuntu/Debian
wget https://repo.percona.com/apt/percona-release_latest.$(lsb_release -sc)_all.deb
sudo dpkg -i percona-release_latest.$(lsb_release -sc)_all.deb
sudo apt update
sudo apt install percona-xtrabackup-80

# CentOS/RHEL
sudo yum install percona-xtrabackup-80

# 验证
xtrabackup --version
# xtrabackup version 8.0.34-29 based on MySQL 8.0.34
```

### 3. 完整流程:备份 → prepare → 恢复

#### (1) 全量备份

```bash
xtrabackup --backup \
  --user=root \
  --password=secret \
  --host=127.0.0.1 \
  --port=3306 \
  --target-dir=/backup/full/2024-01-15_00-00-00 \
  --parallel=4 \
  --compress \
  --compress-threads=4 \
  2> /backup/log/full_backup.log
```

**关键参数**:
| 参数 | 说明 |
|------|------|
| `--backup` | 备份模式 |
| `--target-dir` | 备份目录 |
| `--parallel=N` | 子进程并行数 |
| `--compress` | 启用 qpress 压缩 |
| `--compress-threads=N` | 压缩线程 |
| `--encrypt=AES256` | 启用加密 |
| `--encrypt-key-file=...` | 密钥文件 |
| `--stream=xbstream` | 流式输出 (到远程) |
| `--throttle=N` | 限速 IOPS |
| `--use-memory=2G` | prepare 阶段内存 |

#### (2) Prepare (回放日志,准备一致性)

```bash
# 解压 (若用了 --compress)
xtrabackup --decompress --target-dir=/backup/full/2024-01-15_00-00-00

# Prepare:回放未提交事务 + 已提交但未刷盘事务
xtrabackup --prepare \
  --target-dir=/backup/full/2024-01-15_00-00-00 \
  --use-memory=2G \
  --parallel=4 \
  2> /backup/log/prepare.log
```

**prepare 做了什么**:
- 合并 data pages + redo log
- 回滚未提交事务
- 提交已写入 redo 但未 commit 的事务
- 完成后数据文件处于"干净"状态,可启动

#### (3) 恢复

```bash
# 停止 MySQL
systemctl stop mysqld

# 清空数据目录 (或重命名)
mv /var/lib/mysql /var/lib/mysql.bak

# 复制或移动备份文件
# --copy-back: 复制 (保留原备份)
# --move-back: 移动 (节省空间)
xtrabackup --copy-back \
  --target-dir=/backup/full/2024-01-15_00-00-00 \
  --parallel=4 \
  2> /backup/log/copyback.log

# 修改权限
chown -R mysql:mysql /var/lib/mysql

# 启动 MySQL
systemctl start mysqld
```

### 4. 增量备份

```bash
# === 步骤 1: 全量备份 (周日) ===
xtrabackup --backup \
  --user=root --password=secret \
  --target-dir=/backup/inc/base \
  --parallel=4

# === 步骤 2: 第一次增量 (周一) ===
xtrabackup --backup \
  --user=root --password=secret \
  --target-dir=/backup/inc/inc1 \
  --incremental-basedir=/backup/inc/base \
  --parallel=4

# === 步骤 3: 第二次增量 (周二) ===
xtrabackup --backup \
  --user=root --password=secret \
  --target-dir=/backup/inc/inc2 \
  --incremental-basedir=/backup/inc/inc1 \
  --parallel=4

# === 步骤 4: Prepare (按顺序重放) ===
# 1. 先 prepare 全量
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/inc/base

# 2. 合并第一次增量
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/inc/base \
  --incremental-dir=/backup/inc/inc1

# 3. 合并第二次增量 (最后一次不加 --apply-log-only)
xtrabackup --prepare \
  --target-dir=/backup/inc/base \
  --incremental-dir=/backup/inc/inc2

# 4. 恢复
xtrabackup --copy-back --target-dir=/backup/inc/base
```

> **关键点**:`--apply-log-only` 标记 prepare 阶段不执行 rollback,保证后续增量能继续合并。只有最后一次 prepare 才真正 rollback。

### 5. XtraBackup + binlog 实现时间点恢复

```bash
# === 步骤 1: XtraBackup 全量备份 ===
xtrabackup --backup \
  --user=root --password=secret \
  --target-dir=/backup/full/2024-01-15 \
  --parallel=4

# === 步骤 2: 备份生成 xtrabackup_binlog_info (记录 binlog 位点) ===
cat /backup/full/2024-01-15/xtrabackup_binlog_info
# mysql-bin.000123  456789

# === 步骤 3: 准备备份 ===
xtrabackup --prepare --target-dir=/backup/full/2024-01-15

# === 步骤 4: 恢复数据文件 ===
xtrabackup --copy-back --target-dir=/backup/full/2024-01-15
chown -R mysql:mysql /var/lib/mysql
systemctl start mysqld

# === 步骤 5: 重放 binlog 到目标时间点 ===
# 应用从备份位点 (456789) 到故障前
mysqlbinlog --start-position=456789 \
  --stop-datetime="2024-01-17 10:29:00" \
  /var/log/mysql/mysql-bin.000123 \
  /var/log/mysql/mysql-bin.000124 \
  /var/log/mysql/mysql-bin.000125 \
  | mysql -uroot -p
```

### 6. innobackupex (兼容脚本,XtraBackup 2.4 及之前)

```bash
# 旧版脚本命令 (XtraBackup 2.4 及之前)
innobackupex --user=root --password=secret /backup/full/
innobackupex --apply-log /backup/full/2024-01-15_00-00-00/

# 8.0 中已弃用,统一使用 xtrabackup
```

### 7. 备份到远程 (xbstream 流式)

```bash

xtrabackup --backup \
  --user=root --password=secret \
  --stream=xbstream \
  --compress \
  --parallel=4 \
  --target-dir=/tmp \
  | ssh user@backup-server "cat - > /backup/xb_$(date +%Y%m%d).xbstream"

# 远程恢复
ssh user@backup-server "cat /backup/xb_20240115.xbstream" \
  | xbstream -x -C /tmp/restore
xtrabackup --decompress --target-dir=/tmp/restore
xtrabackup --prepare --target-dir=/tmp/restore
xtrabackup --copy-back --target-dir=/tmp/restore
```

## 九、快照备份 (LVM Snapshot / ZFS Snapshot)

### 1. 原理

利用文件系统或卷管理的**快照**特性,**瞬时**创建数据目录的一致性副本,然后从快照拷贝出真实文件。

```text
LVM Snapshot 流程:
  1. FLUSH TABLES WITH READ LOCK   (全局读锁,几秒)
  2. lvcreate -s /dev/vg0/mysql   (创建快照,秒级)
  3. UNLOCK TABLES
  4. mount 快照
  5. 从快照拷贝文件
  6. 卸载,删除快照
```

### 2. LVM Snapshot 备份脚本

```bash
#!/bin/bash
# 前提:数据目录在 LVM LV 上

DATA_DIR=/var/lib/mysql
LV_PATH=/dev/vg0/mysql
SNAP_SIZE=5G
SNAP_NAME=mysql_snap_$(date +%Y%m%d)
SNAP_MOUNT=/mnt/snap
BACKUP_DIR=/backup/snap_$(date +%Y%m%d)

# 1. 加全局读锁
mysql -uroot -psecret -e "FLUSH TABLES WITH READ LOCK"

# 2. 创建快照
lvcreate -L $SNAP_SIZE -s -n $SNAP_NAME $LV_PATH

# 3. 释放锁
mysql -uroot -psecret -e "UNLOCK TABLES"

# 4. 挂载快照
mkdir -p $SNAP_MOUNT
mount /dev/vg0/$SNAP_NAME $SNAP_MOUNT

# 5. 备份
mkdir -p $BACKUP_DIR
rsync -a $SNAP_MOUNT/ $BACKUP_DIR/

# 6. 清理
umount $SNAP_MOUNT
lvremove -f /dev/vg0/$SNAP_NAME
```

### 3. ZFS Snapshot

```bash
# 创建 ZFS 快照 (秒级)
zfs snapshot tank/mysql@$(date +%Y%m%d_%H%M%S)

# 查看
zfs list -t snapshot

# 发送快照到备份服务器 (流式)
zfs send tank/mysql@2024-01-15 | ssh backup "zfs receive tank/backup/mysql"

# 增量发送
zfs send -i tank/mysql@2024-01-14 tank/mysql@2024-01-15 | \
  ssh backup "zfs receive tank/backup/mysql"
```

### 4. 注意事项

- **必须**有 LVM/ZFS 存储
- 锁时间窗口很小 (秒级)
- 需要专用备份节点执行
- 适合超大数据库 (TB 级)

## 十二、备份验证 (Restore Test)

### 1. 为什么必须验证

> **"备份没验证 = 没有备份"** — 真实的备份失败案例大多在验证环节发现。

**常见问题**:
- 备份文件损坏 (磁盘、传输)
- 备份不完整 (中途失败)
- 备份可恢复但数据缺失
- 备份不可恢复 (如版本不兼容)

### 2. 验证流程

```bash
# === 1. 校验备份文件完整性 ===
# md5 校验
md5sum /backup/full_20240115.sql.gz > /backup/full.md5
# 验证时
md5sum -c /backup/full.md5

# === 2. 周期性恢复测试 (建议每月) ===
# 在独立的测试环境
systemctl stop mysqld
rm -rf /var/lib/mysql/*
gunzip < /backup/full_20240115.sql.gz | mysql -uroot -p
systemctl start mysqld

# === 3. 数据一致性校验 ===
# 行数对比
mysql -uroot -p production -e "SELECT COUNT(*) FROM users" > prod_count.txt
mysql -uroot -p test_restore -e "SELECT COUNT(*) FROM users" > restore_count.txt
diff prod_count.txt restore_count.txt

# 校验和 (CHECKSUM TABLE)
mysql -uroot -p production -e "CHECKSUM TABLE users, orders"
mysql -uroot -p test_restore -e "CHECKSUM TABLE users, orders"

# === 4. 验证关键功能 ===
mysql -uroot -p test_restore -e "SELECT * FROM users LIMIT 10"
mysql -uroot -p test_restore -e "SHOW TRIGGERS"
mysql -uroot -p test_restore -e "SHOW PROCEDURE STATUS WHERE Db='mydb'"

# === 5. 性能验证 (恢复耗时) ===
time gunzip < /backup/full_20240115.sql.gz | mysql -uroot -p
```

### 3. 自动化验证脚本

```bash
#!/bin/bash
# /usr/local/bin/verify_backup.sh
BACKUP_FILE=$1
TEST_DB=test_verify_$(date +%s)

# 1. 校验文件
if [ ! -f "$BACKUP_FILE" ]; then
  echo "ALERT: 备份文件不存在"
  exit 1
fi

# 2. 测试恢复
mysql -uroot -psecret -e "CREATE DATABASE $TEST_DB"
gunzip < $BACKUP_FILE | mysql -uroot -psecret $TEST_DB

# 3. 校验
ROWS=$(mysql -uroot -psecret -N -e "SELECT SUM(TABLE_ROWS) FROM information_schema.tables WHERE table_schema='$TEST_DB'")
echo "总行数: $ROWS"

# 4. 清理
mysql -uroot -psecret -e "DROP DATABASE $TEST_DB"

# 5. 报告
echo "备份验证完成: $BACKUP_FILE"
```

## 十三、自动备份脚本示例 (crontab + mysqldump)

### 1. 完整生产级备份脚本

```bash
#!/bin/bash
# /usr/local/bin/mysql_backup.sh
# MySQL 自动备份 (XtraBackup + mysqldump 双重策略)

set -euo pipefail

# === 配置 ===
MYSQL_USER="backup_user"
MYSQL_PASS="backup_password"
MYSQL_HOST="127.0.0.1"
MYSQL_PORT="3306"
BACKUP_ROOT="/backup/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
WEEKDAY=$(date +%u)
HOUR=$(date +%H)
LOG_FILE="/var/log/mysql_backup_${DATE}.log"

# 保留策略
KEEP_DAILY=7
KEEP_WEEKLY=4
KEEP_MONTHLY=12

# === 工具检查 ===
command -v mysqldump >/dev/null 2>&1 || { echo "mysqldump 未安装"; exit 1; }
command -v xtrabackup >/dev/null 2>&1 || { echo "xtrabackup 未安装"; exit 1; }

# === 日志函数 ===
log() {
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a $LOG_FILE
}

# === 创建备份目录 ===
mkdir -p ${BACKUP_ROOT}/{full,inc,dump,binlog}

# === 1. 全量备份 (每周日 00:00) ===
if [ "$WEEKDAY" -eq 7 ] && [ "$HOUR" -eq 0 ]; then
  log "开始 XtraBackup 全量备份"
  xtrabackup --backup \
    --user=$MYSQL_USER --password=$MYSQL_PASS \
    --host=$MYSQL_HOST --port=$MYSQL_PORT \
    --target-dir=${BACKUP_ROOT}/full/${DATE} \
    --parallel=4 \
    --compress \
    --compress-threads=4 \
    2>> $LOG_FILE

  # 备份 binlog 位点
  cat ${BACKUP_ROOT}/full/${DATE}/xtrabackup_binlog_info > ${BACKUP_ROOT}/full/${DATE}/binlog_info.txt

  log "全量备份完成: ${BACKUP_ROOT}/full/${DATE}"
fi

# === 2. 增量备份 (除周日外每天 00:00) ===
if [ "$WEEKDAY" -ne 7 ] && [ "$HOUR" -eq 0 ]; then
  # 找最新一次全量或增量
  LAST_BASE=$(ls -td ${BACKUP_ROOT}/full/* ${BACKUP_ROOT}/inc/* 2>/dev/null | head -1)

  if [ -n "$LAST_BASE" ]; then
    log "开始增量备份,基于: $LAST_BASE"
    xtrabackup --backup \
      --user=$MYSQL_USER --password=$MYSQL_PASS \
      --host=$MYSQL_HOST --port=$MYSQL_PORT \
      --target-dir=${BACKUP_ROOT}/inc/${DATE} \
      --incremental-basedir=$LAST_BASE \
      --parallel=4 \
      --compress \
      2>> $LOG_FILE
    log "增量备份完成"
  fi
fi

# === 3. 逻辑备份 (每天 03:00) ===
if [ "$HOUR" -eq 3 ]; then
  log "开始 mysqldump 逻辑备份"
  mysqldump -u$MYSQL_USER -p$MYSQL_PASS \
    --host=$MYSQL_HOST --port=$MYSQL_PORT \
    --single-transaction \
    --master-data=2 \
    --routines --events --triggers \
    --all-databases \
    | gzip > ${BACKUP_ROOT}/dump/all_${DATE}.sql.gz

  log "逻辑备份完成: ${BACKUP_ROOT}/dump/all_${DATE}.sql.gz"

  # md5 校验
  md5sum ${BACKUP_ROOT}/dump/all_${DATE}.sql.gz > ${BACKUP_ROOT}/dump/all_${DATE}.sql.gz.md5
fi

# === 4. binlog 实时备份 (每小时) ===
if [ "$HOUR" == "*/1" ] || true; then
  log "备份 binlog"
  # 刷新 binlog (可选)
  mysql -u$MYSQL_USER -p$MYSQL_PASS -e "FLUSH BINARY LOGS"

  # 拷贝到备份目录
  rsync -a /var/log/mysql/mysql-bin.0* ${BACKUP_ROOT}/binlog/ 2>/dev/null || true
fi

# === 5. 清理过期备份 ===
log "清理过期备份"
# 删除 N 天前的逻辑备份
find ${BACKUP_ROOT}/dump -name "*.sql.gz" -mtime +${KEEP_DAILY} -delete
find ${BACKUP_ROOT}/dump -name "*.sql.gz.md5" -mtime +${KEEP_DAILY} -delete

# 删除 N 周前的增量
find ${BACKUP_ROOT}/inc -maxdepth 1 -type d -mtime +$((KEEP_DAILY * 7)) -exec rm -rf {} +

# 每周保留最近 4 周全量
find ${BACKUP_ROOT}/full -maxdepth 1 -type d -mtime +$((KEEP_WEEKLY * 7)) -exec rm -rf {} +

# 每月保留 (1 号保留)
if [ "$(date +%d)" -eq 1 ]; then
  cp -r ${BACKUP_ROOT}/full/$(ls -t ${BACKUP_ROOT}/full | head -1) /backup/monthly/
fi

log "备份任务完成"
```

## 十四、备份策略建议 (金字塔模型)

### 1. 备份金字塔

```text
                    ▲ 高成本、低频
                   ╱ ╲
                  ╱ 月 ╲          月度归档 (异地冷存储,保留 1 年)
                 ╱─────╲
                ╱  周   ╲        周全量 + 增量 (XtraBackup,本地+异地)
               ╱─────────╲
              ╱    日    ╲      日逻辑 (mysqldump,本地+异地)
             ╱─────────────╲
            ╱      时      ╲    小时增量/快照
           ╱─────────────────╲
          ╱       分         ╲  binlog 实时归档
         ╱_____________________╲
        ▼ 低成本、高频
```

### 2. 推荐策略组合

| 业务等级 | 备份策略 | 频率 | RPO | RTO |
|----------|----------|------|-----|-----|
| **核心交易** | XtraBackup + binlog + DR | 6h + 实时 | < 1 分钟 | < 5 分钟 |
| **重要业务** | XtraBackup + mysqldump + binlog | 每日 + 实时 | < 5 分钟 | < 30 分钟 |
| **普通业务** | mysqldump | 每日 | < 1 小时 | < 数小时 |
| **日志/分析** | mysqldump 周备份 | 每周 | < 24 小时 | < 24 小时 |

### 3. 多副本 (3-2-1 + 4-3-2 原则)

```text
3 份数据 (生产 + 备份 1 + 备份 2)
2 个媒体 (磁盘 + 磁带/对象存储)
1 份异地 (异地机房 / S3 / OSS)

进阶 4-3-2:
  4 份数据
  3 种存储介质
  2 个地理位置
```

### 4. 备份存储成本对比

| 存储 | 成本 | 速度 | 适用 |
|------|------|------|------|
| 本地 SSD | 高 | 极快 | 日常恢复 |
| 本地 HDD | 中 | 快 | 周/月备份 |
| NFS | 中 | 中 | 共享 |
| 对象存储 (S3/OSS) | 低 | 慢 | 异地归档 |
| 磁带 | 极低 | 慢 | 长期归档 |
| 蓝光 | 低 | 慢 | 长期归档 |

## 十六、常见备份问题与排查

### 1. 备份失败

| 问题 | 原因 | 解决 |
|------|------|------|
| 锁等待超时 | 备份期间长事务 | 增大 `innodb_lock_wait_timeout` |
| 磁盘空间不足 | 备份太大 | 压缩 + 清理 + 扩容 |
| 权限拒绝 | 备份用户权限不足 | GRANT 权限 |
| binlog 不一致 | 备份时 binlog 已 purge | 开启足够保留期 |
| 版本不兼容 | 跨版本恢复 | 同版本/同平台 |

### 2. 恢复慢

```bash
# 优化点:
# 1. 关闭 binlog 恢复 (如恢复数据到指定库)
mysql -uroot -p -e "SET SQL_LOG_BIN=0"
mysql -uroot -p mydb < /backup/mydb.sql
mysql -uroot -p -e "SET SQL_LOG_BIN=1"

# 2. 关闭外键检查
mysql -uroot -p -e "SET FOREIGN_KEY_CHECKS=0"
mysql -uroot -p mydb < /backup/mydb.sql
mysql -uroot -p -e "SET FOREIGN_KEY_CHECKS=1"

# 3. 增大参数
SET GLOBAL max_allowed_packet = 1024*1024*1024;
SET GLOBAL innodb_buffer_pool_size = 8*1024*1024*1024;
```

### 3. 备份文件损坏

```bash
# gzip 损坏但可恢复
gzip -t /backup/mydb.sql.gz
# 输出: "gzip: /backup/mydb.sql.gz: unexpected end of file" → 损坏

# 尝试恢复
gunzip < /backup/mydb.sql.gz | head -n 100
# 看是否能读
```

## 十七、核心要点速记

- **RPO** = 可容忍数据丢失量,**RTO** = 可容忍停机时间
- **3-2-1 原则**:3 份副本、2 种介质、1 份异地
- **物理备份** = 文件级,**逻辑备份** = SQL 级
- **全量 + 增量 + 差异**:全量是基线,增量最省但恢复慢
- **冷备份** = 停服,**热备份** = 不停服
- **mysqldump --single-transaction** = InnoDB 一致性备份 (单事务)
- **mysqldump --master-data=2** = 记录 binlog 位点 (主从/PITR)
- **mysqldump --routines --events** = 导出存储过程/事件
- **PITR** = 全量恢复 + binlog 重放
- **mysqlpump** = mysqldump 并行升级版,5.7+
- **XtraBackup** = Percona 开源热备份,业界主流
- **XtraBackup 流程**:backup → prepare → copy-back
- **XtraBackup 增量**:基于 `--incremental-basedir`,prepare 需 `--apply-log-only`
- **innobackupex** = 旧版脚本,XtraBackup 8.0 弃用
- **LVM/ZFS Snapshot** = 瞬时快照,适合超大库
- **快照备份** = FLUSH LOCK → lvcreate → UNLOCK → 拷贝
- **物理文件 cp** = 必须停服,简单粗暴
- **mysqlbinlog --start-position/-stop-position** = 按位点恢复
- **mysqlbinlog --start-datetime/-stop-datetime** = 按时间恢复
- **mysqlbinlog --exclude-gtids** = 跳过某 GTID 事务
- **ROW 格式 + binlog_row_image=FULL** = 完整记录变化
- **备份验证** = 周期性 restore test,不可省
- **md5sum/sha256sum** = 备份完整性校验
- **备份用户** = 最小权限 (RELOAD, LOCK TABLES, BACKUP_ADMIN)
- **crontab** = 自动化备份,必加日志
- **3-2-1 + 多副本 + 异地** = 数据安全
- **灾难演练** = 检验备份可用性,定期执行
- **备份策略** = 业务分级 + RPO/RTO + 成本
- **binlog 必须开启** 否则无法 PITR
- **恢复时关闭 binlog** = `SET SQL_LOG_BIN=0` 避免循环复制
- **恢复时关闭外键检查** = `SET FOREIGN_KEY_CHECKS=0` 提速
- **xtrabackup --copy-back** = 恢复 (保留备份),**--move-back** = 移动
- **mysqlbackup (MEB)** = Oracle 官方商业版,功能与 XtraBackup 类似
- **验证脚本** = 至少每季度一次,记录 RTO/RPO
- **清理过期备份** = `find ... -mtime +N -delete`
- **备份脚本** = 必须包含日志、错误处理、退出码
- **快照备份** = 全局锁几秒,适合 7×24
- **binlog 归档** = 异地同步,防勒索病毒
