# MySQL 存储引擎 (Storage Engines)

> 本章覆盖 MySQL 的存储引擎体系:可插拔式架构、各引擎特性对比、InnoDB 数据页结构与行格式、MyISAM/Memory/Archive/CSV/Blackhole/Federated 引擎特点、引擎选择实践,以及 MySQL 8.0 数据字典与原子 DDL 的关键变化。

---

## 一、存储引擎概述

### 1. 什么是存储引擎

**存储引擎 (Storage Engine)** 是 MySQL 中**负责数据存储、索引维护、查询/写入执行的核心组件**。它规定了:

- 数据**如何存储**到磁盘
- 数据**如何索引**(B+Tree、Hash、R-Tree 等)
- 数据**如何查询**(全表扫描、索引查找)
- **事务/锁/外键**是否支持
- **崩溃恢复**机制

存储引擎是 MySQL **区别于其他数据库**的关键设计 —— 数据存取逻辑不耦合到 Server 层,通过统一接口对接。

### 2. 可插拔式架构 (Pluggable Architecture)

MySQL 采用**可插拔式存储引擎架构** (Pluggable Storage Engine Architecture),Server 层 (SQL 层) 通过**统一的 Handler API** 与底层引擎交互。

```text
┌──────────────────────────────────────────────────┐
│            Client/Application Layer              │
├──────────────────────────────────────────────────┤
│              MySQL Server Layer                  │
│  ┌────────────────────────────────────────────┐  │
│  │  连接器  →  查询缓存(8.0移除)  →  分析器   │  │
│  │       ↓                                    │  │
│  │  优化器(Optimizer)  →  执行器(Executor)   │  │
│  └────────────────────────────────────────────┘  │
│              ↓ Handler API ↓                     │
├──────────────────────────────────────────────────┤
│         Storage Engines (可插拔)                 │
│  ┌───────┐ ┌───────┐ ┌────────┐ ┌─────────────┐  │
│  │InnoDB │ │MyISAM │ │ Memory │ │  Archive    │  │
│  └───────┘ └───────┘ └────────┘ └─────────────┘  │
│  ┌───────┐ ┌───────────┐ ┌──────────────────┐    │
│  │ CSV   │ │ Blackhole │ │ Federated(MERGE) │    │
│  └───────┘ └───────────┘ └──────────────────┘    │
└──────────────────────────────────────────────────┘
```

**Server 层与引擎层职责划分**:

| 层级       | 职责                                                                |
|-----------|---------------------------------------------------------------------|
| **Server 层** | 连接管理、查询解析、优化、缓存、内置函数、视图、触发器、权限          |
| **引擎层**   | 数据存储/读取、索引实现、事务、锁、崩溃恢复、I/O                    |

**Handler API**(处理器接口):引擎向上层暴露的标准化操作集合:

- `handler::create()` / `drop()`
- `handler::open()` / `close()`
- `handler::write_row()` / `update_row()` / `delete_row()`
- `handler::index_read()` / `index_first()` / `index_next()`
- `handler::start_stmt()` / `external_lock()`

## 二、InnoDB 详解

**InnoDB** 是 MySQL 5.5 起的**默认存储引擎**,也是生产环境**唯一推荐**的引擎。它是为**事务处理 (OLTP)** 设计的完整 ACID 实现。

### 1. 核心特性

| 特性            | 说明                                                    |
|----------------|--------------------------------------------------------|
| **事务支持**    | 完整 ACID、MVCC、行级锁                                  |
| **锁粒度**    | 默认行锁,支持 GAP 锁、Next-Key Locks                    |
| **外键**      | 支持(FOREIGN KEY 约束)                                  |
| **崩溃恢复**  | Redo Log + Undo Log,自动故障恢复                        |
| **缓冲池**    | 内存缓存数据页、索引页                                   |
| **MVCC**      | 多版本并发控制,读写不阻塞                                |
| **聚簇索引**  | 数据按主键聚簇存储                                       |
| **在线热备**  | 支持 `ibbackup`/XtraBackup 物理热备                     |
| **压缩表**    | 支持透明页压缩 (Transparent Page Compression)           |
| **加密**      | 支持透明数据加密 (TDE, MySQL 5.7+)                     |

### 2. 体系结构

```text
                        MySQL Server
                             ↓ SQL
┌──────────────────────────────────────────────────────────────┐
│                     InnoDB 架构                               │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Memory Pool (内存池)                                  │  │
│  │  ┌──────────────┐ ┌──────────────┐ ┌────────────────┐  │  │
│  │  │ Buffer Pool  │ │  Log Buffer  │ │ Adaptive Hash  │  │  │
│  │  │  (缓冲池)    │ │  (日志缓冲)   │ │     Index      │  │  │
│  │  └──────────────┘ └──────────────┘ └────────────────┘  │  │
│  └────────────────────────────────────────────────────────┘  │
│                              ↓                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  后台线程 (Background Threads)                          │  │
│  │  Master Thread / IO Thread / Purge Thread / Page       │  │
│  │  Cleaner Thread / Redo Log Thread / Undo Log Thread   │  │
│  └────────────────────────────────────────────────────────┘  │
│                              ↓                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  磁盘文件 (Disk Files)                                  │  │
│  │  System Tablespace / User Tablespace / Redo Log        │  │
│  │  Undo Log / Binary Log (Server 层)                    │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**关键组件**:

- **Buffer Pool (缓冲池)**:缓存数据页和索引页,默认 128 MB,通过 `innodb_buffer_pool_size` 调整(生产建议设为物理内存的 60-80%)
- **Log Buffer (日志缓冲)**:写入 Redo Log 前先放这里,定时刷盘,大小 `innodb_log_buffer_size`
- **Adaptive Hash Index (AHI)**:InnoDB 自动为热点 B+Tree 页建立 Hash 索引,加速等值查询
- **后台线程**:Master Thread 负责脏页刷新、插入缓冲合并;IO Thread 负责异步 I/O

### 3. 表空间 (Tablespace)

表空间是 InnoDB 存储数据的**物理容器**,由**段 (Segment) → 区 (Extent, 1 MB) → 页 (Page, 16 KB) → 行 (Row)** 组成。

#### 3.1 物理存储层级

```text
Tablespace (表空间)
  └── Segment (段)             — 索引段、数据段、回滚段
        └── Extent (区, 1MB)   — 64 个连续页
              └── Page (页, 16KB) — 数据页、索引页、undo 页
                    └── Row (行)  — 实际记录
```

#### 3.2 表空间类型

| 类型              | 文件                                | 说明                                          |
|------------------|-------------------------------------|----------------------------------------------|
| **系统表空间**   | `ibdata1`(可多个)                   | 存数据字典(8.0前)、undo log、双写 buffer    |
| **独立表空间**   | `数据库名/表名.ibd`                | 每张表一个文件,**默认开启**(8.0)             |
| **通用表空间**   | 用户自定义 `.ibd` 文件              | 多张表共享一个表空间                          |
| **Undo 表空间**  | `undo_001`, `undo_002`            | MySQL 8.0 引入,undo log 单独存放              |
| **临时表空间**   | `ibtmp1`                          | 临时表存放                                    |

#### 3.3 系统表空间 vs 独立表空间

| 维度          | 系统表空间                  | 独立表空间(推荐)         |
|--------------|----------------------------|-------------------------|
| **存储位置**  | `datadir/ibdata1`           | `datadir/dbname/tbl.ibd` |
| **数据迁移**  | 困难,只能整体导出          | 简单,直接拷贝 `.ibd`    |
| **空间回收**  | 无法回收(共享)             | 可单独 OPTIMIZE TABLE   |
| **并发 I/O** | 集中,可能成为瓶颈          | 分散到多文件             |
| **默认**    | MySQL 5.7 默认             | MySQL 8.0 默认           |

```sql
-- 查看是否启用独立表空间
SHOW VARIABLES LIKE 'innodb_file_per_table';
-- +-----------------------+-------+
-- | Variable_name         | Value |
-- +-----------------------+-------+
-- | innodb_file_per_table | ON    |
-- +-----------------------+-------+

-- 通用表空间示例
CREATE TABLESPACE ts1 ADD DATAFILE 'ts1.ibd' ENGINE=InnoDB;

CREATE TABLE t1 (
    id INT PRIMARY KEY
) TABLESPACE ts1;
```

### 4. InnoDB 数据页结构

**页 (Page)** 是 InnoDB 磁盘管理的**最小单位**,默认大小 **16 KB**(可调整为 4K/8K/16K/32K/64K)。

#### 4.1 页结构总览

```text
┌────────────────────────────────────────────────────┐
│                    File Header (38 字节)           │
├────────────────────────────────────────────────────┤
│                    Page Header (56 字节)           │
├────────────────────────────────────────────────────┤
│              Infimum + Supremum (26 字节)           │
├────────────────────────────────────────────────────┤
│                                                    │
│              User Records (用户记录)                │
│                                                    │
│              [实际行数据,自由链表串联]              │
│                                                    │
├────────────────────────────────────────────────────┤
│              Free Space (空闲空间)                 │
│                                                    │
├────────────────────────────────────────────────────┤
│              Page Directory (页目录)                │
│              [槽位,二分查找定位记录]               │
├────────────────────────────────────────────────────┤
│                    File Trailer (8 字节)           │
└────────────────────────────────────────────────────┘
       总大小: 16 KB = 16384 字节
```

#### 4.2 File Header (文件头,38 字节)

**所有类型的页**都有 File Header,描述页的通用信息。

| 字段             | 字节 | 说明                                       |
|-----------------|------|-------------------------------------------|
| `FIL_PAGE_SPACE` | 4    | 表空间 ID                                  |
| `FIL_PAGE_OFFSET` | 4    | 页号(4字节 = 最多 2^32 页 = 64 TB)        |
| `FIL_PAGE_PREV` | 4    | 上一页(双向链表)                          |
| `FIL_PAGE_NEXT` | 4    | 下一页                                    |
| `FIL_PAGE_LSN`  | 8    | 最后修改的 LSN(Log Sequence Number)        |
| `FIL_PAGE_TYPE` | 2    | 页类型(数据页、索引页、undo 页、系统页)   |
| `FIL_PAGE_FILE_FLUSH_LSN` | 8 | 仅系统表空间第 0 页记录        |
| `FIL_PAGE_ARCH_LOG_NO` | 4 | 归档日志编号                       |

#### 4.3 Page Header (页头,56 字节)

**数据页**专有,记录页内状态。

| 字段                | 字节 | 说明                                          |
|--------------------|------|----------------------------------------------|
| `PAGE_N_DIR_SLOTS` | 2    | Page Directory 槽数量                         |
| `PAGE_HEAP_TOP`    | 2    | 堆顶指针(Free Space 起始)                    |
| `PAGE_N_HEAP`      | 2    | 堆中记录数(含 infimum/supremum)              |
| `PAGE_FREE`        | 2    | 空闲链表头指针                                 |
| `PAGE_GARBAGE`     | 2    | 已删除记录占用的字节数                        |
| `PAGE_LAST_INSERT` | 2    | 最后插入记录的位置                             |
| `PAGE_DIRECTION`   | 2    | 插入方向(连续递增/递减)                       |
| `PAGE_N_DIRECTION` | 2    | 同方向连续插入数量                             |
| `PAGE_MAX_TRX_ID`  | 8    | 修改该页的最大事务 ID                          |
| `PAGE_LEVEL`       | 2    | B+Tree 层级(叶子页=0)                         |
| `PAGE_INDEX_ID`    | 8    | 索引 ID                                       |

#### 4.4 Infimum + Supremum (26 字节)

**页内虚拟记录**,作为记录链表的**头尾边界**。

```text
┌─────────────┐    ┌─────────────┐
│  Infimum    │ →  │   ...       │ →  ...  →  ┌─────────────┐
│  (最小记录) │    │  User       │             │  Supremum   │
│  13 字节    │    │  Records    │             │ (最大记录)  │
└─────────────┘    └─────────────┘             │  13 字节    │
        ↑                                      └─────────────┘
        记录按主键升序链接                        ↑
                                            记录按主键升序链接
```

#### 4.5 User Records (用户记录)

存储**实际行数据**,每条记录格式:

```text
┌────────────┬────────────┬──────────┬─────────────┬───────────┬────────┐
│ 变长字段   │   NULL      │  记录头   │  隐藏列     │  列数据    │ 下一条  │
│ 长度列表   │   标志位    │ (5字节)  │ (DB_TRX_ID │  ...      │ 记录指针│
│ (可选)    │   (可选)    │          │ DB_ROLL_PTR │           │         │
│            │             │          │ DB_ROW_ID) │           │         │
└────────────┴─────────────┴──────────┴─────────────┴───────────┴────────┘
```

**记录头 (5 字节,40 位)**:

| 位       | 含义                                          |
|---------|----------------------------------------------|
| `预留位1/2` | 未使用                                       |
| `delete_flag` | 1 = 已删除(不立即从页删除)                |
| `min_rec_flag` | 1 = B+Tree 非叶子节点最小记录               |
| `n_owned` | 该记录拥有的 slot 数(用于 Page Directory)   |
| `heap_no` | 堆中位置(从 infimum=0 开始)                  |
| `record_type` | 0=普通,1=非叶子节点,2=Infimum,3=Supremum  |
| `next_record` | 相对下一条记录的字节偏移(16 位)            |

**隐藏列 (InnoDB 自动维护)**:

| 列            | 大小     | 说明                                       |
|--------------|---------|-------------------------------------------|
| `DB_ROW_ID`  | 6 字节 | 行 ID(无主键时自动生成)                   |
| `DB_TRX_ID`  | 6 字节 | 最后修改该行的事务 ID                       |
| `DB_ROLL_PTR`| 7 字节 | 回滚指针,指向 Undo Log 中的旧版本          |

#### 4.6 Free Space (空闲空间)

- 插入新记录时**优先使用已删除记录的空间**,其次使用 Free Space
- 删除记录会在记录头标记 `delete_flag=1`,**不立即物理删除**,Purge Thread 后续清理

#### 4.7 Page Directory (页目录)

- 用于**页内二分查找**,加速记录定位
- 每 **4-8 条记录**生成一个**槽 (slot)**
- 槽按主键顺序排列,infimum/supremum 强制为槽
- 查询时先在 slot 中二分定位,再在组内顺序找

#### 4.8 File Trailer (8 字节)

```text
┌─────────────────────────┬──────────────────────┐
│  FIL_PAGE_END_LSN(4字节) │  Checksum (4 字节)   │
│       部分 LSN            │  与 File Header 一致 │
└─────────────────────────┴──────────────────────┘
```

**作用**:页写入磁盘前先写 Header,写完后写 Trailer。**如果中间崩溃,Header 与 Trailer 的 LSN/Checksum 不一致,数据库恢复时会丢弃该页**。

### 5. 行格式 (Row Format)

行格式决定了**行数据在磁盘上的物理布局**,影响空间占用和性能。

#### 5.1 四种行格式

| 行格式        | 引入版本   | 特点                                    |
|--------------|-----------|----------------------------------------|
| **REDUNDANT** | 远古 MySQL | 老式,不推荐                             |
| **COMPACT**  | MySQL 5.0 | 紧凑,引入变长字段长度列表                |
| **DYNAMIC**  | MySQL 5.7 | 默认(8.0),处理超长字段用页外存储         |
| **COMPRESSED**| MySQL 5.7 | 在 DYNAMIC 基础上加页压缩                |

#### 5.2 COMPACT 行格式

```text
┌──────────────────────────────────────────────────────────┐
│ 变长字段长度列表  │ NULL 标志位  │  记录头  │  列1 │ 列2 │ ... │
│ (逆序存放)        │  (位图)      │ (5字节) │  数据 │  数据 │
└──────────────────────────────────────────────────────────┘
```

**完整行布局**:

```text
┌─────────────────┐
│ 变长字段长度列表 │  VARCHAR(n) 实际占用字节数,逆序排列
├─────────────────┤
│ NULL 标志位     │  每个可为 NULL 列占 1 bit
├─────────────────┤
│ 记录头信息      │  delete_flag / n_owned / heap_no /
│ (5 字节)        │  record_type / next_record
├─────────────────┤
│ 隐藏列          │  DB_ROW_ID (可选) / DB_TRX_ID / DB_ROLL_PTR
├─────────────────┤
│ 真实列数据      │  按列定义顺序
└─────────────────┘
```

#### 5.3 COMPACT vs DYNAMIC 关键差异

| 维度              | COMPACT                | DYNAMIC                       |
|------------------|------------------------|-------------------------------|
| **溢出页处理**    | 768 字节前缀 + 溢出页   | 整列溢出(20 字节指针)         |
| **大字段**        | 部分存储在页内          | 全部页外,页内只存指针          |
| **行长度上限**    | ~8 KB(实际更小)        | 4 GB(理论)                    |
| **空间利用率**    | 中                      | 高                            |

**溢出规则**:

- COMPACT:对于 `VARCHAR/TEXT/BLOB`,若行长度超过页大小的一半,前 768 字节放本页,其余放溢出页
- DYNAMIC:若行长度超过页大小的一半,**整个列**放到溢出页(页内只留 20 字节指针)

#### 5.4 行格式对比示例

**示例表**:

```sql
CREATE TABLE t_row_format (
    id INT PRIMARY KEY,
    name VARCHAR(20),
    info VARCHAR(100),
    note TEXT
) ROW_FORMAT = COMPACT;
```

假设 `info` 实际存 80 字节:

```text
COMPACT 行格式下:
┌──────┬──────┬─────────┬─────┬──────┬─────┬────────────────────┐
│ 变长 │ NULL │ 记录头   │ id  │ name │ info│ note               │
│ 长度 │ 标志 │ (5字节) │ 4B  │ 实际 │ 80B │ (如果超长→溢出页)  │
│ 列表 │ 位图 │          │     │ 字节 │     │                    │
└──────┴──────┴─────────┴─────┴──────┴─────┴────────────────────┘
长度列表: info=80, name=实际, note=实际或指针

DYNAMIC 行格式下:
┌──────┬──────┬─────────┬─────┬──────┬─────┬────────────────────┐
│ 变长 │ NULL │ 记录头   │ id  │ name │ info│ note               │
│ 长度 │ 标志 │ (5字节) │ 4B  │ 实际 │ 实际 │ 完整存溢出页      │
│ 列表 │ 位图 │          │     │ 字节 │ 字节 │ (页内只 20B 指针) │
└──────┴──────┴─────────┴─────┴──────┴─────┴────────────────────┘
```

#### 5.5 设置行格式

```sql
-- 创建时指定
CREATE TABLE t1 (...) ROW_FORMAT = DYNAMIC;

-- 修改
ALTER TABLE t1 ROW_FORMAT = COMPRESSED;

-- 查看
SHOW TABLE STATUS LIKE 't1'\G
-- 关注 Row_format 字段
```

**选择建议**:

- 大量 VARCHAR/TEXT/BLOB → **DYNAMIC**
- 需要压缩节省空间 → **COMPRESSED**
- 兼容老版本 → **COMPACT**
- **避免 REDUNDANT**

### 6. 数据页大小

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
-- +------------------+-------+
-- | Variable_name    | Value |
-- +------------------+-------+
-- | innodb_page_size | 16384 |
-- +------------------+-------+
```

| 页大小     | 适用场景                                 |
|----------|-----------------------------------------|
| 4 KB     | SSD 4K 对齐,小数据/小内存               |
| 8 KB     | 通用                                    |
| **16 KB** | **默认值,生产推荐**                     |
| 32 KB    | 大数据、压缩                             |
| 64 KB    | 大数据集(慎重,可能浪费)                 |

> **注意**:`innodb_page_size` 只能在**初始化**时设置,运行时不可修改。

### 7. InnoDB 关键参数

| 参数                              | 默认值    | 说明                            |
|-----------------------------------|----------|-------------------------------|
| `innodb_buffer_pool_size`        | 128M     | 缓冲池大小(主参数,生产 60-80% 内存) |
| `innodb_log_file_size`           | 48M      | Redo Log 文件大小              |
| `innodb_log_buffer_size`          | 16M      | 日志缓冲大小                   |
| `innodb_flush_log_at_trx_commit` | 1        | 刷盘策略(0/1/2)               |
| `innodb_file_per_table`           | ON (8.0) | 独立表空间                     |
| `innodb_flush_method`             | 空       | O_DIRECT / fsync              |
| `innodb_io_capacity`              | 200      | 后台 I/O 速率                  |
| `innodb_thread_concurrency`       | 0 (自动) | 并发线程数                     |

## 三、MyISAM 详解

**MyISAM** 是 MySQL 5.5 之前的默认引擎,以**速度快、占用小**著称,但**不支持事务**。

### 1. 核心特性

| 特性         | 说明                                  |
|-------------|---------------------------------------|
| **事务**    | 不支持                                 |
| **锁粒度**  | 表级锁(读共享、写独占)                 |
| **外键**    | 不支持                                 |
| **索引**    | B+Tree(可压缩)、支持全文索引(FullText) |
| **崩溃恢复**| 不支持(易损坏,需 myisamchk 修复)      |
| **数据压缩**| 支持 `myisampack` 工具                  |
| **计数器**  | 内置 `COUNT(*)` 优化(单独存行数)       |

### 2. 物理文件结构

MyISAM 每张表对应**3 个文件**:

```text
数据库目录/
├── t_user.frm    # 表结构 (Format)
├── t_user.MYD    # 数据文件 (MYData)
└── t_user.MYI    # 索引文件 (MYIndex)
```

| 文件       | 内容                                |
|-----------|------------------------------------|
| `.frm`     | 表结构定义(MySQL 8.0 已移到数据字典) |
| `.MYD`     | 实际数据行                          |
| `.MYI`     | 索引数据(B+Tree)                    |

> MySQL 8.0 起 `.frm` 文件被废除,元数据统一存储在**数据字典** (mysql.ibd) 中。

### 3. 行格式

| 行格式      | 说明                                        |
|------------|--------------------------------------------|
| **FIXED** (静态) | 每行固定长度,CHAR 自动空格填充              |
| **DYNAMIC** (动态) | 变长记录,空间利用率高,但恢复复杂          |
| **COMPRESSED** (压缩) | `myisampack` 压缩后,只读               |

```sql
-- 查看表的行格式
SHOW TABLE STATUS LIKE 't_user'\G
-- Row_format: Dynamic

-- 设置
CREATE TABLE t (id INT, name CHAR(10)) ROW_FORMAT = FIXED;
```

### 4. 索引结构

- **B+Tree 索引**:`.MYI` 文件中存储,数据指针指向 `.MYD` 中的行偏移
- **全文索引 (FullText)**:MyISAM 原生支持,InnoDB 5.6+ 才支持
- **空间索引 (R-Tree)**:MyISAM 支持,InnoDB 不支持

### 5. 并发与锁

- **读操作**:共享锁(S Lock),多个读可并发
- **写操作**:独占锁(X Lock),阻塞所有读写
- **插入/读取速度**:读快,但并发写差

```sql
-- MyISAM 的并发插入
SET GLOBAL concurrent_insert = 2;
-- 0:不允许
-- 1:表无空洞时允许(默认)
-- 2:始终允许(尾插)
```

### 6. 计数器优化

MyISAM 的 `SELECT COUNT(*) FROM table` 是 **O(1)** 操作,因为表元数据中维护了一个**行数计数器**,但有代价:

- `INSERT/DELETE` 会更新计数器,需要锁保护
- `WHERE` 条件下的 `COUNT(*)` 仍是全表扫描

```sql
SELECT COUNT(*) FROM t_myisam;  -- 直接读元数据
-- 性能远高于 InnoDB
```

### 7. myisamchk 修复工具

```bash
# 检查
myisamchk -c /var/lib/mysql/dbname/t_user.MYI

# 恢复
myisamchk -r /var/lib/mysql/dbname/t_user.MYI

# 强制恢复(可能丢数据)
myisamchk -o /var/lib/mysql/dbname/t_user.MYI
```

> MySQL 8.0 起 `myisamchk` 仍可用,但 MyISAM 已不是默认引擎。

## 四、Memory 引擎

**Memory 引擎**(早期叫 HEAP)将数据**存储在内存中**,速度极快,但**重启即失**。

### 1. 核心特性

| 特性         | 说明                                  |
|-------------|---------------------------------------|
| **存储位置** | 内存(不写盘)                          |
| **持久性**  | 重启丢失                              |
| **索引**    | 默认 **HASH 索引**(也支持 B+Tree)      |
| **锁粒度**  | 表级锁                                |
| **事务**    | 不支持                                |
| **并发**    | 读共享/写独占,写阻塞读                  |
| **数据行上限** | `max_heap_table_size`(默认 16MB)    |

### 2. 适用场景

- **临时表**:复杂查询的中间结果(`GROUP BY`、`ORDER BY`)
- **缓存表**:字典表、配置表、热点小数据
- **会话级数据**:临时聚合数据

```sql
CREATE TABLE t_session (
    id INT PRIMARY KEY,
    data VARCHAR(100)
) ENGINE = MEMORY;

-- 内存表大小
SHOW VARIABLES LIKE 'max_heap_table_size';
```

### 3. Hash 索引 vs B+Tree

```sql
-- 显式指定 B+Tree
CREATE TABLE t_btree (
    id INT,
    INDEX USING BTREE (id)
) ENGINE = MEMORY;
```

| 维度       | HASH                      | B+Tree                    |
|-----------|---------------------------|---------------------------|
| **等值查询** | O(1),极快                  | O(log N)                  |
| **范围查询** | 不支持                     | 支持                      |
| **排序**    | 不支持 ORDER BY 利用索引   | 支持                      |
| **LIKE**   | 'abc%' 不走索引            | 'abc%' 可走                |

### 4. 与临时表的区别

MySQL 在以下场景会自动用 Memory 引擎建临时表:

```sql
-- ORDER BY 与 GROUP BY 字段不一致
SELECT * FROM t GROUP BY a ORDER BY b;

-- DISTINCT + ORDER BY
SELECT DISTINCT a FROM t ORDER BY b;

-- UNION
SELECT ... UNION SELECT ...;
```

**临时表配置**:

```sql
SHOW VARIABLES LIKE 'tmp_table_size';        -- 内存临时表阈值
SHOW VARIABLES LIKE 'max_heap_table_size';   -- 单表上限
-- 临时表超过 tmp_table_size → 转磁盘(MyISAM)
```

## 五、Archive 引擎

**Archive 引擎**专为**海量归档数据**(日志、历史)设计,数据写入后**只允许查询,不能修改**。

### 1. 核心特性

| 特性            | 说明                            |
|----------------|--------------------------------|
| **支持的 DML** | 仅 `INSERT` 和 `SELECT`         |
| **压缩**       | 高压缩比(`zlib` 压缩)            |
| **行级锁**     | `INSERT` 用行锁,`SELECT` 高并发 |
| **索引**       | **不支持索引**(只能全表扫描)     |
| **事务**       | 不支持                          |
| **空间占用**   | 比 MyISAM 小 50-80%             |

### 2. 典型场景

- 审计日志(只追加)
- 历史订单、消息存档
- 不需要查询但要长期保存的数据

```sql
CREATE TABLE t_log_archive (
    id INT AUTO_INCREMENT PRIMARY KEY,
    log_time DATETIME,
    content TEXT
) ENGINE = ARCHIVE;
```

### 3. 限制

- 不支持 `DELETE`、`UPDATE`
- 不支持索引 → 大表查询很慢
- 压缩后无法修改 → 适合**只写不改**的场景

## 六、CSV 引擎

**CSV 引擎**将数据**以 CSV 格式存储到文件系统**,本质是文本文件。

### 1. 核心特性

| 特性         | 说明                              |
|-------------|----------------------------------|
| **存储格式** | 纯文本 CSV,逗号分隔                |
| **可读性**   | 任何文本编辑器可看                  |
| **索引**     | 不支持                            |
| **事务**     | 不支持                            |
| **锁粒度**   | 表锁                              |
| **数据交换** | 完美(Excel / 脚本可直接读)         |

### 2. 物理文件

```text
t_csv.CSV    # 数据文件(逗号分隔)
t_csv.CSM    # 表元数据(列数、状态)
t_csv.frm    # 表结构(MySQL 8.0 移除)
```

```sql
CREATE TABLE t_csv (
    id INT NOT NULL,
    name CHAR(20) NOT NULL
) ENGINE = CSV;
```

```bash
cat /var/lib/mysql/dbname/t_csv.CSV
# 1,"Alice"
# 2,"Bob"
# 3,"Charlie"
```

### 3. 典型用法

- 数据交换中转(数据库 ↔ Excel/脚本)
- 数据导入/导出测试
- 注意:**NULL** 用 `\N` 表示,**不需要引号**

## 七、Blackhole 引擎

**Blackhole 引擎**(黑洞)写入数据**立即丢弃**,查询永远返回空。看似无用,实则在特定场景大放异彩。

### 1. 核心特性

| 特性      | 说明                          |
|----------|------------------------------|
| **写入** | 接收写入,立即返回成功,但不存盘   |
| **读取** | 永远返回空集                   |
| **Binlog** | 写入会记 Binlog(关键!)        |
| **用途** | **复制中继**、性能测试、过滤    |

### 2. 典型场景

#### 2.1 主从复制中的过滤

```sql
-- 主库上创建 Blackhole 中转表,避免写入开销
CREATE TABLE t_filter (
    id INT PRIMARY KEY,
    data TEXT
) ENGINE = BLACKHOLE;
```

#### 2.2 复制过滤

```sql
-- 主从复制中,部分表只想复制 SQL,不复制数据
-- 1. 主库建 Blackhole 表
CREATE TABLE t_only_ddl (id INT) ENGINE = BLACKHOLE;

-- 2. DDL 在主库执行
ALTER TABLE t_only_ddl ADD COLUMN name VARCHAR(50);

-- 3. Binlog 记录 DDL,从库回放
-- 4. 主库上不浪费存储,从库得到结构
```

#### 2.3 性能基准测试

```sql
-- 测试 Binlog 写入性能(无数据存储开销)
SET SESSION binlog_format = ROW;
INSERT INTO t_benchmark (data) VALUES ('x');  -- 极快
```

## 八、Federated 引擎

**Federated 引擎**允许**访问远程 MySQL 服务器上的表**,对本地应用透明,像本地表一样查询。

### 1. 核心特性

| 特性       | 说明                                |
|-----------|------------------------------------|
| **存储**   | 本地无数据,数据全在远程              |
| **访问方式** | 通过 `mysql://user@host:port/db/table`  |
| **索引**   | **本地不存储索引**,所有查询发往远程   |
| **事务**   | 受远程引擎支持,本地不参与            |
| **限制**   | MySQL 8.0 默认未编译,需显式启用      |

### 2. 配置启用

```bash
# 启动时加载
mysqld --federated
```

或运行时:

```ini
# my.cnf
[mysqld]
federated = ON
```

### 3. 使用示例

```sql
-- 创建本地 Federated 表,指向远程表
CREATE TABLE t_remote_user (
    id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(100)
) ENGINE = FEDERATED
CONNECTION = 'mysql://user:pass@192.168.1.100:3306/mydb/users';

-- 像本地表一样查询
SELECT * FROM t_remote_user WHERE id = 1;
```

### 4. 适用场景

- 跨服务器数据聚合(分库分表后汇总)
- 数据迁移过渡期
- 不推荐生产大规模使用(网络延迟、单点)

## 十、修改默认存储引擎

### 1. 表级别指定

```sql
CREATE TABLE t_myisam (
    id INT PRIMARY KEY
) ENGINE = MyISAM;

ALTER TABLE t_innodb ENGINE = MyISAM;  -- 转换(实际是重建表)
```

### 2. 会话级别

```sql
SET SESSION default_storage_engine = MyISAM;
CREATE TABLE t1 (id INT);  -- t1 是 MyISAM
```

### 3. 全局级别(运行时)

```sql
SET GLOBAL default_storage_engine = MyISAM;
-- 注:仅对新连接生效,重启后失效
```

### 4. 配置文件永久生效

```ini
# /etc/my.cnf
[mysqld]
default_storage_engine = InnoDB
```

### 5. 引擎转换

```sql
-- InnoDB → MyISAM
ALTER TABLE t1 ENGINE = MyISAM;

-- MyISAM → InnoDB
ALTER TABLE t1 ENGINE = InnoDB;
```

**注意事项**:

- 转换过程会**锁表**(对于大表用 `pt-online-schema-change`)
- 5.7+ 可使用 `ALGORITHM=INPLACE, LOCK=NONE` 部分在线 DDL
- MyISAM → InnoDB 时,**外键**会自动校验,确保数据一致性

## 十一、引擎选择最佳实践

### 1. 选型决策树

```text
                     需要事务?
                  /            \
                Yes             No
                ↓                ↓
         需要外键?         数据量大只追加?
        /         \             ↓
      Yes          No         Yes → Archive
       ↓            ↓
    InnoDB    读多写少?
                /     \
              Yes       No
               ↓        ↓
            MyISAM   临时数据?
             ↓         ↓
        全文索引?    Yes → Memory
        /       \        ↓
      Yes       No    会话级数据
       ↓        ↓        ↓
    MyISAM   跨服务器?
             ↓
          Yes → Federated
```

### 2. 选型速查表

| 业务场景                       | 推荐引擎           | 原因                          |
|------------------------------|------------------|------------------------------|
| **OLTP 业务系统**              | InnoDB           | 事务、行锁、并发、外键         |
| **数据仓库/日志**              | InnoDB (压缩) 或 Archive | 写入频率高,Archive 只追加     |
| **临时中间结果**               | Memory           | 极快,自动释放                  |
| **静态字典表**                | Memory           | 启动时加载,极快                |
| **读写分离从库**              | InnoDB           | 与主库一致                     |
| **历史订单(只读)**           | MyISAM (压缩)    | 占用小,读快                    |
| **数据中转**                  | CSV              | 与 Excel/脚本交换               |
| **复制过滤/中转**            | Blackhole        | 避免存储开销                   |
| **跨库聚合**                  | Federated        | 透明访问远程表                 |

### 3. 生产环境建议

1. **统一使用 InnoDB**:MySQL 8.0 默认,功能最全,管理工具最完善
2. **禁用 MyISAM**:除非有特定需求(全文索引在 5.6 之前)
4. **Memory 限制大小**:避免单表占用过多内存
5. **Archive 仅作归档**:业务主表不用
6. **避免混合引擎**:同一库尽量用同一种引擎,减少管理复杂度

```sql
-- 生产库批量查看引擎
SELECT TABLE_SCHEMA, TABLE_NAME, ENGINE, TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA NOT IN ('mysql','sys','performance_schema','information_schema')
ORDER BY ENGINE, TABLE_SCHEMA;
```

## 十二、MySQL 8.0 的新特性

MySQL 8.0 在存储引擎和元数据管理方面有**重大变化**,尤其是**数据字典**和**原子 DDL**。

### 1. 数据字典 (Data Dictionary)

#### 1.1 5.7 vs 8.0 对比

| 维度            | MySQL 5.7                          | MySQL 8.0                  |
|----------------|------------------------------------|---------------------------|
| **元数据存储**  | `.frm` 文件 + 系统表(MYISAM)      | **数据字典**(InnoDB 表)    |
| **元数据表类型**| MyISAM(无事务)                    | InnoDB(事务一致)           |
| **元数据访问**  | 文件系统 + 内部表                  | 统一的 SQL 接口            |
| **崩溃一致性** | 元数据可能不一致                   | 强一致(InnoDB 事务保护)    |

#### 1.2 数据字典架构

```text
┌──────────────────────────────────────────┐
│           Server Layer (SQL Layer)        │
├──────────────────────────────────────────┤
│           Data Dictionary API             │
├──────────────────────────────────────────┤
│   ┌──────────────────────────────────┐   │
│   │   System Tables (mysql.*)        │   │
│   │   - tables                        │   │
│   │   - columns                       │   │
│   │   - indexes                       │   │
│   │   - tablespaces                   │   │
│   │   - ...(所有元数据)              │   │
│   └──────────────────────────────────┘   │
│         ↓ 存储于 InnoDB 系统表空间        │
└──────────────────────────────────────────┘
```

#### 1.3 优点

- **元数据事务一致**:DDL 与 DML 共享同一事务模型
- **崩溃安全**:系统表 InnoDB 化,自动恢复
- **统一访问**:所有元数据走 SQL 接口,无需解析文件
- **`.frm` 文件废弃**:简化文件管理

### 2. 原子 DDL (Atomic DDL)

**MySQL 8.0 引入原子 DDL**:DDL 操作要么**完整提交**,要么**完整回滚**,**不会留下部分状态**。

#### 2.1 受支持的 DDL

| DDL 类型       | 是否原子 | 说明                       |
|---------------|---------|---------------------------|
| CREATE TABLE  | ✔       |                          |
| DROP TABLE    | ✔       | 含多个表的事务             |
| ALTER TABLE   | ✔       |                          |
| CREATE INDEX  | ✔       |                          |
| DROP INDEX    | ✔       |                          |
| TRUNCATE TABLE | ✔      |                          |
| RENAME TABLE  | ✔       |                          |

#### 2.2 实现原理

```text
DDL 操作过程中:
  1. 记录到数据字典(事务)
  2. 操作存储引擎层文件
  3. 写 Binlog
  ↓
COMMIT → 全部生效
ROLLBACK → 完全回滚(文件状态、字典状态、binlog 全部撤销)
```

**关键点**:DDL 与数据字典修改处于**同一事务**,文件操作通过 InnoDB Redo Log 保证崩溃恢复。

#### 2.3 实战示例

```sql
-- MySQL 5.7:崩溃后可能残留临时文件、临时表、数据字典不一致
-- MySQL 8.0:完全原子

CREATE TABLE t1 (id INT);    -- 成功
DROP TABLE t1;               -- 原子
-- 中途崩溃:不会留下任何中间状态
```

## 十三、核心要点速记

### 1. 引擎速记

- **InnoDB**:MySQL 默认、唯一推荐、支持事务、行锁、MVCC、外键、聚簇索引
- **MyISAM**:表锁、不支持事务、`COUNT(*)` O(1)、`.frm` + `.MYD` + `.MYI`
- **Memory**:内存、HASH 索引、重启丢失、临时表
- **Archive**:只追加、高压缩、不支持索引
- **CSV**:纯文本、可被 Excel/脚本读取
- **Blackhole**:写入丢弃、用于复制过滤
- **Federated**:访问远程表、8.0 默认未编译

### 2. InnoDB 关键点

- **数据页 16 KB**:`innodb_page_size`
- **页结构**:File Header → Page Header → Infimum → User Records → Free Space → Page Directory → File Trailer
- **行格式**:COMPACT(5.0+)/DYNAMIC(5.7+,默认)/COMPRESSED(压缩)
- **隐藏列**:DB_TRX_ID / DB_ROLL_PTR / DB_ROW_ID(无主键时)
- **独立表空间**:每表一个 `.ibd` 文件(8.0 默认)

### 3. MySQL 8.0 关键变化

- **数据字典**:元数据存 InnoDB 系统表,`.frm` 废弃
- **原子 DDL**:DDL 完整提交或完整回滚
- **InnoDB 默认编码**:`utf8mb4`

### 4. 选型口诀

- OLTP → InnoDB
- 只读归档 → Archive
- 临时中间 → Memory
- 数据交换 → CSV
- 复制过滤 → Blackhole
- 跨库访问 → Federated
- **不要用 MyISAM**

### 5. 性能关键参数

```sql
innodb_buffer_pool_size = 物理内存 * 0.7
innodb_log_file_size = 2-4 GB (8.0)
innodb_flush_log_at_trx_commit = 1 (强持久)/ 2 (折中)
innodb_file_per_table = ON
default_storage_engine = InnoDB
```

### 6. 排查命令

```sql
SHOW ENGINES;                              -- 引擎列表
SHOW VARIABLES LIKE 'default%engine%';     -- 默认引擎
SHOW TABLE STATUS LIKE 't%';              -- 表引擎
SHOW ENGINE INNODB STATUS\G                -- InnoDB 详细状态
SELECT * FROM information_schema.ENGINES;  -- 引擎元数据
```
