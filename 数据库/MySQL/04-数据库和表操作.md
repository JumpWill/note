# 数据库和表操作 (Database & Table Operations)

> 本章覆盖 MySQL 中最核心的 DDL(Data Definition Language)操作:数据库的创建/删除、字符集配置、表的完整定义、约束、AUTO_INCREMENT 自增、ALTER TABLE 修改、分区表,以及典型业务表的设计示例。

---

## 一、数据库操作

### 1. CREATE DATABASE

```sql
-- 最简形式
CREATE DATABASE mydb;

-- 完整形式(推荐生产使用)
CREATE DATABASE IF NOT EXISTS mydb
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_unicode_ci;
```

**关键选项**:

| 选项 | 说明 |
|------|------|
| `IF NOT EXISTS` | 库已存在时不报错 |
| `DEFAULT CHARACTER SET` | 默认字符集 |
| `DEFAULT COLLATE` | 默认排序规则 |

### 2. SHOW DATABASES

```sql
SHOW DATABASES;           -- 所有库
SHOW DATABASES LIKE 'my%'; -- 模糊匹配
```

### 3. ALTER DATABASE

```sql
-- 修改库的默认字符集
ALTER DATABASE mydb
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_bin;
```

### 4. DROP DATABASE

```sql
DROP DATABASE mydb;                -- 直接删除
DROP DATABASE IF EXISTS mydb;      -- 存在才删(推荐)
```

> **警告**:DROP DATABASE 会**删除库中所有表**,且不可恢复,生产环境务必备份后再执行。

### 5. 切换数据库

```sql
USE mydb;                -- 切换当前库
SELECT DATABASE();       -- 查看当前所在库
```

## 二、字符集和排序规则

字符集决定了"如何存储字符",排序规则决定了"如何比较字符"。**MySQL 5.7 起推荐统一使用 `utf8mb4`**,因为 MySQL 的 `utf8` 只支持最多 3 字节,无法存储 emoji 表情和部分汉字。

### 1. MySQL 字符集层级

```
MySQL Server (character_set_server)
    └── Database (character_set_database)
            └── Table (character_set)
                    └── Column (character_set)
```

**就近原则**:列级 > 表级 > 库级 > 服务器级。

### 2. 查看字符集

```sql
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';

-- 查看所有可用字符集
SHOW CHARACTER SET;

-- 查看所有排序规则
SHOW COLLATION WHERE Charset = 'utf8mb4';
```

### 3. 常见字符集对比

| 字符集     | 最大字节 | 支持范围                       | 推荐度     |
|------------|----------|--------------------------------|------------|
| `latin1`   | 1        | 西欧字符                       | 不推荐     |
| `gbk`      | 2        | 简体中文                       | 遗留系统   |
| `utf8`     | 3        | 基本 BMP 平面(无 emoji)       | **不推荐** |
| `utf8mb4`  | 4        | 完整 Unicode(含 emoji)        | **强烈推荐** |

### 4. 常见排序规则对比

| 排序规则              | 特点                                  |
|-----------------------|---------------------------------------|
| `utf8mb4_general_ci`  | 速度快,但排序不太精确(不区分大小写)  |
| `utf8mb4_unicode_ci`  | 基于 Unicode 标准,精确但稍慢(推荐)   |
| `utf8mb4_bin`         | 区分大小写、字节级精确比较            |
| `utf8mb4_0900_ai_ci`  | MySQL 8.0 默认,基于 UCA 9.0         |

**命名解读**:

- `_ci`:Case Insensitive(不区分大小写)
- `_cs`:Case Sensitive(区分大小写)
- `_bin`:Binary(字节比较)
- `_ai`:Accent Insensitive(不区分音调)
- `_as`:Accent Sensitive(区分音调)

### 5. 创建时指定

```sql
-- 库级
CREATE DATABASE mydb
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_unicode_ci;

-- 表级
CREATE TABLE t (
    id INT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 列级
CREATE TABLE t (
    name VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin
);
```

### 6. 客户端连接字符集

```sql
SET NAMES utf8mb4;
-- 等价于同时设置下面 3 个
SET character_set_client = utf8mb4;
SET character_set_results = utf8mb4;
SET character_set_connection = utf8mb4;
```

> **生产建议**:服务端、库、表、客户端连接全部统一为 `utf8mb4`,避免"数据看起来乱码"。

## 三、表的创建(CREATE TABLE)

### 1. 完整语法骨架

```sql
CREATE TABLE [IF NOT EXISTS] table_name (
    column1 datatype [column_constraints],
    column2 datatype [column_constraints],
    ...
    [table_constraints]
)
ENGINE = InnoDB
DEFAULT CHARACTER SET = utf8mb4
COLLATE = utf8mb4_unicode_ci
COMMENT = '表注释'
AUTO_INCREMENT = 1;
```

### 2. 完整示例

```sql
CREATE TABLE IF NOT EXISTS users (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
                 COMMENT '用户ID',
    username      VARCHAR(50)     NOT NULL
                 COMMENT '用户名',
    email         VARCHAR(100)    NOT NULL
                 COMMENT '邮箱',
    password_hash CHAR(64)        NOT NULL
                 COMMENT '密码哈希(SHA-256)',
    age           TINYINT UNSIGNED DEFAULT 0
                 COMMENT '年龄',
    status        TINYINT         NOT NULL DEFAULT 1
                 COMMENT '状态:0-禁用 1-正常',
    bio           TEXT            NULL
                 COMMENT '个人简介',
    created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
                 COMMENT '创建时间',
    updated_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
                 ON UPDATE CURRENT_TIMESTAMP
                 COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    UNIQUE KEY uk_email (email),
    KEY idx_status_created (status, created_at)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci
  COMMENT='用户表'
  AUTO_INCREMENT=1000;
```

### 3. 存储引擎选择

| 引擎    | 事务 | 行锁 | 外键 | 适用场景                       |
|---------|------|------|------|--------------------------------|
| InnoDB  | 支持 | 支持 | 支持 | **默认**,OLTP、事务、高并发    |
| MyISAM  | 不支持 | 表锁 | 不支持 | 只读/报表、读多写少(已不推荐) |
| MEMORY  | 不支持 | 表锁 | 不支持 | 临时表、缓存(重启丢失)        |
| CSV     | 不支持 | 表锁 | 不支持 | 数据交换、导入导出             |
| ARCHIVE | 不支持 | 行锁 | 不支持 | 日志归档(只支持 INSERT/SELECT) |

> MySQL 5.5 之后默认引擎就是 InnoDB,生产环境**统一使用 InnoDB**。

### 4. 常用数据类型速查

#### 数值类型

| 类型           | 存储       | 范围(有符号)                          |
|----------------|------------|---------------------------------------|
| `TINYINT`      | 1 字节     | -128 ~ 127                            |
| `SMALLINT`     | 2 字节     | -32768 ~ 32767                        |
| `MEDIUMINT`    | 3 字节     | -8388608 ~ 8388607                    |
| `INT`          | 4 字节     | -2147483648 ~ 2147483647              |
| `BIGINT`       | 8 字节     | -2^63 ~ 2^63-1                        |
| `FLOAT`        | 4 字节     | 单精度浮点                            |
| `DOUBLE`       | 8 字节     | 双精度浮点                            |
| `DECIMAL(M,D)` | 变长       | 精确小数,适合金额                    |

#### 字符串类型

| 类型           | 最大长度        | 特点                          |
|----------------|-----------------|-------------------------------|
| `CHAR(N)`      | 255 字符        | 定长,尾部空格会被截断         |
| `VARCHAR(N)`   | 65535 字节      | 变长,实际长度 + 1~2 字节前缀 |
| `TINYTEXT`     | 255 字节        | 小文本                        |
| `TEXT`         | 65535 字节      | 长文本                        |
| `MEDIUMTEXT`   | 16 MB           | 中等文本                      |
| `LONGTEXT`     | 4 GB            | 超大文本                      |
| `BINARY(N)`    | 255 字节        | 定长二进制                    |
| `VARBINARY(N)` | 65535 字节      | 变长二进制                    |
| `BLOB`         | 65535 字节      | 二进制大对象                  |

> **CHAR vs VARCHAR**:`CHAR(10)` 存 'abc' 占 10 字节,`VARCHAR(10)` 存 'abc' 占 3+1 字节。定长数据(如 MD5、手机号)用 CHAR,变长数据(如姓名)用 VARCHAR。

#### 日期时间类型

| 类型        | 存储     | 范围                          |
|-------------|----------|-------------------------------|
| `DATE`      | 3 字节   | 1000-01-01 ~ 9999-12-31       |
| `TIME`      | 3 字节   | -838:59:59 ~ 838:59:59        |
| `DATETIME`  | 8 字节   | 1000-01-01 ~ 9999-12-31       |
| `TIMESTAMP` | 4 字节   | 1970-01-01 ~ 2038-01-19(UTC)  |
| `YEAR`      | 1 字节   | 1901 ~ 2155                   |

> **DATETIME vs TIMESTAMP**:`TIMESTAMP` 受时区影响(存为 UTC),2038 年问题;`DATETIME` 不受时区影响,推荐用 `DATETIME`。

## 四、列定义详解

### 1. NULL vs NOT NULL

```sql
name VARCHAR(50) NOT NULL        -- 必须有值
nickname VARCHAR(50) NULL         -- 可空(默认就是 NULL)
score INT NULL DEFAULT 0          -- 可空,默认 0
```

**为什么尽量用 NOT NULL**:

- NULL 在索引中需要额外标记,占用更多空间
- 含 NULL 的列做统计、比较(=`NULL` 是未定义的,必须用 `IS NULL`)
- 业务上"无值"往往意味着默认值(0、空字符串、'1970-01-01'),不是真正的未知

### 2. DEFAULT 默认值

```sql
status TINYINT NOT NULL DEFAULT 1          -- 数字默认
name VARCHAR(50) DEFAULT 'anonymous'       -- 字符串默认
created_at DATETIME DEFAULT CURRENT_TIMESTAMP  -- 当前时间
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**默认值生效条件**:

- INSERT 时未指定该列
- 严格 SQL 模式下,NOT NULL 列必须显式给值或带 DEFAULT

### 3. COMMENT 注释

```sql
-- 列注释
email VARCHAR(100) COMMENT '用户邮箱'

-- 查看注释
SHOW FULL COLUMNS FROM users;
SHOW CREATE TABLE users\G
```

> 注释非常重要,一年后回头看代码,DBA 接手,全靠注释理解字段含义。

### 4. ON UPDATE CURRENT_TIMESTAMP

```sql
updated_at DATETIME NOT NULL
    DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP
```

- INSERT 时:自动填当前时间
- UPDATE 时:**任何列变更**,该列自动更新到当前时间
- 一个表**最多只能有 1 列**带 `ON UPDATE CURRENT_TIMESTAMP`(TIMESTAMP/DATETIME)

### 5. 字符集与排序规则(列级)

```sql
username VARCHAR(50)
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_bin     -- 用户名区分大小写
```

## 五、约束(Constraints)

### 1. 主键 PRIMARY KEY

```sql
-- 列内定义
id BIGINT UNSIGNED NOT NULL PRIMARY KEY AUTO_INCREMENT

-- 表级定义(推荐,可指定复合主键)
PRIMARY KEY (id)
PRIMARY KEY (order_id, product_id)  -- 复合主键
```

**主键的特征**:

- **唯一且非空**
- **每张表只能有 1 个**
- InnoDB 主键就是**聚簇索引**(数据按主键物理存储),主键选择直接决定性能

**主键设计原则**:

- 稳定不变(不被业务修改)
- 尽量短(主键索引会出现在所有二级索引叶子节点)
- 推荐:**自增 BIGINT**、雪花算法(Snowflake)、UUIDv7(有序 UUID)

### 2. 唯一键 UNIQUE KEY

```sql
-- 列内定义
email VARCHAR(100) NOT NULL UNIQUE

-- 表级定义(可命名,推荐)
UNIQUE KEY uk_email (email)
UNIQUE KEY uk_username (username)
UNIQUE KEY uk_phone (country_code, phone)  -- 复合唯一
```

**与主键的区别**:

| 维度         | PRIMARY KEY                | UNIQUE KEY                  |
|--------------|----------------------------|-----------------------------|
| 数量         | 1 个                       | 多个                        |
| 是否可空     | 否                         | 是(但 NULL 允许重复)        |
| 是否聚簇索引 | 是(InnoDB)                | 否(普通二级索引)           |
| 用途         | 物理存储顺序、关联外键     | 业务唯一性                  |

### 3. 外键 FOREIGN KEY

```sql
CREATE TABLE orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE RESTRICT      -- 父表删除时限制
        ON UPDATE CASCADE       -- 父表更新时级联
) ENGINE=InnoDB;
```

**参照动作**:

| 动作              | 说明                                       |
|-------------------|--------------------------------------------|
| `CASCADE`         | 父表操作级联到子表                         |
| `SET NULL`        | 子表对应列设为 NULL(必须子表列允许 NULL) |
| `RESTRICT`        | 拒绝操作(默认行为)                       |
| `NO ACTION`       | 同 RESTRICT,标准 SQL                      |

**外键争议**:

- **优点**:保证引用完整性、数据一致
- **缺点**:每次 INSERT/UPDATE/DELETE 都检查外键,影响性能;分库分表后无法使用
- **生产建议**:互联网大厂通常**不用外键**,由应用层保证一致性;小型项目、教学示例用外键方便

### 4. 检查约束 CHECK(MySQL 8.0+)

```sql
CREATE TABLE product (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    price DECIMAL(10,2) NOT NULL CHECK (price >= 0),
    stock INT NOT NULL CHECK (stock >= 0),
    status CHAR(1) NOT NULL CHECK (status IN ('A','B','C'))
);
```

> MySQL 5.7 只解析不生效,8.0+ 才真正强制。

### 5. 索引 KEY/INDEX(详见索引章节)

```sql
KEY idx_status (status)
INDEX idx_user_status (user_id, status)
```

## 六、AUTO_INCREMENT 自增

### 1. 基本用法

```sql
CREATE TABLE t (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50)
);

-- 表选项指定初始值
CREATE TABLE t (...) AUTO_INCREMENT = 1000;

-- 改初始值
ALTER TABLE t AUTO_INCREMENT = 5000;
```

### 2. AUTO_INCREMENT 的存储位置

| MySQL 版本 | 存储位置                                |
|------------|------------------------------------------|
| 5.7 及之前 | 内存中,重启后可能丢失                   |
| **8.0+**   | 持久化到 redo log,重启不丢              |

**8.0 之前的经典 bug**:

```sql
-- 现象:DELETE 一些行后,重启 MySQL,自增值可能回到更小的值
-- 例:id 最大 1000,DELETE 800-1000,重启后 AUTO_INCREMENT 可能仍是 1001
```

MySQL 8.0 将当前最大自增值持久化到 redo log,**每次变更都会写盘**,彻底解决。

### 3. AUTO_INCREMENT 锁机制

#### 早期(< 5.7):表级锁

```sql
-- innodb_autoinc_lock_mode = 0 或 1
INSERT 时会加 AUTO-INC 表锁,等语句结束才释放
高并发 INSERT 性能差
```

#### 现在(默认):轻量级互斥锁

```sql
-- innodb_autoinc_lock_mode = 2(默认,8.0 推荐)
INSERT 时分配自增值极快,几乎无锁
但可能导致主从切换时自增 ID 不一致(Statement 格式 binlog)
```

**三种模式**:

| 模式 | 锁粒度             | 性能 | 主从一致性 |
|------|--------------------|------|------------|
| 0    | 传统表锁           | 差   | 一致       |
| 1    | 轻量锁(默认 5.7)  | 中   | 一致       |
| 2    | 无锁交错          | 最好 | 可能不一致 |

### 4. 锁竞争示例

```sql
-- 会话 A
START TRANSACTION;
INSERT INTO orders(user_id, amount) VALUES (1, 100);  -- id = 100
-- 不提交,继续执行

-- 会话 B(同时执行)
INSERT INTO orders(user_id, amount) VALUES (2, 200);  -- 会等会话 A 释放锁
```

**在高并发 INSERT 场景下**:

- 模式 0/1:并发 INSERT 序列化,**自增 ID 连续**
- 模式 2:并发 INSERT 并发执行,**自增 ID 可能跳号**(回滚也会跳号)

**跳号示例**:

```sql
-- 会话 A
INSERT INTO t(name) VALUES ('a');  -- id = 1
ROLLBACK;                          -- 回滚,id=1 不会再用

-- 会话 B
INSERT INTO t(name) VALUES ('b');  -- id = 2(从 2 开始)
```

### 5. AUTO_INCREMENT 偏移与缓存

```sql
-- 查看和修改
SHOW VARIABLES LIKE 'auto_increment%';

-- auto_increment_offset  起始偏移(主从复制可避免 ID 冲突)
-- auto_increment_increment  步长
SET auto_increment_increment = 2;
SET auto_increment_offset = 1;   -- 主库奇数
-- 从库 SET auto_increment_offset = 2;  -- 从库偶数
```

**经典坑——主从 ID 冲突**:

```sql
-- 双主复制时,两台机器都插入 id=100 的记录会冲突
-- 解决:一台用奇数 ID,另一台用偶数 ID
```

### 6. 手动指定自增值

```sql
-- 可以手动 INSERT,但自增值会跟着涨
INSERT INTO t (id, name) VALUES (10000, 'special');
INSERT INTO t (name) VALUES ('normal');  -- id = 10001
```

## 七、ALTER TABLE 修改表

### 1. 添加列

```sql
ALTER TABLE users ADD COLUMN phone VARCHAR(20) AFTER email;
ALTER TABLE users ADD COLUMN avatar VARCHAR(255) COMMENT '头像URL';

-- 同时加多列(MySQL 8.0.29+)
ALTER TABLE users
    ADD COLUMN phone VARCHAR(20) AFTER email,
    ADD COLUMN nickname VARCHAR(50) AFTER username;
```

### 2. 删除列

```sql
ALTER TABLE users DROP COLUMN avatar;
ALTER TABLE users DROP COLUMN phone, DROP COLUMN nickname;
```

### 3. 修改列(类型/约束)

```sql
-- 改类型
ALTER TABLE users MODIFY COLUMN username VARCHAR(100) NOT NULL;

-- 改名 + 改类型 + 改位置(CHANGE)
ALTER TABLE users
    CHANGE COLUMN username user_name VARCHAR(100) NOT NULL;

-- 重命名表
ALTER TABLE users RENAME TO app_users;
RENAME TABLE users TO app_users;  -- 同效
```

### 4. 添加/删除索引

```sql
-- 添加索引
ALTER TABLE users ADD INDEX idx_phone (phone);
ALTER TABLE users ADD UNIQUE KEY uk_phone (phone);
ALTER TABLE users ADD PRIMARY KEY (id);  -- 表无主键时

-- 删除索引
ALTER TABLE users DROP INDEX uk_phone;
ALTER TABLE users DROP PRIMARY KEY;
```

### 5. 性能优化 ALTER

**MySQL 5.6 之前**:ALTER TABLE 会**锁表**,大表上做列修改可能锁几小时。

**MySQL 5.6+**:`ALGORITHM=INPLACE`、`LOCK=NONE` 在线 DDL。

```sql
-- 查看 DDL 模式
ALTER TABLE users ADD COLUMN phone VARCHAR(20), ALGORITHM=INPLACE, LOCK=NONE;
```

**ALGORITHM 选项**:

| 值       | 含义                                 |
|----------|--------------------------------------|
| DEFAULT  | MySQL 自动选择                       |
| INSTANT  | 仅修改元数据,瞬间完成(MySQL 8.0+) |
| INPLACE  | 不复制表,但可能有锁                 |
| COPY     | 复制表,锁表(慢但兼容性好)           |

**LOCK 选项**:

| 值    | 含义                                 |
|-------|--------------------------------------|
| NONE  | 允许并发 DML(读+写)                |
| SHARED| 只允许读,不允许写                    |
| EXCLUSIVE | 独占,所有访问阻塞               |
| DEFAULT | MySQL 自动选择                     |

### 6. 常用 ALTER 速查

```sql
-- 改表注释
ALTER TABLE users COMMENT = '系统用户表';

-- 改字符集
ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 调整自增初始值
ALTER TABLE users AUTO_INCREMENT = 10000;

-- 移动表到其他库
ALTER TABLE mydb.users RENAME TO newdb.app_users;
```

## 八、表删除与清空:DROP vs TRUNCATE vs DELETE

### 1. 三种方式对比

| 操作                | 类型     | 速度  | 回滚   | 自增 ID | 触发器 | 范围 |
|---------------------|----------|-------|--------|---------|--------|------|
| `DROP TABLE`        | DDL      | 最快  | 不支持 | 表没了  | -      | 表   |
| `TRUNCATE TABLE`    | DDL      | 快    | 不支持 | 重置为初始值 | 不触发 | 表   |
| `DELETE FROM`       | DML      | 慢    | 支持   | 保留   | 触发   | 行   |

### 2. DROP TABLE

```sql
DROP TABLE t;
DROP TABLE IF EXISTS t1, t2;       -- 同时删多张表
```

- 删除整张表(结构和数据)
- **不可恢复**,慎用
- 不触发触发器
- 表上有外键引用时,需要先处理外键

### 3. TRUNCATE TABLE

```sql
TRUNCATE TABLE users;
TRUNCATE TABLE users;   -- 多次执行,结果一样(幂等)
```

- 删除所有行,但**保留表结构**
- 本质:**DROP + CREATE**(所以速度快)
- **自增 ID 重置**
- 不能用于有外键引用的表(除非关闭外键检查)
- 不触发 DELETE 触发器

```sql
-- 清空有外键的表
SET FOREIGN_KEY_CHECKS = 0;
TRUNCATE TABLE users;
SET FOREIGN_KEY_CHECKS = 1;
```

### 4. DELETE

```sql
DELETE FROM users WHERE status = 0;
DELETE FROM users;                  -- 全表删除(慢!)
DELETE FROM users ORDER BY id LIMIT 1000;  -- 分批删除
```

- 按条件删除,**支持事务回滚**
- 自增 ID 不重置
- 触发 DELETE 触发器
- **全表 DELETE 很慢**:一行一行删,产生大量 undo log、binlog

### 5. 实战建议

```sql
-- 大表清空:推荐 TRUNCATE
TRUNCATE TABLE log_2024;

-- 大表按条件清理:分批 DELETE
REPEAT
    DELETE FROM logs WHERE created_at < '2024-01-01' LIMIT 10000;
UNTIL ROW_COUNT() = 0 END REPEAT;
```

## 九、临时表(TEMPORARY TABLE)

### 1. 语法

```sql
CREATE TEMPORARY TABLE tmp_user_stats (
    user_id BIGINT,
    order_count INT,
    total_amount DECIMAL(10,2)
);

-- 基于查询结果
CREATE TEMPORARY TABLE tmp_user_stats AS
SELECT user_id, COUNT(*) AS cnt, SUM(amount) AS total
FROM orders
GROUP BY user_id;
```

### 2. 特点

- 仅在**当前会话**可见,其他会话看不到
- **会话结束自动删除**
- 可与正常表同名(临时表优先级高于正常表)
- 不能用某些引擎(如 InnoDB 不支持压缩临时表)

### 3. 典型用途

```sql
-- 复杂查询的中间结果
CREATE TEMPORARY TABLE tmp_top_users AS
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY user_id
HAVING total > 10000;

-- 与业务表 JOIN
SELECT u.username, t.total
FROM users u
JOIN tmp_top_users t ON u.id = t.user_id
ORDER BY t.total DESC;

-- 用完自动清理(会话结束)
```

## 十、分区表(Partitioned Table)

### 1. 什么是分区

将一张**逻辑表**的数据分散存储到**多个物理子表**中。对应用透明,SQL 不变。

**优势**:

- 大表查询性能提升(分区裁剪)
- 数据维护更方便(快速删除/归档某分区)
- 优化器可以只扫描必要分区

**劣势**:

- 单表分区数 ≤ 8192
- 不支持外键
- 所有唯一键(含主键)必须包含分区键

### 2. RANGE 分区(按范围)

适用场景:按时间分区的日志表、订单表。

```sql
CREATE TABLE orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id, created_at)   -- 注意:主键必须包含分区键
) ENGINE=InnoDB
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p202401 VALUES LESS THAN (TO_DAYS('2024-02-01')),
    PARTITION p202402 VALUES VALUES LESS THAN (TO_DAYS('2024-03-01')),
    PARTITION p202403 VALUES LESS THAN (TO_DAYS('2024-04-01')),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

**查询分区裁剪**:

```sql
-- 只扫描 p202401,其他分区不查
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
```

**新增/删除分区**:

```sql
-- 新增分区
ALTER TABLE orders ADD PARTITION (
    PARTITION p202404 VALUES LESS THAN (TO_DAYS('2024-05-01'))
);

-- 删除分区(快,瞬间完成,数据没了)
ALTER TABLE orders DROP PARTITION p202401;

-- 重组分区
ALTER TABLE orders REORGANIZE PARTITION p_future INTO (
    PARTITION p202404 VALUES LESS THAN (TO_DAYS('2024-05-01')),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

### 3. LIST 分区(按枚举值)

适用场景:按地区、状态分类。

```sql
CREATE TABLE users_by_region (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username VARCHAR(50),
    region TINYINT NOT NULL,           -- 1-华东 2-华北 3-华南 4-西部
    PRIMARY KEY (id, region)
) ENGINE=InnoDB
PARTITION BY LIST (region) (
    PARTITION p_east  VALUES IN (1),
    PARTITION p_north VALUES IN (2),
    PARTITION p_south VALUES IN (3),
    PARTITION p_west  VALUES IN (4)
);
```

### 4. HASH 分区(按哈希均匀分布)

适用场景:想让数据均匀分布,但无明确业务分类键。

```sql
CREATE TABLE sessions (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    token VARCHAR(64),
    PRIMARY KEY (id, user_id)
) ENGINE=InnoDB
PARTITION BY HASH (user_id) PARTITIONS 16;   -- 16 个分区
```

- `HASH(expr) PARTITIONS N`:MySQL 自动算 hash
- `LINEAR HASH(expr) PARTITIONS N`:线性哈希,合并/删除分区更高效

### 5. KEY 分区(类似 HASH,但用 MySQL 内部哈希函数)

```sql
CREATE TABLE events (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    event_key VARCHAR(50) NOT NULL,
    payload JSON,
    PRIMARY KEY (id, event_key)
) ENGINE=InnoDB
PARTITION BY KEY (event_key) PARTITIONS 8;
```

### 6. 子分区(Subpartitioning)

HASH/KEY 分区下可再分 RANGE/LIST 子分区。

```sql
PARTITION BY KEY (user_id) PARTITIONS 4
SUBPARTITION BY RANGE (TO_DAYS(created_at))
SUBPARTITIONS 4 (
    SUBPARTITION sp1 VALUES LESS THAN (TO_DAYS('2024-01-01')),
    SUBPARTITION sp2 VALUES LESS THAN (TO_DAYS('2024-07-01')),
    SUBPARTITION sp3 VALUES LESS THAN (TO_DAYS('2025-01-01')),
    SUBPARTITION sp4 VALUES LESS THAN MAXVALUE
);
```

### 7. 分区信息查询

```sql
SELECT PARTITION_NAME, TABLE_ROWS, DATA_LENGTH
FROM INFORMATION_SCHEMA.PARTITIONS
WHERE TABLE_NAME = 'orders';

EXPLAIN PARTITIONS SELECT * FROM orders WHERE created_at = '2024-02-15';
```

## 十三、设计最佳实践

### 1. 表设计原则

- **每张表必须有主键**(InnoDB 聚簇索引)
- **字段尽量 NOT NULL**,少用 NULL
- **金额用 DECIMAL**,不用 FLOAT/DOUBLE
- **字符串长度合理预估**,避免过长 VARCHAR
- **每个字段加 COMMENT**,便于维护
- **created_at/updated_at 几乎必备**
- 表名、字段名用**小写+下划线**,关键词用反引号

### 2. 命名规范

```sql
-- 表名:小写,下划线分隔,复数形式
users, orders, order_items, product_categories

-- 主键:id (BIGINT UNSIGNED AUTO_INCREMENT)
-- 外键:{关联表}_id
-- 时间字段:{action}_at (created_at, updated_at, paid_at)
-- 布尔/状态:is_{x} 或 status (TINYINT)
-- 索引:idx_{col1}_{col2} 普通索引
--      uk_{col} 唯一索引
```

### 3. 字符集与存储

```sql
-- 全链路 utf8mb4
-- 服务端 utf8mb4 + 客户端 utf8mb4 + 表 utf8mb4 + 列 utf8mb4

-- 时间统一 DATETIME
-- 金额统一 DECIMAL
-- IP 用 VARCHAR(45)(支持 IPv6)
-- 主键 BIGINT UNSIGNED(避免负数浪费一半空间)
```

## 十四、核心要点速记

- **MySQL DDL 三剑客**:CREATE / ALTER / DROP,**对应库、表、列**三级操作
- **字符集推荐统一 `utf8mb4`**(完整 Unicode),排序规则推荐 `utf8mb4_unicode_ci`
- **CHAR vs VARCHAR**:定长用 CHAR,变长用 VARCHAR;**VARCHAR(N) N 是字符数,不是字节数**
- **主键 = 聚簇索引**,建议 BIGINT UNSIGNED AUTO_INCREMENT,稳定不变、尽量短
- **NOT NULL > NULL**:省空间、避免比较陷阱,业务"无值"应给默认值
- **AUTO_INCREMENT** 在 MySQL 8.0+ **持久化到 redo log**,重启不丢
- **AUTO_INCREMENT 锁模式**:0/1 表锁串行,2 无锁交错(并发高但可能跳号)
- **DROP / TRUNCATE / DELETE**:DDL 不可回滚 / DDL 清表重置自增 / DML 支持事务
- **ONLINE DDL**(5.6+):`ALGORITHM=INPLACE, LOCK=NONE`,大表 ALTER 不再锁表
- **CHECK 约束**只在 MySQL 8.0+ 才真正生效,5.7 只解析不执行
- **外键争议**:小型项目/教学用外键;互联网大厂**不用外键**,应用层保证一致性
- **临时表**仅当前会话可见,会话结束自动删,适合存中间结果
- **分区表四大类**:RANGE(按范围,最常用)、LIST(按枚举)、HASH(均匀)、KEY(MySQL 内部哈希)
- **分区表的坑**:所有唯一键(含主键)必须包含分区键;不支持外键;分区数 ≤ 8192
- **分区优势**:查询裁剪、归档快(删分区秒级);**大表按时间分区是常见优化手段**
- **查询元数据三件套**:`SHOW CREATE TABLE`(看 DDL)、`SHOW TABLE STATUS`(看统计)、`INFORMATION_SCHEMA`(标准 SQL)
- **设计三件套**:每个字段加 COMMENT、必备 created_at/updated_at、金额用 DECIMAL
