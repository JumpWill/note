# 性能监控与调优 (Performance Monitoring & Tuning)

## 一、性能监控总览

### 1. 性能调优的目标

- **提高吞吐量**:单位时间处理更多请求
- **降低延迟**:单次查询响应更快
- **提高资源利用率**:不浪费 CPU、内存、IO
- **提高稳定性**:不崩溃、不超时
- **降低成本**:用更少机器做更多事

### 2. 性能调优的层次

```text
1. 业务层    (应用逻辑、SQL 写法)
2. 应用层    (连接池、缓存)
3. 数据库层  (MySQL 引擎、SQL 优化、索引)
4. OS 层     (CPU、内存、IO、网络)
5. 硬件层    (磁盘、网卡、内存)
6. 架构层    (主从、读写分离、分库分表)
```

**调优顺序**:从上层到下层(因为上层问题占 80%)

### 3. 性能调优的方法论

1. **定目标**:SLA/QPS/延迟/错误率
2. **测基线**:现状是什么
3. **定位瓶颈**:CPU/内存/IO/锁/SQL
4. **分析原因**:为什么慢
5. **改一处**:小步迭代
6. **测改进**:对比基线
7. **继续优化**:返回 3

**黄金法则**:**先测量,后优化**(不要盲目调参)

## 二、性能监控指标

### 1. QPS / TPS

**QPS (Queries Per Second)**:每秒查询数
**TPS (Transactions Per Second)**:每秒事务数

```sql
-- 查看 QPS
SHOW GLOBAL STATUS LIKE 'Questions';
SHOW GLOBAL STATUS LIKE 'Queries';

-- 查看 TPS (基于 Com_commit + Com_rollback)
SHOW GLOBAL STATUS LIKE 'Com_commit';
SHOW GLOBAL STATUS LIKE 'Com_rollback';

-- 计算 QPS 脚本
SELECT VARIABLE_VALUE AS questions
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Questions';

-- TPS = (Com_commit + Com_rollback) / 秒数
SELECT 
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Com_commit') +
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Com_rollback') AS total_transactions;
```

**QPS 实时采集脚本**:

```bash
#!/bin/bash
# 每秒采样 QPS
while true; do
  Q1=$(mysql -uroot -p -e "SHOW GLOBAL STATUS LIKE 'Questions'" | awk '{print $2}' | tail -1)
  sleep 1
  Q2=$(mysql -uroot -p -e "SHOW GLOBAL STATUS LIKE 'Questions'" | awk '{print $2}' | tail -1)
  echo "QPS: $((Q2-Q1))"
done
```

### 2. 并发连接数

```sql
-- 最大连接数
SHOW VARIABLES LIKE 'max_connections';
-- 默认 151,生产建议 1000-5000

-- 当前连接数
SHOW GLOBAL STATUS LIKE 'Threads_connected';
-- 当前活跃连接数(正在执行查询)
SHOW GLOBAL STATUS LIKE 'Threads_running';
-- 累计连接数
SHOW GLOBAL STATUS LIKE 'Connections';
-- 累计创建的线程数
SHOW GLOBAL STATUS LIKE 'Threads_created';

-- 缓存的线程数
SHOW VARIABLES LIKE 'thread_cache_size';

-- 详细连接信息
SHOW FULL PROCESSLIST;
SELECT * FROM information_schema.processlist;

-- 杀连接
KILL <thread_id>;
```

**Threads_running 告警阈值**:
- < 5: 正常
- 5-20: 关注
- \> 20: 严重,可能存在慢查询堆积

### 3. 慢查询

```sql
-- 慢查询计数
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- 慢查询配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
-- long_query_time 默认 10s,建议 1-2s

-- 开启慢查询
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL slow_query_log_file = '/var/log/mysql/mysql-slow.log';

-- 未使用索引的查询也算慢查询
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
SET GLOBAL log_queries_not_using_indexes = ON;
```

### 4. 锁等待

```sql
-- InnoDB 行锁等待次数
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';
-- 等待总时长
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time';
-- 平均等待时长
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg';
-- 锁等待最长时间
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_max';

-- 表锁等待
SHOW GLOBAL STATUS LIKE 'Table_locks_waited';
SHOW GLOBAL STATUS LIKE 'Table_locks_immediate';

-- 元数据锁等待(MySQL 5.7+)
SELECT * FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA NOT IN ('mysql', 'performance_schema', 'information_schema');

-- 当前锁等待
SELECT * FROM sys.innodb_lock_waits;
```

### 5. Buffer Pool 命中率

```sql
-- 读取次数
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';
-- 从磁盘读取次数
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';
-- 预读次数
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_ahead';

-- 命中率 = (read_requests - reads) / read_requests * 100%
SELECT 
  (1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests) * 100 
  AS hit_ratio
FROM 
  (SELECT VARIABLE_VALUE AS Innodb_buffer_pool_reads 
   FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') a,
  (SELECT VARIABLE_VALUE AS Innodb_buffer_pool_read_requests 
   FROM performance_schema.global_status 
   WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests') b;

-- 命中率建议 > 99%
```

**Buffer Pool 各状态**:

```sql
-- Buffer Pool 详细信息
SELECT * FROM sys.innodb_buffer_stats_by_table;
SELECT * FROM sys.innodb_buffer_stats_by_schema;

-- Buffer Pool 实时状态
SHOW ENGINE INNODB STATUS;
```

### 6. 磁盘 IO 利用率

```sql
-- 数据读取次数
SHOW GLOBAL STATUS LIKE 'Innodb_data_reads';
SHOW GLOBAL STATUS LIKE 'Innodb_data_writes';
-- 读取字节数
SHOW GLOBAL STATUS LIKE 'Innodb_data_read';
SHOW GLOBAL STATUS LIKE 'Innodb_data_written';
-- fsync 次数
SHOW GLOBAL STATUS LIKE 'Innodb_data_fsyncs';

-- 读取平均字节
SHOW GLOBAL STATUS LIKE 'Innodb_avg_reads_per_request';

-- 系统层面看 IO
-- iostat -x 1
-- iotop
```

### 7. CPU 利用率

```sql
-- 单个查询占用的 CPU
SHOW PROCESSLIST;

-- 当前正在执行的线程
SELECT t.PROCESSLIST_ID, t.PROCESSLIST_INFO, 
       t.PROCESSLIST_TIME, es.THREAD_OS_ID
FROM performance_schema.threads t
LEFT JOIN performance_schema.events_statements_current es USING (THREAD_ID)
WHERE t.PROCESSLIST_ID IS NOT NULL;
```

**CPU 关联分析**:
- CPU 高 + IO 高 → 可能是全表扫描 + 大量磁盘读
- CPU 高 + IO 低 → 计算密集型查询
- CPU 低 + IO 高 → 慢 IO(磁盘瓶颈)

## 三、内置状态信息

### 1. SHOW STATUS

**SHOW STATUS** 显示数百个计数器,分两个级别:

```sql
-- 会话级
SHOW SESSION STATUS LIKE 'Com_%';
-- 全局级(推荐)
SHOW GLOBAL STATUS LIKE 'Com_%';
SHOW GLOBAL STATUS LIKE 'Innodb_%';
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- 重置计数器(谨慎使用)
FLUSH STATUS;
```

**常用计数器分类**:

| 类别 | 计数器 | 含义 |
|------|--------|------|
| **查询类** | `Com_select` | SELECT 次数 |
| | `Com_insert` | INSERT 次数 |
| | `Com_update` | UPDATE 次数 |
| | `Com_delete` | DELETE 次数 |
| | `Questions` | 所有查询(包含 SHOW) |
| | `Queries` | 所有查询(包含存储过程) |
| **连接类** | `Threads_connected` | 当前连接数 |
| | `Threads_running` | 当前活跃线程 |
| | `Connections` | 累计连接数 |

| | `Innodb_rows_updated` | 更新行数 |

### 2. SHOW VARIABLES

```sql
-- 显示所有参数
SHOW VARIABLES;

-- 按模糊查询
SHOW VARIABLES LIKE 'innodb%';
SHOW VARIABLES LIKE '%buffer%';
SHOW VARIABLES LIKE 'max_connections';

-- 显示运行时的参数(已修改)
SHOW VARIABLES LIKE 'long_query_time';

-- 运行时修改(不持久化)
SET GLOBAL long_query_time = 1;
SET SESSION long_query_time = 1;

-- 持久化修改(my.cnf)
[mysqld]
long_query_time = 1
```

**运行时修改 vs 持久化**:
- `SET GLOBAL` 重启失效
- 修改 `my.cnf` 持久化,需重启
- MySQL 8.0+ 支持 `SET PERSIST` 持久化到磁盘

### 4. SHOW ENGINE INNODB STATUS


**关键解读示例**:

```text

-- 等待信号量次数,高说明锁竞争严重

--------
I/O thread 0 state: waiting for i/o request
Pending normal aio reads: 0
Pending writes: 0
-- pending I/O 太多 → 磁盘 IO 瓶颈

----------------------

-- 命中率 99.9%,优秀
```

## 四、performance_schema 详解

### 1. 概览

**performance_schema** 是 MySQL 5.5+ 提供的运行时性能监控引擎,记录各种事件:
- 语句执行
- 等待事件
- 文件 IO
- 内存使用
- 锁等待
- 事务

**配置架构**:

```text
┌────────────────────────────────────────────────┐
│  setup_instruments  (启用哪些探针)              │
│     ↓                                            │
│  setup_consumers   (收集到哪些消费者)           │
│     ↓                                            │
│  events_*_history  (内存环形缓冲)               │
└────────────────────────────────────────────────┘
```

### 2. 配置 setup_instruments

```sql
-- 查看所有探针
SELECT * FROM performance_schema.setup_instruments 
WHERE NAME LIKE 'statement/%';

-- 开启语句探针
UPDATE performance_schema.setup_instruments 
SET ENABLED = 'YES', TIMED = 'YES' 
WHERE NAME LIKE 'statement/%';

-- 开启 IO 探针
UPDATE performance_schema.setup_instruments 
SET ENABLED = 'YES', TIMED = 'YES' 
WHERE NAME LIKE 'wait/io/file/%';

-- 开启表锁探针
UPDATE performance_schema.setup_instruments 
SET ENABLED = 'YES', TIMED = 'YES' 
WHERE NAME LIKE 'wait/lock/table';

-- 持久化写入 my.cnf
[mysqld]
performance_schema = ON
performance_schema_instrument = 'statement/%=ON'
performance_schema_instrument = 'wait/io/file/%=ON'
```

### 3. 配置 setup_consumers

```sql
-- 查看消费者
SELECT * FROM performance_schema.setup_consumers;

-- 关键消费者
-- events_statements_current: 当前语句
-- events_statements_history: 最近 N 条语句
-- events_statements_history_long: 长历史
-- events_waits_history: 等待事件
-- events_stages_history: 阶段事件

-- 启用消费者
UPDATE performance_schema.setup_consumers 
SET ENABLED = 'YES' WHERE NAME LIKE 'events_statements%';

-- 配置历史长度
SET GLOBAL performance_schema_events_statements_history_size = 100;
SET GLOBAL performance_schema_events_statements_history_long_size = 10000;
```

### 4. 常用查询

#### 4.1 锁等待查询

```sql
-- 当前锁等待
SELECT 
  waiting_thd.PROCESSLIST_ID AS waiting_pid,
  waiting_thd.PROCESSLIST_INFO AS waiting_query,
  blocking_thd.PROCESSLIST_ID AS blocking_pid,
  blocking_thd.PROCESSLIST_INFO AS blocking_query
FROM performance_schema.data_lock_waits w
INNER JOIN performance_schema.threads waiting_thd 
  ON w.REQUESTING_ENGINE_LOCK_ID = waiting_thd.THREAD_ID
INNER JOIN performance_schema.threads blocking_thd 
  ON w.BLOCKING_ENGINE_LOCK_ID = blocking_thd.THREAD_ID;
```

#### 4.2 SQL 统计

```sql
-- Top 10 慢查询
SELECT 
  SCHEMA_NAME,
  DIGEST_TEXT,
  COUNT_STAR AS exec_count,
  SUM_TIMER_WAIT/1000000000 AS total_ms,
  AVG_TIMER_WAIT/1000000000 AS avg_ms,
  MAX_TIMER_WAIT/1000000000 AS max_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 全表扫描的查询
SELECT 
  SCHEMA_NAME,
  DIGEST_TEXT,
  COUNT_STAR,
  SUM_NO_INDEX_USED,
  SUM_NO_GOOD_INDEX_USED
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_NO_INDEX_USED > 0
ORDER BY SUM_NO_INDEX_USED DESC;
```

#### 4.3 文件 IO 统计

```sql
-- 文件 IO 排行
SELECT 
  FILE_NAME,
  COUNT_READ,
  SUM_TIMER_READ/1000000000 AS read_ms,
  COUNT_WRITE,
  SUM_TIMER_WRITE/1000000000 AS write_ms
FROM performance_schema.file_summary_by_instance
ORDER BY SUM_TIMER_READ + SUM_TIMER_WRITE DESC
LIMIT 10;

-- 表 IO 统计
SELECT 
  OBJECT_SCHEMA,
  OBJECT_NAME,
  COUNT_READ,
  SUM_TIMER_READ/1000000000 AS read_ms
FROM performance_schema.table_io_waits_summary_by_table
ORDER BY SUM_TIMER_READ DESC
LIMIT 10;
```

#### 4.4 内存使用

```sql
-- 内存使用排行
SELECT 
  EVENT_NAME,
  CURRENT_NUMBER_OF_BYTES_USED/1024/1024 AS current_mb,
  HIGH_NUMBER_OF_BYTES_USED/1024/1024 AS high_mb
FROM performance_schema.memory_summary_global_by_event_name
ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC
LIMIT 10;
```

#### 4.5 元数据锁

```sql
-- 当前元数据锁
SELECT 
  OBJECT_SCHEMA,
  OBJECT_NAME,
  LOCK_TYPE,
  LOCK_DURATION,
  LOCK_STATUS
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA NOT IN ('mysql', 'performance_schema', 'information_schema');

-- 元数据锁等待
SELECT 
  PROCESSLIST_ID,
  PROCESSLIST_INFO,
  PROCESSLIST_TIME
FROM performance_schema.threads
WHERE PROCESSLIST_ID IS NOT NULL;
```

## 五、sys schema(MySQL 5.7+)

### 1. 概览

**sys schema** 是基于 performance_schema 的视图集合,提供更易读的性能信息。

### 2. 会话相关

```sql
-- 会话 IO 统计
SELECT * FROM sys.session 
WHERE conn_id != PS_CURRENT_THREAD_ID()
ORDER BY total_latency DESC
LIMIT 10;

-- 主机汇总
SELECT * FROM sys.host_summary;

-- 数据库统计
SELECT * FROM sys.schema_statistics_with_buffer;

-- 用户统计
SELECT * FROM sys.user_summary;
```

### 3. SQL 分析

```sql
-- 语句分析(慢查询 Top 10)
SELECT * FROM sys.statement_analysis
LIMIT 10;

-- 包含全表扫描
SELECT * FROM sys.statements_with_full_table_scans
LIMIT 10;

-- 错误语句
SELECT * FROM sys.statements_with_errors_or_warnings
LIMIT 10;

-- 排序最多的语句
SELECT * FROM sys.statements_with_sorting
LIMIT 10;

-- 临时表最多的语句
SELECT * FROM sys.statements_with_temp_tables
LIMIT 10;
```

**statement_analysis 关键字段**:

| 字段 | 含义 |
|------|------|
| `query` | SQL 模板 |
| `db` | 库名 |
| `exec_count` | 执行次数 |
| `total_latency` | 总延迟 |
| `avg_latency` | 平均延迟 |
| `lock_latency` | 锁等待延迟 |
| `rows_sent` | 返回行数 |
| `rows_examined` | 扫描行数 |
| `tmp_tables` | 临时表数 |
| `full_scans` | 全表扫描次数 |

### 4. IO 分析

```sql
-- 文件 IO 按延迟
SELECT * FROM sys.io_global_by_file_by_latency
LIMIT 10;

-- 表 IO 延迟
SELECT * FROM sys.schema_index_statistics;
SELECT * FROM sys.schema_table_statistics;

-- 按字节排序
SELECT * FROM sys.io_global_by_file_by_bytes
LIMIT 10;

-- 按等待时间排序
SELECT * FROM sys.io_global_by_wait_by_latency
LIMIT 10;
```

### 5. 锁和事务

```sql
-- InnoDB 锁等待
SELECT * FROM sys.innodb_lock_waits;

-- 锁等待源
SELECT * FROM sys.innodb_lock_waits;

-- memory by thread
SELECT * FROM sys.memory_by_thread_by_current_bytes

```

### 6. 实用查询

```sql
-- 冗余索引
SELECT * FROM sys.schema_redundant_indexes;
```

## 九、调优思路(从 OS 到 MySQL)

### 1. 调优层次

```text
┌────────────────────────────────────────────────┐
│  1. 业务层调优 (算法、SQL、索引)               │  ★★★★★
├────────────────────────────────────────────────┤
│  2. 应用层调优 (连接池、缓存、异步)           │  ★★★★
├────────────────────────────────────────────────┤
│  3. 数据库架构 (主从、分库分表、读写分离)     │  ★★★★
├────────────────────────────────────────────────┤

├────────────────────────────────────────────────┤
│  6. 硬件升级 (CPU、内存、SSD)                  │  ★
└────────────────────────────────────────────────┘

```

**80/20 法则**:80% 性能问题在 20% 的 SQL 上。

### 2. 调优步骤

```text

   ├─ 配置不当

   ├─ 加索引
   ├─ 改写 SQL
   ├─ 调参数

   └─ 对比基线
```

## 十、内存调优

### 1. innodb_buffer_pool_size

**含义**:InnoDB 缓冲池大小,缓存表和索引数据。

```ini
# 推荐值:物理内存的 60-80%
innodb_buffer_pool_size = 16G
```

**调整原则**:
- 专用数据库服务器:物理内存的 70-80%
- 混合部署:物理内存的 50-60%
- 公式: `innodb_buffer_pool_size = 物理内存 * 0.7`

**在线调整**(MySQL 5.7+):

```sql
SET GLOBAL innodb_buffer_pool_size = 16 * 1024 * 1024 * 1024;
```

### 2. innodb_buffer_pool_instances

**含义**:缓冲池实例数,减少并发竞争。

```ini
# 推荐:每个实例至少 1GB
innodb_buffer_pool_size = 16G
innodb_buffer_pool_instances = 8
# 16G / 8 = 2G per instance
```

**MySQL 8.0+**:超过 1GB 自动启用多个 chunk,无需手动配置 instances。

### 3. innodb_log_buffer_size

**含义**:InnoDB 日志缓冲区,事务先写入这里,再刷到 redo log。

```ini
# 默认 16MB,大数据量写入时 32-64MB
innodb_log_buffer_size = 32M
```

**判断是否够用**:

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';
-- 大于 0 表示日志缓冲区太小,需要等待
```

### 4. 连接级内存

| 参数 | 含义 | 默认 | 推荐 |
|------|------|------|------|
| `join_buffer_size` | JOIN 缓冲区 | 256K | 1-4M |
| `sort_buffer_size` | 排序缓冲区 | 256K | 1-4M |
| `read_buffer_size` | 顺序读缓冲区 | 128K | 1-2M |
| `read_rnd_buffer_size` | 随机读缓冲区 | 256K | 1-4M |
| `tmp_table_size` | 内存临时表 | 16M | 64-256M |
| `max_heap_table_size` | 内存表最大 | 16M | 64-256M |
| `thread_stack` | 线程栈 | 256K | 默认 |

**注意**:这些是**每个连接**的内存,连接数 × 大小 = 总内存占用。

```ini
# 计算公式
# max_connections * (sort_buffer + join_buffer + read_buffer + read_rnd_buffer)
# 1000 * (4M + 4M + 2M + 4M) = 14GB
```

**重要**:不要给太多,容易 OOM。

### 5. table_open_cache

```ini
# 表文件描述符缓存
table_open_cache = 2000
# 推荐: max_connections * 每个连接使用表数
```

```sql
-- 调整是否合理
SHOW GLOBAL STATUS LIKE 'Open_tables';
SHOW GLOBAL STATUS LIKE 'Opened_tables';
-- Opened_tables / Open_tables > 1.5 → 太小
```

## 十一、IO 调优

### 1. innodb_io_capacity

**含义**:InnoDB 后台任务的 IO 能力(IOPS)。

```ini
# 机械盘:200-1000
# SATA SSD:1000-2000
# NVMe SSD:5000-20000

# 推荐值
innodb_io_capacity = 2000
innodb_io_capacity_max = 4000
```

**参考值**:

| 存储类型 | IOPS | innodb_io_capacity |
|----------|------|---------------------|
| 7200 RPM HDD | 75-150 | 200 |
| 15000 RPM HDD | 175-210 | 400 |
| SATA SSD | 5000-50000 | 2000 |
| NVMe SSD | 100000+ | 10000 |

### 2. innodb_flush_method

**含义**:InnoDB 数据文件和日志文件的刷盘方式。

```ini
# 推荐:O_DIRECT
innodb_flush_method = O_DIRECT
```

**对比**:

| 值 | 含义 | 适用 |
|----|------|------|
| `fsync` | 默认,fsync() 系统调用 | 通用 |
| `O_DIRECT` | 绕过 OS page cache | Linux + 数据库独占 |
| `O_DSYNC` | 只对日志文件 O_DSYNC | 较少用 |
| `littlesync` | 历史遗留 | 不用 |
| `nosync` | 不刷盘(测试) | 危险 |

**O_DIRECT 优势**:
- 避免双重缓冲(OS 和 InnoDB)
- 减少内存占用
- 适合写密集

### 3. innodb_log_file_size

**含义**:每个 redo log 文件大小。

```ini
# 推荐:2-4GB
innodb_log_file_size = 4G
innodb_log_files_in_group = 2
# 总 redo log = 4G * 2 = 8G
```

**调整原则**:
- 太小:频繁 checkpoint,IO 压力大
- 太大:恢复时间长
- 推荐:能容纳 1 小时写入量

### 4. InnoDB IO 线程

```ini
innodb_read_io_threads = 8
innodb_write_io_threads = 8
# 默认 4,推荐 8-16
```

### 5. 磁盘优化

```ini
# 单表文件
innodb_file_per_table = ON

# 表空间大小
innodb_autoextend_increment = 64

# 异步 IO
innodb_use_native_aio = ON
```

## 十二、并发调优

### 1. max_connections

**含义**:最大连接数。

```ini
# 默认 151,生产建议 1000-5000
max_connections = 2000
```

**判断瓶颈**:

```sql
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Connections';
SHOW GLOBAL STATUS LIKE 'Threads_created';
```

**Threads_created / Connections > 10%** → 线程缓存太小。

### 2. thread_cache_size

**含义**:线程缓存数。

```ini
# 推荐:50-100
thread_cache_size = 100
```

**判断**:

```sql
SHOW GLOBAL STATUS LIKE 'Threads_created';
SHOW GLOBAL STATUS LIKE 'Connections';
-- Threads_created / Connections < 0.01 优秀
```

### 3. innodb_thread_concurrency

## 十三、Redo log 调优

### 1. innodb_log_file_size

```ini
# 推荐:2-4GB
innodb_log_file_size = 4G
```

**调整步骤**:
1. 关闭 MySQL: `mysqladmin shutdown`
2. 删除旧日志: `rm ib_logfile0 ib_logfile1`
3. 启动 MySQL:自动创建新日志

### 2. innodb_log_files_in_group

```ini
innodb_log_files_in_group = 2
# 默认 2,通常无需修改
```

### 3. innodb_flush_log_at_trx_commit (★★★)

**含义**:控制 redo log 刷盘策略。

| 值 | 含义 | 性能 | 安全性 |
|----|------|------|--------|
| **0** | 每次 commit 写入 log buffer,每秒刷盘 | 最高 | 最低(可能丢 1 秒数据) |
| **1** | 每次 commit 立即刷盘(默认) | 最低 | 最高(ACID) |
| **2** | 每次 commit 写入 OS cache,每秒刷盘 | 高 | 中(可能丢 1 秒数据) |

```ini
# 最安全:1
innodb_flush_log_at_trx_commit = 1

# 高性能:2 (主从的从库常用)
innodb_flush_log_at_trx_commit = 2

# 极致性能:0 (应用层做容错)
innodb_flush_log_at_trx_commit = 0
```

**性能对比**:
- 值 1: 1000 TPS
- 值 2: 5000 TPS
- 值 0: 8000 TPS

**数据安全分析**:
- **值 1**:即使宕机,已 commit 的数据不丢失
- **值 2**:宕机但 OS 不挂,数据不丢;OS 挂可能丢 1s
- **值 0**:宕机可能丢 1s 数据

### 4. innodb_flush_log_at_timeout

```ini
# 每 N 秒刷一次日志,默认 1
innodb_flush_log_at_timeout = 1
```

## 十四、SQL 调优

参考第 11 章 SQL 优化,关键点:

### 1. 索引优化

```sql
-- 查看慢查询

-- 关键字段
```

- 字段使用函数
- 隐式类型转换
- 不符合最左前缀
- `OR` 条件
- 范围条件后的索引失效

- `IS NULL` / `IS NOT NULL`(某些场景)

```sql
-- 改写前

-- 改写后(数据量大时)
```

## 十七、性能问题排查流程

### 1. 标准排查流程

```text
1. 现象:系统慢 / 报错 / QPS 下降
   │
   ↓
2. 监控:CPU/内存/IO/连接数
   │
   ├─ CPU 高 → top -H -p PID, perf
   ├─ 内存高 → free, OOM
   ├─ IO 高 → iostat, iotop
   └─ 连接高 → show processlist
   │
   ↓
3. 慢查询:SHOW FULL PROCESSLIST
   │
   ├─ 看到慢 SQL → EXPLAIN
   ├─ 锁等待 → sys.innodb_lock_waits
   └─ 磁盘读高 → Buffer Pool 命中率
   │
   ↓
4. 定位
   │
   ├─ SQL 问题 → 改写 / 加索引
   ├─ 锁问题 → 事务优化
   ├─ 配置问题 → 调 my.cnf
   └─ 资源问题 → 升级 / 拆分
   │
   ↓
5. 验证
   │
   └─ 对比基线,确认改善
```

**案例 1:CPU 100%**

```bash

# 3. perf

```

**案例 2:慢查询**

```sql

-- 2. 看到慢 SQL

-- 3. EXPLAIN

-- 4. 索引

-- 5. 验证

```

## 十八、核心要点速记

### 1. 监控要点

- **QPS/TPS**:`SHOW GLOBAL STATUS LIKE 'Questions' / Com_commit + Com_rollback`
- **慢查询**:`SHOW GLOBAL STATUS LIKE 'Slow_queries'`,配合 `slow_query_log`
- **Buffer Pool 命中率**:`(1 - reads / read_requests) * 100%`,应 > 99%
- **Threads_running**:`> 20` 严重
- **Innodb_row_lock_waits**:行锁等待,持续增长 = 锁竞争严重

### 2. 工具要点

- **SHOW STATUS**:数百个计数器
- **SHOW PROCESSLIST**:当前连接和查询
- **SHOW ENGINE INNODB STATUS**:InnoDB 详细状态
- **performance_schema**:最详细的运行时监控
- **sys schema**:易读的视图
- **pt-query-digest**:慢查询分析之王
- **Prometheus + Grafana**:现代监控

### 3. 调优参数推荐

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `innodb_buffer_pool_size` | 物理内存 70-80% | 最重要 |
| `innodb_log_file_size` | 2-4G | redo log |
| `innodb_flush_log_at_trx_commit` | 1 安全 / 2 性能 | 数据安全 |
| `innodb_io_capacity` | SSD:2000 / NVMe:10000 | 后台 IO |
| `innodb_flush_method` | O_DIRECT | 绕过 OS cache |
| `max_connections` | 1000-5000 | 根据业务调 |
| `thread_cache_size` | 50-100 | 线程缓存 |
| `sync_binlog` | 1 安全 / 0 性能 | binlog 同步 |
| `long_query_time` | 1-2s | 慢查询阈值 |
| `tmp_table_size` | 64-256M | 临时表 |

### 4. 调优金句

- **先测量,后优化**——不要凭直觉调参
- **80/20 法则**——80% 性能问题在 20% SQL 上
- **Buffer Pool 是灵魂**——70% 内存给它
- **innodb_flush_log_at_trx_commit = 2**——读写分离的从库神器
- **慢查询日志 + pt-query-digest**——SQL 优化的利器
- **每次只改一个参数**——避免相互影响
- **改完必须验证**——对比基线
- **架构 > 配置**——读写分离、分库分表往往比调参更有效

### 5. 排查流程速记

1. **现象**:慢 / 报错
2. **指标**:QPS / CPU / IO / 连接
3. **慢查询**:SHOW PROCESSLIST
4. **EXPLAIN**:分析执行计划
5. **定位**:SQL / 锁 / 配置 / 资源
6. **优化**:改 SQL / 加索引 / 调参数
7. **验证**:对比基线

### 6. 核心比率

- **Buffer Pool 命中率** > 99%
- **慢查询比例** < 0.1%
- **磁盘 await** < 5ms(SSD) / < 20ms(HDD)
- **连接数** < 80% max_connections
- **主从延迟** < 1 分钟
- **索引覆盖率** > 95%
- **CPU 利用率** 60-80%(留余量)
