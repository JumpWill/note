# MySQL 高可用架构

## 一、高可用 (HA) 基本概念

### 1. 什么是高可用

**高可用 (High Availability, HA)** 指系统在面对**硬件故障、软件故障、人为操作、突发流量**等异常情况时,仍能持续对外提供服务的能力。

衡量高可用最直观的指标是**可用性 (Availability)**:系统在一段时间内正常服务的时间占比。

```
可用性 = 正常服务时间 / 总时间 × 100%
```

可用性常用"几个 9"来表达,代表全年允许停机的时间窗口:

| 可用性 | 年停机时间 | 适用场景 |
|--------|------------|----------|
| **99% (两个 9)** | 87.6 小时 | 普通业务、内部系统 |
| **99.9% (三个 9)** | 8.76 小时 | 一般互联网业务 |
| **99.99% (四个 9)** | 52.6 分钟 | 金融、电商核心交易 |
| **99.999% (五个 9)** | 5.26 分钟 | 电信级、金融关键链路 |
| **99.9999% (六个 9)** | 31.5 秒 | 几乎不可达 |

> **直观对照**:从"三个 9"到"四个 9",可用时间只提高了 0.09%,但每年停机时间从 8.7 小时骤降到 52 分钟,工程成本往往**指数级上升**。

### 2. 为什么需要高可用

数据库作为最底层的"有状态"组件,在系统中往往是**单点**:

```text
[Web] → [API] → [MySQL (单点)]   ← 这台挂了,所有业务停摆
                       ↓
              所有依赖它的服务全部受影响
```

可能引发故障的常见原因:

- **硬件**:磁盘损坏、内存故障、网卡抖动、电源故障
- **软件**:MySQL bug、操作系统 crash、版本升级失误
- **人为**:误删表、误执行 `DROP`/`TRUNCATE`、配置错误
- **容量**:磁盘写满、连接数耗尽、长事务阻塞
- **网络**:机房光缆中断、ARP 欺骗、DNS 故障
- **自然灾害**:机房断电、空调故障、火灾

### 3. 高可用的核心目标

任何高可用方案都在试图解决三个本质问题:

1. **当主库故障时,如何快速让业务指向新主库**
2. **如何保证数据不丢、不错**
3. **切换过程对业务的影响降到最低**

围绕这三个目标,派生出下面一整套指标体系。

## 二、高可用核心指标

### 1. RTO (Recovery Time Objective)

**RTO:恢复时间目标**,指从灾难发生到系统恢复服务所允许的最大时间。

```
RTO = (故障发生时刻) → (业务再次可用) 的时间差
```

| 业务等级 | RTO 要求 | 典型方案 |
|----------|----------|----------|
| 普通 | 小时级 | 主从 + 手动切换 |
| 重要 | 分钟级 | MHA、MGR 自动切换 |
| 关键 | 秒级 | InnoDB Cluster + Router 自动 |
| 金融核心 | < 30 秒 | 同城多活 + 自动切换 |

RTO 由**故障检测时间**和**主备切换时间**两部分组成,二者都需要尽量压缩。

### 2. RPO (Recovery Point Objective)

**RPO:数据丢失目标**,指故障发生后允许丢失的最大数据量(对应多长时间的数据)。

```
RPO = (故障发生时刻) → (最后一次成功同步的事务点) 的时间差
```

| 复制方式 | RPO | 说明 |
|----------|-----|------|
| 异步复制 | 秒 - 分钟 | 主库不等从库确认,最差丢窗口内数据 |
| 半同步 | 毫秒 - 秒 | 主库等至少一个从库 `ACK`,大幅降低丢数据概率 |
| 强同步 (MGR) | 0 | 多数派确认才提交 |

> **RPO = 0** 是工程上很难的事,通常要付出**性能 + 复杂度**的双重代价。

### 3. SLA 与 SLO

- **SLA (Service Level Agreement)**:与用户/客户约定的**服务等级协议**,通常是合同级承诺,是**对外承诺**。
- **SLO (Service Level Objective)**:内部设定的**服务等级目标**,比 SLA 略紧,是**对内目标**。
- **SLI (Service Level Indicator)**:可观测的**服务等级指标**,如查询成功率、延迟 P99、复制延迟。

```text
SLI (指标) → SLO (目标) → SLA (对外承诺)
                          └─ 比 SLO 更宽松,留 buffer
```

举例:
- **SLI**:5xx 错误率
- **SLO**:月度 99.95%
- **SLA**:年度 99.9% (比 SLO 宽松,确保即使偶尔未达 SLO 也不违约)

### 4. 高可用与一致性 (CAP)

高可用绕不开分布式系统理论:

```text
C - Consistency (一致性)
A - Availability   (可用性)
P - Partition tolerance (分区容忍)
```

在网络分区 (P) 必然发生的现实里,**只能在 C 和 A 之间二选一**。MySQL 的复制本质上是放弃部分 C 换 A:

- **异步复制**:偏 AP,RPO 可能很大
- **半同步**:折中,接近 AP 但降低丢数据风险
- **MGR / 强同步**:偏 CP,强一致但写延迟增加

## 三、高可用架构演进

### 1. 主从复制 (Master-Slave Replication)

最基础、最经典的高可用形态,**单向**主从:

```text
        ┌───► Slave 1  (读)
Master ─┤
        └───► Slave 2  (读 / 备份)
```

- Master 处理**所有写**,Slave 接收 binlog 重放
- Slave 可承担**读**和**备份**
- Master 故障时,**需要手动**把某个 Slave 提升为新 Master

**优缺点**:

| 优点 | 缺点 |
|------|------|
| 简单、稳定、成熟 | 主单点,故障需手动切换 |
| 天然支持读写分离 | 切换有数据丢失风险 (异步) |
| 从库可做在线备份 | 主从延迟会导致读不一致 |

### 2. 主主复制 (Master-Master)

两台互为主从,**都可写**:

```text
Master A ⇄ Master B
  ↑        ↑
写读流量分摊到两边
```

- 注意:双主需避免主键冲突 (auto_increment 错开步长)
- 主主复制天然带**冲突风险**,不推荐常规业务使用
- 常见用法:**双主 + Keepalived VIP** 做虚拟 IP 漂移

### 3. 复制方案的演进史

```text
异步复制 (MySQL 原生)
  │
  ├── 半同步复制 (5.5+, after_sync)
  │
  ├── MMM (Multi-Master Replication Manager)            — 2010s
  ├── MHA (Master High Availability)                   — DeNA, 2011
  │
  ├── MGR (MySQL Group Replication)                    — 5.7.17 正式, 官方
  │
  ├── MySQL InnoDB Cluster (MGR + Router + Shell)      — 8.0
  ├── MySQL InnoDB ClusterSet                          — 8.0.27
  │
  └── Orchestrator (GitHub 开源)                       — GitHub
ProxySQL / MaxScale                                    — 中间件层
```

### 4. 主流方案对比

| 方案 | 一致性 | 自动切换 | 数据丢失 | 复杂度 | 运维成本 | 适用 |
|------|--------|----------|----------|--------|----------|------|
| **主从 + 脚本** | 异步 | 半自动 | 高 | 低 | 低 | 中小业务 |
| **MMM** | 异步 | 自动 | 中 | 中 | 中 | 老旧方案 |
| **MHA** | 异步 | 自动 | 中 (有 binlog 补偿) | 中 | 中 | 经典方案 |
| **MGR 单主** | 强一致 | 自动 | 几乎 0 | 中 | 中 | 中大规模 |
| **MGR 多主** | 强一致 | 自动 | 0 | 高 | 高 | 谨慎 |
| **InnoDB Cluster** | 强一致 | 自动 | 几乎 0 | 中 | 低 (封装好) | 8.0 推荐 |
| **Orchestrator** | 异步/半同步 | 自动 | 依赖复制 | 低 | 低 | 配合主从用 |
| **ProxySQL + MHA** | 异步 | 自动 | 中 | 中 | 中 | 读写分离 + HA |
| **云 RDS/Aurora** | 看实现 | 自动 | 几乎 0 | 无 | 最低 | 上云 |

### 5. 各方案核心选型逻辑

```text
追求极致强一致 + 不愿自己搞 → MGR / InnoDB Cluster
接受异步 + 强自动化 + 文档丰富 → MHA
已经在用主从 + 想引入自动切换 → Orchestrator
读多写少 + 读写分离 → ProxySQL + 主从
机房双活 + VIP → Keepalived + 双主
省心 + 钱到位 → 云数据库
```

## 四、MHA (Master High Availability) 实战

### 1. MHA 简介

**MHA** 由 DeNA (日) 的 Yoshinorim 主导开发,是 MySQL 高可用**自动化切换**的经典方案:

- 监控主库,故障时**自动**选主并切换
- 支持**数据补偿**,从其他从库补齐差异 binlog,降低数据丢失
- 由 Perl 编写,工具链成熟,**社区广泛使用**

### 2. 架构组成

```text
[Manager] ──监控──► [Master]
    │                ↑
    │ 管理 SSH + binlog ───┐
    ↓                ↓    │
[Node]─数据 ──►  [Slave1] [Slave2]
                          (new Master)
```

- **Manager**:调度节点,通常 1 ~ 2 台,只跑 MHA Manager 进程
- **Node**:每个 MySQL 实例都装,负责 binlog 补齐和应用

### 3. 工作流程

```text
1. 探测 (Detection)
   Manager 定时 ping master,超时则判定故障
         ↓
2. 选主 (Master Selection)
   从从库中选出"最接近主"的一台:
   - binlog 最新
   - relay-log 完整
   - 配置 newest_slave 优先级
         ↓
3. 补偿 (Compensation)
   比对各 Slave 与新 Master 的差异
   从拥有最新 binlog 的 Slave 上"补"到新 Master
         ↓
4. 切换 (Switchover)
   应用 VIP/写入新 Master
   其他 Slave reconfigure 指向新 Master
```

### 4. 节点规划

| 角色 | IP | 实例 |
|------|----|------|
| Manager | 10.0.0.10 | manager 进程 |
| Master | 10.0.0.11 | 原主库 |
| Slave-1 (Candidate) | 10.0.0.12 | 优先新主 |
| Slave-2 | 10.0.0.13 | 普通从库 |

### 5. 完整部署步骤

**(1) 主从复制基础 (三台都做)**

```ini
# /etc/my.cnf
[mysqld]
server_id = 11                 # 每台不同
log_bin = /var/lib/mysql/mysql-bin
binlog_format = row
gtid_mode = ON
enforce_gtid_consistency = ON
log_slave_updates = ON
relay_log = /var/lib/mysql/relay-bin
read_only = ON                 # 从库
```

```sql
-- 主库创建复制用户
CREATE USER 'repl'@'%' IDENTIFIED BY 'Repl@123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 从库执行
CHANGE MASTER TO
  MASTER_HOST='10.0.0.11',
  MASTER_USER='repl',
  MASTER_PASSWORD='Repl@123',
  MASTER_AUTO_POSITION=1;
START SLAVE;
SHOW SLAVE STATUS\G
```

**(2) SSH 互信**

```bash
# Manager 到所有 Node 节点
ssh-keygen -t rsa
ssh-copy-id root@10.0.0.11
ssh-copy-id root@10.0.0.12
ssh-copy-id root@10.0.0.13
```

**(3) 安装 MHA Node (所有 MySQL 实例)**

```bash
# RHEL/CentOS
yum install perl-DBD-MySQL perl-Config-Tiny perl-Log-Dispatch \
            perl-Parallel-ForkManager perl-Time-HiRes -y

# 安装 node 包
rpm -ivh mha4mysql-node-0.58-0.el7.centos.noarch.rpm
```

**(4) 安装 MHA Manager**

```bash
rpm -ivh mha4mysql-manager-0.58-0.el7.centos.noarch.rpm
```

**(5) Manager 配置**

```ini
# /etc/mha/app1.cnf
[server default]
manager_workdir=/var/log/mha/app1
manager_log=/var/log/mha/app1/manager.log
user=root
ssh_port=22
repl_user=repl
repl_password=Repl@123

[server1]
hostname=10.0.0.11
port=3306
# candidate_master=1        # 优先提升为主
# check_repl_delay=0

[server2]
hostname=10.0.0.12
port=3306
candidate_master=1
check_repl_delay=0

[server3]
hostname=10.0.0.13
port=3306
```

**(6) 验证**

```bash
masterha_check_ssh --conf=/etc/mha/app1.cnf
masterha_check_repl --conf=/etc/mha/app1.cnf
```

**(7) 启动 Manager (后台)**

```bash
nohup masterha_manager --conf=/etc/mha/app1.cnf \
        --remove_dead_master_conf \
        --ignore_last_failover \
        < /dev/null > /var/log/mha/app1/manager.log 2>&1 &
```

**(8) 故障后恢复**

```bash
# 修复原 master 后,把它作为新 master 的从库重新加入
CHANGE MASTER TO
  MASTER_HOST='10.0.0.12',
  MASTER_USER='repl',
  MASTER_PASSWORD='Repl@123',
  MASTER_AUTO_POSITION=1;
START SLAVE;

# 重启 Manager
masterha_manager --conf=/etc/mha/app1.cnf
```

### 6. MHA 优缺点

| 优点 | 缺点 |
|------|------|
| 自动选主 + 切换 | 异步复制,RPO 不为 0 |
| binlog 补偿机制,丢数据风险低 | Manager 单点 (需 1 主 1 备) |
| 适配多种复制结构 | 只管切换,业务无感知需中间件配合 |
| 文档丰富、实战案例多 | 仅基于 SSH,无内置 VIP |

## 五、MGR (MySQL Group Replication) 实战

### 1. 原理

**MGR** 是 MySQL 5.7.17 推出的**官方**多主/单主集群方案,基于**Paxos 变体 (XCOM + BFT)** 实现**多节点协调**:

```text
[Node1] ⇄ [Node2] ⇄ [Node3]
  ▲  GCS 通讯层 + group_replication 插件
  └─ 多数派确认才提交
```

**核心特性**:

- **多节点写冲突检测**:基于**Global Transaction Id + GTID Set** 决定冲突
- **Paxos 共识**:写事务需要多数派 (`>= floor(N/2)+1`) 确认
- **自动成员管理**:节点加入/离开自动协调
- **一致性协议**:默认 `single primary`,可选 `multi-primary`

**单主模式** (推荐生产):
```text
[Primary]   ──► 写入
   │
   ├──► [Secondary]
   └──► [Secondary]
```

**多主模式**:
```text
[Node A] ⇄ [Node B] ⇄ [Node C]
  写冲突由 MGR 自动检测回滚
```

### 2. MGR 集群架构图

```text
                ┌────────────────────────────────┐
                │        GCS (XCOM)             │
                │   Paxos 共识 + 组成员管理      │
                └────────────────────────────────┘
                  ▲           ▲            ▲
                  │           │            │
            ┌─────┴───┐ ┌─────┴───┐ ┌─────┴───┐
            │  Node1  │ │  Node2  │ │  Node3  │
            │ MGR     │ │ MGR     │ │ MGR     │
            │ Server  │ │ Server  │ │ Server  │
            │ 3306    │ │ 3306    │ │ 3306    │
            └─────────┘ └─────────┘ └─────────┘
              ▲  Binlog via Galera-style Flow
              │
       多数派: 至少 2/3 节点确认,才能提交
```

### 3. 三节点最小集群

| 节点 | IP | server_id | 角色 |
|------|-----|-----------|------|
| Node1 | 10.0.0.21 | 21 | Primary |
| Node2 | 10.0.0.22 | 22 | Secondary |
| Node3 | 10.0.0.23 | 23 | Secondary |

### 4. 完整部署步骤

**(1) my.cnf (三台近似)**

```ini
[mysqld]
server_id = 21                                  # 每台不同
log_bin = /var/lib/mysql/mysql-bin
binlog_format = row
gtid_mode = ON
enforce_gtid_consistency = ON
log_slave_updates = ON
relay_log = /var/lib/mysql/relay-bin

# Group Replication 关键
plugin_load_add = 'group_replication.so'
loose-group_replication_group_name = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee'
loose-group_replication_start_on_boot = OFF
loose-group_replication_local_address = '10.0.0.21:33061'
loose-group_replication_group_seeds = '10.0.0.21:33061,10.0.0.22:33061,10.0.0.23:33061'
loose-group_replication_bootstrap_group = OFF
loose-group_replication_single_primary_mode = ON     # 单主
loose-group_replication_enforce_update_everywhere_checks = OFF
transaction_write_set_extraction = XXHASH64
```

**(2) 启动插件**

```sql
INSTALL PLUGIN group_replication SONAME 'group_replication.so';
SHOW PLUGINS;
```

**(3) 在 Node1 上引导集群**

```sql
SET SQL_LOG_BIN=0;
CREATE USER 'repl'@'%' IDENTIFIED BY 'Repl@123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
GRANT BACKUP_ADMIN ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;
SET SQL_LOG_BIN=1;

CHANGE REPLICATION SOURCE TO
  SOURCE_USER='repl',
  SOURCE_PASSWORD='Repl@123'
  FOR CHANNEL 'group_replication_recovery';

SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;

SELECT * FROM performance_schema.replication_group_members;
```

**(4) Node2 / Node3 加入**

```sql
SET SQL_LOG_BIN=0;
CHANGE REPLICATION SOURCE TO
  SOURCE_USER='repl',
  SOURCE_PASSWORD='Repl@123'
  FOR CHANNEL 'group_replication_recovery';
SET SQL_LOG_BIN=1;

START GROUP_REPLICATION;
```

```sql
-- 检查
SELECT * FROM performance_schema.replication_group_members;
-- 应该看到 3 个 ONLINE
```

**(5) 多主模式 (谨慎)**

```ini
loose-group_replication_single_primary_mode = OFF
loose-group_replication_enforce_update_everywhere_checks = ON
```

应用层需要接受"冲突回滚后重试",业务改造成本不低。

### 5. 流量控制 (Flow Control)

MGR 通过**Flow Control** 控制复制延迟:

```ini
loose-group_replication_flow_control_mode = QUOTA
loose-group_replication_flow_control_certifier_threshold = 100
loose-group_replication_flow_control_applier_threshold = 10000
loose-group_replication_flow_control_min_quota = 0
loose-group_replication_flow_control_min_recovery_quota = 0
loose-group_replication_flow_control_max_quota = 0
```

- 当 Secondary 落后 Primary 超过阈值,会自动**节流** Primary 的写入
- 默认开启 QUOTA 模式,适合**强一致性**场景

### 6. 故障检测

- **心跳**:节点间 5 秒相互探活
- **怀疑超时**:成员一段时间无响应,标记 `UNREACHABLE`
- **自动剔除**:Paxos 流程会在少部分节点故障时**自动重新计算**成员列表
- **少于多数派**:集群拒绝写入,只会读(从单台读仍有风险,需配合 Router)

### 7. MGR 优缺点

| 优点 | 缺点 |
|------|------|
| **强一致性 (RPO 接近 0)** | 网络抖动敏感,RTT 升高性能骤降 |
| 自动成员管理,无脑切换 | 大事务易触发流控 |
| 官方支持,8.0 主推 | 单机写性能比单机异步复制低 |
| 支持单主/多主 | 对 SQL 有限制 (部分 DDL 不兼容) |
| 提供插件式 API 供 Router 探测 | 多主冲突需应用层重试 |

## 六、Orchestrator 实战

### 1. 简介

**Orchestrator** 是 GitHub 开源的 MySQL 复制拓扑管理与故障切换工具:

- 主动**发现**复制拓扑,画出结构图
- 支持**手动**和**自动**故障切换
- 提供**Web UI** 看清拓扑
- 工作流可扩展 (`hooks`)

### 2. 架构与原理

```text
[Orchestrator] ──探测──► [MySQL cluster]
   │
   ├──► 元数据库 (通常 MySQL 本身)
   │
   ├──► API/CLI 控制
   │
   └──► Web UI 拓扑展示
         ↓
      自动检测 + 触发探测 (Corosync/Pacemaker 风格)
```

### 6. 故障切换流程

```text
1. Orchestrator 定时探测 master (默认每 5s)
2. 探测失败 → 标记为 down,验证 (避免误切)
3. 通过 Raft/共识选出 candidate (如启用 Raft)
4. 执行 graceful-master-takeover
   - 写入候选,设为可写
   - 迁移 VIP
   - 其他副本重新指向新主
5. 应用通过 ProxySQL / VIP 自动连通到新主
```

```bash
    -i 10.0.0.12:3306 \
    --alias mycluster

# 强制切换 (故障场景)

    --alias mycluster
```

## 七、MySQL InnoDB Cluster

### 1. 简介

**MySQL InnoDB Cluster** 是 MySQL 8.0 官方主推的高可用套装,**开箱即用**,三件套:

```text
┌───────────────────────────────────────────────┐

              ↕

└───────────────────────────────────────────────┘
              ↕
┌───────────────────────────────────────────────┐
│  MySQL Group Replication ── 数据节点集群      │
└───────────────────────────────────────────────┘
```

### 2. 三组件职责

```bash

  --bootstrap root@10.0.0.21:3306 \

# 自动生成 ./conf/mysqlrouter.conf
```

### 4. InnoDB ClusterSet

**ClusterSet** 是 InnoDB Cluster 在**异地灾备**场景下的扩展,支持**多集群**之间的灾备:

## 八、ProxySQL 读写分离

### 1. 简介

**ProxySQL** 是 MySQL 的高性能代理,工作在应用与数据库之间,**SQL 级别**路由:

- 自动读写分离
- 后端节点健康检查
- 连接池、查询缓存
- 流量镜像、查询重写
- 与 MHA / Orchestrator 集成良好

### 2. 安装

```bash
# RHEL/CentOS
cat > /etc/yum.repos.d/proxysql.repo << 'EOF'
[proxysql_repo]
name=ProxySQL repository
baseurl=https://repo.proxysql.com/ProxySQL/proxysql-2.7.x/centos/$releasever
gpgcheck=1
gpgkey=https://repo.proxysql.com/ProxySQL/repo_pub_key
EOF
yum install -y proxysql
systemctl start proxysql
```

默认监听 **6032 (管理口)** 和 **6033 (业务口)**。

### 3. 关键概念

```text
[App] ──6033──► [ProxySQL] ──┬─► Backend #1 (Master)  hostgroup 0  写
                              ├─► Backend #2 (Slave)   hostgroup 1  读
                              └─► Backend #3 (Slave)   hostgroup 1  读
```

### 4. 配置路由规则

```sql
-- 登录管理端口 6032
mysql -u admin -padmin -P 6032 -h 127.0.0.1

-- 添加后端节点 (写)
INSERT INTO mysql_servers (hostgroup_id, hostname, port, weight, comment) VALUES
  (0, '10.0.0.11', 3306, 1, 'Master'),
  (1, '10.0.0.12', 3306, 1, 'Slave-1'),
  (1, '10.0.0.13', 3306, 1, 'Slave-2');

-- 复制用户
INSERT INTO mysql_users (username, password, default_hostgroup)
VALUES ('app_user', 'App@123', 0);

-- 读写路由规则
INSERT INTO mysql_query_rules (rule_id, active, match_digest, destination_hostgroup, apply)
VALUES
  (1, 1, '^SELECT.*FOR UPDATE$', 0, 1),     -- 锁定读去主
  (2, 1, '^SELECT',                          -- 所有 SELECT 去从
   1, 1),
  (3, 1, '.*',                               -- 其他去主
   0, 1);

-- 使配置生效
LOAD MYSQL SERVERS TO RUNTIME;
LOAD MYSQL USERS TO RUNTIME;
LOAD MYSQL QUERY RULES TO RUNTIME;

SAVE MYSQL SERVERS TO DISK;
SAVE MYSQL USERS TO DISK;
SAVE MYSQL QUERY RULES TO DISK;
```

### 5. 健康检查与读写切换

```sql
-- 健康检查 (ProxySQL 自动执行)
SELECT * FROM mysql_servers;

-- 故障 Master 自动踢出 hostgroup 0
UPDATE mysql_servers SET status='OFFLINE_HARD' WHERE hostname='10.0.0.11';

-- 把新主提升到 hostgroup 0
UPDATE mysql_servers SET hostgroup_id=0 WHERE hostname='10.0.0.12';
```

通过 `proxysql_galera_healthcheck` 或外部脚本 (MHA/O) 联动,可实现自动读写切换。

## 九、Keepalived + 双主复制 (VIP 漂移)

### 1. 经典场景

两台服务器互为主主,前面挂一个**VIP**,对外只暴露这个 IP。一旦某台故障,VIP 自动漂移到另一台:

```text
        VIP: 10.0.0.100
          │
     ┌────┴────┐
 [A Master]  [B Master]
  10.0.0.11   10.0.0.12
   ←───────互主复制───────→
```

### 2. MySQL 配置 (双主)

**A (10.0.0.11)**:
```ini
server_id = 11
auto_increment_increment = 2
auto_increment_offset = 1
log_bin = /var/lib/mysql/mysql-bin
binlog_format = row
gtid_mode = ON
enforce_gtid_consistency = ON
log_slave_updates = ON
```

**B (10.0.0.12)**:
```ini
server_id = 12
auto_increment_increment = 2
auto_increment_offset = 2
log_bin = /var/lib/mysql/mysql-bin
```

### 3. Keepalived 配置

```bash
yum install -y keepalived
systemctl enable keepalived
```

`/etc/keepalived/keepalived.conf` (A 节点):

```nginx
global_defs {
  router_id LVS_DEVEL
}

vrrp_script check_mysql {
    script "/usr/bin/mysqladmin ping -uroot -pRoot@123"
    interval 3
    weight -10
    fall 2
    rise 2
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100                # B 节点配 90
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        10.0.0.100/24
    }
    track_script {
        check_mysql
    }
}
```

### 4. 漂移原理

```text
正常:
  A 持 VIP,MySQL 写
A 故障:
  - MySQL ping 失败
  - Keepalived 收健康检查失败信号
  - priority -10,变为 90
  - B (priority 90) 与 A 同样但 B 的 state 较高?实际:
    - 在 MASTER→MASTER 场景,需要 BACKUP 节点提升
    - 配置: B state BACKUP,priority 90
  - 当 B 检测到 MASTER 不再通告,自己 takeover VIP
  - MySQL 客户端指向 VIP,流量平滑过渡
```

### 5. 优缺点

| 优点 | 缺点 |
|------|------|
| 配置简单 | 双主写入冲突风险 |
| 自动漂移 | 一致性弱 (异步) |
| 资源利用率高 | 不支持多从扩展 |

## 十、中间件方案

### 1. MyCat

**MyCat** 是流行的国产 MySQL 中间件,定位**数据库代理 + 分库分表**:

- 支持 SQL 解析、自动路由、读写分离
- 支持水平分片
- Java 实现,功能强大



配置示例:

```yaml

    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    url: jdbc:mysql://10.0.0.11:3306/test
  ds_slave0:

    url: jdbc:mysql://10.0.0.12:3306/test

rules:
- !READWRITE_SPLITTING
  dataSources:
    test_ds:
      writeDataSourceName: ds_master
      readDataSourceNames: [ds_slave0]
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..1}.t_order_${0..15}

```

特点:
- 性能高 (本地解析 SQL,**无代理跳转**)
- 强耦合,语言绑定
- HA 由应用层 + 数据库自身保证

**MariaDB MaxScale**,MariaDB 自家出品,智能数据库代理:

### 4. 高可用 ≠ 万无一失

- **备份**:即使有 HA,仍需定期**全量 + 增量备份**+ 异地保存
- **演练**:每季度至少做一次"模拟主库故障,看切换多久"
- **变更管控**:大版本升级、DDL、加索引等一律低峰期,做灰度

## 十四、面试题速答

### 1. 主从复制的延迟原因及优化?

> 单线程 SQL 线程:5.6 改进为多线程 (按库/按主键)。
> 大事务延时;DDL 卡顿;网络 RTT。
> 优化:并行复制、加大 relay 线程、`sync_binlog=1`。

### 2. 半同步复制为什么可能丢数据?

> 主等 `ACK` 后提交,但事务实际已写入 binlog + 发送给从后才等。若等待期间主 crash,从可能已收到 binlog 但主未确认,重选主后从应用 binlog,看起来"没丢";但若主最后才提交,binlog 也在从上,**没问题**。真正风险来自**极端组合**:网络分区 + 滑动确认窗口。

### 3. MGR 脑裂如何处理?

> MGR 基于 Paxos,**少数派不再提供写**;网络分区恢复后会自动追上。不会出现双主写。

### 4. MHA 切换超时原因?

> 探测超时 + 补 binlog 慢 + VIP 脚本问题。需要合理配置 `master_ip_failover_script`。

### 5. InnoDB Cluster 与 MGR 区别?

> MGR = 数据层;InnoDB Cluster = MGR + Router + Shell 的产品化打包。

### 6. ProxySQL 如何实现自动读写分离?

> `mysql_query_rules` 匹配 `^SELECT` 路由到从;`mysql_group_replication_hostgroups` 支持 MGR 自动感知。

### 7. 阿里云 RDS 高可用机制?

> 主备基于半同步复制 + 自动 VIP 漂移 + 切换脚本,RTO 通常 < 30 秒,RPO ≈ 0。

### 8. 如何选 HA 方案?

> 一致性优先选 MGR/InnoDB Cluster;运维简单上 RDS/Aurora;老方案稳定 MHA + ProxySQL。

### 9. 高可用方案共同的局限?

> **DDL 仍是大坑** (无论 MGR / 主从,DDL 期间都易阻塞);**机房级灾难**只能靠异地灾备缓解;**人为误操作 (DROP/TRUNCATE) HA 无法保护**,只能靠备份。

### 10. HA 与一致性哪个优先?

> **业务说了算**:金融>强一致;电商有损可追>可用;社交>可用;C 端大多数互联网服务>可用优先。
