# Redis 内存管理与淘汰策略 (Memory Management & Eviction Policy)

> 本章覆盖 Redis 内存管理的完整体系：内存消耗的组成与统计、内存分配器、缓冲区机制、客户端内存回收、内存碎片治理、淘汰策略（8 种）、LRU/LFU 算法实现、大 Key 处理、lazyfree 异步删除、内存监控告警与生产调优实践。Redis 作为典型的内存数据库，内存管理是其区别于磁盘数据库的核心维度。

---

## 一、内存管理概述

### 1. 为什么内存管理是 Redis 的核心

Redis 将所有数据保存在内存中，相比磁盘数据库（MySQL、PostgreSQL）：

```
┌────────────────────────────────────────────────────────────────────┐
│                  Redis vs MySQL 数据存储对比                        │
├────────────────────────────────────────────────────────────────────┤
│  Redis                │  MySQL                                       │
├────────────────────────────────────────────────────────────────────┤
│  数据主存:内存(RAM)    │  数据主存:磁盘(Disk)                          │
│  持久化:异步刷盘       │  持久化:本身就是磁盘                          │
│  读写速度:10w+ QPS    │  读写速度:1w QPS (有索引)                      │
│  容量上限:机器内存     │  容量上限:磁盘大小(可达PB级)                   │
│  单 Key 成本:较高     │  单行成本:较低                                 │
│  淘汰策略:8 种         │  通常靠分库分表,不淘汰                         │
└────────────────────────────────────────────────────────────────────┘
```

**核心矛盾**：内存既快又贵。单机内存通常 64GB ~ 512GB（DDR4/DDR5），相比磁盘的 TB 级容量捉襟见肘。因此 Redis 必须：

| 维度 | 手段 |
|------|------|
| **上限控制** | 通过 `maxmemory` 限制最大使用内存 |
| **超出时清理** | 通过 8 种淘汰策略回收数据 |
| **使用效率** | 选择合适的分配器、压缩底层编码（listpack/embstr） |
| **长期使用** | 控制碎片率、定时清理大 Key |

### 2. 内存管理的"三道防线"

```
┌─────────────────────────────────────────────────────────────────────┐
│                  Redis 内存使用全过程                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   客户端 SET k v                                                     │
│       │                                                             │
│       ▼                                                             │
│   ┌─────────────┐    1. 命令缓冲 (query buffer, 默认 1MB)              │
│   │ 客户端输入    │ ──────────────────────────────────────────────────►│
│   └─────────────┘                                                    │
│                          │                                           │
│                          ▼                                           │
│   ┌──────────────────────────────────────────────────────────┐       │
│   │ Redis 数据集 (used_memory)                              │       │
│   │  - dictEntry / redisObject / listpack / skiplist 等    │       │
│   │  - 这是内存消耗的"主体"                                  │       │
│   └──────────────────────────────────────────────────────────┘       │
│                          │                                           │
│                          ▼                                           │
│   ┌──────────────────────────────────────────────────────────┐       │
│   │ 输出缓冲 (client output buffer)                         │       │
│   │  - 推回客户端前暂存                                       │       │
│   │  - 受 hard-limit / soft-limit 约束                        │       │
│   └──────────────────────────────────────────────────────────┘       │
│                          │                                           │
│                          ▼                                           │
│   ┌──────────────────────────────────────────────────────────┐       │
│   │ 复制缓冲 (repl-backlog) / AOF 缓冲                      │       │
│   │  - 主从同步、AOF 重写期间占用                              │       │
│   └──────────────────────────────────────────────────────────┘       │
│                                                                     │
│   当 used_memory + buffer > maxmemory 时,触发淘汰策略                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 3. 内存消耗的两条曲线

- **常态曲线**：`used_memory` 随业务上下波动，靠 `maxmemory` 兜底
- **异常曲线**：客户端缓冲区膨胀、AOF/RDB 重写、慢查询堆积，会让内存瞬间飙升数倍

> **生产铁律**：监控 `used_memory` 时**必须**同时监控 `mem_fragmentation_ratio`、`connected_clients`、`blocked_clients`，单看 used_memory 是片面的。

### 2. 关键字段含义对照

| 字段 | 含义 | 关注重点 |
|------|------|---------|
| `used_memory` | Redis 实际分配给对象的字节数 | 接近 `maxmemory` 需警惕 |
| `used_memory_rss` | OS 实际为 Redis 进程分配的物理页 | > 1.5 倍 used_memory 表示碎片严重 |
| `used_memory_peak` | 历史峰值 | 判断是否触及水位 |
| `used_memory_lua` | Lua 引擎占用 | 慎用 EVAL 加载大脚本 |
| `mem_fragmentation_ratio` | RSS / used_memory | >1.5 需碎片整理，<1 表示 swap |
| `mem_aof_buffer` | AOF 缓冲 | 写入阻塞时此项会飙升 |
| `mem_replication_backlog` | 主从复制积压 | 大小 = `repl-backlog-size` |
| `mem_clients_normal` | 普通客户端缓冲总和 | 异常飙升需排查输出缓冲泄漏 |
| `allocator_frag_ratio` | 分配器自身碎片率 | jemalloc 通常 1.0~1.2 |

## 三、内存消耗的组成

Redis 内存消耗可拆解为 **4 个组成部分**，生产排障需逐项排查。

```
┌─────────────────────────────────────────────────────────────────────┐
│                  Redis 内存总消耗 = ① + ② + ③ + ④                       │
├─────────────────────────────────────────────────────────────────────┤
│  ① 数据对象内存   ─── Redis 实际存储业务数据的部分                        │
│  ② 进程开销       ─── Redis 自身运行所需的代码、堆栈、内存分配器元数据       │
│  ③ 缓冲区内存     ─── 客户端输出缓冲 / AOF 缓冲 / 复制 backlog 等          │
│  ④ 内存碎片       ─── 分配器因对齐与回收产生的无法使用的"洞"                │
└─────────────────────────────────────────────────────────────────────┘
```

### 1. 数据对象内存（数据集）

这是 Redis 内存消耗的**主体**，约占 60%~85%。每个 key/value 都是一个 `redisObject` 结构：

```c
// redisObject 结构(简化版)
typedef struct redisObject {
    unsigned type:4;        // 类型:string/list/hash/set/zset/stream
    unsigned encoding:4;    // 底层编码
    unsigned lru:24;        // LRU/LFU 时间戳
    int refcount;           // 引用计数
    void *ptr;              // 指向实际数据
} robj;
```

#### (1) 字符串对象

| 编码 | 触发条件 | 内存布局 |
|------|---------|---------|
| `int` | 值为整数且能用 long 表示 | 直接存数值，不分配独立 string |
| `embstr` | 长度 ≤ 44 字节 | 一次分配,redisObject 与 SDS 连续 |
| `raw` | 长度 > 44 字节 | 两次分配,redisObject 与 SDS 分离 |

> **优化提示**：短字符串能用 embstr 编码，访问一次指针即可读取，效率高；将长字符串切分或压缩可显著降低内存。

#### (2) 集合类型编码选择

| 类型 | 元素少时编码 | 元素多时编码 | 切换阈值 |
|------|--------------|--------------|---------|
| Hash | `listpack` | `hashtable` | `hash-max-listpack-entries` (默认 128) |
| Set | `intset` / `listpack` | `hashtable` | `set-max-listpack-entries` (默认 128) |
| Sorted Set | `listpack` | `skiplist + dict` | `zset-max-listpack-entries` (默认 128) |
| List | `listpack` (quicklist 节点) | `quicklist` | 总是用 quicklist |

#### (3) 内存占用估算公式

```
字符串： ~ 50 bytes (embstr) + len(value) bytes
Hash：   ~ 30 bytes/key (listpack) 或 ~ 60 bytes/key (hashtable)
List：   ~ 30 bytes/quicklist-node + len(value)
ZSet：   ~ 50 bytes/member (skiplist) 或 ~ 30 bytes/member (listpack)
```

### 2. 进程开销

Redis 进程自身的内存消耗，包括：

| 部分 | 大小估算 |
|------|---------|
| 代码段 | 10~30 MB（编译后二进制） |
| 全局数据结构 | `server` 结构、`db` 数组、`command table` 等，约几 MB |
| Lua 引擎 | `used_memory_lua` 显示，通常 KB 级 |
| 分配器元数据 | jemalloc 会预留"页/区"用于小块分配，几 MB~几十 MB |
| 文件描述符表 | 每连接 1 个 FD，约几 KB |
| 客户端结构 | 每连接一个 `client` 结构，约 10~20 KB |

> 一般进程开销 < 100 MB，相对数据集较小；但客户端数极多（如 5w+）时，进程开销会成为大头。

### 3. 缓冲区内存

缓冲区是除数据集外的第二大头，**易被忽视但极易出问题**。

#### (1) 客户端输出缓冲 (client output buffer)

Redis 为每个客户端维护一个输出缓冲，分为 **3 个区**：

```
┌─────────────────────────────────────────────────────────┐
│  client output buffer 内存布局                          │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────────────┐  hard limit: class 不同       │
│  │  真实缓冲 (real buf)   │  - normal: 0 (无限制)        │
│  │  qbuf 类似,用于一般    │  - slave:  256 MB (默认)     │
│  │  响应输出              │  - pubsub: 64 MB (默认)      │
│  └──────────────────────┘                               │
│  ┌──────────────────────┐  实时数据流(如 MONITOR)         │
│  │  output list (链表)   │                               │
│  └──────────────────────┘                               │
│  ┌──────────────────────┐  hard-limit / soft-limit      │
│  │  reply 链表 (OBJ)     │  - normal: 0 / 0              │
│  │  如 BIGKEY 输出       │  - slave:  64 MB / 16 MB     │
│  └──────────────────────┘                               │
└─────────────────────────────────────────────────────────┘
```

#### (2) 查询缓冲 (query buffer)

存放客户端发来的命令，单条命令最大支持 **512MB**（`proto-max-bulk-len`），但 query buffer 默认软限制 **1GB**（`client-query-buffer-limit`）。

#### (3) 复制积压 (replication backlog)

主从复制中部分重同步使用的环形缓冲，大小由 `repl-backlog-size` 控制（默认 1MB）。生产建议调到 128MB~1GB，详见复制章节。

#### (4) AOF 缓冲

| 缓冲 | 位置 | 大小 |
|------|------|------|
| AOF rewrite buffer | 进程内 | 实际重写期间累积 |
| AOF child process buffer | 子进程 | 与 RDB 类似,fork 后按需增长 |

### 4. 内存碎片

详见本文第八节。

## 四、内存分配器

Redis 默认使用 **jemalloc**，作为用户态内存分配器，相比 glibc malloc 有显著优势。

### 1. 三种分配器对比

| 分配器 | 来源 | 优点 | 缺点 | Redis 支持 |
|--------|------|------|------|-----------|
| **jemalloc** (默认) | FreeBSD,现由 Facebook 维护 | 线程缓存、碎片率低(1.0~1.2)、性能稳定 | 第三方依赖 | ✓ |
| **glibc malloc** | Linux 标准 | 无需额外依赖 | 碎片率高(可达 1.5+)、多线程锁争用 | ✓ |
| **tcmalloc** | Google | 高并发场景好 | 第三方依赖,碎片率中等 | ✓ (编译时切换) |

### 2. jemalloc 的"大小类 (Size Class)"

jemalloc 将分配请求按 8B、16B、32B、48B、64B、80B、96B、112B、128B …… 直到 256KB、512KB、1MB、2MB…… 等 **大小类** 分配，每一类有独立的"页/区"。

```
┌───────────────────────────────────────────────────────────────┐
│  jemalloc 内存层次                                             │
├───────────────────────────────────────────────────────────────┤
│  Thread Cache  ──► Arena  ──► Bin (按 size class) ──► Page    │
│      线程本地       减少锁争用   每个 bin 维护独立 slab        1 页 = 4KB  │
└───────────────────────────────────────────────────────────────┘
```

**优点**：

- **碎片率低**：相同大小类的对象集中释放，留下的"洞"也可被同大小类复用
- **无锁分配**：thread cache 是线程本地，无需加锁
- **NUMA 友好**：在多 CPU 机器上能感知节点拓扑

### 3. 分配器选择建议

```bash
# 编译时通过 MALLOC=libc 切换到 glibc
make MALLOC=libc

# 默认使用 jemalloc
make
```

> **生产建议**：无特殊需求保持 jemalloc 即可。它是 Redis 在各类 benchmark 中综合表现最好的分配器。

### 4. allocator_frag_ratio 与 mem_fragmentation_ratio 的区别

| 指标 | 含义 |
|------|------|
| `allocator_frag_ratio` | jemalloc **自身** 的碎片率(`stats.allocated` / `stats.active`)，理想值 1.0~1.2 |
| `mem_fragmentation_ratio` | **OS 给 Redis 的 RSS** 与 Redis 实际使用的 `used_memory` 之比，受 jemalloc + OS 页管理双重影响 |

## 五、内存回收机制

Redis 内存回收分为主动与被动两个维度：

```
┌───────────────────────────────────────────────────────────────┐
│                 Redis 内存回收体系                              │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌─────────────────────────┐    ┌─────────────────────────┐    │
│  │  过期键删除 (TTL)        │    │  内存淘汰 (maxmemory)     │    │
│  │  - 惰性删除 (lazy)      │    │  - 8 种策略              │    │
│  │  - 定期删除 (periodic)  │    │  - 触发:内存达 maxmemory  │    │
│  └─────────────────────────┘    └─────────────────────────┘    │
│                                                               │
│  ┌─────────────────────────┐    ┌─────────────────────────┐    │
│  │  lazyfree 异步删除       │    │  客户端内存限制           │    │
│  │  - UNLINK/FLUSH ASYNC   │    │  - listpack-soft-limit   │    │
│  │  - 后台线程释放          │    │  - hard-limit            │    │
│  └─────────────────────────┘    └─────────────────────────┘    │
└───────────────────────────────────────────────────────────────┘
```

### 1. 客户端进程内存回收

每个客户端都有 query buffer (输入) 与 output buffer (输出)。Redis 7 引入了基于 **listpack 的两级限制**：

```
┌─────────────────────────────────────────────────────────────────┐
│  客户端输出 buffer 限制（Redis 7+ 增强）                          │
├─────────────────────────────────────────────────────────────────┤
│  listpack-soft-limit  ───►  软阈值,达到后开始"节流"                │
│  listpack-hard-limit  ───►  硬阈值,达到后立即关闭连接              │
│  listpack-max-listpack-size ──► listpack 大小限制                │
└─────────────────────────────────────────────────────────────────┘
```

#### 客户端输出缓冲完整配置

```bash
# redis.conf 中对普通客户端的输出缓冲
client-output-buffer-limit normal 0 0 0         # 普通客户端无限制
client-output-buffer-limit replica 256mb 64mb 60 # 主从复制:硬 256MB/软 64MB/60 秒
client-output-buffer-limit pubsub 64mb 16mb 60   # 发布订阅:硬 64MB/软 16MB/60 秒

# 客户端查询缓冲(单命令最大)
client-query-buffer-limit 1gb

# 协议批量字符串最大(单元素)
proto-max-bulk-len 512mb

# listpack 限制(Redis 7+)
listpack-soft-limit 128
listpack-hard-limit 512
listpack-max-listpack-size 8192
```

> **soft-limit / hard-limit 含义**：硬阈值是"红线"（立即断开），软阈值是"黄线"（在软阈值持续 N 秒后才断开）。

### 2. 复制缓冲区 (replication backlog)

```bash
# redis.conf
repl-backlog-size 128mb          # 积压缓冲大小
repl-backlog-ttl 3600            # 主节点断开 N 秒后释放 backlog
```

### 3. 主动过期与定期过期

详见《键管理与通用命令》章节。简要回顾：

| 机制 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| 惰性删除 | 访问 key 时检查 TTL | 无额外 CPU | 冷数据长期占用 |
| 定期删除 | 每 100ms 抽样过期字典 | 主动清理 | 可能漏掉 |

> 两者结合是 Redis 经典设计：**lazy + periodic**。

## 六、内存淘汰策略（8 种）

当 `used_memory > maxmemory` 且无法立即释放时，Redis 必须**淘汰数据**腾出空间。Redis 提供了 8 种策略：

### 1. 8 种策略总览

| 策略 | 淘汰范围 | 选择算法 | 适用场景 |
|------|---------|----------|---------|
| `noeviction` | 不淘汰 | - | 写报错（**默认**） |
| `allkeys-lru` | 所有 key | LRU | 通用缓存 |
| `allkeys-lfu` | 所有 key | LFU（4.0+） | 热点数据明显 |
| `allkeys-random` | 所有 key | 随机 | 兜底,无明显热点 |
| `volatile-lru` | 设置了 TTL 的 key | LRU | 部分数据需保留 |
| `volatile-lfu` | 设置了 TTL 的 key | LFU（4.0+） | 部分热点数据 |
| `volatile-random` | 设置了 TTL 的 key | 随机 | 同上 |
| `volatile-ttl` | 设置了 TTL 的 key | TTL 最短优先 | 即将过期数据 |

### 2. 8 种策略详细对比

| 维度 | noeviction | allkeys-lru | allkeys-lfu | allkeys-random |
|------|------------|-------------|-------------|----------------|
| **写命令** | 返回 OOM 错误 | 淘汰后写入 | 淘汰后写入 | 淘汰后写入 |
| **命中** | - | 高（最近访问） | 高（高频访问） | 低 |
| **冷数据** | 全部留存 | 自然淘汰 | 自然淘汰 | 可能留存 |
| **热点识别** | - | 弱（最近） | 强（频率） | 无 |
| **适用业务** | 数据全保留（DB 模式） | 通用缓存 | 热点不均 | 兜底 |

| 维度 | volatile-lru | volatile-lfu | volatile-random | volatile-ttl |
|------|--------------|--------------|-----------------|--------------|
| **淘汰范围** | 仅过期 key | 仅过期 key | 仅过期 key | 仅过期 key |
| **命中** | 中等 | 高 | 低 | 中等 |
| **特点** | 保留永不过期数据 | 同上,LFU 更准 | 简单 | 优先淘汰即将过期 |
| **风险** | 永不过期数据可能占满 | 同左 | 同左 | TTL 设置需精确 |

### 3. 配置方法

```bash
# redis.conf
maxmemory 4gb                              # 设为机器内存的 70%
maxmemory-policy allkeys-lfu               # 推荐 LF
maxmemory-samples 10                       # LRU/LFU 采样数

# 运行时动态修改
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lfu
CONFIG GET maxmemory*
```

> **生产建议**：纯缓存业务推荐 `allkeys-lfu`；有持久化诉求且部分数据不能淘汰用 `volatile-lru`；`noeviction` 仅用于把 Redis 当 DB 用的场景。

### 4. 选型决策树

```
你的 Redis 用途？
│
├── 纯缓存（可丢失）
│   ├── 热点明显（少量 key 被高频访问）
│   │   └── allkeys-lfu ⭐ 推荐
│   └── 访问较均匀
│       ├── 重视最近访问 → allkeys-lru
│       └── 无明显模式 → allkeys-random
│
├── 混合用途（部分数据需保留）
│   ├── 部分 key 永久,部分有过期
│   │   ├── 热点明显 → volatile-lfu
│   │   └── 通用    → volatile-lru
│   └── 想优先淘汰将过期 → volatile-ttl
│
└── 数据全部重要（不能丢）
    └── noeviction（需配套扩内存或迁移）
```

### 5. 触发的命令与返回

```bash
127.0.0.1:6379> SET k v
OK

# 当 maxmemory-policy = noeviction 且内存满时
127.0.0.1:6379> SET newkey newvalue
(error) OOM command not allowed when used memory > 'maxmemory'.

# 读命令仍可执行
127.0.0.1:6379> GET k
"v"
```

## 七、LRU 算法

### 1. 标准 LRU 与 Redis 近似 LRU

**标准 LRU**：为每个 key 维护"最后访问时间"，淘汰时遍历所有 key 找最久未访问的。

```
算法复杂度：O(N) per eviction → 内存大时不可接受
```

**Redis 近似 LRU**：在 eviction pool 中维护一个固定容量的"淘汰候选集"，每次随机采样 N 个 key，与候选集中最差的比较，留下最优的。

### 2. 近似 LRU 工作流

```
┌─────────────────────────────────────────────────────────────┐
│                  Redis 近似 LRU 流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   触发:used_memory > maxmemory                               │
│       │                                                     │
│       ▼                                                     │
│   ┌─────────────────────────────────────────┐                │
│   │ 1. 从全局 dict 随机采样 maxmemory-samples │                │
│   │    个 key(默认 5,推荐 10)                │                │
│   └─────────────────────────────────────────┘                │
│       │                                                     │
│       ▼                                                     │
│   ┌─────────────────────────────────────────┐                │
│   │ 2. 将采样 key 加入 eviction pool (max 16)│                │
│   │    pool 中按 idle 时间排序                 │                │
│   └─────────────────────────────────────────┘                │
│       │                                                     │
│       ▼                                                     │
│   ┌─────────────────────────────────────────┐                │
│   │ 3. 删除 pool 中 idle 时间最大的 key       │                │
│   └─────────────────────────────────────────┘                │
│       │                                                     │
│       ▼                                                     │
│   重复 1-3,直至 used_memory < maxmemory                     │
└─────────────────────────────────────────────────────────────┘
```

### 3. maxmemory-samples 参数

| 值 | 效果 | 性能 |
|----|------|------|
| 1 | 退化为 random | 最快 |
| 5 | 默认值,接近 LRU | 快 |
| 10 | 更接近 LRU | 较慢 |
| 20+ | 接近真 LRU | 明显慢 |

> **生产建议**：设为 10 即可获得 95%+ LRU 效果，对性能影响可忽略。

### 4. 与标准 LRU 对比测试

| 算法 | key 1 | key 2 | key 3 | key 4 | key 5 |
|------|-------|-------|-------|-------|-------|
| 最近访问 | 旧 | 旧 | 旧 | 新 | 新 |
| 真实 LRU 淘汰 | ✓ 淘汰 key 1 | ✓ | ✓ | ✗ | ✗ |
| Redis 近似 LRU | ✓ 大概率 | 大概率 | 大概率 | 偶发 | ✗ |

> 在大量数据下，Redis 近似 LRU 与真实 LRU 的命中率差距通常 < 2%。

## 八、LFU 算法（4.0+）

### 1. LFU 核心思想

LFU（Least Frequently Used）按**访问频率**淘汰，需要更高的频次才能保留。

```
┌─────────────────────────────────────────────────────────┐
│  LFU 决策依据：                                         │
│      score = log(access_count) + ldt(last_decrement_time)│
│                                                         │
│  LRU 决策依据：                                          │
│      score = last_access_timestamp                       │
└─────────────────────────────────────────────────────────┘
```

### 2. LFU 时间衰减机制

LFU 不能让"曾经高频但现在冷"的数据永远占位，需引入衰减。

| 参数 | 默认 | 含义 |
|------|------|------|
| `lfu-log-factor` | 10 | 计数器增量因子,越大增长越慢 |
| `lfu-decay-time` | 1 | 衰减时间(分钟),值越小衰减越快 |

#### 衰减算法

```
衰减时间(分钟) = lfu-decay-time
每过 N 分钟,计数器 -1(若原值 >0),并保持 >=0
新访问时间 - 上次衰减时间 >= lfu-decay-time 时触发
```

### 3. LFU vs LRU 适用场景

| 场景 | LRU | LFU |
|------|-----|-----|
| 周期性热点 | 优 | 优 |
| 突发热点 | 优 | 衰减快则略差 |
| 长尾热点 | 一般 | 优 |
| 大量僵尸数据 | 易留存 | 自然淘汰 |
| 计算开销 | 低 | 中（需衰减维护） |

> **生产推荐**：从 Redis 4.0 起，**默认使用 LFU** 通常是更优选择，因为大部分业务访问都呈幂律分布（少量 key 占大量请求）。

### 4. OBJECT FREQ 与 OBJECT HELP

```bash
127.0.0.1:6379> OBJECT FREQ mykey
(integer) 87                      # 该 key 的访问计数(近似)

127.0.0.1:6379> OBJECT HELP
OBJECT <subcommand> [...]
OBJECT ENCODING <key>
OBJECT FREQ <key>
OBJECT IDLETIME <key>
OBJECT REFCOUNT <key>
OBJECT HELP
```

## 九、内存碎片

### 1. mem_fragmentation_ratio 解读

```
mem_fragmentation_ratio = used_memory_rss / used_memory
```

| 比值 | 含义 | 处置 |
|------|------|------|
| 1.0 ~ 1.5 | 正常 | 无需处理 |
| 1.5 ~ 2.0 | 碎片较多 | 启动自动碎片整理 |
| > 2.0 | 碎片严重 | 立即处理,排查是否扩容 |
| < 1.0 | 使用了 swap | 紧急扩容或减负 |

### 2. 碎片产生原因

```
┌─────────────────────────────────────────────────────────────────┐
│  碎片产生的三大原因                                              │
├─────────────────────────────────────────────────────────────────┤
│  ① 分配器粒度                                                   │
│     - jemalloc 按 size class 分配,小对象共享一个 chunk            │
│     - 即使对象被释放,该 chunk 不能立即被其他 size class 复用       │
│                                                                 │
│  ② Key 删除/修改                                                 │
│     - 大量 key 频繁删除/变更,残留"洞"难以复用                     │
│     - 例:连续 SET 不同长度字符串,分配器碎片严重                    │
│                                                                 │
│  ③ 操作系统内存页                                                │
│     - 即使 Redis 释放内存,OS 不一定立即回收(惰性回收)              │
│     - used_memory_rss 长期高于 used_memory                       │
└─────────────────────────────────────────────────────────────────┘
```

### 3. activedefrag 自动碎片整理（4.0+）

#### 配置

```bash
# redis.conf
activedefrag yes                       # 启用自动碎片整理
active-defrag-enabled no               # 同上,7.0+ 用此配置名

active-defrag-threshold-lower 10       # 碎片率 > 10% 开始整理
active-defrag-threshold-upper 100      # 碎片率 > 100% 全力整理
active-defrag-cycle-min 1              # 最小 CPU 占比 %
active-defrag-cycle-max 25             # 最大 CPU 占比 %
active-defrag-max-scan-fields 1000     # 单次扫描 Hash 字段数
```

#### 推荐生产配置

```bash
active-defrag-enabled yes
active-defrag-threshold-lower 20
active-defrag-threshold-upper 70
active-defrag-cycle-min 5
active-defrag-cycle-max 25
```

### 4. 手动碎片整理

```bash
127.0.0.1:6379> DEBUG RELOAD
OK
```

> **危险操作**：`DEBUG RELOAD` 会序列化所有数据 → 删除 → 重新加载，**生产慎用**，相当于"软重启"。

### 5. 碎片处理完整示例

```bash
# 1. 查看碎片率
127.0.0.1:6379> INFO MEMORY | grep fragmentation
mem_fragmentation_ratio:1.85

# 2. 启用自动碎片整理
127.0.0.1:6379> CONFIG SET activedefrag yes
OK

# 3. 监控整理进度
127.0.0.1:6379> INFO MEMORY | grep active
active_defrag_running:1
active_defrag_hits:1234
active_defrag_misses:5
active_defrag_key_hits:567
active_defrag_key_misses:8
active_defrag_scanned:8901
active_defrag_removed:234

# 4. 关闭自动碎片整理
127.0.0.1:6379> CONFIG SET activedefrag no
OK

# 5. 极端情况:重启(碎片率 > 2.0 持续)
$ redis-cli SHUTDOWN NOSAVE
$ redis-server /etc/redis.conf
```

### 6. 碎片率与 swap

| 现象 | 原因 | 解决 |
|------|------|------|
| `mem_fragmentation_ratio < 1` | Redis 内存被换出到磁盘 | 减少其他进程占用,扩大机器内存 |
| `used_memory_rss` 远大于 `used_memory` | 分配器碎片 / OS 未回收 | 启用 activedefrag |

## 十、大 Key 处理

### 1. 大 Key 的危害

```
┌─────────────────────────────────────────────────────────────────┐
│                  大 Key 的三大危害                                │
├─────────────────────────────────────────────────────────────────┤
│  ① 主线程阻塞                                                   │
│     - DEL/SET/EXPIRE 大 key,主线程同步处理数十毫秒~数秒             │
│     - 同一时间所有客户端命令排队                                   │
│                                                                 │
│  ② 网络带宽阻塞                                                   │
│     - 主从复制时,大 key 全量传输,占用网络                         │
│     - 客户端请求大 value,网卡被打满                               │
│                                                                 │
│  ③ 删除风暴                                                      │
│     - 设置了过期的大 key 在同一时刻过期                             │
│     - DEL 释放内存慢,导致 Redis 卡顿                             │
│     - 主从同步 RBD 重传,雪崩                                    │
└─────────────────────────────────────────────────────────────────┘
```

### 2. 大 Key 的阈值

| 数据类型 | 建议阈值 |
|---------|---------|
| String | > 10 KB |
| Hash | 字段数 > 1000 或总大小 > 10 MB |
| List | 元素数 > 5000 或总大小 > 10 MB |
| Set | 元素数 > 5000 |
| Sorted Set | 元素数 > 5000 |
| Stream | 条目数 > 5000 |

### 3. 查找大 Key

#### (1) redis-cli --bigkeys（推荐）

```bash
$ redis-cli --bigkeys

-------- summary -------
Biggest string found '"session:abc123"' has 20480 bytes
Biggest   list found '"user:feed:1000"' has 5000 items
Biggest    set found '"tag:hot"' has 3000 items
Biggest   hash found '"product:detail:1001"' has 200 fields
Biggest   zset found '"rank:daily"' has 8000 members

12 keys sampled (3.50% of total keys)
40 strings, 100 lists, 20 sets, 30 hash, 5 zsets, 1 stream
```

> **原理**：扫描所有 key,记录每种类型最大的 key。但只能找出"每种类型最大"的 1 个,不够全面。

#### (2) redis-cli --memkeys（Redis 7+）

```bash
$ redis-cli --memkeys
```

#### (3) MEMORY USAGE（精准）

```bash

(integer) 2048

```

#### (4) SCAN + DEBUG OBJECT（脚本化扫描）

```bash

# scan_bigkeys.sh
cursor=0
while [ "$cursor" != "0" ]; do
  result=$(redis-cli SCAN $cursor COUNT 100)
  cursor=$(echo "$result" | head -1)
  keys=$(echo "$result" | tail -n +2)

    size=$(redis-cli MEMORY USAGE "$key")
    type=$(redis-cli TYPE "$key")

      echo "BIGKEY: $key | type=$type | size=${size} bytes"
    fi
  done
done
```

#### (5) RDR（Redis Data Reveal）


#### (1) UNLINK（异步删除，推荐）

| 监控 | 接入 Prometheus + alertmanager |

## 十一、内存优化建议

### 1. 键名简化

```bash
# 优化前
SET user:profile:detail:info:1000 '{"id":1000,"name":"will"}'

# 优化后(去掉冗余层级)
SET u:p:1000 '{"id":1000,"name":"will"}'

# 优化前(过长)
SET cache:order:detail:product:202401010010001 '{"id":...}'

# 优化后(hash tag 方便集群)
SET order:{shard1}:detail:10001 '{"id":...}'
```

> **节省估算**：每 key 短 10 字节,百万 key 节省 10MB,加上 redisObject 开销实际节省更多。

### 2. 选择合适的数据结构

| 场景 | 不推荐 | 推荐 |
|------|--------|------|
| 标签 | List | Set |
| 排行榜 | List + 排序 | Sorted Set |
| 计数器(单字段) | Hash | String + INCR |
| 计数器(多字段) | 多 String | Hash + HINCRBY |
| 短时缓存 | Hash(字段多) | String + JSON |
| 长列表 | List 全量 | List + Listpack 小节点 |

### 3. 用 listpack 替代 hashtable

```bash
# hash-max-listpack-entries 控制切换阈值
hash-max-listpack-entries 128         # 字段 ≤128 用 listpack
hash-max-listpack-value 64            # 单 value ≤64 字节

set-max-listpack-entries 128
set-max-listpack-value 64

zset-max-listpack-entries 128
zset-max-listpack-value 64
```

> 当 Hash 字段少时,listpack 比 hashtable 节省 **60%+ 内存**。

### 4. 控制单 Key 大小

| 类型 | 上限建议 |
|------|---------|
| String | < 10 KB |
| Hash 字段数 | < 1000 |
| List 元素数 | < 5000 |
| Set 元素数 | < 5000 |
| Sorted Set 元素数 | < 5000 |

### 5. 减少元数据

- 用 `int` 编码的 String(数字值直接 int 存储)
- 避免冗余前缀(如 `cache_`, `redis_`)
- 用 `EXPIRE` 而非大对象

### 6. 共享对象池

```bash
# redis.conf
object-sharing-pool-size 1024         # 默认 1024,0 关闭

# 只对 String 整数有效,且需 o(1) 操作
```

> 生产一般关闭,因共享对象会限制 LRU/LFU 精度。

## 十二、多 DB 内存注意事项

### 1. 多 DB 共用 maxmemory

Redis 默认 16 个 db(db0~db15),通过 `SELECT` 切换。**所有 db 共享一个 maxmemory**。

```bash
# redis.conf
databases 16              # db 数量

# 即使在不同 db,只要总内存超 maxmemory 就触发淘汰
127.0.0.1:6379> SELECT 1
OK
127.0.0.1:6379[1]> SET k v
(error) OOM command not allowed when used memory > 'maxmemory'.
```

### 2. 多 DB 的隐患

| 问题 | 说明 |
|------|------|
| 共享 maxmemory | db0 写满可能导致 db1 无法写 |
| DBSIZE 不分库 | 监控指标分 db,需累加 |
| Cluster 不支持 | Redis Cluster 只能用 db0 |
| 备份/迁移复杂 | 跨 db 操作繁琐 |

> **生产建议**：**只使用 db0**。多 db 仅作为"逻辑隔离"工具,且务必在监控中分 db 统计。

### 3. 分 db 监控

```bash
INFO keyspace
# Keyspace
db0:keys=10000,expires=200,avg_ttl=60000
db1:keys=5000,expires=0,avg_ttl=0
```

## 十三、lazyfree 机制

### 1. 为什么需要 lazyfree

默认 DEL 命令是**同步**删除大 key,会阻塞主线程。lazyfree 把"释放内存"的工作交给后台线程:

```
┌─────────────────────────────────────────────────────────────────┐
│  DEL bigkey (同步)                                              │
│  主线程:遍历 listpack / hashtable → 逐元素 free → 整个对象 free    │
│  阻塞:数十毫秒 ~ 数秒                                            │
├─────────────────────────────────────────────────────────────────┤
│  UNLINK bigkey (异步)                                            │
│  主线程:标记对象 + 投递到 bio 任务队列                             │
│  后台线程:异步 free                                              │
│  阻塞:微秒级                                                    │
└─────────────────────────────────────────────────────────────────┘
```

### 2. 支持的命令

| 命令 | 行为 |
|------|------|
| `UNLINK key [key ...]` | 异步删除 |
| `FLUSHDB ASYNC` | 异步清空当前 db |
| `FLUSHALL ASYNC` | 异步清空所有 db |

### 3. lazyfree 配置

```bash
# redis.conf
lazyfree-lazy-eviction yes           # 淘汰时异步释放
lazyfree-lazy-expire yes             # 过期时异步释放
lazyfree-lazy-server-del yes         # DEL 命令改为异步
lazyfree-lazy-user-del no            # UNLINK 始终异步;DEL 由本选项控制
replica-lazy-flush yes               # 从节点执行 FLUSH 时异步
lazyfree-lazy-user-flush no          # FLUSHDB/FLUSHALL ASYNC 由本选项启用

# 异步释放的线程数
bio-cpus-allocator-threshold 1024     # 超过此字节数走异步
```

### 4. lazyfree 监控

```bash
INFO memory
# ...
lazyfreed_objects:2345                # 已异步释放的对象数
```

### 5. 使用建议

| 场景 | 建议 |
|------|------|
| 普通小 key | DEL/UNLINK 均可 |
| 大 key | 必用 UNLINK |
| 全库清空 | FLUSHDB ASYNC |
| 用户代码删除 | 默认 DEL,显式 UNLINK 调优 |

## 十五、生产调优实战

### 1. 案例：内存持续增长至 OOM

```bash
# 1. 看碎片率
127.0.0.1:6379> INFO MEMORY | grep frag
mem_fragmentation_ratio:1.05        # 碎片正常

# 2. 看数据集大小
127.0.0.1:6379> INFO MEMORY | grep used
used_memory:4.2GB
used_memory_peak:4.5GB
used_memory_dataset:4.0GB          # 实际数据占 4GB

# 3. 找大 key
$ redis-cli --bigkeys
Biggest string found '"session:abc"' has 2 MB
Biggest hash found '"product:sku"' has 50000 fields

# 4. 异步删除
127.0.0.1:6379> UNLINK product:sku
(integer) 1

# 5. 释放后查看
127.0.0.1:6379> INFO MEMORY | grep used
used_memory:3.9GB                   # 已降低
```

### 2. 案例：碎片率持续高于 1.5

```bash
# 1. 启用自动碎片整理
127.0.0.1:6379> CONFIG SET active-defrag-enabled yes

# 2. 持续监控
127.0.0.1:6379> INFO MEMORY | grep -E "frag|active_defrag"
mem_fragmentation_ratio:1.45        # 整理后下降
active_defrag_running:1
active_defrag_hits:5678
```

### 3. 案例：从 LRU 切换到 LFU

```bash
# 1. 切换策略
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lfu
OK

# 2. 调大采样数提升精度
127.0.0.1:6379> CONFIG SET maxmemory-samples 10
OK

# 3. 调整 LFU 参数(更适合业务)
127.0.0.1:6379> CONFIG SET lfu-decay-time 5
OK
```

## 核心要点速记

| # | 要点 |
|---|------|
| 1 | **Redis 是内存数据库**,内存管理是核心,**maxmemory + 淘汰策略** 是两道防线 |
| 2 | **内存消耗 = 数据集 + 进程开销 + 缓冲区 + 碎片**,排障要逐项拆解 |
| 3 | `INFO MEMORY` 是必读命令,`mem_fragmentation_ratio` 与 `used_memory_rss` 是关键指标 |
| 4 | **jemalloc** 是默认分配器,碎片率低、并发友好,生产无需替换 |
| 5 | **客户端输出缓冲**分 normal / replica / pubsub,各有 hard-limit / soft-limit |
| 6 | **8 种淘汰策略**:noeviction(默认)、allkeys-lru、allkeys-lfu、allkeys-random、volatile-lru、volatile-lfu、volatile-random、volatile-ttl |
| 7 | **生产推荐 allkeys-lfu**(Redis 4.0+),适合幂律访问;`noeviction` 仅用于 DB 场景 |
| 8 | **LRU 是近似算法**,`maxmemory-samples` 越大越接近真 LRU,生产建议 10 |
| 9 | **LFU 有衰减机制**:`lfu-log-factor`(增量)与 `lfu-decay-time`(衰减),更准识别热点 |
| 10 | **碎片率 > 1.5 启用 `activedefrag`**,< 1 表示使用 swap,需扩容 |
| 11 | **大 Key 危害**:阻塞主线程、占带宽、删除风暴;**用 `--bigkeys` 与 `MEMORY USAGE` 查找** |
| 12 | **删除大 Key 用 `UNLINK`**(异步),比 DEL 不阻塞主线程 |
| 13 | **lazyfree 机制**:`UNLINK`/`FLUSHDB ASYNC`/`FLUSHALL ASYNC` + 4 个 lazyfree 配置项 |
| 14 | **listpack 替代 hashtable** 在小集合时节省 60%+ 内存,合理调整 `hash-max-listpack-entries` |
| 15 | **多 DB 共享 maxmemory**,生产建议只用 db0 |
| 16 | **碎片整理** 优先用 `activedefrag`,极端情况用 `DEBUG RELOAD` 或重启 |
| 17 | **内存优化**:简化键名、选合适结构、控制单 key 大小、用 listpack |
| 18 | **监控告警**:used_memory > 80% maxmemory、fragmentation > 1.5、evicted_keys 异常 |
| 19 | **`PRODUCTION 推荐配置**: maxmemory + allkeys-lfu + samples=10 + activedefrag + lazyfree 全部启用 |
| 20 | **Redis 7+ 新增** listpack-soft/hard-limit、--memkeys 等,提升内存精细化管理能力 |
