# Redis 数据结构与底层编码

## 一、Redis 数据结构总览

很多初学者以为 Redis 只有 5 种数据类型,实际上 Redis 的对象体系是**三层映射**结构:

```text
┌───────────────────────────────────────────────────────────────────┐
│  Redis 对象系统                                                    │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  第一层:用户层(对外数据类型)                                  │  │
│  │  String / Hash / List / Set / ZSet                           │  │
│  │  + 高级类型:Bitmap / HyperLogLog / Geospatial / Stream       │  │
│  │  + Stream / Bloom Filter(Module)                            │  │
│  │                                                              │  │
│  │  特点:开发者直接使用的接口,redisObject.type 字段标识         │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                              ↓ type                               │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  第二层:编码层(encoding)                                    │  │
│  │  embstr / int / raw / hashtable / listpack / skiplist       │  │
│  │  + ziplist(历史) / quicklist / intset / listpack            │  │
│  │                                                              │  │
│  │  特点:同一种类型在不同场景下选择不同编码,redisObject.encoding │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                              ↓ ptr                                │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  第三层:底层数据结构                                         │  │
│  │  SDS / dict / listpack / quicklist / skiplist / ziplist      │  │
│  │  + intset / robj                                             │  │
│  │                                                              │  │
│  │  特点:真正在内存中存储数据的结构                             │  │
│  └──────────────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────────────┘
```

**为什么要设计三层?**

- **解耦**:用户层 API 稳定不变,底层可以根据数据规模和访问模式自动切换更优的编码
- **优化**:小数据用紧凑结构(连续内存、CPU 缓存友好),大数据用通用结构(支持高复杂度操作)
- **演进**:版本迭代只需调整内部编码,无需修改用户接口(典型例子:3.2 用 listpack 替代 ziplist,7.0 用 listpack 全面替代)

**redisObject 通用结构**:

```c
// src/server.h
typedef struct redisObject {
    unsigned type:4;        // 类型:OBJ_STRING / OBJ_LIST / OBJ_HASH ...
    unsigned encoding:4;    // 编码:OBJ_ENCODING_RAW / OBJ_ENCODING_EMBSTR ...
    unsigned lru:LRU_BITS;  // LRU 时间戳(或 LFU 计数器,4.0+)
    int refcount;           // 引用计数(共享对象)
    void *ptr;              // 指向底层数据结构的指针
} robj;
```

> 任意一个 Redis key 在内存中都是一个 `redisObject`,大小为 **16 字节**(64 位系统)。

## 二、五大基础类型总览

### 1. String (字符串)

最简单也最常用的类型。值可以是字符串、整数或浮点数,最大 **512 MB**。

**常用命令**:

| 命令 | 说明 |
|------|------|
| `SET key value [EX s] [PX ms] [NX\|XX]` | 设置值,支持过期和条件 |
| `GET key` | 获取值 |
| `MSET/MGET` | 批量设置/获取 |
| `INCR/DECR/INCRBY/DECRBY/INCRBYFLOAT` | 数值增减(原子) |
| `APPEND key value` | 追加字符串 |
| `STRLEN key` | 字符串长度 |
| `GETRANGE/SETRANGE` | 字符串切片 |
| `SETBIT/GETBIT/BITCOUNT` | 位操作 |

**典型应用**:缓存、计数器、分布式锁(`SET NX PX`)、全局 ID、Session、限流。

### 2. Hash (哈希)

键值对集合(field-value),适合存储**对象**(用户信息、商品规格)。field 和 value 都是字符串,单个 hash 最多 **2³² - 1** 个 field。

**常用命令**:

| 命令 | 说明 |
|------|------|
| `HSET key field value [field value ...]` | 设置 field |
| `HGET key field` | 获取 field 值 |
| `HMSET/HMGET` | 批量设置/获取(4.0 后 HSET 已支持批量) |
| `HGETALL key` | 获取所有 field-value |
| `HDEL key field [field ...]` | 删除 field |
| `HLEN/HEXISTS/HKEYS/HVALS` | 长度/存在/keys/values |
| `HINCRBY key field increment` | field 数值自增 |
| `HSCAN key cursor [MATCH p] [COUNT n]` | 增量迭代 |

**典型应用**:对象存储、用户 Profile、商品属性、标签聚合。

### 3. List (列表)

**双向链表**(实际由 quicklist 实现)实现,有序,可重复,支持头部/尾部 O(1) 插入。最大长度 **2³² - 1**。

**常用命令**:

| 命令 | 说明 |
|------|------|
| `LPUSH/RPUSH key value [value ...]` | 左/右推入 |
| `LPOP/RPOP key [count]` | 左/右弹出 |
| `LRANGE key start stop` | 范围获取 |
| `LINDEX key index` | 按下标获取 |
| `LLEN key` | 列表长度 |
| `LINSERT key BEFORE\|AFTER pivot value` | 指定元素前后插入 |
| `LSET key index value` | 按下标设置 |
| `LREM key count value` | 删除指定元素 |
| `LTRIM key start stop` | 保留区间 |
| `BLPOP/BRPOP/RPOPLPUSH/BRPOPLPUSH` | 阻塞版,用于消息队列 |

**典型应用**:消息队列(简易版)、最新列表(微博时间线)、任务队列。

### 4. Set (集合)

**无序、不重复**的字符串集合。底层是 dict 或 intset,提供交并差运算。最大成员数 **2³² - 1**。

**常用命令**:

| 命令 | 说明 |
|------|------|
| `SADD key member [member ...]` | 添加成员 |
| `SREM key member [member ...]` | 删除成员 |
| `SMEMBERS key` | 获取所有成员(小心大集合) |
| `SISMEMBER key member` | 判断成员是否存在 |
| `SCARD key` | 集合基数 |
| `SPOP key [count]` | 随机弹出一个或多个 |
| `SRANDMEMBER key [count]` | 随机获取(不删除) |
| `SINTER/SUNION/SDIFF` | 交/并/差 |
| `SINTERSTORE/SUNIONSTORE/SDIFFSTORE` | 结果存到目标 key |
| `SSCAN key cursor` | 增量迭代 |

**典型应用**:标签、共同好友、抽奖、UV 统计、黑白名单。

### 5. Sorted Set (ZSet,有序集合)

**有序、不重复**的集合,每个 member 关联一个 score(分数),按 score 升序排列。底层是 **skiplist + dict**(双结构)。

**常用命令**:

| 命令 | 说明 |
|------|------|
| `ZADD key score member [score member ...]` | 添加成员 |
| `ZSCORE key member` | 获取分数 |
| `ZRANGE/ZREVRANGE key start stop` | 按下标范围 |
| `ZRANGEBYSCORE key min max` | 按分数范围 |
| `ZINCRBY key increment member` | 分数自增 |
| `ZCARD key` | 基数 |
| `ZCOUNT key min max` | 区间内成员数 |
| `ZRANK/ZREVRANK key member` | 排名(升/降序) |
| `ZREM/ZREMRANGEBYSCORE/ZREMRANGEBYRANK` | 删除 |
| `ZPOPMIN/ZPOPMAX/BZPOPMIN/BZPOPMAX` | 弹最值 |
| `ZINTERSTORE/ZUNIONSTORE` | 集合运算 |
| `ZSCAN` | 增量迭代 |

**典型应用**:排行榜(销量、积分)、延迟队列、滑动窗口限流、范围查找。

## 三、高级数据类型简介

| 类型 | 引入版本 | 底层 | 核心场景 |
|------|---------|------|----------|
| **Bitmap** | 2.2+ | String(位操作) | 签到、打卡、活跃用户统计 |
| **HyperLogLog** | 2.8+ | String(HLL 算法) | UV 基数统计(误差约 0.81%) |
| **Geospatial** | 3.2+ | ZSet(GeoHash 编码) | 附近的人、地理范围搜索 |
| **Stream** | 5.0+ | radix tree + listpack | 消息队列、事件流 |
| **Bloom Filter** | Module | 位图 + 多个哈希 | 布隆过滤器(RedisBloom 模块) |

### 1. Bitmap

本质是 String 上的位操作,每个 bit 表示 0/1,适合**大规模二值统计**。

```bash
SETBIT sign:user:1 0 1     # 用户1 第0天 签到
SETBIT sign:user:1 1 1     # 用户1 第1天 签到
GETBIT sign:user:1 0       # 查询
BITCOUNT sign:user:1       # 统计签到次数
BITOP OR dest src1 src2    # 多用户并集
```

**空间优势**:1 亿用户每天签到仅占 ~12 MB(1 亿 bit / 8)。

### 2. HyperLogLog

用约 **12 KB** 内存估算**亿级基数**,标准误差 0.81%。**不存储元素本身,不可回查具体 member**。

```bash
PFADD uv:page1 user1 user2 user3
PFADD uv:page1 user2 user4
PFCOUNT uv:page1            # → 4
PFMERGE uv:total uv:page1 uv:page2
```

### 3. Geospatial

底层使用 ZSet,元素坐标被 **GeoHash** 编码为 52 位整数作为 score,支持半径查询。

```bash
GEOADD city 116.40 39.90 beijing
GEOADD city 121.47 31.23 shanghai
GEODIST city beijing shanghai km
GEORADIUS city 116 39 1000 km WITHDIST WITHCOORD
GEOSEARCH city FROMLONLAT 116 39 BYRADIUS 500 km
```

### 4. Stream

5.0 引入,定位**轻量级消息队列**,支持消费者组、ACK、阻塞读、消息回溯。

```bash
XADD mystream * name will age 18
XLEN mystream
XRANGE mystream - + COUNT 10
XREAD BLOCK 0 STREAMS mystream $
XREADGROUP GROUP g1 c1 COUNT 1 STREAMS mystream >
XACK mystream g1 1234567890-0
```

Stream 底层用 **listpack 存消息、rax (radix tree) 存消费者组和消息链表**,详见官方设计文档。

### 5. Bloom Filter(RedisBloom 模块)

判断元素**是否可能存在**(有误判,无漏判),适合**缓存穿透防护、垃圾邮件过滤**。

```bash
BF.ADD user:bf will
BF.EXISTS user:bf will       # → 1
BF.MADD user:bf a b c
BF.RESERVE user:bf 0.01 1000 # 误判率 1%,容量 1000
```

> Bloom Filter 不在 Redis 内核,通过 Module 加载;Redis 内核的 `BF.*` 命令需要在编译时加载 `redisbloom` 模块。

## 四、底层数据结构

### 1. SDS (Simple Dynamic String)

#### (1) 数据结构

Redis **没有直接使用 C 字符串**,而是自己实现了 SDS 作为默认字符串表示(也用于 AOF 缓冲区、客户端输入缓冲区等)。

```c
// sds.h
struct __attribute__ ((__packed__)) sdshdr5 {     // 5.0 已废弃
    unsigned char flags;                           // 低 3 位存类型,高 5 位存长度
    char buf[];
};

struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;        // 已使用字节数
    uint8_t alloc;      // 总分配字节数(不含 header 和 \0)
    unsigned char flags;// 低 3 位类型,高 5 位预留
    char buf[];         // 实际字节数组,末尾 \0
};

struct __attribute__ ((__packed__)) sdshdr16 {
    uint16_t len;
    uint16_t alloc;
    unsigned char flags;
    char buf[];
};

struct __attribute__ ((__packed__)) sdshdr32 {
    uint32_t len;
    uint32_t alloc;
    unsigned char flags;
    char buf[];
};

struct __attribute__ ((__packed__)) sdshdr64 {
    uint64_t len;
    uint64_t alloc;
    unsigned char flags;
    char buf[];
};
```

#### (2) 内存布局

```text
        ┌───┬──────────────┬──────────────┬───────┬───────────────┬─────┐
        │hdr│  len (1/2/4/8) │ alloc (1/2/4/8) │ flags │   buf[N]      │ \0  │
        └───┴──────────────┴──────────────┴───────┴───────────────┴─────┘
         ↑                  ↑                ↑          ↑              ↑
        header             已用长度          已分配       实际字节       末尾\0
                                          (含未用)
```

Redis 根据字符串长度选用不同 header,以节省内存:

| 类型 | header | 适用长度 |
|------|--------|----------|
| sdshdr5 | 1B | < 32(已废弃) |
| sdshdr8 | 3B | < 256 |
| sdshdr16 | 5B | < 65536 |
| sdshdr32 | 9B | < 2³² |
| sdshdr64 | 17B | < 2⁶³ |

#### (3) 与 C 字符串对比

| 维度 | C 字符串 | SDS |
|------|---------|-----|
| **长度** | O(N) 遍历 `strlen()` | **O(1)** 直接读 `len` 字段 |
| **二进制安全** | 不能存 `\0`,以 `\0` 结尾 | **二进制安全**,按 len 判长度,buf 内可有 `\0` |
| **缓冲区溢出** | `strcat` 易溢出 | API 自动检查 alloc,不够则扩容 |
| **内存分配次数** | 每次增长都需重分配 | 空间预分配 + 惰性释放,**减少重分配** |
| **额外开销** | 仅 `\0` 终止符 | len + alloc + flags(几字节) |

> SDS API 通过 **alloc - len** 计算可用空间(`sdsavail`),扩容时优先复用,只有空间不足才 `realloc`,把"分配次数"摊薄到均摊 O(1)。

#### (4) 空间预分配 + 惰性释放

```c
// 增长策略(简化)
new_alloc = len + addlen;
if (new_alloc < SDS_MAX_PREALLOC) {           // 默认 1024*1024 = 1MB
    new_alloc *= 2;                            // 小于 1MB 时翻倍预留
} else {
    new_alloc += SDS_MAX_PREALLOC;              // 否则每次多预留 1MB
}
```

**示例**:`s = "hello"` (len=5) → `sdscat(s, " world")` (新增 6 字节)
- 需分配 ≥ 11 字节 → 按翻倍策略分配 22 字节
- alloc = 22,len = 11,空闲 11 字节(可立即复用)

**惰性释放**:`sdstrim` 不立即归还内存,只更新 `len`,`alloc` 不变,后续追加直接复用。仅当 API 显式释放才真正 `realloc`。

### 2. listpack (紧凑列表,3.2+ 替代 ziplist)

#### (1) 设计动机

ziplist 在级联更新场景下存在 **O(N²)** 的最坏情况(详见下文),Redis 5.0 实验性引入、7.0 全面替代。

#### (2) 结构

```text
┌────────┬────────┬───────┬───────┬───────┬─────┬───────┬─────┬────────┬────────┬────────┐
│ total  │  num   │entry1 │entry2 │ ...   │ ... │entryN │ \0  │end-flag│  (可变)         │
│ Bytes  │  entry │       │       │       │     │       │     │ 0xFF   │                  │
└────────┴────────┴───────┴───────┴───────┴─────┴───────┴─────┴────────┴──────────────────┘
   4B       2B      变长     变长                          1B
```

每个 entry:

```text
┌────────────┬──────────────┬──────────────┐
│ encode-    │  content     │ backlen      │
│ -len/      │  (实际数据)  │ (回退长度)   │
│ content-   │              │              │
│ len        │              │              │
└────────────┴──────────────┴──────────────┘
    1B           变长          1-5B
```

- **encode-len/content-len**:用类似 varint 的编码存 entry 总长度,避免 ziplist 的级联更新
- **backlen**:当前 entry 头到上一 entry 头的字节数,支持反向遍历
- **末尾 \0 + 0xFF**:listpack 结束标记

#### (3) 与 ziplist 对比

| 维度 | ziplist | listpack |
|------|---------|----------|
| **结构** | 连续 entry,每个含 prevlen + encoding + content | 连续 entry,每个含 encode-len + content + backlen |
| **级联更新** | **存在**(prevrawlen 变长需 cascade) | **不存在**(不再依赖前一条的总长度) |
| **反向遍历** | 通过 prevlen 支持 | 通过 backlen 支持 |
| **替换历史** | 7.0 起 List/Hash/ZSet 小集合已弃用 | 5.0 实验性、7.0 全面替代 |

### 3. quicklist (3.2+,linkedlist + listpack 组合)

#### (1) 设计动机

- 双端链表 linkedlist:每个节点一个 malloc,内存碎片多、指针开销大
- ziplist:连续内存,缓存友好,但大列表改造成本高

→ 折中:**双向链表 + 链表节点内嵌 listpack**。

#### (2) 结构

```text
            ┌──────┐     ┌──────┐     ┌──────┐
   prev ←── │quicklist│ ←→ │quicklist│ ←→ │quicklist│ ──→ next
            │  Node   │     │  Node   │     │  Node   │
            │ ┌────┐  │     │ ┌────┐  │     │ ┌────┐  │
            │ │list│  │     │ │list│  │     │ │list│  │
            │ │pack│  │     │ │pack│  │     │ │pack│  │
            │ └────┘  │     │ └────┘  │     │ └────┘  │
            │ size=N  │     │ size=M  │     │ size=K  │
            └──────┘     └──────┘     └──────┘
                 ↑                                ↑
            count 累计                       zlbytes / tail
```

#### (3) 关键字段

```c
typedef struct quicklist {
    quicklistNode *head;        // 头节点
    quicklistNode *tail;        // 尾节点
    long long count;            // 所有 listpack 元素总数
    long long len;              // quicklistNode 数量
    signed int fill;            // 每个 listpack 的最大大小(由 list-max-listpack-size 控制)
    int compress;               // 压缩深度(0=不压缩)
} quicklist;

typedef struct quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *entry;       // 指向 listpack 的指针
    size_t sz;                  // listpack 字节大小
    unsigned int count : 16;    // 该 listpack 内 entry 数
    unsigned int encoding : 2;  // 1=RAW, 2=LZF 压缩
    ...
} quicklistNode;
```

**优势**:既能利用 listpack 的紧凑性,又通过链表节点支持大列表和两端 O(1) 操作。

### 4. skiplist (跳表)

#### (1) 时间复杂度

ZSet 范围查询/排名查询要求 O(log N),skiplist 是 ZSet 的核心实现之一(搭配 dict)。

| 操作 | 平均 | 最坏 |
|------|------|------|
| 查找 | O(log N) | O(N) |
| 插入 | O(log N) | O(N) |
| 删除 | O(log N) | O(N) |
| 范围 | O(log N + M) | O(N) |

#### (2) 多层索引结构图

skiplist 在有序链表上**抽取若干层稀疏索引**,使查找可以"跳"过大量节点:

```text
Level 3:  head ─────────────────────────────────────► 50 ─────────────────────────────►  NIL
                ↓                                       ↓
Level 2:  head ──────────────► 20 ────────────────────► 50 ──────────────► 70 ────────►  NIL
                ↓                 ↓                      ↓                  ↓
Level 1:  head ────────► 10 ────► 20 ────► 30 ────────► 50 ────► 60 ────► 70 ────► 90 ► NIL
                ↓          ↓       ↓        ↓            ↓        ↓        ↓         ↓
Level 0:  head ► 5 ► 10 ► 15 ► 20 ► 25 ► 30 ► 35 ► 40 ► 50 ► 55 ► 60 ► 65 ► 70 ► 80 ► 90 ► NIL
```

**查找示例**:`find 60`

1. Level 3 起步:head → 50(60>50,前进) → NIL,下降到 Level 2
2. Level 2:50 → 70(60<70,后退到 50,下降到 Level 1)
3. Level 1:50 → 60(命中)
4. 仅遍历约 5 个节点即命中

**层数随机化**:每个新插入节点的层数由**幂次定律**随机生成(Redis 中 `ZSKIPLIST_P = 0.25`),保证期望复杂度 O(log N)。

#### (3) Redis 中的 ZSet

```c
typedef struct zset {
    dict *dict;              // member → score 映射(O(1) 按 member 取分)
    zskiplist *zsl;          // 按 score 排序的跳表(O(log N) 范围/排名)
} zset;
```

**双结构原因**:
- skiplist 不擅长按 member 查 score(O(log N) 还不够)
- dict 不擅长按 score 排序/范围
- 二者共享同一份数据,内存换性能

#### (4) 与平衡树对比

| 维度 | skiplist | AVL / 红黑树 |
|------|---------|--------------|
| **时间复杂度** | 平均 O(log N),最坏 O(N) | 严格 O(log N) |
| **实现难度** | 简单 | 复杂(旋转/重平衡) |
| **范围查询** | **天然支持**(沿最底层遍历) | 需中序遍历,实现繁琐 |
| **并发友好** | 局部锁即可 | 全局锁(重平衡牵动多节点) |
| **空间开销** | 多级指针(每节点平均 1.33 层) | 颜色位 + 父指针 |
| **Redis 选择原因** | 实现简单、性能足够、支持 ZRANGEBYSCORE 天然高效 | — |

> Redis 作者 antirez 在 [README](https://github.com/redis/redis/blob/unstable/src/t_zset.c) 注释中明确说:**"There are no skipping lists with this functionality that can be used as a drop-in replacement..."**,skiplist 的实现简洁性是其被选中的核心原因。

### 5. dict (哈希表)

#### (1) 结构

```c
typedef struct dict {
    dictType *type;            // 类型相关操作(哈希函数、key 比较、key/value 释放)
    void *privdata;            // 私有数据
    dictht ht[2];              // 两个哈希表(渐进式 rehash 用)
    long rehashidx;            // rehash 进度,-1 表示未在 rehash
    unsigned long iterators;   // 当前迭代器数量
} dict;

typedef struct dictht {
    dictEntry **table;         // 桶数组
    unsigned long size;        // 桶数量(总是 2 的幂)
    unsigned long sizemask;    // size-1,用于位运算取模
    unsigned long used;        // 已使用 entry 数
} dictht;

typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next;    // 链表 next(冲突链)
} dictEntry;
```

#### (2) 渐进式 rehash ⭐⭐⭐

**问题**:dict 扩容/缩容时,如果一次性把 ht[0] 全部 rehash 到 ht[1],大 dict 会有毫秒级卡顿。

**方案**:把 rehash 拆成**多次、每次少量**的步骤,**摊销**到后续的每次 dict 操作中。

**触发条件**(可在 redis.conf 配置):

| 操作 | 阈值条件 | 默认 |
|------|---------|------|
| 扩容 | `used / size >= 1` 且 `dict_can_resize=1` | load factor ≥ 1 |
| 强制扩容(BGSAVE 期间) | `used / size >= 5` | load factor ≥ 5 |
| 缩容 | `used / size < 0.1` | load factor < 0.1 |

**时序图**:

```text
                    ht[0]                  ht[1]
┌──────────────────────────────┐   ┌──────────────────────────────┐
│ size=4  used=4  load=1.0     │   │ size=8  used=0               │
│ [触发扩容, rehashidx=0]      │   │ [等待中]                      │
└──────────────────────────────┘   └──────────────────────────────┘

   │ 第1次 dictFind / dictAdd / dictDelete
   ▼
rehashidx = 0 → rehash ht[0].table[0] 的桶到 ht[1] → rehashidx = 1

   │ 第2次 dict 操作
   ▼
rehash ht[0].table[1] 的桶 → rehashidx = 2

   │ ... 每次操作搬运一个桶
   ▼
rehashidx = 4 → 全部 rehash 完毕

   │ 下一次 dict 操作
   ▼
ht[0] 释放,ht[1] 提升为 ht[0],分配新 ht[1],rehashidx = -1
```

**关键规则**:

- rehash 期间,**新增**只写到 `ht[1]`(`ht[0]` 不再写)
- rehash 期间,**查找/删除**先查 `ht[0]`,未命中再查 `ht[1]`
- rehash 完成前,**size = ht[0].size + ht[1].size**(used 同理)
- BGSAVE/BGREWRITEAOF 期间**避免扩容**(子进程 COW 节省内存),负载因子阈值提高到 5

#### (3) 负载因子与扩容/缩容

```c
// dict.c
int dictExpand(dict *d, unsigned long size);
int dictRehash(dict *d, int n);  // 每次搬运 n 个桶
```

**rehash 步骤数计算**:Redis 主线程在每次事件循环中,**最多**为 dict rehash 处理 `dictRehashMilliseconds` 毫秒(默认 1ms),限制单次 rehash 的开销。

### 6. ziplist (压缩列表,已被 listpack 替代)

#### (1) 历史背景

7.0 之前,ziplist 是 List/Hash/ZSet 在**元素数较少**时的紧凑编码;7.0 起已替换为 listpack。

#### (2) 结构

```text
┌──────────┬──────────┬─────────┬─────────┬─────┬─────────┬──────┬─────────┬──────┐
│ zlbytes  │  zltail  │ zllen   │ entry1  │ ... │ entryN  │  \0  │ zlend   │      │
│  4B      │   4B     │  2B     │  变长    │     │  变长    │ 1B   │  1B     │      │
│总字节数  │尾节点偏移 │ entry数 │         │     │         │      │0xFF     │      │
└──────────┴──────────┴─────────┴─────────┴─────┴─────────┴──────┴─────────┴──────┘
```

每个 entry:

```text
┌──────────────┬──────────────┬──────────────┐
│ prevrawlen   │  encoding    │  content     │
│ (前一条总长)  │  (类型/长度)  │  (实际数据)  │
│  1B 或 5B    │  1B/2B/5B    │   变长       │
└──────────────┴──────────────┴──────────────┘
```

- **prevrawlen**:前一个 entry 的总字节数,支持反向遍历
- **encoding**:标记 entry 类型(整数 1/2/3/4/8 字节 或 字符串)

#### (3) 级联更新(Cascade Update)

当某个 entry 从 253 字节以内变到 ≥ 254 字节时,`prevrawlen` 由 1B 扩展为 5B,后续 entry 的 `prevrawlen` 可能也需扩展,**链式向后传播**,最坏 O(N²)。**这是 ziplist 被 listpack 替代的核心原因。**

### 7. intset (整数集合)

#### (1) 结构

```c
typedef struct intset {
    uint32_t encoding;  // 元素编码:INTSET_ENC_INT16/INT32/INT64
    uint32_t length;    // 元素数量
    int8_t contents[];  // 有序、不重复的整数数组
} intset;
```

#### (2) 特性

- 仅当 set **所有元素都是整数** 且在阈值(`set-max-intset-entries`,默认 512)内时,使用 intset
- 数组**有序**,支持二分查找(O(log N))
- 添加新元素时若超过现有 encoding 范围,**升级**(全量 realloc),但**不降级**

**升级示例**:`encoding=INT16, {1,2,3}` → 添加 `65535` → 升级为 `INT32`,重新分配数组。

### 8. embstr (嵌入式字符串)

#### (1) 设计动机

对于长度 ≤ 44 字节的字符串,Redis 分配**一块连续内存**同时容纳 `redisObject` + SDS,只需一次 malloc。

#### (2) 内存布局对比

**embstr(≤ 44B)**:

```text
┌──────────────────┬───────────────────────────────────────┐
│ redisObject (16B)│ sdshdr8 (3B) + buf[N] + \0 (1B)       │
│ type/encoding/   │  flags | len | alloc |   实际数据     │
│ lru/refcount/ptr │                                       │
└──────────────────┴───────────────────────────────────────┘
                  一次性 malloc,共 64B(对齐 cache line)
```

**raw(> 44B)**:

```text
┌──────────────────┐         ┌──────────────────────────────┐
│ redisObject (16B)│  ptr ──►│ sdshdr (N bytes) + buf[...]  │
│ ptr 指向外部 SDS │         │  独立的 SDS 内存              │
└──────────────────┘         └──────────────────────────────┘
            两次 malloc
```

#### (3) 为什么是 44 字节

`sizeof(redisObject) + sizeof(sdshdr8) = 16 + 3 = 19` 字节 header。Redis 用 jemalloc/tcmalloc 等分配器,**最小分配单元 64 字节**,剩余 `64 - 19 = 45` 字节给 buf(含 `\0`)。实际 buf 长度阈值 = 44 字节。

#### (4) 编码转换规则

- 长度 ≤ 44B → **embstr**
- 长度 > 44B → **raw**
- 可被解释为整数 → **int**(纯整数专用编码,不存 SDS)

> **注意**:Redis 7.0 引入了 `embstr` 的 64 字节阈值重新调优,但 44 仍是大版本下的主流阈值。

## 七、编码转换阈值

### 1. 完整配置项

所有阈值都可以通过 `redis.conf` 或 `CONFIG SET` 调整,**修改需重启**才会完全生效(部分热加载)。

| 配置项 | 默认 | 含义 |
|--------|------|------|
| `list-max-listpack-size` | `-2` | List 单个 listpack 节点最大大小(quicklist 节点容量);负值表示字节数,正值表示元素数。`-2` = 8KB,`-1` = 4KB,`0` = 64B(legacy 模式),`>0` = 元素数 |
| `list-compress-depth` | `0` | quicklist 两端不压缩的节点数(0=全压缩,1=仅中间压缩,2=两端各留 1 不压缩) |
| `hash-max-listpack-entries` | `128` | Hash 超过此 field 数 → listpack 升级为 hashtable |
| `hash-max-listpack-value` | `64` | Hash 任一 field/value 长度超过此字节 → listpack 升级为 hashtable |
| `set-max-intset-entries` | `512` | Set 整数成员数 ≤ 此值时用 intset,否则用 hashtable |
| `set-max-listpack-entries` | `128` | 7.4+ Set 升级为 hashtable 的元素数阈值(在 listpack 阶段) |
| `set-max-listpack-value` | `64` | 7.4+ Set 单个 member 字节数阈值 |
| `zset-max-listpack-entries` | `128` | ZSet 超过此 member 数 → listpack 升级为 skiplist |
| `zset-max-listpack-value` | `64` | ZSet 单个 member 长度超过此字节 → 升级为 skiplist |
| `string-max-embstr-size` | `44` | String 长度 ≤ 此值用 embstr,否则用 raw |
| `stream-node-max-entries` | `100` | Stream 单个 listpack 节点最大 entry 数 |
| `stream-node-max-bytes` | `4096` | Stream 单个 listpack 节点最大字节数 |

### 2. 升级 vs 降级

```text
listpack  ─── 元素数/长度超阈值 ───►  hashtable / skiplist / quicklist
   ▲                                       │
   │                                       ▼
   └──────── 不会自动降级  ─────────────────┘
```

**重要**:**Redis 不支持编码自动降级**。

- 例如一个 Hash 曾因数据膨胀升级到 hashtable,删除大量数据后**不会**回到 listpack
- 因为降级成本(rehash 一次全量重建)与收益不对称
- 想强制使用某种编码,只能删除 key 重建

### 3. 实战建议

```bash
# 查看当前所有配置
CONFIG GET hash-max-listpack-entries

# 临时调整(部分支持热加载)
CONFIG SET hash-max-listpack-entries 64

# 持久化到 redis.conf
CONFIG REWRITE
```

**调小阈值**:小集合也用 hashtable,提升 HGETALL/HKEYS 性能(但内存变大)
**调大阈值**:更多数据用 listpack,节省内存(但大数据集 listpack 性能差)

### 1. 类型选择决策树

```text
                        ┌─────────────────────────────┐

                        └─────────────────────────────┘
                                       │
        ┌───────────────────┬─────────┴─────────┬───────────────────┐
        ▼                   ▼                   ▼                   ▼
   简单 KV/计数器        对象/属性聚合        队列/栈/时间线       排行榜/范围查
        │                   │                   │                   │
     String              Hash               List                ZSet
                                        (有序、可重复)
                                                            ┌──────────┐
                                                            ▼          │
                                                       去重 / 标签  /  共同好友
                                                            │          │
                                                          Set         Set
                                                       (无序、不重复)

        ┌─────────────────────────┬─────────────────────────────┐
        ▼                         ▼                             ▼
     二值统计                亿级 UV 统计               附近位置 / 消息流
        │                         │                             │
     Bitmap               HyperLogLog             Geospatial / Stream
```

### 2. 编码选择考虑

| 场景 | 推荐编码 | 配置 |
|------|---------|------|
| **小对象(几十字段)** | Hash + listpack | 默认值即可 |
| **大对象(>128 字段)** | Hash + hashtable | 调小 `hash-max-listpack-entries` |
| **排行榜(ZSet)** | ZSet + skiplist | 大集合无脑 skiplist |
| **短 ID 缓存(String)** | String + embstr | 控制在 44B 以内 |
| **超长文本/String** | String + raw | 不可避免 |
| **小整数集合** | Set + intset | 全整数时效率最高 |
| **消息流** | Stream | 5.0+ 默认 |

### 3. 内存优化技巧

```bash
# 1. 用 OBJECT ENCODING 验证编码是否符合预期
OBJECT ENCODING user:1      # 期望 hashtable 或 listpack

# 2. 优先使用 listpack 友好的设计
# - 字段数控制在 hash-max-listpack-entries 以内
# - 单字段值控制在 hash-max-listpack-value 以内

# 3. 利用 Redis 7.0 的 listpack 替代 ziplist(默认即开启)

# 4. 避免大 key(单 key 包含过多元素),使用 SCAN + HSCAN 等增量迭代

# 5. 用 SDS 友好的字符串(短字符串优先)
```

### 4. 性能与内存权衡

```text
紧凑编码(listpack/intset/embstr)        ↔        通用编码(hashtable/skiplist/quicklist)
       ↑                                                   ↑
   内存小、缓存友好                              通用、大数据稳定
   大数据集性能下降                              内存开销大
   适合小数据                                    适合大数据
```

**经验法则**:

- String 长度 ≤ 44B → embstr(更紧凑)
- Hash 字段 ≤ 128 + value 短 → listpack
- Set 全整数且 ≤ 512 → intset(有序+二分)
- List 元素小且少 → quicklist 节点内 listpack
- ZSet 元素 ≤ 128 → listpack(否则 skiplist)

## 十一、核心要点速记

- **Redis 三层结构**:用户层(type)→ 编码层(encoding)→ 底层 ptr(SDS/dict/skiplist/listpack/quicklist/intset/embstr)
- **redisObject 16 字节**:含 type(4b) + encoding(4b) + lru(24b) + refcount(4B) + ptr(8B)
- **五大基础类型**:String / Hash / List / Set / ZSet,加高级类型 Bitmap / HyperLogLog / Geospatial / Stream / BloomFilter
- **SDS 优势**:O(1) 取长度、二进制安全、自动扩容不溢出、空间预分配+惰性释放摊销 O(1)
- **SDS 头类型**:sdshdr8/16/32/64 按字符串长度选择,节省 header 开销
- **listpack 替代 ziplist**:核心是消除级联更新(prevrawlen → encode-len + backlen)
- **quicklist = 双向链表 + listpack 节点**:既紧凑又支持大列表,List 标配
- **skiplist 时间复杂度**:平均 O(log N),最坏 O(N),层数幂次随机生成(P=0.25)
- **ZSet 双结构**:skiplist(范围/排名 O(log N)) + dict(member→score O(1))
- **dict 哈希冲突**:链地址法,新节点插头部
- **dict 渐进式 rehash**:ht[0] + ht[1],每次操作搬运一个桶,均摊扩容开销
- **rehash 期间**:新增只写 ht[1],查找/删除先 ht[0] 后 ht[1]
- **rehash 阈值**:扩容 1.0,缩容 0.1,BGSAVE 期间扩容阈值升到 5
- **intset**:全整数时启用,有序数组支持二分,升级不降级
- **embstr 阈值**:44 字节(64B 对齐 - 19B header),单次 malloc 装 redisObject + SDS
- **Redis 7.0 默认**:List/Hash/ZSet 小集合均使用 listpack
- **OBJECT ENCODING** 查看内部编码:embstr/int/raw/listpack/quicklist/hashtable/skiplist/intset
- **编码升级**:满足阈值自动升级(单向),**不会自动降级**
- **关键阈值配置**:`hash-max-listpack-entries`(128)、`set-max-intset-entries`(512)、`zset-max-listpack-entries`(128)、`list-max-listpack-size`(-2 = 8KB)
- **OBJECT 命令族**:ENCODING / REFCOUNT / IDLETIME / FREQ(LFU),DEBUG OBJECT 看完整字段
- **DEBUG 命令**:POPULATE 灌数据、SLEEP 模拟阻塞、SET-ACTIVE-EXPIRE 关闭主动过期、OBJECTDEST 销毁对象
- **选型决策**:KV/计数 → String;对象 → Hash;队列 → List;去重 → Set;排序范围 → ZSet
- **内存优化**:小集合用 listpack/intset/embstr,避免大 key,常用 SCAN 替代 KEYS
