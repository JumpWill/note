# Redis 高级数据类型

> 在五大基础类型(String / Hash / List / Set / ZSet)之外,Redis 还提供了一组"**面向特定场景**"的高级类型与模块扩展。本章将系统讲解 **BitMap、HyperLogLog、Geospatial、Stream** 四种内置类型,以及 **Bloom Filter、RedisJSON、RediSearch、RedisTimeSeries、RedisGraph** 等主流 Module 的使用方式,并在末尾用一张横向对比表给出选型参考。

---

## 一、BitMap 位图

### 1. 概念与底层

BitMap 并不是一种新的对象类型,而是 **String 类型上的一组位操作指令**。Redis 将 String 看作一段连续的 bit 序列(MSB → LSB),每个 bit 只能是 0 或 1。

| 维度 | 说明 |
|------|------|
| **底层编码** | String(SDS)|
| **取值** | 每个 bit 仅 0 / 1 |
| **正负向索引** | `SETBIT` 偏移从 0 开始,支持负数(从末尾倒数,例如 -1 指最后一个 bit)|
| **自动扩容** | 越界偏移时 Redis 自动补 0 并分配空间,无需手动预分配 |
| **理论上界** | Redis String 最大 512 MB = **2³² bit**,足够覆盖任何常规场景 |

```text
 String 内部 bit 视图(以 8 bit 为单位,共 N 个字节)

 bit 位:  76543210 76543210 ... 76543210
          ┌────────┬────────┐    ┌────────┐
          │ byte 0 │ byte 1 │    │ byte N │
          └────────┴────────┘    └────────┘
 字节偏移:   0        1              N

 说明:
   - SETBIT key offset value  → 偏移 0 即字节 0 的最低位(LSB)
   - GETBIT 读时同样按 offset 寻址
   - 跨字节时自动拼接,无需关心字节边界
```

### 2. 核心命令

| 命令 | 说明 |
|------|------|
| `SETBIT key offset value` | 设置第 offset 个 bit(0/1),offset 从 0 起 |
| `GETBIT key offset` | 读取第 offset 个 bit |
| `BITCOUNT key [start end [BYTE\|BIT]]` | 统计 1 的个数 |
| `BITPOS key bit [start [end [BYTE\|BIT]]]` | 查找指定 bit(0/1)首次出现位置 |
| `BITOP operation destkey key [key ...]` | 多 key 按位运算:AND / OR / XOR / NOT |
| `BITFIELD key [GET type offset] [SET type offset value] [INCRBY type offset increment] [OVERFLOW WRAP\|SAT\|FAIL]` | 位级读写、增减、溢出控制 |

#### (1) SETBIT / GETBIT

```bash
SETBIT sign:user:1001 0 1     # 第 0 天签到(对应 key = "1")
SETBIT sign:user:1001 100 1   # 第 100 天签到
SETBIT sign:user:1001 200 0   # 取消某次签到(等价删除)
GETBIT sign:user:1001 0       # → 1
GETBIT sign:user:1001 365     # → 0(从未签到过)
```

#### (2) BITCOUNT

支持按 **字节区间** 或 **位区间** 统计(7.0+ 支持 BIT 模式)。

```bash
BITCOUNT sign:user:1001                  # 整段
BITCOUNT sign:user:1001 0 30             # 仅统计前 31 个字节(前 248 bit)
BITCOUNT sign:user:1001 0 -1 BYTE        # 同上,负偏移表示末尾
BITCOUNT sign:user:1001 0 0 BIT          # 7.0+ 按位精确统计第一个 bit 段
```

#### (3) BITOP 多元位运算

```bash
BITOP AND  sign:mon  sign:user:1 sign:user:2 sign:user:3   # 三人共同的签到日
BITOP OR   sign:week sign:user:1 sign:user:2 sign:user:3   # 三人任一签到日
BITOP XOR  sign:dif  sign:user:1 sign:user:2               # 仅其中一人签到
BITOP NOT  sign:inv  sign:user:1                           # 按位取反(注意:会强制补齐到等长)
```

返回值为结果 String 的 **字节长度**,可用 `BITCOUNT sign:mon` 得到交集天数。

#### (4) BITPOS

```bash
BITPOS sign:user:1001 1                # 第一个 1 出现的偏移
BITPOS sign:user:1001 0                # 第一个 0 出现的偏移
BITPOS sign:user:1001 1 0 -1 BIT       # 7.0+ 按位精确扫描
```

可用于:**判断某天是否签到、找到连续签到的开始日、定位缺勤段**。

#### (5) BITFIELD(类二进制数组)

`BITFIELD` 把一段 bit 视为**有符号/无符号整数数组**进行读写,适合位级协议、二值压缩存储:

```bash
BITFIELD sign:user:1001 SET u8 0 255       # 把 bit 0-7 当作 u8,设成 255
BITFIELD sign:user:1001 GET u8 0           # 读 u8
BITFIELD sign:user:1001 INCRBY i16 8 1     # bit 8-23 当作 i16,自增 1
BITFIELD sign:user:1001 OVERFLOW SAT INCRBY u8 248 200  # 溢出截断(SAT 模式)
```

`OVERFLOW` 三种策略:
- `WRAP`:环绕回绕(默认)
- `SAT`:饱和到上限/下限
- `FAIL`:溢出时拒绝命令

### 3. 应用场景

| 场景 | 思路 |
|------|------|
| **用户签到** | 一年 365 天 → 一个 key,某位 = 该日是否签到 |
| **日活/留存统计** | 每日一个 BitMap,`BITOP OR` 合并后 `BITCOUNT` |
| **用户画像标签** | 多个 BitMap(性别、地域、兴趣),位运算交叉筛选 |
| **Bloom Filter 简化版** | `BF.RESERVE` 用哈希布隆过滤器;若 key 集合明确且小,BitMap 也凑合 |
| **权限矩阵** | 用 bit 表示角色,位运算校验权限位 |
| **布尔检索** | 用户 × 商品 × 行为的稀疏矩阵,AND/OR 求交集 |

### 4. 完整示例:一年签到统计(800 万用户)

#### (1) 设计

- key 命名:`sign:2026:user:{uid}`
- 偏移 = (当天日期 - 1月1日) = `dayOfYear`,从 0 开始
- 单个用户一年最大 365 bit ≈ 46 B
- **800 万用户 × 46 B ≈ 367 MB**,且可以月维度切片(`sign:202601:user:{uid}` = ~127 B/人/年)

#### (2) 数据准备与签到

```bash
# 用户 uid = 1001,2026-01-01 签到
# 1月1日是当年的第 1 天,偏移 = 0
SETBIT sign:2026:user:1001 0 1

# 签到当天 dayOfYear(假设 3 月 15 日 → 第 74 天)
SETBIT sign:2026:user:1001 73 1

# 连续签到 7 天(73 -> 79)
for i in 73 74 75 76 77 78 79; do
  SETBIT sign:2026:user:1001 $i 1
done
```

#### (3) 个人连续签到天数

```text
思路:用 BITPOS 找到 bit 为 0 的位置,从右往左扫描
```

```bash
# 找到最后一位 0 之前的 1 个数
BITCOUNT sign:2026:user:1001                # 全年累计签到
BITPOS sign:2026:user:1001 0                # 第一个未签到日(若未签到 day = 该值 + 1)

# 从年末倒推:使用 BITPOS 反向搜索(可用 BITPOS + 自定义函数)
# 这里给出常见做法:从某个起点开始,逐位 GETBIT 统计连续 1
```

```python
# Python 示例:计算截止今天 dayOfYear 当天的连续签到
def streak(redis_client, uid, today_day):
    last_zero = -1
    if redis_client.bitpos(f"sign:2026:user:{uid}", 0) is not None:
        last_zero = redis_client.bitpos(f"sign:2026:user:{uid}", 0)
    return today_day - last_zero
```

#### (4) 全平台当日活跃用户

```bash
# 当天所有签到用户:offset dayOfYear = 1
# 方案 A:把当日活跃 uid 写成 Set
SADD dau:20260315 1001 1002 1003 ...

# 方案 B:用 BitMap 全量存储(uid 作为偏移)
SETBIT dau:20260315:b 1001 1
SETBIT dau:20260315:b 1002 1
SETBIT dau:20260315:b 1003 1

# 当日 DAU 数
BITCOUNT dau:20260315:b

# 三日活跃(并集)
BITOP OR dau:3days dau:20260313:b dau:20260314:b dau:20260315:b
BITCOUNT dau:3days

# 三日均活跃(交集)
BITOP AND dau:all3 dau:20260313:b dau:20260314:b dau:20260315:b
BITCOUNT dau:all3

# 仅首日活跃(XOR + 差)
BITOP XOR dau:tmp dau:20260313:b dau:20260314:b
BITOP AND dau:firstOnly dau:tmp dau:20260313:b
BITCOUNT dau:firstOnly
```

#### (5) 内存与性能

| 规模 | 单日 BitMap 大小 | 年维度(46B/人) |
|------|---------------|----------------|
| 1 万用户 | 1.25 KB | 460 KB |
| 100 万用户 | 125 KB | 46 MB |
| **800 万用户** | **1 MB** | **~368 MB** |
| 1 亿用户 | 12.5 MB | 4.6 GB |

> 单次 `SETBIT` / `GETBIT` 时间复杂度 **O(1)**;`BITCOUNT` / `BITOP` 是 **O(N)**,N 为字节数,生产中建议:
>
> - 大 BitMap 拆成多个 key(如按 `uid % 100` 分片)
> - `BITOP OR` 一次性聚合不超过 20 个 key
> - 用 `BYTE` 区间 `BITCOUNT` 限定扫描范围

## 二、HyperLogLog 基数统计

### 1. 概念与定位

**HyperLogLog(HLL)** 是 Redis 2.8 引入的**概率型基数统计算法**,用约 **12 KB** 内存估算**任意大小的集合基数**(理论上限 **2^64**),**标准误差 0.81%**。

| 维度 | 说明 |
|------|------|
| **底层编码** | String(以稀疏/稠密两种稀疏存储 HLL 寄存器) |
| **内存** | 固定 ~12 KB,无论去重多少元素 |
| **误差** | 标准误差 0.81%,由 m=2^14=16384 个寄存器决定 |
| **是否存储元素** | **不存**,不可 `GET` 单个元素,只能 `COUNT` |
| **合并** | 多个 HLL 合并取并集,误差不增长(取所有寄存器最大值) |

### 2. 原理(简化版)

HyperLogLog 基于**伯努利实验**:反复抛硬币直到出现正面,记录第 k 次才出正面的概率约为 **1/2^k**。若某次实验抛了 k 次才出正面,据此可以**反推**该实验中"未曾出现的尾巴长度"。

```text
 算法骨架
 ┌──────────────────────────────────────────────────────────────┐
 │  1. 用哈希函数(如 MurmurHash)把每个元素映射成 64 bit            │
 │  2. 把高位当作桶编号 b(共 m=2^14=16384 桶)                     │
 │  3. 低位从左扫描,首个 1 出现的位置记为 ρ                       │
 │  4. 对桶 b,记录其最大值 max(ρ)                                 │
 │  5. 基数估算 N = α(m) · m² / Σ max(ρ)                          │
 │  其中 α(m) 是调和常数,Redis 用调和平均进一步降低误差          │
 └──────────────────────────────────────────────────────────────┘
```

HLL 不需要遍历元素,**插入和合并都是 O(1)**,查询基数也是 **O(1)**。

### 3. 误差计算示例

假设真实 UV 为 **1000000**(100 万独立用户),HLL 期望输出在 **[991910, 1008090]** 区间(±0.81%)。

| 实际 UV | 期望范围(±0.81%) | 实际误差(若 HLL 输出 998000) |
|---------|------------------|---------------------------|
| 100,000 | 99,190 ~ 100,810 | 0.2% |
| 1,000,000 | 991,900 ~ 1,008,100 | 0.2% |
| 10,000,000 | 9,919,000 ~ 10,081,000 | 0.2% |
| 100,000,000 | 99,190,000 ~ 100,810,000 | 0.2% |

> **不可回查**:HLL 只存"寄存器最大值",**没有 PFGET 这种命令**,也无法判断"某用户是否在某 HLL 中"。

### 4. 命令

| 命令 | 说明 |
|------|------|
| `PFADD key element [element ...]` | 添加元素(去重,重复元素 O(1) 不影响) |
| `PFCOUNT key [key ...]` | 返回基数(单 key / 多 key 合并后估算) |
| `PFMERGE destkey sourcekey [sourcekey ...]` | 把多个 HLL 合并到 destkey |

```bash
# 页面 UV 统计
PFADD uv:page:home  user_001 user_002 user_003
PFADD uv:page:home  user_002 user_004     # user_002 重复,不影响
PFCOUNT uv:page:home                       # → 4

# 多页面去重后的总 UV
PFADD uv:page:detail user_002 user_005
PFCOUNT uv:page:home uv:page:detail        # → 5(去重)

# 把多个 key 合并
PFMERGE uv:20260314 uv:page:home uv:page:detail uv:page:list
PFCOUNT uv:20260314
```

内部细节:

- **稀疏存储**:元素少(< 16000 个)时,Redis 用一种紧凑的 `SPARSE` 编码,**实际占用约 1 KB 左右**
- **稠密存储**:达到阈值后自动转 `DENSE` 编码,固定 12 KB,后续不再增长
- **编码不可逆**:稀疏 → 稠密,**不会**自动转回稀疏

### 5. 应用场景

| 场景 | 用 HLL 替代 Set 的理由 |
|------|----------------------|
| **页面 UV** | Set 存储百万 ID ≈ 数十 MB;HLL 固定 ~12 KB |
| **搜索词去重计数** | 同上,搜索热词基数巨大,但只需要估算值 |
| **注册 IP 数统计** | 千万级 IP,Set 太大;HLL 适合 |
| **跨日合并** | `PFMERGE` 天然支持 |
| **实时大屏** | 固定 O(1) 内存读写 |

**不适用**:
- 需要查询单元素是否存在(`SISMEMBER` 那种)
- 需要 O(N) 内精确去重
- 误差范围不可接受(例如金融去重)

### 6. HLL vs BitMap 对比

| 维度 | BitMap | HyperLogLog |
|------|-------|-------------|
| **底层** | 真实 bit 序列 | HLL 寄存器 + 稀疏/稠密 |
| **精度** | 100% 精确 | 约 99.19% |
| **能查单个 key 元素** | 能(GETBIT/SETBIT) | **不能** |
| **能查某 bit 是否为 1** | **能**(精确) | 不能(只能 COUNT) |
| **多 key 运算** | `BITOP AND/OR/XOR` | `PFMERGE`(只取并) |
| **内存增长** | 线性(O(最大偏移)) | **恒定 ~12 KB** |
| **适合基数** | 已知最大规模(bitmap 大小) | 未知、超大规模 |
| **典型场景** | 签到、活跃、布尔标签 | UV、IP、搜索词 |
| **命令族** | SETBIT / GETBIT / BITCOUNT / BITOP / BITFIELD | PFADD / PFCOUNT / PFMERGE |

> **选型公式**:
> - **需要精确 + 单元素查询** → Set / ZSet
> - **需要布尔交叉 / 单 bit 查询 + 高效内存** → BitMap(已知规模上限)
> - **只要估算值 + 内存恒定** → HyperLogLog

## 三、Geospatial 地理空间

### 1. 概念与底层

Redis 3.2 起,Geospatial(地理空间)被作为独立能力加入,实际底层使用 **Sorted Set**,把经纬度 **按 GeoHash 编码成一个 52 位整数**,作为 ZSet 的 score,城市/POI 名作为 member。

| 维度 | 说明 |
|------|------|
| **底层** | `ZSet`(内部仍用 skiplist + dict) |
| **score** | 52 位 GeoHash 整数 |
| **支持命令** | GEOADD / GEOPOS / GEODIST / GEORADIUS / GEORADIUSBYMEMBER / GEOHASH / GEOSEARCH / GEOSEARCHSTORE |
| **经纬度范围** | 经度 [-180, 180],纬度 [-85.05112878, 85.05112878](极地附近精度严重下降,Redis 限制) |
| **元素上限** | 同 ZSet,理论 2³² - 1 |

### 2. GeoHash 编码简述

GeoHash 把二维经纬度递归二分并交替交织,生成 Base32 字符串。把字符串当 52 bit 整数读:

```text
 经度 39.90 (-180..180) 二分 → 左边 or 右边(0/1)
 纬度 116.40 (-90..90)   二分 → 左边 or 右边(0/1)
 交替穿插经纬 bit,生成 base32 串
 例如:"wx4g8c1y3z5w"
 把它当 52 bit 整数读 → ZSet score
```

```text
 关键特性:
 ┌────────────────────────────────────────────────────────────┐
 │ • 相邻 GeoHash 前缀相同的两个点,真实地理上也很接近            │
 │ • 共 32 字符时,精度约 3.7 cm;12 字符时,精度约 几百米       │
 │ • Redis 截断到 52 bit,精度约 ±5 cm 量级,基本可满足 LBS 业务│
 │ • 邻近查询时:先按 GeoHash 同前缀(或邻域前缀)过滤,再精确距离│
 └────────────────────────────────────────────────────────────┘
```

### 3. 命令

| 命令 | 说明 |
|------|------|
| `GEOADD key [CH] [NX\|XX] longitude latitude member [lng lat member ...]` | 添加/更新地理位置 |
| `GEOPOS key member [member ...]` | 返回经纬度 |
| `GEODIST key member1 member2 [m\|km\|ft\|mi]` | 两点距离 |
| `GEOHASH key member [member ...]` | 返回 11 字符 GeoHash 字符串 |
| `GEOSEARCH key [FROMMEMBER member] [FROMLONLAT lon lat] [BYRADIUS r m\|km\|ft\|mi] [BYBOX w h m\|km\|ft\|mi] [ASC\|DESC] [COUNT n [ANY]] [WITHCOORD] [WITHDIST] [WITHHASH]` | 6.2+ 统一搜索(基于成员/中心点+半径或矩形) |
| `GEOSEARCHSTORE dest src [FROMMEMBER ...] [FROMLONLAT ...] [BYRADIUS ...] [BYBOX ...] [ASC\|DESC] [COUNT n] | 直接把结果存成 ZSet |
| `GEORADIUS key longitude latitude radius m\|km\|ft\|mi [WITHCOORD] [WITHDIST] [WITHHASH] [COUNT n] [ASC\|DESC] [STORE key] [STOREDIST key]` | 6.2 之前的基于坐标搜索,标记 **deprecated**,仍可用 |
| `GEORADIUSBYMEMBER key member radius ...` | 6.2 之前的基于成员搜索,**deprecated** |

#### (1) GEOADD / GEOPOS / GEODIST

```bash
GEOADD city 116.397 39.908 beijing
GEOADD city 121.473 31.230 shanghai
GEOADD city 113.264 23.129 guangzhou
GEOADD city 117.200 39.130 tianjin

GEOPOS city beijing shanghai
# 1) "116.39699804782867432"
# 2) "39.90800007563499091"
# 5) "121.47299960160255432"
# 6) "31.22999947057110305"

GEODIST city beijing shanghai km       # 1067.2648
GEODIST city beijing tianjin km       # 109.7624
```

#### (2) GEOSEARCH(6.2+ 推荐)

```bash
# 半径查询:中心点 (116.40, 39.90),5km 内
GEOSEARCH city FROMLONLAT 116.40 39.90 BYRADIUS 5 km WITHDIST WITHCOORD

# 矩形查询(中心 + 宽×高)
GEOSEARCH city FROMLONLAT 116.40 39.90 BYBOX 10 10 km WITHDIST

# 按成员为圆心
GEOSEARCH city FROMMEMBER beijing BYRADIUS 5 km WITHDIST COUNT 3 ASC
```

输出:

```text
 1) 1) "beijing"
    2) "0.0000"                      # 距中心 km
    3) 1) "116.39"                   # longitude
       2) "39.90"                    # latitude
 2) 1) "tianjin"
    2) "109.7624"
    3) 1) "117.20"
       2) "39.13"
```

#### (3) GEOSEARCHSTORE

```bash
# 直接把搜索结果存成 ZSet(score = 距中心距离),便于做后续运算
GEOSEARCHSTORE city:nearby:beijing city FROMMEMBER beijing BYRADIUS 5 km WITHDIST
ZRANGE city:nearby:beijing 0 -1 WITHSCORES
```

### 4. 应用场景

| 场景 | 说明 |
|------|------|
| **附近的人** | 用户登录时 `GEOADD user:loc uid lng lat`,搜索 `GEOSEARCH` 返回最近 N 个用户 |
| **附近商家** | 商户入驻时 `GEOADD`,客户端按位置搜索(常配合 LBS + 业务过滤) |
| **滴滴打车** | 司机实时 `GEOADD`,乘客下单时搜最近司机 |
| **同城配送** | 校验两地是否同城(GEODIST) |
| **围栏预警** | 持续上报坐标 + GEOSEARCH 判断是否进入/离开某区域 |
| **共享单车** | 实时定位 + 附近可用车辆搜索 |

### 5. 完整示例:附近 5km 内的餐厅

```bash
# 1. 商家入库(北京若干餐厅)
GEOADD restaurants 116.397 39.908 rest:001 "全聚德(前门店)"
GEOADD restaurants 116.412 39.915 rest:002 "海底捞(西单店)"
GEOADD restaurants 116.380 39.910 rest:003 "外婆家"
GEOADD restaurants 121.473 31.230 rest:004 "上海老饭店"
GEOADD restaurants 113.264 23.129 rest:005 "广州酒家"

# 2. 用户搜索:北京西单 (116.38, 39.91) 5km 内的所有餐厅
GEOSEARCH restaurants FROMLONLAT 116.38 39.91 BYRADIUS 5 km \
  WITHDIST WITHCOORD ASC

# 期望输出(rest:004 在上海,不会出现在结果中)
# 1) "rest:003" "外婆家"          距离约 0.3 km
# 2) "rest:001" "全聚德(前门店)"   距离约 1.6 km
# 3) "rest:002" "海底捞(西单店)"   距离约 2.9 km

# 3. 把结果存成 ZSet 用于二级筛选
GEOSEARCHSTORE restaurants:5km restaurants \
  FROMLONLAT 116.38 39.91 BYRADIUS 5 km WITHDIST ASC

# 4. 业务二次过滤(假设筛选人均 < 200 的餐厅,业务表里有 uid → 属性)
# 通过 ZSet 拿所有候选 rest_id,再去 MySQL/ES 拿详情
ZRANGE restaurants:5km 0 -1
```

### 6. 注意事项与边界

| 问题 | 处理 |
|------|------|
| **极地精度问题** | 限制 lat ∈ [-85.05112878, 85.05112878];Redis 自动 clamp |
| **跨经度 180°** | 搜索范围跨 180 度时,`GEOSEARCH` 不会"绕回",需提前过滤 |
| **GeoHash 边界抖动** | 相邻两点 GeoHash 前缀可能突变,只能粗筛;精排由 GEODIST 算 |
| **大 key 性能** | 商家量大时,把 key 按城市分片(`restaurants:beijing` / `restaurants:shanghai`) |
| **GEOADD CH** | `CH` 选项关闭内部 Geohash 距离计算,大并发入库更快;默认 ON(精确) |

## 四、Stream 消息流(5.0+)

### 1. 概念与定位

Redis 5.0 引入 **Stream**,定位**轻量级、持久化的消息队列**。它在 List(`LPUSH/BRPOP`)和 Pub/Sub 基础上补齐了:

- 消息持久化(AOF/RDB)
- 消息 ID 单调递增
- **消费者组**(Consumer Group):每条消息只被组内一个消费者消费
- 消息 ACK + 失败重试(PEL)
- 历史回放(`XRANGE`)

| 维度 | 说明 |
|------|------|
| **底层** | `listpack`(存消息条目)+ `rax`(radix tree,存消费者组、消息链表、消费位点) |
| **消息 ID** | `<milliseconds>-<sequenceNumber>`,毫秒时间戳 + 序号 |
| **最大长度** | 单 stream 元素数同 ZSet(2³² - 1) |
| **消息大小** | 单条消息大小由 `proto-max-bulk-len`(默认 512 MB)约束 |

```text
 Stream 内部结构示意

                 rax (radix tree)
 ┌─────────────────────────────────────────────────────────────┐
 │ msg-id(radix key) ──→ listpack(1) ──→ listpack(2) ──→ ... │
 │                          │             │                    │
 │                          ├── list      ├── list             │
 │                          │   item1     │   itemN            │
 │                          │   item2     │   itemN+1          │
 │                          └─────────────┴────────────────────│
 │                                                              │
 │ group A ──→ last_delivered_id                                │
 │   consumer A1 → PEL(pendings)                                │
 │   consumer A2 → PEL(pendings)                                │
 │ group B ──→ last_delivered_id                                │
 │   consumer B1 → PEL(pendings)                                │
 └─────────────────────────────────────────────────────────────┘
```

### 2. 消息 ID 规则

`XADD mystream * name will age 18` 中的 `*` 表示**自动生成 ID**。Redis 取当前毫秒时间戳 `ms`,若本毫秒已有 N 个消息则序号 = N(从 0 开始):

```text
 ID 格式: <ms>-<seq>
  示例:
   1700000000000-0       # 2023-11-14 22:13:20 第 1 条
   1700000000000-1       # 同毫秒第 2 条
   1700000000001-0       # 下一秒第 1 条(序号重置)

 比较规则:
   整数部分大的 → 大;整数相同时序号大的 → 大;首字符 '-' 用于表达"早于此 ID"
 特殊 ID:
   -          比任何具体 ID 都小(用于 XRANGE - +)
   +          比任何具体 ID 都大
   $          当前 stream 的最大 ID(XREAD 的"只看新")
```

### 3. 命令

| 命令 | 说明 |
|------|------|
| `XADD key [NOMKSTREAM] [MAXLEN/MINID ~\|N/threshold] *\|id field value [field value ...]` | 添加消息 |
| `XLEN key` | 消息条数 |
| `XRANGE key start end [COUNT n]` | 按 ID 升序范围查询(`-` / `+` 表示最小/最大) |
| `XREVRANGE key end start [COUNT n]` | 按 ID 降序 |
| `XDEL key id [id ...]` | 删除消息 |
| `XTRIM key MAXLEN/MINID ~\|N/threshold [LIMIT n]` | 裁剪到指定大小 |
| `XREAD [COUNT n] [BLOCK ms] STREAMS key [key ...] id [id ...]` | 单次/阻塞读 |
| `XREADGROUP GROUP group consumer [COUNT n] [BLOCK ms] [NOACK] STREAMS key [key ...] >\|id` | 消费者组方式读 |
| `XACK key group id [id ...]` | 应答(将消息从 PEL 移除) |
| `XPENDING key group [[IDLE ms] start end count [consumer]]` | 查看 PEL |
| `XCLAIM key group consumer min-idle-time id [id ...] [IDLE ms] [TIME ms] [RETRYCOUNT count] [FORCE] [JUSTID]` | 从其他消费者接管 PEL |
| `XAUTOCLAIM key group consumer min-idle-time start [COUNT count] [JUSTID]` | 7.0+ 自动接管 |
| `XGROUP CREATE key group id\|$ [MKSTREAM] [ENTRIESREAD n]` | 创建消费者组 |
| `XGROUP SETID key group id\|$ [ENTRIESREAD n]` | 重置消费进度 |
| `XGROUP DESTROY key group` | 删除组 |
| `XGROUP CREATECONSUMER key group consumer` | 显式建消费者 |
| `XGROUP DELCONSUMER key group consumer` | 删除消费者 |
| `XINFO STREAM key [FULL [COUNT n]]` | Stream 详情 |
| `XINFO GROUPS key` | 消费者组列表 |
| `XINFO CONSUMERS key group` | 消费者列表 |

### 4. 消费者组机制

```text
 生产者                Stream                  消费者组 G1
  XADD ───────────► [m1 m2 m3 m4 m5 ...] ◄────── XREADGROUP (按 round-robin)
                                                   │
                                                   ▼
                                            consumer A1
                                            consumer A2
                          ┌────────────────── PEL ──────────────────┐
                          │ m3 已读未 ACK                        │
                          │ m4 已读未 ACK                        │
                          │ (XACK 后移除)                           │
                          └────────────────────────────────────────┘

 关键概念:
   • 每个组有 last_delivered_id(消费进度)
   • 每条消息在每个组内只会被一个消费者处理
   • 已读但未 XACK 的消息进入 PEL,XPENDING 可查
   • 消费者宕机后,其他消费者用 XCLAIM/XAUTOCLAIM 接管 PEL
```

### 5. 与 Kafka / Pub/Sub 对比

| 维度 | Redis Pub/Sub | Redis Stream | Kafka |
|------|--------------|--------------|-------|
| **持久化** | 无(订阅者掉线即丢) | 有(RDB/AOF) | 有(磁盘顺序写) |
| **消息回溯** | 不支持 | 支持(XRANGE/XREVRANGE) | 支持(offset) |
| **消费者组** | 不支持 | 支持 | 支持(原生) |
| **每条消息被消费次数** | 所有订阅者各收一份 | 组内 1 个消费者消费 | 组内 1 个消费者消费 |
| **ACK** | 无 | `XACK` + PEL | offset commit |
| **阻塞读** | 无超时控制(`SUBSCRIBE`) | `XREAD BLOCK` | `poll()` |
| **吞吐** | 高但无持久化 | 百万级(单 Stream 单分片) | 千万级(分区分片) |
| **消息大小** | 受 `client-output-buffer-limit` 限制 | 同 | 默认 1 MB(可调) |
| **典型场景** | 实时通知、广播 | 中小规模消息队列、轻量事件溯源 | 大规模日志、事件管道 |

### 6. 应用场景

| 场景 | 说明 |
|------|------|
| **轻量消息队列** | 订单创建 → 通知发货/发短信/统计,Stream + 消费者组 |
| **事件溯源** | 把所有领域事件写入 Stream,通过 `XRANGE` 回溯 |
| **日志收集** | 多服务把日志写 Stream,消费者聚合到 ES/ClickHouse |
| **CDC(变更数据捕获)** | 把 MySQL binlog 变更事件写入 Stream,由下游消费 |
| **实时通知(轻量)** | 不需要严格顺序与重放 → 可选 Pub/Sub;否则用 Stream |

### 7. 完整示例:实时消息流(生产 / 消费 / 消费者组)

#### (1) 生产者写入消息

```bash
XADD orders * order_id O001 user_id 1001 amount 199.00
XADD orders * order_id O002 user_id 1002 amount 88.50
XADD orders MAXLEN ~ 10000 * order_id O003 user_id 1003 amount 320.00
XADD orders * order_id O004 user_id 1001 amount 45.00
```

`MAXLEN ~ N` 用近似裁剪,性能更好(`MAXLEN 10000` 则是精确裁剪)。

#### (2) 单消费者模式(无组)

```bash
# 阻塞读新消息(只读 > 当前位置的新消息)
XREAD BLOCK 0 STREAMS orders $
# 客户端维护 last_id,下次 XREAD 时把 $ 替换

# 回看历史
XRANGE orders - + COUNT 10
XREVRANGE orders + - COUNT 5
```

#### (3) 消费者组模式(多消费者均衡消费)

```bash
# 1) 创建消费者组(从当前最新位置开始)
XGROUP CREATE orders order-group $ MKSTREAM

# 2) 两个消费者,A 读 2 条,B 读 2 条
XREADGROUP GROUP order-group consumer-A COUNT 2 STREAMS orders >
XREADGROUP GROUP order-group consumer-B COUNT 2 STREAMS orders >

# A 会得到 O001、O002
# B 会得到 O003、O004
# 每条消息只进入 1 个消费者的 PEL

# 3) 处理成功后,逐条 ACK
XACK orders order-group 1700000000000-0      # 确认 O001
XACK orders order-group 1700000000000-1      # 确认 O002

# 4) 查看待 ACK 列表
XPENDING orders order-group
# 1) (integer) 2            # 共有 2 条 pending
# 2) "1700000000000-2"      # 最小 pending ID
# 3) "1700000000000-3"      # 最大 pending ID
# 4) 1) 1) "consumer-B"
#       2) "2"               # B 有 2 条 pending

XPENDING orders order-group - + 10
# 详细列出每条 pending 的 consumer / idle time / delivery count

# 5) consumer-A 接管 B 的 PEL(假设 B 宕机 30 分钟)
XCLAIM orders order-group consumer-A 300000 \
  1700000000000-2 1700000000000-3

# 或 7.0+ 自动接管
XAUTOCLAIM orders order-group consumer-A 300000 0 COUNT 10
```

#### (4) 信息查询

```bash
XINFO STREAM orders
# length / radix-tree-keys / groups / last-generated-id / ...

XINFO GROUPS orders
# name / consumers / pending / last-delivered-id / ...

XINFO CONSUMERS orders order-group
# name / pending / idle / ...
```

#### (5) 删除与裁剪

```bash
XDEL orders 1700000000000-2           # 删除指定 ID
XTRIM orders MAXLEN 100000            # 精确裁剪到 10 万条
XTRIM orders MINID 1700000000000-0    # 7.0+ 裁掉比该 ID 早的全部
```

#### (6) 消费幂等建议

Stream **至少一次**投递(可能因网络重试造成重复),业务侧需做幂等:

```text
 推荐幂等方案:
   1. 用消息 ID 作为业务事件 ID,落库时把 ID 作为 UNIQUE 约束
   2. 借助 Redis SETNX:消费前 SET event:dedup:{id} 1 NX EX 86400
   3. 用下游消费者本地表做去重
```

## 五、Bloom Filter 布隆过滤器(RedisBloom 模块)

### 1. 概念与定位

**布隆过滤器**(Bloom Filter)用于判断一个元素**是否可能存在于集合中**:

- **不存在 → 一定不存在**(无漏判)
- **存在 → 可能存在**(有误判,因为不同元素可能哈希到位数组同一位置)

Redis 内核**没有**布隆过滤器,**需要通过 Module 加载**(`redisbloom`,Redis Stack 自带)。Redis Enterprise / 阿里云 Redis / 腾讯云 Redis 多数也提供内置模块。

| 维度 | 说明 |
|------|------|
| **典型误判率** | 0.0001 ~ 0.01 之间可调 |
| **空间复杂度** | m 位数组 + K 个哈希函数(m 与 n·log(1/p) 相关) |
| **插入 / 查询** | 都是 **O(K)**,K 通常 3 ~ 10 |
| **能否删除** | 标准布隆过滤器**不能删**;RedisBloom 提供 **Counting Bloom Filter**(`CF.*`)可选 |
| **是否存储元素** | **不存**,无法回查具体 member |

### 2. 原理

```text
 ┌─────────────────────────────────────────────────────────────────┐
 │  位数组 bit[] (m 位,初始全 0)                                     │
 │                                                                  │
 │   bit[0]  bit[1]  bit[2]  bit[3]  bit[4]  ...  bit[m-1]         │
 │     0      0       0       0       0            0                │
 │                                                                  │
 │  加入元素 e:                                                      │
 │    h1(e)=2, h2(e)=5, h3(e)=9 → 置 1                              │
 │    bit[2]=1  bit[5]=1  bit[9]=1                                    │
 │                                                                  │
 │  查询 e:                                                          │
 │    三个位置 bit[2],bit[5],bit[9]                                 │
 │    全部为 1 → 可能存在                                            │
 │    任一为 0  → 一定不存在                                         │
 └─────────────────────────────────────────────────────────────────┘
```

### 3. 误判率公式

设:
- `n` = 期望插入元素数(capacity)
- `p` = 期望误判率(0 < p < 1)
- `m` = 位数组大小(bit 数)
- `k` = 哈希函数个数

**位数组大小 m**:

```text
       -n · ln(p)
 m = ─────────────────
       (ln 2)²
```

**哈希函数个数 k**:

```text
       m        -ln(p)
 k = ───── · ln ───── = log₂(1/p)
       n         ln 2
```

**示例**:

| n(容量) | p(误判率) | m(bit) | 约等于 KB | k |
|---------|-----------|--------|-----------|---|
| 1,000 | 0.01 | 9,585 | 1.17 KB | 6.6 |
| 100,000 | 0.01 | 958,506 | ~117 KB | 6.6 |
| 1,000,000 | 0.001 | 1,437,752,544 | ~175 MB | 10.0 |
| 100,000,000 | 0.0001 | 191,710,168,561 | ~23 GB | 13.6 |

> 直观结论:**误判率每降低一个数量级,空间翻倍以上**。业务上 0.01(1%)通常足够,不必追求 0.0001。

### 4. 命令

| 命令 | 说明 |
|------|------|
| `BF.RESERVE key error_rate capacity [NONSCALING] [EXPANSION n]` | 创建布隆过滤器(可选自动扩容) |
| `BF.ADD key item` | 添加一个元素 |
| `BF.MADD key item [item ...]` | 批量添加 |
| `BF.EXISTS key item` | 判断是否存在 |
| `BF.MEXISTS key item [item ...]` | 批量判断 |
| `BF.INFO key [CAPACITY\|SIZE\|FILTERS\|ITEMS\|EXPANSION]` | 查看参数与统计 |
| `BF.LOADCHUNK key iterator [DATA chunk]` / `BF.SCANDUMP key iterator` | 2.4+ 增量备份 |
| `CF.RESERVE / CF.ADD / CF.EXISTS / CF.DEL / CF.COUNT` | Counting Bloom(可删) |

```bash
# 1. 创建:误判率 1%,容量 100 万
BF.RESERVE user:bf 0.01 1000000

# 非缩放模式(NONSCALING)固定大小,满了之后报错
BF.RESERVE user:bf 0.01 1000000 NONSCALING

# 自动扩容:每次翻倍,扩到 ~ 32 倍(EXPANSION 默认 2)
BF.RESERVE user:bf 0.01 1000 EXPANSION 2

# 2. 单元素 / 批量
BF.ADD user:bf user:1001
BF.MADD user:bf user:1002 user:1003 user:1004

# 3. 查询
BF.EXISTS user:bf user:1001     # → 1(可能存在)
BF.EXISTS user:bf user:99999999 # → 0(一定不存在)
BF.MEXISTS user:bf user:1002 user:99999999

# 4. 详细信息
BF.INFO user:bf
# 1) Capacity          1000000
# 2) Size              1852843       # 实际占用 bit
# 3) Number of filters 1
# 4) Items inserted    4
# 5) Expansion rate    2
```

### 5. 应用场景

| 场景 | 思路 |
|------|------|
| **缓存穿透防护** | 读 DB 前先问布隆过滤器,过滤掉明显不存在的 key,挡住恶意请求 |
| **爬虫 URL 去重** | 已爬 URL 入过滤,新 URL 先判断再决定是否抓取 |
| **垃圾邮件过滤** | 黑名单邮箱/手机号入过滤,收到时先判断 |
| **推荐去重** | 用户已读文章 ID 入过滤,推荐模块过滤掉 |
| **风控名单** | 把历史欺诈 uid 写入过滤,风控时先判断 |
| **唯一性校验** | 用户名/昵称创建时判断是否已存在 |

**完整示例:缓存穿透防护**:

```python
def get_user(uid):
    # 1. 先查缓存
    user = redis.get(f"user:{uid}")
    if user:
        return user

    # 2. 布隆过滤器拦截不存在的 uid
    if not rbloom.execute_command("BF.EXISTS", "user:bf", str(uid)):
        return None  # 直接拦截,不查 DB

    # 3. 查 DB
    user = db.query("SELECT * FROM user WHERE id=%s", uid)
    if user:
        redis.setex(f"user:{uid}", 3600, user)
        return user

    # 4. 不存在的也要写(避免缓存穿透)
    redis.set(f"user:{uid}:none", 1, ex=60)
    return None
```

> **注意:首次启动需预热**。把所有合法 uid 写入布隆,否则空过滤器会把真实用户全部判为"不存在"。

### 6. 注意事项

| 风险 | 处理 |
|------|------|
| **预热不全导致误杀** | 启动脚本把已有数据全量灌入 |
| **NUM_NONSCALING 满后报错** | 用 `EXPANSION` 允许自动扩容 |
| **只增不删导致误判上升** | 定期重建过滤器 + 重灌数据 |
| **不能列出元素** | 想要遍历请用 Set |
| **业务可接受偶发误判** | 不适合金融交易、库存唯一判定 |

## 六、其他常用模块(Redis Stack)

Redis 4.0 起引入 Module 机制,把"内核之外"的能力作为动态库加载。Redis Stack 把生态主流模块打包发布,**安装一次即可获得 JSON / Search / TimeSeries 等能力**。

### 1. RedisJSON

把 Redis 当**文档数据库**用,原生支持 JSON 数据结构(底层改进自 `ReJSON`),避免业务层反复 `JSON.parse(serialize())`。

| 命令 | 示例 |
|------|------|
| `JSON.SET key $ value` | 存 JSON 文档 |
| `JSON.GET key [path ...]` | 读路径 |
| `JSON.NUMINCRBY key path value` | 数字自增 |
| `JSON.ARRAPPEND key path value [value ...]` | 追加数组元素 |
| `JSON.OBJKEYS / OBJLEN / TYPE` | 对象键查询 |
| `JSON.MERGE / FORGET / CLEAR / DEL` | 合并 / 删除路径 |

```bash
JSON.SET user:1001 $ '{"name":"will","age":18,"tags":["vip","new"]}'
JSON.GET user:1001 $.name                       # "\"will\""
JSON.NUMINCRBY user:1001 $.age 1                # "19"
JSON.ARRAPPEND user:1001 $.tags '"active"'      # 新增 "active" 标签
```

### 2. RediSearch

把 Redis 当**全文检索 + 聚合引擎**,支持二级索引、模糊、向量检索(7.x 起支持 hybrid search)。

| 命令 | 示例 |
|------|------|
| `FT.CREATE idx ON HASH PREFIX 1 user: SCHEMA name TEXT SORTABLE age NUMERIC SORTABLE bio TEXT` | 建索引 |
| `FT.SEARCH idx "@name:will @age:[18 30]" LIMIT 0 10 SORTBY age ASC` | 查询 |
| `FT.AGGREGATE idx "*" GROUPBY 0 @city REDUCE COUNT 0 AS cnt` | 聚合 |
| `FT.SUGADD / FT.SUGGET` | 自动补全建议 |
| `FT.SEARCH idx "*=>[KNN 5 @vec $B]" PARAMS 2 B "\x01\x02..."` | KNN 向量检索 |

### 3. RedisTimeSeries

时序数据库,IO 极高,适合监控 / IoT:

```bash
TS.CREATE cpu:host:01
TS.ADD cpu:host:01 1700000000 65.3         # (时间戳, 值)
TS.RANGE cpu:host:01 1700000000 1700009999  # 查询区间
TS.MRANGE - + FILTER area=cn-east           # 多 series 区间
TS.AGGREGATE cpu:host:01 1700000000 1700009999 AGG avg 60000  # 1 分钟聚合
```

### 4. RedisBloom

除 `BF.*` 之外,还包含 **Counting Bloom / TopK / Cuckoo Filter**(`CF.*`、`TOPK.*`、`CMS.*`),适合滑动窗口、TopN 统计。

### 5. RedisGraph(已停止维护,被 Neo4j / Memgraph 替代)| RedisGears(已并入 Streams + Functions)| 其他

- **RedisGears**:老牌函数式编程模型,部分能力被 Redis Functions 替代
- **RedisLDAP**:企业级 LDAP 鉴权
- **RedisActive-Active / CRDT**:Enterprise 版的地理分布式复制

| 模块 | 能力 | 替代方案 |

## 七、各高级类型横向对比

### 1. 类型选型速查

| 业务需求 | 首选 | 备选 | 关键命令 |
|---------|------|------|---------|
| **二值统计 / 签到 / 活跃** | BitMap | Set | SETBIT / BITCOUNT / BITOP |
| **大规模 UV / IP 数** | HyperLogLog | BitMap(已知上限) | PFADD / PFCOUNT |
| **附近搜索 / LBS** | Geospatial | PostGIS / ES geo | GEOADD / GEOSEARCH |
| **消息队列 / 事件流** | Stream(小中规模) | Kafka / RabbitMQ(大规模) | XADD / XREADGROUP |
| **存在性判断(允许误判)** | Bloom Filter | Set(小规模) | BF.ADD / BF.EXISTS |
| **JSON 文档** | RedisJSON | MongoDB | JSON.SET / JSON.GET |
| **全文/向量检索** | RediSearch | Elasticsearch | FT.SEARCH |
| **时序存储** | RedisTimeSeries | InfluxDB | TS.ADD / TS.RANGE |

### 2. 内存与精度对比表

| 类型 | 内存/数据 | 精度 | 时间复杂度 |
|------|-----------|------|------------|
| **String** | O(长度) | 100% | O(1) |
| **BitMap** | O(最大偏移) bit | 100% | SETBIT/GETBIT O(1),BITCOUNT/BITOP O(N) |
| **HyperLogLog** | **恒定 ~12 KB** | 99.19% | O(1) |
| **Geospatial** | O(N) (ZSet) | 100%(基于 GeoHash 52bit) | GEOADD O(log N),GEOSEARCH O(N+log M) |
| **Stream** | O(N) | 100% | XADD O(1),XRANGE O(N),XREADGROUP O(log N+M) |
| **Bloom Filter** | O(容量·-ln(p)/(ln 2)²) bit | 可配(0.0001~0.01) | O(K) |

### 3. 与基础类型的关系

```text
  高级类型              底层复用基础类型
 ┌─────────────┐
 │  BitMap     │ ───→ String(位操作)
 ├─────────────┤
 │  HyperLogLog│ ───→ String(HLL 寄存器 + 稀疏/稠密)
 ├─────────────┤
 │  Geospatial │ ───→ Sorted Set(score = GeoHash 52bit)
 ├─────────────┤
 │  Stream     │ ───→ listpack(消息) + rax(消费管理)
 ├─────────────┤
 │  Bloom      │ ───→ String(位数组) + 多个哈希(module)
 └─────────────┘
 共同特点:
   1. 都是为特定场景量身定制
   2. 大多在基础类型上做"语义增强"
   3. 命令相对基础类型更"面向业务"
   4. 用错场景会比基础类型更慢、占内存更多
```

## 八、核心要点速记

- **BitMap 是 String 的位操作**:SETBIT / GETBIT / BITCOUNT / BITOP / BITPOS / BITFIELD,底层就是 SDS + 位寻址
- **BitMap 空间优势**:800 万用户一年签到 ≈ 368 MB,单条 SETBIT/GETBIT 是 O(1)
- **BITOP 四种运算**:AND / OR / XOR / NOT;返回字节长度,可与 BITCOUNT 配合统计交集天数
- **BITFIELD 视位为有符号/无符号整数数组**,支持 OVERFLOW WRAP/SAT/FAIL 三种溢出策略
- **HyperLogLog 是基数估算**:固定 ~12 KB,标准误差 0.81%,最多估 2^64 个元素,**不可回查单元素**
- **HLL 命令**:PFADD / PFCOUNT / PFMERGE;PFCOUNT 可一次合并多 key 取并集估算
- **HLL 内部编码**:稀疏 → 稠密(达阈值后),总内存 ~12 KB;稀疏阶段实际占用 ~1 KB
- **Geospatial 底层是 ZSet**:score = 52 bit GeoHash 整数,element 经 GeoHash 编码
- **GEO 命令**:GEOADD / GEOPOS / GEODIST / GEOHASH / GEOSEARCH / GEOSEARCHSTORE;GEORADIUS 已 deprecated
- **GeoHash 简述**:经纬度交替二分并穿插,生成 Base32 串;52 bit 时精度约 ±5 cm 量级
- **GEOSEARCHSTORE 把搜索结果写成 ZSet**:score = 距中心距离,方便二次过滤
- **Stream 5.0+ 引入**:消息 ID = `<ms>-<seq>`,毫秒时间戳 + 序号;特殊 ID 有 `-`/`+`/`$`
- **Stream 命令总览**:XADD / XLEN / XRANGE / XREVRANGE / XREAD(单次)/ XREADGROUP(组)
- **Stream 管理**:XDEL / XTRIM(MAXLEN~近似、MINID 按 ID)/ XINFO STREAM/GROUPS/CONSUMERS
- **Stream ACK 流程**:XREADGROUP 进入 PEL → 业务处理 → XACK 移除;失败时 XPENDING 可查
- **Stream PEL 接管**:XCLAIM 手动 / XAUTOCLAIM(7.0+)按空闲时间自动接管
- **Stream ≥Kafka 主要差距**:水平扩展 / 高吞吐 / 强顺序 / 多分区事务;Stream 更适合中小规模、追求轻量
- **Stream 至少一次投递**:消费侧必须有幂等机制(ID 唯一约束 / Redis SETNX 等)
- **Bloom Filter 通过 Module 加载**:BF.RESERVE / BF.ADD / BF.MADD / BF.EXISTS / BF.MEXISTS / BF.INFO
- **BF 容量与误判率公式**:`m = -n·ln(p) / (ln 2)²`;`k = log₂(1/p)`,n 千万 / p=1% → m ≈ 1.19 亿 bit ≈ 14.5 MB
- **Bloom Filter 特征**:无漏判、有误判;不存元素;不能删除(Counting 除外);需启动时预热
- **BF.RESERVE 选项**:`NONSCALING` 满即报错;`EXPANSION n` 自动倍增容量(默认 2)
- **Redis Stack 模块**:RedisJSON(文档)/ RediSearch(全文+向量)/ RedisTimeSeries(时序)/ RedisBloom(布隆+TopK)
- **常见对照**:BitMap vs HLL vs Set;Stream vs Kafka vs PubSub;Geospatial vs PostGIS / ES
- **不可回查单元素**:HLL、Bloom Filter 都只存"是否可能";需要精确查询请用 Set / ZSet
- **选型三步法**:① 需要精确单元素?否 → ② 内存可接受?否 → HLL / Bloom;③ 场景:签到→BitMap,UV→HLL,LBS→Geo,事件→Stream,去重→Bloom
- **持久化**:BitMap/HLL/Stream/Bloom 全部共享 Redis 的 RDB + AOF 机制,数据可以恢复
- **GEO 边界**:纬度限制 [-85.05112878, 85.05112878];极地范围不可用,Redis 自动 clamp
- **Stream 消息大小**:受 `proto-max-bulk-len`(默认 512 MB)和 `stream-node-max-entries/bytes` 控制
- **所有高级类型命令都建议在低 QPS 时段演练**:BITOP 大范围、BF.RESERVE 大容量、XADD 高并发都要压测
