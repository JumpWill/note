# Redis 架构模式

> 本章系统梳理 Redis 在生产环境中可选的四种架构模式(单机、主从、哨兵、Cluster),从演进路径、核心机制、优缺点、容量规划、客户端接入、选型决策树等维度建立完整的认知框架。后续章节(09 主从复制、10 哨兵、11 Cluster)会对每种模式做深入剖析,本章定位于"全局视图 + 选型决策"。

---

## 一、Redis 架构演进总览

### 1. 演进驱动力

Redis 架构的演进本质上是**业务规模**对**数据量、并发量、可用性**三方面要求不断升级的过程:

```text
┌──────────────────────────────────────────────────────────────────┐
│  单机  ──►  主从  ──►  哨兵  ──►  Cluster  ──►  分片集群 + 多副本   │
│  1台     多副本       自动故障    分布式        多集群混合          │
│  <10GB   冗余+读写分离  秒级切换   16384槽       海量数据            │
└──────────────────────────────────────────────────────────────────┘
       ▲           ▲          ▲           ▲              ▲
       │           │          │           │              │
    简单        数据冗余    高可用      水平扩展       无限扩展
```

### 2. 四种模式速览

| 模式 | 数据量级 | 并发量级 | 可用性 | 部署复杂度 | 代表场景 |
|------|----------|----------|--------|------------|----------|
| **单机** | < 10 GB | 1-5w QPS | 单点 | ★ | 开发测试、小型缓存 |
| **主从** | < 20 GB | 1-10w QPS | 需人工切换 | ★★ | 读写分离、备份 |
| **哨兵** | < 50 GB | 1-10w QPS | 秒级自动 | ★★★ | 中小型业务高可用 |
| **Cluster** | 100GB+ | 10w+ QPS | 自动故障 | ★★★★ | 中大型分布式生产 |

### 3. 核心取舍

```text
            数据量小                数据量大
                │                     │
            单机/主从 ◄──────────► Cluster
                │                     │
        可用性要求低            可用性要求低
                │                     │
        (开发/边缘业务)        (内部离线缓存)
                │
                ▼
        主从+手动切换
                │
                ▼
        哨兵(自动故障)
                │
                ▼
        Cluster(分片+自动)
```

> **核心原则**:能用单机解决的不要分布式、能用主从解决的不要 Cluster。分布式带来分片路由、跨节点事务、客户端复杂度等额外负担,**不是越复杂越好**。

## 二、单机模式 (Standalone)

### 1. 什么是单机模式

单机模式即**单个 Redis 实例**承担全部读写,无副本、无哨兵、无集群。所有数据保存在**一份内存 + 一份持久化文件**(RDB/AOF)中。

```text
                ┌─────────────────────┐
                │    Redis 单实例     │
   Client ────► │  port: 6379         │
   (读/写)      │  maxmemory: 8GB     │
                │  RDB + AOF         │
                └─────────────────────┘
                        │
                        ▼
                ┌─────────────────────┐
                │  /var/lib/redis/    │
                │  dump.rdb           │
                │  appendonly.aof     │
                └─────────────────────┘
```

### 2. 优点

| 优点 | 说明 |
|------|------|
| **部署极简** | 一条命令启动,无配置文件依赖,适合开发环境 |
| **性能最高** | 没有副本同步、没有 Gossip 开销,单线程命令执行无锁 |
| **运维成本低** | 无需关注复制延迟、槽位迁移、选主脑裂 |
| **强一致(单点)** | 数据全部落在一台机器,没有跨节点一致性顾虑 |
| **事务完整** | MULTI/EXEC、Lua 脚本跨 key 无限制 |

### 3. 缺点

| 缺点 | 影响 |
|------|------|
| **单点故障** | 进程崩溃 = 服务完全中断,即使有 RDB 也有数据丢失窗口 |
| **内存上限** | 单机内存受物理机限制,通常 64-256GB 是天花板 |
| **QPS 上限** | 单实例约 10w QPS,超过则 RT 飙升、连接排队 |
| **无水平扩展** | 数据量增长只能纵向加内存,无法横向加节点 |
| **运维风险** | 持久化 fork 会阻塞主线程,大 Key 场景下 IO 抖动明显 |

### 4. 适用场景

```text
✔ 本地开发 / 单元测试
✔ 小型项目(<10GB,非关键业务)
✔ 内部工具缓存(可重建、可丢失)
✔ Session / Token 临时存储(可重新登录)
✘ 生产关键业务(资金、订单、库存)
✘ 大数据量场景(>50GB)
✘ 高并发场景(>10w QPS)
```

### 5. 单机模式下的数据安全补丁

即使使用单机,也要做好**基础防护**:

```conf
# redis.conf 单机模式必配项
port 6379
bind 0.0.0.0
protected-mode yes
requirepass "StrongP@ssw0rd!2026"

# 持久化:开启混合持久化(7.x)
save 900 1
save 300 10
save 60 10000
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes

# 内存管理
maxmemory 8gb
maxmemory-policy allkeys-lru

# 慢查询
slowlog-log-slower-than 10000
slowlog-max-len 128
```

## 三、主从复制模式 (Master / Slave)

### 1. 核心作用

主从复制是 Redis 最基础的**冗余 + 读写分离**方案,通过一台 Master 同步数据到 N 台 Slave,实现**数据冗余、读扩展、故障备份**三大目标。

```text
                          ┌─────────────────┐
                          │   Master        │
                          │  (读写)          │
                          │  replication    │
                          │  stream         │
                          └────────┬────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
     ┌─────────────┐       ┌─────────────┐       ┌─────────────┐
     │  Slave-1    │       │  Slave-2    │       │  Slave-3    │
     │  (读)       │       │  (读)       │       │  (读/灾备)  │
     └─────────────┘       └─────────────┘       └─────────────┘
```

### 2. 三大作用

| 作用 | 说明 |
|------|------|
| **数据冗余** | Master 故障时数据不丢,Slave 是热备份 |
| **读写分离** | Master 写入,Slave 分摊读压力(读多写少场景可显著提升 QPS) |
| **故障备份** | 故障后 Slave 可提升为新 Master(需要人工切换或 Sentinel 协助) |

### 3. 一主多从 vs 级联复制

**一主多从**(扁平结构):

```text
                          ┌─────────────────┐
                          │   Master        │
                          └─────────────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
       Slave-1                 Slave-2                 Slave-3

   优点:结构清晰;缺点:Master 同步压力大(Slave 多时带宽成为瓶颈)
```

**级联复制**(树状结构,缓解 Master 同步压力):

```text
                          ┌─────────────────┐
                          │   Master        │
                          └─────────────────┘
                                   │
                                   ▼
                          ┌─────────────────┐
                          │  Slave-1        │
                          │  (中间节点)      │
                          └─────────────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
       Slave-2                 Slave-3                 Slave-4

   配置:Slave-1 开启 repl-backlog,关闭 read-only=NO(允许继续复制)
   适用:Slave 数量 ≥ 5 时,降低 Master 出网带宽
```

### 4. 优缺点

| 维度 | 优点 | 缺点 |
|------|------|------|
| **数据** | 多副本冗余 | 主从异步复制,Master 宕机可能丢最后几秒数据 |
| **可用性** | Slave 可作为故障切换候选 | **必须人工切换**,不可自动 |
| **读扩展** | 一主多从分散读 | Slave 越多,Master 同步压力越大 |
| **运维** | 配置简单 | 需自研监控切换脚本(否则只能用 Sentinel) |
| **数据量** | - | 仍受单机内存限制,**不解决水平扩展** |

### 5. 关键配置

```conf
# ========== Slave 节点配置 ==========
port 6380
replicaof 192.168.1.10 6379          # 声明主节点
masterauth "your_master_password"     # 主节点认证
replica-read-only yes                 # 从节点只读(强烈推荐)
repl-diskless-sync no                 # 走磁盘中转;大数据集可改 yes
repl-backlog-size 64mb                # 部分重同步缓冲区,适当加大
repl-ping-replica-period 10           # 心跳间隔
repl-timeout 60                       # 复制超时
```

> **详细原理与同步机制见第 10 章《Redis 主从复制》。**

## 四、哨兵模式 (Sentinel)

### 1. 哨兵在主从基础上的角色

Sentinel 是 Redis **官方**的高可用(HA)方案,在主从复制之上提供**自动故障检测、自动故障转移、自动配置发现**三大能力。它**不解决数据量问题**,只解决"单组主从的自动切换"。

```text
                     Sentinel 集群 (推荐 ≥ 3 节点,奇数)
                   ┌────────────────────────────┐
                   │  Sentinel-1   (可能 Leader)│
                   │  Sentinel-2                │
                   │  Sentinel-3                │
                   └─────────────┬──────────────┘
                                 │ 监控 / 仲裁 / 通知
                                 ▼
              ┌─────────── Master ─────────────┐
              │     redis-6379                │
              └──────┬──────────┬─────────────┘
                     │          │
                  复制 ▼          ▼ 复制
              ┌──────────┐  ┌──────────┐
              │ Slave-1  │  │ Slave-2  │
              │ redis-6378│  │ redis-6377│
              └──────────┘  └──────────┘
```

### 2. 哨兵集群要求

| 要求 | 推荐值 | 说明 |
|------|--------|------|
| **节点数量** | **≥ 3,奇数** | 2 节点无法形成多数派,4 节点与 3 节点容错能力相同 |
| **部署位置** | 跨机器、跨机柜 | 避免与 Redis 同机器(否则哨兵挂 = Redis 也挂) |
| **通信** | 哨兵间 + 哨兵-Redis 间均独立 | 哨兵互相独立判定,避免单点 |
| **客户端** | 通过 Sentinel 拿 Master 地址 | 客户端需支持 Sentinel 协议(JedisSentinelPool 等) |

### 3. 故障转移核心流程

```text
T0  Sentinel-A  PING Master 超时  ─► 标记 SDOWN(主观下线)
                │
                ▼
T1  Sentinel-A 询问 Sentinel-B、C
     B 同意 + C 同意 ─► 多数派达成 ─► 标记 ODOWN(客观下线)
                │
                ▼
T2  触发选主流程
     - 过滤:剔除 SDOWN、断连超时、最近 5 秒未回复 INFO
     - 排序:优先级 replica-priority → 复制偏移量 → runid 字典序
     - 选出 Leader Sentinel 发起 failover
                │
                ▼
T3  Leader Sentinel 执行 failover
     1. 向目标 Slave 发 `SLAVEOF NO ONE`,提升为新 Master
     2. 向其他 Slave 发 `SLAVEOF 新 Master`,重新指向
     3. 将旧 Master 标记为新 Master 的 Slave(等其恢复)
     4. 通过 Pub/Sub 通知客户端配置变更
                │
                ▼
T4  客户端收到切换通知,自动连接新 Master(需客户端支持 Sentinel)
     业务感知时间:通常 < 30 秒
```

### 4. 优缺点

| 维度 | 优点 | 缺点 |
|------|------|------|
| **自动切换** | 秒级故障检测 + 自动选主 | 切换期间存在数十秒不可写窗口 |
| **客户端透明** | 客户端通过 Sentinel 自动发现新 Master | 老客户端需改造支持 Sentinel |
| **数据安全** | 多副本冗余 | 主从异步,极端情况丢最后几秒写入 |
| **数据量** | - | **仍受单机内存限制**,不解决水平扩展 |
| **脑裂防护** | 多数派仲裁 | 网络分区下仍可能脑裂,需配置 `min-replicas-to-write` |

### 5. 关键配置

```conf
# ========== Sentinel 节点配置 (sentinel.conf) ==========
port 26379
daemonize yes
logfile "/var/log/redis/sentinel.log"

# 监控的主节点(mymaster 是名字,2 表示至少 2 个 Sentinel 同意才判定下线)
sentinel monitor mymaster 192.168.1.10 6379 2

# 主节点密码(若启用)
sentinel auth-pass mymaster "your_master_password"

# 判定下线时间(默认 30s,可适当调低至 10-15s)
sentinel down-after-milliseconds mymaster 10000

# 故障转移超时(默认 180s)
sentinel failover-timeout mymaster 60000

# 同步并行数(同时向新 Master 发起复制的 Slave 数量)
sentinel parallel-syncs mymaster 1

# 防止脑裂:至少 1 个 Slave 在线才允许写
sentinel set mymaster min-replicas-to-write 1
sentinel set mymaster min-replicas-max-lag 10
```

> **详细原理、SDOWN/ODOWN 判定、Leader 选举、客户端对接见第 11 章《哨兵 Sentinel》。**

## 五、Cluster 集群模式 (Redis Cluster)

### 1. 什么是 Redis Cluster

Redis Cluster 是 Redis **3.0+** 推出的**官方分布式方案**,同时解决**数据分片 + 高可用**两大难题。它通过 **16384 个哈希槽**将数据分散到多台 master,并内置**自动故障转移**机制。

```text
                    Redis Cluster (≥ 6 节点,3 master + 3 replica)
                   ┌───────────────────────────────────────────┐
                   │                  Gossip                    │
                   │   M1 ←─────► M2 ←─────► M3                │
                   │    ↕          ↕          ↕                 │
                   │   S1         S2         S3                 │
                   └───────────────────────────────────────────┘
                      │           │           │
              slot 0-5460   5461-10922   10923-16383
```

### 2. 核心概念

#### 2.1 哈希槽 (Hash Slot)

```text
  key ───► CRC16(key) & 0x3FFF ───► slot 号 (0 ~ 16383)
  "user:1001"  → 0xA3F2 & 0x3FFF → 12176

  16384 slots 在 N 个 master 间摊派:
  ┌──────────────────┬──────────────────┬──────────────────┐
  │  slot 0-5460     │  slot 5461-10922 │  slot 10923-16383│
  │  (5461 个)       │   (5462 个)      │  (5461 个)       │
  │  Master-1        │  Master-2        │  Master-3        │
  └──────────────────┴──────────────────┴──────────────────┘
            │                  │                  │
            ▼                  ▼                  ▼
       Replica-1         Replica-2         Replica-3
```

**为什么是 16384?**

- Gossip 消息携带 slot 位图,**2KB** vs 65536 的 8KB,带宽友好
- Redis 集群主节点一般不超过 1000 个,16384 已足够均匀
- `2^14` 位运算快,客户端路由计算高效

#### 2.2 hashtag(强制同槽)

```bash
# 大括号包裹的部分作为 hashtag,强制同 slot
> CLUSTER KEYSLOT "{user:1000}.profile"
(integer) 2417
> CLUSTER KEYSLOT "{user:1000}.order"
(integer) 2417

# 适用:多 key 操作(MGET/MSET/Lua 脚本跨 key 必须同 slot)
```

#### 2.3 MOVED / ASK 重定向

| 类型 | 含义 | 客户端处理 |
|------|------|-----------|
| **MOVED** | slot 已稳定在新节点(永久重定向) | 更新本地 slot 缓存表,后续请求直连新节点 |
| **ASK** | slot 正在迁移中(临时重定向) | 发送 `ASKING` 命令后再请求,**不更新**本地 slot 表 |

### 3. 故障转移

Cluster 内置自动故障转移,**无需 Sentinel**:

```text
1. Master-2 失联
2. 其他节点本地标记 PFAIL(主观下线)
3. 大多数 Master 认定 PFAIL ─► 升级为 FAIL(客观下线)
4. Master-2 的 Replica 发起选举,自增 currentEpoch
5. 获半数以上 Master 投票 ─► 升为新 Master
6. 广播 Pong 消息通知全集群拓扑变更
```

> **脑裂防护**:选举需多数票,网络分区下不会出现双 Master,这是 Cluster 相比 Sentinel 的一个重要优势。

### 4. 客户端感知

客户端(智能客户端,如 JedisCluster、Lettuce)**本地缓存 slot → node 映射**:

```text
客户端首次请求:
  GET key:A
  ─► CRC16("A") = 8234,slot 8234 → 查本地表 → 路由到 M2
       │
       ▼ (若本地表陈旧)
  M2 返回: -MOVED 8234 192.168.1.12:6380
       │
       ▼
  客户端更新本地表,重发请求到 M3
       │
       ▼
  正常响应
```

### 5. 优缺点

| 维度 | 优点 | 缺点 |
|------|------|------|
| **数据量** | 16384 槽横向扩展,支持 TB 级 | 单 key 仍受单机内存限制 |
| **并发量** | 多 master 分摊 QPS | 多 key 操作必须同 slot(hashtag 解决) |
| **可用性** | 自动故障转移,内置多数派 | 不支持 `SELECT`,仅 db 0 |
| **运维** | 无中心 Proxy,运维工具丰富(`redis-cli --cluster`) | 扩缩容需 reshard,大 key 迁移慢 |
| **事务** | Lua 脚本支持跨 key(同 slot) | MULTI/EXEC 跨 slot 报错 CROSSSLOT |
| **客户端** | 智能客户端本地路由,性能高 | 不支持事务回滚的客户端代码会失败 |

### 6. 关键配置

```conf
# ========== Cluster 节点配置 (redis.conf) ==========
cluster-enabled yes
cluster-config-file nodes-6379.conf
cluster-node-timeout 15000

# slot 覆盖:部分不可用时仍提供服务(生产推荐 no)
cluster-require-full-coverage no

# replica 验证:防止脑裂(至少 1 个 replica 在线才允许写)
cluster-replica-validity-factor 10
cluster-migration-barrier 1

# 集群总线端口(默认 16379,客户端端口 + 10000)
cluster-announce-port 6379
cluster-announce-bus-port 16379
cluster-announce-ip 192.168.1.11
```

> **详细原理、reshard 流程、客户端实现、生产部署见第 12 章《Cluster 集群》。**

## 六、各架构模式对比表

### 1. 核心能力对比

| 能力 | 单机 | 主从 | 哨兵 | Cluster |
|------|------|------|------|---------|
| **数据冗余** | ✘ | ✔ | ✔ | ✔ |
| **读写分离** | ✘ | ✔ | ✔ | ✔ |
| **自动故障转移** | ✘ | ✘(需人工) | ✔(秒级) | ✔(多数派) |
| **客户端配置发现** | ✘ | ✘ | ✔(Pub/Sub) | ✔(MOVED/ASK) |
| **水平扩展** | ✘ | ✘ | ✘ | ✔(16384 槽) |
| **脑裂防护** | ✘ | ✘ | 部分(min-replicas) | ✔(多数派) |
| **多 key 事务** | ✔ | ✔ | ✔ | 部分(需 hashtag) |
| **Lua 跨 key** | ✔ | ✔ | ✔ | ✔(同 slot) |
| **SELECT 多 DB** | ✔(16 个) | ✔ | ✔ | ✘(仅 db 0) |
| **运维复杂度** | ★ | ★★ | ★★★ | ★★★★ |

### 2. 性能与容量对比

| 维度 | 单机 | 主从 | 哨兵 | Cluster(3M3S) |
|------|------|------|------|---------------|
| **单实例 QPS** | 5-10w | 5-10w | 5-10w | 5-10w(每 master) |
| **集群总 QPS** | 5-10w | 5-10w | 5-10w | **15-30w** |
| **单实例内存上限** | 256GB(物理) | 256GB | 256GB | 256GB |
| **集群总容量** | 256GB | 256GB | 256GB | **~768GB(3 master)** |
| **故障切换时间** | - | 人工(分钟级) | 10-30 秒 | 15-30 秒 |
| **数据丢失窗口** | 取决于持久化 | 最后几秒(异步) | 最后几秒(异步) | 最后几秒(异步) |

### 3. 适用业务规模对比

| 业务规模 | 数据量 | QPS | 推荐架构 |
|----------|--------|-----|----------|
| 个人项目 / 工具 | < 1 GB | < 1w | **单机** |
| 中小型业务 | 1-10 GB | 1-5w | **主从** 或 **哨兵** |
| 中型生产业务 | 10-50 GB | 5-10w | **哨兵** |
| 中大型业务 | 50-500 GB | 10w-50w | **Cluster** |
| 大型平台 | > 500 GB | > 50w | **分片 Cluster + 多副本** |

## 七、各模式适用场景详解

### 1. 单机模式适用场景

```text
✔ 开发环境(Docker 一键启动)
✔ 单元测试 / 集成测试
✔ 小型内部工具缓存(可重建)
✔ Session/Token 临时存储(可重新登录)
✔ 边缘业务缓存(如博客浏览量、可丢失数据)

✘ 资金、订单、库存等关键业务
✘ 数据量超过 50GB
✘ QPS 持续超过 5w
```

### 2. 主从模式适用场景

```text
✔ 读多写少(读写比 > 10:1)的中小型业务
✔ 需要数据热备份但可接受人工切换
✔ 业务可拆分(查询走 Slave、报表走独立 Slave)
✔ 备份场景:从节点做 BGSAVE 不影响主
✔ 迁移过渡:从单机过渡到哨兵/Cluster 的中间态

✘ 不可接受人工切换停机的业务
✘ 写入密集场景(Master 同步压力大)
```

### 3. 哨兵模式适用场景

```text
✔ 中小型业务的高可用需求(< 50GB)
✔ 接受秒级自动切换但不需要水平扩展
✔ 客户端可以改造为支持 Sentinel
✔ 需要主从切换对应用透明
✔ 读写分离 + 自动故障的标准生产方案

✘ 数据量超过 50GB(单 master 内存压力)
✘ QPS 超过单 master 极限
✘ 需要事务跨多个 key 但不同业务维度
```

### 4. Cluster 模式适用场景

```text
✔ 大数据量(> 50GB,接近单机上限)
✔ 高并发(> 10w QPS,需要分摊)
✔ 业务可按 key 拆分(订单、用户、商品各占一片)
✔ 多机房部署,需要就近访问
✔ 互联网大型平台标配

✘ 业务强依赖事务跨多个独立 key(无法用 hashtag)
✘ 数据量 < 10GB,运维成本不划算
✘ 客户端无法升级(老旧 jedis 不支持 cluster)
```

## 八、容量规划

### 1. 内存估算

#### 1.1 单 key 内存公式

```text
单 key 内存 ≈ key 字符串 + value 序列化大小 + RedisObject 16B + 编码开销
```

| 数据结构 | 估算公式 | 示例 |
|----------|----------|------|
| **String** | `len(value) + 16B(RedisObject) + 编码元数据` | 1KB 字符串 ≈ 1.02 KB |
| **Hash** | `字段数 × (24B + field 值) + 哈希表开销` | 100 字段每字段 50B ≈ 7 KB |
| **List** | `元素数 × (value + 32B) + 链表/quicklist 开销` | 1000 个 100B 元素 ≈ 130 KB |
| **Set** | `元素数 × (value + 24B) + 哈希开销` | 10000 个 8B ID ≈ 320 KB |
| **ZSet** | `元素数 × (member + score + 32B) + 跳表` | 10000 个 50B 元素 ≈ 800 KB |

#### 1.2 总内存估算

```python
# 总内存 = 数据总量 × 副本数 × 膨胀系数
# 膨胀系数通常 1.5-2(RedisObject、jemalloc 碎片、listpack 等)

total_memory = data_size * replica_count * expansion_factor
             = 100GB * 2 * 1.8
             = 360GB

# 推荐生产 maxmemory 设置为总内存的 70%(留 30% 给 fork、子进程、碎片)
recommended_maxmemory = total_memory * 0.7
                      = 252GB
```

#### 1.3 碎片率监控

```bash
# 碎片率指标
> INFO memory
used_memory:1073741824        # 实际占用
used_memory_rss:1392508928    # 操作系统分配
mem_fragmentation_ratio:1.30  # RSS/used,正常 1.0-1.5

# > 1.5:碎片过多,启用 activedefrag 或重启
# < 1.0:内存被 swap,需扩容
```

### 2. QPS 估算

```text
单实例 QPS 上限(经验值):
- GET/SET:5-10w QPS(内存命中)
- LPUSH/RPUSH:3-5w QPS
- HSET 多字段:2-4w QPS
- ZADD:2-4w QPS
- 复杂 Lua 脚本:1-2w QPS(脚本越复杂越低)

集群总 QPS = N master × 单实例 QPS
         = 6 master × 8w = 48w QPS
```

**压测验证**:

```bash
# redis-benchmark 压测
redis-benchmark -h 127.0.0.1 -p 6379 \
    -t set,get,lpush,hset,zadd \
    -n 100000 -c 50 -d 100 \
    --threads 4

# 关注指标:
# - P50/P99 延迟
# - 吞吐量(requests per second)
# - 错误率
```

### 3. 网络带宽

| 场景 | 带宽估算 |
|------|----------|
| **写入** | `QPS × 平均 value 大小` |
| **主从同步** | 启动时全量 RDB 传输(几十 GB 量级),运行后增量(几 KB/s) |
| **Cluster Gossip** | 每节点每秒 1-5 个 ping,每包 ~2KB,日均 < 100MB |
| **Cluster reshard** | 单 key MIGRATE 流量,大 key 阻塞时间长 |

```text
# 写入带宽示例:
QPS = 50000,平均 value = 1KB
写入带宽 = 50000 × 1KB = 50MB/s

# 推荐万兆网卡(10Gbps = 1250MB/s)满足大部分场景
# 100GB 数据全量同步需 100GB / 1250MB/s ≈ 80 秒
```

### 4. 连接数估算

```conf
# Redis 默认最大客户端连接数
maxclients 10000

# 估算公式:
# 应用实例数 × 每实例连接池大小 × 客户端库系数

应用实例数 = 200 个 Spring Boot Pod
每实例连接池 = 20
客户端库系数 = 1.5 (Lettuce 共享连接更省)

总连接数 = 200 × 20 × 1.5 = 6000
# 此场景下 maxclients = 10000 够用
```

### 4. 选型金句

## 十一、核心要点速记

| 关键词 | 要点 |
|--------|------|
| **演进路径** | 单机 → 主从 → 哨兵 → Cluster,数据量和可用性需求驱动 |
| **单机** | 部署最简、运维最易,适合开发/小型缓存,< 10GB,QPS < 5w |
| **主从** | 数据冗余 + 读写分离,**需人工切换**,不解决高可用自动化 |
| **一主多从** | Master 同步压力大,Slave 多时考虑级联复制 |
| **级联复制** | Slave-1 作为中间节点,降低 Master 出网带宽 |
| **哨兵** | 在主从基础上提供**自动故障检测、转移、配置发现** |
| **哨兵节点数** | **≥ 3 节点、奇数**,跨机器部署,否则无法形成多数派 |
| **Sentinel 三大任务** | 监控、通知、自动故障转移(常扩展为含"配置提供") |
| **SDOWN/ODOWN** | 主观下线(单 Sentinel)/客观下线(多数 Sentinel 同意) |
| **Cluster** | Redis 3.0+ 官方分布式,**16384 槽哈希分片 + 内置 HA** |
| **16384 槽** | `CRC16(key) & 0x3FFF`,Gossip 消息 2KB(带宽友好) |
| **hashtag** | `{user:1000}` 强制同 slot,解决多 key 操作 |
| **MOVED** | 永久重定向,客户端**应更新本地 slot 表** |
| **ASK** | 临时重定向(slot 迁移中),客户端发 `ASKING` 但**不更新**表 |
| **Cluster 选举** | replica 自增 epoch 投票,**多数 Master 同意**才升主 |
| **脑裂** | Cluster 选举需多数票,**天然防脑裂**;Sentinel 需配 `min-replicas-to-write` |
| **数据丢失** | 主从异步复制,极端情况丢**最后几秒**写入 |
| **Cluster 单 DB** | Cluster 模式**仅支持 db 0**,跨 DB 不允许 |
| **CROSSSLOT** | 多 key 跨 slot 报错,必须用 hashtag 解决 |
| **客户端选型** | Lettuce(Netty 异步,推荐) / Jedis(阻塞,池化) / Redisson(分布式锁) |
| **Spring Boot 默认** | 3.x 默认 Lettuce,共享连接,线程安全 |
| **Lettuce vs Jedis** | Lettuce 单连接多线程、Jedis 阻塞需池化,Lettuce 性能更优 |
| **连接池参数** | `max-active` 20-50、`max-wait` 1000ms、`min-idle` 2-5 |
| **容量规划** | `数据 × 副本 × 1.5~2(膨胀)` ≤ `机器内存 × 70%(maxmemory)` |
| **碎片率** | `INFO memory` 的 `mem_fragmentation_ratio`,> 1.5 需关注 |
| **带宽估算** | 写入带宽 = QPS × 平均 value;集群总线 +1w 端口 |
| **选型决策** | 数据量 < 10GB 哨兵/主从、10-100GB Cluster、> 100GB 分片 Cluster |
| **哨兵 vs Cluster** | 哨兵不解决水平扩展,数据量超 50GB 必须 Cluster |
| **运维友好度** | 单机 > 主从 > 哨兵 > Cluster,优先选择满足需求的最低复杂度方案 |
| **云 Redis** | 阿里云/腾讯云 Tair 等底层即 Cluster,免运维但成本略高 |

## 十二、面试题速答

### 1. Redis 架构模式有哪些?各适用什么场景?

> **单机**:开发测试、小型缓存(< 10GB);
> **主从**:读写分离 + 数据冗余,可接受人工切换;
> **哨兵**:在主从基础提供**自动故障转移**,适合中小型生产(< 50GB);
> **Cluster**:分布式分片(16384 槽) + 内置 HA,适合中大型生产(50GB+)。

### 2. 主从、哨兵、Cluster 怎么选?

> 看**数据量、可用性要求、运维能力**三方面:
> - 数据量 < 10GB + 可接受分钟级中断 → 主从
> - 数据量 < 50GB + 必须秒级自动切换 → 哨兵
> - 数据量 > 50GB 或 QPS > 10w → Cluster
> 一句话总结:**数据量决定下限,可用性决定上线**。

### 3. 哨兵和 Cluster 的核心区别?

> **哨兵**只解决"单组主从的高可用",**不解决水平扩展**;
> **Cluster** 同时解决**数据分片 + 高可用**,但部署复杂、客户端需改造。
> 中小业务(< 50GB)用哨兵即可,大型平台(> 50GB)用 Cluster。

### 4. Sentinel 需要几个节点?为什么?

> **至少 3 个,推荐奇数**。
> - 2 节点无法形成多数派(2 节点同时在线才能决策,挂 1 个就瘫痪)
> - 3 节点可容忍 1 个故障,4 节点也只容忍 1 个(4/2=2,挂 2 个瘫痪),所以 3 节点性价比最高
> - 部署应跨机器跨机柜,避免与 Redis 同机器

### 5. Cluster 为什么是 16384 个槽?

> - Gossip 消息携带 slot 位图,**16384 = 2KB**,**65536 = 8KB**,带宽友好
> - Redis 集群主节点一般不超过 1000,16384 个 slot 已足够均匀分配
> - `2^14` 位运算(`& 0x3FFF`)比取模快

### 6. Cluster 如何保证不脑裂?

> 选举需**多数 master 投票通过**才能升主。在网络分区下,**少数派分区的 master 不会获得多数票**,无法完成选举,从而不会出现双 master 同时写入的脑裂。

### 7. 主从异步复制会丢数据吗?怎么尽量避免?

> 会。**默认复制是异步的**,Master 写入后立即返回,不等待 Slave ACK,极端情况下 Master 写完后宕机,Slave 数据落后几秒。
> 缓解:
> - 配 `min-replicas-to-write 1`:至少 1 个 Slave 在线才允许写入
> - 配 `min-replicas-max-lag 10`:Slave 延迟 > 10s 拒绝写入
> - 强一致场景可考虑 `WAIT` 命令(同步等待副本确认)

### 8. Cluster 模式下事务需要注意什么?

> **MULTI/EXEC 不允许跨 slot**,否则报错 `CROSSSLOT`。
> 解决:
> - 用 **hashtag** `{user:1000}` 强制相关 key 落到同一 slot
> - 或改用 **Lua 脚本**(单线程原子执行,Cluster 允许同 slot 跨 key)

### 9. 如何平滑从主从迁移到 Cluster?

> 1. 部署新 Cluster,业务双写(写主从 + 写 Cluster)
> 2. 用 RedisShake / 自研脚本从主从全量 + 增量同步到 Cluster
> 3. 校验数据一致(对比 SCAN 抽样)
> 4. 切读流量到 Cluster,观察一段时间
> 5. 切写流量到 Cluster,主从降级为备份
> 6. 客户端升级支持 Cluster,完成切换

### 10. Spring Boot 默认用哪个 Redis 客户端?

> **Spring Boot 3.x 默认 Lettuce**(Netty 异步、线程安全、支持 Cluster/Sentinel)。
> 如需用 Jedis,排除 Lettuce 依赖并引入 `jedis` 即可。
> Lettuce 优势:**单连接多线程共享**(无需池化),适合高并发;Jedis 阻塞 IO 需连接池。

---

> **本章小结**:Redis 架构模式的选择是**数据量 + 可用性 + 运维成本**的平衡。**能用单机解决的不要分布式**,能用主从解决的不要 Cluster。生产中,**哨兵**是中小型业务的性价比之王,**Cluster**是中大型平台的最终归宿,而**云 Redis**为不愿运维的团队提供了第三条路。后续章节(09/10/11)将分别深入主从、哨兵、Cluster 的实现细节。
