# Redis 安全与监控 (Security & Monitoring)

> 本章覆盖 Redis 在生产环境中的安全防护与可观测性体系：网络安全、密码认证、ACL 访问控制、命令重命名、传输加密、审计日志、监控指标、告警规则、可视化工具与完整生产级配置示例。安全与监控是 Redis 从"玩具"走向"生产"的最后一道门槛。

---

## 一、Redis 安全概述

### 1. 默认配置的风险

Redis 安装后的默认配置**几乎没有任何安全防护**，在公网或弱内网环境下风险极高：

| 风险点 | 默认行为 | 潜在后果 |
|--------|----------|----------|
| 绑定地址 | `bind 127.0.0.1` | 已被部分发行版改为 `bind 0.0.0.0`，暴露到所有网卡 |
| 密码 | `requirepass` 未设置 | 任何能连上端口的人都是 root |
| 保护模式 | `protected-mode yes` | 仅在 bind 非本机且无密码时拒绝外部访问 |
| 危险命令 | FLUSHALL/KEYS/SHUTDOWN 等可随意执行 | 数据被清空、服务被关停 |
| 通信加密 | 明文 RESP 协议 | 抓包即可看到所有 key/value |
| 访问控制 | 无（6.0 之前） | 所有用户共享 root 权限 |

### 2. 历年重大安全事件

**Redis 勒索病毒（2017-2018 集中爆发）**：

- 攻击者通过 `redis-cli` 直接连上未设防的 Redis 6379 端口
- 利用 `CONFIG SET dir /var/spool/cron`、`CONFIG SET dbfilename root` 等命令写入 crontab
- 执行 `SAVE` 把恶意 shell 持久化到磁盘
- 服务器沦为挖矿僵尸、勒索软件分发节点
- 出现大量 `Readme` 勒索留言，要求支付比特币

**其他典型事故**：

- 未授权访问 `KEYS *` 窃取用户 session/token
- `FLUSHALL` 一行命令清空整个业务缓存
- 内部员工利用 `MONITOR` 抓取所有业务请求（含明文密码）

> **铁律**：公网暴露 + 无密码 + 未禁用危险命令 = 把数据拱手送人。

## 二、网络安全

### 1. 绑定本地回环

`redis.conf`：

```conf
# 默认仅监听本地回环
bind 127.0.0.1 ::1
```

> 若要监听多个 IP，使用空格分隔：`bind 192.168.1.10 192.168.1.11`。
> **永远不要**使用 `bind 0.0.0.0` 暴露到所有网络。

### 2. protected-mode（保护模式）

Redis 3.2+ 引入的保护机制，**当同时满足以下三个条件时**会自动开启：

- 未设置 `requirepass`
- `bind` 未绑定 `127.0.0.1` / `::1`
- 客户端不是从回环地址连接

保护模式生效后会拒绝外部连接，连接时会返回：

```text
DENIED Redis is running in protected mode because protected mode
is enabled, no bind address was specified, no authentication
password is requested to clients.
```

生产环境建议**显式**保留 `protected-mode yes`，不要为了"省事"关闭它。

### 3. 防火墙与安全组

即便 Redis 仅监听内网，也应叠加一层主机防火墙：

```bash
# iptables 限制仅 192.168.1.0/24 网段可访问 6379
iptables -A INPUT -p tcp --dport 6379 -s 192.168.1.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 6379 -j DROP

# 保存规则
service iptables save
```

云服务器（AWS、阿里云、腾讯云）通过**安全组**控制入站规则：仅放行业务网段，禁止 `0.0.0.0/0` 访问 Redis 端口。

### 4. VPN / 专线

跨可用区、跨机房的 Redis 访问应通过：

- 阿里云高速通道、腾讯云专线
- AWS Direct Connect
- 自建 IPsec VPN / WireGuard 隧道

**严禁** Redis 直接走公网 + 密码这一"图省事"方案 —— 加密通道是底线。

## 三、密码与认证

### 1. requirepass 配置

```conf
# redis.conf
requirepass your_strong_password_here
```

运行时修改（不重启）：

```bash
redis-cli CONFIG SET requirepass "NewStrongPassword"
redis-cli CONFIG REWRITE
```

### 2. AUTH 命令

```bash
# 客户端认证
redis-cli -a your_strong_password_here PING
# 警告：-a 参数会被 ps 暴露，建议用 --user/--pass 或交互式输入
redis-cli
> AUTH your_strong_password_here
OK
> PING
PONG
```

### 3. 密码强度建议

| 维度 | 建议 |
|------|------|
| 长度 | 至少 32 字符 |
| 字符集 | 大小写字母 + 数字 + 特殊符号 |
| 生成 | `openssl rand -base64 48` |
| 存储 | 落到配置中心（如 Vault、Nacos），不写死在代码里 |
| 轮换 | 90 天至少更换一次 |
| 传输 | 业务代码通过 ENV 注入，不进 Git 仓库 |

> **永远不要**使用 `123456`、`redis`、`password` 这种弱密码 —— `redis-cli -a password` 跑字典攻击一秒钟就被破。

## 四、ACL 访问控制列表（6.0+）

### 1. 为什么需要 ACL

Redis 6.0 之前只有一个 root 用户，所有客户端共享全部权限。ACL 让多用户、细粒度权限成为可能。

### 2. 基础查询命令

```bash
# 列出所有用户
127.0.0.1:6379> ACL LIST
1) "user default on nopass ~* &* +@all"
2) "user app_readonly on >readonly_pwd ~* &* -@all +@read -keys"

# 当前用户
127.0.0.1:6379> ACL WHOAMI
"default"

# 列出所有可用的命令分类
127.0.0.1:6379> ACL CAT
 1) "keyspace"
 2) "read"
 3) "write"
 4) "set"
 5) "sortedset"
 ...

# 列出分类下的具体命令
127.0.0.1:6379> ACL CAT write
 1) "set"
 2) "del"
 3) "lpush"
 4) "rpush"
 ...

# 查看某条命令属于哪个分类
127.0.0.1:6379> ACL CAT DEL
 1) "keyspace"
 2) "write"
 3) "dangerous"
 4) "slow"
```

### 3. ACL 规则详解

ACL 规则由多个字段拼接而成，**顺序无关**：

| 规则 | 含义 | 示例 |
|------|------|------|
| `on` / `off` | 启用 / 禁用账号 | `on` |
| `>password` | 设置明文密码 | `>P@ssw0rd!` |
| `<password` | 校验密码（不存储原文） | `<hashed_pwd>` |
| `#<hash>...` | 密码 SHA-256 哈希 | `#e3c4...` |
| `~pattern` | 允许访问的 key 模式 | `~user:*` |
| `&pattern` | 允许访问的 pub/sub 频道模式 | `&news:*` |
| `+@category` | 允许整个命令分类 | `+@read` |
| `-@category` | 禁止整个命令分类 | `-@dangerous` |
| `+command` | 允许具体命令 | `+get` |
| `-command` | 禁止具体命令 | `-flushall` |
| `+command\|subcommand` | 允许子命令 | `+client\|list` |
| `allcommands` | 等价 `+@all` | `allcommands` |
| `nocommands` | 等价 `-@all` | `nocommands` |
| `allkeys` | 等价 `~*` | `allkeys` |
| `resetkeys` | 清空所有 key 模式 | `resetkeys` |
| `allchannels` | 等价 `&*` | `allchannels` |
| `resetchannels` | 清空所有频道 | `resetchannels` |
| `nopass` | 无密码（必须配 protected-mode） | `nopass` |

> `~` 和 `&` 的 pattern 是 glob 风格：`?` 匹配一个字符、`*` 匹配任意、`[abc]` 字符集。

### 4. 用户管理命令

```bash
# 创建只读用户
ACL SETUSER readonly on >readonly_pwd ~* &* -@all +@read

# 创建只能操作 user:* 的应用账号
ACL SETUSER app_user on >app_pwd ~user:* &* +@all -@dangerous

# 追加规则
ACL SETUSER app_user +get +set -flushall

# 查看用户（以 ACL 规则格式）
ACL GETUSER app_user

# 删除用户
ACL DELUSER app_user

# 保存到配置文件
ACL SAVE
```

### 5. 完整 ACL 配置示例

```conf
# redis.conf
# 1. 关闭默认用户的危险能力
user default off
user default on >default_strong_pwd ~* &* +@all

# 2. 监控账号：只读 + MONITOR 命令
user monitor on >mon_pwd ~* &* +@read +monitor

# 3. 业务应用账号：仅能访问 user: 前缀的 key，禁止 FLUSHALL/KEYS
user app_user on >app_pwd ~user:* +@all -@dangerous -keys -flushall

# 4. 报表分析账号：只读 + SCAN
user analytics on >ana_pwd ~* +@read +scan

# 5. 备份账号：仅能执行 BGSAVE
user backup on >bak_pwd ~* +@read +bgsave +lastsave

# 6. 审计账号：仅能查看统计
user auditor on >audit_pwd ~* +@read +info +client|list +slowlog|get
```

业务代码使用：

```python
import redis
r = redis.Redis(host='redis-host', port=6379, password='app_pwd', username='app_user')
r.set('user:1001', '{"name":"Alice"}')
# FLUSHALL 将被拒绝：(error) NOPERM this user has no permissions to run 'flushall'
```

## 五、命令重命名 / 禁用

### 1. rename-command 语法

```conf
# redis.conf

# 1. 将 CONFIG 重命名为秘密字符串（外部不知情）
rename-command CONFIG "d4f8a2c1e9b7"

# 2. 完全禁用某条命令
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command KEYS ""
rename-command SHUTDOWN "shutdown_8f3a1c"
rename-command DEBUG ""
```

### 2. 应禁用的危险命令清单

| 命令 | 风险 | 处置 |
|------|------|------|
| `FLUSHALL` | 清空全部数据库 | 禁用或仅给 root |
| `FLUSHDB` | 清空当前数据库 | 禁用或仅给 root |
| `KEYS` | 大 key 阻塞主线程 | 禁用，使用 SCAN 替代 |
| `CONFIG` | 运行时改配置 | 重命名为秘密字符串 |
| `SHUTDOWN` | 关闭 Redis | 禁用或重命名 |
| `DEBUG` | 调试命令可能挂起 | 禁用 |
| `CLIENT KILL` | 强制断开连接 | 限特定 IP |
| `BGREWRITEAOF` | 触发高 IO | 仅运维使用 |
| `BGSAVE` | 触发高 IO | 仅运维使用 |

### 3. 注意事项

- 禁用后该命令**任何用户都不能执行**，包括 root
- 重命名后客户端需要知道新名字才能调用
- AOF 持久化会记录"原命令名"，重命名后重启可能无法恢复 —— Redis 6+ 增加了兼容性处理
- 修改后需 `CONFIG REWRITE` 持久化

## 六、传输加密（TLS/SSL）

### 1. 加密方案对比

| 方案 | 适用范围 | 复杂度 |
|------|----------|--------|
| Redis 6.0+ 原生 TLS | 开源 Redis | 低 |
| spiped | Redis 4.x-5.x 升级 | 中 |
| stunnel | 任意版本 | 中 |
| Redis Enterprise | 企业版 | 最低 |
| SSH 隧道 | 临时调试 | 高（不推荐生产） |

### 2. 完整 TLS 配置示例

**生成证书**：

```bash
# 1. CA
openssl genrsa -out ca.key 4096
openssl req -x509 -new -nodes -key ca.key -days 3650 -subj "/CN=Redis-CA" -out ca.crt

# 2. 服务端证书
openssl genrsa -out redis-server.key 2048
openssl req -new -key redis-server.key -subj "/CN=redis.internal" -out redis-server.csr
openssl x509 -req -in redis-server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out redis-server.crt -days 365
cat redis-server.crt ca.crt > redis-server-bundle.crt

# 3. 客户端证书（可选，做 mTLS）
openssl genrsa -out client.key 2048
openssl req -new -key client.key -subj "/CN=redis-client" -out client.csr
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out client.crt -days 365
```

**redis.conf**：

```conf
# 启用 TLS 监听端口（保留原 6379 仅本地，6380 走 TLS）
port 0
tls-port 6380

# 服务端证书
tls-cert-file /etc/redis/certs/redis-server-bundle.crt
tls-key-file  /etc/redis/certs/redis-server.key
tls-ca-cert-file /etc/redis/certs/ca.crt

# 启用客户端证书校验（mTLS，可选）
tls-auth-clients yes

# 允许的 TLS 协议版本
tls-protocols "TLSv1.2 TLSv1.3"

# 加密套件
tls-ciphers "ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305"

# DH 参数（可选）
tls-dh-params-file /etc/redis/certs/redis.dh
```

### 3. 客户端连接 TLS

**redis-cli**：

```bash
redis-cli --tls \
  --cert /path/client.crt \
  --key  /path/client.key \
  --cacert /path/ca.crt \
  -h redis.internal -p 6380
```

**Python (redis-py 4.x+)**：

```python
import redis, ssl

r = redis.Redis(
    host='redis.internal', port=6380,
    ssl=True, ssl_cert_reqs='required',
    ssl_ca_certs='/path/ca.crt',
    ssl_certfile='/path/client.crt',
    ssl_keyfile='/path/client.key',
    password='app_pwd', username='app_user',
)
```

**Java (Lettuce)**：

```java
RedisURI uri = RedisURI.Builder.redis("redis.internal", 6380)
    .withSsl(true)
    .withVerifyPeer(SslVerifyMode.FULL)
    .withAuthentication("app_user", "app_pwd".toCharArray())
    .build();
RedisClient client = RedisClient.create(uri);
```

### 4. 性能影响

TLS 握手比 TCP 多 1-2 个 RTT，传输开销约 3-5%。生产实例通常影响 < 5%，但**必须上 TLS**。

## 七、数据加密

### 1. 应用层加密

Redis 本身不加密磁盘上的 RDB/AOF 文件。敏感字段（手机号、身份证、密码、token）应在写入 Redis 前加密：

```python
from cryptography.fernet import Fernet

key = b'...'  # 来自 KMS
f = Fernet(key)

# 加密后写入
cipher = f.encrypt(b'13800138000')
r.set('user:1001:phone', cipher)

# 读取时解密
plain = f.decrypt(r.get('user:1001:phone'))
```

### 2. 加密 key 管理（KMS 集成）

| 方案 | 特点 |
|------|------|
| AWS KMS | 托管式，FIPS 140-2 |
| 阿里云 KMS | 同上，国内合规 |
| HashiCorp Vault | 开源，可自建 |
| 自建 keyring | 简单但安全等级低 |

业务启动时从 KMS 拉取主密钥，缓存在内存；写入敏感字段时用 envelope encryption（数据密钥 + 主密钥）保证单点泄漏不致命。

### 3. 磁盘加密

若整台 Redis 服务器需要加密，可启用：

- **LUKS（Linux）**：全盘加密
- **AWS EBS 加密**：云盘层加密
- **文件系统加密**：如 eCryptfs

RDB/AOF 文件本身是密文，但**性能损失 5-15%**，适合合规要求高的场景。

## 八、审计

### 1. audit_log 模块（Redis Enterprise）

商业版提供的审计能力，可记录所有命令、用户、时间戳、客户端 IP：

```text
[2024-05-20 14:32:11] user=app_user client=10.0.1.5
  cmd=SET key=user:1001 arg=...
```

### 2. 通用日志（general_log）

开源版可用 `redis-cli` 抓取近似审计日志，但**生产慎用**：

```bash
# 临时开启
redis-cli CONFIG SET slowlog-log-slower-than 0
redis-cli MONITOR > /var/log/redis/monitor.log
```

> MONITOR 会把所有命令转发到客户端，对性能影响极大，仅用于故障定位。

### 3. 慢查询日志（slowlog）

记录执行时间超过阈值的命令，天然适合审计慢查询和可疑操作：

```bash
# 设置慢查询阈值为 10ms
CONFIG SET slowlog-log-slower-than 10000
CONFIG SET slowlog-max-len 1024

# 查看最近 100 条
SLOWLOG GET 100
# 输出：id, timestamp, duration(us), client addr, command
```

### 4. 客户端连接日志

```bash
# 当前所有连接
CLIENT LIST
# 输出字段：id, addr, fd, name, age, idle, flags, db, sub, psub, qbuf, qbuf-free, obl, oll, omem, cmd
```

定期 `CLIENT LIST` 输出到 ELK / Loki，可做连接数趋势、异常 IP 告警。

### 5. 监控重要命令

可使用 iptables + ulogd 或 eBPF 在网络层记录以下命令的调用：

| 命令 | 风险 |
|------|------|
| `CONFIG SET` | 运行时改配置 |
| `DEBUG` | 调试命令 |
| `SHUTDOWN` | 关闭 Redis |
| `BGREWRITEAOF` | 触发高 IO |
| `BGSAVE` | 触发高 IO |
| `SLAVEOF` / `REPLICAOF` | 改复制关系 |
| `CLUSTER MEET` | 加节点 |
| `MIGRATE` | 跨实例数据迁移 |
| `EVAL` | 执行 Lua 脚本 |

## 九、监控指标（INFO 各分节）

### 1. 性能指标

```bash
redis-cli INFO Stats | grep -E 'instantaneous_ops_per_sec|total_connections|rejected_connections|expired_keys'
```

| 指标 | 含义 | 健康范围 |
|------|------|----------|
| `instantaneous_ops_per_sec` | 当前 OPS | 视业务 |
| `total_connections_received` | 累计连接数 | 趋势监控 |
| `rejected_connections` | 超过 maxclients 拒绝数 | **必须为 0** |
| `expired_keys` | 过期 key 累计 | 配合业务 |
| `keyspace_hits` / `keyspace_misses` | 命中 / 未命中 | 命中率 > 95% |
| `latest_fork_usec` | 最近 fork 耗时 | < 50ms |
| `pubsub_channels` | pub/sub 频道数 | 趋势监控 |

命中率计算：

```text
hit_rate = keyspace_hits / (keyspace_hits + keyspace_misses)
```

### 2. 内存指标

```bash
redis-cli INFO Memory
```

| 指标 | 含义 | 告警阈值 |
|------|------|----------|
| `used_memory` | 实际使用字节 | < maxmemory × 0.8 |
| `used_memory_rss` | OS 看到的 RSS | 与 used_memory 接近 |
| `used_memory_peak` | 历史峰值 | 容量规划 |
| `used_memory_dataset_perc` | 数据占比 | < 80% |
| `mem_fragmentation_ratio` | RSS / used_memory | 1.0 ~ 1.5 |
| `mem_allocator` | 分配器 (jemalloc / glibc) | jemalloc 推荐 |
| `lazyfree_pending_objects` | 等待异步释放的对象 | 长期 > 0 告警 |
| `evicted_keys` | 淘汰 key 数 | 应激增告警 |
| `expired_keys` | 主动过期数 | 正常 |

**mem_fragmentation_ratio 解读**：

- `< 1.0`：swap 严重，物理内存不足
- `1.0 ~ 1.5`：正常
- `> 1.5`：内存碎片严重，考虑重启或 `MEMORY PURGE`（4.0+）

### 3. 复制指标

```bash
redis-cli INFO Replication
```

| 指标 | 含义 | 健康范围 |
|------|------|----------|
| `master_repl_offset` | 主节点已复制偏移 | 与 slave 同步增长 |
| `slave_repl_offset` | 从节点已复制偏移 | 与 master 差值小 |
| `master_link_down_since_seconds` | 主从断连时长 | 0 = 正常 |
| `master_sync_in_progress` | 是否正在全量同步 | 0 = 正常 |
| `master_last_io_seconds_ago` | 距上次 IO 秒数 | < 10 |
| `connected_slaves` | 在线从节点数 | = 配置数 |
| `repl_backlog_size` | backlog 缓冲区 | ≥ 2 × peak_QPS × 60s |

延迟计算：

```text
replication_lag = master_repl_offset - slave_repl_offset
```

### 4. 集群指标

```bash
redis-cli INFO Cluster
redis-cli CLUSTER NODES
```

| 指标 | 含义 |
|------|------|
| `cluster_enabled` | 是否启用集群 |
| `cluster_stats_messages_sent` | Gossip 消息数 |
| `cluster_known_nodes` | 已知节点数 |
| `cluster_size` | 实际承担数据的节点数 |
| `cluster_current_epoch` | 当前纪元 |
| `cluster_my_epoch` | 本节点纪元 |

### 5. INFO 各分节速查

| 分节 | 主要内容 |
|------|----------|
| `Server` | 版本、运行时间、进程 ID、模式 |
| `Clients` | 连接数、最大连接阻塞 |
| `Memory` | 内存使用、碎片率 |
| `Persistence` | RDB/AOF 状态、最近 fork/rewrite 耗时 |
| `Stats` | OPS、命中、连接、命令执行总数 |
| `Replication` | 主从偏移、backlog |
| `Keyspace` | 各 db 的 key 数、过期 key |
| `CPU` | CPU 消耗（基于样本计算） |
| `Modules` | 已加载模块 |
| `Commandstats` | 每条命令的调用次数、耗时（需开启） |
| `Cluster` | 集群状态 |
| `Latency` | 延迟监控事件（Redis 2.8.13+） |

> `Commandstats` 需在 redis.conf 中开启 `enable-debug-command yes` 或 `INFO commandstats`。

## 十二、告警规则（PromQL 示例）

### 1. 连接数超限

```promql
# 当前连接数 > maxclients 的 80% 持续 5 分钟
redis_connected_clients / redis_config_maxclients > 0.8
```

### 2. 内存使用率超 80%

```promql
# 内存使用率
redis_memory_used_bytes / redis_memory_max_bytes > 0.8
```

### 3. 命中率下降

```promql
# 5 分钟命中率 < 90%
(
  sum(rate(redis_keyspace_hits_total[5m]))
  /
  (sum(rate(redis_keyspace_hits_total[5m])) + sum(rate(redis_keyspace_misses_total[5m])))
) < 0.9
```

### 4. 主从延迟

```promql
# 副本 lag > 1MB
redis_redis_master_repl_offset - redis_redis_slave_repl_offset > 1048576
```

### 5. 慢查询激增

```promql
# 5 分钟内新增慢查询 > 10 条
rate(redis_slowlog_length[5m]) > 2
# 或
increase(redis_slowlog_length[5m]) > 10
```

### 6. 实例不可达

```promql
# redis_up == 0 持续 1 分钟
redis_up == 0
```

### 7. 淘汰数激增

```promql
# 5 分钟内淘汰 key > 1000
increase(redis_evicted_keys_total[5m]) > 1000
```

### 8. AlertManager 路由

```yaml
# alertmanager.yml
routes:
  - match:
      severity: critical
    receiver: 'oncall-team'
  - match:
      severity: warning
    receiver: 'ops-channel'

  - name: 'oncall-team'

      - url: 'https://oapi.dingtalk.com/robot/send?access_token=XXX'

      - to: 'ops@example.com'
```

## 十三、备份与恢复监控

### 1. RDB 文件监控

```bash
# 最近一次 BGSAVE 状态
INFO Persistence | grep -E 'rdb_last_bgsave_status|rdb_last_bgsave_time_sec|rdb_last_cow_size'
```

| 指标 | 含义 | 告警 |
|------|------|------|
| `rdb_last_bgsave_status` | 1=成功 | 0 持续超 1 小时告警 |
| `rdb_last_bgsave_time_sec` | 最近一次 BGSAVE 耗时 | > 300s 关注 |
| `rdb_last_cow_size` | fork 后 COW 增加内存 | > 1GB 关注 |
| `rdb_current_bgsave_time_sec` | 正在进行的 BGSAVE 耗时 | > 600s 告警 |

**RDB 文件大小**：

```bash
ls -lh /var/lib/redis/dump.rdb
```

对比 `used_memory` 与 RDB 大小，**RDB 通常比内存小 1.5-2 倍**（因为有对象开销和压缩）。

### 2. AOF 文件监控

```bash
INFO Persistence | grep -E 'aof_enabled|aof_last_rewrite_time_sec|aof_current_size|aof_buffer_length|aof_rewrite_in_progress|aof_delayed_fsync'
```

| 指标 | 含义 | 告警 |
|------|------|------|
| `aof_enabled` | 是否开启 | 必须 1 |
| `aof_last_rewrite_time_sec` | 上次 rewrite 耗时 | > 600s 关注 |
| `aof_current_size` | 当前 AOF 大小 | 持续 > 50GB 关注 |
| `aof_buffer_length` | AOF 缓冲长度 | 持续 > 0 关注（落盘慢） |
| `aof_rewrite_in_progress` | 是否正在 rewrite | 0 正常 |
| `aof_delayed_fsync` | 延迟 fsync 次数 | > 10 关注 |

### 3. 备份策略

| 频率 | 方式 | 保留 |
|------|------|------|
| 每 6 小时 | 远程节点 `BGSAVE` + scp 到 OSS | 7 天 |
| 每天 | 从节点 `BGSAVE` + 对象存储 | 30 天 |
| 每周 | 全量冷备 + 异地 | 1 年 |

**验证备份可用性**：


## 十六、Redis 7.0 安全特性

| 特性 | 描述 |
|------|------|
| **MP-AOF（Multi-Part AOF）** | AOF 拆分为 base + incr + manifest，重写更安全 |
| **ACL 增强** | 支持基于 pub/sub 频道的权限控制 (`&*`) |
| **TLS 性能优化** | TLS 握手/传输路径优化，CPU 占用更低 |
| **客户端 buffer 细粒度控制** | `maxmemory-clients`，避免单连接吃光内存 |
| **`FUNCTION` / `FUNCTION LOAD`** | 替代 `EVAL`，函数库持久化、版本化、可审计 |
| **集群 Slot 限制** | 单节点 slot 负载上限，避免热点 |
| **Shard 内部 Pub/Sub** | Cluster 模式不再用全网广播 |
| **主动过期（Active Expire）改进** | 更智能的过期 key 清理 |
| **listpack 全场景** | Hash/List/ZSet 小对象统一 listpack 编码 |
| **RESP3 默认（7.0+）** | 支持更丰富的数据类型映射 |
| **Resource Manager** | 客户端级别 CPU/IO 限制 |
| **RediSearch / RedisJSON 集成** | 模块生态，安全模型同核心 |

**FUNCTION 替代 EVAL 的审计优势**：

```bash
# 加载函数库（版本化、可签名）
FUNCTION LOAD REPLACE "#!lua name=mylib
redis.register_function('mylib_hello', function() return 'hi' end)"

# 列出所有函数
FUNCTION LIST

# 审计调用
SLOWLOG GET
```

## 核心要点速记

1. **默认配置毫无安全性**，必须修改：bind 内网 IP、requirepass、protected-mode。

2. **bind 不要用 0.0.0.0**，公网暴露 = 勒索病毒入口。

3. **密码至少 32 字符**，从 Vault/KMS 注入，90 天强制轮换。

4. **ACL 6.0+ 是标配**：按业务/角色分配用户，禁止共用 default。

5. **必须禁用危险命令**：FLUSHALL/FLUSHDB/KEYS/CONFIG/SHUTDOWN/DEBUG。

6. **rename-command 留一手**：CONFIG 重命名为秘密字符串，disable 是最后手段。

7. **TLS 6.0+ 原生支持**，6.0 以下用 spiped/stunnel。生产一定要加密传输。

8. **敏感字段应用层加密**，主密钥从 KMS 拉取，不落代码。

9. **审计三件套**：slowlog + CLIENT LIST 周期归档 + 关键命令的 eBPF/iptables 日志。

10. **监控核心指标**：`instantaneous_ops_per_sec`、`connected_clients`、`used_memory`、`hit_rate`、`master_repl_offset`。

11. **内存碎片率 `mem_fragmentation_ratio` 1.0~1.5 正常**，> 1.5 考虑重启或 MEMORY PURGE。

12. **告警五大项**：连接数 / 内存 / 命中率 / 主从延迟 / 慢查询。Prometheus + AlertManager 标配。

13. **监控架构**：`redis_exporter` 抓取 `/metrics` → Prometheus → Grafana + AlertManager。

14. **推荐 Grafana Dashboard ID 11835**（官方 redis_exporter 维护）。

15. **备份监控**：RDB 状态、AOF rewrite 频率、aof_delayed_fsync 计数。每天异地归档。

16. **Redis 7.0 升级收益**：MP-AOF、ACL 增强、IO 多线程、FUNCTION 替代 EVAL。

17. **安全与监控不是一次性配置**：定期 review ACL、轮换密钥、验证备份、做故障演练。

18. **出问题第一时间**：CLIENT LIST 查异常 IP → SLOWLOG GET 查可疑命令 → INFO Persistence 看持久化状态。
