# Redis 持久化 (Persistence)

> 本章覆盖 Redis 持久化的完整体系：RDB 快照机制、AOF 日志机制、混合持久化、Redis 7.0 MP-AOF、备份恢复实战、性能影响与监控。理解持久化是 Redis 生产环境数据安全的基石。

---

## 一、持久化概述

### 1. 为什么需要持久化

Redis 是内存数据库，所有数据默认保存在内存中。一旦进程退出、机器宕机、断电重启，**内存中的数据将全部丢失**。持久化的作用是将内存中的数据保存到磁盘，使得 Redis 重启后能够恢复数据。

典型场景：

| 场景 | 后果 |
|------|------|
| 进程崩溃 (redis-server crash) | 内存清零，所有 key 丢失 |
| 服务器宕机/断电 | 同上 |
| OOM 被系统 kill | 同上 |
| 误执行 FLUSHALL / FLUSHDB | 数据清空 |
| 主从切换、故障转移 | 客户端可重连，但若未持久化则数据全丢 |
| 数据迁移、备份恢复 | 需借助持久化文件跨实例恢复 |

> **铁律**：把 Redis 当作纯内存使用，不开启任何持久化 —— 等同于把数据放在没有 UPS 的内存条上，一次掉电就是灾难。

### 2. Redis 提供两种持久化方式

| 方式 | 名称 | 核心思想 | 默认 |
|------|------|----------|------|
| **RDB** | Redis Database | 定时把内存全量快照写入二进制文件 | 默认开启 |
| **AOF** | Append Only File | 把每条写命令追加到日志文件 | 默认关闭 |

两种方式可以单独使用，也可以**同时开启**，Redis 4.0+ 还支持**混合持久化**（RDB + AOF）。

### 3. 持久化与主从复制的区别

- **持久化**：解决单机数据丢失问题（防宕机、防误删）
- **主从复制**：解决高可用问题（防单点故障、读写分离）

主从复制中的从节点通常也会开启持久化，但它的 RDB 是全量同步时由主节点发来的，不是本机自己生成的。

## 二、RDB（Redis Database）持久化

### 1. 工作原理：fork 子进程 + COW（Copy On Write）

RDB 是 Redis 默认的持久化方式，核心是 **fork + COW（写时复制）**：

```text
时间线 ──────────────────────────────────────────────────►

时刻 T0: Redis 主进程接收客户端请求
   ┌──────────────────────────────────────┐
   │ 主进程 (地址空间)                       │
   │   ├── redisDb 数据 (10 GB)            │
   │   ├── 代码段 / 堆 / 栈                 │
   │   └── 文件描述符表                      │
   └──────────────────────────────────────┘

时刻 T1: 用户执行 BGSAVE
   ┌─────────────────────┐      ┌─────────────────────┐
   │ 主进程 (继续服务请求)  │      │ 子进程 (只读遍历)     │
   │   ├── 内存页表指向     │ fork │   ├── 继承相同内存页表 │
   │   │   物理页 P1~Pn   │ ───► │   ├── 继承文件描述符   │
   │   └── 继续接收写命令   │      │   └── 遍历写入 temp.rdb│
   └─────────────────────┘      └─────────────────────┘
                  │                          │
                  │ (此时未发生写, 物理页共享)  │
                  ▼                          ▼
         物理内存 P1...Pn (共享, 只读)

时刻 T2: 客户端执行 SET k v (修改 page P5)
   ┌─────────────────────┐      ┌─────────────────────┐
   │ 主进程               │      │ 子进程               │
   │   ├── 检测 P5 被修改  │      │   ├── 仍持有原 P5 指针│
   │   ├── 复制 P5 → P5'  │      │   │   指向旧物理页   │
   │   ├── 修改页表指向 P5'│      │   └── 持续遍历旧页   │
   │   └── 主进程写新页 P5'│      │       写入 temp.rdb │
   └─────────────────────┘      └─────────────────────┘
         物理内存: P1 P2 P3 P4 [P5'新页] P6 P7
                                     子进程看到的仍是旧 P5
```

**核心要点**：

- **fork**：基于 Linux `fork()` 系统调用，复制主进程的页表（不复制物理内存），速度极快（微秒级，与内存大小无关）
- **COW**：当主进程要修改某页数据时，内核触发"写时复制"，将该页复制一份新物理页，主进程修改新页，子进程仍持有旧页
- **子进程所见**：永远是 fork 时刻的内存快照，与主进程后续修改完全隔离，因此生成的 RDB 文件是**一致性快照**
- **代价**：主进程在写密集场景下，COW 复制会增加内存占用（极端情况下接近翻倍）

> **为什么不用线程**：RDB 是 CPU 密集型操作（序列化 + 压缩 + 写盘），线程共享地址空间会污染主进程内存视图；fork 子进程是唯一安全的方式。

### 2. 触发方式

#### (1) 手动命令触发

| 命令 | 同步/异步 | 是否阻塞主进程 | 说明 |
|------|-----------|----------------|------|
| `SAVE` | 同步 | **是** | 主进程直接执行快照，期间拒绝所有客户端请求 |
| `BGSAVE` | 异步 | 否 | fork 子进程做快照，主进程继续服务 |
| `SHUTDOWN SAVE` | 同步 | 是 | 关闭前同步保存 |
| `SHUTDOWN NOSAVE` | 不保存 | 否 | 关闭不保存（生产慎用） |

```bash
# 阻塞式（生产禁用）
127.0.0.1:6379> SAVE
OK

# 异步式（推荐）
127.0.0.1:6379> BGSAVE
Background saving started

# 查看 BGSAVE 是否完成
127.0.0.1:6379> LASTSAVE
(integer) 1723612345
```

#### (2) 自动触发规则（save m n）

在 `redis.conf` 中配置 `save` 规则，只要**任一规则满足**即触发 BGSAVE：

```conf
# 默认配置（生产常保留）
save 900 1       # 900 秒内至少 1 次修改
save 300 10      # 300 秒内至少 10 次修改
save 60 10000    # 60 秒内至少 10000 次修改

# 关闭自动触发
save ""
```

```text
触发逻辑（伪代码）:
  for each rule (m, n):
      if (now - lastsave_time >= m) and (modifications_since_lastsave >= n):
          BGSAVE()
          lastsave_time = now
          modifications_since_lastsave = 0
```

#### (3) 其他自动触发场景

| 场景 | 触发动作 |
|------|----------|
| 主从首次全量同步 | 主节点自动 BGSAVE 生成 RDB 发给从节点 |
| `debug reload` | 重载数据库，触发 SAVE |
| 执行 `SHUTDOWN` 默认行为 | 先 SAVE 再退出 |
| AOF 重写期间 | 强制先 BGSAVE 生成 RDB 快照（混合持久化场景） |

### 3. 文件名与路径配置

```conf
# 文件名（默认 dump.rdb）
dbfilename dump.rdb

# 文件保存目录（默认 ./，即 redis-server 启动目录）
dir /var/lib/redis/

# 完整路径 = dir + dbfilename
# 默认生成: /var/lib/redis/dump.rdb
```

> **注意**：`dir` 是所有持久化文件（RDB、AOF）的统一目录，修改需谨慎。

### 4. RDB 文件结构

RDB 是二进制压缩文件，结构如下：

```text
┌─────────────────────────────────────────────────────────────────┐
│                       RDB 文件结构                                │
├──────────┬──────────┬───────────┬─────────────────────┬─────┬────┤
│ REDIS    │ rd_ver   │ aux_field │ ... (database 数据)   │ EOF │ CRC│
│ (5 字节) │ (4 字节) │ (变长)     │                       │(1B) │(8B)│
└──────────┴──────────�───────────┴─────────────────────┴─────┴────┘
```

各字段含义：

| 字段 | 长度 | 含义 |
|------|------|------|
| `REDIS` | 5 字节 | 魔数，固定字符串 "REDIS" |
| `rd_ver` | 4 字节 | RDB 版本号（如 "0009" = Redis 7.0） |
| `aux_field` | 变长 | 辅助字段（Redis 5.0+），记录 `redis-ver`、`redis-bits`、`ctime`、`used-mem` 等元数据 |
| `database data` | 变长 | 实际 key-value 数据，按 SELECTDB 分块 |
| `EOF` | 1 字节 | 固定值 0xFF，标志数据结束 |
| `CRC64` | 8 字节 | 整个文件（不含自身）的循环冗余校验 |

**每个 database 数据块内部结构**：

```text
┌──────────┬───────────────────────�─────────┬─────────────────────┬─────┐
│ SELECTDB │ db_number (1/2/4 字节) │ resize  │ key-value 记录 ×N    │ EOF │
│ (1 字节) │   编码长度             │ db 提示 │  (含类型+key+value) │(1B) │
│ 0xFE     │   (变长整数)            │ (可选)  │                     │     │
└──────────┴───────────────────────┴─────────┴─────────────────────┴─────┘
```

**每个 key-value 记录结构**：

```text
┌─────────┬──────┬──────────────┬─────────�────────────┐
│ type    │ key  │   key 内容    │ value   │ value 内容  │
│ (1 字节) │长度 │ (字符串/编码) │ 长度    │ (按类型编码)│
└─────────┴──────┴──────────────┴─────────┴────────────┘
```

type 字段取值：

| 值 | 类型 | value 编码 |
|----|------|------------|
| 0 | STRING | 长度前缀的字节串 |
| 1 | LIST | list-length + 每项长度前缀 |
| 2 | SET | set-size + 每项 |
| 3 | ZSET | zset-size + (score 8B + member) × N |
| 4 | HASH | hash-size + (field + value) × N |
| 5 | ZSET (旧版,带压缩) | 已废弃 |
| 6+ | MODULE/STREAM 等 | 复杂编码 |

### 6. RDB 的优点

- **文件紧凑**：二进制压缩，体积小（10 GB 内存约生成 2-5 GB RDB）
- **恢复速度快**：直接加载到内存，启动时秒级恢复（比 AOF 快一个数量级）
- **适合备份**：单文件便于拷贝、传输、归档（scp 到异地、对象存储）
- **对主进程影响小**：fork 后子进程异步生成，不阻塞服务
- **最大兼容性**：是所有 Redis 版本默认都支持的方式
- **适合主从同步**：从节点全量同步必须依赖 RDB

### 7. RDB 的缺点

- **数据丢失风险高**：两次快照之间的数据全部丢失，典型丢失窗口 1 分钟~数分钟
- **fork 开销大**：内存越大、页表越复杂，fork 阻塞时间越长（虽然 fork 本身快，但复制页表仍与内存大小成正比，10 GB 约 50-100 ms）
- **COW 内存压力**：写密集场景下，主进程会复制大量被修改的页，极端时接近翻倍内存占用
- **不适合频繁修改**：每次修改数据量很大但又需要高频备份的场景（如订单流水），RDB 性价比低

### 8. 适用场景

- **缓存场景**（可容忍几分钟数据丢失）：推荐 RDB 即可
- **冷数据备份**：每日/每小时一次 RDB 即可
- **灾备归档**：RDB 文件最小，最适合长期保存
- **从节点全量同步**：RDB 是主从复制的标准数据源

## 三、AOF（Append Only File）持久化

### 1. 工作原理

AOF 记录**每一条会修改数据的命令**，以 RESP 协议文本追加到 `.aof` 文件。Redis 重启时按顺序重放 AOF 中的命令，恢复数据集。

```text
客户端 SET k1 v1 ──► 主进程执行 ──► 命令写入 AOF 缓冲区 ──► 刷盘策略
                                                            │
                                                  ┌─────────┼─────────┐
                                                  ▼         ▼         ▼
                                              always    everysec     no
                                            (每次 fsync)  (每秒一次)  (OS 自决)
```

### 2. 启用与配置

```conf
# 默认关闭，需手动开启
appendonly yes

# 文件名
appendfilename "appendonly.aof"

# 保存目录（与 RDB 共用）
dir /var/lib/redis/
```

### 3. 三种刷盘策略（核心）

Redis 提供三种 `appendfsync` 策略，决定 AOF 缓冲区何时真正写入磁盘：

| 策略 | 行为 | 数据安全性 | 性能 | 适用场景 |
|------|------|------------|------|----------|
| **`always`** | 每条写命令执行后立即 `fsync()` 刷盘 | **最高**：最多丢失 1 条命令 | 最差：写性能下降 50% 以上 | 金融、订单等绝对不允许丢失的场景 |
| **`everysec`**（默认） | 每秒执行一次 `fsync()`，后台线程刷盘 | **高**：最多丢失 1 秒数据 | 好：折中方案 | **绝大多数生产场景推荐** |
| **`no`** | 不主动 `fsync`，交给操作系统决定（一般 30 秒） | **低**：丢失上次刷盘后到现在的所有数据 | 最好 | 缓存、对数据丢失容忍度高的场景 |

```conf
# 推荐配置
appendfsync everysec
```

**为什么 `everysec` 是默认推荐**：

- `always` 太慢，每次写命令都阻塞在 fsync 上（机械盘 5-10 ms，SSD 0.1-1 ms），QPS 直接被打到几百
- `no` 太危险，OS 调度刷盘完全不可控，断电可能丢几分钟数据
- `everysec` 丢 1 秒数据可接受，性能损失小（后台线程异步刷盘），业界标准

**关键细节**：

- 主进程将命令写入 AOF 缓冲区（内存）后立即返回客户端，**不阻塞**
- 后台专门线程每 100 ms 触发一次刷盘判断（`everysec` 模式下）
- 当后台 fsync 慢于命令写入速度时，AOF 缓冲区可能积压，但不会阻塞主进程

### 4. AOF 重写（Rewrite）机制

#### (1) 为什么需要重写

AOF 是"追加写"，但很多场景会产生大量**冗余命令**：

```bash
# 这 6 条命令在 AOF 中保留
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter

# 但实际上只保留 1 条即可表达相同结果
SET counter 6
```

随着时间推移，AOF 文件会越来越大（一个 key 被改 1 万次就有 1 万条 INCR），但**重放恢复却越来越慢**。

#### (2) AOF 重写原理

AOF 重写**不是**读取旧 AOF 优化压缩，而是**直接遍历当前内存数据库**，生成一份"最小命令集"的新 AOF 文件。

```text
触发 BGREWRITEAOF
        │
        ▼
主进程 fork 子进程
        │
        ├─► 子进程遍历内存 db, 生成新 AOF (temp-rewrite.aof)
        │     例: SET counter 6 (1 条命令代替原 6 条 INCR)
        │
        ├─► 主进程继续接收新命令, 写入 AOF 缓冲区
        │     同时维护一个 "重写缓冲区"
        │     新命令既写旧 AOF (保证旧文件完整)
        │     又追加到重写缓冲区 (供子进程最终合并用)
        │
        ▼
子进程完成新 AOF, 通知主进程
        │
        ▼
主进程将 "重写缓冲区" 中的命令追加到新 AOF 末尾
        │
        ▼
原子替换: 旧 appendonly.aof ← 新 temp-rewrite.aof
```

#### (3) 重写期间时序图

```text
时间 ───────────────────────────────────────────────────────────────►

主进程: 接收命令 ──► 追加到 AOF 缓冲区 ──► 追加到 AOF 重写缓冲区
                                          │
                          fork()          ▼
主进程: ─────────────────────────► 子进程开始遍历内存
                                      │
主进程: 继续服务 ──┐                   │ 遍历 db0/db1/...
                  │                   │  生成最小命令集
                  │ 写命令到达        │  写入 temp-rewrite.aof
                  │   ├─►AOF 缓冲     │
                  │   └─►重写缓冲     │
                  │                   │
主进程: ──────────│───────────────────►│ 子进程写完新 AOF
                  │                   │
                  │                   ▼
主进程: ◄─────────┴───── 子进程发信号给主进程: "新 AOF 完成"
                  │
                  │   主进程: 将重写缓冲区的命令追加到新 AOF 末尾
                  │           (保证重写期间的数据不丢)
                  │
                  ▼
主进程: rename appendonly.aof → appendonly.aof.old.bak
       rename temp-rewrite.aof → appendonly.aof (原子生效)
                  │
                  ▼
        新 AOF 包含:
        [重写起始时的全量数据快照] + [重写期间的所有写命令]
```

#### (4) 触发方式

```bash
# 手动触发
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started
```

自动触发配置：

```conf
# AOF 文件比上次重写时增长的百分比（默认 100，即翻倍才重写）
auto-aof-rewrite-percentage 100

# AOF 文件最小多大才触发重写（默认 64 MB）
auto-aof-rewrite-min-size 64mb

# 计算公式:
#   当 aof_current_size > aof_base_size * (1 + percentage/100)
#   且 aof_current_size > min-size
#   → 自动 BGREWRITEAOF
```

### 5. AOF 文件结构

AOF 是纯文本文件，每条命令按 **RESP 协议** 编码：

```bash
# RESP 协议格式:
# *<参数数量>\r\n
# $<参数长度>\r\n
# <参数内容>\r\n

# 例: SET name redis
*3\r\n
$3\r\n
SET\r\n
$4\r\n
name\r\n
$5\r\n
redis\r\n
```

### 6. MP-AOF（Multi Part AOF，Redis 7.0+）

Redis 7.0 引入了 MP-AOF，将 AOF 文件拆分为多个 part，解决重写期间故障的数据丢失问题。

```text
MP-AOF 目录结构:
/var/lib/redis/
├── appendonlydir/
│   ├── appendonly.aof.1.base.rdb      # 历史 AOF 文件（按时间分段）
│   ├── appendonly.aof.1.incr.aof      # 对应 base 之后的增量命令
│   ├── appendonly.aof.2.base.rdb
│   ├── appendonly.aof.2.incr.aof
│   └── appendonly.aof.manifest        # 清单文件，记录所有 part
└── appendonly.aof                     # 兼容符号链接（指向 manifest）
```

**核心改进**：

| 旧版 AOF 问题 | MP-AOF 解决方案 |
|---------------|-----------------|
| 重写期间主进程崩溃，旧的 AOF 已被截断、新的未生成 | 旧 AOF 保留，重写失败不影响恢复 |
| 只有一个 AOF 文件，无法分段管理 | 拆分为 base + incr 多 part |
| 故障恢复时只能重放整个文件 | 可按 part 选择性重放 |

```conf
# Redis 7.0+ 配置
appendonly yes
aof-use-rdb-preamble yes    # 启用混合持久化（推荐）
```

### 7. AOF 的优点

- **数据安全性高**：`everysec` 模式最多丢 1 秒，`always` 模式几乎不丢
- **可读性好**：文本格式，可手工编辑修复（删错命令、修复错误数据）
- **追加写入**：对主进程几乎无阻塞（除 `always` 策略）
- **重写可压缩**：BGREWRITEAOF 解决膨胀问题
- **MP-AOF 改进**：Redis 7.0+ 解决重写期间崩溃问题

### 8. AOF 的缺点

- **文件大**：通常比 RDB 大 2-10 倍（虽然有重写，但仍包含命令协议头）
- **恢复慢**：重放所有命令，启动耗时长（10 GB AOF 可能要几分钟）
- **磁盘 IO 压力大**：高频写入场景下 fsync 成为瓶颈
- **`always` 模式性能差**：每次写都 fsync，QPS 受限
- **特殊命令注意**：`FLUSHALL` 这种命令也会被记录，恢复时会重放（生产慎用）

## 四、RDB 与 AOF 对比

| 维度 | RDB | AOF |
|------|-----|-----|
| **持久化粒度** | 时间点快照（默认分钟级） | 每条写命令（秒级） |
| **数据安全性** | 较差，可能丢分钟级数据 | 高，everysec 最多丢 1 秒 |
| **文件大小** | 小（压缩二进制） | 大（文本命令） |
| **恢复速度** | **快**（直接加载） | 慢（逐条重放） |
| **写性能影响** | fork + COW，瞬时压力大 | everysec 影响小，always 性能差 |
| **磁盘 IO** | 集中在 BGSAVE 那一刻 | 持续高频 IO |
| **可读性** | 二进制，不可读 | 文本，可人工编辑 |
| **备份归档** | **优**（单文件小） | 一般（文件大、需重写） |
| **主从同步** | 标准数据源 | 不直接使用 |
| **实现复杂度** | 简单 | 复杂（重写、刷盘策略） |
| **Redis 版本兼容** | 全版本 | Redis 1.1+ |

**选型决策树**：

```text
你的数据能容忍分钟级丢失吗?
   │
   ├─ 能 (纯缓存) ──► 仅用 RDB (默认配置即可)
   │
   └─ 不能 (持久化数据)
          │
          ├─ 数据库规模大、恢复时间敏感 ──► 仅用 RDB + 缩短 save 间隔
          │
          └─ 数据绝对重要、能容忍较慢恢复 ──► RDB + AOF (混合持久化)
```

## 五、混合持久化（Redis 4.0+）

### 1. 背景

RDB 恢复快但丢数据多，AOF 数据安全但恢复慢。混合持久化结合两者优点。

### 2. 原理

`aof-use-rdb-preamble yes` 开启后，AOF 重写时的新文件格式如下：

```text
┌──────────────────────────────────────────────────────────┐
│              混合持久化 AOF 文件结构                        │
├──────────────────────────┬───────────────────────────────┤
│   RDB 格式快照 (二进制)    │   AOF 格式增量 (文本)           │
│   (重写时刻的全量数据)      │   (重写期间的新命令)             │
├──────────────────────────┴───────────────────────────────┤
│ Redis 4.0+:                                                │
│   EOF 标记前是 RDB, EOF 后是 AOF 增量                     │
│   恢复时: 先加载 RDB 快照, 再重放 AOF 增量                  │
└──────────────────────────────────────────────────────────┘
```

### 3. 配置

```conf
appendonly yes
aof-use-rdb-preamble yes
```

### 4. 优点

- **启动速度快**：RDB 部分直接加载，比纯 AOF 重放快数十倍
- **数据损失最小**：AOF 增量只覆盖重写期间的新命令，丢失窗口 = 重写耗时（通常几秒）
- **兼顾备份与恢复**：AOF 文件同时具备 RDB 的紧凑性和 AOF 的增量记录

### 5. 缺点

- AOF 文件不可手工编辑（RDB 部分是二进制）
- Redis 4.0 之前版本生成的 AOF 不能被 4.0+ 加载（格式不兼容，向后兼容需谨慎）
- MP-AOF（Redis 7.0+）是其进一步演进

## 六、持久化实战

### 1. 生产环境完整 redis.conf 配置

```conf
# ============================================================
# Redis 持久化生产配置 (Redis 7.2)
# 适用于: 数据重要、内存 16 GB 左右的实例
# ============================================================

# ---------- RDB 配置 ----------
# 启用 RDB（默认即开启）
save 900 1            # 15 分钟内至少 1 次修改
save 300 10           # 5 分钟内至少 10 次修改
save 60 10000         # 1 分钟内至少 10000 次修改

# 文件名与路径
dbfilename dump.rdb
dir /var/lib/redis/
stop-writes-on-bgsave-error yes    # BGSAVE 失败时拒绝写入（保护数据）
rdbcompression yes                  # LZF 压缩 RDB 文件（CPU 换空间）
rdbchecksum yes                     # CRC64 校验（安全换性能）
rdb-del-sync-files no               # 主从同步后是否删除 RDB

# ---------- AOF 配置 ----------
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec                # 每秒刷盘（推荐）

# 自动重写触发条件
auto-aof-rewrite-percentage 100     # 体积翻倍触发
auto-aof-rewrite-min-size 64mb      # 至少 64 MB 才触发

# 混合持久化
aof-use-rdb-preamble yes            # 开启 RDB+AOF 混合

# AOF 加载策略
aof-load-truncated yes              # AOF 文件末尾截断时仍尝试加载（Redis 7 默认）
aof-timestamp-enabled no            # 是否在 AOF 中记录时间戳（影响恢复后数据时间属性）

# ---------- fork 与内存 ----------
# 启用 Transparent Huge Pages (THP) 可能导致 fork 延迟尖刺
# 生产环境推荐禁用 THP:
#   echo never > /sys/kernel/mm/transparent_hugepage/enabled

# ---------- 其他相关 ----------
latency-monitor-threshold 5         # 启用延迟监控（监控持久化阻塞）
slowlog-log-slower-than 10000       # 记录超过 10ms 的慢命令
```

### 2. 备份策略

#### (1) 自动备份（推荐）

通过 crontab 定时执行 BGSAVE 并归档：

```bash
#!/bin/bash
# /opt/redis/backup.sh - 每日凌晨 2 点全量备份

REDIS_CLI="/usr/bin/redis-cli -h 127.0.0.1 -p 6379 -a your_password"
BACKUP_DIR="/data/redis-backup"
DATE=$(date +%Y%m%d_%H%M%S)
RETENTION_DAYS=7

# 1. 触发 BGSAVE
$REDIS_CLI BGSAVE

# 2. 等待 BGSAVE 完成（轮询 LASTSAVE）
LAST_SAVE=$($REDIS_CLI LASTSAVE)
while [ "$($REDIS_CLI LASTSAVE)" == "$LAST_SAVE" ]; do
    sleep 1
done

# 3. 拷贝 RDB 到备份目录
cp /var/lib/redis/dump.rdb $BACKUP_DIR/dump_${DATE}.rdb

# 4. 拷贝 AOF（如开启）
if [ -f /var/lib/redis/appendonly.aof ]; then
    cp /var/lib/redis/appendonly.aof $BACKUP_DIR/appendonly_${DATE}.aof
fi

# 5. 同步到异地（S3 / OSS）
aws s3 cp $BACKUP_DIR/dump_${DATE}.rdb s3://my-bucket/redis/

# 6. 清理过期备份
find $BACKUP_DIR -name "*.rdb" -mtime +$RETENTION_DAYS -delete
find $BACKUP_DIR -name "*.aof" -mtime +$RETENTION_DAYS -delete
```

```cron
# crontab -e

```

## 七、持久化性能影响

### 1. fork 阻塞（巨型数据集）

**问题**：`fork()` 复制页表的速度与虚拟内存大小成正比。10 GB 内存实例 fork 大约需要 50-100 ms，期间主进程被阻塞（无法响应任何命令）。

```text
内存大小        fork 阻塞时间       P99 延迟尖刺
─────────────────────────────────────────────────
  1 GB         ~5 ms              极小
 10 GB         ~50-100 ms         几十 ms
 50 GB         ~200-500 ms        数百 ms
100 GB         ~1-2 s             秒级尖刺
```

**优化方案**：

- **关闭 THP**：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`
- **启用 `jemalloc`**：减少内存碎片
- **避免在高峰期触发 BGSAVE**：手动控制或降低自动 save 频率
- **使用 `repl-backlog-size` 配合**：主从复制分担持久化压力
- **考虑分片**：将单实例拆成多个小实例

### 2. AOF 阻塞（fsync）

**问题**：`everysec` 模式下，后台 fsync 慢于命令写入速率时，AOF 缓冲区会增长但不会阻塞主进程。但 `always` 模式下，每条命令都阻塞在 fsync。

**监控指标**：

```bash
# 查看 AOF 缓冲区状态
redis-cli INFO persistence | grep -E "aof_buffer|aof_rewrite|aof_pending"

# 输出示例:
# aof_enabled:1
# aof_rewrite_in_progress:0     # 0=无重写, 1=正在重写
# aof_rewrite_scheduled:0
# aof_last_rewrite_time_sec:2   # 上次重写耗时
# aof_current_size:12345678     # 当前 AOF 大小
# aof_base_size:6000000         # 上次重写后大小
# aof_buffer_queued:0           # 等待刷盘的字节数（>0 说明 fsync 跟不上）
# aof_buffer_direct:0
# aof_buffer_pending:0          # pending fsync 数
# aof_last_bio_fsync:1723612345 # 上次 fsync 时间戳
# aof_delayed_fsync:0           # 被延迟的 fsync 次数（>0 应告警）
```

### 3. 监控指标汇总

| 指标 | 告警阈值 | 获取命令 |
|------|----------|----------|
| `rdb_last_bgsave_status` | 非 `ok` | `INFO persistence` |
| `rdb_last_bgsave_time_sec` | > 60 秒 | `INFO persistence` |
| `aof_enabled` | 期望值 | `INFO persistence` |
| `aof_last_rewrite_time_sec` | > 300 秒 | `INFO persistence` |
| `aof_delayed_fsync` | > 0 | `INFO persistence` |
| `latest_fork_usec` | > 100 ms | `INFO stats` |
| `rdb_changes_since_last_save` | > 1000000 | `INFO persistence` |
| 磁盘空间 | 使用率 > 80% | `df -h` |
| I/O wait | > 20% | `iostat -x 1` |

### 4. 性能调优清单

- 关闭 `save` 中过于频繁的规则，或直接用 `save ""` 禁用 RDB 自动触发（仅靠 AOF）
- 使用 SSD 盘，机械盘的 fsync 延迟会严重拖累 AOF
- 监控 `aof_delayed_fsync`，增长说明 fsync 跟不上写入速率
- 大实例（> 50 GB）建议关闭自动 BGSAVE，改在低峰期手动触发
- 主从架构中，让从节点承担持久化（主节点 `save ""`，从节点正常开启）

## 八、Redis 7.0 持久化改进

Redis 7.0 在持久化方向做了几项重要升级：

### 1. MP-AOF（Multi Part AOF）

- 详见第三节 6 小节
- 解决重写期间主进程崩溃导致数据丢失的边缘场景
- AOF 文件拆分为 base + incr + manifest 三种文件

### 2. AOF 损坏自动修复

```conf
# Redis 7.0 默认开启
aof-load-truncated yes
```

AOF 文件末尾不完整时（例如宕机导致写入截断），Redis 7 会**自动忽略末尾损坏部分**继续启动并打日志，而 Redis 6 之前会启动失败。

### 3. RDB 文件版本升级

- Redis 7 RDB 版本号升级到 10（`0009` → `0010`）
- 新增对 `FUNCTION`（函数）、`STREAM`（流）等新数据类型的优化编码
- 旧版本 Redis **无法**加载 Redis 7 生成的 RDB 文件（向上兼容，向下不兼容）

### 4. 其他改进

- `aof-timestamp-enabled` 配置项：在 AOF 中记录命令时间戳，支持更精细的 PITR 恢复（实验性）
- `rdb-save-before-aof-rewrite` 控制 AOF 重写前是否先 BGSAVE
- 持久化相关的 INFO 字段更丰富，便于监控

## 核心要点速记

1. **RDB 默认开启，AOF 默认关闭**。`redis.conf` 里 `appendonly yes` 即可开启 AOF。

2. **RDB = 时间点快照**。fork 子进程 + COW 生成，丢失最后一次快照之后的数据。

3. **AOF = 写命令日志**。追加写入，三种刷盘策略：`always`（最安全最慢）/ `everysec`（默认推荐）/ `no`（最快最不安全）。

4. **AOF 重写（BGREWRITEAOF）解决膨胀**。fork 子进程遍历当前内存生成"最小命令集"，重写期间的新命令写入"重写缓冲区"，合并后原子替换。

5. **混合持久化（4.0+） = RDB 段 + AOF 增量段**。配置 `aof-use-rdb-preamble yes`，兼顾恢复速度与数据安全。

6. **MP-AOF（7.0+）** = 多 part 文件 + manifest 清单。解决重写期间崩溃的边缘问题。

7. **fork 是阻塞操作**，内存越大阻塞越长。生产大实例（> 50 GB）需关注 fork 延迟，必要时关闭 THP。

8. **fsync 是 IO 操作**，磁盘速度（SSD vs HDD）直接影响 `everysec` 模式下能否跟上写入速率。

9. **`aof_load_truncated yes` 是 Redis 7 默认**，AOF 末尾损坏会自动忽略。

10. **备份策略：定时 BGSAVE + 异地拷贝**。可通过从节点白嫖异地热备。

11. **监控关键指标**：`rdb_last_bgsave_status`、`aof_delayed_fsync`、`latest_fork_usec`、`aof_last_rewrite_time_sec`。

12. **数据恢复首选混合持久化的 AOF**，其次 RDB；纯 AOF 恢复慢但数据全；纯 RDB 恢复快但丢数据。

13. **主从架构最佳实践**：主节点可关闭自动 BGSAVE（`save ""`），让从节点承担持久化。

14. **`redis-check-rdb` 和 `redis-check-aof --fix`** 是修复持久化文件的官方工具。

15. **RDB 文件不可跨大版本向下兼容**（Redis 7 的 RDB 不能被 Redis 6 读取），升级需谨慎。
