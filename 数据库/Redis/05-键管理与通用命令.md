# 键管理与通用命令 (Key Management & Generic Commands)

> 本章覆盖 Redis 中与"键(Key)"本身打交道的所有命令:键的概念与命名规范、过期(TTL)与过期策略、删除与异步删除、键查找(KEYS / SCAN)、键的元信息查询(EXISTS / TYPE / RENAME 等)、键迁移(MOVE / COPY / DUMP / RESTORE)、OBJECT 内部调试、WAIT 复制同步、TOUCH / SORT、键空间通知(Keyspace Notification)以及 DEBUG 系列调试命令。每一节都给出生产可用的最佳实践与踩坑提示,适合作为日常开发与 SRE 排查的速查手册。

## 一、键(Key)的概念

Redis 是一个典型的 **键值对(Key-Value)** 数据库,所有的数据都以"键 → 值"的方式存储。键(Key)是数据的唯一标识,值(Value)则可以是字符串(String)、哈希(Hash)、列表(List)、集合(Set)、有序集合(Sorted Set)、位图(Bitmap)、HyperLogLog、GEO、流(Stream)等数据结构。键的设计质量,直接决定了系统的可维护性、可观测性、扩展上限与故障恢复效率。

### 1. 键的本质

```
┌─────────────────────────────────────────────────────────────────┐
│                          Redis 数据库                            │
│                                                                 │
│   key1 ──→ "hello"                              (String)        │
│   key2 ──→ { field1: "v1", field2: "v2" }      (Hash)          │
│   key3 ──→ [ "a", "b", "c" ]                    (List)          │
│   key4 ──→ { "x", "y", "z" }                    (Set)           │
│   key5 ──→ { "alice": 88, "bob": 92 }           (Sorted Set)    │
│                                                                 │
│   每个 key 都是顶层对象,内部对象(redisObject)记录:                │
│     - type    : 类型(string / list / hash / set / zset / stream)│
│     - encoding: 底层编码(embstr / raw / int / hashtable /       │
│                 listpack / quicklist / skiplist / stream)        │
│     - refcount: 引用计数(整数对象共享池、客户端引用)             │
│     - lru/idle: LRU/LFU 淘汰算法所需的访问时间信息                │
│     - ptr     : 指向实际数据的指针                               │
└─────────────────────────────────────────────────────────────────┘
```

### 2. redisObject 的关键字段

| 字段        | 作用                                                    | 调优点                                            |
|-------------|---------------------------------------------------------|---------------------------------------------------|
| `type`      | 决定能用哪些命令操作该键                                | 不同 type 不能混用命令(HSET 不能用在 String 上) |
| `encoding`  | 决定实际占用的内存与性能                                | int 比 raw 省内存;listpack 比 hashtable 省内存   |
| `refcount`  | 0~9999 的整数对象会被全局池共享,refcount>1              | 小整数对象共享节约内存                           |
| `lru`       | 对象最近访问时间(秒级 LRU 精度),OBJECT IDLETIME 可读  | maxmemory-policy=allkeys-lru 使用                |
| `lfu`       | 8 位高频 4 位低频计数,OBJECT FREQ 可读                  | maxmemory-policy=lfu* 使用                       |

#### encoding 选择策略

Redis 在不同数据规模下会自动切换底层编码,目的是在**小数据时省内存**、**大数据时保性能**。理解这套切换规则,可以在容量评估时给出更准确的估算。

| 数据类型 | 小规模编码        | 大规模编码     | 切换阈值(默认)             |
|----------|-------------------|----------------|----------------------------|
| String   | int/embstr        | raw            | embstr ≤ 44 字节           |
| Hash     | listpack          | hashtable      | entries 默认 128           |
| Set      | listpack/intset   | hashtable      | entries 默认 512(全整数)   |
| ZSet     | listpack          | skiplist+dict  | entries 默认 128           |
| List     | quicklist         | 同左           | 始终 quicklist             |

> **生产调优点**:`hash-max-listpack-entries` 等参数可以在内存敏感场景调大,把"何时升级到 hashtable"推后,节省内存;性能敏感场景可以调小,提前升级避免 rehash 抖动。

### 3. 键空间(Keyspace)

Redis 默认有 **16 个数据库**(编号 0~15),通过 `SELECT n` 切换。每个数据库都是一个独立的键空间,即 `db0` 的 `user:1` 与 `db1` 的 `user:1` 互不冲突。

```bash
SELECT 0          # 切换到 db0(默认)
SELECT 1          # 切换到 db1
DBSIZE            # 查看当前 db 的键数量
INFO keyspace     # 查看所有 db 的键数量统计
```

输出示例:

```
# keyspace
db0:keys=12345,expires=678,avg_ttl=90000
db1:keys=200,expires=0,avg_ttl=0
db15:keys=10,expires=0,avg_ttl=0
```

> **生产建议**:绝大多数业务系统只使用 `db0` 即可。Redis Cluster 模式下,SELECT 只能使用 0(因为集群共享一个 keyspace,多 db 概念不复存在)。

### 4. 键的生命周期

一个完整的键生命周期通常包括如下阶段,任何一个阶段都可能发生异常退出:

```
创建 ──→ 设置 TTL(可选) ──→ 读写访问 ──→ 过期 / 删除 / 淘汰 ──→ 释放内存
   │                                                              ↑
   │                                                              │
   └─── PERSIST 取消 TTL ────────────────────────────────────────┘
```

其中"释放内存"还有细分路径:

```
DEL / UNLINK(显式删除)
   │
   ▼
expired(惰性/定期过期回收)
   │
   ▼
evicted(到达 maxmemory 触发 maxmemory-policy 淘汰)
   │
   ▼
RDB / AOF(持久化时序列化/反序列化)
```

### 5. 键的内部视图

通过 `OBJECT` 或 `DEBUG OBJECT` 可以看到一个键的内部全貌:

```bash
SET user:profile:1 "will"
DEBUG OBJECT user:profile:1

# Value at:0x7f8b9c000f60 refcount:1 encoding:embstr serializedlength:6 lru:1682345678 lru_seconds_idle:5
```

每一项的含义在第九节 OBJECT 系列命令里详细展开。

## 二、键命名规范

Redis 没有强制的键名规范,但好的命名能让代码可读、可维护、可统计,避免键冲突,也是后续做 SCAN/统计/迁移、容量规划的关键前提。一个团队的键命名规范,应当在新成员入职第一天就被告知。

### 1. 推荐的命名结构

```
业务前缀:模块:业务ID[:子键]
```

| 部分           | 作用               | 示例                                |
|----------------|--------------------|-------------------------------------|
| 业务前缀       | 区分业务/服务      | `user` / `order` / `pay` / `mall`   |
| 模块           | 区分表/对象        | `profile` / `token` / `detail`      |
| 业务 ID        | 主键标识           | `1000` / `20240101001`              |
| 子键(可选)     | 同一对象的不同字段 | `name` / `email` / `cart`           |

### 2. 经典命名示例

```bash
# 用户相关
SET user:profile:1000 '{"id":1000,"name":"will"}'          # 用户完整信息(JSON 序列化)
SET user:session:abc123def '...'                            # 用户会话
SET user:token:1000 'eyJhbGciOi...'                         # 用户 JWT Token
SET user:lock:1000 '1' EX 10 NX                             # 用户级分布式锁(10 秒)

# 订单相关
SET order:detail:20240101001 '...'                          # 订单详情
SET order:status:20240101001 'PAID'                         # 订单状态
LPUSH order:queue:pending 20240101001                       # 待处理订单队列
HSET order:ext:20240101001 remark "VIP客户" courier "顺丰"  # 订单扩展信息

# 限流 / 计数
INCR rate:login:192.168.1.1:20240101                        # IP 当天登录计数
ZADD rank:game:daily 8800 'alice'                           # 游戏日榜

# 缓存相关(常加前缀 cache:)
SET cache:product:detail:1001 '...' EX 3600                 # 商品详情缓存
SET cache:dict:sex '{"0":"未知","1":"男"}' EX 86400         # 字典缓存
SET cache:hot:article:10086 '...' EX 600                    # 热点文章缓存

# 分布式锁
SET lock:seckill:goods:1001 "owner_uuid" EX 30 NX           # 秒杀商品锁

# 位图 / 签到
SETBIT user:sign:202401:1000 0 1                            # 用户 1 月签到第 0 位

# Geo / Stream / 计数器
GEOADD geo:shops 121.473 31.230 "shop:1001"                 # 店铺地理位置
XADD stream:order:events * type "paid" orderNo "20240101001" # 订单事件流
INCR counter:api:user:profile:qps                           # API 调用 QPS

# 布隆过滤器位图(位数组用字符串存储)
SETBIT bloom:user:id 12345 1                                # 标记 userId 12345 已存在

# 业务 ID 命名补充(订单号用日期前缀便于归档)
SET order:detail:20240101001 '...'                          # 订单号 20240101001(日期+序号)
SET invoice:detail:INV20240101001 '...'                     # 发票号

# 计数器
INCR counter:api:user:profile:qps
```

### 3. 命名规范要点

| 要点                  | 说明                                                       |
|-----------------------|------------------------------------------------------------|
| 使用冒号分隔          | 冒号是 Redis 默认的 glob 分隔符,也方便 `MATCH user:*` 模糊匹配 |
| 全部小写              | 避免大小写带来的歧义和 SCAN 漏匹配                       |
| 不使用空格 / 特殊字符  | 键名支持任意二进制,但可读性会极差;也不要混用 `_` 与 `:`   |
| 避免过长              | 单个键名不宜超过 50 字符,过长会浪费内存且影响 SCAN 性能   |
| TTL 与命名分离        | TTL 通过命令设置,不要写在键名里(如 `user:profile:1000:30m`) |
| 加业务前缀            | 多业务共用 Redis 时必须加前缀,防止键冲突                  |
| 用对象而非散键        | `user:profile:1000` 一个 Hash,优于 100 个独立字段键      |
| 业务 ID 类型一致      | 数值 ID 不带前导零,字符串 ID 带类型前缀(如 `u_1000`)    |
| 时间维度命名          | 带日期的键,统一 `YYYYMMDD` 或 `YYYYMMDDHH` 数字格式     |
| 版本号字段            | 缓存键带版本号,便于灰度切换(如 `cache:v2:product:1`)    |

### 4. 反例与改进

```bash
# 反例 1:键名含义不清
SET u1000 'will'             # u?user?url?无法判断
SET a1 'order_data'          # 看不出来是什么
# 改进:
SET user:profile:1000 'will'

# 反例 2:把 TTL 写进键名
SET user:profile:1000:30m '...'
# 改进:用 EX 单独设置,便于运行时调整
SET user:profile:1000 '...' EX 1800

# 反例 3:不加分隔符,后期 SCAN 困难
SET userprofile1000 '...'
# 改进:用 : 分隔
SET user:profile:1000 '...'

# 反例 4:同一对象拆成多个键(浪费键、原子性差、事务难用)
SET user:1000:name 'will'
SET user:1000:age 28
SET user:1000:email '...'
# 改进:用 Hash 存储整个对象
HSET user:profile:1000 name "will" age 28 email "..."

# 反例 5:缓存键不带版本号,数据 schema 变更后无法灰度
SET cache:product:1001 '...'
# 改进:带版本号,便于平滑升级
SET cache:v2:product:1001 '...'

# 反例 6:同一缓存多份命名混乱
SET product:cache:1001 '...'
SET cache:product:1001 '...'
SET p_c_1001 '...'
# 改进:团队统一定一个模板,例如 cache:v{N}:{module}:{id}
```

### 5. 命名规范的工程化

- **代码生成器**:让团队写工具类自动生成键名,避免散落手写。例如:

```java
public class RedisKeys {
    public static String userProfile(long id) { return "user:profile:" + id; }
    public static String userSession(String token) { return "user:session:" + token; }
    public static String orderDetail(String orderNo) { return "order:detail:" + orderNo; }
}
```

- **SCAN 模板化**:把常用 MATCH pattern 做成枚举/常量,如:

```java
public enum ScanPattern {
    ALL_USERS("user:*"),
    ALL_SESSIONS("user:session:*"),
    ALL_ORDERS("order:detail:*");
    // ...
}
```

- **运营可观测**:在 `INFO commandstats` 里看到大量特定 pattern 的 SCAN 调用,可作为命名合理性的间接验证。

## 三、键的过期(TTL)命令

Redis 支持给键设置**生存时间(Time To Live, TTL)**,到期后自动从内存中删除。TTL 是实现缓存自动失效、会话过期、限流窗口、订单超时关闭的关键机制。

### 1. 设置过期时间

| 命令                                    | 单位    | 精度          | 说明                              |
|-----------------------------------------|---------|---------------|-----------------------------------|
| `EXPIRE key seconds`                    | 秒      | 秒级          | 设置过期时间,经典用法             |
| `EXPIREAT key timestamp`                | 秒      | 秒级时间戳    | 到 Unix 时间戳指定时刻过期         |
| `PEXPIRE key milliseconds`              | 毫秒    | 毫秒级        | 精度更高的版本                     |
| `PEXPIREAT key millisTimestamp`         | 毫秒    | 毫秒时间戳    | 毫秒级时间戳过期                   |

#### EXPIRE

```bash
SET session:abc123 "user_data"
EXPIRE session:abc123 1800        # 设置 30 分钟过期

# 7.0+ 选项(精细控制)
EXPIRE session:abc123 60 NX       # 仅当当前没有 TTL 时才设置
EXPIRE session:abc123 60 XX       # 仅当当前已有 TTL 时才更新
EXPIRE session:abc123 60 GT       # 仅当新 TTL 大于当前 TTL 时更新
EXPIRE session:abc123 60 LT       # 仅当新 TTL 小于当前 TTL 时更新
```

返回值:
- `1`:设置成功
- `0`:键不存在,设置失败

#### EXPIREAT

```bash
EXPIREAT order:detail:20240101001 1704038400   # 到 2024-01-01 00:00:00 过期
EXPIREAT cache:flashsale 1704067200 GT         # 仅当新过期时间更晚才更新
```

#### PEXPIRE / PEXPIREAT

```bash
PEXPIRE counter:click:ad:1001 500          # 500 毫秒后过期
PEXPIREAT counter:click:ad:1001 1704038400000  # 毫秒级时间戳
```

### 2. 查询过期时间

| 命令              | 返回值含义                                                  |
|-------------------|-------------------------------------------------------------|
| `TTL key`         | 秒级剩余 TTL,-1=永不过期,-2=键不存在                        |
| `PTTL key`        | 毫秒级剩余 TTL,-1=永不过期,-2=键不存在                      |
| `EXPIRETIME key`  | 秒级绝对过期时间戳(Redis 7.0+),-1=永不过期,-2=键不存在      |
| `PEXPIRETIME key` | 毫秒级绝对过期时间戳(Redis 7.0+),-1=永不过期,-2=键不存在    |

```bash
TTL user:session:abc123
# (integer) 1732            # 还剩 1732 秒

EXPIRETIME user:session:abc123
# (integer) 1732099200      # Unix 秒级时间戳
```

> **小技巧**:`EXPIRETIME` 返回绝对时间戳,适合在分布式系统里对比时间,避免各节点时钟差异带来的 TTL 漂移问题。例如多节点 Redis 集群做一致性过期判断时,优先用绝对时间戳。

### 3. 取消过期(PERSIST)

```bash
PERSIST user:session:abc123     # 移除 TTL,键变为永久
TTL user:session:abc123         # -1 表示永不过期
```

### 4. 过期时间的底层存储

Redis 在每个键的 `redisObject` 之外,通过 **expires 字典**(哈希表)记录带 TTL 的键的过期时间(绝对 Unix 时间戳,毫秒级)。

```
expires (dict<key, expireAt_ms>)
    ├── user:session:abc123  →  1732099200000
    ├── order:lock:2024010   →  1732099200500
    └── rate:login:1.1.1.1   →  1732099260000
```

> expires 字典只在键被设置了 TTL 时才有该条目,**不设 TTL 的键不进入该字典**,节约内存。

### 5. TTL 命令速查表

| 命令              | 时间单位 | 时间类型       | 返回值        |
|-------------------|----------|----------------|---------------|
| EXPIRE k sec      | 秒       | 相对(从现在起) | 1/0           |
| PEXPIRE k ms      | 毫秒     | 相对           | 1/0           |
| EXPIREAT k ts     | 秒       | 绝对时间戳     | 1/0           |
| PEXPIREAT k ts    | 毫秒     | 绝对时间戳     | 1/0           |
| TTL k             | 秒       | 相对(剩余)     | 秒/-1/-2      |
| PTTL k            | 毫秒     | 相对(剩余)     | ms/-1/-2      |
| EXPIRETIME k      | 秒       | 绝对           | ts/-1/-2      |
| PEXPIRETIME k     | 毫秒     | 绝对           | ts/-1/-2      |
| PERSIST k         | -        | -              | 1/0           |

#### TTL 返回值的三种语义

任何 TTL/PTTL/EXPIRETIME 系列命令都返回三种状态值,理解它们的语义是排查过期相关问题的关键:

| 返回值 | 含义                          | 业务处理建议                          |
|--------|-------------------------------|---------------------------------------|
| 正整数 | 剩余过期时间(秒或毫秒或绝对) | 正常返回                              |
| -1     | 键存在,但**没有设置 TTL**     | 业务可能需要主动 SET TTL 或检查配置   |
| -2     | **键不存在**                  | 业务可能需要初始化数据                |

> **常见陷阱**:有团队写 `TTL k` 后判断 `>0` 以为键存在,实际上 **-1 也是"键存在"的状态**,只是没设过期。正确的存在性判断应该用 `EXISTS k`。

### 6. TTL 的常见应用模板

```bash
# 1. 用户会话(绝对过期)
SET user:session:{token} "{userData}" EX 1800

# 2. 短信验证码(短 TTL)
SET sms:code:{mobile} "{code}" EX 300 PX 300000

# 3. 限流窗口(滑动窗口)
ZADD rate:window:{userId} {ts} {ts}
EXPIRE rate:window:{userId} 60

# 4. 缓存(相对业务过期时间)
SET cache:product:{id} "{json}" EX 3600

# 5. 订单超时关闭(到点关单)
SET order:timeout:{orderNo} "1" EXAT 1704038400    # 7.0+ 的 EXAT

# 6. 分布式锁(自动防死锁)
SET lock:{name} {uuid} EX 30 NX
```

## 四、过期策略

仅"打个过期时间戳"是不够的,Redis 还必须决定:**什么时候去检查并删除那些已过期的键**。这关系到内存回收的及时性和 CPU 占用。Redis 综合采用两种策略,既保证访问路径安全,又避免内存长期被冷数据占据。

### 1. 惰性过期(Lazy Expiration)

**原理**:键被访问时才检查是否过期,如果过期则当场删除。

```
客户端 GET key:xxx
       │
       ▼
┌──────────────────┐
│ 查找 dict 字典    │
└────────┬─────────┘
         ▼
┌──────────────────────────────┐
│ 键存在?                        │
└────────┬─────────┬───────────┘
       否         是
       │          │
       │          ▼
       │   ┌──────────────────────────────┐
       │   │ 在 expires 字典中查 TTL?     │
       │   └────────┬─────────┬───────────┘
       │         没设TTL     有 TTL
       │           │          │
       │           │          ▼
       │           │   ┌─────────────────────────────┐
       │           │   │ 当前时间 >= expireAt ?      │
       │           │   └──────┬───────────┬─────────┘
       │           │         否          是
       │           │          │           │
       │           │          ▼           ▼
       │           │      返回值     DEL + 返回 nil
       │           │
       ▼           ▼
    返回 nil      返回值
```

**优点**:对 CPU 友好,只在访问时才检查,不浪费算力在没人访问的键上。
**缺点**:大量已过期但永远不被访问的键(如冷数据),会一直占着内存直到被淘汰。

### 2. 定期过期(Active Expiration)

**原理**:Redis 周期性(由 `hz` 配置控制,默认 10,即每秒 10 次)主动抽取一批设置了 TTL 的键,删除其中已过期的部分。

```
定时任务(每秒 N 次,由 hz 控制)
       │
       ▼
┌─────────────────────────────────────┐
│ ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP│
│ 默认 20,即每次循环最多扫描 20 个键    │
└────────┬────────────────────────────┘
         ▼
┌─────────────────────────────────────┐
│ 随机抽取 expires 字典中的 N 个键     │
│ 检查每个键是否过期                   │
└────────┬────────────────────────────┘
         ▼
┌─────────────────────────────────────┐
│ 删除已过期的,记录删除数量           │
└────────┬────────────────────────────┘
         ▼
┌─────────────────────────────────────┐
│ 删除比例 > 25% ?                    │
│  ┌─是 → 继续下一轮循环              │
│  └─否 → 本轮结束                    │
└─────────────────────────────────────┘
```

> **25% 阈值**:Redis 通过这个阈值判断是否要继续扫描。如果一轮扫描中发现超过 25% 的键已过期,说明过期键还很多,继续扫;否则退出,避免 CPU 浪费。

**优点**:及时回收过期键占用的内存。
**缺点**:会消耗一定的 CPU 资源(但可控,通过 `hz` 和 `active-expire-effort` 调整)。

### 3. 两策略结合(Redis 的实际方案)

```
              ┌──────────────────────┐
              │ 写入/读取键          │
              └────────┬─────────────┘
                       │
                       ▼
              ┌──────────────────────┐
              │ 惰性过期(读时检查)   │ ◄── 保证访问路径上永远返回有效值
              └────────┬─────────────┘
                       │
                       ▼
              ┌──────────────────────┐
              │ 后台定时过期         │ ◄── 保证内存不被冷数据长期占据
              └──────────────────────┘
```

**为什么需要两策略?**

| 只用惰性过期                            | 只用定期过期                       |
|----------------------------------------|-------------------------------------|
| 冷数据过期键永远不释放 → **内存泄漏**  | 扫描会持续消耗 CPU → 性能抖动       |
| 命中率下降时大量过期键残留 → 内存膨胀  | 扫描时机不可控 → 过期键存在窗口     |
| 命中率长期下降 → 内存 OOM 风险         | 高 QPS 时频繁扫描 → RT 抖动         |

### 4. 相关配置

```conf
# redis.conf
hz 10                          # 后台任务频率,1~500,默认 10
active-expire-effort 1          # 1~10,越大后台过期越激进(消耗更多 CPU)
                                # 实际乘数 = 1 + hz * effort
                                # 例如 hz=10, effort=1, 默认每秒最多扫描约 200 个键
```

### 5. 与内存淘汰(Maxmemory Policy)的关系

- **过期策略**:负责"键到期时何时被删除"。
- **淘汰策略**:负责"内存满时按什么规则挑键删除"(LRU/LFU/Random/TTL等)。
- 两者**正交**:`maxmemory-policy` 在内存到顶时被触发,过期策略独立运行。
- 也就是说:**即使没设 TTL,内存到顶时仍会按 LRU/LFU 淘汰**;**即使有 TTL 但内存够用,过期键也不会被自动回收,直到被访问或定期扫描命中**。

## 五、键的删除命令

### 1. DEL(同步删除)

```bash
DEL key1 key2 key3 ...     # 删除一个或多个键
# 返回值:成功删除的键数量(不存在的不计数)
```

特点:
- **同步阻塞**:Redis 主线程遍历 dict 哈希表,逐个释放内存。
- **O(N)**:N 为要删除的键数量。
- **原子性**:在集群中,DEL 涉及多节点时是原子的(集群内自动路由)。
- 适用场景:**少量键**、**非大对象**(普通 String、Hash、Set 等)。

### 2. UNLINK(异步删除,4.0+)

```bash
UNLINK key1 key2 key3 ...   # 与 DEL 接口相同,异步版本
# 返回值:成功删除的键数量
```

特点:
- **立即返回**:仅把键从 dict 中摘除,**真正的内存释放放到后台 BIO(Background I/O)线程**中异步执行。
- **主线程不阻塞**:适合删除大对象(大 List、Hash、Set、Sorted Set)。
- 适用场景:**大 Key 删除**、**热路径上不能卡顿**的场景。

### 3. DEL vs UNLINK 对比

| 维度                | DEL                           | UNLINK                          |
|---------------------|-------------------------------|---------------------------------|
| 主线程阻塞          | 是,O(N)                       | 否,O(1)摘除 dict 节点           |
| 大 Key 友好度       | 卡顿明显                      | **生产首选**                    |
| 实际内存释放时机    | 命令返回前                    | 后台 BIO 线程异步执行           |
| 命令复杂度          | O(N)                          | O(1)(返回前)/O(N)(后台)         |
| 返回值              | 删除数量                      | 删除数量                        |
| 集群支持            | 跨节点原子                    | 跨节点原子                      |
| 引入版本            | 1.0                           | 4.0                             |
| 适用场景            | 删除少量小 Key、脚本关键路径  | **删除大 Key、批量清理**        |

### 4. UNLINK 的底层细节

```
UNLINK key1 key2 key3 ...
       │
       ▼
┌──────────────────────────────┐
│ 主线程:从 dict 中摘除条目   │ ◄── O(1) 哈希表节点删除
│ 维护 refcount(若被多客户端引用)│
└────────┬─────────────────────┘
         ▼
┌──────────────────────────────┐
│ 判断 refcount 是否为 1       │
└────┬────────────────┬────────┘
   等于 1          大于 1
     │              │
     ▼              ▼
   直接释放       仅减少引用计数
   (内存立即回收)
     │
     ▼
┌──────────────────────────────┐
│ 若是复杂对象且有子对象      │ ◄── List/Hash/Set/ZSet
│ 提交到 BIO 异步释放队列     │
└──────────────────────────────┘
```

### 5. 大 Key 删除建议

```bash
# 反例:生产上一个大 Hash 直接 DEL,阻塞主线程几十毫秒到几秒
DEL big:hash:10086     # 可能 STW 几百 ms~几 s,引发雪崩

# 正例 1:UNLINK 异步删除
UNLINK big:hash:10086

# 正例 2:渐进式删除(Hash / Set 等支持 HSCAN/SSCAN 的类型)
HSCAN big:hash:10086 0 COUNT 1000 | xargs -n 1 HDEL big:hash:10086

# 正例 3:改名 + 后台删除(把大 Key 从可达路径摘除)
RENAME big:hash:10086 big:hash:10086:deleting
UNLINK big:hash:10086:deleting

# 正例 4:Redis 6.2+ 的 lazyfree 选项(配置层兜底)
# redis.conf
lazyfree-lazy-user-del yes         # DEL 命令也走异步释放
lazyfree-lazy-server-del yes       # 内部淘汰等场景也走异步
```

### 6. lazyfree 相关配置

```conf
# redis.conf
lazyfree-lazy-eviction yes          # maxmemory 淘汰时异步释放
lazyfree-lazy-expire yes            # 过期键删除时异步释放
lazyfree-lazy-server-del yes        # 内部 rename、swapdb 等异步
lazyfree-lazy-user-del yes          # DEL 走异步(UNLINK 永远异步)
```

### 7. 大 Key 的判定标准与发现

大 Key 是指**单键占用内存过大**或**单键元素过多**,是生产事故的主要诱因之一。各数据类型的经验阈值(仅供参考):

| 类型   | 元素阈值         | 字节阈值     |
|--------|------------------|--------------|
| String | -                | > 10 KB      |
| Hash   | > 5000 field     | > 50 MB      |
| List   | > 5000 elem      | > 50 MB      |
| Set    | > 5000 elem      | > 50 MB      |
| ZSet   | > 5000 elem      | > 50 MB      |

> 实际阈值要结合业务:一个 KV 配置项存 1 MB 的 JSON 也可能是合理的,而一个被频繁访问的热点缓存超过 10 MB 就要警惕。

**发现大 Key 的常用方法**:

```bash
# 1. redis-cli --bigkeys(扫描整个库,适合离线)
redis-cli --bigkeys

# 2. redis-cli --memkeys(采样内存使用,需 Redis 4.0+)
redis-cli --memkeys -n 0 -s 100

# 3. MEMORY USAGE key(单键精确内存)
MEMORY USAGE big:hash:10086
# (integer) 52428800  # 单位字节

# 4. DEBUG OBJECT key(查看 refcount、serializedlength 等内部信息)
DEBUG OBJECT big:hash:10086

# 5. rdb-tools 离线分析 RDB 文件(生产推荐)
rdb -c memory dump.rdb --bytes 1024000 | sort -k4 -nr | head 20
```

### 8. 删除大 Key 的实操流程

```bash
# Step 1:从 SCAN 找到疑似大 Key
redis-cli SCAN 0 MATCH big:* COUNT 100

# Step 2:确认大 Key 的内存占用
redis-cli MEMORY USAGE big:hash:10086

# Step 3:把大 Key 重命名,避免业务再访问
redis-cli RENAME big:hash:10086 big:hash:10086:deleting

# Step 4:异步删除
redis-cli UNLINK big:hash:10086:deleting

# Step 5:监控内存释放
redis-cli INFO memory | grep used_memory
```

### 7. FLUSHDB / FLUSHALL(慎用)

```bash
FLUSHDB                # 清空当前 db
FLUSHDB ASYNC          # 异步清空(4.0+)
FLUSHALL               # 清空所有 db
FLUSHALL ASYNC         # 异步清空所有 db
```

> **生产警告**:FLUSHDB/FLUSHALL 会瞬间清空大量数据,可能引发:
> - 主线程长时间阻塞(同步模式)
> - 大量 AOF/RDB 重写
> - 主从全量重同步
> - **业务级雪崩**(缓存全部丢失)
>
> **必须**通过 `rename-command` 重命名或 ACL 限制,且配合运维审批流程。

```bash
# redis.conf 重命名危险命令
rename-command FLUSHDB ""
rename-command FLUSHALL ""
rename-command KEYS ""
rename-command CONFIG "ADMINCONFIG"
```

## 六、键查找

Redis 中**没有 SQL 那种 `SELECT * WHERE`** 的查询,只能按模式(pattern)在前缀/中间/后缀匹配键名。Redis 提供两种方式:`KEYS`(全扫)和 `SCAN`(游标式)。

### 1. KEYS pattern(生产禁用)

```bash
KEYS *                        # 所有键
KEYS user:profile:*           # 前缀匹配
KEYS *:token:*                # 中间匹配
KEYS order:detail:2024*       # 后缀匹配
KEYS user:[abc]*              # 字符类匹配
KEYS user:?rofile:*           # 单字符匹配
KEYS user:[^a]*               # 反向字符类匹配
```

支持的 glob 模式字符:

| 字符  | 含义                       |
|-------|----------------------------|
| `*`   | 任意数量任意字符           |
| `?`   | 单个任意字符               |
| `[abc]` | 字符类,匹配 a/b/c        |
| `[^a]`  | 反向字符类,不匹配 a       |
| `\`   | 转义                       |

**特点**:
- **O(N)**:扫描整个键空间。
- **阻塞主线程**:扫描期间 Redis 无法处理其他命令。
- 命中数量过大时,**几毫秒到几秒**的主线程阻塞,直接引发客户端超时。
- **生产禁用**(`rename-command KEYS ""` 必须)。

### 2. SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]

#### 基础用法

```bash
SCAN 0                              # 第一次迭代,cursor=0 表示从头开始
SCAN 0 MATCH user:* COUNT 100       # 每次期望扫描 100 个,匹配 user:*
SCAN 0 MATCH user:* COUNT 100 TYPE string   # 只匹配 String 类型
```

返回结构:

```bash
1) "17"                              # 下次迭代的 cursor(0 表示结束)
2) 1) "user:profile:1"
   2) "user:profile:2"
   3) "user:profile:3"
```

#### 关键参数

| 参数     | 默认值 | 说明                                                   |
|----------|--------|--------------------------------------------------------|
| `cursor` | 必填   | 游标,首次传 0,后续用返回值;0=迭代结束                |
| `MATCH`  | 无     | 匹配模式(glob 风格),**只是过滤,不减少扫描量**        |
| `COUNT`  | 10     | 单次遍历的"工作量提示",非精确命中数;可理解为 hint     |
| `TYPE`   | 无     | 类型过滤(6.0+),只返回指定类型                        |

#### 完整迭代示例

```bash
# 数据:user:profile:1 ~ user:profile:10000,user:session:*,user:lock:*

# 第一次迭代:SCAN 0
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 100
1) "23"                                  # 下次迭代的 cursor
2) 1) "user:profile:1"
   2) "user:profile:2"
   3) "user:session:abc"
   4) "user:lock:1000"

# 第二次迭代:SCAN 23
127.0.0.1:6379> SCAN 23 MATCH user:* COUNT 100
1) "47"
2) 1) "user:profile:500"
   2) "user:session:def"
   3) "user:profile:600"

# 第三次迭代:SCAN 47
127.0.0.1:6379> SCAN 47 MATCH user:* COUNT 100
1) "0"                                   # 0 表示迭代结束
2) 1) "user:profile:9999"
   2) "user:lock:999"
```

#### TYPE 过滤示例(6.0+)

```bash
# 只看 String 类型的 user: 前缀键
127.0.0.1:6379> SCAN 0 MATCH user:* TYPE string COUNT 100
1) "12"
2) 1) "user:profile:1"        # String(JSON 序列化的)
   2) "user:token:1000"        # String
```

#### 配套的 HSCAN / SSCAN / ZSCAN

```bash
HSCAN key 0 MATCH field_* COUNT 100       # 扫描 Hash 的 field
SSCAN key 0 MATCH member_* COUNT 100      # 扫描 Set 成员
ZSCAN key 0 MATCH member_* COUNT 100 WITHSCORES  # 扫描 ZSet 成员(可选带 score)
```

### 3. SCAN 的特性与坑

| 特性                                | 说明                                                      |
|-------------------------------------|-----------------------------------------------------------|
| **不保证完整快照**                  | 迭代过程中,新增/删除的键可能返回也可能不返回              |
| **可能返回重复键**                  | 同一键在两次迭代中可能出现两次                            |
| **客户端必须做幂等处理**            | 客户端在 SCAN 遍历中处理键时,需要容忍重复                 |
| **空迭代也是合法迭代**              | 某些次 SCAN 返回空数组但 cursor 非 0,这是正常的           |
| **TYPE 过滤后总量可能很小**         | 每次迭代扫描大量键,但只有少数匹配 TYPE,效率反而更好      |

### 4. KEYS vs SCAN 对比

| 维度              | KEYS                          | SCAN                                       |
|-------------------|-------------------------------|--------------------------------------------|
| 时间复杂度        | O(N),N=总键数                 | O(1)每次调用,整体 O(N)                     |
| 是否阻塞主线程    | **是,完全阻塞**               | **否,分批迭代,每次只做少量工作**         |
| 游标式迭代        | 否,一次性返回全部             | 是,需要循环调用                            |
| 支持 MATCH        | 支持                          | 支持                                        |
| 支持 COUNT        | 否                            | 支持(单次扫描量 hint)                     |
| 支持 TYPE 过滤    | 否(需自己 TYPE 过滤)          | 支持(6.0+)                                |
| 增量期间键变化    | 一次性快照                    | 可能重复返回或遗漏新键(非严格快照)         |
| 生产可用性        | **禁止**                      | **推荐**                                   |
| 适用场景          | 调试、统计总键数(慎用)       | 生产遍历、清理、统计                        |

### 5. 客户端遍历的伪代码模板

```python
cursor = "0"
result = []
while cursor != "0":
    cursor, data = redis.scan(cursor=cursor, match="user:*", count=500, _type="string")
    result.extend(data)
# result 可能包含重复键,需要后续去重
unique_keys = set(result)
```

```java
// Jedis 示例
String cursor = "0";
ScanParams params = new ScanParams().match("user:*").count(500).type("string");
ScanResult<String> res;
do {
    res = jedis.scan(cursor, params);
    cursor = res.getCursor();
    List<String> keys = res.getResult();
    // 处理 keys...
} while (!"0".equals(cursor));
```

> **核心结论**:任何生产环境的"全 key 操作"(扫描、统计、清理),**必须用 SCAN,严禁 KEYS**。

## 七、EXISTS / TYPE / RENAME / RENAMENX / MOVE

### 1. EXISTS(键存在性)

```bash
EXISTS key                            # 单键,返回 1/0
EXISTS key1 key2 key3 ...             # 多键(7.0+),返回存在的数量
```

**注意**:Redis 7.0 之前 `EXISTS` 只能查 1 个键,从 7.0 起支持多键,大幅减少 RTT。

```bash
EXISTS user:profile:1 user:profile:2 user:profile:999
# (integer) 2
```

### 2. TYPE(键的类型)

```bash
TYPE key
# 返回值:
#   "none"        键不存在
#   "string"      字符串
#   "list"        列表
#   "set"         集合
#   "zset"        有序集合
#   "hash"        哈希
#   "stream"      流
#   "ReJSON-RL"   如果使用了 RedisJSON 模块(模块自定义类型)
```

应用:
- 调试时确认键类型。
- 实现通用 KV 接口时,根据类型分发到不同序列化器。

### 3. RENAME(重命名键)

```bash
RENAME key newkey
# 成功返回 OK
# 失败(源键不存在)返回错误
# newkey 已存在时,会被覆盖
```

应用:
- 把"待删除"的大 Key 改名后异步删除。
- 缓存版本切换(`cache:v1:product:1` → `cache:v2:product:1`)。

### 4. RENAMENX(仅当目标不存在时重命名)

```bash
RENAMENX key newkey
# 返回值:
#   1:重命名成功(newkey 不存在)
#   0:重命名失败(newkey 已存在)
```

> **应用**:实现分布式锁的安全释放、临时大 Key 重命名(rename + UNLINK)。

```bash
# 安全释放分布式锁(防止误删其他客户端的锁)
GET lock:order:1000
# "uuid-of-client-a"
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:1000 "uuid-of-client-a"
```

### 5. MOVE(跨 db 迁移,弃用趋势)

```bash
MOVE key db_index
# 把当前 db 的 key 移到目标 db
# 目标 db 已存在同名 key 时返回 0
# 移动成功返回 1,源键不存在返回 0
```

> **注意**:MOVE 仅在**非集群、非 Sentinel** 模式下可用,且 Redis 官方已经推荐用应用层逻辑代替。

### 6. 命令速查

| 命令       | 返回值                  | 用途                          |
|------------|-------------------------|-------------------------------|
| EXISTS     | 存在的数量(7.0+)/1/0   | 存在性判断                    |
| TYPE       | 类型字符串              | 决定用什么命令操作            |
| RENAME     | OK / 错误               | 无脑改名                      |
| RENAMENX   | 1/0                     | 安全改名(避免覆盖)           |
| MOVE       | 1/0                     | 单机跨 db 迁移(弃用趋势)     |

## 八、RANDOMKEY / DUMP / RESTORE

### 1. RANDOMKEY(随机返回一个键)

```bash
RANDOMKEY
# 返回一个随机的 key 名字(任意 db 中随机抽取)
# 当 db 为空时返回 nil
```

应用场景:
- 调试、抽样、抽奖算法原型(非生产高 QPS 场景)。

### 2. DUMP(序列化键的值为 RDB 格式字节流)

```bash
DUMP key
# 返回一段二进制字符串,RDB 格式
# 序列化内容包括值 + 过期时间(若设置)
# 键不存在返回 nil
```

### 3. RESTORE(从 DUMP 字节流恢复一个键)

```bash
RESTORE key ttl serialized-value [REPLACE] [ABSTTL] [IDLETIME idletime] [FREQ freq]
```

| 参数            | 说明                                                       |
|-----------------|------------------------------------------------------------|
| `key`           | 目标键名                                                   |
| `ttl`           | 过期时间,0 表示永不过期                                    |
| `serialized-value` | DUMP 返回的字节流                                      |
| `REPLACE`       | 目标键已存在时,覆盖(必须指定)                              |
| `ABSTTL`        | ttl 解释为绝对 Unix 毫秒时间戳                              |
| `IDLETIME`      | 设置 LRU 闲置时间                                          |
| `FREQ`          | 设置 LFU 频率                                              |

```bash
# 备份一个键
DUMP user:profile:1
# "\x02\x00\x08will\x06\x00..."

# 恢复到目标实例
RESTORE user:profile:backup 0 "\x02\x00\x08will\x06\x00..."
# OK

# 恢复到目标实例,设置 60 秒过期
RESTORE user:profile:backup 60000 "\x02\x00\x08will\x06\x00..."
```

### 4. 典型应用

- 实现"键迁移"应用层逻辑(避免使用已弃用的 MIGRATE 之外的低层 API)。
- 跨实例"深拷贝"某个键。
- 实现 Redis 数据的备份/恢复脚本(类似 RedisSHAKE、redis-dump 等工具的底层都基于 DUMP/RESTORE)。

### 5. DUMP/RESTORE 与序列化版本

DUMP 输出的字节流包含**序列化版本号**,与 Redis 主版本相关。**跨大版本**(如 Redis 6 → Redis 7)可能不兼容,**需做版本兼容测试**。跨语言序列化(Java/Go/Python)通常不直接用 DUMP,而用 JSON/MsgPack 等通用格式。

## 九、OBJECT 系列命令

OBJECT 命令用于查看 Redis 对象(redisObject)的内部调试信息,**生产慎用**,仅用于排查内存、性能、淘汰问题。

### 1. OBJECT REFCOUNT

```bash
OBJECT REFCOUNT key
# 返回值:键对应的 redisObject 的引用计数
# 通常 1 表示唯一持有
# >1 表示被共享(如 0~9999 的整数对象池)
```

应用:诊断对象共享带来的内存节约。

### 2. OBJECT ENCODING

```bash
OBJECT ENCODING key
# 返回底层编码:
#   "embstr"      短字符串(<=44 字节)
#   "raw"         长字符串
#   "int"         整数
#   "hashtable"   Hash/Set/ZSet 字典
#   "listpack"    紧凑编码(小 Hash/Set/ZSet)
#   "quicklist"   List(由多个 listpack 节点组成)
#   "skiplist"    ZSet 的跳表
#   "stream"      Stream 的 RAX
```

应用:分析内存结构,排查大 Key、优化编码。

### 3. OBJECT IDLETIME

```bash
OBJECT IDLETIME key
# 返回键距离上次被访问的秒数
# 用于辅助排查冷数据
# 注意:每次 IDLETIME 自身会重置 idle 时间(类似 OBJECT FREQ 也会重置)
```

### 4. OBJECT FREQ

```bash
OBJECT FREQ key
# 返回 LFU 计数器的对数值(0~255)
# 仅当 maxmemory-policy 为 lfu/lfu-* 时有意义
# 用于观察键的访问热度
```

### 5. OBJECT HELP

```bash
OBJECT HELP
# 列出 OBJECT 子命令的帮助
```

### 6. DEBUG OBJECT(更详细版本)

```bash
DEBUG OBJECT key
# Value at:0x7f8b9c000f60 refcount:1 encoding:embstr serializedlength:6 lru:1682345678 lru_seconds_idle:5
# 输出比 OBJECT 更详细的内部信息,包含内存地址、序列化长度、LRU 详细信息
```

### 7. 命令速查

| 子命令    | 返回值                                  | 用途                       |
|-----------|-----------------------------------------|----------------------------|
| REFCOUNT  | 引用计数                                | 排查对象共享               |
| ENCODING  | 编码字符串                              | 排查编码、估算内存         |
| IDLETIME  | 闲置秒数                                | 冷数据诊断                 |
| FREQ      | LFU 频次                                | 热数据诊断                 |
| HELP      | 帮助                                    | 自我提示                   |

## 十、WAIT 阻塞命令(复制同步)

### 1. 命令格式

```bash
WAIT numreplicas timeout
```

- `numreplicas`:希望至少同步到 N 个副本。
- `timeout`:阻塞等待的最长时间(毫秒),0 表示不阻塞。

### 2. 工作原理

```
client                  master                   replica1, replica2
   │                     │                              │
   │   SET k v           │                              │
   │ ───────────────────▶│                              │
   │                     │  复制传播                     │
   │                     │ ────────────────────────────▶ │
   │   WAIT 1 1000       │                              │
   │ ───────────────────▶│                              │
   │                     │ 等待 numreplicas 个副本 ACK   │
   │                     │ ◄───── ACK ────────────────  │
   │   返回值:1           │                              │
   │ ◀───────────────────│                              │
```

### 3. 返回值

- `N`:在 timeout 内,确实有 N 个副本确认收到写入。
- `0`:超时时间内未能满足 numreplicas。

### 4. 应用场景

```bash
# 写入关键数据后,确保至少 1 个副本同步,再返回客户端成功
SET order:detail:20240101001 '...'
WAIT 1 5000       # 阻塞最多 5 秒,等 1 个副本确认
```

适用:金融、订单、库存等不能容忍主从数据丢失的关键写入。

### 5. 与 WAITOF 的区别

`WAITOF numreplicas timeout` 是 Redis 7.0+ 的加强版,**支持异步复制(failover 后的 ACK)**,语义与 WAIT 相同。在主从切换(replica promotion)过程中,WAITOF 能正确识别新的"已晋升"的副本。

### 6. 注意事项

- WAIT **不保证强一致**:在异步复制场景下,副本可能落后主库毫秒级。WAIT 只是"已收到写命令",不保证副本已 apply。
- WAIT 会**阻塞客户端连接**:timeout 内的请求无法被该连接处理,生产中通常放到连接池里独立使用。
- 高 QPS 场景不建议用 WAIT:会成为瓶颈,优先考虑业务补偿机制。

## 十一、COPY(6.2+)

### 1. 命令格式

```bash
COPY source destination [DB destination-db] [REPLACE]
```

### 2. 行为

- 把 `source` 键的值**浅拷贝**到 `destination`。
- 默认在当前 db 内,可指定目标 db。
- 默认行为:目标键已存在则失败;`REPLACE` 可强制覆盖。
- 不删除源键,与 RENAME 不同。
- 值的拷贝语义:复杂对象(List/Set/Hash/ZSet)是按需深拷贝,对新键做必要的内存分配。

### 3. 示例

```bash
SET user:profile:1 "will"
COPY user:profile:1 user:profile:1:backup
# OK

COPY user:profile:1 user:profile:1:backup DB 1
# 把 backup 副本复制到 db1

COPY user:profile:1 user:profile:1:backup REPLACE
# 目标存在时覆盖
```

### 4. 应用场景

- 数据快照(创建一份副本用于测试/调试)。
- A/B 实验(同一份数据起两个不同前缀的副本)。
- 跨 db 同名复制(集群下不适用,因集群只支持 db0)。

## 十二、TOUCH(更新 LRU 时间戳)

### 1. 命令格式

```bash
TOUCH key1 key2 key3 ...
```

### 2. 行为

- 不修改值,**只更新键的访问时间戳**(LRU 的最近访问时间,或 LFU 的访问频率)。
- 不存在的键也计入返回值(但不影响数据)。

### 3. 示例

```bash
TOUCH user:profile:1 user:profile:2 user:profile:999
# (integer) 2          # 仅前两个键存在
```

### 4. 应用场景

- 防止某些"低频但重要"的键被 LRU 淘汰。
- 配合 `maxmemory-policy allkeys-lru` 时,主动给热数据"续命"。
- 调试时观察哪些键被 TOUCH(配合 OBJECT IDLETIME 反向印证)。
- 实现"预热"机制:服务启动时对热数据做 TOUCH,让 LRU 计数器重置。

## 十三、SORT 排序(外部排序,性能差)

### 1. 命令格式

```bash
SORT key [BY pattern] [LIMIT offset count] [GET pattern [GET pattern ...]]
     [ASC|DESC] [ALPHA] [STORE destination]
```

### 2. 行为

- 对 List / Set / Sorted Set 的元素进行排序。
- 缺省按数字排序(`ALPHA` 才按字符串)。
- **`SORT` 是 Redis 中少有的 O(N+M*log(M)) 复杂度的命令**,性能较差。
- 默认会**新建一个数组**,对内存有压力。
- `STORE` 可把结果存到一个新键,避免返回大量数据。

### 3. 示例

```bash
LPUSH numbers 3 1 4 1 5 9 2 6 5 3 5

SORT numbers                       # 1 1 2 3 3 4 5 5 5 6 9
SORT numbers DESC                  # 9 6 5 5 5 4 3 3 2 1 1
SORT numbers LIMIT 0 5             # 取前 5
SORT numbers STORE sorted:numbers  # 排序后存到新键
```

#### 复杂排序:BY 引用其他键

```bash
# 假设有: 
#   user:1:age → 28
#   user:2:age → 22
#   user:3:age → 35

RPUSH user:list 1 2 3

SORT user:list BY user:*:age GET user:*:name
# 按 user:*:age 的值排序,返回 user:*:name
```

### 4. 性能警告

> **生产建议**:SORT 是"性能毒药",大 List/Set 上禁用。可替代方案:
> - 排序在应用层做(Sorted Set 是 Redis 内建的有序结构,优先用 ZADD/ZRANGE)。
> - 索引数据用 Sorted Set 维护。
> - 必须用 SORT 时,加 `LIMIT` 和 `STORE`,控制单次处理量。

## 十五、键空间通知(Keyspace Notification)

Redis 可以在键发生指定事件时,通过**发布/订阅**机制通知客户端,典型应用:实现缓存失效广播、本地缓存失效、订单过期监控等。

### 1. 启用配置

键空间通知**默认关闭**,需要修改 `notify-keyspace-events` 配置。

```bash
# redis.conf
notify-keyspace-events "Ex"     # 仅开启过期事件
# 或运行时
CONFIG SET notify-keyspace-events "KEA"
```

参数由**事件类别**和**事件标志**组成。

#### 事件类别

| 字符 | 类别               |
|------|--------------------|
| `K`  | Keyspace(键空间)   |
| `E`  | Keyevent(键事件)   |

#### 事件标志

| 字符  | 事件                | 触发时机                          |
|-------|---------------------|-----------------------------------|
| `g`   | DEL                 | 键被 DEL/UNLINK/异步删除          |
| `$`   | String              | String 类型命令                   |
| `l`   | List                | List 类型命令                     |
| `s`   | Set                 | Set 类型命令                      |
| `h`   | Hash                | Hash 类型命令                     |
| `z`   | Zset                | ZSet 类型命令                     |
| `x`   | Expired             | 键过期                            |
| `e`   | Evicted             | 键被 maxmemory 淘汰               |
| `t`   | Stream              | Stream 类型命令                   |
| `d`   | Module              | Module 类型命令                   |
| `A`   | 别名"g$lshzxetd"    | 所有事件                          |

#### 常用配置组合

| 配置          | 含义                          |
|---------------|-------------------------------|
| `""`          | 关闭通知(默认)               |
| `"K"`         | 只启用 Keyspace 通知          |
| `"E"`         | 只启用 Keyevent 通知          |
| `"KE"`        | 同时启用两类通知              |
| `"Ex"`        | 仅订阅过期事件                |
| `"Egx"`       | Keyevent + DEL + 过期         |
| `"KEA"`       | 订阅所有事件(性能开销最大)    |
| `"Kg$lshzxe"` | KS + 过期 + 数据操作事件      |

#### 配置原则

- **按需启用**:只启用业务真正需要的事件类别,避免 `KEA` 带来的 CPU 与网络开销。
- **过期场景优先 `Ex` 或 `Egx`**:大多数业务(本地缓存失效、订单过期)只需要过期通知。
- **变更频繁场景慎用 `KEA`**:每秒数万次写入会触发同等数量级的事件,可能拖垮 Pub/Sub。
- **多 db 监听用通配符**:PSUBSCRIBE `__keyevent@*__:expired` 可以一次监听所有 db。

### 2. 频道命名规则

启用后,Redis 会暴露两类频道:

| 频道名格式                         | 含义(以 db0 为例)                                  |
|-------------------------------------|-----------------------------------------------------|
| `__keyspace@<db>__:<key>`           | 频道名=键名,消息=发生的事件(如 `expired`)        |
| `__keyevent@<db>__:<event>`         | 频道名=事件名,消息=键名                            |

> 注意:`__` 是双下划线,频道名固定前缀。

### 3. 订阅示例(以订阅过期为例)

#### 方式 1:订阅 keyspace(频道名=键名)

```bash
# 客户端 A(订阅方)
SUBSCRIBE __keyspace@0__:user:*
# 接收到的消息示例:
# 1) "message"
# 2) "__keyspace@0__:user:profile:1"
# 3) "expired"
```

#### 方式 2:订阅 keyevent(频道名=事件名)

```bash
# 客户端 A(订阅方)
SUBSCRIBE __keyevent@0__:expired
# 接收到的消息示例:
# 1) "message"
# 2) "__keyevent@0__:expired"
# 3) "user:profile:1"
```

### 4. 完整流程示例

```bash
# 步骤 1:开启过期通知
CONFIG SET notify-keyspace-events "Ex"

# 步骤 2:客户端 A 订阅过期
redis-cli SUBSCRIBE __keyevent@0__:expired

# 步骤 3:客户端 B 设置一个 1 秒后过期的键
redis-cli SET notify:test 'hello' EX 1

# 客户端 A 收到的消息:
# 1) "message"
# 2) "__keyevent@0__:expired"
# 3) "notify:test"
```

### 5. PSUBSCRIBE 模式订阅

```bash
# 订阅所有 db 的过期事件
PSUBSCRIBE __keyevent@*__:expired

# 订阅 user 前缀的所有事件
PSUBSCRIBE __keyspace@0__:user:*
```

### 6. 应用场景

| 场景                          | 实现                                              |
|-------------------------------|---------------------------------------------------|
| 多级缓存一致性                | Redis 失效时通知各应用节点清本地缓存             |
| 订单过期关闭                  | 监听 `__keyevent@0__:expired`,业务系统收到后关单 |
| 监控热点 key 淘汰             | 订阅 `evicted` 事件                               |
| 分布式 session 同步           | 监听特定前缀 session 的删除/过期                  |
| 数据变更审计                  | 订阅 `__keyevent@0__:hset` 等写事件              |

### 7. 注意事项

- **过期事件的时效性**:Redis 只在键被**惰性过期或定期过期触发删除时**才发通知,如果键从未被访问且未被定期扫描命中(理论极端情况下),事件可能不发。
- **重启会丢失**:Redis 重启时不会重新触发已过期的键的事件。
- **Pub/Sub 不持久化**:订阅客户端断开期间的事件**全部丢失**,需要重连或用其他补偿机制。
- **性能影响**:开启过多事件会增加 CPU 消耗,生产建议按需开启(只开 `Ex` / `Egx` 等)。
- **顺序保证**:同一键的多个事件按触发顺序到达,但跨键之间没有全局顺序保证。

## 核心要点速记

### 一、键命名

- 结构:**业务前缀:模块:业务ID[:子键]**,全小写、冒号分隔。
- 加业务前缀避免冲突;TTL 单独用 EX 设置,不要写进键名。
- 同一对象尽量用 Hash 存储,避免散键。
- 缓存键带版本号,便于 schema 升级。

### 二、TTL 与过期

- **EXPIRE / PEXPIRE / EXPIREAT / PEXPIREAT**:设置相对/绝对过期。
- **TTL / PTTL / EXPIRETIME / PEXPIRETIME**:查询剩余/绝对过期时间。
- **PERSIST**:取消过期。
- **过期策略 = 惰性过期 + 定期过期**,前者保证访问路径安全,后者回收冷数据内存。
- 7.0+ 的 EXPIRE 新增 NX / XX / GT / LT 选项,精细控制过期设置行为。

### 三、删除

- **DEL**:同步,O(N),**小 Key 场景**。
- **UNLINK**:异步(4.0+),**大 Key 首选**。
- **FLUSHDB / FLUSHALL**:必须 `rename-command` 屏蔽 + 运维审批。
- lazyfree-lazy-* 配置:从配置层兜底 DEL 的同步释放行为。

### 四、查找

- **KEYS pattern**:**生产禁用**(`rename-command KEYS ""`)。
- **SCAN cursor [MATCH] [COUNT] [TYPE]**:**生产唯一可用**的遍历方式,**游标式、不阻塞、支持 MATCH/COUNT/TYPE**。
- SCAN 可能重复或遗漏,客户端需做幂等处理。
- HSCAN/SSCAN/ZSCAN 分别用于 Hash/Set/ZSet 的元素遍历。

### 五、元信息与重命名

- **EXISTS / TYPE / RENAME / RENAMENX / MOVE**:基础元信息操作。
- 7.0 起 `EXISTS key1 key2 ...` 支持多键,减少 RTT。
- **MOVE** 已弃用趋势,集群/Sentinel 下不可用。

### 六、RANDOMKEY / DUMP / RESTORE

- **RANDOMKEY**:抽样调试。
- **DUMP / RESTORE**:**应用层迁移/备份键**,RDB 格式字节流。
- 跨大版本可能不兼容,需做兼容性测试。

### 七、OBJECT

- **REFCOUNT / ENCODING / IDLETIME / FREQ**:排查内存和淘汰的内部信息。
- **DEBUG OBJECT**:更详细的版本,生产慎用。
- OBJECT 命令本身会重置 idle/lfu,需要观察时优先用 DEBUG OBJECT 或 INFO。

### 八、WAIT

- **WAIT numreplicas timeout**:写入后阻塞等 N 个副本 ACK,关键数据(订单/支付)用。
- 7.0+ 有 **WAITOF** 支持异步复制 ACK。
- 高 QPS 不建议用 WAIT,优先业务补偿。

### 九、COPY / TOUCH

- **COPY src dst [DB n] [REPLACE]**:**浅拷贝**(6.2+)。
- **TOUCH key1 key2 ...**:仅更新 LRU/LFU 时间戳,**防止冷数据被淘汰**,也可用于缓存预热。

### 十、SORT / GETRANGE

- **SORT**:性能差,**生产慎用**,能用 Sorted Set 就用 ZSet。
- **SUBSTR** 已弃用,**用 GETRANGE**。

### 十一、键空间通知

- 配置:`notify-keyspace-events "Ex"`(只启用过期)或 `"KEA"`(所有事件)。
- 两类频道:
  - `__keyspace@<db>__:<key>` 消息是事件名。
  - `__keyevent@<db>__:<event>` 消息是键名。
- 应用:缓存失效广播、订单过期、淘汰监控。
- 注意:Pub/Sub 不持久化,断连期间事件丢失。
- 过期事件有"被动触发"特性,极端情况下可能不发。

### 十二、DEBUG

- **生产必须** `rename-command DEBUG ""` 或 ACL 屏蔽。
- 调试利器:`DEBUG OBJECT`、`DEBUG SLEEP`、`DEBUG SET-ACTIVE-EXPIRE`、`DEBUG POPULATE`。

### 十三、一句话总结

> **生产 Redis 键管理的铁律**:
>
> **命名规范、可观测、可治理**。
>
> 严禁 `KEYS`、慎用 `DEL` 大 Key、优先 `UNLINK`、遍历一律 `SCAN`、过期靠 TTL、事件靠 Keyspace Notification、危险命令一律 `rename-command` 屏蔽、关键写入加 `WAIT`。
