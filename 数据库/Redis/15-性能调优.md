## 一、Redis 性能基准

### 1.1 redis-benchmark 工具详解

`redis-benchmark` 是 Redis 官方提供的基准测试工具，能模拟多客户端并发执行指定命令并统计吞吐量（P99 延迟、每秒操作数）。

**基本用法**：

```bash
# 1. 默认基准（3 个客户端、100000 次请求、SET/GET/SETNX/HSET 等）
$ redis-benchmark -h 127.0.0.1 -p 6379

# 2. 指定测试命令（仅 SET）
$ redis-benchmark -t set -n 100000 -c 50 -d 256
# -t 指定命令集
# -n 总请求数
# -c 并发客户端数（默认 50）
# -d 单值字节数（默认 3）

# 3. 指定并发、连接数、PIPELINE
$ redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 100000 -c 50 -P 10
# -P 每个 pipeline 包含的命令数（默认 1）
```

**完整参数清单**：

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `-h` | 服务器主机 | 127.0.0.1 |
| `-p` | 服务器端口 | 6379 |
| `-s` | 服务器 socket | - |
| `-a` | AUTH 密码 | - |
| `-n` | 总请求数 | 100000 |
| `-c` | 并发客户端数 | 50 |
| `-d` | SET/GET 值字节数 | 3 |
| `-dbnum` | 选择的 DB | 0 |
| `-k` | 是否 keepalive | 1 |
| `-r` | 随机键范围（SADD/ZADD 用） | - |
| `-P` | pipeline 条数 | 1 |
| `-q` | 安静模式（只显示 QPS） | - |
| `--csv` | CSV 输出 | - |
| `-l` | 循环运行 | - |
| `-t` | 仅测试指定命令 | 所有命令 |

## 二、Redis 慢查询分析

### 2.1 慢查询的两个核心配置

```bash
# redis.conf
slowlog-log-slower-than 10000      # 慢查询阈值（微秒）,10000 = 10ms
slowlog-max-len 128                # 慢查询日志最大条数（FIFO 队列）
```

**`slowlog-log-slower-than`**：单位微秒，记录执行时间超过此值的命令。**生产推荐 5-10ms**（5000-10000 μs），过小会记录过多普通命令影响调试。

**`slowlog-max-len`**：慢日志队列最大长度。生产推荐 1000-5000，保留足够历史。

### 2.2 SLOWLOG 系列命令

```bash
127.0.0.1:6379> SLOWLOG GET 10           # 取最近 10 条慢日志
127.0.0.1:6379> SLOWLOG LEN                # 当前队列长度
127.0.0.1:6379> SLOWLOG RESET              # 清空慢日志
127.0.0.1:6379> CONFIG SET slowlog-log-slower-than 5000  # 动态修改阈值
```

### 2.3 慢查询日志输出解读

```text
127.0.0.1:6379> SLOWLOG GET 3
1) 1) (integer) 1234567               # 唯一 id
   2) (integer) 1692345678            # 时间戳（Unix 秒）
   3) (integer) 12543                 # 耗时（微秒），12.5 ms
   4) 1) "HGETALL"                    # 命令名
      2) "user:profile:10086"         # 参数
   5) "127.0.0.1:52345"               # 客户端 ip:port
   6) ""                              # 客户端名称（CLIENT SETNAME）
2) 1) (integer) 1234566
   2) (integer) 1692345670
   3) (integer) 89021                 # 89 ms ← 超时
   4) 1) "KEYS"
      2) "*"
   5) "127.0.0.1:52348"
   6) "monitor-job"
3) ...
```

**关键字段**：

| 字段 | 含义 |
|------|------|
| id | 唯一标识 |
| timestamp | 发生时间 |
| duration | 耗时（μs） |
| argv | 命令与参数 |
| client_addr | 客户端来源 |
| client_name | 客户端逻辑名（用 CLIENT SETNAME 设置） |

### 2.4 慢查询分析实战

```bash
# 1. 找到最耗时的 10 条慢命令
$ redis-cli SLOWLOG GET 1000 | grep -A1 "^\s*[0-9])" | grep duration | sort -k2 -n -r | head

# 2. 统计每类命令的慢查询次数
$ redis-cli SLOWLOG GET 1000 | grep -oP '"[A-Z]+"' | sort | uniq -c | sort -rn

# 3. 通过 CLIENT LIST 找到具体客户端
$ redis-cli CLIENT LIST | grep -E "addr=127.0.0.1:52345"
```

> **生产经验**：80% 的 Redis 性能问题来自 5-10 条 O(N) 命令（HGETALL、KEYS、SMEMBERS）。把慢查询阈值设为 5ms，把 SLOWLOG 接到 ELK 告警，是性价比最高的优化手段。

## 三、Redis 单线程模型（6.0 前）

### 3.1 为什么单线程还快

Redis 6.0 之前的"单线程"指的是**命令执行线程**单线程化，并非整个进程单线程。Redis 仍然有：

- 主线程：负责命令接收、执行、响应、AOF 写、惰性过期
- 后台线程：RDB 持久化、AOF rewrite、关闭文件、AOF fsync（部分异步）

**单线程快的原因**：

| 原因 | 说明 |
|------|------|
| **内存访问** | 数据全在内存，避免 CPU 等待磁盘 IO |
| **非阻塞 IO 多路复用** | epoll/select/kqueue 单线程监听大量连接 |
| **避免锁竞争** | 不存在多线程共享数据，无需加锁 |
| **CPU 亲和性** | 单线程长时间占用 CPU，L1/L2 cache 命中率高 |
| **协议简单** | RESP 协议解析开销小 |

**单线程的代价**：

- **任何一条命令的执行都会阻塞后续所有命令**
- 不适合执行 O(N) 大命令（KEYS、HGETALL 等）
- 单个客户端慢请求会导致整个实例卡顿

### 3.2 Redis 6.0 多线程 IO 详解

```text
┌──────────────────────────────────────────────────────────────────┐
│              Redis 6.0 多线程 IO 架构                               │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   客户端 1 ─┐                                                     │
│   客户端 2 ─┤                                                     │
│   客户端 N ─┤                                                     │
│             ▼                                                     │
│   ┌──────────────────┐                                            │
│   │  IO 线程池（读写）│   ←─ 新增：io-threads 4                     │
│   │  T1 T2 T3 T4      │   并行读取请求、并行回写响应                 │
│   └────────┬─────────┘                                            │
│            │                                                      │
│            ▼                                                      │
│   ┌──────────────────┐                                            │
│   │   主线程（单）    │   ←─ 命令执行仍单线程                       │
│   │   - 命令解析      │   （避免锁开销,保持核心优势）                │
│   │   - 执行命令      │                                            │
│   │   - AOF/RDB 写  │                                            │
│   └──────────────────┘                                            │
│                                                                  │
│   ⚠ 多线程 IO 默认关闭,需显式开启 io-threads-do-reads yes          │
└──────────────────────────────────────────────────────────────────┘
```

**6.0 多线程 IO 适用范围**：

| 阶段 | 多线程？ | 说明 |
|------|---------|------|
| 网络读 | 是 | IO 线程负责把数据从 socket 读到内存 |
| 命令解析 | 是 | IO 线程解析 RESP 协议 |
| 命令执行 | **否** | 主线程单线程执行（保持简单） |
| 网络写 | 是 | IO 线程把响应写回 socket |

> **收益**：高并发场景（10 万+ QPS）下多线程 IO 能让 QPS 提升 50-100%；低并发场景收益甚微。

### 4.2 网络瓶颈

**诊断**：

```bash
# 查看网卡流量
$ sar -n DEV 1 5
$ cat /sys/class/net/eth0/statistics/rx_bytes

# Redis 端延迟
$ redis-cli --latency -h 127.0.0.1 -p 6379
min: 0, max: 1, avg: 0.12 (1152 samples)

# 网络往返
$ redis-cli --latency-history -i 1
```

**解决**：

- 单 key 大 value 压缩 / 拆分
- Pipeline / 多 key 命令减少 RTT
- 客户端就近部署（同机房 / 同可用区）
- 升级到万兆网卡

### 4.3 内存瓶颈

**诊断**：

```bash
$ redis-cli INFO MEMORY
used_memory: 8589934592          # 8GB
used_memory_human: 8.00G
used_memory_rss: 11206656000    # 10.5GB（含碎片）
used_memory_peak: 9000000000
maxmemory: 10737418240          # 10GB
maxmemory_human: 10G
mem_fragmentation_ratio: 1.30   # 碎片率
```

**告警阈值**：

| 指标 | 阈值 | 处理 |
|------|------|------|
| `used_memory / maxmemory` | > 80% | 扩容 / 淘汰 |
| `mem_fragmentation_ratio` | > 1.5 | 启用 activedefrag |
| `mem_fragmentation_ratio` | < 1 | 内存 swap，需扩容 |
| `evicted_keys` 增量 | > 100/min | 调大 maxmemory 或优化 key |

### 4.4 CPU 瓶颈

**诊断**：

```bash
$ top -Hp <redis_pid>        # 看主线程 CPU
$ pidstat -u -p <redis_pid> 1 5
$ perf top -p <redis_pid>    # CPU 热点函数
```

**关键现象**：Redis 进程的 CPU 100% 被**主线程**（通常 PID 最小）占用。

**解决**：

- 找出并替换慢命令（HGETALL → HMGET、KEYS → SCAN）
- 多线程 IO 开启（6.0+）
- 多实例拆分（按业务分片）

### 4.5 磁盘 IO 瓶颈

```bash
$ cat /proc/<redis_pid>/io
```

## 五、客户端优化

### 5.1 连接池配置

**JedisPool 推荐配置**：

```java
JedisPoolConfig poolConfig = new JedisPoolConfig();
poolConfig.setMaxTotal(200);                  // 最大连接数
poolConfig.setMaxIdle(50);                    // 最大空闲
poolConfig.setMinIdle(10);                    // 最小空闲
poolConfig.setMaxWaitMillis(2000);            // 获取连接超时
poolConfig.setTestOnBorrow(false);            // 借时不检测
poolConfig.setTestWhileIdle(true);            // 闲置时心跳检测
poolConfig.setTimeBetweenEvictionRunsMillis(30000);
poolConfig.setMinEvictableIdleTimeMillis(60000);

JedisPool pool = new JedisPool(poolConfig, "redis-host", 6379, 2000, "password");
```

**Lettuce 推荐配置**：

```java
ClientResources resources = ClientResources.builder()
    .ioThreadPoolSize(8)               // IO 线程数
    .computationThreadPoolSize(4)
    .build();

RedisClient client = RedisClient.create(resources, "redis://redis-host:6379");
client.setDefaultTimeout(Duration.ofSeconds(2));

// Lettuce 默认基于 Netty,支持异步、自动重连
```

> **连接数经验公式**：`maxTotal = (核心业务并发线程数 × 1.5) + 备用`。盲目调大连接数会拖垮 Redis（默认 maxclients 10000）。

### 5.2 Pipeline 批量操作

**普通命令（N 次网络往返）**：

```text
客户端            Redis
  │ ──SET k1──►  │
  │ ◄──OK───     │
  │ ──SET k2──►  │
  │ ◄──OK───     │     N 次 RTT
  │ ...           │
```

**Pipeline 模式（1 次网络往返）**：

```text
客户端                     Redis
  │ ──SET k1 SET k2 ...──► │
  │ ◄─OK OK ... (一次性)    │   1 次 RTT
```

**Jedis Pipeline**：

```java
Pipeline p = jedis.pipelined();
for (int i = 0; i < 1000; i++) {
    p.set("k:" + i, "v:" + i);
}
p.sync();
```

**Lettuce 异步 Pipeline**：

```java
RedisAsyncCommands<String, String> async = client.connect().async();
List<RedisFuture<String>> futures = new ArrayList<>();
for (int i = 0; i < 1000; i++) {
    futures.add(async.set("k:" + i, "v:" + i));
LettuceFutures.awaitAll(1, TimeUnit.SECONDS, futures.toArray(new RedisFuture[0]));
```

### 5.3 避免危险命令

| 命令 | 风险 | 替代 |
|------|------|------|
| `KEYS *` | O(N) 阻塞 | `SCAN` 迭代 |
| `MONITOR` | 全量记录，吞吐暴跌 | 用 SLOWLOG 替代 |
| `DEBUG SLEEP` | 阻塞 N 秒 | 仅调试 |
| `FLUSHALL` | 清空所有数据 | 仅测试环境 |
| `CLIENT KILL` | 不当使用会杀错连接 | 谨慎 |
| `SHUTDOWN` | 关闭实例 | 仅维护 |
| `CONFIG SET ... save ""` | 关闭持久化 | 备份后操作 |

## 六、减少网络往返

### 6.1 Pipeline vs MGET/MSET

| 方式 | 命令 | 特点 |
|------|------|------|
| **MSET/MSETNX** | `MSET k1 v1 k2 v2 ...` | 单条原子命令,服务端一次处理 |
| **MGET** | `MGET k1 k2 k3 ...` | 单条原子命令,一次返回多个 value |
| **Pipeline** | 多次 SET/GET | 通用批量,无原子保证 |

**对比**：

| 维度 | MSET/MGET | Pipeline |
|------|-----------|----------|
| 网络往返 | 1 次 | 1 次 |
| 服务端处理 | 单命令,高效 | 拆成 N 命令处理 |
| 原子性 | 是 | 否（按命令分别应答） |
| 灵活性 | 仅支持指定类型 | 任意命令组合 |
| 适用场景 | 简单批量读写 | 复杂组合操作 |

### 6.2 Lua 脚本服务端聚合

```lua
-- 单次 RTT 完成"读-改-写"逻辑
local current = redis.call("GET", KEYS[1])
if current and tonumber(current) > 0 then
    redis.call("DECR", KEYS[1])
    return tonumber(current) - 1
end
return -1
```

```bash
127.0.0.1:6379> EVAL "..." 1 inventory:item:10086
```

**优势**：客户端→服务端 1 次 RTT，服务端原子执行整段逻辑，避免竞态。

**Lua vs Pipeline 选择**：

- 简单批读：MGET / MSET（最快）
- 多 key 关联运算：Lua（原子）
- 多种命令批量执行：Pipeline（最灵活）

### 6.3 Multi-key 命令

| 命令 | 用途 |
|------|------|
| `MSET k1 v1 k2 v2` | 批量写入 |
| `MGET k1 k2 k3` | 批量读取 |
| `MSETNX k1 v1 k2 v2` | 批量写入（仅当所有 key 都不存在） |
| `DEL k1 k2 k3` | 批量删除 |
| `EXISTS k1 k2 k3` | 批量存在性检查 |
| `UNLINK k1 k2 k3` | 异步批量删除 |
| `TOUCH k1 k2 k3` | 批量更新访问时间 |

## 七、持久化性能优化

### 7.1 RDB vs AOF 对吞吐量的影响

| 模式 | 写吞吐 | 持久性 | 适用 |
|------|--------|--------|------|
| **RDB** | 高 | 中（丢失最后一次快照后数据） | 缓存 / 可容忍分钟级丢失 |
| **AOF everysec** | 中（~10% 损耗） | 高（最多丢 1 秒） | 关键数据 |
| **AOF always** | 低（~50% 损耗） | 最高 | 极少用 |
| **RDB + AOF 混合（7.0+）** | 中 | 高 | **生产推荐** |

### 7.2 AOF rewrite 策略

```bash
# redis.conf
auto-aof-rewrite-percentage 100   # 当前 AOF 文件比上次 rewrite 后增长 100% 触发
auto-aof-rewrite-min-size 64mb   # 最小 AOF 文件大小,避免小文件频繁 rewrite
aof-use-rdb-preamble yes         # 7.0+ 混合持久化(推荐开启)
```

**手动触发**：

```bash
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started
```

### 7.3 no-appendfsync-on-rewrite

```bash
# redis.conf
no-appendfsync-on-rewrite yes     # rewrite 期间不 fsync(避免阻塞)
```

**机制**：AOF rewrite 时，主线程 fork 子进程做 rewrite，主线程继续接收命令。开启此配置后，rewrite 期间 appendfsync 改为 no（即不 fsync），减少磁盘 IO 抖动。代价是 rewrite 期间最多丢一次 fsync 周期的数据。

**生产推荐**：开启。rewrite 期间数据丢失是可接受的，但卡顿不可接受。

### 7.4 appendfsync 三种策略

| 值 | 行为 | 性能 | 数据安全 |
|----|------|------|----------|
| `always` | 每条命令 fsync | 最差 | 最高（最多丢 1 条） |
| `everysec` | 每秒 fsync（后台线程） | 良好 | 高（最多丢 1 秒） |
| `no` | 由 OS 决定 | 最好 | 中（取决于 OS） |

**生产推荐 `everysec`**，兼顾性能与安全。

## 八、内存优化（聚焦性能）

### 8.1 减少 BigKey

| 数据类型 | BigKey 阈值 | 影响 |
|----------|-------------|------|
| String | > 10KB | 单命令阻塞 |
| Hash | > 5000 fields | HGETALL 卡顿 |
| List | > 5000 元素 | LRANGE 卡顿 |
| Set | > 5000 元素 | SMEMBERS 卡顿 |
| ZSet | > 5000 元素 | ZRANGE 卡顿 |

**优化方法**：

- 拆分（按时间 / 用户 ID 哈希）
- 压缩 value（gzip / LZ4 / snappy）
- 用 Hash 替代多个 String（同前缀 key）

### 8.2 选择合适编码

Redis 自动选择底层编码（详见第 2 章），可通过 `OBJECT ENCODING key` 查看：

```bash

OK

"embstr"          # 短字符串:连续内存,更快

127.0.0.1:6379> HSET h f v
OK
127.0.0.1:6379> OBJECT ENCODING h
"listpack"        # 小 hash:listpack 编码,更紧凑
```

**编码阈值配置**：

```bash
hash-max-listpack-entries 128
hash-max-listpack-value 64
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

**影响**：小集合用 listpack 节省 60%+ 内存，CPU 也更快。

### 8.3 共享对象池（RedisObject refcount = 1 才共享）

```text
�──────────────────────────────────────────────────────────────────┐
│                  共享对象池机制                                     │
├──────────────────────────────────────────────────────────────────�

│   refcount = 1 时,不共享,独立内存                                  │
```

## 九、慢命令分析

### 9.1 O(N) 命令家族

| 命令 | 复杂度 | 危险等级 | 替代 |
|------|--------|----------|------|
| `KEYS pattern` | O(N) | 极高 | `SCAN` |
| `HGETALL key` | O(N) | 高 | `HSCAN` / `HMGET` |
| `SMEMBERS key` | O(N) | 高 | `SSCAN` |
| `ZRANGE key 0 -1` | O(log N + M) | 中-高 | `ZSCAN` / 分页 |
| `LRANGE key 0 -1` | O(S+N) | 中-高 | 分页迭代 |
| `SORT key` | O(N+M*log M) | 高 | 业务侧排序 |
| `DEL bigkey` | O(N) | 高 | `UNLINK` |
| `MIGRATE` | O(N) | 中 | 业务侧分批 |
| `FLUSHDB/ALL` | O(N) | 高 | 分批清理 |

### 9.2 SCAN 家族替代 KEYS

```bash
# 错误:阻塞,生产禁止
127.0.0.1:6379> KEYS "user:*"

# 正确:游标迭代,不阻塞
127.0.0.1:6379> SCAN 0 MATCH "user:*" COUNT 1000
1) "12345"                     # 下次游标
2)  1) "user:1001"
    2) "user:1002"
    ...

127.0.0.1:6379> SCAN 12345 MATCH "user:*" COUNT 1000
...
```

**完整迭代**：

```java
String cursor = "0";
do {
    ScanResult<String> result = jedis.scan(cursor, new ScanParams().match("user:*").count(1000));
    cursor = result.getCursor();
    // 处理 result.getResult()
} while (!"0".equals(cursor));
```

### 9.3 Hash/Set/ZSet 迭代命令

```bash
HSCAN key 0 MATCH "field:*" COUNT 1000
SSCAN key 0 MATCH "member:*" COUNT 1000
ZSCAN key 0 MATCH "member:*" COUNT 1000
```

**注意**：HSCAN/SSCAN/ZSCAN 返回结果不保证顺序（与 SCAN 一样是游标迭代）。

### 9.4 LRANGE 大范围分页

```bash
# 错误:返回 10 万条数据,阻塞
127.0.0.1:6379> LRANGE biglist 0 -1

# 正确:分页
127.0.0.1:6379> LRANGE biglist 0 99
127.0.0.1:6379> LRANGE biglist 100 199
...

# 更好:用 Sorted Set 替代 List 做分页(可按 score 范围取)
127.0.0.1:6379> ZRANGEBYSCORE zset 0 100 WITHSCORES LIMIT 0 100
```

## 十一、IO 多线程配置（6.0+）

### 11.1 配置项

```bash
# redis.conf
io-threads 4                    # IO 线程数(含主线程),所以 4 表示 3 个 IO 线程 + 1 主线程
io-threads-do-reads yes         # 是否在 IO 线程处理读(默认 no)
```

**线程数选择**：

| CPU 核数 | 推荐 io-threads |
|----------|------------------|
| 4 | 3 |
| 8 | 5-7 |
| 16 | 8 |
| 32 | 8-12 |

> **不要超过 CPU 核数**。超过会因线程上下文切换反而降低性能。

### 11.2 何时启用

| 场景 | 启用建议 |
|------|----------|
| QPS > 10 万 + 多客户端 | 强烈推荐 |
| QPS 1-5 万 | 可启用,收益一般 |
| QPS < 1 万 | 不推荐（徒增复杂度） |
| value 大（> 1KB）| 启用（IO 收益明显） |
| 短连接频繁 | 启用 |

### 11.3 启用步骤

```bash
# 1. 修改 redis.conf
io-threads 4
io-threads-do-reads yes

# 2. 重启 Redis(必须重启,不能 CONFIG SET)
$ redis-cli SHUTDOWN NOSAVE
$ redis-server /etc/redis.conf

# 3. 验证
$ redis-cli INFO stats | grep io_threads
```

## 十二、RESP3 协议（6.0+）

### 12.1 RESP2 vs RESP3

| 维度 | RESP2 | RESP3 |
|------|-------|-------|
| 类型支持 | 5 种 | 多种（含 Map、Set、Double、Boolean、BlobError、Stream、Verbatim） |
| 客户端缓存 | 不支持 | 支持（`CLIENT TRACKING`） |

| Hello 命令 | - | `HELLO 3 AUTH ...` 切换 |

### 12.2 RESP3 客户端缓存（Tracking）

```text
┌──────────────────────────────────────────────────────────────────┐
│                  RESP3 客户端缓存(Tracking)                       │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   Redis 维护 invalidation table,记录被修改的 key                  │
│                                                                  │
│   客户端:GET k1 → 缓存 k1=v1                                     │

│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

```bash

```

**性能收益**：读多写少场景（如 CDN、配置中心），服务端直推失效消息，避免轮询。

## 十三、客户端连接优化

### 13.1 TCP backlog

```bash
# redis.conf
tcp-backlog 511                # Linux 默认 somaxconn
```

**含义**：Redis 监听 socket 的 TCP 连接队列长度。高并发连接场景下，调大此值可避免连接被拒绝（`connect: Connection refused`）。

**建议**：

```bash
# /etc/sysctl.conf
net.core.somaxconn = 1024
net.ipv4.tcp_max_syn_backlog = 8192

# 验证
$ sysctl net.core.somaxconn
net.core.somaxconn = 1024
```

**生产推荐**：`tcp-backlog 1024`（或与 OS 一致）。

### 13.2 TCP keepalive

```bash
# redis.conf
tcp-keepalive 300              # 5 分钟检测一次,默认 300 秒
```

**作用**：服务端主动向客户端发 ACK，检测死连接。避免长时间空闲连接堆积。

**生产推荐**：`tcp-keepalive 60`（1 分钟），更激进地清理死连接。

### 13.3 maxclients 限制

```bash
# redis.conf
maxclients 10000               # 默认 10000
```

**触发**：客户端连接数超过 maxclients 时，Redis 关闭新连接并报错 `max number of clients reached`。

**调优建议**：

```bash
# 1. 临时调整
127.0.0.1:6379> CONFIG SET maxclients 50000

# 2. 永久生效(redis.conf)
maxclients 50000
```

**配套**：

```bash
# /etc/security/limits.conf
redis soft nofile 65536
redis hard nofile 65536

# 启动脚本
ulimit -n 65536
```

> **关键**：操作系统 `ulimit -n` 必须 ≥ maxclients，否则 Redis 启动会失败。

## 十四、集群规模与性能关系

### 14.1 单实例多大数据量合适

| 数据量 | 单实例 QPS 建议 | 说明 |
|--------|----------------|------|
| < 10 GB | 任意 QPS | 通用 |
| 10-50 GB | < 10 万 | 注意 fork 阻塞 |
| 50-100 GB | < 5 万 | 强烈推荐分片 |
| > 100 GB | - | **必须 Cluster 分片** |

**核心原则**：

- 单实例内存 ≤ 50GB（避免 fork 阻塞严重）
- 单实例 QPS ≤ 10 万（避免 CPU 打满）
- 单实例 key 数量 ≤ 1 亿（避免 SCAN 慢）

### 14.2 Cluster 集群 vs 单机性能

| 维度 | 单机 | Cluster |
|------|------|---------|
| 单 key QPS | ~15 万 | ~13 万（略降,因 slot 路由） |
| 整体 QPS | 受限单机 | N 倍水平扩展 |
| 多 key 事务 | 原生支持 | 必须同 slot（用 hashtag） |
| 容量 | 单机内存 | N × 单机内存 |
| 运维 | 简单 | 复杂（迁移、reshard） |

**性能损耗点**：

- 客户端需计算 slot（CRC16）路由
- 跨 slot 操作需在客户端聚合
- MOVED/ASK 重定向在 slot 迁移时增加 RTT
- Gossip 协议占用少量带宽

### 14.3 hashtag 模式

```bash
# 用 {} 强制同 slot
127.0.0.1:6379> MSET {user:10086}.name "Tom" {user:10086}.age "20"
# 这两个 key 一定在同一 slot,MSET 不会失败

127.0.0.1:6379> MGET {user:10086}.name {user:10086}.age
```

## 核心要点速记

| # | 要点 |
|---|------|
| 1 | **性能优化从基准开始**:用 `redis-benchmark` 在目标硬件做基线,记录 GET/SET/INCR 等 QPS 与 P99 延迟 |
| 2 | **慢查询是性能调优的金矿**:`slowlog-log-slower-than 5000` 是生产推荐阈值,把 SLOWLOG 接入告警 |
| 3 | **Redis 6.0 前命令执行单线程**:任何一条慢命令阻塞后续所有命令,O(N) 命令是头号杀手 |
| 4 | **Redis 6.0+ IO 多线程**:高 QPS 场景启用 `io-threads 4` + `io-threads-do-reads yes`,线程数不超过 CPU 核数 |
| 5 | **O(N) 命令必须替换**:`KEYS→SCAN`、`HGETALL→HMGET/HSCAN`、`SMEMBERS→SSCAN`、`LRANGE→分页` |
| 6 | **网络往返是隐性瓶颈**:Pipeline 一次发多条命令,MSET/MGET 一次处理多 key,Lua 服务端聚合 |
| 7 | **客户端连接池必备**:JedisPool / Lettuce 配置合理 `maxTotal`,避免每次新建连接 |
| 8 | **持久化三选一优化**:`appendfsync everysec` + `no-appendfsync-on-rewrite yes` + 7.0 混合持久化 |
| 9 | **内存优化聚焦性能**:减少 bigkey、合理编码阈值、lazyfree 异步删除、activedefrag 碎片整理 |
| 10 | **网络参数调优**:`tcp-backlog 1024` + `tcp-keepalive 60` + `maxclients` 配套 `ulimit` |
| 11 | **集群规模控制**:单实例 ≤ 50GB 内存、≤ 10 万 QPS,超限用 Cluster 水平扩展 |
| 12 | **Cluster 用 hashtag**:`{}` 强制同 slot,保证多 key 原子操作 |
| 13 | **响应协议升级**:RESP3 支持客户端缓存(Tracking),读多写少场景显著降低 RTT |
| 14 | **共享对象池仅小整数**:0-9999 整数共享,长字符串不共享,业务应避免大 value |
| 15 | **性能监控三件套**:`redis-cli --latency` + `INFO stats` + `INFO commandstats`,三者缺一不可 |
| 16 | **慢命令定位**:`INFO commandstats` 按 `usec_per_call` 倒序找最慢命令,精准优化 |
| 17 | **hit_ratio 是缓存健康度**:`keyspace_hits / (hits + misses)`,< 0.8 需扩内存或优化 key 设计 |
| 18 | **大 Key 三害**:阻塞主线程、占带宽、删除风暴;`--bigkeys` + `MEMORY USAGE` 定期扫描 |
| 19 | **Redis 7.0+ 混合持久化**:`aof-use-rdb-preamble yes`,RDB 头部 + 增量 AOF,兼顾恢复速度与数据安全 |
| 20 | **调优 Checklist 闭环**:基准→慢查询→命令替换→客户端→内存→持久化→连接→集群→监控,逐项落地 |
