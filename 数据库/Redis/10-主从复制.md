# Redis 主从复制 (Master-Slave Replication)

> 本章覆盖 Redis 主从复制完整体系:复制意义、配置方式、复制原理、全量同步与部分同步、复制风暴、延迟监控、读写分离、故障转移配合、与 Sentinel/Cluster 衔接。理解主从复制是构建 Redis 高可用架构的基石。

---

## 一、主从复制概述

### 1. 什么是主从复制

Redis 主从复制(Master-Slave Replication)是指将一台 Redis 服务器(主节点)的数据**异步**复制到一台或多台其他 Redis 服务器(从节点)的过程。主节点负责处理所有写入命令,从节点默认对外只读,并实时接收主节点的写入数据,保持与主节点数据一致。

```text
┌────────────────┐                          ┌────────────────┐
│    Master      │ ──── 写入复制流 ────────> │    Slave-1     │
│  (读写)        │                          │   (只读)       │
│                │ ──── 写入复制流 ────────> └────────────────┘
│  replication   │
│  stream        │                          ┌────────────────┐
│                │ ──── 写入复制流 ────────> │    Slave-2     │
└────────────────┘                          │   (只读)       │
                                            └────────────────┘
```

**核心特性**：

- **一个主节点**可以有 **多个从节点**
- **一个从节点**只能有 **一个主节点**（不支持多主复制，除非 Cluster）
- 复制是 **单向** 的：主 → 从，从节点不会反向同步给主
- 复制是 **异步** 的：主节点写入后立即返回，不等待从节点 ACK

### 2. 为什么需要主从复制

| 场景 | 单机问题 | 复制后解决方案 |
|------|----------|----------------|
| 数据丢失 | 宕机/磁盘故障数据全丢 | 多机冗余，单机故障不丢数据 |
| 读压力 | 单机读能力有上限 | 一主多从分散读请求 |
| 写入性能 | 单机写吞吐有限 | 主从分离写入，避免单点瓶颈 |
| 故障恢复 | 单机宕机服务中断 | 从节点可快速提升为主 |
| 运维需求 | 备份需阻塞主进程 | 从节点做备份，不影响主 |

### 3. 复制的三大作用

| 作用 | 说明 |
|------|------|
| **数据冗余** | 主从复制实现数据的热备份，是持久化之外的数据安全保障 |
| **读写分离** | 主节点处理写请求，从节点处理读请求，分摊压力，提升系统吞吐 |
| **故障恢复** | 主节点故障时，可将从节点提升为主节点继续提供服务（需配合 Sentinel） |

## 二、复制的配置

### 1. 命令方式

Redis 5.0 之前使用 `SLAVEOF`，5.0 起推荐 `REPLICAOF`（语义更中性），但 `SLAVEOF` 仍保留兼容。

```bash
# Redis 5.0+ 推荐
REPLICAOF <master_ip> <master_port>

# 旧版兼容
SLAVEOF <master_ip> <master_port>

# 取消复制（使当前节点成为独立主节点）
REPLICAOF NO ONE
SLAVEOF NO ONE
```

**实战示例**：

```bash
# 假设主库 192.168.1.10:6379
127.0.0.1:6380> REPLICAOF 192.168.1.10 6379
OK

# 查看复制状态
127.0.0.1:6380> INFO replication
```

**配置复制账号（主库执行）**：

```bash
# 主库创建只读复制账号（Redis 6.0+ ACL）
127.0.0.1:6379> ACL SETUSER repluser on ">replpass123" ~* +@read +psync +replconf +ping

# 或低版本兼容
127.0.0.1:6379> CONFIG SET requirepass "your_master_password"
```

**从库配置认证**：

```bash
# 方式一：启动时
redis-server --port 6380 --replicaof 192.168.1.10 6379 --masterauth your_master_password

# 方式二：运行时
127.0.0.1:6380> CONFIG SET masterauth "your_master_password"
127.0.0.1:6380> REPLICAOF 192.168.1.10 6379
```

### 2. 配置文件方式

生产环境推荐使用配置文件，永久生效。

```conf
# ========= 从节点 redis.conf =========

# 监听端口
port 6380

# 绑定 IP
bind 0.0.0.0

# 声明主节点（推荐 replicaof，5.0+）
replicaof 192.168.1.10 6379

# 主节点密码（生产必须配置）
masterauth "your_master_password"

# 从节点是否只读（强烈推荐开启）
replica-read-only yes

# 复制策略（diskless 是无盘复制，适合大实例）
repl-diskless-sync no           # 默认 no，使用磁盘中转
repl-diskless-sync-delay 5      # 无盘复制延迟（无盘模式才生效）

# 复制积压缓冲区（部分重同步关键）
repl-backlog-size 1mb           # 环形缓冲区大小，1mb 是最小值
repl-backlog-ttl 3600           # 从节点断开后积压缓冲保留时间（秒）

# 从节点发送心跳间隔（默认 10 秒）
repl-ping-replica-period 10

# 超时相关
repl-timeout 60                 # 复制超时（默认 60 秒）

# TCP backlog
repl-backlog-size 1mb
```

**关键参数说明**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `replicaof` | 无 | 声明主节点 IP:PORT |
| `masterauth` | 无 | 主节点密码 |
| `replica-read-only` | yes | 从节点是否只读 |
| `repl-diskless-sync` | no | 是否启用无盘复制 |
| `repl-backlog-size` | 1mb | 复制积压缓冲区大小 |
| `repl-ping-replica-period` | 10 | 心跳间隔（秒） |
| `repl-timeout` | 60 | 复制超时 |

### 3. 一主多从架构

```text
                          ┌─────────────────┐
                          │   Master        │
                          │   (写入)         │
                          └─────────────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            │                      │                      │
            ▼                      ▼                      ▼
     ┌─────────────┐       ┌─────────────┐       ┌─────────────┐
     │  Slave-1    │       │  Slave-2    │       │  Slave-3    │
     │  (读/备份)  │       │  (读/报表)  │       │  (读/容灾)  │
     └─────────────┘       └─────────────┘       └─────────────┘
```

**适用场景**：读多写少、业务可拆分（如查询走 Slave-1，报表走 Slave-2）。

### 4. 级联复制（树状复制）

当从节点数量很多时，主节点要向所有从节点同步数据，IO 压力剧增。级联复制让部分从节点挂载到中间从节点上。

```text
                                 ┌─────────────────┐
                                 │   Master        │
                                 └─────────────────┘
                                          │
                                          ▼
                                 ┌─────────────────┐
                                 │  Slave-1        │
                                 │  (中间节点)       │
                                 └─────────────────┘
                                          │
                       ┌──────────────────┼──────────────────┐
                       ▼                  ▼                  ▼
                ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
                │  Slave-2    │    │  Slave-3    │    │  Slave-4    │
                └─────────────┘    └─────────────┘    └─────────────┘
```

**配置级联**：

```conf
# Slave-1（中间节点）必须开启 repl-backlog 并允许继续向下复制
replica-read-only yes
repl-backlog-size 10mb

# Slave-2/3/4 配置
replicaof <slave-1_ip> 6380
masterauth "your_master_password"
```

**优点**：降低主节点压力，支持海量从节点。

**缺点**：中间节点故障，其下游全部断流；复制链路变长，延迟叠加。

## 三、复制原理

### 1. 复制的三个阶段

Redis 复制从连接到稳定同步分为三个阶段：

```text
阶段 1: 连接建立阶段
  从 → 主: 发起 socket 连接
  验证身份 (masterauth)
  协商复制参数
  
阶段 2: 数据同步阶段
  从 → 主: PSYNC <replid> <offset>
  主: 根据情况选择 全量同步 或 部分同步
  
阶段 3: 命令传播阶段
  主: 持续将写命令发送给从
  从: 接收并执行, 反馈 ACK
```

### 2. 核心概念

| 概念 | 说明 |
|------|------|
| **`replid`** | 主从复制 ID，标识一个复制流（与 master_run_id 不同） |
| **`offset`** | 复制偏移量，主从各自维护，主从 offset 差值 = 落后字节数 |
| **`repl_backlog`** | 主节点上的复制积压缓冲区，环形结构 |
| **`run_id`** | 服务器运行 ID（每次重启变化），用于识别节点身份 |

### 3. 详细时序图

```text
  ┌──────────────┐                                  ┌──────────────┐
  │   Master     │                                  │   Slave      │
  └──────────────┘                                  └──────────────┘
         │                                                  │
         │  ① 从节点发送 PING (TCP 连接建立后)               │
         │ <──────────────────────────────────────────────── │
         │                                                  │
         │  ② 主节点响应 PONG                                │
         │ ───────────────────────────────────────────────> │
         │                                                  │
         │  ③ 从节点发送 REPLCONF listening-port 6380        │
         │ <──────────────────────────────────────────────── │
         │  (告知主节点自己的端口)                              │
         │                                                  │
         │  ④ 主节点保存从节点信息                            │
         │                                                  │
         │  ⑤ 从节点发送 PSYNC <master_replid> <offset>     │
         │ <──────────────────────────────────────────────── │
         │                                                  │
         │  ⑥ 主节点判断复制方式                              │
         │     ├── 首次同步 → 返回 +FULLRESYNC <replid> <offset> │
         │     ├── 部分同步 → 返回 +CONTINUE                 │
         │     └── 异常 → 返回 -ERR                          │
         │                                                  │
         │  ⑦ 主节点 fork bgsave 生成 RDB                    │
         │     (BGSAVE 在后台, 主进程继续服务)                 │
         │                                                  │
         │  ⑧ 主节点将 RDB 发送给从节点                       │
         │ ───────────────────────────────────────────────> │
         │                                                  │
         │  ⑨ 从节点接收 RDB, 清空旧数据, 加载 RDB            │
         │     (期间从节点阻塞, 不响应客户端)                   │
         │                                                  │
         │  ⑩ 主节点将 bgsave 期间的新命令写入                  │
         │     replication buffer (复制缓冲区)                │
         │     并在 RDB 发送完成后发送给从节点                   │
         │ ───────────────────────────────────────────────> │
         │                                                  │
         │  ⑪ 从节点执行这些增量命令, 完成同步                 │
         │                                                  │
         │  ⑫ 进入命令传播阶段                                │
         │     主节点每秒发送 replication buffer + 心跳        │
         │ <────────────────────────────────────────────────>│
         │     (REPLCONF ACK <offset> 上报复制进度)           │
         │                                                  │
```

### 4. 复制的核心数据结构

**主节点侧**：

```c
// 每个从节点维护的信息
typedef struct slave {
    char host[256];              // 从节点 IP
    int port;                    // 从节点端口
    long long replstate;         // 复制状态机
    long long reploff;           // 主节点发送的 offset
    int slave_listening_port;    // 从节点监听端口
    int fd;                      // socket
    robj *replid;                // 主节点的 replid
    char replid[CONFIG_RUN_ID_SIZE+1];
    long long ack_offset;        // 从节点 ack 偏移
    // ... 缓冲区
} slave;
```

**复制积压缓冲区（repl_backlog）**：

```c
// 环形缓冲区, 默认大小 1mb
char *repl_backlog;
size_t repl_backlog_size;
long long repl_backlog_off;   // 起始偏移
long long repl_backlog_idx;   // 写指针
```

**从节点侧的关键状态**：

```text
master_replid         // 主节点 replid 的复制
master_repl_offset    // 主节点当前的 offset
slave_repl_offset     // 从节点已同步的 offset
```

## 四、复制流程详解

### 1. 连接建立阶段

```text
1. 从节点配置 replicaof <master_ip> <master_port>
2. 从节点根据配置的 IP/PORT 建立 TCP 连接
3. 从节点发送 PING 命令，等待 PONG 响应（验证连通性）
4. 鉴权（masterauth 密码校验）
5. 从节点发送 REPLCONF listening-port <port>（告知主节点自己的端口）
6. 主节点记录从节点信息
```

**关键细节**：

- 主节点为每个从节点创建 **独立的 socket**
- 主节点在 `replicationCron()` 定时任务中检查所有从节点状态
- 连接失败时，从节点会按 `repl-timeout` 周期重试

### 2. 数据同步阶段（核心）

同步阶段是 Redis 复制的核心，分为两种情况：

```text
从节点发送: PSYNC <master_replid> <slave_offset>
                            │              │
                            │              └── 从节点当前偏移
                            └── 期望主节点的 replid

主节点判断:
  ┌────────────────────────────────────────────────────────┐
  │ 情况 1: master_replid == "?" 或 从节点首次同步           │
  │   → 返回 +FULLRESYNC <replid> <offset>   (全量同步)      │
  │                                                        │
  │ 情况 2: replid 匹配 且 offset 在 backlog 范围内         │
  │   → 返回 +CONTINUE                      (部分同步)      │
  │                                                        │
  │ 情况 3: replid 匹配 但 offset 超出 backlog              │
  │   → 返回 +FULLRESYNC <replid> <offset>   (全量同步)      │
  └────────────────────────────────────────────────────────┘
```

### 3. 命令传播阶段

全量同步完成后，主从进入稳定的命令传播阶段：

```text
┌──────────────────────────────────────────────────────────┐
│  主节点:                                                 │
│   1. 执行客户端写命令                                     │
│   2. 写入 AOF 缓冲区                                       │
│   3. 立刻将命令发送给所有从节点                              │
│   4. 异步等待从节点 ACK                                    │
│                                                          │
│  从节点:                                                 │
│   1. 接收主节点命令                                        │
│   2. 写入本地 relay buffer (2.8 之前) 或直接执行 (2.8+)     │
│   3. 回复 ACK: REPLCONF ACK <offset>                       │
│                                                          │
│  主节点:                                                 │
│   1. 接收 ACK, 记录从节点的 ack_offset                     │
│   2. 用于 min-replicas-to-write/lag 安全策略               │
└──────────────────────────────────────────────────────────┘
```

**心跳机制**：

```text
主 ↔ 从: 每 1 秒一次通信
  - 从 → 主: REPLCONF ACK <offset>   (上报复制进度)
  - 主 → 从: 命令流 (如果有新写入)
  
心跳超时检测: repl-ping-replica-period (默认 10s)
  - 超过该时间未收到从节点响应 → 标记从节点为下线
```

### 4. 从节点身份切换

Redis 2.8 之后：

```text
旧版本 (Redis 2.8 之前):
  SYNC 命令: 只能全量同步, 断线重连代价巨大

新版本 (Redis 2.8+):
  PSYNC 命令: 支持部分同步, 利用 repl_backlog 实现增量同步
```

**PSYNC 触发场景**：

| 触发条件 | 结果 |
|----------|------|
| 首次建立复制 | FULLRESYNC |
| replid 不匹配 | FULLRESYNC |
| offset 超出 backlog | FULLRESYNC |
| replid 匹配 + offset 在 backlog | CONTINUE（部分同步） |

## 五、全量复制（Full Resynchronization）

### 1. 触发条件

```text
触发全量同步的 3 种情况:
  ① 从节点首次连接主节点（replid 未知）
  ② 主节点切换（如故障转移后），从节点 replid 不匹配
  ③ 从节点断开太久，offset 已超出 backlog 范围
```

### 2. 全量复制流程图

```text
┌──────────────────────────────────────────────────────────────┐
│                    全量复制流程                                │
└──────────────────────────────────────────────────────────────┘

    ┌─────────┐                              ┌─────────┐
    │ Master  │                              │  Slave  │
    └─────────┘                              └─────────┘
         │                                        │
         │ <──── ① Slave 发送 PSYNC ? -1 ────────│
         │                                        │
         │ ② 判断: 首次同步 → FULLRESYNC            │
         │ ──────── +FULLRESYNC <replid> 0 ─────>│
         │                                        │
         │ ③ 启动 bgsave (fork 子进程)             │
         │      │                                 │
         │      ├── 子进程生成 RDB ────────────────> ④ 接收 RDB
         │      │      │                          │
         │      │      └── 写入 temp-<port>.rdb    │ ⑤ 清空旧数据
         │      │                                 │    加载 RDB
         │      │                                 │    (阻塞客户端)
         │      │                                 │
         │ ⑥ 主节点将 bgsave 期间的新命令            │
         │    写入 replication buffer             │
         │    并发送给 Slave ────────────────────> ⑦ 接收增量
         │                                        │    执行命令
         │                                        │
         │ ⑧ 同步完成, 进入命令传播阶段              │
         │ <══════════════════════════════════════>│
```

### 3. RDB 文件传输的两种方式

#### 方式一：磁盘方式（默认）

```text
主节点 bgsave ──> 写入磁盘 temp-<port>.rdb
                          │
                          ▼
                从 socket 读取并发送 RDB 文件
                          │
                          ▼
                从节点接收 RDB, 加载到内存
```

**优点**：主节点内存压力小（子进程独立写入）。

**缺点**：磁盘 IO 双重开销（bgsave 写盘 + 读盘发送）。

#### 方式二：无盘复制（repl-diskless-sync）

```text
主节点 bgsave ──> 子进程直接将 RDB 写入 socket
                          │
                          ▼
                从节点接收 RDB, 加载到内存
```

**配置**：

```conf
repl-diskless-sync yes
repl-diskless-sync-delay 5      # 等待多个从节点请求, 一起发送
```

**优点**：避免磁盘 IO，适合大实例（内存 > 10GB）。

**缺点**：发送期间主节点阻塞（无法处理新写入）。

### 4. 复制积压缓冲区（repl_backlog）

```text
                    repl_backlog (环形缓冲区)
              ┌─────────────────────────────────┐
              │                                 │
              │  主节点写入的最近命令              │
              │  默认大小: 1mb                    │
              │  范围: offset (master_repl_offset - buffer_size) ~ master_repl_offset
              │                                 │
              └─────────────────────────────────┘
                                       │
   ┌───────────────────────────────────┼───────────────────────────────────┐
   │ 写入方向                          ▼                                   │
   │                                写指针                                │
   │                                                                   │
   │  当空间不足时, 覆盖最旧数据 (环形)                                      │
   └───────────────────────────────────────────────────────────────────┘
```

**关键参数**：

```conf
repl-backlog-size 1mb           # 缓冲区大小 (默认 1mb, 生产建议 100mb+)
repl-backlog-ttl 3600           # 从节点断开后, backlog 保留时间 (秒)
```

**缓冲区大小估算**：

```text
公式: repl_backlog_size >= 主节点每秒写入量 × 最长断线时间

示例:
  主节点每秒写入 10MB, 允许断线 12 小时
  repl_backlog_size = 10MB × 3600 × 12 = 432GB
  
  实际值: 太大, 一般取业务高峰 1-2 小时的数据量
  或根据 SLA 设定: 可容忍 5 分钟断线 → 至少 5 分钟数据量
```

### 5. 全量复制开销

| 资源 | 开销 | 优化方式 |
|------|------|----------|
| **主节点内存** | fork 时 COW，写密集时内存翻倍 | 无盘复制、错峰触发 |
| **主节点 CPU** | 生成 RDB + 压缩 | 大实例禁用自动 BGREWRITE |
| **主节点 IO** | 写 RDB + 发送 | 无盘复制、SSD |
| **主节点网络** | RDB 传输（10GB 内存约 2-5GB RDB） | 提升带宽 |
| **从节点 IO** | 加载 RDB 阻塞 | 错峰触发 |
| **从节点内存** | 加载 RDB 阻塞读写 | 设置 `repl-diskless-load` |

## 六、部分重同步（Partial Resynchronization）

### 1. 概念

部分重同步是 Redis 2.8 引入的优化，**只在主节点累积的 backlog 范围内**恢复中断的复制流。

```text
主节点                        从节点
  │                            │
  │ <══════ 正常同步中 ═══════> │
  │      offset = 1000         │
  │                            │
  │        断线 5 秒            │
  │        (主继续写命令)         │
  │   offset = 1200            │
  │                            │
  │ <──── 重连 ──────────────── │
  │                            │
  │ PSYNC <replid> 1000        │
  │     │                      │
  │     └─ 检查 backlog:        │
  │         1000 ~ 1200 都在    │
  │         → +CONTINUE         │
  │                            │
  │ 发送 1000-1200 的命令       │
  │ ─────────────────────────> │
  │                            │
```

### 2. 复制积压缓冲区（repl_backlog）详解

**结构**：

```text
repl_backlog 是一个 char 数组, 循环使用:

初始状态（全部空闲）:
┌────────────────────────────────────────────────────┐
│░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
└────────────────────────────────────────────────────┘
 ↑                                          ↑
 start                                     write_pos

写入后:
┌────────────────────────────────────────────────────┐
│██████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
└────────────────────────────────────────────────────┘
 ↑                ↑
 start            write_pos
 = master_repl_offset - 写过的字节数

继续写入, 环形回绕:
┌────────────────────────────────────────────────────┐
│██████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░████████│
└────────────────────────────────────────────────────┘
                  ↑                       ↑
                  start                   write_pos
```

**关键变量**：

```c
repl_backlog_size          // 总大小
repl_backlog_off           // 起始 offset (master 上的 offset)
repl_backlog_idx           // 写指针 (0 ~ repl_backlog_size-1)
master_repl_offset         // 主节点当前写入总 offset
```

### 3. 部分重同步流程

```text
Slave 重连时:
  1. 发送: PSYNC <保存的 master_replid> <保存的 slave_repl_offset>
  
  2. Master 收到后:
     - 如果 slave 发来的 replid != master_replid:
         → FULLRESYNC (全量同步)
     - 如果 replid 匹配:
         检查 backlog:
         if (slave_offset >= repl_backlog_off) and 
            (slave_offset <= master_repl_offset):
             → CONTINUE (部分同步)
         else:
             → FULLRESYNC (offset 超出 backlog)
  
  3. 部分同步时:
     - Master 从 backlog 中读取 slave_offset 到 master_repl_offset 之间的命令
     - 发送给 Slave
     - Slave 执行, 追上主节点
```

### 4. 部分同步 vs 全量同步对比

| 维度 | 全量同步 | 部分同步 |
|------|----------|----------|
| **触发条件** | 首次、replid 不匹配、offset 超出 backlog | replid 匹配 + offset 在 backlog |
| **数据量** | 主节点全量数据（RDB 级别） | 缺失的增量命令 |
| **耗时** | 与数据量成正比（10GB ≈ 数十秒~分钟） | 与断线时间成正比（毫秒~秒级） |
| **主节点开销** | fork + 传输 RDB | 读取 backlog 并发送 |
| **从节点开销** | 清空旧数据 + 加载 RDB（阻塞） | 接收并执行增量命令 |
| **网络带宽** | RDB 大小（数 GB） | 增量命令字节数（可能很小） |
| **对客户端影响** | 从节点阻塞（无法响应） | 几乎无影响 |

### 5. 部分同步的局限

```text
部分同步失效的 3 种情况:
  ① 主节点重启（replid 变化）→ 必须全量同步
  ② backlog 太小，offset 已超出 → 全量同步
  ③ 主节点 failover 后, replid 变化 → 全量同步

生产建议:
  - 给主节点设置合理的 backlog size（建议 100MB+）
  - 尽量避免主节点频繁重启
  - 部署 Sentinel 减少 failover 间隔
```

## 七、主从复制的异步问题

### 1. 异步复制原理

Redis 主从复制默认是 **异步** 的：

```text
Client ──SET k1 v1──> Master
                          │
                          ├── ① 执行命令
                          ├── ② 写入 AOF / 响应客户端
                          │
                          │    主节点已经返回 OK 给客户端
                          │
                          └── ③ 异步发送命令给 Slave
                                        │
                                        ▼
                                   Slave 接收并执行
```

**主从不一致窗口**：

```text
T0: Client SET k1 v1 → Master
T1: Master 返回 OK
T2: 客户端从 Slave 读取 k1 → 可能是空（旧值或未同步）
T3: Slave 同步完成, k1 = v1
```

### 2. 主从延迟

**延迟原因**：

| 原因 | 分析 |
|------|------|
| **网络延迟** | 跨机房、跨地域部署 |
| **从节点性能** | CPU/IO 弱于主节点 |
| **从节点负载** | 承担读负载挤压复制线程 |
| **持久化阻塞** | 从节点 BGSAVE / AOF rewrite |
| **大 Key** | 单个命令传输慢 |

**监控延迟**：

```bash
# 从节点执行
127.0.0.1:6380> INFO replication

# 关键字段:
# master_repl_offset:    主节点写入 offset
# slave_repl_offset:     从节点已同步 offset
# 延迟字节数 = master_repl_offset - slave_repl_offset
```

### 3. 数据丢失风险

```text
异步复制下数据丢失的场景:

T0: Client SET k1 v1 → Master
T1: Master 写入内存
T2: Master 异步发送命令给 Slave
T3: Master 宕机 (此时 Slave 还没收到 SET k1 v1)
T4: Sentinel 提升 Slave 为主
T5: 新的主节点丢失了 k1 = v1
```

**丢失窗口**：T1 到 T3 之间所有已写入但未同步到从节点的命令。

### 4. WAIT 命令（准同步复制）

Redis 3.0+ 提供 `WAIT` 命令，将异步复制转换为"准同步"：

```bash
WAIT <numreplicas> <timeout>

# 阻塞当前客户端, 等待至少 numreplicas 个从节点 ACK
# 超时后返回实际 ACK 的从节点数量
```

**示例**：

```bash
127.0.0.1:6379> SET k1 v1
OK
127.0.0.1:6379> WAIT 1 5000
(integer) 1    # 1 个从节点已确认
```

**注意**：

- `WAIT` 不保证数据一定持久化（从节点可能未持久化）
- `WAIT` 会阻塞客户端，影响性能
- Redis 5.0+ 有 `WAITAOF` 类似机制

### 5. min-replicas 安全策略

主节点可以拒绝写入，确保至少 N 个从节点正常同步：

```conf
# 至少 1 个从节点延迟不超过 10 秒
min-replicas-to-write 1
min-replicas-max-lag 10
```

**工作原理**：

```text
Redis 主节点定时检查从节点:
  for each second:
    count = 0
    for each slave:
      if (slave.lag <= min-replicas-max-lag):
        count++
    if (count < min-replicas-to-write):
      拒绝写入
      打印: N replicas lagging, blocking writes
```

**效果**：

| 场景 | 默认异步 | 开启 min-replicas |
|------|----------|-------------------|
| 主节点故障 | 可能丢失未同步数据 | 写入被拒绝（保护） |
| 主从延迟过大 | 正常写入 | 写入被拒绝（保护） |
| 客户端感知 | 立即成功 | 立即失败 |

## 八、复制风暴

### 1. 什么是复制风暴

复制风暴（Replication Storm）指同一时间大量从节点向主节点发起全量同步，导致主节点资源耗尽。

```text
                    主节点 Master
                   /  /  /  |  \  \
                  /  /  /   |   \  \
            全量同步请求 ×100
              (每个从节点都 bgsave)
                  ↓
        主节点 fork 100 次, 内存耗尽
```

### 2. 复制风暴的典型场景

**场景一：批量添加从节点**

```text
场景: 业务扩容，5 个新从节点同时启动
现象: 5 个从节点同时向主节点发起 PSYNC
后果: 主节点同时做 5 次 bgsave, 内存/IO 崩溃
```

**场景二：主节点故障恢复**

```text
场景: 主节点宕机重启, 所有从节点成为孤儿
现象: 主节点启动后, 所有从节点发现 replid 变化, 重新发起全量同步
后果: 主节点一次 fork 多次, 资源耗尽
```

**场景三：backlog 不足**

```text
场景: backlog 配置过小, 大量从节点断开超过 backlog 范围
现象: 从节点重连后必须全量同步
后果: 主节点压力暴增
```

### 3. 解决方案

#### 方案一：级联复制（推荐）

```text
                  ┌──────────────┐
                  │   Master     │
                  └──────────────┘
                          │
                          ▼
                  ┌──────────────┐
                  │  Slave-1     │  ← bgsave 发生在这里
                  │  (中间节点)   │
                  └──────────────┘
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
        Slave-2      Slave-3      Slave-4
      (从 Slave-1 同步)
```

**原理**：让少数中间节点挂载主节点，其他从节点挂载中间节点。

#### 方案二：从节点单机多副本

```text
单台机器上启动多个 Redis 实例:
  - 物理资源充足
  - 多个实例同时接收主节点 RDB 流量
  - 减少主节点 bgsave 次数
```

**注意**：Redis 6.0+ Cluster 的 replica 机制可避免此问题。

#### 方案三：错峰同步

```conf
# 让从节点不要同时 bgsave
# 调整 client-output-buffer-limit 参数
client-output-buffer-limit replica 256mb 64mb 60
```

#### 方案四：Redis 7.0+ Sharded Replication

```text
Redis 7.0+ Cluster 支持分片复制:
  - 主节点不再需要向所有从节点推送
  - 每个分片独立处理
  - 减少单点压力
```

### 3. 延迟监控脚本

```bash
#!/bin/bash
# /opt/redis/check_repl_lag.sh

MASTER_HOST="192.168.1.10"
MASTER_PORT="6379"
SLAVE_HOST="192.168.1.11"
SLAVE_PORT="6380"

# 获取主节点 offset
MASTER_OFFSET=$(redis-cli -h $MASTER_HOST -p $MASTER_PORT INFO replication | 
                grep master_repl_offset | cut -d: -f2 | tr -d '\r')

# 获取从节点 offset
SLAVE_OFFSET=$(redis-cli -h $SLAVE_HOST -p $SLAVE_PORT INFO replication | 
               grep slave_repl_offset | cut -d: -f2 | tr -d '\r')

# 计算延迟字节
LAG_BYTES=$((MASTER_OFFSET - SLAVE_OFFSET))

echo "Master offset: $MASTER_OFFSET"
echo "Slave offset:  $SLAVE_OFFSET"
echo "Lag bytes:     $LAG_BYTES"

if [ $LAG_BYTES -gt 1048576 ]; then
    echo "WARNING: replication lag > 1MB"
    exit 1
fi
```

### 4. 监控指标告警

| 指标 | 告警阈值 | 监控方式 |
|------|----------|----------|
| `master_link_status` | down | INFO replication |
| `lag` | > 10s | INFO replication |
| `lag` | > 60s | 严重告警 |
| `master_last_io_seconds_ago` | > 30s | 心跳超时 |
| `connected_slaves` | < 期望值 | 节点掉线 |
| `repl_backlog_size` | < 1MB | 配置调整 |

## 十、读写分离

### 1. 读写分离原理

```text
                  ┌─────────────────┐
                  │ Redis Cluster    │
                  │ 客户端 (代理)     │
                  └─────────────────┘
                          │
                ┌─────────┼─────────┐
                │         │         │
                ▼         ▼         ▼
              SET       GET       GET
                │         │         │
                ▼         │         │
         ┌──────────┐     │         │
         │  Master  │     │         │
         └──────────┘     │         │
                │         │         │
                └──┐   ┌───┘   ┌─────┘
                   ▼   ▼       ▼
              ┌────────┐ ┌────────┐
              │Slave-1 │ │Slave-2 │
              └────────┘ └────────┘
                 (读)        (读)
```

### 2. 客户端实现

#### Jedis（Java）

```java
public class RedisReadWriteSeparation {
    private static JedisPool masterPool;
    private static List<JedisPool> slavePools = new ArrayList<>();
    private static AtomicInteger slaveIndex = new AtomicInteger(0);
    
    static {
        // 主节点
        masterPool = new JedisPool(new JedisPoolConfig(), "192.168.1.10", 6379);
        
        // 从节点
        slavePools.add(new JedisPool(new JedisPoolConfig(), "192.168.1.11", 6380));
        slavePools.add(new JedisPool(new JedisPoolConfig(), "192.168.1.12", 6381));
    }
    
    public static void set(String key, String value) {
        try (Jedis jedis = masterPool.getResource()) {
            jedis.set(key, value);
        }
    }
    
    public static String get(String key) {
        // 轮询选择从节点
        JedisPool slavePool = slavePools.get(
            slaveIndex.getAndIncrement() % slavePools.size()
        );
        try (Jedis jedis = slavePool.getResource()) {
            return jedis.get(key);
        }
    }
}
```

**更优方案**：使用 Jedis 的 `JedisSentinelPool` 或 `JedisCluster`。

#### Lettuce（Java，Spring Boot 默认）

```java
@Configuration
public class RedisConfig {
    @Bean
    public LettuceClientConfigurationBuilderCustomizer customizer() {
        return builder -> builder.readFrom(ReadFrom.MASTER_PREFERRED);
    }
}
```

**ReadFrom 策略**：

| 策略 | 含义 |
|------|------|
| `MASTER` | 只读主节点 |
| `MASTER_PREFERRED` | 主节点优先，从节点兜底 |
| `REPLICA_PREFERRED` | 从节点优先，主节点兜底 |
| `REPLICA` | 只读从节点 |
| `NEAREST` | 选择延迟最低的节点 |
| `ANY` | 任意可用节点 |

#### Go (go-redis)

```go
package main

import (
    "github.com/go-redis/redis/v8"
    "context"
)

func main() {
    rdb := redis.NewClusterClient(&redis.ClusterOptions{
        Addrs: []string{
            "192.168.1.10:6379",
            "192.168.1.11:6380",
            "192.168.1.12:6381",
        },

    rdb.Set(context.Background(), "k1", "v1", 0)

}
```

### 3. 延迟读取应对

**场景**：客户端写入后立刻从从节点读取，可能读到旧值。

**解决方案**：

#### 方案一：业务容忍

```text
适用于: 缓存场景, 数据过期几秒可接受
方法: 简单读写分离即可
```

#### 方案二：读主

```text
适用于: 强一致场景
方法: 重要读取永远走主节点
```

#### 方案三：客户端重试

```java
public String get(String key) {
    // 先读从节点
    String value = readFromSlave(key);
    if (value == null) {
        // 从节点未同步, 读主节点
        value = readFromMaster(key);
    }
    return value;
}
```

#### 方案四：读自己写入

```text
适用于: 单用户场景
方法: 标记写入操作, 后续读取走主节点
```

### 4. 读写分离的坑

| 坑 | 后果 | 避免 |
|----|------|------|
| **从节点误写** | 主从数据不一致 | `replica-read-only yes` |
| **过期失效** | 从节点不主动过期 | Redis 3.2+ 解决 |
| **延迟读取** | 读到旧值 | 业务容忍或读主 |
| **从节点故障** | 读请求失败 | 客户端自动切换 |
| **主从不一致** | 业务逻辑错误 | 关键操作不依赖复制 |

## 十一、故障转移（与 Sentinel 配合）

### 1. 主从复制的局限

```text
主从复制本身只解决数据冗余和读写分离, 不解决:
  - 主节点故障自动切换
  - 主节点对外的高可用

当主节点宕机:
  1. 从节点不会自动升级为主
  2. 客户端需要手动切换连接
  3. 其他从节点需要手动重新指向新主
  
解决: 配合 Redis Sentinel (第 11 章详细讲述)
```

### 2. Sentinel 简介

```text
Redis Sentinel 是 Redis 官方高可用方案:
  - 监控 (Monitoring): 持续检查主从节点健康
  - 通知 (Notification): 节点异常时通知管理员
  - 自动故障转移 (Automatic failover): 主节点故障时, 自动提升从节点
  - 配置提供者 (Configuration provider): 客户端通过 Sentinel 查询主节点地址
```

**架构**：

```text
             ┌───────────────────────────────┐
             │      Sentinel 集群 (3 节点)     │
             │   监控 + 决策 + 故障转移         │
             └───────────────────────────────┘
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
       Master        Slave-1       Slave-2
```

### 3. 故障转移流程

```text
1. Sentinel 监控发现 Master 失联 (主观下线, SDown)
                │
                ▼
2. Sentinel 集群协商, 多数同意 Master 确实下线 (客观下线, ODown)
                │
                ▼
3. 选举 Leader Sentinel 处理故障转移
                │
                ▼
4. 选出新的 Master (从 slaves 中按优先级选)
                │
                ▼
5. 提升 Slave 为 Master (SLAVEOF NO ONE)
                │
                ▼
6. 通知其他从节点指向新主 (REPLICAOF <new-master>)
                │
                ▼
7. 通知客户端配置更新
```

**详细原理见第 11 章 Sentinel 章节**。

## 十二、复制注意事项

### 1. 生产环境配置建议

```conf
# ========= Master 配置 =========
# 主节点避免持久化让从节点来承担
# save ""
# appendonly no

# ========= Slave 配置 =========
# 从节点必须开启持久化
save 900 1
save 300 10
save 60 10000
appendonly yes
appendfsync everysec

# 启用无盘复制（如果网络优于磁盘）
repl-diskless-sync yes
repl-diskless-sync-delay 5

# 合理 backlog
repl-backlog-size 256mb
repl-backlog-ttl 3600

# 复制超时
repl-timeout 60
repl-ping-replica-period 10

# 主从延迟过大时拒绝写入
min-replicas-to-write 1
min-replicas-max-lag 10

# 从节点只读
replica-read-only yes
```

### 2. 风险与避免

#### (1) 避免在主节点上做耗时长操作

```bash
# ❌ 危险: 主节点阻塞
redis-cli -h master KEYS "*"           # 阻塞主节点
redis-cli -h master FLUSHDB           # 阻塞并清空
redis-cli -h master DEBUG SLEEP 60    # 阻塞 60 秒

# ✅ 正确: 在从节点上做
redis-cli -h slave KEYS "*"
```

**避免命令**：

| 命令 | 风险 | 替代 |
|------|------|------|
| `KEYS *` | 全库扫描, O(N) | `SCAN` |
| `FLUSHALL` | 清空所有数据 | - |
| `FLUSHDB` | 清空单库 | - |
| `DEBUG SLEEP` | 阻塞 | - |
| `DEBUG SEGFAULT` | 崩溃 | - |

#### (2) 主从不一致

**原因**：

```text
- 异步复制延迟
- 从节点被错误写入
- 复制过程中断
- 主从数据初始不一致
```

**检查不一致**：

```bash
# 使用 redis-cli 比较主从
redis-cli -h master -p 6379 DEBUG OBJECT <key>
redis-cli -h slave -p 6380 DEBUG OBJECT <key>
```

#### (3) 避免大 Key

```bash
# ❌ 大 Key 复制慢
SET huge_key "一个 10MB 的值"

# ✅ 拆分
SET huge_key:part1 "..."
SET huge_key:part2 "..."
```

#### (4) 启用复制限速

```conf
# 限制从节点流量（防止从节点过慢影响主节点）
client-output-buffer-limit replica 256mb 64mb 60
```

**含义**：
- 硬限制 256MB：超过则断开从节点
- 软限制 64MB × 60 秒：超过则断开从节点

### 3. 主从切换注意事项

```text
主从切换时:
  1. 确认 master_replid 变化（从节点可能需要全量同步）
  2. 业务确认能容忍短时间中断
  3. 避免脑裂（多个写入点）
  4. 切换后验证所有从节点 replid 一致
```

## 十三、Redis 7.0+ 复制改进

### 1. Sharded Replication

传统复制：
```text
Master ── 推给所有 Slave (一对多)
   │
   └──> Slave-1
   └──> Slave-2
   └──> Slave-3
```

分片复制（Redis 7.0+）：
```text
Cluster Master A ──> Slave A-1 (同节点)
Cluster Master B ──> Slave B-1 (同节点)
Cluster Master C ──> Slave C-1 (同节点)
```

**优点**：每个分片独立复制，避免全局复制风暴。

### 2. 复制优化

| 改进 | 说明 |
|------|------|
| **无盘复制** | 减少磁盘 IO |
| **PSYNC2** | 支持更智能的部分重同步 |
| **多线程 IO** | 实验阶段，提升大实例复制性能 |
| **复制心跳优化** | 减少不必要的网络流量 |

### 3. repl 改进

```text
Redis 7.0+:
  - replicaof 完整替代 slaveof
  - 更清晰的复制状态输出
  - 改进的复制错误日志
```

## 核心要点速记

1. **主从复制解决三个问题**：数据冗余、读写分离、故障恢复基础。

2. **Redis 5.0+ 推荐 REPLICAOF**：与 SLAVEOF 等价，但语义更中性。

3. **复制三阶段**：连接建立 → 数据同步（PSYNC） → 命令传播。

4. **PSYNC 触发场景**：
   - 首次同步 → FULLRESYNC
   - replid 不匹配 → FULLRESYNC
   - offset 超出 backlog → FULLRESYNC
   - replid 匹配 + offset 在 backlog → CONTINUE（部分同步）

5. **全量复制 = RDB + 增量命令**。主节点 BGSAVE 生成 RDB 发送给从节点，期间的写命令通过 replication buffer 同步。

6. **部分同步 = 复制积压缓冲区（repl_backlog）**。backlog 是主节点上的环形缓冲区，保存最近的写入命令。

7. **repl_backlog_size 建议**：至少能覆盖业务高峰 1-2 小时的数据量（生产建议 100MB+）。

8. **无盘复制（repl-diskless-sync）**：适合大实例（内存 > 10GB），避免磁盘 IO 双重开销。

9. **min-replicas 安全策略**：避免主节点宕机时丢失未同步数据，`min-replicas-to-write 1` + `min-replicas-max-lag 10` 是常见配置。

10. **主从延迟监控**：`INFO replication` 中 `master_repl_offset - slave_repl_offset` 是延迟字节数。

11. **复制风暴解决方案**：级联复制（`replicaof <中间节点>`）、分片复制（Redis 7.0+ Cluster）。

12. **复制延迟的本质**：异步复制，主节点写入后不等从节点 ACK 就返回。

13. **WAIT 命令**（3.0+）：阻塞等待指定数量的从节点确认，提供"准同步"能力。

14. **从节点只读**：生产必须设置 `replica-read-only yes`，防止误写。

15. **避免主节点上执行**：KEYS、FLUSHDB、FLUSHALL、DEBUG SLEEP 等长操作。

16. **大 Key 影响复制**：单个 key 过大导致复制延迟，传输慢。

17. **client-output-buffer-limit**：限制从节点缓冲，防止慢从节点拖垮主节点。

18. **主从切换**：单纯主从复制不会自动切换，需配合 Sentinel（第 11 章）或 Cluster（第 12 章）。

19. **生产最佳实践**：
    - 主节点：可能关闭持久化（`save ""`），避免 fork
    - 从节点：开启持久化，承担数据备份
    - 主从版本一致
    - 合理配置 `repl-backlog-size`

20. **Redis 7.0+ Sharded Replication**：每个分片独立复制，避免全局复制风暴。

21. **主从复制不等于高可用**：复制只解决数据冗余和读写分离，高可用需要 Sentinel 或 Cluster。

22. **replid 机制**：Redis 2.8+ 引入，配合 PSYNC 实现增量同步，避免每次断线全量同步。

23. **背背背背背背背背背背背**（不写了，给自己一个提醒）：**生产禁用 `KEYS *`，使用 `SCAN`；生产禁用 `FLUSHALL/FLUSHDB`**。
