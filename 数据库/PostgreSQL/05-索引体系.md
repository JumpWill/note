# PostgreSQL 索引体系

## 一、PostgreSQL 索引概述

### 1. 什么是索引

**索引 (Index)** 是数据库中一种**专门的数据结构**,用于**加速数据的查找与检索**。PostgreSQL 的索引在**物理上独立于表数据存储**(堆表 + 索引分离),通过索引项中的 **TID (Tuple Identifier,行物理地址)** 定位数据行。

PostgreSQL 是**业界索引类型最丰富的关系型数据库**之一。MySQL 主要靠 B+Tree(InnoDB 默认),而 PostgreSQL 内置了 **6 种核心索引方法 + 多种扩展索引**,能覆盖几乎所有业务场景:

```text
                    不带索引                          带索引
            ┌──────────────────┐             ┌──────────────────────┐
            │ 全表扫描 (Seq Scan)│             │ 索引定位 + 堆表回查   │
            │ 时间: O(n)       │             │ 时间: O(log n) + IO  │
            │ 顺序 IO          │             │ 随机 IO + 顺序 IO    │
            └──────────────────┘             └──────────────────────┘
```

### 2. PostgreSQL 索引的本质

- 索引是**一个独立的物理结构**(默认在 `base/<oid>/` 目录下)
- 索引项存储 **索引键 + TID(6 字节的块号 + 偏移量)**
- 维护索引带来**写入开销**(INSERT/UPDATE/DELETE 要同步更新索引)
- 索引是**用空间换时间**的典型方案
- PostgreSQL 的所有二级索引都是**非聚簇索引**(数据按堆存储,索引只存 TID)

```sql
-- 索引项的内部结构(简化)
┌─────────────┬──────────────────┐
│ 索引键 (Key) │ TID (6 字节)     │   ← 一个索引项
│  e.g. 100   │ (block=42, off=3)│
└─────────────┴──────────────────┘
         │              │
         │              └─→ 直接定位到 heap 表的具体行
         └─→ 来自索引列的值
```

### 3. 索引的两大核心作用

#### (1) 减少磁盘 IO

数据库的数据存储在磁盘上,**IO 次数直接决定查询性能**。一个 1 亿行的表,如果全表扫描(Seq Scan),即使每页 8KB,也要扫描上万页。

而 B-Tree 索引(2~4 层)即使表上亿行,也只需要 **2~4 次磁盘 IO** 就能定位到 TID——这就是 PostgreSQL 千万级表毫秒级查询的本质。

#### (2) 避免排序 (加速 ORDER BY / GROUP BY / DISTINCT)

- 索引本身就是**有序**的(B-Tree 按 key 升序存储)
- 如果 ORDER BY / GROUP BY / DISTINCT 的字段正好命中索引,优化器可以**直接按索引顺序读出**,无需额外排序
- 反之,若不命中索引,PostgreSQL 需要把结果集加载到内存,**内存里排序**,代价随数据量线性增长

```sql
-- 假设 idx_created_at 是 B-Tree 索引
EXPLAIN SELECT * FROM orders ORDER BY created_at;     -- Sort 节点
CREATE INDEX idx_created_at ON orders(created_at);
EXPLAIN SELECT * FROM orders ORDER BY created_at;     -- Index Scan,无 Sort
```

### 4. 索引的代价

| 操作 | 影响 |
|------|------|
| INSERT | 需插入索引项(可能页分裂) |
| UPDATE | 若修改索引列,需更新索引(旧 TID 删除 + 新 TID 插入,即 HOT 不适用) |
| DELETE | 索引项标记删除,VACUUM 后清理 |
| SELECT | 维护成本低,只读不写 |
| 磁盘空间 | 索引本身要占空间(GIN/BRIN 通常比 B-Tree 大) |
| 优化器选择 | 索引多了反而让规划器难选 |
| VACUUM | 每个索引都要被 VACUUM 清理,索引越多 VACUUM 越慢 |

> **关键原则**:索引不是越多越好,而是**该有的有,没用的别建**。

### 5. PostgreSQL 索引 vs MySQL 索引

| 维度 | PostgreSQL | MySQL (InnoDB) |
|------|-----------|----------------|
| 存储引擎 | 不可插拔,统一 Heap | 可插拔(InnoDB/MyISAM/Memory) |
| 聚簇索引 | **无聚簇索引**(堆表) | 有聚簇索引(主键) |
| 二级索引叶子 | 存 **TID**(块号+偏移) | 存 **主键值** |
| 回表 | 直接 TID 定位 | 二级索引先拿主键,再回聚簇索引 |
| 索引方法数 | **6+ 种**(B-Tree/Hash/GiST/SP-GiST/GIN/BRIN) | 1~2 种(B+Tree/Hash) |
| 表达式索引 | **原生支持** | 仅 8.0+ 函数索引 |
| 部分索引 | **原生支持** | 不支持 |
| 覆盖索引 | INCLUDE 子句 (11+) | 复合索引天然覆盖 |
| 并发创建 | `CONCURRENTLY` 原生 | Online DDL(5.6+) |

> **PostgreSQL 的核心优势**:索引方法丰富、索引功能强(部分索引、表达式索引、INCLUDE),能精准解决各种业务场景。

## 二、PostgreSQL 索引类型总览

PostgreSQL 提供了 **6 种内置索引方法**,外加多种扩展(btree_gin、btree_gist、bloom、rum、 zombodb 等)。不同索引方法使用不同的**底层算法**,适用于**不同数据类型和查询场景**。

### 1. 索引方法一览

```text
                         PostgreSQL 索引方法
                                 │
        ┌────────┬────────┬─────┴─────┬──────────┬──────────┐
        │        │        │           │          │          │
   ┌────▼───┐┌───▼───┐┌──▼────┐┌────▼────┐┌────▼────┐┌────▼────┐
   │ B-Tree ││ Hash  ││ GiST  ││ SP-GiST ││  GIN    ││  BRIN   │
   └───┬────┘└───┬───┘└───┬───┘└────┬────┘└────┬────┘└────┬────┘
       │        │        │         │          │          │
     默认      等值     地理/全文  空间分割   JSONB/数组   超大表
     通用     查询(10+) tsvector  树形结构  反向索引     块范围
```

### 2. 各索引方法简介

| 索引方法 | 引入版本 | 核心算法 | 主要应用 | 操作符类 |
|---------|---------|---------|---------|---------|
| **B-Tree** | 始终 | 平衡多路 B-Tree | 等值/范围/排序/前缀 LIKE | `int4_ops`、`text_ops` 等 |
| **Hash** | 一直存在;PG 10+ WAL/复制 | 哈希表 | 仅等值查询 | `int4_ops` 等 |
| **GiST** | 始终 | 通用搜索树(平衡) | 几何、全文、范围 | `gist_geom_ops`、`tsvector_ops` |
| **SP-GiST** | 始终 | 空间分割树 | 不平衡数据结构(IP、电话前缀) | `spgist_text_ops` |
| **GIN** | 始终 | 通用反向索引 | JSONB、数组、全文、trigram | `jsonb_ops`、`array_ops` |
| **BRIN** | PG 9.5+ | 块范围索引 | 时序、IoT、日志(超大表) | `brin_minmax_ops`、`brin_bloom_opaque` |
| **Bloom** | 扩展(contrib) | 布隆过滤器 | 多列等值、过滤场景 | bloom extension |

```text
  /    |    \                  │ 1 │→key=50→TID      "事务"→{doc2}

  /|   /|   /|                 │...│
 5 10 70 90 100               │127│
                                └───┘

GiST (平衡搜索树)             SP-GiST (空间分割)         BRIN (块范围摘要)
   [geo1]                     quad-tree                 Range 0~127: [0, 100]
   /  |  \                    /  |  \   \               Range 128~255: [150, 200]
 [...] [...] [...]            /\  /\   /\
                              /\
```

## 三、索引类型对比表

### 1. 总对比表

| 索引 | 算法 | 适合查询 | 适合数据 | 体积 | 写入开销 | 典型场景 |
|------|------|---------|---------|------|---------|---------|
| **B-Tree** | 平衡树 | `=`、`>`、`<`、`BETWEEN`、`ORDER BY`、`LIKE 'abc%'` | 标量(数字、字符串、日期) | 中 | 中 | **默认通用** |
| **Hash** | 哈希表 | `=` (仅等值) | 标量 | 小 | 中 | 大表等值缓存 |
| **GiST** | 平衡多路树 | 包含、相交、最近邻、距离 | 几何、范围、tsvector、IP | 大 | 高 | PostGIS、全文、范围 |
| **SP-GiST** | 空间分割树 | 包含、相等 | 非平衡数据(IP 前缀、电话) | 中 | 中 | IP4、电话号码 |
| **GIN** | 反向索引 | 包含、相交、JSONB 操作符 | JSONB、数组、tsvector、trigram | **大** | **高** | 文档搜索、标签 |
| **BRIN** | 块范围摘要 | 范围查询、MIN/MAX | **天然按物理顺序**的大表 | **极小** | **极低** | 时序、IoT、日志 |
| **Bloom** | 布隆过滤器 | 多列等值过滤 | 等值列很多 | 中 | 中 | 多列等值粗筛 |

### 2. 各索引支持的操作符

| 索引 | 支持的操作符 | 不支持 |
|------|------------|--------|
| B-Tree | `=` `<>` `<=` `>=` `<` `>` `BETWEEN` `IN` `IS NULL` `LIKE 'abc%'` | 任意 LIKE |
| Hash | `=` | 范围、排序、模糊 |
| GiST | 几何: `<<` `&<` `&>` `>>` `~=` `@>` `<@` `&&`<br>全文: `@@`<br>范围: `@>` `<@` `&&` | 任意表达式 |
| SP-GiST | `<<` `>>` `~=` `<@` `@>` `=` | 范围扫描 |
| GIN | JSONB: `@>` `?` `?&` `?\|`<br>数组: `@>` `&&`<br>全文: `@@` | 范围 `<>` `<` `>` |
| BRIN | `=` `<>` `<` `<=` `>` `>=` `BETWEEN` | 模糊匹配、函数 |

### 3. 各索引的空间与性能特征

| 索引 | 索引体积(相对) | 查询速度(等值) | 查询速度(范围) | 写入速度 | UPDATE 友好度 |
|------|--------------|--------------|--------------|---------|-------------|
| B-Tree | 1x(基准) | 快 | 快 | 中 | 一般 |
| Hash | 0.8x | **极快** | N/A | 中 | 一般 |
| GiST | 1.5~3x | 中 | 中 | 慢 | 差 |
| SP-GiST | 0.8~1.2x | 快 | 中 | 中 | 好 |
| GIN | **3~10x** | 中 | 慢 | **慢** | **差** |
| BRIN | **0.001~0.01x** | 中 | **快** | **极快** | 好 |
| Bloom | 0.5~1x | 中 | N/A | 中 | 一般 |

> **核心结论**:数据量小用 B-Tree;超大表用 BRIN;JSONB/数组用 GIN;地理用 GiST;等值专用考虑 Hash。

## 四、B-Tree 索引详解

### 1. B-Tree 算法核心

B-Tree(Balanced Tree,平衡树)是 PostgreSQL **默认的索引方法**(`USING btree` 可省略),适用于绝大多数场景。

#### (1) B-Tree 特征

1. **多路平衡查找树**,每个节点有 m 个 key、m+1 个子节点
2. **非叶子节点只存索引键 (key) + 指针**
3. **叶子节点存 key + TID**(指向堆表的具体行)
4. **叶子节点之间是双向链表**,便于范围扫描
5. 树高度极低:**2~4 层即可支持亿级数据**

#### (2) PostgreSQL B-Tree 与 MySQL B+Tree 区别

| 维度 | PostgreSQL B-Tree | MySQL InnoDB B+Tree |
|------|-------------------|---------------------|
| 数据存储 | **叶子节点存 TID**,数据在堆表 | 叶子节点存**整行**(聚簇)或主键(二级) |
| 表结构 | 堆表(Heap),数据与索引分离 | 索引组织表(IOT),数据=主键索引 |
| 回表 | TID 直接定位物理地址 | 二级索引需再查主键索引 |
| 叶子节点 | key + TID,链表相连 | key + 数据(聚簇)或 key + 主键(二级) |
| 页大小 | **8 KB**(默认) | 16 KB(默认) |
| 非叶子节点 key+指针 | ~ 约 8B+6B=14B | ~ 约 8B+6B=14B |
| 高度(1 亿行) | 约 3~4 | 约 4~5 |

```text
PostgreSQL B-Tree 结构                  MySQL InnoDB B+Tree (聚簇索引)
      [ 50 | 100 ]                              [ 50 | 100 ]
     /    |     \                              /     |      \
    /     |      \                            /      |       \
[10|30]  [70|90]                          [10|30] [70|90]
  /|\      /|\                              /|\      /|\
 5* 10* 30* 70* 90* 100*                整行 整行 整行 整行 整行 整行
 |  |   |   |   |   |                    (数据存在叶子)
 ↓  ↓   ↓   ↓   ↓   ↓
TID → 堆表
(数据独立存储在 heap 文件)
```

#### (3) PostgreSQL B-Tree 结构图

```text
                            PostgreSQL B-Tree (高度 = 3)
                       每个节点可存 ~300 个 key(8KB 页)

                                     [ 50 | 100 ]                    ← 根 (非叶子)
                                    /     |      \
                                  /       |       \
                                 /        |        \
                                /         |         \
                  [ 10 | 30 ]            [ 70 | 90 ]                 ← 非叶子
                  /   |    \            /    |    \
                 /    |     \          /     |     \
                /     |      \        /      |      \
         (叶子节点,有序,双向链表)

    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ 5  10 20 │⇄  │ 25 30 40 │⇄  │ 50 60 70 │⇄  │ 80 90 100│  ← 叶子
    │T1 T2 T3 │    │ T4 T5 T6 │    │ T7 T8 T9 │    │ T10 T11 │    (存 key + TID)
    └──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                        ↓ TID
                                              ┌──────────────────┐
                                              │ 堆表 (Heap)      │
                                              │ 完整行数据       │
                                              └──────────────────┘

    ★ 叶子节点存 key + TID(块号 + 偏移)
    ★ 叶子之间双向链表,范围扫描顺着链表读
    ★ 拿到 TID 后回堆表读完整行(回表 = heap fetch)
```

### 2. B-Tree 适合的查询

| 查询类型 | 示例 | 是否走索引 |
|---------|------|----------|
| **等值** | `WHERE id = 100` | ✅ |
| **范围** | `WHERE age BETWEEN 20 AND 30` | ✅ |
| **不等式** | `WHERE age > 20`、`!=` | ✅ |
| **IN 列表** | `WHERE id IN (1,2,3)` | ✅ |
| **ORDER BY** | `ORDER BY created_at` | ✅ |
| **GROUP BY** | `GROUP BY user_id` | ✅ |
| **前缀 LIKE** | `WHERE name LIKE '张%'` | ✅ |
| **后缀/中缀 LIKE** | `WHERE name LIKE '%张%'` | ❌ |
| **函数** | `WHERE date(create_dt) = '2025-01-01'` | ❌(表达式索引除外) |
| **NOT IN** | `WHERE id NOT IN (1,2,3)` | 通常 ❌ |

### 3. B-Tree 不适合的查询

```sql
-- ✗ 索引列上用函数 → 索引失效
SELECT * FROM user WHERE date(created_at) = '2025-01-01';

-- ✗ 索引列上做计算
SELECT * FROM user WHERE age + 1 = 30;

-- ✗ 前导模糊
SELECT * FROM user WHERE name LIKE '%张%';

-- ✗ 类型不匹配
SELECT * FROM user WHERE phone = 13800138000;  -- phone 是 VARCHAR

-- ✗ OR 滥用(优化器不一定能合并索引)
SELECT * FROM user WHERE name = '张三' OR age = 20;
```

### 4. B-Tree 完整示例

```sql
-- 1) 单列索引
CREATE INDEX idx_user_name ON user(name);

-- 2) 复合索引(多列)
CREATE INDEX idx_user_age_name ON user(age, name);

-- 3) 唯一索引
CREATE UNIQUE INDEX uk_user_email ON user(email);

-- 4) 表达式索引(见第十节)
CREATE INDEX idx_user_lower_email ON user(lower(email));

-- 5) 部分索引(见第九节)
CREATE INDEX idx_active_user ON user(last_login) WHERE status = 'active';

-- 6) INCLUDE 索引(见第十二节,PG 11+)
CREATE INDEX idx_user_id_email ON user(id) INCLUDE (email);
```

### 5. 一次查询的 IO 流程

```text
查询:SELECT * FROM user WHERE id = 89

Step 1 (根节点):   读磁盘 → [ 50 | 100 ] → 89 > 50 且 89 < 100 → 走中间指针
Step 2 (中间节点): 读磁盘 → [ 70 | 90 ]  → 89 < 90 → 走最右指针
Step 3 (叶子节点): 读磁盘 → [ 80 | 89 | 100 ] → 命中 89 → 拿到 TID = (42, 3)
Step 4 (回表):     读堆表 → block 42 第 3 行 → 返回完整行

总计: 4 次磁盘 IO  (B-Tree 高度 3 + 一次堆表 IO)
```

### 6. B-Tree 的实际参数

PostgreSQL 中 B-Tree 的参数与磁盘页大小直接相关:

- **页大小**:`SHOW block_size;` 默认 **8 KB**(比 MySQL 的 16KB 小)
- **非叶子节点 key + 指针约 14B**(int4 key=4B + TID=6B + 头 = 14B)
- **每个非叶子节点可存** ≈ 8KB / 14B ≈ **585 个 key**
- **叶子节点除 key 外,还存 TID 和行指针**
- **假设 TID+key 约 18B,叶子可存 8KB / 18B ≈ 455 个 key**
- **总行数 ≈ 585 × 585 × 455 ≈ 1.56 亿**(3 层)

```text
树高 vs 数据量(PostgreSQL B-Tree, 默认 8KB 页, int4 主键)

       树高 2  ≈           约 27 万行
       树高 3  ≈        约 1.5 亿行
       树高 4  ≈      约 880 亿行(理论上限)
       实际生产树高通常 = 3
```

> **核心推论**:只要 B-Tree 高度 ≤ 4,即使表数据 800 亿,一次查询也只需 3~4 次 IO。这就是 PostgreSQL 单表能撑亿级数据的根本原因。

## 五、Hash 索引

### 1. Hash 索引原理

- 用**哈希函数**把 key 映射到桶(bucket),等值查询**理论 O(1)**
- 哈希表是**无序**的,不支持范围查询、不支持排序、不支持部分索引
- 哈希冲突用**溢出页**处理

```text
Hash 索引原理示意

    key:         哈希函数        bucket:
    "Alice"  ──────────────→    3  → TID(42, 1)
    "Bob"    ──────────────→    5  → TID(42, 5)
    "Peter"  ──────────────→    7  → TID(80, 3)
    "张三"   ──────────────→    1  → TID(100, 2)

★ O(1) 定位
× 不支持: 范围、排序、前缀
```

### 2. PostgreSQL Hash 索引的版本演进

| 版本 | 状态 | 关键改进 |
|------|------|---------|
| PG 9.x 及之前 | **不推荐** | 不写 WAL(崩溃后损坏)、不支持流复制 |
| **PG 10+** | **可用** | **WAL 日志支持、流复制支持、崩溃安全** |
| PG 11+ | 推荐 | 性能改进(溢出页、并发) |
| PG 12+ | 默认推荐 | 进一步优化 |

> **重要**:PostgreSQL 10 之前,Hash 索引**不会写 WAL**,崩溃后必须 REINDEX;**不被复制到备库**。**PG 10+ 已完全修复这两个问题**,但 B-Tree 仍是默认。

### 3. Hash 索引使用

```sql
-- 1) 创建 Hash 索引
CREATE INDEX idx_user_email_hash ON user USING hash (email);

-- 2) 等值查询可以走 Hash 索引
EXPLAIN SELECT * FROM user WHERE email = '[email protected]';
-- Bitmap Index Scan on idx_user_email_hash

-- 3) 范围查询不适用 Hash
EXPLAIN SELECT * FROM user WHERE email > '[email protected]';
-- Seq Scan (不会用 Hash 索引)
```

### 4. Hash vs B-Tree

| 维度 | B-Tree | Hash |
|------|--------|------|
| 等值查询 | 快 O(log n) | **极快 O(1)** |
| 范围查询 | **快 O(log n)** | 不支持 |
| 排序 | **支持** | 不支持 |
| 索引大小 | 1x | 0.8x(略小) |
| 写入开销 | 中 | 中 |
| 实际差异 | **PG 13 测试:Hash 仅快 5~10%** | 多数场景 B-Tree 已够用 |

### 5. 适用场景

```text
Hash 索引适用场景(很有限):
1. 大表(亿级)+ 极频繁等值查询
2. 完全不需要范围查询
3. B-Tree 索引太大的场景(Hash 略小)

Hash 索引不适用:
1. 99% 的普通业务(B-Tree 足够)
2. 需要范围/排序
3. 模糊匹配
```

> **实战建议**:**99% 的场景用 B-Tree**。Hash 索引只在等值查询极端密集且数据量极大时考虑。

## 六、GiST 索引

### 1. GiST 原理

**GiST (Generalized Search Tree,通用搜索树)** 是一种**平衡多路搜索树**,但与 B-Tree 不同,GiST 不关心索引列的"小于/大于"语义,而是**通用化**支持各种自定义数据类型和操作符。

GiST 的核心思想:**"我可以为任何数据类型建立搜索树"**,只要该类型定义了:

- 一致性函数:两个 key 是否可比较
- 联合函数:两个 key 合并后的"上界"
- 惩罚函数:拆分节点的代价
- 拾取函数:选择哪个 key 作为拆分点

```text
GiST 树结构 (以几何类型为例,每个节点是几何图形的"包围盒"):

                    [ 国境框 ]                          ← 根
                   /     |     \
                  /      |      \
            [省框1]  [省框2]  [省框3]                   ← 内部节点
            /  \      /  \      /  \
          /    \    /    \    /    \
        [点/线/多边形...]                              ← 叶子(实际对象 + TID)

★ 每个节点存"可搜索的 key"(几何的 bounding box)
★ 查找时:问"该 bbox 是否包含目标" → 决定走左/右子树
```

### 2. GiST 应用场景

| 数据类型 | 操作符 | 应用 |
|---------|-------|------|
| **几何类型**(point、box、polygon、circle、path) | `<<` `&<` `&>` `>>` `~=` `@>` `<@` `&&` | PostGIS、地图 |
| **范围类型**(int4range、daterange、tsrange) | `@>` `<@` `&&` `=` | 时间区间、IP 段 |
| **全文类型**(tsvector) | `@@` | 全文搜索 |
| **IP 地址**(inet、cidr) | `>>` `<<` `&&` | IP 段查找 |
| **hstore** | `@>` `?` | KV 存储 |
| **ltree** | `~` `@>` `<@` | 树形结构(分类、路径) |

### 3. GiST 索引创建

```sql
-- 1) 几何类型
CREATE TABLE places (
    id     SERIAL PRIMARY KEY,
    name   VARCHAR(64),
    geom   POINT
);
CREATE INDEX idx_places_geom ON places USING gist (geom);

-- 2) 范围类型
CREATE TABLE reservations (
    id      SERIAL PRIMARY KEY,
    room_id INT,
    during  DATERANGE
);
CREATE INDEX idx_res_during ON reservations USING gist (during);

-- 3) 全文搜索
CREATE TABLE articles (
    id      SERIAL PRIMARY KEY,
    title   TEXT,
    content TEXT,
    body    TSVECTOR
);
CREATE INDEX idx_articles_body ON articles USING gist (body);
```

### 4. 完整示例:PostGIS 地理查询

```sql
-- 1) 启用 PostGIS 扩展
CREATE EXTENSION postgis;

-- 2) 建表(经度/纬度 → geometry)
CREATE TABLE restaurants (
    id      SERIAL PRIMARY KEY,
    name    VARCHAR(64),
    -- 4326 = WGS84 坐标系
    location GEOMETRY(Point, 4326)
);

-- 3) 插入数据
INSERT INTO restaurants (name, location) VALUES
    ('北京烤鸭店', ST_SetSRID(ST_MakePoint(116.40, 39.90), 4326)),
    ('上海小笼包', ST_SetSRID(ST_MakePoint(121.47, 31.23), 4326)),
    ('广州早茶',   ST_SetSRID(ST_MakePoint(113.27, 23.13), 4326));

-- 4) 建 GiST 索引
CREATE INDEX idx_rest_location ON restaurants USING gist (location);

-- 5) 查询:找出某点附近 10 公里内的餐厅(米为单位)
--    ST_DWithin 用的是球面距离,GiST 索引能加速
EXPLAIN ANALYZE
SELECT name, ST_Distance(location, ST_SetSRID(ST_MakePoint(116.40, 39.90), 4326)) AS dist
FROM restaurants
WHERE ST_DWithin(
    location,
    ST_SetSRID(ST_MakePoint(116.40, 39.90), 4326),
    10000  -- 10 公里 = 10000 米
)
ORDER BY dist;
-- Bitmap Heap Scan on restaurants
--   Recheck Cond: (location && '...'::geometry)
--   Filter: ((location)::geography && '...'::geography)
--   ->  Bitmap Index Scan on idx_rest_location

-- 6) 包含关系:某多边形内的所有点
SELECT name FROM restaurants
WHERE location @> ST_MakePoint(116.40, 39.90);
-- 包含 → 命中
```

### 5. GiST 范围类型示例

```sql
-- 范围类型常用场景:会议室预订,IP 段
CREATE TABLE bookings (
    id     SERIAL PRIMARY KEY,
    room   INT,
    during DATERANGE
);

-- 排除约束(防止双重预订)
ALTER TABLE bookings ADD CONSTRAINT no_overlap
    EXCLUDE USING gist (room WITH =, during WITH &&);

-- 索引:加快区间查询
CREATE INDEX idx_bookings_during ON bookings USING gist (during);

-- 查询:某时间段内被预订的房间
SELECT room FROM bookings
WHERE during && daterange('2025-01-01', '2025-01-10');
-- && = overlap,命中 idx_bookings_during
```

## 七、GIN 索引(重点)

### 1. 反向索引原理(Inverted Index)

**GIN (Generalized Inverted Index,通用反向索引)** 的核心思想与全文检索中的**倒排索引**一致。

```text
普通索引(正排):
  文档1: "MySQL 索引 性能"        → 文档1
  文档2: "MySQL 事务"            → 文档2
  文档3: "Redis 缓存"            → 文档3

GIN 反向索引(倒排):
  "MySQL"  → 文档1, 文档2          ← 关键词 → 包含它的文档集合
  "索引"   → 文档1
  "性能"   → 文档1
  "事务"   → 文档2
  "Redis"  → 文档3
  "缓存"   → 文档3

★ 查"MySQL 事务" → 求交集 = {文档2}
★ GIN 把数组/JSONB/全文的"值"作为 key,行 TID 作为 value
```

#### GIN 索引结构图

```text
GIN (反向索引) 结构示意

            ┌────────────────────────────┐
            │     GIN 索引元数据          │   (meta page)
            │  - pending list 大小         │
            │  - fastupdate 状态            │
            └────────────────────────────┘
                          │
            ┌─────────────┴─────────────┐
            │                           │
        ┌───▼────┐                  ┌───▼────┐
        │ Entry  │  ...  N 个 ...  │ Entry  │   ← B-Tree 索引所有 key
        │ key=MySQL│                 │ key=事务│
        └───┬────┘                  └───┬────┘
            │                           │
       ┌────▼─────┐                 ┌───▼─────┐
       │ Posting  │                 │ Posting  │  ← 包含该 key 的 TID 列表
       │ List     │                 │ List     │   (叶子节点)
       │ T1, T2   │                 │ T2       │
       └──────────┘                 └──────────┘
            ▲
            │
       ┌────┴─────────────────────────────┐
       │       Pending List (可选)        │   ← fastupdate 缓冲
       │  新插入的 key→TID 暂存这里        │
       │  后台进程定期合并到主索引          │
       └──────────────────────────────────┘

★ Posting Tree:当 TID 列表很大时,用 B-Tree 存 TID(避免线性扫描)
★ Pending List:fastupdate=on 时,新数据先入 pending,定期 merge
```

### 2. GIN 应用场景

| 数据类型 | 操作符 | 应用 |
|---------|-------|------|
| **JSONB** | `@>` `?` `?&` `?\|` | JSONB 字段查询 |
| **数组** | `@>` `&&` `=` | 数组包含、数组相交 |
| **tsvector** | `@@` | 全文搜索 |
| **hstore** | `@>` `?` `?&` | KV 字段 |
| **trigram** | `LIKE` `ILIKE` `~` `~*` | 模糊匹配(任意位置) |

### 3. GIN vs GiST 对比

| 维度 | GIN | GiST |
|------|-----|------|
| 查询速度 | **快**(等值/包含) | 中 |
| 写入速度 | **慢**(要更新反向索引) | 中 |
| 索引体积 | **大**(3~10x) | 1.5~3x |
| 支持类型 | JSONB/数组/全文更全 | 几何/范围/全文 |
| 全文搜索 | **推荐** | 一般 |
| 模糊匹配(trigram) | **唯一选择** | 不支持 |
| 复合索引支持 | 否(只能单列) | 否 |
| 并发更新 | **差** | 好 |
| fastupdate | 支持 | 不支持 |

```text
选型决策:
- 全文搜索 / JSONB / 数组:用 GIN
- 几何 / 范围 / 树形:用 GiST
- 模糊匹配(任意位置 LIKE):用 GIN + pg_trgm
- 写入密集(频繁 UPDATE/INSERT):用 GiST 优先
- 查询密集(数据稳定):用 GIN 优先
```

### 4. GIN 关键参数

#### (1) `fastupdate` (GIN 性能优化)

- **开启**(`fastupdate = on`,默认):新数据先入 **pending list**,后台定期合并
- **关闭**(`fastupdate = off`):每次插入立即更新主索引
- **优势**:批量插入快 3~10 倍
- **代价**:查询前要扫描 pending list,查询略慢
- **调优**:可以通过 `VACUUM` 强制合并

```sql
-- 创建 GIN 索引时开启 fastupdate
CREATE INDEX idx_articles_body ON articles USING gin (body) WITH (fastupdate = on);

-- 修改现有索引
ALTER INDEX idx_articles_body SET (fastupdate = off);
```

#### (2) `gin_pending_list_limit`

- pending list 的最大页数(默认 **4 MB**)
- 超过后自动触发清理
- 调大:减少清理频率,但占用更多内存
- 调小:频繁清理,查询性能稳定

```sql
-- 调大到 16 MB
ALTER INDEX idx_articles_body SET (gin_pending_list_limit = 16384);  -- 单位 KB

-- 强制合并 pending list 到主索引(不 VACUUM)
SELECT gin_clean_pending_list('idx_articles_body'::regclass);
```

### 5. 完整示例:JSONB GIN 索引

```sql
-- 1) 建表
CREATE TABLE products (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(128),
    attributes  JSONB,
    tags        TEXT[]
);

-- 2) 插入数据
INSERT INTO products (name, attributes, tags) VALUES
    ('iPhone 15', '{"brand":"Apple","price":7999,"color":"black"}', ARRAY['phone','apple']),
    ('小米 14',   '{"brand":"Xiaomi","price":3999,"color":"white"}', ARRAY['phone','xiaomi']),
    ('MacBook',   '{"brand":"Apple","price":14999,"color":"gray"}',  ARRAY['laptop','apple']);

-- 3) 创建 GIN 索引(常用操作符类)
--    jsonb_ops:支持 @> ? ?& ?| (默认)
--    jsonb_path_ops:仅支持 @>,但更小更快
CREATE INDEX idx_products_attrs ON products USING gin (attributes);
-- 上面等价于 USING gin (attributes jsonb_path_ops) 仅支持 @>

-- 4) 数组 GIN 索引
CREATE INDEX idx_products_tags ON products USING gin (tags);

-- 5) 查询:JSONB 包含关系
--    含义:attributes 包含 {"brand":"Apple"}
EXPLAIN SELECT * FROM products
WHERE attributes @> '{"brand":"Apple"}';
-- Bitmap Heap Scan → Bitmap Index Scan on idx_products_attrs

-- 6) 查询:数组包含(包含 "apple" 的)
EXPLAIN SELECT * FROM products
WHERE tags @> ARRAY['apple'];
-- Bitmap Index Scan on idx_products_tags

-- 7) 查询:键是否存在
SELECT * FROM products WHERE attributes ? 'color';
-- 也命中 GIN
```

### 6. 完整示例:GIN 全文搜索

```sql
-- 1) 建表
CREATE TABLE articles (
    id      SERIAL PRIMARY KEY,
    title   TEXT,
    content TEXT
);

-- 2) 生成 tsvector 列(GIN 索引此列)
ALTER TABLE articles ADD COLUMN tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('simple', coalesce(title,'') || ' ' || coalesce(content,''))) STORED;

-- 3) 建 GIN 索引
CREATE INDEX idx_articles_tsv ON articles USING gin (tsv);

-- 4) 插入数据
INSERT INTO articles (title, content) VALUES
    ('PostgreSQL 索引', 'B-Tree 是默认索引,GIN 适合全文和 JSONB'),
    ('MySQL 索引', 'InnoDB 用 B+Tree');

-- 5) 全文搜索
SELECT title FROM articles
WHERE tsv @@ to_tsquery('simple', 'GIN & 索引');
-- 命中 idx_articles_tsv

-- 6) 高亮显示
SELECT title, ts_headline('simple', content, to_tsquery('simple', 'GIN'))
FROM articles WHERE tsv @@ to_tsquery('simple', 'GIN');
```

### 7. 完整示例:trigram 模糊匹配

```sql
-- 1) 启用扩展
CREATE EXTENSION pg_trgm;

-- 2) 建表
CREATE TABLE users (id SERIAL PRIMARY KEY, name VARCHAR(64));

-- 3) 建 GIN trigram 索引(用于模糊匹配)
CREATE INDEX idx_users_name_trgm ON users USING gin (name gin_trgm_ops);

-- 4) 模糊匹配(任意位置 LIKE,也能命中索引)
EXPLAIN SELECT * FROM users WHERE name LIKE '%张三%';
-- Bitmap Index Scan on idx_users_name_trgm   ← 通常能命中

-- 5) 相似度匹配
SELECT name, similarity(name, '张三') AS sim
FROM users
WHERE name % '张三'           -- % 操作符表示相似度阈值
ORDER BY sim DESC;
```

## 八、BRIN 索引(重点)

### 1. 块范围索引原理

**BRIN (Block Range Index,块范围索引)** 是 PostgreSQL 9.5 引入的**专为超大表设计**的索引。它**不存储每行的索引项**,而是**按"块范围 (Block Range)"存储摘要信息**。

#### (1) 核心思想

- 把表按**连续的物理块**分组,默认 **128 个块(1 MB)** 一个 Range
- 每个 Range 存**该范围数据的"摘要"**(如 min、max、sum、null count)
- 查询时:先扫 Range 摘要,**排除不匹配的 Range**,再精确查

```text
BRIN (块范围索引) 原理示意

       堆表 (Heap) - 按时间顺序插入,数据天然物理有序
       ┌─────────┬─────────┬─────────┬─────────┬─────────┐
       │ Block 0 │ Block 1 │ Block 2 │ Block 3 │ Block 4 │ ... (共 1 万块)
       │ Range 0 │         │ Range 1 │         │ Range 2 │
       │ ct:100~│         │ ct:200~│         │ ct:300~│
       │  150   │         │  250   │         │  350   │
       └─────────┴─────────┴─────────┴─────────┴─────────┘
            │              │              │
            ▼              ▼              ▼
       ┌─────────┐    ┌─────────┐    ┌─────────┐
       │ Range 0 │    │ Range 1 │    │ Range 2 │     ← BRIN 索引项
       │min=100  │    │min=200  │    │min=300  │       (极小,几 MB)
       │max=150  │    │max=250  │    │max=350  │
       │count=80 │    │count=90 │    │count=85 │
       └─────────┘    └─────────┘    └─────────┘

查询:WHERE created_at BETWEEN 220 AND 240

Step 1: 扫 BRIN 索引,排除 Range 0(min=100, max=150, 不在范围)
Step 2: Range 1 部分命中(min=200, max=250, 需精确查)
Step 3: Range 2 不命中(min=300, max=350)
Step 4: 只对 Range 1 的块做精确扫描(节省大量 IO)
```

#### (2) BRIN 适合的场景

| 场景 | 是否适合 | 原因 |
|------|--------|------|
| **时序数据**(按时间排序插入) | **✅ 最佳** | 数据天然按时间物理有序,Range 摘要精准 |
| **IoT 设备日志** | **✅ 最佳** | 类似时序 |
| **日志表**(append-only) | **✅ 最佳** | 追加写,物理顺序与时间顺序一致 |
| **OLAP 大表** | ✅ 适合 | 数据按某列排序加载 |
| **频繁 UPDATE/DELETE** | ❌ 不适合 | 物理顺序被打乱,摘要不准 |
| **小表(< 100 万行)** | ❌ 不划算 | B-Tree 更好 |
| **无序数据** | ❌ 不适合 | min/max 范围太大,选择性差 |

#### (3) BRIN 优势

| 优势 | 说明 |
|------|------|
| **索引体积极小** | 通常 1MB~几十 MB,1 亿行表 B-Tree 可能几个 GB |
| **写入极快** | 只需更新对应 Range 的 min/max,几乎无开销 |
| **适合范围查询** | 时间范围、ID 范围 |
| **适合 MIN/MAX/AVG** | 聚合操作可仅扫 BRIN |

### 2. BRIN 不适合的场景

```text
BRIN 失效场景:
1. 表数据频繁 UPDATE/DELETE → 物理顺序与逻辑顺序不一致,摘要失效
2. 数据本身无序(随机插入) → 每个 Range 的 min/max 范围太大,选择性差
3. 等值查询需求 > 范围查询 → B-Tree 更好
4. 表很小 → B-Tree 索引本来就不大
```

### 3. BRIN 完整示例:10 亿行日志表

```sql
-- 1) 建表(按 created_at 排序插入)
CREATE TABLE app_log (
    id          BIGSERIAL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    level       VARCHAR(16),
    message     TEXT,
    user_id     BIGINT
) PARTITION BY RANGE (created_at);

-- 或者简单表(单表)
CREATE TABLE app_log (
    id          BIGSERIAL PRIMARY KEY,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    level       VARCHAR(16),
    message     TEXT,
    user_id     BIGINT
);

-- 2) 插入 1 亿行模拟数据(按时间)
INSERT INTO app_log (created_at, level, message, user_id)
SELECT
    '2020-01-01'::timestamptz + (i * interval '1 second'),
    CASE WHEN i % 100 = 0 THEN 'ERROR' ELSE 'INFO' END,
    'log message ' || i,
    (random() * 1000000)::bigint
FROM generate_series(1, 100000000) i;

-- 3) ★ BRIN 索引(关键!)
--    pages_per_range = 128 (默认,1MB 一个 Range)
--    BRIN 索引体积通常 < 1 MB
CREATE INDEX idx_log_created_at ON app_log USING brin (created_at);

-- 4) 查看索引大小
SELECT pg_size_pretty(pg_relation_size('idx_log_created_at')) AS index_size,
       pg_size_pretty(pg_relation_size('app_log'))              AS table_size;
-- index_size  ≈ 几百 KB
-- table_size  ≈ 几个 GB

-- 5) 范围查询(完美命中 BRIN)
EXPLAIN ANALYZE
SELECT * FROM app_log
WHERE created_at BETWEEN '2025-01-01' AND '2025-01-02';
-- Bitmap Heap Scan on app_log
--   Recheck Cond: ((created_at >= ...) AND (created_at <= ...))
--   ->  Bitmap Index Scan on idx_log_created_at
--       (只访问了对应的 Range,跳过绝大部分数据)

-- 6) 聚合查询:某时间段内最大时间
EXPLAIN ANALYZE
SELECT MIN(created_at), MAX(created_at), COUNT(*)
FROM app_log
WHERE created_at BETWEEN '2025-01-01' AND '2025-01-02';
-- 可能只扫 BRIN 即可

-- 7) 对比:B-Tree 索引会非常大
--    CREATE INDEX idx_log_btree ON app_log (created_at);
--    → B-Tree 索引通常 > 2 GB
--    → 写入慢
```

### 4. BRIN 高级选项

```sql
-- 自定义 pages_per_range(每个 Range 几个块)
--   值越小:摘要越精细,选择性越好,但索引越大
--   值越大:摘要越粗糙,索引越小
CREATE INDEX idx_log_brin ON app_log USING brin (created_at)
    WITH (pages_per_range = 32);   -- 32 块 = 256 KB 一个 Range

-- 多种操作符类
--   brin_minmax_ops: 默认,存 min/max(适合数字、时间)
--   brin_inclusion_ops: 适合数组、范围、JSONB
--   brin_bloom_opaque: 布隆过滤器
CREATE INDEX idx_log_level ON app_log USING brin (level)
    WITH (pages_per_range = 16);
```

## 九、部分索引(Partial Index,PG 特色)

### 1. 什么是部分索引

**部分索引 (Partial Index)**:只索引**满足 WHERE 条件的行**,是 PostgreSQL 的特色功能。

### 2. 部分索引的妙用

- **节省空间**:只索引部分数据,索引体积大幅减小
- **写入更快**:大部分数据(不满足 WHERE)不进入索引
- **查询更准**:优化器知道索引只覆盖部分数据,选择性更精准

### 3. 完整示例

```sql
-- 1) 场景:订单表 1 亿行,只有 5% 是"未支付"状态
CREATE TABLE orders (
    id         BIGSERIAL PRIMARY KEY,
    user_id    BIGINT,
    status     VARCHAR(16),  -- pending / paid / shipped / cancelled
    amount     DECIMAL(10,2),
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 2) 错误:全量索引(数据大,无效行多)
CREATE INDEX idx_orders_user ON orders(user_id);
-- 索引包含所有 1 亿行

-- 3) 正确:部分索引(只索引未支付订单)
CREATE INDEX idx_orders_pending_user ON orders(user_id)
    WHERE status = 'pending';
-- 只索引 5% 的行,索引体积是原来的 1/20

-- 4) 查询:未支付订单
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 AND status = 'pending';
-- 命中 idx_orders_pending_user
-- key: idx_orders_pending_user

-- 5) 查询:已支付订单(不命中)
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 AND status = 'paid';
-- 不会用 idx_orders_pending_user(WHERE 不匹配)
```

### 4. 实战应用场景

```sql
-- 场景 1:软删除表(只索引未删除的)
CREATE INDEX idx_users_active ON users(email) WHERE deleted_at IS NULL;

-- 场景 2:只索引"热门"数据
CREATE INDEX idx_products_hot ON products(category) WHERE view_count > 1000;

-- 场景 3:只索引最近的数据(配合分区更佳)
CREATE INDEX idx_logs_recent ON logs(created_at)
    WHERE created_at > '2024-01-01';

-- 场景 4:登录用户表
CREATE INDEX idx_users_login ON users(last_login_at)
    WHERE is_active = TRUE;
```

## 十、表达式索引(Expression Index)

### 1. 什么是表达式索引

**表达式索引**:对**列上的函数或表达式**建立索引,而不是对列本身。

```sql
-- 普通索引:对 email 列建索引
CREATE INDEX idx_users_email ON users(email);

-- 表达式索引:对 lower(email) 建索引
CREATE INDEX idx_users_lower_email ON users(lower(email));
```

### 2. 完整示例

```sql
-- 1) 场景:邮箱不区分大小写查询
CREATE TABLE users (
    id    SERIAL PRIMARY KEY,
    email VARCHAR(128) NOT NULL
);

-- 不建表达式索引:索引失效
EXPLAIN SELECT * FROM users WHERE lower(email) = '[email protected]';
-- Seq Scan (lower(email) 不在普通索引中)

-- 2) 建表达式索引
CREATE INDEX idx_users_lower_email ON users(lower(email));

-- 3) 查询(必须用同样的表达式)
EXPLAIN SELECT * FROM users WHERE lower(email) = '[email protected]';
-- Index Scan using idx_users_lower_email

-- 4) 注意:查询的表达式必须与索引的表达式**完全一致**
SELECT * FROM users WHERE email = '[email protected]';  -- 不会用索引
```

### 3. 更多表达式索引示例

```sql
-- 1) 日期截断(查询某天的所有数据)
CREATE INDEX idx_orders_day ON orders(date_trunc('day', created_at));

SELECT * FROM orders
WHERE date_trunc('day', created_at) = '2025-01-01'::date;

-- 2) 字符串提取(URL 中的域名)
CREATE INDEX idx_urls_domain ON urls(split_part(url, '/', 3));

SELECT * FROM urls WHERE split_part(url, '/', 3) = 'example.com';

-- 3) JSONB 字段提取
CREATE INDEX idx_users_country ON users((address->>'country'));

SELECT * FROM users WHERE (address->>'country') = 'CN';

-- 4) 数学计算
CREATE INDEX idx_orders_discount ON orders((price * quantity));

SELECT * FROM orders WHERE price * quantity > 10000;
```

### 4. 表达式索引要点

- **表达式必须确定性的**(`IMMUTABLE`):同一输入必须得到同一输出
- **查询条件必须用同样的表达式**:否则不会命中
- **支持多表达式**:`CREATE INDEX ON t((a + b), (c || d));`

## 十一、多列索引(联合索引)

### 1. 与 MySQL 一致的最左前缀

PostgreSQL 复合索引(联合索引)的最左前缀规则与 MySQL **完全一致**:

- 复合索引 `(a, b, c)` 相当于建了三个索引:`(a)`、`(a, b)`、`(a, b, c)`
- **不**包含 `(b)`、`(c)`、`(b, c)`

```text
复合索引 (a, b, c) 的存储顺序(按 a, b, c 升序):

(a=1, b=1, c=1) → (a=1, b=1, c=5) → (a=1, b=2, c=3) →
(a=1, b=3, c=9) → (a=2, b=1, c=7) → (a=2, b=4, c=2) → ...

★ 先按 a 排序,a 相同再看 b,b 相同再看 c
★ 跳过 a 直接用 b,c → 无法定位 → 全索引扫描或全表扫描
```

### 2. 完整示例

```sql
-- 1) 建表
CREATE TABLE orders (
    id         BIGSERIAL PRIMARY KEY,
    user_id    BIGINT,
    status     VARCHAR(16),
    created_at TIMESTAMPTZ
);

-- 2) 复合索引
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- 3) 命中规则
EXPLAIN SELECT * FROM orders WHERE user_id = 100;                -- ✅ 命中
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 'paid';  -- ✅ 命中
EXPLAIN SELECT * FROM orders WHERE status = 'paid';              -- ❌ 不命中
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 'paid'; -- ❌ 不命中(OR)
```

### 3. 列顺序设计原则

```text
★ 高频等值列在前
★ 高选择性列在前
★ 范围列放最后
★ 兼顾 ORDER BY / GROUP BY 列
```

```sql
-- 场景 1:WHERE a = ? AND b = ?, ORDER BY c
CREATE INDEX idx_a_b_c ON t(a, b, c);  -- a,b 命中 WHERE,c 命中 ORDER BY

-- 场景 2:WHERE a = ? AND b = ?
CREATE INDEX idx_a_b ON t(a, b);

-- 场景 3:WHERE a IN (?) AND b = ?  -- a 在前
CREATE INDEX idx_a_b ON t(a, b);

-- 场景 4:WHERE a = ? AND b > ?   -- a 等值,b 范围
CREATE INDEX idx_a_b ON t(a, b);
```

### 4. PostgreSQL 特有的多列索引能力

- **任意列顺序**:不像 MySQL 8.0 之前只能 ASC,PostgreSQL 支持 `(a ASC, b DESC)`
- **不同操作符类**:`CREATE INDEX ON t(a, b varchar_ops);`
- **表达式混合**:`CREATE INDEX ON t(a, (b + c));`

```sql
-- 不同方向
CREATE INDEX idx_t_a_b_desc ON t(a ASC, b DESC);

-- 混合表达式
CREATE INDEX idx_t_a_expr ON t(a, (b + c));
```

## 十二、INCLUDE 索引(PG 11+,覆盖索引)

### 1. 什么是 INCLUDE 索引

**INCLUDE 索引**(PG 11+):在索引中**附加存储非 key 列**,但这些列**不参与排序/查找**,仅用于**覆盖查询**(Covering Index),避免回表。

### 2. INCLUDE vs 普通复合索引

| 维度 | 普通复合索引 `(a, b, c)` | INCLUDE 索引 `(a) INCLUDE (b, c)` |
|------|--------------------------|-------------------------------------|
| b、c 参与排序 | **是** | **否**(仅附加存储) |
| 索引体积 | 较大(b、c 参与排序) | 较小(b、c 仅按 heap 顺序附加) |
| 覆盖查询 | ✅ | ✅ |
| 范围/等值查询 | ✅ 命中 a、b、c | ✅ 仅 a 可用于范围 |
| 适用 | 需要多列排序/范围 | 仅需覆盖查询 |

### 3. 完整示例

```sql
-- 1) 表
CREATE TABLE users (
    id    SERIAL PRIMARY KEY,
    email VARCHAR(128) NOT NULL,
    name  VARCHAR(64) NOT NULL,
    age   INT
);

-- 2) 场景:频繁 SELECT id, name FROM users WHERE email = ?
--    普通索引需要回表
--    INCLUDE 索引避免回表

-- 3) 建 INCLUDE 索引
CREATE INDEX idx_users_email_name ON users(email) INCLUDE (name);

-- 4) 验证:覆盖查询无需回表
EXPLAIN SELECT id, name FROM users WHERE email = '[email protected]';
-- Index Only Scan using idx_users_email_name
-- ★ 关键是 Index Only Scan,无需 heap fetch

-- 5) 对比:普通复合索引
CREATE INDEX idx_users_email_name2 ON users(email, name);
-- 也能覆盖,但 name 参与排序,索引可能略大

-- 6) 多个 INCLUDE 列
CREATE INDEX idx_users_email_all ON users(email) INCLUDE (name, age);

-- 7) 查询能完全覆盖
EXPLAIN SELECT id, name, age FROM users WHERE email = '[email protected]';
-- Index Only Scan
```

### 4. INCLUDE 列的限制

- **不能用于排序或范围**:`INCLUDE (b)` 不能让 `WHERE b > 10` 命中索引
- **不能用在 WHERE 中**:`INCLUDE (b)` 不能让 `WHERE b = 'x'` 命中索引
- **只用于 SELECT 列的覆盖**

```sql
-- INCLUDE 列不可用于 WHERE
EXPLAIN SELECT * FROM users WHERE name = '张三';
-- Seq Scan(INCLUDE 中的 name 不参与索引)
```

## 十三、唯一索引(UNIQUE)

### 1. 唯一索引 vs 主键

| 维度 | 主键 (PRIMARY KEY) | 唯一索引 (UNIQUE INDEX) |
|------|------------------|---------------------|
| 数量 | 一张表只能有 1 个 | 一张表可有多个 |
| NULL | **不允许 NULL** | **允许 NULL**(多个) |
| 隐式索引 | 是(自动建唯一索引) | 否 |
| 作用 | 唯一标识行 | 唯一性约束 + 加速查询 |

### 2. 唯一索引创建

```sql
-- 1) 建表时
CREATE TABLE users (
    id    SERIAL PRIMARY KEY,
    email VARCHAR(128) UNIQUE,
    phone VARCHAR(20)
);

-- 2) 表已存在
CREATE UNIQUE INDEX uk_users_email ON users(email);
CREATE UNIQUE INDEX uk_users_phone ON users(phone);

-- 3) 复合唯一索引
CREATE UNIQUE INDEX uk_users_phone_email ON users(phone, email);

-- 4) 部分唯一索引(只对部分行唯一)
CREATE UNIQUE INDEX uk_users_active_email ON users(email)
    WHERE deleted_at IS NULL;
-- 同 email 的"未删除"用户只能有一个,但已删除用户可以有同 email

-- 5) 表达式唯一索引
CREATE UNIQUE INDEX uk_users_lower_email ON users(lower(email));
```

### 3. 唯一索引的妙用

```sql
-- 1) 业务唯一性保证
CREATE UNIQUE INDEX uk_order_no ON orders(order_no);

-- 2) 联合唯一(防止重复关系)
CREATE UNIQUE INDEX uk_user_role ON user_roles(user_id, role_id);

-- 3) 软删除表的"实际唯一"
CREATE UNIQUE INDEX uk_users_active_email ON users(email)
    WHERE deleted_at IS NULL;
```

## 十四、并发创建索引(CONCURRENTLY)

### 1. 传统创建索引的问题

```sql
-- 普通方式:锁表,阻塞所有写入
CREATE INDEX idx_users_email ON users(email);
-- 问题:大表上创建可能**数小时**,期间所有 INSERT/UPDATE/DELETE 都被阻塞
```

### 2. CONCURRENTLY 解决方案

```sql
-- 并发创建:不锁表,但时间更长,且需二次扫描
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
```

### 3. CONCURRENTLY 特性

| 特性 | 普通 CREATE INDEX | CREATE INDEX CONCURRENTLY |
|------|-----------------|--------------------------|
| **是否锁表** | **是**(Share 锁,阻塞写) | **否**(不阻塞读写) |
| **速度** | 快 | **慢 2~3 倍**(需两次扫表) |
| **失败后** | 索引删除,回滚 | **留下 INVALID 索引**,需清理 |
| **事务** | 在事务中 | **不能在事务块中** |
| **应用场景** | 小表、低峰期 | **大表、生产环境** |

### 4. 完整流程与失败处理

```sql
-- 1) 正常创建
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- 2) 失败后清理(invalid 索引)
--    查看无效索引
SELECT indexrelid::regclass AS index_name, indisvalid
FROM pg_index
WHERE NOT indisvalid;

-- 3) 删除无效索引
DROP INDEX CONCURRENTLY IF EXISTS idx_users_email;

-- 4) 重新创建
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- 5) 监控进度(pg_stat_progress_create_index,PG 12+)
SELECT * FROM pg_stat_progress_create_index;
```

### 5. 实战建议

```text
★ 大表(> 1 千万行):必须用 CONCURRENTLY
★ 高峰期:必须用 CONCURRENTLY
★ 配合 pg_stat_progress_create_index 监控
★ 失败后必须清理 INVALID 索引
```

## 十五、REINDEX(重建索引)

### 1. 为什么需要 REINDEX

- 索引**碎片化**(长期 INSERT/DELETE 导致)
- 索引**膨胀**(bloat)
- 索引**损坏**(罕见,但 PG < 10 Hash 索引可能)
- 长期 VACUUM 后索引未释放空间

### 2. REINDEX 方式

```sql
-- 1) 重建单个索引
REINDEX INDEX idx_users_email;

-- 2) 重建表的所有索引
REINDEX TABLE users;

-- 3) 重建 schema 的所有索引
REINDEX SCHEMA public;

-- 4) 重建数据库的所有索引
REINDEX DATABASE mydb;

-- 5) PG 12+ 并发重建(不阻塞读写)
REINDEX INDEX CONCURRENTLY idx_users_email;
REINDEX TABLE CONCURRENTLY users;
```

### 3. REINDEX vs DROP + CREATE

| 方式 | 优点 | 缺点 |
|------|------|------|
| **REINDEX** | 保留索引定义、不需要重新写 SQL | 较慢 |
| **DROP + CREATE** | 更快(全新建) | 需重新指定索引定义 |

```sql
-- 实战:用 REINDEX 重建大索引
REINDEX INDEX CONCURRENTLY idx_log_created_at;
```

## 十六、索引查看

### 1. `\d` 命令(psql)

```sql
-- 1) 查看表的所有索引
\d users

-- 2) 详细定义
\d+ users

-- 3) 仅查看索引
\di
```

### 2. `pg_indexes` 系统视图

```sql
SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE tablename = 'users';
```

### 3. `pg_stat_user_indexes` 使用统计

```sql
-- 查看每个索引的扫描次数
SELECT
    schemaname,
    relname        AS table_name,
    indexrelname   AS index_name,
    idx_scan       AS scan_count,        -- 索引扫描次数
    idx_tup_read   AS tuples_read,       -- 读取的索引项数
    idx_tup_fetch  AS tuples_fetched     -- 通过索引回表次数
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC;
```

### 4. 索引大小与膨胀

```sql
-- 1) 查看索引大小
SELECT
    indexrelname   AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 2) 索引膨胀诊断(需要 pgstattuple 扩展)
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstatindex('idx_users_email');
-- avg_leaf_density:叶节点密度(越接近 90% 越好)
-- dead_percent:死元组百分比
```

### 5. 找出未使用的索引

```sql
-- idx_scan = 0:从未被使用
SELECT
    schemaname || '.' || relname AS table_name,
    indexrelname                 AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'  -- 排除主键
ORDER BY pg_relation_size(indexrelid) DESC;
```

### 6. EXPLAIN 查看 SQL 索引使用

```sql
EXPLAIN SELECT * FROM users WHERE email = '[email protected]';

-- 详细分析
EXPLAIN (ANALYZE, BUFFERS, TIMING) SELECT * FROM users WHERE email = '[email protected]';
```

| 节点 | 含义 |
|------|------|
| **Seq Scan** | 全表扫描(通常表示索引缺失或失效) |
| **Index Scan** | 索引扫描 + 回表 |
| **Index Only Scan** | 覆盖索引,无需回表(最优) |
| **Bitmap Index Scan** | 位图索引扫描(多索引 OR 时) |
| **Bitmap Heap Scan** | 位图回表 |

## 十七、索引失效场景

PostgreSQL 与 MySQL 在索引失效方面**大部分规则相同**,但有 PG 特有的细节。

### 1. 函数计算(除非表达式索引)

```sql
-- ✗ 索引失效
EXPLAIN SELECT * FROM users WHERE date(created_at) = '2025-01-01';
-- Seq Scan on users

-- ✗ 索引失效
EXPLAIN SELECT * FROM users WHERE age + 1 = 30;

-- ✓ 改写后命中
EXPLAIN SELECT * FROM users
WHERE created_at >= '2025-01-01' AND created_at < '2025-01-02';

-- ✓ 表达式索引(让函数索引生效)
CREATE INDEX idx_users_created_date ON users(date(created_at));
EXPLAIN SELECT * FROM users WHERE date(created_at) = '2025-01-01';
-- Bitmap Index Scan on idx_users_created_date
```

### 2. 类型不匹配(隐式类型转换)

```sql
-- phone 是 VARCHAR
EXPLAIN SELECT * FROM users WHERE phone = 13800138000;
-- Seq Scan (隐式转 varchar,索引失效)

EXPLAIN SELECT * FROM users WHERE phone = '13800138000';
-- Index Scan using idx_users_phone  ✅
```

> **PG 比 MySQL 更严格**:MySQL 有时会隐式转换,PG 在某些场景下会拒绝隐式转换或强制索引失效。

### 3. 前导模糊查询

```sql
-- ✗ 不走 B-Tree
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
-- Seq Scan

-- ✓ 前缀匹配可走 B-Tree
EXPLAIN SELECT * FROM users WHERE name LIKE '张%';
-- Index Scan

-- ✓ 中缀匹配用 GIN + pg_trgm(任意位置 LIKE)
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING gin (name gin_trgm_ops);
EXPLAIN SELECT * FROM users WHERE name LIKE '%张%';
-- Bitmap Index Scan on idx_users_name_trgm  ✅
```

### 4. OR 滥用

```sql
-- ✗ 可能走 Seq Scan
EXPLAIN SELECT * FROM users WHERE name = '张三' OR age = 20;

-- ✓ 改写:UNION ALL
EXPLAIN
SELECT * FROM users WHERE name = '张三'
UNION ALL
SELECT * FROM users WHERE age = 20 AND name != '张三';
```

### 5. IS NULL / IS NOT NULL

```sql
-- B-Tree 上 IS NULL 通常可以走索引
EXPLAIN SELECT * FROM users WHERE email IS NULL;

-- IS NOT NULL 在大多数行都为 NULL 时可能失效
EXPLAIN SELECT * FROM users WHERE email IS NOT NULL;
```

### 6. 范围条件后列失效

```sql
CREATE TABLE t (a INT, b INT, c INT, INDEX idx_a_b_c (a, b, c));

-- b 范围,c 失效
EXPLAIN SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 2;
-- 实际只会用 a 和 b,c 不能用于过滤
```

### 7. 表数据量少

```sql
-- 表只有 50 行,优化器认为 Seq Scan 更快
EXPLAIN SELECT * FROM small_table WHERE indexed_col = 'x';
-- Seq Scan on small_table  ← 正常
```

### 8. 统计信息过期

```sql
-- 大量写入后,优化器可能错选
ANALYZE users;   -- 强制更新统计信息

-- 自动 ANALYZE(autovacuum)
SHOW autovacuum;
```

### 9. 索引失效速查表

| 场景 | 失效原因 | 改写方式 |
|------|---------|---------|
| `WHERE date(col) = '...'` | 函数 | 范围或表达式索引 |
| `WHERE col + 1 = N` | 计算 | `WHERE col = N-1` |
| `WHERE varchar_col = 123` | 隐式转换 | `varchar_col = '123'` |
| `WHERE name LIKE '%x%'` | 前导模糊 | 前缀或 GIN trigram |
| `WHERE a = 1 OR b = 2` | OR 拆解 | UNION ALL |
| `IS NOT NULL` | 多数行匹配 | 重新设计 |
| 范围后多列 | b 是范围,后面的列失效 | 调整顺序 |
| 小表 | 优化器选择全表扫 | 正常 |
| 统计过期 | 估算不准 | ANALYZE |

## 十八、索引设计最佳实践

### 1. 黄金原则

```text
1. 不是越多越好:每个索引都增加写入开销
2. 选择性高优先:重复值少的列建索引收益大
3. 高频查询优先:用得多的列才值得建
4. 复合优于多单列:(a,b,c) 一个比 (a) (b) (c) 三个高效
5. 范围列放最后:等值列在前,范围列在后
6. 避免冗余索引:(a) 和 (a, b) 同时存在 → 删 (a)
7. 大表用 CONCURRENTLY:不阻塞生产
8. 大表考虑 BRIN:超大数据 + 范围查询
9. JSONB/数组用 GIN:精准匹配
10. 模糊匹配用 GIN + trigram
```

### 2. 索引选择性估算

**选择性 = 不同值数量 / 总行数**,越大越好(理想是 1,主键完美)。

```sql
SELECT
    COUNT(DISTINCT column_name) / COUNT(*) AS selectivity
FROM table_name;
```

| 列 | 选择性 | 是否建议索引 |
|----|--------|-------------|
| 用户 ID | 1.0 | 必须 |
| 性别(男/女) | 0.0001 | 不建议 |
| 手机号 | 1.0 | 强烈建议 |
| 状态(0/1/2/3) | 0.0003 | 一般(考虑部分索引) |
| 订单号 | 1.0 | 强烈建议 |

### 3. 联合索引顺序设计

```sql
-- 场景 1:WHERE a = ? AND b = ?, ORDER BY c
CREATE INDEX idx_a_b_c ON t(a, b, c);

-- 场景 2:高频 a = ? 等值,偶尔 ORDER BY c
CREATE INDEX idx_a ON t(a);
CREATE INDEX idx_c ON t(c);  -- 拆成两个单列索引

-- 场景 3:WHERE a = ? AND b > ?  -- 范围
CREATE INDEX idx_a_b ON t(a, b);
-- a 等值,b 范围

-- 场景 4:覆盖查询
CREATE INDEX idx_a_b_c ON t(a, b, c);
-- 命中 a、b、c,可避免回表
```

### 4. 常见业务索引设计

#### (1) 用户表

```sql
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    email       VARCHAR(128) NOT NULL,
    phone       VARCHAR(20),
    status      VARCHAR(16) DEFAULT 'active',
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- 1) 邮箱登录
CREATE UNIQUE INDEX uk_users_email ON users(lower(email));
-- 不区分大小写 + 唯一

-- 2) 手机号登录
CREATE UNIQUE INDEX uk_users_phone ON users(phone) WHERE phone IS NOT NULL;

-- 3) 状态过滤(只查活跃用户)
CREATE INDEX idx_users_active_created ON users(created_at DESC)
    WHERE status = 'active';

-- 4) 注册时间排序
CREATE INDEX idx_users_created_at ON users(created_at DESC);
```

#### (2) 订单表

```sql
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    order_no    VARCHAR(32) NOT NULL,
    status      VARCHAR(16) NOT NULL,
    amount      DECIMAL(10,2),
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- 1) 订单号唯一
CREATE UNIQUE INDEX uk_orders_no ON orders(order_no);

-- 2) 用户维度查询
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);
-- 场景:某用户的最近订单

-- 3) 状态过滤(部分索引)
CREATE INDEX idx_orders_pending_user ON orders(user_id)
    WHERE status = 'pending';
-- 场景:未支付订单

-- 4) 范围扫描
CREATE INDEX idx_orders_created ON orders(created_at);
-- 场景:按时间范围统计
```

#### (3) 业务宽表(JSONB 字段)

```sql
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(128),
    attrs       JSONB,
    tags        TEXT[],
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- 1) JSONB GIN 索引
CREATE INDEX idx_products_attrs ON products USING gin (attrs);

-- 2) 数组 GIN 索引
CREATE INDEX idx_products_tags ON products USING gin (tags);

-- 3) 表达式索引(JSONB 字段提取)
CREATE INDEX idx_products_brand ON products((attrs->>'brand'));

-- 4) 时间排序
CREATE INDEX idx_products_created ON products(created_at DESC);
```

#### (4) 时序/日志表(BRIN)

```sql
CREATE TABLE app_log (
    id          BIGSERIAL,
    created_at  TIMESTAMPTZ DEFAULT now(),
    level       VARCHAR(16),
    message     TEXT
);

-- 1) BRIN 索引(超小,适合时序)
CREATE INDEX idx_log_created ON app_log USING brin (created_at);

-- 2) 复合 BRIN(多列摘要)
CREATE INDEX idx_log_created_level ON app_log
    USING brin (created_at, level) WITH (pages_per_range = 64);
```

### 5. 索引维护建议

```sql
-- 1) 定期 ANALYZE 更新统计
ANALYZE users;

-- 2) 查看无效索引
SELECT indexrelid::regclass, indisvalid
FROM pg_index
WHERE NOT indisvalid;

-- 3) 重建膨胀的索引
REINDEX INDEX CONCURRENTLY idx_users_email;

-- 4) 启用自动 VACUUM/ANALYZE
ALTER TABLE users SET (
    autovacuum_vacuum_scale_factor = 0.05,
    autovacuum_analyze_scale_factor = 0.02
);

-- 5) 监控索引使用
SELECT * FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey';
-- 删除长期未用的索引
```

### 6. 索引监控 SQL

```sql
-- 1) 索引大小 TOP 20
SELECT
    schemaname || '.' || relname AS table_name,
    indexrelname                 AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;

-- 2) 重复/冗余索引(用 pgstatindex + 手工对比)

-- 3) 全表扫描 TOP 10(可能缺索引)
SELECT
    relname,
    seq_scan,
    seq_tup_read,
    idx_scan,
    pg_size_pretty(pg_relation_size(relid)) AS size
FROM pg_stat_user_tables
ORDER BY seq_scan DESC
LIMIT 10;

-- 4) 索引命中率(越高越好)
SELECT
    sum(idx_blks_hit) / nullif(sum(idx_blks_hit + idx_blks_read), 0) AS ratio
FROM pg_statio_user_indexes;
```

## 十九、核心要点速记

- **PG 是索引类型最丰富的 DB**:6 种内置(B-Tree/Hash/GiST/SP-GiST/GIN/BRIN)+ 扩展(Bloom/RUM)
- **默认 B-Tree**:绝大多数场景用 B-Tree,适合等值/范围/排序/前缀 LIKE
- **B-Tree 树高 2~4**:8KB 页,3 层可撑 1.5 亿行(整型主键)
- **PG 是堆表**:二级索引叶子存 TID,直接定位堆表,与 MySQL 聚簇索引的"二级索引存主键"不同
- **Hash 索引**:PG 10+ 才完善,仅等值,适用场景窄
- **GiST**:几何/范围/全文/IP/树形,平衡多路树,PostGIS 必选
- **SP-GiST**:空间分割,适合 IP 前缀/电话/不平衡数据
- **GIN(重点)**:反向索引,JSONB/数组/全文/trigram 必选
- **GIN fastupdate**:批量插入快,查询略慢,可手动 `gin_clean_pending_list`
- **BRIN(重点)**:块范围索引,体积极小(1MB~几 MB),适合**物理有序的超大表**(时序/IoT/日志)
- **部分索引**:只索引 WHERE 条件数据,体积小、写入快,PG 特色
- **表达式索引**:对函数结果建索引,查询必须用相同表达式
- **INCLUDE 索引**:PG 11+,覆盖索引避免回表,INCLUDE 列不参与排序
- **唯一索引**:支持表达式/部分唯一,`UNIQUE INDEX ... WHERE ...`
- **CONCURRENTLY**:大表创建索引不锁表,失败后留下 INVALID 索引需清理
- **REINDEX**:PG 12+ 支持 `REINDEX CONCURRENTLY` 不锁表
- **索引失效**:函数/隐式转换/前导模糊/OR/小表/统计过期
- **选择性**:COUNT(DISTINCT col) / COUNT(*) ,越大越适合索引
- **联合索引**:高频/等值/选择性高的列在前,范围列放最后
- **PG 优势 vs MySQL**:部分索引/表达式索引/INCLUDE/BRIN/多索引方法
- **避免过度索引**:每个索引都增加写入开销、定期 ANALYZE/REINDEX

### 索引选型速查

```text
        等值/范围/排序           → B-Tree
        仅等值 + 极端密集         → Hash
        几何/范围/IP/树形        → GiST
        IP 前缀/电话/不平衡数据  → SP-GiST
        JSONB/数组/全文/trigram → GIN
        时序/IoT/日志(超大表)    → BRIN
        只索引热点数据           → Partial Index
        函数计算结果             → Expression Index
        覆盖查询不回表           → INCLUDE Index
```

### 索引设计口诀

```text
        等值列在前,范围列放最后
        高频列在前,选择性高在前
        覆盖查询列,INCLUDE 避免回表
        长串用 trigram,函数计算要表达式
        复合一个顶三个,冗余索引必删除
        大表 CONCURRENTLY,超表用 BRIN
        JSONB 数组用 GIN,几何范围用 GiST
        软删除用部分索引,定期 ANALYZE 不可少
```

### 索引日常巡检

```sql
-- 索引使用率
SELECT * FROM pg_stat_user_indexes ORDER BY idx_scan DESC;

-- 未使用的索引(可考虑删除)
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey';

-- 全表扫描 TOP
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables
ORDER BY seq_scan DESC LIMIT 10;

-- 索引大小 TOP
SELECT relname, indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC LIMIT 20;

-- 索引命中率(越接近 1 越好)
SELECT sum(idx_blks_hit)::float /
       nullif(sum(idx_blks_hit + idx_blks_read), 0) AS hit_rate
FROM pg_statio_user_indexes;
```
