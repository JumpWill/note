# PostgreSQL 体系结构

## 一、PostgreSQL 概述

**PostgreSQL** 是世界上最先进的开源对象-关系型数据库(ORDBMS),起源于 1986 年加州大学伯克利分校的 **POSTGRES** 项目,1995 年加入 SQL 支持后改名为 PostgreSQL。它以**标准 SQL 完整性**、**丰富的数据类型**、**强大的扩展能力**和**多版本并发控制(MVCC)**著称,被业界誉为"开源界的 Oracle"。

**主要特性**:

- 单进程多进程(fork-per-connection)架构
- 完整的事务支持(ACID)
- 多版本并发控制 MVCC(非锁读)
- 丰富的数据类型(JSONB、数组、范围、几何、UUID、网络地址等)
- 可编程性:存储过程、自定义函数、触发器、规则系统
- 可扩展性:用户可以自定义数据类型、索引方法、操作符、函数
- 跨平台(Linux、Windows、macOS)
- 主从复制、流复制、逻辑复制
- 丰富的客户端协议与连接器

与 MySQL 相比,PostgreSQL 走的是**完全不同的设计路线**:

- **MySQL**:可插拔存储引擎、计算与存储分离、单进程多线程
- **PostgreSQL**:**存储与计算耦合**(Heap/MVCC 是核心)、单进程多进程(更稳定)、更严格的标准 SQL 兼容

## 二、PostgreSQL 整体架构总览

PostgreSQL 的架构可以分为**三层**:客户端层、服务端进程层、存储层(文件系统)。服务端又分为 **postmaster 主进程**、**后台进程**、**后端子进程(backend)**。

```text
┌──────────────────────────────────────────────────────────────┐
│  1. 客户端层 (Client Layer)                                  │
│     - psql 命令行、pgAdmin、DBeaver、Navicat、JDBC、libpq   │
│     - 各种语言的 PostgreSQL Connector/Driver                 │
│     - 通过前端/后端协议(Frontend/Backend Protocol)通信       │
├──────────────────────────────────────────────────────────────┤
│  2. 服务端进程层 (Server Process Layer) — 多进程模型        │
│     ┌────────────────────────────────────────────────────┐   │
│     │  postmaster (主进程,常驻)                         │   │
│     │  - 监听端口、接收客户端连接                        │   │
│     │  - fork 出 backend 子进程处理每个连接              │   │
│     │  - 启动并管理后台进程                              │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  后台进程(BG Processes)                            │   │
│     │  - bgwriter       异步刷脏页                       │   │
│     │  - checkpointer   检查点刷盘                       │   │
│     │  - walwriter      WAL 写入                         │   │
│     │  - autovacuum     自动 VACUUM                      │   │
│     │  - archiver       WAL 归档                         │   │
│     │  - stats          统计信息收集                     │   │
│     │  - logical repl   逻辑复制 launcher               │   │
│     ├────────────────────────────────────────────────────┤   │
│     │  backend 子进程(每个客户端一个)                    │   │
│     │  - 解析 SQL → 重写 → 优化 → 执行                  │   │
│     │  - 返回结果集                                       │   │
│     └────────────────────────────────────────────────────┘   │
├──────────────────────────────────────────────────────────────┤
│  3. 共享内存 (Shared Memory)                                │
│     - shared_buffers(数据页缓冲)                           │
│     - WAL buffers(预写日志缓冲)                            │
│     - CLOG(事务状态) / Subtrans                            │
│     - 锁表 / Proc Array / 其他进程通信结构                  │
├──────────────────────────────────────────────────────────────�
│  4. 文件系统层 (File System)                                 │
│     - base/(表/索引数据,按 oid 组织)                        │
│     - global/(系统表) / pg_wal/(WAL 日志)                  │
│     - pg_xact/(事务提交状态)/ pg_stat/(统计)                │
│     - 配置文件 postgresql.conf / pg_hba.conf               │
├──────────────────────────────────────────────────────────────┤
│  5. 操作系统 / 硬件 (OS & Hardware)                          │
│     内存、磁盘(SSD/HDD)、网络、CPU                          │
└──────────────────────────────────────────────────────────────┘
```

**关键设计**:

- **多进程模型**:每个客户端连接对应一个独立的 backend 进程,故障隔离性好
- **存储引擎不可插拔**:Heap/MVCC 是 PostgreSQL 的核心,引擎层是耦合的
- **共享内存**:所有 backend 进程共享 `shared_buffers` 等结构

## 三、进程架构 (Process Architecture)

PostgreSQL 最显著的特征是采用了**单进程派生的多进程模型** —— 每个客户端连接由 `postmaster` fork 出一个独立的 `postgres` backend 进程来处理。这与 MySQL 的单进程多线程模型形成鲜明对比。

### 1. 进程体系总览图

```text

                     │    (主进程 / 守护)      │

                     └────────────┬────────────┘
                                  │ fork (每客户端一次)
              ┌───────────────────┼───────────────────┐

      │  (客户端A)   │    │  (客户端B)   │    │  (客户端N)   │
```

### 2. postmaster 主进程

`postmaster` 是整个 PostgreSQL 实例的总控进程,负责**监听、派发、监护**:

- **监听端口**(默认 5432),接收客户端连接请求
- 完成客户端认证(`pg_hba.conf`)
- **`fork()` 出 backend 子进程**处理该连接
- **启动并监管**所有后台进程(bgwriter、walwriter、checkpointer 等)
- 处理系统信号(`SIGTERM` 优雅关闭、`SIGHUP` 重载配置、`SIGINT` 立即关闭等)
- 当 backend 进程异常退出时,清理资源并做相应处理
- 维护共享内存结构(`shmem`)、信号量、内存映射

```bash

postgres  1258  1234  0 Aug01 ?  00:00:00 postgres: walwriter
```

### 3. 后台进程 (Background Processes)

| 进程                          | 数量     | 主要职责                                                                 |
|-------------------------------|----------|--------------------------------------------------------------------------|
| **bgwriter (background writer)** | 1    | 后台扫描 shared_buffers,把"较脏"的脏页异步刷回磁盘,减少检查点压力       |
| **checkpointer**              | 1        | 周期性触发**检查点**:把所有脏页刷盘并写一个 checkpoint WAL 记录        |
| **walwriter**                 | 1        | 把 WAL Buffer 中的 WAL 记录刷到磁盘的 `pg_wal/` 目录,保证事务持久化    |
| **autovacuum launcher**       | 1        | 协调者,根据表死元组数量调度 **autovacuum worker** 进程清理               |
| **autovacuum worker**         | 0~N      | 真正执行 VACUUM/ANALYZE 的工作进程                                      |
| **archiver**                  | 0~1      | 把已写满的 WAL 文件归档到指定位置(用于 PITR、流复制)                    |
| **stats collector**           | 1        | 收集每个 backend 的 SQL/IO/连接统计,写入 `pg_stat_*` 视图                |
| **logical replication launcher** | 0~1   | 管理逻辑复制槽(subscription)的 worker 进程                              |
| **WAL receiver**              | 0~N      | 从库专用,通过流复制协议接收主库的 WAL                                   |
| **WAL sender**                | 0~N      | 主库专用,把 WAL 流式发送给从库                                         |
| **syslogger**                 | 0~1      | 把日志收集到一个文件(可选,9.6+ 才有)                                   |

> **注意**:PostgreSQL 没有类似 MySQL 的 `Purge 线程`、`Page Cleaner 线程`等线程,所有后台工作都由上述命名进程完成。每个进程职责单一,非常清晰。

### 4. 后端子进程 (Backend Process)

当客户端发起连接时,`postmaster` 调用 `fork()` 派生一个 `postgres` backend 进程,该进程全程为该连接服务:

- 接收客户端发来的 SQL 文本
- **解析器 → 分析器 → 重写器 → 优化器 → 执行器** 完整流水线
- 读取/修改 `shared_buffers` 中的数据页
- 生成 WAL 记录
- 通过 libpq 协议返回结果集
- 客户端断开后,backend 进程**退出**,资源被回收

**与 MySQL 的本质区别**:

| 维度             | PostgreSQL backend       | MySQL Connection Thread    |
|------------------|--------------------------|----------------------------|
| 进程/线程        | 独立 OS 进程             | 线程(共享 mysqld 进程)     |
| 内存隔离         | 完全独立,故障隔离        | 共享,一个线程崩溃可能影响全局 |
| 上下文切换       | 较重(进程切换)          | 较轻(线程切换)             |
| 创建开销         | 较大(fork)              | 较小(thread create)        |
| 长连接累积       | 单进程占用较稳定         | 长连接易导致内存累积        |
| 高并发短连接     | 较弱(fork 开销大)       | 较弱(需 Thread Pool)       |

### 5. 进程模型 vs MySQL 线程模型对比

| 维度             | PostgreSQL(多进程)       | MySQL(多线程)             |
|------------------|--------------------------|----------------------------|
| **进程/线程**    | 1 postmaster + N backend + M bgproc | 1 mysqld + N thread       |
| **内存共享**     | shared_buffers 共享,每进程私有内存 | 几乎全部共享               |
| **故障隔离**     | 一个 backend 崩溃不影响其他 | 一个线程崩溃可能挂掉整个实例 |
| **大内存占用**   | 1 万连接 = 1 万进程(大)  | 1 万连接 = 1 万线程(共享内存) |
| **CPU 切换成本** | 高(进程切换)            | 低(线程切换)               |
| **配置工具**     | PgBouncer(外部连接池)    | Thread Pool(内置)         |
| **典型上限**     | 几百~几千(无连接池)     | 几千(无线程池)             |

**生产实践**:

- 高并发应用必须前置 **PgBouncer** 或应用层连接池,避免 fork 风暴
- `max_connections` 通常配置为 100-500,而不是 MySQL 常见的数千

## 四、客户端/服务器通信

### 1. 通信协议

PostgreSQL 使用自己设计的**前端/后端协议(Frontend/Backend Protocol)**,这是基于 TCP 的**消息驱动**协议。

**协议特点**:

- 全双工(客户端、服务端可同时发消息)
- 基于消息(message),每条消息有 1 字节类型 + 4 字节长度 + 内容
- 支持 SSL/TLS 加密
- 支持 startup 消息、查询消息、Parse/Bind/Execute(扩展协议)等多种模式

**消息类型概览**:

| 方向       | 消息示例                                | 作用                          |
|------------|------------------------------------------|-------------------------------|
| C → S      | `StartupMessage`                        | 启动连接(带 user/database)    |
| C → S      | `Query`                                 | 简单查询(完整 SQL)            |
| C → S      | `Parse` / `Bind` / `Execute`            | 扩展查询(预处理语句)          |
| S → C      | `AuthenticationOk`                      | 认证成功                      |
| S → C      | `RowDescription`                        | 结果集元数据(列名/类型)       |
| S → C      | `DataRow`                               | 一行数据                      |
| S → C      | `CommandComplete`                       | 命令完成                      |
| S → C      | `ErrorResponse` / `NoticeResponse`      | 错误 / 通知                   |
| 双向       | `CopyData`                              | COPY 命令的批量数据传输       |

**简单查询 vs 扩展查询**:

```sql
-- 简单查询(Query 消息)
SELECT * FROM user WHERE id = 1;

-- 扩展查询(Parse + Bind + Execute 三段)
PREPARE stmt AS SELECT * FROM user WHERE id = $1;
EXECUTE stmt(1);
```

扩展查询支持**预处理语句(Prepared Statement)**、**参数化查询**,性能更好且能避免 SQL 注入。

### 2. 传输方式

| 方式              | 说明                                       |
|-------------------|--------------------------------------------|
| **TCP/IP**        | 默认,远程连接,监听 5432                   |
| **Unix Socket**   | 本机连接,默认 `/var/run/postgresql/.s.PGSQL.5432` |
| **SSL/TLS**       | 加密传输,生产推荐                          |
| **Named Pipe**    | Windows                                     |

### 3. 连接流程

```text
客户端                              服务端(postmaster)
   │                                       │
   │  1. TCP 三次握手                       │
   │ <────────────────────────────────────>│
   │                                       │
   │  2. StartupMessage                     │
   │   - protocol_version (3.0)             │
   │   - user/database/options              │
   │ ────────────────────────────────────> │
   │                                       │  3. 读取 pg_hba.conf
   │                                       │     决定认证方式
   │                                       │     (md5/scram-sha-256/peer...)
   │                                       │
   │  4. AuthenticationXXX                   │
   │ <──────────────────────────────────── │
   │                                       │
   │  5. 密码/认证响应                       │
   │ ────────────────────────────────────> │
   │                                       │  6. fork() 出 backend 进程
   │                                       │     (子进程接管该连接)
   │                                       │
   │  7. AuthenticationOk / ReadyForQuery   │
   │ <──────────────────────────────────── │
   │                                       │
   │  8. Query 消息                         │
   │ ────────────────────────────────────> │
   │                                       │  9. 解析/重写/优化/执行
   │                                       │
   │  10. RowDescription + DataRow...       │
   │ <──────────────────────────────────── │
   │                                       │
   │  11. CommandComplete / ReadyForQuery   │
   │ <──────────────────────────────────── │
```

**关键点**:认证完成后,**postmaster 不再参与通信**,后续该连接的所有消息都由 backend 子进程处理。这是与 MySQL(主线程负责通信、子线程执行)的不同。

### 4. 连接参数与认证

**典型连接命令**:

```bash
psql -h 127.0.0.1 -p 5432 -U postgres -d mydb
```

**关键参数**:

| 参数                          | 说明                                       |
|-------------------------------|--------------------------------------------|
| `listen_addresses`            | 监听地址(默认 `localhost`)                 |
| `port`                        | 监听端口(默认 5432)                       |
| `max_connections`             | 最大连接数(默认 100)                       |
| `superuser_reserved_connections` | 给超级用户保留(默认 3)                   |
| `authentication_timeout`      | 认证超时(秒,默认 60)                      |
| `password_encryption`         | 密码加密方式(`scram-sha-256`/`md5`)        |
| `ssl`                         | 是否启用 SSL(`off`/`on`/`require`)         |

**认证方式**(`pg_hba.conf` 中配置):

| 方式                | 说明                                     |
|---------------------|------------------------------------------|
| `trust`             | 无条件允许(仅本机调试)                  |
| `md5`               | MD5 密码(10 以下版本)                  |
| `scram-sha-256`     | SCRAM 认证(11+ 推荐)                    |
| `peer`              | OS 用户名匹配(Unix Socket 专用)         |
| `ident`             | 通过 ident 服务映射(TCP)               |
| `cert`              | SSL 客户端证书                          |
| `ldap` / `radius`   | 外部认证(需扩展)                       |

```conf
# pg_hba.conf 示例
# TYPE  DATABASE        USER            ADDRESS         METHOD
local   all             postgres                        peer
local   all             all                             scram-sha-256
host    all             all             127.0.0.1/32    scram-sha-256
host    all             all             0.0.0.0/0       scram-sha-256
hostssl all             all             0.0.0.0/0       scram-sha-256
```

## 五、查询处理流程

PostgreSQL 一条 SQL 的完整生命周期:**连接 → 解析 → 分析 → 重写 → 优化 → 执行**。这与 MySQL 的"解析 → 预处理 → 优化 → 执行"略有不同(多了一个独立的**重写阶段**)。

### 1. 五大阶段

```text
┌──────────────────────────────────────────────────────────────────┐
│                          客户端                                  │
│  (psql / JDBC / libpq)                                          │
└────────────────────────┬─────────────────────────────────────────┘
                         │  1. 发送 SQL 文本
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  解析器 (Parser)                                                 │
│  - 词法分析(Lex):SQL → Token 序列                              │
│  - 语法分析(Yacc/Bison):Token → Parse Tree(原始语法树)        │
│  - 输出:Raw Parse Tree                                          │
└────────────────────────┬─────────────────────────────────────────┘
                         │  2. 进入分析阶段
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  分析器 (Analyzer / Semantic Analysis)                           │
│  - 语义检查:表/列是否存在、类型匹配、函数存在性                 │
│  - 名字解析:把 token 转成 OID(表 OID、列 OID 等)              │
│  - 输出:Query Tree(带语义的查询树)                             │
└────────────────────────┬─────────────────────────────────────────┘
                         │  3. 进入重写阶段
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  重写器 (Rewriter / Rule System)                                 │
│  - 应用规则系统(RULES):处理视图、UPDATE 规则、INSTEAD 规则      │
│  - 把视图展开成基表查询                                         │
│  - 应用物化视图(MATVIEW)的重写                                 │
│  - 输出:Rewrite 后的 Query Tree                                 │
└────────────────────────┬─────────────────────────────────────────┘
                         │  4. 进入优化阶段
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  优化器 / 规划器 (Planner / Optimizer)                           │
│  - 逻辑优化:子查询提升、谓词下推、外连接消除                   │
│  - 物理优化:枚举路径(Seq Scan / Index Scan / Hash Join...)      │
│  - 成本估算(CBO):估算每条路径的 I/O + CPU 成本                 │
│  - 选择成本最低的 Plan Tree(执行计划树)                        │
│  - 输出:Plan Tree(嵌套的计划节点)                              │
└────────────────────────┬─────────────────────────────────────────┘
                         │  5. 进入执行阶段
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│  执行器 (Executor) — Volcano / Iterator 模型                    │
│  - 自顶向下 Init / Exec / End 调用每个节点                     │
│  - 每个节点从子节点拉取数据,处理后传给父节点                   │
│  - 触发数据页读取、WAL 写入、锁、MVCC 可见性判断               │
│  - 通过 libpq 协议返回结果集给客户端                            │
└────────────────────────┬─────────────────────────────────────────┘
                         │  6. 结果集回到客户端
                         ↓
┌──────────────────────────────────────────────────────────────────┐
│                          客户端                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 与 MySQL 流程对比

| 阶段         | PostgreSQL                                  | MySQL                            |
|--------------|---------------------------------------------|----------------------------------|
| 词法         | Lex(手写)                                  | Lex                              |
| 语法         | Bison/Yacc → Raw Parse Tree                 | Bison → AST                      |
| 语义分析     | 独立 Analyzer → Query Tree                 | 嵌入 Parser 的 Preprocessor      |
| 重写         | **独立的 Rewriter**(规则/视图展开)         | 查询重写归到 Optimizer            |
| 优化         | Planner(标准 CBO + GEQO 遗传)              | Optimizer(RBO + CBO)             |
| 执行模型     | **Volcano / Pull-based**                    | Iterator + Loop                  |
| 计划表示     | Plan Tree(嵌套节点)                        | EXPLAIN 树(迭代器描述)          |

## 六、解析与重写阶段

### 1. 解析器 (Parser)

PostgreSQL 解析器由 **Lex + Yacc/Bison** 自动生成:

- **`gram.y`**(Bison 语法文件)定义 SQL 文法
- **`scan.l`**(Lex 词法文件)定义词法规则
- 编译生成 `gram.c` 和 `scan.c`,链接进 PostgreSQL 二进制

**词法分析**将 SQL 切成 Token:

```sql
SELECT id, name FROM user WHERE age > 18;
```

| Token 类型    | Token 值     |
|---------------|--------------|
| KEYWORD       | SELECT       |
| IDENTIFIER    | id           |
| PUNCT         | ,            |
| IDENTIFIER    | name         |
| KEYWORD       | FROM         |
| IDENTIFIER    | user         |
| KEYWORD       | WHERE        |
| IDENTIFIER    | age          |
| OPERATOR      | >            |
| ICONST        | 18           |
| PUNCT         | ;            |

**语法分析**生成 **Raw Parse Tree**:

```text
SelectStmt
├── targetList
│   ├── ResTarget: column "id"
│   └── ResTarget: column "name"
├── fromClause
│   └── RangeVar: relation "user"
└── whereClause
    └── A_Expr: >
        ├── column "age"
        └── A_Const: 18
```

> 注意:**PostgreSQL 解析器不区分大小写**(除非用双引号),关键字是大小写不敏感的。

### 2. 分析器 (Analyzer)

分析器对 Raw Parse Tree 做**语义解析**:

- 解析表/列名为**对象标识符(OID)**
- 类型推导与检查
- 函数存在性、参数类型匹配
- 聚合函数、分组、排序的合法性
- 权限粗粒度检查

输出 **Query Tree**:

```text
Query
├── commandType: CMD_SELECT
├── resultRelation: 0
├── targetList:
│   ├── TargetEntry: Var(table=16384, attr=1)  // OID 指向实际对象
│   └── TargetEntry: Var(table=16384, attr=2)
├── fromlist:
│   └── RangeTblRef → Relation OID=16384 (alias "user")
└── jointree:
    └── FromExpr
        ├── fromlist: [user]
        └── quals: OpExpr(Var age > Const 18)
```

### 3. 重写器 (Rewriter)

PostgreSQL 独特的 **Rule System** 在重写阶段应用,**这是 MySQL 没有的独立阶段**。

**重写器职责**:

- **视图展开**:把 `SELECT * FROM v_user` 替换为视图定义的查询
- **UPDATE/DELETE 规则**:用户定义的 `CREATE RULE` 把操作重写为另一操作
- **INSTEAD OF 规则**:把对视图的 INSERT/UPDATE/DELETE 替换为对基表的操作
- **物化视图重写**(11+)

**视图展开示例**:

```sql
CREATE VIEW user_v AS SELECT id, name FROM user WHERE active = true;

-- 用户查询
SELECT * FROM user_v WHERE age > 18;

-- 重写后实际执行的 Query Tree 等价于:
SELECT user.id, user.name FROM user
WHERE user.active = true AND user.age > 18;
```

视图的展开在重写阶段完成,因此优化器看到的就是普通的基表查询,**对优化器透明**。

## 七、优化器 / 规划器 (Planner)

PostgreSQL 的优化器称为 **Planner/Optimizer**,是一个**纯 CBO(基于成本)**的优化器,使用**动态规划**枚举候选路径,选择总成本最低者。

### 1. 成本估算 (CBO)

**成本公式**:

```
Total Cost = (disk pages read) × seq_page_cost
           + (rows scanned)  × cpu_tuple_cost
           + (index entries) × cpu_index_tuple_cost
           + (operators eval)× cpu_operator_cost
```

**关键参数**:

| 参数                          | 默认值 | 说明                              |
|-------------------------------|--------|-----------------------------------|
| `seq_page_cost`               | 1.0    | 顺序读一个页的成本                 |
| `random_page_cost`            | 4.0    | 随机读一个页的成本(SSD 建议调到 1.0-1.5) |
| `cpu_tuple_cost`              | 0.01   | 处理一行数据的 CPU 成本            |
| `cpu_index_tuple_cost`        | 0.005  | 处理一个索引项的 CPU 成本          |
| `cpu_operator_cost`           | 0.0025 | 处理一个操作符的 CPU 成本          |
| `effective_cache_size`        | 4 GB   | 优化器假设的 OS 缓存大小           |

### 2. 路径(Path)

优化器为每个表生成多个**访问路径(Path)**,然后组合、排序、挑最优:

| 路径类型             | 适用场景                              |
|----------------------|---------------------------------------|
| **SeqScan**          | 全表扫描,大表返回大量数据时           |
| **IndexScan**        | B-Tree 等值/范围扫描                  |
| **IndexOnlyScan**    | 索引覆盖扫描(无需回表,Vacuum 后有效) |
| **BitmapIndexScan**  | 多索引组合 + BitmapHeapScan           |
| **TidScan**          | 按 ctid 直接定位                      |
| **FunctionScan**     | 函数返回集合                           |
| **ValuesScan**       | VALUES 子句                           |
| **CTEScan**          | CTE 公用表表达式                      |
| **SubqueryScan**     | 子查询                                |
| **ForeignScan**      | 外部表(fdw)                          |

**Join 路径**:

| Join 方法                | 说明                                   |
|--------------------------|----------------------------------------|
| **Nested Loop Join**     | 嵌套循环,适合小数据集                  |
| **Hash Join**            | 哈希连接,适合大数据集等值连接          |
| **Merge Join**           | 归并连接,要求双方已排序                |

### 3. 计划节点 (Plan Node)

优化器生成的 **Plan Tree** 是一个**由节点(Node)组成的树**,每个节点表示一种操作:

```text
HashAggregate
  → Hash Join (cost=120..180)
       → Seq Scan on orders o  (cost=0..50)
       → Hash
            → Index Scan on users u  (cost=0.01..8.50)
                 Index Cond: (u.id = o.user_id)
```

每个 Plan Node 都有标准的接口:

```cpp
// 节点初始化
ExecInitNode(Plan *node, EState *estate, int eflags);

// 拉取下一行
ExecProcNode(Plan *node);

// 清理
ExecEndNode(Plan *node);
```

### 4. 遗传算法 (GEQO)

当 join 的表数量 ≥ `geqo_threshold`(默认 12)时,Planner 自动启用**遗传算法 GEQO (Genetic Query Optimization)**:

- 枚举所有 join 顺序的排列组合是**阶乘级**爆炸(12! = 479001600)
- 动态规划无法处理,改用**遗传算法**:随机生成初始种群,选择/交叉/变异,迭代 N 代
- `geqo_pool_size`、`geqo_generations` 控制种群大小和迭代代数

```sql
-- 查看 GEQO 配置
SHOW geqo;
SHOW geqo_threshold;  -- 默认 12
SHOW geqo_pool_size;  -- 默认 0(自动)
SHOW geqo_generations;-- 默认 0(自动)
SHOW geqo_effort;     -- 默认 5.0
```

### 5. 查看执行计划

```sql
EXPLAIN SELECT * FROM user WHERE age > 18;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM user WHERE age > 18;  -- 实际执行统计
EXPLAIN (FORMAT JSON) SELECT ...;                              -- JSON 格式
EXPLAIN (FORMAT YAML) SELECT ...;                              -- YAML 格式
```

**EXPLAIN 关键字段**:

| 字段              | 含义                                       |
|-------------------|--------------------------------------------|
| `cost`            | 估算成本(startup..total)                  |
| `rows`            | 估算返回行数                              |
| `width`           | 每行平均字节数                            |
| `actual time`     | (ANALYZE)实际耗时(毫秒)                  |
| `actual rows`     | (ANALYZE)实际返回行数                     |
| `Buffers: shared hit/read` | (BUFFERS)缓冲命中 / 磁盘读         |
| `Planning Time`   | 规划阶段耗时                              |
| `Execution Time`  | 执行阶段耗时                              |

> **核心**:PostgreSQL 的 EXPLAIN 输出与 MySQL 不同,它是**真实的 Plan Tree**,从顶层往下读表示**执行顺序**(子节点先于父节点)。

## 八、执行器 (Executor)

### 1. Volcano 模型(迭代器)

PostgreSQL 采用经典的 **Volcano / Iterator 模型**:

```text
父节点: "给我一行数据"
    ↓
子节点: 返回一行(或 NULL 表示结束)
    ↓
父节点: 处理这行,可能传给上层
    ↓
子节点: 再返回一行
    ...
    ↓
子节点: NULL → 结束
```

**优势**:

- 每个 Plan Node 只需实现 `Init/Exec/End` 三个函数
- 节点组合性强,新算子只要实现接口就能插入
- 支持**流水线(pipeline)**执行,无需物化大量中间结果

### 2. 常用执行节点

| 节点                  | 作用                                       |
|-----------------------|--------------------------------------------|
| **SeqScan**           | 顺序扫描表                                 |
| **IndexScan**         | 索引扫描                                   |
| **IndexOnlyScan**     | 仅扫描索引(可见性映射支持)               |
| **BitmapHeapScan**    | 位图扫描(多索引 OR/AND)                  |
| **NestedLoopJoin**    | 嵌套循环 join                              |
| **HashJoin**          | 哈希 join                                  |
| **MergeJoin**         | 归并 join                                  |
| **Sort**              | 排序节点                                   |
| **HashAggregate**     | 哈希聚合                                   |
| **GroupAggregate**    | 分组聚合                                   |
| **Limit**             | 限制行数                                   |
| **Append**            | 多结果集追加(分区表、UNION)               |
| **Materialize**       | 物化中间结果                               |
| **Unique**            | 去重                                       |
| **LockRows**          | FOR UPDATE 行锁                            |
| **ModifyTable**       | INSERT/UPDATE/DELETE 写                    |
| **Result**            | 常量表达式或单行                           |

### 3. 执行流程示例

```sql
SELECT u.name, COUNT(o.id) AS cnt
FROM users u LEFT JOIN orders o ON u.id = o.user_id
WHERE u.age > 18
GROUP BY u.name
ORDER BY cnt DESC
LIMIT 10;
```

执行计划(典型):

```text
Limit (cost=... rows=10)
  → Sort (cost=... ORDER BY cnt DESC)
       → HashAggregate (cost=... GROUP BY u.name)
            → Hash Left Join (cost=...)
                 Hash Cond: (o.user_id = u.id)
                 → Seq Scan on users u
                      Filter: (age > 18)
                 → Hash
                      → Seq Scan on orders o
```

底层实际执行顺序(从最内层往外):

```text
1. Seq Scan users u  → 过滤 age>18 → 流式输出
2. Seq Scan orders o → 流式输出
3. Hash Join → 把 orders 按 user_id 哈希,流式与 users 拼接
4. HashAggregate → 按 name 分组,累加计数
5. Sort → 按 cnt DESC 排序
6. Limit → 取前 10
```

## 九、内存结构 (Memory Structure)

PostgreSQL 的内存分为**共享内存(shared memory)**和**本地内存(local memory)**两块。

### 1. 共享内存

所有 backend 进程共享,启动时由 postmaster 申请:

| 结构                          | 关键参数                       | 作用                                      |
|-------------------------------|--------------------------------|-------------------------------------------|
| **shared_buffers**            | `shared_buffers` (默认 128MB) | 数据页和索引页的缓冲(类比 InnoDB Buffer Pool) |
| **WAL Buffers**               | `wal_buffers` (默认 16MB)     | WAL 记录预写缓冲                          |
| **CLOG(Commit Log)**          | 内部管理                       | 事务提交状态(xid → committed/aborted)    |
| **Subtrans**                  | 内部管理                       | 子事务状态                                |
| **Multixact**                 | `max_multixact`               | 多事务锁状态(行被多个事务锁)             |
| **Proc Array**                | `max_connections`             | 活跃进程数组,提供快照信息                |
| **Lock Manager**              | `max_locks_per_transaction`  | 锁表                                      |
| **Predicate Locks**           | `max_pred_locks_per_transaction` | SSI(可串行化快照)谓词锁                |
| **Background Worker Slots**   | `max_worker_processes`        | 后台进程槽位                              |

**shared_buffers 推荐配置**:物理内存的 **25%**(OLTP) 至 40%(OLAP/数据仓库)。MySQL 的 Buffer Pool 推荐 50-70%,两者定位不同 —— PostgreSQL 依赖 OS 文件缓存更多,所以 shared_buffers 不需要太大。

### 2. 本地内存 (Local Memory)

每个 backend 进程独立分配的内存:

| 结构                          | 关键参数                       | 作用                                  |
|-------------------------------|--------------------------------|---------------------------------------|
| **work_mem**                  | `work_mem`(默认 4MB)           | 排序、哈希聚合、Hash Join 使用的内存  |
| **maintenance_work_mem**      | `maintenance_work_mem`(默认 64MB) | VACUUM、CREATE INDEX、ALTER TABLE 内存 |
| **temp_buffers**              | `temp_buffers`(默认 8MB)       | 临时表缓冲                            |
| **memory for query execution**| -                              | 执行器节点私有(Hash 表、Sort 等)     |
| **catalog cache**             | -                              | 系统表缓存(每个 backend 私有)        |
| **plan cache**                | -                              | 预处理语句的 plan 缓存(每个 backend) |

**work_mem 注意事项**:

- 是**每个操作**的内存上限,不是每个查询的总内存
- 一个复杂查询可能有多个 Sort/Hash 同时进行,实际占用 = `work_mem × 操作数 × 并发`
- 推荐值:512MB~2GB(根据并发数调整),但**慎用过大值**(易 OOM)

```sql
-- 查看当前会话的内存配置
SHOW work_mem;
SHOW maintenance_work_mem;
SHOW temp_buffers;
```

### 3. 内存使用建议

| 参数                          | 推荐范围                | 说明                                |
|-------------------------------|-------------------------|-------------------------------------|
| `shared_buffers`              | 物理内存 25-40%         | 不宜过大,否则 checkpoint 压力       |
| `work_mem`                    | 32MB-2GB               | 与并发数成反比                      |
| `maintenance_work_mem`        | 256MB-2GB              | 大表 VACUUM/索引重建需要大           |
| `effective_cache_size`        | 物理内存 50-75%         | 优化器假设的 OS 缓存                |
| `wal_buffers`                 | 16MB-64MB              | 高写入场景调大                      |

## 十、物理文件结构 (Physical File Structure)

PostgreSQL 把数据存储在一个**集群(Cluster)**中,默认目录(也称 `PGDATA`)包含多个子目录。

```bash
# 查看数据目录
SHOW data_directory;
# 默认: /var/lib/postgresql/16/main
```

### 1. 目录结构

```text
PGDATA/
├── base/                  # 各数据库的数据文件(按 oid 组织)
│   ├── 1/                 # template1 数据

│   │   ├── 16385          # 表 mydb.users 的数据文件
│   │   ├── 16386          # 索引文件
│   │   └── ...
│   └── ...
├── global/                # 集群级系统表(pg_database、pg_authid 等)
│   ├── pg_database
│   ├── pg_authid
│   └── ...
├── pg_wal/                # WAL 日志(16 及之前叫 pg_xlog)
│   ├── 000000010000000000000001
│   └── ...
├── pg_xact/               # 事务提交状态(CLOG)
│   ├── 0000
│   └── ...
├── pg_stat/               # 统计信息持久化
│   ├── db_16384.stat
│   └── ...
```

### 2. 关键目录详解

| 目录              | 作用                                                              |
|-------------------|-------------------------------------------------------------------|
| `base/<oid>/`     | 每个数据库对应一个子目录,文件名是表的 `relfilenode`(oid)         |
| `global/`         | 集群共享系统表(如 `pg_database`、`pg_authid`)                  |
| `pg_wal/`         | WAL 日志文件,默认 16MB/个,循环使用                              |
| `pg_xact/`        | CLOG(事务提交日志),每个文件记录 32K 个事务状态                 |
| `pg_stat/`        | 统计信息收集器的持久化数据,重启后恢复                            |
| `pg_multixact/`   | 多事务共享锁的状态(members/offsets)                              |
| `pg_subtrans/`    | 子事务的提交状态                                                  |
| `pg_logical/`     | 逻辑解码的快照和映射                                              |
| `pg_serial/`      | SERIALIZABLE 隔离级别的序列化冲突检测                            |
| `pg_replslot/`    | 主从复制槽的状态                                                  |

### 3. 单个表在文件系统的存储

每个表(以及索引)对应 **base/<db_oid>/<relfilenode>** 中的一个或多个文件:

- 文件名是**表的 relfilenode**(默认等于 oid,某些操作后会改变)
- 单文件最大 **1GB**(超出会自动创建同名 + `.1`、`.2` 的分片文件)
- 每个文件由多个 **8KB 的页(block)** 组成

```text
base/16384/
└── 16385                    # 表 mydb.users 的第一个 1GB
└── 16385.1                  # 第二个 1GB
└── 16386                    # 索引 idx_users_name
```

## 十一、表和索引的物理结构 (Page Structure)

PostgreSQL 的数据页默认大小是 **8KB**(编译时可配为 4/16/32KB,9.0+ 支持更大)。这是 PostgreSQL 与 MySQL InnoDB(默认 16KB)的关键差异。

### 1. 页(Heap Page)结构

```text
┌──────────────────────────────────────────────────────┐
│                Page (8 KB, 8192 bytes)               │
├──────────────────────────────────────────────────────┤
│  PageHeaderData            │  24 bytes               │
│   - pd_lsn                                        │
│   - pd_checksum                                    │
│   - pd_flags                                       │
│   - pd_lower                                       │
│   - pd_upper                                       │
│   - pd_special                                     │
│   - pd_pagesize_version                            │
├──────────────────────────────────────────────────────┤
│  ItemIdData (Item Pointers) │  每行 4 bytes         │
│   - lp_off   : 指向 HeapTuple 的偏移               │
│   - lp_flags : 状态(used/unused/redirect/dead)      │
│   - lp_len   : tuple 长度                          │
├──────────────────────────────────────────────────────┤
│  Free Space                                      ↕ │
│  (空闲空间,用于插入新 tuple)                        │
├──────────────────────────────────────────────────────┤
│  HeapTuple(s)                                     │
│   - HeapTupleHeaderData (23 bytes)                  │
│     · t_xmin  (插入事务 ID)                        │
│     · t_xmax  (删除/更新事务 ID)                   │
│     · t_cid   (命令 ID)                           │
│     · t_ctid  (物理位置, block+offset)            │
│     · t_infomask2 (属性数量 + 标志)                │
│     · t_infomask  (16 位状态位)                   │
│     · t_hoff   (数据起始偏移)                      │
│   - NullBitmap (可选,如果有 NULL 列)              │
│   - User Data (用户数据,字段值)                   │
│   - Optional OID (可选)                            │
├──────────────────────────────────────────────────────┤
│  Special Space (索引页专用,Heap 页留空)             │
└──────────────────────────────────────────────────────┘
```

**关键指针**:

- **`pd_lower`**:Item Pointer 数组结束位置
- **`pd_upper`**:Heap Tuple 结束位置
- **Free Space**:`pd_upper` 与 `pd_lower` 之间

### 2. Tuple Header 详解 (HeapTupleHeaderData)

每个 Heap Tuple 的前 **23 字节** 是 Tuple Header,这是 PostgreSQL MVCC 的关键:

| 字段         | 大小   | 含义                                                                 |
|--------------|--------|----------------------------------------------------------------------|
| `t_xmin`     | 4 bytes | **插入此 tuple 的事务 ID**(`0` 表示无效)                             |
| `t_xmax`     | 4 bytes | **删除/更新此 tuple 的事务 ID**(`0` 表示未被删除)                   |
| `t_cid`      | 4 bytes | 命令 ID(在事务内多条 SQL 之间的标识)                                 |
| `t_ctid`     | 6 bytes | **当前版本的位置**(`(block_number, item_pointer)`),UPDATE 后会指向新版本 |
| `t_infomask2`| 2 bytes | 属性数量 + 标志位                                                    |
| `t_infomask` | 2 bytes | **16 位状态标志**(见下表)                                          |
| `t_hoff`     | 1 byte  | 用户数据起始偏移(对齐到 MAXALIGN)                                   |

**t_infomask 标志位**(节选):

| 位掩码            | 含义                                              |
|-------------------|---------------------------------------------------|
| `HEAP_HASNULL`    | 该 tuple 含有 NULL 列                              |
| `HEAP_HASVARWIDTH`| 含变长字段                                        |
| `HEAP_HASOID`     | 含 OID 列                                         |
| `HEAP_XMIN_COMMITTED`  | 插入事务已提交(可由 hint bit 加速可见性)   |
| `HEAP_XMIN_INVALID`    | 插入事务已回滚(本 tuple 不存在)             |
| `HEAP_XMAX_COMMITTED`  | 删除事务已提交                              |
| `HEAP_XMAX_INVALID`    | 删除事务已回滚                              |
| `HEAP_UPDATED`        | 该 tuple 已被 UPDATE(旧版本)                |
| `HEAP_MOVED_OFF` / `HEAP_MOVED_IN` | 跨页迁移(老版本)              |

**MVCC 工作原理**(极简版):

```text
会话 A (xid=100) 执行 UPDATE:
  1. 在原 tuple 上设置 t_xmax = 100
  2. 插入新 tuple,设置 t_xmin = 100, t_ctid 指向新位置
  3. 旧 tuple 不会立即删除(死元组),由 VACUUM 回收
```

### 3. 页的填充与空闲空间

- 表的填充因子 `fillfactor` 控制 INSERT 时页保留多少空闲空间
- 默认 100(不留),频繁 UPDATE 的表建议 **70-90**
- 空闲空间不足时,会触发 **page split(页面分裂)** 或扩展新页

```sql
CREATE TABLE hot_table (
  id INT,
  data TEXT
) WITH (fillfactor = 70);
```

## 十二、TOAST (大字段存储机制)

**TOAST (The Oversized-Attribute Storage Technique)** 是 PostgreSQL 处理大字段(超过页大小 1/4 的字段)的机制。

### 1. 触发条件

- 字段长度超过 **~2KB**(单页 8KB 的 1/4)
- 包括 `TEXT`、`VARCHAR`、`BYTEA`、`JSON`、`JSONB`(可能)、数组等

### 2. TOAST 策略

| 策略                | 说明                                                  |
|---------------------|-------------------------------------------------------|
| `PLAIN`             | 不支持 TOAST(只对定长字段有效)                       |
| `EXTENDED`          | 先尝试压缩,压缩后仍超大则用 EXTERNAL(默认)          |
| `EXTERNAL`**        | 不压缩,直接外挂(允许脱离行存)                       |
| `MAIN`              | 先尝试压缩,压缩后仍超大才外挂(行尽量保持完整)       |

```sql
-- 查看 TOAST 策略
SELECT attname, attstorage
FROM pg_attribute
WHERE attrelid = 'mytab'::regclass;
-- 'p' = PLAIN, 'e' = EXTERNAL, 'm' = MAIN, 'x' = EXTENDED

-- 修改策略
ALTER TABLE mytab ALTER COLUMN content SET STORAGE EXTENDED;
```

### 3. TOAST 表

当字段触发 TOAST 时,PostgreSQL 自动创建一个**配套 TOAST 表**:

```text
base/16384/
├── 16385                # 主表 mydb.users
└── 16394                # pg_toast.pg_toast_16385(关联表的 OID)
    └── toast_16385_data    # 实际数据(行 chunk 大小通常 2KB)
```

- TOAST 表有自己的 **TOAST 索引**(chunk_id + sequence_no 唯一)
- 读大字段时,先读主表 → 通过 chunk_id 找 TOAST 表 → 顺序读所有 chunk 拼装

## 十三、PostgreSQL 与 MySQL 架构对比

| 维度                | PostgreSQL                                  | MySQL                                |
|---------------------|---------------------------------------------|--------------------------------------|
| **进程模型**        | 多进程(postmaster + backend)               | 多线程(mysqld 单进程)               |
| **存储引擎**        | 单一 Heap/MVCC(不可插拔)                  | 可插拔(InnoDB/MyISAM 等)            |
| **SQL 标准**        | 高度兼容(几乎全 SQL)                       | 部分兼容(有扩展语法)                |
| **MVCC**            | Heap 多版本 + t_xmin/t_xmax                | Undo Log + ReadView                  |
| **更新机制**        | 写新版本(同表)+ 旧版本 GC 由 VACUUM 回收 | 原地更新 + Undo Log 旧版本          |
| **事务隔离**        | 默认 **Read Committed**,支持 **SSI**      | 默认 **Repeatable Read**(InnoDB)    |
| **DDL 事务**        | 支持(CREATE INDEX 等可在事务中回滚)      | 不支持(隐式提交)                    |
| **表/索引组织**     | Heap(行无序,聚簇索引可选)                | 聚簇索引(InnoDB 主键组织)          |
| **页大小**          | 8KB(默认,可配)                           | 16KB(InnoDB)                        |
| **大字段**          | TOAST(外挂压缩)                           | Antelope/Barracuda(行溢出)         |
| **优化器**          | CBO + GEQO 遗传                            | RBO + CBO                            |
| **执行模型**        | Volcano/Iterator(Pull)                    | Iterator + Loop(混)                |
| **扩展能力**        | 极强(用户自定义类型/索引/函数/操作符)    | 较弱(主要是插件式引擎)            |
| **预写日志**        | WAL (XLog)                                 | Redo Log + Binlog(两套)            |
| **连接池**          | 外部(PgBouncer / 应用层)                 | 内置 Thread Pool                    |
| **典型适用**        | 复杂查询、事务严格、数据仓库、GIS       | OLTP 高并发、Web 应用               |

**架构哲学差异**:

- **MySQL**:**实用主义优先**,通过可插拔引擎给用户选择空间,优化常见路径(InnoDB),追求单节点极致性能。
- **PostgreSQL**:**学术派血统**(POSTGRES 项目源自学术研究),追求**SQL 标准完整性**、**功能完备性**、**可扩展性**,宁可牺牲一些性能换取正确性。

## 十四、核心要点速记

- **架构层次**:客户端 → 服务端进程(postmaster/backend/bg) → 共享内存 → 文件系统
- **多进程模型**:`postmaster` 是主进程,每客户端连接 fork 一个 backend,**MySQL 是单进程多线程**
- **postmaster 职责**:监听端口、认证、fork backend、管理后台进程、信号处理
- **后台进程**:bgwriter(刷脏)、checkpointer(检查点)、walwriter(WAL)、autovacuum、archiver、stats、logical replication
- **backend 职责**:完整 SQL 流水线(解析 → 分析 → 重写 → 优化 → 执行)
- **通信协议**:前端/后端消息协议,基于 TCP,全双工,支持简单查询与扩展查询
- **解析阶段**:Lex + Bison/Yacc → Raw Parse Tree
- **分析阶段**:语义解析、OID 映射 → Query Tree
- **重写阶段**:**PostgreSQL 独有的独立阶段**,处理视图/规则/物化视图展开
- **优化器**:CBO(成本)+ 动态规划 + GEQO 遗传算法(>12 表)
- **执行器**:Volcano / Pull-based / Iterator 模型,Plan Node 嵌套
- **共享内存**:`shared_buffers`(数据页)、`wal_buffers`(WAL)、Proc Array、Lock Manager
- **本地内存**:`work_mem`(排序/哈希,操作级)、`maintenance_work_mem`、`temp_buffers`
- **物理文件**:`base/<db_oid>/<relfilenode>`、`pg_wal/`、`pg_xact/`、`global/` 等子目录
- **页大小**:默认 **8KB**(可配 4/16/32KB),由 Page Header + Item Pointers + Free Space + Heap Tuples 组成
- **Tuple Header**:`t_xmin`、`t_xmax`、`t_ctid`、`t_infomask`(23 字节)是 MVCC 关键
- **MVCC**:UPDATE 写新版本 + 旧版本 GC(由 VACUUM 处理),**不依赖 Undo Log**(这是与 InnoDB 最大区别)
- **TOAST**:大字段(>2KB)自动外挂到 TOAST 表,支持压缩和切块
- **GEQO**:join 表数 ≥ `geqo_threshold`(默认 12)启用遗传算法
- **EXPLAIN**:输出 Plan Tree,真实执行顺序自底向上,与 MySQL 的树形展示不同
- **对比 MySQL**:多进程 vs 多线程、单一引擎 vs 可插拔、MVCC 实现机制不同(Heap 多版本 vs Undo Log)
- **生产实践**:高并发必须用 PgBouncer(避免 fork 风暴),`shared_buffers` 设为物理内存 25-40%,`work_mem` 根据并发调整
