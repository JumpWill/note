# PostgreSQL 高可用架构 (PostgreSQL High Availability)

## 一、高可用概述

### 1. 什么是高可用

**HA (High Availability)** — 系统在长时间内持续提供服务的能力。

**核心指标**:

| 指标 | 含义 | 衡量 |
|------|------|------|
| **RTO** | Recovery Time Objective | 故障到恢复的时间 (恢复速度) |
| **RPO** | Recovery Point Objective | 可容忍的数据丢失量 (数据安全性) |
| **SLA** | Service Level Agreement | 服务等级承诺 (99.9% / 99.99% / 99.999%) |

**可用性等级**:

```text
可用性 99.9% → 每月停机 ≤ 43.2 分钟
可用性 99.99% → 每月停机 ≤ 4.32 分钟 (4 个 9)
可用性 99.999% → 每月停机 ≤ 25.9 秒 (5 个 9)
```

### 2. PostgreSQL HA 的特殊性

- **同步 vs 异步复制**: PG 原生支持,关键配置 `synchronous_commit`
- **不自带故障转移**: PG 本身不提供自动选主,需要外部工具 (Patroni、Repmgr)
- **依赖外部协调服务**: DCS (etcd / Zookeeper / Consul)
- **复制槽 (Replication Slot)**: 防 WAL 提前删除的关键机制

### 3. PG HA 方案演进

```text
手动主从 (基础)
   ↓
自动主从 + 故障检测 (Keepalived + VIP)
   ↓
流复制 + 自动故障转移 (Repmgr)
   ↓
DCS + Patroni (业界标准)
   ↓
官方 pg_auto_failover (PG 14+, 集成度高)
   ↓
云原生方案 (Aurora、Citus、Patroni + Operator)
```

## 二、HA 方案对比

### 主流方案横向对比

| 方案 | 一致性 | 自动切换 | RPO | 复杂度 | 适用规模 | 推荐度 |
|------|--------|----------|-----|--------|----------|--------|
| Keepalived + VIP | 异步 | 是 (秒级) | 秒级 | 低 | 中小 | ⭐⭐⭐ |
| 流复制 + 脚本 | 异步/同步 | 需自己写 | 0-秒级 | 中 | 中小 | ⭐⭐ |
| Repmgr | 异步/同步 | 是 | 0-秒级 | 中 | 中 | ⭐⭐⭐ |
| **Patroni** | 异步/同步 | 是 (秒级) | 0-秒级 | 高 | **大** | ⭐⭐⭐⭐⭐ |
| pg_auto_failover | 异步/同步 | 是 (秒级) | 0-秒级 | 中 | 中大 | ⭐⭐⭐⭐ |
| AWS RDS Multi-AZ | 同步 | 是 | 0 | 低 | 中大 | ⭐⭐⭐⭐ |
| Aurora / Citus | 同步 | 是 | 0 | 高 | 超大 | ⭐⭐⭐⭐⭐ |

### 各方案核心取舍

- **Patroni**: 灵活、生态丰富、社区活跃,但配置复杂
- **Repmgr**: 简单、纯 PG 工具,但功能有限
- **pg_auto_failover**: 官方、集成度高,但相比 Patroni 灵活性差
- **云 RDS**: 零运维,但锁定云厂商

## 三、Patroni (业界标准)

### 1. 架构总览

```text
┌──────────────────────────────────────────────────┐
│                  etcd Cluster (3 节点)            │
│   - Leader 锁存储                                 │
│   - 节点健康状态                                  │
│   - 配置信息                                       │
└──────────────┬───────────────────────────────────┘
               │ HTTP API
   ┌───────────┼───────────┐
   ↓           ↓           ↓
┌────────┐ ┌────────┐ ┌────────┐
│PG Node1│ │PG Node2│ │PG Node3│  ← Patroni 进程管理 PG
│(Master)│ │(Standby│ │(Standby│
└────┬───┘ └────┬───┘ └────┬───┘
     │           │           │
     └───────────┴───────────┘
              ↓
   ┌────────────────────┐
   │ HAProxy + PgBouncer│  ← 入口层 (VIP 可选)
   │   - 读写分离        │
   │   - 健康检查        │
   └────────────────────┘
```

### 2. Patroni 工作原理

- **Leader 选举**: 启动时所有节点向 etcd 抢 leader 锁
- **健康检查**: Patroni 进程监控本地 PG,定期更新 TTL
- **故障检测**: 当 master 的 TTL 过期 (默认 30s),etcd 触发选主
- **自动提升**: standby 节点通过 `pg_ctl promote` 提升为新主
- **配置同步**: DCS 中的 leader 节点配置被新主接管

### 3. Patroni 关键概念

| 术语 | 含义 |
|------|------|
| **DCS** | Distributed Configuration Store (etcd/Consul/ZK) |
| **TTL** | Time To Live, 节点健康状态过期时间 |
| **loop_wait** | 健康检查间隔 (默认 10s) |
| **retry_timeout** | 重试超时 (默认 10s) |
| **master_start_timeout** | 主启动超时 |
| **synchronous_mode** | 同步/异步模式 |

### 4. 完整部署步骤

#### 4.1 etcd 集群 (3 节点)

```bash
# 在每台机器上
ETCD_NAME=etcd1
ETCD_LISTEN_CLIENT_URLS=http://0.0.0.0:2379
ETCD_ADVERTISE_CLIENT_URLS=http://10.0.0.1:2379
ETCD_LISTEN_PEER_URLS=http://0.0.0.0:2380
ETCD_INITIAL_ADVERTISE_PEER_URLS=http://10.0.0.1:2380
ETCD_INITIAL_CLUSTER=etcd1=http://10.0.0.1:2380,etcd2=http://10.0.0.2:2380,etcd3=http://10.0.0.3:2380

etcd --name $ETCD_NAME \
     --listen-client-urls $ETCD_LISTEN_CLIENT_URLS \
     --advertise-client-urls $ETCD_ADVERTISE_CLIENT_URLS \
     --listen-peer-urls $ETCD_LISTEN_PEER_URLS \
     --initial-advertise-peer-urls $ETCD_INITIAL_ADVERTISE_PEER_URLS \
     --initial-cluster $ETCD_INITIAL_CLUSTER \
     --initial-cluster-token etcd-cluster-1 \
     --initial-cluster-state new
```

#### 4.5 启动 Patroni

```bash

# 节点 2、3 (加入集群)

# 查看集群状态
patronictl -c /etc/patroni.yml list
```

#### 4.6 故障切换测试

```bash
# 模拟 master 宕机
systemctl stop patroni  # 在 master 上

# 观察自动切换 (30s 内完成)
patronictl -c /etc/patroni.yml list
```

### 5. Patroni 常用命令

```bash
# 查看集群状态
patronictl -c /etc/patroni.yml list

# 手动切换 (switchover)
patronictl -c /etc/patroni.yml switchover --master pg-node1 --candidate pg-node2

# 故障转移 (failover, 强制)
patronictl -c /etc/patroni.yml failover --master pg-node1 --candidate pg-node2 --force

# 重启集群
patronictl -c /etc/patroni.yml restart pg-cluster

# 重新初始化 (慎用,会清空数据)
patronictl -c /etc/patroni.yml reinit pg-cluster pg-node3

# 编辑配置
patronictl -c /etc/patroni.yml edit-config
```

## 四、HAProxy + PgBouncer 入口层

### 1. HAProxy 配置

```haproxy
global
    maxconn 1000

defaults
    mode tcp
    log global
    option tcplog
    timeout connect 10s
    timeout client 1h
    timeout server 1h

# 主库读端点 (写)
listen pg_master
    bind *:5000
    option httpchk GET /master
    http-check expect status 200
    default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions
    server pg-node1 10.0.0.1:5432 check port 8008
    server pg-node2 10.0.0.2:5432 check port 8008
    server pg-node3 10.0.0.3:5432 check port 8008

# 从库读端点 (读)
listen pg_replicas
    bind *:5001
    balance roundrobin
    option httpchk GET /replica
    http-check expect status 200
    default-server inter 3s fall 3 rise 2
    server pg-node1 10.0.0.1:5432 check port 8008
    server pg-node2 10.0.0.2:5432 check port 8008
    server pg-node3 10.0.0.3:5432 check port 8008

# 统计页面
listen stats
    bind *:7000
    mode http
    stats enable
    stats uri /
```

### 2. PgBouncer 配置

```ini
[databases]
mydb = host=127.0.0.1 port=5000 dbname=mydb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

# 三种池模式
pool_mode = transaction

# 连接池大小
default_pool_size = 20
max_client_conn = 1000
reserve_pool_size = 5

# 超时
server_idle_timeout = 600
client_idle_timeout = 0
query_timeout = 0
query_wait_timeout = 120

# 日志
log_connections = 1
log_disconnections = 1
log_pooler_errors = 1
```

**userlist.txt**:

```text
"postgres" "md5xxxxxxx"
"appuser" "md5yyyyyyy"
```

### 3. 客户端连接

```python
# 写入走 5000 端口
master_dsn = "postgresql://appuser:password@10.0.0.10:5000/mydb"

# 读取走 5001 端口 (可负载均衡到多个 standby)
replica_dsn = "postgresql://appuser:password@10.0.0.10:5001/mydb"

# 或经 PgBouncer
pooled_dsn = "postgresql://appuser:password@10.0.0.10:6432/mydb"
```

## 五、Repmgr

### 1. 架构

```text
Repmgr = PostgreSQL 流复制 + 自动故障转移工具
- 主节点 + 多个 standby
- 通过 repmgrd 守护进程监控
- 元数据存储在 repmgr schema 中
```

### 2. 安装与配置

```bash
apt install postgresql-16-repmgr
```

`repmgr.conf`:

```ini
node_id = 1
node_name = 'pg-node1'
conninfo = 'host=10.0.0.1 user=repmgr dbname=repmgr connect_timeout=2'
data_directory = '/var/lib/postgresql/16/main'

pg_bindir = '/usr/lib/postgresql/16/bin'

# 监控间隔
monitor_interval_secs = 2
# 故障检测阈值
reconnect_attempts = 6
reconnect_interval = 10

# 故障转移配置
failover = automatic
promote_command = '/usr/bin/repmgr standby promote -f /etc/repmgr.conf --log-to-file'
follow_command = '/usr/bin/repmgr standby follow -f /etc/repmgr.conf --log-to-file --upstream-node-id=%n'
```

### 3. 集群注册

```bash
# 主节点
repmgr primary register

# 从节点
repmgr standby register

# 查看集群状态
repmgr cluster show
```

### 4. Patroni vs Repmgr 对比

| 维度 | Patroni | Repmgr |
|------|---------|--------|
| 协调服务 | 必须 (etcd/Consul/ZK) | 不需要 |
| 复杂度 | 高 | 中 |
| 自动切换 | 是 (秒级) | 是 (秒级) |
| 切换 RPO | 0 | 0 |
| 社区活跃 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 与云集成 | 良好 (Operator) | 一般 |
| 学习曲线 | 陡 | 中等 |

## 六、pg_auto_failover (官方方案, PG 14+)

### 1. 架构

```text
┌─────────────────┐
│   pg_autoctl    │  (一个进程, 内含 Monitor + Agent)
└─────────────────┘
        ↓
┌─────────────────┐         ┌──────────────┐
│  Monitor Node   │ ←─HTTP─→│ Primary Node │
│  (状态协调)     │         │ (主)         │
└─────────────────┘         └──────────────┘
        │
        ↓
   ┌─────────────────┐
   │ Secondary Node  │
   │ (备, 可多个)    │
   └─────────────────┘
```

### 2. 工作流程

```text
1. Monitor 节点监控所有 PG 节点
2. Primary 节点心跳停止 → Monitor 检测
3. Monitor 启动选主流程
4. 候选节点争抢锁
5. 获胜候选节点调用 pg_ctl promote
6. 通知客户端新主
```

### 3. 部署

```bash
# 安装 (PG 16+)
apt install postgresql-16-auto-failover

# 创建 monitor 节点
pg_autoctl create monitor \
    --pgdata /var/lib/postgresql/monitor \
    --hostname 10.0.0.1 \
    --pgport 5432

# 创建 primary
pg_autoctl create postgres \
    --pgdata /var/lib/postgresql/main \
    --hostname 10.0.0.2 \
    --pgport 5432 \
    --monitor 'postgres://autoctl_node@10.0.0.1:5432/pg_auto_failover' \
    --formation default

# 添加 secondary
pg_autoctl create postgres \
    --pgdata /var/lib/postgresql/main \
    --hostname 10.0.0.3 \
    --pgport 5432 \
    --monitor 'postgres://autoctl_node@10.0.0.1:5432/pg_auto_failover' \
    --formation default \
    --secondary
```

### 4. 查看状态

```bash
pg_autoctl show state
pg_autoctl show events
pg_autoctl perform switchover
```

### 5. Patroni vs pg_auto_failover 对比

| 维度 | Patroni | pg_auto_failover |
|------|---------|------------------|
| 协调依赖 | 外部 etcd 等 | 内置 Monitor |
| 部署复杂度 | 高 | 中 |
| 切换速度 | 秒级 | 秒级 |
| 灵活性 | 极高 (自定义 callbacks) | 一般 |
| 适用 | 复杂生产环境 | 中等复杂 |

## 七、PgBouncer 连接池

### 1. 三种池模式对比

| 模式 | 复用范围 | 适用场景 | 注意点 |
|------|----------|----------|--------|
| **session** | 一个会话内复用 | 需 prepared statement、长事务 | 默认模式 |
| **transaction** | 一个事务内复用 | **最常用** 短事务、OLTP | 不支持跨事务 prepared statement |
| **statement** | 一条语句复用 | 极端场景 | 不支持事务 |

### 2. 关键配置

```ini
pool_mode = transaction
default_pool_size = 20           # 每个 (user,db) 池大小
max_client_conn = 1000           # 最大客户端连接
reserve_pool_size = 5            # 紧急预留
reserve_pool_timeout = 3

# 超时
server_idle_timeout = 600
client_idle_timeout = 0
query_timeout = 0                # 0 = 不限
query_wait_timeout = 120         # 客户端等连接超时

# 监控
stats_period = 60
```

### 3. PgBouncer 监控

```sql
-- 连接池状态
SHOW POOLS;
SHOW STATS;
SHOW SERVERS;
```

## 八、Pgpool-II

### 1. 特性

- **连接池**: 内置连接池
- **负载均衡**: 读负载均衡到 standby
- **自动故障检测**: watchdog 机制
- **查询缓存**: 内存级结果缓存
- **复制 / 高可用**: 与流复制集成

### 2. 与 PgBouncer 对比

| 维度 | PgBouncer | Pgpool-II |
|------|-----------|-----------|
| 资源占用 | 极小 (~MB) | 较大 (~100MB) |
| 连接池 | ✓ | ✓ |
| 负载均衡 | ✗ | ✓ |
| 故障检测 | ✗ | ✓ (watchdog) |
| 查询缓存 | ✗ | ✓ |
| 在线恢复 | ✗ | ✓ |
| 复杂度 | 低 | 高 |

**生产建议**: **PgBouncer + Patroni + HAProxy** 组合比 Pgpool-II 更主流。

## 九、Keepalived + VIP (传统方案)

### 1. 原理

```text
┌──────────────┐         ┌──────────────┐
│  Master      │         │  Standby     │
│  PG + VIP    │ ←VRRP→  │  PG          │
│  (10.0.0.100)│         │              │
└──────────────┘         └──────────────┘
       │                       │
       └────── 故障时 VIP 漂移 ─┘
```

### 2. 配置

`keepalived.conf`:

```nginx
vrrp_script check_pg {
    script "/usr/local/bin/check_pg.sh"
    interval 2
    weight -20
    fall 3
    rise 2
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass yourpassword
    }

    virtual_ipaddress {
        10.0.0.100/24
    }

    track_script {
        check_pg
    }
}
```

`check_pg.sh`:

```bash
#!/bin/bash
# 检查 PG 是否运行
pg_isready -h 127.0.0.1 -p 5432 || exit 1
exit 0
```

### 3. 缺点

- 仅 IP 漂移, 不感知数据一致性
- 脑裂风险 (split-brain)
- 切换慢, 需人工或脚本配合

## 十、云数据库方案

### 1. AWS RDS for PostgreSQL

- Multi-AZ: 同步复制到另一个 AZ, 自动故障转移
- Read Replica: 跨区域异步复制, 用于读扩展
- Aurora PostgreSQL: 6 副本 + 自研存储层, RPO=0, RTO < 30s

### 2. 阿里云 RDS

- 主备双节点: 同步复制, 自动切换
- 只读实例: 异步复制, 适合读扩展
- PolarDB: 计算存储分离, 兼容 PG

### 3. Azure Database for PostgreSQL

- Flexible Server: 高可用 + 主备切换
- Hyperscale (Citus): 分布式扩展

### 4. 自建 vs 云 DB 对比

| 维度 | 自建 Patroni | 云 RDS |
|------|--------------|--------|
| 运维成本 | 高 | 低 |
| 灵活性 | 高 | 低 |
| 成本 | 低 (大规模时) | 高 |
| SLA | 取决于自己 | 厂商承诺 |
| 锁定 | 无 | 锁定云厂商 |

## 十一、故障转移演练

### 1. 演练流程

```text
1. 准备: 业务低峰期, 通知相关方
2. 制造故障: 停止 master 上的 PG 或 Patroni
3. 观察切换: 等待 30-60s, 检查 HAProxy 健康状态
4. 验证新主: 写入数据, 验证可读写
5. 旧主恢复: 重新加入集群作为 standby
6. 业务恢复: 应用自动重连, 流量恢复
7. 记录: 切换时间、RPO、数据一致性
```

### 2. 监控指标

- **切换时间**: master 失联到新主提供服务的总时间
- **数据丢失量**: WAL 同步延迟 × 切换时间
- **应用重连时间**: 应用连接池刷新 + 业务恢复时间

## 十二、监控与告警

### 1. Patroni REST API

```bash
# 健康状态
```

### 2. 关键告警项

| 指标 | 告警阈值 |
|------|----------|
| Master 不可达 | 30s 内 |
| Standby 复制延迟 | > 1MB |
| Replication Slot 积压 | > 1GB |
| DCS 不可用 | 立即 |
| HAProxy 健康检查失败 | > 3 次 |
| PgBouncer 连接耗尽 | > 90% |

## 十三、选型决策树

```text
是否在云上?
  ├─ 是 → 云 RDS / Aurora / PolarDB
  └─ 否 → 团队规模?
        ├─ 小团队 (< 5 人) → pg_auto_failover (简单)
        ├─ 中等团队 → Repmgr (中等复杂度)
        └─ 大团队 / 关键业务 → Patroni + etcd + HAProxy + PgBouncer
```

## 十四、核心要点速记

- **HA 三大支柱**: RTO (恢复时间) + RPO (数据丢失) + SLA (可用性)
- **PG 不自带故障转移**, 必须借助外部工具 (Patroni/Repmgr/pg_auto_failover)
- **Patroni 是业界标准**: 灵活但复杂, 依赖 DCS (etcd/Consul/ZK)
- **pg_auto_failover 是官方方案**: PG 14+, 集成度高, 中等复杂
- **Repmgr**: 简单、纯 PG 工具, 适合中等业务
- **DCS 必须 ≥ 3 节点 (奇数)**: 防止脑裂
- **复制槽 (replication slot)**: 防 WAL 提前删除
- **PgBouncer**: 用 transaction 模式, 节省后端连接
- **HAProxy**: 健康检查 + 读写分离, 比 VIP 更优
- **PgBouncer + Patroni + HAProxy + etcd**: 经典生产组合
- **Keepalived + VIP**: 传统方案, 但脑裂风险高
- **同步复制**: RPO=0, 但延迟增加
- **异步复制**: 延迟低, 但可能丢数据
- **Pgpool-II**: 功能多但资源消耗大, 现不如 PgBouncer + Patroni 流行
- **云数据库**: 零运维但锁定厂商, 适合中小规模
- **故障演练**: 必须定期演练, 验证切换流程
- **监控**: Patroni REST API + Prometheus + Grafana
- **不要把鸡蛋放一个篮子**: etcd、PG、HAProxy 分布在不同机器
