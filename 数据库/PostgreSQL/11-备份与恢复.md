# PostgreSQL 备份与恢复 (Backup & Recovery)

> 本章覆盖 PostgreSQL 备份与恢复的完整体系:备份策略 RPO/RTO、物理/逻辑/全量/增量/在线离线备份分类、pg_dump/pg_dumpall 逻辑备份详解、pg_basebackup 物理备份、WAL 归档与时间点恢复 (PITR)、流复制与 PITR 结合、备份验证、pgBackRest / Barman / WAL-G 主流备份工具、自动化脚本与灾备演练。

---

## 一、备份概述

### 1. 为什么必须备份

数据库是企业的核心资产,备份是**数据安全最后一道防线**。PostgreSQL 常见故障场景:

- **硬件故障**:磁盘损坏、服务器宕机、SSD 寿命耗尽
- **人为错误**:误删表、误执行 `DROP`/`TRUNCATE`/`UPDATE`、`DELETE` 忘加 `WHERE`
- **软件 Bug**:PG 版本升级失败、应用逻辑导致数据损坏、autovacuum 配置错误
- **自然灾害**:机房火灾、洪水、断电
- **安全攻击**:勒索病毒、SQL 注入、PG 弱口令爆破
- **升级失败**:主从切换、版本升级、回滚、扩展升级 (pg_upgrade)

> **铁律**:没有备份,就没有真正的数据安全。任何高可用、容灾方案都不能替代备份。

### 2. 备份策略核心指标 — RPO 与 RTO

| 指标 | 名称 | 含义 | 衡量 |
|------|------|------|------|
| **RPO** | Recovery Point Objective | 灾难发生后能恢复到的数据时间点 | 可容忍的数据丢失量 |
| **RTO** | Recovery Time Objective | 灾难发生后恢复服务的最长时间 | 业务可容忍的停机时间 |

```text
示例:
  RPO = 1 小时 → 最多丢失 1 小时数据 → 至少 1 小时备份一次
  RPO = 5 分钟 → 需 WAL 归档 + 5 分钟一次基础备份
  RPO ≈ 0      → 需同步复制 + 实时 WAL 流
  RTO = 30 分钟 → 故障后 30 分钟内必须恢复服务
  RTO < 5 分钟  → 需热备 + 自动化恢复脚本

业务分级:
  • 金融核心交易: RPO ≈ 0, RTO < 5 分钟 (同步流复制 + WAL-G 实时归档)
  • 电商订单:     RPO < 5 分钟, RTO < 30 分钟 (异步流复制 + PITR)
  • 内部系统:     RPO < 1 小时, RTO < 4 小时 (每日全量 + WAL)
  • 日志/分析库:  RPO < 24 小时, RTO < 24 小时 (每日 pg_dump)
```

### 3. 备份三原则 (3-2-1 原则)

业界通用的数据保护黄金法则:

- **3** 份数据副本 (生产 + 2 份备份)
- **2** 种不同介质 (本地磁盘 + 异地磁带/对象存储)
- **1** 份异地存放 (Off-site,防机房级灾难)

```text
                    ┌── 备份 1: 本地 SSD/NAS (日常恢复,快)
生产数据 ──┬────────┤
          │        └── 备份 2: 异地对象存储 (S3/OSS/MinIO, 防机房灾难)
          │
          └── 备份 3: 冷归档存储 (低成本, 长期保留, 合规)
```

### 4. PostgreSQL 备份的独特性

PostgreSQL 的备份机制与 MySQL 有显著差异:

```text
┌─────────────────┬────────────────────────┬────────────────────────�
│     维度         │      PostgreSQL        │         MySQL          │
├─────────────────�────────────────────────┼────────────────────────┤
│ 物理日志         │ WAL (Write-Ahead Log)  │ binlog + redo/undo log │
│ 时间点恢复       │ WAL 重放 (原生支持)    │ binlog 重放            │
│ 流复制协议       │ replication protocol  │ binlog dump 协议        │
│ 逻辑备份         │ pg_dump / pg_dumpall   │ mysqldump              │
│ 物理备份工具     │ pg_basebackup          │ XtraBackup             │
│ PITR 目标        │ time / LSN / name      │ time / position        │
│ 一致性机制       │ MVCC + checkpoint      │ MVCC + LSN             │
│ 大对象 (BLOB)    │ pg_largeobject 系统表  │ 引擎内置                │
└─────────────────┴────────────────────────┴────────────────────────┘
```

**PostgreSQL 的核心优势**:
- **WAL 是核心**:WAL 既是恢复日志、又是复制源、又是 PITR 基础
- **MVCC 天然支持一致性快照**:pg_dump 默认就是一致性快照,无需 `--single-transaction`
- **支持恢复到任意 LSN**:通过 `recovery_target_lsn` 精确到日志序列号
- **支持命名恢复点 (restore point)**:`pg_create_restore_point()` 业务打标

## 二、备份分类

### 1. 物理备份 vs 逻辑备份

| 维度 | 物理备份 | 逻辑备份 |
|------|----------|----------|
| **原理** | 复制磁盘上的数据文件 + WAL | 导出 SQL 语句/数据 (COPY/INSERT) |
| **工具** | pg_basebackup、pgBackRest、Barman、tar/rsync | pg_dump、pg_dumpall |
| **速度** | 极快 (TB 级小时级) | 慢 (TB 级数十小时) |
| **跨版本/平台** | 同大版本 / 同 endian | 跨版本、跨平台 |
| **跨架构** | 强相关 (二进制) | 无关 (SQL 通用) |
| **单对象恢复** | 较难 (整库为单位) | 易 (单表/单 schema 即可) |
| **一致性** | 工具保证 + WAL replay | pg_dump 默认 MVCC 一致性 |
| **可读性** | 二进制文件 | 文本 SQL |
| **压缩比** | 中等 | 高 |
| **包含全局对象** | 是 (包含角色、表空间) | pg_dumpall 才包含 |
| **PITR 支持** | 是 (物理 + WAL) | 否 (需配合 WAL 归档) |
| **适用场景** | 大库生产备份、PITR、HA | 小库、迁移、灵活恢复 |

### 2. 全量备份 vs 增量备份 vs 差异备份

```text
时间线:  周一 ── 周二 ── 周三 ── 周四 ── 周五 ── 周六 ── 周日
         │      │      │      │      │      │      │
数据变化: 10      5      8      3      6      4      2 (GB)
```

| 类型 | 周日恢复 | 备份量 | 恢复速度 | 存储成本 | PG 支持 |
|------|----------|--------|----------|----------|---------|
| **全量** | 只需周日全量 | 10 GB (每天) | 最快 | 最高 | pg_basebackup / pg_dump |
| **增量** | 周日全量 + 周一~六所有增量 | 10+5+8+3+6+4+2 = 38 GB | 慢 | 最低 | PG 17+ pg_basebackup / pgBackRest |
| **差异** | 周日全量 + 周六差异 | 10+(5+8+3+6+4+2) = 38 GB | 中 | 中 | pgBackRest / Barman |

**特点**:
- **全量**:单独一份就能恢复,但占空间大
- **增量**:基于上一次备份,空间最小,但恢复需按顺序重放
- **差异**:基于上一次全量,恢复只需全量 + 一次差异,折中方案

> **PostgreSQL 增量备份演进**:PG 17 之前,官方 `pg_basebackup` 仅支持全量;增量需要 pgBackRest / Barman / WAL-G 等第三方工具。PG 17 起 `pg_basebackup --incremental` 原生支持页面级增量。

### 3. 冷备份、温备份、热备份

| 类型 | 数据库状态 | 是否停服 | 一致性 | 适用 |
|------|------------|----------|--------|------|
| **冷备份 (Cold)** | 完全关闭 | 是 | 强一致 | 维护窗口、初始化从库 |
| **温备份 (Warm)** | 只读 / 阻塞写入 | 部分 | 较强 | 可接受短锁 |
| **热备份 (Hot)** | 正常运行读写 | 否 | 工具保证 | 7×24 生产 |

```text
冷备份流程 (PG):
  1. 停止 PG: pg_ctl stop -m fast      # 或 systemctl stop postgresql
  2. 拷贝数据目录: cp -r $PGDATA /backup/
  3. 启动 PG: pg_ctl start

热备份流程 (pg_basebackup):
  1. 客户端连接 PG,启动 replication 连接
  2. PG 在 checkpoint 点开始拷贝数据文件
  3. 备份期间产生的所有 WAL 通过流复制协议同步过来
  4. 备份结束,获得完整一致的基础备份 + WAL 段
```

### 4. 在线备份 vs 离线备份

- **在线备份 (Online)**:数据库运行时执行,业务不中断 — 主要生产场景
- **离线备份 (Offline)**:数据库停机后执行 — 维护窗口、迁移

PG 的 `pg_basebackup` 默认就是**在线热备份**,无需停服。

## 三、备份方式对比

| 方式 | 一致性 | 速度 | 粒度 | 跨平台 | 复杂度 | PITR |
|------|--------|------|------|--------|--------|------|
| **pg_dump** | 强 (MVCC) | 慢 | 对象级 | 强 | 低 | 否 |
| **pg_dumpall** | 强 | 慢 | 全局对象 | 强 | 低 | 否 |
| **pg_basebackup** | 强 (WAL) | 快 | 整库 | 弱 | 低 | 是 |
| **pgBackRest** | 强 | 极快 | 整库 | 中 | 中 | 是 |
| **Barman** | 强 | 快 | 整库 | 中 | 中 | 是 |
| **WAL-G** | 强 | 快 | 整库 + WAL | 中 | 中 | 是 |
| **文件系统快照 (LVM/ZFS)** | 需工具保证 | 极快 | 整库 | 弱 | 中 | 是 |
| **手动物理拷贝** | 需停服 | 快 | 整库 | 弱 | 低 | 是 (需 WAL) |
| **`COPY TO/FROM`** | 弱 | 慢 | 表级 | 强 | 低 | 否 |

## 四、逻辑备份工具 — pg_dump

### 1. pg_dump 概述

**pg_dump** 是 PostgreSQL 自带的**逻辑备份**客户端工具,生成 SQL 脚本 (CREATE + COPY/INSERT)。

- **优点**:跨平台、跨版本、灵活、可选对象、可读到 SQL
- **缺点**:单线程,大库慢
- **本质**:把数据库对象导出为 SQL 语句
- **默认一致性**:开启一个内部 REPEATABLE READ 事务,与 MySQL `--single-transaction` 等价 (但 PG 自动)

### 2. 完整语法

```bash
pg_dump [OPTIONS] [DBNAME]   # 单库
pg_dumpall [OPTIONS]         # 全库 + 全局对象
```

**通用连接参数**:

| 参数 | 说明 |
|------|------|
| `-h, --host=HOSTNAME` | 数据库主机名或 socket 目录 |
| `-p, --port=PORT` | 端口 (默认 5432) |
| `-U, --username=NAME` | 用户名 |
| `-W, --password` | 强制口令提示 |
| `-d, --dbname=NAME` | 数据库名 |
| `-w, --no-password` | 永远不提示口令 |
| `--role=ROLENAME` | 在转储前 SET ROLE |

### 3. 核心参数详解

#### 输出对象控制

| 参数 | 说明 |
|------|------|
| `-t, --table=TABLE` | 仅转储指定表 (可多次使用) |
| `-T, --exclude-table=TABLE` | 排除指定表 |
| `-n, --schema=SCHEMA` | 仅转储指定 schema |
| `-N, --exclude-schema=SCHEMA` | 排除指定 schema |
| `--include-foreign-data=FDW` | 是否包含 FDW 表 (PG 16+) |
| `--no-privileged-access` | 跳过特权调整语句 |

#### 输出内容控制

| 参数 | 说明 |
|------|------|
| `-s, --schema-only` | 只导出 schema (DDL),不导出数据 |
| `-a, --data-only` | 只导出数据,不导出 schema |
| `-c, --clean` | 生成 DROP 对象语句 (CREATE 前) |
| `-C, --create` | 包含 CREATE DATABASE 语句 |
| `-x, --no-privileges` | 不导出 GRANT/REVOKE |
| `-O, --no-owner` | 不设置对象所有权 |
| `--no-tablespaces` | 不输出 `SET default_tablespace` |
| `--no-table-access-method` | 不输出表访问方法设置 (PG 15+) |

#### 输出格式

| 参数 | 说明 |
|------|------|
| `-Fp, --format=plain` | **纯文本 SQL** (默认),可用 psql 恢复 |
| `-Fc, --format=custom` | **自定义二进制**,pg_restore 恢复,可选对象 |
| `-Ft, --format=tar` | **tar 归档**,pg_restore 恢复,可恢复单个表 |
| `-Fd, --format=directory` | **目录格式**,pg_restore 恢复,并行恢复 (PG 5+) |

#### 大对象

| 参数 | 说明 |
|------|------|
| `-b, --blobs` | 导出大对象 (BLOBs) |
| `-B, --no-blobs` | 默认,不导出大对象 |
| `--no-large-privileges` | 不导出 BLOB 权限 (PG 16+) |

#### 压缩与统计

| 参数 | 说明 |
|------|------|
| `-Z, --compress=0-9` | 压缩级别 (仅 custom/directory/tar) |
| `-j, --jobs=N` | 并行转储目录 (仅 -Fd) |
| `-v, --verbose` | 详细模式 |
| `-V, --version` | 版本 |

#### 行为控制

| 参数 | 说明 |
|------|------|
| `-f, --file=FILENAME` | 输出文件 |
| `-E, --encoding=ENCODING` | 输出编码 |
| `--lock-wait-timeout=N` | 锁等待超时 (毫秒),超时则失败 |
| `-S, --superuser=NAME` | 设置超级用户 (用于禁用触发器) |
| `--use-set-session-authorization` | 用 `SET SESSION AUTHORIZATION` 替代 `ALTER OWNER` |
| `--disable-triggers` | 数据导入时临时禁用触发器 (需要超级用户) |
| `--if-exists` | DROP 时使用 IF EXISTS (PG 9.4+) |
| `--inserts` | 使用 INSERT 而非 COPY (慢但通用) |
| `--column-inserts` | 强制每列 INSERT |
| `--load-via-partition-root` | 分区表通过根表导入 (PG 16+) |
| `-h, --help` | 帮助 |

### 4. 备份示例

#### (1) 单库备份

```bash
# 默认纯文本格式,导入用 psql
pg_dump -U postgres -d mydb > /backup/mydb_$(date +%Y%m%d).sql

# 包含 CREATE DATABASE (-C),含 clean (-c)
pg_dump -U postgres -d mydb -C -c > /backup/mydb_full.sql

# 仅导出指定表
pg_dump -U postgres -d mydb -t users -t orders > /backup/users_orders.sql

# 多张匹配表 (正则)
pg_dump -U postgres -d mydb -t 'public.user*' > /backup/users.sql

# 仅导出 schema,无数据
pg_dump -U postgres -d mydb -s > /backup/mydb_schema.sql

# 仅导出数据,无 schema
pg_dump -U postgres -d mydb -a > /backup/mydb_data.sql

# 自定义格式 (-Fc),支持并行 + 可选恢复
pg_dump -U postgres -d mydb -Fc -Z 9 > /backup/mydb.dump

# tar 格式 (-Ft),可提取单表
pg_dump -U postgres -d mydb -Ft > /backup/mydb.tar

# 目录格式 (-Fd),可并行恢复 (需 PG 5+ 工具链)
pg_dump -U postgres -d mydb -Fd -j 4 -f /backup/mydb_dir

# 排除某些表
pg_dump -U postgres -d mydb --exclude-table=public.session_log > /backup/mydb.sql

# 排除大对象
pg_dump -U postgres -d mydb -B > /backup/mydb_no_blob.sql
```

#### (2) Schema 级备份

```bash
# 备份指定 schema
pg_dump -U postgres -d mydb -n app -n audit > /backup/schemas.sql

# 排除某些 schema
pg_dump -U postgres -d mydb --exclude-schema=tmp --exclude-schema=log > /backup/clean.sql
```

#### (3) 大对象备份

```bash
# 包含 BLOB (默认 B=,默认不导出大对象)
pg_dump -U postgres -d mydb -b > /backup/mydb_with_blob.sql

# 仅导出大对象 (PG 16+)
pg_dump -U postgres -d mydb -b --large-objects-only > /backup/blobs.sql
```

#### (4) 压缩备份

```bash
# 文本格式 + 外部 gzip 压缩
pg_dump -U postgres -d mydb | gzip > /backup/mydb.sql.gz

# 自定义格式 + 内置压缩 (-Fc -Z)
pg_dump -U postgres -d mydb -Fc -Z 9 > /backup/mydb.dump
# 比 gzip 高 30%~50%,且 pg_restore 支持部分恢复

# zstd (PG 16+)
pg_dump -U postgres -d mydb --compress=zstd:9 -Fc > /backup/mydb.dump
```

#### (5) 远程备份

```bash
# 远程主机备份
pg_dump -h 192.168.1.10 -p 5432 -U postgres -d mydb -Fc > /backup/mydb_remote.dump

# 通过 SSH 管道
ssh postgres@db-server "pg_dump -Fc -d mydb" > /backup/mydb_remote.dump

# 通过 ssh + pg_dump 流式压缩
ssh postgres@db-server "pg_dump -Fc -Z 9 -d mydb" | pigz > /backup/mydb.dump.gz
```

#### (6) 只导出 INSERT 语句 (兼容性最好)

```bash
# 用 INSERT 替代 COPY (兼容性最好,跨数据库也可用)
pg_dump -U postgres -d mydb --inserts > /backup/mydb_insert.sql

# 每列 INSERT (更慢,但极通用)
pg_dump -U postgres -d mydb --column-inserts > /backup/mydb_col.sql
```

### 5. 备份压缩对比

| 方式 | 命令 | 压缩比 | 速度 | 工具 |
|------|------|--------|------|------|
| **纯文本 + gzip** | `pg_dump \| gzip` | 5-8x | 中 | gzip |
| **纯文本 + pigz** | `pg_dump \| pigz` | 5-8x | 快 (并行) | pigz |
| **纯文本 + zstd** | `pg_dump \| zstd` | 6-10x | 快 | zstd |
| **custom + -Z** | `pg_dump -Fc -Z 9` | 8-12x | 快 | 内置 |
| **custom + zstd** (PG 16+) | `pg_dump -Fc --compress=zstd:9` | 10-15x | 极快 | 内置 |

### 6. 恢复 — psql 与 pg_restore

#### (1) 纯文本格式 (-Fp) → psql

```bash
# 整库恢复
psql -U postgres -d mydb < /backup/mydb.sql

# 含 CREATE DATABASE (-C 输出)
psql -U postgres -f /backup/mydb.sql

# 压缩恢复
gunzip < /backup/mydb.sql.gz | psql -U postgres -d mydb

# 指定数据库 (若备份文件不含 CREATE)
createdb -U postgres mydb
psql -U postgres -d mydb -f /backup/mydb.sql
```

#### (2) 自定义/目录/tar 格式 → pg_restore

```bash
# 整库恢复
pg_restore -U postgres -d mydb /backup/mydb.dump

# 创建数据库再恢复
createdb -U postgres mydb
pg_restore -U postgres -d mydb --create /backup/mydb.dump

# 并行恢复 (目录格式,大库加速)
pg_restore -U postgres -d mydb -j 8 /backup/mydb_dir

# 仅恢复一张表
pg_restore -U postgres -d mydb -t users /backup/mydb.dump

# 仅恢复一个 schema
pg_restore -U postgres -d mydb -n app /backup/mydb.dump

# 不导出权限、不设 owner
pg_restore -U postgres -d mydb -x -O /backup/mydb.dump

# 列出备份内容
pg_restore --list /backup/mydb.dump
pg_restore --list /backup/mydb.tar

# 干跑 (不实际执行)
pg_restore -U postgres -d mydb --dry-run /backup/mydb.dump
```

> **pg_restore 关键参数**:`-d` 目标数据库、`-j` 并行度、`-t` 单表、`-n` schema、`--clean` 先 DROP、`--if-exists` 容错 DROP、`--no-owner` 不设 owner、`--no-privileges` 不恢复权限、`-C` 先建库、`--single-transaction` 单事务恢复。

## 五、pg_dump 完整实战示例

### 1. 单表备份与恢复

```bash
# 备份 users 表
pg_dump -U postgres -d mydb -t public.users -Fc > /backup/users.dump

# 列出备份内容
pg_restore --list /backup/users.dump
# ; Archive created at ...
# ;     Table public.users
# ; ... etc

# 恢复到新库
createdb -U postgres mydb_test
pg_restore -U postgres -d mydb_test /backup/users.dump

# 恢复到现有库
pg_restore -U postgres -d mydb -t users --clean --if-exists /backup/users.dump
```

### 2. 单 schema 备份与恢复

```bash
# 备份 app schema (含所有表、视图、函数)
pg_dump -U postgres -d mydb -n app -Fc > /backup/app_schema.dump

# 列出
pg_restore --list /backup/app_schema.dump

# 恢复 (目标库已存在)
pg_restore -U postgres -d mydb_new -n app /backup/app_schema.dump
```

### 3. 全库备份 (pg_dump + pg_dumpall 配合)

```bash
# === 步骤 1: pg_dumpall 备份全局对象 ===
pg_dumpall -U postgres --globals-only > /backup/globals.sql
# 内容: 角色、tablespace、grant on database、参数等

# === 步骤 2: pg_dump 每个业务库 ===
for db in mydb1 mydb2 mydb3; do
  pg_dump -U postgres -d $db -Fc -Z 9 > /backup/${db}_$(date +%Y%m%d).dump
done

# 恢复顺序: 先 globals,再各库
psql -U postgres -f /backup/globals.sql

  pg_restore -U postgres -d $db /backup/${db}_*.dump
done
```

### 4. 只导出 schema

```bash
# 仅 DDL + 排除某些表

  --exclude-table=public.audit_log > /backup/schema_clean.sql
```

### 5. 只导出数据

```bash

# 仅数据 + INSERT 而非 COPY

```

### 6. 大对象 (BLOB)

## 六、逻辑备份工具 — pg_dumpall (全局对象)

### 1. pg_dumpall 概述

**pg_dumpall** 备份**集群级**对象,`pg_dump` 只能备份单库。

- **导出内容**:角色 (ROLE)、用户、表空间 (TABLESPACE)、ACL、pg_hba.conf 之外的全局配置
- **输出格式**:纯文本 SQL (无 -Fc 选项)
- **使用方式**:必须 `psql -f` 恢复

### 2. 完整语法

```bash
pg_dumpall [OPTIONS]
```

| 参数 | 说明 |
|------|------|
| `-g, --globals-only` | 只导出全局对象 (角色、表空间) |
| `-r, --roles-only` | 只导出角色 |
| `-t, --tablespaces-only` | 只导出表空间 |
| `-a, --data-only` | 只导出数据 |
| `-s, --schema-only` | 只导出 schema |
| `-c, --clean` | DROP 对象 |
| `-h/-p/-U/-w` | 连接参数 |

### 3. 完整示例

```bash
# 备份全局对象 (角色、表空间、ACL)
pg_dumpall -U postgres -g > /backup/globals.sql

# 全库备份 (全局 + 所有库),适合单库或小库
pg_dumpall -U postgres > /backup/all.sql

# 全库备份 + 压缩
pg_dumpall -U postgres | gzip > /backup/all.sql.gz

# 仅角色
pg_dumpall -U postgres -r > /backup/roles.sql

# 仅表空间
pg_dumpall -U postgres -t > /backup/tablespaces.sql

# 恢复全局对象
psql -U postgres -f /backup/globals.sql
```

### 4. pg_dump vs pg_dumpall 对比

| 维度 | pg_dump | pg_dumpall |
|------|---------|------------|
| 范围 | 单库 | 全集群 (所有库 + 全局) |
| 输出格式 | plain/custom/tar/directory | 仅 plain |
| 单表/单 schema 备份 | 支持 (-t/-n) | 不支持 |
| 角色/表空间备份 | 否 | 是 |
| 恢复工具 | psql 或 pg_restore | psql |
| 并行 | -Fd 支持 | 不支持 |
| 大库速度 | 慢 (但可调优) | 极慢 |

## 七、物理备份工具 — pg_basebackup

### 1. 概述

**pg_basebackup** 是 PG 自带的**在线物理热备份**工具 (PG 9.1+),生成集群级**基础备份 (Base Backup)**。

**核心特性**:
- **热备份**:业务无感知,无需停服
- **基于复制协议**:使用 PG 内置 streaming replication protocol
- **包含 WAL**:默认同时流式备份 WAL 段
- **支持压缩、流式、校验**
- **支持增量 (PG 17+)**:页面级增量

```text
pg_basebackup 在做什么:
  1. 以 replication 身份连接 PG
  2. 强制触发一次 checkpoint (保证数据一致性起点)
  3. 流式拷贝整个 $PGDATA 目录
  4. 流式接收备份期间产生的所有 WAL
  5. 生成 backup_label 文件,记录 checkpoint 位点
  6. 备份完成,得到完整一致的基础备份
```

### 2. 完整语法

```bash
pg_basebackup [OPTIONS]
```

| 参数 | 说明 |
|------|------|
| `-D, --pgdata=DIRECTORY` | 备份输出目录 |
| `-F, --format=p\|t` | 输出格式:p=plain(默认),t=tar |
| `-r, --max-rate=RATE` | 限速 (MB/s) |
| `-z, --gzip` | 启用 gzip 压缩 (tar 格式) |
| `-Z, --compress=0-9` | 压缩级别 |
| `-c, --checkpoint=fast\|spread` | checkpoint 模式:fast=立即,spread=平滑 |
| `-X, --wal-method=none\|fetch\|stream` | WAL 处理:none=不取,fetch=备份后取,stream=流式 |
| `-c, --checkpoint=...` | checkpoint 策略 |
| `-P, --progress` | 显示进度 |
| `-v, --verbose` | 详细输出 |
| `-n, --no-cleanup` | 不自动清理 `pg_replslot` |
| `-l, --label=LABEL` | 备份标签 |
| `-T, --tablespace-mapping=OLD=NEW` | 表空间重映射 |
| `--include-wal` | 等价于 `-X stream` |
| `--incremental=...` | **PG 17+** 增量备份 |
| `--target=tibero\|black\|...` | 备份目标 (PG 16+ 引入,默认 local) |
| `-h/-p/-U/-d` | 连接参数 |
| `-w, --no-password` | 不提示口令 |

### 3. 完整示例

#### (1) 基础全量备份

```bash
# 简单全量备份
pg_basebackup -U postgres -D /backup/base_$(date +%Y%m%d) -Fp -P -Xs

# 关键参数:
#   -Fp     纯文件格式 (目录)
#   -P      显示进度
#   -Xs     流式备份 WAL (推荐,保证一致性)

# 完整参数版本
pg_basebackup \
  -h 127.0.0.1 \
  -p 5432 \
  -U postgres \
  -D /backup/base_$(date +%Y%m%d) \
  -F p \
  -P \
  -X stream \
  -c fast \
  -l "Full backup $(date +%Y%m%d_%H%M%S)" \
  -v
```

#### (2) tar 格式备份 (便于传输)

```bash
# tar 格式 + gzip 压缩
pg_basebackup -U postgres -D /backup/base_$(date +%Y%m%d).tar -Ft -z -Z 6 -P -Xs

# 备份文件:
ls /backup/base_*.tar
# base.tar  base.tar.gz  pg_wal.tar.gz
```

#### (3) 限速备份 (生产环境)

```bash
# 限速 100 MB/s,避免 IO 风暴
pg_basebackup -U postgres -D /backup/base -Fp -P -Xs -r 100
```

#### (4) 流式输出到远程

```bash
# 通过 ssh 流式备份到远程主机
pg_basebackup -U postgres -D - -Fp -Xs | ssh backup@backup-server \
  "cat > /backup/pg_base_$(date +%Y%m%d).tar"

# 流式 tar 格式 + 压缩
pg_basebackup -U postgres -D - -Ft -z -Z 6 -Xs | \
  ssh backup@backup-server "cat > /backup/pg_$(date +%Y%m%d).tar.gz"

# 流式到对象存储 (S3)
pg_basebackup -U postgres -D - -Ft -z -Z 6 -Xs | \
  aws s3 cp - s3://mybucket/pg/$(date +%Y%m%d).tar.gz
```

#### (5) 表空间重映射 (恢复时改变路径)

```bash
# 备份时记录原路径,恢复时映射到新路径
pg_basebackup -U postgres -D /backup/base -Fp -Xs \
  -T /var/lib/pg_tablespace/tbs1=/new_path/tbs1

# 备份完成后,backup_label 中会记录映射
```

#### (6) 增量备份 (PG 17+)

```bash
# === 步骤 1: 全量备份 ===
pg_basebackup -U postgres -D /backup/full -Fp -Xs

# === 步骤 2: 第一次增量 ===
pg_basebackup -U postgres -D /backup/inc1 -Fp -Xs \
  --incremental=/backup/full

# === 步骤 3: 第二次增量 ===
pg_basebackup -U postgres -D /backup/inc2 -Fp -Xs \
  --incremental=/backup/inc1

# === 恢复: 按顺序重放 ===
# 1. 准备全量 (应用增量 1)
pg_combinebackup /backup/full /backup/inc1 -o /backup/restored
# 2. 应用增量 2
pg_combinebackup /backup/restored /backup/inc2 -o /backup/restored_final
# 3. 启动恢复
echo "restore_command = 'cp /backup/wal/%f %p'" >> /backup/restored_final/postgresql.auto.conf
pg_ctl start -D /backup/restored_final
```

> **PG 17 之前**:增量备份需依赖 pgBackRest / Barman / WAL-G 等第三方工具。

### 4. 备份的内部原理

```text
pg_basebackup 流程 (基于 replication protocol):

  1. 客户端以 replication=physical 身份连接 PG
     启动连接参数: replication=database

  2. 发送 BASE_BACKUP 命令,带参数:
     - 目标目录
     - WAL 方法 (none/fetch/stream)
     - checkpoint 模式 (fast/spread)
     - 压缩选项

  3. PG 服务端:
     a. 强制执行一次 CHECKPOINT
        → 保证后续从这个 checkpoint 开始一致
     b. 开始流式拷贝 $PGDATA
        → 通过 CopyBoth 模式 (replication 专用)
        → 每个文件独立完成 CRC 校验
     c. 同时根据 WAL 方法处理 WAL:
        - none: 不取 WAL,需后续 archive
        - fetch: 备份完成后取所需 WAL
        - stream: 备份期间流式推送所有新 WAL

  4. 写入 backup_label:
     START WAL LSN: 0/1A000028
     CHECKPOINT LSN: 0/1A000060
     BACKUP METHOD: streamed
     BACKUP FROM: primary

  5. 返回成功
```

### 5. 备份恢复 (基础备份直接启动)

```bash
# 1. 停止目标 PG
pg_ctl stop -D /var/lib/pgsql/15/data -m fast

# 2. 清空或备份原数据目录
mv /var/lib/pgsql/15/data /var/lib/pgsql/15/data.bak

# 3. 复制基础备份
cp -r /backup/base_20240115 /var/lib/pgsql/15/data
chown -R postgres:postgres /var/lib/pgsql/15/data

# 4. (可选) 配置 recovery.signal (PG 12+)
touch /var/lib/pgsql/15/data/recovery.signal

# 5. 配置 postgresql.auto.conf (PG 12+)
cat >> /var/lib/pgsql/15/data/postgresql.auto.conf <<EOF
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2024-01-15 10:30:00'
EOF

# 6. 启动 PG (进入恢复模式)
pg_ctl start -D /var/lib/pgsql/15/data -o "-c wal_level=replica"

# 7. 查看日志
tail -f /var/log/postgresql/postgresql-15-main.log
# LOG:  database system is ready to accept read only connections
# (恢复完成前只读,完成后自动切换为读写)
```

## 九、WAL 归档与 PITR (PG 核心特色)

### 1. PITR 原理

```text
时间点恢复 (Point-In-Time Recovery, PITR) = 基础备份 + WAL 重放

WAL 记录了从某个 checkpoint 到现在的所有数据变更。
PITR 通过重放 WAL,把数据库恢复到指定时间点 / LSN / 名称。

时间线:
  基础备份 (周日 0:00) ──→ 持续 WAL 段 ──→ 目标恢复点 (周三 10:29)
                                                    ↑ 在此点停止

  恢复流程:
  1. 恢复基础备份到 $PGDATA
  2. 配置 restore_command 指向 WAL 归档目录
  3. 配置 recovery_target_*
  4. PG 启动后进入恢复模式
  5. 按需重放 WAL,直到目标点
  6. 提升为读写,恢复完成
```

### 2. 启用 WAL 归档

#### postgresql.conf 配置

```ini
# === WAL 级别:必须 replica 或 logical 才能归档 ===
wal_level = replica                    # PG 14 及之前默认 replica,PG 15+ 默认也是

# === 归档模式 ===
archive_mode = on                      # 启用归档,需重启
# archive_mode = always                # 即使是备库也归档 (级联复制场景)

# === 归档命令 ===
archive_command = 'cp %p /backup/wal_archive/%f'
# 常用模式:
# - 本地归档: cp %p /backup/wal_archive/%f
# - 远程归档: rsync %p backup@backup-server:/backup/wal/%f
# - S3 归档:  test ! -f /backup/wal/%f && \
#             aws s3 cp %p s3://mybucket/wal/%f
# - 测试模式 (不实际归档): /bin/true

# === WAL 参数优化 ===
max_wal_size = 2GB                     # 触发 checkpoint 的阈值
min_wal_size = 512MB                   # 保留最小 WAL
wal_keep_size = 1GB                    # pg_wal 中保留的最小量 (PG 13+,取代 wal_keep_segments)

# === 复制槽 (可选,推荐) ===
max_replication_slots = 10
# 创建复制槽:
#   SELECT pg_create_wal_replication_slot('backup_slot', 'physical');
```

#### 手动创建归档目录

```bash
mkdir -p /backup/wal_archive
chown postgres:postgres /backup/wal_archive
chmod 700 /backup/wal_archive

# 重启 PG
pg_ctl restart -D /var/lib/pgsql/15/data

# 验证归档是否生效
psql -U postgres -c "SELECT pg_switch_wal();"     # 强制切换 WAL
ls /backup/wal_archive/                            # 应看到 WAL 段

# 查看归档状态
psql -U postgres -c "SELECT * FROM pg_stat_archiver;"
# archived_count   | failed_count   | last_archived_wal   | last_archived_time
# 156              | 0              | 0000000100000001000000A0 | 2024-01-15 10:00:00
```

### 3. recovery.conf (PG 12 之前) vs postgresql.auto.conf (PG 12+)

```text
PG 12 重大变更:
  • 不再有 recovery.conf 文件
  • 改为在 $PGDATA 创建空文件 recovery.signal (PG 12-15) 或 standby.signal (备库)
  • 恢复参数写入 postgresql.auto.conf
  • PG 16+: 仅 recovery.signal (备库用 standby.signal)

  PG 版本              恢复信号文件
  ──────────────────────────────────
  PG 12-15              recovery.signal (PITR)/ standby.signal (备库)
  PG 16+                recovery.signal (PITR)/ standby.signal (备库)
  (两者共存: 既做 PITR 又做备库,需两个文件都存在)
```

### 4. 完整 PITR 流程

#### 场景:周三 10:30 误删 users 表,需恢复到 10:29

```bash
# === 步骤 1: 备份当前数据 (防止二次损坏) ===
pg_ctl stop -D /var/lib/pgsql/15/data -m fast
mv /var/lib/pgsql/15/data /var/lib/pgsql/15/data.broken
mkdir -p /var/lib/pgsql/15/data
chown postgres:postgres /var/lib/pgsql/15/data

# === 步骤 2: 恢复基础备份 (上周日 0:00 的 pg_basebackup) ===
cp -a /backup/base_20240114_000000/* /var/lib/pgsql/15/data/
chown -R postgres:postgres /var/lib/pgsql/15/data

# 验证 backup_label (PG 自动识别基础备份起点)
cat /var/lib/pgsql/15/data/backup_label
# START WAL LSN: 0/3000028
# CHECKPOINT LSN: 0/3000060
# BACKUP METHOD: streamed
# BACKUP FROM: primary
# START TIME: 2024-01-14 00:00:00

# === 步骤 3: 创建恢复信号文件 ===
touch /var/lib/pgsql/15/data/recovery.signal

# === 步骤 4: 配置 postgresql.auto.conf ===
cat >> /var/lib/pgsql/15/data/postgresql.auto.conf <<EOF
restore_command = 'cp /backup/wal_archive/%f %p'
recovery_target_time = '2024-01-17 10:29:00'
recovery_target_action = 'pause'        # pause=暂停(可手动 promote),promote=自动提升
EOF

# === 步骤 5: 启动 PG (进入恢复模式) ===
pg_ctl start -D /var/lib/pgsql/15/data -l /tmp/pg_recovery.log

# 查看恢复进度
tail -f /tmp/pg_recovery.log
# LOG:  starting point-in-time recovery to 2024-01-17 10:29:00+08
# LOG:  restored log file "000000010000000300000028" from archive
# LOG:  restored log file "000000010000000300000029" from archive
# ... (持续重放 WAL)
# LOG:  recovery has paused
# LOG:  database system is ready to accept read only connections

# === 步骤 6: 验证 ===
psql -U postgres -c "SELECT COUNT(*) FROM users"
# 10000 (恢复成功)

# === 步骤 7: 提升为读写 ===
pg_ctl promote -D /var/lib/pgsql/15/data
# 或 SELECT pg_wal_replay_pause(); 然后 SELECT pg_wal_replay_resume();

# === 步骤 8: 清理 (恢复完成后) ===
rm /var/lib/pgsql/15/data/recovery.signal
# 删除或保留 postgresql.auto.conf 中的恢复参数(下次重启需重新配置)
```

### 5. recovery_target_* 详解

| 参数 | 含义 | 示例 |
|------|------|------|
| `recovery_target_time` | 恢复到指定时间 | `'2024-01-17 10:29:00+08'` |
| `recovery_target_lsn` | 恢复到指定 LSN | `'0/3000060'` |
| `recovery_target_name` | 恢复到命名恢复点 (restore point) | `'before_misoperation'` |
| `recovery_target_xid` | 恢复到指定事务 ID | `'123456'` |
| `recovery_target_inclusive` | 是否包含目标点 | `true` (默认) / `false` |
| `recovery_target_action` | 恢复后动作 | `pause` / `promote` / `shutdown` |
| `recovery_target_timeline` | 时间线 | `latest` (默认) / 具体 ID |

### 6. 命名恢复点 (Restore Point)

```bash
# 在业务关键节点手动打标
```

## 十、流复制与 PITR 结合

### 1. 完整架构

```text
┌──────────────────────────────────────────────────────────────┐
│                       生产环境                                │
│                                                              │
│   ┌─────────────┐         streaming replication             │
│   │  Primary    │ ─────────────────────┐                     │
│   │  PG 集群    │  replication slot    │                     │
│   └─────────────┘  WAL 流式推送        ↓                     │
│         │                          ┌─────────────┐           │
│         │ archive_mode=on          │  Standby   │           │
│         │ archive_command          │  (异地 DR)  │           │
│         ↓                          └─────────────┘           │
│   ┌─────────────────┐                                          │
│   │  WAL 归档目录    │                                          │
│   │  /backup/wal/   │                                          │
│   └─────────────────┘                                          │
│         │                                                     │
└─────────┼─────────────────────────────────────────────────────┘
          │
          │ 同步/异步 (异地备份)
          ↓
┌──────────────────────────────────────────────────────────────┐
│                  备份服务器 / 对象存储                         │
│                                                              │
│   • pg_basebackup 全量 (每日)                                │
│   • WAL 归档 (持续)                                          │
│   • 异地副本                                                  │
│   • 支持 PITR: 全量 + WAL 重放到任意点                        │
└──────────────────────────────────────────────────────────────┘
```

### 2. 完整步骤:配置流复制 + WAL 归档 + PITR

```ini
# === Primary postgresql.conf ===
wal_level = replica
archive_mode = on
archive_command = 'cp %p /backup/wal/%f'
max_wal_senders = 10
wal_keep_size = '2GB'

# === 创建复制用户 ===
# psql
CREATE USER replicator WITH REPLICATION ENCRYPTED PASSWORD 'secret';

# === pg_hba.conf ===
host replication replicator 192.168.1.0/24 md5

# === 用 pg_basebackup 初始化备库 ===
pg_basebackup -h primary -U replicator -D /var/lib/pgsql/15/data -Fp -Xs -P

# === 备库配置 standby.signal + 连接信息 ===
touch /var/lib/pgsql/15/data/standby.signal
cat >> /var/lib/pgsql/15/data/postgresql.auto.conf <<EOF
primary_conninfo = 'host=primary port=5432 user=replicator password=secret'
restore_command = 'cp /backup/wal/%f %p'
EOF

# === 启动备库 ===
pg_ctl start -D /var/lib/pgsql/15/data
```

### 3. 完整 PITR 恢复 (基于归档 + 备库)

```bash
# === 步骤 1: 准备恢复环境 ===
mkdir -p /var/lib/pgsql/15/recovery
chown postgres:postgres /var/lib/pgsql/15/recovery

# === 步骤 2: 用基础备份初始化 ===
cp -a /backup/full_backup/* /var/lib/pgsql/15/recovery/
chown -R postgres:postgres /var/lib/pgsql/15/recovery

# === 步骤 3: 配置 PITR ===
touch /var/lib/pgsql/15/recovery/recovery.signal
cat >> /var/lib/pgsql/15/recovery/postgresql.auto.conf <<EOF
restore_command = 'cp /backup/wal_archive/%f %p'
recovery_target_time = '2024-01-17 10:29:00'
recovery_target_action = 'promote'
EOF

# === 步骤 4: 启动并验证 ===
pg_ctl start -D /var/lib/pgsql/15/recovery -l /tmp/recovery.log

# 实时查看进度
psql -U postgres -c "SELECT * FROM pg_stat_recovery;"
```

## 十一、备份验证 (Restore Test)

### 1. 为什么必须验证

> **"备份没验证 = 没有备份"** — 真实的备份失败案例大多在验证环节发现。

**常见问题**:
- 备份文件损坏 (磁盘、传输)
- 备份不完整 (中途失败)
- 备份可恢复但数据缺失
- 备份不可恢复 (如版本不兼容、字符集不兼容)
- PITR 恢复不完整 (WAL 段缺失)
- 恢复后应用启动异常 (扩展、表空间)

### 2. 验证流程

```bash
# === 1. 校验备份文件完整性 ===
# md5 校验
md5sum /backup/full_20240115.dump > /backup/full.md5
# 验证时
md5sum -c /backup/full.md5

# 自定义格式内置校验
pg_restore --list /backup/full_20240115.dump > /dev/null
echo "备份文件可解析"

# === 2. 周期性恢复测试 (建议每月) ===
# 在独立的测试环境
pg_ctl stop -D /var/lib/pgsql/test/data -m fast 2>/dev/null
rm -rf /var/lib/pgsql/test/data/*
cp -a /backup/full/* /var/lib/pgsql/test/data/
chown -R postgres:postgres /var/lib/pgsql/test/data
pg_ctl start -D /var/lib/pgsql/test/data
psql -U postgres -d mydb -c "SELECT COUNT(*) FROM users"

# === 3. 数据一致性校验 ===
# 行数对比
psql -U postgres -d production -c "SELECT COUNT(*) FROM users" > prod_count.txt
psql -U postgres -d test_restore -c "SELECT COUNT(*) FROM users" > restore_count.txt
diff prod_count.txt restore_count.txt

# 表级 MD5 校验
psql -U postgres -d production -c "SELECT md5(string_agg(t.*::text, '' ORDER BY id)) FROM users t"
psql -U postgres -d test_restore -c "SELECT md5(string_agg(t.*::text, '' ORDER BY id)) FROM users t"
# 对比两次 MD5,需一致

# === 4. 验证关键功能 ===
psql -U postgres -d test_restore -c "SELECT * FROM users LIMIT 10"
psql -U postgres -d test_restore -c "\df"                # 列出函数
psql -U postgres -d test_restore -c "SELECT * FROM pg_indexes WHERE schemaname='public'"  # 索引

# === 5. PITR 验证 (推荐季度) ===
# 模拟 PITR: 在测试环境重放到指定时间点,验证数据正确
mkdir -p /var/lib/pgsql/pitr_test/data
cp -a /backup/full/* /var/lib/pgsql/pitr_test/data/
touch /var/lib/pgsql/pitr_test/data/recovery.signal
cat >> /var/lib/pgsql/pitr_test/data/postgresql.auto.conf <<EOF
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2024-01-15 12:00:00'
EOF
pg_ctl start -D /var/lib/pgsql/pitr_test/data
# 验证数据是否在指定时间点

# === 6. 性能验证 (恢复耗时) ===
time pg_restore -U postgres -d mydb -j 8 /backup/full.dump
```

### 3. 自动化验证脚本

```bash
#!/bin/bash
# /usr/local/bin/verify_pg_backup.sh
# 用法: verify_pg_backup.sh <backup_file>

set -euo pipefail

BACKUP_FILE=${1:?"用法: $0 <backup_file>"}
TEST_DIR=/var/lib/pgsql/verify_$(date +%s)
TEST_PORT=5433
LOG_FILE=/var/log/pg_verify_$(date +%Y%m%d_%H%M%S).log

echo "=== 验证备份文件: $BACKUP_FILE ==="

# 1. 文件存在性
if [ ! -f "$BACKUP_FILE" ]; then
  echo "[FAIL] 备份文件不存在: $BACKUP_FILE"
  exit 1
fi

# 2. 文件可解析
if pg_restore --list "$BACKUP_FILE" > /dev/null 2>&1; then
  echo "[OK] 备份文件可解析"
else
  echo "[FAIL] 备份文件解析失败"
  exit 1
fi

# 3. 测试恢复 (启动独立 PG 实例)
mkdir -p $TEST_DIR
chown postgres:postgres $TEST_DIR
initdb -D $TEST_DIR --auth-host=trust --auth-local=trust > /dev/null 2>&1
sed -i "s/^port = .*/port = $TEST_PORT/" $TEST_DIR/postgresql.conf
pg_ctl start -D $TEST_DIR -l /tmp/pg_verify.log -o "-p $TEST_PORT"

# 等待启动
for i in {1..30}; do
  pg_isready -p $TEST_PORT -q && break
  sleep 1
done

# 4. 恢复
TEST_DB="verify_$(date +%s)"
createdb -p $TEST_PORT -U postgres $TEST_DB
pg_restore -p $TEST_PORT -U postgres -d $TEST_DB "$BACKUP_FILE"

# 5. 校验
TABLE_COUNT=$(psql -p $TEST_PORT -U postgres -d $TEST_DB -t -c \
  "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='public'")
ROW_COUNT=$(psql -p $TEST_PORT -U postgres -d $TEST_DB -t -c \
  "SELECT SUM(n_live_tup) FROM pg_stat_user_tables")

echo "[OK] 验证成功"
echo "  表数量: $TABLE_COUNT"
echo "  行总数: $ROW_COUNT"

# 6. 清理
pg_ctl stop -D $TEST_DIR -m fast
rm -rf $TEST_DIR

echo "=== 验证完成 ==="
```

## 十五、自动备份脚本

### 1. pg_dump 每日逻辑备份

```bash
#!/bin/bash
# /usr/local/bin/pg_dump_backup.sh
# 每日 pg_dump 逻辑备份 + 压缩 + 清理

set -euo pipefail

# === 配置 ===
PG_HOST="127.0.0.1"
PG_PORT="5432"
PG_USER="backup_user"
PG_PASS="backup_password"
export PGPASSWORD="$PG_PASS"

BACKUP_ROOT="/backup/pg"
DATE=$(date +%Y%m%d_%H%M%S)
KEEP_DAILY=7
KEEP_WEEKLY=4

LOG_FILE="/var/log/pg_backup_${DATE}.log"

# === 工具检查 ===
command -v pg_dump >/dev/null 2>&1 || { echo "pg_dump 未安装"; exit 1; }

# === 日志函数 ===
log() {
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a $LOG_FILE
}

# === 创建备份目录 ===
mkdir -p ${BACKUP_ROOT}/{daily,weekly,globals}

# === 1. 全局对象备份 ===
log "开始备份全局对象"
pg_dumpall -h $PG_HOST -p $PG_PORT -U $PG_USER -g | \
  gzip > ${BACKUP_ROOT}/globals/globals_${DATE}.sql.gz

# === 2. 各库独立备份 ===
DATABASES=$(psql -h $PG_HOST -p $PG_PORT -U $PG_USER -d postgres -t -A -c \
  "SELECT datname FROM pg_database WHERE datistemplate=false AND datname NOT IN ('postgres')")

for db in $DATABASES; do
  log "开始备份数据库: $db"
  pg_dump -h $PG_HOST -p $PG_PORT -U $PG_USER -d $db \
    -Fc -Z 9 -j 4 -b \
    -f ${BACKUP_ROOT}/daily/${db}_${DATE}.dump 2>> $LOG_FILE

  # md5 校验
  md5sum ${BACKUP_ROOT}/daily/${db}_${DATE}.dump > ${BACKUP_ROOT}/daily/${db}_${DATE}.dump.md5

  SIZE=$(du -sh ${BACKUP_ROOT}/daily/${db}_${DATE}.dump | cut -f1)
  log "完成: $db ($SIZE)"
done

# === 3. 每周日归档为 weekly ===
if [ "$(date +%u)" -eq 7 ]; then
  log "周日归档"
  cp -r ${BACKUP_ROOT}/daily/*${DATE}* ${BACKUP_ROOT}/weekly/
fi

# === 4. 清理过期备份 ===
log "清理过期备份"
find ${BACKUP_ROOT}/daily -name "*.dump" -mtime +${KEEP_DAILY} -delete
find ${BACKUP_ROOT}/daily -name "*.dump.md5" -mtime +${KEEP_DAILY} -delete
find ${BACKUP_ROOT}/globals -name "*.sql.gz" -mtime +${KEEP_DAILY} -delete
find ${BACKUP_ROOT}/weekly -name "*.dump" -mtime +$((KEEP_WEEKLY * 7)) -delete

log "备份任务完成"
```

### 2. pg_basebackup 物理备份脚本

```bash
#!/bin/bash
# /usr/local/bin/pg_basebackup_backup.sh
# 每日 pg_basebackup 物理备份 + WAL 归档

set -euo pipefail

PG_HOST="127.0.0.1"
PG_PORT="5432"
PG_USER="backup_user"
export PGPASSWORD="backup_password"

BACKUP_ROOT="/backup/pg_base"
WAL_ROOT="/backup/wal"
DATE=$(date +%Y%m%d_%H%M%S)
KEEP_DAILY=7

LOG_FILE="/var/log/pg_base_backup_${DATE}.log"

log() {
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a $LOG_FILE
}

mkdir -p ${BACKUP_ROOT} ${WAL_ROOT}

# === 1. 全量基础备份 ===
log "开始 pg_basebackup"
pg_basebackup \
  -h $PG_HOST -p $PG_PORT -U $PG_USER \
  -D ${BACKUP_ROOT}/base_${DATE} \
  -Ft -z -Z 6 -P -Xs \
  -l "Full backup ${DATE}" \
  2>> $LOG_FILE

log "基础备份完成: ${BACKUP_ROOT}/base_${DATE}"

# === 2. 归档当前 WAL ===
log "归档 WAL"
psql -h $PG_HOST -p $PG_PORT -U $PG_USER -d postgres -c "SELECT pg_switch_wal();" > /dev/null

# === 3. 清理 ===
log "清理过期备份"
find ${BACKUP_ROOT} -maxdepth 1 -name "base_*" -mtime +${KEEP_DAILY} -exec rm -rf {} +

log "任务完成"
```

## 十六、备份策略建议 (金字塔模型)

### 1. 备份金字塔

```text
                    ▲ 高成本、低频
                   ╱ ╲
                  ╱ 月 ╲          月度归档 (异地冷存储,保留 1 年)
                 ╱─────╲
                ╱  周   ╲        周全量 (pg_basebackup 或 pgBackRest,本地+异地)
               ╱─────────╲
              ╱    日    ╲      日逻辑 (pg_dump,本地+异地)
             ╱─────────────╲
            ╱      时      ╲    小时增量/快照 (pgBackRest diff)
           ╱─────────────────╲
          ╱       分         ╲  WAL 持续归档 (archive_command)
         ╱_____________________╲
        ▼ 低成本、高频
```

### 2. 推荐策略组合

| 业务等级 | 备份策略 | 频率 | RPO | RTO |
|----------|----------|------|-----|-----|
| **核心交易** | pgBackRest + WAL 流复制 + DR | 实时 + 6h | < 1 分钟 | < 5 分钟 |
| **重要业务** | pg_basebackup + WAL 归档 + 流复制 | 每日 + 实时 | < 5 分钟 | < 30 分钟 |
| **普通业务** | pg_dump + WAL 归档 | 每日 + 持续 | < 1 小时 | < 数小时 |
| **日志/分析** | pg_dump 周备份 | 每周 | < 24 小时 | < 24 小时 |

### 3. 多副本 (3-2-1 + 4-3-2 原则)

```text
3 份数据 (生产 + 备份 1 + 备份 2)

进阶 4-3-2:
  4 份数据
  3 种存储介质
  2 个地理位置
```

## 十八、备份加密与安全

### 1. 备份加密的重要性

```text
备份文件包含完整的数据库内容,一旦泄露等同于数据泄露。
常见泄露场景:
  • 备份文件上传至 S3 桶但桶权限配置错误
  • 备份磁带丢失或被盗
  • 运维人员误将备份文件发到公共网盘
  • 异地传输过程中被中间人截获
  • 离职员工带走备份文件

加密策略:
  • 传输加密 (TLS): PG 连接 + S3 HTTPS + SSH 隧道
  • 存储加密: 备份文件本身加密 (AES-256)
  • 密钥管理: 不要把密钥和备份放在一起 (KMS / Vault)
  • 完整性校验: 加密同时附加 SHA-256 校验和
```

### 2. pgBackRest 内置加密

```ini
# /etc/pgbackrest.conf
[global]
repo1-cipher-type=aes-256-cbc            # AES-256-CBC 加密
repo1-cipher-pass=YourStrongPassphrase   # 加密口令

# 生成强密码
openssl rand -base64 32
# 输出: aB3dEf7gH9iJ1kL2mN4oP5qR6sT7uV8wX9yZ0aB1cD2eF3gH4=
```

**使用密钥文件 (更安全)**:

```bash
# 生成密钥文件
openssl rand -base64 32 | sudo tee /etc/pgbackrest/cipher.key
sudo chmod 600 /etc/pgbackrest/cipher.key
sudo chown barman:barman /etc/pgbackrest/cipher.key
```

```ini
# /etc/pgbackrest.conf
[global]
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass-file=/etc/pgbackrest/cipher.key
```

**备份加密效果**:

```bash
pgbackrest --stanza=my_stanza backup
pgbackrest --stanza=my_stanza info
# 输出会显示:
#     cipher: aes-256-cbc
# 备份文件无法直接 cat 读取,需通过 pgBackRest 工具还原
```

### 3. pg_dump 加密 (外部加密)

```bash
# === 方式 1: openssl 加密 ===
pg_dump -U postgres -d mydb -Fc | \
  openssl enc -aes-256-cbc -salt -pbkdf2 -k "YourStrongPassphrase" \
  > /backup/mydb.dump.aes

# 解密恢复
openssl enc -d -aes-256-cbc -pbkdf2 -k "YourStrongPassphrase" \
  -in /backup/mydb.dump.aes | pg_restore -U postgres -d mydb

# === 方式 2: GPG 加密 ===
pg_dump -U postgres -d mydb -Fc | \
  gpg --symmetric --cipher-algo AES256 --compress-algo zlib \
  --output /backup/mydb.dump.gpg

# 解密恢复
gpg --decrypt /backup/mydb.dump.gpg | pg_restore -U postgres -d mydb

# === 方式 3: age 加密 (现代工具) ===
pg_dump -U postgres -d mydb -Fc | \
  age -p -o /backup/mydb.dump.age

# 解密
age -d -i key.txt /backup/mydb.dump.age | pg_restore -U postgres -d mydb
```

### 4. WAL 加密 (PG 13+)

```ini
# postgresql.conf
# 启用 WAL 加密 (PG 13+ 实验性,PG 15+ 正式)
encryption_key_command = '/path/to/keymgr.sh %k'
# 或使用 cluster_key (PG 17+ 简化)
```

### 5. 备份文件访问控制

```bash
# === 严格的文件权限 ===
chmod 600 /backup/pg/*.dump
chmod 700 /backup/pg/
chown -R postgres:postgres /backup/pg/

# === S3 上传加密 ===
aws s3 cp /backup/mydb.dump \
  s3://mybucket/pg/mydb.dump \
  --sse AES256                                        # 服务端加密
aws s3 cp /backup/mydb.dump \
  s3://mybucket/pg/mydb.dump \
  --sse aws:kms \
  --sse-kms-key-id alias/my-key                       # KMS 加密

# === 不要把密码写在命令行 ===
# ❌ 错误
pg_dump -U postgres -d mydb -Fc > /tmp/x.dump &
# ✅ 正确: 使用 ~/.pgpass
cat >> ~/.pgpass <<EOF
127.0.0.1:5432:*:postgres:secret
EOF
chmod 600 ~/.pgpass

# ✅ 或使用 PGPASSWORD 环境变量 (避免 history 泄露)
export PGPASSWORD=$(cat ~/.pg_secret)
pg_dump -U postgres -d mydb -Fc > /backup/x.dump
unset PGPASSWORD
```

## 十九、备份性能优化

### 1. pg_dump 加速技巧

```bash
# === 技巧 1: 使用目录格式 (-Fd) + 并行 (-j) ===
# 比纯文本快 4-8 倍 (取决于 CPU 核数)
pg_dump -U postgres -d mydb -Fd -j 8 -f /backup/mydb_dir

# === 技巧 2: 排除大表 (单独备份) ===
# 备份时跳过日志表、临时表
pg_dump -U postgres -d mydb \
  --exclude-table=public.session_log \
  --exclude-table=public.event_log \
  -Fc > /backup/mydb_main.dump

# === 技巧 3: 调整锁等待超时 ===
# 大库备份时,如遇到锁等待立即失败 (默认 0=永不超时)
pg_dump -U postgres -d mydb --lock-wait-timeout=60000 -Fc > /backup/mydb.dump

# === 技巧 4: 流式压缩 ===
pg_dump -U postgres -d mydb -Fc -Z 6 | \
  pigz -9 > /backup/mydb.dump.gz

# === 技巧 5: 减少网络传输 ===
# 本地备份
pg_dump -h /var/run/postgresql -U postgres -d mydb -Fc > /backup/mydb.dump

# === 技巧 6: 升级 PG 版本 ===
# PG 16+ 的 pg_dump 性能比 PG 13 提升 30-50%
```

### 2. pg_restore 加速技巧

```bash
# === 技巧 1: 并行恢复 (目录格式) ===
pg_restore -U postgres -d mydb -j 8 /backup/mydb_dir

# === 技巧 2: 禁用触发器 (数据导入时) ===
# 仅超级用户可用,导入完成后自动恢复
pg_restore -U postgres -d mydb --disable-triggers /backup/mydb.dump

# === 技巧 3: 增大维护内存 (启动参数) ===
pg_ctl start -D /data -o "-c maintenance_work_mem=4GB -c max_parallel_maintenance_workers=8"

# === 技巧 4: 关闭 WAL/校验 ===
pg_ctl start -D /data -o "-c full_page_writes=off -c fsync=off -c synchronous_commit=off"
# ⚠️ 导入完成后立即重启为正常配置

# === 技巧 5: 关闭外键检查 ===
# PG 不支持全局禁用外键,但可分批导入
# 先导入无 FK 的表,再导入有 FK 的表
```

### 3. pg_basebackup 加速技巧

```bash
# === 技巧 1: 限速避免 IO 风暴 ===
pg_basebackup -U postgres -D /backup/base -Fp -Xs -r 500

# === 技巧 2: 启用压缩 ===
pg_basebackup -U postgres -D /backup/base.tar -Ft -z -Z 6 -Xs

# === 技巧 3: 选择 checkpoint 模式 ===
# -c fast: 立即 checkpoint,备份快但生产有抖动
# -c spread: 平滑 checkpoint,备份慢但生产无感知
pg_basebackup -U postgres -D /backup/base -Fp -Xs -c spread

# === 技巧 4: 网络优化 ===
# 增加 max_wal_senders (允许更多并行连接)
# 提升网络带宽
# 使用专用备份网卡
```

### 4. PITR 加速技巧

```ini
# postgresql.auto.conf (恢复期间)
# === 关闭不必要的同步开销 ===
synchronous_commit = off
full_page_writes = off

# === 增大恢复并行度 (PG 16+) ===
recovery_prefetch = on
recovery_prefetch_workers = 4
maintenance_io_concurrency = 8

# === 增大内存 ===
shared_buffers = 8GB
effective_cache_size = 24GB
```

### 5. 大库备份 (TB 级) 实战

```text
TB 级数据库 (10TB+) 备份挑战:
  • pg_dump 时间长 (数十小时)
  • 网络带宽压力大
  • 磁盘 IO 影响生产
  • 备份存储成本高

解决方案:
  • 必须用物理备份 (pg_basebackup / pgBackRest)
  • 块级增量 + 压缩
  • 流式到对象存储 (避免本地中转)
  • 错峰备份 (凌晨低峰期)
  • 限速保护生产 (--max-rate)

具体场景:
  • 10TB 库: pg_basebackup -r 500 限速,需要 ~5-6 小时
  • pgBackRest 块级增量: 每天仅备份变化块,GB 级
```

## 二十、逻辑复制作为备份策略

### 1. 逻辑复制 vs 物理备份

| 维度 | 物理备份 | 逻辑复制 |
|------|----------|----------|
| **粒度** | 整库 | 表级 |
| **方向** | 单向 | 多向 |
| **跨版本** | 否 | 是 (PG 14+) |
| **跨平台** | 否 | 是 |
| **DDL 支持** | 是 | 否 (PG 15 部分) |
| **延迟** | 即时 | 秒级 |
| **存储** | 快照 | 增量 |
| **用作备份** | 经典方式 | 补充 |

### 2. 逻辑复制配置

```sql
-- === 发布端 (源库) ===
-- 创建发布
CREATE PUBLICATION pub_mydb FOR TABLE users, orders, products;

-- 或发布所有表
CREATE PUBLICATION pub_all FOR ALL TABLES;

-- 查看发布
SELECT * FROM pg_publication;

-- === 订阅端 (目标库) ===
-- 创建订阅
CREATE SUBSCRIPTION sub_mydb
CONNECTION 'host=source-db port=5432 user=repl_user dbname=mydb'
PUBLICATION pub_mydb;

-- 查看订阅
SELECT * FROM pg_subscription;
```

### 3. 逻辑复制用于备份

```text
场景 1: 异构数据库复制
  PostgreSQL (主) → PostgreSQL (备, 不同大版本)
  用作: 平滑升级、跨版本热备

场景 2: 部分表备份
  仅复制关键业务表,过滤大量历史/日志数据
  减少备份体积

场景 3: 跨数据中心同步
  本地写入 → 异地备份库
  实时数据保护
```

### 4. 注意事项

```bash
# ⚠️ 逻辑复制不复制 DDL (PG 15 部分支持)
# PG 15+ 需开启:
ALTER SUBSCRIPTION sub_mydb ENABLE (REFRESH PUBLICATION);

# �️ 逻辑复制不复制 SEQUENCE 变化 (需手动处理)
# 通过 pg_dump --data-only 单独同步 SEQUENCE

# ⚠️ 逻辑复制有延迟,不是真正的"零丢失备份"
# 仍需配合物理备份 + WAL 归档做 PITR
```

### 1. 关键监控指标

```sql
-- === 1. 归档状态 ===
SELECT * FROM pg_stat_archiver;
-- archived_count   已成功归档的 WAL 数量

-- last_archived_time 最近归档时间

-- === 2. 复制状态 (主库) ===
SELECT pid, usename, application_name, client_addr,
       state, sync_state, sent_lsn, replay_lsn,
       (sent_lsn - replay_lsn) AS lag_bytes
FROM pg_stat_replication;

-- === 3. 恢复状态 (备库/PITR) ===
SELECT * FROM pg_stat_recovery;

-- === 4. 备份历史 ===
SELECT * FROM pg_backup_history;

-- === 5. 当前 WAL 位置 ===
SELECT pg_current_wal_lsn();
SELECT pg_walfile_name(pg_current_wal_lsn());
```

### 2. 备份监控脚本

```bash
#!/bin/bash
# /usr/local/bin/check_pg_backup.sh
# 检查 PG 备份健康状况

set -uo pipefail

# === 配置 ===
ALERT_EMAIL="dba@example.com"
ALERT_WEBHOOK="https://hooks.example.com/pg-backup-alert"
WAL_ARCHIVE_DIR="/backup/wal_archive"
MAX_ARCHIVE_LAG_MINUTES=30        # WAL 归档最大延迟
BACKUP_DIR="/backup/pg_base"
MAX_BACKUP_AGE_HOURS=26           # 基础备份最大间隔
MAX_REPLICATION_LAG_MB=100        # 流复制最大延迟

# === 1. 检查归档状态 ===
ARCHIVED=$(psql -U postgres -t -A -c \
  "SELECT archived_count FROM pg_stat_archiver")
FAILED=$(psql -U postgres -t -A -c \
  "SELECT failed_count FROM pg_stat_archiver")
LAST_TIME=$(psql -U postgres -t -A -c \
  "SELECT EXTRACT(EPOCH FROM (now() - last_archived_time))/60 \
   FROM pg_stat_archiver")

echo "归档数: $ARCHIVED, 失败: $FAILED, 延迟: ${LAST_TIME}分钟"

# 告警: 失败数 > 0
if [ "$FAILED" != "0" ]; then
  echo "[ALERT] WAL 归档失败 $FAILED 次" | \
    mail -s "PG 备份告警" $ALERT_EMAIL
fi

# 告警: 归档延迟过大
if (( $(echo "$LAST_TIME > $MAX_ARCHIVE_LAG_MINUTES" | bc -l) )); then
  echo "[ALERT] WAL 归档延迟 ${LAST_TIME}分钟" | \
    mail -s "PG 备份告警" $ALERT_EMAIL
fi

# === 2. 检查基础备份新鲜度 ===
LATEST_BACKUP=$(ls -td ${BACKUP_DIR}/base_* 2>/dev/null | head -1)
if [ -z "$LATEST_BACKUP" ]; then
  echo "[ALERT] 无基础备份"
  exit 1
fi

BACKUP_AGE=$(($(date +%s) - $(stat -c %Y $LATEST_BACKUP)))
BACKUP_AGE_HOURS=$((BACKUP_AGE / 3600))
echo "最新备份: $LATEST_BACKUP (${BACKUP_AGE_HOURS}小时前)"

if [ $BACKUP_AGE_HOURS -gt $MAX_BACKUP_AGE_HOURS ]; then
  echo "[ALERT] 基础备份过旧: ${BACKUP_AGE_HOURS}小时" | \
    mail -s "PG 备份告警" $ALERT_EMAIL
fi

# === 3. 检查流复制延迟 ===
REPL_LAG=$(psql -U postgres -t -A -c \
  "SELECT COALESCE(MAX(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)),0) \
   FROM pg_stat_replication")
REPL_LAG_MB=$((REPL_LAG / 1024 / 1024))
echo "复制延迟: ${REPL_LAG_MB} MB"

if [ $REPL_LAG_MB -gt $MAX_REPLICATION_LAG_MB ]; then
  echo "[ALERT] 复制延迟过大: ${REPL_LAG_MB} MB" | \
    mail -s "PG 复制告警" $ALERT_EMAIL
fi

# === 4. 检查磁盘空间 ===
DISK_USAGE=$(df /backup | awk 'NR==2 {print $5}' | sed 's/%//')
if [ $DISK_USAGE -gt 80 ]; then
  echo "[ALERT] 备份目录磁盘使用 ${DISK_USAGE}%"
fi

echo "检查完成"
```

## 二十二、PostgreSQL 与 MySQL 备份深度对比

### 1. 工具对比

| 工具类别 | PostgreSQL | MySQL |
|----------|-----------|-------|
| **逻辑备份** | pg_dump / pg_dumpall | mysqldump / mysqlpump |
| **物理备份 (开源)** | pg_basebackup / pgBackRest / Barman | XtraBackup (Percona) |
| **物理备份 (商业)** | (无官方商业版,需第三方) | MySQL Enterprise Backup |
| **云原生备份** | WAL-G / pgBackRest | mysqlbackup / XtraBackup |
| **时间点恢复** | WAL 重放 (原生) | binlog 重放 |

### 2. 核心机制对比

```text
┌─────────────────────┬──────────────────────────┬──────────────────────────┐
│       维度          │      PostgreSQL          │         MySQL            │
├─────────────────────┼──────────────────────────┼──────────────────────────┤
│ 物理日志            │ WAL (Write-Ahead Log)   │ redo log + binlog        │
│ PITR 核心           │ WAL 重放                │ binlog 重放              │
│ 一致性机制          │ MVCC + checkpoint       │ MVCC + LSN               │
│ 物理备份起点        │ checkpoint 强制触发      │ LSN + 短暂 read lock     │
│ 复制协议            │ streaming replication   │ binlog dump + IO/SQL     │
│ 增量备份            │ PG 17+ / pgBackRest      │ XtraBackup (成熟)        │
│ 逻辑备份并发        │ PG 16+ (目录格式)       │ mysqlpump (5.7+)         │
│ 跨版本逻辑备份      │ ✅ (pg_dump 兼容)      │ ✅ (mysqldump 兼容)     │
│ 跨版本物理备份      │ ❌ (需 pg_upgrade)     │ ❌ (需 mysql_upgrade)   │
│ 跨平台物理备份      │ ❌ (同 endian 即可)    │ ❌ (同 endian)           │
│ 流式远程备份        ✅ (原生)              │ ✅ (需 xbstream)         │
│ 在线 PITR           │ ✅ (无停机)            │ ✅ (无停机)             │
│ PITR 目标精度       │ time / LSN / name      │ time / position / GTID   │
│ 大对象处理          │ pg_largeobject 系统表   │ 引擎内置                  │
│ 备份加密            │ pgBackRest / 外部加密   │ XtraBackup / MEB        │
│ WAL/binlog 加密    │ PG 13+ (cluster_key)  │ MySQL 8.0+ (binlog_encryption) │
└─────────────────────┴──────────────────────────┴──────────────────────────┘
```

### 3. 命令对比 (常用场景)

```bash
# === 全库逻辑备份 ===
# PG
pg_dump -U postgres -d mydb -Fc -Z 9 > mydb.dump

# MySQL
mysqldump -uroot -p --single-transaction --master-data=2 \
  --routines --events mydb | gzip > mydb.sql.gz


# === 全库物理备份 ===
# PG

# MySQL
xtrabackup --backup --target-dir=/backup/base --user=root --password=xxx


# === 启用 WAL/binlog 归档 ===

# MySQL
[mysqld]

# === 时间点恢复 ===

  /backup/binlog/mysql-bin.0* | mysql -uroot -p
```

### 4. 备份策略对比

| 业务场景 | PostgreSQL 推荐 | MySQL 推荐 |
|----------|----------------|------------|
| **核心交易 (RPO=0)** | 同步流复制 + WAL-G | MGR / XtraBackup + binlog |
| **重要业务 (RPO<5min)** | pgBackRest + 流复制 + WAL | XtraBackup + binlog |
| **普通业务 (RPO<1h)** | pg_basebackup + WAL 归档 | XtraBackup 周 + binlog |
| **小库 (RPO<24h)** | pg_dump 每日 | mysqldump 每日 |
| **TB 级大库** | pgBackRest 块级增量 | XtraBackup 增量 |
| **云环境** | WAL-G / pgBackRest (S3) | mysqlbackup / XtraBackup |

### 5. 选择建议

```text
如果你的项目使用 PostgreSQL:
  • 中小库 (GB 级): pg_dump + WAL 归档
  • 中大库 (TB 级): pgBackRest 或 Barman
  • 云环境: WAL-G 或 pgBackRest (S3)
  • 极简方案: pg_basebackup + archive_command

如果你的项目使用 MySQL:
  • 所有规模: XtraBackup (热备 + 增量)
  • 小库: mysqldump --single-transaction
  • 云环境: mysqlbackup / 自研
  • 商业级: MySQL Enterprise Backup

两者核心差异:
  • PG 的 PITR 更原生,WAL 既做恢复又做复制
  • MySQL 的 binlog 与 InnoDB redo 分离,需协同
  • PG 的物理备份增量更晚成熟 (PG 17)
  • MySQL 的 XtraBackup 生态更成熟
```

## 二十三、备份最佳实践与常见误区

### 1. 备份最佳实践清单

```text
✓ DO (应该做):
  • 至少每周一次完整基础备份 (pg_basebackup 或 pgBackRest)
  • 持续开启 WAL 归档 (archive_mode = on)
  • 保留足够多的 WAL 段,覆盖最长保留期 + 7 天
  • 备份加密传输 + 加密存储
  • 多副本 (3 份以上) + 异地存放
  • 定期执行 restore test (建议每月)
  • 备份前检查磁盘空间 (建议保留 1.5x 备份大小)
  • 备份脚本包含错误处理 + 退出码 + 日志
  • 备份后立即校验 (md5 + 内容验证)
  • 监控归档状态、备份新鲜度、复制延迟
  • 关键操作前手动打恢复点 (pg_create_restore_point)
  • 备份用户最小权限 (REPLICATION + SELECT)
  • 限制备份速度 (--max-rate),保护生产 IO
  • 升级前完整备份 (pg_dump + pg_basebackup)
  • 文档化恢复流程,RTO/RPO 明确

� DON'T (不要做):
  • 不要只依赖一种备份方式
  • 不要把备份和数据库放在同一块磁盘
  • 不要把 WAL 归档和基础备份放在同一目录
  • 不要忘记测试 archive_command (生产前必须验证)
  • 不要在备份过程中停止 PG (除手动冷备份)
  • 不要把密码写在命令行 (用 .pgpass 或 PGPASSWORD)
  • 不要忘记备份全局对象 (角色、表空间)
  • 不要忘记备份大对象 (默认 pg_dump 不导出)
  • 不要忘记 WAL 归档的归档清理 (磁盘占满)
  • 不要跳过备份验证 (没验证 = 没备份)
  • 不要在恢复时忘记配置 recovery.signal
  • 不要在 PITR 后忘记 promote
  • 不要跨大版本做物理备份恢复 (必须 pg_dump 中转)
```

### 2. 常见备份误区

```text
误区 1: "我们有主从复制就够了,不需要备份"
事实: 主从复制只能防硬件故障,无法防误操作。
  误删表会同步到所有从库。
  PITR + 备份才是终极方案。

误区 2: "pg_dump 备份就是完整备份"
事实: pg_dump 是逻辑备份,不包含全局对象 (pg_dumpall 才包含)。
  备份策略必须 pg_dump + pg_dumpall -g 配合。

误区 3: "WAL 归档占空间,关掉省事"
事实: WAL 归档是 PITR 的基础。关掉后只能恢复到基础备份点。
  一旦发生误操作,无法恢复。

误区 4: "备份成功就够了,不需要验证"
事实: 备份未验证 = 没有备份。磁盘、传输都可能损坏。
  必须周期性 restore test。

误区 5: "备份加密后安全"
事实: 加密解决存储泄露,不解决密钥泄露。
  密钥必须和备份分开存放 (KMS / Vault)。

误区 6: "物理备份比逻辑备份好"
事实: 各有优势。逻辑备份灵活、单对象恢复、跨平台。
  物理备份快、PITR 原生。
  生产必须两者结合。

误区 7: "一次备份就能永远恢复"
事实: 备份会过期、损坏、版本不兼容。
  必须多份备份 + 跨时间点 + 跨版本。

误区 8: "本地备份就够了"
事实: 机房级灾难 (火灾、地震) 会摧毁本地备份。
  必须异地备份。
```

### 3. 备份策略决策树

```text
问: 你的业务能容忍多少数据丢失?
  ├─ RPO = 0 → 同步流复制 + WAL-G 实时归档 + pgBackRest
  ├─ RPO < 5 分钟 → 异步流复制 + WAL 归档 + pgBackRest
  ├─ RPO < 1 小时 → pg_basebackup + WAL 归档 (每日)
  ├─ RPO < 24 小时 → pg_dump + WAL 归档 (每日)
  └─ RPO > 24 小时 → pg_dump (每周)

问: 你的数据库多大?
  ├─ < 100 GB → pg_dump 完全够用
  ├─ 100 GB - 1 TB → pg_basebackup / pgBackRest
  └─ > 1 TB → pgBackRest (块级增量) / Barman

问: 你的环境是云还是自建?
  ├─ 云 (AWS/GCP/Azure) → WAL-G / pgBackRest + 对象存储
  ├─ 混合云 → pgBackRest + 多仓库
  └─ 自建机房 → pgBackRest + NFS/SAN + 异地磁带

问: 你需要恢复到任意时间点吗?
  ├─ 是 → 必须 WAL 归档 + restore_command + recovery_target_*
  └─ 否 → 仅基础备份即可

问: 需要加密吗?
  ├─ 是 (合规要求) → pgBackRest AES-256 / 外部加密
  └─ 否 → 普通明文备份
```

### 4. 备份容量估算公式

```text
日备份容量估算:
  日全量 = 数据库大小 × 压缩比 (0.2~0.5) × 保留天数
  日增量 = (变更量) × 压缩比 × 保留天数
  日 WAL = (事务量 / checkpoint 频率) × 16MB × 保留小时数

示例 (1TB 数据库,每天变更 50GB,每天 1 个全量):
  每日全量: 1TB × 0.3 = 300GB
  保留 7 天: 300GB × 7 = 2.1TB
  每日 WAL: 50GB × 0.1 (压缩) = 5GB × 7 = 35GB
  每月差异: 50GB × 0.3 × 30 = 450GB
  合计: 约 2.6TB / 月 (不含长期归档)

结论: 1TB 数据库备份完整保留 30 天 ≈ 3TB 备份存储
```

### 5. 备份恢复流程手册 (Runbook 模板)

```markdown
# PostgreSQL 恢复 Runbook

## 场景 A: 单表误删
1. 立即停止应用对该表的写入
2. 评估最近一次 pg_dump 备份的时间点
3. 启动新的临时 PG 实例
4. 从备份恢复 pg_dump 到临时实例
5. 从临时实例导出丢失的表
6. 导入到生产
7. 验证数据完整性
8. 恢复应用写入

## 场景 B: 整库损坏
1. 评估基础备份 + WAL 归档完整度
2. 选择最近的可用基础备份
3. 在新主机恢复基础备份
4. 配置 postgresql.auto.conf (restore_command)
5. touch recovery.signal
6. 启动 PG 进入恢复模式
7. 应用自动重放 WAL 到目标点
8. pg_ctl promote
9. 验证数据
10. 切换应用连接

## 场景 C: 误执行 TRUNCATE
1. 立即 pg_create_restore_point('before_truncate')
2. 评估 PITR 目标时间点
3. 启动 PITR 恢复流程 (同场景 B)
4. 验证 truncate 之前的数据

## 场景 D: 主机宕机
1. 评估备库状态
2. 若备库健康: 直接 promote 备库
3. 若备库也损坏: 启动 PITR 恢复
4. 切换应用连接到新主库

## 场景 E: 勒索病毒
1. 立即隔离受感染主机
2. 启动异地备份恢复 (PG 不在本地则不受影响)
3. 评估数据泄露范围
4. 启动 PITR 恢复到病毒感染前
5. 重置所有密码、API Key
6. 修补漏洞、重新上线
```

## 二十四、核心要点速记

- **RPO** = 可容忍数据丢失量,**RTO** = 可容忍停机时间
- **3-2-1 原则**:3 份副本、2 种介质、1 份异地
- **PG 备份三大支柱**:pg_dump (逻辑)、pg_basebackup (物理基础)、WAL 归档 (PITR)
- **物理备份** = 文件级,**逻辑备份** = SQL 级
- **全量 + 增量 + 差异**:全量是基线,增量最省但恢复慢
- **冷备份** = 停服,**热备份** = 不停服 (PG 默认)
- **pg_dump 默认一致性** = MVCC 自动快照,无需 `--single-transaction`
- **pg_dump -Fp** = 纯文本,psql 恢复
- **pg_dump -Fc** = 自定义二进制,pg_restore 恢复,可并行/部分
- **pg_dump -Ft** = tar 格式,pg_restore 恢复
- **pg_dump -Fd** = 目录格式,并行转储+并行恢复 (最快)
- **pg_dump -Z 9** = 内置压缩 (比 gzip 高)
- **pg_dumpall -g** = 仅全局对象 (角色、表空间)
- **pg_dump -t/-n** = 单表/单 schema
- **pg_dump -a/-s** = 仅数据/仅 schema
- **pg_dump -b** = 包含大对象 (默认不导出)
- **pg_restore -j** = 并行恢复 (目录格式)
- **pg_restore -t/-n** = 单表/单 schema 恢复
- **pg_basebackup -Xs** = 流式备份 WAL (生产推荐)
- **pg_basebackup -Ft -z** = tar + gzip
- **pg_basebackup -r** = 限速 (MB/s)
- **PG 17+ 增量**:pg_basebackup --incremental + pg_combinebackup
- **WAL 归档三要素**:wal_level=replica、archive_mode=on、archive_command
- **archive_command 模板**:`'cp %p /backup/wal/%f'`
- **archive_mode = always** = 备库也归档
- **PITR = 基础备份 + WAL 重放**
- **PG 12+ 恢复信号**:touch recovery.signal
- **PG 12+ 恢复配置**:写入 postgresql.auto.conf (不再是 recovery.conf)
- **restore_command 模板**:`'cp /backup/wal/%f %p'`
- **recovery_target_time** = 按时间恢复
- **recovery_target_lsn** = 按 LSN 恢复
- **recovery_target_name** = 按命名点恢复
- **pg_create_restore_point('name')** = 手动打标
- **recovery_target_action = pause** = 暂停,验证后再 promote
- **流复制 + PITR** = 全量备份 + WAL 归档 + 备库
- **pgBackRest** = PG 备份首选工具 (增量 + 并行 + 加密 + 远程)
- **pgBackRest stanza** = 一个 PG 集群
- **pgBackRest verify** = 备份校验
- **Barman** = 集中式备份管理,适合多 PG 实例
- **WAL-G** = 云原生备份 (S3/GCS/Azure)
- **备份验证** = 周期性 restore test,不可省
- **md5sum/sha256sum** = 备份完整性校验
- **pg_restore --list** = 列出备份内容
- **备份用户** = 最小权限 (REPLICATION + SELECT)
- **crontab** = 自动化备份,必加日志
- **3-2-1 + 多副本 + 异地** = 数据安全
- **灾难演练** = 检验备份可用性,定期执行
- **备份策略** = 业务分级 + RPO/RTO + 成本
- **WAL 归档必须开启** 否则无法 PITR
- **archive_command 失败** = 检查退出码,PG 会持续重试
- **pg_stat_archiver** = 查看归档状态
- **pg_switch_wal()** = 强制切换 WAL (测试用)
- **pg_wal_replay_pause/resume** = 暂停/恢复 WAL 重放
- **pg_ctl promote** = 提升备库/恢复完成
- **复制槽** = 防止 WAL 被提前清理
- **wal_keep_size** = pg_wal 中保留的最小量
- **max_wal_size/min_wal_size** = WAL 容量阈值
- **pgBackRest 增量** = 块级 diff,高效
- **pgBackRest 流式** = 支持远程仓库
- **恢复时关闭 autovacuum** = `pg_ctl start -o "-c autovacuum=off"`
- **恢复时增大 shared_buffers** = 加速恢复
- **PG 16+ recovery_prefetch** = 并行预取 WAL,加速恢复
- **清理过期备份** = `find ... -mtime +N -delete`
- **备份脚本** = 必须包含日志、错误处理、退出码
- **WAL 归档** = 异地同步,防勒索病毒
- **PG vs MySQL PITR 差异** = PG 原生 WAL 重放,MySQL 需 binlog 重放
- **PG vs MySQL 物理备份** = pg_basebackup vs XtraBackup
- **PG vs MySQL 逻辑备份** = pg_dump vs mysqldump
- **PG 17+ 增量 pg_basebackup** = 原生块级增量
- **pgBackRest repo1-cipher-type** = AES-256 加密备份
- **pgBackRest repo1-retention-full** = 全量备份保留数
- **pgBackRest verify** = 自动备份校验
- **Barman streaming_archiver** = 流式 WAL 接收
- **WAL-G WALG_S3_PREFIX** = 云存储路径
- **WAL-G --delta** = 增量备份
- **pg_restore --clean --if-exists** = 安全覆盖恢复
- **pg_restore --single-transaction** = 单事务恢复
- **pgBackRest --delta** = 增量恢复 (目标库有数据时)
- **backup_label** = pg_basebackup 写入,记录备份起点
- **restore_command %f %p** = %f=文件名, %p=目标路径
- **archive_command %p %f** = %p=WAL 路径, %f=目标文件名
- **recovery.signal** = PG 12+ 启动进入恢复模式标志
- **standby.signal** = PG 12+ 启动进入备库模式标志
- **pg_stat_archiver** = 归档监控视图
- **pg_is_in_recovery()** = 查询当前是否处于恢复模式
- **pg_wal_replay_pause()** = 暂停 WAL 重放 (验证用)
- **pg_wal_replay_resume()** = 继续 WAL 重放
- **pg_create_restore_point()** = 手动打标恢复点
- **pg_wal_lsn_diff()** = 计算两个 LSN 之间的字节差
- **逻辑复制** = publication/subscription (PG 10+)
- **CREATE PUBLICATION** = 创建发布
- **CREATE SUBSCRIPTION** = 创建订阅
- **复制槽 pg_create_replication_slot** = 防 WAL 被提前清理
- **DROP REPLICATION SLOT** = 手动删除复制槽
- **pg_stat_replication** = 流复制状态视图
- **sync_state sync/async** = 同步/异步复制模式
- **pg_basebackup --target** = 远程备份目标 (PG 16+)
- **pg_combinebackup** = 合并增量备份 (PG 17+)
- **备份加密 pgBackRest cipher-pass** = AES-256 加密
- **WAL 加密 encryption_key_command** = PG 13+ WAL 加密
- **cluster.key** = PG 17+ 简化 WAL 加密
- **备份三不要**:不要裸跑、不要明文、不要本地唯一
- **恢复三必须**:必须验证、必须测时、必须文档化
- **3-2-1 原则**:3 份、2 种介质、1 份异地
- **4-3-2 原则**:4 份、3 种介质、2 个地理位置
- **备份用户最小权限** = REPLICATION + SELECT + pg_read_all_settings
- **.pgpass 文件** = 600 权限,免密码交互
- **PGPASSWORD 环境变量** = 避免命令行泄露
- **备份脚本 set -euo pipefail** = 严格模式
- **备份日志 tee -a** = 输出到屏幕 + 文件
- **find -mtime +N -delete** = 自动清理过期备份
- **crontab 备份任务必须加 >>log 2>&1** = 错误捕获
- **备份容量 = DB × 0.3 × 保留天数** = 估算公式
- **WAL 段大小 = 16MB** = 默认 (可调)
- **CHECKPOINT 频率 = checkpoint_timeout** = 默认 5 分钟
- **max_wal_senders** = 限制并发流连接数
- **hot_standby = on** = 备库可读
- **synchronous_standby_names** = 同步备库配置
- **wal_compression = on** = 压缩 WAL (PG 15+ 默认 zstd)
- **full_page_writes = on** = 必须开启 (崩溃恢复)
- **wal_init_zero = on** = WAL 文件预写零 (PG 16+)
- **backup_label 文件** = pg_basebackup 自动写入
- **tablespace_map** = 表空间映射记录
- **PG 备份核心三大工具** = pg_dump + pg_basebackup + pgBackRest
- **PG 备份最佳工具** = pgBackRest (一站式)
- **云原生首选** = WAL-G
- **多实例管理** = Barman
- **跨版本迁移** = pg_dump (不用 pg_basebackup)
- **跨大版本恢复** = 必须 pg_upgrade 或 pg_dump 中转
- **PITR 失败 90% = restore_command 找不到 WAL** = 检查归档目录
- **archive_command 退出码非 0** = PG 持续重试,需查日志
- **failed_count 增长** = 归档失败,告警
- **last_archived_time 滞后** = WAL 写入或归档慢
- **WAL 段缺失** = 复制槽丢失或归档被清理
- **PG 核心要点** = 备份 + 验证 + 演练
