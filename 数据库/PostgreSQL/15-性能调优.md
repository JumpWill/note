# PostgreSQL 性能调优 (Performance Tuning)

> 本章是 PG 系列章节的"压轴":综合第 3~14 章的所有知识点,形成一套**自上而下、可落地**的调优方法论。读者最好已经熟悉 `EXPLAIN`、索引、WAL、VACUUM 等机制,否则部分内容会显得"知其然不知其所以然"。所有涉及细节的章节已标注交叉引用 `(参见第 X 章)`。

## 一、性能调优概述

### 1. 为什么需要性能调优

数据库性能问题的根因通常可以归到 3 类:

- **资源不够**:CPU/内存/IO/网络被打满
- **用错了资源**:SQL 写得太烂 / 索引没建 / 索引建错
- **配置不当**:PG 的默认参数对生产库几乎都偏保守

第三条最容易被忽视:PostgreSQL 的默认配置以**能用、兼容各种环境**为目标,生产环境必须调整。

### 2. 调优金字塔(Tuning Pyramid)

调优必须**自上而下**进行——上层问题占 80%,下层兜底 20%。底层调完了上层不解决,照样慢。

```text
                         ▲  应用层 (SQL 写法、ORM、缓存)
                        ╱ ╲
                       ╱   ╲
                      ╱ SQL  ╲         ← 第 6、15 章重点,80% 性能问题
                     ╱─────────╲
                    ╱   Schema  ╲      ← 第 4 章,表结构决定上限
                   ╱   索引       ╲     ← 第 5 章,B-Tree/GIN/BRIN
                  ╱─────────────────╲
                 ╱   PG 配置参数     ╲   ← postgresql.conf
                ╱   (effective_*,     ╲
               ╱     work_mem,        ╲
              ╱       shared_buffers)  ╲
             ╱───────────────────────────╲
            ╱   操作系统层                 ╲  ← 内核参数、文件系统、HugePage
           ╱   (vm.swappiness, IO Scheduler,╲
          ╱     ext4/xfs, noatime)           ╲
         ╱─────────────────────────────────────╲
        ╱   硬件层                              ╲ ← CPU/内存/磁盘(SSD/NVMe)/网卡
       ╱─────────────────────────────────────────╲
```

**自下而上的工程实践:先确保硬件选型过关 → OS 调到合适 → PG 参数落地 → Schema 设计合理 → 索引生效 → SQL 写出彩**。每一层都必要,但越上层越能解决"软性"问题。

### 3. 调优方法论:PDCA 循环

| 阶段   | 动作                                       | 输出                         |
|--------|--------------------------------------------|------------------------------|
| Plan   | 设定 SLA/QPS/P99 延迟基线                  | 量化目标                     |
| Do     | 收集监控 / `EXPLAIN` / 慢查询              | 现场数据                     |
| Check  | 定位瓶颈:CPU/内存/IO/SQL/锁/配置           | 根因分析                     |
| Act    | 改 SQL/索引/参数,**只改一个变量**             | 一轮变更                     |
| 循环   | 回到 Plan,重新测基线                        | 持续逼近目标                 |

**黄金法则**:**先测量,后优化**——不要凭直觉调参,更不要一上来就改 `shared_buffers`。

### 4. 性能问题的两类来源

| 类型     | 典型症状                                | 诊断工具                       |
|----------|------------------------------------------|--------------------------------|
| **突发性** | 系统刚上线就慢 / 昨天还快今天卡      | `pg_stat_activity`、`EXPLAIN`   |
| **渐进性** | 跑了几个月越来越慢,磁盘占用变多       | `pg_stat_user_tables`、`pgstattuple` |

> 第二类最常见,几乎都是**表膨胀**、**索引膨胀**、**统计信息过期**、**SQL 漂移**(业务改 SQL 没改索引)叠加导致。参见第 10 章 Vacuum。

## 二、硬件层调优

> 调优优先级:**应用 > 数据库 > OS > 硬件**。硬件是兜底层,选型错了上层怎么调都救不回来。

### 1. CPU 选择:频率 vs 核数

| 场景                  | 优先级               | 说明                                        |
|-----------------------|----------------------|---------------------------------------------|
| OLTP(高并发短查询)    | **高频** > 多核      | 单查询快慢更重要                            |
| OLAP(大查询并行)      | **多核** > 高频      | 复杂聚合、Hash Join 喜欢并行                |
| 混合负载              | 高频 + 中等核数      | 现代 PG 已能较好并行                        |

**PostgreSQL 单进程模型**:每个连接占用一个 `backend` 进程,重度依赖**单核单查询**性能。PG 14+ 引入了 leader/worker 并行查询,对 OLAP 友好。但 OLTP 的 `SELECT/INSERT/UPDATE/DELETE` 仍然是单核跑。

```text
OLTP 选型参考:
  - 主频 ≥ 3.0 GHz(3.5+ 更佳)
  - 核数:8~32 起步,看并发连接数
  - 关闭超线程(SMT)?通常不关,PG 不介意
  - 选择稳定的高频系列(Intel Xeon Gold/AMD EPYC)
```

### 2. 内存:PG 与 MySQL 内存模型不同

| 数据库   | 主缓冲机制              | 内存推荐                |
|----------|-------------------------|-------------------------|
| MySQL    | InnoDB Buffer Pool 70-80% | 全部丢给 Buffer Pool    |
| Postgres | shared_buffers **25%**    | 剩下 75% 留给 OS Page Cache |

为什么 PG 不能堆 `shared_buffers`?因为:

- PG **依赖 OS Page Cache**:数据文件 `mmap/read` 时,内核 page cache 才是大头
- PG 的 `shared_buffers` 只是**预读 / 写回 / 锁管理**的中转
- 给太多反而**双层缓冲**,浪费内存、增加锁竞争(`buf_mapping` latch)

```text
内存分配推荐(64GB 机器,OLTP):

  shared_buffers        = 16GB       ← 25%
  OS Page Cache         = ~32GB      ← 50%(实际由内核占用)
  每个连接 work_mem     = 64MB×200   ← 看连接数
  maintenance_work_mem  = 2GB        ← VACUUM/建索引专用
  WAL / Replication / 其他 = 余下
```

### 3. 磁盘:SSD vs NVMe

| 介质             | 4K 随机读 IOPS | 延迟     | 适用                        |
|------------------|----------------|----------|-----------------------------|
| SATA SSD         | 50K-100K       | 100-300µs | 小库/测试环境             |
| NVMe SSD         | 200K-1M        | 50-100µs  | 生产主库                    |
| 高端 NVMe(Optane等) | 500K+        | <50µs    | 高频写/重 IO 负载          |
| HDD(7.2K SAS)   | 150-200        | 5-10ms   | 仅备份/归档                |

**PG WAL 必须放 SSD 或 NVMe**:`fsync` 延迟直接决定事务提交上限。

```text
推荐存储分层:

  /pgdata          ← NVMe SSD(主库)
  /pgdata/pg_wal   ← 独立 NVMe(或 battery-backed RAID 卡)
  /pgdata/pg_log   ← 普通 SSD(日志 IO 不关键)
  /backup          ← HDD/S3(冷归档)
  OS /usr/local    ← SSD(无需顶级)
```

> 不要把 PG 数据盘用 RAID 5/6(写惩罚 4 倍),用 **RAID 10** 或单盘 NVMe + ZFS/Btrfs(开启副本)。

### 4. 网络

PG 主从流复制默认走 TCP,网络带宽和延迟决定复制延迟:

```text
推荐:

  - 千兆起步,万兆首选
  - 同机房内(< 1ms 延迟)RTT
  - 主从 jumbo frame(MTU 9000)开启,但需全链路支持
  - 跨地域复制 → 考虑物理专线 + 压缩
  - 心跳流量和业务流量分离(双网卡绑定)

监控指标:

  - 主从延迟秒数:SELECT EXTRACT(EPOCH FROM now() - pg_last_xact_replay_timestamp());
  - 复制槽状态:SELECT * FROM pg_replication_slots;
```

## 三、操作系统层调优

> OS 调优的边际效益远小于 SQL 调优,但在低层错误时会被放大(内核参数设错可能让 SSD 寿命缩短 50%)。

### 1. Linux 内核参数(/etc/sysctl.conf)

```bash
# /etc/sysctl.d/99-postgres.conf

# ===== 内存 =====
vm.swappiness = 1               # PG 不喜欢频繁 swap(0~1 几乎不换出)
vm.overcommit_memory = 2        # 不要 overcommit;PG fork 子进程瞬间会爆
vm.dirty_ratio = 15             # 脏页占总内存比例(默认值 20 太高)
vm.dirty_background_ratio = 5   # 后台回写触发阈值
vm.dirty_expire_centisecs = 500 # 5 秒开始回写脏页
vm.dirty_writeback_centisecs = 100 # 每秒检查

# ===== 大页(THP)=====
# Debian/Ubuntu 下 transparent_hugepage 可能坏事(MADV_HUGEPAGE 触发 fork 分配大页耗时)
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# ===== 网络 =====
net.core.somaxconn = 4096       # listen backlog(配合 listen_addresses)
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.tcp_tw_reuse = 1
net.core.rmem_max = 16777216    # 16MB 接收窗口
net.core.wmem_max = 16777216    # 16MB 发送窗口
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# ===== 文件描述符 =====
fs.file-max = 524288            # 系统级
fs.nr_open = 524288             # 单进程上限(默认 1048576)

# ===== 共享内存(大共享缓冲需要)=====
kernel.shmmax = 17179869184     # 16GB
kernel.shmall = 4194304

sysctl --system
```

> **特别注意 `vm.swappiness`**:PG 是"内存换 IO"的思路,任何 swap 都会让 SSD 写放大 + 增加 RT。生产环境通常设 `1` 而非 `0`,避免 OOM killer 启动困难。

### 2. 文件系统:ext4 vs xfs

| 文件系统 | 优点                          | 缺点                       | 选择       |
|----------|-------------------------------|----------------------------|------------|
| ext4     | 通用、稳定、`mount options` 多 | 大目录性能稍差、删大文件慢 | 通用       |
| xfs      | 大文件、并发 IO 好            | 不能缩减文件、noatime 必须开 | PG 推荐默认 |
| btrfs    | 快照、压缩                     | PG 上 CoW 写放大,慎用     | 不推荐主库 |
| zfs      | 校验、压缩、快照               | 占内存、双层缓存           | 二次选型   |

**最佳挂载选项**(ext4):

```bash
mount -o noatime,nodiratime,data=ordered,barrier=1 /dev/nvme0n1 /pgdata
# /etc/fstab
UUID=xxxx  /pgdata  ext4  noatime,nodiratime,data=ordered,barrier=1,errors=remount-ro  0  2
```

**xfs 选项**:

```bash
mount -o noatime,allocsize=64m,attr2,inode64,logbufs=8,logbsize=256k /dev/nvme0n1 /pgdata
```

> **必须开启 `noatime`**:否则每次读都会更新访问时间戳,徒增 IO。

### 3. 大页内存(HugePages)

PG 的 `shared_buffers` 在 Linux 上用 **POSIX shared memory**(`/dev/shm` 或 tmpfs),Linux 默认 4KB 页,要管理 16GB `shared_buffers` 需要 400 万个 page table entries,PTE 占满 TLB 后爆跌性能。

```bash
# 查看当前 HugePage
cat /proc/meminfo | grep Huge
# AnonHugePages:    XXXXX  kB
# HugePages_Total:       0
# HugePages_Free:        0
# HugePages_Resev:       0
# HugePages_Surp:        0
# Hugepagesize:       2048 kB

# 设置大页(2MB × 8192 = 16GB)
echo 8192 > /proc/sys/vm/nr_hugepages
# 或:
sysctl -w vm.nr_hugepages=8192
```

让 PG 使用 HugePage(选项开启即可):

```ini
# postgresql.conf
huge_pages = try             # PG 12+:try / on / off
```

- `try`:PG 尝试使用 HugePage,没有就回退到普通页(推荐)
- `on`:必须用 HugePage,否则启动失败
- `off`:不用 HugePage

> 也可以用 **NUMA-aware** 内核参数绑定 PG 进程到特定 NUMA 节点,大型机器(>32 核)推荐启用。

### 4. I/O 调度器

```bash
# 查看当前
cat /sys/block/nvme0n1/queue/scheduler
# [none] mq-deadline kyber bfq

# NVMe 一般是 [none],SSD 可选 mq-deadline
echo mq-deadline > /sys/block/sda/queue/scheduler
```

| 介质        | 推荐调度器 | 理由                      |
|-------------|------------|---------------------------|
| NVMe        | `none`     | NVMe 控制器自带调度,内核排队反而拖后腿 |
| SATA SSD    | `mq-deadline` | 合并、排序请求,适合顺序写   |
| HDD         | `bfq` 或 `mq-deadline` | 旋转盘强相关调度 |

队列深度对 SSD 影响:

```bash
# 调大队列深度,榨干 SSD 并发
echo 256 > /sys/block/nvme0n1/queue/nr_requests
echo 1024 > /sys/block/sda/queue/nr_requests
```

> 更激进的做法是用 **blk_mq 多队列**,内核 ≥ 5.x 默认启用,不用手动配置。

## 四、PG 关键配置参数调优(postgresql.conf)

> **调优前必读**:`SELECT * FROM pg_settings WHERE name IN (...)` 看当前值和单位。改完用 `SELECT pg_reload_conf();` 或 `pg_ctl restart` 应用(部分参数必须重启)。

### 1. 内存类参数

| 参数                    | 默认     | 推荐(64GB 机器) | 作用                                  |
|-------------------------|----------|------------------|---------------------------------------|
| `shared_buffers`        | 128MB    | **16GB(25%)**   | 主缓存,HOT/WARM 数据               |
| `effective_cache_size`  | 4GB      | **48GB(75%)**    | 提示优化器 OS 缓存可用量,**不是实际分配** |
| `work_mem`              | 4MB      | **64MB-256MB**   | 排序/Hash Join 每算子一次             |
| `maintenance_work_mem`  | 64MB     | **2GB**          | VACUUM/建索引/ALTER 专用              |
| `wal_buffers`           | 16MB     | **16MB**         | WAL 缓冲,>16MB 通常无意义           |
| `temp_buffers`          | 8MB      | 32MB             | 临时表缓存                            |
| `huge_pages`            | try      | try              | 见 OS 调优                            |

**经验法则**:

```text
shared_buffers = 物理内存 × 25%  (Linux)
                = 物理内存 × 40%  (Windows/容器)
effective_cache_size = 物理内存 × 50-75%(只给提示,不分配内存)
work_mem = sqrt(可用内存 × 1000),通常 64~256MB
         但小心:每个算子独立,4 个并发 JOIN 都吃 work_mem 就 OOM
maintenance_work_mem = max(2GB, RAM × 5%),越大建索引越快
```

```sql
-- 查询当前 work_mem、shared_buffers
SHOW shared_buffers;          -- 16GB
SHOW work_mem;               -- 64MB
SHOW effective_cache_size;   -- 48GB
SHOW wal_buffers;
```

### 2. work_mem 详解:最容易被调炸的参数

`work_mem` 是**单个查询内部、单算子、每次操作**的内存上限。算子包括:

- `Sort`(排序)
- `Hash Join`(哈希连接)
- `HashAggregate`(哈希聚合)
- `BitmapHeapScan`(位图堆扫描,临时位图)
- `Materialize`(物化 CTE)
- `WindowAgg`(窗口函数)

**坑**:一个查询有 5 个 Sort + 3 个 Hash Join,理论上能用到 8 × work_mem。但并发 N 个查询,理论占用 N × 8 × work_mem。

```ini
# 错误的设置:1GB + 200 并发连接 = 1.6TB 潜在内存
work_mem = 1GB

# 安全做法
work_mem = 64MB
# 或者按需:SET LOCAL work_mem = '256MB'; 在事务级临时调大
```

```sql
-- 在特定会话调大(单次 ETL)
SET work_mem = '2GB';
CREATE INDEX CONCURRENTLY idx_huge ON huge_table(col);
RESET work_mem;
```

### 3. WAL 与 checkpoint 类

| 参数                          | 默认     | 推荐            | 作用                            |
|-------------------------------|----------|-----------------|---------------------------------|
| `wal_level`                   | minimal  | logical/replica | 决定是否能复制                  |
| `wal_buffers`                 | 16MB     | 16MB            | 一般保持默认                     |
| `max_wal_size`                | 1GB      | **4~8GB**       | checkpoint 后保留的 WAL 上限     |
| `min_wal_size`                | 80MB     | 1GB             | 同上,下限                       |
| `checkpoint_timeout`          | 5min     | **15-30min**    | 两次 checkpoint 最大间隔         |
| `checkpoint_completion_target`| 0.5      | **0.9**         | 把 checkpoint 写盘散布到整段时间 |
| `checkpoint_warning`          | 30s      | 60s             | 触发太频繁时的告警阈值          |
| `wal_compression`             | off      | on              | 节省网络/磁盘(默认 zstd 旧版 pglz) |
| `wal_compression`             | off      | lz4 / zstd      | PG 15+:zstd / pglz             |

> **`max_wal_size` 调大**的好处:checkpoint 频率降低 → 写放大降低 → SSD 写寿命延长。但太大意味崩溃后恢复时间长(要从最后一个 checkpoint 重放大量 WAL)。

### 4. autovacuum 类(参见第 10 章)

```ini
# 启用 + 调激进
autovacuum = on
autovacuum_max_workers = 6                # 默认 3,大库建议 6
autovacuum_naptime = 30s                  # 检测间隔(默认 60s,小库 30)
autovacuum_vacuum_scale_factor = 0.05     # 默认 0.2,大表降到 0.02
autovacuum_analyze_scale_factor = 0.025
autovacuum_vacuum_cost_delay = 0          # SSD 设 0,否则节流
autovacuum_vacuum_cost_limit = 2000      # 默认 200,SSD 提到 2000
autovacuum_freeze_max_age = 200000000    # 别调大,否则 XID 回卷风险升高
```

```sql
-- 特定大表的 autovacuum 单独配置
ALTER TABLE huge_log SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 4000
);
```

### 5. 查询规划器类

| 参数                    | 默认 | 推荐(SSD)         | 说明                              |
|-------------------------|------|--------------------|-----------------------------------|
| `random_page_cost`      | 4.0  | **1.1**            | 随机 IO 相对顺序 IO 的代价,SSD 下改 1.1 |
| `effective_io_concurrency` | 1 | **200**            | 预读并发数,SSD 提到 200             |
| `seq_page_cost`         | 1.0  | 1.0                | 顺序 IO 代价(基准)                |
| `default_statistics_target` | 100 | 500-2000         | ANALYZE 采样,值越大统计越精确,ANALYZE 越慢 |
| `cursor_tuple_fraction` | 0.1  | 0.1                | 游标初始读取比例                   |

```ini
random_page_cost = 1.1               # SSD 关键参数
effective_io_concurrency = 200       # SSD 并发预读
default_statistics_target = 1000     # 高质量统计信息
```

为什么 `random_page_cost = 1.1` 这么重要?默认 4 假设"随机 IO 比顺序 IO 慢 4 倍"(HDD 时代),SSD 下两者只差 10%-30%:

```text
random_page_cost = 4(默认,适合 HDD):
  SELECT * FROM t WHERE id = 5;
  规划器认为:"走索引 = 4,扫表 = 1,扫表更便宜" → Seq Scan

random_page_cost = 1.1(SSD):
  同样查询:"走索引 = 1.1,扫表 = 1,差不多,索引还能少读" → Index Scan
```

### 6. 并发与连接

| 参数                  | 默认       | 推荐            | 说明                       |
|-----------------------|------------|-----------------|----------------------------|
| `max_connections`     | 100        | **200-500**     | 配合 PgBouncer 不必太高     |
| `superuser_reserved_connections` | 3 | 3          | 预留管理连接               |
| `idle_in_transaction_session_timeout` | 0 | **5min** | 杀长事务,保护 vacuum |
| `statement_timeout`   | 0          | **0 或 60s**    | 单语句最大执行时间          |
| `lock_timeout`        | 0          | 30s             | 锁等待超时                  |
| `idle_session_timeout`| 0          | 30min           | 空闲连接超时                |
| `tcp_keepalives_idle` | 0(系统默认) | 60              | 防止僵尸连接                |
| `tcp_keepalives_interval` | 0      | 10              | 同上                        |

```ini
# 推荐组合
max_connections = 200
superuser_reserved_connections = 5
idle_in_transaction_session_timeout = '5min'   # 防长事务挡 vacuum
statement_timeout = '60s'                        # 防止失控查询
lock_timeout = '30s'
tcp_keepalives_idle = 60
tcp_keepalives_interval = 10
tcp_keepalives_count = 6
```

> **黄金法则**:能用连接池就别堆 `max_connections`。每个连接占 ~10MB 内存,200 连接 = 2GB 浪费。

### 7. 日志类参数

```ini
# 慢查询(参见第 6 章、第 10 节)
log_min_duration_statement = 1000          # 1 秒以上的查询记录
```

## 五、连接层调优

### 1. 为什么需要 PgBouncer

PG 的 `backend` 进程是**进程级**的:

```text
每条连接 = ~10MB 内存 + 一个进程

5000 并发 × 10MB = 50GB 纯进程占用

而且每次 fork/wait 会涉及:
  - fork 子进程创建 backend
  - 进程切换开销
  - PG 内部缓冲(每个 backend 自己的 catalog cache)
```

PgBouncer 是**轻量级连接池**,把客户端 N 条长连接复用到底层 PG 较少的连接上。

### 2. PgBouncer 三种模式

| 模式                  | 行为                            | 场景                          |
|-----------------------|---------------------------------|-------------------------------|
| `session`             | 客户端断开才释放底层连接(默认) | 长事务、prepared statement 兼容 |
| `transaction`         | 事务结束就释放                  | **最常用,web 应用首选**       |
| `statement`           | 每个 SQL 都换底层连接          | 没有事务语义的只读                |

```ini
# /etc/pgbouncer/pgbouncer.ini
[databases]
myapp = host=127.0.0.1 port=5432 dbname=myapp
myapp_ro = host=127.0.0.1 port=5432 dbname=myapp pool_mode=transaction

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 25
reserve_pool_size = 5
reserve_pool_timeout = 3
server_idle_timeout = 600
client_idle_timeout = 0
query_wait_timeout = 60
application_name_add_host = 1
```

**关键参数**:

- `default_pool_size = 25`:一个数据库池保留 25 条到 PG 的连接
- `max_client_conn = 5000`:接受 5000 客户端连接,排队等待
- `pool_mode = transaction`:推荐模式
- `query_wait_timeout = 60`:客户端等连接最多 60 秒

```bash
# 启动
pgbouncer -d /etc/pgbouncer/pgbouncer.ini

# 查看 pool 状态
psql -h 127.0.0.1 -p 6432 -U pgbouncer pgbouncer
SHOW POOLS;
SHOW STATS;
SHOW SERVERS;
```

## 六、Schema 设计调优

> **Schema 设计决定性能上限**。SQL 调优是在这个上限里抠细节,Schema 错了再调参数也没用。

### 1. 选择合适的数据类型(参见第 3 章)

| 数据类型选择     | 错误                  | 正确             | 节省                |
|------------------|-----------------------|------------------|---------------------|
| 主键             | `UUID`                | `BIGINT`         | 索引小一半          |
| 时间戳           | `VARCHAR(64)` 存 ISO8601 | `TIMESTAMPTZ`  | 比较、索引、转换都快 |
| 金额             | `FLOAT`               | `NUMERIC(15,2)`  | 精度无损,排序正确   |
| 枚举             | `VARCHAR`             | `ENUM` 或 `smallint + lookup` | 索引效率高 |
| JSON 短数据      | `JSONB`               | `JSONB`           | 配合 GIN 索引      |
| 状态 bool        | `INT` (0/1)           | `BOOLEAN`         | 1 字节 vs 4 字节    |

**通用规则**:

```text
1. 更小的类型 → 更小的索引 → 更多缓存命中 → 更快的 IO
2. 不要用 VARCHAR(255) 存 8 字节电话号码
3. 不要用 TEXT 存日期(用 TIMESTAMPTZ,自带时区、B-Tree 友好)
4. 关联表外键必须和被引用字段类型一致(很常见错!)
5. 主键尽量用整数自增 UUID/雪花 id 适度
```

### 2. 主键选择

| 类型        | 优点                       | 缺点                            | 推荐场景        |
|-------------|----------------------------|---------------------------------|-----------------|
| `serial` / `bigserial` | 紧凑、顺序、写友好 | 单库可扩展、分布式不便         | 单库 OLTP       |
| `bigint` 雪花   | 分布式友好、有序性      | 含时间,泄露业务               | 大型分库        |
| `uuid`     | 跨库唯一、无业务含义       | 索引体积大、随机 IO             | 安全敏感场景    |
| `text` 自然主键 | 业务含义               | 字符串索引效率低                | 不推荐          |

```sql
-- serial / bigserial(单库推荐)
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT UNIQUE
);

-- 生成式 uuid(分布式推荐)
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- PG 13+
  user_id BIGINT
);

-- 复合主键(慎用,会拖慢所有外键)
CREATE TABLE user_role (
  user_id BIGINT,
  role_id BIGINT,
  PRIMARY KEY (user_id, role_id)
);
```

### 3. 规范化与反规范化

| 模式       | 优点                       | 缺点                       | 场景                    |
|------------|----------------------------|----------------------------|-------------------------|
| 第三范式   | 更新一致、冗余少            | JOIN 多、读慢               | OLTP 写多                |
| 反规范化   | 读快,避免 JOIN              | 冗余,更新不一致          | OLAP / 报表 / 高频读      |
| 分区表     | 大表拆分,查询局部            | 跨分区查询变慢            | 时间序列表                |

```sql
-- 反规范化示例:把用户名冗余到订单表,免去 JOIN
CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT,
  user_name TEXT,         -- 冗余,但免 JOIN
  amount NUMERIC(15,2),
  created_at TIMESTAMPTZ
);

CREATE INDEX idx_orders_user_name ON orders(user_name);
```

### 4. 分区表策略(参见第 4 章)

按时间分区是最常见的模式:

```sql
-- PG 10+ 声明式分区
CREATE TABLE events (
  id BIGSERIAL,
  payload JSONB,
  created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, created_at)       -- 分区键必须在主键里
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE events_2026_02 PARTITION OF events
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- 自动按月创建
SELECT cron.schedule('create-events-partition', '0 0 25 * *', $$
  DO $$
  DECLARE nxt DATE := date_trunc('month', now()) + interval '1 month';
  BEGIN
    EXECUTE format('CREATE TABLE IF NOT EXISTS events_%s PARTITION OF events
                    FOR VALUES FROM (%L) TO (%L)',
                   to_char(nxt, 'YYYY_MM'),
                   nxt, nxt + interval '1 month');
  END $$;
$$);
```

分区带来的优化:

```text
1. 查询自动裁剪(partition pruning):
   WHERE created_at >= '2026-07-01'  → 只扫对应分区
2. 删除旧数据 = DROP PARTITION(瞬间完成,几百 GB 都不怕)
3. 单个分区可以做 VACUUM FULL 不影响其他
4. 老分区可以单独搬到慢盘
```

## 七、索引调优(参见第 5 章)

### 1. 索引监控:pg_stat_user_indexes

```sql
-- 找出未使用的索引(可以删除的)
SELECT
  schemaname, relname, indexrelname,
  idx_scan,           -- 索引扫描次数
  idx_tup_read,       -- 通过索引读的行数
  idx_tup_fetched,    -- 通过索引 FETCH 的行数
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- 找出低效索引(扫得多但过滤少)
SELECT
  relname, indexrelname,
  idx_scan, idx_tup_read, idx_tup_fetched,
  CASE WHEN idx_tup_read = 0 THEN 0
       ELSE round(idx_tup_fetched::numeric / idx_tup_read * 100, 2)
  END AS fetch_ratio_pct
FROM pg_stat_user_indexes
WHERE idx_scan > 0
ORDER BY fetch_ratio_pct ASC;
```

输出示例:

```
 schemaname |  relname   | indexrelname  | idx_scan | idx_tup_read | idx_tup_fetched | size
 -----------+------------+---------------+----------+--------------+-----------------+--------
 public     | orders     | idx_orders_ts | 123456   | 9876543      | 1024            | 128MB
```

**解读**:`idx_scan` 高(13 万次),但 `idx_tup_fetched` 极低(1024),说明这是个**过滤性很差的索引**,可考虑删除或降级为 BRIN。

### 2. 索引维护

```sql
-- 索引可能膨胀:叶子页利用率< 50% 时考虑 REINDEX
-- 在线重建索引(不锁表)
REINDEX INDEX CONCURRENTLY idx_orders_ts;
REINDEX TABLE CONCURRENTLY my_table;

-- 整库重建(慎用,需要单独连接)
REINDEX DATABASE CONCURRENTLY my_db;

-- 验证索引健康
SELECT
  indexrelname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size,
  indisunique, indisprimary,
  indisvalid
FROM pg_stat_user_indexes
JOIN pg_index USING (indexrelid)
WHERE schemaname = 'public';
```

### 3. 删除无用索引

```sql
-- 1. 候选筛选(过去 N 天没有用到)
SELECT
  schemaname || '.' || relname || '.' || indexrelname AS idx_full,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'   -- 保护主键
  AND indexrelname NOT LIKE '%_unique%'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 2. 备份索引定义(以防搞错)
SELECT pg_get_indexdef(indexrelid) FROM pg_stat_user_indexes
  WHERE indexrelname = 'idx_orders_ts';

-- 3. 删除
DROP INDEX CONCURRENTLY IF EXISTS idx_orders_ts;
```

> **主键能否删除?** 不能。主键必须保留,即使查询少(它支持 `INSERT ... ON CONFLICT`,且是逻辑唯一约束)。

## 八、SQL 调优(参见第 6 章)

> **SQL 调优是 DBA 80% 工作的核心**:一条烂 SQL 可以把高端 SSD 打满,一条好 SQL 在老机器上飞快。

### 1. 避免 SELECT *

```sql
-- ✗ 错:每次都读所有列,无法走 index-only scan
SELECT * FROM orders WHERE user_id = 5;

-- ✓ 对:只取需要的列
SELECT id, amount, created_at FROM orders WHERE user_id = 5;
```

收益:

- **网络传输减少**(关键路径:web→app→db)
- **Heap 访问减少**(覆盖索引直接返回)
- **内存占用减少**(`work_mem` 排序/哈希更小)

### 2. 避免在字段上做函数计算

```sql
-- ✗ 错:导致索引失效
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
SELECT * FROM orders WHERE DATE(created_at) = '2026-08-14';
SELECT * FROM t WHERE amount + 0 = 100;       -- 等价 amount = 100,但函数包裹走不了索引

-- ✓ 对
SELECT * FROM users WHERE email = 'alice@example.com';
SELECT * FROM users WHERE email_ci = 'alice@example.com';  -- 存邮箱"小写形式"列
SELECT * FROM orders WHERE created_at >= '2026-08-14' AND created_at < '2026-08-15';
```

### 3. 优化 LIKE:避免前缀 %

```sql
-- ✗ 错:前缀通配符,B-Tree 失效
SELECT * FROM t WHERE name LIKE '%alice%';
SELECT * FROM t WHERE name LIKE '%alice';

-- ✓ 对
SELECT * FROM t WHERE name LIKE 'alice%';           -- 走 B-Tree

-- 对 '%alice%',考虑:
-- 1. trigram 扩展(支持 LIKE '%中间%' 索引加速)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_name_trgm ON t USING GIN (name gin_trgm_ops);

-- 2. 全文检索(tsvector + tsquery)
ALTER TABLE articles ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', body)) STORED;
CREATE INDEX idx_articles_tsv ON articles USING GIN (tsv);
SELECT * FROM articles WHERE tsv @@ to_tsquery('alice');
```

### 4. JOIN 优化:小表驱动大表

```sql
-- 典型反模式
SELECT u.*, o.*
FROM huge_orders o JOIN small_users u ON o.user_id = u.id;

-- PG 优化器会选合适的驱动顺序,但有时会判断错
-- 提示:用 leading 或 join_collapse_limit 调优
SET join_collapse_limit = 20;       -- 默认 8,PG 才会考虑"重新排列 JOIN 顺序"

-- 或 STRAIGHT_JOIN(MySQL 风格,PG 没有)

-- 或显式临时结果
WITH small_user AS (SELECT * FROM users WHERE status = 'active')
SELECT o.*, u.name
FROM huge_orders o JOIN small_user u ON o.user_id = u.id;
```

```ini
# 让 PG 更激进地尝试多表 JOIN 重排
join_collapse_limit = 20       # 默认 8,从 8 张起考虑
from_collapse_limit = 20       # 默认 8,把子查询上提
geqo_threshold = 16            # ≥ 16 表时启用 GE 优化器
```

### 5. IN vs EXISTS

```sql
-- 子表小(几十条):用 IN
SELECT * FROM users WHERE id IN (SELECT user_id FROM small_groups);

-- 子表大(几十万条):用 EXISTS + 相关子查询
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- IN 和 EXISTS 形式可以转换,优化器通常会选最优,但 IN 加 DISTINCT 时可能退化为去重
SELECT * FROM users WHERE id IN (SELECT DISTINCT user_id FROM orders);  -- ✗
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders GROUP BY user_id); -- ✓
```

### 6. 窗口函数(WINDOW FUNCTION)优化

```sql
-- ✗ 错:嵌套窗口
SELECT *, RANK() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
FROM (
  SELECT *, RANK() OVER (...) rn1  -- 嵌套执行
  FROM t
) sub WHERE rn1 = 1;

-- ✓ 对:一次窗口
SELECT DISTINCT ON (user_id) *
FROM t
ORDER BY user_id, created_at DESC;

-- 或 LATERAL
SELECT u.*, last_order.*
FROM users u,
LATERAL (SELECT * FROM orders o WHERE o.user_id = u.id ORDER BY o.created_at DESC LIMIT 1) last_order;
```

### 7. CTE 优化(PG 12+ 支持内联)

```sql
-- PG 12 之前:CTE 默认物化(类似临时表),可能不优
-- PG 12+:优化器会**自动内联**非递归 CTE,等价于子查询

-- 但有些场景必须物化(出现多次):
EXPLAIN
WITH expensive_query AS (SELECT * FROM huge_t WHERE ...)
SELECT * FROM expensive_query
UNION ALL
SELECT * FROM expensive_query;

-- 强制物化(即使 PG 12+)
WITH MATERIALIZED expensive_query AS (...)

-- 强制内联
WITH NOT MATERIALIZED expensive_query AS (...)
```

### 8. 通用 SQL 金句

```text
1. LIMIT 一定要带,分页用 keyset 而不是 OFFSET
   SELECT * FROM t WHERE id > last_id ORDER BY id LIMIT 50;   -- 快
   SELECT * FROM t ORDER BY id LIMIT 50 OFFSET 1000000;       -- 慢

2. 业务允许的话,COUNT(*) 改 EXISTS

3. UPSERT 用 ON CONFLICT,不要先 SELECT 再 INSERT

4. 大批量 INSERT 用 COPY,不要 INSERT VALUES (...),(...)... 5000 行

5. 批量 UPDATE 分批,避免一个长事务

6. 避免隐式类型转换
   WHERE id = 5            -- int 列,int 常量 OK
   WHERE id = '5'          -- int 列,字面量字符串,索引仍生效但底层强转
   WHERE id = '5'::text    -- int 列,显式 text → 不走索引

7. HAVING 之前用 WHERE 过滤
```

## 十、pg_stat_statements:SQL 级监控

### 1. 安装

```ini
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.max = 10000         # 默认 5000
pg_stat_statements.track = top         # top / all / none
pg_stat_statements.track_utility = on  # 跟踪 DDL
```

```sql
CREATE EXTENSION pg_stat_statements;
```

### 2. 读 pg_stat_statements

```sql
-- TOP 10 最耗时 SQL
SELECT
  substring(query, 1, 100) AS query,
  calls,
  round(total_exec_time::numeric / calls, 2) AS avg_ms,
  round(total_exec_time::numeric, 2) AS total_ms,
  rows,
  shared_blks_hit,    -- 缓存命中页
  shared_blks_read,   -- 磁盘读页
  shared_blks_written,
  local_blks_hit,
  temp_blks_read,
  temp_blks_written,  -- 写到临时磁盘 → 可能需要调大 work_mem
  blk_read_time,      -- PG 14+:IO 时间毫秒
  blk_write_time,
  pg_size_pretty((shared_blks_hit + shared_blks_read) * 8192) AS total_bufs
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

输出示例:

```
              query            | calls | avg_ms | total_ms | rows | shared_blks_hit | shared_blks_read | blk_read_time | blk_write_time
-------------------------------+-------+--------+----------+------+-----------------+------------------+---------------+----------------
 SELECT * FROM orders WHERE... | 12345 |  1234  |  15.2M   | 5678 |    1000000      |   50000          |    1234       |    0
 UPDATE users SET ...          |   234 | 8900   |  2.1M    | 2340 |   5000000       |  100000          |    890        |    234
```

### 3. 关键字段解读

| 字段                          | 解读                                  | 行动                          |
|-------------------------------|---------------------------------------|-------------------------------|
| `calls`                       | 调用次数                              | 高频优先                      |
| `total_exec_time` / `mean_exec_time` | 总/平均耗时                       | 耗时高优先                    |
| `shared_blks_hit / shared_blks_read` | 缓存命中率 = hit/(hit+read)   | < 99% 考虑加 `shared_buffers`  |
| `temp_blks_written`           | 用临时表/文件的次数/字节              | > 0 考虑加 `work_mem`         |
| `blk_read_time / blk_write_time` | 实际 IO 耗时(PG 14+ needs `track_io_timing = on`) | IO 占比高 → SSD/调优索引 |
| `rows`                        | 平均返回行数                          | 异常高可能查全表              |
| `plans`                       | 被规划次数(plan cache 命中)            | 比 calls 少太多 → 规划反复失效 |

### 4. 缓存命中率

```sql
-- 全局缓存命中率(综合 shared/local buffer)
SELECT
  sum(shared_blks_hit) / NULLIF(sum(shared_blks_hit + shared_blks_read), 0) AS shared_hit_ratio,
  sum(local_blks_hit) / NULLIF(sum(local_blks_hit + local_blks_read), 0) AS local_hit_ratio
FROM pg_stat_statements;

-- 或全局视图
SELECT
  blks_hit, blks_read,
  round(blks_hit::numeric / NULLIF(blks_hit + blks_read, 0) * 100, 2) AS hit_pct
FROM pg_stat_database WHERE datname = current_database();
```

> **命中率 < 99%**:考虑加大 `shared_buffers`,或提高 IO(SSD 替代 HDD)。

## 十一、pg_stat_activity:监控当前长事务

### 1. 查当前长事务

```sql
SELECT
  pid,
  usename,
  application_name,
  client_addr,
  state,
  now() - xact_start AS xact_duration,
  now() - query_start AS query_duration,
  wait_event_type, wait_event,
  LEFT(query, 100) AS query_preview
FROM pg_stat_activity
WHERE state IS NOT NULL
  AND state != 'idle'
  AND now() - xact_start > interval '1 minute'
```

### 1. 核心字段

```sql
SELECT
  relname,
  seq_scan,             -- 全表扫描次数
  seq_tup_read,         -- 通过 seq scan 读取的行数
  idx_scan,             -- 索引扫描次数
```

```sql
SELECT

FROM pg_stat_user_tables
WHERE heap_blks_hit + heap_blks_read > 0
ORDER BY hit_pct ASC
LIMIT 20;
```

## 十四、EXPLAIN 分析实战(参见第 6 章)

### 1. 三种 EXPLAIN 模式

```sql
-- 只看计划(快,不执行)
EXPLAIN SELECT * FROM orders WHERE user_id = 5;

-- 真实执行 + 统计信息(执行实际 SQL)
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 5;

-- 输出更多(BUFFERS、FORMAT 等)
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, TIMING, FORMAT TEXT)
  SELECT * FROM orders WHERE user_id = 5;
```

### 2. 关键指标解读

```text
看 EXPLAIN 输出的顺序:

[Sort]
  Sort Key: created_at DESC
  Sort Method: top-N heapsort  Memory: 25kB  ← 内存内排序,work_mem 充足
              external merge Disk: 123MB       ← 落盘,work_mem 不够,需调大!

[Hash Join]
  Hash Cond: (o.user_id = u.id)
  Buckets: 1024  Batches: 8                   ← 多个 batch,内存哈希失败
         ↑ 应该等 1 或 2,说明哈希表过大

[Index Scan]
  Index Cond: (user_id = 5)                   ← 命中索引
  Rows: 10 by index, Rows: 1000 by heap      ← index 定位 10 行,heap 拉 1000(索引膨胀)

[Bitmap Heap Scan]
  Recheck Cond: (status = 'paid')
  Heap Blocks: lossy=200 exact=100           ← lossy > 0 说明 work_mem 不够走 bitmap

[Nested Loop]
  Join Filter: ...
  Rows: 1 by inner → 1 by outer              ← 驱动表小、被驱动表走索引最好
```

### 3. 实战案例

**场景**:用户反馈 "后台报表每页加载 30 秒"。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT DATE_TRUNC('day', o.created_at) AS day, COUNT(*), SUM(o.amount)
FROM orders o
WHERE o.user_id IN (SELECT id FROM users WHERE tenant_id = 5)
  AND o.created_at >= '2026-07-01'
GROUP BY day
ORDER BY day;
```

输出(假设有 5 个 planner 暗示):
```
Sort  (cost=12345.67..12345.68 rows=1 width=...) (actual time=28934.234..28934.235 rows=30 loops=1)
  Sort Key: (date_trunc('day', o.created_at))
  Sort Method: quicksort  Memory: 27kB
  ->  HashAggregate  (cost=12000..12345 rows=10 width=...) (actual time=28934.000..28934.200 rows=30 loops=1)
        Group Key: (date_trunc('day', o.created_at))
        ->  Hash Join  (cost=8000..11000 rows=50000 width=...) (actual time=1200..12345 rows=100000 loops=1)
              Hash Cond: (o.user_id = u.id)
              ->  Seq Scan on orders o  (cost=0..3000 rows=50000 width=...) (actual time=0..1234 rows=50000 loops=1)
                    Filter: ((created_at >= '2026-07-01'::date) AND (user_id = ANY (...)))
                    Rows Removed by Filter: 950000         ← 关键!扫了 100 万行只 5% 命中
              ->  Hash  (cost=7500..7500 rows=10000 width=...) (actual time=234..234 rows=10000 loops=1)
                    ->  Index Scan using idx_users_tenant on users u
                          Index Cond: (tenant_id = 5)

Planning Time: 0.234 ms
Execution Time: 28934.235 ms          ← 慢!
Buffers: shared hit=35000 read=12500   ← 缓存命中率 ~74%
```

**诊断**:`Seq Scan on orders o` 扫了 1M 行 → 没有用索引。`Rows Removed by Filter: 950000` 说明索引能精确过滤。

```sql
-- 加索引(组合索引,包含子查询谓词和时间)
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);
ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT DATE_TRUNC('day', o.created_at) AS day, COUNT(*), SUM(o.amount)
FROM orders o
WHERE o.user_id IN (SELECT id FROM users WHERE tenant_id = 5)
  AND o.created_at >= '2026-07-01'
GROUP BY day
ORDER BY day;
```

优化后:
```
Planning Time: 0.3 ms
Execution Time: 234.5 ms          ← 速度提升 100 倍+
Buffers: shared hit=234 read=89    ← 缓存命中率 72% → 90%
```

### 3. 排查脚本(运维实战)

```bash
#!/bin/bash
# pg_diag.sh - 一键采集 PG 关键诊断信息
# 用法:./pg_diag.sh > /tmp/pg_diag_$(date +%F).log

PGUSER=postgres
PGDB=postgres
PSQL="psql -U $PGUSER -d $PGDB -x"

echo "===== 1. 当前连接和长事务 ====="
$PSQL -c "SELECT pid, usename, application_name, state, now()-xact_start AS xact_dur, LEFT(query, 80) AS query FROM pg_stat_activity WHERE state IS NOT NULL ORDER BY xact_start NULLS LAST;"

echo "===== 2. TOP 10 慢 SQL ====="
$PSQL -c "SELECT substring(query,1,80) AS q, calls, round(mean_exec_time::numeric,2) AS avg_ms, rows FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;"

echo "===== 3. 索引使用情况(可疑的) ====="
$PSQL -c "SELECT schemaname, relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size FROM pg_stat_user_indexes WHERE idx_scan < 50 ORDER BY pg_relation_size(indexrelid) DESC LIMIT 20;"

echo "===== 4. 表死元组 TOP 10 ====="
$PSQL -c "SELECT relname, n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables WHERE n_dead_tup > 1000 ORDER BY n_dead_tup DESC LIMIT 10;"

echo "===== 5. 锁等待 ====="
$PSQL -c "SELECT pg_class.relname AS table, mode, granted, count(*) FROM pg_locks JOIN pg_class ON pg_locks.relation = pg_class.oid GROUP BY relname, mode, granted ORDER BY count(*) DESC;"

echo "===== 6. 复制延迟 ====="
$PSQL -c "SELECT client_addr, state, sync_state, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes FROM pg_stat_replication;"

echo "===== 7. XID 年龄 ====="
$PSQL -c "SELECT datname, age(datfrozenxid) AS age, 2000000000 - age(datfrozenxid) AS remaining FROM pg_database ORDER BY age DESC LIMIT 10;"

echo "===== 8. 缓存命中率 ====="
$PSQL -c "SELECT datname, blks_hit, blks_read, round(blks_hit::numeric/NULLIF(blks_hit+blks_read,0)*100,2) AS hit_pct FROM pg_stat_database WHERE datname NOT IN ('template0','template1') ORDER BY hit_pct ASC;"
```

## 十九、核心要点速记

### 1. 调优金字塔(优先级排序)

```text
  ▲ 应用层 SQL   ← 80% 性能问题在这里
  ▲ Schema 设计
  ▲ 索引
  ▲ PG 配置参数
  ▲ 操作系统
  ▲ 硬件       ← 兜底
```

### 2. PG vs MySQL 内存模型差异

| 维度   | PostgreSQL        | MySQL InnoDB        |
|--------|-------------------|---------------------|
| 主缓冲 | shared_buffers 25% | buffer_pool 70-80% |
| OS 缓存 | PG 强依赖 OS page cache | OS cache 可选 |
| 推荐    | 留更多给 OS       | 多给 Buffer Pool    |

### 3. shared_buffers 黄金规则

- 物理内存 **25%**(Linux)/40%(Windows/容器)
- 别给太多,会让双层缓冲打架

### 4. SSD 关键参数

```ini
random_page_cost = 1.1                  # 必须改!
effective_io_concurrency = 200          # SSD 提升 IO 并发
```

不调这两个,PG 仍按 HDD 选 Plan,索引用不起来。

### 5. work_mem 陷阱

- 默认 4MB 太小,大查询落盘
- 推荐 64MB-256MB
- **并发 N × 算子数 × work_mem** 是潜在内存占用

### 6. 连接池必配

| 层     | 工具              | 作用                     |
|--------|-------------------|--------------------------|
| 应用   | HikariCP / psycopg3 | 控制到 50 以内连接    |
| 代理   | PgBouncer         | transaction 模式,5000 接 25 |
| PG     | max_connections   | 200-500                  |

### 7. 长事务是天敌

| 风险                   | 影响                           |
|------------------------|--------------------------------|
| 长事务                 | 挡 vacuum,持续膨胀            |
| 长事务                 | 推高 XID age,接近 21 亿回卷   |
| 长事务                 | 占用连接、内存,慢查询源头    |

```ini
idle_in_transaction_session_timeout = '5min'
statement_timeout = '60s'
```

### 8. 慢查询三件套

```text
1. log_min_duration_statement  ← 日志记录
2. pg_stat_statements          ← 累计 TOP N
3. auto_explain                ← 自动 EXPLAIN
配上:pgBadger 日报,慢查询整改 SOP
```

### 9. 监控核心指标

| 指标                      | 阈值                | 工具                          |
|---------------------------|---------------------|-------------------------------|
| 慢查询比例                | < 0.1%              | pg_stat_statements            |
| 缓存命中率                | > 99%               | pg_stat_database              |
| 活跃连接                  | < max_connections × 80% | pg_stat_activity         |
| 死元组比例                | < 10%               | pg_stat_user_tables           |
| XID age                   | < 1.5 亿            | pg_database                   |
| 主从延迟                  | < 10s(同机房)        | pg_stat_replication           |
| `temp_blks_written`       | = 0                 | pg_stat_statements             |
| `blk_read_time`           | < 5ms               | pg_stat_statements (PG 14+)   |
| 长事务                    | < 5min              | pg_stat_activity              |

### 10. 调参金句

- **先测量,后优化**——不要凭直觉
- **每次改一个参数**——避免相互影响
- **改完必须验证**——对比基线
- **架构 > 配置**——读写分离、分库分表往往比调参更有效
- **Schema > SQL**——Schema 错了 SQL 怎么调都难
- **YAGNI**——只在瓶颈点优化,不要过度优化非热点
- **80/20 法则**——20% SQL 占 80% 性能问题
- **autovacuum 不能关**——10 起表膨胀问题 9 个是它
- **长事务是元凶**——99% 救不了的慢都跟它有关

### 11. 一句话总结

> **PG 性能调优的本质是定位"短木板"**:从应用 → Schema → 索引 → SQL → 配置 → OS → 硬件,自上而下排查,80% 问题出现在 SQL 烂 + 索引缺 + Schema 错,只有 20% 需要调 `postgresql.conf`。**先定位,后优化;先 SQL,后参数**。
