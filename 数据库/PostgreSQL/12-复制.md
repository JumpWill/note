# PostgreSQL 复制(Replication)

## 一、PostgreSQL 复制概述

PostgreSQL 复制是指将一台 PostgreSQL 数据库服务器(**主库/Primary**)的数据变更同步到一个或多个其他服务器(**从库/Standby**)的过程。复制是构建高可用、读写分离、容灾备份体系的基石。

### 1.1 PG 复制的三大类

| 复制类型               | 传输内容           | 一致性       | 灵活度 | 引入版本     |
|------------------------|--------------------|--------------|--------|--------------|
| **物理流复制** (Streaming Replication) | 整块 WAL 字节流(物理块) | 字节级一致   | 低(整库) | 9.0+ |
| **逻辑复制** (Logical Replication)    | 行级变更(INSERT/UPDATE/DELETE) | 仅 DML,松散一致 | 高(可表级) | 10+ |
| **级联复制** (Cascading Replication)   | 中间 Standby 再向下游发 | 继承上游 | 中 | 9.2+ |

### 1.2 PG 复制的应用场景

```text
┌──────────────────────┬──────────────────────────────────────────────┐
│ 场景                 │ 推荐复制方式                                  │
├──────────────────────┼──────────────────────────────────────────────┤
│ 高可用 / 主备切换    │ 物理流复制(同步或异步)                       │
│ 读写分离 / 报表      │ 物理流复制(异步即可)                         │
│ 跨版本升级 / 迁移    │ 逻辑复制(支持跨大版本)                       │
│ 部分表数据汇聚       │ 逻辑复制(publication 精确控制)              │
│ 异地容灾             │ 物理流复制(异步 + 延迟备库)                   │
│ 多主写入             │ BDR / 第三方方案(原生不支持真正的多主)       │
│ 防误删               │ 物理流复制 + recovery_min_apply_delay         │
└──────────────────────┴──────────────────────────────────────────────┘
```

### 1.3 PG 复制与 MySQL 复制对比

| 维度                | PostgreSQL                          | MySQL                                   |
|---------------------|-------------------------------------|-----------------------------------------|
| 复制载体            | WAL(预写日志)                       | binlog(归档日志)                        |
| 主流复制方式        | 物理流复制 + 逻辑复制                | 基于 binlog 的 ROW / GTID              |
| 内置同步复制        | 支持(`synchronous_commit`)          | 原生不支持,需 MGR 或半同步插件          |
| 级联复制            | 原生支持(`cascade` 模式)            | 需手动开启 `log_slave_updates`          |
| 延迟备库            | 内置(`recovery_min_apply_delay`)    | 需第三方工具                             |
| 复制槽              | 内置(物理 + 逻辑)                   | 无原生概念,需外部协调                   |
| 跨版本/跨平台复制   | 逻辑复制天然支持                    | 主要靠 binlog,但跨大版本有兼容问题      |
| 多主                | 第三方 BDR                          | MGR / Galera                           |

## 二、物理流复制(Streaming Replication)

### 2.1 什么是流复制

**物理流复制**是 PostgreSQL 自 9.0 引入的**主流复制方案**。其核心思想是:

```text
主库持续将 WAL 段(或 WAL 记录)通过网络"流式"推送给从库,
从库通过重放(replay)WAL 实现与主库字节级一致的副本。
```

**关键特性**:

- **基于 WAL**:与 PostgreSQL 自身的事务日志(Write-Ahead Log)同源,事务提交即可被复制
- **字节级一致**:从库的数据文件与主库**完全一致**(物理块级别),不是逻辑行级
- **可热备**:从库可处于只读状态对外提供查询(称为 Hot Standby,9.0+)
- **支持级联**:从库本身可作为"上游"继续向下游推送

### 2.2 物理流复制架构图

```text
                  ┌─────────────────────────────────────────────┐
                  │                Primary (主库)                │
                  │                                              │
   Client ──SQL──>│  backend ──> walwriter ──> pg_wal/         │
                  │                    │                         │
                  │                    ↓                         │
                  │            WAL Sender Process               │
                  │              (为每个从库启动一个)            │
                  └─────────────────┬───────────────────────────┘
                                    │
                ┌───────────────────┼────────────────────┐
                │  TCP 流式传输(WAL 记录 / WAL 文件)        │
                └───────────────────┼────────────────────┘
                                    ↓
                  ┌─────────────────────────────────────────────┐
                  │           WAL Receiver Process              │
                  │           (在从库上)                          │
                  └─────────────────┬───────────────────────────┘
                                    │
                  ┌─────────────────┴───────────────────────────┐
                  │                Standby (从库)                │
                  │                                              │
                  │  Start-up Process ──> replay ──> 数据文件   │
                  │                                              │
                  │  ← 提供只读查询(Hot Standby, 9.0+)          │
                  └─────────────────────────────────────────────┘
```

**关键进程角色**:

| 进程                  | 所在  | 作用                                                     |
|-----------------------|-------|----------------------------------------------------------|
| **WAL Sender**        | 主库  | 每个从库连接对应一个 WAL Sender,负责推送 WAL 记录       |
| **WAL Receiver**      | 从库  | 接收主库发来的 WAL,写入本地 WAL 并通知 Start-up 进程   |
| **Start-up Process**  | 从库  | 应用(apply/replay)WAL 到数据文件                       |
| **Checkpointer**      | 从库  | 与主库一致的检查点节奏                                  |

### 2.3 异步 vs 同步复制

流复制在"何时算事务提交完成"上分为两种模式:

#### (1) 异步复制(默认)

```text
Client ──> 主库: BEGIN; INSERT ...; COMMIT;
主库: 写 WAL ──> commit ──> 立即返回 Client
        │
        └─> WAL Sender 异步推送(不等从库 ACK)
```

**特点**:

- 主库**不等待**从库确认,事务提交即返回
- 性能最佳(主库延迟 ≈ 本地提交)
- 主库宕机时,**已 commit 但未送达从库**的事务会**丢失**(数据丢失窗口)

#### (2) 同步复制

```text
Client ──> 主库: BEGIN; INSERT ...; COMMIT;
主库: 写 WAL ──> 同步发送给至少 1 个从库 ──> 等 ACK ──> commit ──> 返回
```

**特点**:

- 主库必须等待**至少 N 个同步 standby** 确认 WAL 已落盘才 commit
- **零数据丢失**(RPO = 0)
- 主库 commit 延迟 = 网络 RTT × ACK 数
- 任一同步 standby 挂掉,主库会被**阻塞**(直到新的同步 standby 注册)

#### (3) 同步 vs 异步对比

| 维度                 | 异步流复制                     | 同步流复制                                |
|----------------------|--------------------------------|-------------------------------------------|
| **数据丢失 (RPO)**   | 可能丢失(主库宕机)            | 0(等待从库 ACK)                          |
| **主库延迟**         | 最低                           | 增加 1~N 次网络 RTT                       |
| **写吞吐**           | 高                             | 中(每事务多 1 次网络往返)                |
| **主库切换安全**     | 需校验追上                     | 直接切换,数据已对齐                      |
| **从库挂掉影响**     | 不影响主库写入                 | 主库 commit 阻塞(直到新 standby 上来)    |
| **配置项**           | 默认                           | `synchronous_commit = on` + `synchronous_standby_names` |
| **适用场景**         | 多数互联网业务、报表分析       | 金融、强一致、零容忍丢失                  |

### 2.4 synchronous_commit vs synchronous_standby_names

这两个参数**必须配合使用**才能开启同步复制:

| 参数                          | 作用                                                          |
|-------------------------------|---------------------------------------------------------------|
| `synchronous_commit`          | 是否开启同步语义(`on` / `remote_apply` / `remote_write` / `local` / `off`) |
| `synchronous_standby_names`    | 指定哪些 standby 算作"同步候选",以及需要几个 ACK              |

**synchronous_commit 取值详解**:

```text
on                  ──> 等待 WAL 已写入主库 + 已发到所有同步 standby(本地+远程)
remote_apply        ──> 等待同步 standby 已 replay(已应用到数据文件)
remote_write        ──> 等待同步 standby 已写入 WAL(但不一定 replay)
local               ──> 仅等待本地 WAL 落盘,不等待从库
off                 ──> 异步提交,本地 WAL 都不等(最快但可能丢)
```

**synchronous_standby_names 格式**:

```text
# PG 9.6 之前
synchronous_standby_names = 'standby1, standby2'    # 任一即可,顺序敏感

# PG 9.6+ 推荐
synchronous_standby_names = 'ANY 1 (standby1, standby2)'   # 任一
synchronous_standby_names = 'FIRST 2 (s1, s2, s3)'         # 前 2 个
synchronous_standby_names = 'ANY 1 (*)'                    # 任意一个注册的同步候选
```

> 默认值是空字符串,意味着**没有同步 standby**,即便 `synchronous_commit=on` 也只保证本地落盘。

## 三、流复制原理详解

### 3.1 整体数据流

```text
  Primary                              Standby
  ┌──────────┐                         ┌──────────┐
  │ backend  │                         │ startup  │
  │ 执行SQL  │                         │ process  │
  └────┬─────┘                         └────▲─────┘
       │                                   │ notify
       ▼                                   │
  ┌──────────┐       ┌──────────┐    ┌─────┴─────┐
  │ walwriter│ ─WAL─>│ WAL      │ ──>│ WAL       │
  │ 落盘     │       │ Sender   │ TCP│ Receiver  │
  └──────────┘       └──────────┘    └─────┬─────┘
       │                  │                │ 写入 pg_wal/
       ▼                  │                ▼
  ┌──────────┐             │         ┌──────────┐
  │ pg_wal/  │             │         │ pg_wal/  │
  │ (主)     │             │         │ (从)     │
  └──────────┘             │         └──────────┘
                           │                │
                           │                ▼
                           │         ┌──────────┐
                           │         │ startup  │
                           │         │ replay   │
                           │         └────┬─────┘
                           │              ▼
                           │         数据文件 (与主库一致)
                           │
                  (可选) archiver → archive_command → WAL 归档
```

### 3.2 详细时序图

```text
时间 →

T0  Client       INSERT INTO t VALUES (1);
                │
T1  Primary     ├─ backend 写 WAL 到 wal buffers
    (backend)    ├─ walwriter 落盘到 pg_wal/00000001000000000000000A
                ├─ 事务 commit
                │
T2  WAL Sender  ├─ 感知 WAL 写入(基于 LSN)
                ├─ 通过复制连接发送到 Standby WAL Receiver
                │
T3  Standby     ├─ WAL Receiver 接收,写入 wal buffers / pg_wal
    (Receiver)  ├─ 通知 Start-up 进程有新 WAL
                │
T4  Standby     ├─ Start-up 读取 WAL record
    (Startup)   ├─ 解析并 replay(应用)到数据文件
                ├─ 维护 replay LSN
                │
T5  (同步模式)  ├─ Standby 发送 ACK(LSN)给 WAL Sender
                │
T6  WAL Sender  ├─ 收到 ACK 后,主库事务正式 commit 可见
                ├─ 返回 Client "INSERT 1 row"
                │
T7  Client      收到响应
```

**关键 LSN 标识**:

```text
WAL 写入位置     LSN = Log Sequence Number = 高 32 位 segment + 低 32 位 offset
主库写入点       pg_current_wal_lsn()
从库接收点       pg_last_wal_receive_lsn()       ← Standby 上调用
从库回放点       pg_last_wal_replay_lsn()        ← Standby 上调用
                 
同步模式下,主库 commit 时机取决于:
  write_lsn ≥ pg_last_wal_replay_lsn() (remote_apply)
  write_lsn ≥ pg_last_wal_receive_lsn() (remote_write / on)
```

### 3.3 Start-up / replay 进程

从库的 **Start-up Process** 是真正回放 WAL 的进程,持续循环:

```text
loop:
    1. 接收来自 WAL Receiver 的新 WAL(写入 pg_wal/)
    2. 读取尚未 replay 的 WAL record
    3. 调用 xlog replay 函数(每种 WAL 类型对应一个)
    4. 更新 replay LSN,持久化到磁盘 (pg_control)
    5. 通知 WAL Receiver 可以向主库回报 ACK(replay LSN)
    6. 处理 timeline history 文件(主从切换后会用到)
    7. 处理 standby.signal / 恢复参数
    8. sleep & 继续
```

**时间线 (Timeline) 概念**:每次主从切换(提升)会让 standby 进入新的时间线 ID,用于区分"上一任主"和"新主"产生的不同时期 WAL。

## 四、主从复制搭建(PG 12+ 标准流程)

> 本节基于 PG 12+ 的 `standby.signal` 机制(替换了旧版 `recovery.conf`),覆盖 PG 12 / 13 / 14 / 15 / 16 / 17。

### 4.1 环境规划

| 角色        | IP            | 端口  | PG 版本 | data 目录                |
|-------------|---------------|-------|---------|--------------------------|
| Primary     | 192.168.1.10  | 5432  | 16.3    | /var/lib/postgresql/16/main |
| Standby-1   | 192.168.1.11  | 5432  | 16.3    | /var/lib/postgresql/16/main |
| Standby-2   | 192.168.1.12  | 5432  | 16.3    | /var/lib/postgresql/16/main |

### 4.2 主库配置

编辑 `postgresql.conf`:

```ini
# ============= 主库关键参数 =============
listen_addresses = '*'                       # 监听所有地址(若跨机访问)
wal_level = replica                          # ★ 必须 replica 或 logical
                                            # replica = 支持物理流复制
                                            # logical = 同时支持逻辑复制

max_wal_senders = 10                         # ★ 允许的最大 WAL Sender 数量(从库数 + 预留)
max_replication_slots = 10                   # ★ 允许的复制槽数量

archive_mode = on                            # 推荐开启 WAL 归档
archive_command = 'cp %p /var/lib/postgresql/16/archive/%f'

wal_keep_size = 1GB                          # 保留 WAL 量(防止从库落后时被清理)
                                            # PG 13+ 取代了 wal_keep_segments

synchronous_commit = on                      # 默认即 on;开启同步复制时由 standby_names 决定是否同步
# synchronous_standby_names = 'standby1'     # 如需同步复制再打开

# 主库作为 Sender 的连接数 / 带宽 / 鉴权
wal_sender_timeout = 60s
```

**重要参数说明**:

| 参数                     | 推荐值       | 作用                                                                 |
|--------------------------|--------------|----------------------------------------------------------------------|
| `wal_level`              | `replica`    | 必须 ≥ `replica` 才能流复制;`logical` 是逻辑复制必备                |
| `max_wal_senders`        | `N + 2`      | N = 从库数,留 2 个冗余(slot、监控等)                                |
| `max_replication_slots`  | `N + 2`      | 若使用复制槽,数量足够                                                |
| `wal_keep_size`          | `1GB~10GB`   | 防从库落后时主库删 WAL(可与 archive_mode + 槽组合)                 |
| `archive_mode`           | `on`         | 配合 archive_command 归档 WAL,长期保留                              |

### 4.3 pg_hba.conf 配置(主库允许从库连接)

```conf
# /etc/postgresql/16/main/pg_hba.conf

# TYPE  DATABASE        USER            ADDRESS                 METHOD
local   replication     all                                     peer
host    replication     rep_user        192.168.1.0/24          scram-sha-256
host    replication     rep_user        192.168.1.0/24          md5
```

**关键点**:

- **DATABASE 列必须填 `replication`**(这是 PG 保留名,专用于复制连接)
- 用户名 `rep_user` 是即将创建的复制账号
- 鉴权方式 PG 14+ 推荐 `scram-sha-256`,PG 13 及以下用 `md5`

重启主库使配置生效:

```bash
systemctl reload postgresql
# 或
pg_ctl -D /var/lib/postgresql/16/main reload
```

### 4.4 主库创建复制账号

```sql
-- PG 14+
CREATE ROLE rep_user WITH REPLICATION LOGIN PASSWORD 'Rep@12345';

-- PG 13 及以下:CREATE ROLE rep_user REPLICATION LOGIN PASSWORD '...';

-- 若要限制来源网段,建议使用 pg_hba.conf 而非 host-based ACL
```

> **重要**:复制账号必须显式带 `REPLICATION` 属性,否则无法用于流复制连接。

### 4.5 从库初始化(pg_basebackup)

PG 12+ 推荐使用 `pg_basebackup` 一键完成基础备份:

```bash
# 在 Standby 上执行
pg_basebackup -h 192.168.1.10 \
              -p 5432 \
              -U rep_user \
              -D /var/lib/postgresql/16/main \
              -Fp -Xs -P -R
```

**参数说明**:

| 参数      | 含义                                                              |
|-----------|-------------------------------------------------------------------|
| `-Fp`     | 格式为 plain(目录),而非 tar                                       |
| `-Xs`     | 备份过程中流式传输 WAL(`-X fetch` 则在备份结束后再拉)            |
| `-P`      | 显示进度                                                          |
| `-R`      | **关键**:自动生成复制所需的 standby.signal 和 postgresql.auto.conf 中的 primary_conninfo |

执行完 `-R` 后,从库目录会自动生成:

```bash
ls /var/lib/postgresql/16/main/
# data/                ← 基础备份内容
# standby.signal       ← 标记这是 Standby(PG 12+ 新机制)
# postgresql.auto.conf ← 包含 primary_conninfo
```

**关键文件**:

```text
/var/lib/postgresql/16/main/standby.signal
  └─ 空文件,存在即表示"该实例以 Standby 模式启动"
     取代了 PG 12 之前的 recovery.conf

/var/lib/postgresql/16/main/postgresql.auto.conf
  └─ 包含 primary_conninfo:
     primary_conninfo = 'host=192.168.1.10 port=5432 user=rep_user password=Rep@12345 ...'
```

### 4.6 验证 primary_conninfo

```bash
cat /var/lib/postgresql/16/main/postgresql.auto.conf
```

应包含:

```text
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
primary_conninfo = 'host=192.168.1.10 port=5432 user=rep_user password=Rep@12345 application_name=standby1'
```

**手动添加 replication slot**(强烈推荐,见第六章):

```bash
echo "primary_slot_name = 'standby1_slot'" >> /var/lib/postgresql/16/main/postgresql.auto.conf
```

### 4.7 从库配置(可选)

编辑 `postgresql.conf`,加入只读、热备等参数:

```ini
# ============= 从库关键参数 =============
hot_standby = on                              # 允许只读查询(默认 on)
wal_level = replica                           # 与主库一致
max_wal_senders = 5                           # 若该从库作为级联中间节点
wal_receiver_timeout = 60s

# 同步 / 异步的 standby 命名(供主库识别)
# application_name 通常即 standby 名称,主库据此匹配 synchronous_standby_names
```

### 4.8 启动从库

```bash
# 方式 1: systemctl
systemctl start postgresql

# 方式 2: pg_ctl
pg_ctl -D /var/lib/postgresql/16/main start

# 方式 3: postgres 直接启动(便于调试日志)
postgres -D /var/lib/postgresql/16/main
```

启动后,实例会自动:

1. 检测到 `standby.signal` → 进入恢复模式
2. 读取 `primary_conninfo` → 启动 WAL Receiver 连接主库
3. 拉取 WAL → Start-up 进程 replay
4. 追上主库后进入 Hot Standby,接受只读查询

### 4.9 验证复制状态

主库端:

```sql
SELECT pid, usename, application_name, client_addr, state,
       sync_state, sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;
```

从库端:

```sql
SELECT pg_last_wal_receive_lsn() AS receive_lsn,
       pg_last_wal_replay_lsn()  AS replay_lsn,
       pg_last_xact_replay_timestamp() AS last_replay_tx;

-- 是否处于 Hot Standby
SELECT pg_is_in_recovery();
-- true = 正在恢复(从库)
```

健康标志:

```text
主库 pg_stat_replication 中 state = 'streaming' 且 walsenders ≥ 1
从库 pg_is_in_recovery() = true
从库 replay_lsn 持续追赶主库 sent_lsn
```

## 五、同步复制深度配置

### 5.1 配置项详解

```ini
# postgresql.conf(主库)

# 1. 同步候选命名:同步复制必须
synchronous_standby_names = 'ANY 1 (standby1, standby2)'

# 2. 提交等待级别
synchronous_commit = on          # 写盘 + 已发到同步 standby
# synchronous_commit = remote_apply  # 同步 standby 已 replay(更强一致)
# synchronous_commit = remote_write  # 同步 standby 已写 WAL(仅落盘未 replay)
# synchronous_commit = local         # 仅本地落盘
# synchronous_commit = off           # 异步(最快但可能丢)
```

### 5.2 同步候选匹配规则

```text
主库识别同步候选的依据:
  standby 的 application_name 必须出现在 synchronous_standby_names 列表中
  默认 application_name = 主机名或连接串指定的值
```

```sql
-- 在从库的 primary_conninfo 中指定 application_name
-- primary_conninfo = 'host=... user=... application_name=standby1'
```

### 5.3 ANY / FIRST 语法(PG 9.6+)

```text
synchronous_standby_names = 'ANY 1 (s1, s2, s3)'
   → s1/s2/s3 中任一确认即可 commit(推荐:容灾强)

synchronous_standby_names = 'FIRST 2 (s1, s2, s3)'
   → 必须按顺序前 2 个(s1,s2)都确认(强一致 + 容灾)

synchronous_standby_names = '*'
   → 所有注册同步 standby 都要确认

synchronous_standby_names = 'ANY 1 (*)'
   → 所有注册的同步 standby 中任一即可
```

### 5.4 同步复制的性能影响

```text
                    异步 (synchronous_commit=local)
                     │
                     ▼   1 次本地 fsync
                  ┌──────┐
                  │commit│ ← 主库耗时 ≈ 几毫秒
                  └──────┘

                    同步 on / remote_write
                     │
                     ▼   1 次本地 fsync + 1 次 RTT
                  ┌──────┐
                  │      │ ──── WAL 发送到 Standby
                  │commit│ ◄─── ACK(已写入 Standby WAL)
                  │      │
                  └──────┘ ← 主库耗时 = 本地 fsync + 网络 RTT

                    同步 remote_apply
                     │
                     ▼   1 次本地 fsync + 1 次 RTT + replay
                  ┌──────┐
                  │      │ ──── WAL 发送到 Standby
                  │commit│ ──── Standby replay 到数据文件
                  │      │ ◄─── ACK(已 replay)
                  └──────┘ ← 主库耗时 = 本地 fsync + 网络 RTT + Standby replay
```

**性能数据(参考)**:

```text
局域网 RTT ≈ 0.5 ms:
  异步 10000 TPS → 同步 on  ≈ 8000 TPS   (≈ 20% 下降)
  同步 remote_apply         ≈ 7000 TPS   (≈ 30% 下降,Standby 写盘慢时更明显)

跨机房 RTT ≈ 10 ms:
  同步模式 ≈ 2000~3000 TPS   (严重下降,慎用)
```

### 5.5 同步 standby 失效保护

如果唯一同步 standby 宕机,主库 commit 会**无限阻塞**。生产环境务必:

```text
方案 A: 多同步候选(ANY 1 (s1, s2))
        → 任一 standby 在,主库就不会阻塞

方案 B: 应用层短路(谨慎使用)
        SET synchronous_commit = local;  -- 在该会话级别绕过同步

方案 C: 配置同步超时
        PG 没有原生同步超时参数,需结合 replication_timeout + 监控 + 应用层处理
```

## 六、复制槽(Replication Slot)—— 重要机制

### 6.1 复制槽是什么

**复制槽(Replication Slot)** 是 PG 9.4 引入的**主从同步协调机制**:

```text
它记录从库当前的 WAL 消费位置(LSN),
主库绝不会删除"从库还没消费"的 WAL。
```

### 6.2 没有复制槽会怎样

```text
主库 checkpoint 后,WAL 段可能被自动清理(pg_archivecleanup / archive_mode + 保留策略)。

如果从库落后较多 / 长时间断连:
  主库:    WAL 段 000000010000000000000001 ~ 00000001000000000000000F
  从库:    还停留在 000000010000000000000001
  主库:    checkpoint 后,000000010000000000000001 ~ 000000010000000000000005 被删除
  从库:    需要这些 WAL → 报错 "requested WAL segment ... has already been removed"
  → 从库需要重新 pg_basebackup
```

### 6.3 复制槽工作原理图

```text
                主库 pg_wal/
   ┌────────────────────────────────────────────┐
   │ 00000001000000000000000A  ← 当前最新       │
   │ 000000010000000000000009                   │
   │ 000000010000000000000008                   │
   │ 000000010000000000000007  ← Slot 标记点    │
   │ ...                       (不能删除)        │
   │ 000000010000000000000001  ← checkpoint     │
   └────────────────────────────────────────────┘
                │
                │ checkpoint 后,理论上可删除 00000001 ~ 00000007
                │ 但 Slot 记录了从库 LSN = 7,所以这些段必须保留
                ▼
        WAL 段持续堆积(若从库不消费)
        → 主库 pg_wal 目录越来越大
```

### 6.4 物理复制槽

#### (1) 创建

```sql
-- 主库上
SELECT pg_create_physical_replication_slot('standby1_slot');
-- 返回 (slot_name, consistent_point) = ('standby1_slot', '0/3000060')
```

#### (2) 从库使用

在从库 `postgresql.auto.conf` 中加入:

```text
primary_slot_name = 'standby1_slot'
```

这样从库启动时会通知主库:"请保留名为 `standby1_slot` 槽位对应的 WAL 段"。

#### (3) 查看

```sql
SELECT slot_name, plugin, slot_type, database, active, restart_lsn
FROM pg_replication_slots;
```

| 字段            | 含义                                                              |
|-----------------|-------------------------------------------------------------------|
| `slot_name`     | 槽位名称                                                          |
| `plugin`        | 物理槽为 `NULL`;逻辑槽为输出插件名                               |
| `slot_type`     | `physical` / `logical`                                            |
| `database`      | 物理槽为 `NULL`;逻辑槽为源库名                                    |
| `active`        | `t` = 正在被从库使用;`f` = 空闲(无消费者,WAL 堆积风险!)         |
| `restart_lsn`   | 主库需要保留的最早 LSN                                            |

#### (4) 删除

```sql
SELECT pg_drop_replication_slot('standby1_slot');
```

> **警告**:`active = false` 的槽位会持续保留 WAL,造成主库磁盘爆满,必须监控并及时清理无用槽位!

### 6.5 逻辑复制槽

用于逻辑复制,详见第十章。逻辑槽记录的不是物理 LSN,而是逻辑变更位置。

```sql
SELECT pg_create_logical_replication_slot(
    'my_logical_slot',
    'pgoutput'                -- 输出插件
);
```

### 6.6 监控复制槽

```sql
-- 找出不活跃的复制槽(危险:可能导致主库 pg_wal 撑爆)
SELECT slot_name, slot_type, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag_size
FROM pg_replication_slots
WHERE NOT active;

-- 监控告警
-- active = false 且 restart_lsn 落后主库 > 10GB → 告警
```

## 七、级联复制(Cascading Replication)

### 7.1 什么是级联复制

**级联复制**:Standby 不直接连 Primary,而是连另一个 Standby,从后者再拉 WAL。

```text
  ┌──────────┐
  │ Primary  │
  └────┬─────┘
       │ (1 个 WAL Sender)
       ▼
  ┌──────────┐
  │ Standby-1│  ← 中继节点(既是下游又是上游)
  └────┬─────┘
       │ (1 个 WAL Sender)
       ├────────────┐
       ▼            ▼
  ┌──────────┐  ┌──────────┐
  │Standby-2 │  │Standby-3 │
  └──────────┘  └──────────┘
```

### 7.2 适用场景

```text
1. 主库压力分摊:从库很多时,主库只需维持 1 个流复制连接
2. 异地分发:Standby-1 在本地机房,Standby-2/3 在异地,主库无需感知异地
3. 数据分流:不同业务部门拉不同的级联节点
```

### 7.3 配置级联

#### (1) 中继节点(Standby-1)

```ini
# Standby-1 同时作为下游(连 Primary)和上游(供下游连)
wal_level = replica
max_wal_senders = 5                # ★ 必须 ≥ 1,因为它要向下游发
hot_standby = on
```

其 `primary_conninfo` 指向 Primary,并启动后自动从 Primary 拉 WAL。

#### (2) 下游节点(Standby-2)

`primary_conninfo` 指向 **Standby-1**,而非 Primary:

```text
# /var/lib/postgresql/16/main/postgresql.auto.conf
primary_conninfo = 'host=192.168.1.11 port=5432 user=rep_user password=xxx application_name=standby2'
primary_slot_name = 'standby2_slot_on_s1'
```

> 注意:下游 Standby-2 的复制槽如果建在 Standby-1 上,需要 Standby-1 允许该槽创建。

### 7.4 限制与注意事项

```text
1. 级联链路越长,延迟越大(N 跳叠加)
2. 中继节点故障 → 其下游全部断流
3. 中继节点上的 max_wal_senders 决定其可承载的下游数
4. 级联节点的 application_name 必须独立,避免与主库同步候选冲突
```

## 八、延迟备库(Delayed Standby)

### 8.1 什么是延迟备库

**延迟备库**:故意让 Standby 在 replay WAL 时**延迟一段时间**(如 1 小时),以防主库误操作(误删表、误 UPDATE)后从库立刻跟上导致数据丢失。

```text
Primary  ── WAL ──>  Standby
                        │
                        └── recovery_min_apply_delay = 1h
                            (延迟 1 小时再 replay)
```

### 8.2 配置

```ini
# postgresql.conf (Standby)
recovery_min_apply_delay = '1h'      # 延迟 1 小时应用 WAL
                                     # 也支持 '5min' / '300s' / '1d' 等格式
```

```text
生效逻辑:
  Standby 收到 WAL 后,不立即 replay,
  而是等到 WAL 中的 commit 时间 + 1h 后才 apply。
```

### 8.3 防误删流程

```text
14:00:00   主库: DELETE FROM orders WHERE status='archived';  (误删 100 万行)
14:00:01   主库: COMMIT
14:00:05   延迟备库: 收到 WAL,但 replay 时刻 = 14:00:00 + 1h = 15:00:00

14:05:00   DBA 发现误删!

方案 A: 从延迟备库恢复
  1. 停掉延迟备库: pg_ctl stop
  2. 取消延迟: 修改配置 recovery_min_apply_delay = 0
  3. 找到误删时刻前的 LSN,作为 recovery target
  4. 让该 Standby 跑到该 LSN 停止
  5. 导出数据,导入回主库

方案 B: 通过时间点恢复(PITR)从延迟备库 basebackup 导出
```

### 8.4 注意事项

```text
1. 延迟备库不适合做 HA 主备切换的候选(永远落后 1h)
2. 延迟期间 pg_wal 不会被 replay,大量堆积 WAL
3. recovery_min_apply_delay 与 synchronous_commit 无关,不影响主库性能
4. PG 9.4+ 支持
```

## 九、主从切换(Switchover / Failover)

### 9.1 Switchover(计划内切换)

**场景**:主库维护、机房搬迁、版本升级。

```text
步骤:
  1. 主库: pg_ctl stop (停止接收新写入)
  2. 等从库 replay 追上(可通过 pg_last_wal_replay_lsn 监控)
  3. 选择一个 Standby 作为新主,执行 promote
  4. 业务指向新主
  5. 原主降级为 Standby,指向新主
```

#### (1) 手动 promote(从库提升)

```bash
# 在选定的 Standby 上:
pg_ctl promote -D /var/lib/postgresql/16/main
# 或
psql -c "SELECT pg_promote();"
```

promote 触发:

- Standby 退出恢复模式
- 进入正常读写模式
- `pg_is_in_recovery()` 返回 `false`
- 自动删除 `standby.signal`(可选配置)

#### (2) 详细 switchover 流程

```text
   Primary (192.168.1.10)           Standby (192.168.1.11)
        │                                  │
   pg_ctl stop                         pg_last_wal_replay_lsn()
        │                                  │
   等待 stop 完成                       等于主库最后一次 sent_lsn
        │                                  │
        │                              pg_ctl promote
        │                                  │
        │                              Standby 退出恢复模式
        │                                  │
        │                              业务切到 192.168.1.11
        │                                  │
   修改原 primary_conninfo              │
   primary_conninfo 指向 192.168.1.11   │
   启动后自动成为新 Standby            │
        │                                  │
   START WAL Receiver                  START WAL Sender
        └──────────── 流复制恢复 ─────────┘
```

### 9.2 Failover(故障切换)

**场景**:主库宕机,无法恢复。

```text
选最佳的 Standby(数据最新、延迟最小)
   ↓
停其 WAL Receiver(可选)
   ↓
pg_ctl promote
   ↓
业务切到新主
   ↓
其他 Standby 重新指向新主
   ↓
告警 + 后续重构
```

### 9.3 自动 Failover 工具

| 工具              | 特点                                                          |
|-------------------|---------------------------------------------------------------|
| **Patroni**       | 最流行,etcd/ZooKeeper 选主,支持 PG 16+                      |
| **repmgr**        | 2ndQuadrant 开源,简单                                         |
| **pg_auto_failover** | Microsoft 开源,轻量                                         |
| **Pacemaker + Corosync** | 通用 HA 框架,可管 PG                              |
| **Pgpool-II**     | 连接池 + 部分 HA 功能                                         |

> **生产强烈建议**部署自动 Failover 工具,人工切换窗口内业务无法恢复,代价巨大。

### 9.4 时间线(History)与 split-brain 防范

```text
主库切换后,会形成 Timeline 分叉:
  Timeline 1: 老主库产生的 WAL(主库宕机前的)
  Timeline 2: 新主库 promote 后产生的 WAL

若老主库恢复后重新加入集群(没修改 primary_conninfo 指向新主),
会产生"双主脑裂",数据严重不一致。

防范:
  - 老主库恢复后必须先 standby.signal + primary_conninfo 指向新主
  - 或 Patroni/repmgr 自动处理 timeline
```

## 十、逻辑复制(Logical Replication,PG 10+)

### 10.1 逻辑复制 vs 物理复制

| 维度              | 物理流复制                   | 逻辑复制                                 |
|-------------------|------------------------------|------------------------------------------|
| 复制内容          | WAL 字节流(物理块)         | 行级变更(INSERT/UPDATE/DELETE)          |
| 一致性            | 字节级完全一致               | 仅 DML 一致(表/行级)                   |
| 灵活性            | 整库复制                     | 可精确到单表 / 单行级                   |
| 跨大版本          | 不支持(主从 PG 版本差 < 1 个大版本) | 支持(可跨大版本,如 PG 10 → PG 16) |
| 跨平台            | 不支持(主从硬件/OS 一致)    | 支持(可 Linux → Windows)               |
| DDL 复制          | 自动                         | 不自动(需手动或 pglogical 等)          |
| 大表初始化        | pg_basebackup 整库          | 仅订阅目标表(可选)                     |
| 性能开销          | 主库开销极小                 | 主库解析 WAL → 行变更,有额外 CPU       |
| 典型用途          | HA / 读写分离                | 部分同步 / 跨版本迁移 / 数据汇聚       |

### 10.2 逻辑复制核心概念

```text
Publication (发布):   主库侧,定义"我要发布哪些表的变更"
Subscription (订阅):  从库侧,定义"我要从哪个 publication 拉数据"
```

```text
Primary                          Subscriber
  ┌──────────┐                    ┌──────────┐
  │ table t1 │ ─── Publication ──>│ table t1 │ (数据流向)
  │ table t2 │   "pub_t1_t2"     │ table t2 │
  └──────────┘                    └──────────┘
       │                               │
   INSERT/UPDATE/DELETE              apply
```

### 10.3 逻辑复制优势

```text
1. 灵活:可指定只复制某些表,甚至只复制某些行的变更(行过滤)
2. 跨大版本:PG 10 主库 → PG 16 从库,完全没问题
3. 跨平台:Linux 主库 → macOS 从库,可(物理复制不行)
4. 多向汇聚:多个主库汇聚到一个分析库
5. 零停机迁移:逻辑复制追平后切换流量
```

## 十一、逻辑复制搭建

### 11.1 主库配置

```ini
# postgresql.conf
wal_level = logical                       # ★ 必须 logical(覆盖 replica)
max_replication_slots = 10               # ★ 逻辑槽数量
max_wal_senders = 10
```

```bash
pg_ctl reload
```

### 11.2 创建发布(Publication)

```sql
-- 在主库上
-- 发布整个库的指定表
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;

-- 发布 schema 下所有表
CREATE PUBLICATION pub_all FOR TABLES IN SCHEMA public;

-- 发布所有表
CREATE PUBLICATION pub_all_tables FOR ALL TABLES;

-- 添加表
ALTER PUBLICATION pub_orders ADD TABLE customers;

-- 查看
SELECT * FROM pg_publication;
SELECT * FROM pg_publication_tables;
```

**限制**:

```text
- 不能发布系统表
- 不能发布 UNLOGGED / TEMPORARY 表
- 不自动复制 DDL(CREATE/ALTER/DROP TABLE 不会同步)
- 不会复制 TRUNCATE 在某些模式(默认复制,除非指定)
```

### 11.3 从库创建订阅(Subscription)

#### (1) 准备目标表结构

逻辑复制**不会复制 DDL**,所以从库必须有相同的表结构。可以手动同步结构:

```bash
pg_dump -h primary -t orders -t order_items --schema-only > schema.sql
psql -h subscriber -f schema.sql
```

或一次性同步(包括数据):

```bash
pg_dump -h primary --section=pre-data --section=data -t orders > init.sql
psql -h subscriber -f init.sql
```

> 也可以让 Subscription 创建时**自动同步初始数据**(PG 16+,`copy_data = true`)。

#### (2) 创建订阅

```sql
-- 在从库上
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=192.168.1.10 port=5432 user=rep_user password=xxx dbname=primary_db'
    PUBLICATION pub_orders
    WITH (
        copy_data = true,                  -- 同步订阅时已有数据
        create_slot = true,                -- 自动在主库创建逻辑槽
        slot_name = 'sub_orders_slot',     -- 逻辑槽名
        synchronous_commit = off           -- 从库应用提交是否等待;off 更快
    );
```

#### (3) 查看订阅状态

```sql
-- 从库
SELECT subname, subenabled, subconninfo, subslotname, subpublications
FROM pg_subscription;

-- 详细
SELECT * FROM pg_stat_subscription;
```

### 11.4 完整示例

```text
场景: 把 PG 12 的 orders 库实时同步到 PG 16 的 analysis 库,跨大版本。
```

**主库(PG 12, IP 192.168.1.10)**:

```ini
# postgresql.conf
wal_level = logical
max_replication_slots = 5
max_wal_senders = 5
```

```sql
-- 创建发布
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
```

**从库(PG 16, IP 192.168.1.20)**:

```bash
# 同步表结构
pg_dump -h 192.168.1.10 -p 5432 -U rep_user \
    --schema-only --section=pre-data \
    -t orders -t order_items \
    > /tmp/schema.sql

psql -h 192.168.1.20 -U postgres -d analysis -f /tmp/schema.sql
```

```sql
-- 在从库创建订阅
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=192.168.1.10 port=5432 user=rep_user password=xxx dbname=primary_db'
    PUBLICATION pub_orders
    WITH (copy_data = true, create_slot = true);
```

```sql
-- 验证
SELECT * FROM pg_stat_subscription;
-- subname    | subid | pid  | relid | received_lsn | last_msg_send_time | ...
-- sub_orders | 16384 | 5678 |       | 0/3000144    | 2026-08-14 10:30:00 | ...

SELECT COUNT(*) FROM orders;
-- 数据量与主库一致(或随时间追平)
```

### 11.5 逻辑复制与物理复制对比

| 场景                         | 推荐方式      | 原因                                       |
|------------------------------|---------------|--------------------------------------------|
| 主备 HA + 故障切换           | 物理流复制    | 字节一致,DDL 自动同步                     |
| 读写分离(整库副本)          | 物理流复制    | 完整一致,无 DDL 同步顾虑                 |
| 部分表同步到 BI / 分析库     | 逻辑复制      | 灵活,可指定表                             |
| 跨大版本升级(PG 12 → 16)    | 逻辑复制      | 物理复制主从版本差有限制                   |
| 跨平台 / 跨操作系统          | 逻辑复制      | 物理复制字节级不兼容                      |
| 多主汇聚(多源 → 一库)      | 逻辑复制      | 每个源一个 Subscription                   |

## 十二、逻辑复制应用场景

### 12.1 部分数据同步(库间同步)

```text
业务主库 (PostgreSQL)            数据分析库 (PostgreSQL)
   │ orders                            │
   │ users                             │ orders(只读)
   │ logs                              │ users  (只读)
   └─ Publication: pub_bi             └─ Subscription: sub_bi
        FOR TABLE orders, users
```

只同步部分表到 BI 库,大幅降低 BI 库负担。

### 12.2 数据迁移 / 跨版本升级

```text
PG 12 (老) ─── 逻辑复制 ───> PG 16 (新)
   │
   │  1. 老库创建 Publication
   │  2. 新库作为 Subscriber 追上
   │  3. 短暂停写,确认新库数据最新
   │  4. 业务切到新库
   │  5. 删除 Subscription
   │
   ▼
零停机升级
```

### 12.3 数据汇聚(多源 → 一库)

```text
PG-A (订单) ─┐
             ├─ Publication ──>  PG-X (汇聚分析)
PG-B (支付) ─┤
             │
PG-C (用户) ─┘
```

每个源库一个 Publication,汇聚库多个 Subscription。

### 12.4 部分数据下发(总库 → 分库)

```text
PG-Master ── Publication ──> PG-Region1 (华南数据)
                └──────────> PG-Region2 (华北数据)
```

PG-Master 持有全量,通过不同 Publication 的行过滤(`WHERE` 子句)分发不同子集。

PG 15+ 支持 publication 的行过滤:

```sql
CREATE PUBLICATION pub_huanan FOR TABLE users WHERE (region = 'huanan');
```

## 十三、复制延迟监控

### 13.1 物理流复制监控

#### (1) 主库视角:`pg_stat_replication`

```sql
SELECT
    pid,                              -- WAL Sender 进程 ID
    usename,                          -- 复制账号
    application_name,                 -- 从库 application_name(同步候选匹配)
    client_addr,                      -- 从库 IP
    client_port,
    state,                            -- startup / catchup / streaming / backup / stopping
    sync_state,                       -- async / potential / sync / quorum
    sync_priority,                    -- 同步优先级
    write_lsn,                        -- 已写入主库 WAL 的位置
    flush_lsn,                        -- 已发送到的从库位置
    replay_lsn,                       -- 从库已 replay 的位置
    write_lag,                        -- 主库 commit 到从库写入的延迟
    flush_lag,                        -- 主库 commit 到从库 flush 的延迟
    replay_lag,                       -- 主库 commit 到从库 replay 的延迟
    backend_start,
    reply_time
FROM pg_stat_replication;
```

**关键字段解读**:

```text
state = streaming  → 正常流复制中
sync_state = sync   → 同步候选
sync_state = async  → 异步

replay_lag 反映"真实业务延迟":主库事务已提交 N 秒后从库才能读到

write_lag/flush_lag/replay_lag 通常用 human-readable 格式:
  "00:00:00.000123"   = 123 微秒
  "00:00:01.234"      = 1.234 秒
  "00:05:23"          = 5 分 23 秒(严重延迟)
```

#### (2) 从库视角:`pg_stat_wal_receiver`

```sql
SELECT
    pid,
    status,                            -- startup / waiting / streaming
    receive_start_lsn,
    receive_start_tli,
    written_lsn,                       -- 已写入 Standby WAL 的 LSN
    flushed_lsn,
    received_lsn,
    last_msg_send_time,
    last_msg_receipt_time,
    conninfo
FROM pg_stat_wal_receiver;
```

#### (3) 从库 replay 进度

```sql
SELECT
    pg_last_wal_receive_lsn()    AS receive_lsn,
    pg_last_wal_replay_lsn()     AS replay_lsn,
    pg_last_xact_replay_timestamp() AS last_replay_tx,
    EXTRACT(EPOCH FROM now() - pg_last_xact_replay_timestamp()) AS lag_seconds;
```

#### (4) LSN 差值监控

```sql
-- 主库上:计算每个从库的 replay lag(字节)
SELECT
    application_name,
    client_addr,
    replay_lsn,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_lag_pretty
FROM pg_stat_replication;
```

### 13.2 逻辑复制监控

```sql
-- 从库:订阅整体状态
SELECT
    subname,
    pid,
    received_lsn,
    last_msg_send_time,
    last_msg_receipt_time,
    latest_end_lsn,
    latest_end_time
FROM pg_stat_subscription;

-- 单表 apply 进度(PG 13+)
SELECT
    srsubid,
    srrelid::regclass AS table_name,
    srsubstate,                    -- init / data / sync / ready
    r.rsqname,
    received_lsn
FROM pg_subscription_rel r
JOIN pg_stat_subscription s ON r.srsubid = s.subid;
```

**srsubstate 取值**:

```text
init      → 初始化中
data      → 正在 copy 初始数据
sync      → 已同步,等待追平
ready     → 已追上,实时复制中
```

### 13.3 延迟监控告警阈值

```text
异步流复制:
  replay_lag < 5s      正常
  5s ~ 60s             警告
  > 60s                告警(从库压力大 / 主库大事务)
  > 1h                 严重(可能断连)

同步流复制:
  replay_lag 必须接近 0
  否则主库 commit 受影响

逻辑复制:
  received_lsn - latest_end_lsn 持续增大 → apply 慢,告警
```

### 13.4 综合监控 SQL(主库)

```sql
-- 一键查看所有从库的延迟情况
SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    sync_priority,
    write_lag,
    flush_lag,
    replay_lag,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes_raw,
    CASE
        WHEN pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) < 1024*1024 THEN 'OK'
        WHEN pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) < 1024*1024*100 THEN 'WARN'
        ELSE 'CRITICAL'
    END AS health
FROM pg_stat_replication
ORDER BY sync_priority, application_name;
```

## 十四、复制冲突处理

### 14.1 物理复制的"冲突"

物理复制是字节级一致,正常情况下**从库只读,无冲突**。但在以下场景可能出现:

```text
1. Hot Standby 上长查询与 WAL replay 冲突
   → 从库报错 "canceling statement due to conflict with recovery"
2. 主库与从库时钟漂移导致 timestamp 不一致(罕见)
```

#### Hot Standby 冲突参数

```ini
# postgresql.conf (Standby)
max_standby_archive_delay = 30s         # 归档 WAL 引起的冲突,最多等 30s
max_standby_streaming_delay = 30s       # 流式 WAL 引起的冲突,最多等 30s
hot_standby_feedback = on               # 从库向主库反馈"我有长查询",主库延迟清理
```

### 14.2 逻辑复制的冲突

逻辑复制场景下,从库可能被外部直接修改(虽然通常配 `subscription_destination`),产生冲突:

```text
1. 主键冲突:
   主库 INSERT id=1 → Subscriber 已有 id=1(初始数据预装时冲突)

2. UPDATE / DELETE 找不到行:
   主库 UPDATE id=1 → Subscriber 该行已被删

3. Schema 不一致:
   主库 ALTER TABLE 加列 → Subscriber 表结构未更新,apply 失败
```

### 14.3 错误查看

从库日志:

```text
ERROR: duplicate key value violates unique constraint "orders_pkey"
DETAIL: Key (id)=(1) already exists.
CONTEXT: processing remote data for replication origin "pg_16384" during "INSERT" for replication target relation "public.orders"
```

### 14.4 subscription_destination 与 skip_transaction

```sql
-- 跳过单个失败事务
ALTER SUBSCRIPTION sub_orders SKIP (lsn = '0/3000144');

-- 全部跳过(慎用)
ALTER SUBSCRIPTION sub_orders SET (slot_name = NONE);  -- 先停
-- 手动处理后再 enable
ALTER SUBSCRIPTION sub_orders ENABLE;
```

### 14.5 排查脚本

```sql
-- 找最近失败的复制事务
SELECT
    remote_lsn,
    local_lsn,
    received_lsn,
    last_msg_send_time,
    last_msg_receipt_time,
    latest_end_lsn,
    latest_end_time
FROM pg_stat_subscription
WHERE subname = 'sub_orders';
```

日志路径:`$PGDATA/pg_log/` 或 `log_directory` 配置下,关键词 `replication origin`。

## 十五、BDR(Bi-Directional Replication)

### 15.1 什么是 BDR

**BDR(Bidirectional Replication)** 是 PostgreSQL 的双向复制方案(由 2ndQuadrant 开源,现 EDB 维护):

```text
BDR 允许多个 PostgreSQL 节点同时接受写入,
变更在节点间双向同步,实现地理分布式多主。
```

### 15.2 与原生复制对比

| 维度              | 原生流复制                  | 原生逻辑复制               | BDR                              |
|-------------------|-----------------------------|----------------------------|----------------------------------|
| 多主写入          | 不支持                      | 不支持(单主多从)          | 支持                            |
| 冲突处理          | 无冲突                      | 单向无冲突                  | 内置冲突检测(DDL 仍需避免)    |
| 一致性            | 强(单主)                   | 弱                          | 最终一致(冲突可能短暂数据分裂) |
| 复杂度            | 低                          | 中                          | 高                              |
| 适用              | HA / 读写分离               | 部分同步 / 迁移            | 跨地域多活(强一致需求弱)     |

### 15.3 BDR 适用场景

```text
- 跨地域多活(每个地域有本地写入)
- 异地双活容灾
- 分布式写集群
```

### 15.4 注意事项

```text
1. BDR 与 PostgreSQL 主线版本绑定,版本兼容性需关注
2. 业务层应避免同一行多端并发写(由冲突检测兜底,但影响性能)
3. DDL 必须通过 BDR 专用函数执行(bdr.replicate_ddl_command)
4. 不是"强一致多主",只是"最终一致多主"
```

## 十六、复制与 MySQL 对比总结

| 维度                  | PostgreSQL 物理流复制           | PostgreSQL 逻辑复制            | MySQL binlog 复制                |
|-----------------------|----------------------------------|--------------------------------|----------------------------------|
| **复制载体**          | WAL(物理+逻辑解析后)           | 逻辑解析后的行变更             | binlog(ROW/STATEMENT/MIXED)      |
| **内置同步复制**      | 是(`synchronous_commit`)       | 否(需外部协调)               | 否(需半同步插件 / MGR)          |
| **复制槽**            | 内置物理 + 逻辑槽               | 同左                           | 无原生概念,需外部 HA 工具        |
| **延迟备库**          | 内置(`recovery_min_apply_delay`)| 否                             | 需第三方 pt-slave-delay          |
| **级联复制**          | 原生                            | 原生                           | 需 `log_slave_updates`           |
| **跨大版本**          | 不支持(主从版本差有限)        | 支持                           | 不支持跨大版本(主)              |
| **跨平台**            | 不支持                          | 支持                           | 不支持                           |
| **DDL 同步**          | 自动                            | 不自动                         | ROW 模式自动,STATEMENT 受限    |
| **HA 工具**           | Patroni, repmgr                 | pglogical 等                  | MHA, MGR, Orchestrator          |
| **多主**              | 第三方 BDR                      | 不支持                        | MGR / Galera                     |
| **PG 默认 wal_level** | `replica`                       | `logical`                     | N/A                              |
| **配置复杂度**        | 中                              | 中                             | 中                                |
| **运维心智负担**      | 中(物理槽、archive 必懂)      | 中(DDL / 冲突需理解)         | 中(GTID / binlog 位点)           |
| **主流用途**          | HA + 读写分离 + 容灾           | 跨版本 / 部分同步 / 汇聚      | HA + 读写分离 + 容灾            |

**核心差异总结**:

```text
PostgreSQL:   流复制默认异步 + 内置同步切换 + 复制槽防 WAL 丢失 + 逻辑复制跨版本
MySQL:        binlog 复制默认异步 + 半同步插件 + GTID 定位 + 逻辑复制靠 binlog ROW 模式

PG 的"同步复制"是 PG 9.1 以来就有的"原生一等公民",
MySQL 要 MGR(Paxos)才能做到真正的同步多写。
PG 的"逻辑复制"是 PG 10+ 的内置特性,跨大版本很顺;
MySQL 跨大版本复制一直是个坑。
```

## 十七、核心要点速记

- **PG 复制三大类**:物理流复制(整库,字节一致)/ 逻辑复制(表/行级,灵活)/ 级联复制(拓扑分摊)
- **物理流复制载体**:`wal_level = replica` 产生的 WAL 字节流
- **逻辑复制载体**:`wal_level = logical` 解析后的行变更(publication/subscripion 模型)
- **流复制三大进程**:WAL Sender(主) / WAL Receiver(从) / Start-up / replay(从)
- **同步 vs 异步**:`synchronous_commit = on` + `synchronous_standby_names = 'ANY 1 (...)'` = 同步;否则异步
- **synchronous_commit 取值**:`on` / `remote_apply` / `remote_write` / `local` / `off`,由弱到强
- **复制槽(关键)**:防主库 WAL 被删、从库没拉到;必须监控 `active = false` 的槽
- **复制槽分类**:物理槽(用于流复制,`restart_lsn` 物理 LSN)/ 逻辑槽(用于逻辑复制,`restart_lsn` 逻辑位点)
- **PG 12+ 关键变化**:用 `standby.signal` 空文件 + `postgresql.auto.conf` 中的 `primary_conninfo` 取代 `recovery.conf`
- **pg_basebackup -R**:一键生成 standby.signal + primary_conninfo,推荐搭建方式
- **同步候选匹配**:从库的 `application_name` 必须出现在主库的 `synchronous_standby_names` 中
- **synchronous_standby_names 语法**:PG 9.6+ 支持 `ANY 1 (...)` / `FIRST N (...)` / `*`
- **延迟备库**:`recovery_min_apply_delay = '1h'` 防误删;PG 9.4+ 支持
- **级联复制**:`max_wal_senders ≥ 1` 即可,中继节点既是下游又是上游
- **切换**:`pg_ctl promote` 或 `SELECT pg_promote()`;Switchover 计划内,Failover 故障后
- **Patroni / repmgr**:生产推荐自动 Failover 工具,避免人工切换窗口
- **逻辑复制不复制 DDL**:Subscriber 表结构需手动同步(可 `pg_dump --schema-only`)
- **逻辑复制跨大版本**:PG 10 → PG 16 完全没问题;物理复制主从版本差有限制
- **逻辑复制冲突**:`ALTER SUBSCRIPTION ... SKIP (lsn = ...)` 跳过失败事务
- **延迟监控三件套**:主库 `pg_stat_replication` / 从库 `pg_stat_wal_receiver` / `pg_last_wal_replay_lsn()`
- **replay_lag 单位**:human-readable(如 `00:00:01.234` = 1.234 秒)
- **BDR**:第三方多主方案,适用跨地域多活,但不是强一致
- **PG vs MySQL 关键区别**:PG 内置同步复制与复制槽;MySQL 靠半同步插件与外部工具
- **生产推荐架构**:异步流复制 + 复制槽 + 至少 2 个 Standby + Patroni 自动 Failover + 归档 WAL
- **同步复制性能代价**:局域网 RTT 0.5ms 时下降 20-30%,跨机房 RTT 10ms 时下降 70%+
- **复制槽丢失风险**:从库宕机后,其复制槽 `active = false` 但 `restart_lsn` 仍保留 WAL → 主库磁盘撑爆 → 必须监控并清理
- **物理 vs 逻辑复制决策**:HA/读写分离用物理;跨版本/部分同步/汇聚用逻辑
- **`pg_is_in_recovery()`**:true = Standby,false = Primary
