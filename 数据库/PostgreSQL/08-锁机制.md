# PostgreSQL 锁机制 (Lock Mechanism)

## 一、PostgreSQL 锁概述

### 1. 为什么需要锁

PostgreSQL 是一个**多用户并发访问**的关系数据库,同一时刻可能有上百个 backend 进程同时读写同一张表。如果没有锁的保护,**数据一致性**将彻底崩塌。

锁的核心使命是:**在并发访问下,保证事务的隔离性、数据的完整性与一致性**。

```text
                       并发访问的典型问题

   事务 A                            事务 B
     │                                  │
     ├── SELECT balance FROM account    │
     │   WHERE id = 1;   -- 读到 100    │
     │                                  ├── UPDATE account
     │                                  │   SET balance = 50
     │                                  │   WHERE id = 1;
     ├── UPDATE account                │
     │   SET balance = balance - 30    │   ← 已读到旧值 100
     │   WHERE id = 1;                 │
     │                                  │
     ▼                                  ▼
   最终 balance = 70 (期望)
   实际 balance = 20 (丢失更新!)
```

### 2. PostgreSQL 的两种并发控制机制

PostgreSQL 通过 **MVCC + 锁** 协同工作来实现并发控制,这与 MySQL InnoDB 的设计思路**非常类似但又不完全相同**。

| 机制      | 实现方式              | 解决的问题               | 典型应用 |
|-----------|-----------------------|--------------------------|----------|
| **MVCC**  | 每行保存多个版本(xmin/xmax) | 读写不冲突、快照隔离     | 普通 SELECT / DML |
| **锁**    | 阻塞式同步           | 写写互斥、约束保护、并发作业 | DDL、Advisory Lock、行级冲突 |

**重要差异**:

- PostgreSQL 的 **MVCC 默认隔离级别是 Read Committed**(非 Repeatable Read),快照读只在每个**语句**开始时建立,而不是事务开始时。
- PostgreSQL 的**行级锁不是放在独立的锁结构中**,而是直接**存储在行头的 `xmax` 与 `infomask` 字段**中,通过可见性判断自然形成"锁"。
- PostgreSQL 没有 MySQL 那种独立的 **Gap Lock / Next-Key Lock** 机制,它通过 **MVCC + 行级锁 + 唯一索引检查** 的组合来实现类似效果。

### 3. SQL 标准的事务隔离级别

```sql
-- 查看当前隔离级别
SHOW transaction_isolation;
-- PostgreSQL 默认: READ COMMITTED
```

| 隔离级别                | 脏读 | 不可重复读 | 幻读 | PG 实现 |
|-------------------------|------|-----------|------|---------|
| **READ UNCOMMITTED**    | ✔ (实际未使用,等同 RC) | ✔ | ✔ | PG 把所有级别都当成"至少 RC" 实现 |
| **READ COMMITTED** ★    | ✘    | ✔         | ✔    | 默认,语句级快照 |
| **REPEATABLE READ**     | ✘    | ✘         | ✔    | 事务级快照(MVCC,不靠 Gap Lock) |
| **SERIALIZABLE**        | ✘    | ✘         | ✘    | SSI(Serializable Snapshot Isolation) |

> **PostgreSQL 默认是 READ COMMITTED**,通过 **MVCC + 行级锁** 实现,**不依赖 Next-Key Lock**,这一点与 MySQL InnoDB 有根本性差异。

### 4. PostgreSQL 锁体系全景

```text
                        PostgreSQL 锁体系

   ┌─────────────────────────────────────────────────────────┐
   │                  表级锁 (Table-Level)                    │
   │  ACCESS SHARE / ROW SHARE / ROW EXCLUSIVE / ... /        │
   │  ACCESS EXCLUSIVE (共 8 种)                              │
   ├─────────────────────────────────────────────────────────┤
   │                  行级锁 (Row-Level)                      │
   │  FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY   │
   │  SHARE (存储在行头 xmax + infomask,不是独立数据结构)    │
   ├─────────────────────────────────────────────────────────┤
   │                  页级锁 (Page-Level)                     │
   │  仅在某些特殊索引操作中使用(很少暴露给用户)              │
   ├─────────────────────────────────────────────────────────┤
   │                  应用级锁 (Advisory Lock)                │
   │  会话级 / 事务级 / 非阻塞                                │
   ├─────────────────────────────────────────────────────────┤
   │                  其他内部锁                              │
   │  关系扩展锁、虚拟事务锁、WAL Insert 锁、               │
   │  CLOG 锁、子事务锁、Background Worker 锁...             │
   └─────────────────────────────────────────────────────────┘
```

## 二、锁分类总览

### 1. 按粒度划分

| 粒度 | 典型对象 | 开销 | 并发度 | 死锁概率 | 备注 |
|------|----------|------|--------|----------|------|
| 表级锁 | 整张表 / 元数据 | 小   | 低     | 中       | 8 种,DDL/部分 DML 自动加 |
| 行级锁 | 单行元组 | 小   | 极高   | 中       | 存储在行头,无独立锁表 |

| 应用级锁 | 任意 64-bit key | 极小 | 中     | 低       | 业务层自行控制 |

### 2. 按共享/排他划分

| 类型 | 英文 | 简称 | PG 中的别名 |
|------|------|------|--------------|
| **共享锁** | Shared Lock | **S** | `ShareLock` |
| **排他锁** | Exclusive Lock | **X** | `ExclusiveLock` |

## 三、表级锁 (Table-Level Locks)

**表级锁**是 PostgreSQL 锁体系中**最常用、最直观**的部分。它通过 `LOCK TABLE` 命令显式加锁,或者被 **DDL/DML 语句隐式** 加上。

### 1. 八种表级锁总览

| 锁名 | 别名 | 触发语句 | 冲突(阻塞) |
|------|------|----------|-------------|
| **ACCESS SHARE** | `AccessShareLock` | `SELECT` | ACCESS EXCLUSIVE |
| **ROW SHARE** | `RowShareLock` | `SELECT ... FOR UPDATE/SHARE` | EXCLUSIVE, ACCESS EXCLUSIVE |
| **ROW EXCLUSIVE** | `RowExclusiveLock` | `INSERT`, `UPDATE`, `DELETE` | SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| **SHARE UPDATE EXCLUSIVE** | `ShareUpdateExclusiveLock` | `VACUUM` (非 FULL), `ANALYZE`, `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| **SHARE** | `ShareLock` | `CREATE INDEX` (非 CONCURRENTLY) | ROW EXCLUSIVE, SHARE UPDATE EXCLUSIVE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| **SHARE ROW EXCLUSIVE** | `ShareRowExclusiveLock` | 触发器 / `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` | ROW EXCLUSIVE, SHARE UPDATE EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| **EXCLUSIVE** | `ExclusiveLock` | `LOCK TABLE ... IN EXCLUSIVE MODE` | ROW SHARE, ROW EXCLUSIVE, SHARE UPDATE EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| **ACCESS EXCLUSIVE** | `AccessExclusiveLock` | `ALTER TABLE`, `DROP TABLE`, `TRUNCATE`, `REINDEX`, `VACUUM FULL`, `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` | **所有锁** |

### 2. 完整兼容矩阵(★ 重点)

| 已持 \ 申请 | ACCESS SHARE | ROW SHARE | ROW EXCL | SHARE UPD EXCL | SHARE | SHARE ROW EXCL | EXCLUSIVE | ACCESS EXCL |
|-------------|:------------:|:---------:|:--------:|:--------------:|:-----:|:--------------:|:---------:|:-----------:|
| **ACCESS SHARE** | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✘ |
| **ROW SHARE** | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✘ | ✘ |
| **ROW EXCLUSIVE** | ✔ | ✔ | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ |
| **SHARE UPDATE EXCLUSIVE** | ✔ | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **SHARE** | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **SHARE ROW EXCLUSIVE** | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **EXCLUSIVE** | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **ACCESS EXCLUSIVE** | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |

```text
记忆口诀(由弱到强):

  ACCESS SHARE       ← 最弱,SELECT 加
   ↓
  ROW SHARE          ← SELECT FOR 加
   ↓
  ROW EXCLUSIVE      ← INSERT/UPDATE/DELETE 加
   ↓
  SHARE UPDATE EXCL  ← VACUUM/ANALYZE 加
   ↓
  SHARE              ← CREATE INDEX 加
   ↓
  SHARE ROW EXCL     ← 触发器加
   ↓
  EXCLUSIVE          ← 较严,pg_dump 不用
   ↓
  ACCESS EXCLUSIVE   ← 最强,ALTER/DROP/TRUNCATE

  ★ 强锁会阻塞所有弱于它的锁
  ★ 只有"同级别同模式"才能并发(如 SHARE 与 SHARE 兼容)
```

### 3. 每种锁的典型场景

#### (1) ACCESS SHARE — 与 SELECT 对应

```sql
-- 自动加上,无需用户干预
SELECT * FROM user WHERE id = 1;
-- 表上加 ACCESS SHARE

-- 只有 ACCESS EXCLUSIVE 才能阻塞它
-- 也就是说:做 ALTER TABLE 时,所有未提交的 SELECT 都会卡住
```

#### (2) ROW SHARE — 与 SELECT FOR UPDATE/SHARE 对应

```sql
BEGIN;
SELECT * FROM user WHERE id = 1 FOR UPDATE;
-- 表上加 ROW SHARE
-- 阻止 EXCLUSIVE 与 ACCESS EXCLUSIVE
```

#### (3) ROW EXCLUSIVE — 与 INSERT/UPDATE/DELETE 对应

```sql
BEGIN;
INSERT INTO user (name) VALUES ('alice');
-- 表上加 ROW EXCLUSIVE
-- 阻止 SHARE 系列与 EXCLUSIVE 系列
```

#### (4) SHARE UPDATE EXCLUSIVE — 与 VACUUM/ANALYZE 对应

```sql
-- VACUUM (非 FULL)
VACUUM user;
-- 加 SHARE UPDATE EXCLUSIVE
-- 自身互斥(多个 VACUUM 不能同时跑在同一表上)

-- ANALYZE
ANALYZE user;

-- CREATE INDEX CONCURRENTLY (不阻塞 DML)
CREATE INDEX CONCURRENTLY idx_user_name ON user(name);
```

#### (5) SHARE — 与 CREATE INDEX 对应

```sql
-- 普通建索引会阻塞所有写入
CREATE INDEX idx_user_name ON user(name);
-- 表上加 SHARE 锁
```

#### (6) SHARE ROW EXCLUSIVE — 与触发器对应

```sql
-- 添加 / 修改触发器
CREATE TRIGGER trg_user_ai
BEFORE INSERT ON user
FOR EACH ROW EXECUTE FUNCTION audit_func();
-- 加 SHARE ROW EXCLUSIVE 锁
```

#### (7) EXCLUSIVE — 较严,极少自动使用

```sql
-- 手动加锁(几乎不用)
LOCK TABLE user IN EXCLUSIVE MODE;

-- 与所有写操作冲突,但允许普通 SELECT
```

#### (8) ACCESS EXCLUSIVE — 最强锁

```sql
-- ALTER / DROP / TRUNCATE / VACUUM FULL / REINDEX / CLUSTER
ALTER TABLE user ADD COLUMN age INT;
DROP TABLE user;
TRUNCATE user;
VACUUM FULL user;
REINDEX TABLE user;

-- 同时会阻塞所有 SELECT(连快照读都被阻塞!)
```

### 4. 显式加锁命令

```sql
-- 语法: LOCK TABLE table_name IN lock_mode MODE [NOWAIT]

LOCK TABLE user IN ACCESS EXCLUSIVE MODE;
LOCK TABLE user IN SHARE MODE;
LOCK TABLE user IN ROW EXCLUSIVE MODE;

-- NOWAIT: 拿不到锁立即报错,不等待
LOCK TABLE user IN EXCLUSIVE MODE NOWAIT;
-- ERROR: 55P03  could not obtain lock on row in relation "user"

-- 多个表
LOCK TABLE user, order_log IN SHARE UPDATE EXCLUSIVE MODE NOWAIT;
```

## 四、行级锁 (Row-Level Locks)

**行级锁**是 PostgreSQL DML 并发的核心。它的实现方式与 MySQL InnoDB **截然不同**:锁信息**直接存储在元组(tuple)的行头**,而不是维护一个独立的内存锁表。

### 1. 四种行级锁

| 锁 | 命令 | 阻塞 | 被阻塞 |
|----|------|------|--------|
| **FOR UPDATE** | `SELECT ... FOR UPDATE` | FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE | 其他事务的所有行锁 |
| **FOR NO KEY UPDATE** | `SELECT ... FOR NO KEY UPDATE` / `UPDATE` (未改键) | FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE | FOR KEY SHARE |
| **FOR SHARE** | `SELECT ... FOR SHARE` | FOR UPDATE, FOR NO KEY UPDATE | FOR SHARE |
| **FOR KEY SHARE** | `SELECT ... FOR KEY SHARE` | FOR UPDATE | FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE |

```text
记忆口诀:

  FOR UPDATE          ← 最强,会阻塞所有其他行锁
  FOR NO KEY UPDATE   ← 改"非键"列,允许别人读键
  FOR SHARE           ← 锁键、阻止改键,但允许读非键
  FOR KEY SHARE       ← 最弱,只阻止改键
```

### 2. 行级锁的存储原理 — Tuple Header

**PostgreSQL 行级锁的核心秘密:锁信息存在行头**。

```text
  HeapTuple (数据行) 的行头结构:

   ┌────────────────────────────────────────────────────┐
   │  HeapTupleHeaderData                              │
   │  ┌──────────────────────────────────────────────┐  │
   │  │ t_xmin     (4B)  插入该行的事务 ID           │  │
   │  │ t_xmax     (4B)  删除/锁住该行的事务 ID      │  │
   │  │ t_cid      (4B)  命令 ID (cmin/cmax)        │  │
   │  │ t_infomask (2B)  标志位(关键!)              │  │
   │  │ t_hoff     (1B)  数据起始偏移                │  │
   │  │ ...                                           │  │
   │  └──────────────────────────────────────────────┘  │
   │  ... 用户列数据                                    │
   └────────────────────────────────────────────────────┘

   当事务 A 执行 FOR UPDATE 时:
     ① 把行的 xmax 设为 A 的事务 ID
     ② 在 infomask 上打上 HEAP_XMAX_LOCK_ONLY 标志
     ③ 不真的删除/更新行

   当事务 B 也想锁这行时:
     ① 看到 xmax 是某个未提交事务 A 的 ID
     ② 去 Active Transaction 数组里查 A 的状态
     ③ 若 A 未提交,B 必须等待(锁等待队列)
     ④ 若 A 已回滚,B 立刻获得锁(很关键的优化!)
```

### 3. 为什么 PostgreSQL 没有"锁表"(与 MySQL 关键差异)

```text
                   PostgreSQL                MySQL InnoDB
   ┌─────────────────────────────┐    ┌─────────────────────────────┐
   │  行锁存在 Heap Tuple 的      │    │  行锁存在独立的              │
   │  xmax + infomask 上         │    │  memory lock structure       │
   │                             │    │                             │
   │  优点:                      │    │  优点:                       │
   │   ✓ 不需要"锁升级"          │    │   ✓ 锁信息集中、易查询       │
   │   ✓ 锁随行落盘(I/O 后即知) │    │   ✓ 支持显式 Gap Lock       │
   │   ✓ 锁不占内存(共享开销低) │    │   ✓ 死锁检测有 lock dep 图   │
   │                             │    │                             │
   │  缺点:                      │    │  缺点:                       │
   │   ✗ 锁信息分散,查询较慢     │    │   ✗ 行锁太多时内存膨胀       │
   │   ✗ 没有显式 Gap Lock       │    │   ✗ 锁升级表锁(实际不是真升级)│
   │   ✗ 锁监控需读 pg_locks    │    │                             │
   └─────────────────────────────┘    └─────────────────────────────┘
```

### 4. 行级锁的完整命令

```sql
-- 加排他行锁(最强)
SELECT * FROM user WHERE id = 1 FOR UPDATE;

-- 加 NO KEY UPDATE 锁(改非键列时隐式使用)
SELECT * FROM user WHERE id = 1 FOR NO KEY UPDATE;

-- 加共享行锁
SELECT * FROM user WHERE id = 1 FOR SHARE;

-- 加 KEY SHARE 锁(最弱)
SELECT * FROM user WHERE id = 1 FOR KEY SHARE;

-- 组合 NOWAIT / SKIP LOCKED
SELECT * FROM task_queue
WHERE status = 'pending'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;   -- ★ PG 9.5+

SELECT * FROM user WHERE id = 1 FOR UPDATE NOWAIT;
```

### 5. 行级锁与隔离级别的关系

| 隔离级别 | SELECT(无 FOR) | SELECT FOR UPDATE |
|----------|-----------------|---------------------|
| READ COMMITTED | 快照读(MVCC,读已提交的最新版本) | 等同于 REPEATABLE READ 行为 |
| REPEATABLE READ | 事务级快照 | 行锁,持续到事务结束 |
| SERIALIZABLE | 事务级快照 + SSI 检测 | 行锁 + SSI 谓词锁检查 |

> **关键**:在 **READ COMMITTED** 下,`UPDATE/DELETE` 会先读最新提交版本再尝试加锁;在 **REPEATABLE READ** 下,使用事务开始时的快照。

## 五、页级锁 (Page-Level Locks)

### 1. 什么是页级锁

**页级锁**是对**单个数据页 (block/page,默认 8KB)** 的锁,在 PostgreSQL 中**很少暴露给用户**,主要用于:

- 索引页分裂时的同步
- HOT(Heap-Only Tuples)更新链维护
- 某些后台进程的页内操作

### 2. 在 Next-Key 锁概念上的差别

**PostgreSQL 没有像 MySQL 那样显式的 Gap Lock**,但实际效果上,某些操作会产生**等价的间隙锁效应**:

```sql
-- 准备
CREATE TABLE t (id INT PRIMARY KEY);
INSERT INTO t VALUES (10), (20), (30);

-- 会话 A
BEGIN;
SELECT * FROM t WHERE id = 20 FOR UPDATE;
-- 锁 id=20 这一行(xmax 标记)

-- 会话 B
INSERT INTO t VALUES (15);  -- ★ 不阻塞!MVCC 允许它先插入
-- 但提交时,会话 A 重复执行相同 SELECT:
-- 会看到 id=20,但看不到 id=15(快照读)
-- 若会话 A 是 UPDATE/DELETE,会按当前最新提交版本处理

-- 这与 MySQL 的"Next-Key Lock 阻塞 INSERT" 完全相反!
```

### 3. 死锁在页级锁中的触发场景

```text
页级锁的典型死锁场景 — 索引分裂:

   索引页 P1                    索引页 P2
   ┌─────────┐                 ┌─────────┐
   │ [10][30]│                 │ [50][70]│
   │         │                 │         │
   │ 会话 A  │                 │ 会话 B  │
   │ 加 PIN  │                 │ 加 PIN  │
   └─────────┘                 └─────────┘

   会话 A 想在 P1 插入 [20]      会话 B 想在 P2 插入 [40]
   需要 LwLock 加锁            需要 LwLock 加锁
   ↓                            ↓
   但插入可能引发 P1 分裂到 P2  但插入可能引发 P2 分裂到 P1
   ↓                            ↓
   互相等对方的页锁 → 死锁
   ↓
   PG 死锁检测器自动处理
```

## 六、死锁 (Deadlock)

### 1. 什么是死锁

**死锁**:两个或多个事务**互相等待对方释放锁**,形成**循环等待**。

```text
                    死锁的循环等待

       事务 A                      事务 B
          │                            │
          ├─ 持有 row_id=10 的 X 锁    │
          │                            ├─ 持有 row_id=20 的 X 锁
          │                            │
          ├─ 等待 row_id=20 ─────→    │
          │                            │
          │      ←──── 等待 row_id=10 ┤
          │                            │
          ▼                            ▼
       谁也走不动 → PG 检测到死锁
       → 终止其中一个事务(报错 40P01)
```

### 2. PostgreSQL 的处理策略

PostgreSQL **自动检测死锁**,发现后**主动终止其中一个事务**(通常回滚代价最小的事务),让其他事务继续。

```text
  错误码: 40P01
  错误信息:
    ERROR:  deadlock detected
    DETAIL: Process 1234 waits for ShareLock on transaction 5678;
            blocked by process 5679.
            Process 5679 waits for ShareLock on transaction 5678;
            blocked by process 1234.
    HINT:   See server log for query details.
```

**配置项**:

```sql
-- 控制死锁检测的开销(默认 1s 检测一次)
SHOW deadlock_timeout;     -- 默认 1s
SET deadlock_timeout = '500ms';
```

### 3. 死锁产生的四大必要条件

| 条件 | 含义 |
|------|------|
| **互斥** | 锁是排他的(X 锁不能共享) |
| **持有并等待** | 事务持锁不放,继续申请新锁 |
| **不可剥夺** | 锁只能由持有者主动释放(回滚或提交) |
| **循环等待** | 形成 T1 → T2 → T3 → ... → T1 |

> **打破任一条件即可避免死锁**,最常用的是**打破"循环等待"**,即**统一锁顺序**。

### 4. 死锁排查流程

```text
        死锁排查标准流程

   Step 1: 应用报错 ERROR 40P01
            → 捕获该错误码

   Step 2: 立即查 pg_locks 找阻塞关系
            SELECT * FROM pg_locks WHERE NOT granted;

   Step 3: 用 pg_blocking_pids() 反向追溯
            SELECT pg_blocking_pids(pid);

   Step 4: 看 pg_stat_activity 查 SQL
            SELECT pid, query, state, query_start
            FROM pg_stat_activity
            WHERE pid IN (...);

   Step 5: 看 PostgreSQL 日志
            日志中会有完整的 deadlock detail
            (log_lock_waits = on 才记录)
```

## 七、锁等待与超时

### 1. 三种超时参数

| 参数 | 默认值 | 作用范围 | 适用 |
|------|--------|----------|------|
| **lock_timeout** | `0`(永不超时) | 所有锁等待 | 一般建议设,防止无限等待 |
| **statement_timeout** | `0`(永不超时) | 单条 SQL 执行 | 设置过严会误杀长查询 |
| **idle_in_transaction_session_timeout** | `0`(永不超时) | 事务闲置(打开但没操作) | 防长事务占锁 |

```sql
-- 设置锁等待超时(单位:ms)
SET lock_timeout = '5s';          -- 锁等待最多 5 秒

-- 设置单语句超时
SET statement_timeout = '30s';

-- 设置空闲事务超时
SET idle_in_transaction_session_timeout = '60s';

-- 会话级
SET SESSION lock_timeout = '5s';
```

### 2. 三种超时错误码

```text
  超时类型                        错误码    错误信息
  ─────────────────────────────────────────────────────────────
  lock_timeout                    55P03    cancel statement due to lock timeout
  statement_timeout               57014    canceling statement due to statement timeout
  idle_in_transaction_…           25P02    terminating connection due to idle-in-transaction timeout
  query_canceled (Ctrl+C)         57014    canceling query due to user request
```

### 3. 锁等待的完整生命周期

```text
  事务 T 申请行锁
       │
       ▼
  xmax 指向事务已提交? ── 是 ──→ 立即获锁
       │
       否(指向活动事务)
       │
       ▼
  加入等待队列(LOCK LOCK)
       │
       ▼
  lock_timeout 超时? ── 是 ──→ 报 55P03
       │
       否
       │
       ▼
  后台死锁检测器定期扫描(deadlock_timeout)
       │
       ├─ 发现循环 ──→ 报 40P01 deadlock detected
       │
       └─ 未发现
            │
            ▼
        持有者提交/回滚
            │
            ▼
        唤醒等待者,获锁,继续
```

## 八、锁的查看方法

### 1. pg_locks 视图(★ 最核心)

**`pg_locks`** 是 PostgreSQL 查看锁信息的**核心视图**,每个 backend 进程持有的每一把锁都在这里。

#### (1) 字段完整解读

| 字段 | 含义 |
|------|------|
| `locktype` | 锁类型:`relation`(表) / `tuple`(行) / `transactionid`(事务) / `advisory`(应用锁) / `extend`(扩展) / `page`(页) / `object` |
| `database` | 数据库 OID,`pg_database.oid` |
| `relation` | 表/索引的 OID,`pg_class.oid` |
| `page` | 页号(仅 page 类型锁) |
| `tuple` | 元组号(仅 tuple 类型锁) |
| `virtualxid` | 虚拟事务 ID |
| `transactionid` | 事务 ID |
| `pid` | 持有此锁的 backend 进程 PID |
| `mode` | 锁模式:`AccessShareLock`、`RowExclusiveLock`、`ExclusiveLock` 等 |
| `granted` | `t` 已获得,`f` 在等待 |
| `fastpath` | 是否走快路径(fastpath,本地内存优化) |

#### (2) 实用查询 — 当前所有未授予的锁

```sql
SELECT
    pg_class.relname,
    pg_locks.locktype,
    pg_locks.mode,
    pg_locks.granted,
    pg_locks.pid,
    pg_stat_activity.query,
    pg_stat_activity.state,
    pg_stat_activity.query_start,
    age(now(), pg_stat_activity.query_start) AS waiting_time
FROM pg_locks
LEFT JOIN pg_class ON pg_locks.relation = pg_class.oid
LEFT JOIN pg_stat_activity ON pg_locks.pid = pg_stat_activity.pid
WHERE NOT pg_locks.granted
ORDER BY pg_stat_activity.query_start;
```

#### (3) 实用查询 — 行级锁的详细信息

```sql
-- 找出当前所有 tuple-level 锁
SELECT
    pg_locks.pid,
    pg_class.relname,
    pg_locks.locktype,
    pg_locks.mode,
    pg_locks.granted,
    pg_locks.tuple,
    pg_locks.transactionid
FROM pg_locks
JOIN pg_class ON pg_locks.relation = pg_class.oid
WHERE pg_locks.locktype = 'tuple'
  AND pg_locks.granted;
```

### 2. pg_stat_activity 视图

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,              -- active / idle / idle in transaction / fastpath function call
    query,
    xact_start,         -- 事务开始时间
    query_start,        -- 当前语句开始时间
    wait_event_type,    -- 等待类型:Lock / LWLock / IO / IPC
    wait_event,         -- 等待具体事件
    age(now(), xact_start) AS xact_duration,
    age(now(), query_start) AS query_duration
FROM pg_stat_activity
WHERE state IS NOT NULL
ORDER BY xact_start;
```

**关键状态**解读:

| state | 含义 |
|-------|------|
| `active` | 正在执行查询 |
| `idle` | 等待客户端新命令 |
| `idle in transaction` | 事务中但没操作(**危险状态**) |
| `idle in transaction (aborted)` | 事务中且有错误,需 ROLLBACK |
| `fastpath function call` | 调用快路径内置函数 |
| `disabled` | 跟踪被禁用 |

### 3. pg_blocking_pids() 函数

```sql
-- 找出某个 PID 被哪些进程阻塞
SELECT pg_blocking_pids(pid);

-- 反向:哪些进程被这个 PID 阻塞
SELECT pg_blocking_pids(12345);
-- 返回: int[]  例如 {6789, 6790}
```

**完整阻塞链路查询**:

```sql
WITH RECURSIVE blocking_tree AS (
    SELECT
        pid,
        pg_blocking_pids(pid) AS blockers
    FROM pg_stat_activity
    WHERE state = 'active'
      AND wait_event_type = 'Lock'
)
SELECT
    a.pid AS waiting_pid,
    a.usename,
    a.query,
    b.pid AS blocking_pid,
    b.query AS blocking_query,
    b.state AS blocking_state
FROM blocking_tree t
JOIN pg_stat_activity a ON a.pid = t.pid
CROSS JOIN UNNEST(t.blockers) AS bp(pid)
JOIN pg_stat_activity b ON b.pid = bp;
```

### 4. 完整排查 SQL 模板

```sql
-- ========= 模板 1: 当前所有锁等待 =========
SELECT
    blocked_locks.pid     AS blocked_pid,
    blocked_activity.usename  AS blocked_user,
    blocking_locks.pid   AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query    AS blocked_statement,
    blocking_activity.query   AS current_statement_in_blocking_process,
    blocked_activity.application_name AS blocked_application,
    blocking_activity.application_name AS blocking_application
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity
    ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.pid != blocked_locks.pid
    AND blocking_locks.granted
JOIN pg_catalog.pg_stat_activity blocking_activity
    ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;

-- ========= 模板 2: 长事务清单(锁等待源头) =========
SELECT
    pid,
    usename,
    state,
    xact_start,
    age(now(), xact_start) AS duration,
    query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active')
ORDER BY xact_start
LIMIT 20;
```

## 九、Advisory Lock (应用级锁)

### 1. 什么是 Advisory Lock

**Advisory Lock** 是 PostgreSQL 特有的**应用级锁**,由用户**自己定义 key**(整数对或单个 int8)并**自己决定语义**。数据库不强制其含义,完全由应用层协议约束。

```sql
-- 锁的 key 是一个 bigint 或两个 int
pg_advisory_lock(42);                    -- 单 int8
pg_advisory_lock(1, 2);                   -- 双 int4 (key1, key2)
```

### 2. 三类 Advisory Lock

| 函数 | 是否阻塞 | 释放时机 |
|------|----------|----------|
| **`pg_advisory_lock(key)`** | 阻塞 | 必须显式 `pg_advisory_unlock` |
| **`pg_advisory_xact_lock(key)`** | 阻塞 | 事务结束时自动释放 |
| **`pg_try_advisory_lock(key)`** | 非阻塞,返回 bool | 必须显式解锁 |
| **`pg_try_advisory_xact_lock(key)`** | 非阻塞 | 事务结束自动释放 |

```sql
-- 阻塞获取(会话级,即使在事务外也保持)
SELECT pg_advisory_lock(42);   -- 返回 void,拿不到则等

-- 事务级(自动释放,更安全)
BEGIN;
SELECT pg_advisory_xact_lock(1, 100);
-- ... 业务逻辑
COMMIT;    -- 自动释放

-- 非阻塞(立即返回)
SELECT pg_try_advisory_lock(42);
--  true: 拿到
--  false: 拿不到,不等待

-- 解锁
SELECT pg_advisory_unlock(42);   -- 必须配对 pg_advisory_lock
```

### 3. 应用场景

#### (1) 分布式锁

```sql
-- 实现"全局只允许一个实例执行某任务"
CREATE OR REPLACE FUNCTION do_cron_job() RETURNS void AS $$
BEGIN
    -- 用一个固定 key 锁住
    IF pg_try_advisory_xact_lock(1, 1) THEN
        -- 拿到锁,执行实际任务
        PERFORM refresh_materialized_view('user_stats');
    ELSE
        -- 没拿到锁,说明其他实例正在做
        RAISE NOTICE '另一个 worker 已在执行';
    END IF;
END;
$$ LANGUAGE plpgsql;
```

#### (2) 防止并发任务

```sql
-- 一个订单只能被一个 worker 处理
BEGIN;
SELECT * FROM task_queue
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- 在任务上加 advisory lock,防止其他进程同时改
SELECT pg_advisory_xact_lock(hashtext('task:' || task_id));

-- ... 业务处理 ...

COMMIT;
```

#### (3) 抢占式资源分配

```sql
-- 限制"同时最多 N 个进程执行"
-- key 用资源 ID,两个进程想拿同一资源 → 只有一个拿到
BEGIN;
SELECT pg_advisory_xact_lock(hashtext('slot:' || resource_id));
-- ... 抢占 ...
COMMIT;
```

### 4. Advisory Lock 与事务的边界

```text
  会话级(pg_advisory_lock):
    ┌─────────────┐
    │ 会话启动    │ ← 拿锁
    │  ...        │
    │  ...        │ ← 跨事务保持
    │  ...        │
    │ COMMIT      │ ← 不释放
    │  ...        │
    │  ...        │
    │ 显式 unlock │ ← 必须
    │ 会话关闭    │ ← 自动释放
    └─────────────┘

  事务级(pg_advisory_xact_lock):
    ┌─────────────┐
    │ BEGIN       │ ← 拿锁
    │  ...        │
    │  ...        │
    │ COMMIT      │ ← ★ 自动释放
    └─────────────┘

  ★ 推荐优先用 xact 版本,避免忘记 unlock 导致泄漏
```

### 5. 查看 Advisory Lock

```sql
-- 找出当前所有 advisory lock
SELECT
    locktype,
    granted,
    mode,
    pid,
    classid,    -- 双 int key 的第一部分
    objid       -- 双 int key 的第二部分
FROM pg_locks
WHERE locktype = 'advisory';

-- 与应用层映射:
-- SELECT hashtext('user:42')   ← 应用先计算好 hash
-- 再用 SELECT pg_advisory_lock(hashtext('user:42'))
```

## 十一、死锁案例分析

### 案例 1:两表交叉更新导致的死锁

```sql
CREATE TABLE account (id INT PRIMARY KEY, balance INT);
CREATE TABLE order_log (id INT PRIMARY KEY, user_id INT, amount INT);

INSERT INTO account VALUES (1, 100), (2, 100);
INSERT INTO order_log VALUES (100, 1, 50), (200, 2, 30);
```

```text
死锁时序图:

  时刻    事务 A                              事务 B
  ─────  ─────────────────────────────────  ─────────────────────────────────
  T1     BEGIN;                              BEGIN;
  T2     UPDATE account                      UPDATE order_log
          SET balance = balance - 50          SET amount = amount + 10
          WHERE id = 1;                       WHERE id = 100;
          -- 锁 account.id=1                  -- 锁 order_log.id=100
  T3                                       UPDATE account
                                             SET balance = balance + 50
                                             WHERE id = 1;
                                             -- ★ 等 A 释放 account.id=1
  T4     UPDATE order_log
          SET amount = amount - 50
          WHERE id = 100;
          -- ★ 等 B 释放 order_log.id=100
  T5     -- A 等 B,B 等 A → 死锁
  T6     PG 检测到循环等待
          → 报 40P01 deadlock detected
          → 回滚其中一个事务
```

```text
           死锁形成的"等待图"

                ┌──────────────────────┐
                ▼                      │
   事务 A 持 account.id=1       事务 B 持 order_log.id=100
                │                      │
                │ 申请 order_log.id=100 │
                └────► 等待 ◄──────────┘
                        │
                        │ 申请 account.id=1
                        └─────► 回到 A
                          循环 = 死锁
```

**解决**:统一访问顺序,**先 account 后 order_log**,或按 ID 升序排序。

### 案例 2:SERIALIZABLE 隔离级别的 SSI 死锁

```sql
SET transaction_isolation = 'SERIALIZABLE';

-- 事务 A
BEGIN;
SELECT SUM(balance) FROM account WHERE id > 0;   -- 谓词读
-- 不加显式行锁,但 PG 记下谓词:id > 0 的快照

-- 事务 B
BEGIN;
UPDATE account SET balance = balance + 100 WHERE id = 1;
COMMIT;

-- 事务 A
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- ★ 报: could not serialize access due to read/write dependencies
--      among transactions (40001 serialization_failure)
```

**解决**:应用捕获 40001 错误并重试。

### 案例 3:Advisory Lock 嵌套导致的"假死锁"

```sql
-- 事务 A
BEGIN;
SELECT pg_advisory_xact_lock(100);
SELECT pg_advisory_xact_lock(200);
-- ...
COMMIT;

-- 事务 B
BEGIN;
SELECT pg_advisory_xact_lock(200);
SELECT pg_advisory_xact_lock(100);   -- ★ 等 A
COMMIT;
```

```text
   事务 A 持 100,申请 200
   事务 B 持 200,申请 100

   A → 200 ← B
   ↑         ↓
   └──── 100 ─┘

   → 真死锁!PG 会检测并报错
```

**解决**:所有应用**统一锁顺序**(先小后大或按业务约定)。

### 案例 4:批量更新与单行更新的冲突

```sql
-- 100 万行
CREATE TABLE big_table (id INT PRIMARY KEY, v INT);

-- 会话 A
BEGIN;
UPDATE big_table SET v = v + 1 WHERE id BETWEEN 1 AND 1000000;
-- 持 100 万个行锁,事务很长

-- 会话 B
BEGIN;
UPDATE big_table SET v = v + 1 WHERE id = 500000;
-- ★ 等 A 释放 id=500000

-- 等不到 → 超时(若设了 lock_timeout)
```

**解决**:分批提交(`LIMIT 10000`),或设 `lock_timeout`。

### 案例 5:VACUUM 与写入的死锁

```sql
-- autovacuum 跑在后台,加了 SHARE UPDATE EXCLUSIVE
-- 但用户 UPDATE 想加 ROW EXCLUSIVE
-- 通常不冲突(SUE 与 RE 兼容)

-- 但如果是 VACUUM FULL(需 ACCESS EXCLUSIVE),会阻塞所有读写
VACUUM FULL big_table;   -- ★ 严禁高峰期做
```

### 案例 6:同一个连接内多个事务的"自己等自己"

```text
  一个 backend(同一连接)开多个事务时:

  BEGIN;
    UPDATE t SET ... WHERE id = 1;
    -- 此时同一 backend 想再开 BEGIN?
    -- PG 不允许嵌套事务(BEGIN 在事务中只是警告)

  但若用 SAVEPOINT / 子事务:
    SAVEPOINT s1;
      UPDATE t WHERE id = 1;
      -- 自己再访问同行的另一操作?
      -- 同一 backend 不冲突(共享 xid 状态)
```

## 十二、锁与隔离级别的关系

| 隔离级别 | 锁行为 | 适用场景 |
|----------|--------|----------|
| **READ COMMITTED** | 语句级快照,行锁读到最新已提交版本 | 默认,适合大多数 OLTP |
| **REPEATABLE READ** | 事务级快照,行锁基于快照(可能报 "could not serialize" 等) | 一致性报表 |
| **SERIALIZABLE** | SSI(Serializable Snapshot Isolation),检测读写依赖 | 强一致业务(财务) |

```text
  隔离级别对行级锁的影响:

  ┌─────────────────┬──────────────────────────────────────────┐
  │ READ COMMITTED │  UPDATE 先读最新提交版本,再尝试加锁         │
  │                │  若冲突,等待并可能重试("could not find")    │
  ├─────────────────┼──────────────────────────────────────────┤
  │ REPEATABLE     │  UPDATE 基于事务快照,锁基于快照中版本      │
  │ READ           │  冲突时直接报"could not serialize access"  │
  ├─────────────────┼──────────────────────────────────────────┤
  │ SERIALIZABLE   │  同 RR,加 SSI 谓词依赖检测                 │
  │                │  复杂依赖关系下回滚 40001                  │
  └─────────────────┴──────────────────────────────────────────┘
```

## 十三、优化建议

### 1. 核心原则

```text
              PostgreSQL 锁优化"五条铁律"

   1. 事务要短   → 持有锁的时间越短越好
   2. 顺序要统一 → 打破循环等待
   3. 粒度要合理 → 行锁为主,表锁慎用
   4. 隔离够用就行 → 默认 RC,不强求 SERIALIZABLE
   5. NOWAIT/SKIP LOCKED 用起来 → 减少无谓等待
```

### 2. 减少长事务

```sql
-- 设置空闲事务超时
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '30s';

-- 监控长事务
SELECT
    pid,
    state,
    xact_start,
    age(now(), xact_start) AS duration,
    query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active')
  AND age(now(), xact_start) > interval '1 minute'
ORDER BY xact_start;
```

### 3. 合理选择锁粒度

```sql
-- 反例:用 LOCK TABLE 锁整表(超粗)
LOCK TABLE user IN EXCLUSIVE MODE;
SELECT * FROM user WHERE id = 1;

-- 正例:用行级锁
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

### 4. 使用 NOWAIT / SKIP LOCKED

```sql
-- NOWAIT: 拿不到立即报错
SELECT * FROM user WHERE id = 1 FOR UPDATE NOWAIT;

-- SKIP LOCKED: 跳过已锁行,典型用于队列
SELECT * FROM task_queue
WHERE status = 'pending'
LIMIT 10
FOR UPDATE SKIP LOCKED;

-- 应用层配合: 处理 55P03 错误
```

### 5. SKIP LOCKED 实现工作队列

```text
   任务队列应用:

   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │  Worker  │    │  Worker  │    │  Worker  │
   │   A      │    │   B      │    │   C      │
   └────┬─────┘    └────┬─────┘    └────┬─────┘
        │ SELECT ... SKIP LOCKED LIMIT 10 │
        └────────────────┬──────────────────┘
                         ▼
   ┌─────────────────────────────────────────┐
   │           task_queue 表                  │
   │  id │ status   │ locked_by │ ...         │
   │  1  │ pending  │ NULL      │             │
   │  2  │ pending  │ NULL      │             │
   │  3  │ processing │ A       │             │
   │  4  │ processing │ B       │             │
   │  5  │ pending  │ NULL      │             │
   └─────────────────────────────────────────┘

   ★ 多个 worker 并发抢任务,各取未锁定的,互不阻塞
   ★ 比 SELECT FOR UPDATE 快得多(不会无限等待)
```

### 6. 配置项建议

```postgresql
# postgresql.conf 推荐配置
lock_timeout = '5s'                           # 防止无限等待
statement_timeout = '60s'                     # 防止慢查询占锁
idle_in_transaction_session_timeout = '60s'   # 防止僵尸事务
deadlock_timeout = '1s'                       # 死锁检测频率
log_lock_waits = on                           # 记录锁等待日志
```

### 7. 应用层规范

| 规范 | 说明 |
|------|------|
| **统一锁顺序** | 多表操作时按固定顺序加锁 |
| **捕获 40P01/55P03/40001** | 死锁、锁等待、序列化失败的错误码 |
| **捕获后重试** | 死锁/序列化失败应自动重试 1~3 次 |
| **事务只放 DB 操作** | 不在事务内做 HTTP/RPC 调用 |
| **大批量操作分批** | `LIMIT 1000` 每批提交一次 |

## 十四、与 MySQL InnoDB 锁机制对比

### 1. 整体对比表

| 维度 | MySQL InnoDB | PostgreSQL |
|------|--------------|------------|
| 默认隔离级别 | REPEATABLE READ | READ COMMITTED |
| Next-Key Lock | **有**,显式防幻读 | **无**,靠 MVCC + 行锁 |
| Gap Lock | REPEATABLE READ 默认有 | 无 |
| 行锁存储 | 独立内存锁表 | Tuple 行头 xmax + infomask |
| 锁表查看 | `performance_schema.data_locks` | `pg_locks` |
| 阻塞者查看 | `sys.innodb_lock_waits` | `pg_blocking_pids()` |
| 死锁处理 | 自动回滚一个 | 自动回滚一个 |
| 隔离级别强一致 | SERIALIZABLE 用 Next-Key | SERIALIZABLE 用 SSI |
| 表锁数量 | 表锁 + MDL + 意向锁 | 8 种表级锁 |
| 应用级锁 | `GET_LOCK()` | `pg_advisory_lock()` |
| NOWAIT/SKIP LOCKED | 8.0+ 支持 | 9.5+ 支持 |
| 长事务监控 | `information_schema.innodb_trx` | `pg_stat_activity` |
| 自增锁 | AUTO-INC 锁(模式 0/1/2) | 序列(无显式自增锁) |

### 2. 关键差异详解

#### (1) 行锁存储方式

```text
  MySQL InnoDB:
    行锁 → 独立 memory 结构 → 需要额外内存
    删除行时,锁仍占内存一段时间
    大量行锁可能撑爆 lock_pool

  PostgreSQL:
    行锁 → 行头 xmax → 不占额外内存
    删除行时,锁随 tuple 一起落盘
    但需读行才能知道锁状态
```

#### (2) Next-Key Lock vs MVCC

```text
  MySQL 防幻读:
    SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE
    → 加 Next-Key Lock (10, 20],阻塞区间内所有 INSERT

  PostgreSQL 防幻读:
    SELECT ... WHERE id BETWEEN 10 AND 20
    → 不加锁,MVCC 读快照(本事务看不到其他事务新增)
    即使 FOR UPDATE,也只是锁已存在的行,不阻塞 INSERT
```

#### (3) 锁升级

```text
  MySQL:可能锁升级(行锁过多 → 表锁)
  PostgreSQL:永不锁升级(行锁始终是行锁)
             但表级锁可能被自动加上(如 VACUUM FULL)
```

#### (4) 应用级锁

```sql
-- MySQL 应用级锁
SELECT GET_LOCK('user:42', 10);   -- 10s 超时
SELECT RELEASE_LOCK('user:42');
-- 锁名是 string,有命名空间

-- PG 应用级锁
SELECT pg_advisory_lock(42);       -- 单 int8
SELECT pg_advisory_lock(1, 42);    -- 双 int4
-- 用 hash 把业务 key 转成 int
```

### 3. 选择建议

| 场景 | 推荐 |
|------|------|
| 简单 OLTP,大量范围查询 | MySQL InnoDB(Gap Lock 防幻读更直接) |
| 复杂查询、JSONB、自定义类型 | PostgreSQL(MVCC + 行锁更灵活) |
| 强一致报表 | PostgreSQL SSI |
| 任务队列、并发作业 | PostgreSQL SKIP LOCKED / MySQL 8.0 SKIP LOCKED |

## 十五、核心要点速记

### 1. PostgreSQL 锁体系速查

```text
         PostgreSQL 锁机制核心体系

  ┌──────────────┐ ┌──────────────┐ ┌─────────────────────┐
  │ 表级锁 8 种  │ │ 行级锁 4 种  │ │ 应用级 Advisory Lock │
  │ 最强 ACCESS │ │ FOR UPDATE   │ │  会话级 / 事务级    │
  │ EXCLUSIVE   │ │ / NO KEY     │ │  阻塞 / 非阻塞      │
  │              │ │ / SHARE      │ │                     │
  │              │ │ / KEY SHARE  │ │                     │
  └──────────────┘ └──────────────┘ └─────────────────────┘
            ↓               ↓                  ↓
         pg_locks       tuple xmax       pg_locks(advisory)
```

| **AS**(ACCESS SHARE) | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✘ |
| **RS**(ROW SHARE) | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✘ | ✘ |
| **RE**(ROW EXCLUSIVE) | ✔ | ✔ | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ |
| **SUE** | ✔ | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **S**(SHARE) | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **SRE** | ✔ | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **EX**(EXCLUSIVE) | ✔ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |
| **AE**(ACCESS EXCLUSIVE) | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ | ✘ |

### 3. 行级锁兼容矩阵

| 已持 \ 申请 | FOR UPDATE | FOR NO KEY UPDATE | FOR SHARE | FOR KEY SHARE |
|-------------|:----------:|:-----------------:|:---------:|:-------------:|
| **FOR UPDATE** | ✘ | ✘ | ✘ | ✘ |
| **FOR NO KEY UPDATE** | ✘ | ✘ | ✘ | ✔ |
| **FOR SHARE** | ✘ | ✘ | ✔ | ✔ |
| **FOR KEY SHARE** | ✘ | ✔ | ✔ | ✔ |

### 4. 关键 SQL 速查

```sql
-- 查看锁
SELECT * FROM pg_locks WHERE NOT granted;
SELECT * FROM pg_locks WHERE locktype = 'tuple';

-- 查看进程
SELECT pid, state, query, xact_start, wait_event_type, wait_event
FROM pg_stat_activity
WHERE state IS NOT NULL;

-- 找阻塞者
SELECT pg_blocking_pids(<pid>);

-- 杀进程
SELECT pg_cancel_backend(<pid>);       -- 取消当前查询(温和)
SELECT pg_terminate_backend(<pid>);    -- 杀死整个连接(强硬)

-- 设置超时
SET lock_timeout = '5s';
SET idle_in_transaction_session_timeout = '60s';

-- 行级锁
SELECT ... FOR UPDATE;
SELECT ... FOR NO KEY UPDATE;
SELECT ... FOR SHARE;
SELECT ... FOR KEY SHARE;
SELECT ... FOR UPDATE NOWAIT;
SELECT ... FOR UPDATE SKIP LOCKED;

-- 表级锁
LOCK TABLE ... IN ACCESS EXCLUSIVE MODE;
LOCK TABLE ... IN EXCLUSIVE MODE NOWAIT;

-- 应用级锁
SELECT pg_advisory_lock(42);
SELECT pg_advisory_xact_lock(1, 100);
SELECT pg_try_advisory_lock(42);
SELECT pg_advisory_unlock(42);
```

### 5. 排查流程

```text
        锁问题排查标准流程

Step 1: 确认现象
        - 应用报错? deadlock detected (40P01) / lock timeout (55P03)
        - SQL 卡住? 在 pg_stat_activity 看 wait_event

Step 2: 查阻塞关系
        SELECT pg_blocking_pids(pid);
        → 拿到 blocking pid(s)

Step 3: 看锁详情
        SELECT * FROM pg_locks WHERE pid IN (...);
        → 知道锁了哪些表/行,什么模式

Step 4: 分析业务
        - 阻塞事务在跑什么 SQL? 是否长事务?
        - 等待事务的 SQL 是热点吗? 是否带 FOR UPDATE?
        - 是否有索引? 是否走了错索引?

Step 5: 处理
        短期: SELECT pg_cancel_backend(<pid>);
        长期: 缩短事务、统一顺序、NOWAIT/SKIP LOCKED、降隔离级别
```

### 6. 口诀

```text
            锁优化口诀

     锁信息在行头,不占额外内存
     八种表锁记心间,强锁阻塞弱锁
     FOR UPDATE 最强,FOR KEY SHARE 最弱
     NOWAIT 立即错,SKIP LOCKED 跳过锁
     Advisory 锁应用,事务级最安全
     死锁 PG 自动解,捕获错误码重试
     pg_locks 查实时,pg_stat_activity 看状态
     长事务是大忌,idle 立刻回收
```

### 7. 常见陷阱速查

| 陷阱 | 后果 | 解决 |
|------|------|------|
| 长事务 + 远程调用 | 锁占用久,阻塞其他人 | 事务只放 DB 操作 |
| 多表操作顺序不一致 | 死锁 | 统一访问顺序 |
| 范围 FOR UPDATE | 锁多行,易冲突 | 用 SKIP LOCKED 或拆小 |
| SERIALIZABLE 默认 | 大量 40001 报错 | 评估是否真需强一致 |
| 没用 advisory 锁 | 应用并发失控 | 关键资源加 advisory lock |
| VACUUM FULL 高峰期 | 锁全表,业务卡死 | 用 pg_repack 在线重写 |
| 不设 lock_timeout | 锁等待无限堆叠 | 全局设 5~10s |

### 8. 一句话总结

> **PostgreSQL 锁机制的核心,是"用表级锁管元数据/特殊操作、行级锁存在行头天然形成锁、应用级 advisory 锁给业务自定义",而我们日常要做的,是"用 RC 隔离级别 + 短事务 + 统一锁顺序 + NOWAIT/SKIP LOCKED,让并发高效而不混乱"。**
