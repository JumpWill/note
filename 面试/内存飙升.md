# 内存飙升

> **面试高频题**：生产环境某台服务器内存使用率从 30% 突然飙到 95%，应用开始 OOM / 大量 swap，监控告警。**你如何排查？怎么定位根因？怎么恢复？怎么防止复发？**

这道题考察的是：**对 OS 内存模型的理解 + 监控工具熟练度 + 排查方法论 + 长期防复发的工程能力**。

---

## 一、先看问题归属（面试官在考什么）

| 维度 | 占比 | 考察点 |
| --- | --- | --- |
| **OS 内存模型** | ★★★ | RSS / VSZ / Cache / Buffer / Anonymous / Mapped 的区别 |
| **监控工具熟练度** | ★★★ | free / top / vmstat / pmap / smaps / slabtop |
| **进程内分析** | ★★★ | 进程内哪段代码 / 哪种对象在吃内存 |
| **JVM / 运行时** | ★★ | heap / stack / Metaspace / DirectMemory / native |
| **排查方法论** | ★★★ | 是否从系统层面逐步下沉到应用层面 |
| **可观测性 / 报警** | ★ | 长期预防：Prometheus / Grafana / alert |

**答浅的候选人**：只看 `free -h` 看数字、立刻重启服务。
**答深的候选人**：能分清楚 used / cached / buff / avail，看 cgroup、追踪 anonymous vs page cache、分析 jvm heapdump + pmap + smaps，找到代码里误用 bigMap、不释放缓冲池、连接池耗尽等根因。

## 二、内存基础知识（先有模型）

### 1. Linux 内存结构

```text
总内存 (MemTotal)
   │
   ├── Active(anon)              ← 进程堆 / mmap / 匿名页
   ├── Inactive(anon)            ← 没被使用但保留
   │
   ├── Active(file)              ← mapped 文件缓存
   ├── Inactive(file)            ← page cache 干净
   │
   ├── Kernel Stack / PageTables  ← 内核自身
   │
   ├── SReclaimable / SUnreclaim  ← slab（dentry / inode 等）
   │
   └── Hardware Reserved
```

- **Anonymous（匿名页）**：进程堆栈 / mmap 等，进程没了就回收，匿名页不能磁盘化（可 swap）
- **File（文件页 / Page Cache）**：磁盘文件读入，可释放

### 2. `free` 与 `available`

```bash
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           32Gi        28Gi       800Mi       120Mi       3.2Gi       2.9Gi
Swap:           8Gi       3.5Gi       4.5Gi
```

- `used`：应用程序实际占用
- `free`：完全空闲
- `buff/cache`：内核 page cache 与 buffer，**可回收**
- `available`：估算可分配给新进程（≈ free + 部分 buff/cache）

**核心：内存高 ≠ 内存问题**。看 available 才能判断 OOM 是否临近。

## 三、6 步排查法

### 第 1 步：确认是"内存爆"还是"容量紧张"

```bash
free -h
cat /proc/meminfo
nproc
```

看 `MemAvailable`、`SwapFree`、`Cached`、`Buffers`、`AnonPages` 各自的比例。

- AnonPages 涨 + SwapFree 降 = 进程在吃内存
- Cached 涨 + Available 涨 = 在做 page cache，可被释放，**不是问题**

### 第 2 步：找是哪个进程

```bash
top -o %MEM         # 按内存排序
ps aux --sort -%mem | head -20
cat /proc/*/status | awk '/VmRSS|VmSize|Name/{...}' | sort
```

看 VSZ（虚拟）、RSS（实际）、Shared、Code / Data / Lib / Priv dirty 等字段。

### 第 3 步：看清 cgroup 限制

```bash
systemctl status app
systemd-cgtop -m           # cgroup 维度
cat /sys/fs/cgroup/memory/system.slice/app/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/system.slice/app/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/system.slice/app/memory.events
# OOMKills / OOMKill 计数
```

K8s pod：

```bash
kubectl describe pod app-xxx | grep -i 'oom\|limit'
kubectl logs app-xxx --previous
```

### 第 4 步：看进程内的内存构成

```bash
pmap -x <pid>              # 整进程 segment 视图
cat /proc/<pid>/maps        # 完整 segment
cat /proc/<pid>/smaps      # 每段 RSS / PSS / Swap
```

`smap_rollup` 汇总：

```bash
cat /proc/<pid>/smaps_rollup
```

`Pss` 是更准确的"分摊后实际占用"。

### 第 5 步：JVM 应用 / GC / Native 详情

```bash
jcmd <pid> GC.heap_info
jcmd <pid> VM.native_memory
jcmd <pid> Thread.print
jcmd <pid> GC.heap_dump /tmp/heap.hprof
```

或者：

```bash
jstat -gcutil <pid> 1s      # GC 统计
jmap -heap <pid>            # 堆概况
jmap -histo <pid> | head    # 哪些类占内存
```

### 第 6 步：定位代码 / 配置

- 内存泄漏：常用一次性查 heap dump（**重要**：触发 OOM 自动 dump 加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`）
- 大对象分配：Netty / gRPC 的 DirectByteBuf，Netty 自己管理
- 缓冲池：数据库连接池、HTTP 池、CompletableFuture 队列
- Full GC 不及时：MetaSpace 满 + 永久代过载
- 内核态泄漏：cgroup leak / 僵尸进程 / 内核对象

## 四、常见 6 大根因

| 根因 | 现象 | 排查工具 |
| ---- | ---- | -------- |
| **应用内存泄漏** | RSS 稳定增长不释放 | heap dump / pmap / smaps |
| **GC 调优不当 / Full GC 频繁** | Old Gen 满 → Full GC → OOM | jstat / jmap |
| **频繁创建大对象 / 缓存无上限** | 突发 RSS 跳变 | 业务日志 / 应用代码 |
| **Direct Buffer 泄漏** | Native Memory 涨 | jcmd VM.native_memory |
| **JVM 配置 `-Xmx` 偏大** | Container limit 触发 OOM | cgroup memory.events |
| **C / C++ 程序内存泄漏** | RSS / Pss 稳定增长 | valgrind / AddressSanitizer |

### 案例 1：内存泄漏（Java）

```text
- 告警 RSS 持续涨
- GC 次数高
- jstat 显示 Old Gen 满后 Full GC 但占满
- heap dump 后用 Eclipse MAT / VisualVM 看 → 哪个 class 累积最多
```

**修复**：

- 修代码（缓存清理、close 资源、用 WeakReference 等）
- 配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps`
- 监控 Old Gen 增长 + Full GC 次数

### 案例 2：缓存无限膨胀

```text
- 没有 maxSize 的 Caffeine / Guava
- 程序每次请求一个新对象 +1
- jmap -histo 看 ↑ Caffeine BoundedLocalCache ...
```

**修复**：

- 加 `maximumSize` / `expireAfterWrite`
- 用 LRU 策略
- 监控缓存命中率 / 容量

### 案例 3：容器 cgroup OOM

```text
K8s pod 配置 requests=512M limits=1G
Java -Xmx1024m
容器 1G 内存紧张时 cgroup memory.limit_in_bytes 触发 OOM
```

**修复**：

- 调整 `JVM -Xmx` 低于容器 limit，留余地给非堆 / native
- 设 `MaxRAMPercentage` (`-XX:MaxRAMPercentage=75.0`) 让 JVM 根据容器自动调 -Xmx
- K8s podMemory policy 改为 VPA

### 案例 4：file cache 充满

```text
写入文件巨大，单核 iotop 看到 cat / log rotation 写出
File page cache 涨，avail 跌
```

**修复**：

- logrotate 频率 + 大小限制
- 调整 `/proc/sys/vm/dirty_ratio`、`vfs_cache_pressure`
- 显式 `fadvise(POSIX_FADV_DONTNEED)` 释放 cache

### 案例 5：native memory / direct memory

```text
Netty Off-heap leak
JNI 泄漏
malloc 区泄漏
```

**修复**：

- Netty PooledByteBufAllocator 加 monitor
- glibc tcmalloc / jemalloc 调优

### 案例 6：cgroup 跨 pod 干扰

```text
node 内存紧张，其他 pod 抢占本 pod
memory.events `low` 触发
Pod 被驱逐
```

**修复**：

- pod QoS = Guaranteed
- 设 `memory.requests = memory.limits`
- 配置 HPA + VPA

## 五、5 步应急处理

| 步骤 | 行动 |
| --- | --- |
| 1. **取证** | 抓 heap dump、`/proc/<pid>/smaps`、日志、监控曲线 |
| 2. **隔离** | 不立刻重启，导出后用 jmap |
| 3. **止血** | 临时限流 / 自动重启 / 滚动升级 / 滚动扩容 |
| 4. **回滚** | 配合 CI / GitOps 上一个版本 |
| 5. **复盘** | 写 Post-Mortem，写 e2e 复现脚本，加监控 + 告警 + 自愈 |

> **关键**：**保留现场**比立即重启更重要。重启会丢失 RSS 曲线、heap 状态、dmesg OOM 记录。

## 六、长期预防：3 层防御

### 1. 资源管理

```yaml
# K8s
resources:
  requests:
    memory: 512Mi
  limits:
    memory: 1Gi
```

```text
# JVM
-Xms512m -Xmx512m -XX:MaxRAMPercentage=75.0 -XX:NativeMemoryTracking=summary
```

### 2. 监控与告警

```promql
container_memory_working_set_bytes
container_memory_rss
container_memory_failcnt                # cgroup OOM 计数
jvm_memory_bytes_used{area="heap"}
jvm_memory_bytes_used{area="nonheap"}
heap_usage_percent
gc_count{action="end of major GC"}     # Full GC 频率
```

```yaml
# alertmanager
- alert: PodMemoryHigh
  expr: container_memory_working_set_bytes / container_spec_memory_limit_bytes > 0.85
  for: 5m
- alert: PodOOMKilled
  expr: kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

### 3. 自愈策略

- HPA：内存水位触发扩容
- 重试：Spring Retry / Resilience4j
- 熔断：sentinel / Hystrix

## 七、面试回答框架

1. **接到告警如何排查**（1 分钟）
   - `free -h` 看 available / swap
   - `top -o %MEM` 看进程
   - cgroup 维度（`systemd-cgtop`）

2. **定位进程内是什么在涨**（1 分钟）
   - `pmap -x <pid>` 看 segment
   - `cat /proc/<pid>/smaps_rollup` 看 RSS / PSS 占比
   - Java：`jcmd <pid> VM.native_memory` + `GC.heap_info`

3. **6 大根因排查清单**（1 分钟）
   - 应用泄漏、缓存、direct memory、cgroup 限制、Full GC、native leak

4. **应急 vs 长期预防**（1 分钟）
   - 应急：取证 → 隔离 → 止血 → 回滚 → 复盘
   - 长期：资源管理 + 监控告警 + 自愈 + 容量规划

5. **加分项**（0.5 分钟）
   - jemalloc / tcmalloc、Kernel same-page merging、HugePages / Transparent HugePage、`vm.swappiness`、`/proc/sys/vm/overcommit_memory`

```text
内存飙升排查：先看 available / swap，再用 top 看进程，cgroup 维度
深入：pmap / smaps / jcmd / jmap → RSS / heap / native / cgroup limit 区分
应急：取证 → 隔离 → 止血 → 回滚 → 复盘
```
