# 传输大文件

## 一、面试怎么开口

不要上来背 HTTP 协议。先定义清楚"大文件"——**真正考验设计的是"超过单机内存、超过单次请求时长、超过单次连接生命周期"的文件传输**，通常指 GB 级别、需要分钟级传输时间、对失败零容忍的场景。

> 大文件传输的本质是**把"数据搬运"和"业务逻辑"解耦**——不让自己服务的内存、磁盘、带宽成为瓶颈，同时保证断点续传、秒传、并发安全这些非功能性体验。
>
> 我之前做在线教育平台，用户上传教学视频，单文件 2-5GB、高峰期 1.2w 并发上传。早年我们走业务服务器中转：客户端 → Nginx → Java 后端 → OSS，单台 Java 实例内存就给撑爆过——一个 3GB 文件用 `MultipartFile` 接进来直接 OOM，HPA 还没来得及扩就被打挂。后来重构成客户端直传 OSS 配合分片 + 断点续传，后端只做元数据和编排，带宽成本砍掉 60%，服务器从 200 台缩到 30 台。

**关键：面试官想听的不是 HTTP 怎么传文件，是"你怎么保证 5GB 文件传一半断了能续传、怎么避免 OOM、怎么不让用户重复上传、怎么在弱网下还稳"。**

先区分清楚三个常被搞混的场景（面试常考）：

| 场景 | 关键诉求 | 典型文件大小 |
|---|---|---|
| **客户端上传** | 断点续传、秒传、并发安全 | GB 级（视频/设计稿） |
| **服务端分发/下载** | 带宽成本、首屏速度、跨地域 | MB~GB 级（视频/安装包） |
| **服务间传输** | 不落盘、流式、不爆内存 | MB~GB 级（日志/数据/视频转码） |

下面分别给方案，最后给一张总表。

## 二、客户端上传方案（最常问，重点讲这个）

### 方案 ①：客户端直传对象存储 + 分片上传 + 断点续传（**生产首选**）

#### 核心思想
**让客户端直接和对象存储（OSS/S3）打交道，业务服务器只做"鉴权 + 元数据"**。

#### 标准流程

```
① 客户端 → 业务后端：请求上传（带文件名/大小/hash）
② 业务后端：校验权限、查 DB 看是否秒传，
            返回：uploadId + 每片 presigned URL + 已上传分片列表
③ 客户端：并行 PUT 各分片到 OSS（每片 5-10MB，带 Content-MD5 校验）
            失败/断网 → 重试该分片，不重传已成功的
④ 客户端 → 业务后端：所有分片传完，触发 CompleteMultipartUpload
⑤ 业务后端：OSS 合并分片，回调/轮询触发转码、审核等后续流程
```

#### 关键代码骨架

```java
// 1. 业务后端：创建分片上传任务
@PostMapping("/upload/init")
public InitResp initUpload(@RequestBody InitReq req) {
    // ① 秒传：文件指纹已存在，直接返回已有 fileId
    String fingerprint = req.getSha256();
    FileMeta exist = fileRepo.findByFingerprint(fingerprint);
    if (exist != null) return new InitResp(exist.getFileId(), 0, List.of());

    // ② 创建 OSS 分片上传任务
    InitiateMultipartUploadRequest ossReq = new InitiateMultipartUploadRequest(bucket, key);
    String uploadId = ossClient.initiateMultipartUpload(ossReq).getUploadId();

    // ③ 预签名每个分片的 PUT URL（有效期 1 小时）
    List<String> partUrls = IntStream.rangeClosed(1, req.getPartCount())
        .mapToObj(i -> {
            Date expire = new Date(System.currentTimeMillis() + 3600_000);
            GeneratePresignedUrlRequest urlReq = new GeneratePresignedUrlRequest(bucket, key);
            urlReq.setMethod(HttpMethod.PUT);
            urlReq.setExpiration(expire);
            urlReq.addQueryParameter("partNumber", String.valueOf(i));
            urlReq.addQueryParameter("uploadId", uploadId);
            return ossClient.generatePresignedUrl(urlReq).toString();
        }).collect(toList());

    return new InitResp(uploadId, req.getPartCount(), partUrls);
}

// 2. 客户端：并行上传分片 + 断点续传
async function upload(file) {
    const init = await api.initUpload({ sha256: await sha256(file), partCount: Math.ceil(file.size / 8 * 1024 * 1024) });
    const done = await api.getUploadedParts(init.uploadId);  // 拉已传分片，断点续传关键

    const tasks = [];
    for (let i = 1; i <= init.partCount; i++) {
        if (done.includes(i)) continue;             // 已传过，跳过
        const blob = file.slice((i-1) * PART, i * PART);
        tasks.push(retry(() => axios.put(init.urls[i-1], blob, {
            onUploadProgress: e => updateProgress(i, e.loaded)
        })).then(r => ({ partNumber: i, etag: r.headers.etag })));
    }
    const parts = await Promise.all(tasks);
    await api.completeUpload({ uploadId: init.uploadId, parts });
}
```

#### 为什么必须分片（不一次性 PUT）

| 维度 | 整文件 PUT | 分片上传 |
|---|---|---|
| 断点续传 | ❌ 失败重头 | ✅ 只重传失败分片 |
| 并行加速 | ❌ 串行 | ✅ 客户端多线程并行（5-10 倍） |
| 大文件 | 5GB 单请求超时风险高 | 每片 5-10MB，秒传 |
| 网络抖动 | 一次抖动全废 | 单片失败影响小 |

#### 为什么必须直传 OSS（不经过业务服务器）

- **省带宽**：5GB 走业务服务器 = 5GB 出网流量费用（云厂商对出网收费很高）
- **省内存**：业务服务器不接触文件本体，零 OOM 风险
- **横向扩展**：上传性能 = OSS 的能力，与业务 QPS 解耦

#### 现成轮子
- **协议层**：Tus 协议（标准化的可恢复上传协议，`tus.io`，很多开源项目用）
- **SDK**：阿里云 OSS SDK、AWS S3 SDK、MinIO（自建对象存储）
- **Web 上传组件**：Uppy（推荐）、Plupload、`@aws-sdk/multipart-upload`、Vue-uploader
- **秒传原理**：客户端先算 `SHA-256/MD5`（Web Crypto API），传给后端查重，命中直接返回历史 fileId

#### 优缺点
- ✅ 生产标准方案，**5GB 文件轻松传、断点续传天然支持**
- ✅ 业务服务器只做编排，**资源成本最低**
- ❌ 需要后端做权限校验（presigned URL 不能裸发，要带用户身份）
- ❌ 浏览器跨域需要 CORS / 反向代理到 OSS
- ❌ 移动端弱网下分片粒度要调小（2MB 优于 8MB）

### 方案 ②：WebSocket/TCP 长连接中转（**适合小众场景**）

客户端 → 业务服务器（WebSocket）→ OSS。**业务服务器作为流式中转**。

#### 适用场景
- 客户端是**嵌入式设备/小程序/老浏览器**，不支持 S3 协议
- 必须做**实时病毒扫描/内容审核**（在流式过程中同步做）
- 跨云厂商（OSS 不互通，需要中转）

#### 实现要点

```java
// 关键：流式处理，绝不把整个文件读进内存
@PostMapping(value = "/upload/stream", consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE)
public ResponseEntity<StreamingResponseBody> streamUpload(
        @RequestHeader("X-File-Id") String fileId,
        HttpServletRequest request) throws IOException {

    // 1. 流式打开 OSS 的追加写通道
    AppendObjectRequest ossReq = new AppendObjectRequest(bucket, key, request.getInputStream());
    ObjectMetadata meta = new ObjectMetadata();
    meta.setContentLength(request.getContentLengthLong());  // 客户端必须带 Content-Length
    ossReq.setMetadata(meta);

    // 2. 同步触发病毒扫描
    virusScanner.scanAsync(request.getInputStream(), fileId);

    ossClient.appendObject(ossReq);
    return ResponseEntity.ok().build();
}
```

#### 优缺点
- ✅ 业务服务器能"看见"文件流，**可以做实时内容审查/转换**
- ❌ **带宽翻倍**（客户端→业务→OSS 走两遍）
- ❌ 业务服务器仍是瓶颈，**单实例带宽上限就是上限**
- ❌ WebSocket 断线重传要自己实现

### 方案 ③：P2P / WebRTC DataChannel（**特殊场景**）

客户端之间直接传，**不经过服务器**。常见于：
- 视频会议的多人文件共享
- 局域网内大文件互传（AirDrop、Nearby Share）
- 直播连麦

#### 实现要点
- 用 `RTCPeerConnection` + `RTCDataChannel` 建 P2P 通道
- 配合信令服务器（WebSocket）做 offer/answer 交换和 NAT 穿透
- 复杂网络环境（NAT/防火墙）需要 TURN 中继服务器（成本陡增）

#### 优缺点
- ✅ 服务器带宽接近零
- ❌ 客户端实现复杂，移动端体验差
- ❌ NAT 穿透失败率高，需要 TURN 兜底（成本不亚于直传）
- ❌ 面试一般不深入，知道概念即可

## 三、服务端分发/下载方案

### 方案 ④：CDN + HTTP Range（**最主流**）

#### 核心思想
**静态文件全部走对象存储 + CDN，用户就近下载，浏览器自动支持断点续传和多线程**。

#### 关键 HTTP 头

```http
# 客户端请求
GET /video.mp4 HTTP/1.1
Range: bytes=0-1048575          # 请求第 1 个 1MB
User-Agent: Mozilla/5.0...

# 服务端响应
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1048575/5368709120
Accept-Ranges: bytes             # 告诉客户端支持 Range
Content-Length: 1048576
ETag: "abc123"
Last-Modified: Wed, 03 Aug 2026 ...
```

#### 关键实现

```nginx
# Nginx 开启 Range（默认开启，但要确认没被覆盖）
location /files/ {
    alias /data/oss-cache/;
    add_header Accept-Ranges bytes;     # 显式声明
    add_header Cache-Control "public, max-age=31536000, immutable";  # 配合 hash 文件名
    try_files $uri =404;
}

# 零拷贝：sendfile 让内核直接搬运，避免用户态拷贝
sendfile on;
tcp_nopush on;
aio threads;                          # 异步 IO
```

#### 客户端"多线程下载器"原理

```python
# 伪代码：aria2 / idm / 迅雷都是这套
import asyncio, aiohttp

async def download_part(session, url, start, end, path):
    headers = {'Range': f'bytes={start}-{end}'}
    async with session.get(url, headers=headers) as r:
        with open(path, 'ab') as f:
            async for chunk in r.content.iter_chunked(64*1024):
                f.write(chunk)

async def multi_thread_download(url, parts=16):
    total = int((await session.head(url)).headers['Content-Length'])
    chunk = total // parts
    tasks = [download_part(session, url, i*chunk, (i+1)*chunk-1, f'{url}.part{i}') for i in range(parts)]
    await asyncio.gather(*tasks)
```

#### 优缺点
- ✅ 用户体验最好，**首屏秒开、断了能续、可以多线程加速**
- ✅ CDN 扛住 99% 流量，回源压力小
- ❌ 私密文件（付费视频/合同）要走**签名 URL + 防盗链**（Referer / Token / 时间戳）
- ❌ CDN 缓存更新有延迟，紧急下架要走**主动刷新**接口

### 方案 ⑤：P2P 分发（**超大文件、海量分发**）

#### 适用场景
- 游戏客户端更新（10GB+）
- 系统镜像分发
- 直播流媒体（WebTorrent + HLS）

#### 方案
- **BitTorrent 协议**：迅雷/百度网盘底层，`libtorrent` 库
- **WebRTC + WebTorrent**：浏览器原生 P2P，无需安装客户端
- **CDN + P2P 混合（PCDN）**：爱奇艺、字节、腾讯视频在用，热门资源走 CDN，冷门走 P2P

#### 优缺点
- ✅ 服务器带宽成本可降到 1/10 甚至更低
- ❌ 监管风险（PCDN 在国内部分运营商被限制）
- ❌ 实现复杂度高，**非核心业务不要碰**

### 方案 ⑥：流式转发（**业务服务器代理下载**）

```java
@GetMapping("/download/{fileId}")
public ResponseEntity<StreamingResponseBody> download(@PathVariable String fileId) {
    FileMeta meta = fileRepo.findById(fileId).orElseThrow();
    
    // 流式从 OSS 读取，边读边写回响应，绝不缓存到内存
    StreamingResponseBody body = out -> {
        try (InputStream in = ossClient.getObject(meta.getBucket(), meta.getKey()).getObjectContent()) {
            byte[] buf = new byte[64 * 1024];
            int n;
            while ((n = in.read(buf)) != -1) {
                out.write(buf, 0, n);
            }
        }
    };
    
    return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + meta.getName() + "\"")
        .header(HttpHeaders.ACCEPT_RANGES, "bytes")          // 支持断点续传
        .contentType(MediaType.APPLICATION_OCTET_STREAM)
        .body(body);
}
```

#### 什么时候用
- 必须**实时鉴权**（每个用户每次请求都要校验权限）
- 需要**实时加水印/转码**
- 小流量 + 高安全要求

#### 优缺点
- ✅ 完全可控
- ❌ 流量经过业务服务器，**带宽成本高**
- ❌ 业务服务器是瓶颈，**大文件流式转发会拖慢整个服务**（连接数/带宽占满）

## 四、服务间大文件传输（容易被忽略）

### 场景
- A 服务生成 3GB 视频 → B 服务转码 → C 服务入库
- 订单服务导出 500w 行 Excel → 邮件服务发送
- 数据分析服务从 DB 拉 10GB 数据 → 训练服务

### 错误做法 ❌
```java
// 把整个文件读进内存传递
byte[] data = fileStorageService.read(fileId);   // 3GB 直接 OOM
processor.process(data);

// 或者作为方法返回值
String base64 = readAndEncode(fileId);          // 内存爆炸 + CPU 翻倍
```

### 正确做法

**模式 1：流式处理（最常用）**

```java
// A → B 直接用流，不落盘、不入内存
producer.streamTo(processor::consume);

// 或者用响应式
Flux<DataBuffer> stream = fileStorageService.streamRead(fileId);
stream.doOnNext(processor::consume).subscribe();
```

**模式 2：对象存储中转（最稳）**

```
A 生成文件 → 写 OSS → 发消息（带 OSS key）给 B → B 从 OSS 读
```

**代价**：多一次 OSS 读写 + 一致性维护，**但解耦彻底，扩展性最好**。

**模式 3：gRPC streaming（适合实时/长连接）**

```protobuf
service FileTransfer {
    rpc Upload(stream Chunk) returns (UploadAck);
    rpc Download(DownloadReq) returns (stream Chunk);
}
message Chunk {
    bytes data = 1;
    int64 offset = 2;
    string checksum = 3;  // 每片校验
}
```

### 选型

| 场景 | 推荐 |
|---|---|
| 一次性大文件传输 | 对象存储中转（最解耦） |
| 实时/流式处理 | gRPC streaming 或直接流 |
| 微服务调用链 | 不要把大文件塞进 MQ payload（MQ 消息上限几 MB），用消息带 OSS key |

## 六、真正的难点（面试官追问的都在这）

### 1. 秒传怎么实现（高频追问）
- 客户端用 **SHA-256 算文件指纹**（Web Crypto API，浏览器原生支持）
- 大文件**不要一次性算**——用增量 hash：分片读、分片 update hash，内存只占几 MB
- 指纹传到后端查 DB，**命中则直接返回已有 fileId，跳过上传**
- 进阶：用 **MD5 + SHA-256 双指纹**（防碰撞）+ **文件大小 + 文件名** 联合去重

```javascript
// 大文件增量算 SHA-256
async function sha256(file) {
    const chunkSize = 8 * 1024 * 1024;  // 8MB
    const hash = await crypto.subtle.digest('SHA-256', await file.arrayBuffer());
    // 或增量：
    // const hasher = new SubtleHasher();
    // for (let offset = 0; offset < file.size; offset += chunkSize) {
    //     hasher.update(file.slice(offset, offset + chunkSize));
    // }
    // return hasher.digest();
}
```

### 2. 断点续传怎么保证分片不丢不重
- 客户端每次启动上传前，**调用后端"查询已上传分片"接口**，跳过已传分片
- 服务端记录**`uploadId + partNumber → ETag`**，ETag 是 OSS 给每个分片的唯一标识
- `CompleteMultipartUpload` 时必须按 partNumber 升序传所有 ETag
- **OSS 自己的分片有效期 7-30 天**（按存储类型），过期未 complete 自动清理

### 3. 弱网/移动网络怎么优化
- **分片粒度调到 2-4MB**（弱网重传成本小）
- **每个分片独立重试**（指数退避 + 抖动，最多 5 次）
- **多线程并行降到 3-4 个**（再多被运营商 QoS 限速）
- **关键参数**：`tcp_nodelay on`、`net.ipv4.tcp_slow_start_after_idle=0`（关掉慢启动）

### 4. 内存溢出怎么避免
| 错误做法 | 正确做法 |
|---|---|
| `byte[] data = file.readAllBytes()` | `InputStream in = file.newInputStream()` + 循环读 |
| `MultipartFile.getBytes()` | `MultipartFile.getInputStream()` |
| `@RequestBody byte[]` | `@RequestBody InputStream` 或直接流到 OSS |
| 把文件 base64 后传 JSON | 永远不要 base64 大文件（33% 体积膨胀） |

Java 侧关键设置：
```yaml
spring:
  servlet:
    multipart:
      max-file-size: 100MB            # 业务侧只接小文件元数据
      max-request-size: 100MB
  codec:
    max-in-memory-size: 64KB         # WebFlux 流式
tomcat:
  max-swallow-size: -1               # 吞掉大 body 不报错（配 presigned URL 上传时）
```

### 5. 鉴权与防盗链
- **上传**：presigned URL 必须**绑定用户身份**（STS Token、RAM Policy 限制前缀如 `user/${uid}/`）
- **下载**：
  - 公开资源：CDN 直接配缓存规则
  - 私密资源：**签名 URL**（带过期时间 + 用户 IP）+ **Referer 防盗链** + **Token 鉴权**
  - 高安全：每请求回源鉴权（**带宽成本高**）

```nginx
# Nginx 防盗链
location /files/ {
    valid_referers none blocked server_names *.example.com;
    if ($invalid_referer) { return 403; }
}
```

### 6. 大文件分发的带宽优化
- **CDN 回源策略**：大文件开启**回源分片**（Range 回源），避免每次拉全量
- **压缩**：图片走 WebP/AVIF、视频走 H.265，**别在传输层 gzip 视频**（已压缩再压白费 CPU）
- **预热**：重要资源提前 CDN 预热（`Push` 接口），避免冷启动慢
- **QUIC/HTTP/3**：弱网下比 TCP+TLS 快 20-30%，**Cloudflare、字节火山引擎、阿里云 DCDN 都支持**

### 7. 服务间传输的常见坑
- **Kafka/Pulsar 消息体限制**：单条消息几 MB，**大文件不要塞进消息 payload**，用消息带 OSS key
- **gRPC 默认 4MB 限制**：`grpc.max_receive_message_size` 调到 100MB+，但更大就用 streaming
- **HTTP/1.1 队头阻塞**：用 HTTP/2 多路复用，或干脆走 gRPC
- **微服务间长链路传大文件**：每个环节都流式传递，**不要在中间节点落盘**（除非必须做内容审查）

### 8. 安全与合规
- **病毒扫描**：上传完成后异步调 ClamAV / 云厂商扫描服务
- **内容审核**：图片/视频走 AI 审核（阿里云内容安全、AWS Rekognition）
- **敏感信息**：身份证/银行卡图片上传后**加密存储**（OSS 服务端加密 SSE-KMS）
- **审计日志**：所有下载/删除操作必须留痕

### 传统文件传输（4 次拷贝、4 次上下文切换）

硬盘 → 内核缓冲（DMA）→ 用户缓冲（CPU）→ Socket 缓冲（CPU）→ 网卡（DMA）

ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);

ssize_t splice(int fd_in, loff_t *pos_in, int fd_out, loff_t *pos_out, size_t len, unsigned int flags);

WritableByteChannel dstChannel = Channels.newChannel(response.getOutputStream());

## 八、标准回答模板（3 分钟版）

> **定位**：大文件传输的核心挑战是"流式、断点续传、不爆内存、不重复上传"。我把它分三块看：客户端上传、服务端下载、服务间传输。
>
> **客户端上传**：我们用**客户端直传 OSS + 分片上传 + 秒传**。前端先算 SHA-256 发后端查重，命中走秒传；没命中就分 5-10MB 一片并行上传，每片走 presigned URL 直传 OSS，传完调 Complete 合并。后端只做权限校验和元数据，不碰文件本体。断点续传靠 OSS 自己的 uploadId + 客户端拉已传分片列表。这套上线后，5GB 文件 4G 网络下平均 8 分钟传完，带宽成本砍掉 60%。
>
> **服务端下载**：核心是 **CDN + HTTP Range**。资源全部走对象存储 + CDN，浏览器原生支持断点和多线程下载。私密资源走签名 URL + Referer 防盗链。
>
> **服务间传输**：**流式处理 + 对象存储中转**。绝不把大文件读进内存，要么流式传递，要么落 OSS 后用消息带 key 通知下游。
>
> **踩过的坑**：第一版用 `MultipartFile.getBytes()` 接 3GB 文件，OOM 挂了所有节点。第二版没做分片，用户传一半断电必须从头来，用户投诉爆了。第三版没做秒传，公司里同一个 2GB 视频被不同部门传了 200 多次，OSS 账单翻倍。这三个坑踩完，方案才稳下来。
>
> **量化结果**：上传成功率从 85% 提到 99.5%，服务器从 200 台缩到 30 台，月度带宽成本降 60%。

## 九、可能被追问的问题清单

1. **分片多大合适？** —— 5-10MB 是平衡点。小了 HTTP overhead 高、OSS 请求费贵；大了弱网重传成本高。**移动端调到 2-4MB**
2. **分片上传中途换浏览器/换设备能续传吗？** —— 能，**只要 uploadId 和分片列表还在后端**，新设备拉一下已传分片就能续。所以 init 接口的 metadata 要落 DB
3. **秒传会不会泄露隐私？** —— 指纹是单向 hash，**理论上可能碰撞但 SHA-256 概率可忽略**；对超敏感文件关掉秒传
4. **CDN 缓存被恶意刷怎么办？** —— 单 IP 限速 + Referer 防盗链 + 签名 URL + **热点资源自动封禁**（Cloudflare / 阿里云 DCDN 都有）
5. **海外用户上传慢怎么办？** —— **全球加速**（阿里云 GA、AWS Global Accelerator），OSS 的传输加速服务，或**就近接入点**（用户在哪个区域就传哪个区域的 OSS Bucket，跨区复制）
6. **怎么防止上传到一半用户关页面，OSS 上有垃圾分片？** —— **生命周期规则**：未 complete 的分片 N 天后自动清理；init 接口记录 owner，定期扫描清理孤儿分片
7. **大文件上传怎么测？** —— **tc netem 模拟弱网**（`tc qdisc add dev eth0 root netem delay 300ms loss 5%`），用 **5GB 真实文件** 跑全流程，**不能只用小文件**（小文件测不出分片逻辑的 bug）
8. **WebSocket 上传和 HTTP 上传选哪个？** —— 默认 HTTP（分片 + presigned URL），**只有要实时审查/转换才用 WebSocket**
9. **gRPC streaming 和 HTTP/2 streaming 区别？** —— gRPC 有强类型 + 自动重试 + 双向流，HTTP/2 更通用。**性能差异不大，选生态**
10. **P2P 上传在国内合规吗？** —— 个人网盘没事，**企业级 P2P 加速（PCDN）部分运营商会限速甚至封宽带**，要选有牌照的服务商

### 场景 ②：百万级小文件（**面试最常考这个**）

> 200GB 股票 tick 数据：A 股 5000 只 × 250 天 × 多个文件 = **100w+ 个小文件**，每个 50-500KB。**这是小文件问题，不是大文件问题**。

#### 为什么小文件是灾难
- **scp/rsync 单文件传输**：每个文件建一个 TCP 连接，100w 文件 = 100w 次握手，**慢到不可用**
- **`ls` 一个目录 100w 文件**：直接卡死
- **OSS/HDFS**：每个文件一个对象请求，**请求费爆炸**（OSS PUT 1 万次 = 0.05 元，100w 次 = 50 元；HDFS namenode 内存爆）
- **存储 IOPS**：机械盘 100 IOPS 顶天，**100w 文件全列出来要 2.7 小时**

#### 正确做法：先打包/转格式，再传

**方案 1：tar 打包后整体传输（最简单）**

```bash
# 数据源端
tar -cf - stock_data/ | pigz -9 -p 16 > stock_2026.tar.gz    # 多核压缩
# 18 核机器压缩 200GB CSV → ~30GB，耗时 15-20 分钟

# 传输（rsync 走的是单个流，速度快）
rsync -avP stock_2026.tar.gz server:/data/

# 接收端解压到本地或直接入湖
tar -xzf stock_2026.tar.gz -C /data/staging/
```

**方案 2：转 Parquet 后传（生产推荐）**

```python
# 数据源端：先聚合转格式
import pyarrow as pa
import pyarrow.parquet as pq
import glob

# 按 (date, exchange) 分区，1 个 Parquet 文件 256MB-1GB
pq.write_to_dataset(
    table,
    root_path='/data/parquet/',
    partition_cols=['date', 'exchange'],
    compression='snappy'        # 解压快，金融数据 snappy 就够
)
# 200GB CSV → 30-50GB Parquet + 100w 文件 → ~700 个文件
```

**方案 3：DataLoader 直接走数据库 COPY（如果是库导出）**

### 这种题的标准回答模板

> **反问**：先问"200GB 是单文件还是百万级小文件？是一次性导入还是持续增量？数据格式是 CSV、Parquet 还是库 dump？网络是内网还是公网？时效要求？"

> **分场景答**：
> - **单文件 200GB**：内网直接走 `rsync -avP` 或 OSS 多分片并行，**先算账**（1Gbps 27 分钟），落盘后**必须转 Parquet**（200GB → 30GB，查询快 10 倍）
> - **百万级小文件**（最常考）：**先打包成 tar + pigz 多核压缩**，或者**先转 Parquet**（100w 文件 → 700 个文件），再走 rsync。直接传 100w 小文件是灾难，**OSS 请求费 + namenode 内存 + 磁盘 IOPS 三个地方都会爆**

> - **持续增量**：上 Kafka + CDC，**每天不要重传全量**
>
> **验证**：金融数据**零容错**，必须三道关：整体 SHA-256、行数/股票数核对、抽样人工对账。**任何一道不过都不算完成**。
>
> **加分点**：物理寄盘方案（国内金融行业真实做法，200GB 用硬盘快递比传公网便宜）；ClickHouse/DuckDB 等列存数据库；列存压缩比 3-10x；Spark/ClickHouse 的并行导入参数。

### 真实追问清单

1. **200GB 传完了发现数据有问题怎么办？** —— **导入前校验**（不能等全量入完才校验），**用临时表 + 校验通过再 rename**，MySQL 用 `pt-online-schema-change` 的 rename 思路
2. **传输中途网络断了怎么办？** —— rsync `--partial` 续传；OSS 分片记录 uploadId；**永远不要在生产表上直接导入**
3. **导入期间业务表怎么办？** —— 双写、影子表、`pt-online-schema-change`、**核心是导入过程不影响线上查询**
4. **200GB 入库后查询慢怎么办？** —— 转 Parquet + 分区（date/symbol）；建索引；**OLAP 场景用 ClickHouse 而不是 MySQL**
5. **200GB 数据怎么保证不丢一条？** —— **行数 + checksum + 主键唯一性 + 业务抽样**四道关；导入前后跑 `select count(*)` 对比
6. **为什么不用 HDFS？** —— 200GB 单副本 HDFS 没问题；HDFS 适合**后续分析**，导入阶段本地盘 + 列存就够了
7. **为什么不用消息队列？** —— Kafka 单消息几 MB 限制，**200GB 不能塞进消息**，要么走文件传输，要么用 Kafka Connect 抽文件
8. **跨国/跨云怎么传？** —— **专线 > 物理寄盘 > 公网压缩传输**。200GB 公网跨国走 100Mbps 要 4.5 小时，**专线或寄盘都是 1 天内**
