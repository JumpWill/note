# 数据库（多主活 / 多源汇聚 / 数据一致性）

> 本节围绕一道真实高频题展开：
> **"系统要接入多个券商的行情/交易数据，但只写一个数据库，怎么保证数据库多主活 + 数据准确不丢失？"**
> 这个问题跨 6 个领域、8 个子问题，能衍生出 15+ 变种题。

---

## 一、问题归属（先看面试官在考你什么）

这道题**不是单一领域题**，是分布式系统综合能力的试金石。面试官在考察你对以下 6 个领域的理解：

| 归属领域 | 占比 | 考察点 |
|---|---|---|
| **多主复制（Multi-Master Replication）** | ★★★ | 真正理解多主活的含义、冲突解决 |
| **数据集成（Data Integration）/ CDC** | ★★★ | 多个数据源怎么汇聚 |
| **最终一致性 / CAP** | ★★★ | 分布式系统理论 |
| **幂等设计（Idempotency）** | ★★★ | 数据不丢 + 不重的核心 |
| **金融数据一致性** | ★★ | 业务正确性（不是简单的 DB 一致性） |
| **消息队列 / 事件溯源** | ★★ | 削峰、解耦、Exactly-Once |

**为什么要先看归属**：因为很多候选人会把它当数据库复制题来答（提 MySQL 主从、binlog），答浅了；**真正的考点是"如何在多源 + 多主的前提下保证业务层数据正确"**——DB 只是底座，**业务路由 + 幂等键 + 时序控制才是核心**。

### 题目里的两个关键约束

1. **多主活（Active-Active）**：不是一主多从，是多个节点同时可写。这要求**冲突检测与解决**
2. **数据准确不丢失**：包含三层——**不丢（durability）、不重（deduplication）、不错（业务正确性）**

很多候选人会答成"用主从复制"——**方向就错了**，主从不是多主活。

---

## 二、问题拆解（5 个子问题，按依赖顺序）

把这道题拆开看，才能避免漏答：

```
子问题 1：多源数据汇聚（多券商 → 中心）        ← 数据怎么进来
子问题 2：多主活（多个节点同时可写）            ← DB 拓扑怎么设计
子问题 3：数据不丢（durability）              ← 失败场景怎么恢复
子问题 4：数据不重（deduplication）           ← 重复消息怎么去重
子问题 5：数据不错（业务正确性）              ← 冲突数据怎么合并
```

**5 个问题必须全部有解，缺一个就是漏。**下面每个方案都是这 5 个子问题的组合解。

## 三、6 种方案（从简单到复杂，从常见到高级）

### 方案 ① 分布式多活数据库 + 应用层路由（**强一致首选**）

#### 核心思想
**DB 层用真正的多主活分布式数据库，应用层按业务键路由写入**。

#### 拓扑
```
券商A 券商B 券商C
  ↓     ↓     ↓
 Ingestion Service（每个券商一个实例）
  ↓     ↓     ↓
 ┌─────┴─────┴─────┐
 │   TiDB / OceanBase / CockroachDB  │
 │   (多主活，Raft/Paxos 协议保证)     │
 └─────────────────────┘
         ↓
     下游查询服务
```

#### 关键代码骨架（以 TiDB 为例）

```java
// 1. 路由：按 (exchange, symbol) 哈希到不同 TiKV 节点
public class ShardRouter {
    public int route(String exchange, String symbol) {
        // 同一只标的所有券商数据落到同一分片，避免跨分片事务
        return Math.floorMod((exchange + ":" + symbol).hashCode(), 64);
    }
}

// 2. 写入：幂等键 + ON DUPLICATE KEY UPDATE
public class TickIngestService {
    @Transactional
    public void ingest(Tick tick) {
        // 幂等键：exchange + symbol + timestamp 唯一
        String dedupKey = tick.getExchange() + ":" + tick.getSymbol() + ":" + tick.getTimestamp();
        
        // 先查再写（读已写入的最新版本）
        Tick latest = tickRepo.findLatest(tick.getExchange(), tick.getSymbol());
        if (latest != null && latest.getTimestamp() >= tick.getTimestamp()) {
            // 旧数据，丢弃（时序控制）
            return;
        }
        
        // ON DUPLICATE KEY UPDATE：天然幂等，重复插入不报错
        tickRepo.upsert(tick);
    }
}

// 3. SQL：唯一约束兜底
CREATE TABLE ticks (
    exchange    VARCHAR(16),
    symbol      VARCHAR(32),
    ts          BIGINT,
    price       DECIMAL(18, 6),
    volume      BIGINT,
    version     BIGINT DEFAULT 0,    -- 乐观锁版本号
    PRIMARY KEY (exchange, symbol, ts),
    UNIQUE KEY uk_dedup (exchange, symbol, ts)
);
```

#### 多活冲突解决（DB 层）
- **TiDB**：Raft 协议保证写入线性一致；同一行只能被一个 Raft Group 处理，**避免多主冲突**
- **OceanBase**：Paxos 协议，多副本强一致；同样的单行单 Leader 思路
- **CockroachDB**：Range + Raft，同理

**关键事实**：真正的多主活分布式数据库，**底层其实是单 Raft Leader 写入**——所谓"多主活"是**应用层多入口**（多服务都能写），**不是"两个节点同时改同一行"**。这是面试必须澄清的概念。

#### 优缺点
- ✅ DB 层强一致，**RPO = 0**（零数据丢失）
- ✅ 水平扩展好（TiDB 单集群能撑 PB 级）
- ✅ 运维有兜底（少数派故障自动恢复）
- ❌ 成本高（至少 3 副本 × 多机房）
- ❌ 跨地域延迟（金融要求 100ms 内，跨城 30-50ms，跨国会超）
- ❌ 学习曲线陡，运维复杂

#### 一句话话术
> "我们用 TiDB 集群做多主活，应用层多入口接入，DB 底层用 Raft 保证强一致；同标的同时间戳的数据靠唯一约束和版本号去重。"

### 方案 ② Kafka 消息队列 + 幂等消费（**最主流生产方案**）

#### 核心思想
**多个券商的消息先全部进 Kafka 削峰，统一的 Ingestion Service 消费入库**——**数据汇聚层 + 多活写入层分开做**。

#### 拓扑
```
券商A 券商B 券商C
  ↓     ↓     ↓
 Kafka Topic（每个券商一个 Topic，或统一 Topic + exchange 字段）
  ↓
 ┌────────────────────┐
 │ Ingestion Service  │  ← 多实例部署，Kafka Consumer Group 负载均衡
 │ (按 partition 消费)  │     这就是"多主活"：多个消费实例同时工作
 └────────┬───────────┘
         ↓
    MySQL / PG（单库或多库）
         ↓
     下游查询
```

#### 关键代码骨架

```java
// 1. 生产者：多券商统一格式进 Kafka
kafkaTemplate.send("ticks", tick.getExchange(), JSON.toJSONString(tick));

// 2. 消费者：手动 ACK + 幂等键去重
@KafkaListener(topics = "ticks", groupId = "ingestion")
public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
    try {
        Tick tick = JSON.parseObject(record.value(), Tick.class);
        
        // ① 幂等：Redis SETNX 占位，10 分钟过期（比 Kafka 重平衡窗口大）
        String dedupKey = "ingest:" + tick.getExchange() + ":" + tick.getSymbol() + ":" + tick.getTs();
        Boolean firstTime = redis.setIfAbsent(dedupKey, "1", Duration.ofMinutes(10));
        if (Boolean.FALSE.equals(firstTime)) {
            // 已处理过（可能是 Kafka 重平衡重投）
            ack.acknowledge();
            return;
        }
        
        // ② 时序：水位线控制（同标的数据乱序到达要按时间戳排序）
        tickService.ingestWithOrdering(tick);
        
        ack.acknowledge();
    } catch (Exception e) {
        // 不 ACK，等下次重试（DLQ 进死信队列告警）
        log.error("ingest failed, will retry", e);
    }
}

public void ingestWithOrdering(Tick tick) {
    // 用 watermark：标的的最新时间戳记录在 Redis
    String watermarkKey = "watermark:" + tick.getExchange() + ":" + tick.getSymbol();
    Long currentWatermark = (Long) redis.opsForValue().get(watermarkKey);
    
    if (currentWatermark != null && tick.getTs() < currentWatermark - 60000) {
        // 60 秒前的乱序数据直接丢弃
        log.warn("out-of-order tick dropped: {}", tick);
        return;
    }
    
    // 写入数据库
    tickRepo.upsert(tick);
    
    // 更新水位线
    redis.opsForValue().set(watermarkKey, tick.getTs());
}
```

#### 表结构 + UPSERT 兜底

```sql
CREATE TABLE ticks (
    id          BIGINT AUTO_INCREMENT,
    exchange    VARCHAR(16)   NOT NULL,
    symbol      VARCHAR(32)   NOT NULL,
    ts          BIGINT        NOT NULL,         -- 毫秒时间戳
    price       DECIMAL(18,6) NOT NULL,
    volume      BIGINT        NOT NULL,
    source      VARCHAR(16)   NOT NULL,        -- 来源券商
    created_at  TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_dedup (exchange, symbol, ts, source)  -- 关键：唯一约束
);

-- UPSERT：数据库兜底去重
INSERT INTO ticks (exchange, symbol, ts, price, volume, source)
VALUES (?, ?, ?, ?, ?, ?)
ON DUPLICATE KEY UPDATE
    price = IF(VALUES(ts) > ts, VALUES(price), price),   -- 只接受更新的数据
    volume = IF(VALUES(ts) > ts, VALUES(volume), volume);
```

#### Kafka 顺序保证
- **同一标的的数据必须进同一 partition**（用 `symbol` 作 key，或用 `exchange:symbol` 作 key）
- **每个 partition 单消费者线程**（保证有序）
- **跨 partition 的乱序**：用上面的 watermark 机制 + IF 表达式解决

#### Exactly-Once 语义（EoS）
Kafka 0.11+ 支持事务生产者 + 幂等生产者：
```java
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);   // 幂等
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "ingest-tx-1");  // 事务
```

但**真正的 Exactly-Once 要靠"消费幂等 + 业务幂等"**——Kafka EoS 解决不了消费端业务处理失败的问题。

#### 优缺点
- ✅ **生产最主流**，削峰、解耦、可观测
- ✅ 多活天然支持：多个 Ingestion 实例就是"多主"
- ✅ 失败可重放（Kafka 保留 7-30 天）
- ❌ 引入消息队列的运维成本
- ❌ 数据延迟增加（毫秒级）
- ❌ 顺序问题需要业务侧处理

### 方案 ③ CDC（Change Data Capture）多活同步（**适合数据中台**）

#### 核心思想
**每个券商有独立的本地数据库，本地库 → CDC → 中心库**。中心库对外提供统一视图，自身做多主活。

#### 拓扑
```
券商A  →  DB_A  ──┐
券商B  →  DB_B  ──┼──→ Debezium/Canal  →  Kafka  →  中心库
券商C  →  DB_C  ──┘                              (TiDB/OceanBase 多活)
```

#### 适用场景
- **券商给的接口是数据库级别的**（很多传统金融就是直接给库）
- **不想改造券商侧的写入路径**（不能要求他们改）
- **数据中台/数据仓库场景**

#### 关键代码（Debezium 配置示例）

```json
{
  "name": "stock-a-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "db-a.internal",
    "database.port": "3306",
    "database.user": "cdc",
    "database.password": "secret",
    "database.server.id": "1001",
    "database.server.name": "stock-a",
    "table.include.list": "stock_db.ticks",
    "tombstones.on.delete": "false",
    "decimal.handling.mode": "double"
  }
}
```

#### 优缺点
- ✅ 对源库**零侵入**（订阅 binlog 而不改业务）
- ✅ 实时性好（秒级延迟）
- ✅ 适合异构数据库汇聚
- ❌ 链路长，依赖多（binlog + Kafka + 中心库）
- ❌ DDL 同步是难题
- ❌ 中心库仍是单点写入瓶颈（虽然底层可以多主活）

### 方案 ④ 应用层多主 + 业务路由（**金融行业实际做法**）

#### 核心思想
**多个 Ingestion 服务实例同时写同一个数据库的不同分片，业务层用分布式锁或乐观锁避免冲突**。

#### 实战代码（金融行情系统真实场景）

```java
// 1. 按 (exchange, symbol) 路由到不同分片
public class TickIngestionService {
    private static final int SHARD_COUNT = 64;
    
    public void ingest(Tick tick) {
        int shard = Math.floorMod(
            (tick.getExchange() + ":" + tick.getSymbol()).hashCode(), 
            SHARD_COUNT
        );
        
        // 2. 分布式锁（同标的串行写，避免乱序）
        String lockKey = "lock:ticks:" + tick.getExchange() + ":" + tick.getSymbol();
        RLock lock = redisson.getLock(lockKey);
        try {
            lock.lock(5, TimeUnit.SECONDS);  // 5 秒自动释放防死锁
            
            // 3. CAS 乐观锁（防止两个实例同时写）
            int updated = tickRepo.compareAndSet(
                tick.getExchange(), tick.getSymbol(), tick.getTs(),
                tick.getPrice(), tick.getVolume(),
                tick.getVersion()  // 期望版本号
            );
            if (updated == 0) {
                // 版本冲突，重读最新版本再决定
                log.warn("CAS conflict: {}", tick);
            }
        } finally {
            lock.unlock();
        }
    }
}

// SQL: 乐观锁
UPDATE ticks 
SET price = ?, volume = ?, version = version + 1
WHERE exchange = ? AND symbol = ? AND ts = ? AND version = ?;
-- affected rows = 0 表示版本冲突
```

#### 优缺点
- ✅ **金融行业落地最多的方案**（复杂但可控）
- ✅ 业务可控性最强
- ❌ 代码复杂，分布式锁性能瓶颈
- ❌ 容易出现锁竞争

### 方案 ⑤ CRDT / 业务层最终合并（**无中心化**）

#### 核心思想
**数据本身支持并发合并（CRDT，Conflict-free Replicated Data Type），不需要中心协调**。

#### 适用
- 行情数据天然适合（同一标的的多个数据可以合并）
- 不适合：交易数据（不能合并）

#### 简化实战

```java
// 用 LWW-Register（Last-Write-Wins）做时序合并
public class CRDTTick {
    private long timestamp;
    private BigDecimal price;
    private long version;  // 逻辑时钟
    
    public CRDTTick merge(CRDTTick other) {
        // 时间戳大的赢（或者 version 大的赢）
        return this.version >= other.version ? this : other;
    }
}
```

#### 优缺点
- ✅ 无锁、无中心
- ❌ 业务复杂度高
- ❌ 调试困难

**一般只在特殊场景用**，面试知道概念即可。

### 方案 ⑥ 集中式单写 + 读多活（**伪多主，但稳定**）

#### 核心思想
**承认"写"是单点的，但通过 binlog 同步实现"读多活"**——**实际生产中 80% 系统是这个架构**，真正的多主活是少数场景。

#### 拓扑
```
多 Ingestion 写入 → 单一主库 → binlog → 多只读副本 → 下游查询
```

#### 为什么生产中常用
- **写性能要求 1-5k QPS** 就够，主库顶得住
- 读多活可以水平扩展到几十个副本
- 简单、稳定、好维护

#### 优缺点
- ✅ 简单可靠
- ✅ 运维成本低
- ❌ 写性能有上限（不适合 10w+ QPS 写入）
- ❌ 严格意义不是"多主活"

## 五、真正的难点（面试官追问都在这）

### 1. 同一笔数据多券商重复上报怎么办
- **业务层主键**：(exchange, symbol, ts) 联合唯一
- **数据指纹**：MD5(原始 payload) 作为幂等键
- **数据库兜底**：唯一约束 + `ON DUPLICATE KEY UPDATE`

### 2. 乱序到达怎么办（最难的点）
**水位线（Watermark）+ 乱序容忍窗口**：
```java
// 接受最多 60 秒的乱序，超过的丢弃
if (tick.getTs() < currentWatermark - 60000) {
    log.warn("out-of-order, dropped: {}", tick);
    return;
}
```
**Flink 的 Watermark 机制**就是这个思想的工业实现。

### 3. 多主活冲突怎么解决
- **真正的分布式 DB（TiDB/OB）**：底层 Raft/Paxos 自动处理，应用层无感
- **应用层多主**：必须用分布式锁或 CAS
- **业务合并**：LWW、版本号、Vector Clock

### 4. 如何保证 Exactly-Once
- **生产端**：Kafka 幂等生产者 + 事务
- **消费端**：幂等键（Redis SETNX + DB 唯一约束双保险）
- **DB 端**：`ON DUPLICATE KEY UPDATE` / `INSERT ... ON CONFLICT`

### 5. 灾备怎么做
- **同城双活**：两个机房，RPO≈0，RTO < 1 分钟
- **异地容灾**：异步复制，RPO 秒级
- **跨地域多活**：业务层就近写入 + 异步汇聚

### 6. 时序数据怎么选库
- **OLTP（事务）**：MySQL/PG，行情订阅、低延迟查询
- **OLAP（分析）**：ClickHouse/TimescaleDB/Doris，K 线聚合、查询
- **混合**：MySQL 接收 → 异步同步到 ClickHouse

## 六、衍生面试题（这套题库的扩展）

这道题能衍生出 15+ 高频面试题，按主题归类：

### 6.1 分布式数据库类
1. **TiDB / OceanBase 的 Raft 怎么实现多主活？** —— 底层单 Leader，应用层多入口
2. **MySQL Group Replication 和 MGR 的限制？** —— 单写性能差、大事务卡住、最大 9 节点
3. **主从延迟怎么解决？** —— 半同步、并行复制、读走主、强读（`SELECT ... FOR UPDATE`）
4. **分库分表后怎么保证唯一性？** —— 分布式 ID（Snowflake）、分片键设计、冗余表

### 6.2 消息队列类
5. **Kafka 怎么保证不丢消息？** —— `acks=all` + 副本数 ≥ 3 + `min.insync.replicas=2`
6. **Kafka 怎么保证不重？** —— 幂等生产者 + 消费幂等
7. **Kafka 顺序消息怎么实现？** —— 单 partition + 单消费者
8. **RocketMQ 和 Kafka 在金融场景怎么选？** —— RMQ 事务消息更成熟，Kafka 吞吐更高

### 6.3 一致性理论类
9. **CAP 怎么理解？** —— 金融场景多选 CP（强一致），牺牲 P

## 七、5 个最值得展开的衍生题

### 衍生题 1：MySQL 主从延迟怎么解决
```
产生原因：binlog 是异步复制，master 写完即返回，slave 异步拉
常见值：ms-秒级，高负载下分钟级
解决方案：
  - 半同步复制：master 至少收到 1 个 slave ACK 才返回（牺牲 1-2ms 换 RPO≈0）
  - 并行复制：MySQL 5.7+ 按库或按 WRITESET 并发应用
  - 强读走主：实时性要求高的读强制走 master（proxy 层路由）
  - 业务容忍：报表查询走从库，账户余额走主库
```

### 衍生题 2：Kafka 怎么保证不丢消息
```properties
# Producer 端
acks=all                          # 等待所有副本确认
enable.idempotence=true           # 幂等
retries=Integer.MAX_VALUE         # 无限重试
max.in.flight.requests.per.connection=5  # 幂等下允许并发

# Broker 端
min.insync.replicas=2             # 至少 2 个副本写入成功
replication.factor=3              # 副本数 ≥ 3
unclean.leader.election.enable=false  # 禁止脏选举

# Consumer 端
enable.auto.commit=false          # 关闭自动提交
手动处理完业务再 ACK
```

### 衍生题 3：分布式锁怎么实现（Redisson 实战）
```java
RLock lock = redisson.getLock("order:" + orderId);
try {
    // 30 秒自动释放（防业务超时死锁）
    if (lock.tryLock(100, 30000, TimeUnit.MILLISECONDS)) {
        // 业务逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```
**坑**：
- Redis 单点风险（主从切换丢锁）→ RedLock 或 ZK
- 锁粒度太粗（性能差）
- 时钟漂移（TTL 不准）→ 用 ZK 的临时节点

### 衍生题 4：幂等键怎么设计
```
1. 业务键 + 时间窗口：order:{orderId}:{date}    适用：订单
2. 数据指纹：md5(payload)                       适用：行情
3. 流水号：上游给的唯一 ID                       适用：交易
4. 数据库唯一约束兜底                            必做

必须做幂等的操作：扣款、发货、回调、发短信
不用做幂等的操作：纯查询、写日志
```

### 衍生题 5：CDC 同步中 DDL 怎么同步
```
问题：源库 ALTER TABLE，CDC 怎么同步给下游？
方案：
  - pt-online-schema-change（不锁表，影子表）
  - gh-ost（GitHub 开源，原理类似）
  - 业务低峰期做 DDL
  - 下游 DDL 独立维护（不依赖上游 schema 同步）
```

## 八、标准回答模板（5 分钟版）

> **问题归属**：这道题考的不是单一知识点，是分布式系统综合能力——**多主复制、CDC、最终一致性、幂等、金融数据一致性、消息队列**这 6 个领域。
>
> **问题拆解**：我把它拆成 5 个子问题：多源汇聚、多主活、不丢、不重、不错。任何方案都要同时解决这 5 个。
>
> **方案选型**（按场景）：
> - **金融级强一致 + 大规模**：**方案 ① 分布式多活 DB（TiDB/OceanBase）**。DB 层 Raft 协议保证强一致，应用层多入口实现多主活，靠唯一约束 + 乐观锁保证幂等
> - **最主流的生产方案**：**方案 ② Kafka + 幂等消费**。多券商消息进 Kafka 削峰，Ingestion 多实例消费（这就是"多主活"），Redis SETNX + DB UPSERT 双保险去重，watermark 解决乱序
> - **数据中台/对源库零侵入**：**方案 ③ CDC 同步**。Debezium 订阅 binlog 到 Kafka，再到中心库
> - **金融行情系统实际做法**：**方案 ④ 应用层多主 + 分布式锁**。按标的路由分片，Redisson 锁串行化写
> - **简单稳定优先**：**方案 ⑥ 集中式单写 + 读多活**（伪多主但 80% 业务够用）
>
> **关键技术点**：
> 1. **幂等三件套**：唯一约束 + 幂等键 + UPSERT 语义
> 2. **时序控制**：watermark 水位线 + IF 表达式
> 3. **冲突解决**：LWW（Last-Write-Wins）/ 业务合并 / DB 协议层解决
> 4. **可观测**：同步延迟监控 + 重复数据告警 + 数据质量校验
>
> **量化结果**（举例）：落地 Kafka + TiDB 方案后，行情数据接入从 5 个券商扩展到 20 个，端到端延迟 50ms，数据零丢失，去重重试率 < 0.01%。

## 总结：这种综合题的答题心法

1. **先看归属**——这种题考 6 个领域，答不全就漏分
2. **拆子问题**——5 个子问题都要有方案
3. **按场景给方案**——不要只给一个方案，说"看场景"
4. **承认权衡**——CAP 三角矛盾，不要吹"我的方案完美"
5. **量化结果**——能给出数字（延迟、TPS、RPO）就赢了
6. **承认演进**——第一版用方案 ⑥，规模大了上方案 ②，再大上 ①
