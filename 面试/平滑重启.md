# 平滑重启

> **面试高频题**：上线新版本时如何**不停服务、不丢请求**地重启？覆盖 CLI / Web 服务器 / 消息消费者 / 数据库连接池 / 数据库主从切换等场景。

"平滑" = **service upgrade without dropping in-flight requests**。
技术本质：**让进程在收到终止信号后，做收尾工作（排空连接 + flush 状态），再退出**。

## 二、Linux 信号机制基础

```text
进程收到信号
  │
  ├─ 内核默认动作：exit / core / stop / ignore
  │
  └─ 用户进程注册 signal handler → 自定义收尾
```

### 2.1 常用信号

| 信号 | 数字 | 默认 | 含义 |
| --- | --- | --- | --- |
| **SIGHUP** | 1 | exit | 终端断开 / 配置重读（惯用约定） |
| **SIGINT** | 2 | exit | Ctrl+C |
| **SIGQUIT** | 3 | core | Ctrl+\ |
| **SIGILL** | 4 | core | 非法指令 |
| **SIGTRAP** | 5 | core | 调试断点 |
| **SIGABRT** | 6 | core | `abort()` |
| **SIGBUS** | 7 | core | 总线错误 |
| **SIGFPE** | 8 | core | 算术异常 |
| **SIGKILL** | 9 | exit | **不能被捕获**，强制杀 |
| **SIGUSR1** | 10 | exit | 用户自定义 |
| **SIGSEGV** | 11 | core | 段错误 |
| **SIGUSR2** | 12 | exit | 用户自定义 |
| **SIGPIPE** | 13 | exit | 写入关闭的 socket |
| **SIGALRM** | 14 | exit | 定时器到时 |
| **SIGTERM** | 15 | exit | **可捕获**，优雅终止 |
| **SIGCHLD** | 17 | ignore | 子进程退出 / 停止 |
| **SIGCONT** | 18 | resume | 继续 |
| **SIGSTOP** | 19 | stop | **不能被捕获** |
| **SIGTSTP** | 20 | stop | Ctrl+Z |
| **SIGIO / SIGPOLL** | 23 | ignore | I/O 可用 |

### 2.2 关键原则

- **SIGKILL/SIGSTOP 不可捕获、不可阻止**
- SIGTERM 是设计为"软"终止信号的；服务端应捕获
- 多个信号连续到达可能合并（non-real-time signals）

### 2.3 信号发送 / 捕获示例

```bash
# 发
kill -TERM  <pid>
kill -HUP   <pid>        # 重读配置
kill -USR1  <pid>        # 自定义，如刷日志
kill -KILL  <pid>        # 强制杀
kill -0    <pid>        # 检查存在

# 批量
pkill -TERM -f 'nginx'
pkill -HUP nginx          # 重读
```

C / Go / Python 都能注册 handler：

```c
// C
#include <signal.h>
void handler(int sig) { /* cleanup, mark "shutting down" */ }
signal(SIGTERM, handler);
```

```go
// Go：channel + 优雅关闭
sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, syscall.SIGINT, syscall.SIGTERM)
go func() {
    <-sigCh
    // ... 关闭 listener / 排空
}()
```

```python
# Python：atexit + signal
import signal, atexit

def shutdown(*_):
    print("cleaning up...")

signal.signal(signal.SIGTERM, shutdown)
atexit.register(shutdown)
```

## 三、平滑重启模型 4 种

```text
1. PID 替换型：   old PID 被 kill, new PID 接管
   ↓ 风险：old 进程正在处理的请求被截断
   ↓ 解决：graceful shutdown

2. master-worker：master 收到信号后 fork 新 worker, old worker 排空
   ↓ Nginx / uWSGI / Gunicorn / Passenger

3. socket fd 传递：master 持 socket, worker 重启时传 fd
   ↓ systemd socket activation / process inheritance

4. 滚动发布：   LB 摘流 → 部署 → 重新加入 LB
   ↓ K8s / Consul / Envoy
```

### 3.1 信号驱动的"程序承诺"

```text
进程收到 SIGTERM 之后的"正确姿势"：
  1. 标记 "正在关闭"（健康检查返回 unhealthy / readiness = false）
  2. 关闭 listener，停止接受新请求
  3. 等现有请求处理完（或超时）
  4. flush 状态 / 关闭数据库 / ack 完消息
  5. exit(0)
```

经典时间线：

```text
T0  SIGTERM 抵达
T1  进程进入"优雅关闭"状态
T2  LB / kube-proxy 看到 readiness 失败，自动摘除流量（健康检查 interval）
T3  关闭 listener
T4  等待所有 in-flight 处理完（最多 timeout 30s）
T5  释放资源（数据库 / 缓存 / 队列）
T6  exit(0)
```

## 四、典型场景方案

### 场景 1：HTTP 服务（Nginx / Express / Spring Boot）

#### Nginx

```nginx
worker_processes 4;
pid /var/run/nginx.pid;

# 收到 SIGUSR1 时日志轮转
# 收到 SIGQUIT (kill -QUIT) 优雅关闭
# 收到 SIGHUP 重读配置
```

```bash
nginx -s reload           # 等价 SIGHUP
nginx -s reopen           # 重新打开日志
nginx -s quit             # 优雅退出
```

内部：

- master 收到 SIGHUP → 重新读配置 → fork 新 worker → 旧 worker 排空
- 旧 worker 处理完当前请求后退出

#### Node.js Express

```js
const server = app.listen(80);

// 收到 SIGTERM 时
process.on('SIGTERM', () => {
    console.log('SIGTERM received');
    server.close(() => {
        // 关闭数据库 / Redis 连接等
        process.exit(0);
    });
    // 强制超时
    setTimeout(() => process.exit(1), 30 * 1000).unref();
});
```

#### Spring Boot 内嵌 Tomcat

```yaml
server:
  shutdown: graceful          # 启用
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

- 收到 SIGTERM 后，停止接受新请求
- 等待 in-flight 完成（最多 30s）
- 然后退出

#### Netty / Tomcat NIO

- Tomcat 自带 `GracefulShutdown`
- `shutdownGracePeriod` 可配置

### 场景 4：消息消费者（Kafka / RabbitMQ / RocketMQ）

#### Kafka 消费者

```python
# 收到 SIGTERM 后
import signal

shutdown = False

def graceful(*_):
    global shutdown
    shutdown = True
    consumer.wakeup()      # 退出 poll()

signal.signal(signal.SIGTERM, graceful)

while not shutdown:
    msg = consumer.poll()
    process(msg)
    consumer.commit()
# 关闭
consumer.close()
```

要点：

- 显式 commit 已处理 offset
- Kafka client 提供 `consumer.wakeup()` 让 poll() 抛异常退出
- `consumer.close()` 释放连接

#### RabbitMQ 消费者

```python
# 收到 SIGTERM 后停止接收
connection.add_callback_threadsafe(callback)
# callback: basic_cancel + connection.close
```

#### RocketMQ

RocketMQ 自身有优雅停机：

- Consumer 重启前 `shutdownGracefully`
- RocketMQ 5.x Consumer 增加 `concurrentlyEnable` + `maxDelay` 等参数
- 关闭：调用 `consumer.shutdown()` 取消订阅

### 场景 10：systemd socket activation

```ini
# /etc/systemd/system/myapp.socket
[Socket]
ListenStream=8080

# /etc/systemd/system/myapp.service
[Service]
ExecStart=/usr/bin/myapp
ExecStop=/usr/bin/myapp-shutdown
```

systemd 自己持有 socket fd，把 fd 传给 `myapp`。重启时：

- 旧进程仍持有 socket 接收请求（linger TIME_WAIT）
- 新进程接 fd（SO_REUSEPORT）接管新连接
- 旧进程只处理 in-flight，退出
- **零丢包**

### 场景 13+：Nginx 二进制热升级（USR2 信号链）

Nginx 不仅支持配置重载（SIGHUP），还支持"二进制本身"的热升级：通过一组信号让新 master 接管 socket fd，老 master 排空退出。

```text
                     nginx 老 master (pid: 1000)
                          │
                          │  kill -USR2 1000
                          ▼
                     fork 出新 master
                     pid 文件变为 nginx.pid.oldbin
                          │
                          ▼
                     nginx 新 master (pid: 2000)
                     同 listen socket (共享 fd)
                          │
                          │  kill -WINCH 1000
                          ▼
                     老 master 让 worker 优雅退出
                          │
                          ▼
                     kill -QUIT 1000
                     老 master 完全退出

最终：pid 文件恢复为 nginx.pid 指向新 master
```

完整脚本：

```bash
# 1. 查看老 master PID
OLDPID=$(cat /var/run/nginx.pid)

# 2. 备份老二进制（万一回滚）
cp /usr/sbin/nginx /usr/sbin/nginx.old

# 3. 安装新二进制
cp /path/to/new-nginx /usr/sbin/nginx

# 4. 触发热升级：老 master fork 出新 master
kill -USR2 $OLDPID

# 5. 等待新 master 启动 + 端口接管
sleep 2

# 6. 让老 master 通知 worker 退出（保留老 master 监控）
kill -WINCH $OLDPID

# 7. 观察老 workers 退出后，停老 master
kill -QUIT $OLDPID

# 8. 检查是否成功
curl http://127.0.0.1/
cat /var/run/nginx.pid      # 已切换为新 master PID
```

各信号作用：

| 信号 | 行为 |
| --- | --- |
| `SIGHUP` | 重新读取配置（master/worker 重启） |
| `SIGUSR1` | reopen 日志（不重启进程） |
| `SIGQUIT` | 优雅退出 master（worker 排空） |
| `SIGUSR2` | **热升级**：老 master fork 新 master，共享 listen socket fd |
| `SIGWINCH` | 让老 master 的 worker 优雅退出（master 不退） |
| `SIGTERM` | master 收到，优雅退出（worker 排空） |

为什么能"无缝"？

- 老 master fork 出新 master 时**复制了 listen socket fd**
- 双方都 bind 同一个端口（内核 SO_REUSEPORT 允许）
- 老 workers 仍在处理 in-flight，新 workers 处理新连接
- WINCH 让老 workers 关闭 listener，等 in-flight 完成
- 老 master 仍监控 / logs（直到 QUIT 完全退出）
- 整个过程对客户端透明

实战要点：

```bash
# 验证热升级成功
ls /var/run/nginx.pid*        # 通常两个：nginx.pid 与 nginx.pid.oldbin
ps -ef | grep nginx            # 看到新老 master 共存
# 新 master: PID X (新)
# 老 master: PID X + 1 (frozen until QUIT)
```

回滚：

```bash
# 如果新版本有问题
kill -QUIT $(cat /var/run/nginx.pid)
cp /usr/sbin/nginx.old /usr/sbin/nginx
# 新 master 退出，老二进制恢复到 pid 文件
```

扩展（更复杂的"全有"）：

```bash
# 一键热升级脚本
#!/bin/bash
OLD=$(cat /var/run/nginx.pid)
NEW=/opt/nginx/sbin/nginx

kill -USR2 $OLD
sleep 1
kill -WINCH $OLD
sleep 3
# 此时检查新版本
if curl -sf http://localhost/healthz; then
    kill -QUIT $OLD
else
    kill -QUIT $NEW
    cp /usr/sbin/nginx.old /usr/sbin/nginx
fi
```

## 五、进程启动 / 退出钩子汇总

| 语言 | 钩子 |
| --- | --- |
| **C / C++** | `atexit() / signal(SIGTERM, h)` |
| **Go** | `os/signal.Notify + defer` |
| **Python** | `signal.signal + atexit` |
| **Java** | `Runtime.addShutdownHook` / Spring `SmartLifecycle` |
| **Node.js** | `process.on('SIGTERM', ...)` |
| **Rust** | `tokio::signal + ctrlc crate` |
| **PHP** | `pcntl_signal` |

```go
// Go canonical
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()

go func() {
    <-ctx.Done()
    log.Println("shutting down")
    // 排空
}()
```

```python
# Python: signal + atexit
import signal, atexit
running = True
def stop(*_):
    global running
    running = False

signal.signal(signal.SIGTERM, stop)
signal.signal(signal.SIGINT, stop)
atexit.register(stop)
```

## 六、平滑重启 + 快速重试：踢腿

```text
1. 收到 SIGTERM
2. readiness 检查改为 unhealthy
3. LB / kube-proxy 更新路由表（5-10s）
4. 关闭 listener
5. 等待 in-flight 完成（最多 30s）
6. exit

如果 30s 内没退完 → SIGKILL 强制杀
```

K8s 中：

```text
terminationGracePeriodSeconds: 30
容器收到 SIGTERM → 等 30s → SIGKILL
```

如果服务本身需要 60s：

- 给 readiness 让 LB 提前摘掉流量
- `terminationGracePeriodSeconds: 90`

## 七、SO_REUSEADDR / SO_REUSEPORT

为了让新进程立即接管端口：

```c
int yes = 1;
setsockopt(s, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));
```

`SO_REUSEPORT` 让多个进程同时 bind：

```python
sock.setsockopt(SOL_SOCKET, SO_REUSEPORT, 1)
```

注意：

- `SO_REUSEADDR`：可绑定 TIME_WAIT 状态端口
- `SO_REUSEPORT`：多个 listener 内核负载均衡
- Kubernetes / Docker 上需确认 NLB / 节点监听兼容

## 八、滚动 / 蓝绿 / 金丝雀

```text
  Blue (old)         Green (new)         LB / kube-proxy
      │                   │              │
   1. 100% 流量               │
      │                   │
   2. 50% 流量           50% 流量
      │                   │
   3. 0% 流量            100% 流量
      │                   │
   4. 销毁 Blue
```

K8s 中：

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 0%
```

要点：

- `maxUnavailable: 0`：100% 可用
- `maxSurge`：先 surge 出来
- `preStop hook`：触发 readiness

## 十、面试回答模板

1. **什么是平滑重启**（0.5 分钟）
   - 收到 SIGTERM 后做收尾，让 in-flight 请求完成，再退出
   - 关键：readiness → listener 关闭 → flush → exit

2. **Linux 信号机制**（0.5 分钟）
   - SIGTERM 可捕获，SIGKILL/SIGSTOP 不可
   - 进程注册 signal handler
   - atexit / shutdown hook

3. **HTTP 服务怎么做**（1 分钟）
   - Nginx: master/worker 模式
   - Spring Boot: `server.shutdown=graceful`
   - Express: `process.on('SIGTERM')` + `server.close()`

4. **消息消费者怎么做**（1 分钟）
   - Kafka: `wakeup()` + `commit()` + `close()`
   - RabbitMQ: basic_cancel + connection close

5. **K8s / Docker**（1 分钟）
   - `preStop hook` + `terminationGracePeriodSeconds`
   - Rolling update

6. **多进程 / 多实例**（0.5 分钟）
   - SO_REUSEPORT / socket activation
   - 蓝绿 / 金丝雀

7. **加分项**（0.5 分钟）
   - SO_REUSEADDR / TIME_WAIT
   - SIGHUP 重新读配置（Nginx）
   - systemd Notify Type=notify
   - database 异步提交 / async commit

## 十一、一句话总结

```text
平滑重启 = SIGTERM + signal handler + readiness + listener close + drain + exit
场景：HTTP (server.shutdown / process.on) / WS (graceful close)
      MQ 消费者 (wakeup + commit + close)
      DB (async commit / HikariCP graceful)
      K8s (preStop + terminationGracePeriodSeconds)
      systemd (socket activation + SO_REUSEPORT)
关键原则：捕获 SIGTERM（不 SIGKILL），标记 shutdown，关闭 listener，等待 in-flight，最后 exit
```
