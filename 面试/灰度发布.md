# 灰度发布

## 一、面试怎么开口

不要上来背定义。先给**一句话定位 + 一个真实场景**，把话题引到自己准备好的深水区。

> 灰度发布本质是**把"发布"这个一次性动作，拆成可控、可观测、可回退的连续过程**——用小部分真实流量去验证新版本，指标不达标就回滚，达标就放量。
>
> 我在上家公司做订单中心，20 个 Pod、日常 3k QPS、大促峰值 1.2w。有一次重构支付渠道路由逻辑，单测和压测都过了，但线上有个上游老客户端传的字段格式不一样，全量发上去 5 分钟内错误率从 0.02% 涨到 4%。这次事故之后我们落地了全链路灰度，后面同类改动都是先 1% 流量跑 30 分钟，再 10% → 50% → 100%。

**关键：面试官想听的不是"灰度是什么"，是"你怎么保证灰度流量不串、数据不脏、能秒回滚"。**

先说清楚容易混淆的三个词（面试常考）：

| 概念 | 做法 | 特点 |
|---|---|---|
| **蓝绿发布** | 两套完整环境，切换路由一次性全切 | 回滚最快（切回去），但要双倍资源，且没有"小流量验证"阶段 |
| **金丝雀 / 灰度** | 新版本先接少量流量，逐步放大 | 资源开销小，能真实验证，但需要版本共存的兼容性设计 |
| **A/B 测试** | 按用户特征分组，对比**业务指标** | 目的是选方案（哪个转化高），不是验证稳定性；周期以天/周计 |

一句话区分：**蓝绿看"切不切"，灰度看"稳不稳"，A/B 看"哪个好"。**

## 二、方案一：接入层按流量比例分流（Nginx / OpenResty / APISIX）

### 适用场景
单体应用、或改动只落在一个无状态服务上，不涉及跨服务调用链。

### 实现

**A. Nginx `split_clients`（按变量哈希，同一用户稳定命中）**

```nginx
# 按 cookie 里的 uid 哈希，保证同一用户每次都进同一个版本
split_clients "${cookie_uid}" $backend_pool {
    5%      gray_pool;    # 灰度 5%
    *       stable_pool;
}

upstream gray_pool   { server 10.0.1.10:8080; }
upstream stable_pool { server 10.0.1.20:8080; server 10.0.1.21:8080; }

server {
    location /api/ {
        proxy_set_header X-Env $backend_pool;   # 染色标透传下去
        proxy_pass http://$backend_pool;
    }
}
```

**B. 白名单优先（内部员工先跑）**

```nginx
map $http_x_user_id $is_whitelist {
    default   0;
    ~^(10086|10087|10088)$  1;
}
# 白名单命中直接进 gray_pool，未命中再走 split_clients
```

**C. APISIX / Kong 的 traffic-split 插件**——同样能力但配置走 Admin API，**改分流比例不用 reload**，这是它相对原生 Nginx 最大的优势。

```json
{
  "plugins": {
    "traffic-split": {
      "rules": [{
        "match": [{"vars": [["http_x_user_tag", "==", "gray"]]}],
        "weighted_upstreams": [
          {"upstream_id": "gray-svc",  "weight": 5},
          {"upstream_id": "stable-svc","weight": 95}
        ]
      }]
    }
  }
}
```

### 优缺点
- ✅ 改动小，不侵入业务代码，任何语言栈都能用
- ✅ 性能损耗几乎为 0
- ❌ **只能灰度第一跳**。A(灰度) → B → C，请求到了 B 之后就丢标了，B 会随机打到 B 的稳定版和灰度版上，微服务场景下基本不可用
- ❌ Nginx 改比例要 reload（APISIX 无此问题）

### 一句话话术
> "接入层分流适合边缘服务或单体，我们前端 BFF 层就是这么做的。但订单链路有 6 层调用，接入层分流管不到后面，所以往下必须做全链路灰度。"

## 三、方案二：网关染色 + 全链路灰度（微服务标配，重点讲这个）

### 核心思想
**打标 → 透传 → 路由**三步：

1. **打标（染色）**：网关根据规则（用户 ID / 地域 / 设备 / 白名单）给请求打上 `x-env: gray`
2. **透传**：这个标要跟着调用链跑完全程——HTTP header 透传、Dubbo attachment、MQ message header，用 `ThreadLocal`/`TransmittableThreadLocal` 在服务内传递（**异步线程池场景必须用 TTL，用普通 ThreadLocal 会丢标，这是高频追问点**）
3. **路由**：每个服务的实例在注册中心带上元数据标签（Nacos `metadata.version=gray`），负载均衡时优先选同标签实例，**没有灰度实例则回退到稳定版**（fallback 策略必须有，否则灰度服务没部署就 503）

### 落地代码骨架

```java
// 1. 网关：染色
@Component
public class GrayTagFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange ex, GatewayFilterChain chain) {
        String uid = ex.getRequest().getHeaders().getFirst("X-User-Id");
        if (grayRuleService.hit(uid)) {          // 规则来自配置中心，可热更新
            ServerHttpRequest req = ex.getRequest().mutate()
                    .header("x-env", "gray").build();
            return chain.filter(ex.mutate().request(req).build());
        }
        return chain.filter(ex);
    }
    @Override public int getOrder() { return -100; }
}

// 2. 服务内：透传（用 TTL 兼容线程池）
public class GrayContext {
    private static final TransmittableThreadLocal<String> TAG = new TransmittableThreadLocal<>();
    public static void set(String v) { TAG.set(v); }
    public static String get() { return TAG.get(); }
    public static void clear() { TAG.remove(); }   // 必须清，否则线程复用串标
}

// 3. 出口：Feign 拦截器把标带给下游
@Component
public class GrayFeignInterceptor implements RequestInterceptor {
    @Override public void apply(RequestTemplate t) {
        String tag = GrayContext.get();
        if (tag != null) t.header("x-env", tag);
    }
}

// 4. 负载均衡：按标选实例，无灰度实例则降级到稳定版
public class GrayLoadBalancer implements ReactorServiceInstanceLoadBalancer {
    private List<ServiceInstance> filter(List<ServiceInstance> all) {
        String tag = GrayContext.get();
        if (!"gray".equals(tag)) {
            return all.stream()
                .filter(i -> !"gray".equals(i.getMetadata().get("version")))
                .collect(toList());
        }
        List<ServiceInstance> gray = all.stream()
            .filter(i -> "gray".equals(i.getMetadata().get("version")))
            .collect(toList());
        return gray.isEmpty() ? all : gray;      // 关键：兜底
    }
}
```

### 现成轮子
自己造这套至少两周，面试时可以说"我们评估过自研和开源"：
- **Spring Cloud Alibaba + Nacos**：`spring.cloud.nacos.discovery.metadata.version=gray`，配合自定义 `LoadBalancer`
- **Dubbo Tag Router**：原生支持，`RpcContext.setAttachment("dubbo.tag", "gray")`，服务端按 `dubbo.provider.tag` 匹配，是这套里最省事的
- **阿里 MSE / 微服务引擎**：Java Agent 字节码增强，业务代码零改动，商业方案
- **OpenTelemetry Baggage**：用标准的 `baggage` header 传染色标，好处是和链路追踪天然打通，trace 里能直接看到灰度标

### 优缺点
- ✅ 真正解决微服务多跳问题，**能按用户维度精确控制**（VIP 客户永不进灰度）
- ✅ 灰度实例可以只部署 1 个，不用双倍资源
- ❌ 有侵入，全公司所有服务都要接同一套 SDK，推动成本高
- ❌ 异步、MQ、定时任务这些"断链"场景要单独处理（见第八节）

## 四、方案三：Service Mesh（Istio）—— 业务零侵入

### 实现

```yaml
# 1. 定义子集
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata: {name: order-svc}
spec:
  host: order-svc
  subsets:
    - name: v1
      labels: {version: v1}
    - name: v2
      labels: {version: v2}
---
# 2. 路由规则：header 精确匹配优先，其余按权重
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: {name: order-svc}
spec:
  hosts: [order-svc]
  http:
    - match:                                  # 内部员工强制走 v2
        - headers:
            x-user-tag: {exact: "internal"}
      route:
        - destination: {host: order-svc, subset: v2}
    - route:                                  # 其余 5% 放量
        - destination: {host: order-svc, subset: v1}
          weight: 95
        - destination: {host: order-svc, subset: v2}
          weight: 5
```

**流量镜像（Mirror）——这个点很能加分**：把 100% 生产流量**复制**一份打到新版本，响应直接丢弃，用户完全无感。适合验证性能、验证重构后逻辑一致性，风险为零。

```yaml
    - route:
        - destination: {host: order-svc, subset: v1}
      mirror: {host: order-svc, subset: v2}
      mirrorPercentage: {value: 100.0}
```

> 注意：镜像流量会**真实执行写操作**，所以只适合读接口，或者新版本连的是影子库。这是面试官最爱追的坑。

### 优缺点
- ✅ 业务代码零改动，多语言统一（Go/Java/Python 混合栈的救命方案）
- ✅ 路由规则热更新，改权重不重启不 reload
- ⚠️ **Envoy 只自动透传它自己的 trace header，业务染色标仍需应用层传递**——不要以为上了 Mesh 就全自动透传，这是常见误解，答对能加分
- ❌ Sidecar 带来额外延迟（毫秒级）和内存开销（每 Pod 几十~上百 MB）
- ❌ 运维复杂度高，团队没有 K8s / Mesh 基建就别提这个方案

## 五、方案四：K8s 渐进式交付（Argo Rollouts / Flagger）—— 自动分析 + 自动回滚

前三种解决"怎么分流"，这个解决"**谁来决定放量还是回滚**"。前三种要人盯着 Grafana 手动点，这个是自动化的。

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: {name: order-svc}
spec:
  replicas: 20
  strategy:
    canary:
      trafficRouting:
        istio:
          virtualService: {name: order-svc}
      analysis:                          # 每一步都跑指标分析，不达标自动回滚
        templates: [{templateName: success-rate}]
      steps:
        - setWeight: 5
        - pause: {duration: 10m}
        - setWeight: 20
        - pause: {duration: 10m}
        - setWeight: 50
        - pause: {duration: 30m}
        - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: {name: success-rate}
spec:
  metrics:
    - name: success-rate
      interval: 1m
      successCondition: result[0] >= 0.995
      failureLimit: 2                    # 连续 2 次不达标 → 自动回滚
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_requests_total{service="order-svc",version="canary",code!~"5.."}[2m]))
            / sum(rate(http_requests_total{service="order-svc",version="canary"}[2m]))
```

### 优缺点
- ✅ **回滚时间从"人发现 + 人操作"的十几分钟压到 2 分钟以内**，这是可以写进简历的量化指标
- ✅ 发布流程标准化，不依赖发布人的经验
- ❌ 强依赖完善的监控指标体系，指标不准会误杀（要设 `failureLimit` 而不是一次不过就回滚）
- ❌ 只能按流量比例，做不到按用户维度精确控制，需要和方案二/三组合

## 六、方案五：功能开关（Feature Flag）—— 不发版的灰度

### 核心区别
前四种是**部署级灰度**（灰度的是"版本"），Feature Flag 是**代码级灰度**（灰度的是"逻辑分支"）。新旧代码同时在线上，用开关决定走哪条。

```java
if (featureFlag.isEnabled("new-payment-router", userId)) {
    return newRouter.route(order);
} else {
    return oldRouter.route(order);
}
```

配合 Apollo / Nacos / Unleash 做配置热更新，**秒级生效、秒级回滚，不需要重新部署**。

### 什么时候必须用它
- 改动是**业务逻辑分支**而非整个服务（比如换个风控规则）
- 需要按复杂维度圈人（城市 + 会员等级 + 设备型号）
- 大促期间**禁止发布**，但需要一个能随时关掉的兜底开关
- 后端先发布、前端后发布的功能，用开关控制何时对用户可见（**解耦"部署"与"上线"**）

### 优缺点
- ✅ 回滚最快（改配置，秒级），粒度最细
- ✅ 不占额外资源
- ❌ **技术债**：if/else 会越堆越多，必须建立"开关生命周期"制度——功能全量后两周内删除废弃开关，否则一年后没人敢动那段代码
- ❌ 只能灰度这一个点，改动分散在多个服务时不适用

### 选型决策树（面试追问"你们怎么选"时直接答）

```text
改动落点在哪？
├── 单服务 / 边缘 BFF ────────────────→ ① 接入层分流
├── 跨服务调用链（最常见）─────────────→ ② 全链路染色
│   ├── 团队有 Mesh 基建、多语言 ──────→ ③ Istio（替代 ② 自研）
│   └── 想把"决定放量"也自动化 ────────→ ② + ④ 组合
├── 业务逻辑分支 / 开关类需求 ─────────→ ⑤ Feature Flag
└── 大型重构 / 高风险上线 ─────────────→ ② + ④ + ⑤ 三件套
```

### 真实生产往往是组合拳

- **大厂标配**：① BFF 层 + ② 核心链路 + ④ 自动编排 + ⑤ 业务开关
- **中小厂起步**：先做 ① 解决 80% 场景，业务复杂后再上 ②；Mesh 和 Argo 是规模/基建到一定阶段才考虑
- **不要一上来就上 Mesh**：Istio 的 2-5ms 延迟在 1k QPS 下无所谓，在 10w QPS + 长链路下是真能压垮 P99 的

## 八、真正的难点（面试官追问的都在这，答对这几条才算及格线以上）

### 1. 同一用户必须稳定命中同一版本
不能用随机数或轮询分流，否则用户刷新一次就在新旧版本之间来回跳，看到的数据不一致。**必须用 userId / deviceId 做一致性哈希或取模**。

> `hash(uid) % 100 < 5` → 进灰度。这样 5% 是固定的那批人，放量到 10% 时原来那 5% 仍在灰度里，不会有人"被踢出灰度"。

### 2. 数据库变更怎么灰度（最难，也最能体现水平）
新旧版本代码同时在线，**共用一个数据库**。原则是 **DDL 必须向后兼容，用 Expand-Contract（扩展-收缩）三阶段**：

| 阶段 | 动作 | 说明 |
|---|---|---|
| **Expand** | 只加字段 / 加表，加可空列或带默认值 | 老版本代码完全无感 |
| **Migrate** | 新版本双写新旧字段，后台任务回刷历史数据 | 灰度期就在这个阶段 |
| **Contract** | 全量稳定 2 周后，删旧字段 | 单独一次发布 |

**灰度期间绝对禁止**：改字段类型、删列、重命名列、加 NOT NULL 无默认值约束——这些会让老版本代码直接崩。

大表加索引/加列要用 `gh-ost` / `pt-online-schema-change` / MySQL 8 的 Instant DDL，避免锁表。

### 3. 消息队列怎么灰度
灰度服务发的消息，可能被稳定版消费者消费到，逻辑就串了。三种解法：

- **消息染色 + 消费端过滤**：消息 header 带 `x-env=gray`，稳定版消费者收到灰度消息直接 `ack` 跳过（简单但浪费投递）
- **独立 Topic 物理隔离**：灰度走 `topic-gray`，最干净，但要多维护一套 topic 和消费者
- **消费组隔离 + 服务端过滤**：灰度消费者用独立 `consumerGroup`，RocketMQ 用 Tag 或 SQL92 过滤（`MSG_ENV = 'gray'`），Broker 侧就过滤掉，不占客户端资源

定时任务同理：**灰度实例默认不跑定时任务**，用 XXL-Job 的分组/标签路由指定执行实例。

### 4. 缓存污染
新版本改了缓存对象的结构（加了字段、换了序列化方式），老版本读到反序列化失败。

- 缓存 key **加版本前缀**：`order:v2:{id}`，新旧物理隔离，代价是灰度期缓存命中率下降
- 序列化用 **向后兼容的协议**（Protobuf 加字段不破坏兼容；Java 原生序列化最脆弱，别用）
- 灰度期新增字段一律**可空 + 有默认值**，Jackson 反序列化配 `FAIL_ON_UNKNOWN_PROPERTIES=false`

### 5. 长连接 / 有状态服务怎么灰度
WebSocket、gRPC 长连接建立后就不再走负载均衡了，改权重对存量连接无效。

- 靠**连接自然过期 + 新连接按新规则分配**，配合客户端重连退避
- 或者服务端主动发**优雅下线信号**，让客户端分批重连（要控制重连风暴，加随机抖动）
- 有状态服务（如带本地缓存的）优先考虑 **StatefulSet + 分区滚动更新**（`partition` 字段控制只更新序号 ≥ N 的 Pod）

### 6. 观测：灰度期到底看什么指标
只看"没报错"是不够的，要分三层：

| 层级 | 指标 | 阈值示例 |
|---|---|---|
| 系统 | CPU、内存、GC 次数/耗时、线程数 | Full GC 频次不高于稳定版 |
| 服务 | 错误率、P99/P999 延迟、QPS | 错误率 < 0.5%，P99 不劣化超 20% |
| 业务 | 下单成功率、支付转化率、核心漏斗 | 与稳定版差异在置信区间内 |

**关键：所有指标必须能按版本维度拆分**——Prometheus 打点带 `version` label，日志和 Trace 带染色标，否则灰度出问题你在大盘上根本看不出来（5% 的流量出错，整体错误率只涨 0.2%，会被噪声淹没）。

### 7. 灰度的退出条件要预先定义
面试时说这句话很加分：

> "我们规定灰度不是'看着没问题就放量'，而是**发布前就写死放量节奏和回滚阈值**：5% 跑满 30 分钟且错误率 < 0.5% 才能进下一档，任一指标触发阈值立即回滚、不允许人工判断'再观察观察'。因为线上事故最常见的原因就是发布人心存侥幸。"

## 九、标准回答模板（3 分钟版）

> **定位**：灰度发布的目的是用最小的爆炸半径验证新版本，核心是三件事——分流可控、状态可观测、回滚可执行。
>
> **分层方案**：我们是分层做的。边缘 BFF 用 APISIX 的 traffic-split 按比例分流，成本最低；核心微服务链路做全链路染色，网关按 userId 打标，通过 header + Dubbo attachment 透传，Nacos 元数据打标做实例路由，保证一个请求在 6 层调用里都走灰度实例；发布编排用 Argo Rollouts，接 Prometheus 做自动分析，指标不达标自动回滚。业务逻辑级的改动不走发版，用 Apollo 开关控制。
>
> **踩过的坑**：最早我们只做了接入层分流，以为够用，结果下游服务的灰度实例接到了稳定版流量，排查了半天。第二个坑是异步场景丢染色标，线程池里 ThreadLocal 传不下去，换成 TransmittableThreadLocal 才解决。第三个是数据库，有次灰度加了 NOT NULL 字段，稳定版插入直接报错，后来定了规矩：灰度期 DDL 只准 Expand，删列必须等全量后单独发一次。
>
> **量化结果**：落地之后发布导致的 P2 以上故障从每季度 3 次降到 0，平均回滚时间从 12 分钟降到 90 秒。

## 十、可能被追问的问题清单

1. **灰度实例部署几个？** —— 至少 2 个。1 个的话它挂了你分不清是新版本 bug 还是单点故障
2. **两个版本接口不兼容怎么办？** —— 接口变更遵循**只增不改不删**，新增字段可选，老接口保留一个版本周期
3. **怎么防止灰度用户投诉？** —— 优先圈内部员工、低价值用户、非核心时段；VIP 和大客户加白名单永不进灰度
4. **回滚之后灰度期的数据怎么办？** —— 脏数据修复脚本要**发布前就写好**，这是发布方案评审的必检项
5. **灰度和限流熔断的关系？** —— 灰度实例要单独配熔断阈值，避免灰度实例拖垮整体；Sentinel 按 `version` 维度配规则
6. **没有 K8s 怎么做？** —— 物理机时代靠 Nginx upstream 分组 + 配置中心，本质一样，只是编排靠脚本
7. **灰度和混沌工程的关系？** —— 灰度验证"新代码对不对"，混沌验证"系统扛不扛得住故障"，正交的两件事
8. **前端怎么灰度？** —— CDN 按 用户标 返回不同版本的 `index.html`，静态资源带 hash 不冲突；小程序/App 靠应用商店分阶段发布 + 强制更新开关兜底
