# 集群分层 (Cluster Layering)

## 一、集群分层概述

### 什么是集群分层

**集群分层 (Cluster Layering)** 是把一个分布式集群从下到上拆解为若干**职责清晰、边界明确**的层次,让每一层只关注自己应该解决的问题。

**本质**:分布式系统的"职责分工"——把**硬件、操作系统、运行时、调度、编排、应用、数据、流量、运维**等关注点分离,使复杂系统可以被独立设计、演进和运维。

**核心目标**:

- **关注点分离**:每层只解决一类问题
- **可替换性**:底层升级或更换不影响上层
- **可观测性**:每层都有独立的指标和日志
- **可扩展性**:水平扩展时,每层可以独立伸缩
- **故障隔离**:一层故障不会直接拖垮其他层
- **团队分工**:不同团队可以认领不同层级

### 为什么要分层

- **系统太复杂**:不分层无法理解和维护
- **关注点不同**:基础设施、应用、业务的诉求完全不同
- **变更频率不同**:底层几乎不变,业务层每天都在迭代
- **故障爆炸半径**:分层是控制爆炸半径的天然手段
- **复用与共享**:通用能力下沉,业务能力上浮
- **人才与组织**:不同技能栈的工程师可以分工协作

## 二、集群分层模型

### 1. 经典七层模型 (从下到上)

```text
┌─────────────────────────────────────┐
│  L7  业务应用层 (Business Apps)      │  ← 业务功能、领域逻辑
├─────────────────────────────────────┤
│  L6  平台服务层 (Platform Services)  │  ← 中间件、数据库、缓存、消息
├─────────────────────────────────────┤
│  L5  调度编排层 (Orchestration)      │  ← Kubernetes、Service Mesh
├─────────────────────────────────────┤
│  L4  运行时层 (Runtime)              │  ← 容器运行时、虚拟机
├─────────────────────────────────────┤
│  L3  操作系统层 (OS)                 │  ← Linux Kernel、cgroup、namespace
├─────────────────────────────────────┤
│  L2  基础设施层 (Infrastructure)     │  ← 物理机、虚拟机、网络、存储
├─────────────────────────────────────┤
│  L1  硬件层 (Hardware)               │  ← CPU、内存、磁盘、网卡
└─────────────────────────────────────┘
```

### 2. 云原生视角的四层模型

```text
┌─────────────────────────────────────┐
│  应用层 (Application)                │  ← 微服务、业务代码、配置
├─────────────────────────────────────┤
│  平台层 (Platform)                   │  ← K8s、中间件、Service Mesh、可观测
├─────────────────────────────────────┤
│  基础设施层 (Infrastructure)         │  ← 虚拟机、网络、存储、镜像仓库
├─────────────────────────────────────┤
│  硬件层 (Hardware)                   │  ← 物理服务器、交换机、机房
└─────────────────────────────────────┘
```

> 两种模型只是粒度不同,**核心思想一致**:把集群拆成多层,每层只关心自己。

## 三、硬件层 (Hardware)

### 1. 组成

- **CPU**:x86、ARM、RISC-V 等架构
- **内存**:DDR4/DDR5、ECC
- **存储**:HDD、SSD、NVMe
- **网络**:网卡、交换机、光模块
- **电源、散热、机架、机房**

### 2. 关键特性

| 特性 | 说明 |
|------|------|
| **故障域** | 一块磁盘、一个电源、一个机架,都是独立故障域 |
| **NUMA** | 多 CPU 内存访问不均匀,影响性能 |
| **SR-IOV / DPDK** | 网卡硬件特性,网络层会用到 |
| **异构计算** | GPU、NPU、TPU、FPGA,AI 集群关键 |

### 3. 关注点

- 硬件故障率、寿命、兼容性
- BIOS / BMC / IPMI 管理
- 服务器生命周期管理
- 与云厂商的边界:自建 vs IaaS vs 裸金属

---

## 四、基础设施层 (Infrastructure)

### 1. 组成

- **虚拟化 / 虚拟机**:KVM、VMware、Hyper-V
- **网络**:VPC、Subnet、Load Balancer、SDN
- **存储**:块存储、文件存储、对象存储
- **镜像仓库**:Docker Registry、Harbor
- **DNS、NTP、镜像加速**

### 2. 关键能力

- **资源池化**:把物理资源抽象为可分配的虚拟资源
- **网络连通**:东西向、南北向、跨节点、跨地域
- **存储持久化**:有状态服务的基石
- **镜像分发**:全球拉取、本地缓存

### 3. 关注点

- 资源利用率与碎片
- 网络延迟、带宽、抖动
- 存储 IOPS、吞吐、延迟
- 镜像拉取速度、安全扫描

---

## 五、操作系统层 (OS)

### 1. Linux 内核关键能力

| 能力 | 作用 |
|------|------|
| **进程/线程** | 任务调度单位 |
| **内存管理** | 虚拟内存、页面回收、Swap |
| **cgroup** | 资源限制、优先级、隔离 |
| **namespace** | 进程、网络、文件系统等隔离 |
| **网络协议栈** | TCP/IP、netfilter、eBPF |
| **文件系统** | ext4、xfs、btrfs、overlay |

### 2. 容器化关键路径

```text
进程
  ↓ namespace 隔离 (PID/Net/Mount/...)
  ↓ cgroup 限制 (CPU/Memory/IO)
  ↓ capability / seccomp 收敛权限
  ↓ 联合文件系统 (overlayfs)
容器 (Container)
```

### 3. 关注点

- 内核参数调优 (`sysctl`)
- cgroup v1 vs v2 差异
- 资源限制是否生效
- 容器逃逸风险

## 六、运行时层 (Runtime)

### 1. 容器运行时

| 类别 | 例子 |
|------|------|
| **高层运行时** | containerd、CRI-O |

### 2. 关键能力

- **镜像拉取与解压**
- **容器生命周期管理**
- **资源限制的真正执行者**
- **与 kubelet 通信 (CRI)**

### 3. 关注点

- 容器启动速度
- 镜像层缓存
- 运行时安全 (CVE、逃逸)
- 与 Kubernetes 版本的兼容性

## 七、调度编排层 (Orchestration)

### 1. 核心职责

- **调度**:把 Pod 放到合适的节点
- **自愈**:失败时重新调度
- **弹性**:HPA、VPA、KEDA
- **服务发现与负载均衡**
- **配置管理、密钥管理**
- **滚动升级、回滚**

### 2. 核心组件

```text
kube-apiserver    ← API 入口
  ↓
kube-scheduler    ← 调度决策
  ↓
kube-controller-manager  ← 状态收敛
  ↓
cloud-controller-manager ← 云厂商集成
  ↓
kubelet           ← 节点代理
  ↓
etcd              ← 集群状态存储
```

### 3. 关键抽象

| 抽象 | 作用 |
|------|------|
| **Pod** | 最小调度单位,共享网络和存储 |
| **Deployment** | 无状态应用 |
| **StatefulSet** | 有状态应用 |
| **DaemonSet** | 节点级守护进程 |
| **Job / CronJob** | 批处理与定时任务 |
| **Service** | 稳定的访问入口 |
| **Ingress** | 七层路由 |
| **ConfigMap / Secret** | 配置与密钥 |
| **PVC / PV** | 持久化存储 |
| **CRD + Operator** | 自定义资源与控制器 |

### 4. 关注点

- 调度延迟、调度失败
- 控制面可用性 (etcd、API Server)
- 节点压力驱逐
- 多集群、联邦、单元化

## 八、平台服务层 (Platform Services)

### 1. 中间件分类

| 类别 | 典型组件 |
|------|----------|
| **关系数据库** | MySQL、PostgreSQL、TiDB |
| **NoSQL** | MongoDB、Cassandra |
| **KV 存储** | Redis、Memcached、etcd |
| **搜索引擎** | Elasticsearch、OpenSearch、Meilisearch |
| **消息队列** | Kafka、RocketMQ、RabbitMQ、Pulsar |
| **时序数据库** | Prometheus、InfluxDB、TDengine |
| **对象存储** | S3、OSS、MinIO、Ceph |
| **配置 / 注册中心** | Nacos、Consul、ZooKeeper |
| **API 网关** | Kong、APISIX、Envoy Gateway |

### 2. 部署模式

- **集群内置**:与业务部署在同一集群
- **独立集群**:中间件独立部署,业务通过 Service 访问
- **托管服务**:使用云厂商的 PaaS 服务
- **Sidecar 化**:把中间件能力下沉到 Mesh 边车

### 3. 关注点

- 高可用与多副本
- 数据备份与恢复
- 容量与性能
- 多租户隔离
- 升级与兼容

## 九、应用层 (Application)

### 1. 微服务视角

```text
API Gateway
  ↓
BFF (Backend for Frontend)
  ↓
领域服务 (订单、商品、用户、支付)
  ↓
基础设施服务 (通知、文件、ID 生成)
  ↓
数据访问层 (ORM、DAO)
  ↓
数据库 / 缓存 / 消息
```

### 2. 关键模式

- **无状态**:实例可任意替换
- **幂等**:重试不会产生副作用
- **熔断 / 限流 / 降级**:保护自己、保护依赖
- **异步化**:消息队列解耦
- **缓存多级**:本地缓存 + 分布式缓存
- **可观测**:埋点、日志、链路、指标

### 3. 关注点

- 启动速度、优雅停机
- 资源消耗 (CPU/内存/连接)
- 错误率、延迟分布
- 依赖管理、超时设置

## 十、流量与访问层 (Traffic)

### 1. 流量分层

```text
用户
  ↓ CDN / 边缘节点
  ↓ DNS / 智能解析
  ↓ 负载均衡 (LB)
  ↓ API 网关 / Ingress
  ↓ Service Mesh (Sidecar)
  ↓ 应用实例
```

### 2. 关键组件

- **DNS**:智能解析、地理位置路由
- **CDN**:静态加速、边缘缓存
- **L4 LB**:四层负载均衡 (Nginx/LVS/云 LB)
- **L7 LB / API Gateway**:七层路由、限流、鉴权
- **Ingress Controller**:K8s 七层入口
- **Service Mesh**:服务间通信 (Istio、Linkerd)

### 3. 关注点

- 入口瓶颈、单点
- 灰度、流量切分
- 全链路加密、零信任
- 跨地域容灾

## 十五、组织与协作视角的分层

### 1. 团队分层

| 层级 | 典型团队 | 关注点 |
|------|----------|--------|
| **基础设施** | IaaS / 基础架构 | 服务器、网络、机房 |
| **平台** | SRE / 平台工程 | K8s、中间件、可观测 |
| **应用** | 业务研发 | 业务功能、领域建模 |
| **数据** | 数据工程 / 算法 | 数仓、特征、模型 |
| **安全** | 安全 / 合规 | 漏洞、审计、合规 |

### 2. Conway 法则

> **系统结构反映组织结构**

- 分层错位会导致协作成本
- 团队边界应与系统边界对齐
- 平台团队提供"内部产品",业务团队是"客户"

### 3. Internal Developer Platform (IDP)

- 平台团队 = 内部产品经理
- 业务团队 = 用户
- 衡量标准:开发者体验、发布频率、故障恢复时间

---

## 十六、分层的关键设计原则

### 1. 单一职责

- 每层只解决一类问题
- 不要让应用层直接操作磁盘
- 不要让基础设施层理解业务

### 2. 依赖方向

- **上层依赖下层,下层不依赖上层**
- 通过接口/契约通信
- 避免反向依赖 (循环依赖)

### 3. 关注点分离

- 业务与技术分离
- 状态与计算分离
- 控制面与数据面分离

### 4. 边界即治理

- 每层有自己的 SLO
- 每层有自己的指标和告警
- 每层有自己的 Runbook 和 Owner

### 5. 可演进

- 层次不是一成不变的
- 抽象可能过时,适时重构
- 新能力可以新增层次,而非堆积到旧层

---

## 十七、常见误区

- **分层变成"分层官僚"**:每层都加审批,反而拖慢交付
- **抽象泄漏**:上层被迫了解下层细节
- **过度分层**:每层只有几行代码,增加理解成本
- **分层不清**:一个组件同时跨多层,职责模糊
- **数据层被忽视**:只关注应用,数据成为最大风险
- **只关心技术分层,忽略组织分层**:Conway 反噬
- **把"分层"当成"分工":只分人不分事,边界仍模糊
- **缺乏统一可观测**:每层只看到自己,看不到全局
- **安全事后补救**:而非作为横切关注点贯穿所有层

---

## 十八、核心要点速记

- 分层是**关注点分离**,不是为了分层而分层
- 经典七层:**硬件 → 基础设施 → OS → 运行时 → 编排 → 平台服务 → 应用**
- **依赖方向单向**:上层依赖下层,下层不依赖上层
- **可观测性、安全、数据**是横切关注点,贯穿所有层
- **团队分层 = 系统分层**:Conway 法则无法绕过
- 平台团队提供"内部产品",业务团队是"客户"
- 每层都有自己的 SLO、Owner、Runbook
- 分层要有边界,但**不要有官僚**
- 关注演进:层次会过时,抽象要敢于重构
- 安全不能"事后补救",要从镜像、网络、权限、数据全方位覆盖
