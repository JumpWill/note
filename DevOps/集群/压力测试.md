# 集群压力测试 (Cluster Load Testing)

## 一、压力测试概述

### 什么是压力测试

**压力测试 (Load Testing / Stress Testing)** 是在受控环境下,使用**模拟真实业务流量**对系统施加**超过预期负载**或**极端条件**的实验,以发现系统在容量、性能、稳定性和弹性方面的**极限、瓶颈和薄弱点**。

**本质**:用**实验代替猜测**——在没有真实大流量之前,主动让系统"暴露问题"。

**核心目标**:

- **摸清容量上限**:系统能撑多大
- **定位瓶颈**:CPU、内存、磁盘、网络、数据库、锁、线程池
- **验证 SLO**:大流量下是否满足可用性和延迟
- **验证弹性**:扩容、限流、熔断、降级是否按预期工作
- **发现缺陷**:内存泄漏、连接泄漏、死锁、慢 SQL
- **建立基线**:性能回归对比的"参考点"
- **演练应急**:故障、灾备、限流、降级预案是否可行

### 压力测试的常见类型

| 类型 | 目的 | 负载 | 关注点 |
|------|------|------|--------|
| **基准测试 (Benchmark)** | 单组件性能上限 | 极限负载 | 绝对性能、瓶颈 |
| **负载测试 (Load)** | 验证额定容量 | 期望峰值的 1.0~1.2 倍 | SLO、稳定性 |
| **压力测试 (Stress)** | 推到崩溃点 | 远超预期 | 极限、故障模式 |
| **容量测试 (Capacity)** | 找出最大承载 | 阶梯递增 | 拐点、扩容阈值 |
| **峰值测试 (Spike)** | 模拟突发 | 瞬间大流量 | 弹性、缓冲 |
| **耐久测试 (Soak)** | 长时间运行 | 中等持续负载 | 内存泄漏、资源耗尽 |
| **并发测试 (Concurrency)** | 大量并发用户 | 高并发低流量 | 锁、线程、连接池 |
| **故障注入 (Chaos)** | 验证韧性 | 正常 + 故障叠加 | 降级、容错、隔离 |
| **断网/降级测试** | 验证弱网 | 网络抖动、丢包 | 客户端体验 |

## 二、压力测试的核心方法

### 1. 经典三段式

```text
准备阶段:环境、数据、脚本、监控
  ↓
加压阶段:梯度递增、保持、突发
  ↓
分析阶段:指标、瓶颈、改进、回归
```

### 2. 加压模型

- **阶梯递增 (Step Load)**:每分钟加 20%,观察拐点
- **波浪式 (Wave)**:模拟真实业务的波峰波谷
- **恒定压 (Constant)**:长时间恒定负载
- **脉冲式 (Spike)**:瞬间脉冲,看弹性
- **混合场景**:多接口按真实比例混合

### 3. 关注的核心指标

| 维度 | 指标 |
|------|------|
| **吞吐** | QPS / TPS / 带宽 |
| **延迟** | 平均、P50、P90、P95、P99、Max |
| **错误** | 错误率、错误码分布 |
| **资源** | CPU、内存、磁盘 IO、网络、连接数、线程数、GC |
| **依赖** | 数据库慢查询、缓存命中率、消息积压、RPC 失败率 |
| **弹性** | 扩容速度、降级触发、限流生效 |

### 4. 必须建立基线

- **同环境、同脚本、同数据**,才有可比性
- 每次压测保留:**基线 / 本次 / 对比** 三组数据
- 基线 = 上次通过的版本
- 性能回退 > X% 视为不通过

## 三、压测目标与场景设计

### 1. 明确目标

| 目标 | 关键问题 |
|------|----------|
| **容量评估** | 1 台机器能撑多少?10 台呢? |
| **扩容验证** | HPA 能否在 30 秒内扩容到位? |
| **SLO 验证** | 10 万 QPS 下 P99 < 200ms? |
| **故障演练** | 数据库主库挂了能切到从库吗? |
| **降级验证** | 限流是否按预期触发?降级是否生效? |
| **稳定性** | 持续 24 小时 5 万 QPS 会不会 OOM? |
| **回归** | 新版本有没有让性能下降? |

### 2. 场景设计原则

- **贴近真实**:用真实业务模型,不要"理想化"
- **混合比例**:读多写少、热点用户、热门商品
- **数据真实**:数据库表行数、缓存命中率贴近生产
- **包含边缘**:异常、慢响应、空值、超大请求
- **可重复**:脚本、参数、数据集都要可重放

### 3. 典型业务场景模板

```yaml
# 电商场景示例
scenario:
  name: "双 11 大促主流程"
  duration: 30m
  ramp_up: 5m
  mix:
    - api: "GET /home"
      ratio: 0.40
      think_time: 1s
    - api: "GET /product/:id"
      ratio: 0.30
      think_time: 2s
    - api: "POST /cart"
      ratio: 0.15
      think_time: 1.5s
    - api: "POST /order"
      ratio: 0.10
      think_time: 3s
    - api: "POST /pay"
      ratio: 0.05
      think_time: 2s
  data:
    hot_skus: 100      # 热点商品
    user_pool: 1000000 # 用户池
    cart_size: 1~5
  faults:
    - "DB master fail"
    - "1/3 cache node fail"
```

### 4. 数据准备

- **生产脱敏数据**:用户、商品、订单(合规要求)
- **冷热分布**:20% 商品承担 80% 流量
- **空数据 / 边界数据**:无库存、超大请求、特殊字符
- **数据量级**:数据库表行数至少达到生产 1/3

## 四、压测环境

### 1. 环境类型

| 环境 | 用途 | 优点 | 局限 |
|------|------|------|------|
| **生产压测 (全链路)** | 真实容量评估 | 真实可信 | 影响用户、风险大 |
| **预发环境** | 上线前验证 | 隔离 | 与生产差异大 |
| **独立压测环境** | 专项测试 | 灵活 | 资源差异 |
| **生产隔离流量** | 影子流量 | 不影响用户 | 写操作需回滚 |
| **仿真环境** | 架构验证 | 灵活 | 性能数据不可信 |

### 2. 生产压测的注意事项

- **业务低峰期**:深夜、夜间
- **限流兜底**:即使压垮也不影响真实用户
- **影子表 / 影子队列**:写操作不影响真实数据
- **流量标记**:用特殊 header 识别压测流量
- **应急预案**:一键停止,快速回滚
- **法务合规**:用户告知、数据脱敏

### 3. 影子表 / 影子链路

- **影子表**:压测数据写入 `order_shadow`,业务读主表
- **影子队列**:压测消息发送到 `topic_shadow`
- **影子 Token**:压测用户带特殊 Token,业务侧识别

| 工具 | 特点 | 适用 |
|------|------|------|
| **wrk / wrk2** | 轻量、C 语言 | HTTP 高并发基准 |

| **siege** | 多 URL | 混合场景 |

| **Gatling** | Scala DSL | 高并发 Web |
| **JMeter** | GUI、插件丰富 | 复杂场景 |
| **Vegeta** | Go 简单 | 持续加压 |
| **hey** | Go 极简 | 快速压测 |
| **Tsung** | Erlang | 大规模 |
| **Artillery** | Node | API 测试 |

### 2. 专用压测工具

- **数据库**:sysbench、pgbench、HammerDB
- **消息队列**:kafka-producer-perf-test、内置 benchmark
- **缓存**:redis-benchmark、memtier_benchmark
- **RPC**:ghz (gRPC)、自研框架
- **全链路**:阿里云 PTS、京东云压力测试、压测宝
- **混沌工程**:Chaos Monkey、ChaosBlade、Litmus

### 3. 工具选型原则

- **协议匹配**:HTTP、gRPC、WebSocket、TCP
- **性能要求**:能压到目标 QPS
- **场景复杂度**:多接口混合、参数化
- **可视化**:实时图表
- **分布式**:单机打不到时,需要多机联压
- **生态**:团队熟悉度、二次开发

### 4. 工具示例:wrk / k6

```bash

# wrk2 阶梯加压

```

```javascript
// k6 场景示例

  stages: [
    { duration: '2m', target: 1000 },

  check(res, { 'status is 200': (r) => r.status === 200 });
```

- **缓存**:命中率、延迟、淘汰、内存

- **节点**:CPU、内存、磁盘 IO、网络

### 3. 端到端链路

- 关键调用链各阶段耗时

### 4. 实时可视化

## 七、常见瓶颈与定位

### 1. CPU 瓶颈

- **现象**:CPU 接近 100%,延迟飙升
- **定位**:`top`、`perf`、火焰图、JFR
- **常见原因**:序列化、反序列化、复杂计算、热点代码

### 2. 内存瓶颈

- **现象**:频繁 GC、OOM、内存缓慢增长
- **定位**:堆 dump、jmap、pprof
- **常见原因**:内存泄漏、缓存无界、大对象、字符串拼接

### 3. 线程 / 协程瓶颈

- **现象**:响应慢、线程池满、任务拒绝
- **定位**:`jstack`、线程 dump
- **常见原因**:锁竞争、长事务、慢调用拖垮线程

### 4. 连接池瓶颈

- **现象**:大量请求等待连接、超时
- **定位**:连接池监控
- **常见原因**:连接泄漏、慢查询、连接数过小

### 5. 数据库瓶颈

- **现象**:QPS 上不去、慢查询、锁等待
- **定位**:慢 SQL 日志、EXPLAIN、InnoDB 状态
- **常见原因**:缺索引、复杂 JOIN、大事务、全表扫描

### 6. 缓存瓶颈

- **现象**:命中率骤降、响应慢、内存满
- **定位**:缓存监控、Key 分析
- **常见原因**:热点 Key、大 Key、缓存击穿

### 7. 消息队列瓶颈

- **现象**:消费积压、消费延迟
- **定位**:Broker、Consumer 监控
- **常见原因**:消费慢、生产突发、分区不均

### 8. 网络瓶颈

- **现象**:带宽打满、丢包、连接超时
- **定位**:`iftop`、`ss`、网卡监控
- **常见原因**:大文件传输、心跳风暴、跨地域

### 9. 锁与并发

- **现象**:吞吐量卡在某个值,加机器没用
- **定位**:锁监控、火焰图
- **常见原因**:分布式锁、本地锁热点、单点资源

### 10. 第三方依赖

- **现象**:调用外部 API 慢或失败
- **定位**:依赖监控、超时设置
- **常见原因**:第三方限流、网络问题

## 八、性能分析与诊断

### 1. 火焰图 (Flame Graph)

- **作用**:直观看到 CPU 时间花在哪里
- **工具**:perf、async-profiler、bpftrace
- **解读**:宽 = 热点、尖塔 = 异常深调用

### 2. 持续剖析 (Continuous Profiling)

- **工具**:Pyroscope、Parca、Conprof
- **价值**:长期低开销剖析,容易发现偶发热点
- **建议**:接入到所有核心服务

### 3. 链路追踪

- **工具**:Jaeger、Zipkin、OpenTelemetry、SkyWalking
- **价值**:看清请求在每个服务的耗时
- **压测场景**:对比正常 / 压测时各阶段耗时

### 4. 数据库分析

- **慢 SQL 日志**
- **EXPLAIN / EXPLAIN ANALYZE**
- **锁等待分析**
- **InnoDB 状态**
- **Performance Schema**

### 5. OS 层分析

- **CPU**:`top`、`perf`、`vmstat`
- **内存**:`free`、`pmap`、OOM 日志
- **磁盘**:`iostat`、`iotop`
- **网络**:`sar`、`iftop`、`ss`

### 6. 资源画像

每个核心服务应有:
- 典型 QPS 下的 CPU、内存画像
- 关键调用链画像
- 依赖资源画像

## 九、弹性与故障演练

### 1. 弹性验证

- **扩容速度**:HPA 多久能扩容到位
- **缩容策略**:何时缩容、是否抖动
- **冷启动**:新实例多久能接流量
- **预案生效**:限流、降级、熔断是否按配置触发

### 2. 故障演练 (Chaos Engineering)

- **原则**:在受控环境中注入故障,观察系统表现
- **场景**:
  - 杀进程 / Pod
  - 网络延迟、丢包、断网
  - CPU、内存、磁盘打满
  - 数据库主从切换
  - 缓存节点宕机
  - DNS 故障
  - 机房断电(演练级别)

### 3. 限流降级验证

- **触发条件**:是否按阈值正确触发
- **降级策略**:返回缓存默认值 / 友好错误
- **用户体验**:降级页面 / 提示
- **恢复**:故障消除后是否自动恢复

### 4. 数据回滚与补偿

- 压测写数据如何回滚
- 业务补偿任务是否生效
- 影子表与生产表数据一致性

## 十、安全与风险控制

### 1. 数据安全

- **生产压测必须脱敏**:用户、订单、支付
- **影子表 / 影子 Topic**:写操作隔离
- **压测数据清理**:结束后自动清理
- **权限隔离**:压测账号与生产账号分离

### 2. 流量隔离

- **业务低峰期**:避开真实用户
- **白名单**:压测流量走特殊链路
- **染色**:特殊 header / Token 标识
- **熔断兜底**:异常时自动停止

### 3. 容量保护

- **压测配额**:设置最大 QPS 上限
- **紧急停止**:一键 kill
- **限流保护**:被压方限流生效后,压测侧停止加压
- **多角色审批**:大流量压测需审批

### 4. 应急预案

- **数据库压力大**:立即降低压测 QPS
- **依赖故障**:暂停压测,排查依赖
- **数据异常**:立即停止,启动回滚
- **误伤真实用户**:立刻停止,启动回滚

### 5. 合规

- 用户告知 (隐私政策)
- 跨境数据传输合规
- 内部审计与留痕

## 十一、压测报告与决策

### 1. 压测报告内容

- **压测目标与场景**
- **环境与配置**
- **加压模型与梯度**
- **关键指标对比**
- **瓶颈与根因**
- **改进建议**
- **结论与风险**
- **下次压测计划**

### 2. 关键结论示例

```text
✅ 在 5 万 QPS、混合场景下,服务 P99 延迟 180ms < SLO 200ms
✅ CPU 平均 65%,未达瓶颈
✅ HPA 60 秒内扩容到位
❌ 数据库慢查询上升,锁定 3 条 SQL 待优化
❌ 缓存命中率达 92%,仍有 8% 穿透,需补充二级缓存
⚠️ 跨 AZ 流量激增 30%,长期可能导致带宽成本上升
```

### 3. 容量结论

```text
单实例能力:3000 QPS (P99 200ms)
集群目标:5 万 QPS
推荐节点:24 节点 (含 30% 冗余)
建议 HPA 上限:30 节点
```

### 4. 决策闭环

- **不通过**:发版阻塞,优化后重测
- **通过但有风险**:记录风险,提交改进
- **完全通过**:归档,作为下次基线

## 十二、压测在 CI/CD 中的位置

### 1. 测试金字塔中的压测

```text
                /\
               /  \      端到端
              / 压 \     全链路
             /  测  \
            /________\
           /          \
          /  性能测试   \
         /   基准测试    \
        /________________\
       /                  \
      /   单元/集成测试     \
     /______________________\
```

### 2. 压测分层

| 层级 | 频率 | 范围 | 工具 |
|------|------|------|------|
| **微基准** | 每次提交 | 函数/类 | JMH、go test -bench |
| **接口压测** | 每次 PR | 单接口 | k6、wrk |
| **链路压测** | 每次发版 | 关键路径 | 全链路工具 |
| **全链路大压测** | 大促前 | 全部核心 | PTS 等 |
| **容量评估** | 季度 | 整体集群 | 专项 |
| **故障演练** | 月度 | 韧性 | Chaos 工具 |

### 3. 性能门禁

- **PR 阶段**:核心接口微基准变化 < 10%
- **预发**:关键接口 P99 < SLO
- **上线前**:全链路压测通过
- **大促前**:专项容量评估通过

### 4. 持续压测 (Continuous Load Testing)

- **影子流量**:在生产环境持续注入影子流量
- **目的**:长期低开销发现性能漂移
- **工具**:生产流量回放、影子压测平台

## 十三、典型场景的压测重点

### 1. 电商大促

- **重点**:下单、支付、库存、限流、降级
- **场景**:商品详情、购物车、订单、支付、库存扣减
- **瓶颈**:库存扣减、下单链路、数据库写
- **演练**:秒杀、限流、熔断、库存超卖

### 2. 内容 / 信息流

- **重点**:读路径、推荐、缓存
- **场景**:首页、详情、推荐流、评论
- **瓶颈**:缓存命中率、推荐计算、CDN
- **演练**:热点事件、明星内容、缓存击穿

### 3. 直播 / 实时音视频

- **重点**:长连接、推流、播放、互动
- **场景**:登录、推流、播放、点赞、弹幕
- **瓶颈**:长连接数、带宽、消息分发
- **演练**:热门直播间、突发流量、互动峰值

### 4. 金融 / 支付

- **重点**:一致性、幂等、对账
- **场景**:登录、转账、支付、对账
- **瓶颈**:数据库写、分布式事务、幂等校验
- **演练**:重复支付、并发扣款、对账不平

### 5. AI / 推理

- **重点**:GPU 利用率、推理延迟、吞吐
- **场景**:模型推理、批量预测、流式响应
- **瓶颈**:GPU 显存、模型加载、批处理
- **演练**:突发请求、长文本、批量请求

### 6. 游戏

- **重点**:状态同步、广播、登录
- **场景**:登录、匹配、对战、聊天、商城
- **瓶颈**:广播风暴、状态同步、网关连接数
- **演练**:开服、热门时段、外挂流量

## 十四、压测的常见误区

- **只看 QPS,不关注延迟**:100 万 QPS 但 P99 5 秒
- **只看平均值,忽略 P99**:平均延迟掩盖长尾
- **环境与生产差异巨大**:得出的数据不可信
- **数据规模和真实不一致**:1 万 vs 1 亿行表现完全不同
- **没有混合场景**:只压单个接口,忽略调用链路
- **忽视预热**:冷启动和热机性能差异巨大
- **没有清理数据**:上次压测影响下次
- **没有基线对比**:无法判断回退
- **生产压测没有保护**:误伤真实用户
- **压测一次就完事**:性能会随版本、流量漂移
- **只看压测通过,不关注成本**:可能用 3 倍资源达到
- **忽略降级验证**:只在顺境压测
- **不演练故障**:韧性只在理论中
- **没有应急预案**:压垮时手忙脚乱

## 十五、压测成熟度模型

| 等级 | 能力 |
|------|------|
| **L1 入门** | 偶尔压测,人工执行 |
| **L2 规范** | 定期压测,有报告 |
| **L3 平台化** | 平台自助,有统一场景 |
| **L4 持续** | 集成 CI/CD,性能门禁 |
| **L5 智能** | 自动发现瓶颈,自适应压测 |
| **L6 韧性** | 故障演练常态化,自动恢复 |

> 从 L1 到 L3 收益最大,后续阶段投入高,应循序渐进。

## 十六、容量评估与决策

### 1. 容量评估流程

```text
业务预测 (QPS、用户数、订单数)
  ↓
单实例能力测试
  ↓
集群规模估算
  ↓
冗余与峰值预留
  ↓
全链路压测验证
  ↓
容量决策 (节点数、机型、HPA 阈值)
```

### 2. 单实例能力测算

- **保持 P99 < SLO** 时的最大 QPS
- **资源利用率 < 70%** 时的最大 QPS
- **多实例线性度**:实例数 × 单实例能力 = 集群能力

### 3. 容量公式

```text
集群容量 = 单实例能力 × 实例数 × 线性度
目标 QPS = 峰值 QPS × 安全系数 (1.3~1.5)
```

### 4. 扩容阈值设定

- **CPU > 60%** 持续 5 分钟
- **内存 > 70%** 持续 5 分钟
- **P99 延迟 > SLO × 80%**
- **Pending Pod > 0**
- 自定义业务指标 (订单数、用户数)

### 5. 容量看板

- 当前容量 vs 设计容量
- 距离容量上限还有多少
- 历史峰值与时间
- 预测下月容量需求

## 十八、核心要点速记

### 方法与原则

- 压测是**用实验代替猜测**,主动暴露问题
- 三段式:**准备 → 加压 → 分析**
- 阶梯递增找出**性能拐点**,而非"打满为止"
- 必须有**基线**,否则无法判断回退
- 平均值会骗人,要看 **P95 / P99 / Max**
- 压测要看**成本**——同性能下谁更便宜

### 场景与环境

- 场景要**贴近真实**,混合比例、冷热分布
- 数据量至少达到**生产的 1/3**
- 生产压测要有**流量隔离、影子表、染色**
- 大流量压测走**业务低峰期**,配**应急预案**
- 数据要**脱敏**,写操作要**回滚**

### 指标与监控

- 压测侧:QPS、延迟、错误率、并发
- 服务侧:CPU、内存、GC、连接池、线程池
- 依赖侧:数据库、缓存、消息队列、外部 API
- 端到端:**全链路追踪**,看每跳耗时
- 必须有**实时可视化**和**录屏**

### 瓶颈定位

- **CPU**:火焰图、perf、序列化热点
- **内存**:堆 dump、内存泄漏、缓存无界
- **线程**:锁竞争、长事务拖垮线程池
- **数据库**:慢 SQL、锁等待、缺索引
- **缓存**:大 Key、热 Key、击穿、雪崩
- **锁**:分布式锁热点、串行化
- **第三方**:超时、限流、依赖降级

### 弹性与韧性

- 验证 **HPA 扩容速度、冷启动、缩容抖动**
- 注入故障验证**熔断、限流、降级、自动恢复**
- 故障演练常态化,准备应急预案
- **影子流量**持续验证生产环境健康

### 工程化

- 压测是**CI/CD 的一环**,不是"上线前补一枪"
- **微基准 + 接口 + 全链路** 三层压测
- 性能门禁:PR 阶段拦截明显回退
- 容量评估:**单实例能力 × 节点数 × 线性度**
- 保留**30%~50%** 峰值冗余
- 容量规划是**持续过程**,不是季度活动
- 持续剖析 (Continuous Profiling) 是发现性能漂移的关键
- 压测成熟度:**L1 偶尔 → L3 平台化 → L5 智能 → L6 韧性**
- 真正的目标不是"压到更高",而是**在 SLO 约束下,用最少的资源撑住业务**
