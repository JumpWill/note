## 一、秒杀场景的特殊性

### 1.1 典型秒杀业务模型

```text
一个普通秒杀活动:

T0 - 10:00 预告,商品页访问     (读 QPS ~ 5 万)
T1 - 10:00 开抢,瞬时流量涌入   (读 QPS ~ 100 万, 写 QPS ~ 5 万)
T2 - 10:01 流量快速衰减         (QPS 跌回 ~ 5 千)
T3 - 10:30 下单支付峰值          (写 QPS ~ 1 万)
T4 - 24:00 活动结束

总流量: 大促瞬间 = 平时 100-1000 倍
```

### 1.2 秒杀的核心矛盾

```text
三高需求 与 系统现状 的矛盾:

需求                  系统现状
─────────────────────────────────────────
百万 QPS               单一 DB 实例 ~ 几千 QPS
不能超卖                库存竞争 100 个 key 集中
数据强一致             跨机房网络延迟 10ms+
不能宕机                单机故障 = 灾难
防黄牛                  公开 URL 难控

需要:
1. 抗住瞬时百万 QPS
2. 库存不超卖 / 不少卖
3. 服务高可用
4. 防作弊/限流
```

### 1.3 关键指标

```text
性能指标:
- 峰值 QPS: 100 万+
- 平均响应时间: < 200ms
- P99 响应时间: < 1s
- 下单成功率: 取决于库存

可用性指标:
- 系统可用性: 99.99% (4 个 9)
- 故障恢复时间: < 30s
- 数据 RPO: < 1min
- 数据 RTO: < 5min

一致性指标:
- 库存超卖率: 0
- 库存少卖率: < 0.1%
- 订单数据零丢失
```

### 3.3 服务层优化

#### 3.3.1 异步化(削峰关键)

```text
同步流程(慢):
用户下单 → 校验库存 → 扣库存 → 创建订单 → 扣积分 → 发短信
        ↑ 每步都阻塞,RT 长

异步流程(快):
用户下单 → 返回"排队中" → 立即返回
   ↓ (MQ 削峰)
   异步队列处理 → 异步扣库存 → 异步创建订单 → 异步通知

效果:
- 用户响应时间: 500ms → 50ms (10x 提升)
- 服务吞吐: 1000 QPS → 10000 QPS (10x 提升)
```

```java
// 1. 用户请求 (快速返回)
public Result seckillRequest(Long userId, Long itemId) {
    // 1. 预扣 Redis 库存 (原子)
    Long stock = redisTemplate.opsForValue().decrement("stock:" + itemId);
    if (stock < 0) {
        redisTemplate.opsForValue().increment("stock:" + itemId);
        return Result.fail("已售罄");
    }
    
    // 2. 加入订单队列 (异步处理)
    SeckillMessage msg = new SeckillMessage(userId, itemId);
    rocketMQTemplate.asyncSend("seckill-order-topic", msg);
    
    return Result.success("排队中,请等待结果通知");
}

// 2. 消费者 (异步处理)
@RocketMQMessageListener(topic = "seckill-order-topic", consumerGroup = "seckill-consumer")
public void onSeckillMessage(SeckillMessage msg) {
    // 异步创建订单
    Order order = orderService.createOrder(msg.getUserId(), msg.getItemId());
    
    // 异步通知
    notificationService.sendSeckillSuccess(msg.getUserId(), order);
}
```

### 3.4 Redis 库存原子扣减

```java
// 1. Redis Lua 脚本 (原子操作, 防止超卖)
private static final String DECREMENT_STOCK_LUA =
    "local stockKey = KEYS[1]\n" +
    "local stock = tonumber(redis.call('GET', stockKey))\n" +
    "if stock == nil then return -1 end\n" +
    "if stock <= 0 then return 0 end\n" +
    "return redis.call('DECR', stockKey)";

public boolean decrementStock(Long itemId) {
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(DECREMENT_STOCK_LUA, Long.class),
        Collections.singletonList("stock:" + itemId)
    );
    return result != null && result > 0;
}

// 2. 完整扣库存流程
public boolean tryDeductStock(Long itemId, Long quantity) {
    String key = "stock:" + itemId;
    
    // 1. 检查 + 扣减 (原子)
    Long stock = redisTemplate.execute(new DefaultRedisScript<>(
        "if redis.call('GET', KEYS[1]) and tonumber(redis.call('GET', KEYS[1])) >= tonumber(ARGV[1]) then " +
        "redis.call('DECRBY', KEYS[1], ARGV[1]); return 1; " +
        "else return 0; end", Long.class),
        Collections.singletonList(key),
        String.valueOf(quantity));
    
    return stock != null && stock == 1L;
}
```

## 四、高可用优化(High Availability)

### 4.1 高可用原则

```text
1. 无单点
   - 任何组件 ≥ 2 个实例
   - 自动故障转移

2. 服务降级
   - 非核心功能可降级
   - 失败不传染

3. 限流保护
   - 多层限流
   - 主动拒绝超额请求

4. 监控告警
   - 关键指标全监控
   - 5 分钟发现,5 分钟处理

5. 容灾
   - 多机房部署
   - 自动切换
```

### 4.2 多机房部署

```text
同城双中心 (推荐):
  中心 A (主)  ←─── 流量 ────→  中心 B (备)
  ├─ 应用集群      ← 双向同步 →  ├─ 应用集群
  ├─ Redis 集群    ← 主从同步 →  ├─ Redis 集群
  └─ DB 集群      ← 主从同步 →  └─ DB 集群

异地灾备 (可选):
  同城双中心 + 异地灾备
  灾备中心平时不服务,只做数据备份
  灾难时切换
```

### 4.3 服务无状态化

```text
无状态:
- Session 不在本地 (存 Redis)
- 配置中心化 (Nacos / Apollo)
- 文件不在本地 (对象存储)
- 日志不在本地 (ELK)

实现:
1. Session 用 JWT 或 Redis 存储
2. 配置从 Nacos 读取
3. 静态资源用 OSS / S3
4. 日志推送到 Kafka
```

### 4.4 限流降级

#### 4.4.1 多层限流

```text
限流分层:

  CDN / WAF
    ↓ IP 限流, DDoS 防护
  网关层
    ↓ 用户限流, 验证码
  业务服务
    ↓ 业务限流, 库存限流
  数据库
    ↓ 连接池限流

每层都有限流,任一层超限都立即拒绝
```

#### 4.4.2 降级策略

```text
降级优先级:
P0 (核心, 不降级): 下单、支付
P1 (重要, 可降级): 推荐商品、评论
P2 (次要, 易降级): 推荐算法、个性化
P3 (可关闭): 营销活动页、统计

降级方式:
1. 自动降级 (熔断器)
2. 手动降级 (配置开关)
3. 静态化降级 (返回缓存)
4. 拒绝降级 (返回错误)
```

### 4.5 故障转移

```text
应用层故障:
- 健康检查失败 → 摘除节点
- LB 自动剔除 / K8s 重启 Pod

数据库故障:
- 主库故障 → 主从切换
- 从库延迟过高 → 切换读路由

Redis 故障:
- Sentinel 集群自动选主

机房故障:
- DNS 切到备用机房
```

```java
        }
    }
}
```

## 五、高一致性优化(High Consistency)

### 5.1 秒杀的核心一致性问题

```text
核心问题:
1. 不能超卖 (库存不能扣成负数)
2. 不能少卖 (用户抢到但订单失败)
3. 同一用户不能重复抢 (幂等)
4. 下单与支付一致
5. 订单数据零丢失
```

```java
private static final String SECKILL_LUA = 
    "local stockKey = KEYS[1]\n" +
    "local userKey = KEYS[2]\n" +
    "local stock = tonumber(redis.call('GET', stockKey))\n" +
    "if stock == nil or stock <= 0 then return -1 end\n" +
    "if redis.call('SISMEMBER', userKey, ARGV[1]) == 1 then return -2 end\n" +
    "redis.call('DECR', stockKey)\n" +
    "redis.call('SADD', userKey, ARGV[1])\n" +
    "return 1";

public Result seckill(Long userId, Long itemId) {
    Long result = redisTemplate.execute(new DefaultRedisScript<>(
        SECKILL_LUA, Long.class),
        Arrays.asList("stock:" + itemId, "seckill:users:" + itemId),
        userId.toString()
    );

    if (result == 1L) {
        return Result.success("排队中");
    } else if (result == -1L) {
        return Result.fail("已售罄");
    } else if (result == -2L) {
        return Result.fail("已抢购过");
    }
    return Result.fail("失败");
}
```

### 5.6 幂等性设计

```text
幂等性场景:
1. 用户重复点击 (前端防重)
2. 网络重试 (客户端自动重试)
3. 消息队列重试 (消费者)
4. 分布式锁过期 (锁释放了, 业务没完成)

幂等方案:
1. 唯一索引
   - 订单表 (userId, itemId, round) 唯一
   - 重复请求插入失败

2. 唯一请求 ID
   - 客户端生成 requestId
   - 服务端 Redis SETNX 标记
   - 已处理过直接返回结果

3. 状态机
   - 订单状态: 待支付 → 已支付 → 已发货
   - 状态机推进不可逆

4. Token 机制
   - 预生成 token, 用后失效
```

```java
// 1. Redis 幂等 (requestId)
public Result idempotentRequest(String requestId, Function<Result> action) {
    String key = "idempotent:" + requestId;
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, "1", 24, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(success)) {
        // 已处理过, 返回之前的结果 (从 Redis 读取)
        return Result.fromJson(redisTemplate.opsForValue().get(key + ":result"));
    }
    Result result = action.apply();
    redisTemplate.opsForValue().set(key + ":result", result.toJson());
    return result;
}
```

## 六、典型业务场景的方案权衡

### 6.1 场景 1:库存 100 件,100 万人抢

```text
方案: Redis Lua 原子扣减 + 异步订单

流程:
1. 用户请求 (限流: 100 万 → 5 万 QPS)
2. Redis Lua 原子扣减库存 (返回结果: 成功/售罄)
3. 成功 → 加入订单队列 (异步)
4. 异步消费者: 创建订单、扣 DB 库存
5. 推送通知

关键点:
- Redis 库存 = 100 (预热)
- 100 万请求 → 5 万 QPS 通过限流
- 5 万请求 → Redis 原子扣减 → 只有 100 个成功
- 100 个订单 → 异步落库

一致性:
- Redis 原子扣减保证不超卖
- 异步落库有 1-3 秒延迟
- Redis 故障 = 系统不可用 (降级为 DB)
```

### 6.2 场景 2:秒杀下单 + 支付

```text
方案: 本地消息表 + 异步对账

流程:
1. 创建订单 (本地事务, 包含订单 + outbox 消息)
2. 后台轮询 outbox, 发到 MQ
3. 通知支付服务
4. 用户支付
5. 支付成功 → 更新订单状态
6. 定时对账: 找出支付未到账的订单 (异常处理)

一致性:
- 订单与消息在同事务 (原子)
- 消息必达 (轮询 + 重试)
- 支付与订单最终一致
```

### 6.3 场景 3:多用户抢同一 SKU (热点问题)

```text
方案: 库存分段 + 排队

库存分段 (避免单 key 热点):
- 100 件库存, 分成 10 段
- 每段 10 件, 10 个 Redis key
- 用户请求 hash 取模, 落到某一段
- 每段独立扣减, 总和不超过 100

排队:
- 超过库存时, 放入等待队列
- 前面用户放弃时, 后续用户补位
- (复杂的"捡漏"逻辑)
```

### 6.4 场景 4: 防黄牛

```text
策略:
1. 实名认证: 一个人只能买一件
   - Redis SET 记录 userId
   - 已存在则拒绝

2. 设备指纹:
   - 同一设备只能买一次
   - 同一 IP 只能买一次
   - 限制设备/IP 数量

3. 验证码 / 滑块:
   - 增加机器难度

4. 邀请码:
   - 通过邀请码才能抢购
   - 限制黄牛批量操作

5. 限购:
   - 实名认证用户每人最多 1 件
   - 高信用用户最多 2 件
```

## 十、总结

### 10.1 三大维度目标

```text
高性能 (Performance):
  目标: 100 万 QPS, P99 < 1s
  手段: 漏斗削减 + 缓存 + 异步 + 优化
  关键: 限流 + 多级缓存 + 异步削峰

高可用 (Availability):
  目标: 99.99%, 故障 30s 恢复
  手段: 多机房 + 冗余 + 限流降级
  关键: 无单点 + 自动故障转移

高一致性 (Consistency):
  目标: 不超卖, 订单不丢
  手段: Redis 原子 + 分布式锁 + 幂等
  关键: Redis 原子操作 + 异步落库 + 对账
```

```text
秒杀系统 = 高性能(漏斗) + 高可用(冗余) + 高一致性(原子)

  原子操作(Redis Lua) + 分布式锁 + 幂等设计
```

| **异步削峰** | 消息队列 (RocketMQ/Kafka) | 用户响应快, 处理慢 |
| **库存原子** | Redis Lua 脚本 | DECR 原子性 |
| **库存同步** | 异步落库 + 定时对账 | 允许秒级延迟, 不允许超卖 |
| **幂等设计** | 唯一索引 + requestId | 避免重复下单 |
| **防超卖** | Redis 原子 + 分布式锁 + DB 乐观锁 | 多重防线 |
| **高可用** | 多机房 + 服务冗余 + 限流降级 | 自动故障转移 |
| **容灾** | 异地灾备 + DNS 切换 | 5 分钟 RTO |
| **监控** | Prometheus + Grafana + 告警 | 全链路指标 |

---

> **核心思想**: 秒杀系统不是单点优化,而是**全链路协同**。前端削减 + 后端削峰 + 数据原子 + 异步落库 + 监控告警,缺一不可。

## 十一、超卖的问题处理(防超卖完整方案)

> 超卖 (Overselling) 是秒杀系统的**头号灾难**——库存被扣成负数,实际成交数 > 库存数,直接造成公司资金损失与商誉受损。
> 本章系统梳理超卖的根因、防御方案与故障应急。

### 11.1 超卖的本质与危害

#### 1. 什么是超卖

```text
定义: 实际成交订单数 > 实际库存数

正常场景:
  库存: 100 件
  成交: 100 订单
  状态: 卖完即止 ✓

超卖场景:
  库存: 100 件
  成交: 120 订单  ← 灾难!
  状态: 20 个用户付款后无货可发
```

#### 2. 超卖的危害

```text
1. 直接经济损失
   - 退款 + 赔偿
   - 用户流失
   - 品牌信任危机

2. 法律风险
   - 消费者权益保护法
   - 合同违约

3. 系统信任
   - 用户对平台的信任崩塌
   - 后续业务受影响

4. 运营成本
   - 客服解释成本
   - 二次活动损失
```

#### 3. 超卖的常见场景

```text
场景 1: 库存为 1, 多人同时抢
  - 经典超卖
  - 多见于限量首发

场景 2: 秒杀 + 并发
  - 高并发下读+写错乱
  - 1000 个请求同时检查 "stock > 0"
  - 看到 100 个剩余, 全部扣减
  - 最终扣成 -900

场景 3: 分布式节点不同步
  - A 节点看 50 库存,扣 1 → 49
  - B 节点同步延迟,看 50 库存,扣 1 → 49
  - 总共扣 2 次,但实际只应扣 1 次
```

### 11.2 超卖的根因分析

#### 1. 根本原因: 并发与原子性

```text
超卖的本质 = 多个并发请求 看到 同一个非负库存, 各自扣减

触发条件:
1. 并发 (多个请求同时)
2. 非原子 (check + deduct 不是一步)
3. 无锁 (没有同步机制)
```

#### 2. 经典错误示例(读后写)

```java
// ❌ 错误写法: check-then-act
public boolean deductStock(Long itemId) {
    // 步骤 1: 查库存
    int stock = itemMapper.getStock(itemId);
    
    // 问题: 多个请求同时执行到这里, 都读到 stock=1
    if (stock <= 0) {
        return false;
    }
    
    // 步骤 2: 扣减库存
    itemMapper.deduct(itemId);  // 多个请求都执行扣减
    return true;
}
```

```text
时序分析 (库存 1 件, 3 个并发请求):

T0: 请求 A 读到 stock=1
T0: 请求 B 读到 stock=1
T0: 请求 C 读到 stock=1
T1: 请求 A 扣减 → DB stock=0 ✓
T2: 请求 B 扣减 → DB stock=-1 ❌ 超卖!
T3: 请求 C 扣减 → DB stock=-2 ❌ 超卖!
```

#### 3. 错乱的"看似正确"方案

```text
方案 1: 加锁 (但锁粒度不对)
  - 锁整个 item 表 → 性能差
  - 锁整行 → 锁范围过大
  - 锁单个字段 → MySQL 不支持

方案 2: 事务 (但隔离级别不够)
  - 默认 REPEATABLE READ
  - 但 read-modify-write 不是原子的
  - 仍可能超卖

方案 3: 唯一索引 (但不能解决问题)
  - 唯一索引防重复
  - 不能防超卖 (重复 vs 超卖是不同问题)
```

### 11.3 防御方案一: 数据库层(单库)

#### 1. SQL 原子更新(推荐)

```sql
-- 核心: 一条 SQL 完成 check + update
-- 库存 = 库存 - 1 WHERE id=? AND stock > 0

UPDATE item 
SET stock = stock - 1 
WHERE id = #{itemId} 
  AND stock > 0;

-- 判断: affected rows = 1 (成功), = 0 (失败)
```

```java
// 正确写法: 一条 SQL 完成
@Update("UPDATE item SET stock = stock - 1 " +
        "WHERE id = #{itemId} AND stock > 0")
int deductStock(@Param("itemId") Long itemId);

public boolean deduct(Long itemId) {
    int affected = itemMapper.deductStock(itemId);
    return affected == 1;  // 1 = 成功, 0 = 失败
}
```

```text
为什么不会超卖:
- MySQL 的 UPDATE 是行级锁
- 同时只有一个事务能修改这一行
- 第一个事务把 stock 从 1 改成 0
- 后续事务 WHERE stock>0 不成立,affected rows=0

注意:
- 必须用 stock > 0 条件 (不是 stock = 1)
- 必须看 affected rows (不是返回值 0/1)
- 必须在事务内执行
```

#### 2. 乐观锁

```sql
-- 加 version 列
ALTER TABLE item ADD COLUMN version INT DEFAULT 0;

-- 更新时检查 version
UPDATE item 
SET stock = stock - 1, version = version + 1
WHERE id = #{itemId} 
  AND stock > 0 
  AND version = #{oldVersion};
```

```java
public boolean deductWithVersion(Long itemId) {
    // 1. 读
    Item item = itemMapper.selectById(itemId);
    if (item.getStock() <= 0) return false;
    
    // 2. 写 (带版本号)
    int affected = itemMapper.deductWithVersion(itemId, item.getVersion());
    
    // 3. 若 affected = 0, 说明 version 变了, 重试
    if (affected == 0) {
        return deductWithVersion(itemId);  // 递归重试
    }
    return true;
}
```

```text
乐观锁的代价:
- 重试 (高并发下可能多次)
- 性能受影响
- 适合: 冲突不频繁的场景
```

#### 3. 悲观锁 (SELECT FOR UPDATE)

```java
@Transactional
public boolean deductWithPessimisticLock(Long itemId) {
    // 1. 加锁查询
    Item item = itemMapper.selectForUpdate(itemId);
    if (item == null || item.getStock() <= 0) return false;
    
    // 2. 扣减
    itemMapper.deduct(itemId);
    return true;
}
```

```sql
<select id="selectForUpdate" resultType="Item">
    SELECT * FROM item WHERE id = #{itemId} FOR UPDATE
</select>
```

```text
悲观锁的问题:
- 行锁竞争激烈
- 锁等待可能导致超时
- 性能差
- 适合: 数据竞争激烈的核心场景
- 不推荐: 高并发秒杀 (用 Redis Lua 更好)
```

#### 4. 事务 + 唯一约束(防重复下单)

```sql
-- 订单表加唯一索引
ALTER TABLE seckill_order 
ADD UNIQUE INDEX uk_user_item (user_id, item_id, round);
```

### 11.4 防御方案二: Redis 原子层(推荐)

#### 1. Redis Lua 原子脚本 (最推荐)

```lua
-- 完整的 Lua 扣库存脚本
-- KEYS[1]: 库存 key
-- KEYS[2]: 已购买用户 set
-- ARGV[1]: 用户 id

local stockKey = KEYS[1]
local userSetKey = KEYS[2]
local userId = ARGV[1]

-- 1. 检查是否已购买
if redis.call('SISMEMBER', userSetKey, userId) == 1 then
    return -2  -- 已购买
end

-- 2. 检查库存
local stock = tonumber(redis.call('GET', stockKey))
if stock == nil or stock <= 0 then
    return -1  -- 已售罄
end

-- 3. 扣减库存 + 标记用户
redis.call('DECR', stockKey)
redis.call('SADD', userSetKey, userId)
return 1  -- 成功
```

```java
public boolean seckill(Long userId, Long itemId) {
    Long result = redisTemplate.execute(seckillScript,
        Arrays.asList("stock:" + itemId, "seckilled:" + itemId),
        userId.toString());
    
    if (result == 1L) {
        return true;  // 抢到
    } else if (result == -1L) {
        throw new SoldOutException();
    } else if (result == -2L) {
        throw new AlreadySeckilledException();
    }
    return false;
}
```

```text
为什么 Redis Lua 不会超卖:
1. Redis 是单线程执行命令
2. Lua 脚本整体原子执行
3. 多个客户端的 Lua 脚本串行执行
4. check + deduct + SADD 都在一个脚本里

这就是 Redis 原子扣减的精髓!
```

#### 2. Redis 分布式锁 (Redisson)

```java
public boolean seckillWithLock(Long userId, Long itemId) {
    RLock lock = redisson.getLock("seckill:item:" + itemId);
    
    try {
        // 尝试加锁, 等最多 100ms, 锁超时 10s
        if (lock.tryLock(100, 10, TimeUnit.MILLISECONDS)) {
            // 临界区
            int stock = itemMapper.getStock(itemId);
            if (stock <= 0) return false;
            itemMapper.deduct(itemId);
            return true;
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        if (lock.isLocked() && lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
    return false;
}
```

```text
Redisson 优势:
- 内置看门狗 (Watch Dog) 自动续期
- RedLock 算法 (多 Redis 实例)
- 完整的中断响应
- 生产推荐
```

#### 3. Redis 分布式锁的坑

```text
坑 1: 锁过期但业务没完成
  - 锁设了 10s, 业务跑了 15s
  - 锁已过期, 别人加锁
  - 业务跑完会释放别人的锁
  - 解决: Redisson 看门狗 (自动续期)

坑 2: 主从切换数据丢失
  - 主节点加锁, 没同步到从节点
  - 主节点宕机, 从节点升主
  - 锁丢失, 别人加锁成功
  - 解决: RedLock 多 Redis 实例

坑 3: 非原子操作
  - SETNX (无过期时间) + EXPIRE (两步)
  - SETNX 成功后, 应用崩溃
  - 锁永远不释放
  - 解决: SET NX EX 一步完成
```

### 11.5 防御方案三: 数据库 + Redis 双层防线

#### 1. 双层防御架构

```text
                    ┌──────────────────┐
                    │   抢锁请求         │
                    └────────┬─────────┘
                             ↓
        ┌────────────────────────────────────────┐
        │  第一层: Redis Lua (快速过滤)         │
        │  - 99% 请求在此处理                     │
        │  - 不超卖, 也不漏抢                   │
        └────────────────┬───────────────────┘
                         ↓ 抢到
        ┌────────────────────────────────────────┐
        │  第二层: MySQL 原子更新 (兜底)        │
        │  - Lua 失败时的兜底                     │
        │  - 防 Redis 故障时超卖                 │
        │  - UPDATE ... WHERE stock > 0          │
        └────────────────────────────────────────┘
```

#### 2. 完整实现

```java
@Service
public class SeckillService {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Autowired
    private ItemMapper itemMapper;
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    // Lua 脚本
    private static final String SECKILL_LUA = ...;
    
    public Result seckill(Long userId, Long itemId) {
        // 阶段 1: Redis Lua 快速路径 (99% 请求)
        Long redisResult = redisTemplate.execute(
            new DefaultRedisScript<>(SECKILL_LUA, Long.class),
            Arrays.asList("stock:" + itemId, "seckilled:" + itemId),
            userId.toString()
        );
        
        if (redisResult == 1L) {
            // 抢到, 异步创建订单
            sendSeckillMessage(userId, itemId);
            return Result.success("排队中");
        } else if (redisResult == -1L) {
            return Result.fail("已售罄");
        } else if (redisResult == -2L) {
            return Result.fail("已抢购过");
        }
        
        // 阶段 2: Redis 故障降级到 MySQL
        // 这种情况: Redis 不可用, 降级到 DB 处理
        if (redisResult == null) {
            return seckillFromDB(userId, itemId);
        }
        
        return Result.fail("抢购失败");
    }
    
    @Transactional
    public Result seckillFromDB(Long userId, Long itemId) {
        // 1. 检查用户是否已下单 (唯一索引)
        // 2. 原子扣库存 (单 SQL)
        int affected = itemMapper.deductStock(itemId);
        
        if (affected == 0) {
            return Result.fail("已售罄");
        }
        
        // 3. 创建订单 (DB 唯一约束保护)
        try {
            orderMapper.insert(new Order(userId, itemId));
        } catch (DuplicateKeyException e) {
            // 重复下单
            itemMapper.addStock(itemId);  // 补偿回滚
            return Result.fail("已抢购过");
        }
        
        return Result.success("抢购成功");
    }
}
```

### 11.6 防御方案四: 异步消息队列削峰

```text
异步下单流程 (最推荐, 抗超卖最佳):

T0: Redis Lua 预扣 (库存-1, 标记用户)
    ↓
T1: 抢到, 立即返回 "排队中"
    ↓
T2: 异步消费者: 创建订单 (事务)
    ↓
T3: 提交事务
    ↓ (失败)
T4: 补偿: Redis 库存 +1, 移除用户标记

为什么这种方案最稳:
- Redis 减库存是原子的 (不会超卖)
- 创建订单是异步的 (可以容错重试)
- 失败可以补偿 (Redis +1)
- 用户的"下单成功"是即时的 (但实际创建是异步)
```

```java
// 1. Lua 预扣 + 异步下单
public Result seckill(Long userId, Long itemId) {
    // Redis Lua 预扣
    Long result = redisTemplate.execute(SECKILL_LUA, ...);
    if (result == 1L) {
        // 抢到, 发送消息异步创建订单
        SeckillMessage msg = new SeckillMessage(userId, itemId, System.currentTimeMillis());
        rocketMQTemplate.asyncSend("seckill-order-topic", msg);
        return Result.success("排队中,请等待结果");
    }
    return Result.fail("失败");
}

// 2. 异步消费者 (事务内创建订单)
@RocketMQMessageListener(topic = "seckill-order-topic", consumerGroup = "seckill-consumer")
@Transactional
public void createOrder(SeckillMessage msg) {
    try {
        // 1. 创建订单 (唯一约束防重复)
        orderMapper.insert(new Order(msg.getUserId(), msg.getItemId()));
        
        // 2. 减 DB 库存 (用乐观锁, 防超卖最终防线)
        int affected = itemMapper.deductStock(msg.getItemId());
        if (affected == 0) {
            // 库存不足, 回滚订单 + Redis 库存
            orderMapper.deleteByUserAndItem(msg.getUserId(), msg.getItemId());
            redisTemplate.opsForValue().increment("stock:" + msg.getItemId());
            redisTemplate.opsForSet().remove("seckilled:" + msg.getItemId(), 
                                              msg.getUserId());
            log.warn("DB 库存不足, 补偿");
            return;
        }
        
        // 3. 通知用户
        notificationService.sendSeckillSuccess(msg.getUserId());
        
    } catch (DuplicateKeyException e) {
        // 重复下单, 静默忽略
        log.info("用户 {} 已下单", msg.getUserId());
    } catch (Exception e) {
        // 异常补偿
        redisTemplate.opsForValue().increment("stock:" + msg.getItemId());
        redisTemplate.opsForSet().remove("seckilled:" + msg.getItemId(), 
                                          msg.getUserId());
        throw e;
    }
}
```

### 11.7 库存分段: 解决热点 Key

```text
问题: 单个 SKU 100 万请求同时扣库存, 单 Redis key 是热点

解决: 库存分段

原方案:
  key: stock:1001 = 100

分段后:
  key: stock:1001:p0 = 10
  key: stock:1001:p1 = 10
  key: stock:1001:p2 = 10
  ...
  key: stock:1001:p9 = 10
  总计: 100 (10 × 10)

用户请求:
  根据 userId hash, 落到某一段
  例: hash(userId) % 10 = 3 → 落到 p3 段
  
  每段独立扣减, 总和 100
  不会超卖
```

```java
public boolean seckillWithSegment(Long userId, Long itemId) {
    int segment = (int) (Math.abs(userId.hashCode()) % 10);
    String stockKey = "stock:" + itemId + ":p" + segment;
    
    // Redis Lua 扣减当前段
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(SECKILL_SEGMENT_LUA, Long.class),
        Arrays.asList(stockKey, "seckilled:" + itemId + ":p" + segment),
        userId.toString()
    );
    
    return result == 1L;
}
```

### 11.8 兜底机制: 库存对账

```text
对账 = 定时核对 Redis 库存和 DB 库存, 修正不一致

场景:
- Redis 重启 → 库存数据丢失
- Redis 同步问题 → 数据不一致
- 异步消息丢失 → Redis 扣了但 DB 没扣

对账策略:
1. 启动对账: 活动开始前, 从 DB 同步到 Redis
2. 实时对账: 每 N 秒, 抽样核对
3. 结束对账: 活动结束后, 详细核对
4. 差异告警: 差异 > 阈值, 人工介入
```

```java
@Scheduled(fixedRate = 60000)  // 每 60 秒
public void reconcileStock() {
    List<Item> items = itemMapper.selectAllActiveItems();
    
    for (Item item : items) {
        // 1. 读 Redis 总库存 (分段求和)
        int redisStock = 0;
        for (int i = 0; i < 10; i++) {
            String v = redisTemplate.opsForValue().get("stock:" + item.getId() + ":p" + i);
            redisStock += v == null ? 0 : Integer.parseInt(v);
        }
        
        // 2. 读 DB 库存
        int dbStock = item.getStock();
        
        // 3. 比较
        if (Math.abs(redisStock - dbStock) > 10) {
            log.error("库存差异: item={} redis={} db={}", 
                      item.getId(), redisStock, dbStock);
            alarmService.sendAlert("库存差异超阈值", item.getId());
        }
    }
}
```

### 11.9 监控与告警

```text
关键监控指标 (必须配置):

1. Redis 库存
   - 实时库存值 (曲线)
   - 扣减速率 (曲线)
   - 告警: 库存 = 0 时通知

2. DB 库存
   - 实时库存值
   - 扣减速率
   - 告警: 库存 = 0 时通知

3. 一致性
   - 定时检查 Redis 库存 ≈ DB 库存
   - 告警: 差异 > 阈值

4. 订单数 vs 库存数
   - 订单数 ≤ 库存数 (强约束)
   - 告警: 订单数 > 库存数 (超卖!)

5. Lua 脚本执行成功率
   - 99.99% 期望
   - 告警: < 99.9%

6. Redis 异常
   - 主从切换告警
   - 内存使用告警
   - 网络抖动告警
```

### 11.10 超卖故障应急

#### 1. 发现超卖

```text
监控告警 (5 分钟内):
- 订单数 > 库存数 告警
- Redis 库存为负数告警
- 用户反馈"付款无货"

应急响应 (SLA 30 分钟内):
1. 暂停下单入口 (服务降级)
2. 评估超卖规模
3. 决定处理方式:
   - 全部退款 + 补偿优惠券 (推荐)
   - 协调供应商紧急补货
   - 部分发货 + 部分退款
4. 修复超卖根因 (代码层)
5. 修复后压测验证
6. 公开声明 (PR / 客服)
```

#### 2. 紧急下线脚本

```bash
#!/bin/bash
# emergency-stop-seckill.sh
# 超卖应急下线

ITEM_ID=$1

echo "停止 $ITEM_ID 的秒杀..."

# 1. 下线前端入口
kubectl patch ingress seckill-ingress -p '{"spec":{"rules":[]}}'

# 2. 暂停服务
kubectl scale deployment seckill-api --replicas=0

# 3. 关闭 RabbitMQ 消费者
kubectl scale deployment seckill-consumer --replicas=0

# 4. 关闭 Redis 库存
redis-cli DEL "stock:$ITEM_ID" "seckilled:$ITEM_ID"

echo "$ITEM_ID 秒杀已紧急下线"
```

#### 3. 库存回滚 / 补偿

```java
// 紧急补偿: 释放所有 Redis 预扣库存
public void emergencyRollback(Long itemId) {
    String userSetKey = "seckilled:" + itemId;
    Set<String> userIds = redisTemplate.opsForSet().members(userSetKey);
    
    // 1. 清空已购买用户
    redisTemplate.delete(userSetKey);
    
    // 2. 恢复库存 (根据已发订单数)
    int orderedCount = orderMapper.countByItem(itemId);
    int originalStock = itemMapper.getOriginalStock(itemId);
    int actualStock = Math.max(0, originalStock - orderedCount);
    
    redisTemplate.opsForValue().set("stock:" + itemId, actualStock);
    
    // 3. 告警
    alarmService.sendCriticalAlert(
        "紧急回滚: item=" + itemId + 
        " 实际库存=" + actualStock + 
        " 已发订单=" + orderedCount
    );
}
```

### 11.11 防御方案选型决策

```text
按业务场景选:

1. 高并发秒杀 (百万 QPS):
   - Redis Lua + 异步消息 + DB 兜底
   - 分段库存
   - 推荐: 最稳

2. 普通限购 (1 万 QPS):
   - Redis Lua + DB 原子更新
   - 简单可靠

3. 库存极小 (< 100):
   - Redis 分布式锁 (Redisson)
   - + DB 乐观锁
   - 简单但够用

4. 强一致要求 (如金融):
   - 分布式锁 + TCC
   - 性能差, 但最强一致

5. 简单电商 (QPS < 1k):
   - DB 单 SQL 原子更新
   - 简单实用
```

### 11.12 超卖防御 Checklist

```text
□ 必做: 库存操作使用单条 SQL (UPDATE ... WHERE stock > 0)
□ 必做: Redis Lua 脚本 (含 check + deduct + SADD)
□ 必做: 用户唯一性约束 (Redis Set / DB 唯一索引)
□ 必做: 事务 + 失败回滚
□ 推荐: 异步消息队列削峰
□ 推荐: 库存分段 (避免热点)
□ 推荐: Redisson 分布式锁
□ 推荐: 库存对账 (定时核对 Redis vs DB)
□ 推荐: 监控告警 (订单数 vs 库存数, Redis vs DB 差异)
□ 推荐: 应急下线脚本 (一键停止)
□ 推荐: 超卖后用户补偿流程 (退款 + 优惠券)
□ 推荐: 定期演练 (故障 + 应急)
```

### 11.13 一句话总结

```text
防超卖 = 原子 + 异步 + 多层防御 + 对账
  1. Redis Lua 原子扣减 (第一道)
  2. 异步消息异步落库 (削峰)
  3. DB 原子更新 (兜底)
  4. 唯一约束防重复 (第四道)
  5. 分布式锁 (极端保护)

  7. 监控告警 (实时发现)

```
