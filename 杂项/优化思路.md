## 一、秒杀场景的特殊性

### 1.1 典型秒杀业务模型

```text
一个普通秒杀活动:

T0 - 10:00 预告,商品页访问     (读 QPS ~ 5 万)
T1 - 10:00 开抢,瞬时流量涌入   (读 QPS ~ 100 万, 写 QPS ~ 5 万)
T2 - 10:01 流量快速衰减         (QPS 跌回 ~ 5 千)
T3 - 10:30 下单支付峰值          (写 QPS ~ 1 万)
T4 - 24:00 活动结束

总流量: 大促瞬间 = 平时 100-1000 倍
```

### 1.2 秒杀的核心矛盾

```text
三高需求 与 系统现状 的矛盾:

需求                  系统现状
─────────────────────────────────────────
百万 QPS               单一 DB 实例 ~ 几千 QPS
不能超卖                库存竞争 100 个 key 集中
数据强一致             跨机房网络延迟 10ms+
不能宕机                单机故障 = 灾难
防黄牛                  公开 URL 难控

需要:
1. 抗住瞬时百万 QPS
2. 库存不超卖 / 不少卖
3. 服务高可用
4. 防作弊/限流
```

### 1.3 关键指标

```text
性能指标:
- 峰值 QPS: 100 万+
- 平均响应时间: < 200ms
- P99 响应时间: < 1s
- 下单成功率: 取决于库存

可用性指标:
- 系统可用性: 99.99% (4 个 9)
- 故障恢复时间: < 30s
- 数据 RPO: < 1min
- 数据 RTO: < 5min

一致性指标:
- 库存超卖率: 0
- 库存少卖率: < 0.1%
- 订单数据零丢失
```

## 三、高性能优化(High Performance)

### 3.1 前端优化(削减 80% 流量)

```text
- 商品详情页 / 活动页 100% 静态化
```

### 3.3 服务层优化

#### 3.3.1 异步化(削峰关键)

```text
同步流程(慢):
用户下单 → 校验库存 → 扣库存 → 创建订单 → 扣积分 → 发短信
        ↑ 每步都阻塞,RT 长

异步流程(快):
用户下单 → 返回"排队中" → 立即返回
   ↓ (MQ 削峰)
   异步队列处理 → 异步扣库存 → 异步创建订单 → 异步通知

效果:
- 用户响应时间: 500ms → 50ms (10x 提升)
- 服务吞吐: 1000 QPS → 10000 QPS (10x 提升)
```

```java
// 1. 用户请求 (快速返回)
public Result seckillRequest(Long userId, Long itemId) {
    // 1. 预扣 Redis 库存 (原子)
    Long stock = redisTemplate.opsForValue().decrement("stock:" + itemId);
    if (stock < 0) {
        redisTemplate.opsForValue().increment("stock:" + itemId);
        return Result.fail("已售罄");
    }
    
    // 2. 加入订单队列 (异步处理)
    SeckillMessage msg = new SeckillMessage(userId, itemId);
    rocketMQTemplate.asyncSend("seckill-order-topic", msg);
    
    return Result.success("排队中,请等待结果通知");
}

// 2. 消费者 (异步处理)
@RocketMQMessageListener(topic = "seckill-order-topic", consumerGroup = "seckill-consumer")
public void onSeckillMessage(SeckillMessage msg) {
    // 异步创建订单
    Order order = orderService.createOrder(msg.getUserId(), msg.getItemId());
    
    // 异步通知
    notificationService.sendSeckillSuccess(msg.getUserId(), order);
}
```

### 3.4 Redis 库存原子扣减

```java
// 1. Redis Lua 脚本 (原子操作, 防止超卖)
private static final String DECREMENT_STOCK_LUA =
    "local stockKey = KEYS[1]\n" +
    "local stock = tonumber(redis.call('GET', stockKey))\n" +
    "if stock == nil then return -1 end\n" +
    "if stock <= 0 then return 0 end\n" +
    "return redis.call('DECR', stockKey)";

public boolean decrementStock(Long itemId) {
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(DECREMENT_STOCK_LUA, Long.class),
        Collections.singletonList("stock:" + itemId)
    );
    return result != null && result > 0;
}

// 2. 完整扣库存流程
public boolean tryDeductStock(Long itemId, Long quantity) {
    String key = "stock:" + itemId;
    
    // 1. 检查 + 扣减 (原子)
    Long stock = redisTemplate.execute(new DefaultRedisScript<>(
        "if redis.call('GET', KEYS[1]) and tonumber(redis.call('GET', KEYS[1])) >= tonumber(ARGV[1]) then " +
        "redis.call('DECRBY', KEYS[1], ARGV[1]); return 1; " +
        "else return 0; end", Long.class),
        Collections.singletonList(key),
        String.valueOf(quantity));
    
    return stock != null && stock == 1L;
}
```

## 四、高可用优化(High Availability)

### 4.1 高可用原则

```text
1. 无单点
   - 任何组件 ≥ 2 个实例
   - 自动故障转移

2. 服务降级
   - 非核心功能可降级
   - 失败不传染

3. 限流保护
   - 多层限流
   - 主动拒绝超额请求

4. 监控告警
   - 关键指标全监控
   - 5 分钟发现,5 分钟处理

5. 容灾
   - 多机房部署
   - 自动切换
```

### 4.2 多机房部署

```text
同城双中心 (推荐):
  中心 A (主)  ←─── 流量 ────→  中心 B (备)
  ├─ 应用集群      ← 双向同步 →  ├─ 应用集群
  ├─ Redis 集群    ← 主从同步 →  ├─ Redis 集群
  └─ DB 集群      ← 主从同步 →  └─ DB 集群

异地灾备 (可选):
  同城双中心 + 异地灾备
  灾备中心平时不服务,只做数据备份
  灾难时切换
```

### 4.3 服务无状态化

```text
无状态:
- Session 不在本地 (存 Redis)
- 配置中心化 (Nacos / Apollo)
- 文件不在本地 (对象存储)
- 日志不在本地 (ELK)

实现:
1. Session 用 JWT 或 Redis 存储
2. 配置从 Nacos 读取
3. 静态资源用 OSS / S3
4. 日志推送到 Kafka
```

### 4.4 限流降级

#### 4.4.1 多层限流

```text
限流分层:

  CDN / WAF
    ↓ IP 限流, DDoS 防护
  网关层
    ↓ 用户限流, 验证码
  业务服务
    ↓ 业务限流, 库存限流
  数据库
    ↓ 连接池限流

每层都有限流,任一层超限都立即拒绝
```

```java
// Sentinel 多层限流
```

#### 4.4.2 降级策略

```text
降级优先级:
P0 (核心, 不降级): 下单、支付
P1 (重要, 可降级): 推荐商品、评论
P2 (次要, 易降级): 推荐算法、个性化
P3 (可关闭): 营销活动页、统计

降级方式:
1. 自动降级 (熔断器)
2. 手动降级 (配置开关)
3. 静态化降级 (返回缓存)
4. 拒绝降级 (返回错误)
```

### 4.5 故障转移

```text
应用层故障:
- 健康检查失败 → 摘除节点
- LB 自动剔除 / K8s 重启 Pod

数据库故障:
- 主库故障 → 主从切换
- 从库延迟过高 → 切换读路由

Redis 故障:
- Sentinel 集群自动选主
- Cluster 自动故障转移

机房故障:
- DNS 切到备用机房
- 流量切换 (5 分钟内)
```

```java
        // 重试 3 次

            rocketMQTemplate.send("seckill-order-dead", msg);
        }
    }
}
```

## 五、高一致性优化(High Consistency)

### 5.1 秒杀的核心一致性问题

```text
核心问题:
1. 不能超卖 (库存不能扣成负数)
2. 不能少卖 (用户抢到但订单失败)
3. 同一用户不能重复抢 (幂等)
4. 下单与支付一致
5. 订单数据零丢失
```

```java
private static final String SECKILL_LUA = 
    "local stockKey = KEYS[1]\n" +
    "local userKey = KEYS[2]\n" +
    "local stock = tonumber(redis.call('GET', stockKey))\n" +
    "if stock == nil or stock <= 0 then return -1 end\n" +
    "if redis.call('SISMEMBER', userKey, ARGV[1]) == 1 then return -2 end\n" +
    "redis.call('DECR', stockKey)\n" +
    "redis.call('SADD', userKey, ARGV[1])\n" +
    "return 1";

public Result seckill(Long userId, Long itemId) {
    Long result = redisTemplate.execute(new DefaultRedisScript<>(
        SECKILL_LUA, Long.class),
        Arrays.asList("stock:" + itemId, "seckill:users:" + itemId),
        userId.toString()
    );

    if (result == 1L) {
        return Result.success("排队中");
    } else if (result == -1L) {
        return Result.fail("已售罄");
    } else if (result == -2L) {
        return Result.fail("已抢购过");
    }
    return Result.fail("失败");
}
```

### 5.6 幂等性设计

```text
幂等性场景:
1. 用户重复点击 (前端防重)
2. 网络重试 (客户端自动重试)
3. 消息队列重试 (消费者)
4. 分布式锁过期 (锁释放了, 业务没完成)

幂等方案:
1. 唯一索引
   - 订单表 (userId, itemId, round) 唯一
   - 重复请求插入失败

2. 唯一请求 ID
   - 客户端生成 requestId
   - 服务端 Redis SETNX 标记
   - 已处理过直接返回结果

3. 状态机
   - 订单状态: 待支付 → 已支付 → 已发货
   - 状态机推进不可逆

4. Token 机制
   - 预生成 token, 用后失效
```

```java
// 1. Redis 幂等 (requestId)
public Result idempotentRequest(String requestId, Function<Result> action) {
    String key = "idempotent:" + requestId;
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(key, "1", 24, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(success)) {
        // 已处理过, 返回之前的结果 (从 Redis 读取)
        return Result.fromJson(redisTemplate.opsForValue().get(key + ":result"));
    }
    Result result = action.apply();
    redisTemplate.opsForValue().set(key + ":result", result.toJson());
    return result;
}
```

## 六、典型业务场景的方案权衡

### 6.1 场景 1:库存 100 件,100 万人抢

```text
方案: Redis Lua 原子扣减 + 异步订单

流程:
1. 用户请求 (限流: 100 万 → 5 万 QPS)
2. Redis Lua 原子扣减库存 (返回结果: 成功/售罄)
3. 成功 → 加入订单队列 (异步)
4. 异步消费者: 创建订单、扣 DB 库存
5. 推送通知

关键点:
- Redis 库存 = 100 (预热)
- 100 万请求 → 5 万 QPS 通过限流
- 5 万请求 → Redis 原子扣减 → 只有 100 个成功
- 100 个订单 → 异步落库

一致性:
- Redis 原子扣减保证不超卖
- 异步落库有 1-3 秒延迟
- Redis 故障 = 系统不可用 (降级为 DB)
```

### 6.2 场景 2:秒杀下单 + 支付

```text
方案: 本地消息表 + 异步对账

流程:
1. 创建订单 (本地事务, 包含订单 + outbox 消息)
2. 后台轮询 outbox, 发到 MQ
3. 通知支付服务
4. 用户支付
5. 支付成功 → 更新订单状态
6. 定时对账: 找出支付未到账的订单 (异常处理)

一致性:
- 订单与消息在同事务 (原子)
- 消息必达 (轮询 + 重试)
- 支付与订单最终一致
```

### 6.3 场景 3:多用户抢同一 SKU (热点问题)

```text
方案: 库存分段 + 排队

库存分段 (避免单 key 热点):
- 100 件库存, 分成 10 段
- 每段 10 件, 10 个 Redis key
- 用户请求 hash 取模, 落到某一段
- 每段独立扣减, 总和不超过 100

排队:
- 超过库存时, 放入等待队列
- 前面用户放弃时, 后续用户补位
- (复杂的"捡漏"逻辑)
```

### 6.4 场景 4: 防黄牛

```text
策略:
1. 实名认证: 一个人只能买一件
   - Redis SET 记录 userId
   - 已存在则拒绝

2. 设备指纹:
   - 同一设备只能买一次
   - 同一 IP 只能买一次
   - 限制设备/IP 数量

3. 验证码 / 滑块:
   - 增加机器难度

4. 邀请码:
   - 通过邀请码才能抢购
   - 限制黄牛批量操作

5. 限购:
   - 实名认证用户每人最多 1 件
   - 高信用用户最多 2 件
```

## 十、总结

### 10.1 三大维度目标

```text
高性能 (Performance):
  目标: 100 万 QPS, P99 < 1s
  手段: 漏斗削减 + 缓存 + 异步 + 优化
  关键: 限流 + 多级缓存 + 异步削峰

高可用 (Availability):
  目标: 99.99%, 故障 30s 恢复
  手段: 多机房 + 冗余 + 限流降级
  关键: 无单点 + 自动故障转移

高一致性 (Consistency):
  目标: 不超卖, 订单不丢
  手段: Redis 原子 + 分布式锁 + 幂等
  关键: Redis 原子操作 + 异步落库 + 对账
```

### 10.2 一句话总结

```text
秒杀系统 = 高性能(漏斗) + 高可用(冗余) + 高一致性(原子)
  削峰(异步+限流) + 限流(多层) + 缓存(多级)
  无单点(冗余) + 自动切换(故障转移) + 降级(可丢失)
  原子操作(Redis Lua) + 分布式锁 + 幂等设计
```

| **异步削峰** | 消息队列 (RocketMQ/Kafka) | 用户响应快, 处理慢 |
| **库存原子** | Redis Lua 脚本 | DECR 原子性 |
| **库存同步** | 异步落库 + 定时对账 | 允许秒级延迟, 不允许超卖 |
| **幂等设计** | 唯一索引 + requestId | 避免重复下单 |
| **防超卖** | Redis 原子 + 分布式锁 + DB 乐观锁 | 多重防线 |
| **高可用** | 多机房 + 服务冗余 + 限流降级 | 自动故障转移 |
| **容灾** | 异地灾备 + DNS 切换 | 5 分钟 RTO |
| **监控** | Prometheus + Grafana + 告警 | 全链路指标 |

---

> **核心思想**: 秒杀系统不是单点优化,而是**全链路协同**。前端削减 + 后端削峰 + 数据原子 + 异步落库 + 监控告警,缺一不可。
