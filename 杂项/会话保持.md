# 会话保持(Session Persistence)

## 一、什么是会话保持

### 1. 定义

**会话保持**:在分布式 / 多后端架构中,**确保同一个客户端的多次请求都路由到同一个后端服务器**,避免跨节点的会话状态不一致。

```text
客户端          LB / Nginx         后端集群        共享存储
   │               │                  │              │
   ├──请求1──────>├── 路由 → server1 ─┤              │
   │               │                  │              │
   ├──请求2──────>├── 路由 → server1 ─┤  ←── 会话保持
   │               │  (同一后端)        │
   ├──请求3──────>├── 路由 → server1 ─┤
   │               │                  │
   │               ├── server2 ──────>│  ← 不会指向其他节点
   │               └── server3 ──────>│
```

### 2. 为什么需要会话保持

```text
1. 后端使用本地内存 Session
   → server1 有 session,server2 没有 → 用户登录状态丢失

2. 业务缓存亲和(WebSocket 长连接)
   → 用户连到 server1,后续请求须到 server1

3. 文件上传断点续传
   → 文件状态在 server1,换机器后丢失

4. 减少后端间的状态同步成本
   → 让同用户总到同机器,免去状态广播
```

### 3. 会话保持 vs 无状态架构

| 维度 | 会话保持 | 无状态(JWT) |
| ---- | -------- | ----------- |
| 状态位置 | 服务端 | 客户端(签名 token) |
| 后端切换 | 受限 | 任意切换 |
| 跨语言 | 难 | 容易 |
| 注销 | 容易(服务端清状态) | 难(等过期) |
| 性能 | 需查询共享存储 | 仅验签 |
| 适用 | 传统 Web | 微服务 / API |

## 二、Nginx 层的会话保持

### 1. 方式总览

| 方式 | 实现 | 粒度 | 复杂度 | 可靠性 |
| ---- | ---- | ---- | ------ | ------ |
| **IP Hash** | 客户端 IP 哈希到固定 upstream | IP | 低 | 中 |
| **Cookie Insert** | Nginx 注入 Cookie,带 server 信息 | 客户端 | 低 | 高 |
| **Cookie Learn** | Nginx 学习后端响应 Cookie | 客户端 | 中 | 高 |
| **sticky 模块**(Nginx Plus) | 高级会话保持 | 客户端 | 中 | 极高 |
| **route / consistent_hash** | 通用哈希 | key 灵活 | 中 | 高 |

### 2. IP Hash(Nginx upstream)

```nginx
upstream backend {
    ip_hash;                            # 启用 IP 哈希
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}

server {
    location / {
        proxy_pass http://backend;
    }
}
```

#### 原理

```text
hash(client_ip) % N → 后端编号

例:server 数 = 3
client 1.2.3.4   → hash % 3 = 1 → 10.0.0.2
client 5.6.7.8   → hash % 3 = 0 → 10.0.0.1
client 9.10.11.12 → hash % 3 = 2 → 10.0.0.3
```

#### 优缺点

| 优点 | 缺点 |
| ---- | ---- |
| 配置简单(一行指令) | **粒度太粗**:NAT 后所有用户一个 IP → 全到一台 |
| 不依赖 Cookie | 后端增减时**重新哈希**,会话大范围漂移 |
| 无额外存储 | **不均衡**:某些 IP 段请求密集 |

#### 适用场景

- 客户端是真实 IP(无 NAT)
- 后端变化少
- 不需要强一致(漂移可容忍)

### 3. Hash(更灵活)

```nginx
upstream backend {
    hash $cookie_session_id consistent;     # 按 session_id 一致性哈希
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

**特点**:一致性哈希,后端增减只影响少量 key。

### 4. Cookie Insert(Nginx 注入 Cookie)

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    cookie SESSIONID insert indirect nocache;     # Nginx 注入 SESSIONID
}
```

#### 原理

```text
1. 客户端首次请求 → Nginx 路由到 backend
2. Nginx 给响应注入 Set-Cookie: SESSIONID=server1.xxx
3. 客户端后续请求带 Cookie: SESSIONID=server1.xxx
4. Nginx 解析 Cookie,识别 SESSIONID=server1 → 路由到 server1
```

#### 优缺点

| 优点 | 缺点 |
| ---- | ---- |
| 客户端精确路由 | 首次访问没有 Cookie,需 fallback |
| 后端增减仍可工作(失效 Cookie) | 客户端禁用 Cookie 失效 |
| 比 IP Hash 粒度细 | 增加 Cookie 字段 |

### 5. Cookie Learn(响应式学习)

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    # 假设后端响应里有 Set-Cookie: SRV=node1, Nginx 学习后用它路由
}
```

商业版 Nginx Plus 的 `sticky` 指令更完整:

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    sticky cookie srv_id expires=1h path=/;
    # 学习后端 Set-Cookie 中的 srv_id,后续按它走
```

### 6. HAProxy 层面的会话保持

```haproxy
backend backend
    balance roundrobin
    stick-table type ip size 50k expire 30m
    stick on src
```

HAProxy 用 stick-table 维护会话映射,**比 Nginx 的 IP Hash 更精细**。

### 7. Nginx 会话保持方案对比

| 方案 | 粒度 | 漂移风险 | NAT 兼容 | 复杂度 |
| ---- | ---- | -------- | -------- | ------ |
| **ip_hash** | IP | **大**(后端变化时) | 差 | 最低 |
| **hash cookie consistent** | 客户端 Cookie | 小 | 好 | 中 |
| **Cookie insert** | 客户端 | 小 | 好 | 中 |
| **HAProxy stick-table** | IP / cookie | 极小 | 任意 | 中 |

## 三、后端 + Redis Session

### 1. 为什么用 Redis

- **内存存储**:微秒级读写
- **支持 TTL**:自动过期
- **集群扩展**:Redis Cluster / Sentinel
- **多后端共享**:所有应用节点连同一 Redis → 无需会话保持

```text
                     Redis(共享 Session)
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
          Backend 1   Backend 2   Backend 3
              ▲           ▲           ▲
              │           │           │
              └─────── Client ─────────┘
                  (任意后端都能读到同一 Session)
```

### 2. Spring Boot + Spring Session + Redis

#### 引入依赖

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

#### 配置

```yaml
# application.yml
spring:
  session:
    store-type: redis
    redis:
      namespace: myapp:session
      flush-mode: on_save
    timeout: 30m                          # 30 分钟过期
  redis:
    host: redis.example.com
    port: 6379
    password: ${REDIS_PASS}
    lettuce:
      pool:
        max-active: 16
```

#### 使用

```java
@RestController
public class UserController {

    @GetMapping("/profile")
    public User profile(HttpSession session) {
        // Spring Session 自动用 Redis 替代 HttpServlet 内存
        User user = (User) session =.getAttribute("user");
        if (user == null) {
            throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
        }
        return user;
    }

    @PostMapping("/login")
    public void login(@RequestBody LoginRequest req, HttpSession session) {
        User user = userService.authenticate(req);
        session.setAttribute("user", user);
        // session 自动同步到 Redis
    }
}
```

#### Redis 中存储的内容

```text
key:    myapp:session:0d8c3a4e-8a85-4b3d-9f01-xxx
type:   HASH
fields: sessionAttr:user = {id: 1, name: "alice", ...}
        creationTime = 1700000000000
        lastAccessedTime = 1700000060000
        maxInactiveInterval = 1800
TTL:    1800 秒(自动过期)
```

### 3. Express(Node.js) + Redis Session

```javascript
const session = require('express-session');
const RedisStore = require('connect-redis').default;
const redis = require('redis');

const client = redis.createClient({
    socket: { host: 'redis.example.com', port: 6379 },
    password: process.env.REDIS_PASS
});

app.use(session({
    store: new RedisStore({ client, prefix: 'myapp:' }),
    secret: 'keyboard cat',
    resave: false,
    saveUninitialized: false,
    cookie: {
        secure: true,            // HTTPS only
        httpOnly: true,
        maxAge: 30 * 60 * 1000,  // 30 分钟
    }
}));

app.post('/login', (req, res) => {
    req.session.user = { id: 1, name: 'alice' };
    res.json({ ok: true });
});
```

### 4. Django + Redis Session

```python
# settings.py
CACHES = {
    'default': {
        'BACKEND': 'django_redis.cache.RedisCache',
        'LOCATION': 'redis://redis.example.com:6379/1',
        'OPTIONS': {
            'CLIENT_CLASS': 'django_redis.client.DefaultClient',
        }
    }
}
SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
SESSION_CACHE_ALIAS = 'default'
SESSION_COOKIE_AGE = 30 * 60
```

### 5. Redis 集群 / 高可用

```text
Redis Sentinel:
   ┌─────────────────────────────┐
   │ Master + 2 Sentinels         │
   │ 自动故障转移(秒级)           │
   └─────────────────────────────┘

Redis Cluster:
   ┌─────────────────────────────┐
   │ 6+ 节点(3 主 + 3 从)        │
   │ 自动分片,水平扩展           │
   └─────────────────────────────┘

Session 共享时的注意:
   - Session 用 hash tag: {tag}sessionId,保证同用户同节点
   - 配置: spring.session.redis.namespace=myapp:{tag}
```

### 6. Redis 共享 Session 的优缺点

| 优点 | 缺点 |
| ---- | ---- |
| 多后端共享,无需会话保持 | 引入 Redis 依赖 |
| 自动 TTL,无清理逻辑 | 频繁读写(可优化) |
| 毫秒级响应 | 网络/Redis 故障 = Session 不可用 |
| 集群支持好 | 持久化策略需权衡(RDB / AOF) |

## 四、后端 + MySQL Session

### 1. 场景

- **需要 Session 持久化**(Redis 故障不影响登录)
- **合规要求**(审计 Session 历史)
- **小规模应用**(没必要 Redis)
- **不想引入新组件**

### 2. Spring Boot + JDBC Session

#### 依赖

```xml
<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
</dependency>
```

#### Schema(官方)

```sql
-- Spring Session JDBC Schema (MySQL)
CREATE TABLE SPRING_SESSION (
    PRIMARY_ID CHAR(36) NOT NULL,
    SESSION_ID CHAR(36) NOT NULL,
    CREATION_TIME BIGINT NOT NULL,
    LAST_ACCESS_TIME BIGINT NOT NULL,
    MAX_INACTIVE_INTERVAL INT NOT NULL,
    EXPIRY_TIME BIGINT NOT NULL,
    PRINCIPAL_NAME VARCHAR(100),
    CONSTRAINT SPRING_SESSION_PK PRIMARY KEY (PRIMARY_ID)
) ENGINE=InnoDB;

CREATE UNIQUE INDEX SPRING_SESSION_IX1 ON SPRING_SESSION (SESSION_ID);
CREATE INDEX SPRING_SESSION_IX2 ON SPRING_SESSION (EXPIRY_TIME);
CREATE INDEX SPRING_SESSION_IX3 ON SPRING_SESSION (PRINCIPAL_NAME);

CREATE TABLE SPRING_SESSION_ATTRIBUTES (
    SESSION_PRIMARY_ID CHAR(36) NOT NULL,
    ATTRIBUTE_NAME VARCHAR(200) NOT NULL,
    ATTRIBUTE_BYTES BLOB NOT NULL,
    CONSTRAINT SPRING_SESSION_ATTRIBUTES_PK PRIMARY KEY (SESSION_PRIMARY_ID, ATTRIBUTE_NAME),
    CONSTRAINT SPRING_SESSION_ATTRIBUTES_FK FOREIGN KEY (SESSION_PRIMARY_ID)
        REFERENCES SPRING_SESSION(PRIMARY_ID) ON DELETE CASCADE

CREATE INDEX SPRING_SESSION_ATTRIBUTES_IX1 ON SPRING_SESSION_ATTRIBUTES (SESSION_PRIMARY_ID);
```

#### 配置

```yaml

      maximum-pool-size: 16
```

### 5. 优缺点

| ---- | ---- |
| **持久化**:数据库备份即会话备份 | **慢**:磁盘读写,毫秒级 |

| 合规 / 审计容易 | 表膨胀,需清理 |
| 可精确查询(管理后台) | 事务冲突可能 |

## 五、Redis vs MySQL Session 对比

| 维度 | Redis Session | MySQL Session |
| ---- | ------------- | ------------- |
| **读写速度** | **~1ms(内存)** | ~10ms(磁盘) |
| **持久化** | 可选(RDB / AOF) | **天然持久化** |
| **TTL** | **内置** | 需定时清理 |
| **横向扩展** | Cluster / Sentinel | MySQL 主从 / 集群 |
| **运维成本** | 中(额外组件) | 低(已有 DB) |
| **合规 / 审计** | 弱 | **强** |
| **适用规模** | 中-大流量 | 中小流量 / 合规场景 |
| **常见组合** | Spring Session + Redis | Spring Session + JDBC |
| | Django + django-redis | Django + DB(默认) |
| | Express + connect-redis | Express + express-mysql-session |

## 六、Nginx 与后端的会话保持完整链路

### 1. Nginx + Cookie Insert + 后端 Session(任意存储)

```text
Nginx(IP Hash / Cookie Insert)
   ↓
Backend(任意后端,Session 在 Redis / MySQL)
   ↓
共享 Session 存储
```

```nginx
upstream backend {
    ip_hash;                            # 弱会话保持(IP 维度)
    # 或: hash $cookie_SESSIONID consistent;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}

server {
    location / {
        proxy_pass http://backend;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

```java
// 后端:session 存在 Redis,所有 backend 共享
// 即使 Nginx IP hash 后用户偶尔切到另一台,Redis 仍能找到 session
```

### 2. Nginx 不做会话保持,完全依赖后端共享 Session

```nginx
upstream backend {
    # 不做 ip_hash,负载均衡最均匀
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

```java
// 后端:Spring Session + Redis
// 任意后端都能读到 session
```

**优势**:负载均衡最均匀;**前提**:Redis 高可用、延迟可接受。

### 3. 双层:Nginx 粗粒度 + 后端细粒度

```nginx
upstream backend {
    hash $cookie_REGION consistent;       # 按地域分流(粗)
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

```java
// 后端 session 按 user_id 精细
// 用户在某个地域内请求同后端;同一地域内多用户分散到该地域所有节点
```

### 4. 实战:Lua 注入会话标记(OpenResty)

```nginx
location /api/ {
    access_by_lua_block {
        local uid = ngx.var.arg_uid
        if uid then
            ngx.var.upstream = "backend_" .. (uid % 3)   -- 注入 upstream 变量
        end
    }

    proxy_pass http://$upstream;
}
```

## 七、跨语言 / 跨后端的会话共享

### 1. JWT(无状态)

```java
// Java 后端签发
String jwt = Jwts.builder()
    .setSubject("alice")
    .claim("role", "user")
    .setExpiration(new Date(System.currentTimeMillis() + 3600_000))
    .signWith(SignatureAlgorithm.HS256, secret)
    .compact();
```

```python
# Python 后端验证
import jwt
payload = jwt.decode(token, secret, algorithms=["HS256"])
# payload["sub"] = "alice"
```

**优势**:跨语言,任意后端,无需共享存储。

**劣势**:注销困难、Token 体积大(每次请求带)。

- 跨语言需统一序列化(Java Serialization / MessagePack)
- 或用 `serde` / `pickle` / `json` 等通用格式

```python
# Python 写
import redis, json
r.setex(f"session:{sid}", 1800, json.dumps({"user": "alice"}))

# Java 读
String data = = jedj.get("session:" + sid);
User user = objectMapper.readValue(data, User.class);
```

### 3. OAuth 2.0 / OpenID Connect(SSO)

```text
用户 → App A(无 Session) → 跳 OAuth 登录
                            ↓
                          Auth Server
                            ↓
                       返回 access_token
                            ↓
   App A / App B / App C 都用 token 鉴权
   (跨应用共享)
```

适用:多应用统一登录、企业 SSO。

## 八、典型架构对比

### 1. 传统 Web 应用(中小规模)

```text
Nginx(可选 ip_hash)
  └─→ Tomcat / Spring(本地 Session)
      └─→ MySQL(数据)
```

**特点**:简单,Session 在内存;Nginx IP Hash 防 Session 漂移。

### 2. 现代微服务

```text
Nginx / API Gateway
  └─→ 用户服务(无状态 + JWT)
  └─→ 订单服务(无状态)
  └─→ 会话服务(Redis Session,可选)
       └─→ Redis Cluster
```

**特点**:无状态服务扩缩容友好,JWT 携带用户信息。

### 3. 高并发 Web

```text
CDN
  └─→ Nginx(ip_hash / cookie)
       └─→ Backend(Session 存 Redis)
            └─→ Redis Sentinel / Cluster
```

**特点**:多层缓存,Session 共享,Nginx 粗粒度保持。

### 4. 实时通信(WebSocket)

```text
Nginx(stream)
  └─→ Backend(必须 ip_hash,长连接)
       └─→ 业务 Session
```

**特点**:WebSocket 必须粘性路由,Nginx stream 模块支持。

## 九、典型陷阱

### 1. Session 漂移导致登录态丢失

```text
现象:用户频繁掉线
原因:
  - Nginx IP Hash + 后端无 Session 共享
  - 后端变化导致 IP Hash 重新分配

解决:
  - 后端 Session 共享(Redis / MySQL)
  - 或用 cookie hash 一致性
  - 后端不变(滚动升级用蓝绿 / 灰度)
```

### 2. Redis 故障 = 全站登录态失效

```text
现象:Redis 挂了,所有用户重新登录
解决:
  - Redis Sentinel / Cluster 高可用
  - 本地 Session 兜底(Redis 故障时降级到本地)
  - 双写(Redis + 本地,定期同步)
```

### 3. JWT 注销难

```text
现象:用户改密码后旧 token 还能用
解决:
  - 服务端维护 token 黑名单(Redis Set)
  - 短 token 有效期 + 刷新 token
  - 每次请求检查 token 状态
```

### 4. Cookie Secure 与 SameSite 设置错

```javascript
// ❌ HTTPS 下 Cookie 没设 Secure,明文传输
res.cookie('session', value);

// ✅ 正确配置
res.cookie('session', value, {
    secure: true,         // 仅 HTTPS
    httpOnly: true,        // 防 XSS
    sameSite: 'lax',      // 防 CSRF
    maxAge: 30 * 60 * 1000
});
```

### 5. 后端 Session 表无限增长

**现象**:Session 表持续膨胀,占用大量磁盘

**解决**:

- 启用定时清理(Spring Session 自带 / Django `clearsessions`)
- 用 Redis TTL 替代数据库清理
- 拆分历史表(按月分表)

### 6. 跨域 Cookie 丢失

```text
现象:登录成功但前端看不到 Cookie
原因:跨域请求默认不发 Cookie
解决:
  - 前端:withCredentials = true
  - 后端:Access-Control-Allow-Credentials: true
  - SameSite 配置
```

### 7. Cookie 大小超过 4KB

```text
现象:浏览器丢弃 Cookie
解决:
  - 减小 Session id 体积
  - 数据放服务端,Cookie 只放 session_id
  - JWT 用 Header 不用 Cookie
```

## 十、决策表

| 场景 | 推荐方案 |
| ---- | -------- |
| 传统 Web / 内部系统 | 后端内存 Session + Nginx IP Hash |
| 互联网应用 / 中大规模 | **Redis Session + Nginx 任意 LB** |
| 高合规(金融 / 政府) | MySQL Session(可审计) |
| 微服务 / API | **JWT 无状态** |
| 多应用 SSO | OAuth 2.0 / OIDC |
| WebSocket / 长连接 | Nginx IP Hash / stream |
| 跨语言混合栈 | Redis Session(统一序列化) + JWT 兼容 |
| 临时活动页 | 不需要 Session |

## 十二、要点速记

- **会话保持 = 同一客户端请求到同一后端**
- **Nginx 层方式**:ip_hash / cookie insert / sticky / consistent hash
- **IP Hash 简单但粗粒度**:NAT 后失效;后端变化大漂移
- **Cookie 方式粒度细**:依赖客户端 Cookie,首次需 fallback
- **后端共享 Session** 是终极方案:Redis(快)/ MySQL(持久化)
- **Redis Session**:内存、TTL、Cluster、性能极佳
- **MySQL Session**:持久化、审计,但慢、写放大
- **Spring Session**:统一抽象,Redis / JDBC / Hazelcast 任意切换
- **JWT 无状态**:跨语言、无需共享存储,但注销难
- **WebSocket 必须粘性**:Nginx IP Hash / stream
- **Redis 故障 = 全站 Session 失效**:需 Sentinel / Cluster / 兜底
- **JWT 黑名单** 解决注销问题
- **Cookie 必须 Secure + HttpOnly + SameSite**
- **跨域 Cookie**:withCredentials + Allow-Credentials
- **Cookie 大小 ≤ 4KB**
- **Session 表定期清理**:Spring 自带 / Django clearsessions
- **Nginx 层保持 + 后端共享 Session** = 双重保险
- **跨语言 Session**:统一序列化(JSON / MessagePack)
- **架构选型**:传统 Web → 内存 + IP Hash;微服务 → JWT;中大规模 → Redis
- **避免大 Session**:只存 session_id,数据存服务端
- **IP Hash 的漂移**:用一致性 hash 或按业务 key(uid / cookie)
- **sticky 模块是商业版**:开源用 cookie insert 模拟
- **Nginx Plus 的 sticky** 最完整:支持 learn / insert / route / service
- **HAProxy 的 stick-table** 比 Nginx IP Hash 更精细
