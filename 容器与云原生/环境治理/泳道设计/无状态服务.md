# 基于 Istio + User 信息的开发测试环境泳道设计

> 目标：**让开发者只起自己改的服务的 Pod，就能完整跑通调用链验证**，不影响其他人的工作。
> 核心思路 = **Header 透传 + Operator 自动生成 VirtualService + 按 user 路由**。

## 一、原始设计复盘

```text
原始逻辑：
  1. 每个开发人员有 user 身份
  2. 开发自己服务时起一个 dev pod + VirtualService
  3. VirtualService 按 user header 路由：
     - user = 自己 → 走自己 dev pod
     - user = 别人 + 没对应 dev pod → 走原 pod
  4. 流量沿调用链向下游传递，每个服务都按同样规则
  5. 用 Operator：发现带特定 label 的 Pod → 自动生成 VirtualService
```

**用一句话总结**：

> **"开发者只改自己动的那一环，整条链路靠 user header 串起来"**。

## 二、这套设计的 7 个核心优点

| 维度 | 评价 |
| --- | --- |
| **侵入性低** | 业务代码不用动，靠 Mesh 头部传递 |
| **资源效率** | 100 个 dev 不会起 100 份全链路，只起改过的 |
| **互相隔离** | A 的请求只走 A 的 dev pod，不污染 B |
| **不破坏现网** | 其他人没 dev pod 时走原 pod，零风险 |
| **链路可串** | Header 透传保证整条链路用同一个 user 标识 |
| **可自动化** | Operator 扫 label 即可，开发者不用手写 VS |
| **灰度天然支持** | 同一服务被多 dev 改时，按 user 分流天然是灰度 |

**和传统 dev 环境对比**：

```text
传统（每个 dev 一套完整环境）：
  100 dev × 10 服务 × 1 pod = 1000 pod
  资源成本爆炸

本设计：
  100 dev × 平均改 2 服务 × 1 pod = 200 pod
  + 1 套稳定环境（共享）
  节省 80% 资源
```

## 三、关键缺陷 / 需要补充的地方

> 这套设计**方向对**，但**直接落地会踩 10+ 坑**。下面逐一分析。

### 3.1 缺陷 1：Header 注入点没明确

```text
问题：
  user header 从哪来？
  → 前端？登录系统？网关？客户端？

场景：
  - 浏览器发请求：前端要从 cookie / localStorage 拿 user
  - 内部 RPC：调用方要塞 user header
  - 第三方 API：不能带 user header
  - 定时任务 / 异步：没有 user 上下文
```

**必须补的设计**：

```text
1. 入口统一注入（推荐）：
   边缘网关 / 登录后端 注入 X-Lane-User: <username>
   内部所有调用透明透传
   出 mesh 时在 Egress Gateway 剥除

2. 调用方显式透传：
   业务代码用 gRPC interceptor / Spring filter 显式透传
   缺点：业务要改代码

3. 客户端 SDK：
   提供统一 client，自动注入 + 透传
   缺点：每语言一份
```

### 3.2 缺陷 2：gRPC 不走 HTTP header

```text
问题：
  HTTP 用 X-Lane-User header
  gRPC 用 metadata（类似 header 但走 HTTP/2 不同字段）
  → 同一套 VirtualService 规则能匹配 gRPC 吗？
  → Istio 的 header 匹配是 HTTP 层，gRPC 流量能匹配但需要正确识别
```

**补充（详见第七节）**：

```text
- Istio 支持 gRPC 的 header 匹配（按 :authority / :method 之外的普通 header）
- 但 metadata 的 key 是大小写不敏感的，header 也是
- gRPC interceptor 要塞 `x-lane-user`（小写）而非 `X-Lane-User`
```

### 3.3 缺陷 3：链路终止条件不清

```text
问题：
  A 改了 service X，X → Y → Z
  A 发起请求，X 走 A 的 dev pod
  X 调用 Y，Y 看到 user header 是 A
  → Y 没有 A 的 dev pod
  → Y 走原 pod
  → Y 调用 Z
  → Z 看到 user header 是 A
  → Z 没有 A 的 dev pod
  → Z 走原 pod

  现在问题来了：
  - 这条链路上，Y 看到的 user header 是 A
  - 但 Y 实际上跑的是 Y 的"原 pod"（不是 A 改的 Y）
  - 这逻辑对吗？

分两种情况：

  情况 1：Y 没被 A 改 → 应该走原 pod（当前设计）
  情况 2：Y 实际上被 A 改过但 A 没起 dev pod → 那 Y 怎么验证？
```

**补充设计**：

```text
- "改过"的状态：服务版本基于某个 git commit/branch
- A 改 service X 但 Y 用的还是 A 修改前的版本 → 走原 pod OK
- A 也改了 Y 但没起 dev pod → 没法验证（这是 A 的问题）
- Operator 智能推荐：A 改的 commit 涉及的 service 一并起 dev pod

折中：让 Operator 检测 A 的 git 改动，自动给相关 service 创建 dev pod
```

### 3.4 缺陷 4：多人同时改同一服务

```text
问题：
  Alice 改 service X
  Bob 也改 service X
  → 都起 dev pod，label: dev.alice / dev.bob
  → 需要两个 VirtualService 吗？还是一个？

方案 A：两个 VS，分别按 user 匹配
  VS-A: user=alice → pod dev.alice
  VS-B: user=bob → pod dev.bob
  VS-Stable: 其他 → 原 pod
  → 3 个 VS 并存，按顺序匹配

方案 B：一个 VS，多条 rule
  VS-X:
    - match: user=alice → dev.alice
    - match: user=bob → dev.bob
    - route: 默认 → 原 pod
  → 简洁但 VS 是单 resource，A 改了要 merge 到 B 的 VS

方案 C：Operator 协调一个聚合 VS
  所有 dev pod 的路由在一个 VS 里
  冲突时按某种规则（创建时间 / 优先级）
```

**推荐方案 A**：

```text
理由：
  - 各 dev 互不干扰（Operator 给每个 dev pod 生成一个 VS）
  - VS 是声明式的，多个 VS 顺序匹配，逻辑清晰
  - A 不需要等 B 才能改 VS

冲突处理：
  - Operator 给每个 dev pod 生成 VS 时加 ownerReference
  - dev pod 删除 → VS 自动级联删除
```

### 3.5 缺陷 5：资源清理

```text
问题：
  开发者关闭 IDE / 下班 / 离职
  dev pod 留着 → 资源浪费

清理策略：
  1. TTL：dev pod 起 8 小时后自动删
  2. 心跳：VS / Pod 加 annotation last-active-time，每访问一次更新
  3. Idle GC：30 分钟没流量就删
  4. 工作时段：只在工作时间保留（9:00-19:00）
  5. 手动：开发主动删除
```

**推荐组合**：

```yaml
# Dev Pod annotation
metadata:
  annotations:
    lane.dev/ttl: "8h"
    lane.dev/owner: "alice"
    lane.dev/created-by: "operator"
```

### 3.6 缺陷 6：有状态依赖（核心难点）

```text
问题：
  A 改了 service X，X 调用 MySQL / Redis / Kafka
  dev X 用什么 DB？
  
  方案 1：dev pod 用 dev DB
    - 100 dev × 独立 DB = 100 个 DB（贵！）
    - 共享 dev DB：互相影响
    - 折中：动态创建，idle 删
    
  方案 2：dev pod 用主 DB
    - 风险：会污染主库
    - 改造：用 schema-per-dev（按 dev 分 schema）
    
  方案 3：dev pod 跑 stub
    - 用 testcontainers 起临时 DB
    - 适合：单元测试，不适合：链路测试
    
  方案 4：业务层抽象
    - 每个 dev 写代码时考虑多租户
    - DB 用 SELECT ... WHERE tenant_id = 'alice'
    - 改造代价大
```

**推荐方案 1 的变体**：

```text
dev pod 共享一个 dev DB，但：
  - schema：dev 改 schema 时跑 migration，按 dev 分 schema
  - 数据：dev pod 跑 seed 时写到 dev 专属 schema
  - 写操作：dev 只能写自己 schema 的数据
  
或者（更彻底）：
  - 标题是"无状态服务"，假设业务访问的是无状态 API
  - DB 改动不在本设计范围，单独治理（dev DB 平台 / 影子表）
```

### 3.7 缺陷 7：Header 透传的边界

```text
问题：
  所有内部调用都要透传 X-Lane-User
  出 mesh 时必须剥除（安全 / 隐私）
  第三方 API 永远不能带

边界控制：
  1. Egress Gateway 在出 mesh 时剥除特定 header
  2. Istio 的 sidecar outbound listener 配 filter
  3. 业务框架层做白名单（只透传 X-Lane-* 前缀）
```

### 3.8 缺陷 8：可观测性

```text
问题：
  dev pod 怎么跟原 pod 区分？
  链路追踪：跨 dev pod 链 / dev → 原 pod 怎么 trace？
  日志：dev pod 报错怎么快速定位？

补充：
  - log 增加字段 dev_owner=alice
  - trace 增加 tag dev.lane/owner=alice
  - metrics 加 label dev_owner
  - Kiali 拓扑图能区分 dev pod 和 stable pod
```

### 3.9 缺陷 9：强依赖 Service Mesh

```text
问题：
  没有 Istio / Linkerd 怎么办？

备选：
  1. 用 Nginx + Lua + etcd 自研路由（成本高）
  2. 用 Spring Cloud Gateway + 用户态路由（侵入业务）
  3. 用 APISIX / Envoy 直连（需要运维）
  4. 应用层 SDK（每语言一份）
  
  结论：
  - 强依赖 Mesh 是设计前提
  - 团队要接受这个前提
```

### 3.10 缺陷 10：故障 / 紧急回滚

```text
问题：
  VirtualService 写错 → 所有 user 都打到了错的 dev pod
  Operator 抽风 → 批量生成了垃圾 VS
  怎么快速止损？

补充：
  - VS 加 label lane.dev/enabled: "true|false"
  - Operator 监听 disable 标签，删除所有生成的 VS
  - 全局开关：改 ConfigMap 关闭整个 lane 系统
  - 命名空间隔离：dev pod 单独 ns，错了只影响 ns 内
```

### 3.11 缺陷 11：CI/CD 集成 + image 信息流

```text
核心问题（容易漏掉的）：
  Lane CR 需要 dev pod 的 image 字段
  → image 从哪来？谁塞进去？
  → 开发者手动写？CI 自动注入？Operator 从哪查？
  → image 信息贯穿 CI → CRD → Operator → Pod 整条链

3 个角色对 image 的贡献：
  ┌──────────┐    image build+push    ┌──────────┐    Lane CR (含 image)    ┌──────────┐
  │   CI     │ ────────────────────→ │ Registry │ ────────────────────────→ │ Operator │
  └──────────┘                        └──────────┘                          └─────┬────┘
       │                                                                       │
       │ git push 触发                                                          │ 创建 dev pod
       ▼                                                                       ▼
  ┌──────────┐                                                            ┌──────────┐
  │  Git     │                                                            │ Dev Pod  │
  └──────────┘                                                            └──────────┘
```

**3 种 image 信息流的方案**：

```text
方案 A：开发者手填 image（最简单但易错）
  kubectl create lane --image=my-registry.io/svc-x:abc123
  问题：
    - 手敲 SHA 容易错
    - 不记得最新 SHA
    - CI 重建了没同步

方案 B：CI 自动创建/更新 Lane CR（推荐）
  CI 流程：
    1. git push 触发 CI
    2. CI 构建镜像，tag = <git-sha>
    3. CI push 镜像
    4. CI apply Lane CR（spec.image = 新镜像）
  优点：
    - image 永远最新
    - 开发者不用关心 image
  问题：
    - CI 要有 K8s 集群写权限
    - 多个 commit 反复触发 → 频繁重建 pod

方案 C：Operator 监听镜像仓库自动 reconcile（最自动）
  Operator 订阅镜像仓库事件：
    - 发现新 tag → 自动起 dev pod
    - 镜像删除 → 自动清理 dev pod
  优点：
    - 开发者只需 git push，其他全自动
  问题：
    - 需要镜像仓库支持 webhook
    - 要识别"哪个 user 的 dev pod 用哪个镜像"
```

**推荐方案 B（CI 自动 apply Lane CR）**：

```yaml
# .gitlab-ci.yml / .github/workflows 中
build-and-deploy-lane:
  stage: build
  script:
    - IMAGE_TAG=$(git rev-parse --short HEAD)
    - IMAGE="my-registry.io/svc-x:${IMAGE_TAG}"
    - docker build -t ${IMAGE} .
    - docker push ${IMAGE}
    - |
      cat <<EOF | kubectl apply -f -
      apiVersion: lane.dev/v1
      kind: Lane
      metadata:
        name: ${CI_COMMIT_AUTHOR_USERNAME}-svc-x
        namespace: ${CI_COMMIT_AUTHOR_USERNAME}-dev
      spec:
        user: ${CI_COMMIT_AUTHOR_USERNAME}
        service: x
        image: ${IMAGE}                # ← image 来自 CI 构建
        ttl: "8h"
      EOF
```

**image 字段的约束（Operator 端）**：

```go
// reconcileLane 校验 image
func (r *LaneReconciler) validateImage(image string) error {
    // 1. 必须来自公司内部 registry（安全）
    if !strings.HasPrefix(image, "my-registry.io/") {
        return fmt.Errorf("image must be from my-registry.io")
    }

    // 2. tag 必须明确（禁用 latest，防止漂移）
    parts := strings.Split(image, ":")
    if len(parts) != 2 || parts[1] == "latest" {
        return fmt.Errorf("image tag must be pinned (sha or version), not latest")
    }

    // 3. 校验镜像存在（可选，避免起 pod 后 pull 失败）
    //    通过 k8s API 查 registry 或预拉取验证
    return nil
}
```

**image 信息流的边界 case**：

```text
E1：CI 构建失败
  → 没有新 image → Lane CR 不更新 → dev pod 还是旧的
  → 开发者手动起新 Lane 或修复 CI

E2：CI 成功但 push 到镜像仓库失败
  → Lane CR 引用了不存在的 image
  → Operator 创建 pod 时 image pull 失败
  → Pod 卡在 ImagePullBackOff
  → 解决：Operator 在 reconcile 前用 k8s API 校验镜像可拉取

E3：多个 commit 快速 push
  → CI 反复重建 → 反复 apply Lane CR
  → Operator 反复删除重建 pod
  → 解决：Operator 检测 image 变化 → 滚动升级 pod（不是删建）

E4：image 跨集群（多环境）
  → dev / staging / prod registry 不同
  → CRD 加字段 spec.registry 或从 ConfigMap 读

E5：私有镜像仓库鉴权
  → dev pod 需要 imagePullSecrets
  → Operator 自动注入（按 namespace 预创建 secret）

E6：基础镜像变更
  → dev 改了 Dockerfile，CI 重建
  → image tag 变了但 base image 缓存命中
  → dev pod 拉取失败（旧 base 被清理）
  → 解决：CI 保留 base layer 至少 N 天
```

**与 CRD 字段设计的对应关系**：

```yaml
spec:
  # 必填
  image: "my-registry.io/svc-x:abc123"      # ← CI 注入
  user: "alice"                              # ← CI 注入（来自 git author）
  service: "x"                               # ← 开发者声明 / CI 注入

  # 可选（让 CI / 开发者更灵活）
  imagePullPolicy: "Always"                  # 开发镜像频繁变
  imagePullSecrets:
  - name: regcred                            # 私有仓库鉴权
  registry: "my-registry.io"                 # 跨集群时指定
  baseImage: "golang:1.22"                   # 调试时覆盖
```

### 3.12 缺陷 12：调用链上"无 dev pod" 的边界 case

```text
场景：
  A 改 service X，A 没改 service Y，但 A 调试需要从 X 走到 Y
  → X 走 A 的 dev，Y 走原
  → 验证的就是 X 的改动对 Y 的影响
  
  这个 case 没问题。

但：
  A 改 service X 的同时 Y 团队刚发版（v2）了
  → A 调的是 Y 的 v2（不是 A 改之前的 v1）
  → 跟 A 改之前的链路不一样

  解决：
  - dev pod 的下游 Y 用 Y 的 v1 还是 v2？
  - 选 v1（一致性）
  - 选 v2（更现实）
  - 由 Y 团队的版本号决定
```

### 4.1 整体架构

┌──────────────────────────────────────────────────────────────┐
│                          控制平面                            │
│                                                              │
│  ┌─────────────┐    ┌─────────────┐    ┌──────────────┐     │
│  │ Lane CRD    │    │ Operator    │    │ Mesh         │     │
│  │ (开发者声明) │───→│ (生成 VS)   │───→│ (Istio)      │     │
│  └─────────────┘    └─────────────┘    └──────────────┘     │
│                            │                                │
│                            │ watch                          │
│                            ▼                                │
│                  ┌──────────────────┐                        │
│                  │ Dev Pods         │                        │
│                  │ (label: lane.dev)│                        │
│                  └──────────────────┘                        │
└──────────────────────────┬───────────────────────────────────┘
                           │ xDS
                           ▼
┌──────────────────────────────────────────────────────────────┐
│                          数据平面                            │
│                                                              │
│  入口 (Gateway) → 注入 X-Lane-User header                     │
│       │                                                      │
│       ▼                                                      │
│  Pod X (dev.alice) ← Envoy sidecar 拦截                       │
│  header: X-Lane-User=alice                                   │
│       │ 透传                                                  │
│       ▼                                                      │
│  Pod Y (原 pod) ← Envoy 看到 header 但没匹配的 VS            │
│       │                                                      │
│       ▼                                                      │
│  Pod Z (原 pod)                                              │
└──────────────────────────────────────────────────────────────┘

### 4.2 核心流程

```text
Step 1: 开发者声明 Lane CR（或者直接打 label）
  kubectl create -f - <<EOF
  apiVersion: lane.dev/v1
  kind: Lane
  metadata:
    name: alice-svc-x
    namespace: alice-dev
  spec:
    service: x
    image: my-registry.io/svc-x:abc123
    user: alice
  EOF

Step 2: Operator 创建 dev Pod + VirtualService
  Pod:
    name: svc-x-dev-alice
    labels:
      lane.dev/owner: alice
      lane.dev/service: x
      lane.dev/enabled: "true"
    spec:
      containers:
      - image: my-registry.io/svc-x:abc123
        env:
        - name: LANE_OWNER
          value: alice

  VirtualService:
    metadata:
      name: x-lane-alice
      namespace: default
    spec:
      hosts: [x]
      http:
      - match:
        - headers:
            x-lane-user:
              exact: alice
        route:
        - destination:
            host: x
            subset: dev-alice
      - route:                       # 默认走原 pod
        - destination:
            host: x
            subset: stable

Step 3: 用户发起请求
  GET / HTTP/1.1
  X-Lane-User: alice
  Cookie: ...

Step 4: 入口 Gateway / 网关层注入 header（如果没传）
  → 通过登录系统识别 user

Step 5: 请求进 mesh
  Envoy 看到 X-Lane-User: alice
  → 匹配 VS（alice → dev pod）
  → 转给 dev pod

Step 6: dev pod 处理，调用下游
  → 必须透传 X-Lane-User
  → 下游服务也按相同规则

Step 7: TTL 到期 / 开发者手动删
  → Operator 删除 dev pod
  → VS 级联删除（ownerReference）
```

### 5.2 核心 Controller 代码（Go）

```go
// LaneReconciler 核心逻辑（简化版）
package controllers

import (
    "context"
    "fmt"
    "time"

    "github.com/go-logr/logr"
    corev1 "k8s.io/api/core/v1"
    networkingv1 "k8s.io/api/networking/v1"
    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
    "k8s.io/apimachinery/pkg/runtime"
    ctrl "sigs.k8s.io/controller-runtime"
    "sigs.k8s.io/controller-runtime/pkg/client"

    lanev1 "github.com/example/lane-operator/api/v1"
)

type LaneReconciler struct {
    client.Client
    Scheme *runtime.Scheme
    Log    logr.Logger
}

func (r *LaneReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var lane lanev1.Lane
    if err := r.Get(ctx, req.NamespacedName, &lane); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 1. 已经被删除 → 清理资源
    if !lane.DeletionTimestamp.IsZero() {
        return r.cleanup(ctx, &lane)
    }

    // 2. 还没到时间过期 → 检查 TTL
    if r.isExpired(&lane) {
        return r.expireLane(ctx, &lane)
    }

    // 3. 创建 / 更新 dev pod
    if err := r.reconcileDevPod(ctx, &lane); err != nil {
        return ctrl.Result{}, err
    }

    // 4. 创建 / 更新 VirtualService
    if err := r.reconcileVirtualService(ctx, &lane); err != nil {
        return ctrl.Result{}, err
    }

    // 5. 5 分钟重 queue 一次（检查 TTL / 状态）
    return ctrl.Result{RequeueAfter: 5 * time.Minute}, nil
}

// 创建 dev Pod
func (r *LaneReconciler) reconcileDevPod(ctx context.Context, lane *lanev1.Lane) error {
    podName := fmt.Sprintf("%s-dev-%s", lane.Spec.Service, lane.Spec.User)
    namespace := lane.Spec.Namespace

    var existing corev1.Pod
    err := r.Get(ctx, client.ObjectKey{Name: podName, Namespace: namespace}, &existing)
    if err == nil {
        // 已存在，更新最后活跃时间
        return r.updateLastActive(ctx, &existing)
    }

    pod := &corev1.Pod{
        ObjectMeta: metav1.ObjectMeta{
            Name:      podName,
            Namespace: namespace,
            Labels: map[string]string{
                "lane.dev/owner":   lane.Spec.User,
                "lane.dev/service": lane.Spec.Service,
                "lane.dev/enabled": "true",
            },
            Annotations: map[string]string{
                "lane.dev/created-by":   "lane-operator",
                "lane.dev/created-time": time.Now().Format(time.RFC3339),
                "lane.dev/ttl":          lane.Spec.TTL,
            },
            OwnerReferences: []metav1.OwnerReference{
                *metav1.NewControllerRef(lane, lanev1.GroupVersion.WithKind("Lane")),
            },
        },
        Spec: corev1.PodSpec{
            Containers: []corev1.Container{
                {
                    Name:  lane.Spec.Service,
                    Image: lane.Spec.Image,
                    Env: []corev1.EnvVar{
                        {Name: "LANE_OWNER", Value: lane.Spec.User},
                        {Name: "LANE_ENABLED", Value: "true"},
                    },
                },
            },
        },
    }
    return r.Create(ctx, pod)
}

// 创建 VirtualService
func (r *LaneReconciler) reconcileVirtualService(ctx context.Context, lane *lanev1.Lane) error {
    vsName := fmt.Sprintf("%s-lane-%s", lane.Spec.Service, lane.Spec.User)

    // 找原 service 的 subset
    dr := &networkingv1.DestinationRule{}
    if err := r.Get(ctx, client.ObjectKey{
        Name: lane.Spec.Service, Namespace: lane.Spec.Namespace,
    }, dr); err != nil {
        return fmt.Errorf("need DestinationRule for %s: %w", lane.Spec.Service, err)
    }

    // 找原 service 的 port
    svc := &corev1.Service{}
    if err := r.Get(ctx, client.ObjectKey{
        Name: lane.Spec.Service, Namespace: lane.Spec.Namespace,
    }, svc); err != nil {
        return fmt.Errorf("need Service for %s: %w", lane.Spec.Service, err)
    }
    port := svc.Spec.Ports[0].Name
    if port == "" {
        port = strconv.Itoa(int(svc.Spec.Ports[0].Port))
    }

    vs := &networkingv1.VirtualService{
        ObjectMeta: metav1.ObjectMeta{
            Name:      vsName,
            Namespace: lane.Spec.Namespace,
            Labels: map[string]string{
                "lane.dev/owner":   lane.Spec.User,
                "lane.dev/service": lane.Spec.Service,
                "lane.dev/auto":    "true",
            },
            OwnerReferences: []metav1.OwnerReference{
                *metav1.NewControllerRef(lane, lanev1.GroupVersion.WithKind("Lane")),
            },
        },
        Spec: networkingv1.VirtualServiceSpec{
            Hosts: []string{lane.Spec.Service},
            HTTP: []networkingv1.HTTPRoute{
                {
                    Matches: []networkingv1.HTTPMatchRequest{
                        {
                            Headers: map[string]networkingv1.StringMatch{
                                "x-lane-user": {Exact: lane.Spec.User},
                            },
                        },
                    },
                    Route: []networkingv1.HTTPRouteDestination{
                        {
                            Destination: networkingv1.Destination{
                                Host:   lane.Spec.Service,
                                Subset: fmt.Sprintf("dev-%s", lane.Spec.User),
                            },
                        },
                    },
                },
                {
                    // 默认路由：走原 pod
                    Route: []networkingv1.HTTPRouteDestination{
                        {
                            Destination: networkingv1.Destination{
                                Host:   lane.Spec.Service,
                                Subset: "stable",
                            },
                        },
                    },
                },
            },
        },
    }
    return r.applyVS(ctx, vs)
}

// TTL 过期清理
func (r *LaneReconciler) isExpired(lane *lanev1.Lane) bool {
    if lane.Status.LastActiveTime == nil {
        return false
    }
    ttl, _ := time.ParseDuration(lane.Spec.TTL)
    return time.Since(lane.Status.LastActiveTime.Time) > ttl
}
```

### 6.4 VS 优先级 / 顺序

```text
Istio 的 VirtualService 匹配：
  - 多个 VS 作用于同一 host 时，按创建时间排序
  - 同一 VS 内 rule 按 list 顺序
  - 第一个匹配的 rule 胜出

推荐顺序（Operator 生成时按优先级排）：
  1. 高优先级（特殊 user，如 admin）
  2. 普通 user 规则
  3. 默认路由（稳定版本）

实际控制：
  - 用 VS 的 creationTimestamp 排序
  - 老的（先创建）优先
  - 给 admin / 测试用 user 配更早创建的 VS
```

## 七、gRPC 场景的处理

### 7.1 核心问题

```text
HTTP:
  GET /api/v1/users
  X-Lane-User: alice              ← 标准 header

gRPC:
  /myapp.UserService/GetUser
  x-lane-user: alice              ← metadata（小写 key）
  :authority: myapp:50051         ← pseudo header
  :method: POST
```

### 7.2 Istio 的支持

```text
Istio 的 VirtualService 匹配：
  - http[] 段可以匹配 gRPC（Istio 把 gRPC 看作 HTTP/2）
  - headers 匹配对小写 key 大小写不敏感
  - 但 :authority、:method 等 pseudo-header 不能直接匹配
  - x-lane-user 作为普通 header 能匹配
```

### 7.3 gRPC Interceptor 透传

```go
// Go gRPC client interceptor
func LaneUserUnaryClientInterceptor(ctx context.Context, method string, req, reply interface{}, cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {
    user := lane.GetUserFromContext(ctx)
    if user != "" {
        // gRPC metadata 透传
        md, _ := metadata.FromOutgoingContext(ctx)
        md = md.Copy()
        md.Set("x-lane-user", user)
        ctx = metadata.NewOutgoingContext(ctx, md)
    }
    return invoker(ctx, method, req, reply, cc, opts...)
}

// gRPC server interceptor（接收并保存）
func LaneUserUnaryServerInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
    md, _ := metadata.FromIncomingContext(ctx)
    if users := md.Get("x-lane-user"); len(users) > 0 {
        ctx = context.WithValue(ctx, "lane-user", users[0])
    }
    return handler(ctx, req)
}
```

```python
# Python gRPC interceptor
class LaneUserInterceptor(grpc.ServerInterceptor):
    def intercept_service(self, continuation, handler_call_details):
        meta = handler_call_details.invocation_metadata
        user = next((m.value for m in meta if m.key == 'x-lane-user'), None)
        if user:
            # 保存到 context
            pass
        return continuation(handler_call_details)
```

## 八、有状态依赖的取舍

> 标题虽然是"无状态服务"，但实际开发一定会涉及 DB / Redis / 消息队列。

### 8.1 依赖分级

```text
L1：纯计算（无状态）           → 本设计直接解决
L2：读 DB（不写 / 只读）       → dev 共享 dev DB
L3：写 DB（schema 不变）       → dev 共享 dev DB（user 标识）
L4：写 DB（schema 变）         → dev 独立 schema 或 dev DB
L5：写 cache / Redis           → dev 独立 key 前缀
L6：消息队列                  → dev 独立 topic
L7：定时任务 / cron            → dev 关闭 cron
```

### 8.2 推荐方案

```text
L1：lane 解决
L2：dev 共享一个 dev DB
L3：dev pod 写操作时带 user 标识，业务层 / ORM 层自动 WHERE user=?
L4：业务代码改 schema 时配 migration job，按 dev 隔离 schema
L5：Redis key 加 user 前缀（dev.alice:xxx）
L6：Kafka topic 命名加 user 后缀（events.dev.alice）
L7：dev pod 的 cron 关掉
```

### 8.3 不要在 Lane 范围解决

```text
⚠️ 强烈建议把以下放在"开发平台"层而非"lane"层：

  - DB 实例 / schema 管理（用 DBOps 平台）
  - 镜像构建（用 CI/CD 平台）
  - 域名 / 证书（用网关平台）
  - 监控 / 日志（用观测平台）

lane 只做一件事：
  流量路由 + 临时 Pod 生命周期
```

## 十一、完整链路示例

### 11.1 场景

```text
Alice 改了 service X（订单服务）
Bob 改了 service Y（库存服务）

调用链：API Gateway → A → X → Y → DB
- A：API 网关（无人改）
- X：订单（Alice 改）
- Y：库存（Bob 改）
- DB：公共

Alice 调试：
  - Alice dev pod：X-dev-alice
  - Bob dev pod：Y-dev-bob
  - 都在跑

Alice 发请求（X-Lane-User: alice）：
  1. API Gateway → A → 走原（无 lane）
  2. A → X → VS 匹配 user=alice → 走 X-dev-alice ✅
  3. X-dev-alice → Y → 透传 X-Lane-User=alice
     → Y 的 VS：user=alice 但没有 dev-alice 的 Y → 走原 Y
     → 但 Y 的原版本不是 Bob 改的
  4. Y → DB → 走原 DB

Bob 发请求（X-Lane-User: bob）：
  1. API Gateway → A → 走原
  2. A → X → VS：user=bob 没匹配 → 走原 X
  3. 原 X → Y → VS：user=bob 匹配 → 走 Y-dev-bob ✅
  4. Y-dev-bob → DB → 走原 DB

其他人发请求（X-Lane-User: charlie）：
  1. → → → 全部走原（VS 默认 route）
```

### 11.2 关键点

```text
1. Alice 只能验证 X 的改动（Y 走的是原版）
   → 她的 X 改动可能没考虑到 Bob 对 Y 的修改
   → 这是固有限制，不是 bug
   
2. 想完整测试 X + Y 的协同：
   - Alice 需要在 git 仓库拉到 Bob 的 Y 改动
   - 或者在 Bob 没改的版本下测试
   - 或者 Bob 不在时测（没有 dev-bob pod 干扰）

3. 如果需要 A + X + Y 完整链路：
   - Alice 还要起 A 的 dev pod（如果 A 改过）
   - 否则链路中断在某个非 dev 的服务
```

## 十二、风险与降级方案

### 12.1 主要风险

```text
R1: Operator 故障
  → 所有 Lane 失去协调
  → 已有 dev pod 还在跑（不会立即删）
  → 需快速恢复 Operator

R2: VirtualService 写错
  → 流量走错
  → 紧急删除所有 auto VS（命令见 9.4）

R3: dev pod OOM / CrashLoop
  → 资源被吃光
  → ResourceQuota 限制

R4: 链路被某服务的 dev pod 卡住
  → 全链路都受影响
  → dev pod 加 active health check

R5: 数据库污染
  → dev pod 写了脏数据到 dev DB
  → 定期 reset dev DB

R6: 资源超卖
  → 100 dev × 5 pod = 500 pod
  → namespace 配额 + 总配额

R7: 安全问题
  → dev pod 跑恶意代码
  → ResourceQuota + NetworkPolicy + 镜像来源管控
```

### 12.2 降级方案

```text
降级 1：Operator 挂掉
  - dev pod 仍按 K8s 正常调度
  - VS 仍生效（独立资源）
  - 影响：新建 Lane 失败，已有 Lane 正常工作

降级 2：Mesh 挂掉
  - 所有 dev 流量都走默认（用 k8s service 负载均衡）
  - dev pod 还会被调用（按概率）
  - 不可控，业务降级

降级 3：必须停用整套系统
  - 删 Operator Deployment
  - 删所有 auto VS
  - 删所有 dev pod
  - 5 分钟内完成
```

### 12.3 测试用例

```text
T1：单个 dev 走单链路（最简）
T2：多人同时改同服务（VS 合并）
T3：链路中途失败（中间服务没 dev pod）
T4：dev pod 资源耗尽
T5：Operator 重启 / 升级
T6：Istio 升级
T7：网络分区（mesh 部分不可用）
T8：用户切换 user header
```

## 十三、跟传统方案对比

| 维度 | 全套独立 dev 环境 | 共享 dev 环境 | **本设计（Lane）** |
| --- | --- | --- | --- |
| 资源 | 100× | 1× | 1–2× |
| 隔离 | 强 | 弱 | 中 |
| 链路验证 | 完整 | 互相干扰 | 完整 |
| 改一行代码上线测试 | 10 分钟 | 5 分钟 | 30 秒 |
| 适用服务数 | < 5 | > 50 | 任意 |
| 复杂度 | 低 | 低 | 中（要 Operator） |
| 适合团队规模 | < 10 | > 50 | > 20 |

### 适合用 Lane 的场景

```text
✅ 服务数量 > 10
✅ 微服务架构，多个团队协作
✅ 单服务改动多
✅ 资源紧张
✅ 已有 Istio / Service Mesh
✅ 团队有 SRE 能维护 Operator
```

### 不适合用 Lane 的场景

```text
❌ 服务 < 5（直接复制环境）
❌ 没有 Service Mesh（强依赖）
❌ 业务全是 stateful（DB 改动是主战场）
❌ 团队无 K8s / Operator 能力
❌ 业务实时性要求高（每跳 +1ms 不能接受）
```

## 十四、什么时候不适合这套设计

```text
1. 业务改动主要在数据库 schema
   → 重点是 DB 治理，不是流量路由
   
2. 服务依赖复杂，无法用 header 透传
   → 比如大量异步消息、批处理
   
3. 团队还在熟悉 Service Mesh
   → 跑通基础场景后再上 lane
   
4. 业务对性能极度敏感
   → +1ms 都不能接受
   → 建议用 sidecar 模式 + eBPF 优化
   
5. 内部系统 / 一次性服务
   → 投入产出比太低
```

## 十五、一句话总结

> **这套"按 user 路由 + Operator 协调"的设计方向完全正确，本质是"per-user 影子环境"**；
> 落地要补 **Header 注入点 + gRPC 透传 + 资源清理 + 有状态依赖治理 + 可观测性**这 5 块；
> **最大风险是"链路终止条件"——每个 dev 只起自己改的 pod，下游走原 pod，所以验证范围仅限自己改的部分**，
> 想完整链路验证还是要拉通 git + 联合调试。
