# 有状态服务的泳道设计

> 目标：**让有状态服务（DB / Redis / MQ / 本地存储）在多 dev 调试时不互相干扰、不污染数据、能完整链路验证**。
> 适用：MySQL / PostgreSQL / Redis / Kafka / RocketMQ / MongoDB / Elasticsearch / MinIO / 本地盘 / Sidecar 容器。
> 难度：**比无状态高 3-5 倍**，核心难点是"数据隔离"。

## 一、为什么有状态服务的泳道是难题

```text
无状态服务的泳道：
  - 解决"流量"问题
  - 主要靠 Istio + VirtualService 路由
  - 资源消耗可控

有状态服务的泳道：
  - 解决"流量 + 数据 + 状态 + 持久化"4 个问题
  - 流量只是一部分
  - 数据才是核心难点
```

**典型困境**：

```text
场景：Alice 改 order service，要改订单表 schema（加字段）
  - dev pod：alice-order-dev ✅ 容易起
  - DB schema：怎么搞？
    选项 A：用 prod schema → 污染生产数据 💥
    选项 B：每个 dev 一份 DB → 100 dev × 100 GB = 10 TB 💸
    选项 C：共享 dev DB + schema 隔离 → 复杂但可行 ✅
    选项 D：dev pod 用 SQLite 内存 → 丢数据，链路断 ❌
    
场景：Alice 改了消息生产者的格式
  - dev producer 发到 Kafka
  - 同集群的 prod consumer 拿到消息 → 解析失败 💥
  - 必须让 dev 的消息不污染 prod 消费者
  
场景：dev 改了 cache key 的命名
  - dev 写 cache A
  - 旧 pod 读 cache A → 读到 dev 写的脏数据
  - cache 隔离失败
```

**核心区别**：

| 维度 | 无状态 | 有状态 |
| --- | --- | --- |
| 隔离对象 | 流量 + 容器 | 流量 + 容器 + **数据** + **持久化** |
| 资源消耗 | 1×~2× | 2×~10×（数据复制开销） |
| 实现复杂度 | 中 | 高 |
| 链路断点 | 仅 HTTP | HTTP + DB + Cache + MQ + Storage |
| 清理复杂度 | 删 Pod 即可 | 删 Pod + 清数据 + 删 Topic + ... |
| 一致性问题 | 弱一致可接受 | 强一致 / 事务约束 |

## 二、5 大隔离维度

```text
有状态服务的"状态"分布在 5 个地方：
  ┌────────────────────────────────────────────────┐
  │  1. 进程内状态（内存）                          │
  │     例：Java 堆内存里的对象                      │
  │     隔离：进程隔离（Pod 天然隔离）               │
  │                                                │
  │  2. 本地存储（PVC / emptyDir）                  │
  │     例：上传的临时文件                          │
  │     隔离：每 dev 一份 PVC                       │
  │                                                │
  │  3. 中间件（DB / Cache / MQ）                   │
  │     例：MySQL / Redis / Kafka                   │
  │     隔离：实例隔离 / 命名空间隔离 / Schema 隔离  │
  │                                                │
  │  4. 外部存储（S3 / OSS / MinIO）                │
  │     例：用户头像、文件                          │
  │     隔离：bucket 前缀 / 独立 bucket              │
  │                                                │
  │  5. 跨服务共享状态                              │
  │     例：分布式锁、分布式 ID、配置中心            │
  │     隔离：namespace / key prefix                │
  └────────────────────────────────────────────────┘
```

每种状态对应不同的隔离方案，详见后续章节。

## 三、隔离方案全景对比

### 3.1 4 种隔离强度

| 方案 | 隔离强度 | 资源消耗 | 复杂度 | 适合 |
| --- | --- | --- | --- | --- |
| **共享实例 + 命名空间隔离** | 弱 | 1× | 低 | 团队少、改动小 |
| **共享实例 + Schema 隔离** | 中 | 1.2× | 中 | 中型团队、DB schema 稳定 |
| **共享实例 + 库隔离**（每 dev 一库） | 强 | 5×~20× | 中 | 重要业务 |
| **完全独立实例**（每 dev 一套 DB） | 最强 | 10×~50× | 高 | 金融 / 强合规 |

### 3.2 决策树

```text
是否需要 dev 完全独立数据？
  │
  ├─ 是 → 完全独立实例（每 dev 一套）
  │       资源成本 ×10
  │       适合：金融 / 合规
  │
  └─ 否 → dev 共享 dev 实例，逻辑隔离
          │
          ├─ DB schema 经常变？
          │   ├─ 是 → 每 dev 一 schema
          │   └─ 否 → 共享 schema，按 user_id WHERE
          │
          ├─ 有大对象 / 文件？
          │   ├─ 是 → 每 dev 一 bucket
          │   └─ 否 → 共享 bucket，prefix 隔离
          │
          └─ 有消息？
              ├─ 是 → 每 dev 一 topic
              └─ 否 → 共享 topic，按 header 过滤
```

## 四、数据库的泳道设计（MySQL / PG）

### 4.1 方案 A：共享 dev 实例 + Schema 隔离（推荐）

```text
架构：
  prod-mysql（生产，生产数据，绝对不动）
  dev-mysql（共享 dev 实例）
    ├─ schema: order_base                    # 基础 schema
    ├─ schema: order_alice                   # Alice 的改动
    ├─ schema: order_bob                     # Bob 的改动
    └─ schema: order_charlie                 # Charlie 的改动

dev pod 配置：
  - DB_HOST=dev-mysql
  - DB_NAME=order_alice                     # dev pod 用自己的 schema
  - DB_USER=order_alice
  - DB_PASSWORD=<per-user secret>

迁移工具（Flyway / Liquibase / Alembic）：
  - dev pod 启动时跑 migration 到 order_alice schema
  - 不影响 order_bob / order_base
```

**CRD 设计**：

```yaml
apiVersion: lane.dev/v1
kind: Lane
metadata:
  name: alice-order
spec:
  user: alice
  service: order
  image: myregistry/order:abc123
  
  # 新增：有状态依赖声明
  statefulDeps:
    - type: mysql
      host: dev-mysql.lane-system.svc
      baseSchema: order_base                 # 基础 schema
      userSchema: order_alice                # 当前 dev 的 schema
      migration: |
        CREATE TABLE order_items (
          id BIGINT PRIMARY KEY,
          name VARCHAR(255)
        );
        ALTER TABLE orders ADD COLUMN discount DECIMAL(10,2);
      strategy: schema-per-user              # 隔离策略
      ttl: "24h"
    
    - type: redis
      host: dev-redis.lane-system.svc
      keyPrefix: "lane:alice:"               # Redis key 前缀
      strategy: prefix-per-user
      
    - type: kafka
      brokers: dev-kafka.lane-system.svc:9092
      topicPrefix: "lane.alice."             # topic 前缀
      consumerGroupPrefix: "lane.alice."
      strategy: prefix-per-user
```

**Operator 职责**：

```go
// StatefulDepReconciler 协调有状态依赖
func (r *StatefulDepReconciler) Reconcile(ctx context.Context, lane *Lane) error {
    for _, dep := range lane.Spec.StatefulDeps {
        switch dep.Type {
        case "mysql":
            // 1. 创建 user schema（如果不存在）
            if err := r.createMySQLSchema(ctx, dep); err != nil {
                return err
            }
            // 2. 跑 migration（按 user）
            if err := r.runMySQLMigration(ctx, dep); err != nil {
                return err
            }
            // 3. 设置 dev pod 的环境变量
            if err := r.injectEnvVars(ctx, lane, dep); err != nil {
                return err
            }
        case "redis":
            // Redis 不需要预创建，dev pod 启动时用 prefix
            r.injectRedisPrefix(ctx, lane, dep)
        case "kafka":
            // 创建 topic
            r.createKafkaTopics(ctx, dep)
        }
    }
    return nil
}

func (r *StatefulDepReconciler) createMySQLSchema(ctx context.Context, dep *StatefulDep) error {
    db, _ := sql.Open("mysql", dep.AdminDSN)
    defer db.Close()
    
    // CREATE DATABASE IF NOT EXISTS order_alice
    _, err := db.Exec(fmt.Sprintf(
        "CREATE DATABASE IF NOT EXISTS `%s` CHARACTER SET utf8mb4",
        dep.UserSchema,
    ))
    return err
}

func (r *StatefulDepReconciler) runMySQLMigration(ctx context.Context, dep *StatefulDep) error {
    // 1. 基础 schema 作为模板（从 prod 导出的 dump）
    // 2. 在 user schema 上跑 migration
    cmd := exec.CommandContext(ctx, "flyway",
        "-url=" + dep.UserDSN,
        "-locations=filesystem:/migrations",
        "migrate",
    )
    return cmd.Run()
}
```

### 4.2 方案 B：共享 dev 实例 + 库隔离（次推荐）

```text
架构：
  dev-mysql
    ├─ order_alice        # Alice 一整个库
    ├─ order_bob          # Bob 一整个库
    └─ inventory_shared   # 共享库（没人改）

特点：
  - 库名 = user + 服务名
  - dev pod 配 DB_NAME=order_alice
  - migration 跑在自己的库里
  - 资源：N 用户 × N 服务 × 平均库大小
```

### 4.3 方案 C：完全独立实例（金融 / 合规场景）

```text
架构：
  - dev-mysql-alice.lane-system.svc:3306   # Alice 独占实例
  - dev-mysql-bob.lane-system.svc:3306     # Bob 独占实例
  
每个实例：
  - 一套完整 schema
  - 可以随便 drop / create
  - 资源成本 ×10~50
  - 启动慢（DB 起来 30 秒）

实现：
  - StatefulSet 动态创建
  - Operator 监听 Lane CR → 创建对应 DB StatefulSet
  - 数据卷用 PVC（每 dev 一份）
  - idle 时缩容到 0（保留 PVC）
```

### 4.4 方案 D：影子表 / 影子库（生产级方案）

```text
影子库（database replication）：

  prod-mysql → 复制 → shadow-mysql-alice
                                    ↓
                              Alice dev pod 读写这里
                              完全不影响 prod

实现：
  - 用 mysqlbinlog / pg_logical 同步
  - dev pod 启动时从 shadow 复制
  - 成本：存储 + 同步开销

适合：
  - 金融 / 强合规
  - 需要真实数据测试
  - 不能容忍 schema 变更影响
```

### 4.5 Schema 隔离的细节

```sql
-- 1. 创建 user schema（基于 prod schema）
CREATE DATABASE `order_alice` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 2. 复制基础表结构
mysqldump --no-data prod_order | mysql order_alice;

-- 3. dev pod 跑 migration（只在自己的 schema）
USE order_alice;
ALTER TABLE orders ADD COLUMN discount DECIMAL(10,2);

-- 4. 业务代码无感知（DB_NAME 环境变量切换）
--    app 内全部 SQL 走 ORM，ORM 读 DB_NAME
```

**权限隔离**：

```sql
-- 每个 dev 一个 MySQL 用户
CREATE USER 'order_alice'@'%' IDENTIFIED BY 'random_password';
GRANT ALL PRIVILEGES ON `order_alice`.* TO 'order_alice'@'%';

-- 不能访问其他人的 schema
-- 不能访问 prod_* schema
```

### 4.6 数据初始化 / 种子数据

```yaml
# Lane CR 字段
spec:
  statefulDeps:
    - type: mysql
      seed:
        strategy: copy-from-base
        sourceSchema: order_base              # 从基础 schema 复制种子
        tables:                               # 只复制这些表
          - orders
          - products
          - users
        anonymize: true                       # 用户名 / 手机号脱敏
      # 或者
      seed:
        strategy: synthetic                   # 用 faker 生成
        rowsPerTable:
          orders: 1000
          users: 100
```

**脱敏示例**（faker / Python）：


## 五、缓存的泳道设计（Redis）

### 5.1 三种隔离策略

```text
策略 1：key 前缀隔离（最常用）
  prod: order:123 → {prod value}
  alice: order:123 → {alice dev value}
  
  实现：dev pod 配置 keyPrefix=lane:alice:
  业务代码无感知（Redis client 包一层）

策略 2：DB 号隔离（Redis 多 DB）
  db 0 = prod
  db 1 = alice dev
  db 2 = bob dev
  
  实现：SELECT 1
  
策略 3：独立实例
  - 完全隔离
  - 资源消耗大
```

### 5.2 推荐方案：key 前缀 + 透明代理

```go
// Redis Client Wrapper（自动加前缀）
type LaneRedisClient struct {
    client  *redis.Client
    prefix  string                  // "lane:alice:"
}

func (c *LaneRedisClient) Get(ctx context.Context, key string) (string, error) {
    return c.client.Get(ctx, c.prefix+key).Result()
}

func (c *LaneRedisClient) Set(ctx context.Context, key string, value string, ttl time.Duration) error {
    return c.client.Set(ctx, c.prefix+key, value, ttl).Err()
}

// SCAN 时过滤前缀
func (c *LaneRedisClient) Scan(ctx context.Context, cursor uint64, match string, count int64) ([]string, error) {
    keys, cursor, err := c.client.Scan(ctx, cursor, c.prefix+match, count).Result()
    // 去掉前缀返回
    for i, k := range keys {
        keys[i] = strings.TrimPrefix(k, c.prefix)
    }
    return keys, cursor, err
}
```

### 5.3 Cluster 模式下的处理

```text
Redis Cluster 共享一个集群：
  - dev pod 连同一个 cluster
  - 但 key 前缀必须用 hash tag
  
  例子：
    prod: {order}:123 → slot 5000
    alice: {lane:alice:order}:123 → slot 5000
    
  为什么：
    - Cluster 按 key 分布到不同节点
    - 没 hash tag 的话，前缀和原 key 散到不同 slot
    - 用 {} 把前缀包起来，整个 key 走同一 slot
    - MGET / pipeline 才有效
    
  配置：
    keyPrefix: "{lane:alice:}"       # 带 hash tag
```

### 5.4 缓存击穿的防护

```text
场景：dev pod 的 cache 大量 miss
  - dev pod 用新 key 格式
  - 原 key 不命中
  - 全部请求穿透到 DB
  - DB 压力暴增

解决：
  - dev pod 用本地缓存（不查 prod Redis）
  - 或者 dev pod 不依赖 prod cache（独立 cache 实例）
  - 或者限流（dev 入口限流）
```

## 六、消息队列的泳道设计（Kafka / RocketMQ）

### 6.1 隔离挑战

```text
场景：dev producer 发消息到 prod topic
  - prod consumer 收到 dev 消息
  - 解析失败 / 数据污染 💥
  
场景：dev consumer 从 prod topic 读消息
  - 读到 prod 消息
  - dev 流程跑通但用了真实数据
  - 测试不准
  
必须隔离：topic + consumer group + producer 路由
```

### 6.2 Kafka 隔离方案

```text
策略 1：每 dev 一套 topic
  prod: order-events
  alice: lane.alice.order-events
  bob: lane.bob.order-events
  
  producer：dev pod 发到 lane.alice.order-events
  consumer：dev consumer 订阅 lane.alice.order-events
  
策略 2：共享 topic + header 过滤
  topic: order-events（共享）
  header: x-lane-user=alice
  
  producer：写消息时加 header
  consumer：dev consumer 过滤 header == alice
  
策略 3：完全隔离 cluster（重）
```

### 6.3 推荐方案：每 dev 一套 topic（自动化）

```yaml
# Lane CR
spec:
  statefulDeps:
    - type: kafka
      brokers: dev-kafka.lane-system.svc:9092
      topics:
        - nameTemplate: "lane.alice.{originalName}"
        - original: "order-events"
          user: "alice"
          result: "lane.alice.order-events"
      consumerGroupTemplate: "lane.alice.{originalGroup}"
```

**Operator 创建 topic**：

```go
func (r *StatefulDepReconciler) createKafkaTopics(ctx context.Context, dep *KafkaDep, user string) error {
    admin := kafka.NewAdminClient(...)
    defer admin.Close()
    
    topics := []kafka.TopicSpecification{}
    for _, t := range dep.Topics {
        userTopic := strings.ReplaceAll(t.NameTemplate, "{originalName}", t.Original)
        userTopic = strings.ReplaceAll(userTopic, "{user}", user)
        
        topics = append(topics, kafka.TopicSpecification{
            Topic:             userTopic,
            NumPartitions:     t.Partitions,
            ReplicationFactor: 1,                    // dev 环境
        })
    }
    
    return admin.CreateTopics(ctx, topics...)
}
```

### 6.4 生产者路由

```go
// Kafka Producer 自动加 topic prefix
type LaneKafkaProducer struct {
    producer *kafka.Producer
    topicMap map[string]string              // 原 topic → user topic
}

func (p *LaneKafkaProducer) Send(originalTopic string, msg *Message) error {
    userTopic, ok := p.topicMap[originalTopic]
    if !ok {
        return fmt.Errorf("topic %s not configured", originalTopic)
    }
    
    // 加 header（用于 trace）
    msg.Headers = append(msg.Headers, kafka.Header{
        Key: "x-lane-user", Value: []byte(p.user),
    })
    
    return p.producer.Produce(&kafka.Message{
        Topic: userTopic,
        Value: msg.Value,
        Headers: msg.Headers,
    }, nil)
}
```

### 6.5 消费者路由

```go
// Kafka Consumer 订阅 user topic
type LaneKafkaConsumer struct {
    consumer *kafka.Consumer
    user     string
}

func NewLaneKafkaConsumer(user string, brokers []string) *LaneKafkaConsumer {
    c, _ := kafka.NewConsumer(&kafka.ConfigMap{
        "bootstrap.servers": strings.Join(brokers, ","),
        "group.id":          fmt.Sprintf("lane.%s.%s", user, appName),
    })
    return &LaneKafkaConsumer{consumer: c, user: user}
}

func (c *LaneKafkaConsumer) Subscribe(originalTopics []string) {
    userTopics := []string{}
    for _, t := range originalTopics {
        userTopics = append(userTopics, fmt.Sprintf("lane.%s.%s", c.user, t))
    }
    c.consumer.SubscribeTopics(userTopics, nil)
}
```

### 6.6 RocketMQ 的差异

```text
RocketMQ 隔离：
  - topic 隔离 + group 隔离
  - 但 RocketMQ 4.x 的 topic 创建需要人工
  - 用 RocketMQ 5.x 的 Proxy 模式（topic 自动创建）
  - 或者预先创建一批 dev topic（lane.user1.order、lane.user2.order...）
```

## 七、对象存储的泳道设计（MinIO / S3）

### 7.1 隔离策略

```text
策略 1：bucket 前缀（路径隔离）
  prod: s3://myapp/avatars/123.jpg
  alice: s3://myapp/lane/alice/avatars/123.jpg
  
策略 2：独立 bucket
  prod: s3://myapp-prod
  alice: s3://myapp-alice-dev
  
策略 3：独立 MinIO 实例
  - 完全隔离
  - 资源消耗大
```

### 7.2 推荐：bucket 前缀

```go
// S3 Client Wrapper
type LaneS3Client struct {
    client *s3.Client
    prefix string                                  // "lane/alice/"
    bucket string
}

func (c *LaneS3Client) GetObject(ctx context.Context, key string) (*s3.GetObjectOutput, error) {
    return c.client.GetObject(ctx, &s3.GetObjectInput{
        Bucket: aws.String(c.bucket),
        Key:    aws.String(c.prefix + key),
    })
}

func (c *LaneS3Client) PutObject(ctx context.Context, key string, body io.Reader) error {
    _, err := c.client.PutObject(ctx, &s3.PutObjectInput{
        Bucket: aws.String(c.bucket),
        Key:    aws.String(c.prefix + key),
        Body:   body,
    })
    return err
}

func (c *LaneS3Client) ListObjects(ctx context.Context, prefix string) ([]string, error) {
    out, _ := c.client.ListObjectsV2(ctx, &s3.ListObjectsV2Input{
        Bucket: aws.String(c.bucket),
        Prefix: c.prefix + prefix,
    })
    keys := []string{}
    for _, obj := range out.Contents {
        keys = append(keys, strings.TrimPrefix(*obj.Key, c.prefix))
    }
    return keys, nil
}
```

```go
func (r *StatefulDepReconciler) createPVC(ctx context.Context, lane *Lane, dep *PVCDep) error {
    pvcName := fmt.Sprintf("%s-%s-%s", lane.Spec.Service, lane.Spec.User, dep.Name)
    
    pvc := &corev1.PersistentVolumeClaim{
        ObjectMeta: metav1.ObjectMeta{
            Name:      pvcName,
            Namespace: lane.Namespace,

                Requests: corev1.ResourceList{

            },
        },
    }

}
```

```go
// 协调多个 dep
type StatefulDepReconciler struct {
    client.Client
    mysql    MySQLProvisioner
    redis    RedisProvisioner
    kafka    KafkaProvisioner
    s3       S3Provisioner
}

func (r *StatefulDepReconciler) ReconcileAll(ctx context.Context, lane *Lane) error {
    for _, dep := range lane.Spec.StatefulDeps {
        switch dep.Type {
        case "mysql":
            if err := r.mysql.Provision(ctx, dep, lane.Spec.User); err != nil {
                return fmt.Errorf("mysql provision: %w", err)
            }
        case "redis":
            if err := r.redis.Configure(ctx, dep, lane.Spec.User); err != nil {
                return fmt.Errorf("redis configure: %w", err)
            }
        case "kafka":
            if err := r.kafka.CreateTopics(ctx, dep, lane.Spec.User); err != nil {
                return fmt.Errorf("kafka topics: %w", err)
            }
        case "s3":
            if err := r.s3.CreatePrefix(ctx, dep, lane.Spec.User); err != nil {
                return fmt.Errorf("s3 prefix: %w", err)
            }
        case "pvc":
            if err := r.createPVC(ctx, lane, dep); err != nil {
                return fmt.Errorf("pvc: %w", err)
            }
        }
    }
    
    // 全部成功后才注入到 Pod
    return r.injectEnvVars(ctx, lane)
}
```

## 十一、数据生命周期管理

### 11.1 三层 TTL

```text
L1: Lane TTL（默认 8h）
  - dev pod 生命周期
  - pod 删了就不写新数据
  
L2: StatefulDep TTL（默认 24h）
  - DB / Redis / Kafka 数据生命周期
  - 比 Lane TTL 长，给 dev 回来"复活"的机会
  
L3: 归档 TTL（默认 7 天）
  - 删除前的最后机会
  - 用 PVC / 备份保留
  - 7 天后真删
```

### 11.2 清理策略

### 11.3 清理工具

```go
type Cleaner interface {
    Clean(ctx context.Context, user string, lane string) error
}

// MySQL Cleaner
type MySQLCleaner struct {
    db *sql.DB
}

func (c *MySQLCleaner) Clean(ctx context.Context, user string, lane string) error {
    schemaName := fmt.Sprintf("%s_%s", lane, user)
    
    // 1. 归档（mysqldump）
    cmd := exec.CommandContext(ctx, "mysqldump",
        "--single-transaction",
        "--routines",
        schemaName,
    )
    archive, _ := cmd.Output()
    
    s3.PutObject(ctx, "backup/lanes/"+user+"/"+lane+".sql", archive)
    
    // 2. 删除 schema
    _, err := c.db.Exec(fmt.Sprintf("DROP DATABASE `%s`", schemaName))
    return err
}

// Redis Cleaner
func (c *RedisCleaner) Clean(ctx context.Context, user string, lane string) error {
    pattern := fmt.Sprintf("lane:%s:%s:*", user, lane)
    
    iter := c.client.Scan(ctx, 0, pattern, 100).Iterator()
    keys := []string{}
    for iter.Next(ctx) {
        keys = append(keys, iter.Val())
        if len(keys) >= 1000 {
            c.client.Del(ctx, keys...)
            keys = keys[:0]
        }
    }
    if len(keys) > 0 {
        c.client.Del(ctx, keys...)
    }
    return iter.Err()
}

// Kafka Cleaner
func (c *KafkaCleaner) Clean(ctx context.Context, user string, lane string) error {
    admin := kafka.NewAdminClient(...)
    defer admin.Close()
    
    topics := []string{
        fmt.Sprintf("lane.%s.%s.>", user, lane),
    }
    
    _, err := admin.DeleteTopics(ctx, topics...)
    return err
}
```

## 十二、迁移 / Schema 变更的泳道处理

### 12.1 Schema 变更流程

```text
Alice 改了 order 表，加 discount 字段：
  1. Alice 在本地开发
  2. CI 跑 migration → 失败（dev schema 已是新结构）
  3. CI 跑 migration → 成功（dev schema 升级到新结构）
  4. Alice dev pod 启动 → 用新 schema
  5. 测试通过 → 提 PR
  6. PR 合到 develop → 触发集成环境 migration
  7. 集成环境跑新 schema + 新代码
  8. 通过 → 发 release
  
泳道里的特殊处理：
  - 每个 dev 的 schema 是独立的
  - migration 在自己的 schema 上跑
  - 不影响其他 dev
```

### 12.2 冲突 Schema 的处理

```text
场景：Alice 加 discount 字段，Bob 加 tax 字段
  - 都改 orders 表
  - 不同字段，不冲突 → OK
  
场景：Alice 加 discount，Bob 也加 discount（不同类型）
  - 冲突 → 报错
  - 解决：先合一个，另一个 rebase
  
Flyway / Liquibase 的版本管理能帮：
  - V1__add_user.sql
  - V2__add_discount.sql（Alice）
  - V3__add_tax.sql（Bob）
  - 合并到 develop → V1+V2+V3 顺序执行
```

### 12.3 Migration 工具集成

```yaml
        baselineOnMigrate: true            # 已有 schema 也跑
```

## 十三、性能 / 资源问题

### 13.1 资源消耗估算

```text
100 dev × 5 服务 × 5 个有状态依赖 = 2500 个 dep 实例

共享方案资源：
  - 1 个 dev MySQL 实例：4C / 16G / 100GB
  - 100 个 schema 共用
  - CPU: 100 × 0.1 = 10 cores
  - 内存: 100 × 0.1 = 10 GB
  - 存储: 100 × 1 GB schema = 100 GB
  
独立方案资源：
  - 100 个 MySQL 实例 × 0.5C / 2G / 1GB
  - CPU: 50 cores
  - 内存: 200 GB
  - 存储: 100 GB（独立）
  
差异：内存 ×20
```

### 13.2 共享实例的性能隔离

```text
担心：一个 dev 的慢查询拖垮整库

解决：
  1. MySQL Resource Governor（5.7+）限制每 schema 的 CPU
  2. 连接数限制
     CREATE USER 'order_alice'@'%' WITH MAX_USER_CONNECTIONS 10;
  3. slow query 监控 + 自动 kill
     SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND = 'Query' AND time > 30;
  4. dev 实例和生产实例物理分离
```

## 十五、常见反模式

### 15.1 反模式 1：dev 直接连生产 DB

```text
❌ 错误：
  - dev pod 用 prod-mysql 凭据
  - dev 跑 migration 到 prod
  - 污染生产 💥
  
✅ 正确：
  - dev pod 强制用 dev-mysql
  - 用 NetworkPolicy 隔离
  - 用不同 Secret
```

### 15.2 反模式 2：100 dev × 独立 MySQL 实例

```text
❌ 错误：
  - 每个 dev 一套完整 DB
  - 100 个 MySQL StatefulSet
  - 资源爆炸
  - 启动慢
  
✅ 正确：
  - 共享 dev MySQL + schema 隔离
  - 资源消耗可控
```

### 15.3 反模式 3：忽略消息队列隔离

```text
❌ 错误：
  - dev producer 发到 prod topic
  - prod consumer 收到 dev 消息
  - 解析失败 / 数据污染
  
✅ 正确：
  - dev topic + dev consumer group
  - header 过滤
  - Producer 自动包装
```

### 15.4 反模式 4：cache key 不隔离

```text
❌ 错误：
  - dev pod 直接用 prod Redis
  - 写同一个 key
  - 污染 prod cache
  - 旧 pod 读到 dev 写的脏数据
  
✅ 正确：
  - key prefix 隔离
  - 或者 dev 用独立 Redis 实例
```

### 15.5 反模式 5：dev 写文件不隔离

```text
❌ 错误：
  - dev pod 用宿主机目录（hostPath）
  - 多个 dev 共享同一个目录
  - 文件互相覆盖
  
✅ 正确：
  - 用 PVC（每 dev 一份）
  - 或者 emptyDir（临时）
```

### 15.6 反模式 6：dev 数据不清理

```text
❌ 错误：
  - dev pod 删了，schema / topic / S3 留着
  - 100 dev × 长期累积 = 资源泄漏
  
✅ 正确：
  - TTL 到期自动清理
  - OwnerReference 级联删除
  - 定期 GC
```

### 15.7 反模式 7：dev 数据备份到 prod

```text
❌ 错误：
  - dev 跑 migration 顺便 "dump 一份 prod 数据"
  - 写入 dev schema
  - 违反合规
  
✅ 正确：
  - 用 anonymized synthetic data
  - 或者影子库（合规审计）
  - 永远不要 prod 数据进 dev
```

## 十六、什么时候不适合有状态泳道

```text
1. 业务改动几乎全在 DB schema
   → 应该做 DB migration 平台，不是 lane
   → Flyway / Liquibase 的 staging 环境够用

2. 数据合规要求极高（金融、医疗）
   → 影子库 + 合规审计
   → 不允许共享 dev DB

3. 团队完全没用 K8s
   → 投入产出比太低
   → 用传统 dev DB + dbmate / sqlx 工具

4. 业务完全没有 DB
   → 纯计算服务
   → 不需要这一章

5. 团队没有 SRE 维护 Operator
   → Lane + StatefulDep Operator 复杂度高
   → 需要懂 DB / Redis / Kafka 各种工具
```

## 十七、一句话总结

> **有状态服务的泳道本质是"数据隔离"**，5 个隔离维度（进程 / 本地盘 / 中间件 / 外部存储 / 共享状态）；
> **DB 用 schema-per-user + migration 自动化**、**Redis 用 key 前缀 + hash tag**、**Kafka 用 topic-per-user + header 透传**、**S3 用 bucket prefix**；
> **核心难点是资源成本 + 数据一致性 + 合规**，推荐 80% 场景用"共享 dev 实例 + Schema 隔离"，金融/合规用"影子库 + 完全独立实例"；
> **不要让 dev 直接连生产 DB**，必须 NetworkPolicy + Secret 隔离，否则一次污染就是事故。
