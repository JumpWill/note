# 分支管理规范

> 目标：**用统一的分支命名 + 生命周期规则，让代码合并、发布、回滚都清晰可控**。
> 适用：公司内部研发团队（5-100 人规模），微服务 + 多环境部署。

## 一、为什么需要分支规范

```text
没有规范的团队：
  - 分支名乱：fix / new / test / aaa / 最终版本_final_v3
  - 主干脏：dev 分支有 50 个 PR 没合
  - 不知道哪个分支对应哪个环境
  - 发版时手忙脚乱，hotfix 不知道从哪拉

有规范的团队：
  - 看名字知道这个分支干嘛的、给谁用、什么时候删
  - 自动化工具能直接识别分支类型（CI/CD、自动化部署）
  - 主干永远可发布
  - 回滚、hotfix、灰度都有章可循
```

**核心收益**：

| 维度 | 收益 |
| --- | --- |
| **可读性** | 看名字知道分支用途 |
| **可自动化** | CI/CD / GitOps 能直接匹配规则 |
| **可追溯** | 每个环境、每次发版都能 trace 到分支 |
| **可治理** | 批量清理 / 审计 / 权限控制有依据 |
| **降低沟通成本** | 不需要问"这个分支干嘛的" |

## 二、分支命名约定

### 2.1 通用格式

```text
<type>/<scope>-<short-desc>[-<ticket-id>]

示例：
  feature/user-login-LOGIN-1234
  bugfix/order-duplicate-ORDER-567
  hotfix/payment-timeout-PAY-890
  release/v1.2.0
```

### 2.2 类型枚举

| 类型 | 用途 | 生命周期 | 是否合并主干 |
| --- | --- | --- | --- |
| `master` / `main` | 主干（生产代码） | 长期 | 一切最终汇入这里 |
| `develop` | 主开发分支 | 长期 | 一切 feature 最终汇入这里 |
| `release/*` | 发版分支 | 短期（几天） | 合并到 master + develop |
| `feature/*` | 功能开发 | 短期（1-2 周） | 合并到 develop |
| `bugfix/*` | 普通 bug 修复 | 短期（1-3 天） | 合并到 develop |
| `hotfix/*` | 紧急修复 | 极短（小时级） | 合并到 master + develop |
| `experiment/*` | 实验性 | 短期（几天） | 一般不合并 / 看结果 |
| `refactor/*` | 重构 | 短期（1-2 周） | 合并到 develop |
| `docs/*` | 文档 | 短期（1-3 天） | 合并到 develop |
| `chore/*` | 杂事（依赖升级等） | 短期（1-2 天） | 合并到 develop |

### 2.3 命名规则

```text
✅ 推荐：
  feature/login-with-wechat
  bugfix/order-cancel-status
  hotfix/payment-double-charge-PAY-890
  release/v2024-03-15

❌ 不推荐：
  fix                  # 太泛
  new                  # 没意义
  test                 # 看不出改什么
  最终版本             # 中文 / 无类型
  我的修改             # 主观命名
  john_branch          # 私人分支不该长期存在
```

### 2.4 长度 / 字符限制

```text
- 全小写（除 ticket ID）
- 单词用 - 连接，不用 _ 或空格
- 总长不超过 60 字符
- 不含敏感信息（密码、密钥）
- 不含 emoji / 中文 / 特殊符号
```

## 三、核心分支（长期存在）

### 3.1 master / main

```text
作用：生产环境的代码源（神圣不可侵犯）
状态：永远可发布（每次合并必须 CI 全绿）
权限：
  - 直接 push：禁止
  - 合并：仅 Release Manager + Code Owner
  - tag：每个 release 都要打 tag（v1.2.0）

保护规则：
  - 禁止 force push
  - 禁止删除
  - 禁止直接 push（必须 PR）
  - 必须 ≥ 2 人 approve
  - 必须 status check 全绿
```

### 3.2 develop

```text
作用：集成分支，所有 feature 最终汇入这里
状态：随时可发版（每晚从 develop 跑 staging）
权限：
  - 直接 push：禁止
  - 合并：开发者本人即可（自己 feature → develop）

特点：
  - 永远比 master 领先
  - 永远包含下一个 release 的所有 feature
  - 可能有未完成 feature（被 feature flag 控制）
```

### 3.3 master vs develop（经典 Git Flow）

```text
master  ──●─────────────────●─────────────●────  (生产)
          │                 │             │
          │                 │ release/v1  │
          │                 ▼             │
develop ──●──●──●──●──●──●──●──●──●──●──●──  (开发)
          │  │  │  │
          │  │  │  └─ feature/c
          │  │  └─ feature/b
          │  └─ feature/a
          └─ init
```

## 四、工作分支（短期存在）

### 4.1 feature/*

```text
作用：单个功能开发
来源：develop
目标：develop
生命周期：1-2 周
命名：feature/<scope>-<short-desc>[-<ticket>]

示例：
  feature/user-profile-avatar-UP-123
  feature/payment-stripe-integration
  feature/order-export-excel

规则：
  - 必须有对应 ticket（JIRA / 飞书任务）
  - 完成后删源分支
  - 不要在 feature 上嵌套 feature
  - 每周至少 rebase / merge develop 一次（避免长期冲突）

触发 CI：
  - 自动跑单元测试 + lint
  - 自动部署到"开发者预览环境"
  - 不触发 staging / prod
```

### 4.2 bugfix/*

```text
作用：测试阶段 / staging 阶段发现的 bug 修复
来源：develop
目标：develop
生命周期：1-3 天
命名：bugfix/<scope>-<short-desc>[-<ticket>]

与 feature 的区别：
  - bugfix 是修 bug，feature 是加功能
  - 实际上 git 操作一致

示例：
  bugfix/order-duplicate-submission-ORDER-567
  bugfix/login-captcha-missing
```

### 4.3 hotfix/*

```text
作用：线上紧急 bug 修复（生产事故）
来源：master
目标：master + develop（同步）
生命周期：小时级（必须快）
命名：hotfix/<scope>-<short-desc>[-<ticket>]

流程：
  1. 从 master 拉 hotfix/payment-timeout
  2. 修完 → 提 PR 到 master
  3. master CI + 紧急验证
  4. 直接发布（不等 release 周期）
  5. master 合并完成后 → 反向同步到 develop
  6. tag：v1.2.1（递增补丁号）

特点：
  - 必须 1 小时内完成
  - 至少 2 人 review
  - 不允许在 hotfix 上开发新功能
  - 必须有完整回滚方案

⚠️ 反模式：在 hotfix 上加新功能 → 下次 release 会带 N 个无关改动
```

### 4.4 release/*

```text
作用：发版准备（冻结代码、做最后的 bug 修复）
来源：develop
目标：master + develop
生命周期：几天到 2 周
命名：release/v<version> 或 release/<release-date>

示例：
  release/v1.2.0
  release/v2024-03-15
  release/2024Q1

流程：
  1. develop 状态稳定 → 从 develop 拉 release/v1.2.0
  2. release 分支只修 bug，不加 feature
  3. release 分支测试通过 → 合并到 master
  4. master 打 tag：v1.2.0
  5. 立即合并回 develop（同步 bug 修复）

好处：
  - master 始终干净（只有 release 合并）
  - develop 可以继续接新 feature（不被发版阻塞）
  - 出问题时快速定位（master 只有 release 节点）
```

## 五、辅助分支（场景化）

### 5.1 experiment/*

```text
作用：实验性 / spike 性质（A/B 试、技术预研）
来源：develop 或独立
目标：一般不合并 / 看结果决定
生命周期：几天到 2 周

命名：
  experiment/<topic>-<hypothesis>
  experiment/redis-vs-pulsar-cache
  experiment/microservice-vs-monolith

特点：
  - 可能产生大量 commits
  - 不一定能跑通
  - 完成后由 team 决定：
    - 抛弃（删分支）
    - 提炼成 feature/* 重做
    - 直接合并（实验结果好）
```

### 5.2 refactor/*

```text
作用：纯重构（不改行为）
来源：develop
目标：develop
命名：refactor/<scope>-<what>

示例：
  refactor/user-service-split-by-domain
  refactor/order-db-sharding
  refactor/payment-state-machine

规则：
  - 必须有完整测试覆盖（重构前提）
  - 不改对外接口
  - 不改业务行为
  - PR description 写清"前后等价"证明
```

### 5.3 docs/*

```text
作用：仅改文档
来源：develop
目标：develop
命名：docs/<topic>

示例：
  docs/update-readme
  docs/api-documentation
  docs/architecture-decision-record
```

### 5.4 chore/*

```text
作用：杂事（依赖升级、配置变更、CI 调整）
来源：develop
目标：develop
命名：chore/<what>

示例：
  chore/upgrade-go-1.22
  chore/ci-cache-config
  chore/deps-bump-secure
  chore/k8s-manifest-update
```

### 5.5 个人实验分支

```text
作用：开发者本地实验
命名：<username>/<topic>
     alice/try-new-orm

特点：
  - 长期存在没关系
  - 不强制清理
  - 不参与合并（除非升格为 feature/*）
```

## 六、完整生命周期图

### 6.1 Git Flow 完整示意

```text
master    ─●─────────────●────●─────────────●──────●───  (生产)
           │             │    │             │      │
           │  hotfix/v1.2.1  │   │   release/v1.3.0 │
           │             │    │             │      │
           ▼             │    ▼             ▼      │
hotfix    ●──fix──●──────┘    │            ●────●──┘
                              │           bug fix only
                              │
develop    ─●──●──●──●──●──●──●──●──●──●──●──●──●───  (开发)
           │  │  │  │  │  │  │  │  │  │
           │  │  │  │  │  │  │  │  │  └─ feature/h
           │  │  │  │  │  │  │  │  └─ feature/g
           │  │  │  │  │  │  │  └─ feature/f
           │  │  │  │  │  │  └─ feature/e
           │  │  │  │  │  └─ bugfix/d
           │  │  │  │  └─ feature/c
           │  │  │  └─ feature/b
           │  │  └─ feature/a
           │  └─ init
```

### 6.2 Trunk-Based（推荐小型团队）

```text
master    ─●──●──●──●──●──●──●──●──●──●──●──●──●───  (一切都在主干)
           │  │  │  │  │  │  │  │  │  │  │  │
short     ●──●  │  │  │  │  │  │  │  │  │  │  │
branch      │  │  │  │  │  │  │  │  │  │  │  │
           feature/a (1-2 天内合回主干)

特点：
  - 分支短命（< 2 天）
  - 用 feature flag 控制未完成功能
  - 持续集成 / 持续部署
  - 适合：< 20 人团队，强 CI/CD 能力
```

### 6.3 GitHub Flow（最简单）

```text
master    ─●──●──●──●──●──●──●──●──●──●──●──  (主干即生产)
           ▲  ▲  ▲  ▲  ▲  ▲  ▲  ▲  ▲  ▲
           │  │  │  │  │  │  │  │  │  │
feature    ●──●  ●──●  ●──●  ●──●  ●──●
分支       a    b    c    d    e    f    g

特点：
  - 只有 master + feature
  - feature 合到 master → 立即部署
  - 适合：SaaS / Web 服务 / 持续部署
  - 不适合：传统企业 / 多版本并行
```

### 6.4 三种模式对比

| 模式 | 分支数 | 适合 | 复杂度 |
| --- | --- | --- | --- |
| Git Flow | 多（master/develop/feature/release/hotfix） | 传统企业 / 多版本并行 | 高 |
| GitHub Flow | 少（master + feature） | SaaS / 持续部署 | 低 |
| Trunk-Based | 极少（几乎只有 master） | 高 CI/CD 能力团队 | 最低 |

## 七、与 Git 工具链集成

### 7.1 Git Hooks

```bash
# .git/hooks/commit-msg
#!/bin/sh
# 校验分支名
BRANCH=$(git symbolic-ref --short HEAD)
PATTERN='^(master|main|develop|release/.*|hotfix/.*|feature/.*|bugfix/.*|experiment/.*|refactor/.*|docs/.*|chore/.*|[a-z]+/.*)$'

if ! echo "$BRANCH" | grep -qE "$PATTERN"; then
  echo "❌ 分支名 '$BRANCH' 不符合规范"
  echo "✅ 应为: <type>/<scope>-<desc>"
  echo "✅ 类型: master/main/develop/release/hotfix/feature/bugfix/experiment/refactor/docs/chore"
  exit 1
fi
```

### 7.2 GitLab CI 规则

```yaml
# .gitlab-ci.yml
workflow:
  rules:
    - if: '$CI_COMMIT_BRANCH == "master" || $CI_COMMIT_BRANCH == "main"'
      variables:
        DEPLOY_ENV: "production"
        IMAGE_TAG: "stable-${CI_COMMIT_SHORT_SHA}"
    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        DEPLOY_ENV: "staging"
        IMAGE_TAG: "develop-${CI_COMMIT_SHORT_SHA}"
    - if: '$CI_COMMIT_TAG && $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      variables:
        DEPLOY_ENV: "production"
        IMAGE_TAG: "${CI_COMMIT_TAG}"
    - if: '$CI_COMMIT_BRANCH =~ /^hotfix\//'
      variables:
        DEPLOY_ENV: "production"
        IMAGE_TAG: "hotfix-${CI_COMMIT_SHORT_SHA}"
        URGENT: "true"
    - if: '$CI_COMMIT_BRANCH =~ /^feature\//'
      variables:
        DEPLOY_ENV: "dev-preview"
        IMAGE_TAG: "feature-${CI_COMMIT_SHORT_SHA}"
```

### 7.3 GitHub Actions 规则

```yaml
name: Branch CI
on:
  push:
    branches:
      - 'master'
      - 'main'
      - 'develop'
      - 'release/**'
      - 'hotfix/**'
      - 'feature/**'
      - 'bugfix/**'

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Detect branch type
        id: branch
        run: |
          if [[ "${{ github.ref }}" == "refs/heads/master" ]]; then
            echo "type=production" >> $GITHUB_OUTPUT
          elif [[ "${{ github.ref }}" == "refs/heads/develop" ]]; then
            echo "type=staging" >> $GITHUB_OUTPUT
          elif [[ "${{ github.ref }}" =~ ^refs/heads/hotfix/ ]]; then
            echo "type=hotfix" >> $GITHUB_OUTPUT
          fi
```

## 八、与 CI/CD 流水线集成

### 8.1 分支 → 环境 → 流程映射

| 分支 | 自动部署到 | 流程 | 谁来触发 |
| --- | --- | --- | --- |
| `master` | 生产（待 release tag） | 完整流水线 + 灰度 | Release Manager |
| `release/v*` | 预发 / staging | 完整测试 | 自动 |
| `develop` | 集成测试环境 | 跑测试 + 部署 | 自动 |
| `feature/*` | dev preview | 单元测试 + 单服务部署 | 自动 |
| `bugfix/*` | staging | 测试 | 自动 |
| `hotfix/*` | 生产（紧急） | 快速通道 | 手动 + 自动 |
| `experiment/*` | 无 | 仅跑测试 | 不部署 |

### 8.2 GitOps 集成（ArgoCD / Flux）

```yaml
# ArgoCD Application：按分支部署
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp-master
  namespace: argocd
spec:
  source:
    repoURL: git@github.com:myorg/myapp.git
    targetRevision: master            # ← 跟踪 master
    path: deploy/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
---
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp-develop
spec:
  source:
    targetRevision: develop            # ← 跟踪 develop
    path: deploy/overlays/staging
  destination:
    namespace: staging
```

### 8.3 Tag 自动化发版

```yaml
# GitLab CI：tag 触发 production 部署
deploy-production:
  stage: deploy
  script:
    - kubectl set image deployment/myapp myapp=myregistry/myapp:${CI_COMMIT_TAG}
    - kubectl rollout status deployment/myapp
  environment:
    name: production
    url: https://myapp.example.com
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
```

## 九、保护规则 / 权限控制

### 9.1 GitLab 分支保护

```text
Settings → Repository → Protected Branches

master:
  Allowed to merge: Maintainers
  Allowed to push: No one
  Require MR approval: 2
  Require status checks: ci-success, lint-pass

develop:
  Allowed to merge: Developers + Maintainers
  Allowed to push: No one
  Require MR approval: 1
  Require status checks: ci-success

release/*:
  Allowed to merge: Maintainers
  Allowed to push: Developers + Maintainers

hotfix/*:
  Allowed to merge: Maintainers
  Allowed to push: Developers + Maintainers
  Require MR approval: 2
  Require status checks: ci-success, security-scan
```

### 9.2 GitHub 分支保护

```yaml
# .github/settings.yml 或 UI 设置
branches:
  - name: master
    protection:
      required_status_checks:
        strict: true
        contexts:
          - ci/test
          - ci/lint
          - security/scan
      required_pull_request_reviews:
        required_approving_review_count: 2
        dismiss_stale_reviews: true
        require_code_owner_reviews: true
      restrictions:
        users:
          - release-manager
        teams:
          - core-team
      enforce_admins: true
      required_linear_history: true                # 禁止 merge commit
      allow_force_pushes: false
      allow_deletions: false
```

## 十、与泳道 / 环境的关系

### 10.1 分支 × 环境矩阵

| 分支类型 | dev 沙盒 | 集成 | staging | 预发 | 生产 |
| --- | --- | --- | --- | --- | --- |
| `feature/alice-*` | ✅ alice 独占 | ❌ | ❌ | ❌ | ❌ |
| `bugfix/order-*` | ✅ 该 user | ✅ develop 池 | ❌ | ❌ | ❌ |
| `develop` | ✅ 共享 | ✅ | ✅ | ❌ | ❌ |
| `release/v1.2` | ✅ 共享 | ✅ | ✅ | ✅ | ❌ |
| `master` | ✅ 共享 | ✅ | ✅ | ✅ | ✅ |
| `hotfix/pay-*` | ✅ | ✅ | ✅ | ✅ | ✅（紧急） |

### 10.2 分支 → 泳道自动绑定

```text
feature/alice-login-LOGIN-123
       │
       ▼ 自动生成
Lane CR:
  user: alice
  service: login
  image: <branch commit build>
  branchSource: feature/alice-login-LOGIN-123    # ← 记录来源

Operator 行为：
  - 监听到 PR 合并到 develop → 自动删除 Lane
  - 监听到分支删除 → 自动删除 Lane
  - 监听到新 push → 自动更新 image
```

### 10.3 镜像 tag 约定（推荐）

```text
格式：
  master:<git-sha>           生产候选
  release-v1.2.0:<sha>       发布版本
  develop:<git-sha>          集成测试
  feature-<name>:<sha>       功能预览
  hotfix-<name>:<sha>        紧急修复

CI 自动打 tag 脚本：
  BRANCH=${CI_COMMIT_REF_NAME}
  SHA=${CI_COMMIT_SHORT_SHA}

  case "$BRANCH" in
    master|main)
      TAG="${SHA}"
      ;;
    release/*)
      TAG="${BRANCH#release/}-${SHA}"     # 去掉 release/ 前缀
      ;;
    develop)
      TAG="develop-${SHA}"
      ;;
    feature/*)
      NAME=$(echo "$BRANCH" | sed 's/[^a-z0-9-]/-/g')
      TAG="feature-${NAME}-${SHA}"
      ;;
    hotfix/*)
      NAME=$(echo "$BRANCH" | sed 's/[^a-z0-9-]/-/g')
      TAG="hotfix-${NAME}-${SHA}"
      ;;
  esac

  docker build -t myregistry/myapp:${TAG} .
  docker push myregistry/myapp:${TAG}
```

## 十一、Commit 信息规范

> **分支管的是"代码流"，commit 管的是"原子粒度"**。
> 规范化的 commit 信息让 `git log` 可读、CHANGELOG 自动生成、revert 精准、code review 高效。

### 11.1 为什么需要规范

```text
没有规范的 commit：
  $ git log --oneline
  a1b2c3d 修复bug
  d4e5f6g update
  g7h8i9j 1
  j0k1l2m 完成
  m3n4o5p final version
  p6q7r8s 再改一下
  
  → 看到 log 一脸懵
  → 找 bug 找不到对应 commit
  → revert 不知道该回滚哪个
  → CHANGELOG 没人能写

有规范的 commit：
  $ git log --oneline
  a1b2c3d feat(login): add wechat oauth support (LOGIN-1234)
  d4e5f6g fix(order): prevent duplicate submission race condition (ORDER-567)
  g7h8i9j docs(api): update README with new endpoints
  j0k1l2m refactor(payment): split state machine into separate module
  m3n4o5p chore(deps): upgrade go to 1.22
  
  → 一目了然
  → 自动生成 CHANGELOG
  → 精准 revert
  → 团队 review 高效
```

### 11.2 业界标准：Conventional Commits

```text
公司里最常用的规范 = Conventional Commits（Angular Convention 衍生）

格式：
  <type>(<scope>): <subject>
  <BLANK LINE>
  <body>
  <BLANK LINE>
  <footer>

示例：
  feat(login): add wechat oauth support
  
  支持微信扫码登录。用户点击登录按钮后跳转微信授权页，
  回调后通过 code 换取 access_token。
  
  Refs: LOGIN-1234
  Reviewed-by: @bob
```

### 11.3 Type 类型（10 种）

| Type | 用途 | 影响版本 |
| --- | --- | --- |
| `feat` | 新功能 | MINOR（1.0.0 → 1.1.0） |
| `fix` | bug 修复 | PATCH（1.0.0 → 1.0.1） |
| `docs` | 仅文档变更 | 不发版 |
| `style` | 格式（空格、分号等，不改逻辑） | 不发版 |
| `refactor` | 重构（既不是新功能也不是修 bug） | 不发版 |
| `perf` | 性能优化 | PATCH |
| `test` | 测试相关 | 不发版 |
| `chore` | 杂事（构建、依赖、CI） | 不发版 |
| `revert` | 回滚之前的 commit | 同被回滚的 type |
| `build` | 构建系统 / 外部依赖变更 | 不发版 |

### 11.4 Scope 范围（可选但推荐）

```text
Scope 表明改动影响的模块/服务：
  - 服务名：login / order / payment / user
  - 模块名：api / db / cache / config
  - 层次：frontend / backend / infra / docs

示例：
  feat(login): ...
  feat(order-api): ...
  feat(backend-cache): ...
  fix(payment-callback): ...
  
单服务项目可以省略 scope。
```

### 11.5 Subject 标题（强制）

```text
规范：
  - 中文 / 英文都可以，公司统一一种
  - 不超过 50 字符
  - 不大写首字母（除非专有名词）
  - 不加句末标点
  - 祈使语气（"add" 而不是 "added" / "adds"）

✅ 推荐：
  feat(login): add wechat oauth support
  fix(order): prevent duplicate submission
  docs(api): update authentication examples

❌ 不推荐：
  feat(login): 添加了微信登录功能                    # 时态不对 / 中文混用
  Fix(Login): Add Wechat OAuth.                     # 大写 + 句末点
  feat: update                                    # 太泛
  feat(login): add wechat oauth support and also fix the bug in callback and update docs   # 太长
```

### 11.6 Body 正文（可选但强烈推荐）

```text
用途：
  - 解释"为什么"改（不要写"做了什么"，那是 diff 的事）
  - 描述改动前后的差异
  - 标注副作用 / 风险

格式：
  - 每行 ≤ 72 字符
  - 与 subject 空一行分隔
  - 中文 / 英文都可以

示例：
  feat(login): add wechat oauth support
  
  用户反馈原手机号+验证码流程流失率高，
  接入微信扫码登录后预计降低 30%。
  
  涉及的配置：
  - WECHAT_APP_ID（新增）
  - WECHAT_APP_SECRET（新增）
  - LOGIN_WECHAT_ENABLED（默认 false，可灰度）
  
  Refs: LOGIN-1234
```

### 11.7 Footer 页脚（可选）

```text
常见字段：
  Refs: TICKET-ID            # 关联任务 / bug
  Closes: TICKET-ID          # 关闭任务
  Reviewed-by: @username     # review 人
  Co-authored-by: Name <email>    # 共同作者
  BREAKING CHANGE: <desc>    # 不兼容变更
  BREAKING-CHANGE: <desc>    # 同上，GitLab 风格

示例：
  fix(payment): handle timeout in stripe webhook
  
  Stripe webhook 偶发 30s 超时，导致订单状态卡住。
  增加重试 + 超时熔断。
  
  Closes: PAY-890
  Reviewed-by: @bob, @charlie
  BREAKING CHANGE: webhook payload schema changed, see migration guide
```

### 11.8 BREAKING CHANGE（必须标注）

```text
任何不向后兼容的变更必须在 footer 用 BREAKING CHANGE 标注：
  
  ⚠️ 影响 MAJOR 版本号（1.x.x → 2.0.0）

示例：
  feat(api)!: rename /user/list to /users
  
  Restructure user API endpoints for consistency.
  
  BREAKING CHANGE: /user/list renamed to /users. Update all clients.

或者在 type/scope 后加 !：
  feat(api)!: rename /user/list to /users
```


### 11.10 不规范的反例（code review 直接打回）

```text
❌ 太泛：
  feat: update
  
❌ 没 type：
  add wechat login
  
❌ 混合多个改动（一个 commit 干 N 件事）：
  feat(login): add wechat oauth, fix payment bug, update docs
  
  → 应该拆成 3 个 commit

❌ 描述"做了什么"而不是"为什么"：
  fix: changed line 42 from == to =
  
  → 这是 diff 的事，commit 应说明"为什么改"（修什么 bug）

❌ 个人情绪：
  fuck this stupid bug
  最终版本！不要再改了！
  
❌ WIP 占位：
  WIP
  todo
  1
  test
  
❌ 中文 / 英文 / emoji 混用：
  feat(login): 增加了微信登录 🎉
```

### 11.11 Git Hook 强制校验（commit-msg）

```bash
#!/bin/sh
# .git/hooks/commit-msg
# 校验 commit message 格式

COMMIT_MSG_FILE=$1
COMMIT_MSG=$(cat "$COMMIT_MSG_FILE")

# 正则：type(scope)?: subject
PATTERN='^(feat|fix|docs|style|refactor|perf|test|chore|revert|build)(\([a-z0-9_-]+\))?!?: .{1,50}$'

FIRST_LINE=$(echo "$COMMIT_MSG" | head -n 1)

if ! echo "$FIRST_LINE" | grep -qE "$PATTERN"; then
  echo "❌ Commit 信息不符合规范"
  echo ""
  echo "❌ 你的首行: $FIRST_LINE"
  echo ""
  echo "✅ 正确格式: <type>(<scope>): <subject>"
  echo ""
  echo "✅ 合法 type:"
  echo "   feat fix docs style refactor perf test chore revert build"
  echo ""
  echo "✅ 示例:"
  echo "   feat(login): add wechat oauth support"
  echo "   fix(order): prevent duplicate submission"
  echo "   docs(readme): update quick start"
  exit 1
fi

# 检查 subject 长度
SUBJECT_LEN=$(echo "$FIRST_LINE" | wc -c)
if [ "$SUBJECT_LEN" -gt 73 ]; then  # 50 字符 + \n
  echo "⚠️  Subject 过长（$SUBJECT_LEN > 72），建议精简"
fi

# 拒绝 merge commit（强制 squash / rebase）
if echo "$FIRST_LINE" | grep -qE "^Merge "; then
  echo "⚠️  检测到 Merge commit，请用 rebase / squash 合并"
  exit 1
fi
```

### 11.14 与 PR / MR 配合

```text
Commit 信息 → PR title：
  PR title 必须用同一规范
  GitHub / GitLab 默认用首个 commit 信息做 PR title

  feat(login): add wechat oauth support      ← 这就是 PR title

Commit 信息 → Squash merge：
  合并时 squash 所有 commit 为一个
  PR 内可以有 50 个 commit（开发过程）
  squash 后只保留 1 个（PR title 格式）

⚠️ 推荐：
  - feature 分支期间随便 commit（开发过程）
  - merge 时勾选 squash
  - 主干上的每个 commit 都是"完整功能"粒度
```

### 11.15 强制 vs 宽松的选择

```text
🔴 强制（推荐大公司 / 严肃项目）：
  - commit-msg hook 强制校验
  - CI 跑 commitlint，不通过不让 merge
  - 团队培训 + onboarding 必讲

🟡 软性（推荐中小团队过渡期）：
  - PR template 提醒
  - review 时手动纠正
  - 每周发布"规范 commit 之星"

🟢 宽松（不推荐，仅适合 5 人以下）：
  - 仅在 README 里写规则
  - 不强制
  → 3 个月后基本没人遵守
```

### 11.16 常见问题

```text
Q1：开发中怎么 commit？每次小改动都要 commit 吗？
A：要。一个功能从开始到合并可能有 50 个 commit，每个 commit 都是原子的。
   但合并到主干时 squash 成一个"功能粒度"的 commit。

Q2：中文 commit 行不行？
A：可以，但建议英文。理由：
   - 工具链（commitlint / changelog）默认英文
   - 跨国团队友好
   - IDE / GitHub UI 默认英文
   折中：type/scope 英文，subject/body 可以中文。

Q3：commit 必须是"feat/fix"吗？
A：不一定。docs / refactor / chore 都是合法类型。
   关键是要写明"为什么"，不是"做了什么"。

Q4：AI 生成的代码需要单独标注吗？
A：建议在 footer 加 Co-authored-by：
   Co-authored-by: Claude <noreply@anthropic.com>
   透明、可追溯。

Q5：commit 改了 5 个文件算几个 commit？
A：看逻辑关联：
   - 5 个文件改同一功能 → 1 个 commit
   - 3 个文件改功能 + 2 个文件顺带 refactor → 拆 2 个 commit

Q6：能在 commit message 里写敏感信息吗？
A：绝对不能。密码、token、内部域名都不要写在 commit 里。
   已经被 git 记录的就需要 force push + BFG 清理。
```

## 十一、常见反模式

### 11.1 反模式 1：在 master 上长期开发

```text
❌ 错误：
  - 直接在 master 上开发
  - 没有 PR review
  - 出问题时无法定位哪个 commit 导致

✅ 正确：
  - 所有改动走 feature 分支
  - 必须 PR 合并
  - 必须 code review
```

### 11.2 反模式 2：长期不合并的 feature 分支

```text
❌ 错误：
  - feature/login 开发 3 个月
  - 中间 develop 推了几百个 commit
  - 最后 merge 时冲突巨大
  - 解决冲突又花 1 周

✅ 正确：
  - feature 分支 ≤ 2 周
  - 每周 rebase develop 一次
  - 或者用 feature flag 分阶段合
```

### 11.3 反模式 3：release 分支越改越多

```text
❌ 错误：
  - release/v1.2.0 越改越多
  - 加了 3 个 feature
  - 拖延 2 个月
  - 已经不是"发版"分支，是"开发"分支了

✅ 正确：
  - release 分支只修 bug，不加 feature
  - 新功能 → 等下一个 release
  - 或者 release 失败 → 删掉重来
```

### 11.4 反模式 4：hotfix 加新功能

```text
❌ 错误：
  - hotfix/payment-timeout 里
  - 顺便加了 user-profile 优化
  - merge 进 master 后
  - 下次发版莫名其妙带了个 user-profile 改动

✅ 正确：
  - hotfix 只修对应 bug
  - 多余改动 → 拆 PR
```

### 11.5 反模式 5：分支名乱写

```text
❌ 错误：
  fix / new / test / aaa / 最终版本 / 我的修改

✅ 正确：
  bugfix/order-duplicate-ORDER-123
  feature/login-with-wechat-LOGIN-456
```

### 11.6 反模式 6：主干永久分叉

```text
❌ 错误：
  - develop 比 master 领先 200 commits
  - 或者 master 比 develop 领先（hotfix 没同步）
  - 长期分裂

✅ 正确：
  - 定期 release（每周 / 每两周）
  - hotfix merge 后立即反向同步到 develop
```

### 11.7 反模式 7：私人不规范的长期分支

```text
❌ 错误：
  alice/test、bob/wip、carol/tmp 长期存在
  干扰 git log、分支列表、PR 模板

✅ 正确：
  - 临时分支 ≤ 1 周
  - 或者用 personal/ 前缀明确标 private
  - 定期清理（脚本扫 inactive > 30 天的）
```

## 十二、不同规模团队的建议

### 12.1 5 人初创团队


## 十三、迁移 / 落地步骤

### 13.1 第一步：选择模型

```text
1. 评估团队规模、业务形态、CI/CD 能力
2. 选择 Git Flow / GitHub Flow / Trunk-Based
3. 写下团队公认的规范文档（本文档可作模板）
4. 团队 review 并签字确认
```

### 13.2 第二步：保护规则

```text
1. master / develop 加保护
2. 设置 CODEOWNERS
3. 强制 PR + status check
4. 禁止直接 push
```

### 13.3 第三步：自动化

```text
1. CI 配置按分支类型差异化
2. 镜像打 tag 脚本
3. GitOps 应用按分支部署
4. 定时清理 inactive 分支
```

### 13.4 第四步：清理历史

```text
1. 列出所有分支
2. 分类（保留 / 合并 / 删除）
3. 发通知：3 天后将批量删除
4. 批量删除 + 通知 owner
5. 归档重要分支（tag）
```

### 13.5 第五步：持续优化

```text
1. 每月 review 分支情况
2. 统计 PR 平均生命周期
3. 调整规则（合并频率 / review 要求）
4. 培训新成员
```

---

## 十四、一句话总结

> **分支管理本质是把"代码流动"约束成几条可预测的路径**：
> **核心分支长期存在（master / develop）+ 工作分支短命（feature / bugfix / hotfix）+ release 分支冻结**；
> 配合 CI/CD 自动识别分支类型 → 差异化部署，就能做到"看分支名就知道它在哪、会去哪、什么时候消失"。
