# 特性分支开发模式（Feature Branch Workflow）

> 目标：**让每个功能在独立分支上完整开发、测试、合并，避免互相干扰**。
> 适用：任何使用 Git 进行协作的团队，与 Git Flow / GitHub Flow / Trunk-Based 都兼容。

## 一、什么是特性分支开发模式

```text
核心思想：
  任何新功能、Bug 修复、实验性改动
  → 都在独立的"特性分支"上完成
  → 通过 PR/MR 合并回主干
  → 主干永远保持可发布状态

最简单的描述：
  主干是"稳定中转站"
  特性分支是"开发车间"
  PR 是"质检闸门"
```

**关键特征**：

```text
✅ 核心特征：
  - 每个改动一个独立分支
  - 分支通过 PR/MR 合并
  - Code Review 强制
  - CI 全绿才能合并
  - 主干（master / develop）永远可发布

❌ 不是特性分支：
  - 直接在主干上改
  - 用 zip 包分享代码
  - "我合并一下你 pull 一下" 的口头同步
```

## 二、核心原则

### 2.1 单一职责原则

```text
一个特性分支只做一件事：
  ✅ feat/user-login-LOGIN-123        （只做登录）
  ✅ fix/order-duplicate-ORDER-567    （只修这个 bug）
  
  ❌ feat/login-and-payment           （两件事）
  ❌ fix/order-bug-and-refactor       （混在一起）
  
为什么：
  - 出问题容易 revert
  - Code Review 范围清晰
  - 冲突最小化
  - 关联 ticket 清晰
```

### 2.2 原子化原则

```text
分支内的 commit 应该保持原子性：
  - 每个 commit 是可独立回滚的
  - 每个 commit 不破坏构建
  - 每个 commit 单元测试通过
  
  ✅ 好：
    commit 1: add user model
    commit 2: add login API endpoint
    commit 3: add login tests
    commit 4: update docs
    
  ❌ 不好：
    commit 1: add user model
    commit 2: add login API + 改了一堆其他东西
    commit 3: fix typo (无关)
    commit 4: WIP something
```

### 2.3 短命原则

```text
特性分支应尽可能短命：
  - 推荐 ≤ 1 周
  - 极端情况下 ≤ 2 周
  - 超过 2 周 → 拆功能 / 用 feature flag
  
为什么：
  - 时间越长越难 merge（冲突）
  - 时间越长越难 review（diff 太大）
  - 时间越长越容易过期（需求变更）
```

### 2.4 主干稳定原则

```text
master / develop 永远保持：
  - 构建通过
  - 单元测试通过
  - 部署到 staging 不出错
  
禁止：
  - 直接 push 到主干
  - force push 到主干
  - 在主干上"先 push 再 fix"
```

### 2.5 沟通留痕原则

```text
所有决策都要有痕迹：
  - PR description 写清楚改了什么、为什么
  - Code Review 评论保留
  - 重大决策在 PR 评论里 AT 相关人
  - 关联到 ticket（自动留痕）
```

## 三、完整工作流

### 3.1 步骤一：创建分支

```bash
# 1. 确保主干最新
git checkout develop
git pull origin develop

# 2. 创建特性分支
git checkout -b feature/login-with-wechat-LOGIN-123

# 3. 推送到远端（即使只自己用）
git push -u origin feature/login-with-wechat-LOGIN-123
```

**命名**：

```text
feat(login-with-wechat-LOGIN-123)       # 标准命名
bugfix(order-duplicate-ORDER-567)        # bugfix 前缀
hotfix(payment-timeout-PAY-890)          # hotfix 前缀（紧急）

详见分支管理.md 第二章节命名约定。
```

### 3.2 步骤二：开发

```bash
# 在特性分支上正常工作
git add .
git commit -m "feat(login): add wechat oauth config loader"

# 期间主干可能更新
git fetch origin develop
git rebase origin/develop                # 推荐：rebase 保持线性
                                          # 或者 git merge origin/develop

# 推送到远端触发 CI
git push origin feature/login-with-wechat-LOGIN-123
```

**开发过程中的纪律**：

```text
1. commit 信息规范（详见 commit规范.md）
2. 每个 commit 跑单元测试
3. push 前本地 CI 全绿
4. 长时间不开工 → 暂停 / 留 WIP / 让同事接手
```

### 3.3 步骤三：发起 PR

```bash
# 1. 推送最新代码
git push origin feature/login-with-wechat-LOGIN-123

# 2. 在 GitHub/GitLab UI 上 "New Pull Request"

# 3. 填写 PR 模板（必须项）
```

**PR 模板**：

```markdown
## 改动说明
<!-- 简述这个 PR 做了什么、为什么 -->

## 关联 Ticket
- LOGIN-1234

## 改动类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档
- [ ] 其他

## 测试
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 手动验证完成
- [ ] 添加了测试用例

## 截图 / 录屏
<!-- UI 改动必须附图 -->

## Checklist
- [ ] Code Review 通过
- [ ] CI 全绿
- [ ] 文档已更新
- [ ] CHANGELOG 已更新
- [ ] 已通知相关人

## 风险评估
<!-- 对生产有什么影响？需要灰度吗？ -->
```

### 3.4 步骤四：Code Review

```text
流程：
  1. 开发者提交 PR
  2. CI 自动跑（lint / test / build）
  3. CI 全绿 → 自动分配 reviewer
  4. Reviewer 在代码里评论
  5. 开发者修改 / 回复
  6. 达到约定 approve 数 → 可合并
  7. 作者合并 PR

时间要求：
  - 第一个 review 响应：< 4 小时
  - 整体 review 完成：< 24 小时
  - 紧急 PR：< 1 小时
```

### 3.5 步骤五：合并

```bash
# 推荐：squash merge（PR 内多 commit 合成一个）
git merge --squash feature/login-with-wechat-LOGIN-123

# 或在 UI 上勾选 "Squash and merge"

# 合并后：
git push origin develop                   # develop 收到一个 squash commit
git push origin --delete feature/login-with-wechat-LOGIN-123  # 删源分支
```

### 3.6 步骤六：清理

```bash
# 本地
git checkout develop
git branch -d feature/login-with-wechat-LOGIN-123    # 删本地

# 远端（通常自动 / 或手动）
git push origin --delete feature/login-with-wechat-LOGIN-123

# 关闭 ticket
# 在 JIRA / 飞书任务里标记 Done
```

### 3.7 完整流程图

```text
  ┌──────────┐
  │ 主干最新  │
  │ (develop)│
  └────┬─────┘
       │ pull
```

## 四、与三种主流分支模型的对比

### 4.1 Git Flow

```text
Git Flow + 特性分支：
  master: 生产源
  develop: 集成分支
  feature/*: 特性分支（你做的）
  release/*: 发版分支
  hotfix/*: 紧急修复
  
  流程：
  develop → feature/xxx → develop → release/v1.2 → master
  
  特性分支在 Git Flow 里的位置：
  - 从 develop 拉
  - 合回 develop
  - 可能进入 release 分支做最后修复
```

### 4.2 GitHub Flow

```text
GitHub Flow + 特性分支：
  master: 一切都在这里
  feature/*: 特性分支（你做的）
  
  流程：
  master → feature/xxx → master（直接）
  
  特性分支特点：
  - 极短命（< 2 天）
  - 合并后立即部署
  - 用 feature flag 控制未完成功能
```

### 4.3 Trunk-Based Development

```text
Trunk-Based + 特性分支：
  master: 主干（trunk）
  feature/*: 短特性分支（也可以直接在主干）
  
  流程：
  master → feature/xxx（短命）→ master
  
  特性分支特点：
  - 寿命 < 1-2 天
  - 必须搭配 feature flag
  - 强 CI/CD 能力
```

### 4.4 对比表

| 维度 | Git Flow | GitHub Flow | Trunk-Based |
| --- | --- | --- | --- |
| 特性分支寿命 | 1-2 周 | 1-3 天 | < 2 天 |
| 合并目标 | develop | master | master |
| 集成 release 分支 | 是 | 否 | 否 |
| 需要 feature flag | 否 | 推荐 | 必须 |
| 适合团队规模 | 20-100+ | 5-20 | 5-50 |
| 部署节奏 | 每周/每月 | 每天 | 随时 |
| CI/CD 要求 | 中 | 高 | 极高 |

### 4.5 推荐选择

```text
你的情况 → 选哪个：
  - 5 人初创 + 持续部署 → Trunk-Based
  - 10 人 + 每周发版 → GitHub Flow
  - 50 人 + 多版本并行 → Git Flow
  - 不确定 → GitHub Flow（最容易上手）
```

## 五、分支生命周期管理

### 5.1 分支状态机

```text
  [新创建]
     │  push
     ▼
  [开发中] ───────────────┐
     │  push               │ idle
     ▼                     │
  [待 Review]              │
     │  approve            │
     ▼                     │
  [已合并]                 │
     │  cleanup            │
     ▼                     │
  [已删除]                 │
                            │
                            ▼
                       [过期清理]
```

### 5.2 各阶段时长标准

| 状态 | 推荐时长 | 警告时长 | 必须处理 |
| --- | --- | --- | --- |
| 新创建 | 0 | > 7 天 | 拆分或删除 |
| 开发中 | < 5 天 | > 14 天 | 必须 rebase 或拆分 |
| 待 Review | < 1 天 | > 3 天 | reviewer 跟进 |
| 已合并 | < 1 天 | > 7 天 | 自动删除 |
| 过期未清理 | < 7 天 | > 30 天 | 强制删除 + 通知 |

### 5.3 自动清理策略

```bash
# GitLab CI：自动清理已合并的远端分支
stale-branch-cleanup:
  stage: cleanup
  script:
    - |
      git branch -r --merged origin/master | \
        grep -v 'master\|main\|develop' | \
        grep -v '>' | \
        sed 's/origin\///' | \
        xargs -I {} git push origin --delete {}
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'

# GitHub Actions：定时清理
name: Cleanup stale branches
on:
  schedule:
    - cron: '0 2 * * *'                  # 每天凌晨 2 点
jobs:
  cleanup:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Delete merged branches
        run: |
          git branch -r --merged origin/master | \
            grep -vE 'master|main|develop' | \
            sed 's/origin\///' | \
            xargs -I {} git push origin --delete {}
```

### 5.4 过期分支报警

```promql
# Prometheus：监控长期未合并的分支
count(git_branch_age_days{status="open"} > 14)

# GitLab API 拉取
curl -H "PRIVATE-TOKEN: $TOKEN" \
  "$GITLAB_URL/api/v4/projects/$PROJECT_ID/merge_requests?state=opened&per_page=100" \
  | jq '.[] | select(.created_at < (now - 1209600 | todate)) | {iid, title, age_days: ((now - (.created_at | fromdateiso8601)) / 86400 | floor)}'
```

## 六、Code Review 规范

### 6.1 Reviewer 分配

```text
分配规则：
  - 至少 1-2 个 reviewer
  - 自动分配（同组 / CODEOWNERS / round-robin）
  - 跨组改动需要双方 reviewer
  - 高风险改动（auth/payment）需要 senior

CODEOWNERS 示例：
  /src/auth/           @auth-team
  /src/payment/        @payment-team @security-team
  /src/order/          @order-team
  /src/shared/         @backend-team
  /deploy/production/  @sre-team
```

### 6.2 Review 重点

```text
必看项（影响通过的）：
  - 业务逻辑正确性
  - 边界条件 / 异常处理
  - 安全问题（SQL 注入 / XSS / 权限）
  - 性能影响（大数据量 / 循环 / 数据库查询）
  - 兼容性（接口变更 / 数据迁移）
  - 测试覆盖

可选看项（建议但不强制）：
  - 代码风格（用 linter 自动卡）
  - 重构建议
  - 命名优化
  - 文档更新
```

### 6.3 评论规范

```text
✅ 好的评论：
  "这里 N+1 查询，建议用 preload 一次拉完"
  "这个 SQL 没传 user_id，会不会越权？参考 auth.go:42"
  "建议加个单元测试覆盖 null case"

❌ 不好的评论：
  "这写法不好"          # 不说为什么
  "重写一下"            # 没具体建议
  "我想想"              # 没结论
  "🤔"                 # 表情不能代替文字

🔴 禁止的评论：
  "你怎么这么写"        # 人身攻击
  "这都不会"            # 居高临下
  "不是我说你"          # 阴阳怪气
```

### 6.4 Review SLA

| PR 类型 | 首响应 | 整体完成 | Reviewer 数 |
| --- | --- | --- | --- |
| 普通功能 | < 4 小时 | < 24 小时 | ≥ 1 |
| 普通 bug | < 2 小时 | < 8 小时 | ≥ 1 |
| 紧急 hotfix | < 30 分钟 | < 2 小时 | ≥ 2 |
| 安全相关 | < 1 小时 | < 4 小时 | ≥ 2（含安全负责人） |
| 大型重构 | < 1 天 | < 1 周 | ≥ 2 |

### 6.5 Reviewer 轮值

```yaml
# .github/CODEOWNERS 或 config
review_rotations:
  - team: backend
    members: [alice, bob, charlie]
    rotation: weekly
  - team: frontend
    members: [david, eve]
    rotation: weekly
  - team: infra
    members: [frank, grace]
    rotation: weekly
```

## 七、CI/CD 与特性分支的集成

### 7.1 分支 → 流水线映射

```yaml
# GitLab CI 示例
workflow:
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^feature\//'
      variables:
        PIPELINE_TYPE: "feature"
        DEPLOY_ENV: "preview"
    - if: '$CI_COMMIT_BRANCH =~ /^bugfix\//'
      variables:
        PIPELINE_TYPE: "bugfix"
        DEPLOY_ENV: "staging"
    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        PIPELINE_TYPE: "integration"
        DEPLOY_ENV: "integration"
    - if: '$CI_COMMIT_BRANCH =~ /^release\//'
      variables:
        PIPELINE_TYPE: "release"
        DEPLOY_ENV: "pre-prod"
    - if: '$CI_COMMIT_BRANCH =~ /^hotfix\//'
      variables:
        PIPELINE_TYPE: "hotfix"
        DEPLOY_ENV: "production-urgent"
```

### 7.2 特性分支的 CI 流水线

```yaml
stages:
  - lint
  - test
  - build
  - deploy-preview
  - notify

lint:
  stage: lint
  script:
    - golangci-lint run
    - markdownlint docs/
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^(feature|bugfix|hotfix|refactor)\//'

test:
  stage: test
  script:
    - go test -race -cover ./...
  coverage: '/coverage: \d+%\)/'
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^(feature|bugfix|hotfix|refactor)\//'

build:
  stage: build
  script:
    - docker build -t myregistry/myapp:feature-${CI_COMMIT_SHORT_SHA} .
    - docker push myregistry/myapp:feature-${CI_COMMIT_SHORT_SHA}
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^feature\//'

deploy-preview:
  stage: deploy-preview
  script:
    - kubectl set image deployment/myapp-preview myapp=myregistry/myapp:feature-${CI_COMMIT_SHORT_SHA}
    - kubectl rollout status deployment/myapp-preview
  environment:
    name: preview/${CI_COMMIT_AUTHOR_USERNAME}
    url: https://${CI_COMMIT_AUTHOR_USERNAME}.preview.myapp.com
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^feature\//'
      when: manual                    # 需要手动触发（节省资源）

notify:
  stage: notify
  script:
    - |
      curl -X POST $WEBHOOK_URL \
        -d "{\"branch\":\"$CI_COMMIT_BRANCH\",\"author\":\"$CI_COMMIT_AUTHOR\",\"preview\":\"https://${CI_COMMIT_AUTHOR_USERNAME}.preview.myapp.com\"}"
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^feature\//'
```

### 7.3 自动部署预览环境

```text
特性分支 push → 自动部署到：
  - URL：https://alice.preview.myapp.com/feature/login
  - 命名空间：preview-alice
  - TTL：分支删除后 24 小时清理
  - 资源配额：每用户限 1 个预览

详见泳道设计文档。
```

### 7.4 PR 触发的检查

```yaml
# GitHub Actions：PR 触发
on:
  pull_request:
    branches: [develop, master, main]

jobs:
  pr-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Lint
        run: make lint
      - name: Test
        run: make test
      - name: Build
        run: make build
      - name: Security Scan
        run: |
          # 依赖漏洞扫描
          npm audit --audit-level=high
          # SAST 扫描
          sonar-scanner
      - name: Comment Coverage
        uses: codecov/codecov-action@v3
      - name: Label PR
        run: |
          # 根据改的文件自动打 label
          echo "::notice::Affected: $(git diff --name-only origin/${{ github.base_ref }} | head -5)"
```

## 八、特性分支与泳道环境的联动

### 8.1 自动创建预览环境

```text
特性分支：feature/alice-login-LOGIN-123
  ↓
自动创建预览环境：
  URL: alice-login.preview.myapp.com
  Namespace: preview-alice
  包含服务：
    - login（用户改的服务）
    - api-gateway（透传 X-Lane-User: alice）
    - 其他服务（共用 base 环境）
  资源：低配额（0.5 CPU / 1G）
  TTL：24h 无访问删
  
本质：特性分支 → 短命泳道
```

### 8.2 实现机制

```yaml
# PR webhook → Operator 创建 Lane
apiVersion: lane.dev/v1
kind: Lane
metadata:
  name: alice-login-feature
  namespace: preview-alice
spec:
  user: alice
  service: login
  image: myregistry/login:feature-${COMMIT_SHA}
  branchSource: feature/alice-login-LOGIN-123
  ttl: "24h"
  headerName: x-lane-user
```

### 8.3 PR 状态联动

```text
PR 状态变化 → 预览环境联动：

PR opened → 自动起预览环境 + 部署 PR commit
PR updated (new push) → 更新预览环境
PR merged → 触发 staging 部署（staging 池）
PR closed (未合并) → 清理预览环境
分支删除 → 强制清理

通过 GitHub/GitLab webhook + Operator 实现。
```

## 九、合并策略

### 9.1 4 种合并方式对比

| 方式 | 结果 | 主干历史 | 适合 |
| --- | --- | --- | --- |
| Merge Commit | 保留所有 commit + merge commit | 分叉 | Git Flow |
| Squash Merge | 多个 commit 合成 1 个 | 干净线性 | 特性分支（推荐） |
| Rebase Merge | 单个 commit 但保留作者信息 | 干净线性 | 长期分支 |
| Fast-Forward | 直接移动指针 | 干净线性 | 单人 / 短分支 |

### 9.2 推荐：Squash Merge

```bash
# 命令行
git checkout develop
git merge --squash feature/login-with-wechat-LOGIN-123
git commit -m "feat(login): add wechat oauth support (LOGIN-1234)"
git push origin develop

# 或在 GitHub UI 勾选 "Squash and merge"
```

**优点**：

```text
✅ 主干干净（每个 PR 一个 commit）
✅ commit 信息规范（PR title 沿用）
✅ 容易 revert（revert 一个 commit 就够）
✅ blame 清晰（按 PR 看）
✅ changelog 自动生成（按 commit）
```

### 9.3 不推荐：Merge Commit 洪水

```text
❌ 反例：
master: ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─
         │     │     │     │
       merge  merge  merge  merge
         │     │     │     │
         ●─────●─────●─────●   （100 个 feature commit 平行）

问题：
  - 主干看起来一坨 merge commit
  - bisect 不好用
  - 不容易 revert（要 revert merge + 子 commit）
```

### 9.4 Rebase 的取舍

```text
Rebase 的好处：
  - 提交历史线性（干净）
  - 没有 merge commit
  - bisect 友好

Rebase 的坏处：
  - 改了 commit hash（其他人要 re-pull）
  - 已经 push 的 commit 被改写（避免在共享分支上用）
  - force push 风险

适用：
  - 仅在本地 / 私有分支 rebase
  - 共享分支（已 push 给同事）用 merge
  - 合并主干时用 merge / squash，不要 rebase
```

### 9.5 PR 合并配置（GitHub）

```yaml
# GitHub 仓库设置
# Settings → General → Pull Requests
☑ Allow squash merging
  ☑ Default commit message: "Pull request title"
  ☑ Default commit message: "Pull request description"
☑ Allow merge commits
  ☐ Allow rebase merging                # 关掉
☑ Always suggest updating pull request branches
☑ Automatically delete head branches    # 合并后自动删源分支
```

## 十、长期分支的治理

### 10.1 为什么会有长期分支

```text
常见原因：
  1. 复杂功能开发跨多周
  2. 等待 review 时间过长
  3. 团队成员协作多（多人在同一分支）
  4. 等待产品决策
  5. 紧急救火被长期化

健康指标：
  - 95% 的特性分支 < 1 周
  - 99% 的特性分支 < 2 周
  - < 1% 超过 2 周（需要拆分或 feature flag）
```

### 10.2 治理措施

```text
技术手段：
  - CI 监控分支年龄
  - Slack/邮件报警（> 7 天 / > 14 天）
  - 自动 review reminder
  - 周会 review 长分支
  
管理手段：
  - 拆分大功能
  - 用 feature flag 分阶段合
  - 强制时间盒（time-box）：> 14 天强制重新评估
  - 关联 ticket 验证（业务方确认还要不要）
```

### 10.3 长分支的处理策略

```text
情况 1：分支有冲突
  → rebase 到最新主干
  → 解决冲突
  → 提交 PR
  
情况 2：分支功能太大
  → 拆成多个分支
  → 用 feature flag 控制
  → 第一阶段先合基础设施
  
情况 3：分支过期（业务变了）
  → 评估还要不要
  → 不要了 → 删分支
  → 部分要 → 拆分支
  
情况 4：分支 pending review 太久
  → 团队 review SLA 介入
  → 主管 push 进度
```

## 十一、与团队协作的实践

### 11.1 Pair Programming + 特性分支

```text
场景：两人开发同一功能
  - 共享一个特性分支
  - 定期 commit 同步
  - 提交 PR 时两人共同 author

git commit -m "feat(login): add wechat callback handler

Co-authored-by: Bob <bob@example.com>"
```

### 11.2 Mob Programming + 特性分支

```text
场景：3-5 人共同开发
  - 一个人负责 push
  - 其他人负责 review / 讨论
  - 仍然一个 PR / 一个分支
```

### 11.3 多人协作同一文件

```text
场景：A 改 user.go，B 也改 user.go
方案 1：拆 commit，分段合并
  A: commit 1 (接口定义)
  B: commit 2 (实现)
  
方案 2：分文件
  A: user_model.go（数据层）
  B: user_handler.go（HTTP 层）
  
方案 3：先合一个
  A 先合，B rebase 后合
  
方案 4：feature flag
  A 的代码先用 flag 包起来，B 的代码也用 flag
  合并不冲突
```

### 11.4 跨时区协作

```text
挑战：
  - 12 小时时差
  - 早上 push 的 PR 等晚上才能 review
  - 紧急 fix 等不到人

方案：
  - 每个时区至少 1 个 reviewer
  - 重大 PR 提前一天通知
  - 异步 review（详细的 PR description + 截图）
  - 视频会议 review 大改动
```

## 十二、常见反模式

### 12.1 反模式 1：直接在主干上开发

```text
❌ 错误：
  - 直接在 develop 上改
  - 不走 PR
  - 改了 50 个文件一次性 push
  - 同事拉到一半的代码

✅ 正确：
  - 特性分支独立开发
  - PR 合并
  - Review 后再合
```

### 12.2 反模式 2：长期不合并的分支

```text
❌ 错误：
  - feature/login 开发 3 个月
  - 中间 develop 推了几百 commit
  - merge 时冲突 50+ 文件
  - 解决冲突花 1 周

✅ 正确：
  - 每周 rebase / merge develop
  - 或者拆功能
  - 或者用 feature flag 分阶段合
```

### 12.3 反模式 3：大爆炸 PR

```text
❌ 错误：
  - 一次性 PR 改了 100 个文件
  - 8000 行 diff
  - reviewer 看 2 小时看不完
  - 直接 approve（没认真看）

✅ 正确：
  - 拆 PR（按功能 / 按层）
  - 每个 PR < 500 行
  - 大改动拆成 5-10 个小 PR
```

### 12.4 反模式 4：跳过 Review

```text
❌ 错误：
  - "小改动不用 review"
  - 直接 merge
  - 长期养成习惯
  - 出 bug 时无法追溯

✅ 正确：
  - 所有 PR 都 review
  - 紧急 hotfix 可以先合后审（事后补）
  - 但要限时补审（< 24 小时）
```

### 12.5 反模式 5：merge 爆炸

```text
❌ 错误：
  - 一个 PR 内 merge 50 个 feature 分支
  - 历史一坨 merge commit
  - 看不到有效 commit

✅ 正确：
  - 一对一合并（一个 PR 一个 feature）
  - squash merge
  - 主干干净
```

### 12.6 反模式 6：分支命名不规范

```text
❌ 错误：
  fix / new / test / 我的修改 / 最终版本_final_v3

✅ 正确：
  feature/login-with-wechat-LOGIN-123
  bugfix/order-duplicate-ORDER-567
```

### 12.7 反模式 7：分支里有未提交代码

```text
❌ 错误：
  - 写了一半
  - commit 信息乱写
  - 推到共享分支

✅ 正确：
  - 用 WIP / Draft PR
  - 或者本地 commit 但不 push
  - Draft PR 标明未完成
```

## 十四、度量指标

### 14.1 关键指标

| 指标 | 含义 | 健康值 |
| --- | --- | --- |
| **PR Cycle Time** | PR 从创建到合并的时间 | < 3 天 |
| **Review Time** | 第一个 review 到 approve | < 8 小时 |
| **PR Size** | PR 平均改动行数 | < 500 行 |
| **PR Throughput** | 团队每周合并 PR 数 | 10-30 个/人 |
| **Merge Conflicts** | 合并冲突比例 | < 5% |
| **Branch Age** | 分支寿命 | < 7 天 |

### 14.2 数据采集

```bash
# GitHub API 拉取 PR 数据
gh pr list --state all --limit 1000 --json number,createdAt,mergedAt,additions,deletions \
  | jq '.[] | {
      pr: .number,
      created: .createdAt,
      merged: .mergedAt,
      cycle_hours: (((.mergedAt | fromdateiso8601) - (.createdAt | fromdateiso8601)) / 3600 | floor),
      diff_lines: (.additions + .deletions)
    }'
```

### 14.3 团队看板

```text
每周发团队 PR 报告：

1. PR Cycle Time 平均 / P50 / P90
2. 最长 open 的 5 个 PR
3. Reviewer 工作量（review 了多少 PR）
4. 最活跃的开发者
5. 平均 PR 大小
6. 分支寿命分布
```

## 十五、一句话总结

> **特性分支开发模式的本质 = "每件事独立分支 + PR 闸门 + 主干永远干净"**；
> 关键不在于"用 Git"，而在于"分支寿命 < 2 周 + review 必走 + squash merge + 合并即删分支"；
> 配合 CI/CD 自动预览 + 泳道环境，就能做到"push 一行代码 → 自动预览 → 一键合并 → 自动部署"。
