# 场景设计与实验方法 (Scenario Design & Methodology)

> 本章讲解混沌实验的场景设计方法、典型场景库、实验模板与高级技巧。

## 一、场景设计的核心思想

### 1.1 设计原则

```text
好的混沌场景应满足:
  1. 真实性: 模拟真实会发生的事件
  2. 可控性: 爆炸半径可控
  3. 可测量: SLI 明确
  4. 可重复: 相同输入产生相同结果
  5. 价值性: 能发现真实问题
```

### 1.2 场景设计的反模式

```text
反模式 1: "为故障而故障"
  现象: 乱注入故障
  问题: 没目标, 没价值
  解决: 围绕业务假设设计

反模式 2: "盲目压测"
  现象: 直接上压测
  问题: 不知道测什么
  解决: 先有稳态, 再设计故障

反模式 3: "覆盖所有故障"
  现象: 列了 100 种故障
  问题: 不知道哪个有效
  解决: 从高影响/高概率开始

反模式 4: "运行一次就完"
  现象: 一次性演练
  问题: 没形成持续改进
  解决: 持续自动化
```

## 二、典型故障场景库

### 2.1 按层级分类

```text
硬件层:
  - 服务器宕机
  - 磁盘满
  - CPU 满
  - 内存耗尽
  - 网卡故障

网络层:
  - 网络延迟 (100ms, 1s, 5s)
  - 丢包 (1%, 10%, 30%)
  - 网络分区
  - DNS 故障
  - CDN 故障

应用层:
  - 应用崩溃
  - 应用 hang
  - 内存泄漏
  - GC 频繁
  - 异常抛出

中间件层:
  - 数据库慢/挂
  - 缓存失效
  - 消息队列堆积
  - 第三方服务挂

平台层:
  - K8s 节点故障
  - Pod 驱逐
  - 调度失败
  - API Server 不可用
  - etcd 故障

业务层:
  - 支付服务挂
  - 推荐服务挂
  - 风控服务慢
  - 短信网关挂
```

### 2.2 按业务影响分类

```text
P0 致命 (用户直接感知):
  - 全站不可用
  - 支付失败
  - 数据丢失
  - 业务核心挂

P1 严重 (重要功能受损):
  - 部分功能不可用
  - 性能严重下降
  - 数据不一致

P2 一般 (辅助功能受损):
  - 推荐不工作
  - 统计不更新
  - 通知未发送

P3 轻微 (无感知):
  - 日志不记录
  - 监控告警异常
```

## 三、典型实验场景模板

### 3.1 数据库故障场景

#### 场景 1: Redis 主节点宕机

```text
假说:
  "如果 Redis 主节点宕机 5 分钟,
   系统应自动切换到从节点, 服务不中断"

实验设计:
  目标: Redis 主节点
  操作: 杀 Redis 主进程 / 杀 Redis Pod
  持续: 5 分钟
  监控:
    - Sentinel 切换状态
    - 应用 P99 延迟
    - 业务错误率
  验收: P99 延迟增加 < 1s, 错误率 < 0.1%

工具:
  - Redis: redis-cli SHUTDOWN
  - K8s: Chaos Mesh / Litmus pod-kill
```

#### 场景 2: 数据库主从切换

```text
假说:
  "如果 MySQL 主库宕机, 主从自动切换,
   应用重连后无数据丢失"

实验:
  目标: MySQL 主库
  操作: 杀主库 mysqld 进程
  持续: 3 分钟
  监控:
    - MHA 切换状态
    - 应用重连时间
    - 数据丢失情况
  验收: 切换 < 30s, 无数据丢失
```

#### 场景 3: 数据库慢响应

```text
假说:
  "如果数据库 P99 延迟从 10ms 升到 500ms,
   应用 P99 延迟应 < 1s"

实验:
  目标: MySQL Pod
  操作: 注入 500ms 网络延迟
  持续: 5 分钟
  监控:
    - DB P99 延迟
    - 应用 P99 延迟
    - 超时错误数
  验收: 应用延迟 < 1s, 错误率 < 0.5%
```

### 3.2 微服务故障场景

#### 场景 4: 下游服务不可用

```text
假说:
  "如果订单服务调用支付服务失败,
   应有熔断保护, 不影响订单服务整体可用性"

实验:
  目标: 支付服务
  操作: 网络分区 (切断所有流量) / HTTP 500
  持续: 3 分钟
  监控:
    - 订单服务错误率
    - 熔断器状态
    - 降级逻辑触发
  验收: 订单服务 P99 < 1s, 错误率 < 0.1%
```

#### 场景 5: 服务慢响应

```text
假说:
  "如果推荐服务 P99 响应 5s,
   不应影响商品详情页整体性能"

实验:
  目标: 推荐服务
  操作: 注入 5s 延迟
  持续: 5 分钟
  监控:
    - 商品页 P99 延迟
    - 降级策略 (默认推荐)
    - 错误率
  验收: 商品页延迟 < 500ms (降级生效)
```

#### 场景 6: 雪崩效应

```text
假说:
  "如果 A 服务慢响应,
   不应拖垮 B 服务 (熔断 + 限流)"

实验:
  目标: A 服务
  操作: 注入 10s 延迟 + 持续高并发
  持续: 5 分钟
  监控:
    - B 服务错误率
    - 线程池使用
    - 连接池使用
    - 熔断器状态
  验收: B 服务 P99 < 1s, 无雪崩
```

### 3.3 K8s 故障场景

#### 场景 7: Pod 杀

```text
假说:
  "如果 Pod 被杀, K8s 应该在 30s 内重新调度,
   副本数始终保持 3"

实验:
  目标: Deployment 中所有 Pod
  操作: 随机杀一个 Pod
  持续: 每分钟杀一次, 持续 1 小时
  监控:
    - 副本数 (始终 >= 2)
    - 新 Pod 启动时间
    - 服务中断时间
  验收: 新 Pod 30s 内 Ready, 服务不中断
```

#### 场景 8: 节点宕机

```text
假说:
  "如果 K8s worker 节点宕机,
   Pod 应自动迁移, 数据不丢"

实验:
  目标: 1 个 worker 节点
  操作: drain + cordon + 关闭节点
  持续: 10 分钟
  监控:
    - Pod 重新调度时间
    - 副本数
    - 数据持久性 (PV)
  验收: 30s 内迁移完成, 数据无丢失
```

#### 场景 9: K8s API Server 故障

```text
假说:
  "如果 kube-apiserver 不可用 5 分钟,
   已运行的 Pod 不受影响, 故障恢复后能正常调度"

实验:
  目标: kube-apiserver Pod
  操作: 杀 api-server / 断网
  持续: 5 分钟
  监控:
    - 已运行 Pod 状态
    - 调度功能 (新建 Pod)
    - API 请求 (kubectl get)
  验收: 现有 Pod 不重启, API 恢复后能调度
```

### 3.4 网络故障场景

#### 场景 10: 跨机房网络中断

```text
假说:
  "如果机房 A 和机房 B 网络中断,
   机房 A 能独立服务 1 小时以上"

实验:
  目标: 跨机房专线
  操作: iptables DROP / 网络断开
  持续: 30 分钟
  监控:
    - 机房 A 服务可用性
    - 机房 A P99 延迟
    - 数据同步状态
  验收: 机房 A 服务可用, 延迟无明显增加
```

#### 场景 11: DNS 故障

```text
假说:
  "如果外部 DNS 解析失败,
   应有缓存或重试机制保证服务可用"

实验:
  目标: 外部 DNS 服务
  操作: DNS 不可用
  持续: 5 分钟
  监控:
    - 应用错误率
    - DNS 解析成功率
    - 缓存命中率
  验收: 应用错误率 < 0.1%
```

### 3.5 资源故障场景

#### 场景 12: CPU 满载

```text
假说:
  "如果应用 CPU 满载,
   应自动限流, 不影响其他服务"

实验:
  目标: 1 个应用 Pod
  操作: 注入 100% CPU 压力
  持续: 3 分钟
  监控:
    - 应用 P99 延迟
    - 限流触发
    - 错误率
  验收: 限流生效, 不会拖垮其他服务
```

#### 场景 13: 内存 OOM

```text
假说:
  "如果应用 OOM Kill,
   K8s 应自动重启, 但需在合理时间内恢复"

实验:
  目标: 应用 Pod
  操作: 注入 OOM (stress-ng --vm 1)
  持续: 持续到 OOM
  监控:
    - OOM 次数
    - 重启时间
    - 服务恢复时间
  验收: 30s 内自动重启, 60s 内服务恢复
```

## 四、实验编排 (Workflow)

### 4.1 实验编排原则

```text
单个实验 → 场景 → 流程 → Game Day

逐步复杂:
  1. 单元实验: 一个故障, 一个目标
  2. 组合实验: 多个故障, 一个目标
  3. 场景: 多个实验, 多个目标
  4. Game Day: 跨团队, 完整流程
```

### 4.2 实验编排示例

```text
"数据库故障完整演练":
  Phase 1 (5 min): Redis 慢响应
    → 验证应用超时配置
  Phase 2 (5 min): Redis 不可用
    → 验证熔断降级
  Phase 3 (5 min): Redis 恢复
    → 验证快速恢复
  Phase 4 (5 min): 同时 Redis 慢 + MySQL 慢
    → 验证综合韧性

总计: 20 分钟, 4 阶段, 3 个攻击类型
```

## 五、高级实验方法

### 5.1 渐进式爆炸半径

```text
阶段 1: 1 个实例 (1/10)
  观察: 单点故障的最小爆炸半径影响
  风险: 极低
  时长: 1 小时

阶段 2: 部分实例 (3/10)
  观察: 部分故障的影响
  风险: 低
  时长: 1 小时

阶段 3: 大部分实例 (8/10)
  观察: 高故障率
  风险: 中
  时长: 1 小时

阶段 4: 全部实例 (10/10)
  观察: 全局故障
  风险: 高
  时长: 1 小时
```

### 5.2 蓝绿对比

```text
实验设计:

对照组 (Control):
  - 不注入故障
  - 正常运行

实验组 (Experiment):
  - 注入故障
  - 观察影响

对比:
  - 实验前后 SLI 差异
  - 告警触发
  - 用户反馈

用同一时段:
  - 上午对照组
  - 下午实验组
  - 避免业务高峰差异
```

### 5.3 流量分级

```text
灰度注入:

1. 内测流量 (1%)
   - 内部用户
   - 风险最低

2. 真实流量 1% (100 个用户)
   - 风险低
   - 收集反馈

3. 真实流量 5%
   - 风险中
   - 监控

4. 真实流量 20%
   - 风险中高
   - 告警就绪

5. 真实流量 100%
   - 风险高
   - 全员就位
```

## 八、核心要点速记

### 场景设计原则

```text
1. 围绕业务假设设计
2. 从高影响/高概率开始
3. 爆炸半径可控
4. 持续自动化
5. 总结改进
```

### 典型场景分类

```text
数据库: Redis 死/慢/主从切换/MySQL OOM/分库分表
微服务: 下游挂/慢响应/雪崩
K8s:     Pod 杀/节点宕机/API 不可用
网络:    延迟/丢包/分区/DNS 故障
资源:    CPU/内存/磁盘 满
```

### 实验模板

```yaml
目标: 应用 / 服务
稳态: 关键 SLI 范围
假说: 故障 → 预期行为
攻击: 类型 + 持续 + 范围
停止: 时间 / SLI 突破 / 异常
验证: SLI 变化 / 告警 / 用户反馈
```

### 渐进式方法

```text
小范围 (1 实例)
  → 部分 (10%, 50%)
  → 大部分 (90%)
  → 全部 (100%)

单故障
  → 组合故障
  → 雪崩场景
  → Game Day
```

### 关键指标

```text
- 系统 SLI 变化 (延迟、错误率)
- 告警触发时间和数量
- 恢复时间 (MTTR)
- 用户反馈
- 资源使用变化
```

### 选型建议

```text
- 阿里系 → ChaosBlade 一键命令
- K8s 重度 → Chaos Mesh 场景编排
- 商业平台 → Gremlin 完整 Scenarios
- 学习研究 → 经典 Chaos Monkey
- 中间件测试 → Toxiproxy 网络故障
```

## 二、实验最佳实践
