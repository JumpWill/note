# 混沌工程原则与方法论 (Principles & Methodology)

> 本章详解混沌工程的 5 大核心原则、稳态假说设定、实验设计流程与最佳实践。

## 一、混沌工程五大原则

### 1.1 原则一:建立围绕稳态的假说

```text
核心思想:
  不是 "系统不出故障"
  而是 "故障发生时, 系统保持稳态"

稳态 (Steady State):
  系统正常运行时的可观察指标
  - 吞吐量: 1000 QPS
  - 延迟: P99 < 100ms
  - 错误率: < 0.1%
  - 资源使用: CPU < 70%

假说示例:
  "如果 Redis 主节点宕机 5 分钟,
   系统吞吐量应保持 800 QPS 以上 (允许下降 20%)"
```

#### 稳态指标选择 (SLI)

```text
好的 SLI (Service Level Indicator):
  - 可测量 (有数据)
  - 可比较 (有基线)
  - 反映用户体验
  - 持续采集

分类:
  1. 可用性: 系统正常响应请求的比例
     - HTTP 200/全部请求
     - 业务成功率 (下单成功/全部下单)

  2. 性能: 响应时间
     - P50/P95/P99/P999 延迟
     - 吞吐量 (QPS, RPS)
     - 带宽 (BPS)

  3. 正确性: 业务结果
     - 订单成功率
     - 支付成功率
     - 数据一致性

  4. 资源: 系统开销
     - CPU 使用率
     - 内存使用
     - 网络流量
```

#### SLI 基线建立

```bash
# 1. 收集稳态数据 (1-2 周)
# 2. 计算 P50/P95/P99 延迟
# 3. 计算 QPS 平均/峰值
# 4. 错误率
# 5. 资源使用

# Prometheus + Grafana
# 计算 95 分位数作为稳态区间
avg_over_time(http_request_duration_seconds[7d])
quantile_over_time(0.99, http_request_duration_seconds[7d])
```

### 1.2 原则二:多样化真实世界事件

```text
真实世界故障是多样的, 不是单一故障

故障类型:
  1. 硬件故障
     - 服务器宕机
     - 磁盘损坏
     - 网络断开
     - 数据中心断电

  2. 软件故障
     - 应用崩溃
     - 内存泄漏
     - 死锁
     - OOM

  3. 网络故障
     - 延迟
     - 丢包
     - 分区
     - DNS 解析失败

  4. 依赖故障
     - 数据库慢
     - 缓存失效
     - 第三方服务挂
     - 消息队列堆积

  5. 人为故障
     - 配置错误
     - 部署错误
     - 误操作

组合故障:
  - Redis 慢 + 大量请求 → 系统雪崩?
  - 1 个 K8s 节点宕机 + 网络抖动 → 服务降级?
  - 数据库主从切换 + 应用连接池不足 → 雪崩?
```

#### 故障场景库

```text
建立故障场景库, 分类管理:

硬件层:
  - 服务器宕机
  - 磁盘满
  - CPU 满
  - 内存满
  - 网卡故障

网络层:
  - 网络延迟 (100ms, 1s, 5s)
  - 丢包 (1%, 5%, 10%)
  - 重复
  - 乱序
  - 分区 (网络完全中断)
  - DNS 故障

应用层:
  - 进程崩溃
  - 进程 hang
  - OOM Kill
  - 慢响应
  - 异常抛出
  - 返回错误结果

数据层:
  - DB 连接失败
  - DB 慢查询
  - DB 主从延迟
  - 缓存击穿
  - 缓存雪崩
  - 消息队列堆积

平台层:
  - K8s Node 故障
  - Pod OOM
  - Pod 驱逐
  - 调度失败
```

### 1.3 原则三:在生产环境运行实验

```text
为什么必须在生产环境:

1. 测试环境不能完全模拟
   - 流量模式不同
   - 真实数据不同
   - 网络拓扑不同
   - 依赖版本不同

2. 实验室的 "正确" 不代表生产的 "正确"
   - 测试全过, 生产挂掉
   - 太多生产事故

3. 只有生产环境有真实的 "故障模式"
   - 真实流量冲击
   - 真实网络延迟
   - 真实硬件故障

实验前提:
  ✓ 有完善的监控和告警
  ✓ 有快速回滚能力
  ✓ 团队有人值守
  ✓ 爆炸半径可控
```

#### 渐进式生产演练

```text
阶段 1: 测试环境演练
  目的: 验证实验设计
  风险: 0
  频率: 多次

阶段 2: 预生产演练
  目的: 验证真实环境
  风险: 低
  频率: 每周

阶段 3: 生产低峰演练
  目的: 验证生产环境
  时间: 业务低峰 (凌晨/周末)
  风险: 中
  频率: 每月

阶段 4: 生产常态演练
  目的: 持续验证韧性
  时间: 业务时间
  风险: 高
  频率: 自动 (持续)

阶段 5: 全自动演练
  目的: 智能演练
  工具: AI 辅助
  风险: 受控
  频率: 持续
```

### 1.4 原则四:持续自动化运行实验

```text
为什么需要自动化:

1. 一次性实验不够
   - 系统在变化
   - 新的依赖
   - 新的配置

2. 自动化确保覆盖
   - 不会忘记跑
   - 不会偷懒

3. 流水线集成
   - 每次部署后自动验证
   - 变更前自动 baseline

自动化的形式:
  - 定时任务 (CronJob)
  - CI/CD 集成
  - GitOps 触发
  - 事件驱动 (告警触发演练)
```

#### CI/CD 集成示例

```yaml
# GitHub Actions 示例
name: chaos-experiment
on:
  push:
    branches: [main]
  schedule:
    - cron: '0 2 * * 1'  # 每周一 2 点

jobs:
  chaos:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    
    - name: Setup Chaos
      run: |
        curl -fsSL -o chaosblade https://chaosblade.oss-cn-hangzhou.aliyuncs.com/release/latest/chaosblade-1.7.2-linux64.tar.gz
        tar -xzf chaosblade
    
    - name: Pre-experiment check
      run: |
        # 验证稳态
        ./check-steady-state.sh
    
    - name: Run chaos experiment
      run: |
        # 注入 Redis 延迟
        ./blade create redis delay --time 1000 --addr 10.0.0.10:6379
        
        sleep 60
        
        # 检查系统稳态
        ./check-steady-state.sh
        
    - name: Cleanup
      run: |
        ./blade destroy --help
        if [ $? -ne 0 ]; then
          ./blade destroy $(./blade list | awk '{print $1}')
        fi
    
    - name: Generate report
      run: |
        ./generate-chaos-report.sh
```

### 1.5 原则五:最小化爆炸半径

```text
核心: 不要一次性影响整个系统

爆炸半径控制:
  1. 范围控制
     - 1 个实例 / N 个实例
     - 1 个服务 / 全部服务
     - 1 个可用区 / 全部

  2. 时间控制
     - 短时间故障 (1-5 分钟)
     - 快速恢复
     - 自动回滚

  3. 流量控制
     - 1% 用户 → 10% → 50% → 100%
     - 灰度演练

  4. 影响控制
     - 只影响测试环境
     - 只影响非关键服务
     - 业务低峰期
```

#### 爆炸半径设计

```text
设计爆炸半径的步骤:

1. 明确 "成功" 是什么
   - 哪些 SLI 不能变
   - 哪些可以暂时下降

2. 设定最大爆炸半径
   - 最多影响多少实例
   - 最多持续多久
   - 最多影响多少用户

3. 准备回滚方案
   - 一键停止实验
   - 自动恢复
   - 通知机制

4. 监控和告警
   - 实时监控
   - 异常立即停止
   - 报告生成
```

## 二、稳态假说详解

### 2.1 稳态的定义

```text
稳态 (Steady State):
  系统正常运行时的可观察行为特征
  - 量化指标
  - 可重复
  - 代表用户体验

不是稳态:
  - "系统没崩" → 不可量化
  - "CPU 80%" → 单一指标不全面
  - "响应快" → 模糊

好的稳态:
  - "99% 请求 P99 延迟 < 200ms"
  - "错误率 < 0.1%"
  - "吞吐量 1000-1500 QPS 之间"
```

### 2.2 稳态假说模板

```text
标准模板:
  "如果 [故障场景], 
   那么 [稳态指标] 应保持在 [区间]"

示例 1:
  "如果 Redis 主节点宕机 5 分钟,
   那么系统吞吐量应保持 > 800 QPS,
        P99 延迟应 < 500ms,
        错误率应 < 0.5%"

示例 2:
  "如果网络延迟增加 200ms,
   那么下单成功率应保持 > 99%,
        用户感知延迟应 < 1s"

示例 3:
  "如果 50% 的 K8s 节点宕机,
   那么服务应自动迁移并保持可用,
        数据不应丢失"
```

### 2.3 假说设计原则

```text
好的假说:
  1. 可测量
     - 明确量化指标
     - 可对比
     
  2. 具体
     - 不模糊
     - 不抽象
     
  3. 现实
     - 实际可能发生
     - 不是极端情况
     
  4. 有边界
     - 明确时间
     - 明确范围

不好的假说:
  - "系统应该稳定"
  - "服务应该高可用"
  - "用户应该满意"
```

### 2.4 假说示例集

```text
1. 节点故障
   "如果 K8s worker 节点宕机,
    Pod 应在 5 分钟内自动调度到其他节点,
    服务中断时间 < 30 秒"

2. 数据库故障
   "如果 MySQL 主库宕机,
    主从切换应在 30 秒内完成,
    应用重连后无数据丢失"

3. 网络分区
   "如果机房 A 和机房 B 网络完全中断,
    机房 A 应能独立服务 1 小时以上,
    数据双向同步延迟恢复后能自动合并"

4. 缓存失效
   "如果 Redis 集群整体宕机 10 分钟,
    服务应降级到 DB (慢但可用),
    缓存恢复后无需手动干预"

5. 消息堆积
   "如果 RocketMQ 消费延迟 10 分钟,
    服务应自动告警并临时限流,
    不应影响正常请求"

6. 第三方故障
   "如果支付服务完全不可用,
    下单应能继续但支付重试,
    第三方恢复后订单状态应自动同步"
```

## 三、实验设计流程

### 3.1 标准实验流程

```text
实验流程 (8 步):

1. 选择实验对象
   2. 定义稳态
   3. 提出假说
   4. 设计实验
        ↓
5. 准备环境
        ↓
6. 执行实验
        ↓
7. 监控分析
        ↓
8. 总结改进
```

### 3.2 详细流程

#### 步骤 1: 选择实验对象

```text
决定对什么做实验:

优先级 (高 → 低):
  1. 关键路径服务
     - 用户面对的服务
     - 核心交易流程

  2. 高风险服务
     - 经常出问题
     - 依赖复杂
     - 数据关键

  3. 未知行为
     - 长期没出过问题
     - 团队信心不足
     - 实际是脆弱的

评估维度:
  - 业务关键性
  - 当前韧性信心
  - 历史故障频率
  - 复杂度
```

#### 步骤 2: 定义稳态

```text
明确"正常"是什么:

1. 选择 SLI (推荐 3-5 个)
   - 业务 SLI: 成功率
   - 性能 SLI: 延迟
   - 资源 SLI: CPU/内存

2. 收集基线数据 (1-2 周)
   - P50 / P95 / P99
   - 平均/峰值
   - 异常模式

3. 设定稳态区间
   - 例: P99 延迟 = 80-120ms
   - 例: 错误率 < 0.1%
   - 例: 吞吐量 1000-1500 QPS
```

#### 步骤 3: 提出假说

```text
基于稳态, 推断故障影响:

模板:
  "如果 [故障] 发生,
   我们的系统应该 [预期行为]"

假说三要素:
  1. 故障 (清晰可注入)
  2. 预期 (可测量)
  3. 边界 (时间/范围)

示例:
  "如果 Redis 主节点延迟 100ms 持续 5 分钟,
   我们期望 P99 延迟 < 300ms (基线 100ms)
   而非 < 100ms"
```

#### 步骤 4: 设计实验

```text
实验设计清单:

1. 实验类型
   - 延迟
   - 错误
   - 资源耗尽
   - 节点故障
   - 网络分区

2. 实验范围
   - 单实例/部分/全部
   - 单服务/全服务
   - 范围百分比

3. 实验时间
   - 持续多久
   - 业务高峰/低峰

4. 停止条件
   - 达到时间
   - SLI 突破阈值
   - 人工停止
   - 异常情况

5. 监控
   - 实验期间关注什么
   - 实时仪表盘
   - 异常告警
```

#### 步骤 5-7: 执行监控分析

```text
5. 准备
   - 通知相关团队
   - 准备回滚方案
   - 准备监控仪表盘
   - 值守人员就位

6. 执行
   - 在非高峰时段
   - 逐步加大范围
   - 实时监控
   - 记录现象

7. 分析
   - SLI 是否在稳态区间?
   - 系统反应是否符合预期?
   - 发现了什么脆弱点?
   - 监控告警是否及时?
```

#### 步骤 8: 总结改进

```text
实验报告:

1. 实验信息
   - 时间 / 范围 / 实验人

2. 假说 vs 结果
   - 原始假说
   - 实际结果
   - 偏差

3. 发现
   - 脆弱点
   - 监控盲点
   - 流程问题

4. 改进措施
   - 短期 (紧急)
   - 中期 (1 月)
   - 长期 (季度)

5. 跟踪
   - 责任人
   - 时间点
   - 验收标准
```

## 四、故障爆炸半径控制

### 4.1 范围控制

```text
爆炸半径 = 影响范围

可控维度:
  1. 范围
     - 单实例
     - 一定比例 (10%, 50%)
     - 特定标签 (env=canary)

  2. 时间
     - 短时故障 (秒级)
     - 限时实验 (分钟级)
     - 持续监控

  3. 类型
     - 网络 (可恢复)
     - 进程 (可恢复)
     - 资源 (可恢复)
     - 数据 (慎用, 难恢复)
```

### 4.2 灰度演练

```text
阶梯式灰度:

阶段 1: 1 个实例 (1/10)
阶段 2: 3 个实例 (3/10)
阶段 3: 全部实例 (10/10)

每阶段观察:
  - 业务 SLI 是否正常
  - 监控告警是否触发
  - 用户反馈

任意阶段异常:
  - 立即停止实验
  - 恢复环境
  - 分析根因
```

### 4.3 紧急停止机制

```text
必须能立即停止实验:

1. 自动化停止
   - SLI 突破阈值自动停
   - 错误率 > X% 自动停
   - 延迟 > Y ms 自动停

2. 手动停止
   - 一键停止命令
   - 紧急联系人
   - 演练应急流程

3. 时间限制
   - 强制超时
   - 最长持续时间

实现:
  chaosblade create ... --timeout 600  # 10 分钟自动停
```

## 五、渐进式实验方法

### 5.1 从小范围开始

```text
原则: 小 → 中 → 大

阶段 1: 单元测试环境
  - 验证实验设计
  - 验证工具配置
  - 0 影响

阶段 2: 预生产环境
  - 真实流量
  - 真实数据
  - 低影响

阶段 3: 生产低峰
  - 业务低峰时段
  - 部分流量
  - 中影响

阶段 4: 生产常态
  - 业务时间
  - 全流量
  - 高影响
```

### 5.2 故障影响分级

```text
故障严重程度:

P0 致命:
  - 全站不可用
  - 数据丢失
  - 资金损失
  - 必须立即停止

P1 严重:
  - 部分功能不可用
  - 性能大幅下降
  - 需要立即处理

P2 一般:
  - 个别请求失败
  - 性能轻度下降
  - 可观察后处理

P3 轻微:
  - 可自动恢复
  - 短暂影响
  - 记录后处理
```

## 六、核心要点速记

### 五大原则

```text
1. 建立围绕稳态的假说 (Steady State + Hypothesis)
2. 多样化的真实世界事件 (多种故障)
3. 在生产环境运行实验 (Production)
4. 持续自动化运行实验 (CI/CD + 定时)
5. 最小化爆炸半径 (Blast Radius)
```

### 稳态假说模板

```text
"如果 [故障场景] 发生,
 那么 [稳态指标] 应保持在 [区间]"
```

### 实验流程 (8 步)

```text
1. 选择实验对象
2. 定义稳态
3. 提出假说
4. 设计实验
5. 准备环境
6. 执行实验
7. 监控分析
8. 总结改进
```

### 稳态指标 (SLI) 选型

```text
- 可用性: 成功率
- 性能: P50/P95/P99 延迟
- 正确性: 业务结果
- 资源: CPU/内存/网络
```

### 爆炸半径控制

```text
- 范围: 单实例 → 全部
- 时间: 短时 → 持续
- 类型: 网络 → 进程 → 资源
- 影响: 测试 → 生产
```

### 渐进式

```text
小范围 → 预生产 → 生产低峰 → 生产常态
```

### 假说示例

```text
"如果 Redis 主节点延迟 100ms 持续 5 分钟,
 P99 延迟应 < 300ms, 错误率 < 0.5%"
```

### 实验报告要素

```text
1. 基本信息 (时间, 范围, 负责人)
2. 假说 vs 实际结果
3. 发现的脆弱点
4. 改进措施与责任人
```

### 五大核心价值

```text
1. 提前发现脆弱点
2. 验证架构假设
3. 提升 SLA
4. 降低事故成本
5. 建立故障文化
```
