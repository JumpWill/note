# 混沌工程总结与速记 (Summary & Quick Reference)

> 本章总结混沌工程的核心要点,提供速记表,便于快速查阅和面试准备。

## 一、混沌工程核心要点

### 1.1 一句话定义

```text
混沌工程 = 在分布式系统上做受控实验,
        通过主动注入故障来建立系统韧性的信心
```

### 1.2 五大原则

```text
1. 建立围绕稳态的假说
   - 明确"正常"的量化指标 (SLI)
   - 设定预期行为

2. 多样化的真实世界事件
   - 不只测单一故障
   - 覆盖各种组合故障

3. 在生产环境运行实验
   - 测试环境不能完全模拟
   - 真实流量、真实依赖

4. 持续自动化运行实验
   - 一次性实验不够
   - 集成到 CI/CD

5. 最小化爆炸半径
   - 小范围开始
   - 准备回滚方案
```

### 1.3 核心价值

```text
业务价值:
  - 提前发现脆弱点
  - 提升 SLA
  - 降低事故成本
  - 业务连续性

技术价值:
  - 验证架构假设
  - 发现隐藏依赖
  - 提升监控有效性
  - 推动架构改进

团队价值:
  - 建立故障文化
  - 提升应急能力
  - 跨团队协作
  - 工程师成长
```

## 二、Netflix Chaos Monkey 起源

```text
2008: Netflix 决定从自建数据中心迁移到 AWS 云
2010: Chaos Monkey 诞生
   - 工作日 9am-3pm 随机杀 EC2 实例
   - 工程师必须时刻准备恢复
2012: 公开代码
2017: 《混沌工程》书出版
2019: CNCF 推动
现在: 工具生态成熟 (Chaos Mesh, Litmus, ChaosBlade, Gremlin)
```

## 五、稳态与 SLI

### 5.1 稳态定义

```text
稳态 (Steady State):
  系统正常运行时的可观察行为特征
  - 可测量
  - 可比较
  - 反映用户体验

稳态指标 (SLI):
  - 可用性: 成功率 > 99.9%
  - 性能: P99 延迟 < 200ms
  - 错误率: < 0.1%
  - 资源: CPU < 70%, 内存 < 80%
```

### 5.2 假说模板

```text
"如果 [故障场景] 发生,
 那么 [稳态指标] 应保持在 [区间]"

示例:
"如果 Redis 主节点宕机 5 分钟,
  P99 延迟应 < 500ms, 错误率 < 0.5%,
  系统吞吐量应 > 800 QPS"
```

### 5.3 RED/USE 方法

```text
RED 方法 (服务):
  Rate:     每秒请求数
  Errors:   错误数/错误率
  Duration: 响应时间 (P50/P95/P99)

USE 方法 (资源):
  Utilization: 资源使用率
  Saturation:  资源饱和度
  Errors:      错误事件
```

## 六、实验流程速记

### 6.1 四阶段

```text
1. 准备 (1-2 周)
   - 选定目标
   - 定义稳态
   - 提出假说
   - 设计实验
   - 通知团队

2. 执行 (30 分钟 - 4 小时)
   - 启动实验
   - 实时监控
   - 准备停止
   - 记录现象

3. 收尾 (30 分钟 - 1 小时)
   - 销毁实验
   - 验证恢复
   - 收集数据

4. 复盘 (1 周)
   - 写报告
   - 团队分享
   - 改进分配
   - 跟踪验证
```

### 6.2 实验编排

```text
单故障 → 组合故障 → 雪崩场景 → Game Day
小范围 → 部分 → 大部分 → 全部
测试环境 → 预生产 → 生产低峰 → 生产常态
```

### 6.3 渐进式爆炸半径

```text
1. 单实例 (1/10) - 验证工具
2. 部分实例 (3/10) - 验证影响
3. 大部分实例 (8/10) - 验证韧性
4. 全部实例 (10/10) - 验证极限
```

## 七、立即停止条件

```text
任一满足立即停止:
1. SLI 突破阈值 (> 2 倍基线)
2. 错误率 > 设定阈值
3. 数据丢失或损坏
4. 用户投诉
5. 业务影响超出预期
6. 人员不足
7. 真实故障发生
```

### 一键停止脚本

```bash
# ChaosBlade
for uid in $(blade list --type=create -o json | jq -r '.[].uid'); do
  blade destroy $uid
done

# Chaos Mesh
kubectl delete podchaos,networkchaos,stresschaos --all -A

# Toxiproxy
toxiproxy-cli toxic remove -n <proxy> -t <toxic>
```

## 八、典型故障场景

### 8.1 数据库故障

```text
- Redis 主节点宕机 → 主从切换
- Redis 整体不可用 → 缓存击穿
- MySQL 主库宕机 → 主从切换
- MySQL 慢查询 → 业务超时
- 数据库连接池耗尽 → 雪崩
```

### 8.2 微服务故障

```text
- 下游服务不可用 → 熔断降级
- 下游服务慢响应 → 雪崩
- 服务自身崩溃 → 重启恢复
- 服务资源耗尽 → 限流保护
- 服务间网络中断 → 重试退避
```

### 8.3 K8s 故障

```text
- Pod 杀 → 副本重启
- 节点宕机 → Pod 漂移
- K8s API 不可用 → 已运行 Pod 不受影响
- etcd 故障 → 集群不可写
- 调度失败 → 资源不足
```

### 8.4 网络故障

```text
- 网络延迟 → 业务超时
- 丢包 → 重试
- 网络分区 → 降级
- DNS 故障 → 服务发现失败
- 跨机房断网 → 多活容灾
```

### 10.2 ChaosBlade

```bash
# CPU
blade create cpu fullload
blade create cpu usage --usage 80

# 内存
blade create mem load --size 1024

# 网络
blade create network delay --time 1000
blade create network loss --percent 30
blade create network bandwidth --rate 1mbps
blade create network dns --domain example.com

# 进程
blade create process kill --process nginx

# 容器/K8s
blade create k8s pod-kill --names web
blade create k8s pod-network --names web --network-type delay
blade create k8s pod-cpu --names web --cpu-percent 80

# 应用
blade create redis delay --addr 10.0.0.10:6379
blade create mysql delay --addr 10.0.0.11:3306
blade create jvm OOM

# 管理
blade status <UID>
blade list --type=create
blade destroy <UID>
```

### 10.3 Toxiproxy

```bash
# 创建代理
toxiproxy-cli create -n mysql -l 0.0.0.0:20000 -u mysql:3306

# 添加故障
toxiproxy-cli toxic add -n mysql -t latency -a latency=200
toxiproxy-cli toxic add -n mysql -t loss -a probability=0.3
toxiproxy-cli toxic add -n mysql -t bandwidth -a rate=1024

# 移除
toxiproxy-cli toxic remove -n mysql -t latency

# 删除
toxiproxy-cli toxiproxy delete -n mysql
```

### 10.4 Litmus

```yaml
spec:
  appinfo:
    appkind: deployment
    applabel: app=nginx
  chaosServiceAccount: chaos-admin
  experiments:
  - name: pod-delete
```

## 十一、成熟度模型

```text
Level 0: 未开始
Level 1: 手动注入 (脚本)
Level 2: 工具化 (ChaosBlade / Mesh)
Level 3: 流程化 (定期演练)
Level 4: 自动化 (CI/CD 集成)
Level 5: 智能化 (AI 辅助)
```

### 11.1 升级路径

```text
Level 0 → 1: 写第一个 kill 脚本
Level 1 → 2: 引入工具 (ChaosBlade)
Level 2 → 3: 定期演练 (每月)
Level 3 → 4: CI/CD 集成
Level 4 → 5: AI 辅助场景推荐
```

## 十三、面试速记

### 13.1 常见问题

```text
Q1: 什么是混沌工程?
A: 在分布式系统上做受控实验, 通过主动注入故障来建立系统韧性的信心

Q2: 五大原则是什么?
A: 稳态假说 / 多样事件 / 生产环境 / 持续自动化 / 最小爆炸半径

Q3: 混沌工程和测试的区别?
A: 传统测试: 验证已知路径; 混沌工程: 探索未知行为

Q4: Netflix Chaos Monkey 是什么?
A: 2010 年 Netflix 开发的工具, 随机杀 EC2 实例测系统韧性

Q5: 怎么做 Redis 故障演练?
A: 用 Toxiproxy 加延迟, 或 ChaosBlade kill Redis Pod, 观察熔断降级

Q6: 混沌工程成熟度分几级?
A: 5 级 (Level 1 手动 → Level 5 智能化)

Q7: 怎么选工具?
A: K8s → Chaos Mesh; 实验库 → Litmus; 阿里 → ChaosBlade; 商业 → Gremlin

Q8: 实验什么时候停止?
A: SLI 突破阈值 / 错误率超限 / 数据丢失 / 用户投诉

Q9: 怎么写假说?
A: 模板: "如果 [故障], 那么 [稳态指标] 应保持在 [区间]"

Q10: 怎么做生产演练?
A: 渐进式: 小范围 → 部分 → 大部分 → 全部, 业务低峰期
```

### 13.2 概念对比

```text
- 混沌工程 vs 测试: 测试验已知, 混沌探未知
- 混沌工程 vs SRE: SRE 救火, 混沌防火
- 混沌工程 vs 性能测试: 性能测正常, 混沌测故障
- 故障注入 vs 故障测试: 注入是手段, 测试是目的
- 稳态 vs 异常态: 稳态是参考, 异常是偏离
- 爆炸半径 vs 影响范围: 都是控制故障范围
```

### 13.3 选型对比表

## 十四、一句话总结

```text
混沌工程 = 主动故障 + 验证韧性 + 持续改进
  1. 故障不可避免, 主动制造
  2. 假设 + 实验 + 验证
  3. 生产环境演练
  4. 持续改进闭环
  5. 小范围 + 自动化

核心价值: 提前发现脆弱点, 提升 SLA, 降低事故成本
```

### 14.1 三大关键点

```text
1. 找稳态 - 知道"正常"是什么
2. 做实验 - 主动注入故障
3. 持续改进 - 闭环解决问题
```

### 14.2 五大速记

```text
1. SRE: SLO/SLI 是稳态指标
2. 工具: Chaos Mesh / Litmus / ChaosBlade
3. 原则: 稳态 / 真实 / 生产 / 持续 / 最小
4. 流程: 准备 / 执行 / 收尾 / 复盘
5. 价值: 主动发现 / 提升 SLA / 降低成本
```

### 14.3 入门推荐

```text
第一步: 阅读《混沌工程》书
第二步: 选 Chaos Mesh (K8s) 或 ChaosBlade (其他)
第三步: 选一个非核心服务做小范围演练
第四步: 逐步扩大到核心服务
第五步: 集成到 CI/CD
第六步: 定期组织 Game Day
```
