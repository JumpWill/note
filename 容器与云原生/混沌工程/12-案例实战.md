## 二、案例 1: 微服务故障演练(支付场景)

### 场景

```text
业务: 支付服务
架构: 订单服务 → 支付服务 → 银行 API
SLA:   99.99%
```

### 实验设计

```text
假说:
  "如果支付服务响应延迟 5 秒,
   订单服务应该有熔断保护, 不影响下单流程"

实验:
  - 目标: 支付服务
  - 攻击: 5 秒延迟
  - 持续: 3 分钟
  - 监控:
    - 订单成功率
    - 支付成功率
    - 熔断器状态
    - P99 延迟
  - 验收: 订单服务 P99 < 1s, 错误率 < 0.1%
```

### 执行脚本

```bash
#!/bin/bash
# payment-chaos.sh

echo "=== 支付服务故障演练 ==="

# 1. 演练前基线
echo "1. 演练前基线..."
BEFORE_SUCCESS=$(curl -s http://api/metrics | grep order_success_rate | awk '{print $2}')
BEFORE_P99=$(curl -s http://api/metrics | grep order_p99_latency | awk '{print $2}')

echo "基线: 成功率=$BEFORE_SUCCESS, P99=$BEFORE_P99"

# 2. 通知团队
echo "2. 通知团队..."
echo "支付服务演练, 持续 3 分钟, 订单可能延迟 5s"

# 3. 启动故障
echo "3. 启动故障..."
TOXIC=$(curl -s -X POST http://toxiproxy:8474/proxies/payment/toxics \
  -d '{"type": "latency", "attributes": {"latency": 5000}}' | jq -r '.name')

echo "故障已启动, toxic=$TOXIC"

# 4. 观察 (持续 3 分钟)
echo "4. 观察 3 分钟..."
for i in {1..36}; do
  sleep 5
  SUCCESS=$(curl -s http://api/metrics | grep order_success_rate | awk '{print $2}')
  P99=$(curl -s http://api/metrics | grep order_p99_latency | awk '{print $2}')
  PAYMENT_ERROR=$(curl -s http://api/metrics | grep payment_error_rate | awk '{print $2}')
  echo "[$i] 订单成功=$SUCCESS, P99=$P99, 支付错误=$PAYMENT_ERROR"
  
  # 异常检测
  if (( $(echo "$SUCCESS < 0.95" | bc -l) )); then
    echo "ALERT: 订单成功率 < 95%, 立即停止演练"
    break
  fi
done

# 5. 销毁故障
echo "5. 销毁故障..."
curl -s -X DELETE http://toxiproxy:8474/proxies/payment/toxics/latency

# 6. 验证恢复
echo "6. 等待 5 分钟恢复..."
sleep 300
AFTER_SUCCESS=$(curl -s http://api/metrics | grep order_success_rate | awk '{print $2}')
echo "基线: $BEFORE_SUCCESS, 演练后: $AFTER_SUCCESS"

# 7. 报告
cat << EOF
=== 演练报告 ===
假说成立: ✓
订单服务在支付 5s 延迟时: 成功率 $BEFORE_SUCCESS → $SUCCESS
熔断器触发: ✓
降级策略生效: ✓
改进项: 监控告警可更详细
EOF
```

### 结果

```text
演练结果:
  - 订单服务成功触发熔断 (10 秒内)
  - 50% 流量被熔断, 50% 快速失败
  - 整体订单成功率: 99.95% → 95% (5s 内)
  - 5s 后熔断器半开, 试探性请求通过
  - 10s 后完全恢复
  - 业务影响: 控制在 10 秒

改进项:
  1. 熔断器阈值过严, 部分正常请求被误熔断
  2. 监控告警不够详细 (没显示熔断器状态)
  3. 缺少支付服务降级到"余额支付"的备用通道
```

## 三、案例 2: Redis 主从切换演练

### 场景

```text
业务: 核心 API 服务
依赖: Redis Cluster (3 主 3 从)
目标: 验证 Redis 故障时 SLA 不降级
```

### 实验步骤

```bash
# 1. 演练前状态
redis-cli -h redis-master INFO replication
# role:master
# connected_slaves:2

# 2. 准备实验
# 配置 Sentinel (如果未配)
redis-cli -h redis-sentinel SENTINEL masters
# 自动选主

# 3. 启动故障 - 杀 Redis master
echo "杀 Redis master..."
kubectl delete pod redis-master-0 -n production

# 4. 观察故障转移
watch -n 1 "redis-cli -h redis-sentinel SENTINEL get-master-addr-by-name mymaster"

# 5. 观察应用
watch -n 1 "curl -s http://api:8080/metrics | grep -E 'redis_connected|error_rate'"

# 6. 恢复
kubectl apply -f redis-master-statefulset.yaml

# 7. 验证恢复
redis-cli -h redis-new-master INFO replication
```

### 结果

```text
切换时间: 7 秒 (符合预期 < 10 秒)
业务影响: 7 秒内 50 个请求失败
  - 失败请求: 重试机制生效, 第二次成功
  - 用户感知: 无明显卡顿 (因为重试快)

发现问题:
  1. 应用连接池在切换瞬间全部失效
  2. 重连后 30% 连接仍指向旧 master
  3. 监控告警延迟 30 秒才发现 (期望 5 秒)

改进:
  1. 应用连接池加健康检查
  2. 定期刷新连接
  3. 优化监控告警 (从 30s 降到 5s)
```

## 四、案例 3: Redis 雪崩演练

### 场景

```text
业务: 商品详情页
依赖: Redis 缓存商品信息
场景: 模拟 Redis 整体不可用, 验证降级到 DB
```

### 实验

```bash
# 1. 启动故障 - 阻断 Redis 流量
echo "Redis 雪崩演练开始"
TOXIC=$(curl -s -X POST http://toxiproxy:8474/proxies/redis-cluster/toxics \
  -d '{"type": "timeout", "attributes": {"timeout": 0}}' | jq -r '.name')

# 2. 观察应用
watch -n 1 "
  echo '=== 缓存命中率 ==='
  redis-cli -h app INFO stats | grep hit_rate
  echo '=== DB QPS ==='
  curl -s http://api:8080/metrics | grep -E 'db_queries_per_sec'
  echo '=== 业务延迟 ==='
  curl -s http://api:8080/metrics | grep p99_latency
"

# 3. 观察 5 分钟后停止
sleep 300

# 4. 销毁故障
curl -s -X DELETE http://toxiproxy:8474/proxies/redis-cluster/toxics/timeout

# 5. 验证恢复
sleep 60
echo "Redis 已恢复, 业务正常"
```

### 结果

```text
关键发现:
  ✓ 缓存击穿保护生效 (单 key 互斥锁)
  ✓ 服务降级到 DB, 业务可用
  ✗ DB 压力大 (QPS 增长 10 倍)
  ✗ 商品详情延迟 P99 从 50ms 涨到 800ms
  ✗ 部分 DB 连接池耗尽

改进:
  1. 增加 DB 读副本
  2. 实现多级缓存 (本地缓存 + Redis)
  3. 增加 Redis Cluster 节点
  4. 优化热点 key 过期策略
```

## 五、案例 4: K8s 节点故障演练

### 场景

```text
业务: 核心 API
部署: Deployment 3 副本, 跨 2 节点
目标: 验证节点宕机时 Pod 自动漂移
```

### 实验

```bash
# 1. 演练前
kubectl get pod -l app=api -o wide
# api-abc-1   node-1
# api-abc-2   node-1
# api-abc-3   node-2

# 2. 模拟节点宕机
echo "开始演练: 关闭 node-1"
# 方式 1: drain (推荐)
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data --force

# 方式 2: 模拟硬件故障 (更激进)
# ssh node-1 "shutdown -h now"

# 3. 观察 Pod 重新调度
watch -n 1 "kubectl get pod -l app=api -o wide"

# 4. 观察流量
watch -n 1 "curl -s http://api:8080/metrics | grep -E 'error_rate|replicas'"

# 5. 恢复节点
# 启动 node-1 (如果是物理关机)
# 或:
kubectl uncordon node-1

# 6. 验证恢复
sleep 60
kubectl get pod -l app=api -o wide
```

### 结果

```text
关键数据:
  - Pod 重新调度时间: 45 秒 (符合 K8s 默认 5 分钟超时)
  - 业务中断: 30 秒 (重调度期间)
  - 数据丢失: 无 (Pod 无状态)
  - 副本数: 3/3 恢复

发现问题:
  1. Pod 调度时间过长 (45 秒)
     原因: 默认 node-monitor-grace-period 是 40 秒
     解决: 调整到 10 秒 (更快发现节点故障)
  
  2. 部分 Pod 启动慢 (30 秒)
     原因: 镜像拉取慢
     解决: 节点预加载镜像
  
  3. readiness probe 配置过严
     新 Pod 启动后 30 秒才加入 Service
     解决: 优化 readiness probe

改进:
  1. 调整 K8s 节点故障检测参数
  2. 节点预加载基础镜像
  3. 优化 Probe 配置
```

## 六、案例 5: 跨机房网络分区演练

### 场景

```text
业务: 多活电商 (上海 + 北京 双中心)
正常: 两个机房分担流量
故障: 模拟网络中断
目标: 验证单机房能独立运行
```

### 实验

```bash
# 1. 演练前
# 检查当前机房状态
curl -s http://shanghai-api:8080/health
curl -s http://beijing-api:8080/health

# 检查流量分布
curl -s http://api:8080/metrics | grep datacenter_traffic

# 2. 模拟网络中断
echo "断开上海 - 北京 网络"
# 方式 1: 路由器配置 (真实)
# 方式 2: iptables 模拟
iptables -A FORWARD -s 10.0.0.0/8 -d 10.1.0.0/8 -j DROP
iptables -A FORWARD -s 10.1.0.0/8 -d 10.0.0.0/8 -j DROP

# 3. 观察 (5 分钟)
watch -n 5 "
  echo '=== 上海机房 ==='
  curl -s http://shanghai-api:8080/health
  echo '=== 北京机房 ==='
  curl -s http://beijing-api:8080/health
  echo '=== 跨机房请求 ==='
  curl -s --max-time 5 http://shanghai-api:8080/cross-region-test
"

# 4. 恢复网络
iptables -D FORWARD -s 10.0.0.0/8 -d 10.1.0.0/8 -j DROP
iptables -D FORWARD -s 10.1.0.0/8 -d 10.0.0.0/8 -j DROP

# 5. 验证恢复
sleep 60
```

### 结果

```text
关键发现:
  ✓ DNS 切换正常 (1 分钟内)
  ✓ 上海机房独立运行 30 分钟
  ✓ 订单在两个机房都能完成
  ✗ 数据同步延迟 5 分钟
  ✗ 部分用户被分配到不可用机房
  ✗ 跨机房库存不同步

改进:
  1. 优化 DNS 切换 (10 秒内)
  2. 实现数据双向同步
  3. 实现机房级别限流
  4. 完善跨机房数据同步机制
```

## 七、案例 6: 双 11 大促压测 + 故障演练

### 场景

```text
业务: 电商大促
预期: 100 万 QPS
风险: 真实流量 + 故障
目标: 验证限流 + 降级
```

### 完整方案

```bash
#!/bin/bash
# 11-chaos.sh - 双 11 演练

echo "=== 双 11 演练 ==="

# Phase 1: 基础流量 (10 分钟)
echo "Phase 1: 10 万 QPS 基准"
./load-test.sh --qps 100000 --duration 600
./collect-metrics.sh

# Phase 2: 峰值流量 (5 分钟)
echo "Phase 2: 50 万 QPS 峰值"
./load-test.sh --qps 500000 --duration 300

# Phase 3: 峰值 + Redis 故障 (3 分钟)
echo "Phase 3: 50 万 QPS + Redis 故障"
./load-test.sh --qps 500000 --duration 300 &
LOAD_PID=$!
sleep 30
./kill-redis.sh
wait $LOAD_PID

# Phase 4: 峰值 + 数据库故障 (3 分钟)
echo "Phase 4: 50 万 QPS + DB 故障"
./load-test.sh --qps 500000 --duration 300 &
LOAD_PID=$!
sleep 30
./inject-db-latency.sh --time 5000
wait $LOAD_PID

# Phase 5: 恢复 + 验证
./cleanup.sh
./verify-recovery.sh
```

### 结果

```text
完整数据:
                基线      Phase1    Phase2    Phase3     Phase4
实际 QPS:      10万      10万      48万      45万       42万
成功率:         99.95%    99.93%    99.8%     99.2%      98.5%
P99 延迟:       80ms     85ms      200ms     600ms     1.2s
限流触发:       无       无        部分      大量      大量
降级触发:       无       无        无        是        是
Redis 故障:     -        -        -        影响 5%   -
DB 故障:        -        -        -        -         影响 10%

关键发现:
  1. 限流配置合理, 防止了系统雪崩
  2. 降级策略有效, 保护了核心业务
  3. 部分非核心功能丢失
  4. 监控告警全部触发

改进:
  1. 优化限流阈值
  2. 增加降级开关粒度
  3. 提前扩容 Redis 容量
  4. 数据库连接池优化
```

## 八、案例 7: AI 推理服务演练

### 场景

```text
业务: AI 模型推理 (GPU 服务)
架构: K8s + GPU (nvidia)
模型: 7B 大模型, 推理耗时 500ms
```

### 实验

```bash
# 1. GPU 故障演练
echo "GPU 故障演练"
blade create k8s pod-cpu \
  --namespace ai \
  --names inference-0 \
  --cpu-percent 100

# 2. GPU 内存故障
echo "GPU 内存故障"
./gpu-stress --memory 80%

# 3. 模型加载慢
echo "模拟模型加载慢"
./inject-model-load-delay.sh --time 30000

# 4. 节点 GPU 故障
echo "模拟 GPU 节点故障"
kubectl cordon node-gpu-1
kubectl drain node-gpu-1 --ignore-daemonsets

# 5. 网络分区 (推理服务到模型服务)
echo "网络分区"
./simulate-network-partition.sh inference-0 model-server
```

### 结果

```text
GPU 演练关键数据:
  - GPU 故障: 自动迁移到其他 GPU 节点
  - 推理延迟: P99 涨到 2s (1.5s 排队 + 0.5s 推理)
  - 服务可用性: 99.9% (多副本)
  - GPU 利用率: 95%

关键发现:
  1. GPU 共享策略不优化 (MIG 没用)
  2. 模型加载慢 (10s), 影响弹性
  3. GPU 故障检测慢 (30s)

改进:
  1. 使用 MIG (Multi-Instance GPU) 切分
  2. 模型预热
  3. GPU 健康检查
  4. 模型多副本 + 负载均衡
```

```text
    - 熔断效果

    - 监控告警

12:30 - 13:30  午餐 + 讨论

13:30 - 14:30  Phase 4: K8s 故障
  场景: 节点宕机 + Pod 漂移
  操作: drain + cordon
  观察:
    - 调度时间
    - 中断时长
    - 副本数
  复盘:
    - 调度参数
    - 中断时长
    - 改进

14:30 - 15:30  Phase 5: 综合故障
  场景: Redis 慢 + DB 慢
  操作: 同时注入两种故障
  观察:
    - 系统雪崩?
    - 自动降级?
    - 业务影响?
  复盘:
    - 综合韧性
    - 改进方向

15:30 - 16:30  总结改进
  - 汇总所有发现
  - 优先级排序
  - 分配改进项
  - 时间表
  - 责任人
  - 验收标准
```

## 十二、核心要点速记

### 案例分类

```text
数据库: Redis 主从切换 / MySQL 故障 / 雪崩
微服务: 熔断 / 降级 / 雪崩
K8s:     Pod 杀 / 节点宕机
网络:    分区 / 延迟 / 丢包
业务:    双 11 / 黑五
```

### 演练关键数据

```text
- Redis 主从切换: 7 秒
- K8s Pod 漂移: 45 秒
- 数据库故障恢复: 30 秒
- 跨机房切换: 1 分钟
- 缓存击穿保护: 5 秒内
```

### 常见发现 (Top 10)

```text
1. 熔断器配置不当
2. 监控告警延迟
3. K8s 故障检测慢
4. 数据库连接池耗尽
5. Redis 缓存击穿
6. 跨机房数据同步延迟
7. 消息队列积压
8. 限流阈值不准确
9. 降级开关粒度粗
10. 数据备份恢复慢
```

### Game Day 流程

```text
1. 准备 (2 周)
2. 介绍 (30 分钟)
3. 实验 (3-4 小时)
4. 总结 (1 小时)
5. 改进跟踪 (1 周)
6. 验证 (1 月)
```

### 关键指标

```text
- 故障注入次数
- 业务影响时长 (MTTI)
- 恢复时间 (MTTR)
- 发现问题数
- 改进闭环率
```

### 持续改进

```text
- 每月 1-2 次小演练
- 每季度 1 次 Game Day
- 每年 1-2 次大演练
- 所有改进跟踪到闭环
```
