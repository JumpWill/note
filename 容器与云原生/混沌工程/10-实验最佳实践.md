# 混沌工程实验最佳实践 (Best Practices)

> 本章讲解混沌工程实验在生产环境落地的最佳实践,包括实验流程、应急响应、安全合规、团队协作等。

## 一、生产环境实验原则

### 1.1 准备阶段

```text
实验前必备:
  □ 实验方案审批 (变更管理)
  □ 通知相关团队和值班人员
  □ 准备回滚方案 (一键停止)
  □ 准备监控仪表盘
  □ 实验时间选择 (业务低峰)
  □ 准备好实验报告模板
  □ 团队值班 (至少 2 人)
  □ 爆炸半径 (最大影响范围)
  □ 停止条件 (明确阈值)
```

### 1.2 通知模板

```text
【混沌工程实验通知】

时间: 2026-08-19 14:00-15:00
实验: Redis 主节点故障演练
范围: 1 个 Redis 主节点 (限定)
影响: 订单服务可能延迟 1s
影响最大范围: 1% 用户 (灰度)

如发现异常:
  1. 立即联系: 张三 (13800000000)
  2. 紧急停止: blade destroy <UID>
  3. 应急联系人: 王五 (13800000001)

业务影响: 订单服务可能短时延迟, 不会丢单

受通知人:
  - 订单团队 ✓
  - SRE 团队 ✓
  - DBA 团队 ✓
  - 客服团队 ✓
```

## 二、实验流程最佳实践

### 2.1 实验四阶段

```text
1. 准备阶段 (Pre-experiment)
   - 选定目标系统
   - 定义稳态指标
   - 设定假说
   - 准备监控
   - 通知团队
   时长: 1-2 周

2. 执行阶段 (Execution)
   - 在低峰时段执行
   - 小范围开始
   - 实时监控
   - 准备停止
   时长: 30 分钟 - 4 小时

3. 收尾阶段 (Cleanup)
   - 销毁实验
   - 验证系统恢复
   - 收集数据
   时长: 30 分钟 - 1 小时

4. 复盘阶段 (Review)
   - 写实验报告
   - 团队分享
   - 改进跟踪
   时长: 1 周
```

### 2.2 实验执行清单

```text
实验前 24 小时:
  □ 实验方案最终审核
  □ 相关团队确认
  □ 监控仪表盘就绪
  □ 回滚脚本测试
  □ 通知发送

实验前 1 小时:
  □ 值班人员就位
  □ 通讯群建立
  □ 所有监控系统正常
  □ 业务流量正常

实验前 5 分钟:
  □ 最后确认团队
  □ 准备记录
  □ 倒计时开始

实验中:
  □ 实时监控
  □ 记录现象
  □ 与团队同步
  □ 异常立即停止

实验后 30 分钟:
  □ 系统恢复确认
  □ 业务正常确认
  □ 初步数据收集
  □ 通知收尾
```

## 三、应急响应预案

### 3.1 应急停止条件

```text
立即停止实验的条件 (任一满足):

1. SLI 突破阈值
   - 错误率 > 设定阈值的 2 倍
   - 延迟 > 设定阈值的 2 倍
   - 业务影响超过预期

2. 系统异常
   - 数据丢失或损坏
   - 用户投诉
   - 监控系统异常

3. 业务影响扩大
   - 影响范围超出预期
   - 多服务异常
   - 资金损失风险

4. 人员不足
   - 值班人员失联
   - 关键技术专家不在

5. 外部事件
   - 真实故障发生
   - 安全事件
   - 紧急业务活动
```

### 3.2 应急停止流程

```bash
# 1. 立即判断是否需要停止 (1 分钟内)

# 2. 通知团队
# "实验 X 触发停止条件, 立即停止"

# 3. 执行停止命令
blade destroy <UID>
# 或
kubectl delete -f chaos-experiment.yaml

# 4. 验证系统恢复
curl http://api:8080/health
# 等待 SLI 恢复到稳态

# 5. 通知业务方
# "实验已停止, 系统正在恢复"

# 6. 复盘 (24 小时内)
# - 为什么触发停止
# - 假说是否错误
# - 如何改进
```

### 3.3 一键停止脚本

```bash
#!/bin/bash
# chaos-emergency-stop.sh
# 紧急停止所有混沌实验

set -e

echo "=== 紧急停止所有混沌实验 ==="
echo "时间: $(date)"

# 1. ChaosBlade
if command -v blade &> /dev/null; then
    echo "停止 ChaosBlade 实验..."
    for uid in $(blade list --type=create -o json 2>/dev/null | jq -r '.[].uid' 2>/dev/null); do
        echo "  销毁 $uid"
        blade destroy $uid 2>/dev/null || true
    done
fi

# 2. Chaos Mesh
if command -v kubectl &> /dev/null; then
    echo "停止 Chaos Mesh 实验..."
    kubectl delete podchaos --all -A 2>/dev/null || true
    kubectl delete networkchaos --all -A 2>/dev/null || true
    kubectl delete stresschaos --all -A 2>/dev/null || true
    kubectl delete diskchaos --all -A 2>/dev/null || true
    kubectl delete dnschaos --all -A 2>/dev/null || true
    kubectl delete timechaos --all -A 2>/dev/null || true
    kubectl delete kernelchaos --all -A 2>/dev/null || true
    kubectl delete jvmchaos --all -A 2>/dev/null || true
fi

# 3. Litmus
if command -v kubectl &> /dev/null; then
    echo "停止 Litmus 实验..."
    for engine in $(kubectl get chaosengine --all-namespaces -o custom-columns=NAME:.metadata.name,NAMESPACE:.metadata.namespace --no-headers 2>/dev/null); do
        echo "  停止 $engine"
    done
fi

# 4. Toxiproxy
if command -v toxiproxy-cli &> /dev/null; then
    echo "移除所有 toxics..."
    for name in $(toxiproxy-cli -h http://localhost:8474 list -o json 2>/dev/null | jq -r '.[].name'); do
        toxiproxy-cli -h http://localhost:8474 toxic remove -n $name 2>/dev/null || true
    done
fi

echo "=== 全部实验已停止 ==="
echo "请检查系统状态, 并通知相关团队"
```

### 4.3 告警配置

```yaml
groups:
- name: chaos_experiment
  rules:
  - alert: ChaosExperimentRunning
    expr: chaos_experiments_active > 0
    for: 1m
    labels:
      severity: info
    annotations:
      summary: "混沌实验进行中"
  
  - alert: HighErrorRateDuringExperiment
    expr: |
      sum(rate(http_requests_total{status=~"5.."}[1m])) /
      sum(rate(http_requests_total[1m])) > 0.05
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "实验期间错误率超 5%"
  
  - alert: ExperimentUnexpectedDuration
    expr: time() - chaos_experiment_start_time > 3600
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "实验运行超过 1 小时, 可能未正常停止"
```

### 5.1 报告结构

```markdown
# 混沌工程实验报告

## 基本信息
- 实验 ID: chaos-2026-0819-001
- 实验名称: Redis 主节点故障演练
- 实验负责人: 张三
- 实验时间: 2026-08-19 14:00-14:30
- 实验环境: 生产 (低峰时段)
- 参与人员: 张三, 李四, 王五

## 假说
"如果 Redis 主节点宕机 5 分钟,
 应用应自动切换到从节点, 服务不中断"

## 稳态基线
- 业务成功率: 99.95%
- P99 延迟: 50ms
- 错误率: 0.05%

## 实验执行
- 14:00 开始实验
- 14:00:30 Redis 主节点 kill
- 14:00:35 Sentinel 探测到主节点宕机
- 14:00:42 选举新主节点 (耗时 7 秒)
- 14:00:45 应用重连到新主节点
- 14:05 流量完全恢复
- 14:30 实验结束

## 实验结果
- 假说成立: ✓ 是
- 实际表现: 切换 < 10 秒, 无数据丢失
- 业务影响: 7 秒内 0.5% 请求失败
- 恢复时间: 12 秒

## 发现
1. Sentinel 切换正常
2. 应用重连机制有效
3. 监控告警及时 (Sentinel 状态告警)

## 问题
1. 部分旧版本客户端 (1%) 没有自动重连
2. 监控告警阈值过严, 触发 3 次误报
3. 应用启动后第一次连接慢 (300ms)

## 改进措施
| 问题 | 措施 | 责任人 | 截止 |
|------|------|--------|------|
| 老客户端 | 升级 SDK | 张三 | 9/15 |
| 告警误报 | 调整阈值 | 李四 | 9/1 |
| 首连慢 | 优化连接池 | 王五 | 9/20 |

## 实验评分
- 假说符合度: 95%
- 故障响应: 优秀
- 系统韧性: 良好
- 待改进: 中
```

## 八、安全与合规

### 8.1 风险控制

```text
混沌工程风险:

技术风险:
  - 影响生产服务
  - 数据丢失
  - 配置错误

业务风险:
  - 用户体验下降
  - 收入损失
  - 声誉损失

合规风险:
  - 违反 SLA
  - 触发安全告警
  - 客户数据风险

应对:
  1. 变更管理流程 (审批)
  2. 灰度策略 (小范围)
  3. 回滚预案 (一键停止)
  4. 监控告警 (实时)
  5. 业务方知情
  6. 法律合规审查
```

### 8.2 合规要点

```text
1. 数据合规
   - 不影响用户数据
   - 不导出生产数据
   - 符合 GDPR / 个人信息保护法

2. 业务合规
   - 不影响 SLA
   - 不影响合规审计
   - 保留证据链

3. 安全合规
   - 故障注入不绕过安全
   - 不暴露漏洞
   - 不影响安全监控

4. 财务合规
   - 不造成资金损失
   - 不影响计费
   - 保留财务记录
```

### 8.3 法律风险规避

```text
避免:
  1. 影响生产服务造成损失
     解决: 小范围, 低峰期, 一键停止

  2. 暴露给最终用户故障
     解决: 灰度演练, 内部用户优先

  3. 引发监管问题
     解决: 提前沟通, 明确边界

  4. 触发安全事故
     解决: 安全团队参与, 风险评估
```

## 二、监控与可观测性
