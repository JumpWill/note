# Calico 组件详解

> Calico 不是一个二进制，而是一组**按角色分工、互相协作**的组件。
> 按部署位置可以分成三层：节点级、集群级、集成层。
> 这篇按"层 → 组件 → 适用场景"的脉络梳理每个组件的职责和选型时机。

## 一、整体架构

```text
                          ┌──────────────────────────────────┐
                          │      控制平面（集群级 Deployment） │
                          │                                  │
                          │  calico-kube-controllers         │  默认 1 副本
                          │  typha（可选）                    │  大集群减压
                          │  calico-apiserver（v3.21+）      │  大集群独立 datastore
                          │                                  │
                          │  数据存储：K8s etcd / 自管 etcd   │
                          └────────────────┬─────────────────┘
                                           │ watch / apply
                                           ▼
                          ┌──────────────────────────────────┐
                          │  数据平面（每节点 DaemonSet）      │
                          │                                  │
                          │  calico-node                     │
                          │  ├─ Felix      写路由 / 策略     │
                          │  ├─ BIRD       BGP 邻居          │
                          │  ├─ confd      渲染 BIRD 配置     │
                          │  └─ CNI 插件  Pod 创删时调用     │
                          └────────────────┬─────────────────┘
                                           │
                                           ▼
                          ┌──────────────────────────────────┐
                          │  集成层（CLI / Sidecar / 迁移）   │
                          │                                  │
                          │  calicoctl                  运维  │
                          │  dikastes                   Mesh │
                          │  flannel-migration-controller    │
                          └──────────────────────────────────┘
```

**核心认知**：

```text
- 控制平面：1–N 副本 Deployment，集群范围生效
- 数据平面：DaemonSet，每个节点 1 个 Pod（4 个进程）
- 集成层：工具型组件，按需启用

最简化部署 = calico-node + calico-kube-controllers
其他所有组件都是"规模 / 场景需要时再加"
```

## 二、节点级组件（每个 K8s 节点都有）

> 这一层的组件以 **DaemonSet** 形式跑在每个 K8s 节点上，负责真正的网络转发、策略实施、Pod 接入。
> 全部组件都打包在 `calico-node` 这个 DaemonSet Pod 里。

### 2.1 calico-node DaemonSet

```text
位置：每个 K8s 节点 1 个 Pod
镜像：calico/node:v3.x
本质：超级 DaemonSet，一个 Pod 包含 4 个进程
```

**Pod 内 4 个进程一览**：

| 子进程 | 角色 | 主要工作 |
| --- | --- | --- |
| **Felix** | 节点级守护进程 | 写路由、写 iptables/eBPF、做策略实施、报告状态 |
| **BIRD** | BGP 客户端 | 跟其他 BGP 路由器（其他节点 / ToR）交换路由 |
| **confd** | 配置生成器 | 监听 datastore，把 Calico 配置渲染成 BIRD 配置文件 |
| **CNI plugin** | CNI 二进制 | Pod 创建时由 kubelet 调用，给 Pod 配 IP / veth / 路由 |

```bash
# 在 calico-node Pod 里能看到这些进程
kubectl -n calico-system exec ds/calico-node -- ps aux

# 输出（精简）：
# PID  USER     COMMAND
# 1    root     /bin/calico-node -felix
# 7    root     bird -f -s /var/run/calico/bird.ctl
# 10   root     confd -confdir=/etc/calico/confd
# 13   root     /opt/cni/bin/calico  (CNI plugin 等待 kubelet 调用)
```

**适用场景**：所有部署 Calico 的集群（**必装**）。

---

### 2.2 Felix：节点级主角

```text
全名：Felix Daemon
位置：calico-node Pod 内的一个进程
配置文件：/etc/calico/felix.cfg
角色：calico-node 的"主进程"，其他三个其实是辅助
```

**七项核心职责**：

```text
1. 接口管理
   - 创建 veth pair
   - 命名空间搬移到 Pod 网络命名空间
   - 设置接口 MTU、MAC 地址

2. 路由管理
   - 写主机路由表（Pod CIDR / 节点块路由）
   - 调 iproute2 命令（ip route add ...）

3. ARP 管理
   - 写邻居表（ARP / ND）
   - 通告 gratuitous ARP（Pod 迁移时更新）

4. 策略实施（iptables 数据面）
   - 把 NetworkPolicy 翻译成 iptables 规则
   - 默认丢弃 + 放行匹配规则的包

5. 策略实施（eBPF 数据面）
   - 加载 BPF 程序到内核
   - 维护 BPF maps

6. 状态上报
   - 报告本节点状态到 datastore
   - 健康检查（liveness probe 看的就是 Felix）

7. IPAM 集成
   - 从 IPAM 拿 IP 给新 Pod
   - 释放已删 Pod 的 IP
```

**常用命令**：

```bash
# 查 Felix 状态
calicoctl node status

# 看 Felix 日志
kubectl -n calico-system logs ds/calico-node -c calico-node

# 实时看 iptables 规则数量（Felix 写的）
watch -n 1 "iptables -t filter -L | wc -l"
```

**适用场景**：所有部署（**不可关闭**）。

---

### 2.3 BIRD：BGP 客户端

```text
全名：BIRD Internet Routing Daemon
位置：calico-node Pod 内
配置文件：/etc/calico/confd/bird.cfg（由 confd 生成）
```

**四项核心职责**：

```text
1. 建立 BGP 邻居
   - 跟其他 K8s 节点（iBGP）
   - 跟 ToR 交换机（eBGP，可选）

2. 交换路由
   - 把自己节点的 Pod CIDR 通告给邻居
   - 从邻居学其他节点的 Pod CIDR

3. 路径选择
   - 优选最优路径（AS-PATH / local-pref / MED）

4. 路由注入主机
   - 学到的路由写入 Linux 路由表
```

**常用操作**：

```bash
# 进 BIRD 控制台
calicoctl node bird

# 看所有路由
> show route

# 看 BGP 邻居
> show protocols

# 看某邻居详情
> show protocols all bgp1

# 看路由来源
> show route where proto ~ "bgp"
```

**适用场景**：

```text
✅ 启用 BGP（默认模式）
❌ Calico 用 VXLAN / IPIP only 时，BIRD 进程也在但只跑本地协议
❌ Calico 完全用 eBPF 数据面 + 不接 ToR 时，几乎没用
```

---

### 2.4 confd：BIRD 配置生成器

```text
全名：confd
位置：calico-node Pod 内
输入：监听 datastore 的变化
输出：BIRD 配置文件（/etc/calico/confd/bird.cfg）
```

**核心职责**：

```text
1. 监听 datastore 变化
   - Node / BGPConfiguration / BGPPeer / IPPool 等

2. 渲染 BIRD 配置
   - 模板：/etc/calico/confd/templates/bird.cfg.template
   - 用 datastore 数据填充

3. 触发 BIRD reload
   - 配置变化时让 BIRD 重新加载
```

**适用场景**：自动运行（**不可关闭**，属于 Calico 内部机制）。

---

### 2.5 CNI 插件：Pod 网络入口

```text
位置：calico-node Pod 内 + 节点上 /opt/cni/bin/calico, /opt/cni/bin/calico-ipam
调用方：kubelet
触发时机：Pod 创建 / 删除时
```

**两个二进制**：

```text
/opt/cni/bin/calico        主 CNI 插件（处理 CNI 协议）
/opt/cni/bin/calico-ipam   IPAM 插件（只负责 IP 分配）

也可以独立用 host-local IPAM，把 calico-ipam 换成别的
```

**Pod 创建流程**：

```text
kubelet 创建 Pod
  ↓
调用 CNI plugin（/opt/cni/bin/calico）
  ↓
CNI plugin 调 calico-ipam 拿 IP
  ↓
CNI plugin 创建 veth pair
  ├─ 一端放 Pod 网络命名空间（命名为 eth0）
  └─ 一端放主机网络命名空间（命名为 caliXXXXXXX）
  ↓
设置 IP / 路由 / MAC
  ↓
返回 CNI 协议要求的 JSON 给 kubelet
```

**Pod 删除流程**：

```text
kubelet 调用 CNI plugin 的 DEL 命令
  ↓
删 veth pair / 释放 IP / 删路由
```

**适用场景**：所有部署（**必装**）。

## 三、集群级组件（Deployment，跑在控制平面）

> 这一层的组件以 **Deployment** 形式跑在控制平面，集群范围生效。
> 默认 1 副本，大集群要 HA 拉满。

### 3.1 calico-kube-controllers：K8s 资源同步

```text
位置：集群级 Deployment（默认 1 副本）
镜像：calico/kube-controllers:v3.x
特点：Deployment，不是 DaemonSet，只跑 1–2 个 Pod
```

**五项核心职责**：

```text
1. 节点状态同步
   - K8s Node → Calico Node CRD
   - K8s Pod 删除 → Calico 释放 IP

2. 策略同步
   - K8s NetworkPolicy → Calico NetworkPolicy（双向）
   - 支持 Calico 扩展策略能力

3. IPAM GC（垃圾回收）
   - 找孤儿 IP（Pod 没了但 IP 还占着）
   - 释放回 IP Pool

4. 命名空间索引
   - 维护 namespace → profile 映射
   - 老的 namespaced policy 用到

5. RBAC / 节点控制器
   - 给 Calico 创建必要的 RBAC
   - 节点 CRD 管理
```

**挂了会怎样？**

```text
- IPAM 不会自动 GC（孤儿 IP 累积）
- Node CRD 不同步（不影响运行）
- NetworkPolicy 双向同步暂停（已有规则不受影响）
- 集群仍能正常创建 Pod / 转发流量

影响有限但要快速恢复，否则 IP Pool 会慢慢耗尽
```

**适用场景**：所有部署（**默认装**）。

---

### 3.2 calico-apiserver：独立 datastore（v3.21+）

```text
位置：集群级 Deployment（v3.21+ 才用）
镜像：calico/apiserver:v3.x
特点：独立 API server，托管 Calico 的 CRD 资源
```

**出现原因**：

```text
v3.21 之前：
  - 所有 Calico CRD 存在 K8s etcd
  - kube-controllers 同步
  - 集群大时 K8s API Server 压力大

v3.21+（选项 B 模式）：
  - Calico CRD 存到 Calico 自管 datastore
  - calico-apiserver 接管
  - K8s API Server 几乎不感知 Calico
```

**vs calico-kube-controllers**：

| 维度 | kube-controllers | calico-apiserver |
| --- | --- | --- |
| 角色 | 同步 K8s 资源到 Calico datastore | 独立托管 Calico CRD |
| CRD 存储 | K8s etcd | Calico 自管 datastore |
| 适用规模 | < 200 节点 | > 200 节点 |
| Federation 支持 | 弱 | 强 |

**适用场景**：

```text
✅ 大集群（节点 > 200，CRD 数 > 10000）
✅ 对 K8s API Server 压力敏感
✅ 多 Calico 联邦场景
❌ 小集群没必要装
```

### 3.3 Typha：Felix watch 聚合代理

```text
位置：集群级 Deployment（可选）
镜像：calico/typha:v3.x
默认副本：0（不装）；节点多时手动开
```

**出现原因**：

```text
问题：
  - Felix 直接 watch datastore
  - 每节点 1 个 watch 连接 → 100 节点 = 100 个 watch
  - 节点 > 200 时 K8s API Server 明显卡顿

Typha 解决：
  - Typha 充当 Felix 和 datastore 之间的代理
  - Typha watch datastore（只 1 个连接）
  - Felix 跟 Typha 建连（用短连接 / HTTP）
  - 整体 watch 数从 N → 1
```

**架构对比**：

```text
无 Typha：
  Felix × N  →  K8s API  （N 个 watch）

有 Typha：
  Felix × N  →  Typha × 1  →  K8s API  （1 个 watch）
```

**自动扩缩容**（v3.15+）：

```text
calico-typha-horizontal-autoscaler（Deployment）
  - 根据每个 Typha 实例的客户端数自动调副本
  - 默认目标：每个 Typha 服务 20 个 Felix
  - 1000 节点 → 大约 50 个 Typha 副本
```

**适用场景**：

```text
✅ 集群节点 > 50 且 K8s API Server 压力大
✅ 节点 > 200 时强烈推荐
❌ 小集群不需要
```

## 四、集成层组件（CLI / Sidecar / 迁移工具）

> 工具型组件，按业务需求启用，不强制安装。

### 4.1 calicoctl：运维 CLI

```text
位置：客户端工具（不在集群内跑）
安装：单独下载二进制 / kubectl plugin
镜像：calico/ctl
```

**能做的事**：

```text
1. 资源 CRUD
   calicoctl get ippool
   calicoctl apply -f bgp-peer.yaml
   calicoctl delete networkpolicy xxx

2. IPAM 管理
   calicoctl ipam show
   calicoctl ipam release <ip>
   calicoctl ipam get <ip>

3. 节点状态查看
   calicoctl node status
   calicoctl node diags
   calicoctl node bird

4. BGP 查看
   calicoctl get bgppeer
   calicoctl get bgpconfig

5. 配置管理
   calicoctl convert <old-format> --output=<new-format>
```

**三种安装方式**：

```bash
# 方式 1：单独二进制
curl -O https://github.com/projectcalico/calico/releases/download/v3.x/calicoctl
chmod +x calicoctl && mv calicoctl /usr/local/bin/

# 方式 2：kubectl plugin
kubectl calico get ippool

# 方式 3：容器内（每节点都有）
kubectl exec -n calico-system ds/calico-node -- calicoctl get ippool
```

**适用场景**：**运维必备**。

---

### 4.2 dikastes：Service Mesh 策略执行

```text
全名：dikastes（希腊语"判决执行者"）
位置：跟 Envoy 同 Pod 跑的 Sidecar
镜像：calico/dikastes:v3.x
出现版本：v3.6+
```

**核心职责**：

```text
1. 在 Sidecar 层实施 NetworkPolicy
   - Istio 管理的微服务之间的流量
   - 走 Envoy，不走 iptables / BPF
   - 需要 dikastes 拦截 Envoy 请求并查 Calico 策略

2. mTLS 兼容
   - Calico 策略 + Istio mTLS 同时生效
```

**工作原理**：

```text
Pod A (App + Envoy + Dikastes) → Pod B (App + Envoy + Dikastes)
                  ↓                            ↓
              Dikastes 查策略              Dikastes 查策略
                  ↓                            ↓
           Calico datastore             Calico datastore

两端的 Dikastes 都会执行策略判定
```

**适用场景**：

```text
✅ 用 Istio / Linkerd 且 Calico 做网络策略
✅ 想在 L7（HTTP header / gRPC method）做策略
❌ 不用 Service Mesh 就不需要
❌ Calico v3.16+ 才完善
```

---

### 4.3 flannel-migration-controller

```text
位置：集群级 Deployment（一次性 Job）
镜像：calico/kube-controllers
功能：把 Flannel 配置迁移到 Calico
```

**核心职责**：

```text
1. 检测 Flannel
   - 看集群是否在跑 Flannel

2. 数据迁移
   - Flannel 的 subnet config → Calico 的 IPPool

3. 引导切换 CNI
   - 引导用户改 CNI 配置从 flannel 到 calico

4. 一次性
   - 迁移完成后基本就没用了
```

**适用场景**：

```text
✅ 从 Flannel 迁移到 Calico 时
❌ 新部署直接用 Calico 不需要
```

## 五、组件之间的协作关系

### 5.1 数据流向

```text
用户操作（kubectl apply）
   │
   ▼
K8s API Server
   │
   ▼ (Felix / kube-controllers / typha watch)
┌─────────────────┐
│  Calico CRDs    │ (IPPool / NetworkPolicy / BGPPeer ...)
│  (存在 etcd)    │
└────────┬────────┘
         │
         ▼
   ┌─────────────────────────────────────┐
   │            控制平面                  │
   │ calico-kube-controllers (同步 K8s)   │
   │ typha (聚合 watch，可选)             │
   └────────┬────────────────────────────┘
            │ watch 推送
            ▼
   ┌─────────────────────────────────────┐
   │            节点平面                  │
   │ calico-node / Felix                 │
   │   ↓                                │
   │ 写路由 / iptables / eBPF            │
   │ BIRD 跟邻居交换 BGP 路由             │
   └─────────────────────────────────────┘
```

### 5.2 关键调用链

```text
kubelet → CNI plugin (calico) → calico-ipam (拿 IP)
                              → 创建 veth pair (调用 ip 命令)
                              → 写路由 (调用 ip route)
                              → 写 iptables / BPF map

Felix → 调 iptables（写策略）
     → 调 iproute2（写路由）
     → 调 ip6tables / nftables（IPv6）
     → watch datastore（订阅配置）

BIRD → 调 kernel（写路由）
     → 跟其他节点 / ToR 建 TCP 179

confd → watch datastore
      → 写 BIRD 配置
      → reload BIRD
```

## 六、按集群规模选型

### 6.1 单节点 / 测试集群

```text
最少组件：
  ✅ calico-node           (DaemonSet, 1 节点)
  ✅ calico-kube-controllers (Deployment, 1 副本)
  ❌ typha（不需要）
  ❌ calico-apiserver（不需要）

部署方式：manifest 默认即可
```

### 6.2 中型集群（50–200 节点）

```text
组件：
  ✅ calico-node            (DaemonSet, N 节点)
  ✅ calico-kube-controllers (Deployment, 1 副本)
  ✅ typha                  (Deployment, 2–3 副本，可选但推荐)
  ❌ calico-apiserver

开启 typha：
  # FelixConfiguration
  spec:
    typhaAddr: "typha-typha.calico-system.svc:5473"
```

### 6.3 大型集群（200–1000 节点）

```text
组件：
  ✅ calico-node            (DaemonSet, N 节点)
  ✅ calico-kube-controllers (Deployment, 2 副本 HA)
  ✅ typha                  (Deployment, 5–20 副本, + HPA)
  ✅ calico-apiserver       (可选，进一步减压)

调参：
  - typhaScaleAddrThreshold: 50    # 节点数超过 50 才用 typha
  - kubeControllers num-replicas: 2
  - Felix prometheus metrics 端口开
```

### 6.4 超大集群（1000+ 节点）

```text
组件：
  ✅ calico-node            (DaemonSet, N 节点)
  ✅ calico-kube-controllers (Deployment, 3 副本 HA)
  ✅ typha                  (Deployment, 30–100 副本 + HPA)
  ✅ calico-apiserver       (强烈推荐)
  ✅ 自管 etcd              (Calico 专用的 3 节点 etcd 集群)

部署变化：
  - Calico CRD 不再存 K8s etcd
  - 存到 Calico 自管 datastore
  - K8s API Server 几乎不感知 Calico
```

## 七、按业务场景选型

### 7.1 Service Mesh（Istio / Linkerd）

```text
新增组件：
  ✅ dikastes (DaemonSet / Sidecar)

部署方式：
  - 用 istioctl 安装时自动集成
  - 或手动注入 Sidecar
```

```yaml
# 示例：在 namespace 自动注入
apiVersion: v1
kind: Namespace
metadata:
  name: istio-system
  labels:
    istio-injection: enabled
    projectcalico.org/dikastes-injection: enabled
```

### 7.2 跨集群 Federation

```text
新增组件：
  ✅ calico-apiserver
  ✅ federation-controller（v3.21+）

适用场景：
  - 多 K8s 集群共享同一 Calico 控制平面
  - 跨集群 Service Mesh
  - 多集群网络策略
```

### 7.3 Windows 节点

```text
节点组件变化：
  ✅ Linux 节点：calico-node（含 Felix + BIRD + confd）
  ✅ Windows 节点：calico-node-windows（DaemonSet）
     - 包含 Windows Felix
     - 不包含 BIRD（Windows 没原生 BIRD）
     - 走 host-local IPAM 或 Calico Windows IPAM
  ✅ calico-kube-controllers

⚠️ Windows 节点限制：
  - 不能跑 BGP（除非用 Calico Enterprise）
  - 主要走 VXLAN
  - eBPF 数据面不支持
```

### 7.4 eBPF 数据面

```text
对组件的影响：
  - calico-node 内的 Felix 加载 BPF 程序
  - BIRD 几乎没用（eBPF 接管转发）
  - 不用新增组件

优势：
  - iptables 规则从几万条降到 0
  - Service 转发延迟 -30% 到 -50%
  - 详细配置见 ebpf_in_calico.md
```

### 7.5 Flannel 迁移

```text
新增组件：
  ✅ flannel-migration-controller (一次性 Job)

迁移流程：
  1. 装 flannel-migration-controller
  2. 跑迁移（自动检测 Flannel）
  3. 切换 CNI 配置（calico-system 改 ConfigMap）
  4. 重启所有 Pod
  5. 删除 flannel DaemonSet
  6. 删除 flannel-migration-controller
```

## 八、生命周期管理

### 8.1 部署顺序

```text
1. 装 etcd（Calico 自管模式需要 K8s 之外的 etcd）
2. 装 calico-apiserver（如果启用）
3. 装 typha（如果启用）
4. 装 calico-kube-controllers
5. 装 calico-node（每个节点）
6. 装 dikastes（如果用 Service Mesh）
7. 验证：calicoctl node status
```

### 8.2 升级顺序

```text
calicoctl 升级 → CRD schema 检查 → typha → calico-apiserver →
calico-kube-controllers → calico-node (滚动)

⚠️ 必须按这个顺序，否则 Felix 跟 datastore schema 不兼容会 crash
```

### 8.3 单组件故障的影响面

| 组件 | 故障影响 | 恢复优先级 |
| --- | --- | --- |
| **calico-node** | 该节点 Pod 网络不通；其他节点不受影响 | 高（节点级隔离即可） |
| **typha** | Felix 暂时 watch 不到新数据；已有连接不受影响 | 中（多副本时影响有限） |
| **calico-kube-controllers** | IPAM GC / 节点同步 / 策略同步暂停；已有规则不受影响 | 中（要快速恢复否则 IP 耗尽） |
| **calico-apiserver** | 整个集群网络配置不可变；已生效规则不受影响 | 极高（立即恢复） |
| **dikastes** | Service Mesh 流量无 Calico 策略执行（其他流量不受影响） | 低（业务影响有限） |

## 十、选型速查表

| 场景 | 必装 | 推荐装 | 不需要 |
| --- | --- | --- | --- |
| 单节点测试 | calico-node, kube-controllers | - | typha, apiserver |
| 50 节点集群 | calico-node, kube-controllers | typha | apiserver |
| 500 节点集群 | calico-node, kube-controllers | typha (HA), apiserver | - |
| 2000+ 节点 | calico-node, kube-controllers, apiserver | typha (auto-scale) | - |
| Istio 集成 | calico-node, kube-controllers, dikastes | typha | - |
| BGP to ToR | calico-node（含 BIRD） | kube-controllers | apiserver |
| eBPF 数据面 | calico-node | kube-controllers, typha | apiserver (eBPF 暂不依赖) |
| Flannel 迁移 | calico-node, kube-controllers, **flannel-migration-controller** | - | - |
| Windows 节点 | calico-node (Linux), calico-node-windows | kube-controllers | BIRD（Windows 无） |

## 十一、一句话总结

> **Calico = calico-node（每节点干活）+ calico-kube-controllers（集群同步）+ calicoctl（运维接口）**，
> 集群大了加 **typha**（减压）+ **calico-apiserver**（独立 datastore）；
> 跑 Service Mesh 加 **dikastes**；
> 选型原则：**节点 < 50 装最少，节点 50–200 加 typha，节点 > 200 上 apiserver**。
