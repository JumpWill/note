# Calico 核心知识总结

---

## 一、BGP 协议本身（先破除误解）

### 常见误解：BGP 只工作在二层 —— 错

**BGP 是应用层协议（OSI 第 7 层），跑在 TCP 179 上。**

```
┌─────────────────────────┐
│  BGP Update / Keepalive │  ← L7 应用层
├─────────────────────────┤
│  TCP (port 179)         │  ← L4
├─────────────────────────┤
│  IP                     │  ← L3
├─────────────────────────┤
│  Ethernet               │  ← L2
└─────────────────────────┘
```

它必须"踩在 L3/L4 肩膀上"——**先有 IP 可达，再有 TCP 连接**。

### 误解的三个来源

| 来源 | 真相 |
|---|---|
| eBGP 默认 TTL=1 | 是"三层一跳"，不是"二层直连"；`ebgp-multihop 5` 可解除 |
| Calico `CrossSubnet` 同子网不封装 | 说的是**数据面要不要封装**，不是 BGP 跑不了 |
| MetalLB 常和 TOR 同网段 | 是部署便利，配 `ebgpMultihop` 一样跨网段 |

---

## 二、Calico 的关键：控制面 vs 数据面

**这是理解 Calico 的总钥匙。**

| | 走什么 | 能否跨三层 |
|---|---|---|
| **控制面**（BGP 会话） | TCP 179，节点 IP 之间 | ✅ 只要 IP 可达，跨几台路由器都行 |
| **数据面**（Pod 实际流量） | Pod 之间直连 | ⚠️ **取决于物理路由器认不认识 Pod 网段** |

**跨网段真正的障碍**：不是 BGP 跑不了，而是中间路由器收到目标 `172.20.2.x`（Pod 网段）的包，路由表里没这条 → 丢弃。

### 三种模式对比

| 模式 | 同子网 | 跨子网 | 底层要求 |
|---|---|---|---|
| `Always` | 封装 | 封装 | 无 |
| **`CrossSubnet`** ⭐ | **不封装** | 封装 | 无 |
| `Never`（纯 BGP） | 不封装 | 不封装 | **路由器必须认识 Pod 网段** |

> 设备配合（跑 BGP / 静态路由）→ 跨网段也能纯 BGP；设备不配合 → 只能套壳。

## 三、跨机房能力总表

| 模式 | 跨机房 | 性能 | 防火墙放行 |
|---|---|---|---|
| **VXLAN Always** | ✅ | 中 | UDP 8472 |
| **VXLAN CrossSubnet** ⭐ | ✅ | 同机房高/跨机房中 | UDP 8472 |
| **IPIP Always/CrossSubnet** | ✅（有坑） | 中 | **IP Protocol 4**（无端口！） |
| **BGP Never** | ⚠️ 看设备 | **最高** | TCP 179 |

**IPIP 的坑**：用 IP Protocol 4（不是 TCP/UDP，无端口），很多 NAT/防火墙/云直接丢弃，AWS 明确不支持。**跨机房优先 VXLAN。**

### ⚠️ 跨机房最容易踩的坑：MTU

```
物理 MTU 1500
  ├ VXLAN: -50 → Pod MTU 1450
  └ IPIP:  -20 → Pod MTU 1480
```

专线 MTU 非标准时忘了调 → **大包静默丢弃**（小请求正常，大文件卡死，极难排查）。

### 🔴 比选模式更重要：跨机房该不该单集群

etcd 对延迟极敏感（心跳 100ms / 选举超时 1000ms）：

| 机房距离 | RTT | 结论 |
|---|---|---|
| 同城裸光纤 | < 5ms | 勉强可以 |
| 同城普通专线 | 5-20ms | ⚠️ etcd 会抖 |
| 跨城 | > 20ms | ❌ 单集群必炸 |

> **生产标准做法：每机房独立集群 + 上层 GSLB/Ingress 调度。** 跨机房网络只用于服务间调用，不是为了把 etcd 拉在一起。

## 四、路由表结构（三种模式通用）

### 三类路由

```bash
# ① 本机 Pod —— 逐个 /32，指向虚拟网卡
10.233.66.9  dev caliecea98b4801 scope link

# ② 远端节点 —— block 聚合，指向物理网卡 + 节点 IP
10.233.66.64/26 via 192.168.9.102 dev eth0 proto bird

# ③ 防环 —— 本节点 block 内未分配 IP 直接丢弃
blackhole 10.233.66.0/24 proto bird
```

### 关键设计：块级聚合

- 本机 Pod 是 **/32 逐条**（要送到具体 veth）
- 远端是 **/26 block**（每个 block = 64 个 IP）→ **5000 个 Pod 路由条目数也只跟 block 数挂钩**
- **一个节点可以有多个 block**（Pod 用完 64 个地址会再分配）→ 路由表可能出现两条不同网段但 `via` 同一节点 IP 的路由，正常现象

### `blackhole` 的作用

防止"目的地址在本节点 block 内但 Pod 不存在"的包走默认路由绕圈形成环路。**不是错误，是防环保护。**

## 五、三种模式的路由表差异

```
① 纯 BGP
10.233.66.64/26 via 192.168.9.102 dev eth0         proto bird

② IPIP
10.233.66.64/26 via 192.168.9.102 dev tunl0        proto bird onlink

③ VXLAN
10.233.66.64/26 via 192.168.9.102 dev vxlan.calico proto bird onlink
```

**网段、下一跳、`proto bird` 全一样，只有 `dev` 和 `onlink` 变。**

### ⚠️ 反直觉：三种模式 BGP 都在跑

`proto bird` 在所有模式都出现——BGP 一直在跑，只是**通告内容不同**：

| 模式 | BGP 通告内容 |
|---|---|
| 纯 BGP / IPIP | 三层网段（几乎相同，差别只在本地要不要套壳） |
| **VXLAN** | **网段 + VTEP + MAC**（多二层信息） |

**判断模式不能看有没有 bird，要看 `dev`。**

### `onlink` 标志

封装模式独有，含义是"不管下一跳是否真在同一链路，强行发出去"——**这是封装模式能跨三层的技术根源**。纯 BGP 没这个豁免，所以下一跳必须真实可达。

### 完整对比

| 维度 | 纯 BGP | IPIP | VXLAN |
|---|---|---|---|
| FIB 出接口 | 物理网卡 | `tunl0` | `vxlan.calico` |
| `onlink` | ❌ | ✅ | ✅ |
| BGP 通告 | 网段 | 网段 | **网段+VTEP+MAC** |
| **FDB 表** | ❌ | ❌ | ✅ |
| Pod MTU | 1500 | 1480 | 1450 |
| 跨三层依赖 | **需设备配合** | 不需要 | 不需要 |

## 六、规模天花板：Route Reflector

node-to-node mesh（全互联）：

```
连接数 = N × (N-1) / 2
10 节点  → 45 条     ✅
50 节点  → 1225 条   ⚠️
100 节点 → 4950 条   ❌
```

**超过 50-100 节点必须上 RR**：

```yaml
spec:
  nodeToNodeMeshEnabled: false
```
连接数从 N² 降到 N。

## 七、排错速查

```bash
kubectl get nodes
calicoctl node status                        # BGP 邻居 Established?
kubectl get ippool -o yaml | grep -E "ipipMode|vxlanMode"
ip link show | grep -E "tunl0|vxlan.calico"  # 最快判断模式
ip route | grep proto bird                   # 看远端 dev
bridge fdb show dev vxlan.calico             # VXLAN 专属
kubectl exec -n kube-system ds/calico-node -- birdcl show route
```

**一秒判模式**：有 `tunl0` = IPIP，有 `vxlan.calico` = VXLAN，都没有 = 纯 BGP 或单节点。

# Calico VXLAN vs Flannel VXLAN

## 核心差异：查表路径

| | 查表链路 | 表数 |
|---|---|---|
| **Flannel VXLAN** | 路由表 → **ARP 表** → FDB 表 | **3** |
| **Calico VXLAN** | 路由表 → FDB 表 | **2** |

### Flannel：绕一圈

```bash
# ① 路由——下一跳是"隧道IP"，不是节点IP
10.244.1.0/24 via 10.244.1.0 dev flannel.1 onlink
                   ↑ 中间层，需再翻译

# ② ARP——隧道IP → MAC
ip neigh show dev flannel.1
10.244.1.0 lladdr ba:74:f9:db:8e:8a PERMANENT

# ③ FDB——MAC → 真正的节点IP
bridge fdb show dev flannel.1
ba:74:f9:db:8e:8a dst 192.168.9.102 self permanent
                        ↑ 这时才拿到外层封装IP
```

### Calico：直达

```bash
# ① 路由——下一跳直接就是节点物理IP
10.233.66.64/26 via 192.168.9.102 dev vxlan.calico proto bird onlink
                     ↑ 终点，直接可用

# ② FDB——MAC 静态 permanent，无需动态解析
66:xx:xx:xx:xx:xx dst 192.168.9.102 self permanent
```

**关键差异就在 `via`**：

```
Flannel: via 10.244.1.0      ← 隧道IP（中转）
Calico:  via 192.168.9.102   ← 节点IP（终点）
```

Calico 的 BGP 通告时直接告诉内核"这个网段的 VTEP 就是 192.168.9.102"，**路由查完外层 IP 就确定了**。

---

## ⚠️ 但别高估这个差异

**查表路径优雅 ≠ 性能快很多**：

1. 三次查找都在**内核态**，纳秒级，远小于一次封装开销
2. 两者**封装开销完全相同**——都是标准 VXLAN，加 50 字节头
3. 性能大头是**封装本身**（UDP 封装、checksum、内核态切换）

> **Calico VXLAN 与 Flannel VXLAN 实际转发性能同量级。** Calico 真正快的地方是**纯 BGP 模式（零封装）**——但那已经不是 VXLAN 了。

---

## Calico 这样设计图什么

不是图性能，是图**控制面干净**：

| 好处 | 说明 |
|---|---|
| BGP 自动分发 | VTEP/MAC 通过 BGP 同步，节点增删自动收敛；Flannel 靠 flanneld 监听 etcd 静态下发 |
| 支持多 block | 一节点可多 block；Flannel 基本一节点一子网 |
| CrossSubnet 成熟 | 同二层自动不封装；Flannel 的 directrouting 较粗糙 |
| 控制面统一 | 三种模式共用同一套 BGP 机制，切换模式不用换架构 |

---

## 真正该关心的选型差异

| 维度 | Flannel | Calico |
|---|---|---|
| **NetworkPolicy** | ❌ **不支持** | ✅ 完整支持 |
| BGP 纯路由 | ❌ | ✅ |
| 封装 | VXLAN / host-gw | VXLAN / IPIP / 纯 BGP |
| 跨子网策略 | 弱 | ✅ CrossSubnet |
| 运维复杂度 | 简单 | 较重（BIRD、IPPool、BGPPeer） |
| 加密 | ❌ | ✅ WireGuard |

> **NetworkPolicy 是决定性差异**——要做网络隔离（禁止 A 服务访问 B、只放行特定端口），Flannel 直接出局。

## 🔴 一个提醒：你手上是两套集群

| 环境 | Pod 网段 | 网络插件 |
|---|---|---|
| `kubectl get po -o wide` | `10.244.x.x` | **Flannel** |
| `ip route` 那份 | `10.233.66.x` | **Calico**（KubeSphere 默认 `10.233.64.0/18`） |

**别把两套环境的现象混着排查。**

另外那台 `ip route` 的机器有两个疑点待确认：

1. **`wlp3s0` 是无线网卡** —— 生产节点不该用无线跑 Calico，且 Calico 网卡自动检测很可能选错接口导致 BGP 建不起来
2. **路由表里没有远端 block** —— 单节点正常；多节点则是 BGP 没通（现象有迷惑性：同节点 Pod 通信正常，只有跨节点失败）

```bash
kubectl get nodes
calicoctl node status
```

---

**一句话收尾**：

> **Calico 的本质是「控制面统一用 BGP 分发，数据面按模式决定套不套壳」。本机 Pod 永远逐条 /32 走 `caliXXX`，远端按 block 聚合；三种模式的区别只在远端路由的 `dev` 和是否额外维护 FDB 表。相对 Flannel，Calico VXLAN 少查一次 ARP 表是"实现更干净"，但真正拉开差距的是 NetworkPolicy 和纯 BGP 零封装能力。**
