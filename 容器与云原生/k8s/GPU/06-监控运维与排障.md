# 监控、运维与排障

> 目标：GPU 卡上的问题**只有这一台机器能看到**，没有日志、没有事件、没有健康检查——所以必须在 Pod 起来之前就把监控和排障路径准备好。

## 一、GPU Operator：不要手动装驱动

裸机安装驱动的痛苦：升级要停机、内核升级要重装、20 个节点要 20 次。

NVIDIA GPU Operator 把整套东西做成 Operator，一套 Helm 管四件事：

```text
GPU Operator (Helm)
 ├─ driver           编译/安装 GPU 内核驱动（DaemonSet）
 ├─ toolkit          nvidia-container-toolkit，让容器能用 GPU
 ├─ device-plugin    向 kubelet 上报 nvidia.com/gpu 容量
 ├─ dcgm-exporter    采集 GPU 指标，暴露 :9400 给 Prometheus
 ├─ node-feature-discovery  打节点标签
 └─ gpu-operator-validator  检查前置条件
```

```bash
helm install gpu-operator nvidia/gpu-operator \
  --namespace gpu-operator --create-namespace \
  --set driver.enabled=true \
  --set toolkit.enabled=true \
  --set devicePlugin.enabled=true \
  --set dcgmExporter.enabled=true \
  --set nfd.enabled=true
```

**决策**：新建集群用 Operator；改造存量集群先评估——Operator 会接管 `/run/nvidia-container-runtime`，与已有手工安装冲突。

## 二、DCGM Exporter：GPU 监控的事实标准

DCGM（NVIDIA Data Center GPU Manager）是 NVML 之上的官方管理/诊断框架。

```bash
# 本地快速验证
kubectl -n gpu-operator port-forward svc/dcgm-exporter 9400:9400
curl localhost:9400/metrics | grep DCGM_FI_DEV_GPU_UTIL
```

核心指标：

| 指标 | 含义 | 告警阈值参考 |
|------|------|------------|
| `DCGM_FI_DEV_GPU_UTIL` | SM 利用率 % | < 10% 持续 10min（空转） |
| `DCGM_FI_DEV_FB_USED` / `FB_TOTAL` | 显存已用 / 总量 | 使用率 > 95% |
| `DCGM_FI_DEV_MEM_COPY_UTIL` | 显存带宽利用率 % | — |
| `DCGM_FI_DEV_GPU_TEMP` | 温度 | > 85℃ |
| `DCGM_FI_DEV_POWER_USAGE` | 功耗 | > 额定 90% 持续 |
| `DCGM_FI_DEV_XID_ERRORS` | XID 错误计数 | **> 0 立即告警** |
| `DCGM_FI_DEV_PCI_REPLAY_COUNTER` | PCIe 重传 | 持续增长 |
| `DCGM_FI_PROF_GR_ENGINE_ACTIVE` | 计算引擎活跃比例 | < 30%（卡空转） |

> **DCGM_FI_DEV_XID_ERRORS 是最重要的一个**，XID 错误是硬件/驱动的亚健康信号，等同于 CPU 的 MCE。

### Prometheus 抓取

GPU Operator 默认带 ServiceMonitor（需装了 Prometheus Operator）。手写 ServiceMonitor：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: dcgm-exporter
  namespace: gpu-operator
spec:
  selector:
    matchLabels: { app: dcgm-exporter }
  endpoints:
    - port: 9400
      interval: 30s
```

典型 Grafana 面板：SM 利用率、显存使用/容量、GPU 温度、功耗、XID 错误、**按 Pod 的显存占用**（依赖 DCGM 的 Kubernetes Pod Mapping）。

## 三、Pod Mapping：把指标关联到 Pod

DCGM exporter 通过 kubelet 的 `/stats/summary` 把 GPU 上的进程映射到 Pod，指标标签才会出现 `pod` / `namespace`：

```yaml
env:
  - name: DCGM_EXPORTER_KUBERNETES
    value: "true"
  - name: DCGM_EXPORTER_COLLECTORS
    value: "DCGM_FI_PROF_GR_ENGINE_ACTIVE,DCGM_FI_PROF_PIPE_TENSOR_ACTIVE,DCGM_FI_DEV_FB_USED,DCGM_FI_DEV_FB_FREE,DCGM_FI_DEV_GPU_TEMP,DCGM_FI_DEV_XID_ERRORS"
  - name: DCGM_EXPORTER_WATCHDOG_TIMEOUT
    value: "60s"
```

这样才能回答「哪个 Pod 在用卡」和「Pod 说要用 GPU 但卡上没有进程」（调度上了但没用）。

## 四、健康检查

GPU Pod 的 liveness/readiness 是最容易被忽略的：

```yaml
livenessProbe:
  exec:
    command: ["sh", "-c", "nvidia-smi -L | grep -q GPU"]
  initialDelaySeconds: 120      # 模型加载要几分钟，别设 30s
  periodSeconds: 30
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /health
    port: 8000
```

生产推理服务建议：探测 `/health`（能响应但不查模型）+ `/v1/models`（真加载完成），别用 liveness 检测推理链路，模型小卡抖动会被误杀。

## 五、排障决策树

```text
Pod 一直 Pending
├─ Events 说 Insufficient nvidia.com/gpu
│  ├─ 是 → 卡不够，看 quota / node 标签 / 其他 Pod 占着
│  └─ 否 → capacity 为 0 或 nodeSelector 没匹配
└─ 检查：
   kubectl describe pod -l app=x | grep -A5 Events
   kubectl get nodes -o json | jq '.items[].status.allocatable["nvidia.com/gpu"]'
   kubectl get pods -A -o json | jq '[.items[] | select(.spec.containers[].resources.limits["nvidia.com/gpu"]?)] | length'
```

```text
Pod Running 但 crash / nvidia-container-cli 报错
├─ device plugin 状态？
│  kubectl -n gpu-operator logs deploy/nvidia-device-plugin-daemonset
├─ 节点上 nvidia-smi 正常吗？
│  kubectl debug node/gpu-node-1 -it --image=ubuntu -- chroot /host nvidia-smi
└─ toolkit 配置坏？
   kubectl -n gpu-operator exec ds/nvidia-device-plugin-daemonset -- nvidia-container-cli info
```

```text
容器内看不到 GPU（nvidia-smi: command not found 或 0 卡）
├─ 镜像里没装 nvidia-smi → 用 base/runtime/devel 或 pytorch 镜像（utility capability）
├─ NVIDIA_DRIVER_CAPABILITIES 缺 utility
└─ 没声明 nvidia.com/gpu → 没挂载设备节点
```

```text
GPU 利用率 0，但 Pod 在跑
├─ 数据加载慢 → CPU 内存不足，DataLoader worker 少
├─ 小 kernel 太多 → launch 开销主导，考虑 CUDA Graph / torch.compile
├─ 等 NCCL 通信 → 多卡任务卡在 all-reduce
├─ 容器 CPU 被限流 → 调高 cpu limit
└─ MIG 实例分配过小（1g.10gb）+ 模型 OOM 重试循环
```

## 六、常见故障速查

| 症状 | 原因 | 处理 |
|------|------|------|
| `nvidia.com/gpu: N` 但容器里只看到 1 张 | requests 写了、limits 没写（或反之） | 两者都写 |
| Pod 起来后 GPU 一直不释放 | 进程僵死 / client 崩溃 | `nvidia-smi` 看残留 PID，hostPID 排查，SIGKILL |
| 卡显存被占但无进程 | 容器 OOM 后驱动未回收 | 重启 device plugin，`nvidia-smi --gpu-reset -i N` |
| `all CUDA devices within a Node are busy or unavailable` | 节点 compute mode = Exclusive_Process 但被占 | 改 `nvidia-smi -c 0` |
| `device-plugin 起来但 allocatable 为 0` | GPU 被健康检查进程占用（占用型探针） | 探针别跑在 GPU 节点做分配 |
| XID 错误 13/31 | 显存/ECC/硬件问题 | 换卡，报修，`nvidia-smi -q -d ECC` |
| 节点 Ready 但 GPU Pod 排不上 | quota 满 / nodeSelector 标签过期 | 查 ResourceQuota 和 NFD 标签 |
| MIG 切分后 Pod 看不到实例 | MIG profile 名和 resource 名不匹配 | `nvidia-smi mig -lgip` 对齐名称 |
| 驱动升级后卡 CrashLoopBackOff | 驱动容器和宿主内核头文件版本不符 | 检查 `k8s-driver-*-ubuntu-*` tag |

## 七、调试手段

```bash
# 1. 进容器看
kubectl exec -it <pod> -- nvidia-smi
kubectl exec -it <pod> -- python -c "import torch; print(torch.cuda.device_count())"

# 2. 看容器实际生效的环境变量
kubectl exec <pod> -- env | grep -E 'NVIDIA|CUDA|NCCL'

# 3. Node 上直接看（hostPID + chroot）
kubectl debug node/<node> -it --image=nvidia/cuda:12.4.1-base-ubuntu22.04 -- chroot /host

# 4. 看驱动日志
journalctl -k | grep -i nvidia
dmesg -T | grep -i xid

# 5. NCCL 通信调优（多卡不加速时）
export NCCL_DEBUG=INFO            # 打印拓扑与算法选择
export NCCL_P2P_DISABLE=1         # 禁用 P2P（跨 PCIe 时）
export NCCL_IB_DISABLE=1          # 无 IB 网络时禁用 IB
export NCCL_SHM_DISABLE=0
```

## 八、升级与维护

```text
驱动升级流程
1. 调 dcgm/driver 组件的 rollingUpdate 策略为 OnDelete
2. 逐节点：cordon → 等 GPU Pod 排空 → drain → 升级 → 重启 → 验证 nvidia-smi → uncordon
3. 驱动版本向前兼容，CUDA Toolkit 不需要动
```

```yaml
# 让 GPU Pod 优雅排空，避免驱逐时任务硬杀
spec:
  priorityClassName: gpu-workload     # 高优先级，日常不被抢占
  terminationGracePeriodSeconds: 300
```

批量操作：

```bash
kubectl cordon gpu-node-1
kubectl drain gpu-node-1 --ignore-daemonsets --delete-emptydir-data --timeout=600s
# 升级验证
nvidia-smi && python -c "import torch; torch.zeros(1).cuda()"
kubectl uncordon gpu-node-1
```

## 小结

- 新集群上 GPU Operator，不要手工装驱动。
- DCGM Exporter + XID 错误告警是底线。
- 排障第一步永远是「节点上 nvidia-smi 正常吗」，第二步才是 K8s 层。
- GPU 是不可迁移的独占资源：节点维护前必须排空，没有 fallback。
