# 显存与性能模型

> 目标：能**在跑之前算出显存够不够**，能**判断一个 kernel 是算力瓶颈还是带宽瓶颈**。OOM 是 K8s 里 GPU 最常见的故障。

## 一、显存去哪儿了

训练一个模型的显存大致拆成四块：

```text
总显存占用 ≈ 权重 + 梯度 + 优化器状态 + 激活值 + 框架开销 + 碎片
```

| 项 | 大小公式 | BF16 训练 7B 模型 |
|----|---------|-------------------|
| 权重 | `P × 2` | 14 GB |
| 梯度 | `P × 2` | 14 GB |
| Adam 优化器（fp32 m+v+master） | `P × 8~12` | 56~84 GB |
| 激活值 | `∝ batch × seq × hidden × 层数` | 10~30 GB，随配置波动最大 |
| CUDA context + 碎片 | 1~3 GB | ~2 GB |

**结论：BF16 训练 7B 需要约 90~130GB，单张 80G 卡放不下。** 这就是为什么多卡训练不是为了速度，是为了塞得下。

### 推理显存

```text
推理显存 ≈ 权重 + KV Cache + 激活 + 框架开销
```

KV Cache 是长上下文场景的真正瓶颈：

```text
KV Cache(GB) ≈ 2 × layers × heads × head_dim × seq_len × batch × dtype_bytes / 1e9
```

例如 Llama-2-7B（32 层，32 头，head_dim 128），BF16，batch=1，seq=4k：

```text
2 × 32 × 32 × 128 × 4096 × 1 × 2 / 1e9 ≈ 2.1 GB
```

seq 拉到 32k 就是 17GB。**vLLM 的 `gpu_memory_utilization` 默认 0.9 就是把剩余空间尽可能全给 KV Cache**，这就是它吞吐高的原因。

## 二、显存估算速查

| 场景 | 估算 |
|------|------|
| 纯推理（FP16/BF16） | `P × 2 × 1.2`（×1.2 给 KV Cache 和开销） |
| LoRA 微调 | 冻结权重 `P×2` + 激活，可在小卡上跑 |
| 全参数 BF16 + Adam | `P × 16`（经验值） |
| 全参数 + ZeRO-3 / FSDP | 近似线性下降到 `P×16/N + 激活` |
| 量化 INT8 推理 | `P × 1` |
| 量化 INT4 推理 | `P × 0.5` |

快速验证：`P×2.2 GB` 判断能否单卡推理，`P×16 GB` 判断能否单卡训练。

## 三、为什么显存不像 CPU 会 swap

- CPU：物理内存不够 → 页面换到磁盘 → 慢但能跑
- GPU：显存不够 → **CUDA 分配直接失败**，OOM 甚至来不及 Swap

```text
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 2.00 GiB
```

所以 GPU 上的 `resources.limits.memory`（CPU 内存）调大**对显存 OOM 毫无帮助**。只有一种例外：开了 Unified Memory，宿主机内存被当显存的溢出区，此时 CPU 内存调大有用，但会慢到无法接受。

> 由此引出一条 K8s 实践：**GPU Pod 的 CPU memory limit 要给够（至少 2~4 倍显存），但它保护的是 CPU 内存，不是显存。** 显存保护靠 `nvidia.com/gpu` 独占 + 启动参数。

## 四、Roofline：算力瓶颈还是带宽瓶颈

算术强度（Arithmetic Intensity）：

```text
AI = FLOPs / 访存字节数     单位 FLOP/Byte
```

Roofline 拐点：

```text
拐点 AI = 峰值 FLOPS / 显存带宽
```

| 卡 | 峰值 FLOPS (BF16) | 显存带宽 | 拐点 AI |
|----|------------------|---------|---------|
| A100 80G | 312 TFLOPS | 2.0 TB/s | ~156 |
| A100 40G | 312 TFLOPS | 1.55 TB/s | ~200 |
| H100 SXM | ~990 TFLOPS | 3.35 TB/s | ~296 |
| L40S | ~180 TFLOPS | 0.86 TB/s | ~210 |
| RTX 4090 | ~165 TFLOPS | 1.0 TB/s | ~165 |

常见算子的 AI：

| 算子 | AI (FLOP/Byte) | 结论 |
|------|---------------|------|
| 大矩阵乘 GEMM | 10^3 ~ 10^4 | 算力瓶颈（Tensor Core 满载） |
| 大 batch 逐元素 | ~1 | 带宽瓶颈 |
| 归约 (reduce/sum) | ~1 | 带宽瓶颈 |
| 逐元素算子（激活函数、GELU） | ~0.5~1 | 带宽瓶颈，和 GEMM 混在一起吃带宽 |

**这就是「为什么大模型推理里大部分时间花在激活函数和归约上」**——它们的 AI 只有个位数，会把卡的带宽吃满，Tensor Core 在旁边空转。

优化手段：算子融合（Kernel Fusion），把 elementwise + reduce 合成一个 kernel 少读写几遍显存。vLLM、TensorRT、FlashAttention 都是这个思路。

## 五、访存层次

```text
寄存器       ~1 周期      每线程私有
Shared Mem   ~30 周期     每 block 共享，手动管理，可做 bank conflict
L1 / Texture ~50 周期
L2           ~200 周期    全卡共享
显存         ~400-800 周期
```

优化要点：

- **合并访存（coalescing）**：相邻线程访问相邻地址，一 warp 32 次访问合并成 1~4 次事务。
- **Shared Memory bank conflict**：32 个线程访问不同 bank 才并行，同 bank 不同地址串行。
- **Occupancy（占用率）**：同时驻留的 warp 数。太低填不满流水线，太高寄存器放不下。
- **Host-Device 拷贝**：PCIe 只有 32~64GB/s，比显存慢一个数量级，数据预处理放 GPU 上做（DALI）。

## 六、性能排查命令

```bash
nvidia-smi dmon -s pucm -d 1        # 每秒：sm/mem 利用率、功耗
nsys profile -o rep python train.py # 时间线，找 GPU 空隙
ncu ./app                           # Nsight Compute，单 kernel 级别分析
```

看两个利用率：

| sm 利用率 | mem 利用率 | 判断 |
|----------|-----------|------|
| 高 | 高 | 正常，跑满了 |
| 低 | 高 | 带宽瓶颈 → 算子融合、减访存 |
| 高 | 低 | 算力瓶颈，但多半在跑小 kernel / launch 开销 |
| 低 | 低 | 空转 → 等 CPU 喂数据、多进程串行、IO 瓶颈 |

## 七、反推 K8s 参数

| 显存结论 | K8s 动作 |
|---------|----------|
| 模型 + KV Cache > 单卡 | 多卡 Tensor Parallel（`nvidia.com/gpu: 2`），或换大卡 |
| CPU 喂数据慢（mem 低 sm 低） | 提高 CPU limit，DataLoader 加 `num_workers`，固定 CPU 亲和 |
| 通信是瓶颈 | 检查 `nvidia-smi topo -m`，NVLink 别跨 PCIe；用 NCCL 而非 Gloo |
| 显存有余量、算力打满 | 增加并发请求数（推理服务调 `max_num_seqs`），别加卡 |

## 小结

- 显存 = 权重 + 梯度 + 优化器 + 激活，训练约为参数的 16 倍（BF16+Adam）。
- 显存不可 swap，OOM 只能靠模型切分或换卡，CPU limit 无关。
- AI < 拐点就是带宽瓶颈，靠融合算子而不是加算力。
- K8s 上 GPU Pod 要给足 CPU 内存和核数，否则 GPU 饿着。
