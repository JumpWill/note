# 调度与亲和性 (Scheduling & Affinity)

> 本章系统讲解 K8s 的 Pod 调度机制:节点选择、亲和性、污点容忍、优先级、抢占等。

## 一、K8s 调度概述

### 1.1 调度流程

```text
Pod 创建 → kube-scheduler 调度 → 选定 Node → kubelet 启动

调度过程:
1. 预选 (Filtering): 排除不满足条件的节点
   - 资源需求
   - 节点选择器
   - 亲和/反亲和
   - 污点容忍
   
2. 打分 (Scoring): 为剩余节点打分
   - 资源利用均衡
   - 亲和性偏好
   - 已有 Pod 分布
   
3. 选定: 最高分节点
4. 绑定: 写 spec.nodeName
```

### 1.2 调度器配置

```yaml
# kube-scheduler-config (1.18+)
apiVersion: kubescheduler.config.k8s.io/v1beta3
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler
  plugins:
    queueSort:
      enabled:
      - name: PrioritySort
    preFilter:
      enabled:
      - name: NodeResourcesFit
    filter:
      enabled:
      - name: NodeUnschedulable
      - name: NodeName
      - name: NodeAffinity
      - name: NodeResourcesFit
      - name: VolumeRestrictions
    score:
      enabled:
      - name: NodeResourcesFit
      - name: NodeAffinity
      - name: TaintToleration
```

## 三、Node Affinity (节点亲和性)

### 3.1 概念

Node Affinity 是 nodeSelector 的增强版,支持:
- 必须满足 (required)
- 优先满足 (preferred)
- 多种操作符 (In, NotIn, Exists, DoesNotExist, Gt, Lt)

### 3.2 完整示例

```yaml
spec:
  affinity:
    nodeAffinity:
      # 硬要求 (调度失败则 Pending)
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          # 必须运行在 Linux
          - key: kubernetes.io/os
            operator: In
            values: ["linux"]
          # 不能在 us-east-1b
          - key: zone
            operator: NotIn
            values: ["us-east-1b"]
        # 第二个 term (OR 关系)
        - matchExpressions:
          # 或者是 arm64
          - key: kubernetes.io/arch
            operator: In
            values: ["arm64"]

      # 软偏好 (评分,不强制)
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80                 # 1-100
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values: ["nvme-ssd"]    # 优先 NVMe SSD

      - weight: 20
        preference:
          matchExpressions:
          - key: zone
            operator: In
            values: ["us-east-1a"]
```

### 3.3 操作符

```text
In              - 在列表中
NotIn          - 不在列表中
Exists         - key 存在 (不管 value)
DoesNotExist   - key 不存在
Gt             - 大于 (数值)
Lt             - 小于 (数值)
```

## 四、Pod Affinity / Anti-Affinity

### 4.1 概念

根据**其他 Pod 的标签**决定调度,而非节点标签。

```text
适用场景:
- 把相关 Pod 调度到同一节点 (缓存亲和)
- 把相同 Pod 分散到不同节点 (高可用反亲和)
```

### 4.2 Pod Affinity (亲和)

```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache             # 与 cache 应用同节点
            tier: backend
        topologyKey: kubernetes.io/hostname   # 同一节点
        namespaces:
        - production

      # 或 preferred
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: db
          topologyKey: kubernetes.io/hostname
```

### 4.3 Pod Anti-Affinity (反亲和)

```yaml
spec:
  affinity:
    podAntiAffinity:
      # 硬要求: 不要与 cache 同节点
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache
        topologyKey: kubernetes.io/hostname

      # 软偏好: 尽量分散到不同可用区
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: web
          topologyKey: topology.kubernetes.io/zone
```

### 4.4 topologyKey

```text
常用的 topologyKey:
- kubernetes.io/hostname         # 单个节点
- topology.kubernetes.io/zone    # 可用区
- topology.kubernetes.io/region  # 地域
- 自定义标签                     # 节点机房等
```

### 4.5 实战:Web 三副本分散

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.25

      affinity:
        # 软反亲和: 尽量分散到不同节点
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web
              topologyKey: kubernetes.io/hostname
```

## 五、Taints 与 Tolerations (污点)

### 5.1 概念

```text
Taint (污点): 节点上的"拒绝标记"
Toleration (容忍): Pod 上"忍受"污点的声明

工作原理:
- 节点有 Taint → 默认 Pod 不会调度到该节点
- Pod 有 Toleration → 可以调度到该节点 (匹配污点)

使用场景:
1. 专用节点 (GPU、SSD)
2. 隔离环境 (master 节点不调度业务 Pod)
3. 节点维护 (cordon + drain)
```

### 5.2 Taint 操作

```bash
# 给节点打污点
kubectl taint nodes node1 key=value:NoSchedule

# 三种 effect:
# NoSchedule       - 硬拒绝,绝不调度
# PreferNoSchedule - 软拒绝,尽量不调度
# NoExecute       - 驱逐现有 Pod + 不调度新 Pod

# 去除污点
kubectl taint nodes node1 key=value:NoSchedule-

# 常用污点
kubectl taint nodes node1 node-role.kubernetes.io/master=true:NoSchedule
kubectl taint nodes node1 dedicated=gpu:NoSchedule
kubectl taint nodes node1 environment=production:PreferNoSchedule
```

### 5.3 Toleration 配置

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"

  # 容忍所有污点 (不推荐生产)
  - operator: "Exists"

  # 容忍 master 节点
  - key: "node-role.kubernetes.io/master"
    operator: "Exists"
    effect: "NoSchedule"
    tolerationSeconds: 300     # 5 分钟容忍时间
```

### 5.4 实战:GPU 节点

```bash
# GPU 节点打污点
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule
```

```yaml
# GPU Pod 容忍
spec:
  containers:
  - name: ml-training
    image: tensorflow/tensorflow:latest-gpu
    resources:
      limits:
        nvidia.com/gpu: 1       # 申请 1 个 GPU

  tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"

  nodeSelector:
    gpu: "true"                 # 同时指定节点标签
```

### 5.5 节点维护 (cordon / drain)

```bash
# 1. cordon: 标记节点不可调度
kubectl cordon node1
# 节点状态变为 SchedulingDisabled
# 新 Pod 不会调度到该节点
# 现有 Pod 继续运行

# 2. drain: 驱逐 Pod (用于维护)
kubectl drain node1 --ignore-daemonsets
# - 驱逐所有非 DaemonSet Pod
# - 删除 EmptyDir 等本地数据
# - 等 Pod 优雅终止

# 3. uncordon: 恢复调度
kubectl uncordon node1
```

## 六、优先级与抢占

### 6.1 PriorityClass

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000                  # 数值越高优先级越高
globalDefault: false
description: "High priority workloads"
```

```yaml
# Pod 使用
spec:
  priorityClassName: high-priority
```

### 6.2 内置 PriorityClass

```text
system-cluster-critical     - 3000000000
system-node-critical        - 2000000000
system-kube-controller      - 200000000
system-kube-scheduler       - 200000000
```

### 6.3 抢占 (Preemption)

```text
低优先级 Pod 可能被高优先级 Pod 抢占:
1. 高优先级 Pod 调度失败
2. 抢占低优先级 Pod
3. 被抢占的 Pod 优雅终止 (默认 30s)
4. 高优先级 Pod 调度成功

注意:
- 抢占通过 SIGTERM (30s grace period)
- 业务应用要能优雅处理 SIGTERM
- 默认开启,可在 PriorityClass 中禁用
```

## 七、Pod 拓扑分布约束 (Pod Topology Spread Constraints)

### 7.1 概念

K8s 1.18+ 引入,用于**更细粒度的 Pod 分布控制**(比 anti-affinity 更强)。

```yaml
spec:
  topologySpreadConstraints:
  # 规则 1: 尽量在多个节点
  - maxSkew: 1                     # 最大偏差
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway   # 即使不满足也调度
    labelSelector:
      matchLabels:
        app: web

  # 规则 2: 尽量在多个可用区
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: web
```

### 7.2 与 Anti-Affinity 对比

| 维度 | Anti-Affinity | Topology Spread |
|------|---------------|------------------|
| 粒度 | 二元 (同/不同) | 数值 (maxSkew) |
| 灵活度 | 低 | 高 |
| 多拓扑 | 单一 | 多 (节点 + 区域) |
| 推荐 | 简单场景 | 生产推荐 |

## 八、资源 QoS (服务质量)

### 8.1 QoS 等级

```text
K8s 根据 requests/limits 分配 QoS:

在decribe node的时候最下方看到的资源的使用情况就是当前节点上所有的带有资源限制的pod的requests纸盒，而不带requests的pod就不会计算在其中，而使用情况会用于k8s调度来分析节点上的资源情况从而决定调度到哪里去；

1. Guaranteed (保证)
   - 所有容器都设了 limits (cpu + memory)
   - limits == requests (强烈推荐生产关键服务)

2. Burstable (突发)
   - 设了 requests,但 limits > requests 或没设 limits

3. BestEffort (尽力)
   - 都没设 requests 和 limits

驱逐优先级 (内存压力时):
   BestEffort > Burstable > Guaranteed
```

### 8.2 资源限制建议

```yaml
# Guaranteed 配置 (生产关键服务)
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: 500m             # 严格限速 (CPU 节流)
    memory: 512Mi         # 严格限制 (OOM 风险)

# Burstable 配置 (一般服务)
resources:
  requests:
    cpu: 200m
    memory: 256Mi
  limits:
    cpu: 1000m            # 突发允许
    memory: 1Gi

# BestEffort 配置 (非关键/批处理)
# 不设 requests/limits
```

## 九、调度实战

### 9.1 多可用区高可用

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-ha
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.25

      affinity:
        # 硬反亲和: 同一 Node 不能有 2 个 web
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: web
            topologyKey: kubernetes.io/hostname

      topologySpreadConstraints:
      # 软分布: 尽量在不同 Zone
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: web
```

### 9.2 节点维护完整流程

```bash
# 1. 标记节点不可调度
kubectl cordon node-1

# 2. 驱逐 Pod (会优雅终止)
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# --ignore-daemonsets: 忽略 DaemonSet
# --delete-emptydir-data: 删除 emptyDir 数据

# 3. 维护操作
ssh node-1 "yum update -y && reboot"

# 4. 节点恢复后,恢复调度
kubectl uncordon node-1

# 5. 验证
kubectl get nodes
kubectl get pods -o wide
```

## 十、调度性能与扩展性

### 10.1 大规模集群调度优化

```text
10,000+ 节点集群调度优化:

1. 调度器配置
   - percentageOfNodesToScore: 不要默认(会全集群评估)
   - 设置 5-10%, 大幅减少评估节点数

2. 减少非必要调度
   - 静态 Pod (mirror pods)
   - DaemonSet (无需调度)
   - 合理设置 replicas (避免过剩)

3. 预选 (Filtering) 优化
   - 简单 nodeSelector 优于复杂 Affinity
   - 减少不必要的 label 检查

4. 打分 (Scoring) 优化
   - LessAllocated 优先 (资源利用均衡)
   - BalancedAllocation
   - NodeAffinity 优先
```

### 10.2 Scheduler Profile

```yaml
# 多个调度器 Profile
apiVersion: kubescheduler.config.k8s.io/v1beta3
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler

- schedulerName: spot-scheduler
  plugins:
    score:
      enabled:
      - name: NodeResourcesFit   # 优先选择空闲节点
```

## 核心要点速记

### 调度三大手段

```text
1. nodeSelector / NodeAffinity   - 节点级调度
2. Pod Affinity/Anti-Affinity    - Pod 级调度 (其他 Pod 位置)
3. Taints / Tolerations          - 节点拒绝 + Pod 容忍
```

### 调度策略优先级

```text
硬要求 (required) > 软偏好 (preferred)
nodeSelector / nodeAffinity > podAffinity > taints
```

### 实战选型

```text
- 节点池化 → nodeSelector
- 同 Pod 集中 → podAffinity
- 不同 Pod 分散 → podAntiAffinity (硬) / topologySpread (软)
- 专用节点 (GPU) → taints + tolerations
- 多可用区 → topologySpreadConstraints
```

### 节点维护三步

```text
1. cordon   - 标记不可调度
2. drain    - 驱逐现有 Pod
3. uncordon - 恢复调度
```

### 亲和性 vs 反亲和性 vs 拓扑分布

```text
nodeAffinity:
   选择满足条件的节点
podAffinity:
   与某 Pod 同节点 (缓存亲和)
podAntiAffinity:
   与某 Pod 不同节点 (高可用)
topologySpreadConstraints:
   Pod 均匀分布在拓扑域 (推荐)
```

### QoS 三等级

```text
Guaranteed - requests == limits (推荐生产)
Burstable  - requests < limits
BestEffort - 不设 requests/limits
```

## 十、Pod 均匀分散调度（Topology Spread Constraints）

### 10.1 为什么需要均匀分散

```text
业务场景：

  场景 1：高可用（HA）
    - 同一个 Deployment 的多个 Pod 必须在不同节点
    - 防止单节点故障导致全部 Pod 不可用

  场景 2：负载均衡
    - Pod 均匀分布在所有节点
    - 避免某些节点过载

  场景 3：滚动更新
    - 更新时尽量不集中在同一节点
    - 减少单节点资源压力

  场景 4：多机房/多区域
    - Pod 分布在不同 zone/region
    - 应对机房级故障

反例（不均匀分布）：
  ❌ 6 个 Pod 都调度到 node1，node2/node3 闲置
  ❌ 节点故障时全部受影响
  ❌ 资源利用不均
```

### 10.2 5 种实现方式对比

| 方式 | 严格度 | 灵活度 | 复杂度 | 推荐度 |
|------|--------|--------|--------|--------|
| **Pod Topology Spread** | 强 | 高 | 低 | ⭐⭐⭐⭐⭐ |
| **PodAntiAffinity (required)** | 最强 | 低 | 低 | ⭐⭐⭐ |
| **PodAntiAffinity (preferred)** | 软 | 中 | 低 | ⭐⭐⭐ |
| Node AntiAffinity | 中 | 中 | 中 | ⭐⭐ |
| Taints + 节点标签 | 弱 | 高 | 高 | ⭐⭐ |

### 10.3 推荐方式 1：Pod Topology Spread Constraints（强烈推荐）

#### 完整示例

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: production
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.25
      
      # ⭐ Pod 均匀分散调度的核心配置
      topologySpreadConstraints:
      # 约束 1：按节点均匀分布
      - maxSkew: 1              # 最大倾斜度（节点间 Pod 数量差异）
        topologyKey: kubernetes.io/hostname    # 按节点拓扑
        whenUnsatisfiable: ScheduleAnyway    # 满足不了时仍调度
        labelSelector:
          matchLabels:
            app: web            # 匹配标签
    
      # 约束 2：按 zone 均匀分布（多可用区）
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule    # 满足不了不调度
        labelSelector:
          matchLabels:
            app: web
```

#### 配置字段详解

```text
maxSkew: int                # 最大倾斜度（核心参数）
  - 1：节点间 Pod 数差 ≤ 1（最严格）
  - 2：差 ≤ 2（宽松）
  - 推荐：1（生产）

topologyKey: string         # 拓扑域 key
  - kubernetes.io/hostname        # 节点
  - topology.kubernetes.io/zone    # 可用区
  - topology.kubernetes.io/region  # 区域
  - 自定义 topology key

whenUnsatisfiable: enum    # 不满足时怎么办
  - DoNotSchedule（推荐）：不调度
  - ScheduleAnyway：尽量调度

labelSelector:           # 匹配哪些 Pod
  - 不填：当前 Pod
  - 填：匹配 label 的 Pod

matchLabels:               # Pod label 选择
```

### 10.4 推荐方式 2：PodAntiAffinity required

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  template:
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: web
            topologyKey: kubernetes.io/hostname
            # 必须满足：所有 web Pod 不能在同一节点
      containers:
      - name: web
        image: nginx:1.25
```

**注意**：当 replicas > 节点数 时，多余的 Pod 会 Pending。

### 10.5 推荐方式 3：PodAntiAffinity preferred（软约束）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  template:
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100              # 权重 1-100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:1.25
```

**特点**：
- 软约束：尽量满足
- 不满足时：仍会调度
- 不会 Pending

### 10.6 推荐方式 4：Node Affinity + 反亲和组合

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 6
  template:
    spec:
      affinity:
        # 节点亲和：只在特定节点
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: kubernetes.io/os
                operator: In
                values: ["linux"]
        
        # Pod 反亲和：均匀分布
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:1.25
```

### 10.10 常见问题

```text
Q1: Pod Pending，显示 "didn't match topology spread constraint"
A1: 调大 maxSkew（如 1 → 2）
    或 whenUnsatisfiable 改为 ScheduleAnyway
    或增加节点数
    或降低 replicas

Q2: maxSkew 应该设多大？
A2: 推荐 1 或 2
    1 = 严格（节点间最多差 1）
    2 = 宽松（可差 2）
    不能设 0（不倾斜不可能）

Q3: 节点数少于 Pod 数会怎样？
A3: 例：3 节点 6 个 Pod
    - maxSkew=1：3+2+1 分布
    - maxSkew=2：3+3+0 分布
    - whenUnsatisfiable: ScheduleAnyway
      不会 Pending（仍会调度）
    - whenUnsatisfiable: DoNotSchedule
      不会调度（保持 Pending）
    ⚠️ 建议保留 ScheduleAnyway

Q4: 与 PodAntiAffinity 区别？
A4: PodAntiAffinity: 严格反亲和（不计算倾斜度）
    TopologySpread: 计算分布均匀度（maxSkew）
    推荐：优先 TopologySpread（更智能）
    PodAntiAffinity only required 是最严格的

Q5: 多 topologySpreadConstraints 怎么用？
A5: 按顺序应用，每个独立判断
    例：先按 zone 分布，再按 hostname 分布
    两个约束同时满足才行
    第一个约束失败 → 整个失败
```

### 10.11 速记卡

```
Pod 均匀分散调度：

  5 种方式：
    1. topologySpreadConstraints（推荐）
    2. podAntiAffinity required
    3. podAntiAffinity preferred
    4. nodeAntiAffinity
    5. taints + nodeSelector

  topologySpreadConstraints 三要素：
    maxSkew: 1              # 倾斜度
    topologyKey: kubernetes.io/hostname | topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway | DoNotSchedule

  最佳实践：
    - maxSkew: 1
    - topologyKey: kubernetes.io/hostname（同节点）
    - whenUnsatisfiable: ScheduleAnyway
    - 多约束嵌套（zone + hostname）

  反例：
    - 6 Pod 全在 node1（节点故障全挂）
    - 调度不均导致资源浪费

  速记：
    - Topology Spread = 软约束 + 智能计算
    - PodAntiAffinity = 硬约束 + 简单
    - 优先用 Topology Spread
```

## 十一、Pod 驱逐（Eviction）详解

### 11.1 什么是 Pod 驱逐

```text
Pod 驱逐（Eviction） = K8s 主动终止 Pod 的机制

本质：
  - K8s API 调用 Eviction 子资源
  - 通知 kubelet 终止 Pod
  - Pod 删除后由 ReplicaSet 重建
  - 是 Pod 主动被驱逐的机制

与普通删除的区别：
  普通删除（kubectl delete pod）：
    - 立即删除
    - 不受 PDB 限制
    - 不优雅退出（除非加 --grace-period）
  
  驱逐（Eviction）：
    - 通过 Eviction API
    - 必须遵守 PDB
    - 默认优雅退出（30 秒）
    - 可被 Descheduler 或上游系统调用
```

### 11.2 驱逐的 6 大场景

#### 场景 1：节点资源压力（MemoryPressure）

```text
触发条件：节点内存不足
机制：
  - kubelet 检测到节点可用内存低
  - 触发 MemoryPressure 驱逐
  - 驱逐 QoS 为 BestEffort / Burstable 的 Pod
  - 优先驱逐耗资源最多的 Pod

Pod 优先级：
  - Guaranteed（最安全）→ 最后驱逐
  - Burstable → 次之
  - BestEffort（最先驱逐）

Kubelet 配置：
  --eviction-hard=memory.available<500Mi
  --eviction-soft=memory.available<1Gi
  --eviction-pressure-transition-period=1m
  --eviction-max-pod-grace-period=30s
```

#### 场景 2：节点资源压力（DiskPressure）

```text
触发条件：节点磁盘空间不足
机制：
  - kubelet 监控节点磁盘
  - 触发 DiskPressure
  - 驱逐非关键 Pod 释放磁盘
  - 通常驱逐使用了大量磁盘的 Pod（如日志 Pod）

Kubelet 配置：
  --eviction-hard=nodefs.available<10%
  --eviction-hard=imagefs.available<15%
```

#### 场景 3：节点 NotReady（NodeUnschedulable）

```text
触发条件：
  - 节点心跳超时
  - kubelet 无法与 API Server 通信
  - 网络故障

机制：
  - controller-manager 检测到节点 NotReady
  - 标记 NodeController 启动驱逐
  - 驱逐该节点上所有 Pod
  - 让 Pod 重新调度到健康节点

时间：
  - 默认 5 分钟（pod-eviction-timeout）
  - 节点 Ready 恢复后会停止驱逐
```

#### 场景 4：Pod 抢占（Preemption）

```text
触发条件：K8s 调度器抢占
机制：
  - 节点资源不够
  - 调度新 Pod 触发抢占
  - 选择优先级低的 Pod 驱逐
  - 给高优先级 Pod 让位

优先级机制（PriorityClass）：
  - 高 PriorityClass：被驱逐可能性低
  - 低 PriorityClass：容易被驱逐
  - 默认 0（system-cluster-critical=2000000000）
```

#### 场景 5：PDB 控制驱逐

```text
PodDisruptionBudget（PDB）：
  - 限制同时驱逐的 Pod 数
  - 任何主动驱逐都必须遵守
  - Descheduler、VPA、节点维护都受限制

示例：
  - minAvailable: 2（至少 2 个）
  - maxUnavailable: 1（最多 1 个不可用）
  - 触发驱逐时检查
  - 违反 PDB → 跳过驱逐
```

#### 场景 6：主动驱逐（Descheduler）

```text
触发：Descheduler 主动驱逐
场景：
  - 资源不均衡
  - 违反反亲和
  - 低利用率节点平衡
  - 镜像更新
  - 节点维护

详细见 23-Descheduler使用指南.md
```

### 11.3 驱逐的 9 大原因

```text
Pod 驱逐原因（Eviction Reason）：

┌────────────────────────────┬──────────────────────────────────┐
│  Reason                    │  说明                            │
├────────────────────────────┼──────────────────────────────────┤
```

### 11.4 驱逐的发生时间

#### Eviction API 时序图

```text
Pod 驱逐的完整时间线：

  T0：触发条件满足
  T1：调用 Eviction API
      POST /api/v1/pods/<name>/eviction
      Body: {apiVersion, kind, metadata, deletionTimestamp, ...}
  T2：API Server 接收请求
      - 验证 RBAC
      - 检查 PDB（必须满足）
      - 若违反 PDB → 拒绝，返回 403
  T3：通过 PDB 检查
      - 检查 PDB 的 minAvailable
      - 统计当前可用 Pod 数
      - 决定是否允许驱逐
  T4：API Server 设置 Pod 的 metadata.deletionTimestamp
      - 标记 Pod 为终止中
  T5：kubelet watch 到 Pod 删除事件
      - 触发 PreStop hook（如有）
      - 等待 gracePeriod（默认 30 秒）
  T6：执行 PreStop hook
      - 应用可执行 hook
      - 向 API Server 报告完成
  T7：等待 gracePeriod
      - 最多 30 秒（默认）
      - 若 PreStop 完成则立即进入下一步
  T8：发送 SIGTERM 给容器
  T9：等待容器优雅退出
      - 默认 30 秒
      - 容器可捕获 SIGTERM 自定义清理
  T10：超时后发送 SIGKILL
      - 默认 30 秒后
      - 强制杀死容器
  T11：清理 Pod 资源
      - 删除容器
      - 清理网络
  T12：完成驱逐
      - Pod 在 API Server 标记为删除
      - ReplicaSet 控制器重新创建新 Pod
  T13：新 Pod 被调度
       - 调度到其他节点
       - ReplicaSet 创建新副本
  T14：完成循环
```

#### 驱逐各阶段时间

```text
驱逐各阶段时间控制：

  ┌────────────────────┬──────────────┬──────────────────────┐
  │  阶段              │  默认时间    │  控制参数              │
  ├────────────────────┼──────────────┼──────────────────────┤
  │  PDB 检查          │  实时         │  PDB 配置             │
  │  PreStop Hook      │  0 秒        │  hook 自身实现         │
  │  Grace Period      │  30 秒       │  terminationGracePeriodSeconds│
  │  PreStop 完成等待  │  gracePeriod  │  上述配置            │
  │  SIGTERM → SIGKILL │  gracePeriod  │  上述配置            │
  │  Pod 删除          │  实时         │  K8s API              │
  │  ReplicaSet 重建   │  < 1 秒       │  K8s 控制器           │
  │  调度器分配        │  < 100 ms    │  调度器配置           │
  │  镜像拉取          │  数秒 - 数分   │  镜像大小/网络       │
  │  容器启动          │  数秒        │  runtime 启动          │
  └────────────────────┴──────────────┴──────────────────────┘

  完整驱逐周期：30-120 秒（最坏情况）
```

#### 关键时间参数

```text
Pod 驱逐的关键时间参数：

  spec.terminationGracePeriodSeconds：
    - 默认 30 秒
    - 控制 SIGTERM 到 SIGKILL 之间的等待
    - 0 秒 = 立即 kill
    - 60 秒 = 给应用 60 秒清理

  spec.containers[].lifecycle.preStop：
    - 钩子函数
    - 在 SIGTERM 前执行
    - 通常用于清理（flush 数据、注销服务）
    - 默认 0 秒

  preStop 完成机制：
    - 钩子执行完立即进入 SIGTERM
    - 无需等待 gracePeriod 剩余时间
    - 但仍受 gracePeriod 上限

  kubelet --eviction-max-pod-grace-period：
    - 节点压力驱逐时的最大宽限期
    - 默认 30 秒
    - 比 Pod spec.terminationGracePeriodSeconds 小
```

### 11.5 驱逐的完整时间线（实战示例）

```text
T0 (00:00.000)：节点 node1 内存使用 90%

      计算需要驱逐的 Pod：

        - 计算释放内存量
```

### 11.6 驱逐与 PDB 的关系

```text
PDB 限制与驱逐的交互：

  PodDisruptionBudget（PDB）配置：
    apiVersion: policy/v1
    kind: PodDisruptionBudget
    metadata:
      name: web-pdb
    spec:
      minAvailable: 2      # 至少 2 个 Pod 可用
      selector:
        matchLabels:
          app: web

  驱逐决策：
    当前状态：3 个 web Pod
    PDB 要求：minAvailable: 2（即至少 2 个不可驱逐）
    驱逐 1 个 → 剩 2 个 → 满足 PDB → 允许驱逐
    再驱逐 1 个 → 剩 1 个 → 不满足 PDB → 拒绝驱逐

  ⚠️ 重要：
    - 驱逐时检查当前可用数
    - 若不满足 → 跳过该 Pod
    - 不会报错，只是跳过
    - 重要服务必须配置 PDB
```

### 11.7 驱逐最佳实践

```text
1. 关键服务必须配置 PDB
   apiVersion: policy/v1
   kind: PodDisruptionBudget
   metadata:
     name: app-pdb
   spec:
     # 推荐 minAvailable
     minAvailable: 2

   ⚠️ minAvailable 和 maxUnavailable 只能设一个

2. 合理设置 terminationGracePeriodSeconds
   spec:
     terminationGracePeriodSeconds: 30  # 给应用清理时间

3. 配置 preStop hook 优雅清理
   containers:
   - name: app
     lifecycle:
       preStop:
         exec:
           command: ["sh", "-c", "kill -SIGTERM 1 && sleep 5"]
     # 5 秒内完成清理

4. 监控驱逐事件
   kubectl get events --field-selector reason=Evicted -A
   kubectl get events --field-selector reason=Descheduled -A

5. 驱逐时配合 readinessProbe
   readinessProbe:
     httpGet: {path: /healthz, port: 8080}
     initialDelaySeconds: 10
     periodSeconds: 5
   # Service 会立即从 Endpoints 移除不健康的 Pod

6. 滚动更新与驱逐的配合
   - Descheduler 驱逐触发 rolling update
   - maxUnavailable 控制并发
   - maxSurge 控制超额
```

```bash
#         ↑ 已驱逐       ↑

# 2. 查看驱逐原因
kubectl describe pod <pod-name> | grep -A 5 "Status"
kubectl describe pod <pod-name> | grep -B 2 "Evicted"

# 3. 查看所有驱逐事件
kubectl get events -A --field-selector reason=Evicted

# 4. 查看 Descheduler 驱逐
kubectl get events -A --field-selector reason=Descheduled

# 5. 查看驱逐原因分布
kubectl get events -A --field-selector reason=Evicted -o json | \
  jq -r '.items[].reason' | sort | uniq -c

# 6. 模拟驱逐（不真驱逐）
kubectl drain <node-name> --dry-run

# 7. 主动驱逐
kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data

# 8. 取消驱逐
kubectl uncordon <node-name>
```

### 11.9 驱逐 vs 抢占 vs 删除

```text
驱逐（Eviction）：
  - 主动（Descheduler）或被动（节点压力）
  - 遵守 PDB
  - 优雅退出（默认 30s）
  - 触发 ReplicaSet 重建

抢占（Preemption）：
  - 调度器主动
  - 选择低优先级 Pod 驱逐
  - 为高优先级 Pod 让位
  - 仍通过 Eviction API

普通删除（kubectl delete pod）：
  - 立即删除
  - 不受 PDB 限制
  - 默认优雅退出
  - 可加 --force --grace-period=0 强制

主动驱逐（kubectl drain）：
  - 节点维护
  - 逐个驱逐 Pod
  - 遵守 PDB
  - 配合 --ignore-daemonsets
```

### 11.10 驱逐的速记卡

```text
驱逐核心：
  1. 触发：节点压力 / 抢占 / Descheduler / drain
  2. 机制：Eviction API → 标记删除 → preStop → SIGTERM → SIGKILL
  3. 流程：驱逐 → ReplicaSet 重建 → 调度器调度 → 镜像拉取 → 启动
  4. 时间：30-120 秒（含重建）
  5. 限制：必须遵守 PDB

驱逐原因（Reasons）：
  NodeUnschedulable / NodeNotReady / NodeAffinity
  NodeTaints / PodAntiAffinity / PodTopologySpread
  TooManyPods / NodeUnderMemoryPressure
  NodeUnderDiskPressure / NodeUnderPIDPressure
  FailedScheduling / EvictedByKubelet
  EvictedByDescheduler / Preempted / EvictedByPodGC

驱逐生命周期（默认 30s）：
  T0：触发
  T1：API Server 检查 PDB
  T2：设置 deletionTimestamp
  T3：执行 preStop hook
  T4：等待 gracePeriod（30s）
  T5：发送 SIGTERM
  T6：等待容器优雅退出
  T7：超时发送 SIGKILL
  T8：清理资源
  T9：ReplicaSet 重建（数秒）
  T10：调度器分配新节点
  T11：镜像拉取 + 启动

最佳实践：
  - 关键服务配置 PDB
  - 合理设置 terminationGracePeriodSeconds
  - 使用 preStop hook 优雅清理
  - 配合 readinessProbe 快速剔除
  - 监控驱逐事件
  - 排除系统 Pod（excludeRef）
```

### 11.11 驱逐与其他 K8s 概念的关系

```text
驱逐 与 K8s 其他概念的关系：

  调度（Scheduling）：
    新 Pod → 调度器 → 选节点 → 创建

  抢占（Preemption）：
    调度高优先级 Pod → 选低优先级 Pod 驱逐 → 给高优先级让位

  重调度（Descheduler）：
    主动驱逐不符合期望的 Pod → ReplicaSet 重建

  驱逐（Eviction）：
    是上述所有场景的共同执行机制

  节点维护（Drain）：
    主动驱逐节点上所有 Pod → 标记 unschedulable

  Pod GC（Garbage Collection）：
    异步驱逐已终止的 Pod（kubelet --maximum-dead-pods）
```

## 十二、Pod 驱逐的配置详解（软驱逐 vs 硬驱逐）

### 12.1 软驱逐 vs 硬驱逐

```text
K8s 驱逐的两种模式：

  ┌─────────────────┬────────────────────┐
  │  软驱逐           │  硬驱逐             │
  │  (Soft)          │  (Hard)             │
  ├─────────────────┼────────────────────┤
  │  触发条件        │  触发条件           │
  │  阈值有警告期    │  立即触发           │
  │  时间窗口        │  立即驱逐           │
  │  Pod 优雅退出    │  可能立即 kill       │
  └─────────────────┴────────────────────┘

软驱逐（Soft Eviction）：
  - 阈值设置有警告期（--eviction-soft）
  - 超过阈值 + 宽限期（--eviction-soft-grace-period）
  - 期间不驱逐
  - 宽限期到才驱逐
  - 给 Pod 优雅退出时间
  - 适合大多数场景（推荐）

硬驱逐（Hard Eviction）：
  - 阈值无宽限期（--eviction-hard）
  - 超过阈值立即驱逐
  - Pod 立即收到 SIGTERM
  - 宽限期内尽力优雅退出
  - 适合紧急保护场景
```

### 12.2 软驱逐 vs 硬驱逐对比

| 维度 | 软驱逐 | 硬驱逐 |
|------|--------|--------|
| 触发方式 | 阈值+宽限期 | 立即触发 |
| 优雅退出 | 充分 | 尽力 |
| 数据丢失风险 | 低 | 较高 |
| 适用场景 | 日常资源回收 | 紧急保护 |
| 推荐度 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

### 12.3 核心驱逐参数

#### 完整参数对照表

```text
┌─────────────────────────────────┬────────────┬──────────────────┐
│  参数                            │  默认      │  推荐             │
├─────────────────────────────────┼────────────┼──────────────────┤
│  --eviction-hard                │  -         │  节点保护          │
│  --eviction-soft                │  -         │  资源回收          │
│  --eviction-soft-grace-period   │  -         │  优雅退出          │
│  --eviction-pressure-transition-period │ 5m  │  5m               │
│  --eviction-max-pod-grace-period│ 30s       │  30-60s           │
│  --eviction-minimum-reclaim     │  -         │  根据资源定         │
│  --image-gc-high-threshold     │  85%       │  85%               │
│  --image-gc-low-threshold      │  80%       │  80%               │
│  --kube-reserved                 │  -         │  关键资源          │
│  --system-reserved              │  -         │  关键资源          │
│  --max-pods                     │  110       │  根据节点           │
└─────────────────────────────────┴────────────┴──────────────────┘
```

### 12.4 软驱逐配置详解

#### 软驱逐参数

```text
软驱逐（Soft Eviction）：
  - 设置软阈值（--eviction-soft）
  - 设置宽限期（--eviction-soft-grace-period）
  - 资源使用超过软阈值
  - 启动宽限期倒计时
  - 宽限期内继续驱逐
  - 但只在压力持续时驱逐

关键行为：
  - 软阈值是"警告值"
  - 不是立即驱逐
  - 启动倒计时
  - 期间可能恢复
  - 恢复则不驱逐
  - 必须持续超过整个宽限期才驱逐
```

#### 软驱逐完整配置

```yaml
# KubeletConfiguration（10-eviction-soft）
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
evictionHard:
  memory.available:  "200Mi"     # 硬阈值：可用内存 < 200Mi 立即驱逐
  nodefs.available:  "10%"      # 硬阈值：根分区 < 10% 立即驱逐
  imagefs.available: "15%"     # 硬阈值：镜像分区 < 15% 立即驱逐
  pid.available:    "10%"      # 硬阈值：PID < 10% 立即驱逐

evictionSoft:
  memory.available:  "500Mi"   # 软阈值：可用内存 < 500Mi 启动宽限期
  nodefs.available:  "15%"     # 软阈值：根分区 < 15% 启动宽限期
  imagefs.available: "20%"     # 软阈值：镜像分区 < 20% 启动宽限期
  pid.available:    "15%"      # 软阈值：PID < 15% 启动宽限期

# 软驱逐宽限期
evictionSoftGracePeriod:
  memory.available:  "1m30s"  # 软阈值持续 1 分 30 秒才驱逐
  nodefs.available:  "1m30s"  # 给 Pod 充分时间清理
  imagefs.available: "1m30s"
  pid.available:    "1m"

# 软驱逐最小回收量
evictionMinimumReclaim:
  memory.available:  "200Mi"   # 驱逐后至少回收 200Mi
  nodefs.available:  "5%"
  imagefs.available: "5%"
  pid.available:    "5%"

# 资源预留
evictionPressureTransitionPeriod: "5m"   # 软过渡时间
kubeReserved:
  memory:  "500Mi"           # K8s 系统预留
  cpu:     "500m"
systemReserved:
  memory:  "1Gi"
  cpu:     "1"
```

### 12.5 硬驱逐配置详解

#### 硬驱逐参数

```text
硬驱逐（Hard Eviction）：
  - 设置硬阈值（--eviction-hard）
  - 超过阈值立即触发
  - 没有宽限期
  - Pod 收到 SIGTERM
  - 在 gracePeriod 内尽力优雅退出
  - 超时后强制 SIGKILL

  ⚠️ 硬驱逐是最后手段
  - 数据丢失风险高
  - 仅用于节点保护
  - 避免误配置
```

#### 硬驱逐完整配置

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

# 硬驱逐：紧急保护
evictionHard:
  memory.available:  "100Mi"   # 节点内存 < 100Mi 立即驱逐
  nodefs.available:  "5%"      # 根分区 < 5% 立即驱逐
  imagefs.available: "10%"     # 镜像分区 < 10% 立即驱逐
  pid.available:    "3%"       # PID < 3% 立即驱逐
  # 注意：inodes.available 也是硬驱逐指标

# 单 Pod 最大宽限期（驱逐时的 grace period）
evictionMaxPodGracePeriod: 30   # 默认 30s

# 软驱逐：日常资源回收
evictionSoft:
  memory.available:  "500Mi"
  nodefs.available:  "15%"
  imagefs.available: "20%"
  pid.available:    "15%"

evictionSoftGracePeriod:
  memory.available:  "1m30s"  # 软驱逐延迟 1m30s
  nodefs.available:  "1m30s"
  imagefs.available: "1m30s"
  pid.available:    "1m"

# 驱逐最小回收量（驱逐后必须回收的量）
evictionMinimumReclaim:
  memory.available:  "500Mi"
  nodefs.available:  "5%"
  imagefs.available: "5%"
  pid.available:    "5%"

# 资源预留（K8s 系统、DaemonSet 等）
kubeReserved:
  memory:  "1Gi"
  cpu:     "500m"
  ephemeral-storage: "10Gi"

systemReserved:
  memory:  "2Gi"
  cpu:     "500m"
  ephemeral-storage: "10Gi"

# 强制驱逐时的 grace period 上限
evictionMaxPodGracePeriod: 30

# 驱逐压力过渡时间（软驱逐延迟触发）
evictionPressureTransitionPeriod: "5m"
```

### 12.6 软硬驱逐选择策略

#### 软驱逐适用场景

```text
推荐使用软驱逐：
  ✅ 日常资源回收（节点内存 80%）
  ✅ 资源使用逐渐增长
  ✅ 想要给 Pod 充足时间清理
  ✅ 想要避免不必要的中断
  ✅ 内存充足但有压力

示例：
  evictionSoft:
    memory.available: "500Mi"   # 软阈值：500Mi
  evictionSoftGracePeriod:
    memory.available: "2m"      # 2 分钟宽限
  evictionHard:
    memory.available: "100Mi"   # 硬阈值：100Mi（保护节点）
```

#### 硬驱逐适用场景

```text
应该使用硬驱逐：
  ⚠️ 紧急节点保护
  ⚠️ 避免 OOM（节点宕机）
  ⚠️ 避免磁盘满
  ⚠️ 避免 inode 耗尽

示例：
  evictionHard:
    memory.available: "100Mi"   # 硬阈值（节点保护）
    nodefs.available: "5%"      # 磁盘满保护
    imagefs.available: "10%"     # 镜像满保护
```

#### 软硬结合最佳实践

```yaml
evictionHard:                    # 硬：紧急保护
  memory.available: "100Mi"    # 节点保护底线
  nodefs.available: "5%"
  imagefs.available: "10%"

evictionSoft:                    # 软：日常回收
  memory.available: "500Mi"    # 软阈值（给 Pod 准备）
  nodefs.available: "15%"
  imagefs.available: "20%"

evictionSoftGracePeriod:        # 软驱逐宽限
  memory.available: "2m"        # 给 Pod 2 分钟清理
  nodefs.available: "1m30s"
  imagefs.available: "1m30s"

evictionMinimumReclaim:         # 最小回收量
  memory.available: "500Mi"    # 一次驱逐至少回收 500Mi
  nodefs.available: "5%"
```

### 12.12 驱逐配置管理

```bash
# 1. 查看当前配置
kubectl get nodes -o yaml | grep -A 30 "config:"

# 2. 修改 kubelet 配置
sudo vim /var/lib/kubelet/config.yaml

# 3. 重启 kubelet 应用
sudo systemctl restart kubelet

# 4. 验证配置生效
journalctl -u kubelet | grep -i "eviction\|threshold"

# 5. 滚动重启 kubelet（避免服务中断）

# 注意：重启 kubelet 不会重启 Pod
```

### 12.13 驱逐与其他 K8s 配置关系

```text
驱逐相关 K8s 配置体系：

  ┌─────────────────────────────────────┐
  │  Kubelet 配置（节点级）              │
  │  - evictionHard/Soft                 │
  │  - evictionMaxPodGracePeriod        │
  │  - /var/lib/kubelet/config.yaml    │
  └──────────────┬──────────────────────┘
                 │
                 ↓ 影响
  ┌──────────────────────────────────────┐
  │  PodDisruptionBudget（应用级）       │
  │  - 限制同时驱逐 Pod 数             │
  │  - 保护关键服务                     │
  └──────────────┬───────────────────────┘
                 │
                 ↓ 协调
  ┌──────────────────────────────────────┐
  │  PriorityClass（Pod 级）            │
  │  - 抢占优先级                      │
  │  - 影响驱逐顺序                     │
  └──────────────────────────────────────┘

驱逐优先级（综合）：
  1. PriorityClass 高的 Pod 最后驱逐
  2. PDB 内的 Pod 受保护
  3. 软驱逐先于硬驱逐
  4. 节点维护驱逐最后

驱逐决策优先级：
  PriorityClass > PDB > 节点压力
```
