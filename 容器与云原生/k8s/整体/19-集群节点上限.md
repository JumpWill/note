# K8s 集群节点上限与扩展性 (Kubernetes Cluster Scaling Limits)

> 本文档系统讲解 K8s 集群的节点规模上限，影响扩展性的关键因素，以及大规模集群的最佳实践。

## 二、影响集群规模的四大瓶颈

### 2.1 四大瓶颈速记

```text
大规模 K8s 集群四大瓶颈：

  1. etcd（数据存储）
     - 单 KV 存储
     - 受限于网络带宽和磁盘 IO
     - 默认上限 8GB

  2. API Server（控制面）
     - 每次 watch/list 调用
     - 受限于内存和网络
     - 处理所有组件请求

  3. Controller Manager（控制器）
     - 监听全集群资源
     - 全量 reconcile 开销
     - 单点处理所有 CRD

  4. Scheduler（调度器）
     - 每次调度评估所有节点
     - 默认并发 16
     - 大集群调度慢
```

### 2.2 瓶颈示意

```text
┌─────────────────────────────────────────────────────────────┐
│                    K8s 集群组件                              │
│                                                              │
│  ┌──────────────────────────────────────────────────┐    │
│  │              etcd（数据存储）                       │    │
│  │  - 所有集群状态都存在这里                          │    │
│  │  - 网络带宽瓶颈（频繁 watch）                     │    │
│  │  - 磁盘 IO 瓶颈（频繁写）                       │    │
│  │  - 单集群瓶颈                                      │    │
│  └──────────────────────────────────────────────────┘    │
│                            ↑                               │
│  ┌──────────────────────────────────────────────────┐    │
│  │              API Server                            │    │
│  │  - 所有组件的通信中枢                              │    │
│  │  - watch 请求放大（1000 节点 × N 控制器）       │    │
│  │  - 处理所有读写请求                                │    │
│  │  - 内存压力（List/Watch）                          │    │
│  └──────────────────────────────────────────────────┘    │
│                            ↑                               │
│  ┌──────────────────────────────────────────────────┐    │
│  │         Controller Manager                         │    │
│  │  - 多个控制器监听所有资源                          │    │
│  │  - 每个控制器处理全部 CRD                          │    │
│  │  - 单点处理所有 reconcile                          │    │
│  └──────────────────────────────────────────────────┘    │
│                            ↑                               │
│  ┌──────────────────────────────────────────────────┐    │
│  │              Scheduler                            │    │
│  │  - 每次调度评估所有节点                            │    │
│  │  - 默认并发数低                                    │    │
│  │  - 大集群调度慢                                    │    │
│  └──────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

## 三、etcd 性能与扩展

### 3.1 etcd 的关键限制

```text
etcd 默认限制（v3.5+）：

  ┌─────────────────┬──────────────────┐
  │  参数            │  默认值           │
  ├─────────────────┼──────────────────┤
  │  --quota-backend │  8 GB（默认）    │
  │  --max-request-bytes│ 1.5 MB        │
  │  --max-snapshot   │  8 MB 默认        │
  │  推荐最大 key    │  1.5 MB          │
  │  推荐最大 value  │  8 MB            │
  │  KV 总数          │  几百万（建议）   │
  │  watch 数        │  几千/客户端      │
  └─────────────────┴──────────────────┘

  K8s etcd 实际使用：
    - 1 个 Pod ≈ 1-2 KB
    - 1 个 Node ≈ 5-10 KB
    - 100,000 Pod ≈ 200 MB（安全）
    - 5,000 Node ≈ 50 MB（安全）
```

### 3.2 etcd 性能基准

```text
etcd 性能（典型 SSD、3 节点集群）：

  ┌─────────────────┬──────────────────┐
  │  操作            │  性能             │
  ├─────────────────┼──────────────────┤
  │  写             │  10,000 ops/s     │
  │  读             │  30,000 ops/s     │
  │  批量写         │  100,000 ops/s    │
  │  watch 通知       │  5,000/s          │
  │  KV 总数         │  10M+            │
  │  存储大小        │  8 GB（默认）     │
  └─────────────────┴──────────────────┘

  K8s 中 etcd 实际负载：
    - 100 节点 × 100 Pod = 10,000 资源
    - 每次 reconcile = N 次 etcd 写
    - 100 节点 → ~5,000 etcd ops/s
    - 1,000 节点 → ~50,000 etcd ops/s
    - 5,000 节点 → ~250,000 etcd ops/s ⚠️ 超限
```

### 3.3 etcd 优化与扩展

```text
etcd 性能优化清单：

  ┌─────────────────┬──────────────────┐
  │  优化项          │  收益             │
  ├─────────────────┼──────────────────┤
  │  SSD 替代 HDD    │  10-100x IOPS     │
  │  专用服务器       │  隔离干扰         │
  │  调大 --quota-backend│  突破 8GB      │
  │  启用压缩        │  减少磁盘 IO      │
  │  --max-request-bytes│ 优化大对象      │
  └─────────────────┴──────────────────┘

etcd 扩展方案：
  1. K8s v1.28+: Konnectivity（替代 SSH tunnel）
     - API Server 到 kubelet 不走 etcd
     - 减少 etcd 压力

  2. etcd 分片（实验性）
     - K8s v1.29+ 探索中
     - 不同 CR 分片存储

  3. WatchCache 优化
     - API Server 内存缓存
     - 减少 etcd 读压力

  4. CRD 收敛
     - 不必要的 CR 少用
     - 自定义 CR 控制数量
```

## 四、API Server 性能

### 4.1 API Server 工作负载

```text
API Server 处理的所有请求：

  ┌────────────────────────────────────────────────┐
  │  请求类型            │  占比（典型）  │
  ├────────────────────────────────────────────────┤
  │  LIST                │  30-40%        │
  │  WATCH               │  30-40%        │
  │  GET                 │  15-20%        │
  │  CREATE              │  5-10%         │
  │  UPDATE              │  5-10%         │
  │  DELETE              │  2-5%          │
  └────────────────────────────────────────────────┘

  写操作（CREATE/UPDATE/DELETE）：
    - 走 Raft 共识 → etcd 写
    - 延迟较高（10-100ms）
    - 是 etcd 压力的主要来源

  读操作（LIST/WATCH/GET）：
    - 从 etcd 读
    - 或从 API Server 缓存读
    - 是 API Server 内存的主要消耗
```

### 4.2 API Server 性能瓶颈

```text
API Server 资源瓶颈：

  ┌────────────────────────────────────────────────┐
  │  资源            │  典型瓶颈          │
  ├────────────────────────────────────────────────┤
  │  内存            │  WatchCache 占用大 │
  │  CPU            │  序列化/反序列化   │
  │  网络            │  List/Watch 流     │
  │  磁盘            │  etcd 间接影响     │
  └────────────────────────────────────────────────┘

  WatchCache 详解：
    - API Server 在内存中缓存资源
    - 默认 100MB（可调）
    - 大集群推荐 1-2GB
    - 1000 节点 × 100 Pod = 100K 对象
    - 每个对象 ≈ 2-5 KB
    - 总占用：~200-500 MB
```

### 4.3 API Server 调优

```yaml
# kube-apiserver 推荐参数
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
apiServer:
  extraArgs:
    # 并发请求数
    - --max-requests-inflight=2000
    - --max-mutating-requests-inflight=1000
    
    # WatchCache 大小（默认 100MB）
    - --watch-cache-sizes=kube_apiservice=200,apiextensions.k8s.io/CustomResourceDefinition=500,apps/Deployment=2000
    
    # GC 调优
    - --default-watch-cache-size=1000
    
    # 特性开关
    - --feature-gates=APIPriorityAndFairness=true
    
    # 日志
    - --log-level=info
```

## 五、Controller Manager 与 Scheduler

### 5.1 Controller Manager 瓶颈

```text
Controller Manager 默认瓶颈：

  ┌────────────────────────────────────────────────┐
  │  问题              │  说明                │
  ├────────────────────────────────────────────────┤
  │  单实例处理         │  所有控制器跑在一处  │
  │  Watch 数量        │  几千 watch 难以扩展 │
  │  Reconcile 开销    │  100 节点几秒级     │
  │  GC 频繁           │  大集群 GC 压力大   │
  │  leader election  │  单点失效            │
  └────────────────────────────────────────────────┘

  K8s v1.20+ Controller Manager：
    - 单实例可处理 ~200 节点
    - 超过 200 节点需要扩展
    - v1.28 引入 leader election 优化
```

### 5.2 Controller Manager 水平扩展方案

```text
传统 Controller Manager 模式：

  ┌────────────────────┐
  │  Controller Manager  │ ← 单点
  │  (leader)            │
  └────────────────────┘
           │
       监听所有 CRD
           │
       处理所有 reconcile

Controller Manager Sharding（实验性）：

  ┌────────────────────┐
  │  Controller Manager  │ ← Controller Manager 实例 1
  │  Shard 1            │   处理 CRD A
  └────────────────────┘
  ┌────────────────────┐
  │  Controller Manager  │ ← Controller Manager 实例 2
  │  Shard 2            │   处理 CRD B
  └────────────────────┘

  按 CRD 类型或命名空间分片
```

### 5.3 Scheduler 瓶颈

```text
Scheduler 性能瓶颈：

  ┌────────────────────────────────────────────────┐
  │  问题              │  数据                │
  ├────────────────────────────────────────────────┤
  │  默认并发          │  16                 │
  │  评估所有节点       │  100%              │
  │  100 节点调度     │  ~100ms             │
  │  1000 节点调度    │  ~1s                │
  │  5000 节点调度    │  ~5s ⚠️ 慢          │
  └────────────────────────────────────────────────┘

  K8s v1.23+ Scheduler Sharding：
    - 按命名空间分片
    - 多 Scheduler 实例
    - 提升调度并发

  K8s v1.28+ Scheduler Profiles：
    - 自定义调度策略
    - 多 Profile 并存
```

### 5.4 Scheduler 调优

```yaml
# kube-scheduler 推荐参数
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
scheduler:
  extraArgs:
    # 并发度
    - --scheduler-name=default-scheduler
    - --feature-gates=SchedulerSharding=true
    
    # 调度性能
    - --percentage-of-nodes-to-score=50
      # 只评估 50% 节点（最优节点）
      # 大集群可降到 10-30%
    
    # 绑定超时
    - --bind-timeout=10s
```

## 六、Kubelet 与节点瓶颈

### 6.1 Kubelet 默认限制

```text
Kubelet 关键参数与默认：

  ┌─────────────────┬──────────────────┐
  │  参数            │  默认值            │
  ├─────────────────┼──────────────────┤
  │  --max-pods      │  110              │
  │  --node-status-update-frequency│ 10s│
  │  --image-gc-high-threshold│ 85%   │
  │  --image-gc-low-threshold│ 80%    │
  │  --kube-api-burst│  30             │
  │  --kube-api-qps   │  50             │
  └─────────────────┴──────────────────┘

  K8s v1.28+：
    --max-pods 可在 KubeletConfiguration 设置
    单节点推荐 100 Pod
    大内存节点可调到 250
```

### 6.2 单节点最大 Pod 数

```text
单节点 Pod 数计算公式：

  maxPods = min(
    --max-pods 配置,
    节点 CPU / 单 Pod CPU 需求,
    节点内存 / 单 Pod 内存需求,
    节点 PID 数 / 单 Pod PID 需求,
    节点 IP 数 / Pod 数,
  )

  示例：
    节点：16 核 64GB
    Pod：1 核 2GB
    理论：min(110, 16, 32, ...) = 16 个
    实际：约 16-20 个 Pod

  K8s 默认 --max-pods=110
    - 通常不是 CPU/内存限制
    - 是 IP/PID/conntrack 限制
    - 实际部署要综合考虑
```

### 6.3 Kubelet 调优

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
maxPods: 250                          # 提高单节点 Pod 数
nodeStatusUpdateFrequency: 30s        # 减少 API Server 压力
imageGCHighThresholdPercent: 85
imageGCLowThresholdPercent: 80
# kube-api-qps 调整
kubeAPIQPS: 100                       # 默认 50
kubeAPIBurst: 200                     # 默认 100
# cgroup 配置
cgroupDriver: systemd
# 启用镜像预加载
serializeImagePulls: false
# 镜像拉取超时
imagePullProgressDeadline: 5m
```

## 七、网络瓶颈

### 7.1 K8s 网络组件限制

```text
K8s 网络瓶颈（控制面）：

  ┌─────────────────┬──────────────────┐
  │  组件            │  默认限制          │
  ├─────────────────┼──────────────────┤
  │  Service 数量    │  10,000          │
  │  Endpoint 数     │  100,000         │
  │  ClusterIP 总数  │  受限于 Service  │
  │  iptables 规则   │  ~5,000 影响性能 │
  │  conntrack 表   │  受限于内存      │
  └─────────────────┴──────────────────┘

  Service 跨节点通信：
    - 默认通过 kube-proxy iptables
    - 1000 Service = 大量 iptables 规则
    - 影响网络性能
    - 推荐用 IPVS 或 Cilium eBPF
```

### 7.2 Endpoint 数量瓶颈

```text
Endpoint 数量影响：

  1. 每个 Service 后端 Pod 变化
     → Endpoint 对象更新
     → 触发 kube-proxy reload
     → 更新 iptables/IPVS 规则

  2. 大 Service 数量
     → 大量 Endpoint 对象
     → API Server 内存占用大
     → kube-proxy reload 频繁

  优化：
    - 使用 EndpointSlice（K8s v1.21+ GA）
      把 Endpoint 拆分，减少单个对象大小
    - 使用 Cilium 替代 kube-proxy
```

### 7.3 网络策略扩展性

```text
NetworkPolicy 数量与性能：

  ┌─────────────────┬──────────────────┐
  │  Policy 数      │  iptables 性能影响  │
  ├─────────────────┼──────────────────┤
  │  < 100          │  几乎无影响        │
  │  100-1000       │  性能下降 < 5%    │
  │  1000-5000      │  性能下降 10-20%  │
  │  > 5000         │  性能下降明显     │
  │  > 10000        │  需要 eBPF 数据面  │
  └─────────────────┴──────────────────┘

  解决：
    - 使用 Cilium eBPF（10,000+ Policy 仍流畅）
    - 使用 IPVS 替代 iptables
    - 合并 Policy（减少规则数）
```

## 八、大规模集群最佳实践

### 8.1 大规模集群架构

```text
大规模 K8s 集群推荐架构：

  ┌─────────────────────────────────────────────────────┐
  │                    控制面                            │
  │                                                      │
  │  ┌──────────────────────────────────────────────┐  │
  │  │            etcd 集群（3 或 5 节点）           │  │
  │  │  - 专用 SSD 服务器                          │  │
  │  │  - 10GbE 网络                               │  │
  │  │  - 低延迟                                   │  │
  │  └──────────────────────────────────────────────┘  │
  │                       ↑                              │
  │  ┌──────────────────────────────────────────────┐  │
  │  │  API Server × 3（高可用）                   │  │
  │  │  - 16 核 32GB+                              │  │
  │  │  - 负载均衡                                  │  │
  │  └──────────────────────────────────────────────┘  │
  │                       ↑                              │
  │  ┌──────────────────────────────────────────────┐  │
  │  │  Controller Manager + Scheduler              │  │
  │  │  - HA（多实例）                              │  │
  │  │  - Scheduler Sharding                        │  │
  │  └──────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────┘
                          ↑
                  ┌───────┴───────┐
                  ↓               ↓
            Worker 节点 × N   Worker 节点 × N
            （业务 Pod）     （业务 Pod）
```

### 8.2 etcd 部署最佳实践

```text
etcd 集群部署（生产推荐）：

  ┌─────────────┬─────────────┬─────────────┐
  │  etcd-1     │  etcd-2     │  etcd-3     │
  │  (Leader)   │  (Follower) │  (Follower) │
  │  10.0.0.11  │  10.0.0.12  │  10.0.0.13  │
  └─────────────┴─────────────┴─────────────┘
        ↑              ↑             ↑
        └──────── SSD 存储 ────────┘

  推荐配置：
    - 3 节点（容忍 1 节点故障）
    - 5 节点（容忍 2 节点故障）
    - 每节点：8 核 16GB SSD
    - 10GbE 网络互联

  K8s v1.28+ 新特性：
    - Konnectivity：API Server 与 kubelet 走 HTTPS
    - 不再依赖 SSH tunnel
    - 减少 etcd 网络负载
```

### 8.3 K8s 大规模集群配置

```yaml
# kubeadm 配置大规模集群
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 10.0.0.10
  bindPort: 6443
nodeRegistration:
  criSocket: unix:///run/containerd/containerd.sock

---
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
kubernetesVersion: v1.30.0
etcd:
  local:
    extraArgs:
      quota-backend-bytes: "8589934592"     # 8GB
      max-request-bytes: "33554432"          # 32MB
      election-timeout: "5000"
      heartbeat-interval: "500"
    serverCertSANs:
      - 10.0.0.10

apiServer:
  extraArgs:
    - --max-requests-inflight=2000
    - --max-mutating-requests-inflight=1000
    - --default-watch-cache-size=1000
    - --watch-cache-sizes=apps/Deployment=2000,core/Endpoints=5000
    - --feature-gates=APIPriorityAndFairness=true,WatcherConcurrency=true
  timeoutForControlPlane: 4m0s

controllerManager:
  extraArgs:
    - --node-monitor-period=5s
```

## 算法 1：Pod CIDR 与节点规模的关系

### 算法概述

本节讲解 `kubeadm init` 时指定的 `--pod-network-cidr` 与集群可扩展节点数的关系。

### CIDR 容量计算公式

```text
节点可用 IP 数计算公式：

  CIDR 格式：a.b.c.d/n
  节点可用 IP 数 = 2^(32 - n)

  常见 CIDR 对应的总 IP 数：

  ┌─────────────────┬─────────────┬─────────────────┐
  │  CIDR           │  可用 IP 数  │  节点推荐上限    │
  ├─────────────────┼─────────────┼─────────────────┤
  │  /16             │  65,536     │  1,000 - 5,000  │
  │  /17             │  32,768     │  500 - 2,000    │
  │  /18             │  16,384     │  250 - 1,000    │
  │  /19             │  8,192      │  125 - 500      │
  │  /20             │  4,096      │  60 - 250       │
  │  /21             │  2,048      │  30 - 125       │
  │  /22             │  1,024      │  15 - 60        │
  │  /23             │  512        │  7 - 30         │
  │  /24             │  256        │  3 - 15         │
  └─────────────────┴─────────────┴─────────────────┘

  公式推导：
    可用 IP 数 = 2^(32 - CIDR 前缀)
    例如 /16 → 2^(32-16) = 2^16 = 65,536 个 IP
```

### 每节点 IP 占用计算

```text
每个节点需要分配的 IP 数：

  ┌─────────────────┬──────────────────┐
  │  用途            │  IP 数          │
  ├─────────────────┼──────────────────┤
  │  Node 自身 IP    │  1               │
  │  Pod CIDR 块     │  默认 /24（256） │
  │  Service CIDR    │  通常共享       │
  │  预留             │  10-20%         │
  └─────────────────┴──────────────────┘

  关键参数：
    Calico: blockSize=26（/26 = 64 IP/节点）
    Calico 默认: 每个节点 /26 = 64 个 IP
    Flannel: blockSize=24（/24 = 256 IP/节点）

  默认分配下：
    每节点需要 256 个 IP（Pod CIDR）
    /16 CIDR 支持：65536 / 256 = 256 个节点（理论）
    实际推荐：150-200 个节点（保留扩容空间）
```

### CIDR 选择算法

```text
算法 1.1：CIDR 与节点数匹配

  输入：
    N = 目标节点数
    P = 每节点最大 Pod 数（默认 110）
    R = 预留比例（推荐 20-30%）

  输出：推荐的 CIDR

  步骤 1：计算所需总 IP 数
    totalIPs = N × P × (1 + R)
    示例：500 节点 × 110 Pod × 1.3 = 71,500 IP

  步骤 2：选择 CIDR 前缀
    找到最小 n 使得 2^(32-n) ≥ totalIPs
    示例：2^17 = 131,072 ≥ 71,500 → n=17 → /17

  步骤 3：考虑 K8s 内部 IP
    K8s Service CIDR 也需要 IP（默认 /12 = 1M IP）
    与 Pod CIDR 不要重叠

  步骤 4：验证
    检查与现有网络的 CIDR 不重叠
    检查 VPC 安全组允许该 CIDR
```

### 实际选型建议

```text
不同集群规模的 CIDR 推荐：

  ┌─────────────────┬──────────────┬──────────────────┐
  │  集群规模        │  节点数      │  推荐 CIDR       │
  ├─────────────────┼──────────────┼──────────────────┤
  │  小型开发        │  1-10        │  10.244.0.0/20  │
  │  小型生产        │  10-50       │  10.244.0.0/18  │
  │  中型生产        │  50-200      │  10.244.0.0/16  │
  │  大型生产        │  200-1000    │  10.244.0.0/14  │
  │  超大集群        │  1000-5000   │  10.0.0.0/8     │
  └─────────────────┴──────────────┴──────────────────┘

  常用 CIDR 段（避免冲突）：
    Pod CIDR：     10.244.0.0/16,  10.96.0.0/12
    Service CIDR： 10.96.0.0/12（默认）
    Cluster CIDR： 10.0.0.0/8（整体规划）
```

### CIDR 与 CNI 兼容性

```text
不同 CNI 的 CIDR 要求：

  ┌─────────────────┬──────────────────────────┐
  │  CNI            │  CIDR 要求               │
  ├─────────────────┼──────────────────────────┤
  │  Flannel        │  /16 默认，可调整        │
  │  Calico         │  /26 块/节点，最灵活     │
  │  Cilium         │  /16 默认，可调整        │
  └─────────────────┴──────────────────────────┘

  Calico 块大小调整：
    blockSize=24  → /24 = 256 IP/节点
    blockSize=26  → /26 = 64 IP/节点（默认）
    blockSize=27  → /27 = 32 IP/节点

  块大小选择：
    节点 Pod 数少 → 大块（/24）
    节点 Pod 数多 → 小块（/26 或 /27）
    推荐 /26 平衡选择
```

### CIDR 子网划分算法

```text
算法 1.2：Pod CIDR 子网自动划分

  输入：
    clusterCIDR = "10.244.0.0/16"
    nodeCount = 500
    blockSize = 26  # Calico 默认

  输出：每个节点的子网块

  步骤 1：计算每节点 IP 数
    ipsPerNode = 2^(32 - blockSize) = 2^6 = 64

  步骤 2：计算需要的子网块数
    clusterIPs = 2^(32 - 16) = 65,536
    blocksNeeded = nodeCount × ipsPerNode = 500 × 64 = 32,000
    # 注意：实际可能不会立即分配全部

  步骤 3：节点加入时分配
    节点 1 → 10.244.0.0/26
    节点 2 → 10.244.0.64/26
    节点 3 → 10.244.0.128/26
    节点 4 → 10.244.0.192/26
    节点 5 → 10.244.1.0/26
    ...
    节点 N → 10.244.?.?/26

  步骤 4：CIDR 耗尽检测
    used = nodeCount × ipsPerNode
    available = totalIPs
    remaining = available - used
    if remaining / ipsPerNode < 10:
      警告：剩余 IP 不够 10 个节点使用
```

### CIDR 耗尽问题与解决

```text
CIDR 耗尽场景：

  场景 1：Pod CIDR 耗尽
    现象：新 Pod 创建失败
           kubectl describe pod 显示 FailedCreate
    解决：
      - 扩大 Pod CIDR（重建集群）
      - 双栈网络（IPv4 + IPv6）

  场景 2：Service ClusterIP 耗尽
    现象：创建 Service 失败
    默认 Service CIDR 是 /12 = 1M IP
    通常不会耗尽，但需注意

  场景 3：节点 IP 耗尽
    现象：节点无法加入集群
    解决：
      - 提前规划 CIDR 大小
      - 使用 IPv6
```

### CIDR 与 Service / DNS

```text
Service CIDR 与 CoreDNS：

  Service CIDR 默认：10.96.0.0/12
  - 包含 1,048,576 个 IP
  - 几乎不会耗尽
  - 但与 Pod CIDR 不能重叠

  常见 CIDR 组合：
    Pod CIDR:     10.244.0.0/16
    Service CIDR: 10.96.0.0/12
    Cluster CIDR: 10.0.0.0/8

  DNS（CoreDNS）：
    服务发现：<svc>.<ns>.svc.cluster.local
    Pod 解析：<pod-ip>.<ns>.pod.cluster.local

  kubeadm 配置示例：
    kubeadm init \
      --pod-network-cidr=10.244.0.0/16 \
      --service-dns-domain=cluster.local \
      --service-cidr=10.96.0.0/12
```

### CIDR 与集群扩展

```text
CIDR 扩展性设计：

  设计原则：
    1. Pod CIDR 选 /16 或更大（确保足够 IP）
    2. Service CIDR 用 /12（足够所有服务）
    3. 避免与现有网络重叠
    4. 留 30% 冗余（应对扩容）

  扩容场景：
    单集群无法扩展 → 用多集群
    CIDR 耗尽 → 重建集群（不可在线扩 CIDR）

  进阶选择：
    IPv6 Pod CIDR（fc00::/7）
    - 地址空间巨大
    - 未来推荐
    - 双栈过渡

  完整示例：5000 节点集群 CIDR 规划

  输入：
    nodeCount = 5000
    podsPerNode = 100（保守）
    reserveRate = 1.3（30% 预留）

  计算：
    neededIPs = 5000 × 100 × 1.3 = 650,000 IP
    CIDR = 2^(32-n) ≥ 650,000
    n ≤ log2(650,000) ≈ 19.31
    选择 n=19 → /19 = 524,288 IP（不足）
    选择 n=18 → /18 = 262,144 IP（也不足）
    选择 n=14 → /14 = 4,194,304 IP（足够）

  推荐：5000 节点用 /16 或 /14
    /16 = 65,536 IP → 5,000 节点 × 13 IP/节点
    /14 = 4M IP    → 充足空间
```

```text

  /24 = 256 IP    → 1 个节点（256 Pod）
```
