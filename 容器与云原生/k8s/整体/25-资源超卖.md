# K8s 资源超卖（Overcommit）详解

> 资源超卖 = 平台分配的"声明资源" > 节点的"物理资源"。
> K8s 默认就是超卖（request 总和可以超过节点容量），但生产环境要做精细化控制，否则风险极高。
> 这篇讲清楚：为什么超卖、怎么安全超卖、有哪些工具能用。

---

## 一、背景：什么是资源超卖

### 1.1 一句话定义

```text
资源超卖（Overcommit）=
  平台允许 Pod 声明的 request 总和 > 节点的物理资源容量

例：
  节点 64C 256G
  平台允许 Pod request 总和 = 200C 800G
  → 超卖比 = 200/64 = 3.1x CPU，800/256 = 3.1x 内存
```

### 1.2 类比现实

```text
航空公司卖机票：飞机 200 座，卖出 250 张（200% 超卖）
  → 历史经验：60% 航班不会全满
  → 超卖赚钱，但有人误机要赔偿

K8s 集群：节点 64C，分配出 200C request（300% 超卖）
  → 历史经验：Pod 不会同时跑满
  → 超卖省资源，但 OOM / 调度失败要处理
```

### 1.3 资源利用率现状

```text
行业平均（2024 调研数据）：
  - 私有集群 CPU 利用率：8–15%
  - 公有云/容器平台 CPU 利用率：20–40%
  - 内存利用率：30–50%（比 CPU 高）

原因：
  - 业务方"宁多勿少"：request 写最大值，怕调度失败
  - 资源预算机制：申请多少给多少，浪费没成本
  - 业务波峰波谷：电商白天 5 倍于夜间、ToB 工作日 3 倍于周末
  - 节点碎片化：剩 8C 没人用，凑不齐一个 Pod
```

## 二、为什么要做超卖

### 2.1 平台方视角（省钱 / 提效）

```text
✅ 同样的硬件资源跑更多业务
✅ 降低单位业务的资源成本（Cost / Service）
✅ 提高资源利用率（财务/审计指标）
✅ 减少节点数量，简化运维
```

### 2.2 业务方视角（弹性 / 不踩坑）

```text
✅ 不需要精准预估资源（业务方大多数不会做容量规划）
✅ 高峰能拿到资源、低峰让出来
✅ 不需要为"万一"的峰值预留大量 buffer
```

### 2.3 不做超卖的代价

```text
场景 1：申请很保守
  业务方只敢写 0.5C 1G
  → 集群 1000 节点 80% 利用率
  → 实际上 50% 节点可裁掉，浪费 50% 成本

场景 2：申请很激进
  业务方写 8C 16G
  → 调度到节点后只用 1C 2G
  → 节点资源被锁住，其他 Pod 调度不进来

场景 3：不超卖 + 严格配额
  request 总和 = 节点容量
  → 调度器卡死，新 Pod 起不来
  → 业务方有意见："明明还有 30C 没用"
```

## 三、超卖的层次（不同资源类型不一样）

### 3.1 CPU 超卖（最常见）

```text
特点：
  - CPU 是"可压缩资源"（compressible）
  - 满了就 throttled（cgroup 限流），不会 OOM
  - 影响：服务慢，但不会死
  - 业务能感知但不致命

超卖倍数参考：
  - 通用业务：1.5x–2x
  - 在线核心（支付/搜索）：1.0x–1.2x（不超卖）
  - 离线/批处理：5x–10x（白嫖剩余 CPU）

实现机制：
  - request 决定调度（cgroup shares）
  - limit 决定上限（cgroup quota）
  - 超卖 → request 之和 > 物理 CPU
  - 真实使用时按 limit 上限，按需争抢
```

### 3.2 内存超卖（危险）

```text
特点：
  - 内存是"不可压缩资源"（incompressible）
  - 满了直接 OOM Kill 进程
  - 影响：Pod 被杀、请求失败、级联雪崩

超卖倍数参考：
  - 在线业务：1.0x–1.2x（几乎不超卖）
  - 内存型应用（Redis/缓存）：1.0x（绝不超卖）
  - 离线/批处理：1.5x–2x（允许 OOM 风险）

⚠️ 内存超卖 > 1.5x 必须配：
  - Memory QoS（cgroup v2）
  - OOM 优先级（oom_score_adj）
  - 监控告警（提前发现内存压力）
```

### 3.3 存储超卖

```text
类型：
  - 节点本地存储：通常不超卖（ephemeral-storage 限制）
  - 持久卷（PVC）：超卖看存储系统
  - 镜像缓存：可超卖（用同一个 layer）

实现：
  - StorageClass capacity 限制
  - 节点 disk space 监控
  - 镜像 GC 策略
```

### 3.4 网络超卖

```text
特点：
  - 带宽不像 CPU/内存可被 cgroup 严格限制
  - 主要靠 cgroup 对每个 Pod 的网络 classid 限流
  - 实际效果有限

超卖策略：
  - 业务方不感知带宽
  - 平台默认按"最大速率"分配
  - 网络瓶颈通常在节点出口，按"超额认购"原则
```

## 四、实现思路（5 个层次）

### 4.1 第一层：声明机制（request / limit）

```text
核心：
  - request：调度时用，决定 Pod 放哪个节点
  - limit：运行时用，决定 Pod 最大用多少

⚠️ request ≠ limit 的语义：
  - request == limit  →  Guaranteed QoS
  - request < limit   →  Burstable QoS（可突发）
  - request 未设      →  BestEffort QoS（没保障）

超卖的关键设置：
  - request = 业务平均用量（给调度器看）
  - limit  = 业务峰值用量（给 cgroup 看）
  - request 总和 = 节点容量 × 超卖倍数
```

```yaml
# 标准超卖配置（在线服务）
resources:
  requests:
    cpu: 500m      # 平均 0.5 核
    memory: 1Gi    # 平均 1G
  limits:
    cpu: 2         # 峰值 2 核（4x 突发）
    memory: 2Gi    # 峰值 2G（2x 突发）
```

### 4.2 第二层：QoS 等级

```yaml
# Guaranteed（保证型）—— request == limit
# 调度优先级最高，最后被 kill
resources:
  requests:
    cpu: 1
    memory: 2Gi
  limits:
    cpu: 1
    memory: 2Gi
```

```yaml
# Burstable（突发型）—— request < limit
# 中等优先级
resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    cpu: 2
    memory: 2Gi
```

```yaml
# BestEffort（尽力型）—— 不设 request/limit
# 最先被 kill，节点压力大时第一个赶走
containers:
- name: app
  image: myapp
```

**QoS 在 OOM / 驱逐时的优先级**：

```text
OOM Kill 顺序：BestEffort → Burstable → Guaranteed
驱逐顺序（disk / memory pressure）：BestEffort → Burstable → Guaranteed

超卖策略：
  - 核心业务用 Guaranteed（保证不杀）
  - 常规业务用 Burstable（可杀但有限）
  - 测试/批处理用 BestEffort（杀就杀了）
```

### 4.3 第三层：调度器优化

```text
K8s 默认调度器是 MostRequested（最满优先）→ 不适合超卖
超卖集群需要改 LeastAllocated（最空优先）：

  LeastAllocated  →  Pod 优先调度到"已分配少"的节点
                    → 节点资源均匀分布
                    → 适合超卖

  MostAllocated  →  Pod 优先调度到"已分配多"的节点
                    → 节点被打满后下掉
                    → 适合不超卖，省节点

  Balanced       → 平衡 CPU 和内存使用率
```

```yaml
# 在 scheduler 配置里改
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: LeastAllocated
        resources:
        - name: cpu
          weight: 1
        - name: memory
          weight: 1
```

**高级调度策略**：

```text
- NodeResourcesFit：基本资源匹配
- NodeAffinity：节点亲和性
- PodTopologySpread：拓扑打散
- Taints / Tolerations：污点容忍
- ResourceBinding：扩展资源（GPU / RDMA）

超卖集群必开：
  ✅ NodeResourcesLeastAllocated
  ✅ PodTopologySpread（避免热点节点）
  ✅ NodeAffinity（按节点类型分组）
```

### 4.4 第四层：资源压缩 / 自动调整

```text
核心思想：让 Pod 的 request 跟实际使用量尽量接近
工具：
  - VPA（Vertical Pod Autoscaler）：垂直调整 request/limit
  - 在离线混部：在线 / 离线业务复用节点
```

**VPA 三种模式**：

```yaml
# 1. UpdateMode: Off（推荐起步）—— 只推荐，不改
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: myapp-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  updatePolicy:
    updateMode: "Off"    # 只出建议，不真改
```

```yaml
# 2. UpdateMode: Initial（创建时设 request）—— 相对安全
updatePolicy:
  updateMode: "Initial"
  # 重建 Pod 时设新 request，已有 Pod 不动
```

```yaml
# 3. UpdateMode: Auto（自动调整）—— 谨慎使用
updatePolicy:
  updateMode: "Auto"
  # 会重建 Pod，生产慎用（会滚动）
```

**VPA 三大组件**：

```text
1. recommender（推荐器）
   - 收集 Pod 历史使用数据
   - 算出推荐 request/limit
   - 写到 VPA CR 的 status

2. updater（更新器）
   - 决定何时 evict 旧 Pod
   - 用新 request 重建

3. admission-controller（准入控制器）
   - Pod 创建时如果开了 Initial 模式
   - 自动改 Pod spec 的 request
```

### 4.5 第五层：资源回收 / 驱逐策略

```text
当节点压力大时，按以下顺序处理：

① 驱逐 BestEffort Pod
② 驱逐 Burstable Pod（request 用量大的优先杀）
③ 保留 Guaranteed Pod
④ 最后才驱逐 Guaranteed Pod（必须保证服务质量）
```

```yaml
# kubelet 配置软驱逐（资源不足时优雅驱逐）
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
evictionHard:
  memory.available: "500Mi"
  nodefs.available: "10%"
  imagefs.available: "15%"
evictionSoft:
  memory.available: "1Gi"
  nodefs.available: "15%"
evictionSoftGracePeriod:
  memory.available: "2m"
  nodefs.available: "3m"
evictionPressureTransitionPeriod: "30s"
```

### 5.2 VPA（Vertical Pod Autoscaler）

```text
官方地址：kubernetes/autoscaler
GitHub：github.com/kubernetes/autoscaler/tree/master/vertical-pod-autoscaler

能做的事：
  - 监控 Pod 真实使用量
  - 推荐合适的 request/limit
  - 可选自动调整（要重建 Pod）

适用场景：
  ✅ 资源使用相对稳定的业务（无明显波峰波谷）
  ✅ 不知道该写多少 request 的业务
  ✅ 想做成本优化的团队

不适合：
  ❌ 频繁弹性扩缩（HPA）的业务（互相打架）
  ❌ 有状态服务（StatefulSet 调整会断连接）
  ❌ 实时短任务（Job / CronJob）
```

### 5.3 HPA（Horizontal Pod Autoscaler）

```text
官方：K8s 内置
能做的事：
  - 水平扩缩（加 Pod 副本数）
  - 基于 CPU / 内存 / 自定义指标

跟超卖的关系：
  - 不是直接超卖，但配合 VPA 可以"平时少开，高峰多开"
  - HPA 关注"副本数"，VPA 关注"每个副本多大"

避坑：
  - HPA 和 VPA 不能同时管同一个 Pod
  - 要么 HPA（弹性），要么 VPA（压实）
```

### 5.4 Cluster Autoscaler

```text
官方：kubernetes/autoscaler
GitHub：github.com/kubernetes/autoscaler/tree/master/cluster-autoscaler

能做的事：
  - 节点不够时自动加机器（云厂商对接）
  - 节点长期空时自动回收

跟超卖的关系：
  - 超卖 → 节点需求变少
  - 配合 CA → 自动减少节点，节省云费用
```

### 5.5 Karpenter

```text
GitHub：aws/karpenter（AWS 出身，现已多云）
定位：下一代集群自动扩缩，比 CA 更灵活

能做的事：
  - 看 Pod 调度失败 → 拉一台节点
  - 节点合并（consolidation）：低利用率节点迁移后删除
  - Spot / On-demand 混合
  - 节点池（NodePool）分类

优势（vs CA）：
  - 拉节点更快（不通过 ASG / VM Scale Set）
  - 更细粒度节点规格
  - 原生支持多云

适用：
  - AWS / Azure / 阿里云 / 自建 K8s
  - 中大型集群
```

### 5.6 Descheduler

```text
官方：kubernetes-sigs/descheduler
GitHub：github.com/kubernetes-sigs/descheduler

能做的事：
  - 把已有 Pod 重新调度到更合适的节点
  - 解决"调度历史包袱"（节点碎片化）

典型策略：
  - RemoveDuplicates：把相同 Service 的 Pod 打散
  - LowNodeUtilization：找利用率低的节点迁过去
  - RemovePodsViolatingNodeAffinity：违反亲和性的迁走
  - RemovePodsViolatingNodeTaints：容忍被收回的迁走

适用：
  - 长期运行的集群
  - 节点分布不均的集群
  - 配合 Karpenter 用
```

### 5.7 Crane（腾讯云）

```text
GitHub：tencent/crane
定位：云上成本优化 + 弹性 + 超卖一体化平台

能做的事：
  - EffectiveHPA：基于预测的水平扩缩
  - VPA + 自定义算法
  - 资源画像：推荐 request
  - 成本分析：哪些 namespace / workload 最浪费
  - 混部：在离线混部
  - 闲置节点回收

适用：
  - 大型集群
  - 需要成本治理的团队
  - 混部场景
```

### 5.8 Katalyst（字节跳动）

```text
GitHub：kubernetes-sigs/katalyst
定位：超卖 + QoS 精细化 + 混部

核心理念：
  - 引入 Reclaimed Resource 概念
  - 在线 Pod 用专用资源
  - 离线 Pod 抢占空闲资源
  - cgroup v2 严格隔离

适用：
  - 字节内部生产实践
  - 资源利用率极致优化
  - 已有 cgroup v2 + Linux 5.x 内核
```

### 5.9 Koordinator（阿里云）

```text
GitHub：koordinator-sh/koordinator
定位：阿里云内部调度 + 混部 + QoS

能力：
  - 增强调度器（在/离线混部）
  - 资源超卖 + QoS
  - 优先级抢占
  - GPU 调度

适用：
  - 阿里云 ACK 用户
  - 想做混部的团队
  - 资源密集型（AI / 大数据）
```

### 5.10 Volcano

```text

跟超卖的关系：
  - 离线任务的资源池
```

## 六、生产实践路径

### 6.1 第一步：摸清现状

```text
1. 跑资源画像
   - 用 VPA recommender 模式（只推荐不改）
   - 跑 1–2 周，收集所有业务的使用量

2. 看资源利用率
   - CPU / 内存 / 网络
   - 节点级 / namespace 级 / workload 级
   - 找 Top 10 浪费的业务

3. 评估超卖空间
   - request / actual 使用 比值
   - 业务波峰波谷比例
   - 在线 / 离线比例
```

### 6.2 第二步：建立基础机制

```text
1. 命名空间配额（ResourceQuota）
   - 限制每个 namespace 的总 request
   - 防止一个 ns 吃光集群

2. 默认值（LimitRange）
   - Pod 没写 request/limit 时自动填
   - 避免 BestEffort 满天飞

3. QoS 策略
   - 核心业务 → Guaranteed
   - 常规业务 → Burstable
   - 测试 / 批处理 → BestEffort
```

### 6.3 第三步：开启调度优化

```text
1. 调度器改成 LeastAllocated
2. 开启 PodTopologySpread
3. 开启 NodeResourcesFit
4. Descheduler 周期重平衡
```

### 6.4 第四步：引入自动工具

```text
1. VPA recommender 模式试跑（只推荐）
2. HPA 给弹性业务用
3. 离线和在线业务分集群
4. 评估 Crane / Koordinator / Katalyst
```

### 6.5 第五步：监控 + 灰度

```text
1. 资源利用率 dashboard
2. OOM / 驱逐告警
3. 灰度一个 namespace 试运行
4. 持续调优超卖倍数
```

## 七、风险与防护

### 7.1 主要风险

```text
风险 1：OOM 级联
  节点内存爆 → 杀 Pod → 杀的不对 → 雪崩

风险 2：CPU throttling
  业务被限速 → 响应时间涨 → 用户投诉

风险 3：调度失败
  request 太大 → 节点放不下 → Pod 一直 Pending

风险 4：节点热点
  超卖节点容易出现某些节点满载
```

### 7.2 防护措施

```text
✅ 节点级硬驱逐
   memory.available < 500Mi → 触发驱逐

✅ Pod 级优先级
   PriorityClass 配合 scheduler preemption
   核心业务优先级 > 离线业务

✅ 资源监控
   - 节点 CPU / 内存 / 磁盘 / 网络
   - Pod 实际使用量
   - 告警阈值：节点使用 > 80% 告警

✅ 容量 buffer
   永远保留 10–20% 节点资源做应急
   避免超卖比 100% 拉到极限

✅ 灰度策略
   先在测试 namespace 试运行 1 个月
   再扩到非核心业务
   最后才动核心业务
```

### 7.3 应急操作

```text
症状：节点 OOM / CPU throttling 严重

应急：
  1. 立即降级：LimitRange 收紧
  2. 驱逐非核心：kubectl drain 非关键 Pod
  3. 加节点：Cluster Autoscaler 立即触发
  4. 查根因：哪些 Pod 用了最多

回滚：
  - 调大 LimitRange request
  - 把 BestEffort 升级到 Burstable
  - 临时关 VPA
```

## 八、超卖比参考

| 业务类型 | CPU 超卖比 | 内存超卖比 | 备注 |
| --- | --- | --- | --- |
| 在线核心（支付/交易） | 1.0x–1.2x | 1.0x | 几乎不超卖 |
| 在线普通（API/查询） | 1.5x–2x | 1.0x–1.2x | CPU 可超卖 |
| 异步任务（消息消费） | 2x–3x | 1.5x | 延迟不敏感 |
| 离线批处理（ETL） | 5x–10x | 2x–3x | 用空闲资源 |
| 大数据（Spark） | 5x+ | 3x+ | Volcano 调度 |
| AI 训练 | 1.0x | 1.0x | 整机占用 |
| 内存密集（Redis） | 1.0x | 1.0x | 严格不超卖 |
| 机器学习推理 | 1.5x | 1.0x | CPU 弹性 |

---

## 九、一句话总结

> **资源超卖 = 平台允许 request 总和 > 物理容量，靠 QoS 优先级 + 调度策略 + 监控告警做风险控制**；
> 上 VPA 摸底 → 改调度器 → 引入 HPA / Karpenter → 评估混部（Katalyst / Koordinator），
> 核心业务**几乎不超卖**（≤1.2x），离线和批处理**白嫖剩余资源**（5x+）。
