# K8s 集群应该监控什么

> 目标：让"集群是否健康 + 哪里要出事"两件事可观测。监控分四层——**控制面 / 节点 / Pod&容器 / 服务&应用**，每一层各盯一类指标，再加一套**业务/告警**闭环。

---

## 一、控制面（Control Plane）

控制面挂了集群就废了，必须最先看。

| 组件 | 关键指标 | 看什么 |
| --- | --- | --- |
| **kube-apiserver** | `apiserver_request_duration_seconds`（P99）、`apiserver_request_total`（按 code 分类） | 延迟、5xx 比例、in-flight 请求数 |
| **etcd** | `etcd_disk_wal_fsync_duration_seconds`、`etcd_network_peer_round_trip_time_seconds`、`etcd_server_leader_changes_seen_total` | 写盘延迟、leader 切换次数、DB 大小 |
| **kube-scheduler** | `scheduler_pending_pods`、`scheduler_binding_duration_seconds` | 调度队列堆积、binding 耗时 |
| **kube-controller-manager** | `workqueue_depth`、`workqueue_retries_total` | 各 controller 的 workqueue 是否积压、重试风暴 |
| **kubelet** | `kubelet_node_name`、`kubelet_pleg_relist_duration_seconds`、`kubelet_running_pods` | PLEG 重列出错率、单节点 Pod 数 |
| **CNI / kube-proxy** | 各组件自暴的 metric（iptables 规则数、conntrack 数） | 规则数膨胀、conntrack 满 |

**告警思路**：apiserver P99 > 1s、etcd fsync P99 > 10ms、leader 切换、scheduler queue > N 都是 P0。

---

## 二、节点层（Node）

物理/虚拟机的健康度。

- **CPU**：`node_cpu_utilization`（1m/5m load）、分配/限额比
- **内存**：`node_memory_MemAvailable_bytes`（不是 `free`）、`node_memory_Active_bytes`
- **磁盘**：`node_filesystem_avail_bytes`（避免 `df -h` 看 inode）、`node_disk_io_now`、`node_disk_read/write_bytes`
- **网络**：`node_network_receive/transmit_bytes`、`node_network_drop`、`node_network_carrier`
- **系统**：fd 数、进程数、打开文件句柄（`node_filefd_allocated`）
- **GPU**（若有）：温度、利用率、显存（`nvidia_smi` → dcgm-exporter）

**告警思路**：磁盘 > 85%、MemAvailable < 10%、load > 核数 × 2、network drop > 0 持续 N 分钟。

---

## 三、Pod & 容器层

每个 Pod/容器是最常见的事故现场。

- **资源使用**：`container_cpu_usage_seconds_total`、`container_memory_working_set_bytes`，与 `requests/limits` 对比
  - **CPU 节流**：`container_cpu_cfs_throttled_seconds_total`（rate > 0.1 要警觉，说明 limit 太小）
  - **OOM**：`kube_pod_container_status_terminated_reason{reason="OOMKilled"}`
- **状态**：`kube_pod_status_phase`、`kube_pod_container_status_waiting_reason`（CrashLoopBackOff / ImagePullBackOff / CreateContainerConfigError）
- **重启**：`kube_pod_container_status_restarts_total` 累计 + 增量
- **生命周期**：`kube_pod_start_time`、`kube_pod_completion_time`（Job 类）
- **存储**：`kubelet_volume_stats_*`（PVC 使用率、IO 延迟）
- **网络**：`container_network_*_bytes`、TCP 重传（`node_netstat_Tcp_RetransSegs`）

**告警思路**：5 分钟内同 Pod 重启 ≥ 3、OOM 发生、Pending > X 分钟、CFS throttle 占比 > 25%。

---

## 四、服务层（Service / Ingress）

集群外面看到的入口。

- **Service / Ingress 可用性**：黑盒探针（blackbox_exporter）按域名 + path 打，结果写 `probe_success` / `probe_duration_seconds`
- **入口流量**：`nginx-ingress / traefik / istio` 自带的 metric：请求数、4xx/5xx 比例、P50/P95/P99 延迟
- **上游健康**：service endpoint 数 `kube_endpoint_address_available`、endpoint 不可用 = 后端全挂了
- **负载均衡**：`kube_service_spec_external_ip`、iptables/ipvs 规则命中数
- **DNS**：CoreDNS `coredns_dns_request_count_total`、`coredns_dns_response_rcode_count_total{rcode="SERVFAIL"}`、解析延迟

**告警思路**：5xx > 1%、P99 > SLO、CoreDNS SERVFAIL > 0、endpoint ready 数 < 期望。

---

## 五、应用层（业务指标）

k8s 不知道的业务语义，由应用自己暴露。

- **RED 指标**（服务类）：Rate / Errors / Duration，每接口每状态码
- **USE 指标**（资源类）：Utilization / Saturation / Errors，每实例
- **业务指标**：下单数、支付成功率、队列长度、缓存命中率…
- **黄金信号**（Google SRE）：Latency / Traffic / Errors / Saturation
- **JVM / Runtime**：GC 次数/停顿、线程数、连接池（Micrometer / Prometheus client）

暴露方式：Prometheus `/metrics`、OTLP（OpenTelemetry）、StatsD、Datadog dogstatsd 任选其一。

---

## 六、日志 & 链路（与监控互补）

监控看**数字**，日志看**事件**，链路看**因果**——三者一起才能定位。

- **日志**：stdout → Loki / ES / 阿里云 SLS，关键字段：trace_id、level、msg、pod、namespace
- **Trace**：OpenTelemetry SDK → Jaeger / Tempo / SkyWalking
- **事件**：`kube_event`（Warning 级尤其重要：FailedScheduling、FailedMount、BackOff）

---

## 七、采集 & 落地栈（常见组合）

| 层 | 主流方案 |
| --- | --- |
| 指标采集 | **Prometheus**（自托管）/ **VictoriaMetrics**（更省存储）/ **Thanos / Cortex**（长期 + 多集群） |
| 控制面 / 节点 | **node-exporter**、**kube-state-metrics**（K8s 对象）、**cAdvisor**（容器，kubelet 自带） |
| 探针 | **blackbox_exporter**（HTTP/TCP/ICMP）、**probe** |
| 仪表盘 | **Grafana**，社区有现成的 k8s dashboard（ID: 315、6417） |
| 日志 | **Loki + Promtail**（轻）/ **EFK**（重但稳） |
| 链路 | **OpenTelemetry Collector → Jaeger / Tempo** |
| 告警 | **Alertmanager**（路由/抑制/静默），告警分级 P0/P1/P2 |
| 云上托管 | 阿里云 ARMS / 华为云 AOM / AWS CloudWatch Container Insights / Datadog / Grafana Cloud |

## 七点五、Prometheus 各维度采集配置（prometheus.yml）

> 下面是一份**可直接落地**的 `prometheus.yml` 片段，按维度拆分。每个 job 对应上面一层，复制拼装即可。
> 假设已经装好：`kube-prometheus-stack`（含 node-exporter / kube-state-metrics / Prometheus Operator），并通过 `additionalScrapeConfigs` 注入。

### 0. 全局 + Kubernetes 服务发现骨架

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    cluster: prod-beijing-1
    env: production

scrape_configs:
  # —— 1. K8s API Server（控制面入口） ——
  - job_name: kubernetes-apiservers
    kubernetes_sd_configs:
      - role: endpoints
        namespaces:
          names: [default]
    scheme: https
    tls_config:
      ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
      insecure_skip_verify: true
    bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_label_component]
        regex: apiserver
        action: keep
      - source_labels: [__meta_kubernetes_endpoints_name]
        target_label: endpoint
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: apiserver_request_duration_seconds_.*|apiserver_request_total
        action: keep

  # —— 2. Kubelet（含 cAdvisor） ——
  - job_name: kubernetes-nodes-kubelet
    kubernetes_sd_configs:
      - role: node
    scheme: https
    tls_config:
      ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
      insecure_skip_verify: true
    bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
    relabel_configs:
      - target_label: __address__
        replacement: kubernetes.default.svc:443
      - source_labels: [__meta_kubernetes_node_name]
        regex: (.+)
        target_label: __metrics_path__
        replacement: /api/v1/nodes/${1}/proxy/metrics
    metric_relabel_configs:
      # 只要 cAdvisor + kubelet 核心指标，丢掉不要的
      - source_labels: [__name__]
        regex: container_.*|kubelet_.*|pod_.*
        action: keep

  # —— 3. kube-state-metrics（K8s 对象状态） ——
  - job_name: kube-state-metrics
    kubernetes_sd_configs:
      - role: endpoints
        namespaces:
          names: [kube-system]
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_label_app_kubernetes_io_name]
        regex: kube-state-metrics
        action: keep

  # —— 4. node-exporter（节点层） ——
  - job_name: node-exporter
    kubernetes_sd_configs:
      - role: endpoints
        namespaces:
          names: [kube-system]
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_label_app_kubernetes_io_name]
        regex: node-exporter
        action: keep
      - source_labels: [__meta_kubernetes_endpoint_port_name]
        action: keep
        regex: metrics

  # —— 5. CoreDNS ——
  - job_name: coredns
    kubernetes_sd_configs:
      - role: endpoints
        namespaces:
          names: [kube-system]
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_label_k8s_app]
        regex: kube-dns
        action: keep
      - source_labels: [__meta_kubernetes_endpoint_port_name]
        regex: metrics
        action: keep

  # —— 6. Ingress-NGINX（服务层入口） ——
  - job_name: ingress-nginx
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: [ingress-nginx]
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app_kubernetes_io_name]
        regex: ingress-nginx
        action: keep
      - source_labels: [__meta_kubernetes_pod_container_port_name]
        regex: metrics
        action: keep

  # —— 7. blackbox-exporter（黑盒探针） ——
  - job_name: blackbox-http
    metrics_path: /probe
    params:
      module: [http_2xx]
    kubernetes_sd_configs:
      - role: service
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_probe]
        regex: "true"
        action: keep
      - source_labels: [__address__]
        target_label: __param_target
      - target_label: __address__
        replacement: blackbox-exporter.monitoring.svc:9115
      - source_labels: [__meta_kubernetes_service_name]
        target_label: service

  # —— 8. 应用层（按 annotation 自动发现） ——
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      # 只采集打了 annotation 的 Pod
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        regex: "true"
        action: keep
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scheme]
        action: replace
        regex: (https?)
        target_label: __scheme__
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port, __meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        regex: (\d+);(.+)
        target_label: __address__
        replacement: $1:$2
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
```

### 应用 Pod 的标准 annotation

```yaml
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "8080"
    prometheus.io/path: "/metrics"
    prometheus.io/scheme: "http"
```

### etcd / scheduler / controller-manager（静态配置）

这些组件默认不开 metrics，需要在启动参数加 `--listen-metrics-urls=0.0.0.0:2381` 等，然后用静态 target：

```yaml
  - job_name: etcd
    static_configs:
      - targets: ['etcd-0.etcd.kube-system.svc:2381', 'etcd-1:2381', 'etcd-2:2381']
    scheme: https
    tls_config:
      ca_file: /etc/prometheus/secrets/etcd/ca.crt
      cert_file: /etc/prometheus/secrets/etcd/peer.crt
      key_file: /etc/prometheus/secrets/etcd/peer.key
      insecure_skip_verify: true

  - job_name: kube-scheduler
    static_configs:
      - targets: ['kube-scheduler.kube-system.svc:10259']
    scheme: https
    tls_config:
      ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
      insecure_skip_verify: true
    bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
```

### Recording Rules（高频聚合预计算，写到 `_sum:rate5m` 之类）

```yaml
groups:
- name: k8s.rules
  interval: 30s
  rules:
  - record: cluster:cpu_usage:rate5m
    expr: sum(rate(container_cpu_usage_seconds_total{container!=""}[5m]))

  - record: node:memory_available:ratio
    expr: 1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

  - record: pod:oom_kills:increase1h
    expr: sum by (namespace, pod) (increase(kube_pod_container_status_terminated_reason{reason="OOMKilled"}[1h]))

  - record: apiserver:request_latency:p99
    expr: histogram_quantile(0.99, sum by (le, verb) (rate(apiserver_request_duration_seconds_bucket[5m])))

  - record: cluster:fs_inodes_used:ratio
    expr: 1 - (node_filesystem_files_free / node_filesystem_files)
```

### Alert Rules（按维度各举一例）

```yaml
groups:
- name: control-plane
  rules:
  - alert: APIServerHighLatency
    expr: histogram_quantile(0.99, sum by (le) (rate(apiserver_request_duration_seconds_bucket[5m]))) > 1
    for: 5m
    labels: { severity: P0 }
    annotations:
      summary: "apiserver P99 > 1s"

  - alert: EtcdFsyncSlow
    expr: histogram_quantile(0.99, sum by (le) (rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m]))) > 0.01
    for: 5m
    labels: { severity: P0 }

- name: nodes
  rules:
  - alert: NodeDiskWillFillIn24h
    expr: predict_linear(node_filesystem_avail_bytes[6h], 24*3600) < 0
    for: 1h
    labels: { severity: P1 }

  - alert: NodeMemoryPressure
    expr: node:memory_available:ratio > 0.9
    for: 5m
    labels: { severity: P1 }

- name: pods
  rules:
  - alert: PodCrashLooping
    expr: rate(kube_pod_container_status_restarts_total[10m]) * 60 * 5 > 0
    for: 5m
    labels: { severity: P1 }

  - alert: CPUThrottlingHigh
    expr: sum by (namespace, pod) (rate(container_cpu_cfs_throttled_seconds_total[5m])) > 0.25
    for: 10m
    labels: { severity: P2 }

- name: services
  rules:
  - alert: BlackboxProbeFailing
    expr: probe_success == 0
    for: 3m
    labels: { severity: P0 }

  - alert: CoreDNSHighErrorRate
    expr: sum(rate(coredns_dns_response_rcode_count_total{rcode="SERVFAIL"}[5m])) / sum(rate(coredns_dns_request_count_total[5m])) > 0.01
    for: 5m
    labels: { severity: P1 }
```

> **Tip**：上面的 alert rules 用 PrometheusRule CRD 部署（Operator 模式）比裸 yaml 更便于版本管理；用 `kube-prometheus-stack` 时把它们塞到 `additionalPrometheusRules` 即可。

## 八、几条经验

1. **指标 ≠ 告警**：指标多到爆没人看就是噪音，**告警必须有人响应**，每个 PromQL 都要回答"出事了我该找谁"。
2. **看分位数，别只看均值**：P95/P99 才能反映用户体验，mean 被长尾拉偏。
3. **Requests/Limits 是监控的基线**：没有基线，"用了多少"无从判断，OOM 阈值也定不出来。
4. **kube-state-metrics 比 cAdvisor 更上层**：K8s 对象的状态（Deployment 进度、Job 状态）只能从这里拿。
5. **控制面先于业务**：apiserver / etcd / scheduler 出问题，所有告警都会"自相矛盾"，先保控制面。
6. **容量 & 成本也属于监控**：node 数、PVC 总量、出口带宽，季度复盘要用的数平时就要抓。
7. **采样率要分级**：核心服务全采、长尾服务 10%、批处理服务 1%，存储爆炸比监控缺失更常见。
