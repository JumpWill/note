# 高可用集群与升级 (HA & Upgrade)

> 本章系统讲解 K8s 高可用集群的架构设计、etcd 集群、负载均衡、备份恢复与版本升级策略。

## 一、K8s 高可用概述

### 1.1 为什么需要 HA

```text
单 Master 集群风险:
- API Server 单点 → 集群无法访问
- etcd 单点 → 数据丢失
- 升级/故障时停服

生产 HA 要求:
- 多 Master (≥3 节点)
- 多 etcd (3 或 5 节点)
- 跨可用区 (Availability Zone)
- 负载均衡入口 (HAProxy/Nginx/云 LB)
- 节点故障自动迁移 (Pod 漂移)
```

### 1.2 高可用层次

```text
┌─────────────────────────────────────┐
│  控制平面 HA (Control Plane HA)      │
│     - API Server 多实例              │
│     - etcd 集群 (Raft)              │
│     - Scheduler / ControllerManager │
├─────────────────────────────────────┤
│  工作节点 HA (Worker Node HA)       │
│     - 多节点 (≥3 节点)               │
│     - 节点故障 Pod 自动迁移          │
├─────────────────────────────────────┤
│  应用层 HA (Application HA)         │
│     - 多副本 Deployment             │
│     - PDB (PodDisruptionBudget)     │
│     - 反亲和调度                     │
├─────────────────────────────────────┤
│  数据层 HA (Storage HA)              │
│     - 多副本存储 (EBS Multi-Attach)  │
│     - 跨 AZ 副本                    │
└─────────────────────────────────────┘
```

## 二、etcd 高可用

### 2.1 etcd 集群架构

```text
etcd 是 K8s 的 KV 存储,所有集群状态都在 etcd 中

推荐: 3 或 5 节点 etcd 集群

3 节点:
   etcd-1 ←→ etcd-2 ←→ etcd-3
   (容忍 1 节点故障,Raft 多数派 = 2)

5 节点:
   etcd-1 ←→ etcd-2 ←→ etcd-3 ←→ etcd-4 ←→ etcd-5
   (容忍 2 节点故障,适合大规模生产)
```

### 2.2 etcd 部署模式

```text
1. 堆叠式 (Stacked) - 推荐小规模
   etcd 与 kube-apiserver 同节点
   - 简单,资源利用率高
   - 节点故障影响 etcd + apiserver

2. 外部式 (External) - 推荐生产
   etcd 独立集群,与 K8s 控制平面分离
   - 更好的隔离性
   - 可独立扩展 etcd
   - 维护更专业
```

### 2.3 外部 etcd 集群部署

```bash
# 1. 下载 etcd
ETCD_VER=v3.5.10
curl -L https://github.com/etcd-io/etcd/releases/download/${ETCD_VER}/etcd-${ETCD_VER}-linux-amd64.tar.gz \
  -o etcd.tar.gz
tar xf etcd.tar.gz
sudo cp etcd-${ETCD_VER}-linux-amd64/etcd /usr/local/bin/

# 2. 创建 etcd 配置 (每节点)
cat << EOF | sudo tee /etc/etcd/etcd.conf
ETCD_NAME=etcd-1
ETCD_DATA_DIR=/var/lib/etcd
ETCD_LISTEN_CLIENT_URLS=https://10.0.0.11:2379
ETCD_LISTEN_PEER_URLS=https://10.0.0.11:2380
ETCD_INITIAL_ADVERTISE_PEER_URLS=https://10.0.0.11:2380
ETCD_INITIAL_CLUSTER=etcd-1=https://10.0.0.11:2380,etcd-2=https://10.0.0.12:2380,etcd-3=https://10.0.0.13:2380
ETCD_INITIAL_CLUSTER_TOKEN=etcd-cluster-1
ETCD_ADVERTISE_CLIENT_URLS=https://10.0.0.11:2379
ETCD_TRUSTED_CA_FILE=/etc/etcd/ca.pem
ETCD_CERT_FILE=/etc/etcd/etcd.pem
ETCD_KEY_FILE=/etc/etcd/etcd-key.pem
ETCD_PEER_TRUSTED_CA_FILE=/etc/etcd/ca.pem
ETCD_PEER_CERT_FILE=/etc/etcd/etcd.pem
ETCD_PEER_KEY_FILE=/etc/etcd/etcd-key.pem
EOF

# 3. 启动 etcd
sudo systemctl enable etcd
sudo systemctl start etcd

# 4. 验证集群
etcdctl member list
etcdctl endpoint status --cluster
```

### 2.4 kubeadm 部署外部 etcd

```bash
# 在第一个 etcd 节点
sudo kubeadm init phase etcd local \
  --config=/etc/kubernetes/etcd-config.yaml

# 完整配置示例
cat << EOF > /etc/kubernetes/etcd-config.yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
etcd:
  external:
    endpoints:
    - https://10.0.0.11:2379
    - https://10.0.0.12:2379
    - https://10.0.0.13:2379
    caFile: /etc/kubernetes/pki/etcd/ca.crt
    certFile: /etc/kubernetes/pki/etcd/peer.crt
    keyFile: /etc/kubernetes/pki/etcd/peer.key
EOF

# 初始化 Master
sudo kubeadm init \
  --config=/etc/kubernetes/etcd-config.yaml \
  --control-plane-endpoint="LOAD_BALANCER_DNS:6443" \
  --upload-certs
```

### 2.5 etcd 运维

```bash
# 查看集群状态
etcdctl endpoint status --cluster \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 查看 leader
etcdctl endpoint status --cluster -w table | grep -E "Leader|true"

# 备份
etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=... --cert=... --key=...

# 备份验证
etcdctl snapshot status /backup/etcd-xxx.db -w table

# 恢复
etcdctl snapshot restore /backup/etcd-xxx.db \
  --name=etcd-1 \
  --initial-cluster=etcd-1=https://...,etcd-2=https://...,etcd-3=https://... \
  --initial-advertise-peer-urls=https://10.0.0.11:2380 \
  --data-dir=/var/lib/etcd
```

### 2.6 etcc 性能调优

```bash
# 磁盘 IO 优化 (关键!)
# SSD 优于 HDD
# 数据库与 K8s 数据目录分离

# 内核参数
sudo sysctl -w vm.swappiness=0
sudo sysctl -w vm.dirty_ratio=80
sudo sysctl -w vm.dirty_background_ratio=5
sudo sysctl -w net.core.somaxconn=65535

# 数据库大小限制 (默认 2GB,生产建议)
# /etc/etcd/etcd.conf
ETCD_QUOTA_BACKEND_BYTES=2147483648   # 2GB

# 压缩碎片 (定期执行)
etcdctl compact $(etcdctl endpoint status --write-out=json | jq -r '.Status.raftIndex')
etcdctl defrag

# 网络优化
ETCD_LISTEN_CLIENT_URLS=https://10.0.0.11:2379
```

## 三、控制平面 HA

### 3.1 3 Master 高可用架构

```text
┌──────────────────────────────────────────┐
│         HAProxy / Nginx LB (VIP)          │
│         10.0.0.10:6443                  │
└──────────┬─────────┬─────────┬───────────┘
           ↓         ↓         ↓
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ Master-1 │ │ Master-2 │ │ Master-3 │
   │ API      │ │ API      │ │ API      │
   │ etcd     │ │ etcd     │ │ etcd     │
   │ Sched    │ │ Sched    │ │ Sched    │
   │ CtrlMgr  │ │ CtrlMgr  │ │ CtrlMgr  │
   └────┬─────┘ └────┬─────┘ └────┬─────┘
        ↓             ↓             ↓
   ┌──────────────────────────────────────────┐
   │              Worker Nodes                 │
   │      node-1     node-2     node-3        │
   └──────────────────────────────────────────┘
```

### 3.2 HAProxy 配置

```bash
# /etc/haproxy/haproxy.cfg
global
    log /dev/log local0
    maxconn 4000

defaults
    mode tcp
    log global
    option tcplog
    timeout connect 5s
    timeout client 30m
    timeout server 30m

frontend kubernetes
    bind *:6443
    mode tcp
    option tcplog
    default_backend kubernetes-master

backend kubernetes-master
    mode tcp
    balance roundrobin
    option ssl-hello-chk
    server master-1 10.0.0.11:6443 check inter 5s fall 3 rise 2
    server master-2 10.0.0.12:6443 check inter 5s fall 3 rise 2
    server master-3 10.0.0.13:6443 check inter 5s fall 3 rise 2

listen stats
    bind *:9000
    mode http
    stats enable
    stats uri /
```

### 3.3 Nginx Stream LB

```nginx
# /etc/nginx/nginx.conf
stream {
    upstream kubernetes {
        server 10.0.0.11:6443;
        server 10.0.0.12:6443;
        server 10.0.0.13:6443;
    }

    server {
        listen 6443;
        proxy_pass kubernetes;
    }
}
```

### 3.4 kube-apiserver HA 配置

```yaml
# kubeadm-config.yaml (高可用配置)
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 10.0.0.10    # VIP
  bindPort: 6443

apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
controlPlaneEndpoint: "LOAD_BALANCER_DNS:6443"
etcd:
  external:
    endpoints:
    - https://etcd-1:2379
    - https://etcd-2:2379
    - https://etcd-3:2379
```

### 3.5 初始化 HA 集群

```bash
# 1. 准备 (所有 Master 节点)
# - 关闭 swap
# - 加载内核模块
# - 安装 containerd / kubeadm / kubelet / kubectl

# 2. 在第一个 Master 初始化
sudo kubeadm init \
  --control-plane-endpoint="10.0.0.10:6443" \
  --upload-certs \
  --pod-network-cidr=192.168.0.0/16 \
  --service-cidr=10.96.0.0/12

# 3. 其他 Master 加入 (控制平面)
sudo kubeadm join 10.0.0.10:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>

# 4. Worker 加入
sudo kubeadm join 10.0.0.10:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

# 5. 安装 CNI (任一 Master)
kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml

# 6. 验证
kubectl get nodes
# NAME       STATUS   ROLES           AGE
# master-1   Ready    control-plane   5m
# master-2   Ready    control-plane   3m
# master-3   Ready    control-plane   1m
# node-1     Ready    <none>          1m
```

## 四、工作节点 HA

### 4.1 多 Worker 节点架构

```text
推荐配置:
- 至少 3 个 Worker 节点 (生产)
- 跨可用区 (zone)
- 节点规格一致 (便于调度)
- 应用多副本 (Deployment/StatefulSet)

Pod 自动漂移:
- 节点故障 → ReplicationController 检测
- 重新调度到其他节点
- 默认 5 分钟超时 (kube-controller-manager --node-monitor-period)
```

### 4.2 节点自动恢复流程

```text
1. kubelet 失联 (默认 5 分钟)
   ↓
2. node controller 标记 Node NotReady
   ↓
3. replication controller 检测到 Pod 不可用
   ↓
4. 在其他节点重新创建 Pod
   ↓
5. 服务恢复正常

可配置: --node-monitor-period (默认 5s)
        --node-monitor-grace-period (默认 40s)
        --pod-eviction-timeout (默认 5m)
```

### 4.3 PodDisruptionBudget (PDB)

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  # 至少保留 2 个可用
  minAvailable: 2
  # 或百分比
  # minAvailable: 50%
  # 最多不可用 1 个
  # maxUnavailable: 1
  selector:
    matchLabels:
      app: web
```

### 4.4 节点维护流程

```bash
# 1. cordon: 标记不可调度 (但不驱逐)
kubectl cordon node-1

# 2. drain: 驱逐现有 Pod (业务方可控)
kubectl drain node-1 \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --force

# 3. 维护
ssh node-1 "yum update -y && reboot"

# 4. 验证节点恢复
kubectl get nodes

# 5. uncordon: 恢复调度
kubectl uncordon node-1

# 6. 验证 Pod 已调度回来
kubectl get pods -o wide | grep node-1
```

## 五、备份与恢复

### 5.1 备份策略

```text
必须备份的内容:
1. etcd 数据 (所有 K8s 状态)
2. 证书 (/etc/kubernetes/pki/)
3. 配置文件 (/etc/kubernetes/admin.conf 等)
4. 应用数据 (PV/PVC 中的数据)
5. 关键 YAML (Helm values、Manifest)
```

### 5.2 etcd 备份 (核心)

```bash
#!/bin/bash
# backup-etcd.sh
# 每日定时执行

BACKUP_DIR=/backup/etcd/$(date +%Y%m%d)
mkdir -p $BACKUP_DIR

# 1. 备份 etcd
etcdctl snapshot save $BACKUP_DIR/etcd-$(date +%H%M).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 2. 备份证书和配置
tar czf $BACKUP_DIR/k8s-configs.tar.gz \
  /etc/kubernetes/pki/ \
  /etc/kubernetes/admin.conf \
  /etc/kubernetes/manifests/

# 3. 保留 7 天
find /backup -mtime +7 -delete

# 4. 上传到云存储
aws s3 cp $BACKUP_DIR/etcd-*.db s3://my-bucket/etcd/
```

### 5.3 Velero 备份 (推荐)

Velero 是 CNCF 推荐的 K8s 备份工具,备份资源 + PV 数据。

```bash
# 1. 安装 Velero
velero install \
  --provider aws \
  --bucket my-velero-backups \
  --prefix velero \
  --secret-file ./credentials-velero \
  --use-restic

# 2. 创建备份 (整个集群)
velero backup create full-backup-$(date +%Y%m%d) --default-volumes-to-restic

# 3. 只备份某个 namespace
velero backup create prod-backup \
  --include-namespaces production \
  --ttl 720h

# 4. 定时备份
velero schedule create daily-backup \
  --schedule="0 2 * * *" \
  --include-namespaces production

# 5. 查看备份
velero backup get

# 6. 恢复
velero restore create --from-backup full-backup-20260818

# 7. 只恢复某个 namespace
velero restore create --from-backup prod-backup \
  --include-namespaces production
```

### 5.4 灾难恢复 (DR) 演练

```bash
# 1. 模拟 etcd 损坏
sudo systemctl stop etcd
sudo rm -rf /var/lib/etcd/*

# 2. 从备份恢复 etcd
sudo systemctl start etcd  # etcd 服务会因数据为空启动失败

# 3. 重建 etcd 数据
etcdctl snapshot restore /backup/etcd-xxx.db \
  --name=etcd-1 \
  --initial-cluster=etcd-1=https://...,etcd-2=https://...,etcd-3=https://... \
  --data-dir=/var/lib/etcd
sudo systemctl start etcd

# 4. 重启 kube-apiserver
sudo systemctl restart kubelet  # kubelet 会重启 apiserver (静态 Pod)
kubectl get nodes
```

## 六、K8s 版本升级

### 6.1 升级策略

```text
升级前必读:
1. K8s 版本兼容策略 (n-1, n, n+1)
   - kube-apiserver 比 kubelet 高 1 个次版本 (兼容)
   - kubectl 比 apiserver 高 1 个次版本 (兼容)
   
2. 升级顺序:
   - 先 Control Plane (Master)
   - 后 Worker Node

3. 升级方式:
   - kubeadm upgrade (推荐)
   - 二进制升级 (手动)
   - 云厂商托管升级 (EKS/GKE)
```

### 6.2 kubeadm 升级步骤 (1.30 → 1.31)

```bash
# === 1. 查看升级计划 ===
sudo kubeadm upgrade plan

# 输出:
# Components that must be upgraded manually after you've upgraded the control plane with 'kubeadm upgrade':
# - kubelet on 3 nodes
# - dashboard, metrics-server, etc.
#
# Upgrade to the latest stable version:
# - 1.31 version

# === 2. 升级 Master-1 ===

# 2.1 升级 kubeadm
sudo apt-get update
sudo apt-get install -y kubeadm=1.31.0-1.30

# 2.2 验证升级计划
sudo kubeadm upgrade plan

# 2.3 应用升级 (Master 节点)
sudo kubeadm upgrade apply v1.31.0

# 2.4 升级 kubelet 和 kubectl
sudo apt-get install -y kubelet=1.31.0-1.30 kubectl=1.31.0-1.30
sudo systemctl restart kubelet

# 2.5 验证
kubectl get nodes
# NAME       STATUS   ROLES           VERSION
# master-1   Ready    control-plane   v1.31.0

# === 3. 升级 Master-2 和 Master-3 ===
# 同上,逐个升级

# === 4. 升级 Worker 节点 ===

# 4.1 驱逐 Pod
kubectl drain node-1 --ignore-daemonsets

# 4.2 在 node-1 上升级
sudo apt-get install -y kubeadm=1.31.0-1.30
sudo kubeadm upgrade node
sudo apt-get install -y kubelet=1.31.0-1.30
sudo systemctl restart kubelet

# 4.3 解除保护
kubectl uncordon node-1

# 4.4 验证
kubectl get nodes
```

### 6.3 升级后验证清单

```bash
# 1. 节点状态
kubectl get nodes

# 2. 系统 Pod 状态
kubectl get pods -n kube-system

# 3. 应用状态
kubectl get pods -A

# 4. API Server 健康
curl -k https://localhost:6443/healthz
curl -k https://localhost:6443/livez
curl -k https://localhost:6443/readyz

# 5. etcd 健康
ETCDCTL_API=3 etcdctl endpoint health \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 6. CoreDNS
kubectl get pods -n kube-system -l k8s-app=kube-dns

# 7. CNI (Calico)
kubectl get pods -n kube-system -l k8s-app=calico-node
```

### 6.4 升级失败回滚

```bash
# kubeadm 不支持直接回滚
# 只能:
# 1. 重新升级到上一版本 (如果还在维护)
# 2. 从备份恢复整个 etcd
# 3. 重新部署集群

# 预防:
# - 升级前必备份 etcd
# - 测试环境先升级
# - 灰度升级 (一台一台)
```

## 七、生产 HA 实战案例

### 7.1 AWS 上部署 K8s HA

```text
架构:
- 3 Master EC2 (跨 3 AZ)
- 3+ Worker EC2 (按需扩展)
- AWS NLB (负载均衡 Master API)
- AWS EBS (Worker 存储,Multi-Attach)
- AWS S3 (etcd 备份)

部署工具:
- kubeadm (推荐,完全控制)
- kops (AWS 原生集成)
- EKS (托管,零运维)
```

### 7.2 自建 vs 托管对比

| 维度 | 自建 (kubeadm) | 托管 (EKS/GKE) |
|------|----------------|------------------|
| 控制度 | 完全 | 受限 |
| 运维成本 | 高 | 低 |
| 升级 | 自己 | 一键 |
| 高可用 | 自己搭 | 自动 |
| 成本 | 低 | 高 (约 20% 溢价) |
| 适用 | 私有云/特殊需求 | 公有云/通用 |

### 7.3 自建 K8s HA Checklist

```text
□ 3 Master 节点 (跨 3 AZ)
□ 外部 etcd 集群 (3 或 5 节点)
□ HAProxy/Nginx LB 入口
□ Master 节点资源充足 (8C16G 起步)
□ Master 节点禁调度业务 Pod (taint)
□ etcd 使用 SSD + 单独磁盘
□ etcd 启用 TLS + 客户端证书
□ Secret 启用 etcd 加密
□ 安装 Metrics Server + Dashboard
□ 安装 Ingress Controller
□ 配置 PodSecurity 准入控制
□ 集成企业 IDP (OIDC)
□ 安装 Prometheus + Grafana + Alertmanager
□ 安装 Velero (备份)
□ 定期演练恢复流程
□ 文档化运维 Runbook
```

## 核心要点速记

### HA 层次

```text
控制平面 HA:  3 Master + LB + etcd 集群
工作节点 HA: 3+ Worker + 多副本 Deployment
应用 HA:      Deployment + PDB + 反亲和
数据 HA:      多副本存储 + 跨 AZ
```

### etcd HA

```text
3 节点: 容忍 1 故障
5 节点: 容忍 2 故障
堆叠式: etcd 与 Master 同节点
外部式: etcd 独立集群 (生产推荐)
```

### 升级流程

```text
1. 备份 etcd
2. 测试环境先升级
3. 升级 Master (一台一台)
4. 升级 Worker (kubectl drain → 升级 → uncordon)
5. 验证集群健康
6. 监控应用状态
```

### 备份策略

```text
- etcd: 每日快照 (核心)
- 资源: Velero (推荐)
- 应用数据: 应用层备份
- 配置: Git 仓库
```

### 关键命令

```bash
# 备份
etcdctl snapshot save /backup/etcd.db
velero backup create <name>

# 节点维护
kubectl cordon <node>
kubectl drain <node>
kubectl uncordon <node>

# 升级
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.31.0
```

### 生产最低配置

```text
- 3 Master (8C16G, SSD, 万兆网络)
- 3 Worker (16C64G, SSD)
- 3 etcd (4C8G, NVMe SSD, 单独磁盘)
- HAProxy/Nginx (4C8G, HA)
- 所有节点跨 3 AZ
```
