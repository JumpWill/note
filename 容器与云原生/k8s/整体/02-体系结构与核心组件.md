# K8s 体系结构与核心组件 (Architecture & Components)

> 本章系统讲解 Kubernetes 整体架构、Control Plane 与 Worker Node 的所有核心组件、组件间协作流程。

## 一、K8s 整体架构

### 1.1 两层架构总览


### 1.2 核心组件职责表

| 组件 | 运行位置 | 职责 |
|------|----------|------|
| **kube-apiserver** | Master | API 入口,所有组件通信枢纽 |
| **etcd** | Master | 集群状态 KV 存储 |
| **kube-scheduler** | Master | Pod 调度决策 |
| **kube-controller-manager** | Master | 运行各种控制器(副本/节点/服务) |
| **cloud-controller-manager** | Master | 云厂商集成(可选) |

| **kube-proxy** | Worker | 网络代理,Service IP 转发 |
| **容器运行时** | Worker | 运行容器(containerd/CRI-O) |

## 二、Control Plane(控制平面)

### 2.1 kube-apiserver (API 服务器)

**角色**:K8s API 入口,所有组件间的通信都通过它。

```text
功能:
1. REST API 服务 (HTTPS, 默认 6443)
2. 认证 (Authentication)
3. 授权 (Authorization, RBAC)
4. 准入控制 (Admission Control)
5. 资源 CRUD
6. 资源 Watch(监听变化)
7. 数据持久化到 etcd
```

**关键参数**:

```yaml
# /etc/kubernetes/manifests/kube-apiserver.yaml
spec:
  containers:
  - command:
    - kube-apiserver
    - --advertise-address=10.0.0.10
    - --etcd-servers=https://127.0.0.1:2379
    - --secure-port=6443
    - --service-cluster-ip-range=10.96.0.0/12
    - --client-ca-file=/etc/kubernetes/pki/ca.crt
    - --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
    - --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
    - --service-account-key-file=/etc/kubernetes/pki/sa.pub
    - --authorization-mode=Node,RBAC
    - --enable-bootstrap-token-auth=true
    - --enable-admission-plugins=NodeRestriction,ServiceAccount
    - --audit-log-maxage=30
```

### 2.2 etcd (分布式 KV 存储)

**角色**:K8s 的"数据库",存储所有集群状态(资源对象)。

```text
特点:
1. 强一致性 (Raft 共识协议)
2. 高可用 (3 节点或 5 节点)
3. Watch 机制(API Server 监听变化)
4. Key-Value 存储
5. 性能: 写入 ~10000 QPS, 读取 ~30000 QPS
6. 数据存储在 /var/lib/etcd/
```

**etcd 部署模式**:

```text
1. 堆叠式 (Stacked)
   - etcd 与 APIServer 同节点
   - 简单,但 HA 受限于 Control Plane HA

2. 外部式 (External)
   - etcd 独立集群
   - 推荐生产使用,APIServer HA 与 etcd HA 解耦
   - 性能更好,运维更专业
```

**etcd 关键操作**:

```bash
# 查看集群状态
etcdctl endpoint status --cluster \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 查看 key 数量
etcdctl get /registry --prefix --keys-only | wc -l

# 备份
etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=... --cert=... --key=...

# 恢复
etcdctl snapshot restore /backup/etcd-xxx.db \
  --data-dir=/var/lib/etcd-restore
```

**etcd 性能调优**:

```bash
# 磁盘 IO 优化(关键!)
# 使用 SSD,IOPS 至少 5000+
# 数据库与 K8s 数据目录分开

# 内核参数
sudo sysctl -w vm.swappiness=0
sudo sysctl -w vm.dirty_ratio=80
sudo sysctl -w vm.dirty_background_ratio=5
sudo sysctl -w net.core.somaxconn=65535

# 数据库大小限制 (默认 8GB,生产建议 ≤ 2GB)
# 修改 /etc/etcd/etcd.conf
ETCD_QUOTA_BACKEND_BYTES=2147483648  # 2GB

# 压缩
etcdctl compact $(etcdctl endpoint status --write-out=json | jq -r '.Status.raftIndex')
etcdctl defrag
```

### 2.3 kube-scheduler (调度器)

**角色**:为新创建的 Pod 选择最合适的 Worker 节点。

```text
调度流程:
1. 监听 Pod(未指定 nodeName)
2. 过滤 (Filtering) - 排除不满足条件的节点
   - 资源需求 (CPU/内存)
   - 节点选择器 (nodeSelector)
   - 污点容忍 (Toleration)
   - 节点亲和性 (Affinity)
3. 打分 (Scoring) - 为剩余节点打分
   - 资源利用率均衡
   - 亲和性偏好
   - 已有 Pod 分布
4. 选择最高分节点
5. 绑定 (Bind) - 写回 API Server
```

**调度策略示例**:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  # 节点选择器: 必须有 disktype=ssd 标签
  nodeSelector:
    disktype: ssd

  # 亲和性
  affinity:
    # 节点亲和: 倾向于 zone=us-east-1a
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: zone
            operator: In
            values: ["us-east-1a"]

    # Pod 反亲和: 不与 db-pod 同节点
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: db
        topologyKey: kubernetes.io/hostname

  # 容忍污点
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"

  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: 500m
        memory: 256Mi
```

### 2.4 kube-controller-manager (控制器管理器)

**角色**:运行 K8s 内置的所有控制器,持续 reconcile 期望状态与实际状态。

```text
内置控制器 (几十种):
1. ReplicaSet Controller: 维护 Pod 副本数
2. Deployment Controller: 管理 Deployment 滚动升级
3. StatefulSet Controller: 有状态应用管理
4. DaemonSet Controller: 守护进程管理
5. Node Controller: 节点健康监控
6. Service Controller: 维护 Service Endpoints
7. Endpoint Controller: 维护 Endpoint 对象
8. Namespace Controller: Namespace 清理
9. ServiceAccount Controller: 默认 SA 创建
10. PersistentVolume Controller: PV 管理
11. Deployment Controller
12. Job Controller
13. CronJob Controller
14. HorizontalPodAutoscaler Controller (HPA)
15. VerticalPodAutoscaler Controller (VPA)
16. ...
```

**Reconcile 循环示例**:

```text
期望: Deployment 副本数 = 3
实际: 当前 Pod 数 = 2

Controller 检测到差异
   ↓
创建新 Pod (期望 → 实际)
   ↓
监听 Pod 状态变化
   ↓
持续 reconcile
```

### 2.5 cloud-controller-manager (云控制器)

**角色**:与云厂商集成(AWS/GCP/Azure/Aliyun 等)。

```text
功能:
1. Node Controller - 云上节点生命周期
2. Route Controller - 云路由配置
3. Service Controller - 云负载均衡器
4. Volume Controller - 云存储卷挂载

作用:
- 将云厂商特定逻辑与 K8s 核心解耦
- 让 K8s 核心保持厂商中立
```

## 三、Worker Node(工作节点)

### 3.1 kubelet (节点代理)

**角色**:K8s 在每个 Worker 节点上的"管家",管理 Pod 生命周期。

```text
职责:
1. 监听 API Server 分配的任务 (Pod)
2. 调用 Container Runtime 启动容器
3. 挂载 Volume
4. 配置网络 (CNI)
5. 健康检查 (Probe)
6. 上报 Pod 状态、节点资源
7. 执行 Pod 的生命周期钩子 (Prestop/Poststart)
```

**关键配置**:

```yaml
# /var/lib/kubelet/config.yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
address: "0.0.0.0"
port: 10250
cgroupDriver: systemd
cgroupsPerQOS: true
enforceNodeAllocatable:
  pods: "110"
authentication:
  anonymous:
    enabled: false
  webhook:
    enabled: true
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt
```

### 3.2 kube-proxy (网络代理)

**角色**:维护节点上的网络规则,实现 Service IP 转发。

```text
三种模式:
1. iptables (默认, Linux)
2. IPVS (Linux, 性能更好)
3. userspace (已废弃)
```

**IPVS 模式启用**:

```bash
# 修改 kube-proxy ConfigMap
kubectl -n kube-system edit cm kube-proxy
# mode: "ipvs"
# ipvs:
#   scheduler: "rr"  # 轮询
```

**iptables 工作原理**:

```bash
# 创建 Service 时
kubectl expose deployment nginx --port=80

# API Server 分配虚拟 IP: 10.96.10.50
# kube-proxy 在所有节点上创建 iptables 规则:
# 10.96.10.50:80 → DNAT → 任意 Pod IP:80

# 客户端访问 10.96.10.50:80 时
# iptables 自动负载均衡到后端 Pod
```

### 3.3 Container Runtime (容器运行时)

**演进历史**:

```text
- Docker (原始默认, K8s 1.20+ 弃用, 1.24+ 移除)
- containerd (CNCF, 当前推荐)
- CRI-O (Red Hat 推荐)
- Docker Engine (通过 cri-dockerd shim)
```

**containerd 配置**:

```toml
# /etc/containerd/config.toml
version = 2

[plugins."io.containerd.snapshotter.v1.native"]
  [plugins."io.containerd.snapshotter.v1.native"]... 

[plugins."io.containerd.grpc.v1.cri"]
  sandbox_image = "registry.k8s.io/pause:3.9"
  [plugins."io.containerd.grpc.v1.cri".containerd]
    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
        runtime_type = "io.containerd.runc.v2"
```

### 4.2 关键点

```text
1. API Server 是唯一与 etcd 通信的组件
2. 所有组件间通信都经过 API Server
3. 调度决策在 Scheduler,不在 API Server
4. kubelet 主动 watch API Server,不被动接收
5. CRI 是容器运行时接口(containerd/CRI-O 实现)
```

## 五、K8s 资源对象模型

### 5.1 API 资源分类

```text
核心 (core):
- Pod
- Service
- ConfigMap
- Secret
- Namespace
- Node
- PersistentVolume
- PersistentVolumeClaim

应用 (apps/v1):
- Deployment
- StatefulSet

批处理 (batch/v1):
- Job
- CronJob

网络 (networking.k8s.io/v1):
- Ingress
- NetworkPolicy

权限 (rbac.authorization.k8s.io/v1):
- Role
- RoleBinding
- ClusterRole
- ClusterRoleBinding
- ServiceAccount

存储:
- StorageClass
- VolumeAttachment

扩展:
- CustomResourceDefinition (CRD)
```

### 5.2 资源结构

每个资源都包含:

```yaml
apiVersion: apps/v1  # 必填
kind: Deployment      # 必填 (类型)
metadata:             # 元数据
  name: my-app
  namespace: default
  labels:
    app: my-app
  annotations:
    ...
spec:                 # 期望状态 (用户定义)
  replicas: 3
  ...
status:               # 实际状态 (K8s 维护)
  replicas: 3
  readyReplicas: 3
  ...
```

### 5.3 Group/Version/Kind (GVK)

```text
资源通过 GVK 唯一标识:
  Group: apps
  Version: v1
  Kind: Deployment

例: apiVersion: apps/v1, kind: Deployment

不同版本可共存(v1beta1 与 v1):
  apiVersion: networking.k8s.io/v1
  apiVersion: networking.k8s.io/v1beta1
```

## 六、控制器模式

### 6.1 声明式 API

```text
传统命令式:
  "启动 3 个 nginx"
  "再启动 1 个 → 4 个"
  "关掉 1 个 → 3 个"

K8s 声明式:
  "我要 3 个 nginx 副本"
  (K8s 自动维持 3 个)
```

### 6.2 Reconcile 循环

```text
┌─────────────────────────────────────────┐
│           Controller                     │
│                                          │
│   ┌──────────────────┐                  │
│   │ 1. Watch 资源变化 │                  │
│   └────────┬─────────┘                  │
│            ↓                              │
│   ┌──────────────────┐                  │
│   │ 2. 获取期望状态   │  (Spec)          │
│   │ 3. 获取实际状态   │  (Status)        │
│   └────────┬─────────┘                  │
│            ↓                              │
│   ┌──────────────────┐                  │
│   │ 4. 比较状态差异   │                  │
│   └────────┬─────────┘                  │
│            ↓                              │
│   ┌──────────────────┐                  │
│   │ 5. 执行协调操作   │  (创建/删除/更新) │
│   └────────┬─────────┘                  │
│            ↓                              │
│   ┌──────────────────┐                  │
│   │ 6. 更新资源状态   │  (Status)        │
│   └──────────────────┘                  │
│                                          │
│   持续循环 (每秒)                        │
└─────────────────────────────────────────┘
```

### 6.3 自定义控制器

```go
// Go 写自定义 Controller
// 使用 controller-runtime 框架

type MyResourceReconciler struct {
    client.Client
    Scheme *runtime.Scheme
}

func (r *MyResourceReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // 1. 获取自定义资源
    var myResource myv1.MyResource
    if err := r.Get(ctx, req.NamespacedName, &myResource); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    
    // 2. 期望状态 vs 实际状态
    // 3. 协调操作
    
    return ctrl.Result{Requeue: true}, nil
}
```

## 七、etcd 深度详解

### 7.1 数据模型

```text
etcd 是 K8s 的唯一持久化存储

K8s 对象 → JSON/YAML → etcd key-value

例:
  /registry/pods/default/nginx-abc123
  {
    "apiVersion": "v1",
    "kind": "Pod",
    "metadata": {"name": "nginx-abc123", "namespace": "default"},
    "spec": {...},
    "status": {...}
  }
```

### 7.2 K8s 对象在 etcd 中的路径

```text
/registry/
├── pods/<namespace>/<pod-name>
├── services/<namespace>/<service-name>
├── deployments/<namespace>/<deployment-name>
├── configmaps/<namespace>/<configmap-name>
├── secrets/<namespace>/<secret-name>
├── nodes/<node-name>
├── namespaces/<namespace-name>
└── ...
```

### 7.3 备份策略

```bash
# 定期备份脚本 (cron 每日执行)
#!/bin/bash
BACKUP_DIR=/backup/etcd/$(date +%Y%m%d)
mkdir -p $BACKUP_DIR

etcdctl snapshot save $BACKUP_DIR/etcd-$(date +%H%M).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/etcd-client.crt \
  --key=/etc/kubernetes/pki/etcd/etcd-client.key

# 保留 7 天
find /backup/etcd -mtime +7 -delete
```

## 八、K8s 高可用架构

### 8.1 Control Plane HA(3 Master)

```text
┌─────────────────────────────────────────────┐
│              HAProxy / Nginx LB              │
│              (VIP: 10.0.0.10)                │
└────────┬─────────┬──────────┬────────────────┘
         ↓         ↓          ↓
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ Master-1 │ │ Master-2 │ │ Master-3 │
   │  API     │ │  API     │ │  API     │
   │  etcd    │ │  etcd    │ │  etcd    │
   │  Sched   │ │  Sched   │ │  Sched   │
   │  Ctrl    │ │  Ctrl    │ │  Ctrl    │
   └────┬─────┘ └────┬─────┘ └────┬─────┘
        ↓             ↓             ↓
   ┌──────────────────────────────────┐
   │        Worker Nodes              │
   │   node-1  node-2  node-3 ...    │
   └──────────────────────────────────┘
```

### 8.2 etcd HA(3 或 5 节点)

```text
3 etcd 节点:
   etcd-1 ←→ etcd-2 ←→ etcd-3
   (允许 1 节点故障)

5 etcd 节点:
   etcd-1 ←→ etcd-2 ←→ etcd-3 ←→ etcd-4 ←→ etcd-5
   (允许 2 节点故障)
   写入性能下降,但读性能更好

K8s 推荐:
- Control Plane 3 节点(etcd 与 API Server 同节点)
- 或 etcd 独立 3-5 节点 + Control Plane 2+ 节点
```

### 8.3 Worker Node 池化

```text
生产建议:
- 同构 Worker 节点 (相同规格)
- 至少 3 个 Worker 节点 (HA 基础)
- 跨可用区部署
- 节点池化 (不同业务不同规格)
```

## 核心要点速记

### 两层架构

```text
Control Plane (Master):
  - kube-apiserver: API 入口
  - etcd: 状态存储
  - kube-scheduler: Pod 调度
  - kube-controller-manager: 控制器循环
  - cloud-controller-manager: 云集成

Worker Node:
  - kubelet: 节点代理
  - kube-proxy: 网络代理
  - containerd: 容器运行时
```

### Pod 创建流程

```text
1. kubectl apply → API Server
2. API Server 认证/授权/准入
3. 写 etcd
4. Scheduler 监听 + 调度决策
5. API Server 写回 spec.nodeName
6. kubelet watch → 启动容器
7. 上报状态 → etcd
8. kubectl get pods 看到 Running
```

### 控制器模式

```text
声明式 API:
  用户定义 Spec (期望状态)
  Controller 持续 reconcile
  写回 Status (实际状态)

K8s 一切皆控制器
```

### 关键设计

```text
1. API Server 是唯一与 etcd 通信的组件
2. 所有组件 watch API Server,不直接通信
3. Scheduler 决策但不执行
4. kubelet 主动 watch + 主动调用 CRI
5. 任何组件崩溃都不影响其他组件
```

### HA 关键

```text
- Master 至少 3 节点
- etcd 3 或 5 节点
- Worker 至少 3 节点
- 跨可用区
- API Server 前置 LB (HAProxy/Nginx/云 LB)
```
