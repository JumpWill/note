# K8s 日志收集 —— 原理与实现方式

> 理解：**容器日志 = 进程的 stdout/stderr**，K8s 本身**不存**日志，只在节点本地临时保留。生产要做集中分析/告警/合规，必须有"日志管道"把日志从节点搬到后端。

---

## 一、容器日志到底存在哪

### 1.1 容器写 stdout → container runtime 重定向到 JSON log driver

```text
应用进程 (PID 1)
   │ stdout/stderr
   ▼
┌────────────────────────────────────────┐
│  Container Runtime (containerd/dockerd) │
│  ├─ 用 shim 接管 PID 1 的 stdio         │
│  └─ 写入 /var/log/containers/<pod>_<ns>_<container>-<id>.log │
└────────────────────────────────────────┘
```

文件格式默认是 **JSON**，每行一个对象：

```json
{"log":"2024-09-01 10:23:45 INFO request handled\n","stream":"stdout","time":"2024-09-01T10:23:45.123Z"}
```

> ⚠️ **容器一重启，旧日志就没了**（默认 emptyDir 临时卷）。所以"采集必须实时"——延迟就丢。

### 1.2 K8s 提供的三个原生查看入口（都不够用）

| 方式 | 命令 / 路径 | 局限 |
| --- | --- | --- |
| `kubectl logs` | 直接读 runtime log 文件 | 只能看当前容器，重启前能看到之前的，重启后只能看新日志 |
| `kubectl logs -p` | 看上一个实例 | 节点回收 / Pod 漂移到别节点 → **彻底没了** |
| 节点 `/var/log/containers/` | kubelet 软链到 `/var/log/pods/` | 日志只在**当前节点**，Pod 漂走就没了 |

**结论**：这三种都**不能**满足生产需要（保留周期短、不能聚合、不能全文检索）。必须**外采**。

## 二、采集方式：三大流派

```text
方案 A: DaemonSet 节点 Agent（⭐ 主流）
方案 B: Sidecar 容器
方案 C: 不部署 Agent，直接 API 拉（基本淘汰）
```

### 方案 A：节点 DaemonSet（**90% 的生产方案**）

每个节点跑一个日志 Agent Pod（DaemonSet 保证每个 Node 一个实例），从本节点所有容器的日志文件读取并转发。

```text
┌──────────────────────────── Node 1 ────────────────────────────┐
│                                                                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     ┌────────────┐  │
│  │ Pod A    │  │ Pod B    │  │ Pod C    │     │ Fluent Bit │  │
│  │ (stdout) │  │ (stdout) │  │ (stdout) │ ──► │ DaemonSet  │──┼──►  日志后端
│  └──────────┘  └──────────┘  └──────────┘     └────────────┘  │
│       ▼             ▼             ▼                  ▲          │
│   /var/log/containers/*.log (kubelet 软链) ─────────┘          │
└────────────────────────────────────────────────────────────────┘
```

**优点**：
- 资源占用低（每节点一个 Agent 复用）
- 部署简单，K8s 原生支持
- 无侵入，业务不用改

**缺点**：
- 看不到 Pod 内文件（如写到 `/tmp/*.log` 的应用日志，需要业务改打到 stdout）
- 多租户隔离差，所有 Pod 日志走同一管道

**主流 Agent**：

| Agent | 特点 | 后端 |
| --- | --- | --- |
| **Fluent Bit** | C 写的，最轻量（~10MB 内存），**默认首选** | 几乎所有 |
| **Fluentd** | Ruby 写的，生态最全但吃内存 | ES / Kafka |
| **Filebeat** | Elastic 栈官方，K8s 友好 | ES / Loki |
| **Vector** | Rust 写的，性能强，配置现代 | Loki / S3 |
| **Promtail** | Loki 官方，**已被 Grafana 标记为 deprecated**，新项目用 Grafana Alloy | Loki |

### 方案 B：Sidecar 容器

在每个业务 Pod 里加一个日志 sidecar，业务日志写到 sidecar 能读取的位置（通常是 shared volume）。

```text
Pod
├── Container: app (writes to /var/log/app/app.log)
├── Container: log-sidecar (tails /var/log/app/app.log → stdout)
└── Volume: shared-logs (/var/log/app)
```

**典型用法**：
1. 业务**无法改打到 stdout**（老应用 / 第三方）
2. 需要在 sidecar 里做**自定义处理**（敏感信息脱敏、字段提取）
3. 多行日志（Java stack trace）需要定制解析

**优点**：完全隔离，每个 Pod 自己管
**缺点**：资源开销翻倍（每 Pod 多一个容器），规模化差

**官方 API 模式**（K8s 1.27+ GA）：用 `NativeSidecars` + `RestartPolicy=Always` 让 sidecar 跟主容器一样生命周期——但仍要业务自定义。

### 方案 C：不部署 Agent

应用自己调日志后端 SDK（如 `elasticsearch-py`）直推。**几乎没人用**——业务侵入大、可靠性差（业务挂了日志也没了）。

## 三、采集的核心组件

不管用哪种 agent，逻辑上都是这几块：

```text
┌────────────────────────────────────────────────────────────────────┐
│                        日志 Agent（DaemonSet / Sidecar）            │
│                                                                    │
│  ┌──────┐    ┌──────┐    ┌──────────┐    ┌──────┐    ┌─────────┐  │
│  │Input │──► │Parser│──► │ Filter   │──► │Buffer│──► │ Output  │  │
│  │tail  │    │json  │    │ enrich   │    │disk  │    │ http/kafka │ │
│  │      │    │regex │    │ redact   │    │      │    │         │  │
│  └──────┘    └──────┘    └──────────┘    └──────┘    └─────────┘  │
│   读文件      解析      补字段 / 脱敏    抗背压       发到后端      │
└────────────────────────────────────────────────────────────────────┘
```

### 3.1 Input（读哪 / 怎么读）

```yaml
# Fluent Bit 举例
input:
  - name: tail                          # 持续追踪文件
    path: /var/log/containers/*.log     # 路径（容器日志默认位置）
    refresh_interval: 10                # 多久扫一次新文件
    rotate_wait: 5                      # logrotate 等待
    db: /var/lib/fluent-bit/pos.db      # 断点续传（重启不丢日志的关键）
```

**关键**：必须用带 position DB 的 tail，不能用普通 `cat`——容器日志会被 logrotate 切分 / 业务 Pod 频繁起停，agent 重启后必须从上次位置继续。

### 3.2 Parser（结构化）

日志默认是 JSON，但很多应用写**纯文本**（Nginx access log、Java log4j）。需要 parser：

```text
Nginx 原始:  192.168.1.1 - - [01/Sep/2024:10:23:45 +0000] "GET /api HTTP/1.1" 200 1024
                                                       ▼ regex
Parser 后:   {ip:"192.168.1.1", method:"GET", path:"/api", status:200, bytes:1024}
```

主流做法：
- **业务自己打 JSON**（最稳，Java 用 logback-encoder、Go 用 logrus/slog、Python 用 structlog）
- Agent 端 regex 解析（兜底，但脆）

### 3.3 Filter / Enrichment（补字段 + 脱敏）

**补字段**（K8s 元数据）：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `kubernetes.pod_name` | 容器 log 文件路径解析 | 关联到 Pod |
| `kubernetes.namespace` | 同上 | 多租户 |
| `kubernetes.container_name` | 同上 | 多容器 Pod 区分 |
| `kubernetes.node_name` | env `NODE_NAME` 或 downward API | 节点维度聚合 |
| `trace_id` | 应用自己打 | 关联到链路追踪 |

**脱敏**（生产必做）：

```text
[脱敏前]  user login: phone=13800138000, id_card=110101199001011234
[脱敏后]  user login: phone=138****8000, id_card=1101**********1234
```

正则或字典匹配 → 替换。Fluent Bit 有 `grep` / `modify` / `lua` 插件。

### 3.4 Buffer / 背压（生产稳定性核心）

```text
Agent ──► Buffer (Memory + Disk) ──► Output
                                        │
                            ┌───────────┼───────────┐
                            ▼           ▼           ▼
                         后端 A      后端 B     重试队列
                       (Loki)      (Kafka)    (磁盘满了写本地)
```

**为什么必须有 buffer**：
- 后端短暂不可用（5min）→ 日志不能丢
- 流量峰值（双 11）→ 不能直接 OOM

**实现**：
- 内存 buffer + 溢出到磁盘（Fluent Bit 的 `[OUTPUT] storage.total_limit_size`）
- 磁盘满了的兜底：本地持久化文件 + 告警（K8s 节点挂了还能补救）
- 多 output 通道分流（实时告警走 Kafka + 长期存储走 S3）

### 3.5 Output（发到哪）

| 后端 | 协议 | 特点 |
| --- | --- | --- |
| **Loki** | HTTP / Promtail push API | 不建索引，**标签即索引**，省存储 |
| **Elasticsearch** | HTTP Bulk | 全功能全文检索，但贵 |
| **Kafka** | 协议本身 | 中转层，下游再分流（数仓 / 审计 / 监控） |
| **阿里云 SLS** | SDK | 国内云上首选，免运维 |
| **S3 / OSS** | S3 API | **冷存储**，日志归档 / 合规 |

## 四、典型架构模式

### 4.1 简单架构（单集群、中小规模）

```text
Node (DaemonSet)
  └─ Fluent Bit ──HTTP──► Loki / ES / SLS
```

### 4.2 Kafka 中转（高可靠 / 多路分发）

```text
Node (DaemonSet)
  └─ Fluent Bit ──► Kafka（保留 3 天）
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
             ClickHouse   Elasticsearch  S3 (冷存)
             (指标分析)    (全文检索)     (合规归档)
```

**优点**：Agent 只管推 Kafka，挂了 / 后端慢都不丢日志
**缺点**：多一套组件要运维

### 4.3 多集群联邦

```text
Cluster A ──► Fluent Bit ──┐
Cluster B ──► Fluent Bit ──┼──► 中央 Kafka / Loki
Cluster C ──► Fluent Bit ──┘
```

每个集群出口带宽有限 → 走专线 / VPN 到中央日志集群。

## 五、日志的保留策略

| 阶段 | 保留期 | 成本 | 存储介质 |
| --- | --- | --- | --- |
| **热** | 0–7 天 | 高 | ES / Loki 热节点 |
| **温** | 7–30 天 | 中 | ES 冷节点 / Loki OSS |
| **冷** | 30 天+ | 低 | S3 / OSS / 归档存储 |

> **合规要求**（金融 / 医疗）：通常**至少 180 天**，需要专门规划存储。
> K8s 日志本身**无合规能力**——采集链路的设计要保证**全链路不丢**。

## 六、关键设计要点

### 6.1 日志标签（labels / tags）的设计

后端（尤其 Loki）的检索性能强依赖标签维度。**标签 = 低基数业务维度**：

```text
✅ 推荐标签：
   {cluster="prod-1", namespace="payment", app="order-api", level="error"}

❌ 不要做标签（基数爆炸）：
   {user_id="12345", request_id="abc", ip="1.2.3.4"}
```

业务字段应该放日志**正文**（content），不要全塞标签。

### 6.2 日志格式统一

```text
[统一前] 格式五花八门：text / JSON / 自定义 → 解析成本高、检索体验差
[统一后] 推荐所有应用输出 JSON：

{"ts":"2024-09-01T10:23:45.123Z","level":"INFO","msg":"...",
 "trace_id":"abc","span_id":"def","caller":"main.go:42"}
```

**怎么落地**：
- 框架 SDK 强制（logrus JSON formatter / logback-encoder / python structlog）
- CI 检查（grep 业务代码禁止 `fmt.Println` / `System.out.println`）
- 兜底：Agent 端用 parser 转

### 6.3 资源限制

Agent 单节点资源开销估算：

```text
Fluent Bit:   ~30MB 内存, ~50m CPU（默认配置）
Filebeat:     ~100MB 内存, ~100m CPU
Fluentd:      ~200MB+ 内存, ~200m CPU（plugin 多时翻倍）
```

`resources.requests` 必须设，否则 OOMKilled 时整个节点日志就丢了。

### 6.4 多行日志

Java stack trace、Nginx 长访问日志、Python traceback 都是**多行**：

```text
错误日志：
java.lang.NullPointerException
  at com.example.Foo.bar(Foo.java:42)
  at com.example.Main.main(Main.java:13)
```

**必须**做多行合并，否则后端每行单独存，检索体验极差。

```yaml
# Fluent Bit 多行解析示例
[FILTER]
    Name multiline
    Match *
    Type parser
    Parser java
    Key_Name log
```

### 6.5 容器内文件日志（写到 /tmp/*.log 那种）

DaemonSet 看不到——必须改成 stdout 或加 Sidecar：

```yaml
# 方案：emptyDir + sidecar
volumes:
  - name: app-logs
    emptyDir: {}
containers:
  - name: app
    volumeMounts:
      - { name: app-logs, mountPath: /var/log/app }
  - name: log-shipper
    image: busybox
    args: [/bin/sh, -c, 'tail -F /var/log/app/*.log']
    volumeMounts:
      - { name: app-logs, mountPath: /var/log/app }
```

## 七、方案选型决策树

```text
                        ┌─ 集群 < 50 节点
                        │   └─ 简单架构：DaemonSet + 直连后端
                        │
                        ├─ 集群 50–500 节点
                        │   └─ 稳态架构：DaemonSet + Kafka + 多路分发
                        │
                        ├─ 集群 > 500 节点或多集群
                        │   └─ 联邦架构：每集群独立 Kafka，中央聚合
                        │
                        ├─ 必须全文检索
                        │   └─ 后端选 ES / SLS
                        │
                        ├─ 成本敏感 + 主要是 K8s 元数据检索
                        │   └─ 后端选 Loki（标签查询便宜）
                        │
                        └─ 业务日志格式不可控 / 必须自定义处理
                            └─ 方案 B（Sidecar）
```

## 八、踩坑清单

| 现象 | 原因 |
| --- | --- |
| Pod 重启后日志"丢一段" | Agent 用普通 `cat` 不用 `tail`，要 `pos.db` |
| 后端压力突然被打满 | Agent 没限速 + 没 buffer——加 `storage.total_limit_size` |
| 某些节点日志采不到 | DaemonSet 没调度到（如 taint）；节点 selector 写错 |
| ES 索引越来越大 | 没配 ILM / 索引生命周期；要按日期 rollover |
| Loki 查不到日志 | 标签名拼错 / 时区不一致 / batch 太大被 429 |
| 时延高（>1min） | buffer 设太大 / 后端写入慢 / 网络问题 |
| 日志里有明文密码 | 没脱敏——加 filter 或业务侧处理 |
| 日志全在但没 trace_id | 业务没接 OpenTelemetry；日志 / Trace / Metric 必须一起规划 |
| 节点 OOM 把 agent 杀了 | 没设 `resources.limits`，kubelet OOM 优先级被砍 |

## 九、最佳实践

1. **业务**一律打 **JSON 到 stdout**，格式统一：ts / level / msg / trace_id
2. **Agent 用 DaemonSet**，不要每 Pod 一个 Sidecar（除非必须）
3. **生产后端必带 buffer**：Agent 内存 + 磁盘双层 buffer
4. **日志分级**：ERROR 单独标签 / 单独通道 → 告警
5. **链路打通**：日志带 `trace_id`、指标带 `pod`、trace 自动关联 → 排障三件套
6. **资源限制**：DaemonSet 的 `requests` 必须设，`limits` 给到 2–3× 留 buffer 余量
7. **敏感信息**：日志在业务侧脱敏，不依赖 Agent 正则（漏掉就是事故）
8. **监控 Agent 自己**：Agent 挂了 = 整个节点日志断流，要监控 Agent 的健康（心跳 / lag）
9. **保留期分层**：热 / 温 / 冷三级，省钱
10. **CI 卡格式**：禁止 `println` 进 stdout——`grep -r 'fmt.Print\|System.out\|console.log' src/` 进 pre-commit
