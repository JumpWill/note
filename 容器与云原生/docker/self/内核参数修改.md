# 容器内核参数修改（sysctl）

> 本文档系统讲解容器（特别是特权容器）中 Linux 内核参数（`sysctl`）的修改：哪些可以修改、哪些受限制、作用范围，以及如何通过 runc 自定义单个容器的内核参数。

## 一、容器与内核参数概述

### 什么是 sysctl

**sysctl** 是 Linux 提供的**运行时内核参数调整接口**，通过 `/proc/sys/` 虚拟文件系统暴露。

```text
/proc/sys/
├── kernel/             # 内核通用参数
│   ├── pid_max
│   ├── threads-max
│   └── ...
├── net/                # 网络参数
│   ├── ipv4/ip_forward
│   ├── ipv4/tcp_keepalive_time
│   └── ...
├── vm/                 # 虚拟内存参数
│   ├── dirty_ratio
│   ├── swappiness
│   └── ...
├── fs/                 # 文件系统参数
│   ├── file-max
│   ├── inode-max
│   └── ...
└── net.core.somaxconn   # 跨子系统参数
```

### 容器中为什么需要修改内核参数

```text
1. 网络性能调优
   - net.core.somaxconn（socket 最大连接数）
   - net.ipv4.tcp_tw_reuse（TIME_WAIT 复用）

2. 内核行为调优
   - kernel.shmmax（共享内存最大值）
   - kernel.msgmax（消息队列最大值）

3. 文件系统调优
   - fs.file-max（最大文件描述符）
   - fs.inode-max（最大 inode 处理数）

4. 性能优化
   - vm.dirty_ratio（脏页比例）
   - vm.swappiness（swap 倾向）

5. 业务需求
   - Java 应用需要大共享内存
   - 数据库需要高 fd 上限
   - 高并发服务需要调大 backlog
```

### 容器内核参数的两层空间

```text
┌─────────────────────────────────────────────────────────┐
│                    宿主机内核空间                        │
│   /proc/sys/  实际的内核参数                            │
│   - fs.file-max: 1000000                                │
│   - net.ipv4.ip_forward: 1                              │
└─────────────────────────────────────────────────────────┘
       ↑                              ↑
       │                              │
┌──────────────┐              ┌──────────────┐
│   容器 1     │              │   容器 2     │
│  (特权)      │              │  (非特权)    │
│              │              │              │
│ /proc/sys/   │              │ /proc/sys/   │
│ 可见宿主     │              │ 隔离的视图   │
│ 全部参数     │              │ 受限的子集   │
└──────────────┘              └──────────────┘
```

## 二、特权容器 vs 普通容器

### 特权容器（Privileged Container）

```yaml
# Docker 运行特权容器
docker run -d --name priv \
  --privileged \
  --network host \
  nginx:alpine

# K8s 运行特权 Pod
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: priv
    image: nginx:alpine
    securityContext:
      privileged: true
```

**特权容器的特性**：

```text
特权容器获得几乎所有 Linux capabilities：
  - CAP_SYS_ADMIN        系统管理
  - CAP_SYS_PTRACE       调试进程
  - CAP_NET_ADMIN        网络管理
  - CAP_SYS_MODULE       加载内核模块
  - CAP_SYS_RAWIO        原始 I/O
  - ... （几乎全部 40+ capabilities）

可以访问设备：
  /dev/  下几乎所有设备
  /dev/mem     物理内存
  /dev/sda     磁盘
  /dev/kmsg    内核日志
```

### 普通容器 vs 特权容器对比

| 维度 | 普通容器 | 特权容器 |
|------|---------|---------|
| **Capabilities** | 默认少量（CHOWN、SETUID、NET_BIND_SERVICE） | 几乎全部 40+ |
| **设备访问** | 受限（mknod 受限） | 完全访问 /dev |
| **挂载权限** | 不能挂载敏感文件系统 | 可挂载任何东西 |
| **网络配置** | 受限（不能改路由表） | 完全访问 |
| **内核参数** | 受限（白名单 sysctls） | 可修改大部分 |
| **安全风险** | 低 | **高**（等同宿主机 root） |

### 普通容器的内核参数隔离

```text
普通容器启动时：
  1. 容器内的 /proc/sys 是宿主的只读视图
  2. 只有安全白名单中的 sysctl 可以修改
  3. 其他 sysctl 不可见或只读

例如：
  容器内执行：sysctl net.ipv4.ip_forward
  结果：只读，不能修改（即使 root 用户）

  容器内执行：sysctl kernel.shmmax
  结果：受限于 seccomp 规则
```

### 2. K8s 中按命名空间配置

```yaml
# kubelet 配置（/var/lib/kubelet/config.yaml）
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# 默认允许的非安全 sysctl
allowedUnsafeSysctls:
  - kernel.msg*
  - kernel.sem
  - kernel.shm*
  - fs.mqueue.*

# 完全禁用非安全 sysctl（推荐）
allowedUnsafeSysctls: []
```

### 3. Pod 中配置 sysctl

```yaml
# 安全 sysctl（默认允许）
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-demo
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"
      - name: net.ipv4.tcp_syn_retries
        value: "3"
  containers:
  - name: app
    image: nginx
```

```yaml
# 非安全 sysctl（需要 kubelet 配置允许）
apiVersion: v1
kind: Pod
metadata:
  name: unsafe-sysctl
  annotations:
    sysctls: "kernel.shmmax=2147483648"
spec:
  securityContext:
    sysctls:
      - name: kernel.shmmax
        value: "2147483648"
  containers:
  - name: app
    image: java-app
```

### 4. 完整可修改 sysctl 列表（容器内验证）

```bash
# 在容器内查看可修改的 sysctl
# 普通容器（Docker run）：
docker run --rm alpine sh -c '

  done | head -40

# 特权容器（可访问所有 sysctl）：
docker run --rm --privileged alpine sh -c '
  ls /proc/sys/
'
```

## 四、容器中不可修改的内核参数

### 1. 受限制的 sysctl 分类

```text
以下 sysctl 默认禁止在容器中修改：

1. 内核通用（kernel.*）
   - kernel.msgmax         系统消息队列最大值
   - kernel.msgmnb         单队列最大字节
   - kernel.msgmni         消息队列标识符最大值
   - kernel.shmmax         共享内存段最大值
   - kernel.shmmni         共享内存段标识符最大值
   - kernel.shmall         共享内存总量

2. 文件系统（fs.*）
   - fs.aio-max-nr         异步 I/O 最大数
   - fs.mqueue.*           POSIX 消息队列
   - fs.nr_open            单进程最大 fd

3. 网络特殊（net.* 限部分）
   - net.ipv4.ip_forward           路由转发（隔离）
   - net.ipv4.conf.*.rp_filter     反向路径过滤
   - net.ipv4.tcp_syncookies       SYN cookies

4. 虚拟内存（vm.*）
   - vm.overcommit_memory          内存超额分配
   - vm.overcommit_ratio           超额分配比例
   - vm.panic_on_oom               OOM 时 panic
   - vm.zone_reclaim_mode          NUMA 回收
```

### 2. 不可修改的原因

```text
1. 安全风险
   - 允许修改 net.ipv4.ip_forward 可让容器路由流量
   - 允许修改 kernel.shmmax 可消耗宿主内存

2. 隔离破坏
   - 修改影响宿主机全局
   - 破坏 cgroup 隔离

3. 稳定性风险
   - 不当修改可导致系统崩溃
   - 影响所有容器和宿主机
```

### 3. 容器内修改被限制参数的实际表现

```bash
# 在普通容器内尝试修改 net.ipv4.ip_forward
docker run -d --name test alpine sleep 3600
docker exec test sysctl -w net.ipv4.ip_forward=1
# sysctl: setting key "net.ipv4.ip_forward": Read-only file system

# 在普通容器内尝试修改 kernel.shmmax
docker exec test sysctl -w kernel.shmmax=2147483648
# sysctl: setting key "kernel.shmmax": Read-only file system

# 在普通容器内读取
docker exec test cat /proc/sys/kernel/shmmax
# 18446744073709551615  ← 与宿主机相同，但只读
```

### 4. 限制机制（seccomp + namespace）

```text
容器如何限制 sysctl 修改：

1. seccomp profile
   - Docker 默认 seccomp profile 拒绝 sysctl 系统调用
   - 只有特权容器（--privileged）才允许

2. Mount namespace
   - /proc/sys 是 bind mount（只读）
   - 容器看到的是 namespace 隔离的视图

3. User namespace（rootless 容器）
   - 非 root 用户看不到特权路径

4. Capabilities
   - CAP_SYS_ADMIN 才能修改大部分 sysctl
   - 普通容器默认没有
```

## 五、内核参数的生效范围

### 1. sysctl 范围分类

```text
Linux sysctl 按作用域分为四类：

1. 进程级（Process）
   - 影响单个进程
   - 例子：kernel.random.entropy_avail
   - 容器内修改不影响其他进程

2. 线程级（Thread）
   - 影响单线程
   - 例子：kernel.sched_child_runs_first
   - 容器内修改不影响其他线程

3. 命名空间级（Namespace）
   - 影响整个 namespace（容器/Pod）
   - 例子：net.ipv4.ip_forward
   - 容器内修改只影响本容器

4. 系统级（System-wide / Global）
   - 影响整个系统
   - 例子：kernel.shmmax、fs.file-max
   - 容器内修改会修改宿主机参数（特权容器）
```

### 2. 普通容器 vs 特权容器的生效范围

```text
┌─────────────────────────────────────────────────────────┐
│              宿主机内核参数                              │
│   /proc/sys/kernel/shmmax = 18446744073709551615       │
└─────────────────────────────────────────────────────────┘
       ↑                              ↑
       │ 共享系统级参数                │
┌──────────────┐              ┌──────────────┐
│   容器 1     │              │   容器 2     │
│  (普通容器)  │              │ (特权容器)   │
│              │              │              │
│ 查看：       │              │ 查看：       │
│ 18446...     │              │ 18446...     │
│              │              │              │
│ 修改 net.*  │              │ 修改 net.*  │
│ 仅本容器生效 │              │ 仅本容器生效 │
│              │              │              │
│ 修改 kernel. │              │ 修改 kernel. │
│ 失败（只读） │              │ 成功→改全局  │
└──────────────┘              └──────────────┘
```

### 3. K8s 中的特殊行为

```yaml
# 安全 sysctl（命名空间级）
# 修改只影响当前 Pod 所在的网络命名空间
apiVersion: v1
kind: Pod
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"
  containers:
  - name: app
```

```text
K8s Pod 中 sysctl 修改规则：

1. 安全 sysctl（白名单内）
   - 命名空间级，只影响当前 Pod
   - Pod 删除后参数消失
   - 不影响宿主机或其他 Pod

2. 非安全 sysctl（需 kubelet 配置）
   - 节点级，影响整个节点
   - 多个 Pod 修改可能冲突
   - 危险操作

3. Pod 网络命名空间
   - net.* sysctl 修改作用于 Pod 的网络 NS
   - 不影响宿主机网络配置
```

### 4. 容器间 sysctl 共享情况

```text
普通容器：
  - 容器 A 修改 net.core.somaxconn = 2048
  - 容器 B 看到的仍然是 1024（默认值）
  - 各自隔离的命名空间

特权容器：
  - 容器 A 修改 kernel.shmmax = 10G
  - 宿主机和其他特权容器都看到 10G
  - 共享系统级参数

Pod 共享网络命名空间（Pod 内多容器）：
  - 这些容器看到的 net.* sysctl 相同
  - 修改会影响 Pod 内所有容器
```

## 六、runC 自定义容器内核参数

### 1. runC 概述

**runC**（OCI Runtime）是 Docker、containerd、Podman 等容器运行时的底层实现，遵循 OCI 规范。

```text
OCI 容器运行时生态：

┌─────────────────────────┐
│     Docker / Podman      │  ← 用户接口
└──────────┬──────────────┘
           │
┌──────────▼──────────────┐
│      containerd          │  ← 容器守护进程
└──────────┬──────────────┘
           │
┌──────────▼──────────────┐
│       runC / crun       │  ← OCI Runtime（实际创建容器）
└──────────┬──────────────┘
           │
┌──────────▼──────────────┐
│    Linux 内核 + cgroup  │
└─────────────────────────┘
```

### 2. OCI Runtime Spec 中的 sysctl

OCI Runtime Spec 通过 `linux.sysctl` 属性设置容器 sysctl。

```json
{
  "ociVersion": "1.0.2",
  "process": {
    "user": {
      "uid": 0,
      "gid": 0
    },
    "args": [
      "/bin/sh"
    ],
    "env": [
      "PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
    ],
    "cwd": "/"
  },
  "root": {
    "path": "rootfs"
  },
  "linux": {
    "sysctl": {
      "net.ipv4.ip_forward": "0",
      "net.ipv4.tcp_keepalive_time": "300",
      "kernel.shmmax": "2147483648",
      "kernel.shmmni": "4096"
    }
  }
}
```

### 3. Docker runC 实际配置路径

#### 路径 1：Docker CLI --sysctl 参数（普通容器）

```bash
# Docker 20.10+
docker run -d \
  --name sysctl-demo \
  --sysctl net.core.somaxconn=1024 \
  --sysctl net.ipv4.tcp_keepalive_time=300 \
  nginx:alpine

# 在容器内验证
docker exec sysctl-demo sysctl net.core.somaxconn
# net.core.somaxconn = 1024
```

**限制**：Docker CLI 的 `--sysctl` 只能修改**安全白名单**中的参数。

#### 路径 2：Docker 配置文件添加 sysctl（特权容器）

```json
# /etc/docker/daemon.json
{
  "default-runtime-opts": {
    "sysctl": {
      "net.core.somaxconn": "1024",
      "kernel.shmmax": "2147483648"
    }
  }
}
```

```bash
sudo systemctl restart docker
```

#### 路径 3：runC 直接创建容器（最灵活）

```bash
# 1. 准备 rootfs
mkdir /tmp/mycontainer/rootfs
docker export $(docker create nginx:alpine) | tar -C /tmp/mycontainer/rootfs

# 2. 创建 config.json
cat > /tmp/mycontainer/config.json << 'EOF'
{
  "ociVersion": "1.0.2",
  "process": {
    "user": { "uid": 0, "gid": 0 },
    "args": ["/bin/sh"],
    "env": [
      "PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
    ],
    "cwd": "/",
    "capabilities": {
      "bounding": ["CAP_SYS_ADMIN"],
      "effective": ["CAP_SYS_ADMIN"],
      "permitted": ["CAP_SYS_ADMIN"]
    }
  },
  "root": { "path": "rootfs" },
  "mounts": [
    {
      "destination": "/proc",
      "type": "bind",
      "source": "/proc",
      "options": ["rbind", "nosuid", "noexec", "nodev", "ro"]
    }
  ],
  "linux": {
    "sysctl": {
      "net.ipv4.ip_forward": "0",
      "net.core.somaxconn": "65535",
      "kernel.shmmax": "2147483648",
      "kernel.shmmni": "4096",
      "vm.swappiness": "10",
      "net.ipv4.tcp_max_syn_backlog": "65535"
    }
  }
}
EOF

# 3. 用 runC 启动容器
cd /tmp/mycontainer
runc run mycontainer

# 在容器内验证
cat /proc/sys/kernel/shmmax
# 2147483648  ← 自定义值生效

cat /proc/sys/net/core/somaxconn
# 65535
```

### 4. runC 配置参数详解

```json
{
  "linux": {
    "sysctl": {
      "key1": "value1",
      "key2": "value2"
    }
  }
}
```

```text
关键点：
  1. sysctl 是对象而不是数组
  2. value 必须是字符串（即使是数字）
  3. 参数必须在内核中存在
  4. 非特权容器只能修改白名单参数
  5. 特权容器（带 CAP_SYS_ADMIN）可以修改大部分参数
```

### 5. 通过 containerd 配置

```toml
# /etc/containerd/config.toml
version = 2

[plugins."io.containerd.grpc.v1.cri"]
  [plugins."io.containerd.grpc.v1.cri".containerd]
    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
        runtime_type = "io.containerd.runc.v2"
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
          # 自定义 sysctl（容器创建时生效）
          # 注意：runc 1.1.0+ 支持
          # 这里通过 seccomp profile 或 OCI hook 实现
```

```yaml
# 通过 K8s Pod securityContext 配置 sysctl
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-custom
  annotations:
    sysctls: "kernel.shmmax=2147483648,kernel.shmmni=4096"
spec:
  securityContext:
    sysctls:
    - name: kernel.shmmax
      value: "2147483648"
    - name: kernel.shmmni
      value: "4096"
  containers:
  - name: app
    image: java-app
    securityContext:
      privileged: true    # 必需，用于非安全 sysctl
```

```bash
# 语法
```

## 八、K8s 自定义 Pod 内核参数

### 1. 安全 sysctl（推荐）

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: safe-sysctl
spec:
  securityContext:
    sysctls:
      # 这些 sysctl 是安全白名单
      - name: net.core.somaxconn
        value: "1024"
      - name: net.ipv4.tcp_keepalive_time
        value: "300"
      - name: net.ipv4.tcp_max_syn_backlog
        value: "65535"
      - name: net.core.rmem_max
        value: "26214400"
      - name: net.core.wmem_max
        value: "26214400"
  containers:
  - name: app
    image: nginx
```

### 2. 非安全 sysctl（需开启）

```bash
# 1. 修改 kubelet 配置
cat > /var/lib/kubelet/config.yaml << 'EOF'
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
allowedUnsafeSysctls:
  - kernel.msg*
  - kernel.sem
  - kernel.shm*
  - fs.mqueue.*
EOF

systemctl restart kubelet
```

```yaml
# 2. Pod 中使用（带警告）
apiVersion: v1
kind: Pod
metadata:
  name: unsafe-sysctl
  annotations:
    sysctls: "kernel.shmmax=2147483648,kernel.shmmni=4096"
spec:
  securityContext:
    sysctls:
      - name: kernel.shmmax
        value: "2147483648"
      - name: kernel.shmmni
        value: "4096"
  containers:
  - name: app
    image: java-app
    securityContext:
      # 非安全 sysctl 需要特权模式
      privileged: true
```

### 3. 通过 Pod Security Standards 控制

```yaml
# restricted 策略：禁止所有 sysctl
# baseline 策略：只允许安全 sysctl
# privileged 策略：允许所有

apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: PodSecurity
  configuration:
    apiVersion: pod-security.admission.config.k8s.io/v1
    kind: PodSecurityConfiguration
    defaults:
      enforce: "restricted"
      audit: "restricted"
      warn: "restricted"
    exemptions:
      usernames: []
      runtimeClasses: []
      namespaces: [kube-system]
```

## 十、安全考虑与最佳实践

### 1. 安全风险

```text
特权容器的安全风险：

1. 容器逃逸
   - 特权容器获得几乎所有 capabilities
   - 攻击者可挂载宿主机文件系统
   - 攻击者可访问宿主机设备

2. 内核破坏
   - 可加载内核模块
   - 可修改内核参数（系统级）
   - 可能导致系统崩溃

3. 数据泄露
   - 可读取宿主机任意文件
   - 可访问其他容器数据

4. 网络攻击
   - 可开启 IP 转发进行 MITM
   - 可修改网络配置
```

### 2. 最佳实践

```text
1. 避免使用特权容器
   - 仅在必要时使用 --privileged
   - 使用更细粒度的 capabilities
   - 优先使用安全 sysctl 白名单

2. 使用 K8s 安全策略
   - 启用 PodSecurity Standards restricted
   - 设置 allowedUnsafeSysctls 为空
   - 使用 PodSecurityPolicy / OPA Gatekeeper

3. 监控 sysctl 修改
   - audit log 记录 sysctl 修改
   - 检测异常修改（kernel.shmmax 突然变小等）
   - 关联告警

4. 备份与恢复
   - 修改前备份原值
   - 文档化修改目的
   - 准备回滚方案

5. 测试验证
   - 在测试环境验证 sysctl 生效
   - 性能测试确认效果
   - 监控容器稳定性
```

### 3. 审计检查

```bash
# 查看 Pod 安全配置
kubectl get pod -A -o json | \
  jq '.items[] | select(.spec.securityContext.privileged==true) | 
  {name: .metadata.name, namespace: .metadata.namespace}'

# 查看 Pod 的 sysctl 配置
kubectl get pod -A -o json | \
  jq '.items[] | select(.spec.securityContext.sysctls) | 
  {name: .metadata.name, sysctls: .spec.securityContext.sysctls}'
```

## 十一、核心要点速记

### sysctl 三大维度速记

```
维度 1：是否可以修改
  - 安全白名单 → 普通容器可修改
  - 非安全 → 特权容器或 kubelet 配置后可修改
  - 系统级 → 容器修改影响宿主机

维度 2：作用范围
  - 进程级 → 仅影响本进程
  - 命名空间级 → 影响本 Pod / 容器
  - 系统级 → 影响整个宿主机

维度 3：实现方式
  - Docker run --sysctl
  - K8s Pod securityContext.sysctls
  - runC config.json linux.sysctl
  - 容器运行时配置（containerd 配置）
```

### 普通容器 vs 特权容器

```
普通容器：
  - 默认 capabilities（少）
  - sysctl 白名单
  - /proc/sys 只读视图
  - 安全优先

特权容器：
  - 几乎所有 capabilities
  - 可修改大部分 sysctl
  - 可访问宿主机设备
  - 功能优先（牺牲安全）
```

### 可修改 sysctl 分类速记

```
安全白名单（普通容器）：
  - net.* （网络参数）
  - 少量 vm.* 和 fs.*

需 kubelet 配置（非安全）：
  - kernel.msg*
  - kernel.sem
  - kernel.shm*
  - fs.mqueue.*

默认禁止：
  - kernel.shmmax 等（系统级）
  - vm.overcommit_memory（全局）
  - net.ipv4.ip_forward（网络路由）
```

### runC 自定义 sysctl

```json
{
  "linux": {
    "sysctl": {
      "key1": "value1",
      "key2": "value2"
    }
  }
}
```

```text
关键点：
  1. 必须有 CAP_SYS_ADMIN 能力
  2. 必须挂载 /proc 为 rbind
  3. value 必须是字符串
  4. key 必须存在于内核
```

### K8s 配置方式

```yaml
# 安全 sysctl
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"

# 非安全 sysctl（需配置）
# 1. kubelet 加 allowedUnsafeSysctls
# 2. Pod 设 securityContext.sysctls
# 3. 通常需要 privileged: true
```

### 一句话总结

```
特权容器可以修改大部分 sysctl
普通容器只能修改安全白名单
sysctl 修改范围：
  - 网络级 → 仅影响本容器
  - 系统级 → 影响整个宿主机（特权）
配置方式：
  - Docker --sysctl
  - K8s securityContext.sysctls
  - runC config.json
```

### 速查表

| 方式 | 命令 | 限制 |
|------|------|------|
| Docker run | `--sysctl key=value` | 仅安全白名单 |
| Docker daemon | daemon.json + sysctl | 所有参数 |
| Docker Compose | sysctls 字段 | 仅安全白名单 |
| K8s 安全 | securityContext.sysctls | 仅安全白名单 |
| K8s 非安全 | kubelet allowedUnsafeSysctls | 所有参数 |
| runC | config.json linux.sysctl | 所有参数 |

### 最佳实践

```
1. 优先使用安全 sysctl（白名单内）
2. 必须用非安全时：
   - 严格审查必要性
   - kubelet 加 allowedUnsafeSysctls
   - Pod 设 securityContext
   - 容器通常需要 privileged: true
3. 优先使用 runC config.json 定制单个容器
4. 测试环境验证后再生产
5. 监控和审计
```
