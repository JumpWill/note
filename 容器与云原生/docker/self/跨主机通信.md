## 一、为什么需要跨主机通信

### 1.1 单主机 vs 跨主机

```text
┌─────────────────────────────────────────────────────────────┐
│                  单主机容器通信                                  │
│                                                              │
│   ┌─────────┐  veth  ┌─────────┐  bridge ┌─────────┐     │
│   │ Container│───────│ docker0  │────────│ Container│     │
│   │  172.17  │       │  172.17  │        │  172.17  │     │
│   │   .0.2   │       │   .0.1   │        │   .0.3   │     │
│   └─────────┘        └─────────┘        └─────────┘     │
│                                                              │
│   ✓ 简单: docker0 bridge 自动转发                              │
│   ✗ 限制: 只能在一台主机内                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ 跨主机
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                  跨主机容器通信                                  │
│                                                              │
│   主机 A (192.168.1.10)            主机 B (192.168.1.20)     │
│   ┌─────────┐                  ┌─────────┐                  │
│   │ Container│   网络隧道/VXLAN  │Container│                  │
│   │10.244.0.2│◄──────────────►│10.244.1.2│                  │
│   └────┬────┘                  └────┬────┘                  │
│        │ eth0                      │ eth0                    │
│   ┌────▼──────────────────────────────▼─────────────────┐  │
│   │         overlay network (192.168.1.0/24)              │  │
│   └───────────────────────────────────────────────────────┘  │
│                                                              │
│   ✗ 难点: 容器 IP 互通、跨主机网络抽象、性能                       │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 跨主机通信的三大挑战

```text
1. IP 寻址
   - 容器 IP 在不同主机不能冲突
   - 需要统一地址规划

2. 数据转发
   - 不同主机之间的容器如何互通
   - 性能损耗 vs 灵活性

3. 服务发现
   - 容器 IP 动态变化
   - 需要稳定的访问入口
```

## 二、底层基础:Linux 网络命名空间

### 2.1 Network Namespace 隔离

```text
┌─────────────────────────────────────────────────────────────┐
│                  Linux Network Namespace                      │
│                                                              │
│  默认 Network Namespace (Host)                                │
│  ┌────────────────────────────────────────┐                 │
│  │  eth0  (192.168.1.10)                   │                 │
│  │  lo    (127.0.0.1)                       │                 │
│  │  route table                            │                 │
│  └────────────────────────────────────────┘                 │
│                                                              │
│  ┌─────────────────────────────────────┐  ┌──────────────┐ │
│  │ Container Netns 1                     │  │Container Netns│ │
│  │  eth0 → veth1 → docker0              │  │ 2            │ │
│  │  172.17.0.2                          │  │  eth0 → veth2 │ │
│  │  lo 127.0.0.1                         │  │  172.17.0.3  │ │
│  └─────────────┬───────────────────────┘  └──────┬───────┘ │
│                │                                 │         │
│                └────────────┬────────────────────┘         │
│                             │                              │
│                        docker0 bridge                       │
│                       172.17.0.1                           │
└─────────────────────────────────────────────────────────────┘

每个 Netns 拥有:
  - 独立的网卡 (eth0)
  - 独立的路由表
  - 独立的 iptables 规则
  - 独立的 socket
```

### 2.2 veth pair (虚拟以太网对)

```text
veth pair 是跨 netns 的"网线":

  Container Netns 1              Host Netns
  ┌──────────────────┐           ┌──────────────────┐
  │                  │           │                  │
  │  eth0 (172.17.0.2)│◄────────►│ vethxxx (172.17.0.4)│
  │                  │  veth pair │                  │
  └──────────────────┘           └──────────────────┘

veth 特性:
  - 成对出现,一端在容器,一端在 Host
  - 一端发出,另一端接收
  - 类似"虚拟网线"
  - docker0 / cbr0 网桥连接 veth 和物理网卡
```

### 2.3 bridge (Linux 网桥)

```text
bridge (网桥) 是 L2 交换机,连接多个网络:

  ┌────────────────────────────────────────┐
  │           docker0 / cbr0 桥              │
  │                                         │
  │  ┌──────┐  ┌──────┐  ┌──────┐          │
  │  │ veth1│  │ veth2│  │ veth3│          │
  │  └─┬────┘  └─┬────┘  └─┬────┘          │
  └────┼─────────┼─────────┼─────────────┘
       │         │         │
   Container  Container  Container
      A         B         C

bridge 工作原理:
  - 学习 MAC 地址表
  - 同一 bridge 内转发
  - 不同 bridge 隔离
```

## 三、Docker 跨主机通信方案

### 3.1 方案概览

```text
Docker 跨主机通信方案对比:

┌──────────────────┬──────────────┬──────────────┬──────────────┐
│      方案          │   性能       │   复杂度     │   适用场景   │
├──────────────────┼──────────────┼──────────────┼──────────────┤
│ Host 网络          │ 最高 (无开销) │ 简单         │ 监控 Agent    │
│ macvlan / ipvlan │ 高 (直连网络) │ 中           │ 传统应用     │
│ Overlay 网络      │ 中 (封装开销) │ 中           │ Swarm 集群   │
│ 自定义网络方案     │ 视方案而定   │ 高           │ 大规模生产   │
│ Flannel / Calico  │ 中           │ 高           │ 跨主机生产   │
└──────────────────┴──────────────┴──────────────┴──────────────┘
```

### 3.2 Host 网络模式 (性能最高)

```text
Host 网络模式: 容器直接使用 Host 网络栈

  主机 A (192.168.1.10)              主机 B (192.168.1.20)
  ┌──────────────────┐               ┌──────────────────┐
  │ Container         │               │ Container         │
  │ Netns: share host │    主机网络   │ Netns: share host │
  │  IP: 192.168.1.10│◄─────────────►│  IP: 192.168.1.20│
  │  Port: 8080       │               │  Port: 9090       │
  └──────────────────┘               └──────────────────┘

# 命令
docker run --network host nginx
# 容器直接使用宿主 IP 和端口

优点:
  - 零网络开销
  - 性能最优

缺点:
  - 端口冲突
  - 无网络隔离
  - 不安全
```

### 3.3 macvlan 网络模式

```text
macvlan: 给容器分配独立的 MAC 地址,像物理机一样接入网络

              Switch / 路由器
                     │
        ┌────────────┼────────────┐
        │            │            │
   ┌────▼───┐  ┌────▼───┐  ┌────▼───┐
   │ Host A │  │ Host B │  │  Router │
   │ eth0.10│  │ eth0.20│  └────────┘
   │MAC:AA..│  │MAC:BB..│
   │ IP:    │  │ IP:    │
   │10.0.0.10│  │10.0.0.20│
   └────────┘  └────────┘

# 创建 macvlan 网络
docker network create -d macvlan \
  --subnet=10.0.0.0/24 \
  --gateway=10.0.0.1 \
  -o parent=eth0 \
  my-macvlan

# 启动容器
docker run --network my-macvlan nginx
# 容器获得独立 MAC 和 IP,看起来像独立机器

优点:
  - 容器有独立 IP (像虚拟机)
  - 无 NAT 性能损耗
  - 传统应用兼容

缺点:
  - 需要交换机支持混杂模式
  - 消耗 MAC 地址
  - 跨主机需二层连通
```

### 3.4 ipvlan 网络模式

```text
ipvlan: 类似 macvlan,但共用 MAC 地址

  ┌──────────────────────────────────┐
  │  Host eth0 (MAC: AA:BB:CC:DD:EE:FF) │
  │                                  │
  │  ┌────────────────────────────┐ │
  │  │  Container 1                 │ │
  │  │  IP: 10.0.0.10              │ │
  │  │  MAC: AA:BB:CC:DD:EE:FF (共用)│ │
  │  └────────────────────────────┘ │
  │                                  │
  │  ┌────────────────────────────┐ │
  │  │  Container 2                 │ │
  │  │  IP: 10.0.0.11              │ │
  │  │  MAC: AA:BB:CC:DD:EE:FF (共用)│ │
  │  └────────────────────────────┘ │
  └──────────────────────────────────┘

ipvlan 模式:
  - L2: 共享父接口 MAC
  - L3: 父接口处理路由,容器有独立 IP
  - 不消耗 MAC 地址

优点: 解决 macvlan 的 MAC 耗尽问题
缺点: 不支持混杂模式的交换机会拒绝
```

### 3.5 Overlay 网络模式 (Swarm)

```text
Overlay 网络: Docker Swarm 的默认跨主机方案

  Host A (10.0.0.10)                     Host B (10.0.0.20)
  ┌─────────────────────┐              ┌─────────────────────┐
  │ Swarm Node            │              │ Swarm Node            │
  │ ┌─────────────────┐ │              │ ┌─────────────────┐ │
  │ │ Container        │ │              │ │ Container        │ │
  │ │ IP: 10.0.0.2     │ │              │ │ IP: 10.0.0.3     │ │
  │ └────────┬────────┘ │              │ └────────┬────────┘ │
  │          │          │              │          │          │
  │  ┌───────▼──────┐   │   VXLAN      │  ┌───────▼──────┐   │
  │  │  Overlay     │◄────────────────►│  │  Overlay     │   │
  │  │  Network     │   Tunnel (UDP)  │  │  Network     │   │
  │  └──────────────┘   │   Port 4789  │  └──────────────┘   │
  └─────────────────────┘              └─────────────────────┘

# 初始化 Swarm
docker swarm init
docker swarm join --token <token>

# 创建 overlay 网络
docker network create -d overlay my-overlay

# 启动服务
docker service create --network my-overlay --name web nginx
docker service create --network my-overlay --name api my-api

原理:
  - 每个 Swarm Node 都有 Overlay 网桥 (Gossip 协议)
  - 跨主机通过 VXLAN 隧道 (UDP 4789)
  - 容器间通过 DNS 服务发现
```

### 3.6 Overlay 网络详解

```text
Overlay 网络详细结构:

  Host A                                    Host B
  ┌────────────────────────┐              ┌────────────────────────┐
  │ 物理网卡 eth0 (10.0.0.10)│              │ 物理网卡 eth0 (10.0.0.20)│
  │        │                 │              │        │                 │
  │  ┌─────▼────────────┐    │              │  ┌─────▼────────────┐    │
  │  │  docker_gwbridge  │    │              │  │  docker_gwbridge  │    │
  │  │  (172.18.0.1)     │    │              │  │  (172.18.0.1)     │    │
  │  └────────┬─────────┘    │              │  └────────┬─────────┘    │
  │           │              │              │           │              │
  │  ┌────────▼─────────┐    │  VXLAN UDP   │  ┌────────▼─────────┐    │
  │  │   overlay netns  │◄────────────────►│  │   overlay netns  │    │
  │  │  10.0.1.0/24     │   Port 4789     │  │  10.0.1.0/24     │    │
  │  └────────┬─────────┘    │              │  └────────┬─────────┘    │
  │           │              │              │           │              │
  │  ┌────────▼─────────┐    │              │  ┌────────▼─────────┐    │
  │  │  service_netns   │    │              │  │  service_netns   │    │
  │  │  Container A     │    │              │  │  Container B     │    │
  │  │  10.0.1.5        │    │              │  │  10.0.1.8        │    │
  │  └──────────────────┘    │              │  └──────────────────┘    │
  └────────────────────────┘              └────────────────────────┘

三层网络:
  1. 物理网络 (10.0.0.0/24) - Host 互通
  2. Overlay 网络 (10.0.1.0/24) - 容器互通 (VXLAN 封装)
  3. 服务网络 - 单个 Service 内部通信

VXLAN 封装:
  原始包: [IP: 10.0.1.5 → IP: 10.0.1.8] [TCP]
  封装后: [UDP 4789, 10.0.0.10 → 10.0.0.20] [IP: 10.0.1.5 → IP: 10.0.1.8] [TCP]
```

### 3.7 自定义 Overlay 网络 (生产方案)

```text
常见自定义方案:

1. Flannel (简单 Overlay)
   ┌─────────────────────────────────────┐
   │  Host A            Host B            │
   │  ┌──────┐         ┌──────┐          │
   │  │flan- │ VXLAN   │flan- │          │
   │  │nel   │ Tunnel  │nel   │          │
   │  └──────┘         └──────┘          │
   └─────────────────────────────────────┘
   - flanneld 在每台机器
   - 后端: vxlan / host-gw / udp
   - 简单易用

2. Calico (BGP / VXLAN)
   ┌─────────────────────────────────────┐
   │  Host A            Host B            │
   │  ┌──────┐   BGP    ┌──────┐          │
   │  │cali- │◄──────►│cali- │          │
   │  │co    │         │co    │          │
   │  └──────┘         └──────┘          │
   └─────────────────────────────────────┘
   - calico-node 在每台机器
   - BGP 协议通告路由
   - 支持 NetworkPolicy
```

### 3.8 Docker 网络模式总结对比

| 模式 | 性能 | 隔离 | 跨主机 | 复杂度 | 推荐场景 |
|------|------|------|--------|--------|----------|
| bridge (默认) | 中 | 中 | ✗ | 低 | 单主机测试 |
| host | 最高 | 弱 | ✓ | 极低 | 监控 agent |
| overlay | 中 | 中 | ✓ | 中 | Swarm 集群 |
| macvlan | 高 | 强 | ✓ | 中 | 传统应用 |
| ipvlan | 高 | 强 | ✓ | 中 | 大量容器 |
| none | - | 强 | ✗ | 低 | 安全敏感 |
| 自定义(Flannel/Calico) | 中 | 强 | ✓ | 高 | K8s / 生产 |

## 四、Kubernetes 跨主机通信原理

### 4.1 K8s 网络模型三原则

```text
K8s 网络设计三原则 (Dan Williams):

1. 每个 Pod 都有独立 IP
   - Pod 之间无需 NAT 互通
   - 所有 Pod 可在同一扁平网络

2. 集群内任意 Pod 可访问任意 Pod
   - 不管在哪个节点
   - 不管使用什么 Service

3. Agent (kubelet) 可与本机 Pod 通信
   - 无 NAT/端口映射
```

### 4.2 K8s Pod 网络基础

```text
每个 Pod 内部:
  ┌─────────────────────────────────┐
  │           Pod                    │
  │  ┌─────────────┐  ┌──────────┐ │
  │  │   App        │  │   App     │ │  (单 Pod 多容器)
  │  │ Container A │  │Container B│ │
  │  │ eth0@netns  │  │eth0@netns│ │
  │  └──────┬──────┘  └────┬─────┘ │
  │         │ pause        │       │
  │         └─────┬───────┘       │
  │               │               │
  │         eth0 (共享网络命名空间) │
  │         IP: 10.244.1.5        │
  └─────────────┬───────────────────┘
                │ veth pair
        ┌───────▼───────┐
        │   cbr0/cni0   │  (节点网桥)
        │  10.244.0.0/16 │
        └───────┬───────┘
                │ 物理网卡
        ┌───────▼───────┐
        │  eth0 (物理)  │
        │ 192.168.1.10  │
        └──────────────┘

每个 Pod 内部:
  - 共享 network namespace
  - 所有容器共享同一个 IP (Pod IP)
  - 通过 lo 互通
  - 通过 eth0 对外通信
```

### 4.3 K8s 跨主机通信全景

```text
                          K8s 集群
  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  Host A (worker-1)              Host B (worker-2)        │
  │  192.168.1.10                     192.168.1.20            │
  │  ┌──────────────┐                ┌──────────────┐         │
  │  │ cbr0 桥       │                │ cbr0 桥       │         │
  │  │ 10.244.1.0/24│                │ 10.244.2.0/24│         │
  │  └──────┬───────┘                └──────┬───────┘         │
  │         │                              │                │
  │  ┌──────▼─────┐                ┌──────▼─────┐           │
  │  │ Pod A      │                │ Pod B      │           │
  │  │ 10.244.1.5 │                │ 10.244.2.8 │           │
  │  └────────────┘                └────────────┘           │
  │         │                              │                │
  │  ┌──────▼─────┐                ┌──────▼─────┐           │
  │  │ eth0       │                │ eth0       │           │
  │  │ 物理网卡   │                │ 物理网卡   │           │
  │  └──────┬─────┘                └──────┬─────┘           │
  │         │                              │                │
  │         └──────────────┬───────────────┘                │
  │                         │                               │
  │                    物理交换机                           │
  │                                                            │
  │  关键问题: Pod A 怎么访问 Pod B (跨主机)?                    │
  └────────────────────────────────────────────────────────────┘
```

### 4.4 CNI 插件的作用

```text
CNI (Container Network Interface):

  kubelet 创建 Pod
       ↓
  kubelet 调用 CNI 插件 (例如 Calico)
       ↓
  CNI 插件负责:
    1. 创建网络命名空间
    2. 创建 veth pair
    3. 一端放入 Pod Netns (eth0)
    4. 另一端放入网桥 (cbr0/cni0)
    5. 分配 IP 地址
    6. 设置路由
    7. 设置 iptables 规则
       ↓
  Pod 启动

主流 CNI 插件:
  - Flannel (简单, Overlay)
  - Calico (BGP / VXLAN, 功能丰富)
  - Cilium (eBPF, 高性能)
  - Weave Net
  - Cilium
  - Multus (多网卡)
```

## 五、主流 CNI 插件详解

### 5.1 Flannel

#### 5.1.1 Flannel 架构

```text
Flannel 架构:

  Host A (10.0.0.10)                Host B (10.0.0.20)
  ┌──────────────────┐               ┌──────────────────┐
  │  kubelet           │               │  kubelet           │
  │  ┌──────────────┐  │               │  ┌──────────────┐  │
  │  │ flanneld      │  │   VXLAN/UDP  │  │ flanneld      │  │
  │  │ 分配 IP:      │  │   隧道       │  │ 分配 IP:      │  │
  │  │ 10.244.0.x    │◄────────────────►│ 10.244.1.x   │  │
  │  └──────────────┘  │               │  └──────────────┘  │
  │         │          │               │         │          │
  │  ┌──────▼─────┐    │               │  ┌──────▼─────┐    │
  │  │ cbr0       │    │               │  │ cbr0       │    │
  │  │ Pod A      │    │               │  │ Pod B      │    │
  │  │ 10.244.0.5 │    │               │  │ 10.244.1.8 │    │
  │  └────────────┘    │               │  └────────────┘    │
  └──────────────────┘               └──────────────────┘
                          ▲
                          │
                etcd (存储子网分配信息)

Flannel 后端:
  - vxlan: VXLAN 封装, 默认推荐
  - host-gw: 主机路由, 性能最好但需要 L3
  - udp: UDP 封装, 兼容性最好
```

#### 5.1.2 VXLAN 数据流

```text
Pod A (10.244.0.5) → Pod B (10.244.1.8) 数据流:

原始包:
  ┌──────────────────────────────────┐
  │ IP: 10.244.0.5 → 10.244.1.8        │
  │ TCP: 80                           │
  └──────────────────────────────────┘

Host A 封装 (VXLAN):
  ┌──────────────────────────────────────┐
  │ 外层 IP: 10.0.0.10 → 10.0.0.20        │
  │ 外层 UDP: 4789 (VXLAN)               │
  │ VXLAN Header: VNI 1                 │
  │ ┌────────────────────────────────┐  │
  │ │ 内层 IP: 10.244.0.5 → 10.244.1.8  │  │
  │ │ TCP: 80                          │  │
  │ └────────────────────────────────┘  │
  └──────────────────────────────────────┘

Host B 解封装:
  - 接收 UDP 4789 包
  - 提取 VXLAN 内层包
  - 根据 VNI + 内层 MAC 转发到 cbr0
  - 送达 Pod B
```

### 5.2 Calico

#### 5.2.1 Calico BGP 模式

```text
Calico BGP 模式 (推荐, 性能最优):

  Host A (10.0.0.10)                Host B (10.0.0.20)
  ┌──────────────────┐               ┌──────────────────┐
  │  Bird (BGP)        │   BGP Peer   │  Bird (BGP)        │
  │  192.168.1.10     │◄─────────────►│ 192.168.1.20      │
  │  └────────┬──────┘               │  └────────┬──────┘  │
  │           │                       │           │         │
  │  宣告路由:                        │  宣告路由:        │
  │  10.244.0.0/24 via 10.0.0.10    │  10.244.1.0/24     │
  │           │                       │           │         │
  │  ┌────────▼──────┐               │  ┌────────▼──────┐  │
  │  │ cbr0 桥       │               │  │ cbr0 桥       │  │
  │  │ Pod A        │               │  │ Pod B        │  │
  │  │ 10.244.0.5   │               │  │ 10.244.1.8   │  │
  │  └──────────────┘               │  └──────────────┘  │
  └──────────────────┘               └──────────────────┘

原理:
  - Calico 用 BGP 协议通告 Pod CIDR
  - Host A 知道: 10.244.0.0/24 通过 10.0.0.10 到达
  - Host B 知道: 10.244.1.0/24 通过 10.0.0.20 到达
  - 无需隧道, 直接路由

优点:
  - 性能最佳 (无封装)
  - 支持 NetworkPolicy
  - 支持 BGP 与现有网络集成
```

#### 5.2.2 Calico VXLAN 模式

```text
当 BGP 不可用时 (如云环境), 使用 VXLAN:

  Host A                                 Host B
  ┌──────────────────────┐               ┌──────────────────────┐
  │  calico-node           │               │  calico-node           │
  │  VTEP (10.0.0.10)     │    VXLAN      │  VTEP (10.0.0.20)     │
  │  └────────┬───────────┘   Tunnel     │  └────────┬───────────┘
  │           │               Port 4789     │           │            │
  │  ┌────────▼─────────┐                │  ┌────────▼─────────┐   │
  │  │ Pod A            │◄───────────────►│  │ Pod B            │   │
  │  │ 10.244.0.5       │                │  │ 10.244.1.8       │   │
  │  └──────────────────┘                │  └──────────────────┘   │
  └──────────────────────┘               └──────────────────────┘

VXLAN 模式适用场景:
  - 云环境 (无法配置 BGP)
  - 多网卡服务器
  - 网络分段环境
```

#### 5.2.3 Calico IPIP 模式

```text
Calico IPIP (IP-in-IP) 模式:

  Host A (10.0.0.10)                  Host B (10.0.0.20)
  ┌──────────────────┐                ┌──────────────────┐
  │ IPIP Tunnel       │                │ IPIP Tunnel       │
  │  tunl0            │                │  tunl0            │
  │  └────────┬───────┘                │  └────────┬───────┘
  │           │                         │           │         │
  │  ┌────────▼──────┐                │  ┌────────▼──────┐  │
  │  │ Pod A        │◄───────────────►│  │ Pod B        │  │
  │  │ 10.244.0.5   │ IPIP 封装       │  │ 10.244.1.8   │  │
  │  └──────────────┘                │  └──────────────┘  │
  └──────────────────┘                └──────────────────┘

IPIP 模式:
  - 原始 IP 包再封装一层 IP
  - 不需要 BGP
  - 比 VXLAN 性能稍好
  - 不支持 NetworkPolicy 高级特性
```

#### 5.2.4 Calico Felix 组件

```text
Felix (Calico Agent) 在每个节点运行:

  ┌────────────────────────────────┐
  │  calico/node                     │
  │  ┌────────────────────────┐   │
  │  │ Felix                   │   │
  │  │ - 配置路由表            │   │
  │  │ - 配置 iptables         │   │
  │  │ - 实施 NetworkPolicy   │   │
  │  │ - 报告状态             │   │
  │  └────────────────────────┘   │
  │  ┌────────────────────────┐   │
  │  │ Bird (BGP 客户端)       │   │
  │  └────────────────────────┘   │
  │  ┌────────────────────────┐   │
  │  │ confd                   │   │
  │  │ (配置同步)             │   │
  │  └────────────────────────┘   │
  └────────────────────────────────┘

Felix 主要工作:
  - 监听 etcd 中 Pod IP 变化
  - 写入 Linux 路由表
  - 配置 iptables 规则
  - 实施 NetworkPolicy (K8s 入口规则)
```

### 5.3 Cilium (eBPF)

#### 5.3.1 Cilium 架构

```text
Cilium 使用 eBPF 内核技术, 无需 iptables / Netfilter:

  Host A                                 Host B
  ┌────────────────────────┐            ┌────────────────────────┐
  │  cilium-agent           │            │  cilium-agent           │
  │  ┌──────────────────┐  │            │  ┌──────────────────┐  │
  │  │  eBPF Programs   │  │            │  │  eBPF Programs   │  │
  │  │  (内核态)        │  │            │  │  (内核态)        │  │
  │  └────────┬─────────┘  │            │  └────────┬─────────┘  │
  │           │             │            │           │             │
  │  ┌────────▼─────────┐  │  VXLAN /   │  ┌────────▼─────────┐  │
  │  │ cilium_netns     │  │  Geneve    │  │ cilium_netns     │  │
  │  │ Pod A            │◄────────────►│  │ Pod B            │  │
  │  │ 10.244.0.5       │  │            │  │ 10.244.1.8       │  │
  │  └──────────────────┘  │            │  └──────────────────┘  │
  └────────────────────────┘            └────────────────────────┘

eBPF 优势:
  - 在内核态处理网络, 无需切换到用户态
  - 无需 iptables 规则, 性能极佳
  - 支持高级 NetworkPolicy (L7)
  - 可观测性强 (Hubble)
```

#### 5.3.2 eBPF 网络路径

```text
Cilium eBPF 数据包路径 (内核态):

  Pod A 发送包
       ↓
  Pod A veth (cilium_host@host)
       ↓
  eBPF 程序处理 (bpf_redirect)
       ↓
  ┌─────────────────────────────────────┐
  │  if dest IP 是同节点 Pod:           │
  │    → 直接转发到目标 Pod veth        │
  │  if dest IP 是其他节点 Pod:        │
  │    → 封装到 cilium_vxlan           │
  │    → 通过 eth0 发送到目标节点       │
  │  if dest IP 是 Service IP:          │
  │    → 负载均衡到后端 Pod            │
  └─────────────────────────────────────┘

完全在内核态处理, 无用户态参与!
```

#### 5.3.3 Hubble 可观测性

```text
Hubble 是 Cilium 的可观测性组件:

  ┌────────────────────────────────────┐
  │  Hubble Relay (聚合)               │
  │  ┌──────────────────────────┐     │
  │  │  Hubble UI (可视化)        │     │
  │  │  http://hubble.example.com│     │
  │  └──────────────────────────┘     │
  └────────────────────────────────────┘
          ↑
  Hubble Agent (每个节点)
  ┌────────────────────────────────────┐
  │  /var/run/cilium/hubble/sock.sock │
  │  → eBPF events                      │
  │  → L3/L4/L7 流量                     │
  │  → Network Policy 决策              │
  └────────────────────────────────────┘

Hubble 能力:
  - 服务依赖图 (自动发现)
  - 流量可视化 (实时)
  - DNS 查询监控
  - Network Policy 调试
```

## 六、Kube-Proxy 三种模式对比

### 6.1 Kube-Proxy 作用

```text
Kube-Proxy 的核心职责:
  - 监听 Service 和 Endpoints 变化
  - 配置 iptables/IPVS/eBPF 规则
  - 实现 Service ClusterIP 的负载均衡
  - 实现流量转发

Service 访问 Pod 的请求流:
  客户端 → Service ClusterIP (10.96.x.x) → Kube-Proxy 规则 → 后端 Pod
```

### 6.2 iptables 模式 (默认)

```text
iptables 模式工作原理:

  客户端 192.168.1.100
       │
       ↓
  Service ClusterIP 10.96.10.50:80
       │
       ↓
  iptables PREROUTING (DNAT)
       │
       ↓ 选择一个后端 Pod
       ↓
  Pod A 10.244.0.5:8080 (概率 33%)
       或
  Pod B 10.244.1.8:8080 (概率 33%)
       或
  Pod C 10.244.2.3:8080 (概率 33%)
       │
       ↓
  iptables POSTROUTING (MASQUERADE)
       │
       ↓ 返回

iptables 规则示例:
  -A KUBE-SERVICES -d 10.96.10.50/32 -p tcp --dport 80 \
     -j KUBE-SVC-XYZ
  -A KUBE-SVC-XYZ -m statistic --mode random \
     --prob 0.333 -j KUBE-SEP-POD1
  -A KUBE-SVC-XYZ -m statistic --mode random \
     --prob 0.500 -j KUBE-SEP-POD2
  -A KUBE-SVC-XYZ -j KUBE-SEP-POD3

特点:
  - 默认模式
  - 简单稳定
  - 大集群时规则数多 (数千条)
  - 性能线性下降
```

### 6.3 IPVS 模式

```text
IPVS 模式:

  客户端 192.168.1.100
       │
       ↓
  Service ClusterIP 10.96.10.50:80
       │
       ↓
  IPVS 虚拟服务器 (10.96.10.50:80)
       │
       ↓ 选择后端
  ┌────────────────────────────────┐
  │ IPVS 调度算法:                    │
  │  - rr (轮询, 默认)               │
  │  - lc (最少连接)                  │
  │  - dh (目标哈希)                  │
  │  - sh (源哈希)                    │
  │  - sed (最短期望延迟)             │
  │  - nq (永不排队)                  │
  └────────────────────────────────┘
       │
       ↓
  Pod A 10.244.0.5:8080

配置:
  --kube-proxy-mode=ipvs

特点:
  - 哈希表查找 O(1)
  - 支持多种调度算法
  - 大集群性能更好
  - 需要 IPVS 内核模块
```

### 6.4 eBPF / nftables 模式 (K8s 1.29+)

```text
nftables 模式 (K8s 1.29+):

  客户端 192.168.1.100
       │
       ↓
  Service ClusterIP 10.96.10.50:80
       │
       ↓
  nftables 规则集
       │
       ↓ 性能更好, IPv6 优化
  Pod A 10.244.0.5:8080

特点:
  - Linux 5.x 内核优化
  - 比 iptables 性能好
  - 比 eBPF 简单
```

### 6.5 Kube-Proxy 模式对比

| 维度 | iptables | IPVS | nftables |
|------|----------|------|----------|
| **查找复杂度** | O(n) | O(1) | O(log n) |
| **大集群性能** | 差 (规则多) | 好 | 好 |
| **调度算法** | 仅 random | 多种 | 仅 random |
| **IPv6 支持** | 一般 | 好 | 优秀 |
| **成熟度** | 高 | 高 | 新 (1.29+) |
| **推荐** | 小集群 | 大集群 | 新版本 |

## 七、Service 跨节点访问全流程

### 7.1 完整流程图

```text
场景: Pod A 在 Host-1 调用 Service "web" (ClusterIP 10.96.10.50)
      后端有 Pod-1 (Host-1) 和 Pod-2 (Host-2)

  ┌──────────────────────────────────────────────────────────────────┐
  │                                                                  │
  │  Pod A (10.244.0.5)              Service ClusterIP: 10.96.10.50  │
  │  ┌──────────────────┐           ┌──────────────────┐            │
  │  │  App code        │           │  iptables 规则   │            │
  │  │  curl http://web │──────────►│  KUBE-SERVICES   │            │
  │  └──────────────────┘           └────────┬─────────┘            │
  │                                          │                       │
  │                                  PREROUTING DNAT                 │
  │                                          │                       │
  └──────────────────────────────────────────┼───────────────────────┘
                                             │
                                             ↓
                              选一个后端 Pod (iptables random / IPVS 算法)
                                             │
                          ┌──────────────────┴──────────────────┐
                          │                                     │
                          ↓                                     ↓
              ┌──────────────────────┐        ┌──────────────────────┐
              │  Pod-1 (10.244.0.10)    │        │  Pod-2 (10.244.1.15)    │
              │  Host-1                │        │  Host-2                │
              └──────────────────────┘        └──────────────────────┘
```

### 7.2 数据包详细流转

```text
以 Pod A 调用 Service "web" 为例 (iptables 模式):

步骤 1: DNS 解析
  Pod A 内:
    /etc/resolv.conf: nameserver 10.96.0.10 (CoreDNS)
    nslookup web.default.svc.cluster.local
    → 返回 10.96.10.50 (Service ClusterIP)

步骤 2: 发出请求
  curl http://web:80/
  实际访问 10.96.10.50:80

步骤 3: Kube-Proxy 规则 (每个节点都有)
  iptables -t nat -A PREROUTING ...
  # ClusterIP 不是本机 IP,需要 DNAT
  
  iptables -A KUBE-SERVICES -d 10.96.10.50/32 -p tcp --dport 80 \
    -j KUBE-SVC-XXX
  
  iptables -A KUBE-SVC-XXX -m statistic --mode random \
    --prob 0.500 -j KUBE-SEP-POD-1
  iptables -A KUBE-SVC-XXX -m statistic --mode random \
    --prob 1.000 -j KUBE-SEP-POD-2
  
  # 选择一个 Pod (随机), DNAT 到 Pod IP:80

步骤 4: 如果选 Pod-2 (跨节点)
  Pod A (10.244.0.5) → Host-1 网桥 (cbr0) → eth0 → 物理网络
  → Host-2 eth0 → cbr0 → Pod-2 (10.244.1.15)

  沿途路由:
    Pod-2 10.244.1.15 via 10.0.0.20 (Host-2)
    Host-1 路由表知道 10.244.1.0/24 怎么走
    (由 Flannel/Calico/Cilium 设置)

步骤 5: 返回路径
  Pod-2 → cbr0 → eth0 → 物理网络 → Host-1 eth0 → cbr0 → Pod A
```

### 7.3 同节点 vs 跨节点访问对比

```text
同节点访问 (Pod A → Pod-1, 都在 Host-1):

  Pod A (10.244.0.5)  →  cbr0 桥  →  Pod-1 (10.244.0.10)
       │
       └─── 桥接转发, 无 NAT
       └─── 延迟: < 1ms
       └─── 性能损耗: 极小

跨节点访问 (Pod A → Pod-2):

  Pod A (10.244.0.5)  →  cbr0  →  eth0  →  物理网络  →  eth0  →  cbr0  →  Pod-2
       │                                              │
       └────────── 经过物理交换机 ─────────────────┘
       └─── 延迟: 1-10ms (取决于网络)
       └─── VXLAN 模式: 再增加 ~10us 封装开销
```

### 7.4 Headless Service (无 ClusterIP)

```text
Headless Service: ClusterIP = None, 直接返回 Pod IP

  Service "web-headless"
  spec:
    clusterIP: None
    selector:
      app: web

  DNS 查询 web-headless.default.svc.cluster.local
  → 返回所有 Pod IP (轮询):
      Pod-1.default.svc.cluster.local
      Pod-2.default.svc.cluster.local
      Pod-3.default.svc.cluster.local

用途:
  - StatefulSet (稳定网络标识)
  - 自定义负载均衡
  - 直连 Pod 场景
```

### 9.3 资源消耗对比

```text
CNI 资源占用 (单节点):

CNI            CPU       内存      备注
──────────────────────────────────────────
Flannel        极低       20MB      最轻量
Calico         低        50-100MB   含 BGP 客户端
Cilium         中        200MB+    含 eBPF 运行时
Weave Net      中        100MB     
Docker Swarm   中        200MB+    自带 ingress
```

### 9.4 生产选型最佳实践

```text
推荐方案 (按场景):

1. 中小企业 (< 100 节点)
   → Calico + iptables
   → 文档丰富, 稳定可靠
   → 支持 NetworkPolicy

2. 大型企业 (> 100 节点)
   → Cilium + eBPF
   → 性能最佳
   → Hubble 可观测性
   → L7 NetworkPolicy

3. 简单场景
   → Flannel + host-gw
   → 配置最简单
   → 性能足够

4. 传统企业 (已有 BGP)
   → Calico + BGP
   → 与现有网络集成
   → 性能最好

5. K8s 新版本 (1.29+)
   → Cilium 或 nftables kube-proxy
   → 现代化方案
```

## 十、核心要点速记

### 三大跨主机方案对比

```text
1. Docker Overlay (Swarm)
   - VXLAN 隧道
   - 简单易用
   - 适合 Swarm 集群

2. K8s + Flannel
   - VXLAN / host-gw
   - 配置简单
   - 适合 K8s 入门

3. K8s + Calico
   - BGP / VXLAN / IPIP
   - NetworkPolicy
   - 企业级首选

4. K8s + Cilium
   - eBPF 技术
   - 性能最佳
   - 现代化推荐
```

### Kube-Proxy 三种模式

```text
iptables  - 默认, 简单, 小集群
IPVS      - 大集群, 性能好, 推荐
nftables  - K8s 1.29+, 现代化
```

### CNI 选型速记

```text
Flannel  - 简单场景, 入门
Calico   - 企业级, 功能丰富
Cilium   - 高性能, 现代化, eBPF
```

### K8s 网络三原则

```text
1. 每个 Pod 一个 IP
2. Pod 之间无 NAT 互通
3. Agent 与 Pod 可通信
```

### 关键概念速记

```text
namespace  - 网络隔离
veth pair  - 跨 netns 的网线
bridge     - L2 交换机 (cbr0, docker0)
overlay    - 跨主机隧道 (VXLAN)
BGP        - 路由协议 (Calico)
eBPF       - 内核态网络 (Cilium)
CNI        - K8s 网络接口标准
Service    - K8s 服务抽象 + ClusterIP
iptables   - 规则转发 (Kube-Proxy 默认)
IPVS       - 哈希表转发 (K8s 大集群)
```

### 排查思路

```text
1. Pod 无法访问 Service?
   → 检查 Kube-Proxy 规则 (iptables-save / ipvsadm)
   → 检查 Service Endpoints (kubectl get endpoints)
   → 检查 Pod label 与 Service selector 匹配

2. Pod 无法跨节点通信?
   → 检查 CNI 状态 (calicoctl, cilium status)
   → 检查路由表 (ip route)
   → 检查网桥 (brctl show)
   → 检查防火墙 (iptables, nft)

3. 跨主机网络性能差?
   → 确认 CNI 后端 (host-gw 性能最好)
   → 检查 MTU 是否一致
   → 检查物理网络
   → 监控 CNI 资源使用
```
